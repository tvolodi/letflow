VERDICT: CONFIRMED DIVERGENCE. autofix_file/1's decode-based decision acts
on the FIRST occurrence ("DONE" -> target "COMPLETED"), but
splice_top_level_status/2 edits the LAST occurrence ("COMPLETE" ->
"COMPLETED") instead. The FIRST occurrence -- the one the tool's own
decision logic actually reasoned about -- is left as "DONE" in the output
file: an illegal, non-@legal_statuses value, silently left in place, while
the tool reports {:fixed, "DONE", "COMPLETED"} to its caller and stdout.
The very next lint_handoffs run then reports a fresh H1 violation on that
same (unedited) first occurrence. No crash, no raise -- this is silent
mis-repair, not the documented "internal invariant violation" raise path
(that raise only fires when the scanner finds NO depth-1 status key at
all, which is not this case).
