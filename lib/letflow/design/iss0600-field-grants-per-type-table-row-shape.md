# Design: ISS-0600 — `FieldGrants.redact_page/2` crashes on promoted per-type-table rows

**Run:** fix/ISS-0600-20260911 (GH#1245, queue task 600) · **Author:** CODE-DESIGNER ·
**Status:** proposed — awaiting CODE-DESIGN-VALIDATOR.

**Scope: one production file, `lib/letflow/entities/query/field_grants.ex` (one new
private-function clause + one `@spec` correction — no behavior change to any existing
clause), plus one test file,
`test/letflow/entities/query_cursor_field_grants_test.exs` (new test cases only). No
migration. `lib/letflow/routers/entities.ex` is explicitly OUT of scope — see §6.**

## 1. Problem restatement (verified directly, not paraphrased from the issue text)

Confirmed against current `main` (this branch's own merge-base):

- `lib/letflow/entities/query/field_grants.ex:136` — `redact_item/2` has exactly one
  clause: `defp redact_item(%Latest{field_values: field_values} = item, restriction_set)`.
  It is a **thin wrapper**: its entire body is
  `%{item | field_values: redact_field_values(field_values, restriction_set)}` — i.e. it
  delegates the actual redaction work to the already-public, already-pure
  `redact_field_values/2` (line 112-121) and only handles the "which struct/map field
  holds `field_values`, and how do I write it back" concern itself. This matters directly
  for §4 below: the fix is a one-line-bodied sibling clause, not new redaction logic.
- `redact_page/2` (line 130-134)'s `@spec` reads
  `Pagination.Page.t(Latest.t()) -> Pagination.Page.t(Latest.t())` — this is the line the
  issue names as now-false.
- `lib/letflow/entities/query/compiler.ex:120-128` defines `entity_row()` as a **plain
  map** (no struct, no `Ecto.Schema`):
  `%{record_id: String.t(), field_values: map(), deleted: boolean(), entity_def_version:
  binary() | nil, last_event_global_seq: integer(), inserted_at: NaiveDateTime.t(),
  updated_at: NaiveDateTime.t()}`. It is a **public** `@type` (no `@typep`), already
  referenced fully-qualified (`Letflow.Entities.Query.Compiler.joined_row()`) from inside
  `field_grants.ex` itself at line 187/189 for `redact_joined_page/2`'s own `@spec` — so
  there is precedent in this exact file for citing `Compiler`'s types by full qualification
  without adding an `alias`.
- `compiler.ex:657-694` — `compile_plain/5`'s `{:per_type_table, table_name}` branch pipes
  through `select_entity_row/1` (line 684-694), whose `select` maps exactly those seven
  keys off the per-type table's columns — this is where the plain map shape is actually
  produced for a non-join query, confirmed structurally (not just by the `@type`
  declaration).
- `lib/letflow/entities/record/latest.ex:19-36` — `Latest` is an `Ecto.Schema` struct with
  fields `entity_type`, `record_id`, `field_values`, `deleted`, `entity_def_version`,
  `last_event_global_seq`, plus `timestamps()` (`inserted_at`/`updated_at`), plus its
  autogenerated `id`/`__meta__`. **`field_values` is genuinely the only field
  `redact_item/2`'s existing clause reads or writes** — every other field passes through
  the struct-update syntax untouched. No other field of either shape needs
  shape-specific handling; `field_values` is the sole point of contact for redaction in
  both row shapes.
- Live confirmation of the crash's real-world shape, from
  `test/letflow/entities/query_joins_test.exs`'s existing AC8 test (line 502-526): a
  `compile/2` call with **no `join` key** against a promoted entity type (`"widget"`),
  executed via plain `Repo.all(query, prefix: schema)`, returns
  `[%{field_values: %{"sku" => "ABC-1"}}]` — a bare map, not a `%Latest{}` struct. This is
  the exact non-`%Latest{}` value `redact_item/2` must also accept; §5 below reuses this
  file's own `promote_and_create_table!/5` helper (line 112-135) to build the equivalent
  fixture inside the FieldGrants test file.
- `test/letflow/entities/query_cursor_field_grants_test.exs` — confirmed the file's actual
  path (matches the issue's naming). Its `AC2` describe block (line 421-496) is the one
  `redact_page/2` test today, and it only ever constructs `%Latest{}` rows (via
  `create_record!/2`, which calls `Records.create_record/2` — never a promoted per-type
  table).

**Confirmed per the task brief's own instruction:** `lib/letflow/routers/entities.ex`
exists on `main` (from REQ-310, already merged) but contains **zero** references to
`redact`, `FieldGrants`, or `Query.Cursor` anywhere in the file (checked directly). The

## 2. Root cause (one sentence)

`redact_item/2` was written (REQ-231) before per-type tables existed (REQ-296/297/298
landed later); nothing after that later work extended it to the second row shape
`Compiler.compile_plain/5` had, by then, started producing for the identical
non-join/`redact_page/2` call path — the two features were never made to agree on the one
function that sits between them.

## 3. Fix — add one sibling clause, correct one `@spec`, nothing else

### 3.1 `redact_item/2` — new second clause

Add a new `defp redact_item/2` clause **immediately after** the existing
`%Latest{field_values: field_values} = item` clause (line 136-138), not before it — clause
order matters here: Elixir tries clauses top-to-bottom, and a `%Latest{}` struct also
structurally matches a bare `%{field_values: ...}` pattern, so the existing `%Latest{}`
clause must keep priority so a `%Latest{}` value continues to hit it first, unchanged. The
new clause:

- **Pattern:** `%{field_values: field_values} = item`, guarded `when is_map(item)` (the
  guard is redundant given the pattern already implies a map, but stated explicitly for
  the same self-documenting-guard convention this codebase already uses elsewhere in this
  module, e.g. `load_restrictions/3`'s `when is_binary(user_id) and is_binary(entity_type)
  and is_binary(prefix)`).
- **Body:** identical in shape to the existing clause's body —
  `%{item | field_values: redact_field_values(field_values, restriction_set)}`. This is
  the "ideally sharing the core redaction call rather than duplicating it" outcome named
  in the task brief: both clauses already share the real redaction logic, because both
  only ever call the existing public `redact_field_values/2`; no new private helper is
  introduced, since introducing one to wrap a call that's already a single expression
  would add indirection without removing duplication (the two clause *bodies* are
  identical text, but that text is only one line — a shared helper would just rename the
  duplication, not remove it. Flagged as a deliberate no-op decision, not an oversight).
- No new module attribute, no new public function. `redacted_sentinel/0`,
  `load_restrictions/3`, `redact_field_values/2`, `redact_joined_page/2`, and
  `redact_joined_item/2` are all untouched — same signatures, same bodies, same tests
  green, mirroring this file's own REQ-300 comment convention (line 140-146) of stating
  exactly what is *not* touched by a change.

Because `%{item | field_values: ...}` (map-update syntax) works identically whether `item`
is a plain map or a struct, both clause bodies really are the same expression — the only
reason two clauses exist at all is that the *pattern* differs (`%Latest{...}` vs. a bare
`%{...}`), not the body.

### 3.2 `redact_page/2` — `@spec` correction

Current (line 130-131):

```
@spec redact_page(Pagination.Page.t(Latest.t()), restriction_set()) ::
        Pagination.Page.t(Latest.t())
```

New:

```
@spec redact_page(
        Pagination.Page.t(Latest.t() | Letflow.Entities.Query.Compiler.entity_row()),
        restriction_set()
      ) :: Pagination.Page.t(Latest.t() | Letflow.Entities.Query.Compiler.entity_row())
```

`Compiler.entity_row()` is referenced fully-qualified, matching this file's own existing
convention for `Compiler.joined_row()` a few lines below (line 187, 189) — no new `alias`
is introduced (the file currently has no `alias Letflow.Entities.Query.Compiler`, and
adding one just for this one `@spec` would be inconsistent with how the file already cites
`joined_row()`). `Compiler.entity_row()` is already a public `@type` (confirmed: no
`@typep`), so it is legally referenceable from another module with no export change
needed on `compiler.ex`'s side.

`redact_page/2`'s **function head and body are unchanged** — `%Pagination.Page{items:
items} = page` already accepts a page holding either row shape; only the type declaration
was wrong, and only the type declaration changes.

### 3.3 Not touched, and why

- `redact_joined_page/2`/`redact_joined_item/2` (REQ-300, line 180-202): these operate on
  `Compiler.joined_row()` — a map keyed by `:primary`/entity-type-string, each value
  itself an `entity_row()` — and already call `entity_row.field_values` directly (line
  200) with no struct-vs-map branching at all, because a joined result is **always** the
  plain-map shape (`compile_joined/6` always uses `apply_joined_select/2`, never
  `Latest`-struct selection — confirmed at `compiler.ex:716-724`). This code path was
  never broken and needs no change.
- `Cursor.paginate/5`'s own `@spec` (`cursor.ex:110-124`) also still literally reads
  `{:ok, Pagination.Page.t(Latest.t())}` and is equally stale for the exact same reason
  (it, too, predates per-type tables) — but the issue's fix direction (①-③, listed in the
  task brief) names only `field_grants.ex`'s two spots. Fixing `Cursor.paginate/5`'s
  `@spec` is a legitimate, closely-related latent inaccuracy but is **not part of this
  fix's scope** — flagged here as an open question (§7), not silently folded in, so
  ELIXIR-DEV doesn't second-guess whether it was supposed to be included.

## 4. Test design — extend `query_cursor_field_grants_test.exs`, mirror the existing AC2
shape, reuse `query_joins_test.exs`'s promotion helper

### 4.1 New fixture: bring in the per-type-table promotion helper

Add a private helper to `query_cursor_field_grants_test.exs`, copied (not imported —
matches this codebase's established "duplicate small test helpers across files rather than
reach into another test module's private functions" convention, e.g. the ISS-0583 design's
§5.2 reasoning) from `test/letflow/entities/query_joins_test.exs:112-135`:

- `promote_and_create_table!(schema, tenant_id, entity_type, attribute, pg_type, opts \\
  [])` — verbatim copy of that function. Needs its own `alias
  Letflow.TenantProvisioning.ColumnPromotion` added to this test file's alias list (not
  currently present) and `tenant_id` threaded through `provisioned_tenant/0`'s existing
  return map (`%{tenant_id: tenant_id, schema_name: schema}` — `provisioned_tenant/0`
  already returns `tenant_id` per its current body at line 56-78, just not currently
  destructured by any existing test in this file — no change needed to
  `provisioned_tenant/0` itself, only to the new test's own destructuring pattern).

### 4.2 New `describe` block — "promoted per-type-table row shape (ISS-0600)"

Placed immediately after the existing `"AC2 -- per-field, per-user redaction
(FieldGrants)"` block (after line 496), structured as a direct parallel to that block's own
third test (`"redact_page/2 redacts every item's field_values while preserving
next_cursor/count"`, line 471-485) so the two are easy to compare side by side:

- **Setup:** `provisioned_tenant()` → `%{tenant_id:, schema_name:}`; create an active
  definition for a fresh entity type (e.g. `"promoted_customer"`, to avoid any fixture
  collision with the existing `"customer"` entity type used elsewhere in this file) with
  fields `"customer_name"` (string, queried), `"age"` (integer, queried), `"ssn"` (string,
  queried) — same field set as the existing `valid_definition/1` fixture, for direct
  comparability; call `promote_and_create_table!(schema, tenant_id, "promoted_customer",
  "customer_name", "text")` to give it a real per-type table (any promoted column is
  sufficient to make `resolve_binding_source/2` return `{:per_type_table, _}` — matching
  `query_joins_test.exs`'s own AC8 pattern of promoting just one column to trigger the
  branch). Create one record via `create_record!/2` with
  `%{"customer_name" => "Alice", "age" => 30, "ssn" => "123-45-6789"}`. Insert an
  `entity_field_restrictions` row for `("promoted_customer", "ssn")`, mirroring the
  existing AC2 setup exactly.

- **Test 1 — "redact_page/2 accepts a promoted per-type-table row (`entity_row()` map
  shape) and redacts it identically to the `%Latest{}` path" (regression test for the
  reported crash):**
  1. `Compiler.compile(%{entity_type: "promoted_customer"}, schema)` → `{:ok, query}` —
     **no `join` key**, so this compiles through `compile_plain/5`'s
     `{:per_type_table, _}` branch, i.e. the exact path named in the issue.
  2. `Repo.all(query, prefix: schema)` → assert the raw result is `[%{field_values: %{...
     }} = row]` and explicitly `refute match?(%Letflow.Entities.Record.Latest{}, row)` —
     this assertion is the direct proof the fixture reproduces the reported row shape, not
     an assumption.
  3. Build a page: `Letflow.Api.Pagination.page_response([row], "some-next-cursor")`.
  4. `FieldGrants.load_restrictions(user_without_grant.id, "promoted_customer", schema)` →
     `{:ok, restriction_set}` (new user via the existing `create_user!/2` helper).
  5. **The crash-reproducing call:** `FieldGrants.redact_page(page, restriction_set)` —
     before the fix, this raises `FunctionClauseError` inside `redact_item/2`; after the
     fix, it must return successfully.
  6. Assert on the result exactly as the existing AC2 `redact_page/2` test does:
     `redacted_page.next_cursor == "some-next-cursor"`, `redacted_page.count == 1`, and
     the single item's `field_values["ssn"] == FieldGrants.redacted_sentinel()` while
     `field_values["customer_name"] == "Alice"` and `field_values["age"] == 30` pass
     through unredacted — proving the promoted-table path redacts the *same* fields the
     `%Latest{}` path does, under the *same* restriction set, with no divergence.

- **Test 2 — "a user holding an explicit grant sees the field populated, promoted-table
  shape" (direct parallel of the existing AC2 grant test, line 456-469):** same setup,
  `insert_user_grant!(schema, grant_user.id, "promoted_customer", "ssn")`, assert
  `redact_page/2`'s output has `field_values["ssn"] == "123-45-6789"` (unredacted) — proves
  the grant-override behavior is identical across both row shapes, not just the
  default-deny direction.

These two tests are the "extend `query_cursor_field_grants_test.exs` to cover the promoted
shape" item (③) from the issue's fix direction, satisfied by direct parallel structure to
the file's own existing `%Latest{}` coverage rather than a divergent new test shape.

### 4.3 No change to any existing test

Every existing test in `query_cursor_field_grants_test.exs` (AC1, ISS-0522 site 2, the
existing AC2 block, AC4) continues to exercise the unchanged `%Latest{}` clause and passes
unmodified — this fix adds a clause, it does not alter one.

## 6. SECURITY-REVIEWER call — YES, route this through SECURITY-REVIEWER

This is field-redaction code enforcing INV-2-shaped tenant-data-shaping (which fields a
given user may see for a given entity type) — exactly the class of change
`security-invariants.md` names as always in scope, and this module's own moduledoc (line
1-50) is explicit that it is the sole mechanism implementing that guarantee for query
reads. Concretely, SECURITY-REVIEWER should confirm:

- The new `redact_item/2` clause redacts via the exact same `redact_field_values/2` call
  as the existing clause — no parallel/divergent redaction logic was introduced that could
  drift out of sync with the `%Latest{}` path over time (§3.1 argues this structurally,
  SECURITY-REVIEWER should independently confirm it holds after implementation).
  SECURITY-REVIEWER already reached the equivalent conclusion for REQ-311's own
  router-side `redact_plain_page/2` workaround (both shapes ultimately call the same
  public `redact_field_values/2` — noted as already confirmed security-equivalent in the
  task brief) — this fix is the same equivalence claim, one layer lower in the same
  module, and should get its own explicit sign-off rather than inheriting the prior one by
  assumption.
- No new field of either row shape (`entity_def_version`, `last_event_global_seq`,
  `deleted`, `record_id`, timestamps) is exposed by the new clause beyond what the
  existing `%Latest{}` clause already exposes — both clauses only ever touch
  `field_values`, confirmed structurally in §1/§3.1.
- The `@spec` correction is documentation-only (no runtime behavior change) and does not
  itself need independent verification beyond confirming it matches the two shapes
  `redact_page/2` can now genuinely receive.

## 7. Open questions (none block ELIXIR-DEV — flagged for completeness)

- `Cursor.paginate/5`'s own `@spec` (`cursor.ex:110-124`) has the identical
  `Pagination.Page.t(Latest.t())`-only staleness, for the identical root cause. Not fixed
  here since the issue's fix direction scopes this fix to `field_grants.ex` only. Worth a
  follow-up issue/requirement so dialyzer's blind spot here is closed at its source, not
  just at `field_grants.ex`'s consuming end.
- Whether `redact_item/2`'s two clauses should eventually be collapsed into one (since
  `%{item | field_values: ...}` works identically for both a struct and a plain map, a
  single pattern `%{field_values: field_values} = item` would already match both shapes
  with no `%Latest{}`-specific clause at all). Deliberately **not** proposed as the fix
  here: the issue's authoritative fix direction (①) explicitly says "add a clause," and
  collapsing the existing clause changes more surface area (touches the `%Latest{}` path's
  own clause, currently untouched and covered by existing green tests) than this fix
  needs to. Noted as a possible future simplification, not adopted now.
