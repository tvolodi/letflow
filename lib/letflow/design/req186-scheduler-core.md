# REQ-186 — Timers schema and scheduler core (SCH-01/02/05/06)

Status: design artefact. Owner: CODE-DESIGNER, implementer: ELIXIR-DEV.
Implements the architecture `lib/letflow/design/req185-scheduler-firing-architecture.md`
(REQ-185) already decided — this document does not re-open any of REQ-185's
seven decisions (supervised `GenServer` ticker, no Oban, `FOR UPDATE SKIP
LOCKED` claim, no startup-sweep lock, per-tenant-schema iteration, per-timer
transaction isolation, exhausted timer → `dlq_entries` with `entry_type:
"timer"`). It resolves REQ-185's one open item left explicitly to this
requirement (§3's REVIEWER note): which isolation mechanism the fire loop
uses. **Decision, made here: transaction/rescue boundary only — no new
`Task.Supervisor`.** Each claimed timer fires inside its own
`Repo.transaction/1`; a raise inside that function is caught by an explicit
`try/rescue` before the transaction function returns, converting it to a
`{:error, _}` tuple so `Repo.transaction/1`'s own rollback-on-`{:error, _}`
contract applies — no process boundary is introduced, because REQ-185 §7
already establishes that per-timer transaction isolation alone is sufficient
("the unit of failure isolation is the single timer's own transaction"), and
this project's `Task.Supervisor`-per-concern idiom (five existing instances)
is reserved for calls that themselves block or can hang (external HTTP
calls, VM invocations) — a `Repo.transaction/1` around ordinary Ecto writes
has no such hang risk, so adding a sixth `Task.Supervisor` here would be
unneeded machinery, consistent with REQ-185's own dependency-adoption
discipline (§3 point 4).

Core only: no route, no controller, no `web/` change (matches the
core/route split REQ-176→178, REQ-181→182, REQ-183→184 already established).

## 1. Schema: `timers` (tenant-scoped, Decision 0003 Decision B)

Lives inside each tenant's own Postgres schema (via Ecto `:prefix`), **not**
the public/global schema — same tenant-scoping idiom as `dlq_entries`
(REQ-176) and `tasks`. `tenant_id` is retained as an intra-schema column
(Decision B's addendum: the Postgres schema is the isolation boundary, the
column is not) but is never caller-supplied — derived server-side from
`opts[:prefix]` via `Letflow.TenantProvisioning.tenant_id_for_schema_name/1`,
matching every REQ-072+ tenant-scoped write in this codebase (`Letflow.Dlq`'s
own moduledoc states the identical discipline).

Migration structure: the `if prefix() do ... end` guard (mandatory for every
tenant-scoped migration, per `20260818110003_create_tasks.exs`'s and
`20260829000001_create_dlq_entries.exs`'s own headers), registered in
`Letflow.TenantProvisioning.tenant_scoped_migrations/0` alongside `dlq_entries`
and `tasks`.

last-modified column nothing in the acceptance criteria requires.

### 1.2 Indexes

- **`idx_timers_pending_fire_at`** — partial index on `(fire_at)` **WHERE
  `status = 'pending'`** — the poller's one hot query (acceptance criterion
  1). This is the literal R-Co partial index, ported unmodified per REQ-186's
  own SCOPE text.
- No index on `tenant_id` alone (same rationale as `dlq_entries`: the
  Postgres schema, not this column, is the actual isolation boundary, and no
  query in this design filters by `tenant_id` in isolation).
- No index on `instance_id` — REQ-186's own scope has no query filtering
  timers by `instance_id` (REQ-187's cancellation wiring, a future
  requirement, may need one; not added speculatively here).

### 1.3 CHECK constraint 1 — `status` domain (acceptance criterion 2)

**`chk_timers_status`**: `status IN ('pending', 'fired', 'cancelled',
'failed')`. A raw SQL `execute/1` statement inside the migration's `if
prefix() do` block (Ecto's `create table` DSL has no native CHECK-constraint
builder; this codebase's existing precedent for a DB-level CHECK — verified
by grepping every migration under `priv/repo/migrations/` for
`ADD CONSTRAINT.*CHECK` — is a literal `execute("ALTER TABLE ... ADD
CONSTRAINT ... CHECK (...)", "ALTER TABLE ... DROP CONSTRAINT ...")`
two-argument form inside `change/0`, giving Ecto both the forward and the
`mix ecto.rollback` reverse statement without a separate `up/0`/`down/0`
split). The constraint is added on the fully-qualified, prefix-interpolated
table name (`"#{prefix()}"."timers"`), inside the same `if prefix() do`
guard as the rest of this migration.

An insert attempt with `status = 'expired'` (or any value outside the four)
is rejected by Postgres itself — a `Postgrex.Error` with `postgres.code:
:check_violation` — independent of whatever the Ecto changeset's own
`validate_inclusion/3` already catches at the application layer; the DB
constraint is the acceptance-criterion-mandated backstop, not a substitute
for the changeset check (both exist, changeset first for the ordinary
friendly-error path, DB CHECK second as the structural guarantee).

### 1.4 CHECK constraint 2 — recurrence all-or-nothing shape (acceptance criterion 3)

**`chk_timers_recurrence_shape`**, R-Co's own name, ported verbatim as a
second raw `execute/1` CHECK, same mechanism as §1.3:

```
(repeat_expression IS NULL AND repeat_interval_us IS NULL
   AND repeat_total IS NULL AND fired_count IS NULL)
OR
(repeat_expression IS NOT NULL AND repeat_interval_us IS NOT NULL
   AND fired_count IS NOT NULL AND fired_count >= 0
   AND (repeat_total IS NULL OR (repeat_total >= 1 AND fired_count <= repeat_total)))
```

Two admissible shapes only:

1. **All four NULL** — a non-recurring timer (the only shape REQ-186 itself
   ever writes; REQ-188 is the first requirement that writes the other
   shape).
2. **`repeat_expression`, `repeat_interval_us`, `fired_count` all non-null**,
   `fired_count >= 0`, and — only when `repeat_total` is also non-null —
   `repeat_total >= 1 AND fired_count <= repeat_total`. `repeat_total` alone
   may be `NULL` (an unbounded `"R/..."` series) while the other three are
   required together.

A row inserting `repeat_expression` without `repeat_interval_us` (any
column from the "non-null trio" present without the other two) falls into
neither admissible shape and is rejected by Postgres with `check_violation`
— acceptance criterion 3's negative case. A row inserting all four
consistently (e.g. `repeat_expression: "R3/PT1H"`, `repeat_interval_us:
3_600_000_000`, `repeat_total: 3`, `fired_count: 0`) satisfies shape 2 and
succeeds — the positive case.

### 1.5 `Letflow.Scheduler.Timer` Ecto schema (`lib/letflow/scheduler/timer.ex`)

Field list mirrors §1.1's column table exactly (Elixir type column below is
the `Ecto.Schema` field type, not the Postgres column type from §1.1 — the
two are Ecto's own standard mapping, e.g. `:binary_id` ↔ `uuid`,
`:utc_datetime_usec` ↔ `timestamp(6)`):

- `id` — `:binary_id`, `@primary_key {:id, :binary_id, autogenerate: false}`
  (same as `Letflow.Dlq.Entry`'s own primary-key declaration — the
  application generates the UUID at `create/2` time via `Ecto.UUID.generate/0`,
  not an autogenerated default).
- `tenant_id` — `:binary_id`.
- `instance_id` — `:binary_id`.
- `token_id` — `:binary_id`.
- `timer_type` — `:string`.
- `node_id` — `:string`.
- `fire_at` — `:utc_datetime_usec`.
- `status` — `:string`, default `"pending"`.
- `fired_at`, `cancelled_at`, `failed_at` — `:utc_datetime_usec`.
- `cancel_reason` — `:string` (Ecto's mapping for a `:text` column stays
  `:string` at the schema layer, same as `Letflow.Dlq.Entry.full_reason`).
- `fire_error_count` — `:integer`, default `0`.
- `repeat_expression` — `:string`.
- `repeat_interval_us` — `:integer` (Ecto has no native `:bigint` primitive
  distinct from `:integer` at the schema layer; the migration column type is
  `:bigint`, matching R-Co's microsecond-precision interval needing more than
  32-bit range).
- `repeat_total`, `fired_count` — `:integer`.
- `created_at` — `:utc_datetime_usec`.

No `timestamps/1` macro call (matches §1.1's "no `inserted_at`/`updated_at`"
decision).

**Changesets** (mirroring `Letflow.Dlq.Entry`'s multi-changeset shape —
`insert_changeset/2`, `retry_changeset/2`, `discard_changeset/2`, one
changeset per distinct write path rather than one do-everything changeset):

- `arm_changeset/2` — used by `create/2` (§2.1). Casts
  `[:id, :tenant_id, :instance_id, :token_id, :timer_type, :node_id, :fire_at,
  :repeat_expression, :repeat_interval_us, :repeat_total, :fired_count,
  :created_at]`; `status` is not castable through this changeset (always
  forced to `"pending"` by the context function, matching `Letflow.Dlq.enqueue/2`'s
  own "four fields the changeset can't override" discipline). Validates
  `timer_type` via `validate_inclusion/3` against the four R-Co values
  (application-layer companion to the DB not having a CHECK on this column,
  per §1.1). Validates required: `id`, `tenant_id`, `instance_id`,
  `timer_type`, `node_id`, `fire_at`, `created_at`.
- `fire_changeset/2` — used by the fire-transaction step (§4.3). Casts only
  `[:status, :fired_at]` (always sets `status: "fired"`). No other field is
  writable through this changeset.
- `retry_increment_changeset/2` — used by the failure-accounting step (§5.2).
  Casts only `[:fire_error_count]`.
- `fail_changeset/2` — used by the terminal-failure step (§5.3). Casts only
  `[:status, :failed_at]` (always sets `status: "failed"`).
- `rearm_changeset/2` (reserved for REQ-188, not called by any REQ-186
  function) — would cast the recurrence quartet plus `fire_at`/`status` for
  a newly-created re-armed row. Named here only so REQ-188's own design does
  not have to guess a name; REQ-186 defines the atom but no function calls
  it.

## 2. Context module: `Letflow.Scheduler` (`lib/letflow/scheduler.ex`)

Plain Ecto context module, no process — same shape as `Letflow.Dlq`/
`Letflow.Tasks`. The poller (§3) is a separate module that calls into this
one; this module itself starts no processes and owns no state.

### 2.1 `create/2` — SCH-01 arming

```
@type arm_attrs :: %{
        required(:instance_id) => Ecto.UUID.t(),
        required(:timer_type) => String.t(),
        required(:node_id) => String.t(),
        required(:fire_at) => DateTime.t(),
        optional(:token_id) => Ecto.UUID.t() | nil,
        optional(:repeat_expression) => String.t() | nil,
        optional(:repeat_interval_us) => non_neg_integer() | nil,
        optional(:repeat_total) => pos_integer() | nil,
        optional(:fired_count) => non_neg_integer() | nil
      }
@spec create(
        multi_or_repo :: Ecto.Multi.t() | Ecto.Repo.t(),
        arm_attrs(),
        opts :: [prefix: String.t()]
      ) :: Ecto.Multi.t() | {:ok, Timer.t()} | {:error, Ecto.Changeset.t()}
```

Signature deliberately accepts **either** a caller-supplied `Ecto.Multi.t()`
**or** a bare repo/no-multi call, mirroring the requirement's own text
("must accept a caller-supplied `Ecto.Multi` or repo so REQ-187 can enlist
it in the same transaction as the state transition that armed it") and this
codebase's existing composable-step precedent
(`Letflow.Engine.ExecutionError.append_multi/3` — appends steps onto a
caller's already-open `Multi`, opens no transaction of its own; contrast
`Letflow.Dlq.enqueue/2`, which does open its own transaction because nothing
composes it into a larger one). Concretely, two entry points sharing one
private builder:

- `create(%Ecto.Multi{} = multi, attrs, opts)` — appends one named
  `Ecto.Multi.insert/4` step (inserting the `arm_changeset/2`-built changeset
  under `opts[:prefix]`) onto `multi` and returns the extended `Multi.t()`
  **unexecuted** — the
  caller (REQ-187's transition-arming code) runs `Repo.transaction/1` itself,
  in the same transaction as its own state-transition event append. This
  function never calls `Repo.transaction/1` and never touches `Repo`
  directly when given a `Multi` — same "zero `Repo` calls of its own"
  invariant `ExecutionError.append_multi/3`'s own moduledoc states
  (INV-EE61-7's shape, restated here for this module).
- `create(Letflow.Repo, attrs, opts)` — standalone convenience form for a
  caller with no existing `Multi` (test setup, or a future call site with no
  surrounding transaction of its own); wraps the same changeset in
  `Repo.insert/2` directly and returns `{:ok, Timer.t()} | {:error,
  Ecto.Changeset.t()}` rather than a `Multi.t()`.

`tenant_id` is derived from `opts[:prefix]` via
`Letflow.TenantProvisioning.tenant_id_for_schema_name/1` — never accepted
from `attrs` (same discipline as `Letflow.Dlq.enqueue/2`; `arm_attrs()`
above has no `:tenant_id` key). `id` is generated internally
(`Ecto.UUID.generate/0`) before building the changeset, not accepted from
`attrs`, so REQ-187's caller never has to invent one. `created_at` is set
internally to `DateTime.utc_now() |> DateTime.truncate(:microsecond)`.
`status` is always forced to `"pending"`. When none of `repeat_expression`/
`repeat_interval_us`/`repeat_total`/`fired_count` are supplied in `attrs`,
all four are inserted as `nil` (shape 1 of §1.4's CHECK) — REQ-186's own
callers (REQ-187) never populate the recurrence quartet; only REQ-188's
future re-arm path will.

### 2.2 `poll_and_fire/1` — the tick entry point

```
@type poll_result :: %{
        tenant_schema: String.t(),
        claimed: non_neg_integer(),
        fired: non_neg_integer(),
        errored: non_neg_integer(),
        exhausted: non_neg_integer()
      }
@spec poll_and_fire(tenant_schema :: String.t()) :: poll_result()
```

Called once per tenant schema per tick by the `Poller` `GenServer` (§3), never
called by application code directly. Never raises — every per-timer failure
is caught internally (§4, §5) and folded into the returned counts, so one
tenant schema's poll pass always returns a result map even when every
claimed timer in it errored. This is what makes "the remaining due timers in
the same poll cycle are still attempted" (acceptance criterion 6) hold: the
`Poller`'s own per-tenant loop (§3.2) never sees an exception propagate out
of `poll_and_fire/1` for one tenant, so it always proceeds to the next
tenant schema regardless of how the current one's timers fared, and this
function's own inner loop (§4.1) never lets one timer's failure stop it from
attempting the rest of the claimed batch either.

### 2.3 Claim step (§4 REQ-185's decided mechanism)

```
@spec claim_due_timer_ids(tenant_schema :: String.t(), limit :: pos_integer()) ::
        [Ecto.UUID.t()]
```

Runs, **outside** any per-timer fire transaction, a single query:

```
SELECT id FROM timers
WHERE status = 'pending' AND fire_at <= now()
ORDER BY fire_at
LIMIT <max_timers_per_cycle>
FOR UPDATE SKIP LOCKED
```

expressed via `Ecto.Query`'s `lock("FOR UPDATE SKIP LOCKED")` composed with
`where/3`/`order_by/3`/`limit/3` (never a hand-written SQL string, matching
INV-7 and `Letflow.Dlq`'s own `fetch_and_lock_entry/3` idiom — the one
divergence from that precedent being `SKIP LOCKED` instead of plain `FOR
UPDATE`, which Ecto's `lock/3` accepts as a literal string argument the same
way). This claim query runs in its own short-lived transaction that commits
immediately after selecting the ids — it does **not** hold the row locks
across the whole batch's firing (each timer's own fire step, §4.3, re-locks
and re-checks its single row inside its own transaction). Selecting ids only
(not full rows) and re-fetching-with-lock per timer inside §4.3's own
transaction is the concrete mechanism this design uses to keep the "claim"
and "fire" steps as separate, individually-bounded transactions — this is a
deliberate choice, not an oversight: holding one open transaction across an
entire batch-claim-then-fire-each-in-sequence would make the WHOLE claim's
row locks live for the duration of every timer's fire attempt, artificially
widening lock scope and contradicting §4's own "each timer fires in its own
transaction" isolation unit. A row selected by the claim query but no longer
`status = 'pending'` by the time §4.3 re-locks it (a vanishingly narrow race
— nothing else in this design updates `status` between the two steps within
the same poll pass) is treated identically to "already fired," §4.4.

### 2.4 Fire step — one timer, one transaction (§4.3)

```
@spec fire_timer(timer_id :: Ecto.UUID.t(), tenant_schema :: String.t()) ::
        {:ok, :fired} | {:ok, :already_final} | {:error, term()}
```

Body, inside one `Repo.transaction/1`:

1. `SELECT ... FOR UPDATE` (plain, not `SKIP LOCKED` — this step already
   knows the row exists and wants to wait for, not skip, a conflicting
   lock-holder if one somehow still exists) the single `timers` row by `id`.
2. If `status != "pending"` (already `"fired"`/`"cancelled"`/`"failed"` —
   the double-poll idempotency case, §4.4), the transaction commits
   immediately, no-op, returning `{:ok, :already_final}`. Nothing is
   written.
3. Otherwise: compute `now = DateTime.utc_now() |> DateTime.truncate(:microsecond)`
   and `fired_late = DateTime.compare(now, timer.fire_at) == :gt`.
4. Apply `Timer.fire_changeset/2` (`status: "fired"`, `fired_at: now`) and
   `Repo.update/2`.
5. Append the `TIMER_FIRED` event (§6) via `Letflow.EventStore.append/2`,
   payload including `fired_late`, `scheduled_fire_at` (the timer's own
   `fire_at`, ISO-8601), and `actual_fired_at` (`now`, ISO-8601) — always
   present, `fired_late` is `false` and the two timestamps are within one
   poll interval of each other for the ordinary on-time case; SCH-05's
   requirement ("carries `fired_late: true` together with both the
   scheduled `fire_at` and the actual firing timestamp… whenever the actual
   firing time is later than fire_at") is satisfied by always including both
   timestamps and setting the boolean correctly, not by conditionally
   omitting fields.
6. Both writes (the `timers` row update and the event append) happen inside
   this **one** transaction — a crash or constraint violation on step 5
   rolls back step 4 too, so a `"fired"` timer with no corresponding event
   is structurally impossible, matching REQ-025's own event-append-inside-
   the-same-transaction discipline used everywhere else in this codebase.

A raise anywhere in steps 1–6 is caught by `Repo.transaction/1`'s own
`try/rescue` boundary — this function's *caller* (§2.5) wraps the
`Repo.transaction/1` call itself in an explicit outer `try/rescue` as a
second, defense-in-depth layer, because an `Ecto.Multi`/`Repo.transaction/1`
callback that raises (rather than returning `{:error, _}`) by default lets
`Repo.transaction/1` itself re-raise after rolling back — `Repo.transaction/1`
rolls the DB transaction back automatically on an internal raise, but it
does **not** turn that raise into a normal `{:error, reason}` return value on
its own; the caller must convert it. This is the concrete mechanism behind
REQ-185 §7's claim that "a raise there is trapped before it can escape the
per-timer step" — the trapping happens in `fire_timer/2`'s own caller (§2.5),
explicitly, via `try/rescue`, not implicitly via `Repo.transaction/1` alone.

### 2.5 Failure accounting — the ISS-303/ISS-0618 fix (§4/§5 of REQ-186's SCOPE, §7/§8 of REQ-185)

```
@spec attempt_fire(timer_id :: Ecto.UUID.t(), tenant_schema :: String.t()) ::
        :fired | :already_final | :errored | :exhausted
```

The per-timer loop body `poll_and_fire/1` (§2.2) calls once per claimed id.
Exact sequence (a description of required behavior, not an Elixir
expression — the exact `try`/`rescue` syntax is ELIXIR-DEV's to write):

1. Call `fire_timer/2` (§2.4) wrapped in the explicit outer `try`/`rescue`
   named there. A normal return (`{:ok, _}` or `{:error, _}`) passes through
   unchanged; a raise that escapes `fire_timer/2` itself is caught here and
   converted into an `{:error, {:raised, exception}}` value instead of
   propagating further.
2. `{:ok, :fired}` → returns `:fired`. `{:ok, :already_final}` → returns
   `:already_final` (§4.4 — the second poll over an already-fired timer;
   counted separately from `:fired` in `poll_result()` so a test can assert
   "second poll appends no second event" precisely, though this atom itself
   is a loop-internal detail — `poll_result()`'s public `fired` count only
   increments on the first, real `:fired` outcome, never on `:already_final`).
3. Any `{:error, _}` result (from step 4/5/6 of `fire_timer/2` failing, or
   the outer rescue in step 1 catching a genuine raise) triggers the
   **separate** failure-accounting transaction:
   - A **new**, second `Repo.transaction/1` (deliberately not the same
     transaction that just rolled back in step 1 — that transaction is
     already gone; this is why the requirement calls it "a SEPARATE
     transaction") re-locks the same row (`SELECT ... FOR UPDATE`),
     applies `Timer.retry_increment_changeset/2` with
     `fire_error_count: current + 1`, and commits.
   - If the just-incremented `fire_error_count` is now `>=
     max_fire_retries()` (§7, default 3): **within that same second
     transaction**, additionally apply `Timer.fail_changeset/2` (`status:
     "failed"`, `failed_at: now`) and call `Letflow.Dlq.enqueue/2` (§7) —
     both inside this one accounting transaction, so "reaches max retries"
     and "lands in the DLQ" are atomic with each other (never a `"failed"`
     timer with no DLQ row, never a DLQ row for a timer still `"pending"`).
     Returns `:exhausted`.
   - Otherwise (still below the threshold): returns `:errored`. The timer's
     `status` stays `"pending"` (acceptance criterion 6's own wording:
     "increments `fire_error_count` and leaves the timer 'pending'").
4. Whatever this function returns, `poll_and_fire/1`'s own loop (§2.2)
   **always proceeds to the next claimed id** — nothing in this function's
   contract, or its caller's, treats `:errored`/`:exhausted` as a reason to
   stop. This is the literal mechanism behind acceptance criterion 6's "the
   remaining due timers in that same poll cycle are still attempted": the
   loop is a plain `Enum.map/2` (or `Enum.reduce/3` accumulating the
   `poll_result()` counts) over the claimed id list, with `attempt_fire/2`
   as the mapping function — no `Enum.each` short-circuit, no `with`-chain
   that halts on the first non-`:ok`, and (per §2.4's own explicit
   `try/rescue`) no raise ever reaches this loop from the mapping function
   to short-circuit it implicitly either.

### 2.6 DLQ landing (§7, `entry_type: "timer"`)

`enqueue_attrs()` fields populated for a timer's DLQ entry (REQ-185 §8's
"OQ-1", resolved here as this requirement's own job), described as a table
rather than a literal map (the exact map-construction expression is
ELIXIR-DEV's to write):

| `enqueue_attrs()` key | Value |
|---|---|
| `entry_type` | The literal string `"timer"` |
| `instance_id` | The timer row's own `instance_id` |
| `reference_id` | The timer row's own `id` |
| `reason` | A short sentence naming the timer's `node_id` and the configured `max_fire_retries()` value it exhausted |
| `error_detail` | A map with string keys `"timer_id"`, `"node_id"`, `"timer_type"`, `"fire_at"` (ISO-8601), `"fire_error_count"` — each read from the timer row |
| `first_failed_at` | See note below |
| `last_failed_at` | The current timestamp, at the moment this exhausting attempt is recorded |

Note on `first_failed_at`: `Letflow.Scheduler.Timer` itself has no
`first_failed_at` column of its own (§1.1 has no such field — only
`dlq_entries` does) — `first_failed_at` here is populated from the exact
same `now` computed at the moment `fire_error_count` first went from `0` to
`1`, which this design does **not** separately track on the `timers` row.
**Open question (not silently resolved — see §9 OQ-1):** since `timers` has
no column recording when its *first* failed attempt happened, this field is
populated with the same `now` as `last_failed_at` (i.e., both equal the
exhausting attempt's timestamp) rather than a genuinely earlier value. This
is an accepted, stated imprecision, not a defect masked as one — no
acceptance criterion requires `first_failed_at` to differ from
`last_failed_at` for a timer's DLQ entry specifically (contrast
`Letflow.Engine.ExecutionError`'s own DLQ landing, §8's precedent, which
also sets both to the same `now` for the identical reason — verified in
`execution_error.ex` lines 220/242-243 above, `first_failed_at: now,
last_failed_at: now`, the exact same pattern this design reuses).
`Letflow.Dlq.enqueue/2` is called with `opts: [prefix: tenant_schema]` —
tenant-scoped, no cross-schema write, matching Decision B.

## 3. `Letflow.Scheduler.Poller` — the `GenServer` ticker (`lib/letflow/scheduler/poller.ex`)

Implements REQ-185 §2's Decision 1 (supervised `GenServer` ticker) and §6's
Decision 5 (iterates tenant schemas per tick via the `tenant_schemas`
registry).

### 3.1 State and lifecycle

```
@type state :: %{}
```

No meaningful state is carried between ticks — the poller is a pure
scheduling loop, matching REQ-185 §2b's own "no in-memory state to recover"
property. `start_link/1` takes no required args, registering the process
under its own module name. `init/1` schedules the **first** `:tick` message
to itself with **zero** delay — not delayed by a full interval — matching
REQ-185 §2b's "its very first tick immediately runs the same claim query,"
which is what makes a restart catch up on missed timers with zero
special-cased recovery logic.

### 3.2 `handle_info(:tick, state)`

1. Reads config (§7) fresh on every tick — `poll_interval_ms/0`,
   `jitter_ms/0`, `max_timers_per_cycle/0` — so a config override made
   mid-run (e.g. by a test calling `Application.put_env/3`) takes effect on
   the very next tick, not only at process start (this is the mechanism
   behind acceptance criterion 8's "asserting the poller uses the
   override").
2. Enumerates every provisioned tenant schema:
   `Letflow.TenantProvisioning.Registration` rows with a non-`nil`
   `migrations_applied_at` (i.e., a schema whose migrations — including this
   requirement's own `timers` migration — have actually been replayed;
   verified against `lib/letflow/tenant_provisioning.ex`'s own
   `Registration` schema and its `migrations_applied_at` field, §1's own
   citation of this table). Reads `Repo.all/2` over `Registration`, selecting
   `schema_name`, filtered `where: not is_nil(r.migrations_applied_at)` —
   the same "only a fully-provisioned tenant is queryable" guard
   `Letflow.EventStore.Registry`'s own `resolve_schema_name/1` establishes
   for a single tenant, generalized here to "all of them."
3. For each tenant schema (in the order `Repo.all/2` returns — no ordering
   guarantee beyond that; nothing in the acceptance criteria requires
   cross-tenant fairness ordering), calls `Letflow.Scheduler.poll_and_fire/1`
   and discards/logs the returned `poll_result()` (no acceptance criterion
   requires the `GenServer` to expose these counts anywhere yet — a future
   observability requirement may; not invented here).
4. Schedules the next tick: the delay is `poll_interval_ms()` plus a
   uniformly-random extra amount in the inclusive range `0..jitter_ms()`
   milliseconds (when `jitter_ms() > 0`; when it is `0`, the delay is
   exactly `poll_interval_ms()`, with no random-number call made at all —
   the random draw must be skipped rather than degenerately called with a
   zero-width range). Each node's `Poller` process rolls its own jitter
   independently via the BEAM's own per-process default PRNG seeding — no
   shared seed is threaded through, matching SCH-06's "randomised
   independently per node with no shared seed" requirement. Jitter is
   applied **only** to this scheduling delay, never to any `fire_at` value
   written or read anywhere in `Letflow.Scheduler` (SCH-06's other half —
   `fire_at` is always the caller-supplied absolute timestamp from REQ-187's
   own arming call, never adjusted by this module).
5. `{:noreply, state}`.

A raise anywhere inside one tenant schema's `poll_and_fire/1` call
propagating out of `handle_info/2` would crash the `Poller` process itself,
which — per §2.2's own contract — should not happen (`poll_and_fire/1` never
raises, by construction of §2.5's per-timer `try/rescue`). No additional
`try/rescue` wraps the `Enum.each` over tenant schemas in step 3, because
`poll_and_fire/1`'s own contract already guarantees it cannot raise; adding
a second, redundant rescue layer here would duplicate §2.5's
already-established isolation boundary for no additional safety property
(the same "don't restore already-redundant machinery" reasoning REQ-185 §4
applies to R-Co's per-timer advisory lock).

### 3.3 Supervision (`lib/letflow/application.ex`)

One line added to the existing `children` list (§0 item 5):
`{Letflow.Scheduler.Poller, []}`. Placement: after the existing
`InstanceSupervisor`/`SandboxPool` children (the `Poller` has no ordering
dependency on any Task.Supervisor the way `SandboxPool` does on its own —
see `application.ex`'s existing comment about *that* specific ordering
constraint, which does not apply here), before `http_child()`'s conditional
`Bandit` listener (matches this project's own convention of listing
background/internal processes before the externally-facing HTTP listener).
No new `Task.Supervisor` (this design's own opening decision, restated).

## 4. Missed-timer recovery (SCH-05, acceptance criterion 4)

No separate "recovery" or "sweep" code path exists — per REQ-185 §5's own
decision, the *ordinary* claim query (§2.3: `status = 'pending' AND fire_at
<= now()`) is already restart-tolerant and catch-up-safe by construction. A
timer created with `fire_at` in the past becomes eligible the instant it is
inserted; the very next tick's claim query for its tenant schema selects it
(it satisfies `fire_at <= now()` immediately), and §2.4's fire step marks
`fired_late: true` because `DateTime.compare(now, timer.fire_at) == :gt`
holds. A timer created with `fire_at` in the future is correctly excluded
from that same poll's claim query (`fire_at <= now()` is false for it) and
is not touched until a later tick's `now()` has advanced past it — this is
what makes "two explicit tests" (one per-timer creation time) meaningfully
different rather than trivially both passing by accident: the past-`fire_at`
test asserts a row **appears** in the claim result and gets fired with
`fired_late: true`; the future-`fire_at` test asserts the **same poll pass**
(same tick, same tenant schema) does **not** include that row at all.

## 5. Idempotency (double-poll, acceptance criterion 5)

Guaranteed structurally by §2.4 step 2 (`fetch_and_lock` + `status != "pending"`
early-return before any write) combined with §2.3's own claim query only ever
selecting `status = 'pending'` rows in the first place. Concretely: poll #1
claims the row (id in `claim_due_timer_ids/2`'s result), fires it, commits
`status: "fired"`. Poll #2's own `claim_due_timer_ids/2` call runs the
identical query — `WHERE status = 'pending' AND fire_at <= now()` — and the
now-`"fired"` row no longer matches `status = 'pending'`, so it is not even
selected by poll #2's claim query; `fire_timer/2` (§2.4) is never invoked a
second time for this row at all. (§2.4 step 2's own "already final" branch is
a second, redundant-but-cheap safety net for the narrow window where a row
was claimed by `claim_due_timer_ids/2` but had already transitioned by the
time `fire_timer/2`'s own lock+check ran — not the primary mechanism
preventing a genuine double-fire across two separate ticks, which the claim
query's own `WHERE status = 'pending'` filter already rules out on its own.)
No second `TIMER_FIRED` event is ever appended for an already-`"fired"` row,
and `fired_at` is never overwritten (§1.1's own note) — both follow directly
from `fire_timer/2` never reaching its write steps (4/5) once step 2's
early-return fires.

## 6. Event registration (scope item 6, REQ-025's pattern)

New event type: **`"TIMER_FIRED"`**. Registered by appending one entry to
`lib/letflow/tenant_provisioning.ex`'s existing `@platform_event_type_seed_attrs`
list (the exact mechanism verified in §"reading" above — six existing
entries: `INSTANCE_STARTED`, `TASK_COMPLETED`, `INSTANCE_CANCELLED`,
`INSTANCE_PINS_REBOUND`, `SUB_PROCESS_COMPLETED`, `EXECUTION_ERROR`, plus
three `DEFINITION_*`/`PROMOTION_*` platform events — `TIMER_FIRED` becomes
the tenth), seeded by `maybe_seed_platform_event_types/2` via
`Letflow.EventStore.Registry.register_type/2` immediately after a tenant
schema's migrations replay, idempotent by construction
(`{:error, :duplicate_event_type_version}` treated as success, same as
every existing entry).

The new seed-list entry, described field-by-field (matching the six
existing entries' own `name`/`schema_version`/`description`/`json_schema`
shape — the exact map literal is ELIXIR-DEV's to write):

- `name`: `"TIMER_FIRED"`.
- `schema_version`: `1`.
- `description`: states that this event is emitted by
  `Letflow.Scheduler.fire_timer/2` (SCH-01/05) when a pending timer's
  poll-and-fire transaction commits.
- `json_schema`: a JSON Schema object requiring exactly six string/boolean
  properties, all required: `timer_id` (string), `node_id` (string),
  `timer_type` (string), `fired_late` (boolean), `scheduled_fire_at`
  (string, ISO-8601), `actual_fired_at` (string, ISO-8601) — matching
  §2.4 step 5's payload fields one-for-one.

`Letflow.EventStore.append/2` is called from `fire_timer/2` (§2.4 step 5)
with `event_type: "TIMER_FIRED"`, `instance_id: timer.instance_id`, an
`idempotency_key` deterministically derived from the timer's own id and its
firing (e.g. `"timer_fired:#{timer.id}"` — stable across a hypothetical
retried call for the *same* commit attempt, distinguishing it from the
poll-level idempotency §5 already establishes at the `status` level; ES-05's
own idempotency-key uniqueness constraint is a second, independent
safety net here, not the primary double-fire guard), `actor_id:
Letflow.EventStore.platform_actor_id()` — **corrected post-implementation**
from this section's original text, which stated a literal `actor_id: nil`
on the (incorrect) assumption that this codebase has a precedent for
system-initiated events carrying a `nil` actor. `Letflow.EventStore.append/2`
itself requires `attrs[:actor_id]` to cast via `Ecto.UUID.cast/1` (its own
`fetch_uuid/3` helper returns `{:error, :missing_actor_id}` for `nil`,
verified directly in `event_store.ex`), so a literal `nil` here would make
every `fire_timer/2` call fail and never fire a single timer.
`Letflow.EventStore.platform_actor_id/0` is this codebase's own
already-established sentinel for exactly the "no human/API actor" case
(`Letflow.EventStore.PlatformEvents`'s own moduledoc, point 4), and is what
`lib/letflow/scheduler.ex`'s shipped implementation uses instead — flagged
by ELIXIR-DEV, verified by SECURITY-REVIEWER and REVIEWER
(WF02-REQ186-20260829 Step 2c/2d), no other part of this design changes.
`payload` is built from the fields in §2.4 step 5.

## 7. Configuration (scope item 5)

Config key: `config :letflow, :scheduler, [...]`, read via
`Application.get_env(:letflow, :scheduler, [])`, same shape as
`Letflow.SandboxPool`'s own `:sandbox_pool` key
(`lib/letflow/sandbox_pool.ex` line 226,
`Application.get_env(:letflow, :sandbox_pool)[:provision_timeout_ms]`) —
verified precedent for "a keyword list under one atom key, read fresh at the
point of use, no compile-time `@` module attribute caching it."

| Key | Default | Read by |
|---|---|---|
| `:poll_interval_ms` | `5000` | `Poller.handle_info/2` (§3.2 steps 1/4) |
| `:jitter_ms` | `0` | `Poller.handle_info/2` (§3.2 steps 1/4) |
| `:max_timers_per_cycle` | `64` | `Letflow.Scheduler.claim_due_timer_ids/2`'s `limit` argument (§2.3), read by `poll_and_fire/1` before calling it |
| `:max_fire_retries` | `3` | `Letflow.Scheduler.attempt_fire/2`'s exhaustion check (§2.5 step 3) |

Four private accessor functions in `Letflow.Scheduler` (or a small shared
`Letflow.Scheduler.Config` module, implementer's choice — not load-bearing
either way): `poll_interval_ms/0`, `jitter_ms/0`, `max_timers_per_cycle/0`,
`max_fire_retries/0`. Each reads the `:scheduler` application-env keyword
list fresh (no compile-time caching), takes its own key out of that list,
and falls back to this section's stated default when the key is absent —
the same "read fresh, keyword-list default" shape
`Letflow.SandboxPool`'s own `:provision_timeout_ms` accessor already uses.
No static `config/{dev,test,prod}.exs` entry is
required for the defaults to take effect (`Application.get_env/3`'s own
third-argument default, `[]`, combined with `Keyword.get/3`'s implicit `nil`
on a missing key, falls through to each accessor's own `|| default`) — a
test overriding, say, `:poll_interval_ms` does so via
`Application.put_env(:letflow, :scheduler, poll_interval_ms: 50)` inside its
own `setup`, matching `Letflow.SandboxPool`'s own override-in-test precedent
verified in `iss0220-sandbox-pool-provision-timeout.md`'s own citation of the
identical mechanism, and restoring the prior value in `on_exit/1` so the
override doesn't leak into later tests (same discipline that design doc's
own citation already documents at line ~1258 for `:sandbox_pool`).
