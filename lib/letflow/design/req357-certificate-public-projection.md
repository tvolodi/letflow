# REQ-357 — Design: the certificate public projection and its issuance wiring

Stage S10 (P3, certificate issuance — motivation S10 gap 6's vertical half).
Bucket **C** — per decision 0022 rule 1 this document names exams and certificates
throughout, deliberately (the entry's own text: "this half CANNOT be stated without
naming certificates and exams"). Owner: `CODE-DESIGNER`. Status: design only.

This document does **not** re-derive the unauthenticated-read pattern, the mount, the
sub-router, the handle registry, the limiter, or the ten-case refusal path — all of that
is REQ-323/0028 (pattern) and REQ-352 (platform machinery), both already built and
merged (`lib/letflow/public_read.ex`, `lib/letflow/public_read/handle.ex`,
`lib/letflow/public_read/projection.ex`, `lib/letflow/routers/public_read.ex`,
`lib/letflow/routers/public_read_handles.ex`). This document designs exactly the two
things REQ-357 owns: **(1)** the certificate `Letflow.PublicRead.Projection`
implementation and its registration, and **(2)** the wiring that mints a handle at
certificate-issuance time through REQ-352's existing writer, `issue_handle/4` — no new
writer, no new HTTP route, no new registry.

## 0. Premises re-verified against the tree (2026-09-15)

- `Letflow.PublicRead.Projection` (`lib/letflow/public_read/projection.ex:1-47`) is
  exactly the behaviour REQ-323 §4.4 specified: `@callback schema() :: module()` and
  `@callback project(resource(), handle_meta()) :: {:ok, %{optional(String.t()) =>
  term()}} | :skip`, with `handle_meta :: %{issued_at: DateTime.t(), kind: String.t()}`.
- `Letflow.PublicRead.resolve/2` (`lib/letflow/public_read.ex:126-208`) performs round-trip
  1 (join `public_read_handles` → `tenants.status`), decides cases 2–5 in memory, then
  round-trip 2 as `Repo.get(projection_module.schema(), handle.resource_id, prefix:
  prefix)`, and turns `:skip` from `project/2` into `:not_found` — i.e. case 7 (§4.2) is
  already wired generically; this design supplies only the predicate.
- `Letflow.PublicRead.issue_handle/4` (`lib/letflow/public_read.ex:44-99`) is the sole
  writer: `(tenant_id, kind, resource_id, opts)` → `{:ok, %{handle: plaintext, record:
  Handle.t()}} | {:error, Ecto.Changeset.t()}`. It mints, hashes, inserts, audits, and
  returns the plaintext exactly once. It performs no permission check itself — enforcement
  is the caller's route's job (§5 below).
- `Letflow.Routers.PublicReadHandles` (`lib/letflow/routers/public_read_handles.ex`)
  already exists as a **separate**, generic, authenticated `POST /public-read-handles`
  route gated on policy key `:PublicReadHandlesIssue`, mounted under
  `Letflow.Plugs.ApiPipeline` (tenant-scoped, nowhere near `/api/public`). Its own
  moduledoc states: *"Role grant for `:PublicReadHandlesIssue` is deliberately left to
  the requirement that authors the first concrete issue path consuming this permission."*
  REQ-357 is that requirement. §5.3 below is this document's answer.
- `lib/letflow/exam/certificate.ex` (REQ-355, merged) is the certificate issuance context
  module. Its `certificate` entity type is a **bucket-A entity record**
  (`priv/packs/bilimbaga/entity_definitions/certificate.json`), created via
  `Letflow.Entities.Records.create_record/2` and read back as a
  `%Letflow.Entities.Record.Latest{}` struct — **not** a bespoke Ecto schema/table. This
  is the load-bearing fact for §2.
- `Letflow.Entities.Record.Latest` (`lib/letflow/entities/record/latest.ex`) has
  `@primary_key {:id, :binary_id, autogenerate: true}` **and** a separate `record_id`
  field (a freshly-minted UUID, distinct from `id`, generated by
  `Letflow.Entities.Records.create_record/2:164`). `Letflow.Entities.Record.Latest.get/3`
  looks a row up by `(entity_type, record_id)` — **not** by the Ecto primary key `id`.
  `Letflow.Exam.Certificate.certificate_view/1` exposes `record.record_id` as the
  candidate-facing `"id"` field (`certificate.ex:343`). This distinction is the hinge of
  §2.2 below and is the single most important fact in this design to get right.

## 2. The projection module

### 2.1 Module and file

`Letflow.Exam.CertificatePublicProjection`, `lib/letflow/exam/certificate_public_projection.ex`
— colocated with the rest of the `Letflow.Exam.*` vertical (matching
`Letflow.Exam.Certificate`, `Letflow.Exam.Session`), not under `Letflow.PublicRead.*`
(that namespace is REQ-323/0028's own vocabulary-neutral platform machinery and must stay
free of vertical-specific modules, per 0028's Consequences: "A new unauthenticated read
contributes a kind string and a projection module").

```elixir
@behaviour Letflow.PublicRead.Projection
```

### 2.2 `schema/0` — and the resource_id substitution this design makes explicit

```elixir
@spec schema() :: module()
def schema
```

Returns `Letflow.Entities.Record.Latest`.

**This is only correct if `resource_id` (the column `Letflow.PublicRead.resolve/2` feeds
to `Repo.get(schema(), resource_id, prefix:)`, §0) is the `Letflow.Entities.Record.Latest`
row's own primary key — `id` — and NOT `record_id`.** `Repo.get/3` matches on the Ecto
primary key unconditionally; `Latest`'s primary key is `id`, and `record_id` is an
ordinary (non-key) column read by an entirely different function (`Latest.get/3`, which
`resolve/2` never calls). A handle minted with `resource_id = record.record_id` (the
identifier every OTHER surface in this vertical uses — `certificate_view`'s own `"id"`
field, `session_id` foreign keys) would silently 404 forever: `Repo.get(Latest,
record.record_id, prefix:)` searches for a row whose **`id`** equals a value that is, in
fact, some *other* row's `record_id`, or matches nothing at all.

**Decision, stated so a later reader does not rediscover this the hard way:** §5's
wiring passes **`record.id`** (the `Letflow.Entities.Record.Latest` struct's own
autogenerated primary key), never `record.record_id`, as `issue_handle/4`'s
`resource_id` argument. `record.id` is stable once inserted (the certificate entity type
is create-only — no `update_record`/`delete_record` call in this vertical ever touches a
certificate row, so `record_id`'s own `ON CONFLICT (record_id) DO UPDATE` upsert path,
which could in principle only affect non-key columns, never runs for this entity type in
practice) and is never exposed to any HTTP caller — it exists purely as the internal join
key this design's wiring uses.

**Invariant this design relies on, stated rather than silently assumed:** every row
`Repo.get(Latest, resource_id, prefix:)` reaches via a handle registered under kind
`"certificate"` has `entity_type == "certificate"`, solely because `issue_handle/4` is
only ever called with `kind: "certificate"` from §5's one wiring point, which only ever
supplies a certificate record's own `id`. `Letflow.PublicRead.resolve/2`'s generic
round-trip 2 does **not** re-check `entity_type` (inherited from REQ-352's design,
unchanged here) — this is safe because `id` is already a global, unique, per-row primary
key across every entity type sharing the `entity_record_latest` table, so no other kind's
resource_id could collide with a certificate's. Flagged explicitly (open question OQ-1,
§8) rather than silently relied upon, since a future kind's own projection author should
not assume this holds without re-deriving it for their own entity type.

### 2.3 `project/2` — the publishability predicate and the field set

```elixir
@spec project(resource :: Letflow.Entities.Record.Latest.t(), handle_meta :: Letflow.PublicRead.Projection.handle_meta()) ::
        {:ok, %{String.t() => term()}} | :skip
def project(resource, _handle_meta)
```

**Publishability predicate (AC-7):** `:skip` when `resource.deleted == true`; otherwise
`{:ok, data}`. No certificate entity-type row in this vertical is ever soft-deleted by any
existing write path today (`Letflow.Exam.Certificate` never calls `delete_record/2` for a
`certificate`), but `Letflow.Entities.Record.Latest.deleted` is a real, generic field
every entity record carries, and a future admin/retraction path could set it — the
predicate must hold regardless of whether such a path exists yet, exactly as REQ-323 §4.2
case 7 requires ("a per-kind publishability predicate"). This is the one piece of §4.2's
ten-case table this design supplies; the other nine are REQ-352's own generic mechanism.

**MUST be pure** (behaviour's own contract, §0): reads only `resource.field_values` and
literal constants. No `Repo`, no `Application`, no clock read — the branding/candidate
name/exam title were already captured into `resource.field_values` at issuance time by
`Letflow.Exam.Certificate`, so nothing here needs a second read of anything.

**The `data` field set — every field justified against INV-2 individually (AC-1):**

| Key | Source (`resource.field_values[...]`) | Type | INV-2 justification — why an anonymous holder of the forwarded link is entitled to it |
|---|---|---|---|
| `"candidate_name"` | `"candidate_name"` | `String.t()` | This is the certificate's entire reason to exist: proving *who* earned it. A certificate whose public rendering omits the name it certifies is not a certificate. Distinguished from the envelope's generically-forbidden "personal identifier" class (§2.4 below) because it is not an internal identifier (`user_id`, email, actor id) — it is the tenant-chosen display name the candidate itself supplied at account creation, captured once at issuance specifically so it can be shown on the certificate the candidate requested be issued (`Letflow.Exam.Certificate`'s own "Branding snapshot" section: captured so a later name change does not alter an already-issued certificate — the same "deliberately chosen to publish" test req323 §4.4 sets). |
| `"exam_title"` | `"exam_title"` (a `localized_text` map, all locales) | `map()` | The subject matter of the certification — analogous to a diploma naming the credential earned. Contains no candidate-specific or tenant-internal data; it is exam content already visible to every candidate who takes the exam. |
| `"score_pct"` | `"score_pct"` | `float()` (via the same `to_float/1` coercion `Letflow.Exam.Certificate.certificate_view/1` already applies) | The achievement the certificate certifies. The tenant's whole reason for issuing a certificate is to let the score be verified by a third party (an employer, another institution) holding the link — withholding it would make the certificate unable to serve its stated purpose. |
| `"issued_on"` | `"issued_at"` (the certificate record's own field, ISO-8601, stamped by `Letflow.Exam.Certificate` at issuance) | `String.t()` (ISO-8601) | The certification date — core content a certificate displays (analogous to a diploma's date), not an internal audit timestamp. **Deliberately named `"issued_on"`, not `"issued_at"`, to avoid confusion with the pattern's own top-level envelope key `"issued_at"` (§3), which is the *handle's* mint time (`Handle.inserted_at`) — a different fact that will usually, but not necessarily, coincide with this one** (see §5.2 for why they coincide in practice for this kind). req323 §4.4's forbidden-field list bars a resource's own `inserted_at`/`updated_at` (the storage row's operational timestamps) — this is neither: it is a business field the tenant explicitly entered into the certificate record as its certification date, semantically identical to `exam_title`/`score_pct` in kind, not to a row's storage metadata. |
| `"branding_snapshot"` | `"branding_snapshot"` (the three-key map `{"app_name", "logo_url", "brand_colors"}` — see below) | `map()` | Needed to render the certificate with the issuing tenant's identity (a certificate with no issuer shown is not a credential). **Explicitly checked against req323 §4.4's generic forbidden list, which bars "tenant display name" at pattern level:** `branding_snapshot`'s `"app_name"` is not `tenants.name`/slug/id — it is `Letflow.Routers.TenantConfig.branding_from_settings/1`'s own three-key allowlisted map (`app_name`, `logo_url`, `brand_colors`, `tenant_config.ex:288-297`), the **exact same map** `GET /api/tenant-config` already serves **fully unauthenticated, to anyone, for every tenant**, today. Including it here discloses nothing `/api/tenant-config` does not already disclose with zero access control; it is not a new tenant-identity leak, it is the same one REQ-078 already accepted. Flagged for SECURITY-REVIEWER as the sharpest field-inclusion call in this table, per req323 §4.4's own governing rule ("adding a field... is a security change, not a feature... a stated reason why an unauthenticated... audience is entitled to it") — the reason stated above is that reason. |

**What is explicitly excluded, and why (AC-2):**

| Excluded | Why |
|---|---|
| `session_id` | An internal cross-entity foreign key with no display purpose; exposing it would let a holder correlate this certificate to the session subsystem's own identifiers for no benefit to the certificate's stated purpose. |
| `record.record_id` / `record.id` (the certificate's own record identity, in either form) | "No internal record id" (AC-2, req323 §4.4's own forbidden list). The envelope's `"kind"` + the handle itself are the only identifiers a holder needs. |
| `tenant_id`, tenant slug, tenant `status` | Never read by this projection at all — `resource.field_values` carries none of them; `Letflow.PublicRead.resolve/2`'s own row (`handle.tenant_id`) is never passed to `project/2` (the `handle_meta()` type is deliberately narrow, §0) so there is no way for this module to leak it even by mistake. |
| candidate `user_id`/email | Never captured into `certificate.field_values` at all (`Letflow.Exam.Certificate`'s own entity definition has no such field) — structurally absent, not filtered out. |

### 2.4 The reusable rule this table applies

req323 §4.4's generic forbidden list ("no tenant display name... no personal identifier...")
is a **default for a pattern with no concrete instance in view** — it correctly refuses
to pre-judge every future kind's own disclosure question. Bucket C exists precisely so a
concrete kind can answer that question with domain judgment rather than inherit the
generic default uncritically. This table is that answer for `certificate`, and each row
states the same test req323 §4.4 sets rather than a different one: *"would the tenant
accept this being world-readable the moment someone forwards the link?"* For a
certificate specifically, the answer for `candidate_name`/`exam_title`/`score_pct`/
`branding_snapshot` is yes by the certificate's own definition of what it is; the answer
for every excluded field is no.

## 5. Wiring the mint into REQ-355's authenticated issue path

### 5.1 Where, precisely

`lib/letflow/routers/exam_sessions.ex`'s existing route:

```
authz_post "/:id/certificate", :ExamCertificateIssue do
  handle_issue_certificate(conn, conn.params["id"])
end
```

delegating to `handle_issue_certificate/2` (`exam_sessions.ex:415-429`), which calls
`Letflow.Exam.Certificate.issue_or_get_for_user/3` and renders via
`render_issue_certificate/2` (`:431-466`). **This is the only call site this design
touches.** No new route, no new `authz_*` declaration, no new policy key.

### 5.2 What changes in `Letflow.Exam.Certificate`

**Problem this section exists to solve:** `issue_or_get_for_user/3` today discards
`Letflow.Entities.Records.create_record/2`'s own `is_duplicate` flag
(`certificate.ex:294-305`: `{:ok, %{record: record}} -> {:ok, record}`), and
`certificate_view/1` exposes no field a caller could use to distinguish "just issued"
from "already existed." A handle must be minted **exactly once per certificate** — not
once per HTTP call — so the wiring needs to know which call is the create.

**Two signature changes, both additive, no behavior change to any existing guard:**

1. `issue_or_fetch/4` (private, `certificate.ex:282-307`) changes its return shape from
   `{:ok, record}` to **`{:ok, record, first_issuance :: boolean()}`**, where
   `first_issuance` is `not is_duplicate` — the exact `is_duplicate` value
   `Records.create_record/2` already returns (`{:ok, %{record: record, is_duplicate:
   is_duplicate}}`), simply threaded through instead of discarded.
2. `certificate_view/1` becomes `certificate_view/2`, taking `(record, first_issuance)`,
   and `certificate_view()`'s type gains two fields:

```elixir
@type certificate_view :: %{
        id: String.t(),
        session_id: String.t(),
        issued_at: DateTime.t(),
        candidate_name: String.t(),
        exam_title: term(),
        score_pct: float(),
        branding_snapshot: map(),
        first_issuance: boolean(),
        public_read_resource_id: String.t()
      }
```

   `public_read_resource_id` carries `record.id` — the `Letflow.Entities.Record.Latest`
   row's own primary key, per §2.2 — never `record.record_id`. Both new fields are
   **internal wiring fields, not part of the authenticated HTTP response** — §5.4 states
   this explicitly so `certificate_json/1` is not accidentally widened to leak them.

`issue_or_get_for_user/3`'s own `@spec` is unchanged (`{:ok, certificate_view()} |
{:error, issue_error() | term()}`) — only what `certificate_view()` itself contains
grows.

### 5.3 What changes in `lib/letflow/routers/exam_sessions.ex`

`render_issue_certificate/2`'s success clause changes from:

```elixir
defp render_issue_certificate(conn, {:ok, certificate}),
  do: Response.ok(conn, certificate_json(certificate))
```

to a version that, **only when `certificate.first_issuance == true`**, calls
`Letflow.PublicRead.issue_handle/4` with:

- `tenant_id`: `conn.assigns.auth_context.tenant_id` (the same source every other route
  in this router already uses — never a request-supplied value, INV-1),
- `kind`: the literal `"certificate"`,
- `resource_id`: `certificate.public_read_resource_id`,
- `opts`: `[]` (no `expires_at` — a certificate's validity is not time-boxed; §8 OQ-2
  flags whether it should be, since REQ-357's own scope does not decide certificate
  expiry policy),

and, on `{:ok, %{handle: plaintext}}`, includes the plaintext in the JSON response as a
new top-level key on the **authenticated** response (not the public envelope of §3 — this
is the candidate's own private view of their own certificate): `"public_handle" =>
plaintext`. On replay (`first_issuance == false`), this key is simply **absent** — the
plaintext cannot be recovered (only its SHA-256 is ever stored, INV-4), so a second call
for the same session returns the certificate without a link, exactly as the candidate
saw it minus the one-time credential they were already shown.

**Handle-mint failure is non-blocking relative to the certificate itself, decided here so
this is not left ambiguous:** if `issue_handle/4` returns `{:error, changeset}`, the
route still responds `200` with the certificate (already durably created — its own
transaction already committed) and omits `"public_handle"`, logging a warning. The
alternative — wrapping both writes in one transaction so either both succeed or neither
does — would require restructuring `Records.create_record/2`'s and `issue_handle/4`'s
own, already-shipped, independent `Ecto.Multi`/`Repo.transaction/1` calls into a shared
one, which is exactly the kind of second write surface the requirement forbids
inventing. Flagged as OQ-3 (§8) rather than silently declared final, since it is a real
tradeoff (a candidate whose first mint attempt failed gets no automatic retry — see
OQ-3's full statement) that a later reader could reasonably want revisited, but it does
not block this requirement's own acceptance criteria, none of which test the
partial-failure path.

### 5.4 `certificate_json/1` — must NOT widen

`certificate_json/1` (`exam_sessions.ex:541-...`) already hand-selects fields by pattern
match; this design requires it to keep doing so — `first_issuance` and
`public_read_resource_id` must **not** appear in its output. The new `"public_handle"`
key is added by `render_issue_certificate/2` **after** calling `certificate_json/1`
(`Map.put(certificate_json(certificate), "public_handle", plaintext)`), never by teaching
`certificate_json/1` about the wiring fields. This keeps the internal/public boundary
exactly where AC-2's discipline expects it, one layer removed from the already-public
envelope of §3.

### 5.5 The permission-atom question (AC-6, `:PublicReadHandlesIssue`) — answered, not silently assumed

**Decision: no new policy-key check is added to `POST /exam-sessions/:id/certificate`.**
The candidate reaching `handle_issue_certificate/2` has already passed
`:ExamCertificateIssue` (`AuthorizedRouter`'s single per-route policy-key gate, §0's
citation of `authorized_router.ex:22-27`: `Letflow.Plugs.Authorize` runs once, at route
match, for every request reaching this router — there is no second, separate
authorization boundary to cross for a plain function call made *inside* an already
-authorized handler). `Letflow.PublicRead.issue_handle/4` itself performs no permission
check (§0) — enforcement is structurally the calling route's responsibility, and this
route's `:ExamCertificateIssue` gate already is that enforcement for this call, in the
same way `Letflow.Exam.Certificate.issue_or_fetch/4` already calls
`Letflow.Entities.Records.create_record/2` directly with no second permission check of its
own (the precedent this codebase already establishes for one authenticated context module
calling another's write function in-process).

**Consequence, stated explicitly rather than glossed over:** under this decision,
`:PublicReadHandlesIssue` (the policy key `Letflow.Routers.PublicReadHandles`'s own
moduledoc names) gains **no route consumer** from this requirement — no role is granted
it, and `POST /public-read-handles` remains reachable by nobody until some future
kind's issuance path chooses to go through that HTTP route instead of an in-process call.
This is flagged as OQ-4 (§8) for REVIEWER's real judgment, per the requirement's own
instruction that the A/B tradeoff be presented rather than asserted — the alternative
(granting the candidate's role `:PublicReadHandlesIssue` and additionally requiring it,
even though the call never traverses that router) would give the atom a nominal consumer
without changing what actually gates the mint, which reads as compliance-by-decoration
rather than a real second check; this design's recommendation is therefore to leave the
atom unconsumed here and let it acquire its first real consumer whenever a future kind's
issuance path is itself the generic HTTP route rather than an in-process call.

## 7. Rule-2 A/B analysis — for REVIEWER's real adjudication (AC-9)

**The honest question, stated by the requirement itself:** a projection is a hand-built
field allowlist over one record, and REQ-352's registration mechanism is explicitly
generic (`Application.fetch_env!/2` over a `{kind_string, module}` map) — so why is this
not a **declarative field allowlist in config** (e.g. `%{"certificate" => %{fields:
["candidate_name", "exam_title", "score_pct", ...], skip_when: {"deleted", true}}}`,
interpreted generically by `Letflow.PublicRead.resolve/2` itself) rather than a hand-built
Elixir module implementing a behaviour?

### 7.1 Argument for the declarative-config side

- `project/2`'s actual logic here is genuinely thin: read five fixed keys out of
  `field_values`, rename one (`"issued_at"` → `"issued_on"`), coerce one to float, and
  return `:skip` on one boolean field. Every step is expressible as data: a list of
  `{source_key, target_key}` pairs, one coercion tag, one `{field, value}` skip predicate.
  This is structurally identical in shape to `Letflow.Entities.Record.Validator`'s own
  field-list-driven validation, which is *already* declarative over a definition — so
  there is a real platform precedent for "read a JSON entity definition and derive
  behavior from it" existing one layer over in this exact vertical.
- REQ-352's own registration mechanism (`:public_read_kinds` config map) is *already* the
  generic, declarative half of this feature — a config-driven allowlist for the `data`
  sub-map would be a natural, small extension of a mechanism that already exists, not a
  new capability class.
- A config-only kind would remove an entire source file from the tree per kind, and would
  make adding the *second* kind (whatever it turns out to be) plausibly zero-code if its
  shape is equally thin — lowering the bar for future kinds is a real value, mirroring
  why REQ-323 made the *registration* itself generic in the first place.

### 7.2 Argument for the hand-built-module side (this design's recommendation)

- **The rename and the coercion are not incidental to this field set — they are the
  exact places a generic interpreter would need its own escape hatch, and every escape
  hatch reopens the config-vs-code question at a smaller scale.** `"issued_on"` is not a
  passthrough of `field_values["issued_at"]`'s *key* — it is a deliberate rename chosen in
  §2.3 specifically to avoid a name collision with the envelope's own top-level
  `"issued_at"` key, a judgment call about what a reader of raw JSON could confuse, not a
  mechanical field copy. `to_float/1`'s three-clause dispatch (`float`, `integer`,
  `Decimal`) already exists as executable code in `Letflow.Exam.Certificate` itself
  (`certificate.ex:360-362`) precisely because `score_pct`'s stored representation is not
  uniform — a declarative allowlist would need its own coercion vocabulary (a `:decimal`
  type tag, interpreted by *some* code, somewhere) to express this, which does not remove
  the code, it just moves it into a generic interpreter that now has to be right for
  every future kind's coercions at once, a harder review surface than one kind's own
  five-line function.
- **The publishability predicate is not a single static comparison a config format could
  express without inventing a predicate language.** `resource.deleted == true` happens to
  be one boolean field today, but req323 §4.4 defines the callback as "declines to
  publish" in the general case, not "checks one boolean" — a future certificate-adjacent
  refinement (e.g., a retracted-for-cause certificate distinguished from a merely-deleted
  one, or a predicate over more than one field) is exactly the kind of thing a hand-built
  function absorbs for free and a declarative allowlist would need a second config
  sub-language for. Building that sub-language now, for one predicate that is a single
  field-equality check today, is speculative generality of the same shape 0022 already
  warns against elsewhere in this stage (`docs/migration/stage-10-bilimbaga-vertical.md`'s
  own repeated pattern of declining a generic capability built for exactly one caller).
- **The behaviour (`schema/0` + `project/2`) already exists, is already shipped, and is
  already the abstraction boundary REQ-352/REQ-323 chose** — deliberately, and with
  REVIEWER's own prior sign-off recorded in decision 0028 ("Adopted on REVIEWER's
  recommendation: the projection contract is now a behaviour... rather than prose"). A
  declarative-allowlist alternative is not a small variation on that decision, it is a
  *different* decision about the same boundary, made by a different, later, single-kind
  requirement — reopening an already-reviewed platform decision on the strength of one
  instance's field set being simple is the reopening 0028 itself asks a later requirement
  not to do casually (`docs/migration/decisions/0028...md`'s own "load-bearing for every
  later stage" framing, applied here to REQ-352's, not just 0028's, own design choice).
  If a genuinely declarative pattern emerges once a second and third kind exist and are
  compared, that comparison — not this single instance — is the right moment to
  generalize (the same "second or third caller" test this stage's REQ-355 rule-2
  sign-off already applied to a different module, `docs/migration/
  stage-10-bilimbaga-vertical.md:785-796`).
- **§2.2's `resource_id`/primary-key substitution is executable reasoning, not a field
  mapping.** Nothing about *which* field of `Letflow.Entities.Record.Latest` a handle's
  `resource_id` must equal is expressible in the kind of config a declarative allowlist
  would carry — it is a fact about `Repo.get/3`'s semantics that this design had to
  derive by reading `Letflow.Entities.Record.Latest`'s own primary-key declaration and
  `Records.create_record/2`'s own `record_id`-vs-`id` distinction. A config format
  describing "which entity type" would not, by itself, prevent a future kind's author
  from repeating the exact mistake §2.2 warns against; a hand-built `schema/0` forces
  that reasoning to be re-done, consciously, per kind — which is the safer default for a
  security-reviewed disclosure surface.

### 7.3 Recommendation

**Keep the hand-built module.** The field-selection-and-rename part of `project/2` is,
conceded, thin enough that a declarative form could express it — but the publishability
predicate's open-ended future shape, the coercion logic already living as code one layer
up in this same vertical, and the primary-key substitution reasoning in §2.2 are not
declarative-shaped today and forcing them to be would either (a) invent a small predicate
/coercion sub-language inside `:public_read_kinds`' config for a benefit only visible once
a second kind exists, or (b) silently under-specify the predicate and coercion behavior
for whichever future kind's shape does not fit today's field set. Both costs are paid now,
for a savings (one fewer `.ex` file) that materializes only if a second kind turns out to
need nothing more expressive than this one does — which is not yet known. This is
REVIEWER's call to make, not this document's to finalize; the arguments above are stated
so that call is a real adjudication rather than a rubber stamp.

## 8. Open questions — stated, not silently resolved (AC-9's neighbors)

- **OQ-1.** `Letflow.PublicRead.resolve/2`'s round-trip 2 does not verify
  `entity_type == "certificate"` on the fetched `Letflow.Entities.Record.Latest` row
  (§2.2) — safe today because `id` is a global unique key across every entity type and
  only this kind's own wiring ever supplies a certificate's `id` as a handle's
  `resource_id`, but this reasoning is per-kind and must be re-derived, not assumed, by
  any future kind that also projects off `Letflow.Entities.Record.Latest`. Not this
  requirement's job to add the check (it would be a change to REQ-352's own generic
  `resolve/2`, out of this requirement's scope fence) — flagged for whichever future
  kind's design next relies on the same table.
- **OQ-2.** Certificate handles are minted with `expires_at: nil` (§5.3) — no expiry
  policy. REQ-357's own text does not decide this either way; a later requirement (or a
  REVIEWER note on this one) may want a stated retention/expiry policy for certificate
  links specifically, distinct from the pattern's generic `expires_at` mechanism, which
  this design merely declines to use rather than deciding is wrong to use.
- **OQ-3.** If `issue_handle/4` fails on first issuance (§5.3), no automatic retry path
  exists: the certificate record's own idempotent-replay branch (`first_issuance ==
  false` on every subsequent call) will never again attempt a mint, because the registry
  has no "does a live handle already exist for this resource" query (deliberately, per
  req323 §3.3 — no listing/lookup surface beyond exact-handle-match). A candidate whose
  first mint attempt failed has a certificate with no public link, permanently, unless a
  future requirement adds a recovery path. Not blocking for this requirement's acceptance
  criteria (none test this path), but a real gap a later reader should not assume was
  overlooked rather than considered.
- **OQ-4.** §5.5's permission-atom decision (no `:PublicReadHandlesIssue` consumer is
  created by this requirement) is this design's recommendation, not a foreclosed
  question — REVIEWER may instead conclude the atom should be actively granted and
  checked even for an in-process call, as defense in depth. Stated as open per the
  requirement's own instruction to present the real tradeoff rather than assert one side.

## 10. For SECURITY-REVIEWER (flagging the surface, not pre-adjudicating it)

This is a tenant-data-path change under decision 0028's own naming ("the first
`/api/public` instance is... a named SECURITY-REVIEWER hard gate") — but the mechanism
being gated is entirely REQ-352's, already reviewed. What is genuinely new here, and what
SECURITY-REVIEWER's re-review should focus on:

1. **INV-2** — §2.3's field table is the substance of this gate, per the requirement's
   own framing. The `branding_snapshot` row is the one this design flags as needing the
   closest look (it is a deliberate divergence from req323 §4.4's generic "no tenant
   display name" default, justified by the `/api/tenant-config` precedent already
   disclosing the same map unauthenticated).
2. **INV-1** — not re-litigated; §2.2's `resource_id` substitution is a correctness
   concern (does the query find the right row?), not a scoping concern (the `prefix:`
   derivation is unchanged, still fed by the handle's own `tenant_id` column, still never
   caller-supplied).
3. **INV-5** — the publishability predicate (§2.3) is the one new case-7 mechanism; it is
   a single boolean read with no query and no branch that could vary round-trip count,
   so it does not disturb REQ-352's existing round-trip discipline.
4. **INV-4** — no new plaintext-handle handling; §5.3's `"public_handle"` field is
   returned once, over the *authenticated* channel, by the same writer that already
   returns it once (`issue_handle/4`'s own contract, unchanged) — not logged, not
   persisted a second time.
