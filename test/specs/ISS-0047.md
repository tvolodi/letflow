# Test Spec: ISS-0047 — `insert_or_fetch/4`'s `on_conflict` only arbitrates the `(external_realm, external_id)` index, not `users.username`

**Issue:** `docs/issues/ISS-0047.yaml` (severity: MINOR, tags: identity, concurrency,
pre-existing). **Design:**
`lib/letflow/design/iss-0047-username-race-conflict-target.md`. **Fix:**
`lib/letflow/identity.ex` (`insert_or_fetch/4`'s `{:error, %Ecto.Changeset{}}` branch,
plus new private helpers `username_unique_conflict?/1`, `get_by_username/2`,
`identity_matches?/2`), commit `548c338`.

## Criterion (from the design's §5)

Two genuinely independent Postgres connections racing to provision the **identical**
`(external_realm, external_id)` + identical `preferred_username` identity must both
resolve to `{:ok, %{user: ..., created: _}}` for the **same** underlying user id —
never `{:error, %Ecto.Changeset{}}` for either racer — because Postgres's own
unique-index conflict-check ordering nondeterministically raises on either the
`(external_realm, external_id)` arbiter (already handled, pre-existing) or the
separate `users.username` unique index (the ISS-0047 gap: not the named
`conflict_target:` arbiter, so `on_conflict: :nothing` never suppressed it, and the
resulting changeset error was — before this fix — always treated as a permanent
failure instead of being checked against the possibility that the "conflicting"
username-holder is this call's own race opponent).

## Test case: `test/letflow/identity_test.exs` — describe "provision_oidc_user/4 — ISS-0047 regression: username-index race resolves cleanly"

**Why this test exists (not just a restatement of the criterion):** the project's
existing REQ-018 acceptance-criterion-3 race test (`identity_test.exs` lines 259-355)
cannot exercise this bug at all — it deliberately uses `:manual` sandbox mode +
`Sandbox.allow/3`, which routes both racing `Task`s through **one shared
connection/transaction**, serializing the two `INSERT`s so Postgres's own
per-connection conflict-check ordering (the thing ISS-0047 depends on) never has a
chance to vary. A genuinely new mechanism — two independently checked-out `:auto`-mode
connections — is required to reproduce the bug and prove the fix, per the design's §5
guidance. This is why the fix couldn't have been caught by the pre-existing suite and
why a dedicated regression test is needed rather than extending the existing race
test in place.

**Nondeterminism handled by looping, not by a single run:** ISSUE-FIXER's own
reproduction against real Postgres hit the bug 4/6 runs, not 6/6 — a single race
attempt is not adequate evidence either that the bug exists (pre-fix) or that the fix
holds (post-fix) reliably. The test loops 10 independent race attempts within one
`test`, each attempt using a **freshly generated** `identity_context()` (unique
`realm`/`external_user_id`/`preferred_username` per attempt via the existing
`identity_context/1` helper) so no attempt's outcome can be masked or contaminated by
a previous attempt's already-committed row. Each attempt re-runs the full
barrier-synchronized two-`Task` race (reusing the existing race test's
`send(parent, {:ready, ...})` / `receive do :go end` barrier pattern, lines 284-301,
so both tasks reach `provision_oidc_user/4`'s own select-first step at effectively the
same wall-clock instant rather than being serialized by `Task.async/1`'s own
scheduling) and asserts, per attempt:

- both `Task` results are `{:ok, %{user: %User{id: _}, created: _}}` — never
  `{:error, %Ecto.Changeset{}}` for either racer (this is the core ISS-0047 proof:
  before the fix, a `username`-index-losing racer surfaced exactly that changeset
  error instead of resolving cleanly).
- both results carry the **same** `user.id`.
- exactly one of the two `created` flags is `true`.
- exactly one row exists in `users` afterward for that attempt's `(external_realm,
  external_id)`.

**Mechanism, and why it differs from the existing race test:** `provisioned_tenant!/0`
(called once before the loop) already puts `Ecto.Adapters.SQL.Sandbox` in `:auto`
mode for its own migration-replay step (existing file convention, see this file's
moduledoc). Unlike the existing REQ-018 race test, this new test **does not** switch
back to `:manual` mode + `Sandbox.allow/3` afterward — it stays in `:auto` mode for
the race itself, so each spawned `Task` gets its own independently-checked-out
connection automatically, which is the exact "two genuinely independent Postgres
connections" setup the design's §5 specifies as required to exercise this bug at all.
