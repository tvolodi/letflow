# Test Spec: ISS-0048 — `Letflow.SandboxPool` owner-crash/kill reclaim

**Issue:** `docs/issues/ISS-0048.yaml` (the `SandboxPool` half, per ISSUE-FIXER's
scoping — `handoffs/WF03-ISS0048-20260818/step-01-issue-fixer.json`'s `result.summary`).
**Design:** `lib/letflow/design/iss-0048-sandbox-pool-owner-crash-reclaim.md`.
**Fix:** `lib/letflow/sandbox_pool.ex` (`handle_provision_now/2`,
`service_next_waiter/1`, `handle_call({:release, ...})`, and a new
`handle_info({:DOWN, ref, :process, _pid, _reason}, state)` branch dispatching to a new
`find_active_by_owner_ref/2` helper), commit `ef1e4c8` (plus the same-process
claim/release contract rework in `729e7b4`).

## Criterion (from the design's INV-SP-DOWN-2, §5.4, and the handoff's §10.1)

A claim whose owning process — the process that called `SandboxPool.claim/2` — dies for
**any exit reason** (a hard kill, a linked-crash propagation, an ExUnit-timeout kill)
before calling `SandboxPool.release/2` must be reclaimed automatically: its Postgres
schema dropped and its quota slot freed for a subsequent `claim/2`, within one
message-passing round-trip of Erlang delivering the `:DOWN` message. Before this fix,
`try/rescue` — the only safety net that existed — never runs on an `exit` signal, only
on a raised exception, so a killed owner's schema and quota slot leaked forever (the one
live orphan `sandbox_5050499590a9426186656f72f7296622` ISSUE-FIXER reproduced).

## Test case: `test/letflow/sandbox_pool_test.exs` — describe "owning process killed between claim/2 and release/2 (ISS-0048 regression)"

**Why this test exists (not just a restatement of the criterion):** every existing test
in this file either calls `release/2` itself on the happy path, or lets `claim/2` time
out via the pre-existing `:claim_timeout` mechanism (a *queued waiter* never receiving a
slot) — neither exercises an already-*granted* claim's owner dying. Critically, this
test uses `Process.exit(owner_pid, :kill)`, **not** a raised exception: `try/rescue`
(the pre-fix safety net, still present and unchanged in
`Letflow.Definitions.run_replay_span/8`) already handles a raised exception correctly —
a test that raised inside the owner process would pass identically before and after
this fix and would prove nothing about the actual gap ISS-0048 identifies. Only a real
`exit` signal reaches the code path this fix adds.

The claim is made from a `spawn/1`-ed process (not the test process, and not
`Task.async/1` — `Task`'s own normal-return exit is already exercised by this file's
pre-existing "a queued waiter is served" test and is a *different*, already-correct
code path once the same-process claim/release contract rework landed in `729e7b4`).
The spawned process claims, relays the claim back to the test process via a
`send/receive` rendezvous (avoiding any race between "the claim succeeded" and "the
test process proceeds"), then blocks forever in a `receive` with no matching clause —
so it never calls `release/2`, and is still alive, still holding the claim, at the
moment the test kills it.

Assertions, in order:

1. Before the kill: the schema physically exists in `information_schema.schemata`, and
   the pool (`max_concurrent: 1`) is genuinely quota-exhausted (`claim(0, pool)` returns
   `{:error, :sandbox_unavailable}`) — so the later "slot freed" assertion isn't vacuous.
2. `Process.exit(owner_pid, :kill)`, confirmed delivered via a `Process.monitor/1` +
   `assert_receive {:DOWN, ..., :killed}` on the *test's* own monitor of the owner (not
   `SandboxPool`'s internal one) — proof the kill genuinely happened, independent of
   whether the fix under test correctly reacts to it.
3. **Core regression assertion:** polls (`wait_until_schema_dropped/2`, matching this
   file's existing `wait_until_waiter_queued/2` bounded-polling idiom, up to 2s) until
   the schema no longer exists in `information_schema.schemata`, then asserts it via a
   direct `refute schema_exists?/1` — a real Postgres query, not an inferred return
   value.
4. A subsequent `claim(1_000, pool)` against the still-`max_concurrent: 1` pool
   succeeds immediately and produces a **different** `sandbox_id` — proof the `active`
   map entry itself (not just the physical schema) was removed, i.e. the quota slot was
   genuinely freed, not merely that an orphaned schema was dropped by some unrelated
   path.
