# Test Spec: ISS-0050 — `DropLegacyPublicIdentityTables` guard crashes with `42P01` on a tenant schema missing an identity table

**Issue:** `docs/issues/ISS-0050.yaml`. **Diagnosis:**
`handoffs/WF03-ISS0050-20260818/step-01-issue-fixer.json` (ISSUE-FIXER, root cause).
**Design:** `lib/letflow/design/iss-0050-drop-legacy-guard-missing-table.md`.
**Fix:** `priv/repo/migrations/20260819000004_drop_legacy_public_identity_tables.exs`
(the guard `DO $$` block — a `to_regclass(format('%I.<table>', schema_name)) IS NULL`
existence check now precedes each per-table dynamic `EXECUTE format(...)`), commit
`cf4c064`.

## Criterion (from the handoff's acceptance criteria)

A `public.tenant_schemas` row whose physical schema is missing one or more of
`groups`/`users`/`tenant_role` (e.g. `TenantProvisioning.provision_tenant_schema/1`
ran but `replay_migrations/2` did not finish for that tenant, or a leaked/incomplete
fixture row from an interrupted test process — ISSUE-FIXER's diagnosis traced a live
example of exactly this shape) must no longer crash the
`DropLegacyPublicIdentityTables` guard with `** (Postgrex.Error) ERROR 42P01
(undefined_table)`. Instead, the guard must treat the missing table as "copy not
verifiable for this tenant" — `RAISE NOTICE` and fold it into the existing
`v_all_copied := FALSE` skip-the-drop path, the same conservative behavior the guard
already applies to the "row exists in `public` but not copied to the tenant schema"
case.

## Test case: `test/letflow/identity_migration_test.exs` — describe "DropLegacyPublicIdentityTables migration guard (REQ-063 §5) -- skip-on-uncopied-row", test "ISS-0050 regression: a tenant schema missing one identity table makes the guard SKIP the drop, not raise 42P01" (line 407)

**Why this test exists (not just a restatement of the criterion):** every pre-existing
test in this describe block exercises the guard's *row-level* copy-completeness check
(a row present in `public.<table>` but absent from the tenant's own copy) — none of
them ever produce a tenant schema that is missing an entire table object. The ISS-0050
bug is a distinct failure mode entirely: it is not about row parity at all, it is about
Postgres needing to resolve `%I.groups`/`%I.users`/`%I.tenant_role` to a real relation
at **parse time** the moment the dynamic `EXECUTE format(...)` runs, regardless of
whether the `WHERE` clause would match any rows — so a genuinely absent table crashes
the guard even with zero relevant `public` rows in play. Without this test, nothing in
the suite would ever construct a tenant schema in that "provisioned but not fully
replayed" physical shape, so the bug (and any future regression of the fix) would go
undetected.

**Mechanism:** provisions a real tenant via the file's existing `provisioned_tenant!/0`
helper (real schema, full migration replay — so `groups`/`users`/`tenant_role` all
genuinely exist in the tenant schema to start), then directly
`DROP TABLE IF EXISTS "<schema>".groups CASCADE` to reproduce the exact physical shape
ISSUE-FIXER's diagnosis found live in the shared test database (a `tenant_schemas`
registry row + a real, `CREATE SCHEMA`'d schema, missing one of the three identity
tables) without needing to fabricate a whole interrupted-`replay_migrations/2` code
path. Runs the drop migration via the same `Ecto.Migrator.run/4` mechanism the file's
other guard tests already use, and asserts:

- the `Ecto.Migrator.run/4` call itself completes normally and returns `[version]` —
  it must not raise (`Postgrex.Error` or otherwise).
- all three legacy `public.groups`/`public.users`/`public.tenant_role` tables still
  exist afterward (`to_regclass('public.<table>')` is non-`NULL`) — the guard skipped
  the drop, matching its own "an incomplete copy for even one tenant/table" skip
  discipline.

Cleanup: `provisioned_tenant!/0`'s own `on_exit` (schema `DROP SCHEMA ... CASCADE` +
`tenant_schemas`/`tenants` row deletes) already covers the provisioned tenant; this
test additionally registers its own `on_exit` to delete the
`schema_migrations` row for its migration-run `version` (same pattern as every other
test in this describe block). No new orphaned state is left behind — verified directly
against the live database after the fail-then-pass run below (see that section).
