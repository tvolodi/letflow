# Test Spec: ISS-0056 — `:HUMAN_TASK` edge-condition permission + fallback-edge validation (CHK-14 loosened, new CHK-19)

**Issue:** `docs/issues/ISS-0056.yaml`.
**Design:** `lib/letflow/design/iss-0056-human-task-fallback-edge-validation.md`.
**Fix:** `lib/letflow/definitions/graph.ex`, commit `0f8bd06` on
`feature/WF03-ISS0056-20260818` — `check_non_gateway_condition_absence/1` (CHK-14)
renamed to `check_unpermitted_edge_condition/1` and re-guarded to also permit a
`:HUMAN_TASK`-sourced edge to carry a condition (new `human_task_source?/3` helper);
new `check_human_task_fallback_edge/1` (CHK-19, violation code
`:human_task_no_fallback_edge`) requiring a `:HUMAN_TASK` node with any
"really-conditioned" outgoing edge to also have at least one fallback-candidate
outgoing edge.
**Test tier:** unit (pure module, no I/O — same tier as the rest of `graph_test.exs`).

## Criteria (from the design doc §11's acceptance-criteria traceability table)

1. Loosen CHK-14 to also permit real conditions on `:HUMAN_TASK`-sourced edges.
2. Add CHK-19: a `:HUMAN_TASK` node with any really-conditioned outgoing edge must have
   at least one fallback-candidate outgoing edge, else `:human_task_no_fallback_edge`.
3. CHK-14's original protection (non-gateway, non-HUMAN_TASK sources still forbidden
   from carrying a condition) must remain intact — no over-permission of a third
   source type.
4. The single-edge, no-condition case, and the single-edge, really-conditioned,
   no-fallback case (design doc §6's edge-case table), are both covered explicitly,
   since the second has no precedent in CHK-13/16 and is easy to get backwards.

## Test cases — `test/letflow/definitions/graph_test.exs`, describe `"validate_edge_conditions/1 — ISS-0056: HUMAN_TASK condition permission"`

1. **"a single conditioned, non-default HUMAN_TASK edge is now permitted (regression
   fix)"** — proves criterion 1: this is the load-bearing case ISS-0056 exists to fix.
   Before the fix, CHK-14 forbade a condition on *any* non-gateway source, which blocked
   REQ-048's entire conditioned-task-completion feature outright, not just the
   "multiple conditions, no fallback" case named in the issue text. Includes a fallback
   edge so this test isolates CHK-14's permission from CHK-19's separate requirement.

2. **"two really-conditioned HUMAN_TASK edges, no fallback -> :human_task_no_fallback_edge
   fires (ISS-0056 reproduction)"** — proves criterion 2, and is the literal scenario
   filed in ISS-0056 (discovered during REQ-048's review): a `:HUMAN_TASK` with 2+
   conditioned edges and nothing to resolve to if every condition evaluates false at
   `complete_task/3` time. Without CHK-19 this graph passes validation and only fails
   much later, at runtime, in production.

3. **"two really-conditioned HUMAN_TASK edges plus an is_default: true fallback ->
   valid"** — proves CHK-19 does not over-fire on the legal, intended shape: REQ-048's
   own target scenario (multiple conditions + one explicit fallback edge). Without this
   case, a CHK-19 implementation that always fires on 2+ conditioned edges (ignoring
   whether a fallback exists) would pass test case 2 but incorrectly reject valid graphs.

4. **"two really-conditioned HUMAN_TASK edges plus an implicit (non-default,
   blank-condition) fallback -> valid"** — proves the fallback-candidate predicate
   accepts an *implicit* fallback (blank/nil condition, not explicitly marked
   `is_default: true`), matching `really_conditioned?/1`'s own implicit-fallback
   semantics in `transition.ex`. Without this case, an over-strict CHK-19
   implementation requiring `is_default: true` specifically would reject a legitimate,
   already-correctly-handled-at-runtime graph shape.

5. **"single HUMAN_TASK edge, blank condition -> no CHK-19 violation (the common
   case)"** — proves CHK-19 doesn't fire on the everyday single-unconditioned-edge
   shape (design doc §6 row 2). Guards against an implementation that treats "any
   outgoing edge" rather than "any *really-conditioned* outgoing edge" as CHK-19's
   trigger.

6. **"single HUMAN_TASK edge, real condition, not default -> CHK-19 fires (no
   precedent in CHK-13/16, §6 row 1)"** — proves the single-edge case is *not* treated
   as automatically legal just because there's "nothing else to conflict with." This is
   explicitly flagged in the design doc as a genuinely new invariant (neither CHK-13 nor
   CHK-16 requires an `:EXCLUSIVE_GATEWAY` to have a default/fallback edge to exist at
   all) — worth its own test given how easy this boundary is to get backwards (a
   plausible-looking-but-wrong implementation might special-case "only one edge" as
   always valid).

7. **"a SERVICE_TASK source with a condition still fires :unexpected_edge_condition
   (CHK-14's original guard intact)"** — proves criterion 3: a regression guard
   confirming the broadened CHK-14 guard did not accidentally over-permit a third
   source type beyond `:EXCLUSIVE_GATEWAY`/`:HUMAN_TASK`. Without this, a
   too-permissive rewrite of CHK-14's condition (e.g. `edge.condition != nil` guard
   dropped entirely by mistake) would silently pass every source type.
