# Test Spec: ISS-0059 — Collision-proof tenant slug suffix across 30 test files

**Issue:** `docs/issues/ISS-0059.yaml`.
**Design:** `lib/letflow/design/iss059-flaky-slug-collision-fix.md`.
**Fix:** `test/support/tenant_slug.ex` (new `Letflow.TenantSlugFixture.unique_slug/1`),
commit `6b84c1a` on `feature/WF03-ISS0059-20260819` — replaces each of 30 affected
`insert_tenant!/0`-style helpers' `"<prefix>-#{System.unique_integer([:positive,
:monotonic])}"` slug expression with `Letflow.TenantSlugFixture.unique_slug(<prefix>)`,
an `Ecto.UUID.generate/0`-derived suffix.
**Test tier:** unit (pure functions, no `Letflow.Repo`/`Ecto.Sandbox` dependency) +
property (`StreamData`).

## Bug recap

`System.unique_integer([:positive, :monotonic])`'s uniqueness guarantee is scoped to a
single BEAM VM run, not across runs. Every one of the 30 affected files runs
`Ecto.Adapters.SQL.Sandbox.mode(Letflow.Repo, :auto)` (real, non-rolled-back commits) in
at least one code path. If a prior `mix test` invocation crashed or was killed before
its `on_exit` cleanup ran, a `tenants` row survives with a slug like `"req027-1"`. The
next `mix test` VM's counter restarts from a low value (observed: `1`, every time — see
test case 1 below) and can regenerate that exact slug, colliding against
`tenants_slug_index` (`Ecto.InvalidChangesetError`).

## Criteria (from the design doc)

1. The new shared helper `Letflow.TenantSlugFixture.unique_slug/1` returns
   `"<prefix>-<UUID>"`, collision-proof across VM restarts because it is not derived
   from any in-process counter or wall-clock value that resets.
2. The fix must be shown to address a real, reproducible bug — not just a happy-path
   test of the new helper's shape.

## Test cases — `test/support/tenant_slug_test.exs`

1. **"three independent, freshly-started BEAM VMs produce the identical first
   unique_integer/1 value -> identical slug"** — proves the bug is real and
   mechanically reproducible, not hypothetical. Spawns three genuinely separate OS
   processes (`System.cmd("elixir", ["-e", ...])`), each a fresh BEAM VM, each
   computing the exact expression the pre-fix `insert_tenant!/0` helpers used as their
   very first `unique_integer` call. All three produce the same value (observed `1` in
   every local run), so the derived slug `"req027-1"` is identical across all three
   "VM runs" — precisely the collision ISS-0059 describes against a real unique index.

2. **"three independent, freshly-started BEAM VMs each computing unique_slug/1 produce
   three distinct slugs"** — the same spawn-independent-VMs method applied to the
   post-fix mechanism (`mix run --no-start -e 'Letflow.TenantSlugFixture.unique_slug(...)'`
   in three separate OS processes), proving criterion 1: unlike the counter, the UUID
   suffix does not repeat across VM restarts, because `Ecto.UUID.generate/0`'s
   randomness carries no in-process state to reset.

3. **"generating thousands of slugs from arbitrary prefixes never produces a
   duplicate"** — `StreamData` property test, 2,000 generated prefixes in one run,
   asserting zero collisions among the resulting slugs. Standing in for what a
   thousand-VM-restart fuzz run would show, without needing to actually spawn
   thousands of OS processes.

4. **"unique_slug/1 always returns `<prefix>-<36-char UUID>`, never depending on call
   order or repetition count"** — property test asserting the shape invariant
   (`<prefix>-` prefix, correct total length) and no-collision holds for 1–25 calls per
   prefix across 30 randomized `(prefix, repeat_count)` pairs, guarding against an
   implementation that happens to pass case 3's single large batch by luck of the
   generator's shrinking/ordering.

## Coverage check

- [x] Every acceptance criterion above has ≥1 test case listed.
- [x] Property test included (case 3, 4) per the state/invariant-space size (all
      possible prefixes × arbitrary call counts) being far too large for example-based
      tests alone to give confidence.

## Fail-then-pass verification (WF-03 Step 4 regression-test requirement)

This bug class (a monotonic in-process counter's guarantee being scoped to a single VM
run) cannot be reproduced by the usual "run the same test file against a pre-fix
*implementation* of the same function" method, because the pre-fix code has no
`unique_slug/1` function to call at all — the fix is the introduction of a new shared
helper, not a behavior change to an existing one. Two different, real (not simulated)
verifications were used instead:

**1. Pre-fix commit check — the helper genuinely does not exist before the fix.**

```
$ git show ee8fc38:test/support/tenant_slug.ex
fatal: path 'test/support/tenant_slug.ex' exists on disk, but not in 'ee8fc38'
$ git diff --stat 6b84c1a^ 6b84c1a -- test/support/tenant_slug.ex
 test/support/tenant_slug.ex | 24 ++++++++++++++++++++++++
 1 file changed, 24 insertions(+)
```

`ee8fc38` is `6b84c1a`'s (this branch's fix commit) direct parent. Confirms
`test/support/tenant_slug_test.exs` (this spec's test file) would fail to compile
at all against the pre-fix tree — `Letflow.TenantSlugFixture` is undefined there.

**2. Mechanism-level fail-then-pass, verified live in this run** — since a
git-checkout comparison for this specific bug class only proves "the module didn't
exist yet" (true but not illuminating about *why* the fix works), test cases 1 and 2
above directly construct and run both the pre-fix mechanism (bare
`System.unique_integer([:positive, :monotonic])`, spawned across independent fresh
VMs) and the post-fix mechanism (`unique_slug/1`, spawned the identical way) side by
side, in the same test file, in the same run:

```
$ mix test test/support/tenant_slug_test.exs --seed 0
...
Finished in 2.8 seconds (2.8s async, 0.00s sync)
2 properties, 2 tests, 0 failures
```

Test case 1 passing means the assertion `Enum.uniq(slugs) == [hd(slugs)]` held — i.e.
the pre-fix mechanism's three independent "VM runs" *did* collide, which is the bug
being reproduced, mechanically, live, every time this test runs (not a one-off
observation). Test case 2 passing means the post-fix mechanism's three independent "VM
runs" did *not* collide. Together these two tests are the fail-then-pass proof for
this bug class: the same assertion shape (three independent VMs, compare resulting
slugs) fails to distinguish the VMs under the old mechanism (they're identical — that
IS the failure) and succeeds under the new one (they're distinct).

This is the honest alternative the WF-03 procedure allows when a literal
pre-fix-commit-vs-post-fix-commit re-run isn't informative for the bug class at hand:
both mechanisms are proven, live, in the same run, using OS-process-level real VM
restarts rather than any in-process simulation.
