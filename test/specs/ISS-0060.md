**Fix:** `test/letflow/identity_migration_test.exs` — new `with_only_this_tenant_visible!/2`,

**Test tier:** integration (real Postgres, `Letflow.DataCase`, `async: false` — matches the

## Bug recap

The drop migration's guard does a global scan over `public.tenant_schemas` (every
registered tenant, not just the one under test). Under full-suite concurrency, another
test's tenant can be mid-provisioning (`migrations_applied_at: nil`) at the exact moment
the guard-PROCEEDS test runs its `Ecto.Migrator.run/4` call — the guard sees that
unrelated, genuinely-incomplete row and folds it into `v_all_copied := FALSE`, flipping a
correct PROCEED into a false SKIP. Two prior recurrences (ISS-0048, ISS-0050) of this same
test/line were already marked `resolved`; this is a third recurrence, same root shape,
confirmed not caused by the run that discovered it (`docs/issues/ISS-0060.yaml`'s
`description` field lists the full innocent-diff evidence).

## Why this is a RACE, not a deterministic bug — and what that means for proof strategy

Unlike a typical bug, there is no deterministic input that reproduces the failure through
the *existing* code path alone — the false SKIP only happens when genuine suite-level
concurrency happens to schedule another tenant's provisioning mid-flight during this one
test's guard call. A test cannot reliably force that timing without either (a) actually
running the full suite many times and hoping to catch it (slow, still probabilistic, not a
real regression test), or (b) directly constructing the exact database state the race
produces and testing the mechanism against that state deterministically. This spec uses
(b), the same standard applied to ISS-0059 (see `test/specs/ISS-0059.md`'s own "Bug recap"
and fail-then-pass sections) — a race-condition-class bug gets its race window
mechanically reconstructed and tested against, rather than a fabricated fail-then-pass
narrative pretending timing was actually reproduced.

## Fail-then-pass achievability (WF-03 Step 4) — stated honestly

**Not achievable as a literal pre-fix-code-vs-post-fix-code re-run**, for the same reason
ISS-0059 wasn't: the fix is the *introduction* of new helpers
(`with_only_this_tenant_visible!/2`, `ensure_backup_table!/0`,
`restore_orphaned_guard_backup_rows!/0`) into the test file itself, not a behavior change
to an existing, independently re-runnable function. The pre-fix commit
(`git log --oneline -1 1ef4ba4^` → `cfd73a4`) has no `with_only_this_tenant_visible!/2` at
all — checking it out and running a test that calls it would fail to *compile*, which is
uninformative in the same way ISS-0059's spec already documented ("proves the module
didn't exist yet, not why the fix works").

```
$ git show cfd73a4:test/letflow/identity_migration_test.exs | grep -c with_only_this_tenant_visible
0
$ git show 1ef4ba4:test/letflow/identity_migration_test.exs | grep -c with_only_this_tenant_visible
4
```

Confirms the helper is genuinely new in the fix commit, not a pre-existing function this
spec could re-target at the old commit.

**Mechanism-level fail-then-pass, verified live, in the same test, in the same run** — the
honest substitute (test case 1 below): the exact database state the race produces is
constructed directly (a second, real, FK-satisfying tenant row with
`migrations_applied_at: NULL`, sitting in `public.tenant_schemas` — indistinguishable to
the guard's SQL from a genuinely concurrently-provisioning tenant), and the SAME guard SQL
is run twice against that SAME fake row: once unwrapped (proving the false SKIP is real
and mechanically reproducible on demand, not hypothetical) and once wrapped in the fix
(proving the fix's mechanism — hiding other tenants' rows for the call's duration —
actually changes the outcome from SKIP to PROCEED). This is a real fail/pass pair using the
production migration's own guard logic, not a rewritten toy version of it.

## Test cases — `test/letflow/identity_migration_test.exs`

1. **"ISS-0060: unwrapped guard SKIPs with a racer tenant visible; `with_only_this_tenant_visible!/2` hides it and the guard PROCEEDS"**
   (in the existing `"DropLegacyPublicIdentityTables migration guard (REQ-063 §5) --
   skip-on-uncopied-row"` describe block). Provisions and fully copies one real tenant
   (guard should PROCEED for it in isolation), then inserts a second real tenant's
   `tenant_schemas` row directly with `migrations_applied_at: NULL` — the exact race
   condition. Step 1 runs the guard unwrapped against that state and asserts all three
   legacy tables SURVIVE (the false SKIP, reproduced live). Step 2 runs the guard again,
   wrapped in `with_only_this_tenant_visible!/2`, against the identical still-present fake
   row, and asserts all three tables are DROPPED. Finally asserts the fake row is restored
   to `public.tenant_schemas` (unchanged, `migrations_applied_at` still `NULL`) and the
   backup table is empty — the exact behavior the pre-fix code had no mechanism for (it
   never moved anything, so it never needed to restore anything, and never did).

2. **"ISS-0060: self-heal of an interrupted `with_only_this_tenant_visible!/2` run" —
   `restore_orphaned_guard_backup_rows!/0` restores a stale backup row to
   `public.tenant_schemas` and empties the backup table"**. Directly constructs the crash
   window design section 5 describes: a row sitting in
   `public.iss060_tenant_schemas_guard_backup` with no corresponding row in
   `public.tenant_schemas` (simulating a BEAM crash between the move-out and move-back
   statements). Calls `restore_orphaned_guard_backup_rows!/0` — the exact private helper
   this file's own `setup` block invokes before every test — directly (a fresh stale row
   could only be constructed *after* this test's own `setup` had already run once, so
   calling the helper directly here is equivalent coverage of the same code path `setup`
   exercises on a later test run). Asserts the row reappears in `public.tenant_schemas`
   and disappears from the backup table.

   Checked whether ELIXIR-DEV's implementation step left behind a committed scratch-test
   version of this proof: no `handoffs/*ISS-0060*` or `test/support` fixture exists for it
   (`find handoffs -iname "*0060*"` returns nothing) — this is the first and only committed
   version of the self-heal proof.
