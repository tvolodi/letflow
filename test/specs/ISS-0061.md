# Test Spec: ISS-0061 — Duplicate migration version `20260819000001` blocks `mix ecto.migrate`/`mix test`

**Issue:** `docs/issues/ISS-0061.yaml`. **Fix:** commit `75d0452` on this branch, which
renames `priv/repo/migrations/20260819000001_drop_transition_events.exs` to
`20260819000005_drop_transition_events.exs`, resolving the collision with the
independently-merged `20260819000001_create_groups_tenant_scoped.exs`.

## Criterion (from the issue)

No two files under `priv/repo/migrations/` may share the same leading Ecto migration
version number. Two independently-merged files sharing a version
(`20260819000001_create_groups_tenant_scoped.exs` from REQ-063/Decision 0006 D1, and
`20260819000001_drop_transition_events.exs` from REQ-046/#199) made
`Ecto.Migrator` raise `Ecto.MigrationError: migration version 20260819000001 is
duplicated`, which fails `mix ecto.migrate` and, transitively, `mix test` (it runs
migrations against the sandbox DB before any test body executes) — for every host
working the shared backlog, not just the one that first hits the collision.

## Test case: `test/letflow/migration_filenames_test.exs` — describe "priv/repo/migrations/ version prefixes", test "no two migration files share the same leading version number"

**Why this test exists (not just a restatement of the criterion):** nothing else in
the suite inspects `priv/repo/migrations/` as a set — every other migration-adjacent
test (`test/letflow/definitions/migrations_test.exs`,
`test/letflow/engine/migrations_test.exs`, etc.) verifies what one specific migration
*does* once applied, none of them verify a *structural* property of the migrations
directory as a whole. The ISS-0061 bug is exactly a structural property violation (a
naming/id collision across two files that individually compile and individually apply
fine), the same collision class already on record in `docs/anti-patterns.md` for
module names and `docs/issues/ISS-NNNN.yaml` entries — this is its first occurrence
against a migration version number. Per the anti-patterns entry's own framing ("worth
its own anti-patterns entry once fixed... since Ecto's own duplicate-version guard is
what caught it here"), a fast, DB-free, always-running check catches this before
`mix ecto.migrate` does, and before a second host on this 4-host backlog can hit it
again independently. A second test in the same file
("every migration filename starts with a purely numeric version prefix") guards the
adjacent malformed-filename case so a future rename typo (e.g. a stray non-numeric
prefix) fails loudly here too, rather than surfacing as a confusing `Ecto.Migrator`
ordering issue instead.

**Mechanism:** pure filesystem/string test, no database — lists `priv/repo/migrations/
*.exs`, splits each filename on the first `_` to extract its numeric version prefix
(`docs/guides/test_developer_guide.md` "Pure functions first": this is a static
property of files on disk), groups by version, and asserts no group has more than one
member. On failure, the assertion message names every colliding file explicitly (not
just "duplicate found"), matching the acceptance criterion in this handoff's
instructions.
