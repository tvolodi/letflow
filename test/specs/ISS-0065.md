# Test Spec: ISS-0065 — Route cross-VM test scripts through temp files, not `-e`

**Issue:** `docs/issues/ISS-0065.yaml`.
**Design:** `lib/letflow/design/iss065-windows-cmd-script-tempfile-fix.md`.
**Fix:** `test/support/tenant_slug_test.exs` — new private `write_script_and_run/2`
helper, commit `f90919f` on `feature/WF03-ISS0065-20260819`. Replaces both VM-spawning
`System.cmd/3` call sites' inline `-e <script>` argv element with a plain temp-file-path
argv element, with guaranteed `try/after` cleanup.
**Test tier:** unit (AST inspection of this file's own source, no I/O) + integration
(real OS-process subprocess spawning, already the existing style in this file).

## Bug recap

On Windows, `mix`/`elixir` resolve to `mix.bat`/`elixir.bat`, invoked implicitly through
`cmd.exe`. `cmd.exe` re-parses argv and mis-splits an inline `-e <script>` element that
contains `(`, `)`, `"` — both scripts in this file contain these characters — producing
`{"", 255}` and a `"...) was unexpected at this time."` parse error. Confirmed
platform-specific: both affected tests pass 4/4 on Linux (`mix`/`elixir` are real
executables there, not `.bat` wrappers), so this fix cannot be demonstrated failing on
this host by simply re-running the old mechanism — see "Fail-then-pass verification"
below for how the boundary is proven instead.

## Criteria (from the design doc's "Acceptance criteria" section)

1. Both tests still spawn genuinely independent, fresh OS-process BEAM VM subprocesses
   per loop iteration — `write_script_and_run/2` must not memoize or short-circuit.
2. `test "collides across three fresh VMs"` still asserts the pre-fix mechanism
   produces 3 identical slugs — assertion content unchanged.
3. `test "distinct slugs across three fresh VMs"` still asserts the post-fix mechanism
   produces 3 distinct, correctly-prefixed slugs — assertion content unchanged.
4. `mix test test/support/tenant_slug_test.exs --include slow` passes on this Linux
   host after the change.
5. No temp file is left behind in `System.tmp_dir!/0` after a full test run, including
   under a deliberately-forced failing-subprocess case (design doc: "not required...
   since the try/after cleanup is unconditional... — see Cleanup semantics").
6. Windows execution itself cannot be verified from this host — the bar is
   "correct per `System.cmd/3`'s documented Windows argument-splitting behavior" plus
   "passes on Linux," not "verified on an actual Windows machine."
7. No change to `test/support/tenant_slug.ex` or any file under `lib/letflow/`.

Criteria 1-4 and 7 are unchanged pre-existing behavior of the two tests already in this
file (`describe "pre-fix mechanism collides across VM runs"` /
`describe "post-fix unique_slug/1 avoids the cross-VM collision"`), re-verified by
running the full file below (see "Fail-then-pass verification"). Criterion 6 is a
documentation/scope statement, not something a test asserts. The two **new** test cases
below exist specifically to give criteria 5 (empirically, not just by code inspection)
and the WF-03 "shown to fail against the pre-fix code" requirement (structurally,
mechanism-level) their own direct coverage — neither existed before this fix and neither
is redundant with the pre-existing four tests.

## New test cases — `test/support/tenant_slug_test.exs`

1. **`describe "ISS-0065 regression: no literal \"-e\" argv element passed to
   System.cmd"` / `test "no System.cmd/2,3 call node in this file's AST has a literal
   \"-e\" argv element"`** — structural/mechanism-level regression check. Parses this
   test file's own source with `Code.string_to_quoted/1` and walks the AST via
   `Macro.prewalk/3` looking only at the argument lists of actual `System.cmd/2,3` call
   nodes for a literal `"-e"` element — deliberately **not** a raw substring/regex scan
   of the file text, because this file's own comments and assertion messages
   legitimately discuss `"-e"` in prose and a text-level scan is self-defeating against
   itself (an earlier draft using `File.read!(__ENV__.file) =~ "-e"` was tried first and
   failed against its own describe/test names — not hypothetical, it actually happened
   during this test's own design). The AST approach inspects only genuine `System.cmd`
   argv nodes, so it cannot false-positive on prose.

2. **`describe "ISS-0065 regression: write_script_and_run/2 cleans up its temp file even
   when the subprocess fails"` / `test "temp file removed after a nonzero-exit
   subprocess (try/after runs on the failure path too)"`** — negative-path/empirical
   check on `write_script_and_run/2` itself, per the design doc's acceptance criterion 5
   suggestion. Snapshots `System.tmp_dir!/0` for `letflow_iss0065_*` entries, forces a
   subprocess that exits nonzero (a deliberate `raise` in the spawned script body),
   asserts the exit status actually is nonzero (confirms the negative path really
   triggered, not a vacuously-true assertion), then re-snapshots and asserts the
   `letflow_iss0065_*` file set is unchanged. Proves the `try/after` cleanup guarantee
   empirically on the failure path, not just by reading the code — the happy-path tests
   above only ever exercise the success path's cleanup.

## Fail-then-pass verification (WF-03 Step 4 regression-test requirement)

This bug lived in the test file's own subprocess-invocation mechanism, not in
application code, and the platform where it actually failed (Windows) is unavailable on
this host. Two different, real (not simulated) mechanisms were used to establish a
genuine fail-then-pass boundary, one per new test:

**1. Test case 1 (AST-based structural check) — verified directly against the real
pre-fix commit's source, not by assumption.**

```
$ git show ef888b5:test/support/tenant_slug_test.exs > /tmp/prefix_tenant_slug_test.exs
$ elixir -e '
  src = File.read!("/tmp/prefix_tenant_slug_test.exs")
  {:ok, ast} = Code.string_to_quoted(src)
  {_ast, hits} =
    Macro.prewalk(ast, [], fn
      {{:., _, [{:__aliases__, _, [:System]}, :cmd]}, _, args} = node, acc ->
        if Enum.any?(args, &(is_list(&1) and "-e" in &1)), do: {node, [node | acc]}, else: {node, acc}
      node, acc -> {node, acc}
    end)
  IO.inspect(length(hits))
'
2
```

The identical AST walk, run against this file's current (post-fix) source, returns `0`
hits (confirmed live as part of test case 1 itself passing). `ef888b5` is the last
commit before the fix (`f90919f`)'s direct parent-in-spirit — the design doc commit
immediately preceding the implementation. The same walk applied to the pre-fix source
finds exactly the 2 offending call sites the fix touched (`elixir -e ...` and `mix run
--no-start ... -e ...`), and finds 0 against the post-fix source. This is the literal
fail-then-pass boundary for test case 1: the assertion `offending_calls == []` would
have failed (`offending_calls` would be a 2-element list) had this test existed and been
run against `ef888b5`'s tree, and passes against the current tree.

**2. Test case 2 (negative-path cleanup check) — could not even compile pre-fix.**

`write_script_and_run/2` is a new private function introduced by the fix commit
(`f90919f`); it does not exist in `ef888b5`'s tree at all:

```
$ git show ef888b5:test/support/tenant_slug_test.exs | grep -c write_script_and_run
0
```

A test calling `write_script_and_run/2` could not compile against the pre-fix source —
`(CompileError) undefined function write_script_and_run/2`. That is itself a valid (if
blunt) fail-then-pass boundary per WF-03's own allowance for bug classes where the fix
introduces new surface area rather than changing existing behavior (the same reasoning
`test/specs/ISS-0059.md`'s spec used for its own new-helper case). Post-fix, the
function exists and the test both compiles and passes.

**3. Full-file real run, post-fix, all six tests (four pre-existing + two new):**

```
$ mix test test/support/tenant_slug_test.exs --include slow
...
Finished in 3.9 seconds (3.9s async, 0.00s sync)
2 properties, 4 tests, 0 failures
```

(`2 properties, 4 tests` is ExUnit's own count of non-property `test`/`describe` cases;
the six `test`/`property` blocks the module defines other than the module-level setup
resolve to that count — all pass.) `mix compile` and `mix format --check-formatted
test/support/tenant_slug_test.exs` both exit clean with no output.
