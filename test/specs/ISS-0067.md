# Test Spec: ISS-0067 — `resolve_parent_token_record_id/2`'s persisted-vs-derived check

**Issue:** `docs/issues/ISS-0067.yaml` (GH#228), severity MINOR, category type-safety
**Design:** `lib/letflow/design/iss067-token-id-persisted-check.md`
**Test tier:** unit+integration (real Postgres, `Letflow.DataCase`, DIRECTIVE T-1)
**Test files:** `test/letflow/engine_sub_process_test.exs` (existing file, two new `describe`
blocks + two new graph-fixture helpers added; no new file)

## Change summary

`Letflow.Engine`'s private `cast_parent_token_record_id/1` decided whether a `token_id`
reaching a `SUB_PROCESS` node mid-hop-chain was a genuinely persisted `tokens` row or a
derived `PARALLEL_GATEWAY` split/join branch id by calling `Ecto.UUID.cast/1` and treating
cast failure as proof of "derived" — a string-shape heuristic that happens to work today
only because persisted ids are UUID-shaped and derived ids (`transition.ex`'s
`token.token_id <> "/" <> index` and `origin_token_id <> "/" <> node.id <> "/joined"`) are
not. ELIXIR-DEV's fix replaces it with `resolve_parent_token_record_id/2`, which takes the
`token_id` and a real `MapSet` of this hop chain's own persisted `TokenRecord` ids
(`original_active_tokens`, already loaded once per hop chain, mirroring
`do_reconcile_token_records/4`'s existing idiom) and does a pure `MapSet.member?/2` check.
Same `{:ok, token_id} | {:error, {:sub_process_after_split_join_not_supported, token_id}}`
contract as before, so no caller of `prepare_sub_process_children_for_completion/8`'s
`with`/`else` needed to change.

## Why this needs real coverage, not just "existing tests still pass"

Per REVIEWER's own handoff note on this run and ISSUE-FIXER's diagnosis (confirmed again
here): before this run, **zero** tests anywhere in the suite referenced
`resolve_parent_token_record_id`, `cast_parent_token_record_id`, or the
`{:sub_process_after_split_join_not_supported, _}` tuple by name. The 72 existing
SUB_PROCESS tests across `test/letflow/engine_sub_process_test.exs` and
`test/letflow/engine/sub_process_test.exs` exercise SUB_PROCESS flows broadly, but none of
them specifically construct the "parent token_id is a derived split/join branch id, not a
persisted one" scenario this function's correctness property is actually about — passing
end-to-end proves the mechanism swap didn't *regress* anything those tests happen to touch,
not that the new classification logic is *correct* for the one case it exists to handle.
This is explicitly not a pure string-format refactor (unlike ISS-0071): the old and new
mechanisms are only proven outcome-equivalent against today's actual split/join minting
scheme, and that equivalence is exactly the kind of thing that should be pinned down by a
direct test, not left to incidental pass-through coverage.

`resolve_parent_token_record_id/2` is `defp` — unreachable directly from outside
`Letflow.Engine` — so the only available seam is integration-level: drive a real
`PARALLEL_GATEWAY` split immediately followed by a `SUB_PROCESS` node through the public
`Letflow.Engine.complete_task/3` surface, and assert the exact rejection tuple. A positive
(accept) counterpart is added alongside it so both branches of the classification are
directly asserted, not just the failure one.

## Test cases

1. **Negative — a derived split-branch token_id is rejected.**
   `graph_parent_split_then_subprocess/1` builds `START -> HUMAN_TASK("gate") ->
   PARALLEL_GATEWAY("split") -> {SUB_PROCESS("sp1"), SUB_PROCESS("sp2")} ->
   PARALLEL_GATEWAY("join") -> END`. Completing "gate" triggers, within the same
   `complete_task/3` hop chain: `Transition.dispatch_parallel_split/4` mints two branch
   token_ids in-memory (`"#{gate_token.id}/0"`, `"#{gate_token.id}/1"`, neither ever
   written to a `tokens` row), `advance_until_stable/4` immediately lands them on
   `sp1`/`sp2`, and `dispatch_sub_process_entry/4` emits a `{:sub_process_start, ...}`
   pending event for each. `prepare_sub_process_children_for_completion/8`'s
   `Enum.reduce_while/3` hits the first one (`"#{gate_token.id}/0"`, edge `e3` declared
   first so branch index 0) and calls `resolve_parent_token_record_id/2`, which must find
   it absent from `persisted_token_ids` and reject.
   See `test/letflow/engine_sub_process_test.exs`, describe
   `"ISS-0067 -- resolve_parent_token_record_id/2 rejects a derived split/join branch
   token_id"`. Asserts:
   - `Engine.complete_task/3` returns exactly
     `{:error, {:sub_process_after_split_join_not_supported, "#{gate_token.id}/0"}}` —
     pins the exact rejected token_id, not just the error shape.
   - The whole transaction rolled back (the `{:error, reason}` return from the
     `"transition"` `Multi.run/3` step aborts the `Ecto.Multi`, unlike the
     `SUB_PROCESS_MISSING_REQUIRED_INPUT`-style failures elsewhere in this file which
     commit via `set_instance_error`): the gate task is still `:pending`, the parent
     instance is still `:active` (never `:error`), the `instance_projections` row count is
     unchanged, and zero child instance rows exist for this parent.

2. **Positive — a genuinely persisted parent token_id is accepted.**
   `graph_parent_task_then_subprocess_no_split/1` builds `START -> HUMAN_TASK("gate") ->
   SUB_PROCESS("sp") -> END` — no split/join anywhere, so the token reaching `"sp"` is
   `"gate"`'s own already-persisted `tokens.id`. This exercises the *same*
   `prepare_sub_process_children_for_completion/8` code path as the negative case above
   (a hop chain reached via `complete_task/3`, not `create/2`'s separate root-SUB_PROCESS
   path), so it is a direct counterpart, not incidental coverage: every other
   SUB_PROCESS test that reaches this function via a persisted id (the AC3
   interface-violation tests, which reuse `graph_parent_task_then_subprocess/2`) does so
   only on the way to an unrelated, later failure at `SubProcess.prepare_child_activation/4`
   — none of them assert the accept branch's own success outcome directly.
   See `test/letflow/engine_sub_process_test.exs`, describe
   `"ISS-0067 -- resolve_parent_token_record_id/2 accepts a genuinely persisted parent
   token_id"`. Asserts:
   - `Engine.complete_task/3` returns `{:ok, result}` with `result.instance_status ==
     :active` and `result.current_nodes == ["sp"]`.
   - A real child `InstanceProjection` row exists with `parent_instance_id == created.instance_id`.
   - The gate's own `TokenRecord` (`gate_token.id`) now has `status == :waiting` and
     `waiting_child_instance_id == child.instance_id` — the same persisted token_id the
     classification check accepted is the one that ends up parked waiting on the child.

## Why not a WF-03 fail-then-pass regression test

This is a WF-03 issue-resolution run (ISS-0067, MINOR, discovered by REVIEWER, not a field
bug), and the task's own scope note frames it as "add direct coverage of the correctness
property itself... not just rely on whatever existing SUB_PROCESS tests already pass
end-to-end" rather than as a fail-then-pass regression demonstration. The design doc's own
"Byte-identical-output justification" section already establishes that, for every
`token_id` value reachable under today's actual minting scheme, the old
(`Ecto.UUID.cast/1`-based) and new (`MapSet.member?/2`-based) mechanisms produce identical
output — so these two new tests would pass identically against the pre-fix code too (the
old heuristic already rejects a `"<uuid>/0"`-shaped derived id, since it isn't
UUID-castable, and already accepts a real UUID-shaped persisted id). Checked out the
pre-fix commit's `cast_parent_token_record_id/1` mentally against both scenarios via the
design doc's own worked equivalence proof rather than re-running `mix test` against a
checkout: no divergent input exists in the codebase today for these tests to distinguish
pre-fix from post-fix behavior on. What these tests *do* newly guard is the mechanism
itself (a future change to `transition.ex`'s branch-id minting scheme — e.g. switching to
UUID-shaped derived ids — would only be caught by these tests continuing to exercise the
real classification path with real data, not by a test that merely re-derives the same
string-shape assumption the old heuristic depended on).

## Why not a new test file

`test/letflow/engine_sub_process_test.exs`'s own moduledoc states its convention: DB-integration
coverage driven through the real public `Letflow.Engine`/`Letflow.Definitions` surface,
never a direct `Letflow.Engine.SubProcess` call — exactly the seam these two tests need.
Both new `describe` blocks reuse every existing fixture/helper in the file
(`provisioned_tenant/0`, `active_definition!/2`, `start_attrs/2`, `complete_attrs/1`,
`pending_task_for_instance!/2`, `child_projection!/2`, `child_projections/2`,
`instance_projection_count/1`) and add only two new graph-fixture helpers, matching the
file's existing `graph_*` helper pattern. `test/letflow/engine/sub_process_test.exs` (the
pure-layer file) is not touched — its own moduledoc scopes it to input/output filtering,
`Transition`'s `:SUB_PROCESS` dispatch clauses, and the AC5 struct-update regression, none
of which reach `resolve_parent_token_record_id/2` (that function lives in `Letflow.Engine`,
not `Letflow.Engine.Transition` or `Letflow.Engine.SubProcess`).
