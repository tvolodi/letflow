# Test Spec: ISS-0069 (Part 2) — `mix letflow.check.test` gate for unused-default-arg warnings

**Issue:** ISS-0069 — "Remove unused default values in test helpers (full sweep +
gate)". **Design:** `lib/letflow/design/iss0069-unused-default-warnings-fix.md`.
**Fix under test:** `lib/mix/tasks/letflow.check.test.ex`
(`Mix.Tasks.Letflow.Check.Test`), committed at `e95746e`/`1b969c0` on this branch.

This spec covers WF-03 Step 4 (regression test) for **the gate itself**. Part 1 of
ISS-0069 (the repo-wide sweep removing 9 unused `defp` defaults) is a warning-only
cleanup with no new executable surface to test beyond "the suite still compiles/runs,"
already covered by the full existing suite passing. Part 2 introduced new,
independently-testable logic — the gate task — which is what this spec targets.

## Criterion (from the design doc's Part 2 "Exit-code contract" + Verification item 3)

`mix letflow.check.test` must:
1. Exit non-zero (raise) when the underlying `mix test` subprocess's captured
   stdout+stderr contains the literal substring `"default values for the optional
   arguments"` — even if the subprocess itself exited `0` (a warning, not a test
   failure) — and print the offending line(s) so the failure is actionable.
2. Exit `0` when the subprocess exited `0` and that substring is absent, **even when
   other, already-deferred warning classes are present** (ISS-0044 Groups 1/3, the
   out-of-scope `tenant` variable) — the gate must not become a blanket
   `--warnings-as-errors` in disguise.
3. Exit non-zero when the subprocess itself exited non-zero (a real test
   failure/error), regardless of the substring — a real test failure must never be
   masked just because the ISS-0069 substring happens to be absent.

Design doc Verification item 3 required this be proven with a negative control (manual
reintroduction of a default arg, confirm the gate catches it, revert) — this spec turns
that one-off manual proof into a permanent, automated, fail-then-pass test.

## Test cases: `test/mix/tasks/letflow_check_test_test.exs`

1. **`"raises and reports the offending line when the target substring is present, even though the underlying subprocess exited 0"`**
   — proves criterion 1. Exists because this is exactly ISS-0069's own warning class
   recurring (e.g. someone reintroduces a `\\ <literal>` default on a `defp` test
   helper) — the one scenario the whole gate exists to catch. Asserts a `Mix.Error` is
   raised whose message contains the target substring.

2. **`"passes (no raise) when the subprocess exits 0 and the target substring is absent, even with unrelated warnings present"`**
   — proves criterion 2. Exists specifically to guard against the gate silently
   regressing into a blanket `--warnings-as-errors` (the design doc's round-2 rework
   context: the earlier, wrong version of Part 2 did exactly this and blocked on
   ISS-0044's already-deferred classes). Fixture output includes the
   `register_test/4 is deprecated` and unused-`tenant`-variable warning text
   verbatim, asserts the task still reports `"OK"` and does not raise.

3. **`"raises when the subprocess itself exits nonzero, regardless of the substring"`**
   — proves criterion 3. Exists to guard against a bug where the gate only looks at
   the substring and forgets to also fail on genuine test failures/errors, which would
   silently turn `mix letflow.check` green on a broken suite.

### Why fake the `mix test` subprocess rather than run it for real

`Mix.Tasks.Letflow.Check.Test.run/1`'s detection logic (`String.contains?/2` against
the fixed substring, plus the exit-code branching) is inline inside `run/1`, which
shells out to `mix test` via an OS-level `Port`. Actually running the real `mix test`
subprocess from inside an ExUnit test would recurse the entire ~1000-test suite into
itself for every case above — slow, and irrelevant to what's actually being tested
(the task's own decision logic, not whether the wider suite currently has warnings).

Instead, each test case prepends a temp directory containing a fake executable named
`mix` onto `PATH`, so `System.find_executable("mix")` — called internally by `run/1`
— resolves to a tiny script that prints controlled, canned output and exits with a
controlled status, standing in for what a real `mix test` subprocess would have
printed. `run/1` itself is called directly and unmodified: the `Port.open/2` call, the
streaming `collect/2` loop, the `String.contains?/2` check, `Mix.raise/1`, and the
offending-line extraction all execute for real in every case. No refactor of
`lib/mix/tasks/letflow.check.test.ex` was made or needed to write this test.

### Fail-then-pass, actually verified

Per WF-03 Step 4 / `docs/guides/test_developer_guide.md` §5, this was verified by
actually breaking the implementation, not by assertion:

1. `mix test test/mix/tasks/letflow_check_test_test.exs` against the committed
   implementation (`@target_substring "default values for the optional arguments"`):
   **3 tests, 0 failures.**
2. `lib/mix/tasks/letflow.check.test.ex`'s `@target_substring` temporarily changed
   (via `sed`, uncommitted) to `"THIS_STRING_WILL_NEVER_MATCH_ANYTHING_xyz123"` —
   simulating the detection logic being absent/broken. Re-running the same test file:
   **3 tests, 1 failure** — case 1 above (`"raises and reports the offending
   line..."`) failed with `Expected exception Mix.Error but nothing was raised`,
   exactly as expected since the broken substring can never match the fixture output.
3. `git checkout -- lib/mix/tasks/letflow.check.test.ex` to revert the temporary
   breakage (confirmed clean via `git status --porcelain`, zero diff). Re-running:
   **3 tests, 0 failures** again.

This confirms the test suite fails when the gate's detection logic is broken and
passes when it is intact — real coverage of the fix, not a tautological assertion on
the implementation's own literals (the test never references
`Mix.Tasks.Letflow.Check.Test.@target_substring` — it hardcodes the same substring
independently, as the contract text, not by reading the implementation's attribute).
