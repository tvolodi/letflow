# Test Spec: ISS-0071 — shared `derive_idempotency_key/3` helper for sub_process.ex

**Issue:** `docs/issues/ISS-0071.yaml` (GH#255), severity MINOR, category type-safety
**Design:** `lib/letflow/design/iss071-idempotency-key-helper.md`
**Test tier:** unit+integration (real Postgres, `Letflow.DataCase`, DIRECTIVE T-1)
**Test files:** `test/letflow/engine_sub_process_test.exs` (existing file, assertions added,
no new file)

## Change summary

`Letflow.Engine.SubProcess` previously derived a secondary `idempotency_key` at three
call sites by hand-interpolating a literal suffix string directly into an inline
string. The fix (ELIXIR-DEV, this run) replaces all three inline expressions with calls
to one new private helper, `derive_idempotency_key(base, suffix, ids)` (`Enum.join([base,
suffix | ids], "::")`), plus three named module attributes for the three suffix literals.
Per the design doc's own Acceptance criteria, this is explicitly a **pure refactor**:
byte-identical output for the same inputs at all three call sites, no behavior change, no
new public API (the helper stays `defp`).

## Why this is not a WF-03-style regression test

ISS-0071 is not a bug — the pre-refactor code already produced correct, pairwise-distinct
idempotency keys (REVIEWER's own finding confirmed the three suffixes were already
distinct by direct string comparison). There is no pre-fix/post-fix behavioral delta to
prove fail-then-pass against; the "before" and "after" code are required, by the design's
own acceptance criteria, to produce identical output. A fail-then-pass demonstration
would therefore be meaningless here (there is nothing to fail against — both versions
must pass identically). What *is* worth new coverage is a different question: whether the
newly-introduced, named, reusable abstraction (`derive_idempotency_key/3`) is itself
verified to produce the exact `base::suffix::id[::id...]` format at each of its three call
sites, rather than relying only on the pre-existing tests' indirect confirmation that
*some* string got written and downstream behavior (event counts, merge results) was
unaffected.

## Decision: add targeted assertions, not a new test file

Per ISSUE-FIXER's confirmation (recorded in the design doc and in this run's task
context): before this change, no existing test in `test/letflow/engine_sub_process_test.exs`
or `test/letflow/engine/sub_process_test.exs` asserted on the derived `idempotency_key`
value's exact string content — only on the caller-supplied *base* `idempotency_key` and on
downstream event counts/payloads. That was adequate for the pure-refactor's own safety net
(byte-identical-output is implicitly covered by every existing assertion continuing to
pass unchanged), but it means the new helper's exact join format
(`base::suffix::id1[::id2]`) was not independently pinned down anywhere.

`derive_idempotency_key/3` is `defp` — private to `Letflow.Engine.SubProcess` — so it
cannot be unit-tested directly from outside the module (no `apply/3`-based private-function
test either; that would fight the module boundary the design deliberately keeps, see
design doc "New private helper" section: "nothing outside this module calls it today").
The next-best, and only available, direct check is to assert on the exact
`idempotency_key` value the helper produces as observed through the `Letflow.EventStore.Event`
row it ultimately gets persisted into (`Event.idempotency_key`, `lib/letflow/event_store/event.ex:87`)
at each of the three real call sites, driven through the same public `Letflow.Engine`
surface `test/letflow/engine_sub_process_test.exs` already uses (never a direct
`Letflow.Engine.SubProcess` call, matching this file's own stated convention).

All three call sites now have a dedicated assertion added to an existing test that already
exercises that call site end-to-end — no new `describe`/`test` blocks, no new file:

1. **Call site 1** — `append_instance_started_event_for_child/8`
   (`base = Map.get(attrs, :idempotency_key)`, `suffix = @sub_process_start_suffix`,
   `ids = [child_instance_id]`). Added to the existing AC1 test
   (`"AC1 -- ... a parent variable not named in inputs is demonstrably absent from the
   child"`): after the existing assertions, queries the child's own `INSTANCE_STARTED`
   event by `instance_id`/`event_type` and asserts
   `event.idempotency_key == "#{attrs.idempotency_key}::sub_process_start::#{child.instance_id}"`.

2. **Call site 2** — `append_completion_multi/4`'s `error_idempotency_key`
   (`base = idempotency_key` (the completing task's own), `suffix =
   @sub_process_completion_error_suffix`, `ids = [parent_token.instance_id,
   child_instance_id]`). Added to the existing AC3/AC8
   `SUB_PROCESS_MISSING_REQUIRED_OUTPUT` test — the one existing test that reaches this
   call site (the child completes successfully but the parent's own output-interface
   validation rejects the merge, routing through `to_error_args/6` into an
   `EXECUTION_ERROR` event carrying `error_idempotency_key`). Captures the child's own
   `complete_attrs()` map in a named variable (`child_complete_attrs`, was previously
   inline) so its `idempotency_key` is available for the assertion, then asserts
   `event.idempotency_key == "#{child_complete_attrs.idempotency_key}::sub_process_completion_error::#{created.instance_id}::#{child.instance_id}"`
   against the `EXECUTION_ERROR` event already fetched by that test.

3. **Call site 3** — `append_sub_process_completed_event/8`
   (`base = idempotency_key` (the completing task's own), `suffix =
   @sub_process_completed_suffix`, `ids = [parent_instance_id, child_instance_id]`). Added
   to the existing AC4 test (`"AC4 -- ... a child variable not named in outputs is
   demonstrably absent from the parent afterwards"`), which already fetches the resulting
   `SUB_PROCESS_COMPLETED` event via `sub_process_completed_events/2`: asserts
   `event.idempotency_key == "#{output_attrs.idempotency_key}::sub_process_completed::#{created.instance_id}::#{child.instance_id}"`.

Each assertion pins the exact `base`/`suffix`/`ids`-ordering contract the design doc's
"Exact call-site arguments" table specifies for that row — a suffix typo, a swapped `ids`
order (e.g. `child_instance_id` before `parent_instance_id`), or a dropped `"::"` join
element at any of the three sites would now fail one of these three assertions, which none
of the pre-existing assertions in this file could have caught (they only checked event
*counts* and event *payloads*, never `idempotency_key`'s own value).

## Why not a new file / why these tests, not new ones

- `docs/agents/instructions/core-directives.md`'s "no manufactured busywork" spirit and
  this run's own task framing point toward extending existing, already-passing
  integration coverage over inventing a new, narrower unit-test file for a `defp`
  function that has no reachable external seam.
- Reusing the AC1/AC3/AC4 tests that already drive each of the three call sites end-to-end
  through the real public `Engine.create/2` / `Engine.complete_task/3` surface keeps the
  new assertions inside this file's own stated convention (`engine_sub_process_test.exs`'s
  moduledoc: "driven through the real public `Letflow.Engine`/`Letflow.Definitions`
  surface (never a direct `Letflow.Engine.SubProcess` call)").
- No test in `test/letflow/engine/sub_process_test.exs` (the pure-layer file) touches
  `derive_idempotency_key/3` at all — its own moduledoc scopes it to input/output
  filtering, `Transition`'s `:SUB_PROCESS` dispatch, and the AC5 struct-update regression,
  none of which reach the idempotency-key derivation call sites. No change made there.
