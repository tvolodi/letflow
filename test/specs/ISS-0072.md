# Test Spec: ISS-0072 — Register the 5 unregistered production event types

**Issue:** `docs/issues/ISS-0072.yaml` (GH#257), severity MAJOR
**Design:** `lib/letflow/design/iss072-event-type-registration.md`
**Fix commit:** `eb69dd7` (`fix(WF03-ISS0072): seed 5 more production-written event types at
provisioning`), branch `feature/WF03-ISS0072-20260819`
**Pre-fix commit:** `09ac8ee`
**Test tier:** unit+integration (real Postgres, `Letflow.DataCase`, DIRECTIVE T-1)
**Test file:** `test/letflow/tenant_provisioning_event_seed_test.exs`

## Bug summary

`Letflow.TenantProvisioning.maybe_seed_platform_event_types/2` only ever seeded
`"INSTANCE_STARTED"` into a tenant's `event_type_registry`. Five event types with real
production writers (`TASK_COMPLETED`, `INSTANCE_CANCELLED`, `INSTANCE_PINS_REBOUND`,
`SUB_PROCESS_COMPLETED`, `EXECUTION_ERROR`) had no registry row in any real,
non-test-fixture tenant schema, so `Letflow.EventStore.append/2` rejected every one of
them with `{:error, :unknown_event_type}` — silently, in production, invisible in the
test suite only because every test file exercising these write paths self-registered its
own fixture's event type via `Registry.register_type/2` before calling the code under
test.

The fix (`lib/letflow/tenant_provisioning.ex`) restructures the single-entry
`@instance_started_event_type_attrs` into a 6-entry `@platform_event_type_seed_attrs`
list and rewrites `maybe_seed_platform_event_types/2`'s body as an `Enum.reduce_while/3`
fold that registers all 6 (idempotently — `{:error, :duplicate_event_type_version}` still
folds to success) at the same point in `replay_migrations/2` `INSTANCE_STARTED` was
already seeded.

## Why a fixture-self-registering test would prove nothing

ISS-0072's bug is specifically that a tenant provisioned the *normal, production* way —
`TenantProvisioning.provision_tenant_schema/1` + `TenantProvisioning.replay_migrations/2`
against its **default** manifest, no caller-supplied `migration_source` — had no registry
row for these 5 types. Every existing test file that exercises `complete_task/3`,
`cancel_instance/3`, `PinRebind.rebind_pins/3`, `SubProcess`'s completion path, or
`ExecutionError.append_execution_error_event/2` works today only because its own fixture
calls `Registry.register_type/2` for itself first — which is exactly the workaround that
made this bug invisible to the test suite for as long as it existed. A regression test
that also self-registers would pass identically against the pre-fix and post-fix code,
proving nothing about whether the actual production gap is closed. `test/letflow/
tenant_provisioning_event_seed_test.exs` therefore never calls `Registry.register_type/2`
itself anywhere — every event type it successfully appends was seeded by
`TenantProvisioning` alone.

## Test cases

1. **The 5 newly-seeded types append successfully against a real, non-fixture tenant
   schema** — `describe "ISS-0072: the 5 newly-seeded event types now append against a
   real tenant schema"`, one generated test per type (`TASK_COMPLETED`,
   `INSTANCE_CANCELLED`, `INSTANCE_PINS_REBOUND`, `SUB_PROCESS_COMPLETED`,
   `EXECUTION_ERROR`). This is the core regression proof: each provisions a tenant via
   `provision_tenant_schema/1` + default-manifest `replay_migrations/2` only, then calls
   `EventStore.append/2` with a minimal payload matching that type's `json_schema` (per
   the design doc §4) and asserts `{:ok, %{event: event, is_duplicate: false}}`. Exists
   because this is literally ISS-0072's own bug statement — these 5 calls are exactly
   what silently failed with `{:error, :unknown_event_type}` in any real tenant before
   the fix.

2. **`INSTANCE_STARTED` still works** — `describe "INSTANCE_STARTED still works
   (pre-existing seed, not touched by ISS-0072's 5 additions)"`. Exists to prove the
   `Enum.reduce_while/3` rewrite of `maybe_seed_platform_event_types/2`'s body didn't
   regress the one entry that already worked pre-fix — a rewrite from a single call to a
   fold over a list is exactly the kind of change that could silently drop or reorder the
   first element.

3. **A genuinely still-unregistered type stays rejected** —
   `describe "still-unregistered types remain rejected..."`, using `DEFINITION_PROMOTED`
   (one of the 3 types the design doc §1 names as deliberately excluded — no production
   writer exists for it). Exists to prove the fix seeds exactly the 6 named types, not
   indiscriminately everything reachable — without this case, a bug that seeded *all*
   known type names (masking a design mistake) would pass case 1 undetected.

4. **`replay_migrations/2` re-run stays idempotent (OQ-1, production-code half)** —
   `describe "OQ-1: replay_migrations/2 re-run against an already-seeded tenant stays
   idempotent"`. Calls `replay_migrations/2` a second time against an already-provisioned
   tenant, asserts it still returns `{:ok, _}` overall, that `event_type_registry` still
   holds exactly 6 rows (not 12), and that a type seeded by the *first* call is still
   appendable after the second call. Exists because the fix changed a single
   `register_type/2` call into a 6-iteration fold with fail-fast semantics — this proves
   the fold's idempotency-folding (`{:error, :duplicate_event_type_version} -> {:cont,
   :ok}`) genuinely covers all 6 entries on a re-run, not just the first.

The 2 that passed were exactly the 2 cases that should be unaffected by ISS-0072: the
`INSTANCE_STARTED` regression case (already worked pre-fix) and the `DEFINITION_PROMOTED`
negative control (correctly rejected both pre- and post-fix, since it's still

Result against the fix commit (`a147d0f`, `feature/WF03-ISS0072-20260819`'s HEAD at time

This 2/8 → 8/8 split (not 0/8 → 8/8, and not passing identically both ways) is the
positive confirmation this test file actually exercises ISS-0072's specific bug, not

Additionally, cross-checked the pre-fix seed list directly rather than relying only on

consistent with, and explaining, the empirical failures above.

## OQ-1 finding (design doc §9 — investigated, not assumed away)

The design doc's OQ-1 flagged, but did not resolve, whether pre-existing test files
calling `Registry.register_type/2` directly for their own fixtures (naming
`engine_cancel_instance_test.exs`, `engine_complete_task_test.exs`, `event_store_test.exs`
as examples) would now collide with this seed if they also run `replay_migrations/2`
against the default manifest first.

**Investigated, and the collision is real and already active on this branch**, not merely
theoretical:

- `event_store_test.exs`'s own `register_event_type!/2` fixture generates a fresh
  **unique** type name per call (`unique_type_name/0`, e.g. `"EVT_1234"`) — it never
  reuses one of ISS-0072's 6 seeded names, so it does **not** collide. Confirmed by
  reading the file directly.
- `engine_complete_task_test.exs` and `engine_cancel_instance_test.exs` **do** collide:
  each calls `TenantProvisioning.replay_migrations(tenant.id)` (default manifest, so
  ISS-0072's seed runs) and then its own `register_event_type!/2` helper hard-asserts
  `{:ok, _event_type} = Registry.register_type(%{"name" => "TASK_COMPLETED", ...}, ...)`
  (or `"INSTANCE_CANCELLED"`) at `schema_version: 1` — the exact `(name, schema_version)`
  pair ISS-0072's seed already registered. `Registry.register_type/2`'s own monotonicity
  check (`registry.ex:243-244`) returns `{:error, :duplicate_event_type_version}` for an
  exact version match, which is *not* what these fixtures' hard `{:ok, _} = ...` match
  expects, so the fixture setup itself now raises a `MatchError` and every test depending
  on it fails before its own body runs.
- Ran the full suite on this branch (`mix test`, commit `a147d0f`): **80 tests fail**,
  spanning ~13 test files (`Letflow.Engine.PinRebindTest`,
  `Letflow.Engine.ReconstructionTest`, `Letflow.EngineSubProcessTest`,
  `Letflow.Engine.SnapshotWriterTest`, `Letflow.EngineCompleteTaskTest`,
  `Letflow.EngineCancelInstanceTest`, `Letflow.EngineExecutionErrorTest`, and others).
  Directly reproduced and confirmed the exact `MatchError` mechanism above for the 14
  failures in `engine_complete_task_test.exs` + `engine_cancel_instance_test.exs`
  specifically (`mix test test/letflow/engine_complete_task_test.exs
  test/letflow/engine_cancel_instance_test.exs`).

This is **not** covered or fixed by `test/letflow/tenant_provisioning_event_seed_test.exs`
(this file registers nothing itself, so it cannot exhibit this collision) — filed
separately as `docs/issues/ISS-0073.yaml`
([GH#267](https://github.com/tvolodi/letflow/issues/267)), BLOCKER severity, since fixing
~13 pre-existing test fixture files is a substantially larger and different scope than
ISS-0072's own WF-03 run (one new regression test file for the production fix this run
was dispatched to cover). This finding must be resolved (via ISS-0073) before
`feature/WF03-ISS0072-20260819` can be considered CI-green — the fix's production code is
correct and this file proves it, but the branch's existing test suite is not currently
passing as a whole because of this collision.
