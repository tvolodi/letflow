# Test Spec: ISS-0079 — verify pin overrides against the injected `Lookup`

**Issue:** `docs/issues/ISS-0079.yaml` (GH#298), severity MAJOR
**Design:** `lib/letflow/design/iss-0079-pin-override-verification.md`
**Fix commit:** `a0d9c27` (`fix(ISS-0079): verify pin overrides against the injected Lookup,
close GH#298`), branch `feature/WF03-ISS0079-20260820`
**Pre-fix commit:** `f32b4f7` (= `a0d9c27~1`, current tip of `main`)
**Test tier:** unit (pure module, no `Letflow.Repo`, `async: true`)
**Test file:** `test/letflow/engine/pin_resolver_test.exs`

## Bug summary

Pre-fix, `PinResolver.resolve_one_ref/4` and `resolve_variable_schema/3` took a
caller-supplied `pin_overrides` entry (`kind`, `ref`, `resolved_id`, `version`)
**verbatim**, calling `lookup_fun` only for a *non*-overridden ref. An override could
assert any `resolved_id`/`version` string, including ones naming nothing that exists,
and it was written into the `INSTANCE_STARTED` event payload as an authoritative,
permanent pin (pins are immutable thereafter except via PIN-05 rebind, and `pin_for/3`
has "no fallback, ever" — a bad pin poisons every later execution-time lookup for the
instance's whole lifetime). `kind: :module` overrides were unconditionally accepted too
(no categorical or per-lookup gate), and an override naming a ref the graph doesn't
enumerate was silently ignored rather than surfaced as an error.

The fix (`lib/letflow/design/iss-0079-pin-override-verification.md`, Decisions 1-4)
makes every override an overlay that is **verified against `lookup`** before
acceptance:

- `kind: :catalog_entry` / `kind: :module` — accepted only if
  `lookup.catalog_lookup.(ref)` / `lookup.module_lookup.(ref)` returns
  `{:ok, %{version: v}}` with `v` equal to the override's own `version`; the accepted
  pin's `resolved_id`/`version` are taken from the **lookup result**, never the
  caller-supplied override.
- `kind: :variable_schema` — accepted only if `lookup.variable_schema_lookup.(nil, ref)`
  confirms the same `version`; the accepted pin's `resolved_id` is forced to `nil`
  unconditionally (the lookup result has no `resolved_id` field to substitute).
- `kind: :module` remains a legal override kind (Decision 3 — Letflow does not inherit
  R-Co's unconditional rejection, which was itself only a consequence of R-Co having no
  module catalog at all); it is verified the same uniform way as `catalog_entry`.
- An override naming a `{kind, ref}` outside the enumerated pin set is
  `{:error, {:unresolved_pin_override, ref}}` (Decision 4), not a silent no-op.

`resolve_error()` gains the `{:unresolved_pin_override, ref}` variant (Decision 2).

## Why a verbatim-echo test would prove nothing (and why the pre-existing test had to be rewritten, not just extended)

The pre-fix test suite already contained a test at the same location
(`describe "resolve/4 -- overrides substitute for the lookup, no lookup call at all for
an overridden ref"`) that asserted the *old, vulnerable* behavior directly: it used a
`raise_if_called_lookup/1` fixture and asserted an override's `resolved_id`/`version`
came through **verbatim**, with the lookup function never called. That test is not
merely stale documentation — it is a standing assertion that the vulnerable behavior is
*correct*, and it fails outright against the fix (`lookup.catalog_lookup` is now called
for `svc-a` and raises, per `raise_if_called_lookup/1`'s own contract). Confirmed by
direct `mix test` run against the fix branch before any test changes were made:

```
1) test resolve/4 -- overrides substitute for the lookup, no lookup call at all for an
   overridden ref a matching override entry is used verbatim, source: :override, and the
   corresponding lookup function is never called (Letflow.Engine.PinResolverTest)
   ** (RuntimeError) catalog_lookup must not be called, got service_id: "svc-a"
Result: 33/34 passed
```

This test was therefore **replaced**, not left alongside new coverage — a suite
containing both "override is verbatim" and "override is verified" assertions
simultaneously would be self-contradictory and could never pass against any single
version of the code.

## Test cases

All in `describe "resolve/4 -- ISS-0079: a matching override is VERIFIED against
lookup, never taken verbatim"` unless noted:

1. **Version mismatch → rejected, not silently accepted** — an override asserts
   `version: "9.9.9"` for a ref the lookup confirms exists but at `version: "1.0.0"`.
   Asserts `{:error, {:unresolved_pin_override, ref}}`. This is the core vulnerability:
   pre-fix, `resolve_one_ref/4` never called `lookup_fun` for an overridden ref at all,
   so this mismatch went undetected and `"9.9.9"` would have been written into the pin
   set verbatim.

2. **Lookup reports `:not_found` → rejected** — same shape, lookup returns
   `{:error, :not_found}` for the overridden ref. Distinct failure mode from case 1
   (mismatch vs. absence), both must produce the same error per the design's uniform
   verification rule.

3. **Version match → accepted, but `resolved_id`/`version` come from the *lookup
   result*, not the caller-supplied override** — the override supplies
   `resolved_id: "caller-asserted-sid"`; the lookup confirms the same `version` but
   under `resolved_id: "lookup-confirmed-sid"`. Asserts the accepted pin's
   `resolved_id` is the lookup's value. This is the precise verbatim-vs-verified
   distinction ISS-0079 was filed over: a caller successfully verifying a real
   `version` must not also get to assert an arbitrary, unverified `resolved_id`
   alongside it.

4. **`variable_schema` override, verified → `resolved_id` forced to `nil`** — the
   override supplies `resolved_id: "caller-asserted-vs-id"`; lookup confirms the
   version. Asserts the accepted pin's `resolved_id` is `nil`, never the caller's
   value — `variable_schema_lookup_result` carries no `resolved_id` field at all, so
   there is no lookup-confirmed value to substitute the way `catalog_entry`/`module`
   do; `nil` is the only value with no unverified claim attached.

5. **`variable_schema` override, version mismatch → rejected** — same as case 1 but
   for the `variable_schema` kind, confirming the verification rule is uniform across
   all three kinds, not special-cased to `catalog_entry`.

6. **`kind: :module` override, verified → still accepted** — confirms Decision 3:
   Letflow does not adopt R-Co's categorical rejection of module overrides. Verified
   the same way as `catalog_entry` (case 3's shape, `resolved_id` from the lookup).

7. **`kind: :module` override, unverifiable → rejected the same way an unverifiable
   `catalog_entry` override is** — confirms module overrides get no special leniency;
   an unverifiable module override is caught by the same uniform verification rule
   with no categorical ban required.

8. **Override naming a ref NOT in the enumerated pin set → error, not a silently-
   ignored no-op** (Decision 4) — an override names `"svc-never-referenced"`, which no
   graph node references. Asserts `{:error, {:unresolved_pin_override, ref}}`. The
   enumerated ref (`svc-a`) in the same graph resolves successfully, proving the stray
   check specifically catches the unreferenced ref rather than a coincidental failure
   elsewhere.

9. **Override naming a ref that IS enumerated, but under the WRONG `kind` → treated as
   stray, not loosely matched by ref alone** — `"shared-name"` is enumerated as
   `:catalog_entry`; an override claims `kind: :module` for the same ref string.
   Asserts `{:error, {:unresolved_pin_override, ref}}` (Decision 4's stray-ref path),
   confirming `find_override/3`'s `{kind, ref}` matching is exact, not ref-only.

## Verified fail-then-pass (WF-03 requirement)

`main` (`f32b4f7`) is the exact parent of the fix commit (`a0d9c27~1`), so a git
worktree at `main` gives pre-fix code directly — no separate checkout needed:

```
git worktree add ../letflow-scratch-iss0079 main
cp test/letflow/engine/pin_resolver_test.exs ../letflow-scratch-iss0079/test/letflow/engine/
cd ../letflow-scratch-iss0079
# deps/ symlinked from the main worktree (no network available); _build compiled fresh
# locally so the fix branch's own _build cache is never touched or polluted.
MIX_ENV=test mix compile
mix test test/letflow/engine/pin_resolver_test.exs
```

**Result against pre-fix code (`f32b4f7`): 33/42 passed, 9 failed** — every one of the
9 new cases above (cases 1-9) failed. Sample failures:

- Case 3 (`resolved_id` sourced from lookup): pre-fix returned
  `resolved_id: "caller-asserted-sid"` (the override's own value) where the test
  expects `"lookup-confirmed-sid"` (the lookup's value) — `right: %{resolved_id:
  "caller-asserted-sid", ...}` vs. the asserted `"lookup-confirmed-sid"`.
- Case 2 (`:not_found` → rejected): pre-fix returned `{:ok, [...]}` with the override
  accepted verbatim, where the test expects `{:error, {:unresolved_pin_override,
  "svc-a"}}`.
- Case 7 (unverifiable module override → rejected): pre-fix returned `{:ok, [...]}`
  with `resolved_id: "caller-asserted-mid"` accepted verbatim.
- Case 8 (stray ref → error): pre-fix returned `{:ok, [...]}` with the enumerated
  `svc-a` pin present and the stray override silently dropped, no error at all.

The remaining 33 tests (all pre-existing, unrelated coverage plus the rewritten
verbatim-override test's replacement not yet present at this pre-fix checkout — see
below) passed identically, confirming the failures are isolated to exactly the 9 cases
targeting this bug.

**Result against the fix (`a0d9c27`, this run's branch tip): 42/42 passed.**

This 33/42 → 42/42 split, isolated to exactly the 9 new cases, is the positive
confirmation this test file exercises ISS-0079's specific bug and not some unrelated
always-passing or always-failing condition.

Additionally, cross-checked the pre-fix mechanism directly rather than relying only on
the empirical run: `lib/letflow/engine/pin_resolver.ex` at `main` (`f32b4f7`) shows
`resolve_one_ref/4`'s override branch as

```elixir
case find_override(overrides, kind, ref) do
  %{resolved_id: resolved_id, version: version} ->
    {:ok, %{kind: kind, ref: ref, resolved_id: resolved_id, version: version, source: :override}}
  nil ->
    ref |> lookup_fun.() |> interpret_lookup(kind, ref)
end
```

— `lookup_fun` is reachable only via the `nil` (no-override) branch; the override
branch returns `{:ok, ...}` built entirely from `find_override/3`'s own return value,
with no call to `lookup_fun` anywhere in that branch. This directly explains every
empirical failure above and confirms the worktree run measured the actual pre-fix
mechanism, not an artifact of the test environment.

Worktree removed after verification (`git worktree remove ../letflow-scratch-iss0079
--force`); no state left behind in the main working tree.
