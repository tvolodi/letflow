## 3. Part A — `mix letflow.check_toolchain`

### 3.1 Why the tests are shaped this way

The task's only public function is `run/1`. Every helper — the parser, the
Elixir comparison, the OTP major-only rule, the row rendering — is private,
and the pin file is read from the *current working directory* with no way to
pass a path. So no test can call the parse or the comparison rule directly.
Every test therefore drives the real `run/1` end to end against a fixture
`.tool-versions` written into a fresh temp directory that is made the working
directory for the duration of the call, capturing stdout and stderr
separately. Nothing in the module is mocked, stubbed, or refactored.

Two consequences, both deliberate:

- `async: false`. `File.cd!/2` moves the working directory for the whole VM,
  not for one process, so the file cannot run concurrently with itself. The
  cd window is held to the single `run/1` call for the same reason.
- Warnings are captured with `capture_io(:stderr, ...)`, because the task
  writes them to `:stderr` on purpose.

The test file does **not** shell out to a nested `mix test` the way
`letflow_check_test_test.exs` must; it calls `run/1` in-process, and the
whole file finishes in 0.4s.

### 3.2 No hardcoded toolchain version anywhere (AC11)

ISS-0106 *is* a cross-host toolchain-drift issue, so a test that only passes
on Elixir 1.20.3 / OTP 29 would be a fresh instance of the problem being
fixed. There is not one hardcoded version string in the test file. This was
ensured structurally, not by inspection:

- Every fixture is generated at run time from `System.version/0` and
  `List.to_string(:erlang.system_info(:otp_release))` — the same two sources
  the task itself reads — via the private helpers `running_elixir/0` and
  `running_otp/0`. These are functions, not module attributes, so they are
  evaluated when the test runs rather than when it was compiled.
- Every *off-pin* fixture is derived from the running value by
  `off_pin/1`, which appends `"9"`. The result differs from the running
  value in length, so it can never equal it on any host — inequality is a
  property of the construction, not of the host.
- The one literal that looks like a version, `.7.13`, is a *suffix* appended
  to the running OTP major (`"#{running_otp()}.7.13"`). It exists so that the
  erlang pin is always a full version that `otp_release` can never report,
  which is what forces the major-only rule to be exercised rather than
  bypassed. It is never compared to anything on its own.

### 3.4 The OTP major-only rule, and how a naive comparison fails (AC3)

`.tool-versions` must pin a *full* Erlang version (`erlang 29.0.5`) because
asdf requires one, but `:erlang.system_info(:otp_release)` reports only the
**major** (`~c"29"`). T-M2 pins `<running major>.7.13` and runs against a
host reporting `<running major>`, and asserts a clean match.

**If the rule were a naive full-string comparison,** the expected value would
be the whole token `<major>.7.13`, which can never equal the running
`<major>` — so the task would emit a `TOOLCHAIN OFF PIN` block on a
*correctly pinned* host, permanently, on every run. Because the warning is
deliberately unsuppressible, that false positive would train every reader to
ignore the one message the whole mechanism consists of. T-M2 then fails on
`assert stderr == ""` and on `assert stdout =~ "letflow.check_toolchain: OK"`.

This is not a prediction. It was measured — see mutant A in §4.2, which
turns `expected_otp_major/1` into exactly that naive comparison and takes the
file from 30/30 to 17/30.

### 3.5 F6 — how "unreadable" is induced for real

A *directory* named `.tool-versions` makes `File.read/1` return
`{:error, :eisdir}`. Measured on this host before the test was written:

```
F6 read(dir): {:error, :eisdir}
```

That is a real unreadable-file path through the shipped code, not a
simulated one, and it works the same on POSIX.

### 3.6 F7 — a stated limitation, and what the test does instead

**Finding.** F7 is the one failure mode with no portable external trigger.
Its condition is `File.cwd/0` returning `{:error, _}`, which happens when the
working directory ceases to exist. A process can arrange that on POSIX by
deleting its own cwd; **Windows refuses.** Measured on this host:

```
rm_rf own cwd:      {:error, :eacces, "...\\probe23526"}
File.cwd after rm:  {:ok, "c:/Users/tvolo/AppData/Local/Temp/probe23526"}
```

Two other candidate inductions were probed and rejected: an over-long cwd
(`File.cd` fails with `:eio`, so the cwd never changes) and invalid UTF-8 in
the pin file (the parse absorbs it — `[["elixir","1.2.3"], [<<255,254>>], []]`
— which is correct behaviour, not F7).

Making F7 directly inducible would need a public seam on the module — an
injectable path or an exposed comparison function — and **adding one is a
design change that routes through CODE-DESIGNER, not through TEST-DESIGNER.**
It is reported here rather than invented.

**What T-F7 does.** It performs the real induction (cd into a temp dir,
delete it, check `File.cwd/0`) and branches on whether the OS permitted it:

- *induced* (POSIX, e.g. the hetzner host): asserts the real F7 block —
  `TOOLCHAIN PIN NOT CHECKED`, `Could not determine the project directory`,
  and `run/1 == :ok`.
- *not induced* (Windows, this host): asserts the structural guarantee the
  branch rests on — that the cwd is obtained with the non-raising
  `File.cwd()` and never `File.cwd!`, and that the F7 branch text is present.

Either branch asserts something a regression would break; neither is a no-op
and the test is not skipped. On this host the second branch was taken.

### 3.7 F8 — induced for real, without touching the module

The MATCH path is the only path that writes to stdout, and `IO.puts/1`
raises `ArgumentError` when the process's group leader answers the Erlang IO
protocol with an error reply. Measured before the test was written:

```
IO.puts to error device: {:raised, ArgumentError,
 "errors were found at the given arguments:\n\n  * 1st argument: operation not supported (enotsup)\n"}
```

So T-F8 runs a matching fixture in a spawned process whose group leader is a
process that refuses every IO request. `check/0` then raises for real, from
inside, on a line that ships in the module. The outer guard must catch it,
report F8 on `:stderr` (a device registered by name, hence unaffected by the
group leader), and still return `:ok`. Nothing in the module is stubbed. The
group leader is swapped only inside a spawned process, so the test process
keeps its own.

An earlier variant used a *dead* group leader (also verified to raise, with
`ErlangError :terminated`). The refusing-device form was preferred because it
does not depend on `:erlang.group_leader/2` accepting a dead pid, which is
not a documented guarantee.

### 3.8 T-I5 — why a structural test is in a behavioural file

The design states that the absence of any build-aborting construct "is
checkable by grep over this file, and their presence would be a defect
regardless of the surrounding logic". T-I5 is that grep, run over the module
with its `"""`-delimited doc blocks stripped out — necessary because the
moduledoc names `File.read!/1`, `File.cwd!/0` and "Mix abort" in prose
precisely in order to say it does *not* call them, and would otherwise
register false positives against itself. (Same shape as the self-check recipe
in `lib/letflow/engine/variable_merge.ex`.)

It guards the "never fails the build" property against a future edit on a
path no behavioural test happened to exercise. It is the only structural test
in the file; every other test drives real behaviour.

## 5. ExUnit name-length check (AC8)

`docs/anti-patterns.md` records four separate occurrences of ExUnit's
255-character cap on `"test " <> describe <> " " <> test_name` being
exceeded, each of which failed the *entire* suite at compile time with
`SystemLimitError`. The anti-pattern entry says documentation alone has not
prevented recurrence, so this was measured rather than eyeballed.

A script extracted every `describe`/`test` pair from the new file and
computed the combined string ExUnit builds:

```
test/describe pairs found: 30

75  test failure modes F7 an unavailable working directory warns and returns ok
70  test failure modes F4 no erlang line reports NOT PINNED and returns ok
70  test failure modes F3 no elixir line reports NOT PINNED and returns ok
69  test parse contract a trailing comment is stripped from a pinned line
68  test matching pin the -otp-NN suffix is discarded and never compared

MAX = 75 chars
UNDER 200: OK (ExUnit hard cap is 255)
```

**Maximum measured combined length: 75 characters**, against a 200-character
working limit and a 255-character hard cap. Spec citations (`T-M2`, `T-F8`, …)
live in `#` comments above each test, never in the name string, which is what
keeps the names short.
