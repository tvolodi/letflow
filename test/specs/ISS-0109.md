## 1. Bug recap

Every ISS-0109 failure was a test that provisioned a real tenant schema through a
hand-rolled fixture whose **only** oracle was `assert {:ok, _} =
TenantProvisioning.replay_migrations(tenant_id)`. Ecto's migrator re-applies nothing for a
version already present in `schema_migrations`, so a schema can hold every version row and
still be missing the table one of them created. Against that state the old oracle returns
`{:ok, []}` and the fixture reports success; the damage surfaces hundreds of lines later as
an opaque `42P01` (or `3F000` when the whole schema is gone), by which time the state that
caused it is unrecoverable. The teardown's `DROP SCHEMA` / `DELETE` / `DELETE` triple
carried nothing identifying whose it was, which is what turned the diagnosis into a
five-hour reconstruction across a UTC-vs-local log skew.

The gap is at the **fixture layer**. Design §2 established there is no production defect,
and `lib/letflow/tenant_provisioning.ex` is unmodified (INV-F-2).

## 2. The fail-first position — stated honestly, because the literal form does not apply

WF-03 Step 4 normally requires checking out the pre-fix commit, running the new test, and
observing it **fail** there. **That form is impossible for this run, and this spec does not
pretend otherwise.**

The fix is a **new module**. Pre-fix, `Letflow.TenantFixture` does not exist, so
`test/letflow/support/tenant_fixture_test.exs` would not *fail* against the pre-fix commit —
it would not **compile**. A file that does not compile is evidence about nothing. No claim
of a pre-fix run of this test file is made anywhere in this spec or in the test code, and a
green post-fix run is **not** offered as fail-first evidence.

**What the fail-first property actually is here:** pre-fix **detection was absent on
identical database state**. The old fixture's entire oracle passes against a schema that is
missing a table; the new one fails against that same schema. This has been measured twice
already, and this spec cites those measurements rather than re-deriving them from argument:

| Measurement | Who | Result |
|---|---|---|
| `promotion_assertion_runs` dropped, version `20260818090001` left recorded, then a **second** `replay_migrations/1` | CODE-DESIGN-VALIDATOR, `handoffs/WF03-ISS0109-20260821/step-02b-code-design-validator.json` | returned `{:ok, []}` — and the table was **still absent** |
| The same constructed state, read through the new capture | ELIXIR-DEV, `handoffs/WF03-ISS0109-20260821/step-03-elixir-dev.json` | `tables_missing: ["promotion_assertion_runs"]`, `versions_missing: []` |

Same database state. Old oracle green, new oracle red. **That** is the regression proof.

**It is also re-derived mechanically, in one test, rather than only cited.** Test C1.2
below constructs the state and, in the same test body, runs *the pre-fix fixture's complete
oracle* (`assert {:ok, []} = TenantProvisioning.replay_migrations(tenant_id)`), confirms the
table is still absent, and then shows `assert_schema_complete!/2` raising on that same
state. That is the closest executable equivalent of a fail-first run available when the
"before" side of the comparison is an assertion that no longer exists in a file.

**Where an ordinary fail-first proof does exist**, design §7 says so per case: C1, C2 and C3
each construct a broken state that the *pre-fix* fixture accepts, so each of those three is
a direct behavioural before/after, not merely a new-function-exists test. C4, C5 and C6 fail
first trivially (the functions and the log line do not exist pre-fix), which design §7.4/§7.5/§7.6
already labels as the weaker form; they are not upgraded here beyond what they are.

**The one item with no fail-first proof at all**, per design §7.7: the two modules' adoption
of the helper is a zero-behaviour-delta refactor, and no test in this spec pretends
otherwise. Its evidence standard is **behaviour preservation**, not fail-first: both modules
pass in full, pre- and post-adoption. ELIXIR-DEV captured 8 and 12 passing before and 8 and
12 after; that pairing was re-run during this step (`20 passed` for the two modules
together, quoted in §6) and TEST-RUNNER re-derives it independently at Step 4b.

## 3. Case-by-case mapping — design §7 C1..C6 to named tests

All 14 tests live in `test/letflow/support/tenant_fixture_test.exs`. Every test that
constructs damage uses `provisioned_tenant!(teardown: false)` plus its own `on_exit/1`
cleanup, exactly as design §7 requires, so the fixture's own teardown can neither repair nor
race the state under assertion. Nothing depends on wall-clock timing, unseeded randomness,
concurrency, or a full-suite run; verified green at seeds `0`, `7` and `424242`.

### C1 — a table dropped while its migration version stays recorded (failure 14's state)

Construction: provision normally, then `DROP TABLE "<schema>"."promotion_assertion_runs"`,
leaving the schema, the other 18 tables, and every `schema_migrations` row intact.

1. **"is reported by the capture as exactly that one table missing."** Asserts
   `tables_missing == ["promotion_assertion_runs"]`, `versions_missing == []`,
   `schema_present? == true`, and that version `20260818090001` is still in
   `applied_versions`. *Why it exists:* `versions_missing == []` is the load-bearing half —
   it is what proves check 3 (versions) cannot see this failure and check 2 (tables) is not
   redundant with it. A test that asserted only `tables_missing` would leave the design's
   "neither subsumes the other" claim untested.
2. **"passes replay's old oracle and still fails the completeness check."** The regression
   test proper (§2). Runs the pre-fix oracle on the constructed state and asserts it returns
   `{:ok, []}`; asserts the table is *still* absent afterward; then asserts
   `assert_schema_complete!/2` raises an `ExUnit.AssertionError` whose message names
   `promotion_assertion_runs` and `tables_missing`. *Why it exists:* it is the before/after
   comparison itself, executed rather than argued.

### C2 — a schema dropped with its registration row left in place (failure 3's state)

Construction: provision normally, then `DROP SCHEMA "<schema>" CASCADE`, leaving the
`tenant_schemas` row.

3. **"is captured as observed-absent with the registration still present."** Asserts
   `schema_present? == **false**` (observed absent, not `nil`), `registration_present? ==
   true`, `provisioned_at != nil`, `tables_present == []`, `tables_missing` equal to the
   full 19-table oracle, and that `assert_schema_complete!/2` raises naming
   `information_schema.schemata`. *Why it exists:* it pins the `false` end of the
   `boolean() | nil` distinction (see §4) and, in the same construction, exercises the
   §3.5 derived-field rule naturally: `"<schema>".schema_migrations` is unreadable once the
   schema is gone, so `applied_versions` is **unobserved** and the test asserts
   `versions_missing == []` — *not* all 31 manifest versions. An unobserved set reported as
   an observed absence is precisely the false accusation INV-F-10 forbids.
4. **"characterization only: re-provisioning returns ok and leaves it empty."** Explicitly
   labelled a **characterization** test in the code and here, per design §7.2's warning:
   it pins the *documented* idempotency of `provision_tenant_schema/1` (it returns `{:ok,
   %Registration{}}` and recreates an empty schema), and is **not** a regression assertion —
   there is no production behaviour change. It then asserts the fixture now catches the
   empty schema re-provisioning leaves behind (all 19 tables missing).

### C3 — a replay that stopped short

5. **"is reported alongside the table that version created."** Construction: delete the
   **highest** manifest version (`20260821000002`) from `"<schema>".schema_migrations` and
   drop the table it creates (`variable_schemas`). Asserts `versions_missing ==
   [20260821000002]`, `tables_missing == ["variable_schemas"]`, and that the raised message
   names both. *Why it exists:* it is the mirror image of C1 — the case check 3 catches and
   check 2 alone would report only half of. Together C1 and C3 prove both checks are
   required.

### C4 — capture fidelity, the INV-F-4 negative case, the §3.5 failure boundary

6. **"reports every field faithfully on one clock basis"** (healthy tenant). Asserts
   `schema_name`, `tenant_id`, `registration_present? == true`, `schema_present? == true`,
   `provisioned_at`/`migrations_applied_at` non-nil, `tables_missing == []`,
   `versions_missing == []`, `pg_backend_pid` an integer, `assert_schema_complete!/2 ==
   :ok`, and two clock checks: `|db_now - observed_at_utc| < 120s` (a **bound**, not
   equality — its purpose is to catch a *basis* error such as local time wearing a `Z`, the
   skew that cost the diagnosis five hours, not to police microsecond jitter) and
   `observed_at_utc >= provisioned_at`.
7. **"returns ok for a wholly absent tenant instead of raising"** — **INV-F-4's negative
   case**. A freshly generated UUID with no registry row and no schema returns `{:ok,
   state}` with `registration_present? == false` and `schema_present? == false`, and does
   **not** raise. Also asserts `versions_missing == []` for the same unobserved-set reason
   as C2.
8. **"returns capture_failed only for a failure outside the field guards."** A malformed
   `tenant_id` (`"not-a-uuid"`) yields `{:error, {:capture_failed, exception}}` whose message
   names the offending argument. *Why it exists:* §3.5 makes the boundary **normative** —
   `{:error, {:capture_failed, _}}` is the outer net only, reachable when *no* field can be
   attempted, and never by a single field's query failing. This test pins the one documented
   route to it; tests 9 and 10 pin the other side of the same boundary.
9. **"degrades a failed field to nil and never to an observed absence."** *The distinction
   test.* Runs the capture on a **healthy** tenant from inside a deliberately aborted
   transaction, so every per-field query raises at once. Asserts `registration_present? ==
   nil` **and** `refute … == false`, same for `schema_present?` — see §4. Asserts both
   derived pairs degrade to `[]`: `tables_missing == []` with `tables_present == []`, and
   `versions_missing == []` with `applied_versions == []`. Asserts the oracle has 19 entries
   and the manifest is non-empty, so the numbers a naive derivation would have produced (19
   and 31) are shown to be non-zero rather than assumed.
10. **"does not fail a passing test when the capture itself degraded"** — **INV-F-10**. In
    the same aborted-transaction condition, `assert_schema_complete!/2` returns `:ok` for a
    healthy tenant (proved by a message that is only sent if the call did not raise), and the
    same tenant then passes the assertion normally outside the transaction, so nothing was
    masked. *Why it exists:* if `nil` and `false` were interchangeable, a diagnostic whose
    own query failed would turn a green test red — the exact defect REVIEWER's step-03d
    ruling corrected in the design.

### C5 — the teardown log line and the closed phase vocabulary

11. **"emits one marked teardown line naming the schema and its presence."** Asserts
    **exactly one** line containing the literal marker `LETFLOW_TENANT_FIXTURE`, with
    `phase=teardown` (from the closed vocabulary), `schema=<schema>`, `tenant_id=<id>` and
    `schema_present_before_drop=true`. *Why it exists:* this line is the whole of scope item
    B — a `phase=teardown` line in a raw log is, by construction, a post-test teardown and
    never a mid-test drop, which is the inference ISS-0109's diagnosis had to re-establish
    by hand.
    **Mechanism, and why it is not `capture_log/1`:** `ExUnit.CaptureLog` installs and
    removes its handler around a function call made *inside the test body*, and the
    fixture's teardown runs from `on_exit/1`, after the test process has exited — no
    `capture_log/1` wrapper written in a test body can span it. The test therefore installs
    a minimal `:logger` handler (`…TenantFixtureTest.LogCollector`, filtered to the marker,
    collecting into an unlinked `Agent`) from an `on_exit/1` callback ordered **LIFO** to run
    *before* the fixture's teardown callback, and asserts from a second callback ordered to
    run *after* it. The alternative — making the teardown callable from a test body — would
    have required modifying `test/support/tenant_fixture.ex`, which both gates passed and
    this step must not touch.
12. **"logs a failure phase under CaptureLog and never phase=teardown"** — the
    closed-vocabulary half, and this one *is* under `ExUnit.CaptureLog.capture_log/1`,
    because failure-path lines are emitted synchronously in the test body. Asserts the log
    contains `LETFLOW_TENANT_FIXTURE phase=incomplete_schema` and the missing table's name,
    and `refute log =~ "phase=teardown"`.
13. **"emits no teardown line while the test body is still running"** — also under
    `capture_log/1`. A successful `provisioned_tenant!/1` emits no `phase=teardown` line
    during the test. *Why it exists:* the vocabulary's guarantee is only worth something if
    `teardown` is emitted **exclusively** on the teardown path; tests 11–13 together pin
    both directions.

### C6 — the oracle-rot guard (design §3.3, INV-F-7)

14. **"observed tables equal expected_tenant_tables/0 in both directions."** Provisions one
    throwaway tenant and asserts `expected -- observed == []` **and** `observed -- expected
    == []`, each with a message naming the offending tables. *Why it exists:* it is what
    makes the hard-coded 19-entry list safe to hard-code — the day a 32nd manifest entry
    lands that creates a table, this test fails loudly instead of the oracle quietly
    weakening.
    **Binding constraint honoured (REVIEWER step-03d ruling 3):** the observed set is read
    from `capture_schema_state/1`'s `tables_present`, **not** from a raw
    `information_schema.tables` query. `tables_present` excludes `schema_migrations` (whose
    contents are captured separately as `applied_versions`) and `expected_tenant_tables/0`
    excludes it too, so unfiltered set equality holds in both directions. A raw catalog read
    would return `schema_migrations` and fail the second direction spuriously — the test
    would go red for the wrong reason.

## 4. The `boolean() | nil` distinction is asserted as a distinction

Design §3.2 (as corrected at step-03d) types `registration_present?` and `schema_present?`
as `boolean() | nil`, where **`false` = observed-absent** and **`nil` = not-observed**.
Treating them as interchangeable erases the property the correction exists to protect —
`schema_present?: false` from a *failed* schemata query would make `assert_schema_complete!/2`
raise against a perfectly healthy schema (INV-F-10).

Both ends are asserted, and asserted against each other:

| Condition | `registration_present?` | `schema_present?` | Test |
|---|---|---|---|
| Healthy tenant | `true` | `true` | 6 |
| Registration row present, schema really dropped | `true` | **`false`** | 3 |
| Nothing exists at all | **`false`** | **`false`** | 7 |
| Healthy tenant, every query failing | **`nil`** (with `refute == false`) | **`nil`** (with `refute == false`) | 9 |
| Healthy tenant, every query failing, assertion run | — | — | 10: returns `:ok`, does not raise |

Test 9's explicit `refute state.schema_present? == false` alongside `assert … == nil` is
deliberate: `assert x == nil` alone would still pass under a hypothetical implementation
that conflated them only in one direction, and the pair states the distinction as the
property rather than as a coincidence of one value.

## 5. Test-name length — measured mechanically

ExUnit's test name becomes an atom; this repo has broken its own full suite **four** times
on the 255-character limit (`docs/anti-patterns.md`, PR #351). Names were measured, not
eyeballed, over the full `"test " <> describe <> " " <> name` string ExUnit constructs:

```
$ awk '/^  describe "/ { match($0, /"(.*)" do/, a); d=a[1]; next }
       /^    test "/ { match($0, /test "(.*)" do/, b); print length("test " d " " b[1]) }' \
      test/letflow/support/tenant_fixture_test.exs | sort -rn | head -1
140
```

**Measured maximum: 140 characters (141 bytes — one name contains a `§`), on**
`test C4 -- capture_schema_state/1 failure boundary (design §3.5, INV-F-4) returns
capture_failed only for a failure outside the field guards`. That is 115 characters of
headroom under the 255 limit.
