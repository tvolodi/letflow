# Test Spec: ISS-0216 — `Letflow.Api.Pagination.decode_cursor/4` empty-prefix bypass

**Issue:** ISS-0216.
**Design:** `lib/letflow/design/iss0216-pagination-prefix-guard.md`.
**Fix:** `lib/letflow/api/pagination.ex` — `check_prefix/2` gains a new leading
function-head clause (`defp check_prefix(_decoded, "")`) that raises `ArgumentError`,
placed ahead of the existing size/`String.starts_with?/2` clause, which is otherwise
unchanged — commit `2b0d881`.
**Test file:** `test/letflow/api/pagination_test.exs`
(`Letflow.Api.PaginationTest`, `describe "decode_cursor/4 and prefix validation
(AC3)"`, 2 new tests).
**Run:** `WF03-ISS0216-20260826`, WF-03 Step 4.

## Criterion

`decode_cursor/4` delegates its cross-endpoint isolation check to `check_prefix/2`,
which (pre-fix) computed:

```elixir
byte_size(decoded) >= byte_size(prefix) and String.starts_with?(decoded, prefix)
```

When `prefix == ""`, `byte_size(prefix) == 0`, so the size guard is true for every
`decoded` binary, and `String.starts_with?(decoded, "")` is `true` unconditionally per
Elixir's own documented semantics (every binary "starts with" the empty string). Both
conjuncts pass regardless of what `decoded` actually contains, so `check_prefix/2`
returned `:ok` for **any** decoded payload whenever `prefix` was `""` — defeating the
cross-endpoint cursor isolation `decode_cursor/4`'s own moduledoc documents this
parameter as providing. A cursor minted by one endpoint (e.g. under `"T:"`) would be
silently accepted by a hypothetical caller that passed `""` as its own prefix, exactly
as if it had been minted under that endpoint.

After the fix, `check_prefix/2`'s new leading clause intercepts `prefix == ""` before
the size/`starts_with?` logic ever runs, and raises `ArgumentError` (a caller-contract
violation, not payload validation — hence a raise rather than an `{:error, atom}`
tuple, consistent with `decode_cursor/4`'s own `@spec`, which is left unchanged: `raise`
is not itself a return type in the `@spec`, so no signature change was required or
made).

## Why these two cases, and how they avoid the vacuity trap

The obvious single test — `decode_cursor(encoded, "", 2)` raises `ArgumentError` — is
already behavioral (not name-resolution): pre-fix, `check_prefix/2` runs and returns
`:ok`, so no exception happens at all and the test genuinely fails for the reason the
issue describes. Two cases are included rather than one because a single case leaves a
question about *what* triggers the raise open to a lazier "fix" (e.g. one that special-
cases only well-formed 2+-colon cursors) that would still close ISS-0216's literal
GH-facing report without closing the actual defect (`check_prefix/2` never inspects
`decoded`'s shape at all — the defect is purely in the prefix argument).

1. **A realistic cursor, matching the design's own worked example** (`"T:"`, a real
   timestamp, a real key) — proves the raise fires on the exact call shape every real
   route handler in `lib/letflow/routers/*` and `lib/letflow/{tasks,instances,
   definitions}.ex` would make if one of them ever regressed to passing an empty
   prefix.
2. **A payload with no colons at all** (`"anything"`) — proves the raise is
   unconditional on `prefix == ""` alone, independent of `decoded`'s shape. This rules
   out an implementation that only rejects empty-prefix-and-malformed-cursor
   combinations, which would still leave well-formed-cursor-plus-empty-prefix as a live
   bypass (the actual ISS-0216 exploit shape) unaddressed.

Neither case depends on wall-clock time beyond using `System.system_time(:microsecond)`
to mint a *fresh, unexpired* cursor for case 1 — the same non-flaky pattern the
suite's other AC3/AC4 cases already use (a cursor built "just now" can never be
`:expired ` against a 24h window without a race). Case 2 needs no timestamp at all: the
raise happens in `check_prefix/2`, executed by `decode_cursor/4`'s `with`-chain before
`extract_expiry_timestamp/2` or `check_expiry/2` ever run, so an arbitrary payload with
no timestamp-shaped suffix is sufficient and deliberately used to keep that
independence visible in the test itself.

## Deliberately not tested

No test exercises a non-`binary()` `prefix` (e.g. `nil`, an atom) — the design's §5
explicitly scopes this fix to the empty-string case only; `decode_cursor/4`'s own
`@spec` already types `prefix :: String.t()`, and guarding non-conforming types was
called out as out-of-scope by both CODE-DESIGNER and REVIEWER (step-03c) to avoid
scope creep beyond ISS-0216's actual report.
