# Test Spec: ISS-0220 — `Letflow.SandboxPool` claim/release call-timeout budgets

**Issue:** ISS-0220 / GH#450 / `letflow-queue` task 220.
**Design:** `lib/letflow/design/iss0220-sandbox-pool-provision-timeout.md` (the
regression-test contract this spec implements is its §10).
**Fix:** `lib/letflow/sandbox_pool.ex` — `@call_timeout_buffer_ms 5_000` deleted and
replaced by `@default_provision_timeout_ms 44_000` plus three new public functions
(`provision_timeout_ms/0`, `claim_call_timeout/1`, `release_call_timeout/0`), with
`claim/2` and `release/2` deriving their `GenServer.call/3` timeouts from them —
commit `451201b`.
**Test file:** `test/letflow/sandbox_pool_call_timeout_test.exs`
(`Letflow.SandboxPoolCallTimeoutTest`, 4 tests).
**Run:** `WF03-ISS0220-20260822`, WF-03 Step 4.

## Criterion

`claim/2` conflated two unrelated waits into one number. `max_wait_ms` bounds **queue
parking only** — how long a caller may sit in the pool's `waiting` queue — yet
`claim/2`'s `GenServer.call/3` timeout was `max_wait_ms + @call_timeout_buffer_ms`
with `@call_timeout_buffer_ms = 5_000`, a constant whose own comment states it was
sized so the call timeout would "not be smaller than `GenServer.call`'s own default
5_000" — a statement about `GenServer`'s default, never about what provisioning
costs. That made 5_000 ms the **entire budget** for `provision_sandbox/0`: one
`CREATE SCHEMA` plus `Ecto.Migrator.run/4` over all 31 tenant-scoped migrations, 32
transactions. Measured provisionings reach 15 373 ms (design §4.1), so correct work
was being converted into caller-side `{:timeout, {GenServer, :call, …}}` exits.
`release/2` carried the same defect in a third form: it called `GenServer.call/2`
with no timeout argument at all, i.e. the implicit 5_000 ms default (design §3.2).

After the fix:

1. The provisioning budget is a named, configurable, publicly derivable quantity —
   `provision_timeout_ms/0`, defaulting to the measurement-derived 44 000 ms
   (design §4.5), overridable via
   `config :letflow, :sandbox_pool, provision_timeout_ms: n`.
2. `claim/2`'s call timeout is `max_wait_ms + provision_timeout_ms()` — the queue wait
   the caller asked for **plus** one calibrated provisioning, not instead of it.
3. `release/2`'s call timeout is `provision_timeout_ms()`, so the release path has a
   *derived* bound rather than `GenServer.call/2`'s implicit default.

## Why these cases, and how they avoid the vacuity trap (design §10.1)

The obvious test — asserting the new constant equals the new constant — would pass
against any value the implementation happened to pick, and would "fail" pre-fix only
because a function does not exist yet. That is a name-resolution failure, not a
behavioural one, and WF-03 Step 4 says it proves nothing.

So the two load-bearing cases pin the derived number **where it is actually
consumed**: inside a real `GenServer.call/3`'s own timeout exit reason.
`GenServer.call/3` exits with `{:timeout, {GenServer, :call, [server, request,
timeout]}}`, and that third list element *is* the integer the client computed.
Matching on it is a direct behavioural observation of the derivation.

**The black-hole technique.** `claim/2`'s `pool` argument is a `GenServer.server()` —
any pid. A process that receives and never replies
(`spawn(fn -> Process.sleep(:infinity) end)`) makes the call run to its **full**
timeout deterministically, with zero schemas created, zero dependence on real
provisioning latency (the test's runtime is exactly the tiny configured budget), and
no stale reply left in the mailbox. A test *about* a timing defect that was itself
timing-sensitive would be self-defeating; this one is not, and needs no database at
all — hence plain `ExUnit.Case`, not `Letflow.DataCase`. `async: false`, because
RT-1..RT-3 mutate `Application.env` at runtime.

Rejected alternatives, for the record: `:sys.suspend/1` on a real pool leaves the
`{:"$gen_call", …}` queued for after `:sys.resume/1`, provisioning a sandbox for a
dead caller; and racing a real provisioning against a tiny budget makes the test
depend on the very latency distribution it is meant to be independent of.

## The four cases, and which ones carry fail-first weight

| Case | Pre-fix outcome | Fail-first weight |
|---|---|---|
| RT-1 | `UndefinedFunctionError` — `claim_call_timeout/1` does not exist | **none** |
| **RT-2** | **observed 5000 / 7000 against expected 1234 / 3234** | **yes** |
| **RT-3** | **observed 5000 against expected 1234** | **yes** |
| RT-4 | `UndefinedFunctionError` — `provision_timeout_ms/0` does not exist | **none** |

**Only RT-2 and RT-3 are the fail-then-pass demonstration.** RT-1 and RT-4 are drift
guards that happen to be unwritable pre-fix; they are reported as such and are not
counted toward Step 4's evidence. Both observed outcomes below are real output from a
run against the pre-fix module, not predictions.

### RT-1 — the derivation is a function of the configured budget

Under a `provision_timeout_ms: 1_234` override: `claim_call_timeout(w) == w +
provision_timeout_ms()` for `w ∈ {0, 1, 1_000, 2_000, 60_000}`, and
`release_call_timeout() == provision_timeout_ms()`.

*Why it exists:* **on its own this IS the tautology §10.1 warns about** — it asserts
the derivation equals itself. It is a drift guard on the two derivations and is
meaningful **only in combination with RT-2/RT-3**, which observe the same two numbers
behaviourally. The test carries that caveat in its own comment so a future reader does
not mistake it for the substance of the contract.

*Pre-fix:* `UndefinedFunctionError`. **No fail-first weight.**

### RT-2 — a config override is honoured end-to-end by a real `claim/2` call

Under the same `1_234` override, against a black hole `hole`:

```
assert {:timeout, {GenServer, :call, [^hole, {:claim, 0}, 1_234]}} =
         catch_exit(SandboxPool.claim(0, hole))
assert {:timeout, {GenServer, :call, [^hole, {:claim, 2_000}, 3_234]}} =
         catch_exit(SandboxPool.claim(2_000, hole))
```

*Why it exists, and why it is not vacuous:* it observes the real public `claim/2`
making a real `GenServer.call/3`, and pins two things at once — that the config
override reaches the client at all, **and** that `max_wait_ms` is *added to* rather
than *replaced by* the budget. The second assertion is what makes `1_234` vs `3_234`
discriminating; a single assertion at `max_wait_ms = 0` could not tell those two
derivations apart. `1_234` is deliberately distinctive and non-round, so a passing
match cannot be a coincidence of some other default.

*Why it is runnable pre-fix:* the expected timeouts are written as **literals** derived
from the config value the test itself sets, so the assertion depends on no function
introduced by the fix. **One of the two cases carrying fail-first weight.**

*Pre-fix:* observed `5000` (i.e. `0 + 5_000`) and `7000` (i.e. `2_000 + 5_000`) — the
override ignored entirely. Both matches fail.

### RT-3 — `release/2` uses the budget, not `GenServer`'s 5 000 ms default

```
assert {:timeout, {GenServer, :call, [^hole, {:release, ^sandbox_id}, 1_234]}} =
         catch_exit(SandboxPool.release(sandbox_id, hole))
```

*Why it exists:* this pins design §3.2 — the mis-sizing nobody named. Without it
nothing prevents `release/2` silently reverting to `GenServer.call/2`. That matters
beyond tidiness: `Letflow.Definitions.safe_release/2` is the wrapper written
specifically to contain release failures, and it contains them with `rescue`, which
**structurally cannot catch the `exit` a call timeout raises** — so an over-budget
release escapes its own containment, on the path that is already handling an
exception. This is the same `rescue`-doesn't-catch-`exit` shape ISS-0048 was about,
recurring one function away.

**The second of the two cases carrying fail-first weight.**

*Pre-fix:* observed `5000` against the expected `1_234`. Match fails.

### RT-4 — the shipped default is in force

With **no** `:provision_timeout_ms` key configured anywhere (the shipped state per
design §6, which is exactly what makes this a real observation rather than a
restatement of a config file): `provision_timeout_ms() == 44_000`, plus
`< 60_000` and `> 15_373`.

*Why it exists:* the equality is an honest change-detector, justified **only** because
this entire issue is a number silently left un-sized; its comment names design §4 so
that changing it forces re-reading the derivation. The two inequalities are **also
drift guards, not independent properties** — given the equality they are strictly
implied and can never fail on their own. They earn their place purely as documentation
of the ceiling (ExUnit's per-test timeout, §4.4) and the hard exclusion (floor 1, the
highest observed legitimate provisioning, §4.1) on the same screen as the number they
bound. They are not reported as separate coverage.

A `refute Keyword.has_key?(…, :provision_timeout_ms)` precondition guards the case
from being quietly satisfied later by a config file that starts setting the key.

*Pre-fix:* `UndefinedFunctionError`. **No fail-first weight.**

## §8.0 — no existing assertion was weakened

Stated explicitly, because a reviewer reading `git diff 2151bb9 451201b --
test/letflow/sandbox_pool_test.exs` sees a set of raised timeouts and would be right to
suspect a weakened test. It is not one. That diff (81 lines changed in one file, ELIXIR-DEV's,
not this step's) contains **no** removed test, no `@tag :skip`, no tag exclusion, no
`async` change, no relaxed pattern or equality, and no `assert` converted to a
`refute`/`assert_raise`. What changed is exclusively:

- three literal rendezvous bounds (`3_000`, `3_000`, `2_000`) replaced by
  `claim_rendezvous_timeout/1` / `pool_op_rendezvous_timeout/0`, both derived from
  `SandboxPool.claim_call_timeout/1` / `release_call_timeout/0` plus a separate,
  visibly small `@rendezvous_slack_ms 1_000`;
- `wait_until_schema_dropped/2` re-bounded by a monotonic-time deadline instead of an
  attempt count, with the identical `flunk/1` message and the identical `:ok` result.

A rendezvous bound is not an assertion about the system under test; it is the patience
of the observer. Each test still proves exactly what it proved before: the queued
waiter *is* served with a **different** sandbox id and a **real** schema in
`information_schema.schemata`; the killed owner's schema *is* dropped for real and its
quota slot *is* freed; the held claim *is* untouched by a timed-out waiter;
`max_wait_ms <= 0` *is* rejected without ever queueing.

Nothing in `test/letflow/sandbox_pool_call_timeout_test.exs` touches, relaxes or
duplicates any of that — it is a new file adding four cases and removing none.

## Deliberately not tested

Per design §10.4: **no test runs the suite at `TEST_PARALLEL_N=4` to "prove" ISS-0220
is fixed.** That is a load-dependent, non-deterministic observation costing ~20
minutes, whereas RT-1..RT-4 pin the actual defect deterministically in milliseconds. A
green N=4 run remains useful **corroboration** for RELEASE-VALIDATOR — the pre-fix base
rate was 2 of 2 red, including one run with sibling workspaces verifiably idle — but the
signal is asymmetric: a red N=4 run landing in the ISS-0220 files is near-conclusive
that the fix did not land, while a green one is also what a lucky run looks like.
RT-1..RT-4 are the proof.
