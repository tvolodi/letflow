# Test Spec: ISS-0224 — `Letflow.SandboxPool` provisioning must not block the pool's mailbox

**Issue:** ISS-0224 / GH#457 / `letflow-queue` task 224.
**Design:** `lib/letflow/design/iss0224-sandbox-pool-async-provisioning.md` (the
regression-test contract this spec implements is its §10, as amended by rework
rounds 1 and 2).
**Fix:** `lib/letflow/sandbox_pool.ex` — every `Repo` call moved out of the pool's
callbacks into a single serialized `Task.Supervisor.async_nolink/3` worker, with a
FIFO `db_queue` of `{:provision, _}` / `{:drop, _}` ops and at most one `in_flight`;
plus `lib/letflow/application.ex` gaining `{Task.Supervisor, name:
Letflow.SandboxPool.TaskSupervisor}` **before** `{Letflow.SandboxPool, []}` — commit
`011df42`.
**Test file:** `test/letflow/sandbox_pool_test.exs`, new `describe "provisioning does
not block the pool's mailbox (ISS-0224 regression)"` block (RT-1..RT-8), plus three
new helpers (`sandbox_schema_names/0`, `query_without_holding/1`, `spawn_claimer/3`)
and their supporting pollers.
**Comment-only correction:** `test/letflow/definitions/promotion_assertion_rerun_test.exs`
(design §9.1) — no assertion, bound or technique changed.
**Run:** `WF03-ISS0224-20260822`, WF-03 Step 4.

## Criterion

`handle_call({:claim, max_wait_ms}, from, state)` dispatched to
`handle_provision_now/2`, which called `provision_sandbox/0` — a `CREATE SCHEMA` plus
a replay of 31 migrations — **inside the pool's own callback**. `service_next_waiter/1`
did the same. A `GenServer` executing a callback processes no other message, so for
the whole duration of one provisioning the pool's mailbox was frozen, including a
parked waiter's own `Process.send_after`-scheduled `{:claim_timeout, _}`.

`claim/2`'s `@doc`, the moduledoc's "Two budgets" section and `req039-…md` §4.4 step 3
all state that `max_wait_ms` bounds **queue parking only**. None says "plus one
provisioning". It is therefore a documented-contract violation at any magnitude, and
the magnitude is unbounded by anything the contract names — not `max_wait_ms`, not
`provision_timeout_ms/0` (a caller-side allowance that aborts nothing).

Measured pre-fix at `max_wait_ms: 200`: waiter overshoot 246–320 ms, with the waiter's
reply latency equal to the concurrent provisioning's latency **to the millisecond** in
19/20 runs. Post-fix the design's prototype measured overshoot at 1–3 ms.

After the fix:

1. No `Repo` call runs inside any pool callback. Provisioning and `drop_schema/1` alike
   run in one serialized worker Task, so at most one DB operation is ever in flight and
   peak `DBConnection` demand attributable to the pool stays at 2 — exactly what the
   fully-synchronous module peaked at.
2. `max_wait_ms` is honoured: a parked waiter's timer message is serviced on schedule
   even while another caller is being provisioned.
3. A slot is reserved and its owner monitored **before** any DB work starts, closing the
   window in which a claim-in-progress had no owner monitor at all.
4. Five death paths — parked waiter, owner-dies-during-provisioning, owner-dies-with-a-
   queued-reservation, worker-Task-crash, owner-dies-on-top-of-its-own-release-DROP —
   each leak neither a quota slot nor a Postgres schema, and none takes the pool down.

## How these cases avoid the two traps (design §10.1)

**Trap 1 — failing pre-fix for the wrong reason.** A test that calls a function the fix
introduces fails pre-fix with `UndefinedFunctionError`/`KeyError`, which proves the
function exists, not that the defect did. Both cases carrying fail-first weight
(RT-2, RT-7) therefore use only the shipped public surface — `start_link/1`, `claim/2`,
`release/2` — and observe only wall-clock latencies. The cases that need post-fix-only
introspection (`in_flight`, `db_queue` via `:sys.get_state/1`) are the death-path cases,
which the contract requires as *coverage* but explicitly not as fail-first
demonstrations; each is labelled **post-fix-only** in its own comment and below.

**Trap 2 — a "mechanism" assertion that is really a race.** Round 0's RT-2(c) ("the
first completion message has `label == :w2`") was called "immune to absolute timing
noise" and marked a deterministic pre-fix failure. Measured against the shipped pool it
held **3/20** in CODE-DESIGNER's window, **5/20** in CODE-DESIGN-VALIDATOR's and **0/20**
in a third — a biased coin flip, which would have licensed a regression test that goes
green against unfixed code roughly a quarter of the time. **It is deleted, not repaired,
and is not implemented here.** The surviving load-bearing assertion is RT-2**(d)**, and
the test's own comment says so, so a future reader does not re-add the ordering
assertion as an "improvement".

## The eight cases, and which carry fail-first weight

| Case | What it probes | Pre-fix outcome | Fail-first weight |
|---|---|---|---|
| RT-1 | control arm: the timer itself works when nothing provisions | **passes** (by design) | none |
| **RT-2** | a parked waiter's `max_wait_ms` vs. a concurrent provisioning | **(d) red: `t_w2 = 507 ms` against `t_w1 = 520 ms`** | **yes** |
| RT-3 | death path (a) — caller dies while parked in `waiting` | **passes** (INV-SP-6 guard) | none |
| RT-4 | death path (b) — caller dies **during** its provisioning | flunks: no `in_flight` in the pre-fix state | none (post-fix-only) |
| RT-5 | death path (b') — caller dies with its reservation **queued** | flunks: no `db_queue` in the pre-fix state | none (post-fix-only) |
| RT-6 | death path (c) — the provisioning **worker Task** crashes | flunks: no worker to kill pre-fix | none (post-fix-only) |
| **RT-7** | a DB-free `claim(0)` vs. a concurrent provisioning | **(c) red: `t_probe = 453 ms` against `t_b = 486 ms`** | **yes** |
| RT-8 | death path (e) — owner dies on top of its own release-DROP | flunks: no deferred DROP pre-fix | none (post-fix-only) |

**Only RT-2 and RT-7 are the fail-then-pass demonstration**, and per design §10.3 both
are required — neither may be dropped, and RT-2(d) may not be replaced by a
message-ordering assertion. RT-1 and RT-3 pass on both sides by design; RT-4/5/6/8 are
mandatory death-path *coverage* whose techniques have no pre-fix analogue, so they are
reported as such and are not counted toward Step 4's evidence. All observed outcomes
below are real output from real runs, not predictions.

### The shared vacuity floor, and why it is not a new constant

RT-2(a) and RT-7(a) are **premise guards**, not tolerances: each `flunk/1`s, naming the
measured value, if the concurrent provisioning it depends on came in under
`@vacuity_floor_ms = 200`. Below that threshold the defect cannot exist at all, so a
green ratio would be vacuous rather than informative.

The value is **reused, never re-derived here**: design §10.4 governs it, from six
independent measurement windows whose lowest observed single provisioning is 411 ms
(ISSUE-FIXER, ~1500 samples), with the validator's own fresh 150-sample round-2 window
putting the minimum at 423 ms. 200 ms sits 2.06× below the governing figure. **One**
value serves both guards deliberately — they guard the same quantity class (one
provisioning latency) — so the count of new constants in this contract remains **zero**.
Everything else is either a ratio of two quantities measured inside the same test on the
same host (RT-2(d), RT-7(c)) or a polling bound derived from
`SandboxPool.release_call_timeout/0` via the helpers this file already had.

### RT-1 — CONTROL: a parked waiter times out on schedule when nothing is provisioning

Pool `max_concurrent: 1`. O claims the only slot and never releases it. W1 parks with
`max_wait_ms: 60_000`; W2 parks **behind** W1 with `max_wait_ms: 50`.

Asserts W2 gets `{:error, :sandbox_unavailable}` with `t_w2 >= 50`, that W1 is never
served (read from the pool's own `waiting`/`active` state plus a zero-cost
`refute_received`, rather than by waiting out a `refute_receive` window that would add a
bound), and that after killing W1 and releasing O no `sandbox_%` schema survives.

*Why it exists:* on its own it asserts nothing about ISS-0224. Its whole job is to make
RT-2's failure **attributable to the mailbox blocking rather than to the timer** — if
the `{:claim_timeout, _}` machinery were simply broken, RT-1 would be red too and RT-2
would prove nothing. It is the arm that is identical to RT-2 in every respect except the
one variable under test.

*Pre-fix:* passes. **No fail-first weight**, by construction.

### RT-2 — FAIL-FIRST #1: `max_wait_ms` is honoured while a different waiter is provisioned

Identical to RT-1 except **O releases** once both waiters are confirmed parked, so W1 is
promoted and provisioned while W2's 50 ms timer runs. `t_w1` and `t_w2` are each measured
with `System.monotonic_time/1` **inside** their own claimer process, around the `claim/2`
call only.

- **(a) premise** — `t_w1 >= 200`, else `flunk/1` naming the measured value and §10.4.
- **(b)** — W1's result is `{:ok, %SandboxClaim{}}`, W2's is
  `{:error, :sandbox_unavailable}`.
- **(d) the load-bearing fail-first** — `2 * t_w2 < t_w1`.

*Why (d) is not vacuous and needs no constant:* it is a ratio of two quantities measured
inside this same test on this same host, so a slow or fast host moves both sides. Pre-fix
it is false because W2's reply is gated on W1's provisioning rather than on W2's own
timer — the pool is inside the release callback, which does the DROP, promotes W1, and
provisions it, all before it looks at the mailbox again. Post-fix the smaller side
contains no DB work at all: the design's prototype measured `t_w2 ∈ [51, 53]` against
`w2_wait = 50` (overshoot 1–3 ms) and a minimum ratio `t_w1/t_w2` of 7.91, i.e. ~4×
headroom over the 2× threshold.

*Ordering is not raced:* W1 is spawned and confirmed parked before W2 is spawned, so W2
is genuinely behind W1 in the FIFO queue and the window between W2 parking and the test
observing it is one 5 ms poll interval rather than however long two spawns happen to take.

*Pre-fix, four independent runs (real output, §"Fail-then-pass verification" below):*
`t_w2 = 507 / 520`, `498 / 513`, `656 / 665`, `572 / 591` ms — W2's reply tracks W1's
provisioning to within 9–19 ms every time. **Red in 4/4.**

### RT-3 — death path (a): the caller dies while parked in `waiting`

Pool `max_concurrent: 1`; O holds the slot; W parks with `max_wait_ms: 60_000`; the test
polls until `:queue.len(waiting) == 1`, kills W, and polls until it is 0.

Asserts **no schema leak** (the only sandbox schema in existence is still O's — a parked
waiter never had one provisioned for it), **no slot leak** (after O releases, a fresh
`claim(0, pool)` succeeds), and that the pool is alive.

*Why it exists:* this is INV-SP-6, and it held **before** the fix. Its job is to keep
holding across a refactor that moved the owner monitor from "after a successful
provisioning" to "at reservation time" — exactly the kind of change that can silently
turn a waiter's `caller_ref` into something the `:DOWN` dispatch misclassifies. A guard,
not a regression.

*Pre-fix:* passes. **No fail-first weight.**

### RT-4 — death path (b): the caller dies **during** its provisioning

**Post-fix-only technique.** Pool `max_concurrent: 1`. Snapshot the sandbox schemas,
spawn O calling `claim(1_000, pool)`, poll `:sys.get_state(pool)` until `in_flight` is a
`{:provision, _}`, capture the pre-minted `schema_name`, and kill O.

Asserts, bounded by `SandboxPool.release_call_timeout/0`: the pool drains
(`in_flight == nil`, `db_queue` empty), **no schema leak** (the snapshot is restored —
the pool let the worker finish and then dropped what it produced, rather than killing it
mid-migration and abandoning an open transaction), **no slot leak** (a fresh
`claim(0, pool)` succeeds), and the pool is alive.

*Why it cannot be written against pre-fix code:* this window **has no owner monitor at
all** pre-fix — the monitor is established only after a successful provisioning — so
there is nothing to observe and nothing to react to. It also reads `in_flight`, which
does not exist in the pre-fix state.

*Pre-fix:* flunks on the `in_flight` poll, and the flunk message prints the pre-fix state
shape (`%{active: …, waiting: …, max_concurrent: 1}` — no `in_flight`, no `db_queue`),
which is itself the evidence that the technique is post-fix-only. **No fail-first weight;
not counted toward Step 4's evidence.**

### RT-5 — death path (b'): the caller dies while its reservation is **queued**

**Post-fix-only.** Exercises design §7 step 3 clause B **case 4**. Pool
`max_concurrent: 2`. A claims (its provisioning goes in flight); B claims **while A's is
in flight**, so B's `{:provision, _}` op queues. The test polls until `db_queue` holds
exactly one `{:provision, _}`, reads B's pre-minted `schema_name` out of it, and kills B.

Asserts the queued reservation is discarded, that B's schema name **never appears** in
`information_schema.schemata` (nothing was created for it and nothing must be created
afterwards), that the schema set returns to baseline once A completes and releases, that
**both** slots are returned (two fresh `claim(0, pool)` calls succeed), and that the pool
is alive.

*Pre-fix:* flunks — there is no `db_queue` and a claim is either provisioned inline or
parked, so the state has no analogue. **No fail-first weight.**

### RT-6 — death path (c): the provisioning worker Task itself crashes

**Post-fix-only.** Exercises design §7 step 3 clause B **case 1**. Pool
`max_concurrent: 1`. Poll until `in_flight` is a `{:provision, _}`, read
`in_flight.task_pid`, and `Process.exit(task_pid, :kill)` — a genuine abnormal exit, not
a stubbed return value.

Asserts O receives **`{:error, :provision_failed}`** — the exact atom
`definitions.ex:1495` matches on, not a generic error — **no schema leak** (the snapshot
is restored, which is possible *only* because the pool pre-minted the schema name, so a
worker that died without returning anything is still nameable), **no slot leak**, and
that **the pool survives**: `Process.alive?/1` plus a successful subsequent claim. That
last assertion is precisely what `Task.Supervisor.async_nolink/3` buys over `Task.async/1`,
whose link would have taken the pool down and stranded every live claim.

*Pre-fix:* flunks — provisioning runs on the pool process itself, so there is no worker
to kill and an equivalent kill would simply destroy the pool. **No fail-first weight.**

### RT-7 — FAIL-FIRST #2: a DB-free `claim(0)` is answered immediately while a provisioning runs

Pool `max_concurrent: 1`. The **test process** claims the only slot (so it is also the
process that releases it — the same-process contract). W parks with
`max_wait_ms: 60_000`. The test process releases its claim, and **the instant `release/2`
returns** issues a probe `claim(0, pool)` — a path that touches no database at all.
`t_probe` is the probe's latency; `t_b` is W's own claim latency.

- **(a) premise** — `t_b >= 200`, else `flunk/1` naming the measured value and §10.4.
  Added in design round 2 (F3): without it the ratio in (c) goes green pre-fix on any
  host that provisions in under 80 ms, silently. Same shape, same threshold and the
  **same** floor as RT-2(a).
- **(b)** — the probe's result is `{:error, :sandbox_unavailable}`; W's is
  `{:ok, %SandboxClaim{}}`.
- **(c) the load-bearing fail-first** — `4 * t_probe < t_b`.

*Why this is a second, independent mechanism and not a restatement of RT-2:* RT-2
observes a **timer message** being starved; RT-7 observes a plain **synchronous call**
being starved. The same atom is returned in both arms, so the discriminator is purely
latency, and no constant is involved — `t_b` is measured in the same test.

*Why the ordering is deterministic rather than raced* — this is why RT-7 is shaped around
a waiter promotion instead of the bare "spawn B, then probe" of §10.3's prose, and it is
a deliberate strengthening:

1. In **both** arms `release/2`'s reply is issued from **inside** a callback that then
   goes on to promote the parked waiter. Pre-fix, `handle_call({:release, _})` runs
   `drop_schema/1`, calls `GenServer.reply(from, :ok)`, and *then* calls
   `service_next_waiter/1`, which provisions W synchronously in that same callback.
   Post-fix, `complete_op/3` replies and the same callback then does only bookkeeping.
   So a probe sent by this process the instant `release/2` returns is **guaranteed** to
   land behind a pool that is still inside that callback, and what differs between the
   arms is exactly how much longer that callback runs. A bare "spawn B, then probe" would
   instead be a genuine race between two independent senders — the same class of mistake
   as the deleted RT-2(c).
2. The probe can also never race into a **free** slot, under any interleaving: `active`
   still holds the released entry when the probe is queued (post-fix it is retained until
   the DROP resolves), and by the time the callback ends W has been promoted into the
   slot. So `slots_in_use` is 1 continuously between callbacks and (b) holds regardless
   of scheduling.

*Pre-fix, four independent runs:* `t_probe / t_b` = `453 / 486`, `464 / 499`, `622 / 649`,
`486 / 526` ms — the probe sat in the blocked mailbox for essentially the whole
provisioning every time. **Red in 4/4.** Post-fix, measured probe latency is 0 ms.

### RT-8 — death path (e): the owner dies on top of its own release-DROP

**Post-fix-only.** Exercises design §7 step 3 clause B **case 4b** and INV-SP-A4(e). Pool
`max_concurrent: 2`.

1. O1 claims and holds a slot; the test records its `sandbox_id`.
2. A claims the second slot; the test polls until A's provisioning is in flight — a
   ≥ 411 ms window, which is what makes the state below stable enough to read directly
   rather than race.
3. O1 is told to release. It calls `release/2` **itself** (same-process contract) and
   blocks in its own `GenServer.call`; the DROP is scheduled behind A's provisioning.
4. The test polls until O1's release-DROP is scheduled, then kills O1, then polls until
   the pool has processed the `:DOWN` (O1's `sandbox_id` gone from `active`).

Asserts:

- **no duplicate drop** — **exactly one** `{:drop, _}` op exists for O1's `sandbox_id`.
  Round 1's behaviour (falling through to the case-5 reclaim) would show **two** here:
  the original `:release` op plus a fresh `:reclaim` op. This is the whole point of the
  case, and it is a deterministic read, not a timing observation;
- that op has `purpose == :release_orphaned`, `from == nil`, `owner_ref == nil`;
- the slot was freed **in the `:DOWN` callback itself** (INV-SP-DOWN-2/3), not deferred to
  the DROP's completion;
- **no reply is sent to the dead release caller** (`refute_received`);
- then, once the pool drains: **no schema leak** (baseline restored — O1's schema dropped
  exactly once, A's on release), **no slot leak** (two fresh `claim(0, pool)` calls both
  succeed), `in_flight == nil` with an empty `db_queue`, and **the pool is alive** —
  it never crashed replying to a dead caller.

**One deliberate strengthening over §10.3 as written.** §10.3 specifies counting the
`{:drop, _}` ops for O1's `sandbox_id` over `db_queue` **alone**. That form is correct but
has a narrow window: if A's provisioning happens to complete between the `:DOWN` and the
read, the pool pumps the retargeted DROP into `in_flight` and a queued-only count reads
zero. That is a loud red rather than a silent green, so it is not a correctness hole —
but it is an avoidable flake. This implementation counts over `db_queue` **∪**
`in_flight.op`. The two forms **discriminate identically** (round 1's case-5 fall-through
still shows two ops under either), and the union is not subject to the window at all.
Recorded here rather than done silently.

*Pre-fix:* flunks — there is no `db_queue` and no deferred DROP at all, so the scenario
has no pre-fix analogue. **No fail-first weight.**
