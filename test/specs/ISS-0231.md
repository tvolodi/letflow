# Test Spec: ISS-0231 — requirement-registration drift detection

**Issue:** ISS-0231. **Run:** `WF03-ISS0231-20260822`, WF-03 Step 4.
**Design:** `lib/letflow/design/iss0231-requirement-registration-drift-detection.md`,
built to §7.4 **as amended by §11.4 (MAJOR-1) and §11.7 (MINOR-1/-2/-3/-4/-5), and by
§11.6's OQ-5 ruling** — §11 supersedes the design body where the two differ.
**Fix under test:** `lib/mix/tasks/letflow.check_requirements_registration.ex` (new),
wired into `mix.exs`'s `letflow.check` alias at position 2, plus the `TASK_QUEUE.md`
sentence replacement of §11.5 — commit `001cd84`.
**Test file:** `test/mix/tasks/letflow_check_requirements_registration_test.exs` (new),
two modules: the hermetic fixture suite (`async: true`, no filesystem, no database) and
`…TaskTest` (`async: false`, temp-directory corpora — `run/1` reads
`docs/requirements.yaml` from the cwd and has no path seam).

## Criterion

ISS-0221's `resolution_note` claimed that every requirement in `docs/requirements.yaml`
carried an `impl_order`, "checked via a full-file scan, not a sample". The claim was
false when written. `TASK_QUEUE.md` permitted two surface forms for an unregistered
requirement, and the deferral marker

    # impl_order: UNREGISTERED -- see the S8 note above

contains the substring the verifying scan matched (`impl_order:`). Twenty-one
deliberate deferrals were counted as registrations and the scan concluded zero
unregistered. Nothing re-checked the conclusion; the only symptom of the underlying
condition is an idle pipeline, so a false all-clear about queue registration was
unfalsifiable by any automated gate.

After the fix, registration state is **classified, total, and printed on every gate
run**: four states (`:registered`, `:deferred`, `:neither`, `:unclassified`), a fallback
clause that is a failure rather than a bucket, R1–R6 with an exit-code contract, and an
unconditional deferred roster.

## The two traps this spec is built around

**Trap 1 — the pre-fix failure proves nothing.** The fix *adds* a module, so every test
here fails pre-fix with `UndefinedFunctionError`, which demonstrates only that the
module is new. WF-03's "when the pre-fix failure is 'the code under test does not exist'"
clause therefore governs: the fail-first requirement is discharged by mutating the
shipped logic and recording which tests go red per mutant. That table is §"Mutation
evidence" below, and it is the load-bearing part of this spec.

**Trap 2 — the live corpus cannot discriminate, and now discriminates even less than
the design assumed.** Design §7.2, re-derived by CODE-DESIGN-VALIDATOR in §11.1, showed
that under **M1** (the ISS-0231 bug verbatim) the then-111-entry corpus classified as
111/0/0/0, so R1, R2 and R5 all still held and a corpus-only suite still passed.

Mid-run a sibling session landed `c84c27a` (PR #495), registering REQ-115..139. After
rebase the live corpus is

    115 entries = 115 registered + 0 deferred + 0 neither + 0 unclassified

— **zero deferred entries.** With nothing left to misclassify, M1 produces *no visible
change at all* against the real file, and the same collapse hits M5 (`:deferred`
promoted to hard-fail), whose only designed detector was the live corpus. The hermetic
fixture group is therefore not a convenience; it is the whole test. Confirmed
empirically: M1 and M5 are detected by ten and five hermetic tests respectively, and by
no `T-LIVE-*` test.

## What happened to T-ROSTER

Design §7.4 specified `T-ROSTER` against the live corpus; §11.6's OQ-5 ruling revised it
to the unpinned form, asserting among other things that **the printed deferred count is
greater than zero**. On this branch that count is zero, so the test as specified fails.

§11.6 ruled in advance what such a failure means: *"the deferred set is now empty,
confirm that is intended and retire this test", not "regression".* It is intended —
`c84c27a` registered the set through real `register_task` calls. So `T-ROSTER` is
**retired in its live-corpus form, and the property it protected is relocated, not
deleted**:

| | where the property lives now |
|---|---|
| the real test | **F-ROSTER-AGREEMENT** — a hermetic fixture with a deliberately non-empty deferred set. Asserts the roster names at least one id, prints a matching non-zero total, that every printed id is in the `:deferred` bucket, and that no `:registered` id is printed. Permanently true, and red under M1. |
| the live half | **T-ROSTER-LIVE-AGREEMENT** — the same agreement stated *conditionally*, deriving its expectation from the report instead of pinning a count: an empty deferred set implies the explicit `none` line; a non-empty one implies every deferred id is printed with a matching total. True of any corpus; never goes stale. |

The reasoning is recorded in the test file's own moduledoc as well, so a future reader
does not have to find this spec.

## Test inventory

Every test whose assertion names a rule id goes through `scan/1` and asserts on
`report.violations` (§11.7 MINOR-1 — `classify_entry/1` returns an `entry()`, which has
no violations field and cannot express R3–R6). Only pure state-assignment tests call
`classify_entry/1` directly.

Every fixture is wrapped by `doc/1` in a realistic two-key file carrying a `stages:`
section. That is deliberate: it makes every count assertion sensitive to **M9**.

## Findings recorded rather than papered over

**1. M8a needed a test the design did not specify, and the design's stated reason for
anchoring is only half the defence.** Design §4.4 argues the marker pattern is anchored
so that `impl_order: 5  # was UNREGISTERED until Tuesday` is not read as a deferral. That
input does **not** discriminate an unanchored pattern, because
`classify_registration/2`'s `cond` tries the field form first and the field form still
matches — so on the first sweep M8a was the one mutant the suite did not catch, at 29/29
green. The anchoring is genuinely load-bearing for a *different* input class: a line
carrying the bare token and the word UNREGISTERED but matching neither shape (e.g.
`# impl_order was UNREGISTERED before Tuesday`), which the shipped classifier sends to
`:unclassified` and an unanchored pattern absorbs into `:deferred`. F-ANCHOR was extended
with two such lines; M8a then failed at 28/29. The `cond` ordering is a real second layer
of defence, and M8b (unanchored *and* reordered) is the mutant that isolates the regex.

**2. `impl_order_hint: 7` and `impl-order: 7` are `:neither`, not `:unclassified`.**
Design §7.4's F-NOVEL-FORM predicted `:unclassified`. The shipped trigger is the *bare*
token, `~r/\bimpl_order\b/`, and neither string contains it — `_` and `-` sit on the
wrong side of the word boundary — so these entries carry no attributed `impl_order` line
at all. This is a bucket difference, not a hole: `:neither` hard-fails under R1 exactly
as `:unclassified` hard-fails under R2, nothing is silently absorbed, and §3(d) is
satisfied as written. Pinned in F-NOVEL-FORM-ADJACENT-TOKEN so the question is not
re-derived and so a change to the trigger regex — which *would* be a behaviour change —
turns a test red. F-NOVEL-FORM was rebuilt from forms that do carry the bare token.

**3. `classify_entry([])` raises `FunctionClauseError`.** The function has no `[]`
clause. It is unreachable from `scan/1` — the splitter only emits lists headed by the
`- id:` line — so it is characterised in F-CLASSIFY-EMPTY rather than reported as a
defect, and `classify/1` in the test file guards against ever producing one. The
assertion goes through `apply/3`, because a literal `[]` argument is a compile-time type
error under `--warnings-as-errors`, which `mix letflow.check` runs.

**4. A fixture's own prose can trip the classifier.** Two fixtures initially failed
because a `title:` field read "no impl_order line of any form" — an attributed line
carrying the bare token, so the entry classified `:unclassified` instead of `:neither`.
Fixed by rewording, with an inline note. This is the module's designed behaviour (§3(d))
and the same hazard §6.5 records for the module's own moduledoc; it is worth knowing that
it reaches fixture prose too.

## Nothing from §7.4 was silently dropped

Every fixture spec, live-corpus spec and task-level spec of §7.4 is present, except
`T-ROSTER`, which §11.6 pre-authorised retiring under exactly the condition that
occurred, and whose property is relocated as described above. Two specs were **changed**
rather than dropped, and both changes are recorded in the table and in the findings
above: F-NOVEL-FORM's inputs, and F-ANCHOR's scope. Four tests were **added** beyond
§7.4 — F-DEFERRED-GREEN (M5 lost its detector when the live deferred set emptied),
F-DUP-ID (R4 had no test in §7.4 at all), F-CRLF, and T-TASK-R6-MISSING-FILE.

## Constraints held

`async: true` for the hermetic suite; no database; no new dependency; every fixture an
in-memory string. `docs/requirements.yaml` is read (`File.read!`) by the four `T-LIVE-*`
tests and is **never written** by anything in this file. `lib/` was restored to its
committed state after every mutant, verified each time.
