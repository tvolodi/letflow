# Test Spec: ISS-0275 — `letflow-web` client missing `oidc-audience-mapper`

**Issue:** ISS-0275. **Run:** `WF03-ISS0275-20260822`, WF-03 Step 4.
**Design:** `lib/letflow/design/iss0275-audience-mapper-fix.md`.
**Fix under test:** `priv/keycloak/realms/bpm-default.json` (existing file, existing
`letflow-web` client — content edit only, no new module), commit `b92a93e`.
**Test file:** `test/letflow/api/keycloak_realm_audience_mapper_test.exs` (new, 4 tests).

## Criterion

`Oidcc.Token.validate_jwt/3` (`deps/oidcc/src/oidcc_token.erl`) unconditionally requires
an access token's `aud` claim to contain the configured `client_id`
(`"letflow-web"`, per `config/dev.exs`/`config/test.exs`'s `:oidc` config). Pre-fix, the
tracked realm fixture's `letflow-web` client had only the `realm-roles` protocol mapper
— nothing populated `aud` — so every real Keycloak-issued token failed validation and
every authenticated request 401'd. The fix adds a second protocol mapper,
`letflow-web-audience` (`protocolMapper: "oidc-audience-mapper"`), to that client's
`protocolMappers` array.

This is a static-fixture test (no live Keycloak, no live token) that the tracked file
actually carries that mapper with the config keys that make it effective, so a future
edit to `bpm-default.json` cannot silently drop it again. Live end-to-end verification
(a freshly-provisioned Keycloak container issuing a token with `aud: "letflow-web"`) was
already performed by ELIXIR-DEV during the fix and is not repeated here — this spec
covers the regression-guard layer, not the original live proof.

| Acceptance criterion | Proved by |
|---|---|
| `letflow-web`'s `protocolMappers` contains a mapper with `protocolMapper == "oidc-audience-mapper"` | test 1, `"a protocol mapper of type oidc-audience-mapper is present"` |
| That mapper's `config["included.client.audience"] == "letflow-web"` | test 2, `"its config sets included.client.audience to letflow-web"` |
| That mapper's `config["access.token.claim"] == "true"` | test 3, `"its config sets access.token.claim to \"true\""` |
| The pre-existing `realm-roles` mapper (`oidc-usermodel-realm-role-mapper`) is still present and unmodified | test 4, `"the realm-roles ... mapper is still present and unmodified"` — asserts the full mapper map by equality, so any future accidental edit to it (while touching the same array to add/change other mappers) fails loudly |

`id.token.claim == "false"` is documented as deliberate in the design (§2.1) but not
independently asserted — it's not one of the four acceptance criteria the task specified,
and asserting it would duplicate the intent of the `access.token.claim` check without
adding coverage of a distinct failure mode (a wrong `id.token.claim` value does not
reproduce the 401 bug; only `access.token.claim` does, since `Oidcc.Token.validate_jwt/3`
validates the access token, not the ID token).
