# Spec: ISS-0276 — `mix letflow.seed` dev-bootstrap default tenant

Issue: `docs/issues/ISS-0276.yaml` (GH#546). Design:
`lib/letflow/design/iss0276-dev-bootstrap-seed.md`. Implementation:
`lib/mix/tasks/letflow.seed.ex` (`Mix.Tasks.Letflow.Seed`).

Test file: `test/mix/tasks/letflow.seed_test.exs`.

## Why this is the "code under test does not exist pre-fix" case (mutation required)

`lib/mix/tasks/letflow.seed.ex` is a brand-new module — there is no pre-fix commit where
`Mix.Tasks.Letflow.Seed` exists in any older form. Checking out any commit before this
run's Step 3 and running the new test file would fail with `UndefinedFunctionError` /
`Mix.NoTaskError` for every single test, which proves the module is new and nothing
about whether the tests actually discriminate a correct implementation of the task's
logic from a subtly wrong one (wrong attrs, broken idempotency fallback, etc.). Per
`docs/agents/workflows/WF-03_issue_resolving.md`'s Step 4 non-existence clause, the
fail-first requirement is instead satisfied by mutating the shipped implementation and
showing the new tests catch each mutant — see "Mutation testing" below for the two
mutants applied and their measured results.

## Acceptance criteria and the test cases proving each

### AC1 — running the task against a fresh DB creates a `bpm-default` tenant row

**Test:** `"AC1 -- run/1 creates the bpm-default tenant row with idp_realm_id set"`
(`describe "AC1 ..."`). Calls `Mix.Tasks.Letflow.Seed.run([])` directly against the real
sandboxed `Letflow.Repo`, then reads the row back with `Repo.get_by(Tenant,
idp_realm_id: "bpm-default")` and asserts both `slug` and `idp_realm_id` are literally
`"bpm-default"`.

**Why this exists, not just a restatement of the AC:** the design's whole point (§2 step
2) is that the attrs map literal must actually carry `"idp_realm_id" => "bpm-default"`
into `create_tenant/1` — a task that created *a* tenant but forgot that one key (exactly
Mutant 1 below) would satisfy a weaker assertion like "a tenant got created" while still
leaving ISS-0276's real symptom (AuthPipeline can't resolve the realm) unfixed. Asserting
`idp_realm_id` specifically is what makes this test discriminating rather than
decorative.

### AC2 — `resolve_tenant_by_realm("bpm-default")` succeeds post-seed and the tenant is
usable

**Test:** `"AC2 -- resolve_tenant_by_realm succeeds post-seed and the schema is fully
provisioned"`. Runs the task, then calls
`Letflow.Identity.resolve_tenant_by_realm("bpm-default")` directly (the exact function
`AuthPipeline`'s tenant-resolution step calls per the design and moduledoc) and asserts
`{:ok, %Tenant{}}` with matching `slug`/`idp_realm_id`. It additionally confirms the
tenant is not just a bare row: `TenantProvisioning.schema_name_for_tenant/1` +
`information_schema.schemata`/`information_schema.tables` show the tenant's Postgres
schema exists and contains the tenant-scoped tables migration replay is supposed to
create. This is the level task.description specifies ("resolve_tenant_by_realm/1 and the
returned tenant's fields, not a full HTTP+Keycloak round trip") — a full `AuthPipeline`
HTTP round trip needs a real bearer token/Keycloak realm this suite's existing patterns
don't provide for an ad hoc dev-seed row, so schema-completeness is the closest
"resolves past tenant-resolution and is actually usable" proxy available at this layer,
matching `Letflow.TenantFixture`'s own completeness-checking precedent in this repo.

**Why this exists:** AC1 alone would pass for a task that inserted the row but never
called `provision_tenant_schema/1`/`replay_migrations/1` — the row would exist but the
tenant would be unusable (no schema, no tables), which is exactly the state ISS-0276's
bug left developers in before this fix (a `POST /tenants`-shaped row with no working
schema is a different, but equally broken, failure mode). This test would catch a
regression that skipped provisioning/replay even if AC1's row-level test kept passing.

### AC3 — idempotency: running the task twice does not crash, results in exactly one row

**Test:** `"idempotency -- running the task twice does not crash and leaves exactly one
bpm-default tenant"`. Calls `Seed.run([])` twice in the same test and asserts both calls
return `:ok`, exactly one `Tenant` row has `idp_realm_id == "bpm-default"` afterward, and
`resolve_tenant_by_realm/1` still resolves correctly post-re-run.

**Why this exists:** this is the design's §4 duplicate-slug fallback — the one
non-idempotent link (`create_tenant/1` returning `{:error, :duplicate_slug}` on the
second call) has to be caught and redirected to `resolve_tenant_by_realm/1` rather than
propagating as a crash or creating a second, colliding row. This is exactly Mutant 2
below.

### AC3 (doc, "documented") — no test needed

Per task.description, doc coverage for ISS-0276's third acceptance criterion (the
`README.md` "Running it" addition and the task's own `@moduledoc`) is prose-only and is
covered by Step 3's README change (see the ELIXIR-DEV/REVIEWER handoffs for this run,
`step-03-elixir-dev.json` / `step-03c-reviewer.json`), not by an executable test — there
is no application logic there to assert against.

## Mutation testing (see "Why this is the non-existence case" above)

Applied in a throwaway git worktree (`../letflow-mutant-wt`) off this branch's `HEAD`, so
the main checkout was never mutated. Both mutants target the exact traps design §4 and
§2 exist to close:

- **Mutant A — omit `idp_realm_id` from `@attrs`.** Simulates the exact original bug
  shape (no code path setting `idp_realm_id`) reappearing inside the fix itself. Expected
  and measured: AC1 and AC2 fail (idp_realm_id is `nil`, so both the direct field
  assertion and `resolve_tenant_by_realm/1` — which queries by `idp_realm_id` — fail);
  idempotency test result recorded too.
- **Mutant B — break the idempotency fallback** (make the `{:error, :duplicate_slug}`
  branch `Mix.raise/1` unconditionally instead of resolving-and-continuing). Simulates a
  regression to a non-idempotent task. Expected and measured: only the idempotency test
  fails (`Mix.raise/1` inside a second `Seed.run/1` call raises `Mix.Error`, which is not
  rescued anywhere in the test, so the test process itself fails); AC1/AC2 (each of which
  runs the task exactly once) stay green.

Full per-mutant test output is quoted in this run's TEST-DESIGNER handoff
(`handoffs/WF03-ISS0276-20260822/step-04-test-designer.json`) `result.summary`.
