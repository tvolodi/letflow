# Test Spec: ISS-0289 — UserDetailPage.tsx wired into router, UsersPage.tsx's inline duplicate retired

**Issue:** ISS-0289. **Run:** `WF03-ISS0289-20260823`, WF-03 Step 4.
**Design:** `lib/letflow/design/iss0289-user-detail-page-routing.md`.
**Fix under test:** `web/src/router.tsx` (route `admin/users/:id -> <UsersPage/>` renamed
and repointed to `admin/users/:userId -> <UserDetailPage/>`) and `web/src/pages/admin/UsersPage.tsx`
(inline detail/edit branch — no `PLATFORM_ADMIN` gate, no group-membership editing —
removed entirely), commit `da37fb3`.
**Test file:** `web/src/__tests__/router.iss-0289.test.tsx` (new, 2 tests).

## Criterion

Before this fix, `web/src/pages/admin/UserDetailPage.tsx` existed in the tree
(complete: `QueryStateBoundary`/`classifyError` pattern, real `DeactivateUserDialog`,
full group-membership editing, `PLATFORM_ADMIN` role gate) but was never reachable —
`router.tsx` mapped `admin/users/:id` to `<UsersPage/>`, whose own inline detail/edit
branch was a partial stand-in (no group-membership editing, no role gate — any
authenticated user landing on that URL saw a fully editable form). REQ-121 discovered
the orphaned file and deliberately left the routing decision to this issue.

Both acceptance criteria describe a URL-shape-level behavior, not something provable
by unit-testing either page component in isolation — `UserDetailPage.tsx` itself is
**unchanged** by this fix (design §4.2: "No changes... its `useParams()` destructure of
`userId` now matches the router's renamed `:userId` param"), so a component test that
imports `UserDetailPage.tsx` directly would pass identically before and after the fix
and prove nothing about the bug. The bug was entirely in the *mapping* — which
component a given URL resolves to — so the test targets that mapping directly, via
`react-router`'s own `matchRoutes`/`router.routes` against the real config in
`web/src/router.tsx`, rather than hardcoding either the pre-fix or post-fix param name.

| Criterion | Proved by |
|---|---|
| Navigating to the admin user detail URL renders `UserDetailPage`, not `UsersPage` | `TC-ISS0289-01` — inspects `router.routes`' child route list directly: the bare list path (`admin/users`) still maps to `UsersPage`, and the parameterized detail path maps to `UserDetailPage`, not `UsersPage` |
| A non-`PLATFORM_ADMIN` user navigating to the detail URL is gated, not shown an editable form (the concrete regression SECURITY-REVIEWER flagged as previously absent) | `TC-ISS0289-02` — resolves the real route match for `/admin/users/user-42` via `matchRoutes(router.routes, url)`, renders exactly that matched route element with a mocked non-admin session, and asserts the `"You do not have permission to manage users."` gate text renders and `admin-user-detail-form` does not |

## Why route-level, not component-level

Per the suggested test targets, a route-level test was chosen over a component-level one
specifically because the defect is "wrong component wired to a route," not a defect
inside either component. `TC-ISS0289-01` pins the wiring structurally (which `element`
type a given `path` entry carries). `TC-ISS0289-02` goes one level further and proves
the wiring's *behavioral consequence* — resolving the match the same way the real
router would for a concrete URL, then rendering exactly that resolved element, so the
test is agnostic to which param name (`:id` pre-fix, `:userId` post-fix) is in force.

`TC-ISS0289-01` fails pre-fix because `router.tsx` registered only `admin/users/:id ->
<UsersPage/>` — no route both carries a param and points at `UserDetailPage`, so
`children.find(...)` returns `undefined` and `toBeDefined()` fails before the element-type
assertion is even reached. `TC-ISS0289-02` fails pre-fix because the resolved match for
that URL is `UsersPage`'s inline branch, which renders the editable
`admin-user-detail-form` unconditionally for any authenticated user — the permission text
never appears, confirmed by the captured DOM dump in the actual pre-fix test run (elided
above; full inline form with `admin-user-display-name`, `admin-user-email`,
`admin-user-status`, `admin-user-save`, `admin-user-deactivate` testids, no `PLATFORM_ADMIN`
check anywhere in the component).

## Guard note

The non-admin session fixture originally used `tenant_slug: 'acme'`, which tripped the
`tenant-slug-in-source` source-scan guard (`web/tests/guards/forbidlist.ts` — hardcoded
platform tenant slugs are forbidden outside an explicit allowlist of test directories that
does not include `web/src/__tests__/`). Changed to a non-matching placeholder
(`'demo-co'`) rather than adding this new directory to the guard's allowlist, since no
other guard-listed directory exists for this specific test's location and the fixture
value itself is arbitrary. Re-verified clean after the change:
