# Test Spec: ISS-0295 — e2e Keycloak port/client_id hardcoded across 33 spec files, no shared constant, client_id had no override mechanism

**Issue:** ISS-0295 (to be recorded at `docs/issues/ISS-0295.yaml` by ISSUE-FIXER at
WF-03 Step 5). **Design:** commit `297f5be` ("design(ISS-0295): e2e Keycloak config
consolidation (port 8082, client_id letflow-web)"). **Fix:** `web/tests/e2e/helpers.ts`
(new exported `BPM_IDP_BASE_URL` / `BPM_IDP_CLIENT_ID` constants, both
`process.env`-derived with defaults) plus 27 consuming spec files updated to import
from there instead of redeclaring locally, commit `f7aec1d`.

## Criterion

`web/tests/e2e/*.ts` (33 files) each independently hardcoded a stale Keycloak port
(`8081`) and client_id (`bpm-platform-api`), with **no shared constant** — any test
override of the port required editing many files, and the client_id had **no override
mechanism at all** (a bare string literal, not even read from an env var). The fix's
acceptance criteria are:

1. `web/tests/e2e/helpers.ts` exports `BPM_IDP_BASE_URL` and `BPM_IDP_CLIENT_ID`, both
   derived from `process.env` with sane defaults (`http://localhost:8082` /
   `letflow-web`).
2. No spec file under `web/tests/e2e/` hardcodes the port or client_id literal any
   more — they import the shared constants from `helpers.ts` instead.

## Test case: `web/tests/unit/iss-0295-e2e-idp-config.test.ts`

**Why this test exists (not just a restatement of the criterion):** the bug's nature
is "staleness can recur because there's no shared constant / no override mechanism" —
so the regression test asserts the *invariant* the fix establishes, not today's literal
values, and does so two ways:

- **TC-1** (`describe: "BPM_IDP_CLIENT_ID / BPM_IDP_BASE_URL are exported and
  env-overridable"`) dynamically imports `helpers.ts` (via `vi.resetModules()` +
  dynamic `import()`, since the constants are computed once at module-eval time from
  `process.env`) under three env conditions: no override (asserts the documented
  defaults), `BPM_IDP_CLIENT_ID` set, and `BPM_IDP_BASE_URL` set. This directly targets
  the part of the bug that had **zero** prior fix: `BPM_IDP_CLIENT_ID` was a bare
  literal (`'bpm-platform-api'`), not even read from `process.env`, so no test against
  the pre-fix code could ever have overridden it — proving this closes the gap, not
  just that a value happens to match today.
- **TC-2** (`describe: "no hardcoded IdP literals outside helpers.ts"`) statically
  scans every `*.ts` file under `web/tests/e2e/` (via `fast-glob`, same technique as
  the project's existing `tests/guards/source-scan.spec.ts`), excluding `helpers.ts`
  itself, for the literal substring `bpm-platform-api` or a bare `8081` token. This
  targets "this class of staleness cannot recur" directly: it is a structural
  assertion about the whole source tree, not a spot-check of one or two files, so a
  future contributor re-introducing a local hardcoded constant in any new or existing
  spec file fails the build immediately.

## Fail-then-pass proof

Pre-fix `helpers.ts` (commit `275e9f1`, `main` tip before the fix) does not export
`BPM_IDP_BASE_URL` or `BPM_IDP_CLIENT_ID` at all — `KEYCLOAK_BASE_URL` and
`KEYCLOAK_CLIENT_ID` were private, non-exported bindings, and `KEYCLOAK_CLIENT_ID` was
the bare literal `'bpm-platform-api'` with no `process.env` involvement whatsoever.
This is genuinely new behavior being added (an override mechanism that did not exist,
plus a tree-wide invariant that was never enforced before), not merely "the same
function exists under a different name" — so a direct fail-then-pass against pre-fix
`main` is legitimate proof per WF-03 Step 4, rather than requiring the
does-not-exist/mutation fallback procedure.
