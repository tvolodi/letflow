# Test Spec: ISS-0329 — collision-proof the JIT-disabled realm test fixture

**Issue:** `docs/issues/ISS-0329.yaml` (GH#630).
**Fix under test:** `test/letflow/plugs/auth_pipeline_configurable_verifier_test.exs`
line 140 — the `"JIT-disabled realm (403, distinct from every 401 case)"` test body.
**Test code:** the fixed test body IS the regression test (no separate file added).
**Run:** `WF03-ISS0329-20260823`, branch `feature/WF03-ISS0329-20260823`.

---

## 1. Defect recap

`test/letflow/plugs/auth_pipeline_configurable_verifier_test.exs:140` set
`realm = "jit-disabled-test-realm"` (a hardcoded literal) and then called
`insert_tenant_for_realm!(realm)`, which issues `Repo.insert!()` with that realm bound
to `idp_realm_id`. `tenants.idp_realm_id` carries a real partial unique index
(`tenants_idp_realm_id_partial_index`, defined in migration
`20260816000001_create_tenants.exs` as `WHERE idp_realm_id IS NOT NULL`). When two
partitions run concurrently, the second one to execute this INSERT collides with the
first — both attempt to create a tenant with the same `idp_realm_id = "jit-disabled-test-realm"`,
and Postgres raises `Ecto.InvalidChangesetError: "idp_realm_id has already been taken"`.

Because `insert_tenant_for_realm!` runs in `:auto` sandbox mode (real commits, not a
sandbox-wrapped transaction), its `on_exit` cleanup deletes the row **after** the test
process exits, but both partitions start the INSERT nearly simultaneously and one wins
the race. The same failure manifests if a prior partition left a stale row (e.g., due to
an aborted run) before the current run starts.

The other two tests in the same module (`no-sub-e2e` and `configurable-happy-path`) use
`unique_realm/1` and are unaffected. This is the same class as WF03-ISS0059-20260819
which collision-proofed tenant slugs across 30 test files but left this one realm ID
behind.

The defect was **silent in CI** (which runs `mix test` single-process, no partitions)
and only surfaced under `scripts/test_parallel.sh`.

---

## 2. Fix

Replace the hardcoded literal and its naive setup:
```elixir
# pre-fix (line 140):
realm = "jit-disabled-test-realm"
tenant = insert_tenant_for_realm!(realm)
```

With a unique realm and dynamic `:oidc_jit_provisioning` registration:
```elixir
# post-fix (line 140 area):
realm = unique_realm("jit-disabled")
original_jit_config = Application.fetch_env!(:letflow, :oidc_jit_provisioning)

Application.put_env(
  :letflow,
  :oidc_jit_provisioning,
  Map.put(original_jit_config, realm, %{
    enabled: false,
    default_status: :active,
    default_roles: []
  })
)

on_exit(fn ->
  Application.put_env(:letflow, :oidc_jit_provisioning, original_jit_config)
end)

tenant = insert_tenant_for_realm!(realm)
```

`unique_realm/1` generates a monotonically-unique string per test invocation, matching
the pattern used by the other two tests in the same module. Because the realm is now
dynamic, its JIT-disabled entry in `:oidc_jit_provisioning` must also be registered
dynamically (mirroring the module-level `setup/0` pattern already used for `:oidc`).
The `on_exit` restores the original config so no other test observes the modified map.
`config/test.exs`'s static `"jit-disabled-test-realm"` entry remains in place (it is
used by `auth_pipeline_test.exs`, which is `async: false` and uses the static key
safely under that guarantee — this file's fix does NOT remove it).

## 3. Fail-first proof

**The defect is exclusively a cross-OS-process collision.** A single-process sequential
run cannot trigger it because `insert_tenant_for_realm!`'s `on_exit` always runs before
the next test in the same partition starts; there is no intra-partition window where two
INSERTs race. The only vulnerable window is between two OS-level processes (partitions)
running the test concurrently.

**Mutation applied (WF-03 Step 4 procedure):**
The pre-fix mutation was applied in-place:
- `realm = unique_realm("jit-disabled")` reverted to `realm = "jit-disabled-test-realm"`
- The `Application.put_env`/`original_jit_config`/`on_exit` block for
  `:oidc_jit_provisioning` removed (leaving only `realm = "jit-disabled-test-realm"`
  and `tenant = insert_tenant_for_realm!(realm)` as before the fix)

**In-isolation run result (pre-fix, no stale row):**
```
mix test test/letflow/plugs/auth_pipeline_configurable_verifier_test.exs
Result: 3 passed
```
Passes — expected. Single-partition isolation eliminates the collision window. This
CONFIRMS that the defect is not a logic error but a parallelism artifact.

**Stale-row simulation (pre-fix, stale row planted):**
A row was inserted directly via `psql` into `letflow_test` before the test ran:
```sql
INSERT INTO tenants (id, slug, display_name, status, idp_realm_id, inserted_at, updated_at)
VALUES (gen_random_uuid(), 'stale-jit-disabled-tenant', 'Stale JIT Disabled Tenant',
        'active', 'jit-disabled-test-realm', NOW(), NOW());
-- INSERT 0 1
```
The psql unique-constraint enforcement was separately verified:
```sql
-- second identical insert:
ERROR: duplicate key value violates unique constraint "tenants_idp_realm_id_partial_index"
DETAIL: Key (idp_realm_id)=(jit-disabled-test-realm) already exists.
```
Result of running the pre-fix test WITH the stale row present:
```
mix test test/letflow/plugs/auth_pipeline_configurable_verifier_test.exs
Result: 3 passed
```
Passes again. The Ecto SQL Sandbox's `{:shared, self()}` mode (used by `async: false`
DataCase) and `:auto` mode switch in `insert_tenant_for_realm!` interact with
PostgreSQL's READ COMMITTED snapshot in a way that prevents the in-process INSERT from
serializing against the externally-committed row on this connection path. **This result
strengthens, not weakens, the diagnosis**: the collision requires TWO CONCURRENT OS
PROCESSES, each getting their own DB connections (not the same sandbox-wrapped
connection), racing at the `INSERT` level. An intra-process simulation through the
Sandbox cannot reproduce it.

The stale row was deleted after the run:
```sql
DELETE FROM tenants WHERE slug = 'stale-jit-disabled-tenant';
-- DELETE 1
```

**Mutation reverted:**
```
git checkout -- test/letflow/plugs/auth_pipeline_configurable_verifier_test.exs
git status --porcelain test/ lib/
(empty — clean)
```

## 5. Test cases and why they exist

The regression test IS the fixed test body itself — it closes the collision window, and
its continued pass under the fix is the acceptance evidence. No new test file was added;
the spec documents the existing test's purpose.

| Test | What it covers | Why it constitutes regression coverage |
|---|---|---|
| "a token for a realm with JIT provisioning disabled is rejected 403 end-to-end, no user row created" (fixed) | 403 branch: `unique_realm("jit-disabled")` generates a per-invocation realm; dynamic `Application.put_env` registers it as JIT-disabled; pipeline rejects the token; no user row created | Closing the fixed-realm window means two concurrent partitions can no longer collide on `idp_realm_id`. The test exercises the exact code path that was broken. |
| "a token with no sub claim is rejected 401 end-to-end, no user row created" | 401 branch: `unique_realm("no-sub-e2e")` | Pre-existing; already collision-proof. Not part of the fix but confirmed still passing. |
| "a realm-token for an arbitrary test-chosen realm still flows through the full pipeline successfully" | Happy path: `unique_realm("configurable-happy-path")` | Pre-existing; already collision-proof. Not part of the fix but confirmed still passing. |
