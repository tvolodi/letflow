# Test Spec: ISS-0343 — `Backfill.run/1` tolerance for a concurrently-vanished tenant schema

**Issue:** `docs/issues/ISS-0343.yaml`.
**Fix under test:** `lib/letflow/event_store/registry.ex` (new `:tenant_schema_missing`
error variant, `rescue_missing_schema/1` private helper, three wrapped call sites) and
`lib/letflow/tenant_provisioning/backfill.ex` (new `case` clause in `Backfill.run/1`).
**Design:** `lib/letflow/design/iss0343-backfill-missing-schema-tolerance.md`.
**Test code:**
`test/letflow/event_store/registry_tenant_schema_missing_test.exs` (new file, Registry
layer) and `test/letflow/tenant_provisioning/backfill_test.exs` (one new test appended,
Backfill layer).
**Run:** `WF03-ISS0343-20260826`, branch `feature/WF03-ISS0343-20260826`.

---

## 1. Defect recap

Under `scripts/test_parallel.sh`, `TenantFixture.provisioned_tenant!/1` flips
`Ecto.Adapters.SQL.Sandbox.mode(Letflow.Repo, :auto)` for the whole partition process
and never restores `:manual` (documented, intentional — INV-F-6). Every `async: false`
test sharing that partition's connection pool therefore loses per-test transactional
isolation: writes are real and committed. `TenantFixture.teardown/2` issues
`DROP SCHEMA IF EXISTS "<schema>" CASCADE` for its own tenant with no lock coordinating
it against any other concurrently-running test. `Backfill.run/1`
(`lib/letflow/tenant_provisioning/backfill.ex`) reads **every** tenant's `Registration`
row up front (`Repo.all(Registration)`), then calls `Registry.register_type/2` for each
one in turn. If a *different*, concurrently-running test's teardown drops its own
tenant's schema in the window between that listing and the corresponding
`Registry.register_type/2` query, the query fails with an uncaught
`%Postgrex.Error{postgres: %{code: :undefined_table}}` — `relation
"tenant_*.event_type_registry" does not exist` — which unwinds straight out of
`Enum.reduce_while/3` and crashes the **entire** backfill sweep, not just the one
affected tenant. This is the observed `Letflow.TenantProvisioning.BackfillTest` failure
shape under parallel test runs (see `handoffs/WF03-ISS0343-20260826/step-01-issue-fixer.json`
for the full diagnosis, including why this is a genuine DDL-vs-query race and not a
naming collision).

## 2. Fix

`Letflow.EventStore.Registry.register_type/2` and `get_type/2` now return
`{:error, :tenant_schema_missing}` — a new, typed error distinct from
`:tenant_not_provisioned` — instead of letting the underlying `Postgrex.Error` escape,
via a new private `rescue_missing_schema/1` helper that rescues only the exact
`%Postgrex.Error{postgres: %{code: :undefined_table}}` shape and re-raises everything
else. `Backfill.run/1` gains one new `case` clause treating `{:error,
:tenant_schema_missing}` the same way it already treats `:tenant_not_provisioned` — log
a warning, count it as `skipped`, and continue the reduction — so one tenant's vanished
schema no longer halts the sweep for every other tenant.

## 3. Why the tests are deterministic rather than race-timing-dependent

The underlying defect is a **low-frequency, timing-dependent race** between two
concurrently-running OS test partitions — not reliably reproducible on demand (the
issue-fixer's own step-01 diagnosis ran `scripts/test_parallel.sh` once and did not
reproduce it in that single attempt). Rather than attempting to reproduce the race's
timing, these tests reproduce the exact **end-state** the race produces —
"a tenant's `Registration` row exists, but its physical Postgres schema does not" —
deterministically, on every run: provision a real tenant via
`TenantProvisioning.provision_tenant_schema/1` + `replay_migrations/1` (so a real
schema and `Registration` row both exist), then `DROP SCHEMA ... CASCADE` that schema
directly (the same `drop_schema!/1` helper `registry_test.exs` already uses)
**without** deleting the `Registration` row. This is the same query-vs-missing-schema
condition the race produces, exercised on every single test run rather than only when a
timing window happens to line up — a stronger, not weaker, regression test.

## 4. Fail-then-pass proof

**Method:** a throwaway `git worktree` was created at the pre-fix commit
(`4d20542^` = `54a0c14`, the last commit before ELIXIR-DEV's ISS-0343 fix), the two new
test files were copied into it unchanged, `deps/` was symlinked from the main
checkout, `MIX_ENV=test mix compile` was run against the pre-fix `lib/` (confirmed via
`grep -n tenant_schema_missing` on the pre-fix `registry.ex`/`backfill.ex`: zero
matches), a dedicated throwaway test database was created
(`MIX_TEST_PARTITION=98 mix ecto.create && mix ecto.migrate`), and the new tests were
run against it.

**Pre-fix run (worktree, `54a0c14`):**
```
MIX_ENV=test MIX_TEST_PARTITION=98 mix test test/letflow/event_store/registry_tenant_schema_missing_test.exs test/letflow/tenant_provisioning/backfill_test.exs
...
Result: 5/8 passed
Failed: 3 tests
```
The 3 failures are exactly the 3 new tests targeting the fix, each failing with an
**uncaught** `** (Postgrex.Error) ERROR 42P01 (undefined_table) relation
"tenant_....event_type_registry" does not exist`:

1. `register_type/2 tolerates a Registration row whose physical schema has vanished` —
   raised from `Letflow.EventStore.Registry.insert_with_monotonicity_check/2`
   (`registry.ex:233`, the pre-fix line for the unguarded `current_max` query).
2. `get_type/2 tolerates a Registration row whose physical schema has vanished` —
   raised from `Letflow.EventStore.Registry.get_type/2` (`registry.ex:175`).
3. `regression: ISS-0343 -- a tenant whose schema vanished mid-sweep is skipped, not a
   crash of the whole run` — raised from `insert_with_monotonicity_check/2`, propagating
   through `Backfill.run/1`'s `Enum.reduce_while/3` (`backfill.ex:26`) and crashing the
   whole `Backfill.run(v2_attrs())` call — exactly the "one tenant's vanished schema
   crashes the entire sweep" defect this fix addresses. The other, healthy tenant in
   this test never got updated because the crash happened first.

The remaining 5 pre-existing tests (the ISS-0332 backfill tests and the control test in
the new Registry file, which does not drop any schema) passed unchanged, confirming the
failures are isolated to the new schema-missing-tolerance assertions, not a broken
worktree/environment.

The throwaway worktree and its dedicated test database were removed after the run
(`mix ecto.drop`, `git worktree remove --force`).

**Post-fix run (this branch, `feature/WF03-ISS0343-20260826`, HEAD):**
```
MIX_ENV=test mix test test/letflow/event_store/registry_tenant_schema_missing_test.exs test/letflow/tenant_provisioning/backfill_test.exs test/letflow/event_store/registry_test.exs
Finished in 24.9 seconds (0.00s async, 24.9s sync)
Result: 36 passed
```
All 36 tests pass, including the 3 that failed pre-fix and all 33 pre-existing
`RegistryTest`/`BackfillTest` tests (no regression).

## 5. Test cases and why they exist

| Test | File | What it covers | Why it constitutes regression coverage |
|---|---|---|---|
| `get_type/2` returns `{:error, :tenant_schema_missing}`, not an uncaught `Postgrex.Error` | `registry_tenant_schema_missing_test.exs` | `get_type/2`'s single `Repo.one/2` call site, wrapped by `rescue_missing_schema/1` | Directly proves the fix's typed-error contract for `get_type/2`, the second of the two public functions the design doc changes |
| `register_type/2` returns `{:error, :tenant_schema_missing}`, not an uncaught `Postgrex.Error` | `registry_tenant_schema_missing_test.exs` | `insert_with_monotonicity_check/2`'s `fetch_current_max/2` query (the first of its two wrapped call sites — a fresh event-type name always hits this path first) | Directly proves the fix's typed-error contract for `register_type/2`'s monotonicity pre-check query, the call site the original `BackfillTest` failure actually crashed on (see fail-then-pass proof, failure 3) |
| control: a tenant whose schema was NOT dropped is unaffected | `registry_tenant_schema_missing_test.exs` | `get_type/2` returning `:unknown_event_type` and `register_type/2` returning `{:ok, ...}` for a healthy, still-provisioned tenant | Proves the fix narrows to the diagnosed failure mode only — ordinary, non-race behavior for `get_type/2`/`register_type/2` is unchanged |
| `regression: ISS-0343 -- a tenant whose schema vanished mid-sweep is skipped, not a crash of the whole run` | `backfill_test.exs` | `Backfill.run/1`'s new `{:error, :tenant_schema_missing}` case clause: a healthy tenant is updated (`skipped` count 1, `updated` count 1) *despite* a different tenant's schema having vanished in the same sweep, and the vanished tenant's `Registration` row is confirmed to still exist (not `:tenant_not_provisioned`) | Directly proves the top-level acceptance criterion: one tenant's vanished schema no longer halts `Backfill.run/1` for every other tenant — the exact defect ISS-0343 reports, exercised at the layer the original bug report was filed against |
