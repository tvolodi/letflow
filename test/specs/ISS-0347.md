# Test Spec: ISS-0347 — `BadMapError` crash in `print_advisory/1` on a parse-failed handoff

**Issue:** ISS-0347. **Run:** `WF03-ISS0347-20260826`, WF-03 Step 4.
**Design:** `lib/letflow/design/iss0347-lint-handoffs-advisory-shape.md`.
**Fix under test:** `lib/mix/tasks/letflow.lint_handoffs.ex` — `lint_file/2`'s `{:error, reason}`
branch (JSON decode/read failure) changed `advisory: []` to
`advisory: %{path: path, warnings: [], size_info: %{desc_len: 0, summary_len: 0}}`, the same
literal shape the `:non_json` branch and the successful `:json` branch already produce.
Fix commit: `07a766ea0f6d5ded44cb8b467928b2b18024ec8c` ("fix(ISS-0347): normalize lint_file/2
parse-error advisory shape"). Parent (pre-fix) commit: `c30f672`.
**Test file:** `test/mix/tasks/letflow.lint_handoffs_test.exs` — two tests added to the existing
`existing .json handoff behavior (H1-H5) is unaffected` describe block: `F-PARSE-ADVISORY-SHAPE`
and `F-BOM-PARSE-ADVISORY-SHAPE`.

## Criterion

`run/1` calls `print_advisory(results)` for every discovered handoff file before it ever checks
whether to `Mix.raise/1`. `print_advisory/1` does unchecked dot-access on each result's
`advisory` field (`r.advisory.warnings`, and later `size_info.desc_len`/`summary_len`). Every
branch of `lint_file/2` produced a `%{path:, warnings:, size_info:}` map for `advisory` **except**
the `{:error, reason}` branch (hit when a handoff-shaped file fails `File.read` or
`Jason.decode`), which produced the bare literal `[]`. The first time any handoff-shaped file in
the corpus had invalid JSON (or a decode-rejected leading UTF-8 BOM), `print_advisory/1`'s
dot-access on that file's `advisory` raised `%BadMapError{term: []}` and crashed the entire
`mix letflow.lint_handoffs` run — not just failed it, crashed it, so even the legitimate hard
violations for every *other* file in the run went unreported.

| Acceptance criterion (from the Step-4 handoff) | Proved by |
|---|---|
| Parse-error branch does not raise `BadMapError`; completes and reports the parse error as a normal violation/advisory entry | `F-PARSE-ADVISORY-SHAPE` (invalid JSON), `F-BOM-PARSE-ADVISORY-SHAPE` (leading UTF-8 BOM) |
| Fail-then-pass demonstrated against the actual fix commit | See below |
| No wall-clock/randomness dependence | Both tests write a fixed literal to a per-test `System.tmp_dir!()` path; no `DateTime.utc_now`, no `:rand` |
| Self-sufficient, isolated fixture | Both tests reuse the `dir` fixture from the enclosing `describe` block's `setup` (a uniquely-suffixed temp dir via `System.unique_integer/1`, removed in `on_exit`) — not a shared hardcoded path |

## Why this is the ordinary fail-then-pass case, not the mutant clause

`lint_file/2` already existed pre-fix, and its `{:error, reason}` branch already existed —
this fix only changes one line inside an existing branch of an existing function (the literal
assigned to `advisory:`). The pre-fix function is fully present and callable; the regression is
about its *output shape*, not its existence. WF-03's "code under test does not exist" clause
(which requires mutation evidence) does not apply — the ordinary checkout-pre-fix-commit /
confirm-red / confirm-green procedure is the right one, and is exactly what was run.

## What the test does

Both new tests reuse the `existing .json handoff behavior (H1-H5) is unaffected` describe
block's `setup`, which creates a fresh, uniquely-named temp directory per test run
(`System.tmp_dir!()` joined with `System.unique_integer([:positive])`) and removes it in
`on_exit` — no shared or hardcoded path, no cross-test interference.

- `F-PARSE-ADVISORY-SHAPE`: writes `"{not valid json"` to a fixture file, calls
  `LintHandoffs.lint_file(path, @empty_schema)` directly (the real function `run/1` maps over
  every discovered file), confirms it lands in the `{:error, reason}` branch (`parse_error != nil`,
  a single `hard_new` violation with `rule: "PARSE"`), then performs **the exact same dot-access
  `print_advisory/1` performs** — `result.advisory.warnings`, `result.advisory.size_info.desc_len`,
  `result.advisory.size_info.summary_len` — and asserts each returns the expected zero-value
  without raising.
- `F-BOM-PARSE-ADVISORY-SHAPE`: same shape assertions, but the fixture is otherwise-valid JSON
  prefixed with a leading UTF-8 BOM (`"﻿"`), which `Jason.decode/1` rejects, landing in the
  same `{:error, reason}` branch via a different real-world trigger (a file saved by an editor
  that writes a BOM) rather than syntactically broken JSON.

Neither test calls the private `print_advisory/1` directly (it is a `defp`, not callable from
outside the module) — instead they reproduce its exact access pattern inline against the real
`lint_file/2` output, which is both the most faithful reproduction available from outside the
module and a direct assertion on the actual regression (the `advisory` field's shape).
