# Test Spec: ISS-0381 — `Letflow.Dlq.Entry.insert_changeset/2` cast list vs. docstring

**Issue:** `docs/issues/ISS-0381.yaml` (former id `ISS-0353`).
**Design:** `lib/letflow/design/iss0381-dlq-entry-insert-changeset-fix.md` (§9 specifies
the exact proof shape these tests implement).
**Fix under test:** `lib/letflow/dlq/entry.ex`'s `insert_changeset/2` — `cast/3`'s field
list narrowed from 17 to 12 fields (drops `:tenant_id`, `:status`, `:retry_count`,
`:retry_history`, `:created_at`); two `put_change/3` calls added for `:tenant_id` and
`:created_at`, placed after `cast/3` and before `validate_required/2`.
**Fix commit:** `d21d5095` (parent/pre-fix: `d21d5095^`).
**Test code:** two new `describe` blocks appended to `test/letflow/dlq_test.exs`
(existing file — no direct `insert_changeset/2` call existed there before).
**Run:** `WF03-ISS0381-20260831`, branch `feature/WF03-ISS0381-20260831`.

## 1. Defect recap

`insert_changeset/2`'s docstring claimed `status`, `retry_count`, `retry_history`,
`tenant_id`, and `created_at` were "deliberately not castable" — the actual `cast/3`
call listed all five as castable. This was harmless only because the sole caller,
`Letflow.Dlq.enqueue/2`, pre-sanitizes `attrs` via `Map.take/2` before ever reaching the
changeset — caller discipline, not the changeset itself, was the real enforcement
boundary. These tests call `insert_changeset/2` **directly**, bypassing `enqueue/2`
entirely, to prove the changeset's own mechanism now enforces the invariant its
docstring describes.

## 2. Two test shapes, per design §9

### 2.1 `:status` / `:retry_count` / `:retry_history` — value-divergence proof

A raw, unfiltered `attrs` map is built by hand with non-default values for all three
fields (`status: :discarded`, `retry_count: 7`, a non-empty forged `retry_history`),
plus the ordinary required `:entry_type` so validity turns only on the protected-field
assertions. `insert_changeset/2` is called directly with a fresh `%Entry{}`.

**Why this is fail-first-discriminating (design §9's own reasoning):** pre-fix, `cast/3`
casts all three fields verbatim from `attrs`, so `Ecto.Changeset.get_field/3` would
return the caller-supplied `:discarded`/`7`/the forged list. Post-fix, none of the three
is in `cast/3`'s field list at all, so `get_field/3` falls back to the struct's own
schema default (`:pending`/`0`/`[]`). This is the sharp, unambiguous assertion design §9
calls out as genuinely discriminating between pre- and post-fix behavior.

`:tenant_id`/`:created_at` round-trip checks are also included in this test as a sanity
check that the required fields are still populated correctly — but per design §9 these
are explicitly **not** fail-first discriminating on their own (both `cast/3` pre-fix and
`put_change/3` post-fix read the same `attrs` map), so they carry no regression-proof
weight by themselves; the second test below is what proves the `tenant_id`/`created_at`
mechanism actually changed.

### 2.2 `:tenant_id` / `:created_at` — mechanism (cast-vs-put_change error-shape) proof

Design §9 explicitly warns that a value round-trip for `:tenant_id`/`:created_at`
passes on **both** sides of the fix and proves nothing. The discriminating assertion
instead targets the mechanism: a malformed, non-castable value for each field
(`tenant_id: "not-a-uuid"`, `created_at: "not-a-timestamp"`) is passed via `attrs`
directly to `insert_changeset/2`.

- **Pre-fix:** `:tenant_id`/`:created_at` are in `cast/3`'s field list → `Ecto.UUID`
  and `:utc_datetime`'s own type-casting is attempted on these raw strings, fails, and
  `cast/3` adds an `"is invalid"` error to `changeset.errors` for each → `changeset.valid?
  == false`.
- **Post-fix:** neither field is in `cast/3`'s field list → `put_change/3` performs no
  type-casting at all, writes the raw string straight into `changeset.changes` → no cast
  error is added for either field → `changeset.valid?` is `true` at this level (any real
  type mismatch is deferred to `Repo.insert/2`, out of scope for a changeset-level test).

The test asserts `changeset.valid?`, the absence of `:tenant_id`/`:created_at` keys in
`changeset.errors`, and that `Ecto.Changeset.get_change/2` returns the raw uncast string
for both fields — confirming `put_change/3`, not `cast/3`, is what wrote them.

## 4. Test cases and why they exist

| Test | Covers | Why it constitutes regression coverage |
|---|---|---|
| "a raw, unfiltered attrs map with non-default status/retry_count/retry_history is ignored in favor of schema defaults" | `cast/3`'s narrowed field list (drops `:status`/`:retry_count`/`:retry_history`) | Directly proves the top-level defect: a caller-supplied override for these three fields can no longer reach the changeset via `cast/3`, regardless of `attrs` content — the value-divergence proof design §9 calls the "sharpest, unambiguous" assertion |
| "a malformed (non-UUID) tenant_id and a non-parseable created_at surface no changeset-level cast error, deferring failure past changeset validity" | the two `put_change/3` calls for `:tenant_id`/`:created_at` | Proves the mechanism actually changed from `cast/3` to `put_change/3` for these two fields specifically, via the cast-vs-put_change error-shape divergence design §9 identifies as the only discriminating assertion available for fields that still read from the same `attrs` map on both sides of the fix |
