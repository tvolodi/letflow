`lib/letflow/routers/instances.ex`), `Letflow.Scheduler.resolve_advance_target/3` (new

1. Un-skip `shipment-ops-timeout-escalation.yaml` step 2 (`via: skip` → `via: api`) so the

2. Add direct coverage of `resolve_advance_target/3`'s branches and the route's error paths
   — at handoff time **zero** tests anywhere in the suite referenced
   `resolve_advance_target` by name (confirmed by grep before writing any test), and
   `test/letflow/routers/instances_test.exs` had no `advance-timer` tests at all.

## Why this needs real coverage, not just "the scenario passes now"

`resolve_advance_target/3` has seven distinct outcomes (design §3): 0/1/2+ pending timers
with no `timer_id`, and not-found/not-pending/wrong-instance/correct for an explicit
`timer_id` (the last three folding into one `{:error, :no_pending_timer}` — the "same-404"
discipline). The REQ-206 scenario alone only ever exercises exactly one of these seven (the
"exactly one pending timer, no `timer_id`" success path) — passing it proves the happy path
works, nothing about the six other branches, the 400/404/422 status mapping, or the new
`:InstancesAdvanceTimer` authz wiring actually being enforced at the router (as opposed to
just declared, which AC4's existing generic route-walk already checks separately).

## A pre-existing bug this pass uncovered (not part of ISS-0389's own scope, fixed as a
## necessary side effect of exercising the fixture for real)

Un-skipping step 2 required actually dispatching `process_shipment_dispatch.yaml` through
`Letflow.Engine.create/2` for the first time ever — no test had done this before.
`test/letflow/simulation/req206_swiftroute_test.exs`'s own `swiftroute-shipment-ops-timeout-
escalation` describe block destructured `definitions: %{approval: definition}` (the
unrelated `SimpleShipmentApproval` graph used by the *other* scenario in this file)
instead of `%{dispatch: definition}` — inert while step 2 was a no-op `:skip` (both graphs
satisfy an ACTIVE-status check identically), but wrong the moment step 2 needs a real
pending timer against the real graph. Fixed as part of this un-skip; see that test's own
comment block for the full explanation.

Separately, dispatching the real graph for the first time also surfaced a genuine,
independent structural bug: `parallel-fork` had both `in_degree > 1` (both
`injury-check`'s false-branch edge and `safety-notification`'s edge converged directly onto
it) and `out_degree > 1` (its own fork edges) — `Letflow.Engine.Transition`'s
`gateway_role/2` classifies that shape as `:combined_unsupported`, which `Engine.create/2`
correctly rejects. Fixed with a new pure-merge `injury-check-merge` `EXCLUSIVE_GATEWAY`
node inserted between the injury-check branches and `parallel-fork`, so `parallel-fork`
itself is now a pure split. See `process_shipment_dispatch.yaml`'s own header comment for
the full mechanism.

## Test cases

### 1. `Letflow.Scheduler.resolve_advance_target/3` — `test/letflow/scheduler_test.exs`

**`describe "ISS-0389: resolve_advance_target/3 -- timer_id absent (0/1/2+ pending)"`:**
- Zero pending timers → `{:error, :no_pending_timer}`.
- Exactly one pending timer → `{:ok, timer}` (id matches).
- A pending timer belonging to a *different* instance is not counted (still 0 for the
  instance under test).
- A non-pending (fired) timer for the instance is not counted (still 0).
- Two or more pending timers → `{:error, :ambiguous_pending_timers}`.

**`describe "ISS-0389: resolve_advance_target/3 -- timer_id present (same-404 fold)"`:**
- `timer_id` matches a real pending timer on the same instance → `{:ok, timer}`.
- `timer_id` does not exist at all → `{:error, :no_pending_timer}`.
- `timer_id` exists but is not pending (already fired) → `{:error, :no_pending_timer}`.
- `timer_id` exists, is pending, but belongs to a *different* instance (the cross-instance
  guard) → `{:error, :no_pending_timer}`.

All seven of the design's §3 branch outcomes are covered directly, isolated from
`fire_timer/2` and the engine — pure targeting-resolution correctness, exactly matching
this function's own `@spec`.

### 2. Router-level — `test/letflow/routers/instances_test.exs`, `describe "advance-timer"`

Uses a new `graph_timer_end/0` fixture (`START -> TIMER("timer", duration_iso8601: "P1D")
-> END`) and `start_instance_with_timer!/1` helper, giving a fresh instance exactly one
real, armed, force-fireable pending timer (REQ-187's engine arms it automatically on token
arrival).

- **AC5** — empty JSON body (`{}`) against an instance with exactly one pending timer →
  200, `timer_status: "fired"`, `node_id: "timer"`. End-to-end proof the firing actually
  drove the token off the TIMER node: since the graph is `TIMER -> END`, firing completes
  the instance (`instance_status == :completed`) and leaves zero pending timers.
- **AC6** — an instance with zero pending timers (a plain `HUMAN_TASK` graph, no timer
  ever armed) → 404.
- **AC7** — no `timer_id`, two or more pending timers (a second timer armed directly via
  `Scheduler.create/2`) → 400; both timers remain pending (nothing fired).
- **AC8** — a `timer_id` naming a real pending timer belonging to a *different* instance →
  404, not a cross-instance fire; both instances' timers remain pending afterward
  (explicitly asserted, not just the status code).
- **AC9** — a syntactically invalid `instance_id` → 422; a syntactically invalid `timer_id`
  → 422 (timer remains pending).
- Design §4's "body present but not a JSON object" → 400 (a JSON array body; timer remains
  pending).
- Authorization: a caller with `TASK_WORKER` (does not hold `:InstancesAdvanceTimer`) → 403,
  and the timer is not fired. This is a router-enforcement test, distinct from
  `authorization_enforcement_test.exs`'s existing generic route-walk (AC4), which only
  proves the declared policy key resolves to a real `endpoint_policy_key/2` clause, not
  that the router actually denies an unauthorized caller end to end.

### 3. Simulation scenario — `test/letflow/simulation/req206_swiftroute_test.exs`

`swiftroute-shipment-ops-timeout-escalation` describe block rewritten: step 2 is now
`via: api`, asserting `outcome == :ok`, `captured["timer_status"] == "fired"`,
`captured["node_id"] == "ops-escalation-timer"`. Step 3 (`GET /instances/:id`) asserts the
instance is still `ACTIVE` (the `ops-assessment`/`finance-estimate` `HUMAN_TASK`s are still
outstanding, so `parallel-join` cannot fire yet) — and, since `GET`'s own response shape
(`instance_map/1`) carries no `tokens` field (only `POST /:id/reconstruct` does), the actual
"token moved off the TIMER node" proof reads `current_nodes` directly off the real
`instance_projections` row: `ops-escalation-timer` is absent, `ops-assessment` and
`finance-estimate` are still present.

`process_shipment_dispatch.yaml` gained a real `ops-escalation-timer` TIMER node (forked in
parallel with `ops-assessment`/`finance-estimate`, feeding `parallel-join`), matching this
fixture's own long-standing header description ("Exercises: parallel fork/join, timer
escalation") for the first time — the pre-existing `timeout-ops-assessment` comment-only
edge on the `ops-assessment` `HUMAN_TASK` was never a real engine timer mechanism (REQ-187
only arms a timer for a genuine `node_type: TIMER` node; a `HUMAN_TASK` has no
boundary-timer mechanism in this engine), and is left untouched (out of this issue's scope).

## Non-existence mutation check (per WF-03 "code under test did not exist")

`resolve_advance_target/3`, the route, and the `:InstancesAdvanceTimer` permission are all
brand new in this run — a pre-fix/post-fix regression demonstration is not meaningful here
(the pre-fix "failure" would just be `UndefinedFunctionError`/404-route-not-found, proving
nothing about the new logic's correctness). Per the workflow's own instruction for this
case, a mutant was applied to the shipped logic instead:

**Mutant:** in `lib/letflow/scheduler.ex`'s `resolve_advance_target/3`, the `[_ | _] ->
{:error, :ambiguous_pending_timers}` clause was changed to `[_ | _] -> {:error,
:no_pending_timer}` (silently collapsing the ambiguous-timers case into the
zero-timers case).

**Measured result:** `mix test test/letflow/scheduler_test.exs test/letflow/routers/instances_test.exs`
went from 80 passed / 0 failed to **78 passed / 2 failed**, with exactly the two tests
written to catch this branch failing:
1. `ISS-0389: resolve_advance_target/3 -- timer_id absent (0/1/2+ pending) two or more
   pending timers -> {:error, :ambiguous_pending_timers}` (`scheduler_test.exs`)
2. `advance-timer no timer_id against an instance with two or more pending timers returns
   400` (`instances_test.exs`, AC7)

No other test in either file was affected — the mutant's blast radius matched exactly the
tests designed to catch it, and nothing else.

**Revert:** the clause was restored to `[_ | _] -> {:error, :ambiguous_pending_timers}`,
and `mix test test/letflow/scheduler_test.exs test/letflow/routers/instances_test.exs`
returned to 80 passed / 0 failed, confirming the revert.
