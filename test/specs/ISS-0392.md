build-time skip/defer)
**Fix commit:** `e30873f8` (entirely `lib/letflow/engine.ex`)
**Test tier:** unit+integration (DB-integration, `Letflow.DataCase`, real Postgres per

**Test file:** `test/letflow/engine_sub_process_test.exs`, `describe "ISS-0392 -- a

## The scenario (design doc §5)

1. A parent process definition: `START -> HUMAN_TASK("gate") -> SUB_PROCESS("sp") ->
   END` (`graph_parent_task_then_subprocess_no_split/1`, already existing in this file,
   used unmodified by ISS-0067's own tests).
2. A child process definition referenced by `SUB_PROCESS("sp")` that is itself `START ->
   END` — no intervening task at all (`graph_child_immediate/0`, new). This is what
   drives `prepare_child_activation/4` to `InstanceState.status == :completed`
   **synchronously**, before any `Ecto.Multi` step for the child exists.
3. Start the parent instance (reaches `HUMAN_TASK("gate")`, pending).
4. Call `Engine.complete_task/3` on the `"gate"` task. This single hop chain reaches
   `SUB_PROCESS("sp")`, spawns the child, the child completes synchronously inside the
   same transaction, and that completion chains back into the parent
   (`sub_process_completed`), advancing the parent to `END` — the exact collision
   ISS-0392 files: `build_task_activation_and_reconciliation_multi/3`'s own
   `{:task_records, parent_instance_id}` step (call 1, built unconditionally for the
   gate-completion hop chain) collided with the child's own completion cascade's
   `{:task_records, parent_instance_id}` step (call 2, appended by
   `SubProcess.build_completion_write_steps/12` when the synchronous-completion branch
   fires) — both keyed on the same `parent_instance_id`.

## Test cases

1. **"single-level: gate completion cascades through synchronous child completion, no
   raise, no orphan task row"** — `test/letflow/engine_sub_process_test.exs:1023`.
   Reproduces ISS-0392's own filed repro exactly (the single-level case, the only one
   ISS-0392 itself files a scope claim about). Asserts, in order:
   - `Engine.complete_task/3` does **not** raise (pre-fix: raises `RuntimeError`
     `"cannot merge Multi; ... task_records: ..."` — verified below, this is not an
     assertion inside the test itself since ExUnit cannot both let a raise propagate and
     assert `{:ok, _}` in the same test; the fail-then-pass verification captures this
     half).
   - Returns `{:ok, result}` — the Multi commits.
   - `result.instance_status == :active`, not `:completed` — this is *not* a claim about
     the fix; it documents that `complete_task/3`'s own return value reflects
     `final_instance_state`, the pre-cascade snapshot from call (1)'s own transition,
     evaluated *before* the child's synchronous completion cascades back in. Asserting
     this explicitly (rather than only the projection) prevents a future reader from
     mistaking the return value for where the fix's effect is observable.
   - The **persisted parent projection** reaches `status: :completed` — this is where
     design doc §2.3's dominance argument (call 2's diff, computed after the cascade,
     strictly dominates call 1's) is actually observable: `reconcile_projection/4`
     writes from the further-advanced state the cascade produces, not from
     `final_instance_state` alone.
   - No orphan/duplicate task row: the total task-row count for the parent instance is
     unchanged before/after, and the only row that ever existed is the original gate
     task. Design doc §5 point 6 states this is a *structural* guarantee under the fix
     (call 1's step for `parent_instance_id` is never built at all when the scenario's
     predicate is true, so there is no earlier-snapshot `pending_task_nodes` row to have
     inserted in the first place) — not a race outcome to verify probabilistically. This
     is the assertion that most directly exercises the fix's own mechanism (the
     `skip_task_activation?` predicate), as opposed to merely "it didn't crash."
   - A single `SUB_PROCESS_COMPLETED` event exists on the parent's stream, naming the
     right child — confirms the completion actually propagated through the intended
     path (call 2's cascade), not some other, coincidentally-non-crashing path.

   *Deliberately not asserted:* the child's own `InstanceProjection.status`. Read
   `sub_process.ex:520-544`'s `insert_child_instance_projection/8`: it hardcodes
   `status: :active` at insert time regardless of `child_initial_state.status`, and
   nothing later in this hop chain updates that row. This is pre-existing behavior,
   orthogonal to ISS-0392's own scope (the collision and its fix are both about the
   *parent's* `{:task_records, parent_instance_id}` Multi step, not the child's
   projection row) — asserting it here would either fail on both pre-fix and post-fix
   code (proving nothing about the fix) or require silently expanding this issue's scope
   to a second, unrelated defect. Flagged in this spec rather than asserted so it isn't
   lost; not filed as a new issue by TEST-DESIGNER since diagnosing whether it is worth
   fixing is ISSUE-FIXER's call, not this handoff's.

2. **"multi-level cascade: two synchronous SUB_PROCESS completions in one transaction,
   distinct instance_ids never collide"** — `test/letflow/engine_sub_process_test.exs:
   1100`. Design doc §5 point 7's second scenario: an outer (grandparent) instance whose
   own `SUB_PROCESS("outer_sp")` points at the step-1 parent definition (itself
   containing `SUB_PROCESS("sp")` pointing at the synchronously-completing child).
   Structured as two hops:
   - Completing `"outer_gate"` spawns the middle instance as `outer_sp`'s child. The
     middle instance's own first node is `HUMAN_TASK("gate")`, so it does **not**
     complete synchronously on spawn — it is left `:active`, waiting on its own `"gate"`
     task. This hop is asserted to leave the outer instance `:active` and the middle
     instance's projection `:active`: it establishes the baseline (this hop alone never
     touches the predicate at all, since the middle child's own
     `child_initial_state.status` is `:active`, not `:completed`) before the actually
     cascading hop below.
   - Completing the **middle** instance's own `"gate"` task is the hop that cascades: it
     spawns the innermost child (synchronous completion, collides on
     `{:task_records, middle_instance_id}` — §2's predicate firing for the middle
     instance), which chains the middle instance to `:completed`, which in turn fires
     `maybe_cascade_to_grandparent/6`'s `:completed` clause and chains the **outer**
     instance to `:completed` too, appending a second, independently-keyed
     `{:task_records, outer_instance_id}` step. Per design doc §3.2, these two
     `instance_id`s are distinct by construction, so the second append never collides
     with anything *regardless* of the fix — this variant exists to confirm the
     single-level fix doesn't regress the (already-non-colliding) multi-level case, not
     to exercise a second instance of the predicate.
   - Same no-orphan-task-row assertions as test 1, now checked independently at both the
     middle and outer `instance_id`s — the fix's per-`instance_id` scoping (design doc
     §2.2's predicate is evaluated once per hop chain, not globally) is worth confirming
     doesn't leak across levels.
   - `SUB_PROCESS_COMPLETED` events on both the middle and outer streams.

## Why these two cases, not more

Design doc §5 names exactly these two scenarios (single-level, the core repro; and
multi-level cascade, confirming the fix doesn't regress or interact badly with the
already-non-colliding multi-level path). §6 OQ-2 explicitly flags a third, deeper
scenario — `instance_id` reuse as its own multi-level SUB_PROCESS ancestor (a
self-ancestor collision the fix does **not** address, by the design's own admission) —
as an open question for ORCH/TEST-DESIGNER to decide is in- or out-of-scope for this
fix's closure, not silently resolved by omission. **This test spec does not add a third
case for it**: constructing a definition where an instance is its own multi-level
SUB_PROCESS ancestor is not confirmed reachable through any currently-enforced
graph-validation rule (design doc §6 OQ-2's own caveat — REQ-062's graph-validation
rules are not re-read in full here to settle this), and ISS-0392's own filed scope
(`docs/issues/ISS-0392.yaml`) only covers the single-level collision actually observed in
production. Recommendation: if this gap is judged worth closing, file it as its own
follow-up issue via `docs/agents/protocols/ISSUE_QUEUE.md`, distinct from ISS-0392 (which
this fix closes for the case ISS-0392's own repro exercises), rather than growing this
regression test to speculatively cover a scenario neither the filed issue nor the design
names.
