## 2. Finding: gap in the cyclic-escape cross-order assertion (fixed)

Design doc §2.4b's own assertion-1 spec states: "TEST-DESIGNER should assert both
fixtures' full result tuples are equal, not just that each independently succeeds."
The as-written test (before this pass) checked `counter_a`/`counter_b`'s
`expected_from_branches` **against each fixture's own `branch_ids`**, and checked `"B"`
is present in each fixture's own token list — real assertions, but never a direct
comparison of fixture-A's outcome against fixture-B's outcome. That is exactly the gap
the design doc calls out: a bug that makes both orders *independently* satisfy their own
per-fixture shape (e.g. both resolve to *some* singleton, both register *some*
`JoinCounter` under `"JOIN"`) while still differing from each other between orders would
not have been caught.

**Why an exact `InstanceState` equality isn't the right shape here (confirmed by reading
`dispatch_parallel_split/4`, transition.ex:748–798):** `branch_id`/`token_id` for each new
token is `token.token_id <> "/" <> Integer.to_string(index)` — purely positional in
`edges_out`, independent of which node the edge targets. Reversing the split's edge order
(as `cyclic_escape_graph_reversed_edges/0` does) therefore reverses *which* node
`"t1/0"`/`"t1/1"` land on, so the two fixtures' `new_state.tokens` lists are genuinely,
correctly different in content (by design, not a bug) — asserting `new_state_a == new_state_b`
would be a false requirement. What **is** invariant regardless of edge order —
because `branch_ids` itself is computed purely from `length(edges_out)` and the parent
`token_id`, never from targets — is the full `%JoinCounter{}` built from it: same
`join_node_id` ("JOIN"), same `origin_token_id`, same `expected_from_branches` set, same
(empty) `received_from_branches`/`cancelled_branches`. This is the genuine
order-independence signature of a sound SCC-keyed memo, and is exactly what a
plain node-keyed memo (iteration 2) cannot guarantee — confirmed by design §2.4b's trace
showing `memo["GW"]` differing in *shape* (singleton `:dead_end` vs. a non-singleton
two-element set) between entry orders, which would surface here as one of the two
`JoinCounter`s failing to exist at all (an `{:error, :no_matching_join}` for that
order), or, in a hypothetical partially-fixed variant, as the two `JoinCounter`s existing
but disagreeing.

**Fix applied** (`test/letflow/engine/parallel_gateway_test.exs`, the
`cyclic_escape_graph/0` `describe` block): added
`assert Enum.sort(branch_ids_a) == Enum.sort(branch_ids_b)` and
`assert counter_a == counter_b` — a direct, literal cross-order comparison of the one
value that must be order-invariant, with a comment explaining why (not a restatement of
the assertion).

## 3. `diamond_chain_graph(40)` — confirmed a genuine regression guard, empirically

Design §4 left the exact `k` to TEST-DESIGNER's judgment, suggesting `k = 20` as a
sufficient illustrative value; the shipped test uses `k = 40`. Rather than trust the
design doc's complexity argument alone, this pass empirically confirmed the guard by
reverting `lib/letflow/engine/transition.ex` to each prior iteration and re-running the
suite (procedure and full output in §4 below). Result: at `k = 40`, iteration 1's
unmemoized per-path-copy scheme did not merely run slower — it **hit ExUnit's 60-second
default test timeout and was killed**, a decisive, unambiguous failure mode for a CI
suite (as opposed to "1.8s vs 4ms," which could be missed under load-induced timing
noise). This confirms `k = 40` is comfortably large enough to be a real regression guard
for this defect class, not an accidentally-too-small value that "happens to still pass
fast" under either algorithm.

## 5. Test cases and why they exist

| Test | Covers | Why it constitutes regression coverage |
|---|---|---|
| "a branch that passes through an EXCLUSIVE_GATEWAY before reconverging on the join still resolves and splits successfully" | §2.2.2 step 5's broadening (any non-`PARALLEL_GATEWAY` branching node no longer auto-fails a branch) | Directly reproduces ISS-0398.yaml's own reported scenario (a multi-edge `EXCLUSIVE_GATEWAY` inside a fork branch); fails pre-ISS-0398 (§4a), passes on every ISS-0398 iteration including the shipped fix |
| "a branch whose EXCLUSIVE_GATEWAY has one path reaching the join and another dead-ending still fails the whole split" | §2.5's per-branch singleton-leaf-set agreement rule | Proves the broadened search doesn't over-eagerly accept a branch just because *one* of its internal paths reaches the right gateway — a real false-positive risk the broadening itself introduces |
| "a 40-diamond chain resolves correctly and completes well within a generous time budget" | §2.2.2's memoization (the fix for SECURITY-REVIEWER's exponential-blowup BLOCKER) | Empirically confirmed (§4b) to time out ExUnit's 60s default under iteration 1's unmemoized scheme at this `k`, and to complete in under 2s post-fix — a genuine, empirically-verified complexity regression guard, not merely a correctness check |
| "cyclic_escape_graph/0 and its edge-order-reversed twin produce identical results" | §2.2.1's SCC-keyed memoization (the fix for CODE-DESIGN-VALIDATOR's memo-key-unsoundness BLOCKER) | Empirically confirmed (§4b) to fail under iteration 2's plain node-keyed memo at this exact shape (a cycle through a gateway with an internal escape edge); this pass added the literal cross-order `JoinCounter` equality assertion (§2) the design doc calls for, closing a gap where the test checked per-fixture shape but never fixture-A-vs-fixture-B agreement directly |
| "a pure escape-less cycle (no gateway reachable) fails the whole split cleanly" | §2.2.1/§2.2.2 step 2's empty-aggregate semantic correction (a live back-edge contributes no leaf, not `:dead_end`) | Confirms the *new* empty-set treatment for an escape-less cycle still produces the same external `{:error, :no_matching_join_found}` outcome iteration 2's `:dead_end`-based treatment would also have produced for this specific shape — a "doesn't regress this adjacent case" check, not a defect-discriminating one by itself |

## 6. Isolation conventions confirmed

- All 6 new fixtures are plain functions returning a fresh `%Graph{}` literal each call
  (`branch_with_exclusive_gateway_graph/0`, etc.) — no shared mutable state, no
  module-level `setup`, matching `three_branch_graph/0`'s existing pattern.
- `describe`-scoped, one fixture (or fixture pair) per new `describe` block, mirroring
  the AC1–AC6 groups' own one-graph-per-scenario convention.
- The module remains `async: true` (no `Letflow.Repo`/`Ecto.Sandbox` dependency anywhere
  in this file) — unaffected by the new tests, all of which are pure `Transition.transition/3`
  calls over in-memory structs.
- `diamond_chain_graph/1`'s parameterization (`k`) is a plain function argument, not a
  process/application-level configuration value — no risk of one test's `k` leaking into
  another's expectations.
