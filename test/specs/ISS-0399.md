# Test Spec: ISS-0399 — Content-scanning/antivirus pipeline for instance attachments

**Issue:** ISS-0399, GH#781 — REQ-211's `Letflow.Repository.Attachments.upload/2`
deliberately deferred AV/content-scanning of uploaded attachment bytes. This fix closes
that deferral: a synchronous, reject-before-persist scan step, a pluggable
`Letflow.Repository.AttachmentScanner` behaviour with a real default adapter
(`SignatureHeuristic`, EICAR-signature detection), a new `scan_status` column
(`instance_attachments`), and a `get_content/2` gate that blocks byte-serving for
anything not `:clean`.

**Run:** WF03-ISS0399-20260907, WF-03 Step 4. **Design:**
`lib/letflow/design/iss0399-attachment-content-scanning.md` (§1 schema, §2 sync/
reject-before-persist decision, §3 scanner behaviour + default adapter, §4 function
signatures, §5 what happens to an infected/failed row, §6 SECURITY-REVIEWER invariants,
§7 open questions). Implementation commit: `60f3614e` (`feat(ISS-0399):
content-scanning/AV pipeline for instance attachments`). SECURITY-REVIEWER and REVIEWER
already PASSed that commit on this branch.

**Code under test:**
- `lib/letflow/repository/attachment_scanner.ex` — `Letflow.Repository.AttachmentScanner`
  behaviour (new).
- `lib/letflow/repository/attachment_scanner/signature_heuristic.ex` — default adapter
  (new).
- `priv/repo/migrations/20260907020001_add_scan_status_to_instance_attachments.exs` —
  `scan_status` column, `null: false, default: "pending"` (new).
- `lib/letflow/repository/attachment.ex` — schema gains `scan_status` (`Ecto.Enum`).
- `lib/letflow/repository/attachments.ex` — `upload/2`'s new scan step,
  `run_attachment_scan/2`'s rescue-wrapped adapter call, `get_content/2`'s
  `check_scan_status_clean/1` gate.
- `lib/letflow/routers/instances.ex` — new error-to-status mapping for
  `{:error, :infected, _}` (422), `{:error, :scan_unavailable}` (503), and
  `get_content/2`'s `{:error, :not_available}` (409).

**Why this is a wholly-new-module case, not an existing-behavior fix:** the scanner
module, the `scan_status` column, and every code path this design adds did not exist
before commit `60f3614e`. Per WF-03's "When the pre-fix failure is 'the code under test
does not exist'" clause, the ordinary fail-then-pass-against-the-pre-fix-commit proof is
trivially satisfiable here (every new test would just raise `UndefinedFunctionError`
against `main`, which proves the module is new and nothing about whether these tests
discriminate a correct implementation from a wrong one). The **Mutation-testing
addendum** below is what actually demonstrates coverage, per that clause's requirement.

## AC1 — clean (non-EICAR) upload gets `scan_status: :clean` and is servable

**Criterion (design §2 step 6, §4.2):** an upload whose bytes are not flagged is marked
`:clean` and its content remains fetchable via `get_content/2`.

**Why this exists, not just what it restates:** proves the scan step is on the *happy*
path too — a scan that always rejected, or that never actually wired `scan_status` into
the insert, would still make every existing REQ-211 upload test fail; this closes that
gap explicitly with an assertion on the returned `scan_status` field itself, not just
"upload succeeded."

**Test case:** `test/letflow/repository/attachments_test.exs`, describe `"ISS-0399:
clean upload is scanned, marked :clean, and servable"` — uploads ordinary text bytes,
asserts `attachment.scan_status == :clean`, then calls `get_content/2` and asserts the
returned artifact's content matches exactly.

## AC2 — EICAR-signature upload is rejected, nothing persisted

**Criterion (design §2 step 3, §5):** `upload/2` returns `{:error, :infected, verdict}`;
neither `repository_artifacts` nor `instance_attachments` gains a row.

**Why this exists, not just what it restates:** the design's whole reject-before-persist
guarantee (§2.1(a)) is only real if nothing is written on the infected path — a test
that only checked the return value would miss a bug that returns the right error tuple
while still leaving a row behind (Mutant A below is exactly this trap). Asserted
directly via `Repo.aggregate(..., :count, ...)` on both tables, not inferred from a
subsequent `get/2` call.

**Test case:** `test/letflow/repository/attachments_test.exs`, describe `"ISS-0399:
EICAR-signature upload is rejected and nothing is persisted"`, test `"upload/2 returns
{:error, :infected, verdict} and creates neither an instance_attachments nor a
repository_artifacts row"`.

## AC3 — a scanner exception fails closed, never a false-clean

**Criterion (design §2 step 3, §6 INV-8):** if the configured adapter raises,
`run_attachment_scan/2`'s `rescue` clause must turn that into `{:error, reason}`, which
`upload/2` maps to `{:error, :scan_unavailable}` — never a silent `{:ok, :clean}`.

**Why this exists, not just what it restates:** `SignatureHeuristic` itself can never
raise (design §3.2, pure binary match), so this path is only exercised by a future/
non-default adapter — meaning without a dedicated test double, this branch would be
completely unexercised by anything else in this suite, and a broken rescue clause (the
literal trap named in the issue's own instructions, Mutant B below) would ship
undetected. A test-double `RaisingScanner` module (`@behaviour
Letflow.Repository.AttachmentScanner`, `scan/2` unconditionally raises), swapped in via
`Application.put_env(:letflow, :attachment_scanner, ...)` (same idiom as
`platform_test.exs`'s `put_service_caller!/1`), makes this reachable.

**Test case:** `test/letflow/repository/attachments_test.exs`, describe `"ISS-0399: a
scanner adapter exception fails closed, never a false-clean"`, test `"an adapter that
raises returns {:error, :scan_unavailable}, not a false {:ok, :clean}, and nothing is
persisted"` — asserts the exact return tuple AND that both tables' row counts stay at 0
(the only way {:error, :scan_unavailable} being returned while something got persisted
anyway could otherwise slip through unnoticed).

## AC4 — `get_content/2` never serves a non-`:clean` attachment's bytes

**Criterion (design §4.2):** any `scan_status` other than `:clean` (`:pending`,
`:infected`, `:error`) returns `{:error, :not_available}`; metadata (`get/2`, `list/2`)
is unaffected.

**Why this exists, not just what it restates:** `upload/2`'s own reject-before-persist
guarantee (AC2) already makes an `:infected`/`:error` row structurally unreachable via
`upload/2` itself — the ONE row shape this gate can ever actually observe in practice is
a **pre-existing** row from before this migration shipped, which defaults to `:pending`
(design §1.1). Since `upload/2` can never produce such a row, the ONLY way to exercise
this gate at all is to construct one directly, bypassing `upload/2` entirely — exactly
what these tests do (`Repository.upsert_content/6` + `Attachment.changeset/2` +
`Repo.insert/2`, mirroring how `repository_artifacts`/`instance_attachments` rows
legitimately end up in that state). Both `:pending` and `:infected` are covered
separately since design §4.2 states the gate treats them uniformly but the design
explicitly reserves `:infected`/`:error` as "not reachable via this module's own code
today, but not provably unreachable forever" (§5) — worth its own test, not merged into
the `:pending` case, precisely because that clause anticipates a future write path this
suite should not assume away.

**Test cases:** `test/letflow/repository/attachments_test.exs`, describe `"ISS-0399: a
non-:clean attachment's content is never servable via get_content/2"`:
- `"a :pending row (pre-existing/backfilled shape) is rejected with {:error,
  :not_available}"` — also asserts `get/2` still succeeds and reports `scan_status:
  :pending` (metadata path unaffected, per design §4.2's last paragraph).
- `"an :infected row (not reachable via upload/2, simulated directly) is rejected with
  {:error, :not_available}"`.

## AC5 — an infected-upload attempt is audit-logged without leaking raw bytes

**Criterion (design §2 step 3):** one structured `Logger.warning/2` entry names
`tenant_id`/`instance_id`/`uploaded_by`/`content_hash`, never the raw bytes.

**Why this exists, not just what it restates:** the design is explicit that this log
line exists so a rejected malicious-upload attempt is not silently invisible to
operators (since, by AC2, no `instance_attachments` row exists to record it any other
way) — a test that only checked "some log line appeared" would miss both halves of the
actual requirement: that the RIGHT fields are present (so an operator can act on it) and
that the raw content is absent (so the log itself doesn't become a vector for exactly
the payload it's warning about).

**Test case:** `test/letflow/repository/attachments_test.exs`, describe `"ISS-0399:
EICAR-signature upload is rejected and nothing is persisted"`, test `"an EICAR upload
rejection is audit-logged with tenant/actor/hash metadata but never the raw bytes"` —
`ExUnit.CaptureLog.capture_log([metadata: :all], fn -> ... end)`, asserts the message
text plus `tenant_id`/`instance_id`/`uploaded_by`/hex-encoded `content_hash` all appear,
and `refute`s the literal `"EICAR-STANDARD-ANTIVIRUS-TEST-FILE"` substring appears
anywhere in the captured output.

## AC6 — `SignatureHeuristic` adapter unit coverage

**Criterion (design §3.2):** a real, deterministic EICAR-substring scanner —
`content_type`-independent, cannot return `{:error, _}`.

**Why this exists, not just what it restates:** a pure function with no I/O gets a
direct unit test per the test developer guide's "pure functions first" principle,
independent of the context-module-level integration tests above — this isolates the
detection LOGIC itself (does it match a substring correctly, is it a real match and not
a loose heuristic) from the upload pipeline's own wiring, so a future adapter swap or
refactor gets a fast, DB-free signal.

**Test cases:** `test/letflow/repository/attachment_scanner/signature_heuristic_test.exs`
(new file), describe `"scan/2"`: ordinary content → `:clean`; empty content → `:clean`;
exact EICAR string → `:infected`; EICAR as a substring of larger content → `:infected`;
`content_type` never consulted (same EICAR payload flagged under `"application/pdf"` and
`"image/png"`); a near-miss (one character altered inside the signature) → `:clean`
(proves this is a real substring match, not a loose heuristic); never returns
`{:error, _}` for any input tried.

## AC7 — route-level error mapping (design §7 OQ-4): 422 / 503 / 409

**Criterion:** `{:error, :infected, _}` → 422, `{:error, :scan_unavailable}` → 503 (both
from the `POST .../attachments` upload route), and `get_content/2`'s
`{:error, :not_available}` → 409 (the byte-content `GET` route) — none of the three may
be a 500 or a 404.

**Why this exists, not just what it restates:** the context-module-level tests above
prove `Letflow.Repository.Attachments` returns the right tagged tuples; this AC proves
the HTTP layer actually maps them to the documented statuses, per
`lib/letflow/routers/instances.ex`'s own `render_upload_attachment/2` and
`handle_get_attachment_content/3` clauses — a route-mapping bug (e.g. an `:infected`
clause accidentally falling through to the generic 500 handler) would be invisible to
every test above.

**On why the 422 test uses a fixture scanner instead of literal EICAR bytes over real
HTTP multipart:** initially written against real EICAR bytes through
`Plug.Parsers`'s real multipart temp-file path (matching this file's other multipart
tests' own established idiom). That version flaked reproducibly on this dev machine with
`** (File.Error) could not read file ... : I/O error` — Windows Defender (a live,
real-world antivirus product on this host) detected and quarantined/deleted the EICAR-
content temp file between Plug writing it and the route reading it back, which is a
correct real-world AV behavior, not a defect in this code. Since the actual EICAR-
detection logic is already covered independently at both the context-module level (AC2)
and the unit level (AC6), this test's own job — proving the ROUTE's status-code mapping,
which is orthogonal to which scanner produced the `:infected` verdict — is served just
as well, and more reliably, by a fixture `AlwaysInfectedScanner` swapped in via
`Application.put_env/3` (matching the 503 test's own `UnavailableScanner` idiom
immediately below it).

**Test cases:** `test/letflow/routers/req212_attachments_routes_test.exs`:
- describe `"ISS-0399: POST upload rejected by the scanner -> 422, nothing persisted"` —
  `AlwaysInfectedScanner` fixture returns `{:ok, :infected, "fixture-verdict"}`; asserts
  `conn.status == 422`, the JSON `detail` names both "content scan" and the verdict, and
  `list/2` shows no persisted row.
- describe `"ISS-0399: POST upload when the scanner adapter is unavailable -> 503,
  nothing persisted"` — `UnavailableScanner` fixture returns
  `{:error, :simulated_unavailable}`; asserts `conn.status == 503` and nothing persisted.
- describe `"ISS-0399: GET content for a non-:clean attachment -> 409"` — constructs a
  `:pending` row directly (same technique as AC4), dispatches the byte-content `GET`
  route, asserts `conn.status == 409` — distinct from the 404 (nonexistent/cross-tenant)
  and 500 (`:content_missing`) cases this same route already covers elsewhere in this
  file.

## AC8 — the corrected moduledoc assertion

**Criterion (design §4.3):** `Letflow.Repository.Attachments`'s moduledoc's old
"Content-scanning deferral" section (which said this was a "deliberately deferred
follow-up") must be REPLACED, not appended to, by a statement of the mechanism actually
shipped — the deferral is resolved, so a test still asserting deferral language would be
asserting something no longer true.

**Why this exists, not just what it restates:** this is the KNOWN BROKEN TEST named
explicitly in this run's own handoff — ELIXIR-DEV correctly replaced the deferral
section per design §4.3, but the pre-existing test in
`test/letflow/repository/attachments_test.exs` (describe `"moduledoc content
statements"`) still asserted the OLD deferral text and was failing at commit `60f3614e`.
Fixed here by asserting what the moduledoc SHOULD now say (mentions "synchronous",
"reject-before-persist", and the default adapter's fully-qualified name) and explicitly
`refute`ing the old "deliberately deferred follow-up" phrase is still present — this is
a positive assertion of the corrected behavior, not merely a deletion of the old,
now-wrong check.

**Test case:** `test/letflow/repository/attachments_test.exs`, describe `"moduledoc
content statements"`, test `"states per-tenant dedup boundary, no-canonicalisation, and
the real content-scanning mechanism (ISS-0399)"`.

## Mutation-testing addendum (WF-03 "code under test does not exist" clause)

Per the workflow's own instruction, since every ISS-0399 code path is new (no pre-fix
commit exists where these functions/module were present-but-buggy), fail-then-pass
against a pre-fix checkout would be vacuous. Instead: the shipped logic was mutated
**in a throwaway `git worktree`** (`../letflow-2-mutwt`, detached at this branch's test
commit `0f92da2a`) — the working checkout used for this handoff was never touched by any
mutant. Three mutants, each targeting one of the specific traps named in this run's own
task brief, applied and reverted one at a time; baseline (unmutated) run in the worktree
first confirmed **30 passed** (`attachments_test.exs` + `signature_heuristic_test.exs`).

### Mutant A — infected branch does not short-circuit (persists anyway)

**Change (`lib/letflow/repository/attachments.ex`, `upload/2`'s `case
run_attachment_scan(...)`):** the `{:ok, :infected, verdict}` clause additionally calls
`do_upload_after_scan/6` (the same persistence path the `:clean` branch uses) before
returning `{:error, :infected, verdict}` — i.e., the function still reports rejection to
its caller while silently persisting the infected content anyway with
`scan_status: :clean`.

**Result: 28/30 passed.** Exactly the two tests targeting this trap failed:
- `"upload/2 returns {:error, :infected, verdict} and creates neither an
  instance_attachments nor a repository_artifacts row"` — failed because both
  `Repo.aggregate` counts were now `1`, not `0`.
- `"an EICAR upload rejection is audit-logged with tenant/actor/hash metadata but never
  the raw bytes"` — failed on the `refute log =~ "EICAR-STANDARD-ANTIVIRUS-TEST-FILE"`
  assertion: with `metadata: :all` capturing debug-level Ecto query logs too, the
  mutant's own `INSERT INTO ... repository_artifacts` query log line contained the raw
  EICAR bytes verbatim, which the test correctly flagged as a leak.

Both failures are the exact, specific consequence of this mutant — no other test in
either file was affected.

**Reverted:** `git checkout -- lib/letflow/repository/attachments.ex` in the worktree;
`git status --porcelain lib/ test/` empty; re-ran the same two files: **30 passed.**

### Mutant B — the rescue clause returns a false-clean instead of an error

**Change (`run_attachment_scan/2`'s `rescue` clause):**
```elixir
rescue
  _exception -> {:ok, :clean}
```
(was `{:error, Exception.message(exception)}`).

**Result: 29/30 passed.** Exactly one test failed:
- `"an adapter that raises returns {:error, :scan_unavailable}, not a false {:ok,
  :clean}, and nothing is persisted"` — `upload/2` returned `{:ok, %Attachment{}}`
  instead of `{:error, :scan_unavailable}`, since the mutated rescue clause made a
  raising adapter look identical to a genuinely clean scan.

No other test in either file was affected.

**Reverted:** `git checkout -- lib/letflow/repository/attachments.ex`; `git status
--porcelain lib/ test/` empty; re-ran: **30 passed.**

### Mutant C — the `scan_status != :clean` gate in `get_content/2` is removed

**Change (`check_scan_status_clean/1`):**
```elixir
defp check_scan_status_clean(%Attachment{}), do: :ok
```
(collapsed both clauses — the `:clean`-only guard and the `{:error, :not_available}`
fallback — into one clause that always succeeds).

**Result: 28/30 passed** (plus an unrelated-but-informative compiler warning at the
route layer, `lib/letflow/routers/instances.ex:1176`, noting its own
`{:error, :not_available}` clause "will never match" once this gate can no longer
produce it — independent confirmation the mutant genuinely removed the guard, not just
that this test file's own assertions happened to fail). Exactly the two tests targeting
this trap failed:
- `"a :pending row (pre-existing/backfilled shape) is rejected with {:error,
  :not_available}"`.
- `"an :infected row (not reachable via upload/2, simulated directly) is rejected with
  {:error, :not_available}"`.

No other test in either file was affected.

**Reverted:** `git checkout -- lib/letflow/repository/attachments.ex`; `git status
--porcelain lib/ test/` empty; re-ran: **30 passed.**

### Worktree cleanup

`git worktree remove ../letflow-2-mutwt --force` after the third revert-and-verify.
