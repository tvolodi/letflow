# Test Spec: ISS-0408 — hop-chain-local join token needs a real `TokenRecord` before task-activation/reconciliation

**Issue:** `docs/issues/ISS-0408.yaml` (GH#800), severity MAJOR, tags engine/parallel-gateway/token-record/task-activation
**Design:** `lib/letflow/design/iss0408-join-token-record-insert-fix.md`
**Test tier:** unit+integration (real Postgres, `Letflow.DataCase`, DIRECTIVE T-1)
**Test file:** `test/letflow/iss0408_join_token_record_test.exs` (new file)

## Bug summary

`Letflow.Engine.Transition.fire_join/5` mints a synthetic, non-UUID `token_id`
(`counter.origin_token_id <> "/" <> node.id <> "/joined"`) for the token produced when a
`PARALLEL_GATEWAY` join fires. Before this fix, any hop chain where that join's own
outgoing edge led to a further dispatch-needing node (e.g. another `:HUMAN_TASK`, not
straight to `:END`) reached `Letflow.Engine.TaskActivation.append_multi_from_existing_records/6`'s
`cast_token_record_id/1`, which rejects any non-UUID `token_id` via `Ecto.UUID.cast/1` —
`{:error, {:invalid_token_record_id, token_id}}` — because no `TokenRecord` row existed
yet for the freshly-joined token. `join -> :END` was unaffected (ISS-0396's own fix/test),
because a token consumed directly by `:END` is simply dropped and nothing looks up a
`TokenRecord` for it.

The fix (commits `542f2974`..`74aba472` on branch `feature/WF03-ISS0408-20260902`) adds a
new `Letflow.Engine.insert_hop_chain_new_token_records/5` step that inserts a real
`TokenRecord` row for any token new *within the current hop chain* (present in
`final_instance_state.tokens`, absent from `original_active_tokens`) — and rewrites
`final_instance_state`'s token ids to the real, just-inserted ids — before task-activation
and reconciliation run. This runs at **both** call sites that build a task-activation/
reconciliation `Multi` from a pre-existing set of `TokenRecord`s:

1. `Letflow.Engine.build_task_activation_and_reconciliation_multi/4`, reached via
   `complete_task/3`'s own hop-chain tail (`build_complete_task_tail_multi/6`).
2. `Letflow.Engine.persist_timer_fired_advance/6`, reached via
   `advance_after_timer_fired/3` (`Letflow.Scheduler.fire_timer/2` /
   `Letflow.Scheduler.poll_and_fire/1`).

## Why this needs a fail-then-pass regression test, not just new coverage

This is a WF-03 fix to **existing, already-shipped** behavior (`fire_join/5`,
`cast_token_record_id/1`, `do_reconcile_token_records/5` all predate this fix and are
unchanged by it — see design doc §4's "Explicitly UNCHANGED" list). The pre-fix failure is
a real, reproducible error against real code that already existed, not
`UndefinedFunctionError` for a module that didn't exist yet — so the standard WF-03
fail-then-pass proof applies directly (`docs/agents/workflows/WF-03_issue_resolving.md`,
Steps 2-4) and the mutation-testing alternative for "code under test does not exist" does
**not** apply here.

## Test cases

1. **`complete_task/3` call site — the main scenario.**
   `graph_join_then_human_task/0` builds `START -> PARALLEL_GATEWAY(split) ->
   HUMAN_TASK(task_a) / HUMAN_TASK(task_b) -> PARALLEL_GATEWAY(join) ->
   HUMAN_TASK(after_join) -> END` — the distinguishing feature vs. the already-passing
   `engine_test.exs:graph_start_parallel_split_join_end` fixture is that the join's own
   outgoing edge leads to another `:HUMAN_TASK`, not directly to `:END`. `Engine.create/2`
   reaches `task_a`/`task_b` both pending. Completing `task_a` alone leaves the join
   waiting (`join_outcome/1` `:wait`) — this always succeeded, pre-fix and post-fix.
   Completing `task_b` is the hop chain that fires the join and immediately continues to
   the newly-pending `HUMAN_TASK(after_join)` — this is the exact call `fire_join/5`'s
   synthetic id previously broke.
   See `test/letflow/iss0408_join_token_record_test.exs`, describe
   `"join -> HUMAN_TASK via complete_task/3 (the main scenario)"`. Asserts:
   - The second `complete_task/3` call returns `{:ok, result}` with
     `result.instance_status == :active` and `result.current_nodes == ["after_join"]`.
   - Exactly one new `tokens` row exists for the join-merged token: a real, UUID-castable
     `id`, `node_id == "after_join"`, `branch_id == nil` (join-merged, per `fire_join/5`),
     `status == :active`.
   - Exactly one new `tasks` row exists for `HUMAN_TASK(after_join)`, `status == :pending`,
     whose `token_id` FK resolves to that same newly-inserted `tokens` row.
   - Both original branch `TokenRecord`s (`task_a`'s, `task_b`'s) are reconciled to
     `status == :completed` by the pre-existing, unchanged `do_reconcile_token_records/5`
     — confirms the fix didn't disturb existing reconciliation behavior.

2. **`persist_timer_fired_advance/6` call site — the TIMER path.**
   `graph_join_then_human_task_via_timer/1` builds the same "join leads to a further
   HUMAN_TASK" shape, but branch `b` is a `:TIMER` node (per
   `test/letflow/engine/timer_wiring_test.exs`'s own
   `graph_parallel_split_task_and_timer/1` precedent, itself the ISS-0397 timer-fire
   parity fixture) rather than a second `HUMAN_TASK`, so the join-closing branch
   completion arrives via `Letflow.Scheduler.poll_and_fire/1` ->
   `advance_after_timer_fired/3` -> `persist_timer_fired_advance/6`, not `complete_task/3`
   — this is the design's §3.5 call site, the second of the two the issue names as equally
   affected. `task_a` completes normally first (join still waiting); the timer then fires.
   See `test/letflow/iss0408_join_token_record_test.exs`, describe
   `"join -> HUMAN_TASK via a TIMER-fired closing branch (persist_timer_fired_advance/6)"`.
   Asserts:
   - `Scheduler.poll_and_fire/1` returns `%{fired: 1, ...}` (not `errored: 1` — see the
     pre-fix run below for what a failure here actually looks like).
   - The same three assertions as case 1 (join-merged `tokens` row shape, the new
     `HUMAN_TASK(after_join)` `tasks` row and its FK, `instance_projections.status ==
     :active`), confirming the fix behaves identically at both call sites.

Both `describe` blocks together satisfy the design task's explicit requirement that
"both call sites need the fix" have their own coverage (§6 point 7 of the design doc) —
neither is skipped, and constructing the TIMER-path fixture was straightforward by
directly reusing `timer_wiring_test.exs`'s own established
`graph_parallel_split_task_and_timer/1` pattern, so there is no coverage gap to report for
this requirement.

Pre-fix commit identified: `751d5806` — the merge-base of
`feature/WF03-ISS0408-20260902` against `main`, immediately preceding this branch's own
design/fix commits (`7ef45d33`, `542f2974`, `74aba472`).

**only** this new test file copied on top (confirmed via `git status --porcelain` showing
exactly one untracked file, nothing else). Removed via `git worktree remove --force` after
use; the main working checkout's `git status --porcelain` was confirmed to show only the
new test file before and after, at no point touched by the pre-fix run.

**Pre-fix run** (`mix test test/letflow/iss0408_join_token_record_test.exs` in the
worktree, `MIX_DEPS_PATH`/`MIX_BUILD_PATH` pointed at the main checkout's already-fetched
deps/build to avoid a redundant `mix deps.get`): **0/2 passed, 2 failed.**

Case 1 (`complete_task/3`) failed with the predicted error, exact reason tuple:

```
match (=) failed
code:  assert {:ok, after_b} = result
left:  {:ok, after_b}
right: {:error,
        {:invalid_token_record_id,
         "f1fe156c-e752-4177-973e-4e093154d2fa/join/joined"}}
```

Case 2 (TIMER path) failed via `Scheduler.poll_and_fire/1`'s own by-design
never-raise/never-propagate contract (`lib/letflow/scheduler.ex`'s `poll_and_fire/1` "Never
raises — every per-timer failure is caught internally and folded into the returned counts"
— `attempt_fire/2`'s `rescue`, and `record_fire_failure/2`'s own catch), so the visible
test failure is the aggregate count, not the raw tuple:

```
code:  assert %{fired: 1} = Scheduler.poll_and_fire(schema_name)
left:  %{fired: 1}
right: %{errored: 1, fired: 0, claimed: 1, exhausted: 0, tenant_schema: "tenant_a7f0261f090840f2be67aa66538c4b27"}
```

To confirm this `errored: 1` is the *same* root cause and not a different pre-existing
TIMER-path defect, a scratch probe (not committed, removed after use) called
`Letflow.Scheduler.fire_timer/2` directly (bypassing `poll_and_fire/1`'s own
error-swallowing) against the identical pre-fix worktree/fixture and confirmed the raw,
underlying error:

```
RAW fire_timer/2 result: {:error,
 {:invalid_token_record_id, "12f9232c-6abd-40c5-bb6a-23bc3cfed0f8/join/joined"}}
```

Confirming both call sites fail via the identical `{:invalid_token_record_id, _}` guard
pre-fix, exactly as ISSUE-FIXER's diagnosis and the design doc's §6 point 5 predicted.

**Post-fix run** (same test file, current branch `feature/WF03-ISS0408-20260902` at
`74aba472`): **2 passed, 0 failed.**
