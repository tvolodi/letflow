# Test Spec: ISS-0421 (narrowed) — bounded per-tenant concurrency in `Letflow.Scheduler.Poller`

**Issue:** ISS-0421, narrowed to concern 1 only (concerns 2/3 already resolved by
REQ-219/ISS-0451 — see `handoffs/WF03-ISS0421-20260904/step-01-issue-fixer-diagnosis.json`).
Each of `Letflow.Scheduler.Poller`'s seven per-tick sweeps now iterates its
tenant schemas via `Task.async_stream/3` (bounded concurrency) instead of
`Enum.each/2` (fully serial). See
`lib/letflow/design/iss0421-poller-bounded-concurrency.md` for the full design.

**Test tier:** unit — `test/letflow/admission_test.exs` (new `Letflow.Admission`
accessor) and `test/letflow/scheduler/poller_test.exs` (Poller-level behavior),
both existing files, same conventions as their surrounding REQ-216/REQ-218 tests.

**Written by:** TEST-DESIGNER (WF-03 step-05), after REVIEWER's PASS
(`handoffs/WF03-ISS0421-20260904/step-04d-reviewer-recheck.json`) carried
forward 2 required coverage gaps and this step's own independent AC-to-test
traceability pass found 2 more (the fault-isolation and single-query
invariants had no dedicated automated test at all — only informally reasoned
about in the design doc and manually spot-checked by REVIEWER/ELIXIR-DEV).

## Coverage carried forward from REVIEWER (both closed this run)

1. **`global_cap/1` non-default-value regression** — REVIEWER's step-04d
   flagged that no test proved `Admission.global_cap/1` reads LIVE
   per-instance state rather than a hardcoded/cached default. Closed by
   `test/letflow/admission_test.exs`, `describe "ISS-0421: global_cap/1 reads
   this instance's own live global_cap, not a default"`, 3 tests:
   - `pool_size: 3, reserved_headroom: 2` (the exact non-default config
     REQ-218's own poller tests use) → `global_cap/1` returns `1`, not the
     default-config `8`.
   - A second, different non-default pair (`pool_size: 12,
     reserved_headroom: 2` → `10`) — proves the accessor isn't a second
     hardcoded constant that happens to match one particular config — PLUS
     a cross-check that this is the SAME number `try_acquire(:global)`'s own
     independently-implemented admission count enforces (10 real admissions
     succeed, the 11th is rejected).
   - The documented default-config case (`pool_size: 10, reserved_headroom:
     2` → `8`) for completeness/regression against the design doc's own
     worked example.

   **Mutation-verified** (this step, foreground): changed
   `handle_call(:global_cap, _from, state)` to reply a hardcoded `8`
   regardless of `state.global_cap`. Re-ran `mix test
   test/letflow/admission_test.exs`: 2 of the 3 new tests failed (the
   default-config test still incidentally passed, since `8` happens to be
   the mutated hardcoded value too — expected and not a gap, since that
   specific case cannot distinguish live-read from a same-valued hardcode by
   construction). Reverted (`diff` against pre-mutation file: empty),
   re-ran: 18/18 passed in that file.

2. **Hardcoded-literal-regression for the 6 gated sweeps** — REVIEWER and
   ELIXIR-DEV had both manually confirmed (sed-substituting the old
   `@admission_gated_max_concurrency 8` literal back into `poller.ex` and
   re-running REQ-218's AC1/AC2/AC3(per-schema)/AC5 tests, which failed) that
   the test suite genuinely catches a regression to a hardcoded bound — but
   only as a one-off manual exercise, not a permanent, explicitly-labeled
   test. Closed by `test/letflow/scheduler/poller_test.exs`, `describe
   "ISS-0421 regression: the 6 gated sweeps' max_concurrency derives live
   from Admission.global_cap/0, not a hardcoded literal"`, 1 test: with
   `global_cap` forced to `1` (`pool_size: 3, reserved_headroom: 2`), 5
   schemas' due timers (more than REQ-218 AC2's own 3, for a wider,
   less-marginal margin against the old hardcoded `8`) all fire within a
   single tick. Deterministic in both directions (not merely
   probabilistically likely to catch a regression): with the live accessor,
   `max_concurrency == 1` means Poller never holds more than one admission
   unit at a time (no self-contention), so every attempt is uncontested and
   succeeds; with a hardcoded `8` (or any value `> 1`) and 5 schemas racing
   the SAME sole `global_cap == 1` unit at once, `Admission` grants exactly
   one and permanently rejects the rest (no retry), so strictly fewer than 5
   would fire.

   **Mutation-verified** (this step, foreground): globally replaced
   `Admission.global_cap()` with the literal `8` at all 6 call sites in
   `poller.ex` (the exact mutation REVIEWER/ELIXIR-DEV each performed by
   hand). Re-ran `mix test test/letflow/scheduler/poller_test.exs`: `Result:
   15/19 passed`, 4 failed — this new test PLUS the same 3 REQ-218 tests
   (AC1, AC2, AC5) REVIEWER's own manual pass already named (this run's
   antagonist-based AC3 test did not happen to fail on this particular run,
   consistent with its own documented nondeterminism/retry design — it is
   not the test this regression targets). Reverted (`diff` against
   pre-mutation file: empty), re-ran: 19/19 passed.

## Gaps found by this step's own independent AC-to-test traceability pass

This step re-read ISS-0421's remaining-in-scope acceptance properties
directly from the design doc (§4 "AC1: fault isolation", §3 "AC3: peak
DBConnection checkouts stated/justified", §5 "AC4: single query per tick
preserved" — using the numbering the routing handoff uses) rather than
assuming REVIEWER's 2 carried-forward items were the only gaps. Two more were
found:

3. **AC1 (fault isolation) — no test exercised the actual NEW mechanism.**
   Every existing fault-isolation-shaped test in `poller_test.exs`
   (REQ-218 AC5, ISS-0444's three describes) exercises either an existing
   PRE-ISS-0421 inline `rescue` (the four `maybe_run_ordering_*`/similar
   sweeps) or `Scheduler.poll_and_fire/1`'s/`run_retention_sweep/1`'s own
   internal `Postgrex.Error{code: :undefined_table | :undefined_schema}`
   rescue (ISS-0444, `lib/letflow/scheduler.ex`) — NOT the NEW top-level
   `try/rescue` this fix's design §4b adds at the `poll_and_fire`/
   `retention_sweep` `Task.async_stream/3` call sites specifically for the
   two operations that had no rescue of their own before this fix. Nothing
   in the existing suite forces a raise that reaches THAT new rescue.
   Closed by `describe "ISS-0421 AC1: new top-level per-task rescue"`, 1
   test: drops the `fire_at` column from one schema's `timers` table,
   producing a Postgrex `:undefined_column` error — a code NOT in
   `poll_and_fire/1`'s own rescue's matched list (only `:undefined_table`/
   `:undefined_schema`), so it re-raises out of `claim_due_timer_ids/2` and
   reaches poller.ex's new rescue for the first time in this codebase's test
   suite. Asserts: the tick does not crash, a different (healthy) schema's
   own `poll_and_fire` still completes in the same tick (blast radius is
   exactly one task, not the whole `Task.async_stream` batch), and the log
   line is the NEW rescue's own (`"poller sweep task raised"`, from
   `log_task_raise/4`), not the pre-existing Scheduler-level
   `"tenant schema unavailable"` line — proving this was caught by the new
   mechanism, not incidentally by the old one.

   **Mutation-verified** (this step, foreground): removed the `try/rescue`
   wrapper around the `poll_and_fire` call site, leaving `with_admission/3`
   called directly (exactly what the code looked like before this fix, for
   that one call site). Re-ran `mix test test/letflow/scheduler/poller_test.exs`:
   `Result: 18/19 passed`, exactly 1 failure — this new AC1 test, and no
   other. Reverted (`diff` against pre-mutation file: empty), re-ran: 19/19
   passed.

4. **AC4 (single query per tick preserved) — unchanged property, but never
   itself encoded as an automated invariant.** The design doc (§5) asserts
   `fetch_tenant_schemas/0` is still called exactly once per
   `handle_info(:tick, state)`, unchanged by this fix — true by inspection,
   but "true by inspection" is exactly the kind of claim REQ-218's own AC4
   test (source-text grep for `{:tenant,`) already established this
   codebase's convention of converting into an executable check rather than
   leaving as a one-off reading. Closed by `describe "ISS-0421 AC4:
   tenant_schemas/0 is still queried exactly once per tick"`, 1 test: reads
   `poller.ex`'s own source text, isolates `handle_info(:tick, state)`'s
   body, and asserts the substring `fetch_tenant_schemas()` occurs exactly
   once inside it — mirroring the existing "no second ticker"
   (`use GenServer` grep) and REQ-218 AC4 (`{:tenant,` grep) tests' own
   established idiom for encoding a structural/textual invariant as a real,
   automated assertion rather than an informally-quoted grep in a handoff.

## AC3 (peak DBConnection checkouts stated/justified) — traceability, no new test needed

AC3 is fundamentally the arithmetic identity design §3a/§3b/§3c states
(`global_cap = pool_size - reserved_headroom`, `max_concurrency == live
global_cap` for the 6 gated sweeps, `max_concurrency == live
reserved_headroom` for the one unwrapped sweep, `global_cap +
reserved_headroom == pool_size`), not a separately-observable runtime
behavior distinct from what items 1–2 above already exercise:

- `Admission.global_cap/1`'s new tests (item 1) directly verify the
  `pool_size - reserved_headroom` derivation at multiple non-default
  configs, including the exact numbers §3a/§3c's worked example cites.
- The existing `AdmissionTest` `describe "AC1: global cap = pool_size -
  reserved_headroom"` block (pre-existing, untouched by this run) already
  proves `try_acquire(:global)` itself enforces exactly that derived number
  as the real admission ceiling — the fact AC3's whole argument depends on.
- Item 2's mutation-verified regression test is the one that ties
  `max_concurrency` itself to that same live number for the 6 gated sweeps —
  the missing link a hardcoded literal would have broken.
- `Letflow.Admission.reserved_headroom/1`'s own existing REQ-218-era test
  coverage (unchanged by this run) covers the unwrapped
  `maybe_refresh_active_instances/1` sweep's half of the same identity.

No additional runtime test would exercise anything these don't already
cover — AC3's "stated and justified" bar is an arithmetic argument over
values these tests already pin down, not an independent behavior.
