## 0. Why the standard fail-first shape does not transfer, and what replaces it here

WF-03 Step 4 normally requires a test shown to fail against pre-fix code and pass
post-fix. ISS-0426's defect is a genuine flake: ISSUE-FIXER's Step 1 diagnosis could not
reproduce the filed failure even under 24 concentrated OS-level CPU burners plus 48 runs
of the affected test (`handoffs/WF03-ISS0426-20260902/step-01-issue-fixer-diagnosis.json`).
A "test that fails pre-fix" for this defect would therefore itself be a test that fails
only probabilistically, on some hosts, sometimes — writing one and citing it as
fail-first evidence would be exactly the speculation `core-directives.md` forbids ("No
speculation... run it and quote the actual result").

The design's own §4 states the fix's correctness is **structurally**, not
**statistically**, verifiable: after the fix, the wall-clock-race branch is unreachable
from the 14 repointed call sites by construction (no `Task.yield` call exists in
`run_script_sync/3`'s chain at all; no `after` clause exists in
`run_with_heap_limit_sync/4`'s `receive` block at all). This spec's coverage locks in
that structural claim via three properties (below), and satisfies WF-03's fail-first
requirement the way its own "When the pre-fix failure is 'the code under test does not
exist'" section prescribes for a fix that ships brand-new functions: since
`run_script_sync/3` and `run_with_heap_limit_sync/4` did not exist pre-fix, any test
calling them fails pre-fix with `UndefinedFunctionError` — which proves the functions
are new and nothing about whether these tests discriminate a *correct* seam from a
*wrong* one. That requirement is therefore satisfied by **mutation** (§3 below), not by
a pre-fix run of this file.

## 1. The three properties, and why each exists

### Property (a) — seam equivalence (highest-value coverage)

**Claim:** `run_script_sync/3` and `run_with_heap_limit_sync/4` return the *same
outcome* as their racing counterpart (`execute_with_manifest/3`, called with a timeout
generous enough not to plausibly fire) for the same workload, across every outcome
shape the 14 repointed Group-1 call sites use: `:ok`, `budget_exceeded`,
`script_error`, `memory_limit_exceeded`.

**Why it exists:** 14 call sites across 11 tests were repointed from
`execute_with_manifest/3` onto the two new seams. A seam that structurally cannot
produce `{:error, {:wallclock_timeout, _}}` but *also* silently changed what it returns
for a normal outcome (wrapped an error differently, dropped a field, swallowed an
exception into the wrong shape) would let all 11 repointed tests keep passing for the
wrong reason — the repointed tests only ever assert their own single expected outcome
against a matching `assert`, so none of them individually proves the seam's return
shape is faithful to the original code path it replaced. This property is the one this
spec adds that no pre-existing test (repointed or not) actually checks.

**Test cases** (`describe "ISS-0426: seam equivalence (property a)"`):

1. `"run_script_sync/3 returns the same :ok shape as execute_with_manifest/3 for a
   natural-completion workload"` — `return 1 + 1` through both paths; asserts both
   return `{:ok, %{manifest_hash: _}}` with the **same** hash value (proves
   `run_script_sync/3` doesn't just happen to return `:ok`, it computes the identical
   `Manifest.compute_hash/2` result the racing path does).
2. `"run_script_sync/3 returns the same budget_exceeded shape as execute_with_manifest/3"`
   — `while true do end` under a 500-instruction budget through both paths; asserts
   `sync_result == racing_result` (full structural equality — both fields, budget
   value included).
3. `"run_script_sync/3 returns the same script_error shape as execute_with_manifest/3"`
   — REQ-162 AC7's own filed-failure workload (the `local function f() ... 1 // 0 ...
   end` shape that produced ISS-0426's original filed failure) through both paths;
   asserts `message`, `stack_trace`, and `capabilities` match field-by-field (not a
   blind `==`, since `instruction_count`'s `{:consumed, count}` arm can legitimately
   differ by a handful of VM instructions between two independent sandbox evaluations
   of the same script — the design does not claim instruction-for-instruction
   determinism, only that the error *shape* and message/stack_trace content match).
   An earlier draft of this test also asserted
   `refute match?({:error, {:wallclock_timeout, _}}, sync_result)` here; running it
   confirmed it reproduces the exact same "clause will never match" type-checker note
   REVIEWER's step-03c ruling addressed at line 466 (same root cause: `run_script_sync/3`'s
   `@spec` categorically excludes that shape). REVIEWER's ruling says to preserve the
   *existing* line-466 instance as a standing proof, but explicitly "do NOT add more
   assertions of that shape elsewhere" — this would have been exactly that, and it was
   also strictly redundant with the `assert {:error, {:script_error, sync_error}} =
   sync_result` line immediately above it (a positive pattern match into the
   `script_error` shape is a strictly stronger, more informative check than a negative
   match against one specific other shape). Removed before this spec's final measurement
   for both reasons — see §4.
4. `"run_with_heap_limit_sync/4 returns the same memory_limit_exceeded shape as
   execute_with_manifest/3's heap-limited path"` — REQ-156 AC-2's own gigabyte-allocating
   workload under a 16 MB limit through both the new seam and `execute_with_manifest/3`'s
   `max_heap_words:`-configured path (which itself still routes through the
   *unmodified* `run_with_heap_limit/5`); asserts `sync_result == racing_result`.

### Property (b) — the memory limit still binds through the new heap-limited seam

**Claim:** `run_with_heap_limit_sync/4` still enforces `max_heap_size: kill: true` — a
smaller configured `max_heap_words` still halts an allocating script
(`:memory_limit_exceeded`) while a materially larger one on the same script still lets
it complete (`:ok`).

**Why it exists:** the task description names this explicitly — REQ-156/LUA-09's bound
must be *shown* intact through the new path, not assumed carried over from
`run_with_heap_limit/5` because the two functions look similar. `run_with_heap_limit_sync/4`
removes the `after` clause entirely (that is the whole point of the seam), and it would
be possible to make that change while *also* accidentally dropping or weakening the
`max_heap_size` spawn_opt — a regression this property is specifically positioned to
catch, since REQ-156's own pre-existing AC-1/AC-2 tests (now repointed onto this same
seam) would no longer independently confirm it if the seam itself were broken in a way
that happened to still satisfy their exact literal assertions by accident (it wouldn't,
in practice, but this property makes the "the limit is load-bearing, not a no-op"
argument directly, with its own two-value comparison, rather than relying on the
repointed tests to make it implicitly).

**Test case** (`describe "ISS-0426: memory limit still binds through the unbounded-wait
seam (property b)"`):

1. `"a smaller configured max_heap_words still halts an allocating script; a larger one
   still lets it complete"` — the same `@moderate_allocating_script`-shaped workload
   REQ-156 AC-1 uses, run twice through `run_with_heap_limit_sync/4`: once under a
   ~1 MB limit (asserts `{:error, :memory_limit_exceeded}`), once under a ~200 MB limit
   on the identical script (asserts `{:ok, %{manifest_hash: _}}`). The two-outcome
   contrast is what proves the limit is load-bearing, mirroring REQ-156 AC-1's own
   established "two different configured limits, two different outcomes" pattern.

### Property (c) — the `:lua_wallclock_race` tag partition is wired correctly and still genuinely races

**Claim:** exactly the 11 tests design §2.2/§2.4 names carry `@tag :lua_wallclock_race`
(no more, no fewer); `test/test_helper.exs` actually excludes that tag by default; and
the isolated `--only lua_wallclock_race` partition still runs and passes exactly those
11 tests, i.e. they remain live, genuine assertions of timeout behavior rather than
silently-never-running dead code.

**Why it exists:** the task description names the worst failure mode of a tagging fix
explicitly — tests excluded everywhere, therefore never running (and never failing)
again. SECURITY-REVIEWER and REVIEWER both independently confirmed the current state
(11 passed / 37 excluded isolated, at the time they gated), but that is a snapshot, not
a standing guard — nothing before this spec would catch a future edit that silently
drops the tag from one of the 11, tags an unrelated 12th test, or removes the tag from
`test/test_helper.exs`'s `exclude:` list. Property (c) turns that snapshot into three
structural/mechanism-level regression guards.

**Test cases** (`describe "ISS-0426: :lua_wallclock_race tag-partition integrity
(property c)"`):

1. `"exactly 11 tests in this file carry @tag :lua_wallclock_race"` — parses this test
   file's own source with `Code.string_to_quoted/1` and walks the AST via
   `Macro.prewalk/3`, counting actual `@tag :lua_wallclock_race` attribute nodes —
   deliberately **not** a raw substring/line count, because this describe block's own
   comments and the test's own failure message legitimately mention the string
   `"@tag :lua_wallclock_race"` in prose (confirmed empirically during this test's own
   design: a naive `grep -c "@tag :lua_wallclock_race"` over the finished file returns
   15, not 11, because it also matches those four prose occurrences — the AST walk
   correctly returns 11). This is the same idiom
   `test/support/tenant_slug_test.exs`'s ISS-0065 regression test already established
   in this codebase for exactly this reason (parsing the file's own AST to avoid a
   text scan self-defeating against its own prose).
2. `"test/test_helper.exs's ExUnit.start/1 excludes :lua_wallclock_race"` — reads the
   real `test/test_helper.exs` file (not a copy, not a hardcoded assumption of its
   content) and AST-walks it for an `ExUnit.start/1` call whose `:exclude` keyword
   option list contains `:lua_wallclock_race`.
3. `"the isolated --only lua_wallclock_race partition runs and passes exactly 11
   tests"` — actually shells out to `mix test --only lua_wallclock_race
   test/letflow/engine/lua/executor_test.exs` as a real subprocess (the identical
   invocation `mix letflow.check.test`'s own `run_lua_wallclock_race_tests/0` uses) and
   asserts both a `0` exit code and that the captured output contains `"Result: 11
   passed"`. This is the one test in this new coverage that is itself a live
   `mix test` invocation rather than a pure in-process assertion — deliberately, since
   it is the only way to prove the 11 tests are still actually being *executed and
   passing* in their isolated partition, not merely tagged.

- [x] Property (a) — seam equivalence — 4 test cases, one per outcome shape Group 1

- [x] Property (b) — memory limit still binds through the new path — 1 test case,
      two-value load-bearing contrast (not a single-value assertion that could pass
      by coincidence).
- [x] Property (c) — tag-partition wiring integrity — 3 test cases: tag count (static),
      exclude-list wiring (static), isolated-partition liveness (dynamic/live
      subprocess run).
- [x] No test in this new coverage depends on wall-clock time or unseeded randomness
      (`docs/guides/test_developer_guide.md` DIRECTIVE T-... / principle 3) — property
      (a)/(b)'s comparisons use generous, non-racing timeouts on the racing side
      specifically so neither arm of the comparison itself flakes under load; property
      (c)'s subprocess test asserts exact counts, not timing.

      of them asserts on which of two racing wall-clock outcomes wins; tagging them
      would incorrectly exclude structural coverage from the default run for no reason.

## 3. Fail-first via mutation (WF-03 "code under test does not exist" case)

Both `run_script_sync/3` and `run_with_heap_limit_sync/4` are new functions added by
this fix — no pre-fix run of this file's new tests is possible (`UndefinedFunctionError`
for every call site), so per WF-03's own governing section, fail-first is satisfied by
mutating the shipped logic and recording which of the new tests fail per mutant. All
four mutants below were applied in a **throwaway `git worktree`**
(`git worktree add <scratchpad>/mutant-wt HEAD`, with its own independently-fetched
`deps`/`_build` — not shared with the main working tree or its `_build`, to avoid any
risk of corrupting a concurrent build) — the real working tree in this run's actual
checkout was **never mutated**. The worktree's copy of
`test/letflow/engine/lua/executor_test.exs` was updated to this run's finished new-test
content before any mutant was applied, so every mutant is measured against the exact
tests reported in this spec, not an earlier draft.

**Note on mutant 3's evolution, recorded rather than silently discarded (documentation
honesty — mirrors this project's own "record a required correction rather than leaving
it for someone else to notice" norm cited in the design doc's §1.2(c)):** the first form
of mutant 3 used `Task.yield(1)` (a literal, still-racing 1ms wait, closer to the task
description's own literal suggestion of "restore an `after` clause... with a tiny
timeout"). Applied to the full file, it deterministically caught the file's 3
pre-existing REQ-154 tests every time (3 separate `--seed` runs, identical 3-failure
result each time), but this spec's own new property-(a) tests 1-3 passed inconsistently
under it (failed when run in isolation via `--trace` on specific line numbers, passed
inside the full-file `async: true` run) — because those three tests' own workloads
(`return 1 + 1`, a 500-instruction budget loop, one `1 // 0` script_error script) are
fast enough that whether they complete inside a literal 1ms wait genuinely depends on
scheduler contention from the other ~55 concurrently-scheduled `async: true` tests in
the same run, i.e. the exact non-determinism this whole issue is about. Using a
non-deterministic mutant to demonstrate deterministic test coverage would have been a
methodological error, not a smaller version of a correct one, so the mutant was
rewritten to force `handle_yield_result(nil, task, 1)` unconditionally — removing the
race from the *mutant itself* rather than papering over it with more repeated runs —
and re-measured, landing on the 12-test, fully reproducible result in the table above
(re-confirmed 3 times, identical 12/33 result each time). This mirrors this project's
own established caution about wall-clock-dependent test infrastructure — the same
lesson ISS-0426 itself exists to teach, applied here one level up, to the mutant used to
test the fix rather than to the fix's own tests.

**Mutants are temporary probes.** All four were applied and measured inside the
throwaway worktree only. Each was reverted with `git checkout -- <path>` inside that
worktree before the next mutant was applied, and the worktree itself was removed
(`git worktree remove --force <path>`) once mutation testing finished. The revert of
each mutant was verified in place (worktree `git status --porcelain lib/ test/` empty
except the intentional test-file addition, and `mix test
test/letflow/engine/lua/executor_test.exs` re-run to the clean 45 passed / 11 excluded
baseline) before the next mutant was applied — see this handoff's `result.summary` for
the final, real-repo-scoped revert verification (`git status --porcelain lib/ test/`
against the actual run branch, which was never mutated at all).

## 4. Standing ruling carried forward, not re-decided

REVIEWER's step-03c gate ruled that `executor_test.exs:466`'s
`refute match?({:error, {:wallclock_timeout, _}}, result)` — inside the pre-existing
`"AC-4 regression guard: budget_exceeded is unaffected by a generous timeout and stays
distinct"` test — stays as-is: the "clause will never match" type-checker note it
produces is a non-fatal, CI-invisible (test-file-only) standing proof that
`run_script_sync/3`'s categorical unreachability guarantee (design §2.1.1b) continues to
hold, and would silently disappear if a future change broke that guarantee. This spec
does not touch that assertion. As noted in §1's property-(a)-test-3 description, an
earlier draft of that test added a second `refute match?({:error, {:wallclock_timeout,
_}}, ...)` of the same shape; it was removed once running the file showed it reproduces
the identical "clause will never match" warning, which is exactly what the ruling's "do
NOT add more assertions of that shape elsewhere" instruction forbids. This spec's
finished test file carries only the one, pre-existing, REVIEWER-blessed instance at
line 466 — unchanged and unduplicated.
