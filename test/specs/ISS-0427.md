# Test Spec: ISS-0427 — wire `assert_clone_parity!/2` to its two promised use sites

**Issue:** ISS-0427 — tenant test-schema provisioning clones from a prepared template
instead of replaying migrations. Design:
`lib/letflow/design/iss0427-tenant-test-schema-template-clone.md`. This step (TEST-DESIGNER,
WF-03 Step 4) responds to REVIEWER's Step 3c gate MAJOR finding
(`handoffs/WF03-ISS0427-20260904/step-03c-reviewer.json`): `assert_clone_parity!/2` — the
13-dimension structural parity check the entire safety argument for cloning rests on — was
called from **zero places** in shipped code, despite design §3.4 promising two runnable use
sites and design §11's acceptance table claiming both were wired.

**Test tier:** integration (real Postgres, real clone/template mechanism) plus one dispatch
regression test. No formal `docs/requirements.yaml` acceptance criteria list exists for a
WF-03 issue fix — the implicit requirements below are restated from the issue's own text and
REVIEWER's gate.

---

## What was wired (production/test-support code, not application `lib/`)

1. **Use site 1 (build-time self-check)** — `test/support/tenant_template.ex`'s
   `template_self_check!/0` now calls a new private function,
   `assert_template_parity_against_independent_reference!/0`, which builds a SECOND schema
   (`"tenant_template_refcheck"`) via the real, unmodified `TenantProvisioning.replay_migrations/2`
   against a throwaway `Tenant`/`Registration` row (reusing the exact `insert_throwaway_tenant_and_registration!/1`
   technique `build_template!/0` already used, generalized to accept a target schema name), then
   calls `assert_clone_parity!("tenant_template_refcheck", "tenant_template", dimensions: [1,2,3,4,5,6,8,9,10,11,12,13])`
   — dimension #7 excluded per design §3.4 item 1's own text (row-for-row `event_type_registry`
   equality is moot between two independent seedings, not skipped for cost reasons). The reference
   schema and its throwaway rows are dropped in an `after` block regardless of outcome. This runs
   inside `ensure_template!/0`'s build path — once per BEAM VM/partition, not once per clone.
2. **Fixed the stale inline comment.** `template_self_check!/0`'s comment previously claimed to run
   "the full parity self-check" while its body only did two `MapSet` diffs — corrected to describe
   the two cheap pre-checks as a fast fail-fast gate BEFORE the real assertion, and the real
   assertion is now the added `assert_template_parity_against_independent_reference!/0` call.
3. **Use site 2 (permanent regression test)** — new file `test/support/tenant_template_test.exs`:
   clones a throwaway tenant and asserts full 13-dimension parity against the template, every
   suite run, unconditionally (no `:dimensions` restriction).
4. **N+1 fix in `check_sequences/2`** (dimension #5), per REVIEWER's MINOR finding — batched into
   one `information_schema.columns`-driven query per schema side, identical technique to the
   already-fixed `recreate_sequences!/1`. The now-dead `columns_in/2` helper was removed.
5. **Dispatch-default regression test** — new file `test/support/tenant_fixture_dispatch_test.exs`.

## Non-vacuity verification for the wiring itself (use site 1)

Verified via a throwaway `mix run` probe (not committed — a one-off structural verification, same
class as ELIXIR-DEV's own earlier tamper-and-detect proofs):

- Happy path: `ensure_template!/0` on a fresh database succeeded (`elapsed_ms=5803`), confirmed by
  querying `information_schema.schemata` that `tenant_template_refcheck` was NOT left behind
  afterward (only `tenant_template` remained).
- Tamper: built a real template via `ensure_template!/0`, then dropped a real, live FK
  (`instance_projections_parent_instance_id_fkey`) directly from the built template (bypassing the
  clone mechanism entirely — this corrupts the TEMPLATE itself, exactly the case use site 1 exists
  to catch), reset the process-local `persistent_term` marker (simulating a fresh VM), and called
  `ensure_template!/0` again. It raised:
  ```
  TENANT_TEMPLATE_PARITY reference=tenant_template_refcheck candidate=tenant_template
    [dim #3] constraints: missing=[{"group_members", "f", "FOREIGN KEY (group_id) REFERENCES groups(id)"}]
  ```
  (a second probe run reproduced the same shape against a different randomly-selected FK). This is
  the "a broken template must never silently serve broken clones" invariant (design §5), now proven
  against the wired code path rather than only against a hand-written direct call.

## Cost measurement and recommendation (item 4)

Measured directly (`mix run`, real Postgres, `letflow_test265` partition, warm connection pool),
five interleaved runs each unless noted:

| Operation | Cost |
|---|---|
| `clone_tenant_schema!/1` alone (no parity check) | ~1046 ms |
| `assert_clone_parity!/2`, all 13 dimensions | avg **1562.8 ms** (1467–1651 ms) |
| `assert_clone_parity!/2`, 12 dimensions (use-site-1 shape, no #7) | avg **1226.0 ms** (933–1553 ms) |
| `ensure_template!/0` full build (1 replay + use-site-1 12-dim check) | 5803–10951 ms (one-time, per BEAM VM) |
| dimension #5 alone, current batched form | avg **14.2 ms** |
| dimension #5 alone, pre-fix per-`(table,column)` N+1 form (measured for comparison, not shipped) | avg **768.7 ms** — **54.1x slower** |

**The decisive number: a full 13-dimension `assert_clone_parity!/2` (~1563 ms) costs MORE than
`clone_tenant_schema!/1` itself (~1046 ms).** Running it on every clone would not merely erode the
2.0x win this issue measured — it would make every provisioning call ~2.5x *slower* than the
`:replay` baseline it replaces (clone 1046 ms + full check 1563 ms ≈ 2609 ms vs. replay's own
~1313 ms median from ELIXIR-DEV's own measurement). This is not a marginal tradeoff; it is a
straightforward net loss if wired on the hot path.

**Recommendation: run the full 13-dimension check ONLY in the dedicated regression test
(use site 2, `tenant_template_test.exs`) and the 12-dimension subset ONLY at template-build time
(use site 1, once per BEAM VM/partition) — exactly as designed, and exactly what this step
implemented. Do NOT wire any form of `assert_clone_parity!/2` into `clone_tenant_schema!/1`'s own
per-clone path.** Argument, with numbers:

- Use site 1's cost (1226 ms) is paid ONCE per BEAM VM/partition, amortized across however many
  tests that partition runs (typically hundreds per the issue's own 755-provisioning count) — at
  that amortization, its per-test marginal cost is negligible even though the absolute number looks
  large in isolation.
- Use site 2's cost (1563 ms, once per suite run for that one test file) is likewise a fixed,
  bounded, one-time cost — not multiplied by every test that provisions a tenant.
- A per-clone check would multiply ~1563 ms by every one of the suite's real provisioning call
  sites — at the issue's own cited 755-provisioning figure, that is potentially +19.7 minutes of
  pure parity-check overhead added to the suite, against a clone mechanism whose entire reason to
  exist is shaving ~0.6 s off each of those same 755 calls (per ELIXIR-DEV's own 2.0x/1.8x
  measurement). This would not merely "erode" the win the design's own §3.4 item 1 anticipated —
  it would convert a real, measured, substantial win into a net regression, several times over.
- The N+1 fix applied to dimension #5 this step (54.1x on that one dimension) was necessary
  regardless of where the check runs — it is what keeps use site 1's own one-time 12-dimension cost
  at ~1.2 s instead of what it would have been unbatched (dimension #5 alone would have cost ~770 ms
  more per invocation without the fix, pushing use site 1 toward ~2 s and use site 2 toward ~2.3 s).
  Applying it did not change WHERE the check should run — it made the two use sites it already runs
  at meaningfully cheaper than they would otherwise have been.
- A "behind a flag" option was considered and rejected: it would either default off (defeating the
  point — the check exists so it always runs, per design §5's no-silent-fallback stance) or default
  on (reintroducing the exact per-clone cost problem above). The two-use-site design the code doc
  already specifies is strictly better than a flag: both use sites are unconditional, and neither is
  on the per-test hot path.

## MAJOR finding — `normalize/3`'s schema-qualifier stripping is blind to a "present but
## pointing at the template" coupling, contrary to design §3.2's own claims

**Discovered while wiring use site 1 and building use site 2's non-vacuity tests, exactly the kind
of discovery this run's own dispatch asked to be stopped and reported rather than silently patched
around.** This is a defect in the **parity-check verification code itself**
(`test/support/tenant_template.ex`'s `normalize/3` helper and every dimension built on it), not in
the clone mechanism (`do_clone/2`) — a genuinely correct clone still passes every dimension
correctly, and a clone missing a constraint/trigger/sequence entirely is still caught correctly (see
test case 2 above, and dimension #5's `pg_get_serial_sequence`-based "sequence namespace leak" check,
which is structurally immune — see below). What is NOT caught is the specific "object is PRESENT in
the clone but its definition still literally references the TEMPLATE schema" shape — exactly the
hazard design §0.1 finding 1 (FKs), §0/§0.1 findings 3–4 (sequences), and §0.4 (triggers/functions)
each name as the primary risk this whole design exists to prevent, and exactly what design §3.2 item
3's own text claims dimension #3 catches ("catches both 'FK missing entirely' ... and 'FK present but
pointing at the wrong schema'").

**Root cause.** `normalize/3` (`test/support/tenant_template.ex`) is:

```elixir
defp normalize(text, reference_schema, candidate_schema) do
  text
  |> String.replace(~s(#{reference_schema}.), "")
  |> String.replace(~s(#{candidate_schema}.), "")
end
```

It unconditionally strips BOTH schema qualifiers from BOTH sides' text before comparing. This is
correct for the ordinary case (a genuinely clone-local object correctly qualified to its own schema
on each side — stripping each side's own qualifier makes the two texts comparable). It is **blind**
to the regression case: if the CANDIDATE side's own definition text still literally contains the
REFERENCE schema's qualifier (because the object is present but was never repointed), that qualifier
gets silently erased by the exact same normalization step that legitimately strips it from the
correct case — so a repointed object's normalized text becomes indistinguishable from a correctly
recreated one.

**Independently reproduced three times, each via a real Postgres probe against a real clone (not
asserted, not inherited from any other agent's claim):**

1. **FK repoint (dimension #3).** Took a real FK from a real clone
   (`group_members_user_id_fkey`/`instance_projections_parent_instance_id_fkey`, reproduced with two
   different FKs on two separate runs), dropped it, re-added it with its definition's schema
   qualifier rewritten from the clone's own schema to `tenant_template.` (the exact "present but
   pointing at the wrong schema" shape). `assert_clone_parity!/2` returned `:ok`.
2. **Sequence-default repoint (dimension #5's `column_default` half, folded into dimension #2's
   comparison, AND dimension #5's own comparison).** Repointed a clone column's `DEFAULT` to
   `nextval('"tenant_template"."events_global_seq_seq"')` directly (the exact "sequence trap" shape
   design §0 names, simulating a clone mechanism regression that forgot the repoint step).
   `assert_clone_parity!/2` returned `:ok`. Root cause confirmed further: `pg_get_serial_sequence`
   (what dimension #5's OTHER assertion — "sequence namespace leak" — actually uses) resolves via
   `pg_depend`'s `OWNED BY` relationship, not the literal `DEFAULT` text, and this tamper changes only
   the `DEFAULT` text, not sequence ownership — so that one assertion, which IS structurally immune to
   the `normalize/3` blind spot (it never does text-normalization comparison), is simply never
   *reached* by this particular tamper shape. The `column_default`-text comparison inside dimension
   #2 (which DOES go through `normalize/3`) is what should have caught it and did not.
3. **Trigger-function repoint (dimension #8).** Dropped a real trigger from a real clone and
   recreated it with its `EXECUTE FUNCTION` clause repointed at the TEMPLATE's own function object
   (the exact shape ELIXIR-DEV's own handoff claimed to have proven caught, "Proof 4"). Traced
   precisely why that earlier claim does not hold under direct re-verification: `pg_get_functiondef`
   for a function's own definition does not embed any reference to a DIFFERENT schema inside its
   body (the function bodies in this codebase are plain `RAISE EXCEPTION` statements, no
   cross-schema calls) — so once `normalize/3` strips each side's own schema qualifier from the
   `CREATE OR REPLACE FUNCTION <name>()` header, the reference's own copy of `artifact_versions_immutable()`
   and the repointed clone's now-adopted copy of the TEMPLATE's `artifact_versions_immutable()`
   normalize to **byte-identical text**, and the two multisets compare equal.
   `assert_clone_parity!/2` returned `:ok`.

**Why this was not caught earlier, stated plainly.** ELIXIR-DEV's own "Proof 4" (step-03-continued
handoff) reported a raise with function-def frequency 1 vs 2 — but that proof's tampering method
(described narratively, not independently re-run by this step against the CURRENT shipped code)
evidently produced a genuinely different function OID/text shape than the minimal, mechanical
DROP-TRIGGER-then-CREATE-TRIGGER-with-rewritten-qualifier repoint this step used. This step's
reproduction used the simplest, most direct construction of "a trigger present but invoking the
template's function" — and it passed silently. Whatever difference explains the earlier proof's
result was not preserved in a committed test, which is precisely why REVIEWER's own finding-8(a)
required a PERMANENT test file rather than trusting an ad-hoc script's narrative — and precisely why
this step's own permanent, `@tag :skip`, committed reproduction (rather than another one-off script)
is the right artifact to leave behind.

**Scope decision for this step.** Per this run's own explicit instruction ("STOP and report rather
than adjusting the check to pass"), `normalize/3` and the dimension logic built on it were **not**
modified. TEST-DESIGNER's role does not include changing parity-check production/test-support logic
(`test/support/tenant_template.ex` beyond the mechanical N+1 batching REVIEWER already scoped and the
use-site-1 wiring this dispatch explicitly asked for). The three affected non-vacuity tests are
committed as `@tag :skip` with a full inline explanation, not deleted and not silently made to pass
by weakening their assertions — they are the regression proof whoever fixes `normalize/3` needs, and
removing `@tag :skip` is the acceptance test for that future fix.

**Severity and blast radius, stated precisely.** This does NOT mean the clone mechanism itself
(`do_clone/2`) is broken — every real, non-tampered clone this step produced passed all 13
dimensions correctly (test case 1), and the "missing entirely" shape of every hazard is still caught
correctly (test case 2, and ELIXIR-DEV's own FK-drop/trigger-drop proofs, independently
re-confirmed working here too). What is compromised is the SAFETY NET's ability to catch a **future**
regression that reintroduces the "present but pointing at the template" coupling the design's own
hazard analysis (§0, §0.1, §0.4) identifies as the primary risk — exactly the shape a subtle,
partial implementation bug in `readd_foreign_keys!/1`, `recreate_sequences!/1`, or
`readd_triggers_and_functions!/1` (e.g. a qualifier-substitution regex that matches less than
intended) would produce. The check would currently pass such a regression silently.

## Fail-then-pass verification (WF-03, use-site-1 wiring specifically)

Use site 1 did not exist before this step (`assert_template_parity_against_independent_reference!/0`
is new code, not a fix to existing logic) — this is the "code under test did not exist" case, so a
literal pre-fix/post-fix diff is not the applicable check. Per
`docs/agents/workflows/WF-03_issue_resolving.md`'s "code under test does not exist" procedure,
non-vacuity is instead proven by mutation: the tamper-and-revert proof in "Non-vacuity verification
for the wiring itself" above (dropped a real, live FK from a real built template; `ensure_template!/0`
raised citing dimension #3; reverted by rebuilding the template fresh) is that mutant, with its
measured result quoted verbatim above. A second, independent FK on a second run reproduced the same
raise shape, confirming this was not a one-off artifact of which FK happened to be selected.
