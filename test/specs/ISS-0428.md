# Test Spec: ISS-0428 — Adopt `scripts/test_parallel.sh` inside `mix letflow.check.test`

**Issue:** `docs/issues/ISS-0428.yaml`.
**Design:** `lib/letflow/design/iss0428-parallel-runner-in-check-test.md`.
**Fix:** `lib/mix/tasks/letflow.check.test.ex` (rewrite), commit on
`fix/ISS-0428-parallel-runner-in-check-20260904` (ELIXIR-DEV, step-03 handoff) —
`run_main_suite/0` now shells out to `bash scripts/test_parallel.sh` instead of plain
`mix test`, and the ISS-0069 substring gate is re-pointed at the N per-partition log
files the runner writes instead of the wrapper's own aggregated stdout.
**Test tier:** unit-level, driven through the real public entry point (`run/1`) via a
faked `bash`/`mix` executable on `PATH` — no mocked internals, no un-privatized
functions. See the test file's own moduledoc for the full technique writeup and the two
alternatives weighed and rejected.
**Test file:** `test/mix/tasks/letflow_check_test_test.exs` (full rewrite of the
pre-existing file, which tested the pre-ISS-0428 contract and no longer applies).

## Why this test file needed a full rewrite, not incremental fixes

The pre-existing file faked `mix` on `PATH` so `System.find_executable("mix")` —
called internally by the old `run/1`'s single subprocess call — resolved to a
controlled fake. `run_main_suite/0` now calls `System.find_executable("bash")` and
shells to `bash scripts/test_parallel.sh` instead, so the old interception point is
gone. Measured before this rewrite (ORCH's dispatch, corroborated independently):
`mix test test/mix/tasks/letflow_check_test_test.exs` (pre-fix test file, post-fix
implementation) → 0/3 passed, all three failing with `scripts/test_parallel.sh exited 1`
instead of the `Mix.Error` substring/exit assertions each test expected — the fake
`mix` never got a chance to intercept anything.

## Why this file matters more than ordinary test-file rot

This suite is the ONLY automated coverage of the ISS-0069 warning gate. ISS-0428's own
design doc (§1.1) is explicit that pointing the substring check at the wrong stream
makes the gate go green while checking nothing, permanently — nobody would notice from
a passing CI run until the warning class recurred unchecked (it has recurred 7 times
already: REQ-178/187/191/195/203, per `docs/anti-patterns.md`). The
CODE-DESIGN-VALIDATOR's own proof that the re-pointed algorithm works
(`handoffs/WF03-ISS0428-20260904/step-02b-code-design-validator.json`) is a one-off
manual injection experiment recorded in a handoff — not durable, not re-run on the next
commit. This test file is what makes that proof durable.

## Criteria (from the design doc, §9's own acceptance-criteria coverage map)

1. The re-pointed gate must still catch a real ISS-0069-shaped warning, with
   per-partition attribution (design §1.2 steps 4-5).
2. The gate must pass clean when the substring is absent, even with unrelated
   warnings present (unchanged behavior from before ISS-0428).
3. A real test failure (wrapper exits nonzero) must still raise, regardless of the
   substring — and failure-mode parity (design §4.2) requires printing the failing
   partition's full log content before raising.
4. **Hard-failure path 1**: the `partition logs in <dir>` line absent/unparseable must
   never pass silently (design §1.2 step 2's "Error shape").
5. **Hard-failure path 2**: zero `partition-*.log` files found must never pass silently
   (design §1.2 step 3's "Error shape").
6. **The ORDERING RULE** (design §1.2 step 1, CODE-DESIGN-VALIDATOR MINOR finding):
   when the wrapper exits nonzero AND the log-dir line is absent, the wrapper's
   nonzero exit must be reported FIRST, not "log line missing" — the common real case
   is a `mix compile` failure inside `test_parallel.sh`'s own pre-compile step.

## Test cases — `test/mix/tasks/letflow_check_test_test.exs`

1. **"raises and reports the offending line, with partition attribution, when the
   target substring is present in a per-partition log even though the wrapper exited
   0"** (criterion 1) — the central non-vacuity proof. Fakes `bash` to point at a
   synthetic two-partition-log fixture directory where only `partition-1.log` carries
   the injected warning; asserts the raised message names `[partition 1]` and never
   `[partition 2]`.

2. **"passes (no raise) when the wrapper exits 0 and the target substring is absent
   from every partition log, even with unrelated warnings present"** (criterion 2) —
   negative control: two unrelated real warning strings (the two ISS-0044-deferred
   classes) present in the fixture, asserting neither triggers the gate.

3. **"raises when the wrapper itself exits nonzero (real test failure), regardless of
   the substring, and prints the failing partition's full log content before
   raising"** (criterion 3) — asserts both the `Mix.raise` message (`"exited 1"`,
   `"Partition logs:"`) and, separately, the captured stdout contains the failing
   partition's actual assertion detail (`"Assertion failed"`) and the `FAILED` marker
   — the failure-mode-parity requirement, not just the raise itself.

4. **"hard-fails when the wrapper exits 0 but never prints a parseable
   partition-log-directory line"** (criterion 4) — fakes `bash` printing only the
   `N=...` header line, omitting the log-dir line entirely; asserts `Mix.raise` fires
   (never a silent pass) with the expected "never printed" wording.

5. **"hard-fails when the log-dir line is present but the directory contains zero
   partition-*.log files"** (criterion 5) — fakes `bash` pointing at a real, empty
   fixture directory; asserts `Mix.raise` fires with the "zero partition-*.log files"
   wording.

6. **"when the wrapper exits nonzero AND the log-dir line is absent, reports the
   wrapper's nonzero exit FIRST, not 'log line missing'"** (criterion 6, the ORDERING
   RULE) — fakes `bash` mirroring the real `mix compile`-failure-inside-test_parallel.sh
   case (exit 1, only the `ERROR pre-compile failed` line printed, no log-dir line at
   all). Asserts the raised message leads with `"exited 1 before ever printing"` and
   explicitly asserts it does NOT contain the "log line missing" framing — both a
   positive and a negative assertion, since either ordering produces *some* raise, and
   only the positive/negative pair actually pins down which one shipped.

## Technique — why faking `bash` (not un-privatizing internals, not a real end-to-end run)

Three options were weighed (full argument in the test file's own moduledoc, condensed
here):

1. **Fake `bash` on `PATH` (chosen).** `run_main_suite/0`'s only interaction with the
   outside world is `System.find_executable("bash")` + a Port-spawned
   `bash scripts/test_parallel.sh` call whose captured stdout is parsed. A fake `bash`
   printing a controlled `test_parallel: partition logs in <dir>` line (pointing at a
   synthetic fixture directory with real `partition-N.log` files) drives
   `run_main_suite/0` and every private helper it calls
   (`find_partition_log_dir/1`, `partition_logs/1`, `check_substring_across_logs/1`,
   `report_partition_failures/1`) for real, unmodified, exactly as committed. Verified
   directly before writing the final test file: six ad-hoc `mix run --no-start` probes
   against the real shipped `run/1` using this exact technique, one per criterion above.
   Real quoted output (paraphrased to the load-bearing line per probe; full transcripts
   were scratch, deleted after use per the file-placement rule):

   ```
   # criterion 1 (real occurrence, exit 0):
   RAISED: mix letflow.check.test: FAILED -- "default values for the optional
   arguments" warning found (ISS-0069's own class recurring):
     [partition 1] test/x.exs:1: warning: default values for the optional
   arguments in foo/1 are never used
   Partition logs: .../scratch/probe_warn_dir

   # criterion 3 (wrapper exits nonzero, logs present):
   RAISED: mix letflow.check.test: FAILED -- scripts/test_parallel.sh exited 1
   (real test failure/error). Partition logs: .../scratch/probe_fail_dir

   # criterion 4 (log-dir line absent, exit 0):
   RAISED: mix letflow.check.test: FAILED -- scripts/test_parallel.sh exited 0
   but never printed a "test_parallel: partition logs in <dir>" line. ...

   # criterion 5 (zero partition-*.log files):
   RAISED: mix letflow.check.test: FAILED -- partition log directory
   .../scratch/probe_zerologs_dir contains zero partition-*.log files. ...

   # criterion 6 (ORDERING RULE -- exit 1 AND log-dir line absent):
   RAISED: mix letflow.check.test: FAILED -- scripts/test_parallel.sh exited 1
   before ever printing its partition-log-directory line (the most common
   cause is a `mix compile` failure ...)
   ```

   (Criterion 2, the clean-pass negative control, produced `RUN_OK` with an `"OK --
   no test failures, no ISS-0069 warnings"` line in captured stdout, not a raise — the
   sixth probe.) All six match the assertions the corresponding test case in the
   committed file below makes.
2. **Test the log-parsing logic directly against fixtures, bypassing the subprocess.**
   Rejected as the *sole* technique — the three parsing/globbing functions are `defp`
   today, and the design's own §6 (public interface) does not ask for them to become
   `def`. Un-privatizing them permanently for this file's sake would be a bigger
   footprint than option 1 needs, since option 1 already reaches every one of them
   through the real public entry point, including their *composition* (the ordering
   rule specifically depends on how `run_main_suite/0` sequences two error checks
   against each other — an isolated unit test of each function alone would not catch a
   regression in that sequencing, only option 1's end-to-end-through-`run/1` shape
   does). Flagged explicitly, not silently decided: if a future maintainer wants
   isolated unit tests of the parsing pieces, the minimal change is promoting exactly
   those three functions from `defp` to `def`/`@doc false def` — nothing more.
3. **A real end-to-end run of `scripts/test_parallel.sh`.** Rejected for a test that
   runs on every commit: multi-minute wall clock, non-deterministic N-across-hosts,
   real Postgres dependency — exactly the slow/flaky addition to a suite
   `core-directives.md` warns against manufacturing. That real-integration coverage
   already exists as evidence in the ELIXIR-DEV and CODE-DESIGN-VALIDATOR handoffs, and
   continues to be exercised going forward by TEST-RUNNER/RELEASE-VALIDATOR's own full
   `mix letflow.check.test` runs (which necessarily invoke the real script) — this file
   does not need to re-pay that cost to preserve that coverage.

## Fail-then-pass verification (WF-03 Step 4 regression-test requirement)

`run_main_suite/0` (the code this file's tests exercise) is not a "code did not exist"
case for WF-03's carve-out purposes — it already existed, committed, on this branch
before this TEST-DESIGNER step began (ELIXIR-DEV's step-03 handoff). So the applicable
fail-then-pass proof is: (a) the OLD test file genuinely fails against the NEW
implementation, and (b) the NEW test file passes against the NEW implementation and is
shown, by mutation, to be sensitive to the specific traps it exists to catch — not
merely present.

**(a) Old test file fails against the new implementation.** Precisely measured by
ORCH's own dispatch for this run, quoted verbatim as this step's task block:
`mix test test/mix/tasks/letflow_check_test_test.exs` (old file, against the new,
already-committed `run_main_suite/0`) → **0/3 passed, all three failing**, by name:
"raises and reports the offending line... even though the underlying subprocess exited
0", "raises when the subprocess itself exits nonzero, regardless of the substring", and
"passes (no raise) when the subprocess exits 0 and the target substring is absent...".
TEST-DESIGNER attempted to independently re-reproduce this by `git stash`-ing the new
file back to disk and re-running, but the old file's `install_fake_mix/2` fakes `mix`,
not `bash` — `run_main_suite/0` shells to the REAL `bash`, which launches the REAL,
16-partition `scripts/test_parallel.sh` (since nothing intercepts it), which takes
several minutes and was killed mid-run rather than paid for a second time (its result
would only re-confirm ORCH's already-precise, already-quoted number, at real cost to
this host and to sibling sessions sharing it). **The underlying mechanism was
independently verified instead** (cheaper and more informative than re-running the
same slow probe): `System.find_executable("bash")` resolves to the real
`bash.exe`/`bash.bat` regardless of what fake `mix` is on `PATH`, since `run_main_suite/0`
never calls `System.find_executable("mix")` at all — confirmed by direct code read of
`lib/mix/tasks/letflow.check.test.ex:126` and by this file's own six probes (below),
which prove the converse positively: faking `bash` (not `mix`) is what intercepts
`run_main_suite/0`, which is the same fact stated the other way around.

**(b) Mutation testing — two mutants applied directly to the shipped
`lib/mix/tasks/letflow.check.test.ex`, each reverted and the revert verified, per
`docs/agents/workflows/WF-03_issue_resolving.md`'s "revert with `git checkout --`, then
VERIFY the revert" procedure:**

*Mutant 1 — break the ORDERING RULE* (removed the `:not_found when exit_code != 0`
branch of `run_main_suite/0`'s case statement, collapsing it into the generic

## Reliability and cost

All six test cases run through the fake-`bash`/`mix`-on-`PATH` seam — no real
subprocess recursion into `mix test`/`scripts/test_parallel.sh`, no real Postgres
dependency beyond what `Letflow.TenantSchemaReaper` sweeps already run at suite
boundaries (unrelated to this file). Measured wall clock for the full file:
`mix test test/mix/tasks/letflow_check_test_test.exs --seed 0` → **0.7 seconds, 6
tests, 0 failures** (quoted output above). Deterministic: no wall-clock-sensitive
assertion, no unseeded randomness, `async: false` matching the original file (each
test mutates the shared `PATH` env var, so cannot run concurrently with itself or with
another test file's own `PATH` manipulation).
