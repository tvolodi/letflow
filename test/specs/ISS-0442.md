# Test Spec: ISS-0442 — `--autofix` minimal-diff rewrite

**Issue:** ISS-0442 — `lint_handoffs --autofix` used to `Jason.decode` the whole file,
mutate the `status` key, and `Jason.encode!(pretty: true)` the whole map back out,
turning a one-field fix into an ~84-line diff (alphabetical key re-sort + pretty-print
reflow at every nesting level). Fixed by ELIXIR-DEV per
`lib/letflow/design/iss0442-lint-handoffs-minimal-diff-autofix.md` (option (b)): a
depth- and position-aware raw-text scan (`splice_top_level_status/2`) that locates the
exact `status` value token belonging to the root object and replaces only that token's
bytes, leaving every other byte of the file untouched.

**Run:** WF03-ISS0442-20260904, WF-03 Step 4. **Design:**
`lib/letflow/design/iss0442-lint-handoffs-minimal-diff-autofix.md` §2. **Reviewer
gate:** `handoffs/WF03-ISS0442-20260904/step-03-reviewer.json` (PASS, with one REQUIRED
follow-on condition — see AC1 below).

**Code under test:** `rewrite_top_level_status!/3` and `splice_top_level_status/2` in
`lib/mix/tasks/letflow.lint_handoffs.ex`. Both are **newly added** functions — they
replace `write_json!/2`, which no call site invokes any more — so there is no pre-fix
version to check out and prove red against. Per WF-03's "code under test does not
exist" clause, fail-first evidence here is a **mutation**, not a checked-out commit: see
"Mutation evidence" below.

---

## AC1 (REQUIRED, named by REVIEWER) — nested `result.status` is never mistaken for the
## top-level `status`

**Criterion:** a file with a FIXABLE top-level `status` (one of `PASS`/`COMPLETE`/`DONE`)
and a nested `result.status` present in the same file must, after `--autofix`, have (a)
its top-level status corrected to `COMPLETED` and (b) its nested `result.status`
byte-identical to its pre-fix value.

**Why this exists, not just what it restates:** this is the exact collision
ISSUE-FIXER originally demonstrated on a real fixture (top-level `"PASS"` next to a
nested `result.status: "PASS"`), and REVIEWER independently reproduced a mutation
(removing the `depth == 1` guard in `handle_string_token/5`) that survives **all 43**
pre-existing tests while silently corrupting the wrong field: it leaves the top-level
status unfixed and rewrites the nested `result.status` instead. Every existing fixture
combining both nesting levels used an already-legal top-level `COMPLETED`, which hits
the `:skip` branch before `rewrite_top_level_status!/3` is ever called — so the splice
code itself was never previously exercised on a file that also has a nested `status`
key. Without a test that reaches the splice branch on such a file, this is vacuous
coverage: the depth-tracking mechanism that is the entire point of this fix could be
deleted and nothing would fail.

**Test case:** `T-AUTOFIX-NESTED-STATUS-COLLISION-PASS-PASS`
(`test/mix/tasks/letflow.lint_handoffs_test.exs`). Asserts the decoded top-level and
nested values directly, AND asserts the whole rewritten file is byte-identical to a
hand-computed expectation (stronger than the decode-based checks: it proves the ONLY
changed span anywhere in the file is the top-level value token).

**Mutation evidence:** removed the `depth == 1` guard from `handle_string_token/5`
(`if depth == 1 and key_follows?(after_string) do` → `if key_follows?(after_string) do`)
in the tracked file, re-ran `test/mix/tasks/letflow.lint_handoffs_test.exs`, reverted.
See this test-designer's handoff `result.summary` for the measured before/after counts.
`T-AUTOFIX-NESTED-STATUS-COLLISION-PASS-PASS` and
`T-SPLICE-PRESERVES-ESCAPES-BRACES-ARRAY-NO-NEWLINE` both fail under the mutant (2
failures); all other 45 tests in the file are unaffected, confirming the new tests are
what actually kill it, not incidental breakage elsewhere.

## AC2 — escapes, embedded structural characters, and inline arrays inside string
## values never affect depth tracking or key detection

**Criterion:** a document containing a string value with an escaped quote and a
literal, unbalanced `{`/`}` character inside it, plus an inline single-line array
elsewhere, is rewritten with only the top-level status token changed — the escaped
quote, the embedded brace, and the array's original single-line formatting are all
byte-identical afterward.

**Why this exists:** this is the design's own §2.2 string-scanning correctness
property (depth is tracked only *outside* strings; `consume_json_string/1` must resolve
string boundaries before the depth-changing clauses ever see the characters). It is
also the concrete mechanism that makes AC1 safe in general — if a literal `{` inside a
string value were misread as a real nesting brace, depth tracking (and therefore the
whole `depth == 1` discriminator AC1 depends on) would desync. Also proves effect (2)
from the original bug (pretty-print reflow) does not recur: the inline array's
single-line formatting is preserved exactly, not exploded one-element-per-line the way
`Jason.encode!(pretty: true)` used to.

**Test case:** `T-SPLICE-PRESERVES-ESCAPES-BRACES-ARRAY-NO-NEWLINE`. Also asserts no
trailing newline is force-appended (the design's other named, explicit §2.2 promise —
"no fallback to the old whole-document re-encode ... no trailing newline append").

## AC3 (preserved-behavior regression) — refusal branches untouched by this fix

**Criterion:** `FAIL`, missing, and `null` top-level status values are still refused
(file left byte-identical, reported on stdout, still a hard violation) exactly as
before this fix — this fix only changes *how* a fix is written to disk, never *which*
files get fixed/refused/skipped.

**Why this exists:** the design's §3 "Preserved behavior" section explicitly names
this property; `T-AUTOFIX-REFUSES-FAIL` already covered the `FAIL` case pre-existing in
this suite. Missing and `null` status were not previously exercised through the
`run/1 --autofix` path (only through direct `lint_file/2` calls, which don't touch the
autofix/refusal machinery at all) — closing that gap here.

**Test cases:** `T-AUTOFIX-REFUSES-MISSING-STATUS`, `T-AUTOFIX-REFUSES-NULL-STATUS`.

## Known gap intentionally NOT covered here (flagged, not worked around)

While designing AC1's fixture, a document with a **duplicate top-level `status` key**
was investigated as a candidate edge case (the design's §2.2 step 2 explicitly claims
last-key-wins "mirroring `Jason.decode/1`'s own last-key-wins semantics"). Direct
verification against this project's pinned Jason version found the opposite:
`Jason.decode!(~s({"status":"a","status":"b"}))` returns `%{"status" => "a"}` —
**first**-key-wins, not last — while `scan_for_status/4`'s `best` accumulator is
unconditionally overwritten on every depth-1 match, i.e. genuinely last-*match*-wins.
For a duplicate-key document these two disagree on which occurrence is "the" status,
so `--autofix` edits a different span than the one `autofix_file/1` actually decided to
fix based on, and the very next lint pass then reports a fresh H1 violation on the
(unedited) first occurrence. Reproduced directly (not merely reasoned about) via a
throwaway fixture and quoted in this test-designer's handoff `result.summary`.

This is a real, latent defect, but it is orthogonal to every acceptance criterion this
run is scoped to — duplicate top-level keys are themselves malformed JSON that no real
handoff file has ever contained — and committing a test for it would require asserting
the buggy behavior as "correct" to pass, which this project's Forbidden section rules
out. Flagged here and in the handoff for ORCH to route as a new issue if judged worth
fixing, not silently worked around.
