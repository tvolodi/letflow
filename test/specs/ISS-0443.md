# Test Spec: ISS-0443 — `lint_handoffs` rejects unrecognized flags instead of silently ignoring them

**Issue:** ISS-0443 — `mix letflow.lint_handoffs`'s hand-rolled flag parsing
(`find_dir_flag/1`'s `[_other | rest]` catch-all) silently discarded any token it
didn't recognize. A mistyped `--autofx` or `--dr` produced a confident, healthy `OK`
exit-0 result with no indication the flag was meaningless — the same
"plausible-looking input silently produces a wrong-but-green result" shape ISS-0440
itself exists to prevent. Discovered by REVIEWER during `WF03-ISS0440-20260903`,
independently reproduced by ORCH with `mix letflow.lint_handoffs --bogus-flag-xyz`.

**Run:** WF03-ISS0443-20260907, WF-03 Step 4. **Design:**
`lib/letflow/design/iss0443-lint-handoffs-strict-flag-parsing.md` (§1 for the
`parse_flags/1`/`raise_invalid_flag/1` replacement shape, §4 for the test-ability
checklist this spec follows). **Fix commit:** `c357f97a` (`fix(ISS-0443): reject
unrecognized lint_handoffs flags via OptionParser strict mode`). REVIEWER and
SECURITY-REVIEWER already PASSed that commit on this branch, including their own
independent live-verification of AC1-AC4 before TEST-DESIGNER's step.

**Code under test:** `Mix.Tasks.Letflow.LintHandoffs.parse_flags/1` (new private
helper), `raise_invalid_flag/1` (new private helper), `resolve_dir/1` (existing
public function, now delegates to `parse_flags/1`), and `run/1` (existing, now calls
`parse_flags/1` once instead of hand-parsing `--dir`/`--autofix` separately). All in
`lib/mix/tasks/letflow.lint_handoffs.ex`. Single parse point: `OptionParser.parse(args,
strict: [dir: :string, autofix: :boolean])`.

## AC1 — an unrecognized flag produces a loud failure naming the offending flag and
## non-zero exit, demonstrated by a real run with actual output quoted

**Criterion (`docs/issues/ISS-0443.yaml`):** the confident-green shape (a mistyped
flag silently discarded, exit 0, healthy `OK` banner) must become a loud, non-zero-exit
failure that names the specific offending flag.

**Why this exists, not just what it restates:** the defect was specifically that
*nothing* observable distinguished a mistyped flag from a correctly-typed one — a test
that only checks "the function returns something different" would miss the actual
complaint, which is that the failure must be *loud* (raises, names the flag) rather
than silent. The two typo shapes named in the issue itself (`--autofx`, `--dr`) are
covered as concrete regression cases, not just the synthetic `--bogus-flag-xyz` ORCH
used to reproduce it, since a fix that only handled one shape by coincidence would be
underspecified.

**Test cases** (`test/mix/tasks/letflow.lint_handoffs_test.exs`, describe
`"ISS-0443 -- resolve_dir/1 rejects an unrecognized flag (unit level)"` and `"ISS-0443
-- run/1 end-to-end: an unrecognized flag never produces a confident OK"`):
- `F-UNKNOWN-FLAG-RAISES` — `resolve_dir(["--bogus-flag-xyz"])` raises `Mix.Error`
  matching `~r/unrecognized flag "--bogus-flag-xyz"/`.
- `F-UNKNOWN-FLAG-AUTOFX-TYPO` — `resolve_dir(["--autofx"])` raises naming `--autofx`.
- `F-UNKNOWN-FLAG-DR-TYPO` — `resolve_dir(["--dr", "x"])` raises naming `--dr`.
- `T-UNKNOWN-FLAG-RUN-RAISES` — `run/1` end-to-end (not just the helper) raises for
  `--bogus-flag-xyz`.
- `T-UNKNOWN-FLAG-RUN-NO-OK-BANNER` — after the raise, `capture_io`'s captured stdout
  contains neither `"OK --"` nor `"new violations"` — proves no partial/confident-green
  output leaked out before the raise fired.

**Real-run evidence (this session, live):**

```
$ mix letflow.lint_handoffs --bogus-flag-xyz

EXIT: 1

EXIT: 1
```

FAIL/missing/null/non-string `--autofix` refusal behavior ISS-0440 already implemented

writing new tests, this AC is satisfied by re-running ISS-0440's own pre-existing test
suite unmodified — a design-review point (§4 item 2) explicitly calling out that

regression.

## AC4 — if `OptionParser` is adopted, confirm it doesn't reject/reinterpret any
## argument form existing call sites rely on

**Criterion:** the switch to `OptionParser.parse(strict: ...)` must not change the
outcome of any call shape a real caller (production code or test) actually uses.

**Why this exists, not just what it restates:** this is the regression-prevention
counterpart to AC1's rejection-path tests — proving the new strict parser is *strict
in the right direction only*. Two additional shapes the design specifically flags as
worth locking in with a permanent test (§0's load-bearing finding, §4 item 1's
`--autofix=notabool` note) get their own new tests here, since they were previously
only manually verified by REVIEWER, not covered by a committed test:

- a **malformed value for a recognized flag** (`--autofix=notabool`) — `strict:`
  produces a *different* `invalid` entry shape (`{flag, value}` with a non-nil value)
  than an unrecognized flag (`{flag, nil}`), and `raise_invalid_flag/1` has a
  dedicated third clause for it (design §1.2) that no prior test exercised.
- a **bare positional argument** (`mix letflow.lint_handoffs foo`) — `OptionParser`'s
  `strict:` mode does not reject this on its own (design §0's load-bearing finding: it
  lands in `remaining`, not `invalid`), so `parse_flags/1` needed its own explicit
  `remaining != []` check (design §1.1 step 3, §1.4) to close this gap. Without a test,
  a future refactor that dropped that check would silently reopen exactly the "typo
  swallowed, real corpus scanned" failure mode this whole issue exists to close (design
  §1.4's own stated rationale: a caller who meant `--dir foo` but dropped the `--dir`
  would previously have had `foo` silently discarded too).

**Test cases** (`test/mix/tasks/letflow.lint_handoffs_test.exs`):
- `F-AUTOFIX-INVALID-VALUE` — `resolve_dir(["--autofix=notabool"])` raises `Mix.Error`
  matching `~r/invalid value "notabool" for flag "--autofix"/`.
- `F-BARE-POSITIONAL-REJECTED` — `resolve_dir(["foo"])` raises matching
  `~r/unexpected argument\(s\) \["foo"\]/`.
- `T-AUTOFIX-INVALID-VALUE-RUN-RAISES` — same assertion via `run/1` end-to-end.
- `T-BARE-POSITIONAL-RUN-RAISES` — same assertion via `run/1` end-to-end.

Every legitimate call shape (`[]`, `["--dir", path]`, `["--autofix"]`,
`["--autofix", "--dir", path]`, and the reverse order) is covered by AC2's
pre-existing, still-passing suite — no fifth call shape exists anywhere in `mix.exs`
or CI (confirmed by grep, design §0, re-confirmed this session).

**Real-run evidence (this session, live):**

```
$ mix letflow.lint_handoffs --autofix=notabool
** (Mix) letflow.lint_handoffs: invalid value "notabool" for flag "--autofix"
EXIT: 1

$ mix letflow.lint_handoffs foo
** (Mix) letflow.lint_handoffs: unexpected argument(s) ["foo"] -- this task takes no positional arguments
EXIT: 1
```
