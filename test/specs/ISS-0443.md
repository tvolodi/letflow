# Test Spec: ISS-0443 — lint_handoffs strict flag parsing

**Issue:** ISS-0443 — `mix letflow.lint_handoffs`'s `run/1` parsed `--dir` and
`--autofix` by hand, silently discarding any other flag. A mistyped `--autofx` or
`--dr` produced a confident `OK, 0 new violations` exit-0 result with no indication
the flag was meaningless — a caller reasonably concludes their command did what they
asked when it did not.

**Run:** WF03-ISS0443-20260907, WF-03 Step 4. **Design:**
`lib/letflow/design/iss0443-lint-handoffs-strict-flag-parsing.md`. **Fix commit:**
`c357f97a` (replaces hand-rolled parsing with `OptionParser.parse(args, strict: [dir:
:string, autofix: :boolean])`). **Test commit:** this run's Step 4 commit.

**Code under test:** `Mix.Tasks.Letflow.LintHandoffs.resolve_dir/1` and `run/1`
(`lib/mix/tasks/letflow.lint_handoffs.ex`). `resolve_dir/1`'s signature/return type
(`[String.t()] :: String.t()`) is unchanged; internally it now delegates to
`OptionParser.parse/2` in strict mode instead of the deleted `find_dir_flag/1`
hand-walk.

---

## AC1 — an unrecognized flag produces a loud failure naming the offending flag and a
## non-zero exit, demonstrated by a real run

**Criterion (`docs/issues/ISS-0443.yaml`):** an unrecognized flag must raise, naming
itself, rather than being silently discarded.

**Why this exists:** the defect's whole shape is a *confident green for an action that
never happened* — a test that only checks "no output" or "some error" without naming
the flag would miss the actual usability requirement (a caller needs to see which flag
they mistyped).

**Test cases** (`test/mix/tasks/letflow.lint_handoffs_test.exs`, `describe "ISS-0443 --
resolve_dir/1 rejects an unrecognized flag (unit level)"` and `describe "ISS-0443 --
run/1 end-to-end: an unrecognized flag never produces a confident OK"`):
- `F-UNKNOWN-FLAG-RAISES` — a generic unrecognized flag (`--bogus-flag-xyz`) raises
  `Mix.Error` naming itself.
- `F-UNKNOWN-FLAG-AUTOFX-TYPO` — the issue's own motivating example, `--autofx`
  (missing the second `i`), is rejected by name.
- `F-UNKNOWN-FLAG-DR-TYPO` — the issue's own other motivating example, `--dr`, is
  rejected by name.
- `T-UNKNOWN-FLAG-RUN-RAISES` — the same case exercised end-to-end through `run/1`.
- `T-UNKNOWN-FLAG-RUN-NO-OK-BANNER` — explicitly asserts no `"OK --"` / `"new
  violations"` banner text is ever printed when a flag is rejected, i.e. the rejection
  happens *before* any scan output, closing the "confident green" shape directly.

**Real-run evidence (REVIEWER, independently re-verified):**
```
$ mix letflow.lint_handoffs --bogus-flag-xyz
** (Mix) letflow.lint_handoffs: unrecognized flag "--bogus-flag-xyz" -- known flags are --dir <path> and --autofix
```
Exit code 1.

## AC2 — `--dir`/`--autofix` continue to work exactly as ISS-0440 specified

**Criterion:** the empty-scope refusal, banner, and FAIL/missing/null/non-string
autofix refusal from ISS-0440/ISS-0442/ISS-0457 are unchanged, each re-demonstrated by
a real run.

**Why this exists:** `resolve_dir/1`'s external contract (same input/output shape) is
the thing the refactor must not break; the four pre-existing tests already covering
this behavior are the actual proof, not a restatement.

**Test cases (pre-existing, unmodified, still passing against the new implementation):**
`F-DIR-DEFAULT`, `F-DIR-EXPLICIT`, `F-DIR-ORDER-INDEPENDENT`, `F-DIR-MISSING-VALUE` —
the last of these is the load-bearing one: the new implementation's `{"--dir", nil}`
branch produces the byte-identical pre-existing message
(`"--dir given with no path argument"`) so this test needed no changes, distinguishing
it textually from the new unrecognized-flag message.

**Real-run evidence (REVIEWER):**
```
$ mix letflow.lint_handoffs
letflow.lint_handoffs: OK -- 0 new violations across 2398 handoff files under "handoffs" (25 pre-existing grandfathered, traced to ISS-0190).
```
Exit code 0 — normal healthy path unaffected.

## AC4 — OptionParser does not reject or reinterpret any legitimate existing call form

**Criterion:** adopting `OptionParser.parse/2` must not change behavior for any
argument form the existing call sites actually use.

**Why this exists:** `OptionParser.parse/2` in strict mode has real edge behavior
(e.g. `--flag=value` vs. `--flag value`, positional arguments landing in `remaining`
rather than `invalid`) that could silently reinterpret a previously-accepted form if
not checked directly.

**Test cases:**
- `F-AUTOFIX-INVALID-VALUE` / `T-AUTOFIX-INVALID-VALUE-RUN-RAISES` — `--autofix=notabool`
  (a type-mismatch value for a *recognized* flag) is rejected with a distinct "invalid
  value" message, proving `OptionParser`'s type-checking is wired in without being
  confused with the "unrecognized flag" case.
- `F-BARE-POSITIONAL-REJECTED` / `T-BARE-POSITIONAL-RUN-RAISES` — a bare positional
  argument (`foo`, no leading `--`) is rejected, closing an additional silent-swallow
  the old hand-parsing also had (positional tokens were previously ignored entirely).
- `F-DIR-DEFAULT`/`F-DIR-EXPLICIT`/`F-DIR-ORDER-INDEPENDENT` (AC2, above) confirm the
  two legitimate flags in both `--dir <path>` positional-value form and any order
  still parse identically to before.

is what they silently did with an unrecognized flag) — the standard fail-then-pass
rule applies, not the mutation-testing addendum for wholly-new code.

code genuinely swallowed every one of these cases silently.
