# Test Spec: ISS-0446 — throwaway-supervisor `on_exit` check-then-act teardown race

**Issue:** ISS-0446 — `service_task_dispatcher_test.exs`'s throwaway-supervisor
`on_exit` guard (`if Process.alive?(sup_pid), do: Supervisor.stop(sup_pid)`) is a
check-then-act race across a process boundary: `Process.alive?/1` can observe `true`
and the linked supervisor can still die mid-flight before `Supervisor.stop/1`'s
monitored call completes, making `Supervisor.stop/1` exit `{:shutdown, ...}` instead of
returning `:ok`. Fixed by ELIXIR-DEV (commit `414f0b26`) per
`lib/letflow/design/iss0446-throwaway-supervisor-teardown-race-fix.md` — the ad-hoc
`Supervisor.start_link/2` + `on_exit` guard is replaced entirely with
`ExUnit.fetch_test_supervisor/0` + `start_supervised!/1`, which has no
`Process.alive?` check anywhere in its teardown path (`ExUnit.OnExitHandler`'s
`terminate_supervisor/2` is a blocking `Process.monitor/1` + `receive {:DOWN, ...}`).

**Test tier:** structural/mechanism verification (this is a MINOR test-infrastructure
bug fix, not a `docs/requirements.yaml` REQ — no formal acceptance criteria list; the
implicit requirements are "the race is removed" and "no test coverage is lost," both
addressed below).

## Why no regression test was committed to the suite (decision, argued)

REVIEWER's Step 3c gate (`handoffs/WF03-ISS0446-20260904/step-03c-reviewer.json`, item
5) is directive here: a test that reproduces the *original* CI race on demand, under
real (unwidened) timing, is structurally impossible in this suite — the race requires
loaded/contended scheduling this suite cannot control or guarantee locally (confirmed
again below: the fix's own file, run quietly and in isolation, is 42/42 clean both
before and after the fix, exactly as the CI report itself observed 3192/3192 passing
locally on the run where CI failed). What IS achievable is a widened-timing *analog*:
a supervised child whose `terminate/2` does deliberate, measurable work, to force the
same class of scheduling window CI's load produces. I built and ran that analog (this
document, below) rather than skip verification — but I did **not** commit it to
`test/`, for three reasons weighed explicitly:

1. **A committed sleeping-`terminate/2` test adds real runtime to every future CI run,**
   and this project already carries two live, documented CI-flake sources (ISS-0352
   `wasm_hang`, ISS-0426 `lua_wallclock_race`). A new deliberately-slow, timing-shaped
   test is exactly the shape that becomes the next flake citation, and the analog only
   reproduces reliably under **concurrent (`async: true`) scheduler contention** (see
   below) — a single, isolated, `async: false` instance of it is *not* reliably
   flaky on quiet hardware, which is a further reason a lone committed copy would not
   even reliably re-demonstrate anything on a typical CI run; it would need many
   concurrent siblings to load the scheduler the way this analog required, which is a
   worse tradeoff than the flake risk it would be bought to avoid.
2. **A committed test asserting "the OLD racy shape crashes under contention" tests
   ExUnit's own `on_exit`/link-teardown behaviour, not any Letflow application logic.**
   The old shape no longer exists in the shipped test file at all (ELIXIR-DEV deleted
   it outright, not merely wrapped it) — a permanent test built only to demonstrate that
   deleted code was broken has no shipped counterpart to regress against and would be
   manufactured busywork per this role's own scope test, not real coverage of anything
   Letflow owns.
3. **The safety argument for the fix is structural, not statistical**, and REVIEWER's
   gate already treated the structural argument (no `Process.alive?` check anywhere in
   `ExUnit.OnExitHandler.terminate_supervisor/2`, independently re-verified against
   real source at `on_exit_handler.ex:61-70` by both CODE-DESIGNER and REVIEWER) as
   sufficient on its own to pass the gate, with the widened-timing probe explicitly
   named "corroborating evidence," not a precondition. A one-off verification run,
   reported honestly with real output, satisfies that corroborating-evidence role
   without paying the committed-flake-risk cost for a passive statistical demonstration
   that adds nothing to what the structural argument already establishes.

Weighed against this: an uncommitted probe leaves no durable, automatic guard against
someone reintroducing this exact check-then-act pattern in this file later. I looked
for a cheap, non-timing-based guard instead of dropping the question — see "Considered
and rejected" below. None was in scope to add here without expanding beyond this
issue's own file, so this residual is reported, not silently accepted.

**Considered and rejected: a static/grep-based guard.** `grep -rn
"on_exit.*Process.alive?" test/` shows this exact check-then-act shape
(`on_exit(fn -> if Process.alive?(pid), do: <stop-call> end)`) already exists in **eight
other places** in this suite (`test/letflow/definitions/promotion_assertion_rerun_test.exs:127`,
`test/letflow/event_store/platform_events_test.exs:316`,
`test/letflow/sandbox_pool/fixture_loader_test.exs:47`,
`test/letflow/sandbox_pool_test.exs:103,662,1458,1486`,
`test/support/service_catalog_reaper_test.exs:247`). A cheap Credo-style or `mix
letflow.check.*`-style grep gate against this pattern would be a real, non-timing-based
guard — but it would apply suite-wide, not to this one file, making it a scope
expansion beyond ISS-0446's own affected-file list. **Reported as a candidate follow-up
finding for ORCH to file as its own issue, not fixed here** (`docs/agents/protocols/ISSUE_QUEUE.md`
governs; not actioned in this handoff per "Unblock-Everything"'s scope boundary — this
is a defect merely *noticed*, not one blocking this task's own acceptance).

## What was actually run, and why it counts as evidence (not proof)

**Baseline (necessary, not sufficient) — matches ELIXIR-DEV's own Step 3 run:**
`mix test test/letflow/engine/service_task_dispatcher_test.exs` on the current
(post-fix) branch: 42 passed, 0 failures. This shows the fix broke no assertion in the
real file; it does **not** demonstrate the race is gone, because the race never
reliably reproduced under quiet local conditions even pre-fix.

**Widened-timing mechanism analog (the real evidence).** Built two throwaway ExUnit
scripts (never committed; run via bare `elixir <script>.exs`, deleted immediately
after use — `git status --porcelain scratch/ test/ lib/` confirmed empty afterward):

- **OLD shape**: 80 `async: true` test cases, each replicating the exact deleted
  pattern — `Supervisor.start_link/2` (no name) starting one child GenServer whose
  `terminate/2` does `Process.sleep(5)` (matching ISSUE-FIXER's own validated
  widening value from Step 1), followed by
  `on_exit(fn -> if Process.alive?(sup_pid), do: Supervisor.stop(sup_pid) end)`.
  `async: true` was necessary, not incidental — early attempts at `async: false` (one
  test at a time, sequential) reproduced **zero** failures across 10+80+ runs at sleep
  values from 1ms to 50ms, because a single test's own on_exit callback and its
  supervisor's link-teardown aren't contending with anything else for scheduler time.
  Only concurrent (`async: true`) scheduling — many of these tests' on_exit callbacks
  and link-teardowns competing for BEAM scheduler slots at once — reproduces the
  window CI's shared, loaded hardware supplies. This is itself a finding worth
  recording: the race is not merely "rare," it is specifically a **concurrency-load**
  phenomenon, consistent with the issue's own note that CI (shared, loaded runners)
  hits it and a quiet local run does not.

  Four runs of the 80-case OLD-shape file: **6/80, 2/80, 8/80, 9/80 failures.**
  Captured failure detail (via a minimal custom ExUnit formatter, since the default
  formatter's output was not appearing under bare `elixir script.exs` invocation)
  reproduces the CI failure's **exact** shape and stacktrace:
  ```
  ** (exit) exited in: GenServer.stop(#PID<0.358.0>, :normal, :infinity)
      ** (EXIT) exited in: :sys.terminate(#PID<0.358.0>, :normal, :infinity)
          ** (EXIT) shutdown
  stacktrace:
    (elixir 1.20.3) lib/gen_server.ex:1144: GenServer.stop/3
    (ex_unit 1.20.3) lib/ex_unit/on_exit_handler.ex:140: ExUnit.OnExitHandler.exec_callback/1
    (ex_unit 1.20.3) lib/ex_unit/on_exit_handler.ex:126: ExUnit.OnExitHandler.on_exit_runner_loop/0
  ```
  matching ISS-0446.yaml's cited CI stacktrace line-for-line (`gen_server.ex:1144` /
  `on_exit_handler.ex:140`). A second, related failure shape also appeared
  (`Process.alive?` returned `true` but the process was gone by the time
  `GenServer.stop/3` itself dispatched, raising `:noproc`) — the same unsynchronized
  check-then-act class the issue describes, just resolved on the other side of the
  race window; both are check-then-act failures with no assertion in the test body
  itself failing, exactly as ISS-0446 describes ("only teardown blew up").

- **NEW shape**: the same 80-case structure, using the shipped fix's exact call
  sequence — `{:ok, sup} = ExUnit.fetch_test_supervisor()`,
  `pid = start_supervised!({SlowChild, []})`, no `on_exit` of any kind — same
  `Process.sleep(5)` in `terminate/2`, same `async: true` concurrency.

  Five runs of the 80-case NEW-shape file: **0/80 failures every time (400/400 total,
  0 failures).**

**What this shows, stated without overclaiming (per the task's explicit instruction):**
this is evidence of **mechanism** — it demonstrates that the specific check-then-act
class ISS-0446 describes is real, reproduces reliably under concurrent scheduling
load with the *exact* pre-fix code shape and the *exact* CI stacktrace, and does not
reproduce at all (0/400) with the shipped fix's code shape under identical load. It is
**not** proof that the specific CI race, or races like it, can never recur in this
suite in general — different timing, different hardware, or an unrelated future change
elsewhere could still produce a superficially similar failure. The claim this evidence
supports is narrower and structural: the specific check-then-act pattern this issue
targeted has been removed, not merely made statistically less likely to lose.
