# Test Spec: ISS-0446 — throwaway-supervisor `on_exit` check-then-act teardown race

**Issue:** ISS-0446 — `service_task_dispatcher_test.exs`'s throwaway-supervisor
`on_exit` guard (`if Process.alive?(sup_pid), do: Supervisor.stop(sup_pid)`) is a
check-then-act race across a process boundary: `Process.alive?/1` can observe `true`
and the linked supervisor can still die mid-flight before `Supervisor.stop/1`'s
monitored call completes, making `Supervisor.stop/1` exit `{:shutdown, ...}` instead of
returning `:ok`. Fixed by ELIXIR-DEV (commit `414f0b26`) per
`lib/letflow/design/iss0446-throwaway-supervisor-teardown-race-fix.md` — the ad-hoc
`Supervisor.start_link/2` + `on_exit` guard is replaced entirely with
`ExUnit.fetch_test_supervisor/0` + `start_supervised!/1`, which has no
`Process.alive?` check anywhere in its teardown path (`ExUnit.OnExitHandler`'s
`terminate_supervisor/2` is a blocking `Process.monitor/1` + `receive {:DOWN, ...}`).

**Test tier:** structural/mechanism verification plus one committed regression test
(this is a MINOR test-infrastructure bug fix, not a `docs/requirements.yaml` REQ — no
formal acceptance criteria list; the implicit requirements are "the race is removed"
and "no test coverage is lost," both addressed below).

## Corrected mechanism: what actually makes the race reproduce

Independently re-verified (throwaway scripts, `elixir <script>.exs`, deleted after
use) before deciding anything:

- **`async: false`, no `trap_exit`, 20 sequential cases, `Process.sleep(5)` in
  `terminate/2`:** the race DOES reproduce sequentially — 5 runs of a 20-case module
  gave 0, 0, 1, 3, 1 failures. This already falsifies the original "zero across
  100+ async:false runs" claim; the original version's `async: false` attempts must
  have been tried only "one test at a time" (a single isolated test, re-run as a fresh
  process each time) rather than "many sequential tests inside one module, one BEAM
  VM" — the latter is what supplies the necessary condition, and the two are not the
  same experiment. The real necessary ingredient is **enough `on_exit`-driven
  supervisor start/stop cycles happening back-to-back inside one BEAM VM run** — not
  concurrent scheduler contention specifically. `async: true` is *a* sufficient way to
  supply that condition (many siblings' `on_exit` cycles overlapping), but so is a
  large-enough sequential batch in one module; `async: true` is not necessary.
- **Adding `Process.flag(:trap_exit, true)` to the child GenServer's `init/1` makes
  the race fully deterministic, not just more likely.** With `trap_exit` set, the
  child converts the incoming link-exit signal into a normal message and always
  actually executes its slow `terminate/2` body before dying — turning "the shutdown
  is sometimes slow enough to matter" into "the shutdown is always exactly this slow,"
  which removes the remaining randomness from *how wide* the window is (the remaining
  non-determinism, if any, is only in exactly when the `on_exit`-runner process's
  `Process.alive?/1` check lands relative to that now-fixed window). Measured: a
  SINGLE trap_exit test case, `async: false`, `Process.sleep(5)` in `terminate/2`,
  reproduced the old check-then-act shape's crash in **10/10 runs**, with the exact CI
  stacktrace (`GenServer.stop/3` → `:sys.terminate` → `EXIT shutdown`, through
  `on_exit_handler.ex:140`). The identical single-case harness run against the shipped
  fixed shape (`ExUnit.fetch_test_supervisor/0` + `start_supervised!/1`, no `on_exit`)
  passed **10/10 runs**, 0 failures. Wall time per run: well under 1 second.

**Is `trap_exit` still testing the same mechanism, or a different one?** The same one.
`trap_exit` does not change *what* races — it only removes a second source of
randomness (how long the child actually takes to die) so that the *one* race this
issue is about (the `on_exit` callback process's `Process.alive?/1` check racing the
link-exit signal's delivery to the supervisor) is isolated and exercised on every run
instead of only some. Without `trap_exit`, a non-trapping child's actual death can
itself be fast or slow depending on unrelated BEAM scheduling, adding noise on top of
the real race; `trap_exit` removes that noise. This is why the coordinator's
measurement and my own converged exactly (10/10 vs. their reported determinism) once
both used a trapping child, whereas the non-trapping 20-case version above still
showed run-to-run variance (0-3 out of 20).

## What is committed

Added one test to `test/letflow/engine/service_task_dispatcher_test.exs`, in the
existing `describe "boot gating"` block, immediately after the test ISS-0446's fix
already touches (line ~1113, "...independently startable as a real GenServer under a
throwaway supervisor"). A file-local helper module,
`Iss0446RegressionGuard.SlowTrapChild`, is defined at the bottom of the test file for
its exclusive use.

**Why this test, and not a synthetic re-enactment of the deleted old shape asserting
"the old shape crashes":** the coordinator's rework instruction asked this directly,
and it matters. A test built to assert that the *deleted* `Supervisor.start_link/2` +
`on_exit` pattern crashes would be testing ExUnit's/OTP's own `on_exit`-runner and
link-teardown behavior in the abstract — that pattern no longer exists anywhere in
this file for such a test to regress against, so it would prove nothing about
Letflow's own code going forward and would be manufactured busywork per this role's
own scope test. **The durable, Letflow-owned property worth guarding instead is: this
suite's own established fixture idiom for "start a throwaway child under an isolated
supervisor inside a test" — `ExUnit.fetch_test_supervisor/0` +
`start_supervised!/1`, with no `on_exit` callback — tears down cleanly even when a
child's shutdown is deliberately slow.** That is a property of *this test suite's own
chosen idiom* (used by the test directly above this one, and by
`test/letflow/admission_test.exs` and `test/letflow/scheduler/poller_test.exs`), not a
claim about ExUnit's public contract in the abstract. **Corrected per REVISION NOTE 2
above: this is a narrower claim than rework 1's version made.** It does NOT mean, and
must not be read as meaning, that this test catches a reintroduction of the
check-then-act pattern at the actual fix site (the test directly above it) — measured
false, see REVISION NOTE 2. The synthetic `SlowTrapChild` module is necessary despite
this framing: the real
`Letflow.Engine.ServiceTaskDispatcher.Poller` neither traps exits nor does slow work in
`terminate/2`, so it would not exercise the teardown window at all — this is exactly
why the test above it uses the real `Poller` for its own `which_children/1` proof,
while this new test uses a synthetic child for its different, timing-shaped proof. The
two tests are complementary, not redundant.

**Reliability, measured (not merely asserted):**
- The new test in isolation (`mix test ..._test.exs --only line:1136`): **5/5 runs**,
  0.4-0.5s each, all passed.
- The whole modified file (`mix test test/letflow/engine/service_task_dispatcher_test.exs`,
  43 tests total, real Postgres via `Letflow.DataCase`): **5/5 full-file runs**, 34.5s-38.4s
  each (dominated by the file's other DB-backed tests, not this one), all "43 passed",
  0 failures.
- Fail-first proof, performed **in the real shipped test file itself** (not a
  throwaway script), since the new test module did not exist pre-fix and WF-03's
  ordinary fail-then-pass shape needs a real discriminating run: temporarily replaced
  the new test's body with the exact deleted old shape (`Supervisor.start_link/2`,
  unnamed, + `on_exit(fn -> if Process.alive?(sup_pid), do: Supervisor.stop(sup_pid) end)`),
  using the same `SlowTrapChild` fixture — **5/5 mutant runs failed**, every time, with
  the exact CI stacktrace (`GenServer.stop/3` → `:sys.terminate` → `EXIT shutdown`,
  through `on_exit_handler.ex:140`). Reverted via a pristine backup copy;
  post-revert SHA256 of the file matched the pre-mutation SHA256 exactly
  (`e34091b81d3eddf01b11553eeee7574a0a464c47fa5a6e15391347c2da3fc3f4`); re-ran the full
  file post-revert (`43 passed`, 0 failures) to confirm the revert was clean, not just
  byte-identical.
- `mix letflow.check.test` (full suite, forces fresh warnings-as-errors recompile,
  checks for ISS-0069 dead-default-argument warnings): **`mix letflow.check.test: OK --
  no test failures, no ISS-0069 warnings.`** `Result: 3193 passed (6 properties, 3187
  tests), 21 excluded` — one more passed than the pre-existing 3192 baseline, matching
  exactly the one new test added. `Finished in 1609.7 seconds`.

**What this proves, and its limit, stated without overclaiming (corrected by REVISION
NOTE 2):** the new test reliably (10/10 pre-fix-shape-crashes, 10/10 fixed-shape-clean
during design verification; 5/5 + 5/5 in the shipped harness; 24 further clean

the exact check-then-act construct ISS-0446 removed — **when that construct is
reintroduced inside THIS test's own body, against its own synthetic fixture.** It does
NOT reliably discriminate that same construct being reintroduced at the actual
ISS-0446 fix site (the neighboring test) while this test is left alone — measured at
only ~13% (2/15, validator; 0/5, my own spot-check) detection via the original
