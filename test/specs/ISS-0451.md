# Test Spec: ISS-0451 — Bound a PERSISTENT Poller fault so it cannot exhaust the top-level `Letflow.Supervisor`'s own restart budget

**Issue:** `docs/issues/ISS-0451.yaml` — MAJOR, filed by REVIEWER while gating REQ-219
(`handoffs/WF02-REQ219-20260903/step-02d-reviewer.json`). REQ-219 already isolates a
*single* `Letflow.Supervisor.Pollers` budget-exhaustion event (proven by
`pollers_test.exs`'s own AC4 test — see `test/specs/REQ-219.md` item 5), but a
*persistent* (never-clearing) Poller fault re-exhausts that same budget again almost
immediately after every restart, and (per ISSUE-FIXER's live probe) cascades to take
down the whole application — `Letflow.Repo`, Bandit included — in well under one
second.

**Design doc:** `lib/letflow/design/iss0451-poller-crash-budget-isolation.md`
(rework iteration 3, CODE-DESIGN-VALIDATOR-approved at iteration 2, REVIEWER's own
iteration-3 note confirms no further production-code change was required).

**Test tier:** unit/integration against the real, application-supervised process tree
(`Process.monitor/1`, `Process.whereis/1`, `Supervisor.terminate_child/2` +
`Supervisor.start_child/2`) — no `Letflow.DataCase`/tenant fixture, since nothing here
touches `Letflow.Repo`'s row data, only its supervised process identity, same class as
`pollers_test.exs`.

**Test files:**
* `test/letflow/supervisor/pollers_breaker_test.exs` (new, TEST-DESIGNER, `async: false`)
* `test/letflow/supervisor/pollers_test.exs` (existing AC4 test, already updated by
  ELIXIR-DEV per design §5's rework-iteration-3 procedure — verified below, not
  reauthored)

## Why mutation testing, not fail-then-pass against a pre-fix commit

`Letflow.Supervisor.PollersBreaker` is a **brand-new module** (added by this fix, not a
change to existing behavior) — per
`docs/agents/workflows/WF-03_issue_resolving.md`'s "When the pre-fix failure is 'the
code under test does not exist'" section, checking out the pre-fix commit and running
this new test would only ever produce `UndefinedFunctionError`/module-not-found for
every assertion, which proves the module is new and nothing about whether the test
discriminates a *correct* breaker implementation from a *wrong* one. That check was not
run for this reason; mutation testing (below) is the substitute the workflow doc
mandates for exactly this situation.

## Mutation testing

Both mutants were applied **in place** (technique 2 of the two the workflow doc
offers), each followed by a `git checkout --` revert and a re-run confirming both `git
status --porcelain lib/ test/` is empty and the test file re-runs green. A throwaway
`git worktree` (technique 1, preferred) was attempted first, but `_build`/`deps` do not
exist in a fresh worktree checkout and are gitignored — provisioning them from scratch
would require a `mix deps.get`/full recompile with no guarantee of network access in
this sandbox, so the in-place-and-revert technique was used instead, per the workflow
doc's own "or, if applied in place" alternative.

**Mutant 1 — remove the trip-threshold check (`lib/letflow/supervisor/pollers_breaker.ex`,
`handle_pollers_down/1`'s `:closed`-with-active-observation-timer clause).** Changed the
2nd-`:DOWN`-while-`:closed` branch from `trip_to_open(state)` to the same
restart-and-rearm-the-observation-timer behavior as the 1st-`:DOWN` branch — i.e. the
breaker never transitions to `:open` no matter how many times Pollers re-exhausts.

* Ran `mix test test/letflow/supervisor/pollers_breaker_test.exs` against the mutant.
* **Result: 0/1 passed.** The test's own `wait_for_breaker_open/1` poll (design §6.2
  step 4) timed out after 5 seconds and `assert wait_for_breaker_open(), "PollersBreaker
  did not reach :open within the timeout"` failed with exactly that message — the test
  is directly sensitive to the trip-threshold logic the mutant removed.
* Reverted via `git checkout -- lib/letflow/supervisor/pollers_breaker.ex`.
* Verified: `git status --porcelain` empty; re-ran
  `mix test test/letflow/supervisor/pollers_breaker_test.exs` — **1 passed**, 0
  failures.

**Mutant 2 — revert the `:temporary` child-spec change (`lib/letflow/application.ex`'s
children list).** Changed `Supervisor.child_spec(Letflow.Supervisor.Pollers, restart:
:temporary)` back to a bare `Letflow.Supervisor.Pollers` list entry — i.e. Pollers
reverts to the implicit `:permanent` default, restoring the top-level auto-restart path
`PollersBreaker`'s entire design exists to eliminate.

* Ran `mix test test/letflow/supervisor/pollers_breaker_test.exs` against the mutant.
* **Result: 0/1 passed.** The test's own trigger step (design §6.2 step 3 — the same
  `terminate_child/2` then `start_child/2` sequence `pollers_test.exs`'s own AC4 test
  and this design's mechanism both use) raised `** (CaseClauseError) no case clause
  matching: {:error, :already_present}` — because a `:permanent` child's spec is NOT
  deleted by `terminate_child/2` (only a `:temporary` child's is), so the subsequent
  `start_child/2` call for the same id fails differently than the `:temporary`-carrying
  code the test was written against. This is direct evidence the test's own restart
  mechanism (and, transitively, `PollersBreaker`'s identical `restart_pollers/0`
  private function) depends on the `:temporary` child-spec change specifically, not
  incidentally.
* Reverted via `git checkout -- lib/letflow/application.ex`.
* Verified: `git status --porcelain` empty; re-ran
  `mix test test/letflow/supervisor/pollers_test.exs test/letflow/supervisor/pollers_breaker_test.exs`
  — **5 passed**, 0 failures (both files together, confirming no cross-file
  interference from the revert).

## Verification of ELIXIR-DEV's existing AC4 update against design §5

Read `test/letflow/supervisor/pollers_test.exs`'s current `describe "AC4: crash-loop
isolation"` test (lines 85-157) against design doc §5's revised 9-step procedure
(rework iteration 3) line by line:

1. Captures `repo_pid_before`, `pollers_pid_before`, `infrastructure_pid_before` — matches.
2. Sets `:start_scheduler` and `:force_poller_crash` — matches.
3. Single trigger, `Supervisor.terminate_child/2` only, no test-issued `start_child/2`
   call — matches (§5 step 3's explicit "do NOT follow it with a test-issued
   `start_child/2` call").
4. `wait_for_breaker_restart/2` polls both `Process.whereis/1` for a new pid and
   `breaker_state() == :closed` together — matches §5 step 4 exactly.
5. Clears `:force_poller_crash` and restores `:start_scheduler` immediately after the
   wait succeeds — matches.
6. Asserts `Letflow.Repo`/`Letflow.Supervisor.Infrastructure` pids unchanged — matches.
7. New-pid assertions against the breaker-restarted pid (`!= nil`, `!= pollers_pid_before`)
   — matches.
8. New confirming assertion `breaker_state() == :closed` — matches (§5's own "cheap to
   add" step 8).
9. `on_exit` teardown restores env and calls the `start_child/2`-based `restart_pollers!/0`
   helper — matches, including the documented tolerance for
   `{:error, {:already_started, pid}}` from a breaker/test-teardown race (§5's "Second,
   previously-unflagged consequence" text).

**Confirmed: ELIXIR-DEV's existing update matches design §5's spec exactly** — no
further change to `pollers_test.exs` was needed for this step.
