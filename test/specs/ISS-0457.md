# Test Spec: ISS-0457 — `splice_top_level_status/2` first-match-wins on a duplicate

## top-level `status` key

**Issue:** ISS-0457 — the ISS-0442 raw-text scanner (`scan_for_status/4`) resolved a
duplicate depth-1 `"status"` key by keeping the **last** match (`best` unconditionally
overwritten on every depth-1 match), while `autofix_file/1`'s decision logic
(`Jason.decode(raw)` then `Map.get(data, "status")`) is driven by `Jason.decode/1`'s own
**first**-key-wins duplicate-key resolution (confirmed against the pinned `jason 1.4.5`:
`Jason.decode!(~s({"status":"a","status":"b"}))` → `%{"status" => "a"}`). On a
duplicate-top-level-`status` document the two mechanisms disagreed on which occurrence
is "the" status, so `--autofix` edited the wrong span: the FIRST occurrence — the one
`autofix_file/1` actually reasoned about — was left byte-identical (an illegal,
non-`@legal_statuses` value) while the tool reported `{:fixed, ...}` and the LAST
occurrence was rewritten instead. Fixed by ELIXIR-DEV per
`lib/letflow/design/iss0457-splice-first-wins.md` §2 (option (a), conditional
preservation shape (i)): `best` is now set exactly once, on the FIRST depth-1 `"status"`
match, and never overwritten by a later one.

**Run:** WF03-ISS0457-20260904, WF-03 Step 4. **Design:**
`lib/letflow/design/iss0457-splice-first-wins.md` §2. **Reviewer gate:**
`handoffs/WF03-ISS0457-20260904/step-03c-reviewer.json` (PASS).

**Code under test:** `scan_for_status/4` / `handle_string_token/5` in
`lib/mix/tasks/letflow.lint_handoffs.ex`, via the public `splice_top_level_status/2` and
`LintHandoffs.run/1 --autofix` entry points. This is a change to **existing** behavior
(`scan_for_status/4` already existed and was last-match-wins from the ISS-0442 merge,
commit `373f5363`, onward) — not a from-scratch module — so per WF-03's ordinary rule
(not the "code under test does not exist" mutation clause), fail-first evidence here is
the **pre-fix commit itself**, checked out in a disposable worktree.

## AC1 — duplicate top-level `status` key: FIRST occurrence corrected, every LATER

## occurrence left byte-identical

**Criterion:** for a document with two depth-1 `"status"` keys mapping to different
`@autofix_map` entries (e.g. first `"DONE"`, second `"COMPLETE"`, both mapping to
`"COMPLETED"`), after `--autofix`: (a) the FIRST occurrence is rewritten to its mapped
value (`"COMPLETED"`), and (b) the SECOND (and every later) occurrence is left
byte-identical to its pre-fix value.

**Why this exists, not just what it restates:** this is the mirror image of
ISSUE-FIXER's originally demonstrated divergence
(`handoffs/WF03-ISS0457-20260904/diagnosis/divergence-probe-transcript.txt`): under the
pre-fix last-match-wins scanner, the SECOND occurrence got rewritten and the FIRST was
silently left as an illegal value while the tool claimed success. Asserting only "the
file now decodes to `status: COMPLETED`" would pass under EITHER selection rule (since
`Jason.decode/1` only ever sees one occurrence after a whole-file decode) and would not
distinguish first-wins from last-wins at all — the assertion has to inspect the RAW
bytes at both occurrence sites, not just the decoded map, to actually discriminate the
two behaviors. Two distinct `@autofix_map` source values (`"DONE"` and `"COMPLETE"`,
both from the fixture ISSUE-FIXER already produced) are used deliberately so the
divergence is visible in *which span* gets edited, not merely in the resulting value —
same technique ISS-0442's own `T-AUTOFIX-NESTED-STATUS-COLLISION-PASS-PASS` uses for the
same reason.

**Test case:** `T-AUTOFIX-DUP-TOP-LEVEL-STATUS-FIRST-WINS`
(`test/mix/tasks/letflow.lint_handoffs_test.exs`). Uses a fixture equivalent to
`handoffs/WF03-ISS0457-20260904/diagnosis/dup-status-fixture.json` (same shape: two
depth-1 `status` keys, `"DONE"` first and `"COMPLETE"` second, separated by an
unrelated field and a nested `result.status` so neither occurrence is adjacent or
mistaken for the nested one). Asserts:

1. The rewritten file decodes with top-level `"status" => "COMPLETED"` (`Jason.decode/1`
   only ever sees the first occurrence after a rewrite, so this alone is necessary but
   not sufficient — see (2)/(3)).
2. The RAW rewritten text contains the literal substring `"status": "COMPLETED"` at the
   position corresponding to the FIRST pre-fix occurrence (was `"DONE"`).
3. The RAW rewritten text still contains the literal substring `"status": "COMPLETE"`
   (unchanged) at the position corresponding to the SECOND pre-fix occurrence — proving
   it was left untouched, not merely that *some* occurrence still decodes usefully.
4. The whole rewritten file is byte-identical to a hand-computed `expected` string —
   the strongest form, proving the ONLY changed span anywhere in the file is the first
   occurrence's value token (same technique as ISS-0442's
   `T-AUTOFIX-NESTED-STATUS-COLLISION-PASS-PASS`).

**Fail-then-pass evidence:** checked out commit `373f5363` (`main`'s tip immediately
before this run's ELIXIR-DEV Step 3 change — the ISS-0442 merge commit, i.e. the last
commit carrying the last-match-wins scanner) into a disposable `git worktree`, copied
this test into that worktree's test file, ran it there: **FAILS** (old code rewrites the
SECOND occurrence, not the first). Ran the same test on this run's own branch
(`feature/WF03-ISS0457-20260904`): **PASSES**. Both real, unedited command outputs are
quoted in this test-designer's handoff `result.summary` — not asserted.
