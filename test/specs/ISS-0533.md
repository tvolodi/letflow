# Test Spec: ISS-0533 — Recursive metadata sanitization + level/message-preserving rescue in `Letflow.Obs.Logger`

**Issue:** ISS-0533, GH#1076 — `Letflow.Obs.Logger`'s JSON formatter (`safe_value/1`)
did not recurse into tuples/lists/maps, so metadata shaped like Bandit's
`plug: {Router, []}` or OTP's nested `error_logger.report_cb` function reference
either crashed `Jason.encode!/1` or fell through to `encode_entry/3`'s `rescue`
branch, which then hardcoded `"level" => "error"` and discarded the real message —
burying genuinely important log content (e.g. a real startup-crash message) behind a
synthetic "log encoding failed" string.

**Run:** WF03-ISS0533-20260908, WF-03 Step 4. **Design:**
`lib/letflow/design/iss0533-log-formatter-safe-value-recursion.md` (§1 recursive
`safe_value/2`, §1.1 tuple/struct wholesale-inspect rule, §1.2 `@max_sanitize_depth 6`
work-bound, §2 rescue-branch fix). Implementation commit: `d985d626`
(`fix(ISS-0533): recursive metadata sanitization + level/message-preserving log
rescue`). REVIEWER already PASSed this commit on this branch (not a tenant-data path,
SECURITY-REVIEWER correctly skipped).

**Code under test:** `lib/letflow/obs/logger.ex` — `safe_value/1,2` (new recursive
worker + `safe_leaf/1` + corrected `jason_encodable?/1`), `encode_entry/3`'s `rescue`
branch.

**Why this is an existing-behavior fix, not a wholly-new-module case:** both
`safe_value/1` and `encode_entry/3`'s `rescue` branch existed before `d985d626` — the
fix rewrites their bodies, it does not create new code from nothing. The ordinary
WF-03 fail-then-pass-against-the-pre-fix-commit proof applies (see "Fail-then-pass
proof" below); the mutation-testing addendum is not required.

## AC1 — Bandit-style tuple metadata does not crash; real level preserved; whole-tuple inspect

**Criterion (design §1.1):** a tuple anywhere in metadata (e.g. `plug: {Router, []}`)
is never decomposed element-by-element into a JSON array; it is replaced wholesale by
`inspect/1` of itself, and the log call succeeds with the entry's real level, not a
crash or a force-promoted `"error"`.

**Why this exists, not just what it restates:** this is the issue's own primary
reproduction (a real Bandit/Plug router-config tuple landing in metadata on every
request). A test that only checked "does not raise" would miss the pre-fix bug's
second failure mode — a crash caught by the rescue branch, which hardcoded the level
to `"error"` regardless of what the real event level was. Asserting both `decoded["level"]`
and the exact inspected string form (not just "some string appeared") closes both gaps.

**Test case:** `test/letflow/obs/logger_test.exs`, `"ISS-0533 AC1: Bandit-style tuple
metadata does not raise; real level preserved; tuple inspected wholesale"` — metadata
`%{plug: {Letflow.Obs.LoggerTest.FunRefTarget, []}}` at level `:info`; asserts
`decoded["level"] == "info"`, `decoded["message"]` unchanged, and
`decoded["plug"] == "{Letflow.Obs.LoggerTest.FunRefTarget, []}"`.

## AC2 — nested function-reference metadata (OTP `report_cb` shape) is sanitized in place

**Criterion (design §1.1, §1.3):** a function reference nested one level inside
metadata (`%{error_logger: %{report_cb: &Mod.fun/1}}`, the OTP crash/shutdown-report
shape named in the issue) is sanitized to its inspected string form at the position
where it's found — not dropped, not left raw, not crashing the whole entry.

**Why this exists, not just what it restates:** this is the issue's second confirmed
reproduction and is the one case that specifically exercises map-value recursion
(`safe_value/2`'s `is_map` clause) rather than the top-level-only pre-fix behavior — a
fix that only handled top-level pids/refs/funs/ports/tuples (as the pre-fix code
already did) but never actually recursed into nested maps would still fail this test.

**Test case:** `test/letflow/obs/logger_test.exs`, `"ISS-0533 AC2: nested
function-reference metadata (OTP report_cb shape) does not raise; sanitized in place"`
— asserts `decoded["level"] == "warn"`, `decoded["message"]` unchanged, and
`decoded["error_logger"]["report_cb"]` is a string containing
`"FunRefTarget.some_fun/1"`.

## AC3 — depth-limit behavior at and beyond `@max_sanitize_depth` (6)

**Criterion (design §1.2):** recursion is work-bounded at 6 levels; behavior at and
past that boundary must not crash and must not silently lose the real level/message.

**Why this exists, not just what it restates, and a note on what was actually
verified (not assumed) about the boundary's exact shape:** the design doc states the
cutoff behavior as "the remaining sub-term ... is replaced wholesale by `inspect/1` of
itself." Before writing these tests, that claim was checked against the real running
code (`mix run` probes, not read-and-assumed) using `build_nested/2` to place a `pid`
at controlled depths. The **verified actual behavior** is more precise than the design
prose: `safe_value(v, 0)` matches unconditionally on the literal depth `0`, before any
`is_map`/`is_list`/`is_tuple` guard is consulted, and hands off to `safe_leaf/1`.
`safe_leaf/1` inspects pid/reference/function/port/tuple/encoder-less-struct — so a
*non-container* value landing exactly at the cutoff is correctly wholesale-inspected,
matching the design's intent precisely. But a *container* (map/list) still present at
the cutoff is NOT itself inspected — `safe_leaf/1`'s catch-all clause returns it
unchanged, raw, with whatever unsanitized values it still contains further inside. This
is a real, verified discrepancy between the design doc's prose and the shipped code's
literal behavior (not a defect these tests paper over — see "Note for REVIEWER/OQ"
below); these tests assert the **real, observed** behavior rather than the design
doc's literal wording, per this workflow's own instruction to "assert on the actual
behavior."

Two sub-cases, both empirically probed first:
- A `pid` placed by exactly 6 `%{next: ...}` wrappings (`build_nested(6, pid)`) is
  reached exactly when the recursion budget hits 0 — **verified sanitized** (inspected
  string), proving the boundary is inclusive, not off-by-one.
- A `pid` placed by 7 wrappings (`build_nested(7, pid)`, one level past budget) is
  **verified NOT sanitized** — the raw pid survives inside the untouched innermost
  map, which then makes `Jason.encode!/1` raise downstream in `encode_entry/3`, which
  is caught by the rescue branch (AC4). The formatter still does not crash and the
  real level/message still come through — the work-bound's actual safety property
  ("never crash the caller, never force-promote the level") holds even though the
  literal "wholesale inspect at the cutoff" mechanism only applies to non-container
  leaves, not to a container still present at the cutoff.

**Test cases:** `test/letflow/obs/logger_test.exs`:
- `"ISS-0533 AC3: a value exactly at @max_sanitize_depth (6 levels) is still
  sanitized"` — asserts no `metadata_encode_error` key and the pid is found sanitized
  at `get_in(decoded, ["deep", "next", "next", "next", "next", "next", "next"])`.
- `"ISS-0533 AC3: a value one level beyond @max_sanitize_depth is left unsanitized at
  the cutoff (not crashed, not silently dropped) — real level/message still
  preserved"` — asserts `decoded["level"]`/`decoded["message"]` are the real values,
  not crashed, not force-promoted.

**Note for REVIEWER/future work (not silently resolved here):** the depth-0 clause
order (`safe_value(v, 0)` matching before any container-type guard) means a
container — not just a non-container leaf — can still reach the cutoff unsanitized.
Whether that's worth tightening (e.g. having the depth-0 clause dispatch to the same
container-then-leaf logic as the depth>0 clauses, just without decrementing further)
is a design question, not something these regression tests silently patch around;
flagged here explicitly so it's visible at TEST-DESIGN-VALIDATOR and beyond rather than
buried in a comment only.

## AC4 — rescue-branch fallback preserves the real level/message, replaces only metadata

**Criterion (design §2.2):** on any encode failure the `rescue` branch preserves
`base` (`timestamp`/`level`/`trace_id`/`component`/`message`, all pre-computed,
always-safe binaries) verbatim and replaces only the `additional` metadata portion
with a diagnostic fallback — never hardcoding `"level" => "error"` or overwriting
`message` with a synthetic "log encoding failed" string (the pre-fix bug, and the
literal defect ISS-0533 reports).

**Why this exists, not just what it restates, and why no mock/test-double was
needed:** the task brief suggested a synthetic non-finite-float or mocked encode
failure if no real path was reachable. One *is* reachable and was verified directly:
the AC3 depth-exceeded case (a raw `pid` surviving past the sanitization cutoff inside
an otherwise-untouched container) is a genuine, real trigger for `Jason.encode!/1` to
raise inside `encode_entry/3` — so this test exercises the actual rescue branch via
actual code, not a double standing in for a path that's otherwise unreachable. This is
more honest coverage than mocking a seam.

**Test case:** `test/letflow/obs/logger_test.exs`, `"ISS-0533 AC4: encode_entry/3's
rescue branch preserves the real level/message and only replaces the metadata
portion"` — level `:warning`, message `"rescue branch real message"`, metadata
containing a pid 7 levels deep (past the cutoff, per AC3). Asserts
`decoded["level"] == "warn"` (not hardcoded `"error"`), `decoded["message"]` is the
real message (not a synthetic "log encoding failed" string), `component` is non-blank,
`"metadata_encode_error"` is present (the diagnostic marker fired), and the original
`"deep"` metadata key is absent from the fallback output (only the diagnostic
replacement appears, not the raw unencodable value).
