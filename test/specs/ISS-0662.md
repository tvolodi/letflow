# Test Spec: ISS-0662 — real trusted click freezes EntityCrudPage's renderer

**Issue:** `docs/issues/ISS-0662.yaml`. **Design:**
`docs/frontend/iss-0662-entity-crud-page-click-freeze-fix.md`. **Fix:** commit
`14b04903` (`deferClickState`, applied to `EntityCrudPage.tsx` and
`DataTable.tsx`) plus follow-up commit `0bf883fc` (double-submit race guard in
`confirmDelete`), both on `issue/ISS-0662-20260914`.

## Criterion

Per ISSUE-FIXER's diagnosis and the design doc's §0/§6 acceptance-criteria table, a
REAL, UA-trusted click (or keyboard activation) on any of the following must
**not** freeze the browser tab's main thread, and must produce the correct
resulting UI state:

1. `entity-create-action` — opens the create modal (`entity-form-modal`).
2. `EntityRecordForm`'s Cancel button (inside the create/edit modal) — closes
   the modal.
3. A row's `entity-delete-*` action — opens `ConfirmDialog` (`confirm-dialog`).
4. `DataTable`'s sortable column header (`datatable-header-<field>`) — applies
   sorting (`datatable-sort-indicator-<field>` appears).
5. (Design doc §3.3, commit `0bf883fc`, SECURITY-REVIEWER's PASS-WITH-NOTES) a
   rapid real double-click on `ConfirmDialog`'s confirm button, once the
   `deferClickState` fix widened the click-to-mutate window to a full
   macrotask, must fire **exactly one** DELETE request for the record, not
   two.

A "hangs forever" bug could produce a false pass if a test only checks for
absence of a Playwright timeout without checking the resulting UI state
actually appeared (the fix could silently swallow the deferred update) — every
test below pairs a bounded-time assertion with an assertion on the real
resulting state.

## Test case: `web/tests/e2e/iss-0662-entity-crud-click-freeze.e2e.spec.ts`

**Why these specific test cases (not just a restatement of the criteria):**

- **TC-ISS-0662-01/02/03/04** each drive a REAL trusted gesture — `hover()` +
  `page.mouse.down()` + `page.mouse.up()`, exactly the mechanism the design
  doc's own tests 1-13 used to isolate the bug — NOT `Locator.dispatchEvent`,
  which never reproduced the freeze at all (ISSUE-FIXER's own finding), and
  not a bare `Locator.click()` for the assertion under test, whose built-in
  actionability-retry machinery makes it hard to bound a hang to a tight,
  diagnostic timeout distinct from Playwright's own (much longer) defaults.
  Each races the real `mouse.up()` call against an explicit 5000ms bound
  (`BOUND_MS`, well under Playwright's 30s default and comfortably above the
  ~1-2s this design's own tests measured post-fix), so a regression fails
  fast with a clear "froze the renderer" message instead of a generic
  30-45s Playwright timeout.
- Four separate action types are covered, not just the two the original
  filing named (create + Cancel) — the design doc's own corrected scope
  (ISSUE-FIXER's diagnosis) found the freeze on delete and on `DataTable`'s
  sort header too, and explicitly calls out that "the original filing's
  narrower framing under-covers what ISSUE-FIXER found" (design doc §4).
- **TC-ISS-0662-05** targets the second, narrower defect the deferral fix
  itself introduced (SECURITY-REVIEWER's PASS-WITH-NOTES on commit
  `14b04903`, closed by `0bf883fc`): deferring `confirmDelete`'s
  `deleteMutation.mutate()` call by one macrotask widened the window in which
  a second click/Enter on the still-enabled confirm button could schedule a
  duplicate delete for the same record. This is a distinct trap from the
  freeze itself — a fix that defers correctly but with no re-entrancy guard
  would still freeze-test-clean while double-submitting — so it needs its
  own test, driving two real trusted clicks back-to-back (`mouse.down()` /
  `mouse.up()` twice, no synthetic delay) and counting real DELETE requests
  via a `page.on('request', ...)` listener, not a mocked/stubbed count.
- Every test also asserts the correct **end state**, not merely that the
  click resolved: `entity-form-modal` visible/not-visible, `confirm-dialog`
  visible, `datatable-sort-indicator-name` visible, exactly one DELETE
  request. This guards specifically against a "resolves fast but the
  deferred state update is silently dropped" regression, which a
  bounded-timeout-only assertion would not catch.
- `TC-ISS-0662-02` and `-05` use `trustedClickBounded` (not a bare `.click()`)
  for their own setup click too, since that setup step (`entity-create-action`
  / `entity-delete-*`) is itself one of the frozen paths — using a bare
  `.click()` there was tried first and produced a real, but less diagnostic,
  failure (Playwright's own "Test timeout of 45000ms exceeded" instead of
  this file's own bounded error) against pre-fix code; see the fail-then-pass
  proof below for both the before and after form of that fix.

## Fail-then-pass proof

This is a fix to EXISTING, already-shipped behavior (`EntityCrudPage.tsx` and
`DataTable.tsx` predate this fix by several requirements) — the
does-not-exist/mutation fallback in WF-03 Step 4 does not apply; a direct
fail-then-pass against pre-fix code is required and was performed.

**Pre-fix commit tested:** `a88fc67b` (`14b04903^`, i.e. `HEAD` immediately
before either ISS-0662 fix commit landed — the tip of `docs(ISS-0662): record
diagnosis, correct scope and severity to MAJOR`, still carrying the
unmodified `EntityCrudPage.tsx`/`DataTable.tsx`).

**Verification performed (this run, `issue/ISS-0662-20260914`, TEST-DESIGNER):**

1. Created a throwaway `git worktree` at `a88fc67b`, symlinked `node_modules`
   from the primary checkout (no reinstall), and copied *only* the new spec
   file into it — nothing else from the fix commits. Ran, against the same
   live dev backend (`:4000`) and Keycloak/Postgres already running for this
   session, on an isolated dev-server port (`E2E_BASE_URL=http://127.0.0.1:4174`)
   so it did not collide with the primary checkout's own `:4173` server:

   ```
   NODE_OPTIONS=--dns-result-order=ipv4first E2E_BASE_URL=http://127.0.0.1:4174 \
     npx playwright test tests/e2e/iss-0662-entity-crud-click-freeze.e2e.spec.ts --reporter=list
   ```

   Result: **5 failed (5)**, each ~17s (the bounded-click race resolving
   after the intended 5000ms, plus Playwright's own retry/actionability
   overhead around it — not the 45s test-level timeout):

   - `TC-ISS-0662-01`: `Error: ISS-0662 regression: trusted click on
     "entity-create-action" did not resolve within 5000ms (froze the
     renderer)`
   - `TC-ISS-0662-02`: `Error: ISS-0662 regression: trusted click on
     "entity-create-action (setup)" did not resolve within 5000ms (froze the
     renderer)`
   - `TC-ISS-0662-03`: `Error: ISS-0662 regression: trusted click on
     "entity-delete-<record-id>" did not resolve within 5000ms (froze the
     renderer)`
   - `TC-ISS-0662-04`: `Error: ISS-0662 regression: trusted click on
     "datatable-header-name" did not resolve within 5000ms (froze the
     renderer)`
   - `TC-ISS-0662-05`: `Error: ISS-0662 regression: trusted click on
     "entity-delete-<record-id> (setup)" did not resolve within 5000ms (froze
     the renderer)`

   (An earlier pass of this same verification, before `TC-ISS-0662-02`/`-05`
   were switched from a bare `.click()` to `trustedClickBounded` for their
   own setup step, reproduced the same underlying freeze but surfaced it as
   Playwright's own `Test timeout of 45000ms exceeded` on those two tests
   instead of this file's bounded message — still a genuine failure, but a
   less diagnostic one. Both forms are real evidence the pre-fix tree
   freezes on these actions; the file was tightened afterward for uniformity
   and to avoid ever depending on Playwright's own test-level timeout.)

   The worktree was removed after the run (`git worktree remove --force
   .../iss0662-prefix-wt`); `git worktree list` and `git status --porcelain`
   in the primary checkout confirm no residue (see below).

2. Ran the same, now-tightened spec file against the tip of
   `issue/ISS-0662-20260914` (commit `0bf883fc`, both fix commits present):

   ```
   NODE_OPTIONS=--dns-result-order=ipv4first npx playwright test \
     tests/e2e/iss-0662-entity-crud-click-freeze.e2e.spec.ts --reporter=list
   ```

   Result: **5 passed (5)**, ~1.0-1.8s each.

This satisfies WF-03 Step 4's fail-then-pass requirement: the same test file
(after the setup-click tightening described above, itself verified fail then
pass in its final form) fails against pre-fix code for the stated reason and
passes against post-fix code.
