# Test Spec: ISS-0694 — bilimbagaEntities test exclusion set omitted `certificate`

**Issue:** ISS-0694. **Run:** `WF03-ISS0694-20260916`, WF-03 Step 4.
**Fix under test:** `web/src/config/__tests__/bilimbagaEntities.test.ts` — commit

## Criterion

The ISS-0655 regression test (`bilimbagaEntities.test.ts`) asserts that every
admin-manageable pack entity type under `priv/packs/bilimbaga/entity_definitions/` has
a corresponding `BILIMBAGA_ENTITY_TYPES` wiring entry, excluding a hand-maintained set
of types with no admin-authoring path. Pre-fix, that exclusion set
(`RUNTIME_STATE_ENTITY_TYPES`) named only the five runtime-state satellite types
(`session`, `session_answer`, `session_event`, `session_question`,
`session_question_score`). It did not name `certificate` — a REQ-355 pack entity type
that is legitimately absent from `BILIMBAGA_ENTITY_TYPES` for an unrelated reason (its
own admin-authoring route is deliberately deferred, not an architectural runtime-state
fact) — so the test's own second `it` block failed against real, correct production
code: a false positive in the test itself, not a real regression of ISS-0655's tag-drop
bug.

Post-fix, the set is renamed `NO_ADMIN_AUTHORING_ENTITY_TYPES`, `certificate` is added
to it, and both prose comment blocks are rewritten to name both exclusion reasons
(runtime-state vs. deferred-by-requirement-scope) accurately.

## Why no separate test file was written

This fix's entire logic lives inside the test file itself — there is no separate
production module encoding "certificate is excluded because REQ-355 defers its
admin-authoring route." The modified test file *is* the regression artifact: its
before/after state is the fail-then-pass proof, and the existing second `it` block
(`'every admin-manageable pack entity type has a BILIMBAGA_ENTITY_TYPES entry'`) already
self-guards against the exact regression — if `certificate` (or any future entry) were
removed from `NO_ADMIN_AUTHORING_ENTITY_TYPES` without a matching removal from the real
pack directory, that same assertion goes red again, which is exactly what step 1 below
demonstrates by directly reproducing it. Writing an additional, separate test would only
re-assert the same array-membership check the existing test already makes — redundant
coverage of the same fact via the same mechanism, not a new guarantee.

This is **not** a "pre-fix failure is that the code under test did not exist" case
(WF-03's mutation-testing fallback): `bilimbagaEntities.ts`, `BILIMBAGA_ENTITY_TYPES`,
and `certificate.json` all pre-existed the fix and were unchanged by it. The pre-fix
failure is a real, reproducible `AssertionError` against the then-current test logic,
so the ordinary fail-then-pass proof (verified independently below, not merely trusted
from ISSUE-FIXER/FRONTEND-DEV's reports) is sufficient and the mutation-evidence
requirement does not apply.

**Decision: no additional test file is warranted.** The modified
`bilimbagaEntities.test.ts` is sufficient coverage on its own.
