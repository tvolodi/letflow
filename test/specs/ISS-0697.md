# Test Spec: ISS-0697 — injectable executable resolver removes the PATH-mutation TOCTOU race in `mix letflow.check.test`'s own test suite

**Issue:** `docs/issues/ISS-0697.yaml`. **Design:**
`lib/letflow/design/iss0697-check-test-executable-resolver-fix.md`. **Fix:**
`lib/mix/tasks/letflow.check.test.ex` (new `resolve_executable/1` seam reading
Application env `{:letflow, :check_test_executable_resolver}`, three call sites
rewired through it) + `test/mix/tasks/letflow_check_test_test.exs`
(`install_executable_resolver/2`, renamed from `activate_fake_bin_dir/2`, stops
mutating real `PATH` entirely), commit `543205c7`.

## Criterion (design doc's Acceptance criteria, items 2 and 3)

1. A real (non-test) `mix letflow.check.test` invocation stays byte-for-byte
   unaffected by the seam (the Application env key defaults to real
   `System.find_executable/1` when unset).
2. `test/mix/tasks/letflow_check_test_test.exs` never mutates real `PATH` again
   (grep-checkable) — the hazard *mechanism*, not merely one symptom of it, is gone.
3. An unmapped/unfaked executable name must not silently fall through to a real
   `System.find_executable/1` search — it must resolve to `nil` and fail loudly via
   `stream_and_capture/2`'s own `"executable not found"` raise.

The actual TOCTOU race itself (a *different*, concurrently-scheduled `async: true`
test winning a race on real, OS-process-global `PATH` between this file's two
`System.find_executable("bash")` calls) is inherently non-deterministic — it depends
on BEAM scheduling — so it cannot be literally reproduced on demand. Instead, these
three new tests deterministically prove the *root cause is structurally removed*:
resolution no longer consults real `PATH` at all, so no scheduling outcome can ever
make it pick up a real executable.

## Test cases: `test/mix/tasks/letflow_check_test_test.exs` — describe "ISS-0697 regression: resolver seam immune to real PATH mutation"

**Why these tests exist (not just a restatement of the criteria):**

### 1. `"run/1 succeeds via the override even when real PATH is mutated (prepended) afterward, never touching the PATH-prepended trap"`

Directly simulates the worst case of the actual race: real `PATH` is mutated
**after** `install_executable_resolver/2` has already installed the override but
**before** `run/1` does its own resolution/spawning — exactly the TOCTOU window
ISS-0697 diagnosed, collapsed into one deterministic sequence instead of depending on
scheduling luck. `run/1` is driven to real completion (`== :ok`) and the captured
output is asserted to show the normal success path, proving the mutation had zero
effect.

Uses a **trap directory** (`install_path_trap/2`, fake `bash`/`mix` that exit `97`
and print a distinctive `"TRAP-CONSULTED-REAL-PATH"` marker) prepended onto the real
`PATH`, rather than either (a) leaving real `PATH` untouched (wouldn't test
anything — the hazard is specifically about `PATH` *changing* underneath the
resolver) or (b) replacing `PATH` outright with total garbage. (b) was tried first
and rejected for two independent reasons, both confirmed live during test
development: it broke the Windows `mix.bat` fixture's own internal use of `findstr`
(a real Windows tool the fixture needs from `PATH` to dispatch on argv shape — an
artifact of the test harness, not of the code under test, so failing on it would be a
false signal), and — more importantly — if real `PATH` search *were* still consulted
(the exact regression this test exists to catch), wiping `PATH` outright would also
hide the real `bash`/`mix` from the *pre-fix* mechanism, silently masking the
recursion hazard instead of surfacing it loudly. The trap technique fixes both: real
`PATH`'s own entries (including the ones Windows tooling needs) stay intact, and if
resolution is ever again `PATH`-dependent, the trap shadows the real executables
first and fails **loudly** (`refute io =~ "TRAP-CONSULTED-REAL-PATH"` would catch it)
without ever reaching a real `bash`/`scripts/test_parallel.sh` invocation.

### 2. `"install_executable_resolver/2 never mutates real PATH (hazard mechanism itself is gone)"`

Captures `System.get_env("PATH")` immediately before and after calling
`install_executable_resolver/2`, and asserts byte-for-byte equality. This is the
direct, minimal proof of design-doc criterion 2 above: the hazard's own mechanism
(a `System.put_env("PATH", ...)` call inside the installer) is gone, not merely
avoided by convention or masked by a passing higher-level test.

### 3. `"an unmapped executable name resolves to nil, not a silent fallback to real PATH search"`

Reads the installed resolver function back out of
`Application.get_env(:letflow, :check_test_executable_resolver)` and calls it
directly with a name that was never faked, asserting `nil`. This is deliberately
**not** driven through `run/1` (which would, correctly but riskily for a proof step,
end up invoking whatever *real* executable this host's real `PATH` actually resolves
that name to, if this "no fallback" invariant ever regressed) — the direct call is
bounded, deterministic, and spawns no subprocess at all.

## Fail-then-pass verification (WF-03 regression-test requirement)

This is a behavioral fix to **existing** code (`System.find_executable/1` calls that
already existed in `letflow.check.test.ex` pre-ISS-0697, not a newly-created module),
so the standard fail-then-pass rule applies directly — the "pre-fix code does not
exist" mutant-testing carve-out (WF-03 §"When the pre-fix failure is 'the code under
test does not exist'") does not apply here.

**Pre-fix commit:** `67f642a6` (the commit immediately before `543205c7` on this
branch — confirmed via `git log --oneline` that `543205c7` is the sole ISS-0697 fix
commit and `67f642a6` is its direct parent). Verified using a throwaway `git worktree`
(`git worktree add ../letflow-iss0697-prefix-check 67f642a6`, removed afterward via
`git worktree remove --force`) so the working checkout was never mutated — the
worktree's own `test/mix/tasks/letflow_check_test_test.exs` had the same three new

attributable only to the mechanism under test. Deps/build were shared read-only from
the main checkout via `MIX_DEPS_PATH`/`MIX_BUILD_PATH` (no network access available;
