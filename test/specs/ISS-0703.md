# Test Spec: ISS-0703 — `Letflow.Oidc.TokenVerifier.Oidcc.verify_bearer_token/2` exception handling

**Issue:** ISS-0703 (WF-03), live-confirmed `CaseClauseError` at `jose_base64url.decode!/2`,
reached via `Oidcc.Token.validate_jwt/3`, propagating uncaught through the real adapter and
crossing `Letflow.Plugs.AuthPipeline.verify_token/1` to reach Bandit as a raw HTTP 500 with an
empty body.
**Design:** `lib/letflow/design/iss0703-oidc-verifier-exception-handling.md` (section 7 —
TEST-DESIGNER guidance — specifies exactly what this file must cover).
**Test tier:** unit (direct adapter call) + integration (full `AuthPipeline.call/2`), both
against the REAL `Letflow.Oidc.TokenVerifier.Oidcc` adapter, real Keycloak.
**Test file:** `test/letflow/integration/keycloak_auth_pipeline_test.exs` (existing file, one
new `describe` block added; no new file — see "Why this file, not a new one" below).
**Run:** `mix test --include keycloak test/letflow/integration/keycloak_auth_pipeline_test.exs`
(excluded from every default `mix test`/`mix letflow.check.test` invocation, same as the rest
of this file — `@moduletag :keycloak`).

## Why not `test/letflow/plugs/auth_pipeline_test.exs`

That file is configured (`config/test.exs`) against `Letflow.Oidc.TokenVerifierDouble` — a
string-equality stub that never touches real `oidcc`/`jose` parsing. It structurally cannot
exercise this defect or its fix: a malformed `raw_token` there is just a string that fails an
`==` comparison, never anything that reaches `jose_base64url.decode!/2`. This is exactly the
diagnosis's "why existing tests didn't catch it" finding. No change to that file.

## Why this file, not a new one

`test/letflow/integration/keycloak_auth_pipeline_test.exs` already runs its whole module
against the real Oidcc adapter (its own `setup` overrides `:token_verifier` to
`Letflow.Oidc.TokenVerifier.Oidcc` for every test) and already has the reachability probe,
tenant fixture, and `call_pipeline_with_token/1` conn-building helper this regression test
needs verbatim. Adding a `describe` block here reuses all of that instead of duplicating it in
a second file — matching the design doc §7's own instruction ("add to it rather than creating
a new file, unless TEST-DESIGNER finds a structural reason not to" — no such reason was found).

## Test cases

All four live in the new `describe "ISS-0703 regression — malformed raw_token never crashes
the real adapter"` block.

1. **Unit-level, JSON-blob fixture (the confirmed live trigger shape).**
   `verify_bearer_token/2 returns {:error, {:verifier_crashed, ...}} instead of raising, for a
   JSON-blob raw_token` calls `Letflow.Oidc.TokenVerifier.Oidcc.verify_bearer_token/2` directly
   with `raw_token = ~s({"access_token":"eyJhbGciOiJSUzI1NiJ9.not-a-real-jwt.sig",...})` — the
   exact shape that triggered the live incident (a caller accidentally sending a whole
   token-endpoint JSON response instead of just its `access_token` field) — against the real
   configured `provider_name` (`config :letflow, :oidc`'s `Letflow.Oidc.DefaultProvider`, whose
   reachability this file's `setup_all` has already proven). Asserts
   `{:error, {:verifier_crashed, %{kind: :error, classification: classification}}}` with
   `classification` an atom. Exists because this is the exact defect: on pre-fix code this call
   raises `CaseClauseError` and crashes the test process instead of returning a tuple — proven
   below under "Fail-then-pass proof."

2. **Unit-level, dotted-garbage fixture (breadth beyond the one confirmed shape).**
   Same assertion shape, `raw_token = "not-base64url.not-base64url.not-base64url"` — a
   deliberately dot-segmented (superficially JWT-shaped) string where every segment is
   non-base64url garbage. Exists to prove the fix isn't narrowly special-cased to the one JSON
   shape but covers the general "malformed segment reaches `jose_base64url.decode!/2`" failure
   class. **Fixture choice note:** an *undotted* plain-garbage string (e.g.
   `"not-base64url-at-all"`) was tried first and does **not** reach this crash chain at all —
   `oidcc`'s own earlier shape check rejects it with a normal `{:error, :no_matching_key}`
   without ever entering `verify_bearer_token/2`'s rescue/catch boundary (confirmed empirically:
   `mix run` probe against this branch's own code, see the "Fixture verification" note below).
   Using it would not be a fail-first fixture for this regression — it would already pass
   pre-fix — so the dotted, three-segment shape is used instead, confirmed to reach the same
   `jose_base64url.decode!/2` `CaseClauseError` chain as the JSON-blob fixture.

3. **Integration-level, JSON-blob fixture.** `AuthPipeline.call/2 rejects a JSON-blob bearer
   token with a clean 401, not a 500 crash` builds a `Plug.Conn` via this file's own
   `call_pipeline_with_token/1` helper with `Authorization: Bearer <json-blob fixture>` and
   drives it through the real, unmodified `Letflow.Plugs.AuthPipeline.call/2`. Asserts
   `conn.halted`, `conn.status == 401`, `content-type` header contains `application/json`, and
   body `%{"error" => "unauthorized", "detail" => "invalid or expired bearer token"}` — the
   pipeline's documented single-401-collapse shape (`auth_pipeline.ex:156-157`), proving the
   crash no longer reaches Bandit as a raw 500 with an empty body.

4. **Integration-level, dotted-garbage fixture.** Same assertion shape as case 3, with the
   dotted-garbage fixture from case 2.

**Explicit non-leakage assertion (SECURITY-REVIEWER's BLOCKER, design §3a), present in every
unit-level case (1 and 2):** for each fixture, a small set of representative substrings
(each >= 4 chars, hand-picked from the fixture's most distinctive content —
`@json_blob_substrings`/`@garbage_substrings`) is asserted absent from both (a) the returned
`classification` value converted to a string (`to_string/1`), and (b) the `Logger.warning/1`
output captured via `ExUnit.CaptureLog.capture_log/1` for that same call. This is the structural
property design §3a establishes: `classification` is built only from `exception.__struct__` (a
fixed atom naming the exception type) or a small fixed set of constant atoms — never from
`Exception.message/1`, `inspect/1`, or any other formatting of the caught value's content — so
it can never contain a `raw_token` fragment by construction. The test asserts this is actually
true for both fixtures used here, not just that the design intends it.

## Fixture verification (why the dotted-garbage string, not something else)

Ran a scratch probe (`mix run`, this branch's post-fix code) against five candidate `raw_token`
fixtures to find a genuine second fail-first case beyond the JSON blob:

```
result: {"json_blob", {:error, {:verifier_crashed, %{kind: :error, classification: CaseClauseError}}}}
result: {"garbage_plain", {:error, :no_matching_key}}
result: {"garbage_dotted", {:error, {:verifier_crashed, %{kind: :error, classification: CaseClauseError}}}}
result: {"garbage_two_dots_bad_chars", {:error, {:verifier_crashed, %{kind: :error, classification: CaseClauseError}}}}
result: {"single_word", {:error, :no_matching_key}}
```

`"garbage_dotted"` (`"not-base64url.not-base64url.not-base64url"`) reaches the rescue branch;
plain undotted strings do not (oidcc's own shape check short-circuits them into a normal,
already-non-crashing `{:error, reason}` even pre-fix). Chose `"garbage_dotted"` as the second
fixture specifically because it is a genuine second fail-first case, not merely "different
input that happens to also pass post-fix."

## Fail-then-pass proof (performed this run)

Per WF-03's regression-test discipline, all four new tests were run against the pre-fix
`oidcc.ex` (`git show main:lib/letflow/oidc/token_verifier/oidcc.ex`, temporarily swapped in
place of the fixed file, no `rescue`/`catch` clauses) and then against the post-fix file.

**Pre-fix run** (`MIX_ENV=test mix test --include keycloak
test/letflow/integration/keycloak_auth_pipeline_test.exs`): `Result: 3/7 passed`, `Failed: 4
tests` — all four new ISS-0703 tests failed, each with the exact `** (CaseClauseError) no case
clause matching:` crash propagating up through `jose_base64url.decode!/2` →
`oidcc_token.int_validate_jwt/4` → (for the integration cases) `auth_pipeline.ex:250` — i.e. the
process-crashing defect itself, reproduced live by the test. The three pre-existing tests in
this file (AC1/AC2/AC3) still passed, confirming the swap didn't break anything unrelated.

**Post-fix run** (fix restored, `git diff lib/letflow/oidc/token_verifier/oidcc.ex` empty):
`Result: 7 passed` — all four new tests plus all three pre-existing tests pass.

**Cleanup verified:** the temporary pre-fix swap was fully reverted; `git diff
lib/letflow/oidc/token_verifier/oidcc.ex` shows no changes and `git status --porcelain` shows
only `test/letflow/integration/keycloak_auth_pipeline_test.exs` and this spec file modified —
no stray `lib/` changes.
