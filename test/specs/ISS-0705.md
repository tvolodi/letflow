# Test spec: ISS-0705 — sandbox `:auto`-mode restore leak in `tenants_test.exs`

**Run:** WF03-ISS0705-20260917 · Step 4 (TEST-DESIGNER) · **Issue:**
`docs/issues/ISS-0705.yaml` · **Fix commits:** `9fcd5fcb` (initial wrap),
`5a8da536` (rework-1, adds the `on_exit/1` line this test guards).

## What the fix actually changed (and what it didn't)

`test/letflow/routers/tenants_test.exs`'s `"creates a tenant row, provisions a
real schema, and replays real migrations"` test used to flip
`Ecto.Adapters.SQL.Sandbox.mode(Letflow.Repo, :auto)` inline, with no restore
anywhere. The fix (§1 of
`lib/letflow/design/iss0705-sandbox-mode-restore-fix.md`) wraps the test body in
`Letflow.Test.SandboxAutoMode.provision!/2` (self-restoring, `try/after`) and
adds `SandboxAutoMode.enter_auto_mode!(Letflow.Repo)` as the first line of the
test's own `on_exit/1` cleanup callback.

**Important, empirically-verified correction to the task handoff's framing**
(`handoffs/WF03-ISS0705-20260917/step-04-test-designer.json`, which asked for a
test proving "the pool is left in `:auto` mode... vs. restored to `:manual`"):
that framing does not hold up under direct testing. Two independent
experiments — described below — showed the **global** `Ecto.Adapters.SQL.Sandbox`
mode ends up identical whether the true pre-ISS-0705 commit (`9fcd5fcb^`) or the
current fixed tip is used, for this test specifically. This is not a flaw in
the fix; it is `DBConnection.Ownership`'s own documented safety net:
*"a connection's mode reverts to `:manual` if its owner terminates"* (the exact
wording `DBConnection.OwnershipError` itself reports). `Letflow.DataCase`'s
standard `setup` (`Sandbox.checkout/1` + `Sandbox.mode(repo, {:shared, self()})`
for every non-async test) establishes owner-tracking on the test process
*before* the test body runs; when that process later exits — regardless of
what `Sandbox.mode/2` calls the test body itself made in between — the pool
auto-reverts to `:manual`. This masks the historically-real leak for any test
using `Letflow.DataCase`'s own setup, in both the pre-fix and post-fix code.

### Experiment 1 (informs the design above, not part of the shipped test)

A black-box probe (`Letflow.Routers.TenantsIss0705SandboxModeRegressionTest`,
first draft) ran an ordinary `Letflow.Repo.insert!/1` from a separate, unowned
`ExUnit.Case` module placed immediately after the provisioning test (same file,
so module-registration order is deterministic — see "Ordering pitfall" below).
Run against `9fcd5fcb^` (true pre-fix) and the fixed tip, **both** produced the
identical `DBConnection.OwnershipError` ("...mode reverts to :manual if its
owner terminates") after one retry past a transient `:exit` race. No
discriminating signal — this design was abandoned in favor of the one below.

### The actual, still-real hazard this test targets

`SandboxAutoMode.provision!/2`'s own `after`-block restore (mode `:manual` +
fresh checkout) runs **synchronously in the original test process**, the
instant the wrapped function returns — before the enclosing `test ... do`
block itself returns. Any `on_exit/1` callback *registered inside* that
wrapped function still only **runs** later, in a separate
`ExUnit.OnExitHandler` process, after the original test process has already
exited. So an `on_exit/1` callback that itself calls `Letflow.Repo` needs
`:auto` mode re-entered from *inside itself* (`SandboxAutoMode.enter_auto_mode!/1`)
— it cannot rely on `provision!/2`'s already-elapsed, already-superseded
restore. Skipping this raises `DBConnection.OwnershipError` from the
`OnExitHandler` process. This is not hypothetical: ELIXIR-DEV's own Step 3
attempt hit exactly this crash
(`handoffs/WF03-ISS0705-20260917/step-03-elixir-dev.json`), which rework-1
(`5a8da536`) fixed by adding the `enter_auto_mode!/1` line.

## The test

`Letflow.Routers.TenantsIss0705SandboxModeRegressionTest`
(`test/letflow/routers/tenants_test.exs`, appended directly below
`Letflow.Routers.TenantsTest` in the same file) reproduces this shape directly
and self-containedly — no dependency on `TenantsTest`'s own test or any
cross-test/cross-file ordering:

```elixir
tenant_id =
  SandboxAutoMode.provision!(Letflow.Repo, fn ->
    tenant = <ordinary Tenant insert via Repo>

    on_exit(fn ->
      SandboxAutoMode.enter_auto_mode!(Letflow.Repo)   # <- the fix
      Repo.delete_all(from(t in Tenant, where: t.id == ^tenant.id))
    end)

    tenant.id
  end)

assert is_binary(tenant_id)
```

If the `on_exit/1` callback's `Repo.delete_all/1` call raises, ExUnit reports
that as this test failing — which is the observable signal.

### Ordering pitfall found and avoided

An earlier draft placed this module in its **own separate file**. Cross-file
test-module registration order under `mix test` is **not** deterministic by
command-line argument order — it follows `Kernel.ParallelCompiler`'s
compilation-completion order (a scheduler race), confirmed empirically: an
otherwise-identical probe listed *second* on the command line ran *before*
`TenantsTest`'s provisioning test on one invocation. Also confirmed
empirically (`test/letflow/order_probe_test.exs`, a throwaway probe, not
committed): `async: true` cases always run to full completion before any
`async: false` case starts, in this project's ExUnit configuration — so an
`async: true` checker can never observe state left behind by a same-invocation
`async: false` test at all. The final design sidesteps both hazards by being
fully self-contained in one test (no cross-test dependency) — the safest
option, and also why it needed no `--seed 0` or multi-file invocation to be
meaningful.
