### 1. Do `assertBackendHealthy`/`assertServiceReadiness` need a focused unit test?

**Yes — added.** These are simple `GET` + throw-on-non-2xx wrappers, but they
are the entire fix: the exact defect (polling `/health/ready` instead of
`/health`) lives inside them, and `npm test` — the only suite CI actually
runs (`web/package.json`'s `"test"` script excludes `tests/e2e/**`) — had
zero prior coverage of them. Without a unit test, this fix's own regression
protection depends entirely on someone manually re-running Playwright against
a live backend, which is exactly the kind of check CI does not perform. This
codebase already has an established precedent for exactly this pattern:
`web/tests/unit/iss-0295-e2e-idp-config.test.ts` imports
`web/tests/e2e/helpers.ts` under vitest's `node` environment and asserts on
its exported behavior — no Playwright runtime needed, since the functions
only take an `APIRequestContext`-shaped object with a `.fetch(url)` method,
which is trivially mockable.

Added `web/tests/unit/iss-0706-e2e-health-precondition.test.ts`:
- **TC-1/TC-2** (`assertBackendHealthy`): resolves silently on a 2xx `GET
  ${apiBaseUrl}/health` response and never polls `/health/ready`; throws with
  the real status + URL on non-2xx.
- **TC-3/TC-4** (`assertServiceReadiness`): checks backend liveness first,
  then Keycloak discovery, resolving when both are healthy; short-circuits
  (propagating the backend's own error, never touching the Keycloak check —
  verified via the mock's call list) when the backend check throws; throws
  with a Keycloak-specific message when backend is healthy but Keycloak is
  not.
- **TC-5**: every one of the 10 files ISS-0706's own commit claims to have
  fixed imports `assertBackendHealthy`/`assertServiceReadiness` from
  `./helpers`, and none of them hardcodes a Letflow-backend `/health/ready`
  URL any more (Keycloak's own, legitimate `/health/ready` probes — e.g.
  `uat-tenant-url.e2e.spec.ts`'s `requireIdpReady` — are explicitly excluded
  from the check by variable-name context, not accidentally caught).
  Deliberately scoped to exactly these 10 files, not repo-wide — see item 3
  below for why.

### 2. Does `TC-TD-UI-01-04`'s hard-fail branch need more than the sibling-pattern proof?

**No new test added; sibling-pattern proof is the most practical here.**
Independently re-verified FRONTEND-DEV's claim by running the test for real
against a live local backend (`localhost:4000`) and Keycloak
(`localhost:8082`), both confirmed reachable:

```
$ BPM_TEST_URL=http://localhost:4000 BPM_IDP_BASE_URL=http://localhost:8082 \
  npx playwright test tests/e2e/tenant-dashboard.e2e.spec.ts -g "TC-TD-UI-01-04" --reporter=list

  ✘ TC-TD-UI-01-04: dashboard data tiles show only tenant-scoped results (763ms)

        at loginWithTenantToken (tests/e2e/tenant-dashboard.e2e.spec.ts:89:11)
  1 failed
```

The readiness precondition (`assertServiceReadiness`) passed cleanly — the
failure is further downstream, at `loginWithTenantToken`'s own tenant-slug
lookup, because this DB has no `default`/`swiftroute` tenant fixtures seeded.
This is the identical environment constraint TEST-DESIGNER hit on ISS-0702
(`test/reports/report-20260917-WF03-ISS0702-20260917.yaml`): the
`swiftroute`/`default` cross-tenant fixtures require running the full
`sim-company-onboarding.pipeline.e2e.spec.ts` onboarding pipeline first, which
is out of scope to provision here. The exact hard-fail branch
(`if (!swiftResp.ok()) throw ...`) is a one-off inline assertion in the test
body, not a reusable function, so it cannot be unit-tested in isolation
without a refactor CODE-DESIGNER never called for. The byte-identical
sibling pattern (`TC-TD-UI-03-01`, verified working against a real confirmed
404) remains the best available proof of the pattern's correctness in this
environment.
