### 1. Do `assertBackendHealthy`/`assertServiceReadiness` need new/changed unit coverage?

`web/tests/e2e/helpers.ts` is unchanged by this diff (confirmed via

is a pure *consumer*-side change: 9 files switch from a local, buggy
duplicate readiness check to calling the already-fixed, already-unit-tested
shared helper. The helper's own behavior — TC-1..TC-4 in
`web/tests/unit/iss-0706-e2e-health-precondition.test.ts` (2xx resolves,
non-2xx throws with real status+URL, backend-then-Keycloak ordering,

function behaves changed, only who calls it. Writing new tests against
unchanged function bodies would be manufactured busywork, not real
coverage.

What *does* need checking is the narrower question of whether each of the 9
call sites invokes the helper correctly (right arguments, no dangling

concern.

### 2. Does TC-5's scoped grep-regression need extending to the 9 new files?

**Yes — extended for real, not left as a "natural follow-up."** ISS-0707
itself exists because ISS-0706's original grep was scoped too narrowly
(flat `web/tests/e2e/*.ts`, not recursive into subdirectories) and silently
missed a real recurrence of the identical bug class. Leaving TC-5 scoped to
only the original 10 would reproduce that exact same category of blind
spot at the test level: a future PR that reintroduces a local
`/health/ready` duplicate in any of these 9 newly-fixed files (all of which
sit in subdirectories — `onboarding/`, `admin/`, `pipelines/` — precisely
the directories the original scope-gap missed) would sail through CI
undetected, for the same reason the bug went undetected in the first place.
This is a small, mechanical, already-proven-pattern addition, not new
design — exactly the kind of "legitimate small addition" the dispatch brief
allows for.

Extended `web/tests/unit/iss-0706-e2e-health-precondition.test.ts`:
- Split the file list into `ISS_0706_FIXED_FILES` (original 10, unchanged)
  and `ISS_0707_FIXED_FILES` (new 9, paths relative to `E2E_DIR` —
  `onboarding/onb-ui-01..04.e2e.spec.ts`, `admin/services.e2e.spec.ts`,
  `pipelines/{onboarding-wizard,sim-admin-processes,admin-user-lifecycle,
  sim-company-onboarding}.pipeline.e2e.spec.ts`), merged into `FIXED_FILES`
  (19 total). `platform-login-routing-by-role.pipeline.e2e.spec.ts` is
  deliberately excluded, matching `docs/issues/ISS-0707.yaml`'s own scope
  note: its `/health/ready` poll only `console.warn`s (non-blocking), not
  the same hard-fail bug.
- **Bug found and fixed while extending this:** the original TC-5 import
  check used `/from '\.\/helpers'/`, which only matches `'./helpers'`.
  ISS-0706's 10 files sit directly under `tests/e2e/` and do import from
  `'./helpers'`, so the original regex happened to work — but ISS-0707's 9
  files sit one directory deeper (`tests/e2e/onboarding/`, etc.) and
  correctly import from `'../helpers'`, which the old regex does not match.
  Left as-is, extending `FIXED_FILES` alone would have made TC-5
  permanently fail against *correct* code (a false positive on all 9 new
  files, forever) — not exercise real coverage. Fixed the regex to
  `/from '\.\.?\/helpers'/`, matching both `'./helpers'` and `'../helpers'`
  and verified in the same way as the rest of this fix (see Verification
  below): this alone was a real defect this coverage-assessment step
  caught, not something I merely asserted would work.
