## Bug summary

`GET /api/v1/tenants`'s real response envelope (`lib/letflow/api/pagination.ex`'s `Page`
struct, `@derive {Jason.Encoder, only: [:items, :next_cursor, :count]}`) has never sent a
`total` field — only `items`, `next_cursor`, `count` (`count` is `length(items)` for the
current page only). `web/src/api/tenants.ts`'s `TenantListResponse` type declared a
fictional `{ items, total, limit, offset }` shape; `PlatformDashboardPage.tsx`'s tile read
`.total ?? 0`, which was always `undefined`, so the fallback fired unconditionally and the
tile always rendered `0` regardless of real tenant count (confirmed live against QA: 2
real tenants, tile showed `0`). `TenantsPage.tsx` had the same latent defect in its
offset/`total`-based pagination math, not yet visibly broken only because the real tenant
count stayed under `PAGE_SIZE` (20).

Fix: `TenantListResponse` corrected to the real `{ items, next_cursor, count }` shape;
`PlatformDashboardPage.tsx` reads `count`; `TenantsPage.tsx` migrated to cursor-based
pagination (`cursorStack: string[]`, `PaginationControls totalItems={null}`), following
`AuditLogPage.tsx`'s established precedent for endpoints that cannot provide a cross-page
total.

## Additional gap analysis (this review — no new tests needed)

Per this run's task, checked four specific edge cases for a real, uncovered gap. None
found; reasoning recorded here rather than padding with low-value tests:

1. **Cursor stack reset on navigate-away-and-back.** `cursorStack` is plain
   `useState<string[]>([])` local to `TenantsPage`; React Router unmounts the component on
   navigation away and remounts fresh on return, which resets all local state including
   `cursorStack` by construction. There is no persistence mechanism (no URL param, no
   context, no module-level variable) that could make stale state survive a remount — this
   is not a testable gap, it's a property of `useState` itself, and adding a test for it
   would only assert on React's own remount semantics, not on any Letflow-authored logic.

2. **Search + pagination cursor-stack reset.** Already covered directly — see test case 4
   above (`TenantsPage.pagination.test.tsx`'s third test, "changing the search filter
   resets pagination to page 1"). It drives an actual page-2 navigation, then changes
   `tenants-search`, and asserts both the DOM (back to page-1 content, Previous disabled)
   and the exact cursor value sent on the next request (`undefined`). This is precisely the
   "stale cursor from a different search context" bug class named in this review's task —
   already closed, not a gap.

3. **Rapid double-click on Next.** Traced through the actual data flow:
   `TenantsPage`'s pagination block is gated by `{data && (...)}` (line 254 of
   `TenantsPage.tsx`), and the query has no `keepPreviousData`/`placeholderData` configured
   (confirmed via `grep -n "keepPreviousData\|placeholderData"` returning no matches in
   `TenantsPage.tsx`, `AuditLogPage.tsx`, or `tenants.ts`). TanStack Query's default
   behavior on a query-key change (new cursor) is to return `data: undefined` while the new
   page is in flight — so the entire pagination block, Next button included, unmounts
   during a real in-flight fetch, structurally preventing a second click from firing before
   the first one's cursor is applied. This is an existing, shared property of the
   `PaginationControls`/cursor-pagination pattern already in production use by
   `AuditLogPage.tsx` and `DlqPage.tsx`, not something ISS-0711's fix introduced or could
   regress independently — out of scope for this issue's regression coverage.

4. **`PlatformDashboardPage` zero-tenants tile (`count: 0`).** Checked whether this is
   distinguishable, as a regression test, from the bug itself. It is not: pre-fix code
   reads `.total`, which is `undefined` on every real response regardless of the real
   `count` value, so pre-fix code renders `'0'` for *any* real response — including one
   where the true count actually is `0`. A new test asserting `count: 0` renders `'0'`
   would pass against both the pre-fix buggy code and the post-fix correct code, so it adds
   no mutation-killing/regression-catching power beyond what TC-REQ369-03 (`37`) and
   TC-ISS0711-05 (`2`) already provide together (a mutant that reverts `count` to `total`,
   or that hardcodes any wrong constant other than `0`, is already caught by those two
   non-zero, differently-valued cases). Concluded this is a real, but non-regression,
   general-coverage nicety — not added, per this run's mandate to avoid padding with
   low-value tests when existing coverage is already adequate.
