# Test Spec: ISS-0721 — `Letflow.Entities.EventTypes.seed!/1` never wired into tenant provisioning

**Issue diagnosis:** `handoffs/WF03-ISS0721-20260919/step-01-issue-fixer-diagnosis.json`.
**Design:** `lib/letflow/design/iss0721-entity-event-type-seeding.md`. **Fix:**
`lib/letflow/tenant_provisioning.ex` (new private `maybe_seed_entity_event_types/2`,
wired as a second `:ok <-` clause in `replay_migrations/2`'s `with`-chain), commit
`c1d72550`.

## Criterion (from the design's §6)

A freshly-provisioned tenant, migrated only through `replay_migrations/2`'s default
manifest path (`using_default_manifest? == true`), must have the three
`ENTITY_RECORD_CREATED/UPDATED/DELETED` event types registered in its
`event_type_registry` as a side effect of provisioning alone — with **no** explicit,
manual call to `Letflow.Entities.EventTypes.seed!/1` anywhere in the test's own setup.
Before the fix, every call site of `seed!/1` outside `event_types.ex` itself was a
test fixture; production tenant provisioning never called it, so the first real
entity-record write against a freshly-provisioned tenant failed with
`{:error, :unknown_event_type}` via
`Letflow.EventStore.Registry.validate_payload/3`. The fix must also be idempotent: a
second `replay_migrations/2` call against an already-seeded tenant (simulating a
tenant re-migration) must not error, and writes must keep succeeding afterward.

## Test case: `test/letflow/tenant_provisioning/entity_event_type_seeding_test.exs`

**Why this test exists (not just a restatement of the criterion):** every other test
file in `test/letflow/tenant_provisioning/` and `test/letflow/entities/` (e.g.
`column_promotion_test.exs`, `constraint_fk_activation_test.exs`,
`test/letflow/entities/records_test.exs`) calls `EventTypes.seed!/1` manually inside
its own `provisioned_tenant/0` fixture, as established project convention before this
fix existed. Reusing any of those fixtures as-is would make the fix's effect
unobservable — the manual `seed!/1` call would mask whether `replay_migrations/2`
itself now seeds the event types. This file's fixture
(`provisioned_tenant_no_manual_seed/0`) is deliberately a copy of that same pattern
with the manual `seed!/1` line removed, so the only source of seeding left in the test
is whatever `replay_migrations/2` does on its own — the exact mechanism this
regression test must prove.

Two tests, per the design's §6 items 1-5:

1. **"the three ENTITY_RECORD_\* event types are registered as a side effect of
   provisioning alone"** — provisions a tenant via `provisioned_tenant_no_manual_seed/0`
   (which calls `provision_tenant_schema/1` then `replay_migrations/1` with no
   `migration_source`, i.e. the default-manifest path, and nothing else). Asserts
   `Letflow.EventStore.Registry.get_type/2` returns `{:ok, _}` for all three event
   type names (the registration-exists check), **and**, per the design's explicit
   instruction that this alone would be a weaker proof, drives real writes through the
   actual production path: `Letflow.Entities.Records.create_record/2`,
   `update_record/2`, and `delete_record/2` for a freshly created active definition,
   asserting each succeeds (`{:ok, %{record: _}}`, never `{:error, :unknown_event_type}`).
   All three entity-record commands are exercised because each appends a distinct
   event type (`ENTITY_RECORD_CREATED`/`UPDATED`/`DELETED`), and the pre-fix gap
   affected all three identically (the same missing `event_type_registry` rows).

2. **"a second replay_migrations/2 call against the same tenant does not error, and
   writes still succeed"** — provisions a tenant the same way, then calls
   `TenantProvisioning.replay_migrations(tenant_id)` a second time (simulating a
   tenant re-migration) and asserts `{:ok, _}`, then performs a real
   `Records.create_record/2` write and asserts it still succeeds. This exercises the
   design's §4 claim that `seed!/1`'s own internal `Enum.reduce_while/3` already
   tolerates `{:error, :duplicate_event_type_version}` per event type (folding it into
   `skipped` rather than halting), so `maybe_seed_entity_event_types/2` needs no extra
   idempotency handling of its own — a regression in that internal tolerance would
   surface here as either the second `replay_migrations/2` call itself erroring, or
   the subsequent write failing.

rule applies in its straightforward form, not the mutation-testing fallback for a
genuinely new module.
