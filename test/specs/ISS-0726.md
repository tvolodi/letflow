# Test Spec: ISS-0726 — OIDC hard-navigation path restore (`/exam` deep link)

**Issue:** `docs/issues/ISS-0726.yaml`.
**Design:** `lib/letflow/design/iss-0726-oidc-redirect-path-restore.md`.
**Fix commit:** `a9f27d26` on `feature/WF03-ISS0726-20260919`.
**Fix:** new `web/src/auth/safeRestorePath.ts` (`isSafeRestorePath`); `oidcRedirectArgs.ts`'s
`buildRedirectArgs()` gains an optional `capturePath` param and captures a validated
path as `state`; `ProtectedRoute.tsx` passes the current path at redirect time;
`OidcCallbackPage.tsx`'s post-login `navigate()` prefers a validated restored
`user.state` over the role-based fallback (including for `PLATFORM_ADMIN`).
**Test tier:** two-tier per the design doc §6 — Vitest unit (fast, isolated) +
Playwright e2e (real Keycloak round trip).

## Acceptance criteria and why each test case exists

| # | Criterion | Test case(s) | Why this case, not just a restatement |
|---|---|---|---|
| 1 | `isSafeRestorePath` accepts legitimate root-relative paths (with query/fragment) | `safeRestorePath.test.ts` "legitimate root-relative paths" block | Proves the validator isn't overly strict and would actually let real app navigation through — a validator that rejects everything passes trivially otherwise |
| 2 | Rejects protocol-relative (`//`) and backslash-normalized variants | "protocol-relative and scheme-embedded payloads" block, incl. `//evilhost` (no dot) | The no-dot case specifically isolates the item-4 protocol-relative check from the item-7 path-character-class check — a dotted host (`//evil.com`) would be caught by the character class alone even if item 4 were silently missing, which would leave a real gap (see mutant A below) undetected by a less careful suite |
| 3 | Rejects any embedded URL scheme (`javascript:`, `data:`, `https:`) anywhere in the string, not just at the start | "protocol-relative and scheme-embedded payloads" block | Covers both a bare scheme and a scheme buried inside a query string (`/x?to=javascript:alert(1)`), matching design §1.3 item 6's explicit "anywhere in the string" requirement |
| 4 | Rejects `..` path traversal and percent-encoded slash bypass attempts | "path traversal and encoding-bypass payloads" block | Design §1.4 states the path character class has no `.` or `%` at all, so traversal/encoding tricks are rejected as disallowed characters, not parsed-and-canonicalized — these cases prove that boundary directly |
| 5 | Rejects unicode homoglyph substitutions | "unicode homoglyph payloads" block | A Cyrillic lookalike or fullwidth solidus is not in `[A-Za-z0-9\-_/]`, so it's rejected by the same character-class mechanism — proves the validator doesn't special-case ASCII-looking-but-isn't input |
| 6 | Rejects injected markup/whitespace in query or fragment | "injected-markup payloads" block | Exercises design §1.3 item 8's RFC 3986-based query/fragment character class directly (`<`, `>`, `"`, backtick, raw space) |
| 7 | Oversized-string boundary is exactly 2048 chars, not approximate | "oversized string boundary" block: 2048 exact → true, 2049 → false | Design §1.3 item 2 states the boundary precisely; a fencepost error (`>=` vs `>`) is exactly the kind of bug a "roughly 2048" test would miss — this is confirmed as a real, catchable mutant (Mutant C below) |
| 8 | Non-string `value` is always rejected (type guard) | "non-string inputs" block | `user.state` is typed `unknown`; proves the guard actually narrows rather than assuming string-shaped input |
| 9 | `buildRedirectArgs(capturePath)` includes `state` only for a *safe* `capturePath`; omits the key (not `state: undefined`) otherwise | `buildRedirectArgs.test.ts` TC-ISS0726-01/02/03 | Design §2.3 step 5 explicitly calls out that the key must be *omitted*, not set to `undefined` — TC-ISS0726-02/03 assert `'state' in result` is `false`, which a looser `expect(result.state).toBeUndefined()` alone would not distinguish from an explicit `undefined` value |
| 10 | Existing zero-argument `buildRedirectArgs()` call sites (TC-OIDC-F02-01/02/03) keep passing unmodified | re-ran `buildRedirectArgs.test.ts` in full (see below) | Design §5 requires this; verified by running the whole file, not just the new cases |
| 11 | `OidcCallbackPage.tsx` prefers a validated `user.state` over the role-based fallback, for both `PROCESS_OPERATOR` and `PLATFORM_ADMIN` | `OidcCallbackPage.test.tsx` TC-ISS0726-04/05 | TC-ISS0726-05 specifically proves design §3.1 item 1's explicit "no role-based carve-out" — a `PLATFORM_ADMIN` user with a validated `state` must land there, not on `/platform-dashboard`, which is the opposite of REQ-369's pre-existing TC-REQ369-05 behavior when `state` is absent |
| 12 | An unsafe/tampered `user.state` falls back to the role-based destination rather than navigating to it | `OidcCallbackPage.test.tsx` TC-ISS0726-06 | This is the open-redirect regression test the design doc names explicitly (§6.1) — proves the restore-side re-validation (design §3.1 item 2) actually fires, not just the capture-side one |
| 13 | Existing `OidcCallbackPage.test.tsx` cases (TC-REQ369-05/06, no `state` key at all) keep passing unmodified | re-ran the full file (see below) | Design §5 requires this |
| 14 | Hard navigation to `/exam` restores `/exam` (not `/` or `/platform-dashboard`) after a real Keycloak round trip | `iss-0726-oidc-deep-link-restore.e2e.spec.ts` TC-ISS-0726-01 | This is the only layer that exercises the real `state`/`localStorage`/Keycloak-redirect mechanics (design §0) — the Vitest layer mocks `signinRedirectCallback` entirely and cannot prove the round trip itself works, only that the logic is correct once `user.state` arrives |

## Playwright e2e — real run against a live backend + Keycloak

**Update (post-handoff correction):** ISSUE-FIXER found a real gap in the first
version of this spec — `page.goto('/exam')` ran with a fresh browser context and no
`?realm=` query param, so `resolveRealmFromUrl()` (`web/src/auth/tenantConfig.ts`,
pre-existing behavior, not introduced by this fix) had no `sessionStorage`/URL realm
slug to resolve, `buildRedirectArgs()` short-circuited to `undefined`, and the fix's
own state-capture path never ran regardless of whether the fix worked. Fixed by
seeding `sessionStorage['bpm_realm_slug'] = 'bpm-default'` via `page.addInitScript`
before `page.goto('/exam')` — the approach ISSUE-FIXER proved against a live stack.

Per `docs/agents/workflows/WF-03_issue_resolving.md`'s "When the pre-fix failure is
'the code under test does not exist'" subsection: a naive pre-fix-commit test run
would only prove the module didn't exist (an unresolved-import failure), which says
nothing about whether the 38 `safeRestorePath` test cases actually discriminate a
correct implementation from a broken one. So the fail-first requirement is satisfied
instead by **mutating the shipped logic** (in place, then reverted and verified — no
`git worktree` used) and recording which tests fail per mutant.

### Mutants applied to `isSafeRestorePath` (web/src/auth/safeRestorePath.ts)

Baseline (unmutated, current committed code):

```ts
export function isSafeRestorePath(value: unknown): value is string {
  if (typeof value !== 'string') return false
  if (value.length === 0 || value.length > 2048) return false
  if (!value.startsWith('/')) return false
  if (value.startsWith('//')) return false
  if (value.includes('\\')) return false
  if (/[a-zA-Z][a-zA-Z0-9+.-]*:/.test(value)) return false
  ...
}
```

Baseline run: `38 passed (38)`.

**Note on suite iteration:** the first version of the "protocol-relative" test cases
used only dotted hostnames (`//evil.com`, `//evil.com/path`). Applying Mutant A against
that version showed **0 tests failed / 38** — the path-portion character-class check
(item 7) independently rejects any `.` in the string, masking the missing item-4 check
entirely. A `//evilhost` (no dot) case was added to `safeRestorePath.test.ts` specifically
to isolate item 4 from item 7 before mutation testing continued — this is recorded here
as it's a real gap the mutation process itself caught in the test design, not swept
under the "it works" summary.

**Mutant A — drop the protocol-relative check**
(remove `if (value.startsWith('//')) return false`):

- Result: **1 test failed / 38** — `//evilhost (no dot, protocol-relative only) -> false`
  (returned `true` instead of `false`).
- Proves the suite is sensitive to item 4 specifically, independent of item 7's
  character-class check.

**Mutant B — drop the embedded-scheme check**
(remove `if (/[a-zA-Z][a-zA-Z0-9+.-]*:/.test(value)) return false`):

- Result: **2 tests failed / 38** — `javascript: scheme embedded in query -> false` and
  `scheme embedded anywhere in string -> false` (both returned `true` instead of
  `false`).
- Proves the suite is sensitive to the scheme-detection check specifically — these two
  cases have no other check that would reject them (both start with `/`, are within
  the length bound, contain no `//`, no backslash, and their path portion up to `?` is
  a bare `/x` or `/redirect` which passes the path character class).

**Mutant C — off-by-one on the length boundary**
(`value.length > 2048` → `value.length >= 2048`):

- Result: **1 test failed / 38** — `exactly 2048 chars -> true (at the boundary, still
  allowed)` (returned `false` instead of `true`).
- Proves the suite is sensitive to the exact boundary value stated in design §1.3 item
  2, not just "somewhere around 2048."

- [ ] **Known gap, scoped out — zero-prior-context/hostname-resolved candidate path
      NOT exercised by any automated test in this repo.** `docs/issues/ISS-0726.yaml`'s
      original bug report is a candidate bookmarking `/exam` with *no prior visit* —
      no `sessionStorage['bpm_realm_slug']`, no `?realm=` param. In that scenario,
      realm resolution has to come from the hostname-based fallback in
      `web/src/auth/tenantConfig.ts`, before `buildRedirectArgs()`'s state-capture path
      (this PR's fix) ever runs. The e2e spec here (`iss-0726-oidc-deep-link-restore.e2e.spec.ts`,
      TC-ISS-0726-01) seeds `sessionStorage['bpm_realm_slug'] = 'bpm-default'` via
      `page.addInitScript` before `page.goto('/exam')` — see "Playwright e2e" section
      above — specifically so realm resolution succeeds and the capture/restore
      mechanism under test in this PR can actually run. That seeding proves the
      capture/restore mechanism works **once a realm is resolved**; it does not, and
      cannot, exercise the hostname-fallback resolution path itself, since seeded
      `sessionStorage` short-circuits `resolveRealmFromUrl()` before the hostname
      branch is ever reached. Hostname-based realm resolution for the true
      zero-prior-context path is tracked separately as `docs/issues/ISS-0727.yaml`
      (`qa.bizdala.com` tenant-config-by-host resolves to the wrong realm for
      bilimbaga) — that issue is explicitly `ai-dala-infra`/QA-host-config work, not a
      `web/` code fix, and is currently blocked on infra access this environment
      lacks (no per-tenant subdomain routing available locally, so an e2e case for
      this path cannot be constructed here without solving ISS-0727 inside this PR,
      which would be scope creep against this PR's design doc §0/§6). This remains an
      **unverified-by-automation gap** until ISS-0727 is resolved and a hostname-fallback
      e2e case can be added on top of it.
