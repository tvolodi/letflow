# Test Spec: ISS-0728 — CANDIDATE has no in-app navigation path to `/exam`

**Issue:** `docs/issues/ISS-0728.yaml`.
**Design:** `lib/letflow/design/iss0728-candidate-exam-nav.md`.
**Fix commit:** `97273401` on `feature/WF03-ISS0728-20260919` (parent: `9ef91dcf`).
**Fix:** `AppShell.tsx`'s `Role` type widened to include `'CANDIDATE'`; a new
`NAV_ITEMS` entry (`{ to: '/exam', label: 'Exams', roles: ['CANDIDATE'] }`) inserted
after "My Tasks"; `PermissionDenied.tsx` reads `useAuth()` and renders `<Link
to="/exam">Go to Exams</Link>` for a CANDIDATE session, unchanged `<Link
to="/tasks">My Tasks</Link>` otherwise.
**Test tier:** Vitest unit only — this is client-side nav-visibility/presentational
logic; no new executable backend or e2e surface per design §6/§5.4 (design explicitly
scopes a live-QA re-check as a recommended follow-up, not a substitute for unit
coverage here).

## Acceptance criteria and why each test case exists

| # | Criterion | Test case(s) | Why this case, not just a restatement |
|---|---|---|---|
| 1 | CANDIDATE sees the new "Exams" nav entry, pointing at `/exam` | `AppShell.candidate-nav.test.tsx` "CANDIDATE sees the 'Exams' nav entry, linking to /exam" | Proves both that the label renders AND that its `href` is exactly `/exam`, not just any link — a test asserting only text presence would pass even if the `to` were wrong |
| 2 | CANDIDATE does not see any other nav entry (the new entry doesn't accidentally widen visibility) | `AppShell.candidate-nav.test.tsx` "CANDIDATE does NOT see any other nav entry" | The design's own §2 change is additive to `NAV_ITEMS`; this proves the CANDIDATE role wasn't accidentally also added to any pre-existing entry's `roles` array — a positive-only test suite (case 1 alone) would miss that class of bug entirely |
| 3 | No regression: PLATFORM_ADMIN, PROCESS_DESIGNER, PROCESS_OPERATOR, TASK_WORKER do NOT see "Exams" | `AppShell.candidate-nav.test.tsx` four "does NOT see 'Exams'" cases, one per role, each also asserting that role's own pre-existing nav entry (Question Bank / Definitions / Question Bank / My Tasks) is still present | This is the specific scrutiny point REVIEWER/CODE-DESIGN-VALIDATOR called out: a filter bug (e.g. an unconditional `push` instead of appending to the gated array, or `roles: []` meaning "everyone") could make "Exams" leak to every role — the four negative assertions catch that class of regression, which the existing `AppShell.bilimbaga.test.tsx` cannot, since it predates this change and asserts nothing about "Exams" |
| 4 | CANDIDATE session's `PermissionDenied` renders "Go to Exams" linking to `/exam`, not "My Tasks" | `PermissionDenied.test.tsx` "CANDIDATE session renders 'Go to Exams' linking to /exam" | Proves the role-aware branch fires and produces the exact label/href design §3 specifies; also asserts the old "My Tasks" link is absent for this session, ruling out both links rendering simultaneously |
| 5 | Non-CANDIDATE session (e.g. TASK_WORKER) still renders the unchanged "My Tasks" → `/tasks` link | `PermissionDenied.test.tsx` "non-CANDIDATE session (TASK_WORKER) still renders 'My Tasks' linking to /tasks" | Proves the fix is additive-only for every other role — the existing behavior described in design §3 ("byte-for-byte unchanged" for non-CANDIDATE) is an executable check here, not just a design claim |
| 6 | `session: null` (pre-load state) does not throw and falls back to "My Tasks" → `/tasks` | `PermissionDenied.test.tsx` "no-session (session: null) falls back to 'My Tasks' linking to /tasks without throwing" | `session?.roles.includes('CANDIDATE')` must be `undefined`-safe per design §5.2 case 3 — a naive `session.roles.includes(...)` without the optional-chain would throw on this exact case, which is real (the component can render before the session finishes loading) |

## Fail-then-pass verification (WF-03 Step 4)

`AppShell.tsx` and `PermissionDenied.tsx` are both **pre-existing files modified by
the fix**, not new files — this is not the "code under test does not exist" case
(`docs/agents/workflows/WF-03_issue_resolving.md`'s mutation-testing fallback does not
apply here), so a direct pre-fix-commit run is the correct verification.

Swapped `web/src/components/layout/AppShell.tsx` and
`web/src/components/ui/PermissionDenied.tsx` for their pre-fix content
(`git show 9ef91dcf:<path>`, the fix commit's own parent), keeping the two new test
files as committed, and re-ran:

```

      Tests  3 failed | 6 passed (9)
```

The 3 failures were exactly the CANDIDATE-positive cases:
- "CANDIDATE sees the 'Exams' nav entry, linking to /exam" — failed (`getByText('Exams')`
  never resolves; pre-fix `NAV_ITEMS` has no CANDIDATE-gated entry, so CANDIDATE's
  `visibleNav` is empty).
- "CANDIDATE does NOT see any other nav entry" — failed on its own leading `waitFor`
  (`getByText('Exams')`), same root cause.
- "CANDIDATE session renders 'Go to Exams' linking to /exam" — failed (pre-fix
  `PermissionDenied` is role-blind, always renders "My Tasks" → `/tasks`).

The other 6 cases (the four no-regression role cases + the two non-CANDIDATE/null
`PermissionDenied` cases) passed against pre-fix code too, as expected — those
assertions describe behavior that was already true before the fix and remains true
after it.

Restored the fix commit's content (`git diff --stat` against the two source files
showed empty output after restore, confirming a byte-exact revert) and re-ran:
