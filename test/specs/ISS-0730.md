# Test Spec: ISS-0730 — Promotion-review GUI route wiring (PLATFORM_ADMIN gated)

**Issue:** ISS-0730 (BLOCKER). **Run:** WF-03 Step 4, TEST-DESIGNER.
**Design:** `lib/letflow/design/iss0730-promotion-review-page-routing.md`.
**Fix under test:** `web/src/router.tsx` (new leaf route
`definitions/:id/promotions/:reviewId -> <PromotionReviewPage/>`) and new file
`web/src/pages/definitions/PromotionReviewPage.tsx`, commit `ec4d5e0b`
(REVIEWER and SECURITY-REVIEWER both PASSed this commit; not yet pushed at the
time this spec was written).
**Test file:** `web/src/__tests__/router.iss-0730.test.tsx` (written by
FRONTEND-DEV as part of implementation, 2 tests; strengthened here to 4 tests).

## Criterion

Before this fix, none of the promotion-review React components
(`PromotionReviewStateMachine`, `PlanDigestView`, `NonSkippableApprovalGate`,
`ConflictRejectionAlert`) were reachable through any GUI route — `router.tsx`
had no entry mentioning `promotion` at all, and a live PLATFORM_ADMIN session
against `qa.bizdala.com` confirmed every plausible guessed URL 404'd
(ISS-0730.yaml lines 41-45). The issue's own `fix_direction` and the design's
§2/§3 settle the fix's acceptance bar as exactly three things:

1. A route exists and resolves to `PromotionReviewPage` (not some other
   component, and not absent).
2. A non-`PLATFORM_ADMIN` session hitting that URL is redirected to
   `/instances`, per the identical client-side-gate pattern already used by
   `AuditLogPage`/`HealthDashboardPage`/`MetricsPage` (design §3.1).
3. No stale/wrong path (the ones actually tried live and confirmed 404 in the
   issue) becomes newly, accidentally reachable as a second route to the same
   page.

This is a **route-wiring** defect, not a defect inside any of the already-built
child components (design §0 confirms `PromotionReviewStateMachine`/
`NonSkippableApprovalGate`'s own props/behavior are unchanged) — so, matching
the established pattern for this class of bug in this codebase (see
`test/specs/ISS-0289.md`), the tests target the *route mapping itself* via
`react-router`'s own `router.routes` / `matchRoutes`, not a standalone render
of either page component.

| Criterion | Proved by |
|---|---|
| `definitions/:id/promotions/:reviewId` maps to `PromotionReviewPage`; the parent `definitions/:id` is untouched (still `DefinitionEditorPage`) | `TC-ISS0730-01` |
| A non-`PLATFORM_ADMIN` session navigating to a concrete review URL is redirected to `/instances`, and no gated child (`NonSkippableApprovalGate`) ever mounts for that session | `TC-ISS0730-02` |
| A `PLATFORM_ADMIN` session navigating to the same URL is **not** redirected — the reviewer this route exists for can actually reach it | `TC-ISS0730-03` (added in this pass; the original two tests only proved a non-admin is turned away, never that the intended user gets through — an inverted role check would still pass TC-ISS0730-02 trivially wrong in the other direction while silently locking out every real reviewer) |
| None of the concrete wrong URLs the issue's live investigation actually tried (`/admin/promotions`, `/promotions`, `/definitions/promotions`, `/admin/definitions/promotions` — ISS-0730.yaml lines 41-45) resolve to `PromotionReviewPage` | `TC-ISS0730-04` (added in this pass) |

`TC-ISS0730-04` note: `/definitions/promotions` structurally matches the
pre-existing dynamic `definitions/:id` leaf (`id: "promotions"`) — ordinary
param-matching behavior, not a route this fix creates or could plausibly
break. That one path is therefore asserted narrowly ("does not resolve to
`PromotionReviewPage`") rather than "matches no route at all"; the other three
guessed paths assert the stronger "matches no route" via the same check
(since their matched leaf, if any, is never `PromotionReviewPage` either — the
test asserts on the resolved element type uniformly across all four paths for
one consistent code path).

## Why the pre-fix "does not exist" rule applies, and what was done about it

This is new code, not a fix to existing behavior — `PromotionReviewPage.tsx`
did not exist before this fix at all, so a bare pre-fix-checkout-and-confirm-fail
is trivially satisfiable (every test in the file fails to even *import*, which
proves the file is new and nothing about whether the tests discriminate a
correct implementation from a wrong one). Per
`docs/agents/workflows/WF-03_issue_resolving.md`'s "When the pre-fix failure is
'the code under test does not exist'" section, the fail-first requirement is
satisfied here instead by **mutating the shipped logic** and recording which
tests fail for each mutant, plus (for completeness) the trivial pre-fix check.

### Mutation testing (the real fail-first evidence)

All three mutants were applied one at a time in a **throwaway `git worktree`**
of the fixed commit (`ec4d5e0b`, `../letflow-mut-iss0730`, `node_modules`
junctioned from the primary checkout — the primary working tree was never
mutated), each reverted with `git checkout --` and the revert verified before
the next mutant. Baseline (unmutated, strengthened 4-test file) in that
worktree: **4/4 pass**.

**Mutant (a) — wrong route path.** `web/src/router.tsx`:
`{ path: 'definitions/:id/promotions/:reviewId', ... }` →
`{ path: 'admin/promotions/:reviewId', ... }`.

```
 × TC-ISS0730-01: ... → expected undefined to be defined
 × TC-ISS0730-02: ... → expected null not to be null
 × TC-ISS0730-03: ... → expected null not to be null
 Tests  3 failed | 1 passed (4)
```

3/4 fail (TC-01/02/03 — every test that depends on the real URL resolving to
something); TC-04 still passes (it only asserts *wrong* paths don't resolve to
`PromotionReviewPage`, which remains true — the mutant just moved the real
route to a different wrong path, it didn't create a false positive there).
Confirms `TC-ISS0730-01` (and, transitively, 02/03) catches a wrong route
path.

**Mutant (b) — inverted role gate.** `web/src/pages/definitions/PromotionReviewPage.tsx`:
`if (!isPlatformAdmin) return <Navigate to="/instances" replace />` →
`if (isPlatformAdmin) return <Navigate to="/instances" replace />`.

```
 × TC-ISS0730-02: ... → element found: <div data-testid="instances-redirect-target" />
   (the non-admin session is no longer redirected — full inline dump shows
   "Promotion Review" heading rendered instead)
 × TC-ISS0730-03: ... → expected element not to be in the document, found
   <div data-testid="instances-redirect-target" />
   (the admin session is now wrongly redirected)
 Tests  2 failed | 2 passed (4)
```

2/4 fail — exactly the two role-gate tests, from opposite directions (TC-02:
non-admin no longer turned away; TC-03: admin now wrongly turned away). TC-01
and TC-04 pass unaffected (route mapping itself is untouched by this mutant).
Confirms `TC-ISS0730-02` and `TC-ISS0730-03` together catch an inverted role
check — neither alone would have caught both directions of this mutant, which
is exactly why TC-ISS0730-03 was added in this pass.

**Mutant (c) — wrong redirect destination.** Same file:
`<Navigate to="/instances" replace />` → `<Navigate to="/dashboard" replace />`.

```
 × TC-ISS0730-02: ... → Unable to find an element by:
   [data-testid="instances-redirect-target"]
   (stderr: "No routes matched location "/dashboard"" — the MemoryRouter in
   the test only registers "/instances" as a landing target, matching the
   design's specified destination)
 Tests  1 failed | 3 passed (4)
```

1/4 fails — `TC-ISS0730-02`, the one test that asserts the specific redirect
*destination*, not just that a redirect happens. TC-01/03/04 pass unaffected.
Confirms `TC-ISS0730-02` is sensitive to the exact redirect target, not merely
"some redirect occurred."

## Not covered here, and why

  `lib/letflow/routers/promotions.ex` and the promotion-review state machine
  are untouched, already covered by their own existing test suites.

  A live-browser e2e exercise of the actual approve/release flow through this

  WF-03 run.

  scope per the design's §5 non-goals — nothing to test because nothing was
  built for them in this fix.
