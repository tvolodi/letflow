## AC1 — revoke-then-immediately-retry, no sleep/refresh

**Test:** `test/letflow/plugs/iss0736_oidc_live_revocation_test.exs`
(`Letflow.Plugs.Iss0736OidcLiveRevocationTest`), 2 tests:

1. *"an OIDC session with PLATFORM_ADMIN succeeds on a PLATFORM_ADMIN-only
   route; revoking group membership (no re-auth) makes the identical bearer
   token fail 403 on the very next identical request"* — grants
   `PLATFORM_ADMIN` via `Letflow.Identity.create_group/2` +
   `Letflow.Identity.add_group_member/3` (the same functions the corrected
   `web/` GUI path now calls), dispatches `GET /api/v1/identity/tokens`
   through the real `Letflow.Router.call/2` chain with the fixed OIDC
   sentinel token (`Letflow.Oidc.TokenVerifierDouble`'s
   `"valid-test-token"`) and asserts 200 + `"PLATFORM_ADMIN" in roles`, then
   calls `Letflow.Identity.remove_group_member/3` (no re-auth, no sleep) and
   re-dispatches the *identical* request with the *identical* bearer token,
   asserting 403.
2. *"deactivating the account (users.status) also takes effect on the very
   next request, same JWT"* — same shape, but revokes via
   `Letflow.Identity.update_user_status/3` (`:inactive`) instead of a group
   membership removal, proving the `:inactive` short-circuit independently
   of the role-narrowing path.

**Why these exist, not just a restatement of the AC:** before the fix,
`authenticate_oidc/2` sourced `conn.assigns[:auth_context][:roles]` from the
JWT's own claims (`IdentityContext.roles`), never from `group_members`/
`tenant_role`/`users.status` — so neither test 1's revoke nor test 2's
deactivate could have any effect on an already-issued session's next
request; only the fix's new `verify_local_account_state/2` step (a live,
uncached `Repo` read per request) makes the second dispatch in each test
observe the change. The two tests are independent (revoke-role vs.
deactivate-account) because the design's own §1.1 makes them two separate
code paths (`:inactive` short-circuits before any role query; a narrowed
role set flows through as a normal `{:ok, []}`-shaped value) — one test
covering only one of the two would leave the other's live-check unproven.

## AC2 — reachable through web/'s own GUI

**Test:** `web/src/api/__tests__/identity.removeMembers.test.ts` — asserts
`groupsApi.removeMembers(groupId, userId)` issues `DELETE
/api/v1/identity/groups/:id/members/:user_id` (the real, router-backed
route), not the pre-fix `/api/v1/admin/groups/:id/members` (a route that
does not exist on the backend at all). Why this exists: the backend-side
fix (AC1) is provably correct in isolation, but AC2 requires the *GUI* path
to actually reach it — before the fix, `GroupsPage.tsx`'s "remove member"
button could never have worked (wrong path, and the discarded-array
signature), so a passing AC1 test alone would not prove AC2.
