## AC1 — every `groupsApi` call targets a prefix a real backend route serves

The six real routes are `lib/letflow/routers/identity.ex:178-204`, mounted at
`/identity` by `lib/letflow/plugs/api_pipeline.ex:141` under `/api/v1`
(`lib/letflow/router.ex:130`). The only `/admin/*` mount in the pipeline is
`/admin/services` (`api_pipeline.ex:154`), so every pre-fix `/api/v1/admin/groups...`
call fell through to the catch-all at `:203-205` and 404'd **after** successful
authentication — a dead end behind a button that looked like it worked.

| Row | Case ID | What it asserts |
|---|---|---|
| 1 | `T-0765-LIST` | `list()` → method `GET`, URL contains `/api/v1/identity/groups`, does not contain `/api/v1/admin/groups` |
| 2 | `T-0765-CREATE` | `create(body)` → `POST /api/v1/identity/groups`, parsed request body deep-equals the object passed |
| 3 | `T-0765-DELETE` | `delete('g-1')` → `DELETE /api/v1/identity/groups/g-1` |
| 4 | `T-0765-ADD-PATH` | `addMember('g-1','u-1')` → `POST /api/v1/identity/groups/g-1/members` |
| 7 (i) | `T-0765-MEMBERS` | `members('g-1')` → `GET /api/v1/identity/groups/g-1/members`, no `/api/v1/admin/` |
| 10 | `T-0765-NO-ADMIN-PREFIX` | `it.each` over all six surviving functions: no captured URL contains `/api/v1/admin/` |

**Why row 10 exists on top of rows 1-7, and is not redundancy to trim.** Rows 1-7 each
pin one function to one specific correct path; row 10 is the *class* guard. It
enumerates every function on the surface, so a seventh function added later with a bad
prefix is caught without anyone remembering to write a bespoke row for it — the exact
failure mode that produced ISS-0765 in the first place (ISS-0736 fixed one function of
eight and the sibling seven were left carrying the identical defect for three days).
One `it.each` case per function so a failure names the culprit rather than reporting
"the table failed".

**Why row 10 is scoped to `groupsApi`'s own captured URLs and not to file content.**
`/api/v1/admin/` still legitimately appears in `identity.ts` at `:73-88` (`rolesApi`),
which is **ISS-0812's** scope, not this run's. A whole-file absence assertion would go
red for a reason that has nothing to do with this fix — a false alarm that a later
reader would have to re-derive from scratch. Design §6.1's closing paragraph makes this
binding, and REVIEWER re-confirmed the premise is still true at `bcddcebf`.

**Why row 7's path half is kept even though row 10 also covers `members`.** Row 7 is a
single `it` carrying both halves of the `.members` correction. Without a discriminating
assertion of its own, its no-unwrap half (below) would sit alone in a block that can
never be red, which is the thing a coverage gate should refuse.

## AC2 — regression coverage mirroring `identity.removeMembers.test.ts`

| Row | Case ID | What it asserts |
|---|---|---|
| 5 | `T-0765-ADD-BODY` | the add-member `POST` body deep-equals `{ user_id: 'u-1' }`, and `'user_ids' in body` is `false` |
| 6 | `T-0765-ADD-ARITY` | `typeof groupsApi.addMember === 'function'`, `.length === 2`, and `'addMembers' in groupsApi` is `false` |
| 7 (ii) | `T-0765-MEMBERS` | with the double resolving the real wire envelope, the awaited value deep-equals it: `items.length === 1`, `count === 1`, `next_cursor === null`, `Array.isArray(result) === false` |
| 11 | `T-0765-REMOVE-UNCHANGED` | `removeMembers('g-1','u-1')` still issues `DELETE /api/v1/identity/groups/g-1/members/u-1` |

**Why rows 5 and 6 are separate.** Row 5 is about the *wire body*, row 6 about the
*exported surface*. `resolve_member_user_id/1`
(`lib/letflow/routers/identity.ex:525-537`) matches `%{"user_id" => id}` as its first
clause and, on the `%{"user_ids" => [first | _rest]}` clause, silently discards
everything after the head — a decision the comment at `:483-489` records as a
deliberate R-Co port choice. A client could therefore send `{user_id}` on the wire and
*still* advertise a plural `addMembers` signature that no caller can rely on; row 6 is
what closes that, by asserting the misleading name is gone, not merely unused.

**Why row 7(ii) exists although it can never be red pre-fix.** It is a **forward
regression guard**, and the spec records it as such rather than counting it as
fail-first evidence — see "Fail-first evidence" below. It goes red the moment anyone
reintroduces an `.items` unwrap inside `groupsApi.members`, which is precisely what
design INV-B forbids and what decision (b) rejected on
`docs/guides/frontend_developer_guide.md` §4 rule 1 (no adapter inside `web/` that
normalises an API mismatch, because it hides the gap from every other client including
the mobile tier).

**Why row 11 duplicates an assertion `identity.removeMembers.test.ts` already makes.**
That file is left byte-unchanged (design INV-C). Row 11 is an enumeration row: its job
is to prove ISS-0765 did not regress the ISS-0736 correction while rewriting the object
literal around it, and to make the `groupsApi` table complete in one place so a future
reader auditing this surface does not have to know that one of eight functions is
covered in a different file.

| 9 | `T-0765-SURFACE` | `Object.keys(groupsApi).sort()` deep-equals `['addMember','create','delete','list','members','removeMembers']` |

closure assertion that stops a fourth pass silently re-adding either one under a new
name.

`handoffs/WF03-ISS0765-20260924/step-04-test-designer.json`.

### Why no runtime row can carry decision (b)'s evidence

`request<T>` (`web/src/api/client.ts:158-169`) ends in
`return response.json() as Promise<T>`, and `T` is erased at runtime. Pre-fix
`client.get<User[]>(…)` and post-fix `client.get<GroupMemberPage>(…)` are byte-identical
against the same response body. The `.members` retype is a **type-only** change, so the
fail-first requirement is met by mutating the shipped change — WF-03 Step 4's clause for
"when the pre-fix failure is non-existence", applied by analogy, with both mutants
specified by the design (§7.1) rather than improvised here.

`GroupMemberPage` and the retyped `groupsApi.members`, revert **only** §3.2's six

fix (a missed `.members` consumer producing `members.map is not a function` in the
members dialog).

**CAVEAT N-1, carried from the design gate and confirmed by measurement.** The design
predicted diagnostics at the reverted `:103, :223, :227, :228` sites and flagged that
list as a **floor, not an exact expectation**. What tsc actually emitted, at the
mutant's own line numbering, is `:104`, `:224` and `:228` — the design's `:103/:223/:227`
shifted by the removed `useMemo` line. There is **no diagnostic for the design's `:228`
reasoning** (`user.user_id` not existing on `GroupMember`), because that line sits inside
the callback of the `.map` that just failed to resolve; the diagnostic surfaces instead
as `TS7006` implicit-any on the callback parameter at `(228,41)`, precisely the
characteristic the gate predicted. The mutant was **not** adjusted to manufacture the
missing diagnostic. Four distinct source positions and five diagnostics is well above the
floor, and the probe discriminates the trap.

## What this spec does **not** prove

Every command in this run type-checks, lints or exercises the code against a `vi.fn()`
double whose `Response` the test itself constructs. **No HTTP request leaves the
process and no Letflow instance was dialled** — `FRONTEND-DEV` recorded that a probe of
`http://localhost:4000/api/v1/identity/groups` got no connection (HTTP 000), and
REVIEWER carried that gap forward rather than claiming it away.

So it remains unproven *by execution* that `/api/v1/identity/groups`,
`/api/v1/identity/groups/:id`, `/api/v1/identity/groups/:id/members` and the
`{ user_id }` add-member body return 2xx against a running server with a real
`:GroupsManage`-bearing token. The route table was read from source and the six routes
demonstrably exist, so the correction is sound *by construction* — but construction is
not execution, and a divergence between the route macros as written and the pipeline as
actually mounted at runtime is the one class of defect no test in this run can catch.

**Owner:** `UAT-RUNNER`, once an instance is up. Scope: list groups, open Manage
members, add a member, remove a member, delete an empty group. This gap must not be
closed out at Step 5 as if end-to-end evidence existed.

Separately, the members dialog still shows at most the first page (50 members,
`Letflow.Api.Pagination.default_page_size/0`) and `GroupMemberPage.next_cursor` is
returned but unread — design §3.3/OQ-2, pre-existing behaviour this fix makes reachable
for the first time, deliberately not fixed and deliberately not tested here.
