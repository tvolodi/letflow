# Test Spec: ISS-0766 — permanent loss of the migration-seeded "bpm-default" tenant row

**Issue:** `docs/issues/ISS-0766.yaml`.
**Fix:** `test/support/bpm_default_realm_displacement.ex` — new private `ensure_seeded!/1`,
called at the top of both `displace!/0` and `with_lock/1`, under the module's existing
`@lock_key` advisory lock. Branch: `fix/ISS0766-self-healing-realm-seed-20260927`.
**Test tier:** integration (real Postgres via `Letflow.DataCase`, `:auto` sandbox mode —
DIRECTIVE T-1, no mocks).

## Bug recap

The migration-seeded `"bpm-default"` tenant row is a singleton: `mix ecto.migrate` never
re-inserts it once the seed migration is recorded as applied. This project's test
databases (`letflow_test#{N}`) are long-lived and reused across many unrelated `mix
test`/`scripts/test_parallel.sh` invocations. If the OS process running a `displace!/0`
caller is killed abnormally (SIGKILL, OOM-kill, CI timeout/cancellation) between its
`Repo.delete!` and its `on_exit`-deferred restoration, the row is gone from that
physical database **permanently** — every later `displace!/0`/`with_lock/1` call against
that same database observed `nil` forever, with no re-seeding path. Confirmed live
(ISSUE-FIXER's reproduction) to deterministically break
`test/letflow/identity_test.exs`'s `resolve_tenant_by_realm/1`/`resolve_realm_by_tenant/1`
tests (REQ-019 AC1) and `test/letflow/plugs/iss0778_platform_role_seeding_e2e_test.exs`'s
T4 — the same mechanism, two different callers.

No dedicated test file for `test/support/bpm_default_realm_displacement.ex` existed
before this one — its behavior was only ever exercised indirectly via callers, all of
which run under normal (already-seeded) conditions, so nothing in the suite would catch
`ensure_seeded!/1` being silently removed or broken.

## Criteria

1. `with_lock/1` self-heals: if the `"bpm-default"` tenant row is missing when
   `with_lock/1` is called, `ensure_seeded!/1` re-inserts it (same shape the seed
   migration uses: `slug`/`idp_realm_id` = `"bpm-default"`, `display_name` = `"Default
   Tenant"`, `status` = `:active`) *before* running the caller's `fun`, so a caller like
   `identity_test.exs`'s `insert_default_tenant!/0` (`Repo.get_by!/2`, which raises
   `Ecto.NoResultsError` on a miss) succeeds instead of raising.
2. `ensure_seeded!/1`'s repair is idempotent / non-destructive when the row is already
   present: `ON CONFLICT (slug) DO NOTHING` must not disturb the pre-existing row's
   identity.
3. `displace!/0` shares the identical `ensure_seeded!/1` call site and must not
   raise/crash when the row is missing (functional smoke coverage — see the test file's
   own moduledoc for why displace!/0's self-heal effect can't be proven synchronously
   within one test body: its restoration is deferred to an `on_exit` callback that runs
   only after this test process itself has exited, and probing it from within the same
   test would deadlock on the still-held advisory lock).

## Test cases — `test/support/bpm_default_realm_displacement_test.exs`

1. **"re-seeds the bpm-default tenant row when it is missing, before running fun"**
   (criterion 1) — deletes the row via raw SQL (bypassing `displace!/0`/`with_lock/1`
   entirely, simulating an already-corrupted database exactly as ISSUE-FIXER's manual
   reproduction did), then calls `with_lock/1` with a `fun` that does
   `Repo.get_by!(Tenant, idp_realm_id: "bpm-default")` — the same bang-read
   `insert_default_tenant!/0` uses, so this test fails with the exact
   `Ecto.NoResultsError` ISS-0766's `process_note` quotes from real CI runs if the fix
   is ever removed. Asserts the returned tenant's `slug`/`display_name`/`idp_realm_id`/
   `status` match the seed migration's values, and that the row is durably visible via
   an independent read afterward.

2. **"is a no-op repair when the row is already present"** (criterion 2) — calls
   `with_lock/1` without deleting the row first, asserts the returned tenant's `id`
   is unchanged, ruling out a delete-and-reinsert implementation that would pass
   criterion 1 for the wrong reason.

3. **"does not raise when the bpm-default row is missing"** (criterion 3) — deletes the
   row, calls `displace!/0` directly, asserts it returns `:ok` without raising.

## Mutation proof (WF-03 Step 4 — pre-fix vs. post-fix)

`ensure_seeded!/1` is new code (did not exist pre-fix), so "run against the pre-fix
commit" would trivially fail with a `UndefinedFunctionError`/compile error and prove
nothing about the actual repair logic. Per
`docs/agents/workflows/WF-03_issue_resolving.md`'s "When the pre-fix failure is 'the
code under test does not exist'" procedure, a mutant of the SHIPPED fix was applied
instead, to prove the new test genuinely discriminates:

- **Mutant:** commented out the `ensure_seeded!(lock_conn)` call in `with_lock/1`
  (`test/support/bpm_default_realm_displacement.ex`, the line inside `with_lock/1`'s
  `try` block, right before `fun.()`).
- **Result with mutant applied:** `mix test
  test/support/bpm_default_realm_displacement_test.exs` — 1 failure:
  `test with_lock/1 self-heals via ensure_seeded!/1 (ISS-0766) re-seeds the bpm-default
  tenant row when it is missing, before running fun` failed with
  `** (Ecto.NoResultsError) expected at least one result but got none in query` at the
  `Repo.get_by!/2` call inside the test's own `fun` — exactly the failure mode ISS-0766
  describes. The other 2 tests in the file still passed (they don't delete the row
  first / don't touch `with_lock/1`'s missing-row path).
- **Reverted the mutant** (restored the `ensure_seeded!(lock_conn)` call) and re-ran the
  same file: 3/3 passed.

This proves the new test fails when the fix is absent and passes when it is present —
genuinely discriminating, not a test that only ever runs against already-correct code.
