# Test Spec: ISS-0768 — RoleRegistry cross-tenant isolation regression

**Issue:** ISS-0768 (`docs/issues/ISS-0768.yaml`). **Run:** `WF03-ISS0768-20260921`,
WF-03 Step 6 (TEST-DESIGNER).
**Fix under test:** `lib/letflow/identity/role_registry.ex` — `list_roles/1` and
`upsert_role/3` now take `opts :: [prefix: String.t()]` and thread it through every
`Repo` call, fixed by commits `ddfa3cdf` ("thread tenant prefix through RoleRegistry")
and `4724703f` (rework 1, `Keyword.fetch!` binding). Pre-fix (`d894d1f6`), these
functions were `list_roles/0`/`upsert_role/2` and always queried the ambient
`search_path`/default schema — `public`, which (post-REQ-063) has no `tenant_role`
table at all, so `POST /roles` 500'd for every tenant unconditionally.
**Test file:** `test/letflow/role_registry_test.exs` — new `describe` block "ISS-0768
regression — prefix genuinely scopes RoleRegistry to one tenant's own schema", plus two
new private helpers (`insert_group!/2`, `provision_second_tenant!/0`).

## Criterion

ISS-0768.yaml's own acceptance criteria (`fix_direction`) require: "a regression test
creating a role for one tenant and confirming it is queryable only in that tenant's own
schema (not visible via a different tenant's prefix, not written to public)."
SECURITY-REVIEWER's step-04 addendum (a non-blocking finding from an independent
concurrent pass, confirmed by direct read of the file) found this genuinely missing:
every test already in `role_registry_test.exs` provisions exactly **one** tenant schema
per test (`setup`'s own `TenantProvisioning.provision_tenant_schema/1` call) and every
assertion in the file only ever queries that same single schema. None of them can tell
"correctly scoped to tenant A" apart from "the `prefix:` option is silently ignored and
every call just hits whatever schema `search_path` happens to point at" — both would
look identical under a single-schema fixture. This gap is closed by standing up a
**second**, genuinely independent tenant schema in the same test and probing across it.

## Test case

One test, `"role created under tenant A's prefix: visible via A's own prefix, absent
via tenant B's prefix, absent from public"`, with four assertions covering all four
acceptance-criteria clauses:

1. **Positive case** — `RoleRegistry.list_roles(prefix: schema_a)` includes the role
   just created via `RoleRegistry.upsert_role(name, group_a.id, prefix: schema_a)`.
   Without this, the negative cases below would be vacuously true for a
   RoleRegistry that writes/reads nothing at all.
2. **Negative case 1 (cross-tenant)** — `RoleRegistry.list_roles(prefix: schema_b)`,
   `schema_b` a real second Postgres schema provisioned mid-test
   (`provision_second_tenant!/0`), does **not** include the role. This is the
   assertion no pre-existing test in the file could make, since none of them ever had
   a second schema to probe against.
3. **Negative case 2 (not written to public)** — a direct `Repo.all/2` against
   `TenantRole` with `prefix: "public"` is asserted to fail with
   `Postgrex.Error`/`undefined_table` (`relation "public.tenant_role" does not
   exist"`), confirmed empirically live against this branch's schema (REQ-063 moved
   `tenant_role` out of `public` entirely — there is no `public.tenant_role` table
   left to hold a stray row, or to return an empty result set from). This is treated
   as the **stronger** form of "not written to public" the acceptance criterion asks
   for: structurally impossible, not merely empty.
4. `schema_a != schema_b` is asserted directly, so the test cannot silently degenerate
   into probing the same schema twice under two different names.

The issue's own acceptance criteria explicitly separate "not visible via a different
tenant's prefix" from "not written to public" as two independently required
assertions — case 2 is not implied by case 1 (case 1 only exercises the *read* side of
`RoleRegistry`'s own prefix handling; case 2 checks where `upsert_role/3` actually
*wrote* the row, independent of `RoleRegistry`'s own later reads).

### Fixture notes

`provision_second_tenant!/0` mirrors `test/letflow/identity/user_test.exs`'s own
`provision_tenant_schema!/0` two-tenant pattern (grepped per the handoff's own
instruction, rather than inventing a new shape): a second schema needs
`Ecto.Adapters.SQL.Sandbox` `:auto` mode for `Ecto.Migrator`'s migration replay, and
switching to `:auto` mode checks in (rolls back) whatever `:manual`-mode transaction
`setup` established for tenant A. The test therefore switches the *whole* `Repo` to
`:auto` mode as its first line, before inserting anything, so tenant A's own role
insert is a real, committed row rather than something later discarded when tenant B is
provisioned — same ordering constraint `user_test.exs`'s "same username, two different
tenant schemas" test documents and solves the same way. `insert_group!/2` is a sibling
of the file's existing `insert_group!/1`, taking an explicit `prefix:` instead of
relying on ambient `search_path` — needed here because two schemas are alive at once,
so there is no single ambient schema for a bare `Repo.insert!/1` to target correctly.

## Fail-first / mutation evidence (WF-03 requirement)

The fix (`ddfa3cdf`/`4724703f`) already existed on this branch before this test was
written — this is a coverage-closing test, not the original fix-verifying one, so the
"pre-fix code does not exist" WF-03 clause does not strictly apply. Verified anyway,
live, via mutation testing against the current (fixed) code:

**Mutant:** in `lib/letflow/identity/role_registry.ex`'s `list_roles/1`, changed

    Repo.all(from(t in TenantRole, order_by: [asc: t.name]), prefix: prefix)

to

    Repo.all(from(t in TenantRole, order_by: [asc: t.name]))

(the `prefix` binding kept, renamed `_prefix`, to isolate this from an unused-variable
warning) — i.e. silently ignore the caller-supplied prefix, exactly ISS-0768's original
defect for this function.

**Result:** `MIX_ENV=test mix test test/letflow/role_registry_test.exs` under the
mutant: **14/15 passed, 1 failed** — the ONLY failure was this spec's own new test:

    1) test ISS-0768 regression — prefix genuinely scopes RoleRegistry to one
       tenant's own schema role created under tenant A's prefix: visible via A's
       own prefix, absent via tenant B's prefix, absent from public
       (Letflow.Identity.RoleRegistryTest)
       test/letflow/role_registry_test.exs:439
       ** (Postgrex.Error) ERROR 42P01 (undefined_table) relation "tenant_role" does not exist
       code: names_a = RoleRegistry.list_roles(prefix: schema_a) |> Enum.map(& &1.name)

(Positive case failed first — with the prefix ignored, `list_roles/1` fell back to
whatever `search_path` pointed at post-`:auto`-mode-switch, which is not `schema_a`.)

**Revert:** the mutant was reverted (`git diff lib/letflow/identity/role_registry.ex`
confirmed empty afterward) and the full file re-run: **15/15 passed**, confirming the
revert restored exactly the pre-mutant behavior with no other side effect.

This demonstrates the new test is load-bearing: it is the only test in the file that
goes red when `list_roles/1`'s prefix-threading is broken.
