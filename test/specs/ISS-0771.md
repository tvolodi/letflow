# Test Spec: ISS-0771 — Automatic tenant-scoped migration replay on every app start

**Issue:** `docs/issues/ISS-0771.yaml` — no deploy-time or boot-time step ever replayed
tenant-scoped migrations against tenants that already existed before a new
tenant-scoped migration merged, causing a full authenticated-request outage across both
QA tenants after REQ-378's migration shipped. Fix design:
`lib/letflow/design/iss0771-tenant-migration-replay-on-deploy.md`.

**Fix shape:** two brand-new pieces of code, not a change to existing behavior —
`Letflow.TenantProvisioning.replay_all_pending/0` (new public function) and
`Letflow.TenantProvisioning.MigrationReplayBoot` (new boot-time supervision-tree
child). Per `docs/agents/workflows/WF-03_issue_resolving.md`'s "When the pre-fix
failure is 'the code under test does not exist'" section, a fail-then-pass run against
pre-fix code is trivially satisfied here (every test in these two files would fail with
`UndefinedFunctionError`/`Protocol.UndefinedError`/module-not-found against the
pre-fix tree) and proves nothing about whether the tests discriminate a *correct*
implementation from a *wrong* one. **Mutation testing is therefore mandatory and is
the real evidence of coverage** — see "Mutation testing" below.

## Scope test

Real application-executable Elixir logic: `lib/letflow/tenant_provisioning.ex`
(`replay_all_pending/0`, new function) and
`lib/letflow/tenant_provisioning/migration_replay_boot.ex` (new module, new file). Not
docs-only, not build-config. Full TEST-DESIGN-VALIDATOR / TEST-RUNNER chain applies.

## Test cases

1. **Idempotent no-op second run** — see
   `test/letflow/tenant_provisioning_test.exs` describe
   `"replay_all_pending/0 (ISS-0771)"`, test `"calling it twice against a fully
   migrated tenant is a safe no-op both times"`. Proves the design's §3 idempotency
   guarantee: two consecutive calls against a tenant with zero pending migrations
   return the same `%{ok: [...], error: []}` shape for that tenant, the tenant's own
   `Registration` row count never grows past 1, and the schema's table count is
   unchanged across both calls (no duplicate DDL).
2. **One tenant's failure does not abort replay for other tenants** — same file,
   test `"one tenant's broken schema does not abort replay for a healthy sibling
   tenant"`. Provisions two tenants, then makes one genuinely unreachable
   (`DROP SCHEMA ... CASCADE` on its own physical schema, its `Registration` row left
   dangling — the design doc's own example of a "corrupt/unreachable schema"), then
   calls `replay_all_pending/0` once and asserts the healthy tenant lands under `:ok`
   while the broken one lands under `:error` with a `{:migration_failed, _}` reason —
   in the same call, proving Layer 1 + Layer 2's per-tenant isolation (design §4).
3. **Real replay against a genuinely pending migration** — same file, test `"actually
   applies a migration that is pending against an already-provisioned tenant"`.
   Provisions a tenant (fully migrated), then reverts the tenant's schema to a state
   where the most recent tenant-scoped migration
   (`20260921000001_add_role_claims_synced_at_to_users.exs` — REQ-378's own migration,
   the one ISS-0771's incident hinged on) is pending again: drops the
   `users.role_claims_synced_at` column it adds and deletes its
   `schema_migrations` row. Calls `replay_all_pending/0` and confirms the tenant lands
   under `:ok`, the column is back, and the `schema_migrations` row is back — i.e. a
   real DDL replay happened, not a false-positive no-op.
4. **`MigrationReplayBoot.start_link/1` always returns `:ignore`, even under a total
   per-tenant failure** — `test/letflow/tenant_provisioning/migration_replay_boot_test.exs`,
   test `"returns :ignore and logs the failing tenant even when a tenant's replay
   fails"`. Breaks one provisioned tenant the same way as case 2, calls
   `start_link(nil)` directly, and asserts the return is exactly `:ignore` (never
   `{:error, _}`, never a raised exception) — this is the test that is sensitive to
   mutant 2 below. Also asserts (via `ExUnit.CaptureLog`) that the failing tenant's
   `tenant_id`/`schema_name`/`reason` were logged and that the always-emitted summary
   line names a nonzero failed count.
5. **`MigrationReplayBoot.start_link/1` logs the healthy-path summary line too** —
   same file, test `"logs a 0-failed summary line on the healthy path"`. Calls
   `start_link(nil)` against whatever tenants are currently provisioned with none
   deliberately broken, and asserts the summary log line is present with a `0 failed`
   count — proves the "logs nothing on the healthy path" gap design §2.2 calls out is
   actually closed, not merely asserted in prose.

## Fixtures used

`Letflow.TenantFixture.provisioned_tenant!/1` (`test/support/tenant_fixture.ex`) for
every provisioned-tenant setup — the current established fixture for a real,
fully-migrated tenant schema (registers its own `on_exit/1` teardown: drops the schema,
deletes the `Registration` row, deletes the `Tenant` row). No new provisioning
machinery invented. `test/support/sandbox_auto_mode.ex`'s `SandboxAutoMode` module is
not used directly — `TenantFixture.provisioned_tenant!/1` already flips
`Ecto.Adapters.SQL.Sandbox` to `:auto` mode itself and this file stays `async: false`
end to end, matching `tenant_provisioning_test.exs`'s own established pattern for why
that is safe (no other test's connection to disturb while a sync module runs).

## Mutation testing (WF-03 "code under test does not exist" path)

Both mutants below were applied in a throwaway `git worktree` created off this
branch's HEAD (`.claude/worktrees/iss0771-mutant-check`, removed after use), never in
this working checkout — `lib/` in this checkout was never touched. Real pass/fail
counts recorded in the TEST-DESIGNER handoff's `result.summary`.

**Mutant 1 — remove `replay_all_pending/0`'s own per-tenant `rescue`** (targets the
per-tenant isolation guarantee, design §4 "Layer 2"): deletes the `try/rescue` around
`replay_migrations(tenant_id)` inside the `Enum.reduce/3`, leaving a bare call. Since
Layer 1 (`replay_migrations/2`'s own internal `rescue`) already converts every reachable
exception into a tagged `{:error, _}` tuple today, this mutant alone does not change any
currently-reachable behavior — it removes only the *second, independent* safety net the
design explicitly calls "not redundant paranoia without a reason" (§4). To make the
resulting gap observable by a test — proving Layer 2 is load-bearing, not decorative —
the mutant additionally changes `replay_migrations/2`'s own `rescue` clause to
re-raise instead of returning a tagged tuple, for exactly one reason: this is the
"a future change to `replay_migrations/2` reintroduces an unrescued raise path" scenario
§4 names by name as the reason Layer 2 exists. Test case 2 above is run against this
combined mutant and expected (and confirmed) to fail — the sibling-tenant call now never
gets a `%{acc | error: [...]}` catch, so the raise propagates out of
`Enum.reduce/3` and the whole `replay_all_pending/0` call crashes for every tenant, not
just the broken one.

**Mutant 2 — `MigrationReplayBoot.start_link/1` propagates instead of always returning
`:ignore`**: changes `start_link/1` to `if error != [], do: raise("boot replay failed"),
else: :ignore` after `run_replay/0`. Test case 4 above is run against this mutant and
expected (and confirmed) to fail — it deliberately breaks one tenant before calling
`start_link/1`, so under this mutant the call raises instead of returning `:ignore`.
