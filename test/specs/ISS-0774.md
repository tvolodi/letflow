## Criterion

Before this fix, `tenant_role.name` was a single, untyped string column written from
two structurally unrelated call sites: (1) platform-permission provisioning, binding
one of `Letflow.Api.Authorization.roles/0`'s six closed literal strings, and (2)
process-definition `HUMAN_TASK` routing, binding an arbitrary,
process-definition-chosen name (e.g. `role-ops-manager`, from
`test/fixtures/simulation/swiftroute/process_route_approval.yaml`'s `ops-review` node).
`Letflow.Identity.list_effective_role_names/2` read both indiscriminately and fed the
result through `Authorization.roles_from_strings/1`, which silently drops any name
outside the closed set. A user whose *only* `tenant_role` membership was a
process-routing name therefore had their effective platform-role set silently reduced
to `[]`, with no distinguishing signal from "holds genuinely no roles at all" — the
live SwiftRoute/T-0140 diagnostic (Marco/Alice, `role-ops-manager`/`role-ceo`) that
discovered this issue. The fix adds a `kind :: :platform_role | :process_routing_role`
column, makes `upsert_role/4` validate `kind: :platform_role`'s name against the closed
set (loudly, before any DB write), filters `list_effective_role_names/2` to
`kind: :platform_role` rows only, and adds `check_platform_role_coverage/2` as an
explicit, named, provisioning-time signal for the gap.

| Acceptance criterion | Proved by |
|---|---|
| AC2 "either succeed, or receive an explicit, actionable... signal" — provable by a test | T3 (`check_platform_role_coverage/2` names the gap, then clears once the companion grant exists) |
| AC2 "successfully access... tasks assigned to their role/group" once the design's remedy is applied | T4, second scenario (200 + task visible) |
| AC2/AC3 request-time behavior for a process-routing-role-only caller is unchanged (still 403), now for the structurally correct reason | T4, first scenario, read together with T2/T3 (T4 alone cannot distinguish *why* it is 403 — see T4's own rationale below) |
| Upsert-time validation is asymmetric by design (§2.3) — a typo'd platform-role grant is rejected loudly, not silently mis-tagged | T1 |
| `list_effective_role_names/2`'s kind filter is the actual mechanism closing the silent-`[]` bug | T2 |
| AC3 SwiftRoute/T-0140 UAT unblock | Not a new automated test on its own (UAT-RUNNER's territory) — T4's first scenario *is* the SwiftRoute persona shape (same role name, `role-ops-manager`, same fixture file) reproduced under `mix test`; design §4 states the fixture/provisioning-script change (add each persona's `TASK_WORKER` companion membership) this design's decision requires before the real UAT scenario passes |

## Test cases

### T1 — `test/letflow/role_registry_test.exs`, `describe "ISS-0774 T1 — upsert_role/4 kind-conditional name validation (design §2.3/§3)"`

Four tests:

1. `kind: :platform_role` with a name IN the six recognized literals (`"TASK_WORKER"`)
   succeeds. Exists to prove the *positive* validation path still works, not just the
   rejection.
2. `kind: :platform_role` with a name NOT in the closed set (`"PLATFORM_ADMN"`, a
   plausible typo of `"PLATFORM_ADMIN"`) returns
   `{:error, :name_not_a_recognized_platform_role}` **and writes no row** — the direct
   proof this is a loud, before-any-write rejection, not a silently-created dead
   binding (the exact failure mode ISS-0774's root cause describes for a mistyped
   platform-role grant). Both the return value AND the absence of a persisted row are
   asserted, since "loud" specifically means both.
3. `kind: :process_routing_role` accepts a name outside the closed set
   (`"role-ops-manager"`, the actual SwiftRoute fixture value) — proves the
   open-ended domain has no literal-set check at all, matching §2.3's asymmetric
   design.
4. `kind: :process_routing_role` also accepts one of the six platform-role literal
   strings — proves the two domains are distinguished by the explicit `kind`
   parameter alone, not by inspecting the name's shape (guessing at a string's shape
   was itself part of ISS-0774's root cause).

### T3 — `test/letflow/role_registry_test.exs`, `describe "ISS-0774 T3 — check_platform_role_coverage/2 (design §2.5/§3, AC2 'provable by a test')"`

Four tests:

1. A user holding only a `role-ops-manager` (`:process_routing_role`) membership gets
   `{:error, {:missing_platform_role, %{held_process_routing_roles: ["role-ops-manager"], held_platform_roles: []}}}`
   — the exact-gap-naming AC2 asks for, asserted as a full structural equality (not
   just pattern-matching the error tag), since AC2's own wording is "actionable" and a
   partial match would not prove the gap is *named*.
2. The SAME user, after also being granted a `TASK_WORKER` (`:platform_role`)
   membership via a second group, gets `:ok` — proves the check transitions cleanly
   once the design's own prescribed remedy (a companion platform-role grant) is
   applied, checking the gap is still reported before the grant (not merely "eventually
   :ok") as an explicit intermediate assertion.
3. A user holding at least one platform role (and zero process-routing roles) gets
   `:ok` — the ordinary case, proving `:ok` isn't merely "no process-routing roles held
   coincidentally".
4. A user with **no** `tenant_role` membership at all gets `:ok`, not an error — proves
   this function's documented "not this function's scenario" branch: an
   entirely-unprovisioned user isn't a coverage gap, just an unprovisioned one.

### T2 — `test/letflow/identity_test.exs`, `describe "list_effective_role_names/2 (ISS-0774 T2 — design §2.4/§3)"`

One test, two assertions in sequence against the same user: with only a
`role-ops-manager` (`:process_routing_role`) membership,
`list_effective_role_names/2 == []`; after additionally granting a `TASK_WORKER`
(`:platform_role`) membership, `list_effective_role_names/2 == ["TASK_WORKER"]` — the
process-routing name never appears in either state. This is the test that isolates the
kind filter itself, independent of any router/plug machinery — T4 below confirms the
request-time *symptom* is unchanged, but only T2 proves *why* (the filter, not an
accidental cancellation elsewhere in the request pipeline).

### T4 — `test/letflow/routers/tasks_test.exs`, `describe "ISS-0774 T4: GET /tasks/inbox, process-routing-role-only vs. +companion platform role"`

Two tests, both reproducing the exact SwiftRoute/T-0140 fixture shape (group bound to
`role-ops-manager`, the literal role name used by
`test/fixtures/simulation/swiftroute/process_route_approval.yaml`'s `ops-review` node;
a real `HUMAN_TASK`-routed task assigned to that role so an actual assignable task row
exists). Unlike this file's other tests, which hand-type a `roles:` list into
`build_conn/4`, both tests derive that list via a **real call to
`Identity.list_effective_role_names/2`** against real `tenant_role`/`group_members` rows
— the same function `Letflow.Plugs.AuthPipeline` calls in production — so the router-level
result is tied to the actual identity-layer fix rather than merely re-exercising
`build_conn/4`'s own bypass of `AuthPipeline`.

1. Process-routing-role-only caller: `Identity.list_effective_role_names/2` is asserted
   `== []` directly (this assertion alone is what a "kind filter removed" mutant
   breaks — see Mutant 1 below), then `GET /tasks/inbox` -> `403`,
   `problem+json`. This is the regression guard that the *previous* silent-`[]`-then-403
   bug and the *current*, intentional no-platform-role-held-then-403 behavior are not
   accidentally conflated by this test's assertions alone — T2/T3 are what prove *why*
   it's 403.
2. Same caller, plus a companion `TASK_WORKER` (`:platform_role`) membership via a
   *second*, separate group (matching real provisioning shape — a platform-role grant
   is not the same group as a routing-role's):
   `Identity.list_effective_role_names/2 == ["TASK_WORKER"]`, then `GET /tasks/inbox`
   -> `200`, and the task routed to `role-ops-manager`'s group is present in the
   response body — the direct proof of AC2's "successfully access... tasks assigned to
   their role/group" once the design's own remedy is applied.

## Regression proof — code-did-not-exist case (WF-03 §"When the pre-fix failure is
'the code under test does not exist'")

`upsert_role/4`'s `kind` parameter, `tenant_role.kind`, `list_effective_role_names/2`'s
filter, and `check_platform_role_coverage/2` are all new in this fix (`upsert_role/3`
had no `kind` at all; the column did not exist). A pre-fix run of these tests would fail
with `UndefinedFunctionError`/`Ecto.QueryError` for every test in the affected files —
proving these tests exercise *new* code, but nothing about whether they discriminate a
correct implementation from a wrong one. Per WF-03, the fail-first requirement is
therefore satisfied by mutating the shipped logic instead, in a throwaway worktree
(`/tmp/claude-1001/.../scratchpad/wt-iss0774-testdesign`), reverting each mutant via
`git checkout --` and verifying the revert (`git status --porcelain` clean for the
mutated file, full re-run green).

**Mutant 1 — `lib/letflow/identity.ex`: removed `list_effective_role_names/2`'s
`tr.kind == :platform_role` filter** (restores the exact pre-fix unfiltered read that
caused ISS-0774's silent-`[]` bug).

- Ran `test/letflow/identity_test.exs` + `test/letflow/routers/tasks_test.exs`:
  **112/115 passed, 3 failed.**
- Failures: T2's own test (`list_effective_role_names/2 (ISS-0774 T2 ...)`), and BOTH
  T4 tests — T4 fails not on the final HTTP status (which stays 403/200 either way,
  since `Authorization.roles_from_strings/1`'s own closed-set drop still filters an
  unrecognized name downstream) but on T4's own `assert effective_roles == [...]`
  assertion against the real `Identity.list_effective_role_names/2` return value, which
  the mutant changes directly. This confirms T4's design choice to assert on the real
  function's output (not just the eventual HTTP status) genuinely adds discriminating
  power beyond what T2 alone already covers.
- Reverted via `git checkout -- lib/letflow/identity.ex`; `git status --porcelain
  lib/letflow/identity.ex` empty; re-ran the same two files: **115/115 passed.**

**Mutant 2 — `lib/letflow/identity/role_registry.ex`: collapsed
`validate_platform_role_name(:platform_role, name)` to unconditionally `:ok`**
(restores the pre-fix silent-dead-binding behavior T1 exists to catch — a typo'd
platform-role name would be accepted and written instead of rejected).

- Ran `test/letflow/role_registry_test.exs`: **22/23 passed, 1 failed** — exactly T1's
  "fails loudly with `{:error, :name_not_a_recognized_platform_role}`... not a silent
  dead binding" test, and no other test in the file (confirms the mutant's blast radius
  matches its target precisely: T1's other three tests and every pre-existing test in
  the file are unaffected).
- Reverted via `git checkout -- lib/letflow/identity/role_registry.ex`; `git status
  --porcelain lib/letflow/identity/role_registry.ex` empty; re-ran:
  **23/23 passed.**

Both mutants target the specific traps their respective fix pieces exist to handle (the
kind filter; the closed-set validation) rather than arbitrary breakage, per WF-03's
requirement. TEST-DESIGN-VALIDATOR is expected to independently re-apply at least one
of these two mutants and reproduce its reported count.
