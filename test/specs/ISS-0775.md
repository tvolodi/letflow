# Test Spec: ISS-0775 — `resolve_group_ids_for_role_names/2`'s write path is not
# scoped by `tenant_role.kind`

**Issue:** ISS-0775 (MINOR, GH-1684, Q-773). **Run:** `WF03-ISS0775-20260921`, WF-03
Step 4.
**Design:** `lib/letflow/design/iss-0775-oidc-role-sync-kind-scoping.md`, §2.1 (fix
mechanism), §3 (test plan T1-T3).
**Fix under test:** `lib/letflow/identity.ex` — `resolve_group_ids_for_role_names/2`
(private, called only from `sync_role_claims_from_token/3`) gains one `where`
predicate: `t.kind == :platform_role`.
**Test file:** `test/letflow/identity_test.exs`, new `describe "sync_role_claims_from_token/3
— kind-scoped write path (ISS-0775)"` block (placed immediately after the existing
`describe "sync_role_claims_from_token/3 (ISS-0773)"` block, per the design's own
"either placement satisfies this design" note). `bind_role_to_group!/2` widened to
`bind_role_to_group!/3`, taking an explicit `kind` param instead of always inserting
`:platform_role` — deliberately call-site-breaking; the one pre-existing call site
(the ISS-0773 self-healing-retry test) was updated to pass `:platform_role` explicitly.

## Criterion

Before this fix, `resolve_group_ids_for_role_names/2` matched every claimed OIDC role
name against `tenant_role.name` with no `kind` predicate. Since
`Letflow.Oidc.ClaimMapping.resolve_roles/2` passes whatever string list an IdP token's
configured claim path carries straight through, unfiltered and unvalidated against
`Authorization.role_from_string/1`'s closed set, a token claiming a string that happens
to match an existing `:process_routing_role`-kind `tenant_role.name` would get a
`group_members` row written for that group via `sync_role_claims_from_token/3` — HUMAN_TASK
task-assignment eligibility the token holder never legitimately earned through this
platform's own provisioning path (`RoleRegistry.upsert_role/4` + `add_group_member/3`).
The fix adds `t.kind == :platform_role` to the query, mirroring
`list_effective_role_names/2`'s existing (ISS-0774) filter, so a claimed name can now
only ever resolve to a `group_id` when it matches a `:platform_role`-kind row.

| Acceptance criterion (derived, design §6 — issue itself carries no separate AC list) | Proved by |
|---|---|
| Fix must not break the legitimate `:platform_role`-kind OIDC-claim-sync flow (REQ-378) | T1 |
| A token claiming a name matching only a `:process_routing_role`-kind row writes nothing, and the existing ISS-0773 zero-resolution warning still fires for it | T2 |
| The `kind` predicate discriminates correctly when a token claims names of BOTH kinds simultaneously in one claim list (not just when tested in isolation) | T3 |
| Write-path fix ties back to the read-path guarantee ISS-0774 already established (`list_effective_role_names/2`), not assumed to compose | T1/T2/T3 each additionally assert `list_effective_role_names/2`'s output |

## Test cases

### T1 — platform-kind claim still writes (no REQ-378 regression)

Provisions an OIDC user, binds `"TASK_WORKER"` to a fresh group via
`bind_role_to_group!("TASK_WORKER", :platform_role, schema_name)`, calls
`sync_role_claims_from_token/3` with `roles: ["TASK_WORKER"]`. Asserts exactly one
`group_members` row for that user, matching the bound group's id;
`role_claims_synced_at` is stamped (`%DateTime{}`); and
`list_effective_role_names/2` returns `["TASK_WORKER"]`. Exists to prove §2.1's added
predicate does not regress the one genuinely legitimate flow this write path serves —
the specific flow that made the issue's own suggested alternative direction (b) wrong
(design §1.2).

### T2 — routing-kind claim writes nothing, and the existing zero-resolution warning still fires

Binds `"role-ops-manager"` via `bind_role_to_group!("role-ops-manager",
:process_routing_role, schema_name)`, calls `sync_role_claims_from_token/3` with
`roles: ["role-ops-manager"]`. Asserts zero `group_members` rows;
`role_claims_synced_at` stays `nil`; `ExUnit.CaptureLog.capture_log/1` shows the
existing ISS-0773 "zero group_ids resolved" warning, naming `"role-ops-manager"` in
the claimed-roles list; and `list_effective_role_names/2` returns `[]`. This is the
direct proof of the actual fix — a claimed name that only matches a
`:process_routing_role`-kind row must resolve to nothing for that write path, and the
claim must be visibly (not silently) rejected, mirroring the existing
"non-stamping + warning" contract this function already had for a name matching no row
at all.

### T3 — one claim list holding both kinds' names writes only the platform-kind membership

Binds both `"TASK_WORKER"` (`:platform_role`) and `"role-ops-manager"`
(`:process_routing_role`) to two distinct fresh groups, then calls
`sync_role_claims_from_token/3` with `roles: ["TASK_WORKER", "role-ops-manager"]` — both
names claimed in the SAME token. Asserts exactly one `group_members` row, matching the
`"TASK_WORKER"` group's id (not the `"role-ops-manager"` group's); `role_claims_synced_at`
is stamped; `list_effective_role_names/2` returns `["TASK_WORKER"]`. This is the test
that cannot pass by accident of a single-tenant_role fixture or test ordering — T1/T2
each exercise one kind alone, so a filter that happened to match "whichever row exists"
rather than genuinely discriminating on `kind` could still pass both of them. T3 is the
one case the issue itself names explicitly ("a token claiming a role-name string that
matches an existing `tenant_role` of EACH kind").

## Regression proof — fail-first against pre-fix code (real code existed pre-fix, not the "code did not exist" case)

`resolve_group_ids_for_role_names/2` and `sync_role_claims_from_token/3` both existed,
unchanged in shape, before this fix — only one `where`-clause predicate was added
(`git show 3a153051 -- lib/letflow/identity.ex`: 10 insertions, 2 deletions, entirely
inside `resolve_group_ids_for_role_names/2`'s comment and query). So the WF-03
"pre-fix failure is the code under test did not exist" carve-out does not apply here;
fail-first was verified directly against the real pre-fix function body instead of by
mutation.

Procedure: in this worktree, temporarily replaced `lib/letflow/identity.ex` with its
pre-fix content (`git show 34930a67:lib/letflow/identity.ex`, the last commit before the
fix — `34930a67` is the design commit, `3a153051` is the fix commit, and the two differ
only in this one file per the stat above) and ran the full file:

```
mix test test/letflow/identity_test.exs
```

Result: **58/60 passed, 2 failed** — exactly:
1. `T2: a claimed name matching a :process_routing_role-kind row writes nothing, and the
   zero-resolution warning fires`
2. `T3: one token claiming both a :platform_role-kind and a :process_routing_role-kind
   name (that collide across kinds) writes only the platform-kind membership`

T1 passed even pre-fix, as expected (a `:platform_role`-kind claim was never broken by
this bug — it's the no-regression control, not a discriminating test). No other test in
the file was affected, confirming the two new tests' blast radius matches the fix
precisely.

Reverted via `git checkout -- lib/letflow/identity.ex`; `git status --porcelain
lib/letflow/identity.ex` was empty afterward (confirmed clean revert). Re-ran the same
file against the real (fixed) code: **60/60 passed.**
