# Test Spec: ISS-0777 — `entity_type`/`attribute` identifier-format validation

**Issue:** `docs/issues/ISS-0777.yaml` (BLOCKER, blocks REQ-375 AC5).
**Design:** `lib/letflow/design/iss-0777-entity-type-identifier-validation.md`.
**Fix (WF-03, commit `08e4f387` on `feature/WF03-ISS0777-20260921`):**
- `lib/letflow/platform/migration_rollout.ex` — `start_rollout/3` gains a
  fail-fast identifier-format check before its first `Repo` call.
- `lib/letflow/tenant_provisioning.ex` — `register_column_promotion/4` gains
  the same check, independently, before `resolve_tenant_ids/1`.
- `lib/letflow/routers/platform_migrations.ex` — `handle_start/1` maps the two
  new `{:error, :invalid_entity_type | :invalid_attribute}` results to a clean
  RFC 9457 422 body, via the existing `Validation.problem/1` pairing.
Passed SECURITY-REVIEWER and REVIEWER before this test-design run.

## Bug recap

Before this fix, `POST /platform-migrations/rollouts` with a hyphenated
`entity_type` (e.g. `"pl-rollout-95a456dd"`, REQ-375's own e2e fixture
convention) reached `Letflow.TenantProvisioning.checked_table_name/1`'s
`ArgumentError` raise unhandled, surfacing as a bare HTTP 500. No caller on the
write path (`@start_schema`, `register_column_promotion/4`,
`start_rollout/3`) validated identifier format before that point — the value
was only checked when DDL actually ran, several calls and one `Repo.insert`
deep. Two independently-reachable call sites needed the same fix:
`Letflow.Platform.MigrationRollout.start_rollout/3` (the only caller-facing
entry point for this router) and `Letflow.TenantProvisioning.register_column_promotion/4`
(also reachable directly from `entities/definitions.ex`, bypassing
`start_rollout/3` entirely).

## Why this is not a "code under test did not exist" case

Every function touched by the fix (`start_rollout/3`,
`register_column_promotion/4`, `checked_table_name/1`) already existed and was
already reachable pre-fix (REQ-374/REQ-297) — the defect is a missing
validation branch inside existing functions, not new functionality replacing
an absent no-op. WF-03's "code under test did not exist" mutant-reporting
requirement therefore does not apply here; the ordinary pre-fix/post-fix
behavior-diff standard applies instead (see "Pre-fix vs. post-fix
verification" below).

## Criteria (from the design doc §5/§6)

1. `POST /platform-migrations/rollouts` with the issue's exact repro
   `entity_type: "pl-rollout-95a456dd"` returns a clean 422 (not a 500/crash),
   with an RFC 9457 body naming `field: "entity_type"`,
   `constraint: "identifier_format"`.
2. The same holds for an invalid `attribute`.
3. Rejection happens before any write — no `platform_migration_rollouts` row,
   no `entity_column_promotions` row, for the rejected pair.
4. `Letflow.Platform.MigrationRollout.start_rollout/3` returns
   `{:error, :invalid_entity_type}` / `{:error, :invalid_attribute}`
   immediately, with zero `Repo` writes of any kind (the fail-fast property
   SECURITY-REVIEWER specifically verified).
5. `Letflow.TenantProvisioning.register_column_promotion/4` rejects the same
   invalid input independently when called directly (not just via the
   rollout path) — proving the defence-in-depth layer works on its own.
6. No regression: a fully valid `entity_type`/`attribute` pair (including the
   legitimate underscored form of the issue's own fixture value) still
   succeeds exactly as before.

## Test files

1. `test/letflow/routers/platform_migrations_test.exs` — new
   `describe "ISS-0777 -- identifier-format validation at the router boundary"`
   block, added to REQ-374's own router test file (established in the same
   WF-02 run this issue was found during). `Letflow.DataCase`, `async: false`,
   direct `Letflow.Routers.PlatformMigrations.call/2` dispatch, same
   conventions as every other test in that file.
   - **Test A** — the issue's own exact repro value
     (`entity_type: "pl-rollout-95a456dd"`): 422, `field: "entity_type"`,
     `constraint: "identifier_format"`, `received` echoes the caller-supplied
     value, no `Rollout`/`ColumnPromotion` row written. Covers criteria 1, 3.
   - **Test B** — same shape for an invalid `attribute`
     (`"some-attr"`, valid `entity_type`): 422, `field: "attribute"`. Covers
     criterion 2.
   - **Test C** — table-driven boundary coverage: uppercase, leading digit,
     65-char (over the 64-char cap), space, dot — each rejected 422, no row
     written. Exercises every distinct shape `DDL.valid_identifier?/1`'s regex
     (`^[a-z][a-z0-9_]{0,63}$`) excludes, not just the hyphen case, so a future
     change to the regex's boundary (off-by-one on length, wrong anchor) has a
     failing test to catch it.
   - **Test D** — the legitimate underscored form of the same fixture value
     (`attribute: "pl_rollout_95a456dd"`, real `entity_type: "invoice"`)
     succeeds with 200 and a real rollout id. Proves the fix does not
     over-reject — this exercises the exact value most likely to be
     mistakenly excluded by an off-by-one in the regex, since it differs from
     the rejected Test A value by exactly the one character class the fix
     must distinguish (hyphen vs. underscore). Covers criterion 6.

2. `test/letflow/platform/migration_rollout_test.exs` — new
   `describe "ISS-0777 -- start_rollout/3 rejects an invalid identifier before any write"`
   block, added to REQ-374's own context-module test file. `Letflow.DataCase`,
   `async: false`, direct `MigrationRollout.start_rollout/3` calls (bypassing
   HTTP).
   - Invalid `entity_type` → `{:error, :invalid_entity_type}`, with
     `Repo.aggregate/2` row counts on `Rollout`, `Outcome`, and
     `ColumnPromotion` captured before and after the call and asserted equal
     (not merely that the eventual HTTP response would be 422) — proves the
     check runs before `Repo.get_by(Rollout, ...)`, the function's first
     `Repo` call. Covers criterion 4.
   - Invalid `attribute` (valid `entity_type`) → `{:error, :invalid_attribute}`,
     same zero-write proof.
   - Both invalid → deterministically `{:error, :invalid_entity_type}` (checked
     first, per design §4.1's stated order).
   - No regression: a fully valid pair still returns `{:ok, rollout_result()}`
     and produces a real outcome for the target company, unchanged from
     REQ-374's own existing happy-path coverage in this same file. Covers
     criterion 6.

3. `test/letflow/tenant_provisioning/column_promotion_test.exs` — new
   `describe "ISS-0777 -- register_column_promotion/4 rejects an invalid identifier before any write"`
   block, added to REQ-297's own context-module test file. `Letflow.DataCase`,
   `async: false`, direct `TenantProvisioning.register_column_promotion/4`
   calls — **not** routed through `MigrationRollout`, so this layer's
   protection is proven independently of `start_rollout/3`'s own check
   (design §2's "belt-and-suspenders" rationale: this is the sole protection
   for `entities/definitions.ex`'s call site if its own upstream guarantee is
   ever weakened).
   - Invalid `entity_type` → `{:error, :invalid_entity_type}`, `Repo.aggregate/2`
     row count on `ColumnPromotion` scoped to that `entity_type` unchanged
     (before == after == 0) — no transaction opened, no row of any kind.
     Covers criterion 5.
   - Invalid `attribute` (valid `entity_type`) → `{:error, :invalid_attribute}`,
     same zero-write proof.
   - Both invalid → deterministically `{:error, :invalid_entity_type}`.
   - No regression: the existing REQ-297 AC1 happy path (real,
     `Validator`-checked `entity_type`/`attribute`) still succeeds unchanged —
     confirms the new `cond` branch is a pure prefix to the existing function
     body, not a rewrite of it. Covers criterion 6.

## Pre-fix vs. post-fix verification

Verified directly rather than asserted: checked out the pre-fix commit
(`08e4f387^`, i.e. `HEAD` immediately before ISS-0777's fix commit) into a
throwaway worktree and ran the new router-level Test A
(`entity_type: "pl-rollout-95a456dd"`) against it.

- **Pre-fix:** the request raises an unhandled `ArgumentError` inside
  `checked_table_name/1` (surfaces as an ExUnit test-crash trace, not a
  status-code assertion failure — the response is never sent because the
  request process crashes first), confirming the issue's own repro is real
  against the code this fix touches.
- **Post-fix (`08e4f387`, this branch's tip):** the identical request returns
  a clean `422` with the `identifier_format` `FieldError` body, no crash.

This directly satisfies "shown to fail against the pre-fix code and pass
against the fix" without needing a mutant-testing pass (this is not a
"code under test did not exist" case — see above).

## Out of scope (design doc §6.4)

`checked_table_name/1`'s own `ArgumentError` raise is not deleted or converted
by this fix, and no test in this suite asserts it no longer exists — only that
it is no longer *reachable* via `POST /rollouts` for a value the API accepts.
A direct unit test of that raise still firing for a row that bypassed
`register_column_promotion/4` (simulating the invariant violation via a raw
`Repo.insert!`) is optional per the design and not added here — not required
to close this issue.
