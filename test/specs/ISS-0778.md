# Test spec: ISS-0778 — no seeding path for REQ-378's DB-backed platform-role sync

**Run:** WF03-ISS0778-20260922 · Step 4 (TEST-DESIGNER) · **Design:**

## Issue's stated acceptance criterion

"A freshly-provisioned tenant's intended admin user can authenticate and reach a
PLATFORM_ADMIN-gated endpoint without manual DB bootstrap." The design's §5 lays out
a four-tier test plan (T1-T4), reasoned bottom-up so a failure at any level
localizes the regression precisely rather than only proving the outermost behavior.
This spec follows that plan exactly.

## T1 — `RoleRegistry.seed_default_platform_role_groups/1` (design §3.1/§2.4)

**Test:** `test/letflow/role_registry_test.exs`, describe block "ISS-0778 T1 —
seed_default_platform_role_groups/1 (design §3.1/§2.4)", 2 tests:

1. *"seeds all six platform-role literals as group+tenant_role bindings, in
   Authorization.roles/0's own order, and a second call converges on the same
   bindings (no duplicates)"* — calls the function against a freshly-migrated
   tenant schema, asserts `length(roles) == 6`, names match
   `Letflow.Api.Authorization.roles/0` in its own declared order, every row is
   `kind: :platform_role`, exactly 6 `groups`/`tenant_role` rows exist (re-selected
   from Postgres, not trusted from the return value). Calls it a **second time**
   and asserts identical `group_id`s and still-6 row counts — the idempotency
   claim design §2.4 makes mandatory (both the normal onboarding-creation path and
   `TenantOnboarding.recover_provisioning/1` must be safe to call more than once).
2. *"against a tenant schema that already has unrelated process-routing-role
   bindings, only the six platform-role names are affected"* — proves the seeding
   function is scoped to the platform-role literal set, not "every row in
   `tenant_role`" (the ISS-0774 domain distinction this codebase already draws).

**Why these exist, not just a restatement of the criterion:** the design's core
claim is "seed all six, idempotently" (§2.1 explains why all six, not just
`PLATFORM_ADMIN` — the issue's own motivating symptom). A test asserting only
`{:ok, _}` would not distinguish a correct implementation from one that seeds one
role, seeds duplicates on a second call, or silently touches unrelated rows.

## T2 — `sync_role_claims_from_token/3` genuinely resolves the seeded binding (design §0)

**Test:** `test/letflow/identity_test.exs`, describe block "ISS-0778 T2:
sync_role_claims_from_token/3 after seeding", 2 tests:

1. *"before seeding: PLATFORM_ADMIN claim resolves to zero grants; after seeding,
   the SAME claim/user resolves and syncs"* — reproduces the issue's own root
   cause directly (a claimed `"PLATFORM_ADMIN"` role resolves to `role_claims_synced_at:
   nil` and `list_effective_role_names/2 == []` before any `tenant_role` row
   exists), then calls `RoleRegistry.seed_default_platform_role_groups/1` and
   re-runs the **identical** `sync_role_claims_from_token/3` call against the
   **same** user — now stamps the marker and resolves
   `["PLATFORM_ADMIN"]`. The explicit before/after contrast on the same user is
   what proves the seeded row is what closed the gap, not a coincidental pass.
2. *"seeding closes the gap for all six platform-role literals (design §2.1)"* —
   loops over all six `Authorization.roles/0` literals, provisioning a distinct
   user per literal and confirming each syncs and resolves — extends test 1's
   single-role proof to the "why all six" design decision.

**Why this exists, not just a restatement:** the design's own §0 states the sync
mechanism (`sync_role_claims_from_token/3`, `resolve_group_ids_for_role_names/2`)
was **already correct** before this fix — the gap was purely a missing data-seeding
step. A test that only exercised the seeding function in isolation (T1) would not
prove that the seeded row is genuinely *usable* by the real, unmodified sync
mechanism; this tier is that proof.

## T3 — `TenantOnboarding.provision_and_migrate/1` seeds roles as part of real provisioning (design §3.3)

**Test:** `test/letflow/tenant_onboarding_test.exs`, describe block "ISS-0778 T3:
provision_and_migrate/1 seeds platform roles as part of real provisioning", 2
tests:

1. *"a freshly-provisioned tenant has all six tenant_role rows present, with no
   extra manual step"* — calls `provision_and_migrate/1` (no direct
   `RoleRegistry`/`Identity` call by the test), then queries `tenant_role`
   directly under the returned `schema_name` — six rows, `kind: :platform_role`,
   names matching `Authorization.roles/0`. Confirms the tenant reached `:active`
   too, not merely that seeding succeeded in isolation.
2. *"seeding failure blocks activation (tenant stays :migrating) and is
   recoverable once the failure clears"* — the negative half design §3.3
   explicitly requires. See "Fixture mechanics" below for how this failure is
   forced deterministically. Asserts `{:error, {:role_seeding_failed,
   :group_not_found}}`, the tenant stays `:migrating` (not `:active`), zero
   `tenant_role` rows exist (seeding halted on the first role name in
   `Authorization.roles/0`'s order before any of the other five were attempted),
   then — after removing the forced failure — `recover_provisioning/1` (AC9's
   entry point) converges cleanly: all six roles present, tenant `:active`.

**Why these exist, not just a restatement:** T1 proves the seeding function works
in isolation; this tier proves the **onboarding orchestration itself** invokes it,
matching the issue's own AC ("no extra manual step"). The failure-path test proves
design §3.3's explicit ordering claim — a role-seeding failure must **not** let a
tenant reach `:active` with its role bindings unseeded, which would reproduce
ISS-0778 under a different trigger (a role-seed DB error instead of "nobody ever
wrote the seeding code").

### Fixture mechanics for the failure-path test (deterministic, not a race)

Every one of `RoleRegistry`'s own explicit validation branches (name format, the
closed platform-role-name-literal check) is structurally unreachable for a name
that already IS one of `Authorization.roles/0`'s own six literals — the seeding
loop never passes anything else. The only two failure modes actually reachable
through `provision_and_migrate/1`'s real call path are (a) a genuine concurrent
delete racing `do_upsert_role/4`'s `Repo.get(Group, group_id)` check, and (b)
infrastructure-level corruption (e.g. a dropped unique index), which Ecto does
**not** convert into a graceful `{:error, _}` — it raises an uncaught
`Postgrex.Error` instead, which would crash `provision_and_migrate/1` rather than
exercise its documented tagged-error branch. (a) is unseeded-randomness-dependent
(forbidden, `docs/guides/test_developer_guide.md` principle 3); (b) doesn't produce
the graceful shape the design documents at all.

The test instead installs a real, deterministic Postgres `AFTER INSERT` trigger on
the tenant schema's own `groups` table that deletes the just-inserted
`"PLATFORM_ADMIN"` row, synchronously, inside the **same transaction** as the
`INSERT` itself — every single time, no timing dependency. This exploits
`RoleRegistry.get_or_create_group_by_name/2`'s own existing defensive post-insert
verification (`insert_group/2`, written for the "on_conflict :nothing raced against
a concurrent insert" case: `if Repo.get(Group, id, prefix: prefix) do ... else
fetch_group_by_name(...) end`) — the trigger makes that check genuinely observe a
vanished row every time, so `get_or_create_group_by_name/2` falls through to
`fetch_group_by_name/2`, finds nothing either, and returns `{:error,
:group_not_found}` for real. No modification to any `lib/` code; a real Postgres
DDL fixture, not a mock (DIRECTIVE T-1).

## T4 — end-to-end proof of the issue's own stated AC (design §5, §6)

**Test:** `test/letflow/plugs/iss0778_platform_role_seeding_e2e_test.exs`
(`Letflow.Plugs.Iss0778PlatformRoleSeedingE2eTest`), 1 test:

*"POST /onboarding provisions a tenant; a PLATFORM_ADMIN-claiming OIDC token
reaches a PLATFORM_ADMIN-gated route; a non-privileged token still 403s on the same
tenant"* — dispatches a real `POST /api/v1/onboarding` (PLATFORM_ADMIN-authenticated
via a real API token) through `Letflow.Router.call/2`, gets `201`, confirms the
resulting tenant is `:active`. Then dispatches `GET /api/v1/tenants`
(`:TenantsManage`) with a real OIDC bearer token (via a new
`Letflow.Oidc.Iss0778PlatformAdminTokenVerifierDouble` sentinel claiming
`PLATFORM_ADMIN`) — `200`, `"PLATFORM_ADMIN" in auth_context.roles`,
`auth_context.tenant_id` is the freshly-onboarded tenant. Negative control:
restores the suite's default double and hits the **same** route on the **same**
tenant with the existing `"valid-test-token"` sentinel (claims `["VIEWER"]`) —
`403`, `auth_context.roles == []` (not `["VIEWER"]` — `AuthPipeline`'s OIDC branch
attaches the live, DB-derived role set, `Identity.list_effective_role_names/2`,
never the JWT's own claimed roles directly; `"VIEWER"` is not one of the six seeded
literals, so it resolves to nothing).

No step in this test calls `Letflow.Identity.add_group_member/3`,
`Letflow.Identity.RoleRegistry.upsert_role/4`, or any other manual bootstrap
function directly — every grant this test observes is produced by the real
onboarding-provisioning path (T3's mechanism) plus the real, unmodified OIDC
JIT-sync path (T2's mechanism), exercised together exactly as a real deployment
would exercise them. This is the direct, executable proof of the issue's own
stated acceptance criterion, and of the exact manual step UAT-RUNNER had to perform
by hand during REQ-375's testing.

**Why this exists, not just a restatement:** T1-T3 each prove one layer works in
isolation or in combination with its immediate neighbor. Only this tier proves the
**full chain** — a real HTTP onboarding call through to a real HTTP
PLATFORM_ADMIN-gated request — with zero manual bootstrap, which is exactly what
the issue reports as missing and exactly what UAT-RUNNER had to work around by
hand.

### Fixture mechanics for T4's realm binding (design §6 open question, resolved)

`POST /api/v1/onboarding`'s own `@create_schema` accepts no `idp_realm_id` field at
all (confirmed by direct read, `lib/letflow/routers/onboarding.ex`), and
`Letflow.Identity.Tenant`'s own moduledoc documents `idp_realm_id` as immutable
after creation (`update_changeset/2`'s cast list structurally excludes it) — so
there is no *supported* path to bind a freshly-onboarded tenant to a specific OIDC
realm through this codebase's public API at all. The test resolves this the same
way `test/letflow/plugs/iss0736_oidc_live_revocation_test.exs` already resolves an
adjacent gap: `Letflow.Support.BpmDefaultRealmDisplacement.displace!/0` takes
exclusive, test-owned control of the `"bpm-default"` realm the suite's OIDC test
doubles already recognize, then the test binds the freshly-onboarded tenant to that
realm directly via `Repo.update_all/2` (a raw, changeset-bypassing write — the only
way to set `idp_realm_id` post-creation at all) — standing in for the out-of-band
IdP-realm-configuration step a real deployment's operator performs once a new
tenant is provisioned (explicitly out of this codebase's scope, design §1/§4). This
is realm/IdP-configuration plumbing, not a `Letflow.Identity`/`RoleRegistry`
role-bootstrap call — it sets up *which* tenant a token's `iss` claim resolves to,
not the platform-role grant itself.

`test/support/iss0778_platform_admin_token_verifier_double.ex` is a new, additive
`Letflow.Oidc.TokenVerifier` double (sentinel `"iss0778-platform-admin-token"`,
realm `bpm-default`, claims `["PLATFORM_ADMIN"]`) — the existing
`Letflow.Oidc.TokenVerifierDouble` (`"valid-test-token"`, `["VIEWER"]`) and
`Letflow.Oidc.Iss0736RoleClaimTokenVerifierDouble` (`"iss0736-role-claim-token"`,
`["PROCESS_OPERATOR"]`) are both unmodified — neither can claim `PLATFORM_ADMIN`.

## "Code under test did not exist" — mutation-testing evidence (WF-03, non-existence case)

`RoleRegistry.seed_default_platform_role_groups/1`, the new `TenantOnboarding`
seeding step, and the T4 endpoint's success path are all **new** logic this fix
adds — the fail-first requirement against pre-fix `main` is trivially satisfied
(pre-fix, `RoleRegistry.seed_default_platform_role_groups/1` is
`UndefinedFunctionError`; `provision_and_migrate/1` has no third `with` clause).
Per `docs/agents/workflows/WF-03_issue_resolving.md`'s "When the pre-fix failure is
'the code under test does not exist'" section, that alone proves nothing about
whether the new tests discriminate a correct implementation from a wrong one — so
two mutants were applied directly to this branch's shipped code (in this worktree,
`git checkout --` reverted, revert verified below), each targeting a specific trap
the design exists to handle:

### Mutant 1 — drop the role-seeding step from `provision_and_migrate/1`'s `with` chain

`lib/letflow/tenant_onboarding.ex`: removed the third `with` clause
(`{:ok, _tenant_roles} <- seed_platform_roles(registration.schema_name)`) entirely,
simulating "the fix's onboarding-wiring never happened" (design §2.2's core claim —
seeding must run as part of the real orchestration, not merely exist as a callable
function).

```
mix test test/letflow/role_registry_test.exs test/letflow/identity_test.exs \
  test/letflow/tenant_onboarding_test.exs \
  test/letflow/plugs/iss0778_platform_role_seeding_e2e_test.exs
```

**Result: 88/91 passed, 3 failed** — exactly T3's both tests (success case: zero
`tenant_role` rows seeded; failure-path case: `provision_and_migrate/1` now
succeeds unconditionally, so the sabotage-trigger assertion of `{:error,
{:role_seeding_failed, _}}` fails) and T4's full end-to-end test (the OIDC request
403s instead of 200, since no roles were ever seeded). T1 and T2 (unaffected — both
call `RoleRegistry`/`Identity.sync_role_claims_from_token/3` directly, not through
`TenantOnboarding`) correctly still pass, confirming the mutant is localized to
exactly the onboarding-orchestration layer it targets.

Reverted: `git checkout -- lib/letflow/tenant_onboarding.ex`. Verified:
`git status --porcelain lib/ test/` showed only this run's legitimate test-file
changes (no `lib/` diff), and the full 4-file suite re-ran to `Result: 91 passed`
(after mutant 2 below, in the same verification pass).

### Mutant 2 — wrong `kind` tag in `seed_default_platform_role_groups/1`

`lib/letflow/identity/role_registry.ex`: changed `upsert_role(name, :platform_role,
group_id, opts)` to `upsert_role(name, :process_routing_role, group_id, opts)` —
simulating the exact ISS-0774 conflation this domain distinction exists to prevent
(design §2.1's "why all six" reasoning depends on every seeded row genuinely being
tagged `kind: :platform_role`, since `list_effective_role_names/2` and
`resolve_group_ids_for_role_names/2` both filter on that column).

```
mix test test/letflow/role_registry_test.exs test/letflow/identity_test.exs \
  test/letflow/tenant_onboarding_test.exs \
  test/letflow/plugs/iss0778_platform_role_seeding_e2e_test.exs
```

**Result: 86/91 passed, 5 failed** — T1's first test (asserts `kind ==
:platform_role` on every seeded row), both T2 tests (a `:process_routing_role`-kind
binding is invisible to `resolve_group_ids_for_role_names/2`'s
`kind == :platform_role` filter, so the sync still resolves to zero grants even
post-"seeding"), T3's success test (asserts `kind: :platform_role` on the six rows
`provision_and_migrate/1` produces), and T4's end-to-end test (the OIDC request
still 403s — the seeded rows exist but are the wrong domain, so
`sync_role_claims_from_token/3` never grants the claim). T3's failure-path test
correctly still passes (unaffected — it never reaches a successful seed to check
`kind` on).
