# ISS-0782 — Users admin screen routing regression

Run: `WF03-ISS0782-20260923`. Fixes `web/src/api/identity.ts`'s
`usersApi.list/get/create/update` and `rolesApi.list` hardcoding nonexistent
`/api/v1/users*` / `/api/v1/admin/*` paths instead of the real,
router-backed `/api/v1/identity/*` mount (`lib/letflow/plugs/api_pipeline.ex`
only ever forwards `/identity`). This broke the entire Users admin screen
against any real backend, for every tenant. Fix commit: `2e36f8c2`.

## Why existing coverage didn't catch this

Per ISSUE-FIXER's diagnosis (`handoffs/WF03-ISS0782-20260923/step-01-issue-fixer-diagnose.json`):
the only test touching `identity.ts` before this run was
`web/src/api/__tests__/identity.removeMembers.test.ts` (ISS-0736's regression
test), which covers exactly one `groupsApi` call and nothing in
`usersApi`/`rolesApi`. `web/tests/e2e/f5-admin-users.e2e.spec.ts` already
existed and drives the real Users admin screen against a real backend, but
evidently was not exercised against a live instance recently enough to catch
this before it shipped — this is the exact "mocked-only coverage" gap the
issue's own `suggested_fix` calls out.

## Test cases added

### 1. `web/src/api/__tests__/identity.usersRoles.test.ts` (new, mocked-fetch unit level)

Mirrors `identity.removeMembers.test.ts`'s established convention: spy on
`window.fetch`, call the api function, assert the exact URL/method hit — a
real fetch-call assertion, not a mock of `client` itself.

| Test | Proves |
|---|---|
| `usersApi.list -> GET /api/v1/identity/users` | AC: `usersApi.list`'s path is the real, router-backed one, not the nonexistent `/api/v1/users` |
| `usersApi.get -> GET /api/v1/identity/users/:id` | Same for `usersApi.get` (used by `UserDetailPage.tsx` via `useAdminUser`) |
| `usersApi.create -> POST /api/v1/identity/users` | Same for `usersApi.create`, and specifically that it moved off the `/api/v1/admin/*` prefix entirely, not just off `/api/v1/users` |
| `usersApi.update -> PATCH /api/v1/identity/users/:id` | Same for `usersApi.update` — the single call site shared by both `useUpdateAdminUser` and `useDeactivateAdminUser` |
| `rolesApi.list -> GET /api/v1/identity/roles` | Same for `rolesApi.list`, used by both `UsersPage.tsx` (create-user role picker) and `UserDetailPage.tsx` (role assignments) |

This is a fast, sub-second guard against a future regression reintroducing a
wrong path literal — it does NOT by itself satisfy WF-03 Step 4's live-e2e
requirement (mocked-only coverage is exactly the class of gap that let this
ship undetected), which is why test case 2 below exists.

### 2. `web/tests/e2e/f5-admin-users.e2e.spec.ts` (existing, augmented)

Read in full before deciding this. `ADM-UI-01: user list shows required
table columns and supports search` already drives `/admin/users` through a
real login, real SPA, real backend (`API_BASE_URL`/`BPM_TEST_URL`) — its
`admin-users-table` visibility assertion WOULD already fail pre-fix (see
"Fail-then-pass proof" below), since `QueryStateBoundary`
(`web/src/components/ui/QueryStateBoundary.tsx`) renders `FetchError`
instead of the table's children on a query error, and a 404 from
`usersApi.list`/`rolesApi.list` classifies as `'fetch-failure'`
(`web/src/utils/classifyError.ts`).

Added one explicit assertion directly above the existing `admin-users-table`
check:

```ts
await expect(page.getByText('Something went wrong loading this content.')).not.toBeVisible()
```

This is the exact copy `FetchError` renders
(`web/src/components/ui/FetchError.tsx`) and the exact symptom text
UAT-RUNNER captured filing ISS-0782 ("The real screen showed 'Something went
wrong loading this content.'"). Making it explicit means a future regression
reproducing this exact routing defect fails on a clear, named assertion
instead of a bare visibility timeout on `admin-users-table` that could be
misread as a flaky-load issue.

**Pre-fix**: `web/src/api/identity.ts` temporarily overwritten in place with
`git show 2e36f8c2^:web/src/api/identity.ts`'s content (the one file the fix

— the new assertion fails, live, in a real browser against a real backend,

Working tree restored (`cp` back the post-fix file); verified byte-identical
to the committed version via `diff` (no output) and `git status --porcelain
web/src/api/identity.ts` empty.

**Post-fix**: same command, this branch's real `identity.ts`. The new
assertion now **passes** — `'Something went wrong loading this content.'` is
no longer rendered, proving ISS-0782's routing defect is fixed. The test
still does not reach a full green run in this dev environment: it fails one
assertion later, on `admin-users-table` visibility, because the page instead
renders `PermissionDenied`'s "You do not have access to this area. Contact
your tenant administrator." — a 403, not a 404. This is a **separate,
pre-existing environment gap** already independently identified in Step 1's
diagnosis (curl reproduction: `403 /api/v1/identity/users`,
`403 /api/v1/identity/roles` — a route match, so a policy denial, not a
routing miss) and corroborated live here by the backend's own log:
`sync_role_claims_from_token/3: zero group_ids resolved for a non-empty
claimed-role list -- user will read roles: [] and gain no grants
(claimed_roles=["PLATFORM_ADMIN"])`. This dev realm's `admin-user` has no
`UsersManage`/`RolesManage` group mapping — unrelated to `identity.ts`'s
path literals, not touched by this fix's scope, and not something
TEST-DESIGNER should paper over by loosening the test. **This is why Level 1
(the mocked unit test) is this run's fully-green fail-then-pass proof**;
Level 2 demonstrates the specific ISS-0782 symptom flips from present to
absent live, but a full-suite live PASS for `ADM-UI-01..04` is blocked on
this separate, already-diagnosed permission-provisioning gap in the shared
dev realm, which is outside this issue's scope to fix.

Backend (`erl.exe`) stopped after the run (`taskkill`); the shared
`letflow-postgres-1`/`letflow-keycloak-1` containers were left running and
untouched, as found.
