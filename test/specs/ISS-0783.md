# Test spec: ISS-0783 (queue Q-782 / GH-1725) — TenantSwitcher re-entrancy guard

Design doc: `lib/letflow/design/iss0783-tenantswitcher-reentrancy-guard.md`
(PASSED CODE-DESIGN-VALIDATOR and REVIEWER).
Fix file: `web/src/auth/TenantSwitcher.tsx`.
Test file extended: `web/src/auth/__tests__/TenantSwitcher.test.tsx` (was 6
tests covering REQ-384 §6.1; now 11 — the 6 original plus 5 new for this
issue, under a new `describe` block).

This is a WF-03 regression test for a fix to **existing** behavior
(`TenantSwitcher` shipped under REQ-384, PR #1728) — the standard
fail-then-pass rule applies directly, not the "code doesn't exist yet"
mutation-testing exception.

## Reachability finding (verified empirically before writing final assertions)

Two assumptions from a literal reading of the design doc's §5(a) turned out
not to be reachable through the component's real, rendered DOM, confirmed by
running probes rather than assumed:

1. **Option buttons and the retry button can never be observed
   simultaneously mounted AND `disabled=true`.** `onSelect` sets `pending`
   true in the exact same React state batch that also runs `setOpen(false)`
   (closing the menu) and, for a retry-triggered call, `setErrorSlug(null)`
   (unmounting the retry block). React 18 commits a batch atomically, so
   there is no intermediate frame where the menu or error/retry block is
   still rendered while `pending` is true. Their `disabled={pending}` wiring
   (`TenantSwitcher.tsx` lines 96 and 135) is real and correct, but only
   verifiable by reading the source, not by a runtime DOM assertion, without
   modifying the already-reviewed implementation to expose internals (out of
   scope for TEST-DESIGNER).
2. **A `disabled` React button cannot be forced to dispatch `onClick` via
   direct DOM manipulation of the `.disabled` property.** Verified by
   reading `react-dom`'s `shouldPreventMouseEvent` (checks the fiber's
   `props.disabled`, not the live DOM attribute) and confirming empirically:
   setting `element.disabled = false` on the real node and then
   `fireEvent.click`-ing it still does not invoke the handler, because
   React's own click gate reads its last-committed props, not the mutated
   DOM property. This means the "fake pointer event" bypass the design doc
   raises as a hypothetical is not constructible through
   `@testing-library` + jsdom, and a contrived same-tick nested-`act()`
   double-dispatch (which *can* slip past both the DOM guard and the
   in-function guard, per an isolated probe against a minimal reproduction)
   does not represent a realistic double-click and was excluded rather than
   used to manufacture a misleading regression assertion.

Given both findings, the trigger button (always mounted, never conditionally
rendered away) is the one element a real double-click race is testable
against, and the tests below use it plus the retry re-invocation path (which
shares the same `onSelect`) as the realistic proof of the fix.

## Acceptance criteria and test cases

**(a) Disabled while pending.**
- `TC-ISS0783-01`: after selecting an option with a deferred/unresolved
  `switchTenant` mock, the trigger button carries `disabled` and the menu
  has closed (existing, unaffected behavior). Proves the guard's visible
  effect on the one control that stays mounted throughout.

**(b) No double-invocation.**
- `TC-ISS0783-02`: a second click on the (disabled) trigger while the first
  `switchTenant` call is pending neither reopens the menu nor increases the
  call count past 1. The same is then shown for `retry`, which the design
  doc (§4) says "automatically inherits the guard" since it calls the same
  `onSelect` — clicking retry starts a second real pending call (count → 2),
  and the retry/error block unmounts in that same instant, leaving nothing
  rendered that could fire a further, redundant call.

**(c) Resets on settle, all three outcomes.**
- `TC-ISS0783-03` ('ok'/success): after the deferred promise resolves,
  `pending` resets, the trigger re-enables, and no sub-UI slug renders.
- `TC-ISS0783-04` ('error'): `pending` resets, trigger and retry both
  re-enable, the error block renders (existing behavior unaffected).
- `TC-ISS0783-05/06` ('interaction_required'): `pending` resets, trigger
  re-enables, the interaction-required block renders, and — combined with
  criterion (d) — its sign-in button is confirmed not disabled.

**(d) Sign-in button is never gated by `pending`.**
- Covered by `TC-ISS0783-05/06`'s final assertion: immediately after the
  interaction-required branch renders (right when `pending` has just reset
  to `false`, per the design doc's own timing note in §3), the sign-in
  button is not disabled. This directly confirms the reasoned exclusion in
  design doc §3 — `onSignInToTenant` never calls `switchTenant`.

**(e) No regression to the 6 pre-existing tests.**
- Verified by running the full file: `TC-REQ384-16` through `TC-REQ384-21`
  are unmodified and all still pass alongside the 5 new tests (11/11). No
  existing assertion's expected value changed.

## Fail-then-pass verification (performed, not assumed)

1. Saved the fix as a diff: `git diff main -- web/src/auth/TenantSwitcher.tsx`
   (the fix was uncommitted working-tree content on
   `feature/WF03-ISS0782-20260929`, confirmed via `git log` showing the
   file's last commit as `3fc17582`, the pre-fix REQ-384 commit).
2. Reverted the file to `main`'s pre-fix version
   (`git checkout main -- web/src/auth/TenantSwitcher.tsx`) and ran the full
   test file: **3 of the 5 new tests failed** (`TC-ISS0783-01`,
   `TC-ISS0783-02`, `TC-ISS0783-03`) — `expect(element).toBeDisabled()`
   failing because pre-fix `TenantSwitcher` has no `disabled` prop at all,
   and the menu-closed assertion failing because nothing ever disables the
   trigger to stop the reopen. `TC-ISS0783-04`/`05-06` incidentally passed
   pre-fix too (their core assertions — error/interaction-required block
   rendering and sign-in not being disabled — hold regardless of the guard,
   since pre-fix code never disables sign-in either); the 3 failures above
   are sufficient to demonstrate the new coverage exercises the actual fix.
   8/11 passed, 3/11 failed — full failing output captured in the WF-03
   session log.
3. Restored the fix (`git apply` of the saved diff, since the file was
   uncommitted) and verified `git diff main -- web/src/auth/TenantSwitcher.tsx`
   byte-for-byte matched the pre-revert saved diff. Re-ran the full file:
   **11/11 passed.**
4. `git status --short web/` after restoration shows exactly
   `M web/src/auth/TenantSwitcher.tsx` (the original fix, unchanged) and
   `M web/src/auth/__tests__/TenantSwitcher.test.tsx` (this new test
   coverage) — no stray diff on the fix file.
