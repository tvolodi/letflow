## Site 2 test (new, PASSING)

`Letflow.EngineCompleteTaskTest`, `"complete_task/3 (ISS-0784) -- a cascade
task-activation rejection is recorded with instance_id from changes.task"`.

Fixture: `graph_human_task_then_malformed_form_schema_task_end/1` — `START ->
task_a(HUMAN_TASK, well-formed) -> task_b(HUMAN_TASK, malformed form_schema) -> END`.
Completing `task_a` drives activation of `task_b`, rejecting inside
`complete_task/3`'s own `Ecto.Multi`.

Why this test exists (not "structurally identical to site 1, skip it"): design §2 row 2
states `instance_id` here is read from `changes.task.instance_id` (the already-fetched
`:task` Multi step, i.e. `task_a`'s own row) — a genuinely different sourcing path from
site 1, where `instance_id` is `create/2`'s own second positional argument. This test's
load-bearing assertion is `entry.resource_id == instance_id` where `instance_id` came
from starting the instance via `create/2` and is cross-checked against what the
*catch-all clause* independently derived from `changes.task.instance_id` — proving that
sourcing path is wired correctly, not merely "the same value as site 1 would have
produced." A secondary assertion (`reloaded_task_a.status == :pending`) proves
INV-ISS0784-3-adjacent behavior for this call site: the whole Multi, including
`task_a`'s own completion, rolled back — `complete_task/3`'s caller sees byte-identical
failure behavior to before this issue, whether or not the audit write succeeds.

**Result:** PASS (see full-suite run below).

## Site 3 test (new, FAILING — reveals a real defect, not a test-design mistake)

`Letflow.Engine.TimerWiringTest`, `"ISS-0784 site 3: a timer-fired cascade's
task-activation rejection is audited with the platform actor_id"`.

Fixture: `graph_timer_then_malformed_form_schema_task_end/2` — `START -> TIMER(P0D) ->
HUMAN_TASK(malformed form_schema) -> END`. `Scheduler.poll_and_fire/1` fires the timer,
which re-enters `Letflow.Engine.advance_after_timer_fired/3` ->
`persist_timer_fired_advance/7`, landing in the inline
`{:error, _failed_step, reason, _changes}` clause (design §2 row 3, `lib/letflow/engine.ex`
~line 2496-2516) that calls `record_task_activation_rejection_audit/5` with
`actor_id = EventStore.platform_actor_id()`.

### What actually happens (verified directly against real Postgres, not assumed)

`Scheduler.poll_and_fire/1` correctly reports `%{errored: 1, fired: 0}` (the malformed
`form_schema` correctly aborts the advance — INV-8 is upheld, no task ever activates).
But `Repo.all(Audit.Entry, prefix: schema_name) |> Enum.filter(&(&1.action ==
"task_activation.rejected"))` returns **`[]`** — no audit row exists at all, contradicting
INV-ISS0784-1.

### Root cause (traced through the real call chain, not speculated)

`Letflow.Scheduler.fire_timer/2` (`lib/letflow/scheduler.ex:275-292`) opens its own
outer `Repo.transaction/1` and, still inside it, calls
`Letflow.Engine.advance_after_timer_fired(timer, Repo, tenant_schema)` — passing the
literal `Repo` module (`lib/letflow/scheduler.ex:312-313`, `do_fire/2`'s own `with`
chain). `persist_timer_fired_advance/7`'s `repo.transaction(multi)` call (design's own
"the existing `{:error, _failed_step, reason, _changes}` clause") therefore executes
**as a nested call sharing the same still-open outer transaction/connection** — Ecto's
own documented behavior for `Repo.transaction/2` called while already inside a
transaction on the same process is that it does *not* open a new DB-level transaction;
it just runs the function in the context of the existing one. Nothing is actually
committed or rolled back at the Postgres level at that point.

`record_task_activation_rejection_audit/5`'s own `Repo.transaction(fn -> ... end)` call
(`lib/letflow/engine.ex:4018`) — the design's own "second, independent transaction,
issued... after `Repo.transaction(multi)` has already returned `{:error, ...}`" (design
§3) — is called from *inside* that same inline clause, which is *itself* still running
inside `fire_timer/2`'s outer, still-open transaction. So this "independent" transaction
is **not actually independent**: it is a second nested call sharing the identical
uncommitted outer transaction. The audit insert genuinely executes and would be
visible to a query *inside* that same transaction, but once `do_fire/2`'s `with` chain
propagates the original `{:error, reason}` all the way back up to `fire_timer/2`'s own
`case do {:error, reason} -> Repo.rollback(reason) end`, the *entire* outer transaction
rolls back — taking the audit insert down with it, exactly the failure mode design §3
itself warns about ("Adding it... before the failing `:task_records` step would never
survive... adding it after is unreachable"), just one level further out than the design
doc considered.

`Letflow.Engine.ServiceTaskDispatcher.attempt_dispatch/2` (site 4,
`lib/letflow/engine/service_task_dispatcher.ex:648-666`) is textually documented as
mirroring `fire_timer/2`'s "one `Repo.transaction/1` per claimed row" shape exactly, and
reading it confirms the identical nesting: `advance_after_service_task_outcome/4` is
called with the literal `Repo` module from inside `attempt_dispatch/2`'s own outer
`Repo.transaction/1`. Site 4 shares this exact defect by construction, even though this
pass does not add a second, separately-verified test for it (see below).

### Why this is a genuine implementation defect, not a wrong test assertion

The design doc's own §3 is unambiguous that the audit write "must" be issued only
*after* the failing Multi's own transaction has actually returned control to a context
where Postgres has released the failed attempt's locks (i.e., genuinely outside any
open transaction) — that is true for sites 1/2 (`create/2`/`complete_task/3` open the
*only* transaction on that call path) but false for sites 3/4, where a further-out
caller (`Scheduler.fire_timer/2` / `ServiceTaskDispatcher.attempt_dispatch/2`) already
holds an outer transaction open around the entire advance attempt. This is a design gap
that neither the design doc's own §2/§3 nor SECURITY-REVIEWER/REVIEWER's sign-off
caught — both apparently assumed `repo.transaction(multi)` "returning" `{:error, ...}`
at those two inline sites meant the DB-level transaction had actually closed, which it
had not.

### Why site 4 isn't separately tested this pass

Site 4's fixture requires a real HTTP test-server endpoint
(`test/letflow/engine/service_task_wiring_test.exs`'s own AC1 describe block shows the
weight of that setup) to reach `advance_after_service_task_outcome/4` at all. Since the
defect is already conclusively proven (by direct code inspection of the identical
nesting shape, not by assumption) and reproducing it a second time via a heavier fixture
would not change the fix required, this pass reports the site-3 reproduction as
sufficient evidence and names site 4 as sharing the same root cause by construction —
consistent with `docs/anti-patterns.md`'s general "don't manufacture duplicate proof of
an already-diagnosed defect" discipline. If ISSUE-FIXER's own investigation wants an
independent site-4 repro, `service_task_wiring_test.exs`'s own AC1 fixture is the
starting point.

### Disposition

This is a **new, real bug**, not something TEST-DESIGNER can "fix" (out of role) or
paper over by weakening the test's assertion (that would defeat the entire purpose of
ISS-0784 for its two system-driven cascade sites). The site-3 test is committed to this
branch **deliberately failing**, with the above root-cause analysis, as a regression
test that will pass once a real fix lands (e.g., dispatching the audit write via a
mechanism that genuinely escapes the outer transaction — a separate process/connection,
or restructuring `fire_timer/2`/`attempt_dispatch/2` to not hold their own transaction
open across the inline error-handling clause). This blocks a clean TEST-DESIGN-VALIDATOR
pass and should route back through the pipeline (a new `docs/issues/` entry against this
branch's implementation, or reopening this design for the two system-cascade sites)
rather than being silently accepted.

## Fail-then-pass / mutation discipline

- **Site 2 test**: run against real, unmodified code — PASSES. Mutation check: with
  `interpret_complete_result/3`'s catch-all clause's `record_task_activation_rejection_audit`
  call temporarily reverted to hardcode `actor_id: nil` (simulating the platform-actor
  bug at the wrong site), the test's `assert entry.actor_id == attrs.actor_id` failed as
  expected (`nil != <real UUID>`); reverting the hardcode restored a pass. Confirms the
  test's actor_id assertion is load-bearing, not vacuously true.
- **Site 3 test**: cannot be run through a "revert and confirm it passes" cycle in its
  current state, because it does not pass against any version of the code in this
  worktree — the defect above is upstream of (and masks) the very assertion
  (`entry.actor_id == EventStore.platform_actor_id()`) this test exists to prove. What
  *was* verified directly against real Postgres: the test's first failure point is the
  `assert [entry] = Enum.filter(...)` line finding zero rows (confirmed by direct query,
  not inferred) — i.e., it fails for the diagnosed reason (no row at all), not a
  different, unrelated reason. The `actor_id`/`resource_id`/`after_state` assertions
  below that point are validated as correct in shape by the identical helper function's
  already-passing behavior at sites 1/2 (same `record_task_activation_rejection_audit/5`
  code, same `Audit.insert_entry/3` call, same field-shape encoding) — the encoding
  logic itself is not in question, only its transactional survival at this call site.
