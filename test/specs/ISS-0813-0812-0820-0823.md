## ISS-0813 — Dead admin-prefix guard

### Problem

`rolesApi.create` in `web/src/api/identity.ts` used `'/api/v1/admin/roles'` — a prefix
that doesn't exist in `Letflow.Routers.Identity.__authz_routes__/0`. The fix corrected
the path to `'/api/v1/identity/roles'` and added a static source-scan guard
(`dead-admin-prefix` in `web/tests/guards/forbidlist.ts`) to prevent reintroduction.

### Acceptance criteria

**AC-ISS0813-1:** `web/src/**/*.{ts,tsx}` must contain no `'/api/v1/admin/*'` path
string except paths explicitly in `allowedPaths` for the guard pattern.

**AC-ISS0813-2:** The `dead-admin-prefix` guard pattern's offender fixture must exist
(`web/tests/guards/fixtures/offender/dead-admin-prefix.txt`) and the regex must match
its content.

### Test cases

| ID | Test file | Target | Criterion |
|----|-----------|--------|-----------|
| TC-ISS0813-01 | `tests/guards/source-scan.spec.ts` | `source-scan > web/src/**/*.{ts,tsx,css} has no guard violations` | AC-ISS0813-1 |
| TC-ISS0813-02 | `tests/guards/meta-control.spec.ts` | `meta-control: fixture coverage > dead-admin-prefix > offender fixture exists` | AC-ISS0813-2 |

**Why each test exists:**

- **TC-ISS0813-01** proves the guard fires in real source files. It is not sufficient to
  verify the regex is correct in isolation — the guard only has value if it scans the
  actual `web/src/` tree and fails when a violation is present. A unit test of the
  regex alone would not catch a scan that skips the file.

- **TC-ISS0813-02** proves the meta-control fixture is wired correctly. A guard whose
  offender fixture is missing or doesn't match the regex is silently disabled — the
  source-scan test would still pass (nothing to scan against), hiding the guard's own
  malfunction.

### Mutation evidence

Applied: `rolesApi.create` URL → `'/api/v1/admin/roles'`  
Target: `npx vitest run tests/guards/source-scan.spec.ts`

Reverted: `git checkout -- web/src/api/identity.ts`  
Verify: `git status --porcelain web/src/` → empty ✅

**Mutant B — meta-control offender fixture:**

## ISS-0812 — Identity API regression coverage

(`/api/v1/admin/roles` → `/api/v1/identity/roles`) and all `tokensApi.*` endpoints

## ISS-0820 — definitionsApi.search parameter correction

### Problem

`definitionsApi.search` accepted `{ q, limit?, offset? }` but
`Letflow.Routers.Definitions.handle_search/1` only reads `q`, `cursor`, and
`page_size`. `limit` and `offset` were silently ignored by the backend. The fix
corrected the TypeScript type signature to `{ q, cursor?, page_size? }`.

### Acceptance criteria

**AC-ISS0820-1:** Calling `definitionsApi.search({ q })` must send only `q` in the URL
— no `limit=` or `offset=` query params.

**AC-ISS0820-2:** `page_size` and `cursor` must be forwarded verbatim when provided.

**AC-ISS0820-3:** The search endpoint URL must be `/api/v1/definitions/search`.

**AC-ISS0820-4 (type-level):** The TypeScript signature must accept `cursor`/`page_size`
and reject `limit`/`offset` — enforced by `tsc -b` (`npm run type-check`).

### Test cases

| ID | Test file | Target | Criterion |
|----|-----------|--------|-----------|
| TC-ISS0820-01 | `src/api/__tests__/definitionsSearch.iss0820.test.ts` | `sends q and no limit/offset` | AC-ISS0820-1 |
| TC-ISS0820-02 | `src/api/__tests__/definitionsSearch.iss0820.test.ts` | `sends page_size when provided` | AC-ISS0820-2 |
| TC-ISS0820-03 | `src/api/__tests__/definitionsSearch.iss0820.test.ts` | `sends cursor when provided` | AC-ISS0820-2 |
| TC-ISS0820-04 | `src/api/__tests__/definitionsSearch.iss0820.test.ts` | `calls /api/v1/definitions/search` | AC-ISS0820-3 |

### Mutation evidence

**Nature of the mutation:** Changing the TypeScript type signature from
`{ q: string; cursor?: string; page_size?: number }` back to
`{ q: string; limit?: number; offset?: number }` is a **compile-time-only** change.
TypeScript types are erased at runtime; both signatures serialize the passed object
keys identically via `params as Record<string, unknown>`.

**Runtime test result:** All 4 tests **PASSED** with the mutant applied. This is
expected — calling `search({ q: 'onboarding' })` produces the same URL regardless of
which optional params the type accepts. The runtime Vitest tests cannot detect this
mutation.

**Type-check evidence (decisive gate):**  
Running `npx tsc -b tsconfig.json` with the mutant applied produced 3 mutation-specific
TS2353 errors:

```
src/api/__tests__/definitionsSearch.iss0820.test.ts(42,46): error TS2353:
  'page_size' does not exist in type '{ q: string; limit?: number | undefined; offset?: number | undefined; }'
src/api/__tests__/definitionsSearch.iss0820.test.ts(51,46): error TS2353:
  'cursor' does not exist in type '{ q: string; limit?: number | undefined; offset?: number | undefined; }'
src/hooks/useDefinitions.ts(93,54): error TS2353:
  'page_size' does not exist in type '{ q: string; limit?: number | undefined; offset?: number | undefined; }'
```

`npm run check` includes `type-check` before vitest — the regression is caught at the
full CI gate. The Vitest tests (TC-ISS0820-01 through TC-ISS0820-04) provide runtime
behavioral proof; the compile-time gate closes the type-signature gap.

Reverted: `git checkout -- web/src/api/definitions.ts`  
Verify: `git status --porcelain web/src/` → only `identity.iss0812.test.ts` ✅

## ISS-0823 — GroupsPage truncation warning

### Problem

`usersApi.list` uses `page_size: 200` (the server's hard maximum). When the backend
returns `next_cursor !== null`, the tenant has >200 users and the dropdown is
incomplete. The fix adds a visible `data-testid="user-list-truncated-warning"` element
when truncation is detected.

### Acceptance criteria

**AC-ISS0823-1:** When `usersApi.list` returns `next_cursor !== null`, the "Manage
members" panel must show a warning element with `data-testid="user-list-truncated-warning"`
containing the text "more than 200 users" and "first 200".

**AC-ISS0823-2:** When `next_cursor` is `null`, no truncation warning is shown.

**AC-ISS0823-3:** The `availableUsers` subtraction must not crash when the user list is
truncated.

### Test cases

| ID | Test file | Target | Criterion |
|----|-----------|--------|-----------|
| TC-ISS0823-01 | `src/pages/admin/__tests__/GroupsPage.iss0823.test.tsx` | `shows truncation warning when usersApi.list returns next_cursor (>200 users)` | AC-ISS0823-1 |
| TC-ISS0823-02 | `src/pages/admin/__tests__/GroupsPage.iss0823.test.tsx` | `no truncation warning when usersApi.list returns next_cursor: null (≤200 users)` | AC-ISS0823-2 |
| TC-ISS0823-03 | `src/pages/admin/__tests__/GroupsPage.iss0823.test.tsx` | `availableUsers subtraction is safe when user list is truncated (no crash or false exclusion)` | AC-ISS0823-3 |

**Why TC-ISS0823-01 uses `waitFor` + `getByTestId`:**

The warning is conditional on `users?.next_cursor` from a mocked `useQuery` result.
The `waitFor` is necessary because React may schedule the render asynchronously after
the click. `getByTestId` throws if the element is absent — it is intentionally not
`queryByTestId` (which would silently pass if the element is missing).

### Mutation evidence

Result: **1 test FAILED** — TC-ISS0823-01: `getByTestId('user-list-truncated-warning')` throws element not found  
Counts: 1 failed, 2 passed
