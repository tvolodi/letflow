## ISS-0815 — User Wire Shape (`roles` optional)

### Root cause
`GET /api/v1/identity/users` and `GET /api/v1/identity/users/:id` are served by
`user_map/1` in `lib/letflow/routers/identity.ex`. That function does not emit
`roles`. The frontend `User` interface previously declared `roles: string[]` (required),
which forced every `User` object to include `roles` even though the backend never sends
it. Any code that relied on `user.roles` would receive `undefined` at runtime.

### Fix
`roles?: string[]` (optional) in the `User` interface, inside the legacy/optional block.

### Acceptance criteria

**AC-ISS0815-1:** A `User` value that contains only the 8 fields emitted by `user_map/1`
(auth_source, display_name, email, id, inserted_at, status, updated_at, username) is a
valid `User` without compile errors.

**AC-ISS0815-2:** The runtime key set of a minimal `userMapPayload` object equals exactly
those 8 keys.

**AC-ISS0815-3:** Omitting `roles` from a `User` literal is legal — the field is absent
at runtime, not `undefined`.

**AC-ISS0815-4:** `inserted_at` (not `created_at`) is the correct timestamp field name.

### Test cases

| ID | Criterion | Why it exists |
|----|-----------|---------------|
| TC-ISS0815-01 | `userMapPayload` satisfies all 8 required fields | Confirms the base wire shape compiles and the values are as expected |
| TC-ISS0815-02 | `Object.keys(userMapPayload).sort()` equals `USER_MAP_KEYS` | Runtime check: catches a future `user_map/1` addition or removal not yet reflected in the type |
| TC-ISS0815-03 | `_userWithoutRoles` omits `roles` and the field is absent at runtime | Directly pins the `roles?` optionality; the compile-time guard fails tsc if `roles` is made required again (see mutant analysis) |
| TC-ISS0815-04 | `inserted_at` is present; `created_at` is absent | Documents the field-rename fix (wrong name previously caused runtime lookups to silently return `undefined`) |

**File:** `web/src/types/__tests__/user-wire-shape.test.ts`

### Mutation analysis

| Mutant | Change | vitest | tsc | Verdict |
|--------|--------|--------|-----|---------|
| `roles?: string[]` → `roles: string[]` | Makes `roles` required again in `User` interface | **6 passed** — vitest does NOT enforce types | **Exit 2 — TS2741 on lines 26 and 39** — `userMapPayload` and `_userWithoutRoles` both missing required `roles` | **Caught by tsc**; primary guard is compile-time |

**Key finding:** The test's protection mechanism is compile-time (the `const _userWithoutRoles: User = { ... }` assignment). Vitest transpiles TypeScript without type-checking, so the runtime test suite alone is insufficient. `npm run type-check` (or CI's `tsc -b`) is the actual guard.

## ISS-0814 — User.status Casing (lowercase `active`/`inactive`)

### Root cause
`user_map/1` emits `Atom.to_string(user.status)` where `status` is an Ecto.Enum with
values `[:active, :inactive]`. The wire values are lowercase: `"active"`, `"inactive"`.
The frontend previously typed `status: string`, accepting uppercase values like `"ACTIVE"`
that the backend never sends. Code comparisons like `u.status === 'active'` would fail if
the actual wire value were uppercase.

### Fix
`status: 'active' | 'inactive'` — literal type narrowing in the `User` interface.

### Acceptance criteria

**AC-ISS0814-1:** `User.status` accepts only `'active'` and `'inactive'` (lowercase) at
compile time.

**AC-ISS0814-2:** A patch payload for `usersApi.update` uses lowercase values.

### Test cases

| ID | Criterion | Why it exists |
|----|-----------|---------------|
| TC-ISS0814-01 | Wire values are `'active'` / `'inactive'`; compile assignments `const _active: User['status'] = 'active'` succeed | Pins the lowercase wire convention end-to-end |
| TC-ISS0814-02 | `activePatch.status` is `'active'`, not `'ACTIVE'`; `inactivePatch.status` is `'inactive'`, not `'INACTIVE'` | Documents the expected write-path payload casing to prevent a future uppercase regression in the mutation body |

**File:** `web/src/types/__tests__/user-wire-shape.test.ts`

### Mutation analysis

| Mutant | Change | vitest | tsc | Verdict |
|--------|--------|--------|-----|---------|
| `status: 'active' \| 'inactive'` → `status: string` | Removes narrowing; any string is accepted | **6 passed** — runtime values `'active'`/`'inactive'` are still valid strings | **Exit 0** — widening to `string` creates no compile errors | **NOT CAUGHT** |

**Documented coverage gap — primary mutant:** Type widening from `'active' \| 'inactive'` to `string` is detected by neither vitest nor tsc. The only protection is the type literal itself — which vitest bypasses. This gap exists because the test fixtures always supply correct lowercase values; no test verifies that an uppercase value (`'ACTIVE'`) is rejected.

**Documented coverage gap — alternative mutant (UsersPage status column):**
`UsersPage.tsx:88–89` renders the badge as `u.status === 'active' ? 'ACTIVE' : 'INACTIVE'`.
Changing this comparison to `u.status === 'ACTIVE'` would silently break the active/inactive
display for all users (all users would render 'INACTIVE'). No current vitest covers
`UsersPage`'s status column rendering. A future `UsersPage` integration test should:
1. Render `UsersPage` with a mock user having `status: 'active'`
2. Assert the status badge displays `'ACTIVE'` (the uppercase display label)
This would catch an uppercase-comparison reversion in `UsersPage.tsx`.

## ISS-0811 — GroupsPage Members Column Removed; Group Type Corrected

### Root cause
`group_map/1` in `lib/letflow/routers/identity.ex` emits only:
`{id, name, display_name, description, created_at}`. It does NOT emit `is_system` or
`member_count`. The frontend previously:
1. Declared `Group.is_system` and `Group.member_count` as required fields
2. Rendered a "Members" column using `g.member_count ?? 0` — showing a phantom `0` for
   every group because `member_count` is always `undefined` from the wire

### Fix
1. `is_system?: boolean` and `member_count?: number` (both optional) in the `Group` interface
2. Members column removed from `GroupsPage.tsx` columns array

### Acceptance criteria

**AC-ISS0811-1:** The groups table has no "Members" column header.

**AC-ISS0811-2:** Group rows render correctly using only `group_map/1` wire fields.

**AC-ISS0811-3:** Delete button is visible for all groups (no longer conditionally hidden
by phantom `is_system`/`member_count`).

### Test cases

| ID | Criterion | Why it exists |
|----|-----------|---------------|
| TC-ISS0811-01 | `queryByRole('columnheader', { name: /members/i })` returns null | Directly pins the column's removal; fails if the column is added back |
| TC-ISS0811-02 | Group name `'operators'` and display name `'Operators'` render from wire-shape data | Confirms the component renders real group_map/1 fields, not phantom values |
| TC-ISS0811-03 | Delete button with `data-testid="delete-group-g-1"` is in the document | Confirms is_system guard removed; Delete is no longer conditionally hidden |

**File:** `web/src/pages/admin/__tests__/GroupsPage.iss0811.test.tsx`

### Mutation analysis

**TC-ISS0811-01 failure output (exact):**

## ISS-0809 — Cancel Dialog Shows Real Definition Name/Version

### Root cause
`InstanceDetailPage.tsx` passed `instanceName` to `CancelInstanceDialog` as:
```tsx
instanceName={`${instance.definition_name} v${instance.definition_version}`}
```
`GET /api/v1/instances/:id` does not emit `definition_name` or `definition_version`
(only `definition_id`). Both fields are always `undefined` on the wire, producing the
string `"undefined v undefined"` in the dialog.

### Fix
`InstanceDetailPage.tsx` now reads the definition from a separate `useDefinition` call
and passes:
```tsx
instanceName={definition ? `${definition.name} v${definition.version}` : '—'}
```

### Acceptance criteria

**AC-ISS0809-1:** The dialog renders the real definition name and version when loaded.

**AC-ISS0809-2:** The dialog renders `'—'` when the definition has not yet loaded (not `'undefined v undefined'`).

**AC-ISS0809-3:** The dialog is hidden when `open=false`.

### Test cases

| ID | Criterion | Why it exists |
|----|-----------|---------------|
| TC-ISS0809-01 | Dialog with `instanceName='hire-process v1.0'` shows `"This will cancel instance hire-process v1.0."` and no `undefined` text | Confirms the dialog renders whatever instanceName it receives correctly |
| TC-ISS0809-02 | Dialog with `instanceName='—'` shows `"This will cancel instance —."` and no `undefined` text | Pins the placeholder fallback (correct behavior when definition is loading) |
| TC-ISS0809-03 | `open=false` renders no `role="dialog"` element | Basic visibility contract |

**File:** `web/src/components/instances/__tests__/CancelInstanceDialog.iss0809.test.tsx`

### Mutation analysis

| Mutant | Change | vitest | tsc | Verdict |
|--------|--------|--------|-----|---------|
| `definition ? \`${definition.name} v${definition.version}\` : '—'` → `` `${instance.definition_name} v${instance.definition_version}` `` in `InstanceDetailPage.tsx` | Reverts to the pre-fix expression | **3 passed** — tests do NOT detect the mutation | N/A | **NOT CAUGHT** |

**Documented integration gap:** The `CancelInstanceDialog` tests operate at **component
isolation** level. They inject `instanceName` as a literal prop:
```tsx
React.createElement(CancelInstanceDialog, { instanceName: 'hire-process v1.0', ... })
```
They never mount `InstanceDetailPage`. Therefore the mutation in `InstanceDetailPage`'s
prop-building expression is **completely invisible** to these tests.

**What the current tests DO protect:**
- TC-ISS0809-01/02 verify that `CancelInstanceDialog` itself does not inject `"undefined"` text when rendering a normal or placeholder `instanceName`. This prevents the dialog component from introducing the bug independently.
- TC-ISS0809-02 would catch a regression if the `CancelInstanceDialog` component were changed to render something with `undefined` in it.

**What the current tests do NOT protect:**
- A reversion in `InstanceDetailPage.tsx`'s prop expression. The integration-level
  path — where `ProcessInstance.definition_name` is `undefined` → the string
  `"undefined v undefined"` is constructed → passed as `instanceName` → rendered in the
  dialog — is not exercised.

**Recommended integration test (not yet written):**
Mount `InstanceDetailPage` with:
- `useInstance` returning an instance without `definition_name`/`definition_version`
- `useDefinition` returning `undefined` (loading/unavailable)
- Open the cancel dialog
- Assert `screen.queryByText(/undefined/)` is null in the dialog

This test would fail against the pre-fix prop expression and pass against the fix.
