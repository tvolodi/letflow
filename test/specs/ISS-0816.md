## The change this step made: T6 now discriminates

### What was wrong

`REVIEWER` (OBS-1, `handoffs/WF03-ISS0816-20260925/step-03d-reviewer.json`) measured
that reverting `GroupsPage.tsx`'s `queryFn` from `groupsApi.listAllMembers` to
`groupsApi.members` left **3 of T6's 4 cases green**. **This step reproduced that
measurement before changing anything** — mutation **M1** below, `1 failed | 3 passed`,
confirmed to the case.

The single failing case was *"the page queries the drain, never the single-page members
call"*, which `FRONTEND-DEV` added on its own initiative. The design's own nominated
headline assertion — §7 row T6, *"a second-page member is not offered in the
dropdown"* — **passed against the unfixed page.**

The reason is structural, not a mistake in the test. `ISS-0824` records that
`GroupsPage` cannot be rendered under a real `QueryClientProvider` without hanging the
jsdom event loop, so `useQuery` is mocked. In its original form the test *handed the
component a ready-made complete member set*. It therefore exercised `availableUsers`'
set difference — code this fix never touched — over data the test supplied, rather than
the thing ISS-0816 actually fixed: that the page **obtains** a complete set.

### What was done instead

The ISS-0824 constraint is real and was **not** removed: T6 still mocks `useQuery` and
still never touches a real query provider. What changed is *where the member data comes
from*.

1. `@/api/identity` is no longer module-mocked with hand-written stubs. It is the real
   module with `vi.spyOn` applied per case. This matters because
   `groupsApi.listAllMembers` reaches its page fetch **through `groupsApi.members`**
   (`web/src/api/identity.ts:114`), so doubling that one property lets the **real drain
   run** against a stubbed wire.
2. The headline case stubs only the wire — `groupsApi.members` — returning the first
   fifty members plus `next_cursor: 'cursor-page-2'` on a cursorless request, and
   `u-51` with `next_cursor: null` on a cursored one.
3. The dialog is rendered **twice**, the way react-query itself resolves a query. Pass
   one lets the page run its own `queryFn` and captures the promise it returns; pass
   two feeds back exactly the value that `queryFn` produced as the query's `data`.

The member set under assertion is therefore whatever the **page** fetched, never
whatever the test supplied. A page that dials `groupsApi.members` once holds 50 members
and offers `u-51` as addable; a page that dials the drain holds 51 and does not.

The nominated assertion is placed **first** among the substantive checks in that case,
deliberately, so that it is the assertion that fires against a pre-fix page rather than
one of the mechanism checks that follow it.

### Protecting the case that already discriminated

OBS-1's third requirement. *"The page queries the drain, never the single-page members
call"* now carries an in-file comment naming what it proves, recording that it was the
**only** red case before this step, citing the OBS-1 handoff, and stating explicitly
that it is not redundant with the headline case — one pins **which** function the page
dials, the other pins the **consequence** of dialing the right one. The file header
carries the same warning at greater length, plus the instruction to promote the file to
a real `QueryClientProvider` if `ISS-0824` is ever fixed.

Both non-discriminating cases are labelled as such in place, so a later reader is not
misled about what they cover. All four cases now stub the wire, so no case in the file
can reach `window.fetch` under any mutation of the page.

## Fail-first evidence (WF-03 Step 4)

WF-03's **non-existence clause** applies to T4/T5/T5b/T5c: pre-fix `listAllMembers` did
not exist, so every case in `identity.members.test.ts` fails with a module error, which
proves the module is new and nothing about whether the tests discriminate a correct
implementation from a wrong one. The clause is satisfied by **mutating the shipped
logic and recording which cases fail per mutant**.

**Every mutant was applied in a throwaway `git worktree` detached at `0059711e`, under
the session scratchpad. The working checkout was never mutated.** Its `node_modules`
was a real `robocopy` copy, never a junction, precisely so that removing the worktree
could not reach the real tree through a link.

### Drain group — `web/src/api/identity.ts`, 6 cases, baseline 6 passed

| Mutant | Change | Cases failed | Count |
|---|---|---|---|
| **M2** | cap off-by-one: `request < MAX` → `request <= MAX` | T5, T5c | 2 failed / 4 passed |
| **M3** | suppress the exactly-20 boundary: `next_cursor === null` gated on `request < MAX - 1`, so reaching the cap always reports `truncated: true` | T5b | 1 failed / 5 passed |
| **M4** | **stale cursor** — the `cursor = page.next_cursor` advance is deleted, so every request repeats page one's (absent) cursor | T4, error-propagation | 2 failed / 4 passed |

M2 and M3 reproduce `REVIEWER`'s AC-R6 measurements exactly. M4 and M5 are new and

## Environment note — `web/node_modules` was empty at step start

`web/node_modules` in the working checkout contained **0 entries** when this step
began, so nothing under `web/` could be run at all. A full real copy (398 entries, 194
MB, 20 035 files) survived in an unrelated worktree
(`.claude/worktrees/agent-a46167727a1e72911`) with a byte-identical
`package-lock.json`, which establishes that the loss was of the directory's contents,
not of a dependency-tree change.

The most probable cause is the hazard this run's own dispatch warned about: a prior
step junctioned `node_modules` into a throwaway worktree and then removed that worktree
with a recursive delete that traversed the link. Restored with
`npm ci --no-audit --no-fund` → `added 607 packages in 8s`, back to 398 top-level
entries, `package-lock.json` unchanged. Recorded here because it is a silent,
cross-step destructive failure mode with no test that would ever catch it.

**This step therefore copied rather than linked.** `robocopy /E /MT:32` put a real
194 MB copy of `node_modules` into the mutation worktree in 6.4 s. At that cost there
is no reason to use a junction for this purpose again.

## What remains unproven

`REVIEWER`'s `what_remains_unproven` is carried forward unchanged and is **not** closed
by this step. Mocked green is not integration evidence:

- **No live backend** (docker daemon down). The drain has never spoken to
  `lib/letflow/routers/identity.ex:552`. T4/T5/T5b/T5c do run against the **real**
  `web/src/api/client.ts` with only `window.fetch` doubled, so URL construction,
  query-param serialization and the cursor round-trip through the real client are
  genuinely exercised — but that the server accepts `page_size=200` and returns the
  assumed envelope is verified by source reading only.
- **No real query provider** (`ISS-0824`). T6's two-pass helper reproduces react-query's
  resolve-then-render sequence faithfully enough to make the assertion discriminate, but
  it is not react-query. `queryKey`/`enabled`/`refetch` wiring, retry and refetch-on-focus
  semantics, `QueryStateBoundary` interaction, and the notice's rendering in a real tree
  remain unproven.
- **No e2e or UAT coverage** of the Add-member dropdown against a real tenant with more
  than fifty group members.
- **The `truncated: true` branch has never been reached against a real server** — it
  needs a group of more than 4 000 members, so it is a bound rather than a path.

One item is now **narrower** than `REVIEWER` left it: the claim *"the page obtains a
complete member set"* was pinned by a single assertion at the end of Step 3d. It is now
pinned by two, one of which derives its data from the page's own fetch.
