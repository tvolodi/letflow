## Why criterion 5 has no direct unit test on `check_registry_coverage/2`

`check_registry_coverage/2` is `defp` (private) — unlike every other function this suite calls
directly (`handoff_files/1`, `lint_file/2`, `guard_empty_scope/2`, `run_autofix/1`,
`pre_floor_file?/2`, `rewrite_top_level_status!/3`, `splice_top_level_status/2`, all `def`s),
it has no public entry point, matching this test file's existing, consistent convention of only
unit-testing public functions directly and reaching private ones through `run/1`'s CLI surface.

Its single-file short-circuit is proved at the `run/1` level by two complementary tests instead:

- `T-FILE-OK` shows the returned registry-coverage pair is forced-empty (`[]`/`[]`) for a
  single-file target, even though the real `handoffs/registry.json` currently holds 334
  `runs[]` entries (verified directly: `python3 -c "import json;
  print(len(json.load(open('handoffs/registry.json'))['runs']))"` → `334`). If
  `do_check_registry_coverage/2` had actually executed against a lone tmp fixture whose
  fabricated run-id cannot match any of those 334 real entries, `missing_on_disk` could not
  possibly come back empty — an empty pair is therefore *positive* evidence the registry read
  was skipped, not merely that this fixture happens to coincidentally match the real corpus.
- `T-DIR-MODE-H5-RUNS-AND-READS-REGISTRY` shows the *same* registry file genuinely consulted —
  and a real mismatch reported by name — the moment the scan target is a directory instead of a
  file, using the exact same kind of fabricated-run-id fixture.

Together these two tests discriminate the short-circuit's two branches as precisely as a direct
unit test on the private function would, without requiring a production visibility change this
task was not asked to make.

## Test inventory

### `handoff_files/1` and `guard_empty_scope/2` (unit level)

- **`F-FILE-DISCOVERED`** — `handoff_files/1` given `"handoffs/registry.json"` (a real file that
  a directory scan's own `registry_file/1` exclusion would normally reject) returns exactly
  `["handoffs/registry.json"]`, proving single-file mode is genuinely unfiltered against both
  the `step*.*` glob and the registry.json exclusion.
- **`F-FILE-MISSING-RAISES-DOES-NOT-EXIST`** — a nonexistent single-file-shaped path: `handoff_files/1`
  returns `[]`, and `guard_empty_scope/2` raises with `/does not exist/`, mirroring
  `F-NONEXISTENT-DIR-RAISES`'s directory-shaped proof of the same `empty_scope_reason/1`
  precedence rule.

### `run/1` single-file mode, isolated tmp fixture

- **`T-FILE-OK`** — a well-formed single handoff file at a tmp path: `run/1` returns `:ok`; the
  printed banner contains the exact substring `"OK -- 0 new violations across the single
  handoff file"` and does **not** contain `"1 handoff files"`; the banner also names the scanned
  path (`inspect(path)`); the H5 section contains `"skipped: H5 is a corpus-level check, not
  applicable to a single-file scan"`; both `missing_from_registry` and `missing_on_disk` print as
  `[]` (see "criterion 5" analysis above).
- **`T-FILE-MISSING-RUN-RAISES-DOES-NOT-EXIST`** — `run/1` with a nonexistent single-file-shaped
  `--dir` target raises `/does not exist/` and never prints an `"OK --"` banner.
- **`T-FILE-VIOLATIONS-LINTED-DIRECTLY`** — `run(["--dir", "handoffs/registry.json"])`: this real
  file has no top-level `"status"` key (H1) and two top-level keys (`"_comment"`, `"runs"`) not
  in `@schema_top_keys` (H3). `run/1` raises `/found \d+ new violation/`; stdout contains
  `"NEW HARD VIOLATIONS"`, `"[H1] handoffs/registry.json"`, and `"[H3] handoffs/registry.json"`;
  stdout does **not** contain `"does not exist"` or `"discovered 0 files"` — proving the file was
  linted as the named target, not silently treated as an empty/invalid scope.

### Directory mode is unchanged

- **`T-DIR-MODE-H5-RUNS-AND-READS-REGISTRY`** — a tmp directory containing one flat handoff file
  (no `<run_id>/` subdirectory): `run/1` returns `:ok`; the banner contains `"across 1 handoff
  files"` (unchanged directory-mode wording) and does **not** contain `"the single handoff
  file"` or the single-file skip-note; the H5 section names the fabricated basename-derived
  "run_id" (`"step-01-agent.json"`, since `Path.relative_to(dir) |> Path.split() |> hd()` on a
  flat file yields its own basename) as `"missing from registry.json"` — direct, positive
  evidence the real `registry.json` was actually read in directory mode.
