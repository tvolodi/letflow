# Test Spec: ISS-0831 — `mix letflow.check_boundaries` must not silently swallow a non-zero `mix xref` exit

**Issue:** `docs/issues/ISS-0831.yaml`. **Design:**
`lib/letflow/design/iss0831-check-boundaries-exit-code.md`. **Fix:**
`lib/mix/tasks/letflow.check_boundaries.ex` (new injectable `run_xref/0` seam reading
Application env `{:letflow, :check_boundaries_xref_runner}`, mirroring ISS-0697's
`resolve_executable/1` convention; `run/1` now captures `exit_code` and `Mix.raise/1`s
before parsing when it is non-zero), commit `56612666`.

## Criterion (design §4, "Test-designer notes")

1. A non-zero `mix xref` exit must cause `run/1` to raise loudly (`Mix.raise/1`), not
   silently parse whatever (possibly empty/garbage) output it got.
2. The raised message must include both the literal exit code and the captured output
   text, so a human/agent reading CI output sees what `mix xref` actually said.
3. The raise must fire **before** `parse_xref_output/1`/`classify_edges/2` ever run —
   ordering matters, not just "it eventually fails somehow."
4. The existing exit-0 success path (parse → classify → OK/violation summary) must be
   unchanged — this is a pure additive guard, not a behavior change on the happy path.
5. The injectable seam's default (no Application env override configured) must still
   fall through to a real `System.cmd("mix", ["xref", ...])` call — a genuine, non-test
   invocation of `mix letflow.check_boundaries` is unaffected.

## Test cases: `test/mix/tasks/letflow.check_boundaries_test.exs` — describe "run/1 -- mix xref non-zero exit (ISS-0831)"

**Why these tests exist (not just a restatement of the criteria):**

### 1. `T-XREF-EXIT-NONZERO-RAISES`

Installs `Application.put_env(:letflow, :check_boundaries_xref_runner, fn -> {"some xref error text", 1} end)`
and calls `CB.run([])`, asserting via `assert_raise Mix.Error, ~r/mix xref exited 1/`
that the raise actually fires. This is the discriminating test: it proves the
non-zero-exit guard genuinely executes on a real call to `run/1`, not merely that the
source reads as if it would (which is exactly what the fail-then-pass verification
below confirms — see the pre-fix run).

### 2. `T-XREF-EXIT-NONZERO-MESSAGE-INCLUDES-OUTPUT`

Same injection with a distinct fake output string (`"internal xref crash: bad_state"`),
asserting the raised `Mix.Error`'s `.message` contains **both** `"exited 1"` and the
captured output text, as two independent assertions. Proves the fix's "loud, not
silent" intent includes surfacing *what* `mix xref` said, not merely *that* it failed —
a raise with a generic message would satisfy test 1 but not this one.

### 3. `T-XREF-EXIT-NONZERO-SKIPS-PARSE`

Injects a fake non-zero exit whose output (`"lib/a.ex\n\`-- lib/b.ex\n"`) is
deliberately a **well-formed, parseable xref edge** — chosen specifically so it would
*not* crash `parse_xref_output/1` if the raise-before-parse ordering ever regressed and
parsing ran anyway. Asserts the raised message contains the exit-code text and
`refute`s it contains `"OK --"` or `"violation"` (the strings the parse/classify/report
path would produce). This proves the "before attempting to parse output" ordering
constraint from the issue's fix direction, not just that a raise happens somewhere.

### 4. `T-XREF-EXIT-ZERO-UNCHANGED`

Injects `fn -> {"", 0} end` and asserts `CB.run([]) == :ok` — the regression guard
proving the new exit-code check doesn't false-positive on the success path (an empty,
valid xref output with exit 0 must still resolve to the normal "0 edges, 0 violations"
OK path, not an accidental raise).

### 5. `T-XREF-RUNNER-DEFAULT-IS-REAL-SYSTEM-CMD`

Asserts `Application.get_env(:letflow, :check_boundaries_xref_runner) == nil` in the
default (no override configured) state. The actual proof that the default falls
through to a real subprocess call is the existing end-to-end test in
`CheckBoundariesTaskTest` ("exits 0 on the current branch tree (AC2)"), which shells
out to the real `mix letflow.check_boundaries` with no env override set anywhere and
asserts exit 0 — called out explicitly per the design's §4 item 5 so a regression
there is treated as a hard failure of this fix, not an unrelated flake.

## Async-safety / cleanup

`{:letflow, :check_boundaries_xref_runner}` has no legitimate non-test setter, so
cleanup is an unconditional `Application.delete_env/2` in `on_exit/1` (not
restore-prior-value) — same convention ISS-0697 established for its own injectable-seam
key.

## Fail-then-pass verification (WF-03-style rigor applied to a WF-02 fix)

This is a behavioral fix to **existing** code (`run/1` already existed pre-fix,
discarding `exit_code`) — not a "code under test does not exist" case, so the mutant-
testing carve-out doesn't apply; the direct fail-then-pass check is sufficient and was
performed.

## Known unrelated flake observed during full-suite verification

Running the full `mix letflow.check.test` (parallel partitioned runner) twice against
the post-fix working tree produced `545/546 passed` both times, with the sole failure
being `CheckBoundariesTaskTest "exits 0 on the current branch tree (AC2)"` —
**pre-existing, already-tracked as `KNOWN_ISS_0832_CLASS`** in multiple prior, unrelated
test reports (e.g. `test/reports/report-20260926-WF03-ISS0848-20260926.yaml`,
`report-20260925-WF02-REQ403-20260925.yaml`, `report-20260925-WF02-REQ404-20260925.yaml`).
Root cause: that test's `System.cmd/3` subprocess inherits `MIX_TEST_PARTITION=N` from
`scripts/test_parallel.sh`'s own environment without pinning `MIX_ENV=test`, so the
subprocess defaults to `MIX_ENV=dev` and a config guard rejects that combination. This
is unrelated to ISS-0831 — it was never touched by this fix or these new tests, and it
reproduces identically on unrelated branches. `mix test test/mix/tasks/letflow.check_boundaries_test.exs`
run directly (not through the partitioned runner) passes all 29/29 cleanly, as shown
above.
