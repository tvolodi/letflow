# Test Spec: ISS-0878 — Cross-process-unique `unique_realm/1` fixture

**Issue:** `docs/issues/ISS-0878.yaml`.
**Design:** `lib/letflow/design/iss0878-unique-realm-cross-process-fix.md`.
**Fix:** `test/support/tenant_slug.ex` (new `Letflow.TenantSlugFixture.unique_realm/1`),
branch `feature/WF03-ISS0878-20260929` — replaces each of 4 affected files' private
`unique_realm/1` (`"<prefix>-#{System.unique_integer([:positive, :monotonic])}"`) with a
thin delegating wrapper calling `Letflow.TenantSlugFixture.unique_realm(prefix)`, an
`Ecto.UUID.generate/0`-derived suffix.
**Test tier:** unit (pure function, no `Letflow.Repo`/`Ecto.Sandbox` dependency) +
property (`StreamData`).

## Bug recap

`System.unique_integer([:positive, :monotonic])`'s uniqueness guarantee is scoped to a
single BEAM VM process, not across processes. `scripts/test_parallel.sh` shards the
suite across N independent OS processes (separate BEAM VMs) against one shared Postgres
instance, and `tenants_idp_realm_id_partial_index` is a single global unique index with
no partition scoping. Two partitions independently making their first
`unique_realm(same_prefix)` call in the same window can produce an identical string and
collide on insert (`Ecto.InvalidChangesetError`, `idp_realm_id: ["has already been
taken"]`).

Unlike ISS-0059's `unique_slug/1` bug (a single VM's counter restarting after a prior
crashed run), this collision is a race between two *concurrently running* VMs, which is
inherently timing-dependent and cannot be reliably forced on demand within a single test
run. This spec proves the fix's **discriminating property** instead of attempting to
reproduce the race itself: does the generated string's suffix match the format
`Ecto.UUID.generate/0` produces (collision-proof by construction, since its 122 bits of
randomness carry no in-process/cross-VM state to repeat) or not?

## Criteria (from the design doc)

1. `Letflow.TenantSlugFixture.unique_realm/1` returns `"<prefix>-<UUID>"`, built on
   `Ecto.UUID.generate()`, not any process-local counter.
2. Default argument `"realm"` is preserved (several `identity_test.exs` call sites call
   `unique_realm()` with no argument).
3. All 4 call sites (`auth_pipeline_test.exs`, `authorization_ac9_test.exs`,
   `provider_registry_multi_realm_test.exs`, `identity_test.exs`) delegate to the shared
   helper rather than keeping their own `System.unique_integer/1`-based copy.
4. The fix must be shown to discriminate a correct (UUID-based) implementation from the
   old, broken (counter-based) one — not just assert a happy-path shape that any
   sufficiently-random generator would also satisfy.

## Test cases — `test/support/tenant_slug_test.exs`

Added to the existing `Letflow.TenantSlugFixtureTest` module (already houses ISS-0059's
`unique_slug/1` coverage — same module, same file, per project convention of one shared
support-fixture spec file per `test/support/*.ex` module), under the describe block
`"unique_realm/1 uses a UUID suffix, not a process-local counter (ISS-0878)"`:

1. **"no duplicates across a thousand calls in the same process"** — baseline sanity
   check only. Trivially true for both the old and new implementation (any sufficiently
   unique generator passes this within one process), included because
   `provider_registry_multi_realm_test.exs` alone makes 12+ calls per run and needs this
   in-process guarantee — but this test ALONE does not prove the fix; see case 2.

2. **"the generated suffix matches the Ecto.UUID.generate/0 format"** — the
   discriminating assertion (criterion 4). Regex-matches the suffix after `"<prefix>-"`
   against `~r/^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/` (the exact
   shape `Ecto.UUID.generate/0` produces) across 30 randomized `(prefix, repeat_count)`
   pairs. A `System.unique_integer/1`-based suffix produces bare decimal digits and can
   never match this regex — see "Fail-then-pass verification" below for a live
   demonstration against `unique_realm/1` itself.

3. **"default prefix (\"realm\") also gets a UUID-format suffix"** — covers criterion 2:
   the zero-argument call path (`identity_test.exs`'s convention) independently gets the
   same UUID-format guarantee as the explicit-prefix path.

## Call-site delegation (criterion 3) — confirmed by direct read, not re-tested

Per the design doc's own framing (this class of change is a mechanical
delegate-to-shared-helper substitution, already checked by REVIEWER), each of the 4
files' wrapper body was read directly against the branch diff
(`git diff origin/main...feature/WF03-ISS0878-20260929 -- test/`):

- `test/letflow/plugs/auth_pipeline_test.exs:64-66` —
  `defp unique_realm(prefix), do: Letflow.TenantSlugFixture.unique_realm(prefix)`
- `test/letflow/api/authorization_ac9_test.exs:49` —
  `defp unique_realm(prefix), do: Letflow.TenantSlugFixture.unique_realm(prefix)`
- `test/letflow/oidc/provider_registry_multi_realm_test.exs:83` —
  `defp unique_realm(prefix), do: TenantSlugFixture.unique_realm(prefix)` (uses the
  file's existing `alias Letflow.TenantSlugFixture`)
- `test/letflow/identity_test.exs:80-82` —
  `defp unique_realm(prefix \\ "realm"), do: Letflow.TenantSlugFixture.unique_realm(prefix)`

All 4 delegate to the single shared, now-tested implementation; no wrapper keeps its own
generation logic. This is a lightweight confirmation, not a new test, per the design
doc's explicit scoping ("no new test file for this helper itself" was the pre-existing
guidance for `unique_slug/1`'s precedent — this run adds one anyway per WF-03's
non-existence-case mutation rule below, since `unique_realm/1` is new).

## Fail-then-pass verification (WF-03 Step 4 regression-test requirement)

`Letflow.TenantSlugFixture.unique_realm/1` is a **new function** (did not exist on
`origin/main`), so per WF-03's "When the pre-fix failure is 'the code under test does
not exist'": a bare pre-fix-commit re-run only proves the function didn't exist yet,
which discriminates nothing about a correct-vs-broken implementation and is
insufficient on its own. Per that section, a mutation-based proof was performed instead,
**in place** (not a worktree), with the revert verified per the fallback technique.

**Baseline — tests pass against the real (correct) implementation:**

```
$ mix test test/support/tenant_slug_test.exs
...
Finished in 7.9 seconds (7.9s async, 0.00s sync)
Result: 9 passed (4 properties, 5 tests)
```

**Mutant applied** — `test/support/tenant_slug.ex`'s `unique_realm/1` body temporarily
changed back to the pre-fix buggy pattern:

```elixir
def unique_realm(prefix \\ "realm") when is_binary(prefix) do
  "#{prefix}-#{System.unique_integer([:positive, :monotonic])}"
end
```

**Mutant result — the two discriminating tests fail, exactly as expected:**

```
$ mix test test/support/tenant_slug_test.exs
...

     expected the default-prefix call to also produce a UUID-format suffix, got: realm-1005

  2) property unique_realm/1 uses a UUID suffix, not a process-local counter (ISS-0878) the generated suffix matches the Ecto.UUID.generate/0 format (Letflow.TenantSlugFixtureTest)

         * Clause:    prefix <- StreamData.string(:alphanumeric, min_length: 1, max_length: 20)
           Generated: "p"

           Generated: 1
     expected every unique_realm/1 suffix to match the Ecto.UUID.generate/0 format ... got: ["1028"]

Finished in 7.3 seconds (7.3s async, 0.00s sync)
Result: 7/9 passed (3/4 properties, 4/5 tests)

Case 1 ("no duplicates across a thousand calls") and the call-order/shape-prefix half of
case 2 still pass under the mutant — expected, since those don't check the suffix
*format*, only its distinctness/prefix, which the counter mechanism also satisfies
within one process. Only the two assertions that check the UUID-format regex fail,
confirming the coverage is sensitive to exactly the trap ISS-0878 fixes (a
process-local counter masquerading as cross-process-unique), not merely present.

**Mutant reverted, revert verified:**

(The only modified path is this run's own new test file — `test/support/tenant_slug.ex`
is back to its pristine, branch-committed content; nothing under `lib/` was ever

```

the mutant (old buggy mechanism) fails 2/9, the fix (current implementation) passes 9/9,
