# Test Spec: ISS-0937 -- retention + tenant-template-parity tests depended on the real UTC month

**Issue:** ISS-0937 (Q-920, GH#2077). **Design:** `lib/letflow/design/iss0937-month-boundary-test-clock.md` (section 3).
**Fix (test support only, no `lib/` change):** `test/support/partition_clock.ex` (`Letflow.Test.PartitionClock`),
`test/support/tenant_template.ex` (`check_table_set/2` ignores dynamic month partitions on BOTH sides),
`test/support/tenant_fixture.ex` (`req376_dynamic_partition_table?/1`), three retention test files use the helper.
**Test files:** `test/support/partition_clock_test.exs` (new), `test/support/tenant_template_test.exs` (new ISS-0937 describe).

## Criteria

A. A fixture month used as "eligible for retirement" is eligible on EVERY real date (production rule:
   `today >= first_day_of_next_month(M) + min_partition_age_days`); last calendar month is not, on the 1st.
B. The table-set parity dimension must not report date-dependent `events_yYYYYmMM` /
   `events_archive_yYYYYmMM` partitions as drift, while still reporting genuine drift.

## Shape

No test reads the real date or DB for criterion A (injected `today`, independent oracle that re-implements the
production rule). Criterion B builds two throwaway schemas with FIXED literal table names and calls the real
public `assert_clone_parity!/3` restricted to dimension #1.

| Test | Why it exists |
|---|---|
| eligible for every day 2024-01-01..2027-12-31 x N in [1,2,7,31,400] | Core property: 1461 days (48 months, leap day, every 1st/2nd). Kills any offset that is ineligible on some day or ignores N. |
| latest eligible month (next month NOT eligible) | Kills an over-conservative offset (e.g. -2), which the first test cannot see. |
| legacy derivation ineligible exactly on the 1st (24 months) | Pins the original bug in pure date arithmetic and proves the oracle is sensitive to it; also asserts the fix is eligible on those same days. |
| explicit boundary dates | Exact `{y, m}` for 2026-10-01, 10-02, 10-31, 2027-01-01, 2028-03-01 (readable worked examples). |
| shift_months across year boundaries | Pure helper arithmetic both directions. |
| source scan of the 3 retention test files | Their DB-backed tests cannot be date-pinned (no production clock seam), so assert they derive via `PartitionClock`, none uses the legacy derivation, none hard-codes the override age. |
| stale dynamic partition on candidate not "extra" | The exact CI failure (`extra=["events_y2026m09"]`), date-independent. |
| dynamic partition only on reference not "missing" | Mirror direction. |
| events_archive dynamic partitions ignored | Second regex alternative. |
| non-partition extra table still raises (message has only `widgets_extra`) | Anti-vacuity: filter must not hide real drift, and the stale partition must not leak into the message. |
| genuinely missing non-partition table still raises | Missing-direction anti-vacuity. |
| invalid names (`m13`, `y26m09`, `eventsx_`, `events_extra`) not ignored | Pins the regex bounds; kills a loosened filter/regex. |
| fixed `events_default` extra on candidate still reported | Pins the "dynamic-only" decision (fixed tables are not date-dependent). |
