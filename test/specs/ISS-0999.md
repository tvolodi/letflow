# Test Spec: ISS-0999 -- Per-event-type payload allowlist on `GET /promotions/platform-events`

**Issue:** ISS-0999 (`docs/issues/ISS-0999.yaml`; Q-981 / GH #2266; the queue's own number for it is ISS-0981, a
different local issue). Design: `lib/letflow/design/iss0999-platform-events-allowlist.md` (section 5 maps the
criteria, section 6 lists the tests). Workflow: WF-03 regression. **Tier:** integration (real Postgres, real tenant
schemas, router-level dispatch, the real `PlatformEvents` adapters and `Promotion.promote_definition/3`; no mocks).
All modules `async: false` (VM-global platform pin; restored by the fixture's `on_exit`, and explicitly after the
operator pass). No wall-clock or unseeded-random dependence; cursor strings are never compared.

Fail-first: the old key-suffix walk (REQ-446) kept `source_definition_id`, `review_id`, `actor_id`, teardown `error`
and every foreign id under a non-`*tenant_id` key; the 5 updated T-7 tests failed against it, and the T-10 reader
assertions fail against it (mutant M1 below restores the walk and measures it).

## Criterion to test mapping

| Acceptance criterion | Test (file) | Why it exists |

| Two-tenant scenario: operator promotes B into A; no identifier of B or of the operator in A's body | `non_operator_reader_sees_no_identifier_of_b_or_the_operator` (T-10) | Real path: review seeded in P's schema, `Promotion.promote_definition/3` with the real event adapter. Harness note (deviation from design 6.4, flagged): the design says A's admin reads with `["TENANT_ADMIN"]`; through the
test harness's hand-assigned `auth_context` (`Fixture.router_conn/5`, no scope facts) the route answers 403 for
`TENANT_ADMIN` (docs/roles.md marks `PromotionsRead` yes for it, conditional on the ownership proof). T-10 therefore
uses `["PLATFORM_ADMIN"]` held in A while the pin is P (a non-operator), the same reader T-7 uses.

## KNOWN residuals (accepted; named by SECURITY-REVIEWER; NOT tested as failures)

* R1: the serialised plan's `entries` graph JSON (`before`/`after`) on `GET /promotions/:id/context` is not shaped (unchanged; T-8 pins it as documentation).
* R2: `/context` still uses the key-suffix shaping, so `tenantId`, `tenant_ids` and `source_tenant` pass there.
  ACCEPTED, TRACKED: Q-1003 / GH #2291 / ISS-1021 (depends on Q-981; its issue file ships with that fix PR).
* R3: the `teardown_error` field (review/run teardown error text on the review routes and `/context`) is unchanged; only the platform-events teardown `error` payload key is allowlisted away.
* R4: tenant-authored string values (`process_key`, `from_version`, `to_version`) are kept as plain scalars and could contain any text, including an identifier; and the `sandbox_id` is kept, so the same pool-slot id correlates events across a tenant's own reads.
* R5: behaviour change: tenant admins lose `actor_id` and the payloads of unregistered/tenant-registered event types on this route (the audit route remains the actor-attributing surface).
