# ISS-1032 (Q-1014 / GH #2317) and ISS-1033 (Q-1015 / GH #2318): test spec

Design: `lib/letflow/design/iss1032-1033-identity-id-and-bound-group-hardening.md` (section 4 test list T-01..T-34).
Code under test: `Identity.delete_group/2` (`{:error, :bound_to_role}`), `Identity.cast_id/1`, the `with_cast_id` order in `Letflow.Routers.Identity`.
Tests: `test/letflow/api/identity_id_hardening_test.exs` (new, 38 tests: T-01..T-34, T-12b, T-12c, T-35 and one spelling-table sanity test) and the tightened
`test/letflow/api/platform_escalation_guard_test.exs` (30 tests, count unchanged). `async: false` (the platform pin is VM-global), real Postgres, direct dispatch
into the router, callers: `TENANT_ADMIN` of the pinned platform tenant P (the guard-triggering, non-platform caller) and the operator (`PLATFORM_ADMIN` of P).

Style notes. "Unknown" ids are FIXED uuids (no generated ids in the compared bytes); every 404 comparison is byte-for-byte against the 404 of the same caller on a
plain unknown canonical id (the fixture's `trace_id` is a fixed assign, so the comparison is exact). Every negative has a positive control on a real row, so no
denial or 404 is vacuous. No test depends on time or unseeded randomness. No test helper declares a default argument.

## KNOWN residuals (design section 8)

* R1. Domain functions (`get_user`, `add_group_member`, `remove_group_member`, `list_group_members`, `revoke_token`, `create_token`) still raise on uncastable ids when
  called outside the router (OQ-3). Not tested: every HTTP path casts first; T-14 pins that `cast_id/1` is total.
* R2. `POST /groups/:id/members` with an unknown well-formed group and an invalid body stays 422 (guard, validation, lookup). T-23 asserts the 422-over-404 order for the
  body user id on a real group only.
* R3. Group deletes and refusals are not audited (the router audits no refusals; `delete_group` is not audited on success). T-10 pins the current no-write behaviour so a
  future audit-coverage requirement changes it deliberately.
* R4. `web/` does not yet render the 409 for group delete; no frontend test here.
* R5. A bound group WITH members answers the pre-existing unified 404 (T-08 documents it; the operator sees 409 on the memberless platform group and 404 once it has members).
* Additional: the login-directory part of T-18 / T-10 compares the global `tenant_login_directory` row count, so it would miss a
  same-count rewrite of a row; the user-row and audit-count comparisons cover the writes the routes actually make.
