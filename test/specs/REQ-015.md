# Test Spec: REQ-015 — Ecto schema/migrations for tenants, users, groups, tenant_role

**Requirement:** REQ-015 (`docs/requirements.yaml`) — Add `priv/repo/migrations` and
corresponding `lib/letflow/` Ecto schema modules for `tenants`, `users`, `groups`, and
`tenant_role`.

**Requirement's acceptance criteria (verbatim):**
1. "priv/repo/migrations gains migrations for tenants, users, groups, and tenant_role,
   all applying cleanly via mix ecto.migrate"
2. "corresponding lib/letflow/ Ecto.Schema modules exist for all four tables with
   @moduledoc citing the R-Co adp-04/04a/04b design doc each table's shape is ported
   from"
3. "the migration moduledoc explicitly states whether Ecto :prefix/schema-per-tenant
   provisioning is built in this requirement or deferred, per this requirement's own
   description"
4. "users has a partial unique index on (external_realm, external_id) WHERE
   external_id IS NOT NULL, not a plain unique constraint"
5. "no DB-level CHECK constraint enforces auth_source-vs-external-fields consistency;
   the schema moduledoc states this is deferred to application-level changesets"

**Test tier:** unit+integration (DB-backed, via `Letflow.DataCase` / real Postgres
sandbox — this is schema/constraint verification, not pure-function logic, so there is
no meaningful "pure function" tier here; no state-machine/closed-transition-set exists
at this requirement's scope, so no property test applies either — see
`docs/guides/test_developer_guide.md` §2, which scopes property tests to modules with a
closed set of legal states/transitions, not present here).

**Explicitly NOT covered by this spec (and why):** no changeset function exists on any
of the four schemas — REQ-015's own design (`lib/letflow/design/identity-schema.md` §3)
defers all changeset/validation behavior to REQ-018/019/020. Writing a test against
`Tenant.changeset/2` or similar would be testing code that does not exist yet. Tests
below construct structs directly and call `Repo.insert/1`, matching this project's
existing pattern for changeset-less schemas (`Letflow.RowApproval.Approval`,
`Letflow.Events.TransitionEvent`).

## Test cases

Criterion 1 (migrations apply cleanly) is proven implicitly, not by a dedicated test:
`mix.exs`'s `test` alias runs `ecto.create --quiet, ecto.migrate --quiet, test` (see
`mix.exs`), so every test below — by virtue of touching the DB inside
`Letflow.DataCase`'s sandboxed connection — only runs at all if all four migrations
already applied cleanly. A dedicated "migrations ran" test would be redundant with what
every other test in this file already proves as a side effect. Criterion 2
(`@moduledoc` citations) and criterion 3 (migration moduledoc statement) are documentation
checks with no executable behavior to assert on — verified by direct reading (already
done: all four `lib/letflow/identity/*.ex` files and all four migration header comments
cite the correct R-Co source and state the schema-per-tenant deferral explicitly, see
`lib/letflow/design/identity-schema.md` §2/§3 and the implemented files themselves), not
by ExUnit.

The test cases below target the two criteria that ARE genuine, non-trivial DB-enforced
behavior (criteria 4 and 5), plus the other DB-level invariants the design document
(§5, "Invariants this design establishes") explicitly calls out as worth protecting
against regression: the partial-index NULL-safety property, the plain unique indexes,
the asymmetric FK strategy (one FK present, two deliberately absent), and the
`Ecto.Enum` values-list declarations.

### `test/letflow/identity/tenant_test.exs`

1. Two tenants inserted with `idp_realm_id: nil` both succeed — proves the partial
   unique index on `tenants.idp_realm_id` does NOT collide multiple NULLs (the
   `WHERE idp_realm_id IS NOT NULL` predicate excludes NULL rows from the index
   entirely). This is exactly the behavior REQ-015's design (§2.1) and
   CODE-DESIGN-VALIDATOR's rework cycle scrutinized — a regression here (e.g. someone
   dropping the `where:` clause to "simplify" the index) would make the second insert
   raise, and this test would catch it.
   See `tenant_test.exs:"two tenants with idp_realm_id: nil can both be inserted (partial index does not collide NULLs)"`.
2. Two tenants inserted with the same non-null `idp_realm_id` — the first succeeds, the
   second raises `Ecto.ConstraintError` — proves the partial index DOES enforce
   uniqueness on the rows it's supposed to cover (non-null values). Without this test, a
   regression that silently dropped the unique index (while keeping the `WHERE` clause
   docs) would go undetected.
   See `tenant_test.exs:"two tenants with the same non-null idp_realm_id: the second raises a constraint error"`.
3. Two tenants inserted with the same `slug` — the second raises `Ecto.ConstraintError`
   — proves the plain (non-partial) unique index on `tenants.slug` is enforced. This is
   the acceptance-criteria-adjacent "global uniqueness" invariant from the design (§2.1).
   See `tenant_test.exs:"two tenants with the same slug: the second raises a constraint error"`.
4. Inserting a tenant via `Ecto.Changeset.cast/3` with `status: "bogus"` (not in
   `[:active, :migrating]`) is rejected by the changeset (`valid?: false`, error on
   `:status`) — proves the `Ecto.Enum` values list was declared correctly on `Tenant`.
   A typo in the values list (e.g. `:migrateing`) would silently either accept the typo
   value or reject a real one; this test pins the exact declared set.
   See `tenant_test.exs:"casting an invalid status value is rejected by the Ecto.Enum declaration"`.

### `test/letflow/identity/user_test.exs`

5. Two users inserted with `external_id: nil` (and arbitrary/absent `external_realm`)
   both succeed — proves the partial unique index on `users (external_realm,
   external_id)` does not collide multiple NULLs. This is REQ-015 acceptance criterion 4
   directly.
   See `user_test.exs:"two users with external_id: nil can both be inserted (partial index does not collide NULLs)"`.
6. Two users inserted with the same non-null `(external_realm, external_id)` pair — the
   first succeeds, the second raises `Ecto.ConstraintError` — proves the partial index
   DOES enforce uniqueness on the rows it covers. This is the other half of acceptance
   criterion 4 ("partial unique index," not "no index at all").
   See `user_test.exs:"two users with the same (external_realm, external_id): the second raises a constraint error"`.
7. Two users inserted with the same `username` — the second raises
   `Ecto.ConstraintError` — proves the plain unique index on `users.username` (design
   §2.2, adp-04 OQ-1's global-uniqueness resolution) is enforced.
   See `user_test.exs:"two users with the same username: the second raises a constraint error"`.
8. A user inserted with `tenant_id` set to a freshly-generated UUID that does not match
   any row in `tenants` succeeds — proves the deliberate ABSENCE of a DB-level FK from
   `users.tenant_id` to `tenants.id` (design §2.2's asymmetric-FK rationale) is real, not
   accidentally enforced. This is arguably the highest-value test in this batch: a
   future migration change that accidentally added `references(:tenants)` back onto
   this column (e.g. someone "fixing" what looks like a missing FK without reading the
   design rationale) would make this insert start raising, and this test would catch
   that regression immediately — the exact case the requirement's own task description
   calls out as worth protecting.
   See `user_test.exs:"a user can reference a tenant_id with no matching tenants row (no DB-level FK enforced)"`.
9. Inserting a user via `Ecto.Changeset.cast/3` with `auth_source: "bogus"` (not in
   `[:internal, :oidc]`) is rejected by the changeset — proves the `Ecto.Enum` values
   list on `User.auth_source` was declared correctly (same rationale as case 4).
   See `user_test.exs:"casting an invalid auth_source value is rejected by the Ecto.Enum declaration"`.
10. No DB CHECK constraint enforces auth_source-vs-external-fields consistency
    (acceptance criterion 5): a user inserted with `auth_source: :internal` and both
    `external_id`/`external_realm` non-null succeeds at the DB level (would be invalid
    under adp-04a's rule 2, but that rule is explicitly NOT a DB constraint per this
    requirement — REQ-018/019 own it). This proves the DB layer stays permissive here as
    designed, rather than a stray CHECK constraint someone added later silently starting
    to reject rows the design says must pass through to the application layer.
    See `user_test.exs:"auth_source/external-fields inconsistency is NOT rejected at the DB level (no CHECK constraint)"`.

### `test/letflow/identity/group_test.exs`

11. A group inserted with `tenant_id` set to a freshly-generated UUID with no matching
    `tenants` row succeeds — same rationale as case 8, applied to `groups.tenant_id`
    (design §2.3, same asymmetric-FK omission).
    See `group_test.exs:"a group can reference a tenant_id with no matching tenants row (no DB-level FK enforced)"`.

### `test/letflow/identity/tenant_role_test.exs`

12. A `tenant_role` inserted with `group_id` set to a freshly-generated UUID with no
    matching `groups` row raises `Ecto.ConstraintError` — proves the DB-level FK from
    `tenant_role.group_id` to `groups.id` (the one FK that DOES exist in this batch,
    design §2.4) is actually enforced, not just declared in the migration file. This is
    the direct counterpart to cases 8/11: the design draws an explicit asymmetric-FK
    distinction (`tenant_role.group_id` has a real FK, `tenant_id` columns don't), and
    both halves of that asymmetry need their own regression protection — a test suite
    that only checked the absent FKs would leave the present one unverified.
    See `tenant_role_test.exs:"a tenant_role with a group_id that matches no groups row raises a constraint error"`.
13. A `tenant_role` inserted with `group_id` referencing a real, freshly-inserted
    `groups` row succeeds — the FK's positive case, proving the constraint doesn't
    over-reject valid references.
    See `tenant_role_test.exs:"a tenant_role with a group_id that matches a real groups row succeeds"`.
14. Two `tenant_role` rows inserted with the same `name` — the second raises
    `Ecto.ConstraintError` — proves the plain unique index on `tenant_role.name`
    (design §2.4) is enforced.
    See `tenant_role_test.exs:"two tenant_roles with the same name: the second raises a constraint error"`.
