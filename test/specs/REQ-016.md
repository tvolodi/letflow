# Test Spec: REQ-016 — Add `ueberauth_oidcc` dependency and supervise `Oidcc.ProviderConfiguration.Worker`

**Requirement:** REQ-016 (`docs/requirements.yaml`, stage S1) — add `{:ueberauth_oidcc,
"~> 0.4"}` to `mix.exs`, add a supervised `Oidcc.ProviderConfiguration.Worker` child spec
to `lib/letflow/application.ex`, sourced from config, not a hardcoded issuer URL.

**Requirement's acceptance criteria (verbatim):**
1. "mix.exs lists ueberauth_oidcc ~> 0.4, mix deps.get resolves it"
2. "lib/letflow/application.ex's children list includes a supervised
   Oidcc.ProviderConfiguration.Worker child spec, sourced from config rather than a
   literal hardcoded issuer URL"
3. "mix compile --warnings-as-errors passes"
4. "if the worker cannot reach a real issuer in this environment, that is stated
   explicitly"

**Test tier:** unit/integration (real supervision tree, no mocks — `Letflow.Application`
boots for real on every `mix test` invocation, same process every other test in this
suite already runs inside). No pure-function tier applies: this requirement adds no
pure logic, only dependency/config/supervision wiring. No property test applies: there
is no closed state/transition set here (contrast `Letflow.ProcessInstance`) — a
provider-configuration worker's own internal retry/backoff state machine belongs to
`oidcc`, a third-party library, not to Letflow's own code.

## Scope test (run before writing anything, per TEST-DESIGNER's mandate)

This requirement is almost entirely config/supervision wiring, not application logic
with a testable pure-function surface. Each criterion was checked individually for
whether it has real, non-redundant executable surface to test against:

**Criterion 1 (mix.exs / mix.lock resolution) — not independently tested.** This is a
fact about `mix.exs`'s dependency list and `mix.lock`'s resolution output, not
ExUnit-testable application behavior. Writing a test that asserts `mix.exs`'s deps list
contains `:ueberauth_oidcc` would be checking the file against itself — it would only
ever fail if someone hand-deleted the line, and an ExUnit test is a strange, indirect
way to catch that compared to just reading the file. This criterion is instead verified
by direct inspection, quoted here as real evidence, not asserted on faith:
- `mix.exs` line 40: `{:ueberauth_oidcc, "~> 0.4"}` is present in `deps/0`.
- `mix.lock` lines 11 and 20 confirm both `:oidcc` (3.8.0, transitive) and
  `:ueberauth_oidcc` (0.4.2, direct) are resolved/locked hex packages.
- `mix compile --warnings-as-errors` (see criterion 3) would fail immediately if
  `Oidcc.ProviderConfiguration.Worker` weren't a real, resolved module — so every green
  compile is itself live, continuous re-verification that resolution succeeded, on top
  of the one-time `mix.lock` inspection above.

**Criterion 2 (supervised child spec, config-sourced) — THIS is tested.** This is the
one criterion with genuine, non-redundant executable surface: whether the child spec
described in `application.ex`'s source is actually wired into the real, running
supervision tree (not just present as dead code that nothing exercises), and whether it
reads its `issuer`/`name` from config rather than a hardcoded literal. Both are
verifiable by booting the app (which every `mix test` run already does once, as part of
ExUnit's normal app-start path) and inspecting the live tree. See "Test cases" below.

**Criterion 3 (mix compile --warnings-as-errors) — not a distinct test case.** Every
test run in this suite starts with `mix compile` (directly, and again implicitly via
`mix letflow.check`'s `compile --warnings-as-errors` step). If the new dependency or
child-spec code introduced a compile warning or error, no test below — or any existing
test — would even run. The full test suite passing (see "Full-suite run" below) is
itself the proof for this criterion; a dedicated ExUnit test asserting on compiler
output would be redundant busywork, not additional coverage.

**Criterion 4 (unreachable-issuer behavior stated explicitly) — covered by implicit
app-boot, not a dedicated test, and here is why that's a deliberate conclusion rather
than an oversight:**

The empirical work this criterion asks for — does the worker crash the application when
the configured issuer is unreachable? — was already done by ELIXIR-DEV and independently
confirmed by REVIEWER via manual boot observation over a 30-second window (see
`lib/letflow/design/req016-oidc-dependency-supervision.md` §7 and §11 item 2): the
original `backoff_type: :stop` (library default) crashed the whole `Letflow` application
within ~150ms; the corrected `backoff_type: :random` was verified to keep the app and
the worker alive indefinitely against the same unreachable placeholder. That finding is
not application behavior Letflow's test suite should re-derive — it is a static fact
about `oidcc`'s own source (`deps/oidcc/src/oidcc_backoff.erl`'s `type()` spec has no
`:stop` branch in the `random` clause, confirmed by REVIEWER reading the source
directly), and re-testing a third-party library's internal state machine inside
Letflow's suite would be testing `oidcc`, not Letflow.

What IS worth noting is that this suite's own successful, repeated execution is a live,
continuous instance of exactly the non-crash scenario criterion 4 is asking about:
`config/test.exs`'s `:oidc` issuer is `https://placeholder-keycloak.invalid/realms/bpm-default`
— the same class of permanently-unreachable `.invalid`-TLD placeholder used in the
manual verification — and every `mix test` run boots `Letflow.Application` against it.
The full-suite run captured below shows the actual log line this produces:

```
03:05:28.886 [error] Metadata load failed for issuer https://placeholder-keycloak.invalid/realms/bpm-default. Retrying in 1519 ms. Error Details: {:configuration_load_failed, {:failed_connect, [{:to_address, {~c"placeholder-keycloak.invalid", 443}}, {:inet, [:inet], :nxdomain}]}}
```
— followed by 35/35 tests passing, including the new `application_test.exs` cases that
directly assert the worker process is still alive at that point. This is real,
non-fabricated evidence of "worker cannot reach a real issuer, and this does not crash
the application" on every single test run, not a one-time manual observation that could
go stale. A dedicated test that explicitly waits multiple retry intervals (multiple
seconds, given `backoff_min`/`backoff_max` defaults of 1000ms/30000ms) to watch several
retries happen would add wall-clock cost and flakiness risk (per Test Developer Guide
principle 3, "deterministic only... no dependency on wall-clock time") without proving
anything the criterion-2 tests plus this passive observation don't already establish.
**Conclusion: no dedicated test case for criterion 4 beyond what criterion 2's tests and
the suite's own boot-and-run already provide implicitly on every invocation.**

## Test cases

### `test/letflow/application_test.exs`

1. **"the OIDC provider-configuration worker is alive and registered under its
   configured name"** — reads `Application.fetch_env!(:letflow, :oidc)`'s
   `:provider_name`, then asserts `Process.whereis/1` resolves it to a live pid. This
   proves the worker was actually started under the exact name config supplies, not a
   different/default name, and that it's still alive (not started-then-immediately-
   crashed) at the point the test suite runs — which, given `config/test.exs`'s
   unreachable placeholder issuer, is direct evidence the `:random` backoff decision
   holds in practice, not just in the design doc's reasoning.
   See `application_test.exs:"the OIDC provider-configuration worker is alive and registered under its configured name"`.
2. **"Letflow.Supervisor supervises the OIDC worker as a real child, not just
   config-referenced"** — calls `Supervisor.which_children(Letflow.Supervisor)` and
   asserts an entry exists whose child module list is `[Oidcc.ProviderConfiguration.Worker]`,
   type `:worker`, with a live pid. This is the direct, load-bearing test for acceptance
   criterion 2: it proves the child spec described in `application.ex`'s source is
   actually present in the real supervision tree Letflow boots, not dead code that
   compiles but was never added to the `children` list (e.g. a copy-paste into the wrong
   list, or a spec that silently got dropped in a later edit). A regression that removed
   this child from the list — accidentally or via a bad merge — would make this test fail
   immediately; nothing else in the suite would catch that, since no other test
   references OIDC at all.
   See `application_test.exs:"Letflow.Supervisor supervises the OIDC worker as a real child, not just config-referenced"`.
3. **"the worker's issuer/name are sourced from config, not hardcoded, and match what
   booted"** — asserts `Application.fetch_env!(:letflow, :oidc)` returns a non-empty
   `:issuer` string and an atom `:provider_name`, and that `Process.whereis/1` on that
   exact `:provider_name` resolves. This is the config-sourcing half of criterion 2: if
   `application.ex` were changed to pass a literal hardcoded atom/string instead of
   reading `Application.get_env/fetch_env!`, the live registered name could drift from
   what config declares without any other symptom (the app would still boot, the worker
   would still run, just under a name nothing else could look up via config) — this test
   would catch that drift because it derives the expected name from config and then
   checks the live process was registered under that same value, rather than hardcoding
   the expected atom in the test itself.
   See `application_test.exs:"the worker's issuer/name are sourced from config, not hardcoded, and match what booted"`.
