# Test Spec: REQ-017 — Pure claim-mapping module (OIDC-08 equivalent)

**Requirement:** REQ-017 (`docs/requirements.yaml`, stage S1) — port
`src/oidc/claim_mapping.zig`'s `mapVerifiedClaims` as a pure Elixir function
(`Letflow.Oidc.ClaimMapping.map_verified_claims/3`) mapping verified OIDC claims to a
`Letflow.Oidc.IdentityContext` struct, using a per-realm `Letflow.Oidc.ClaimMappingConfig`
for configurable claim paths.

**Requirement's acceptance criteria (verbatim):**
1. "the mapping function has no Repo call, no HTTP call, and no other I/O anywhere in its
   call graph — verified by inspection and stated explicitly in the handoff"
2. "given claims missing every optional field, the function returns defaults matching
   claim_mapping.zig's Key Invariant 3 (email->\"\", preferred_username->sub value,
   roles->[], display_name->nil, tenant_id->nil) rather than erroring"
3. "given claims with no sub/subject, the function returns an error (not a default),
   matching claim_mapping.zig's SubClaimMissing"
4. "@moduledoc cites src/oidc/claim_mapping.zig as the ported source"

**Test tier:** unit + property. `Letflow.Oidc.ClaimMapping`, `Letflow.Oidc.ClaimMappingConfig`,
and `Letflow.Oidc.IdentityContext` are pure, I/O-free modules (design doc §9's call-graph
enumeration; `Application.fetch_env!/2` only appears in `ClaimMappingConfig.for_realm/1`,
which is one level above `map_verified_claims/3` and not part of its call graph). Plain
`ExUnit.Case`, no `Letflow.DataCase`, no `Ecto.Adapters.SQL.Sandbox` — there is no DB
interaction anywhere in the module(s) under test, so the sandboxed-Postgres test case
this project uses elsewhere (`process_instance_test.exs`, `application_test.exs`) would be
the wrong tool here, not a stricter one. All tests run `async: true`.

## Scope test (run before writing anything, per TEST-DESIGNER's mandate)

Unlike REQ-016 (supervision/config wiring with almost no pure-function surface), REQ-017 is
the opposite case: three new modules under `lib/letflow/oidc/`, two of which
(`ClaimMapping`, `ClaimMappingConfig`) contain real branching logic with a precisely
specified defaulting/short-circuit behavior. This has genuine, non-redundant executable
surface — routed through the full TEST-DESIGN-VALIDATOR / TEST-RUNNER chain, not fast-tracked
to RELEASE-VALIDATOR.

Per-criterion scope check:

- **Criterion 1 (zero I/O)** — SECURITY-REVIEWER and REVIEWER already confirmed this by
  reading the module's full call graph (design doc §9); "zero I/O" is a static property of
  which functions the code calls, not a runtime behavior an assertion can observe directly
  (there is no `Repo` call to *not* make that a test could distinguish from "the test
  environment happened to have no DB traffic right now"). Re-deriving it here: every test
  below calls `map_verified_claims/3` directly, in-process, with fabricated in-memory
  `claims` maps and no application/database/network setup of any kind — no
  `Letflow.DataCase`, no `Ecto.Adapters.SQL.Sandbox.checkout`, no started `Letflow.Repo`
  connection is needed for any test in this file to pass, which is itself concrete evidence
  the function touches none of those. Not adding a dedicated "returns fast with unreachable
  inputs" test beyond that — every example/property test below already uses claim data that
  could never resolve against any real IdP, and all pass in well under a millisecond each
  (see the full run below), so a separate no-timeout test would just be re-asserting the
  same thing the whole suite already demonstrates on every run.
- **Criterion 2 (defaulting behavior)** — the primary tested surface. See "Test cases"
  below; every field's specific default, both individually and in combination, is covered.
- **Criterion 3 (sub-missing error case)** — tested directly, both `nil` and `""` subject,
  plus the converse (non-empty subject with all other claims missing never errors).
- **Criterion 4 (moduledoc citation)** — confirmed by direct inspection, not an ExUnit test
  (an assertion that reads the source file's own `@moduledoc` string and checks it contains
  a substring would be checking the file against itself — see REQ-016's spec for the same
  reasoning applied to its criterion 1). Direct inspection:
  `lib/letflow/oidc/claim_mapping.ex` lines 2-6 cite `src/oidc/claim_mapping.zig`'s
  `mapVerifiedClaims` explicitly in the `@moduledoc`; `identity_context.ex` lines 2-6 and
  `claim_mapping_config.ex` lines 2-6 likewise cite the same source file for the structs
  they port. All three present.

Additionally tested beyond the four acceptance criteria (design doc §5/§7 make these
specific, non-obvious rules that the criteria only summarize at "Key Invariant 3" level):

- `resolve_claim_path/2`'s dotted-path walk, non-map-mid-path, and absent-path behavior
  (design doc §5's citation of `resolveJsonPath`, "never raises").
- `resolve_roles/2`'s short-circuit-on-first-list-typed-path rule, including the case where
  an earlier path resolves to a non-list value (must be skipped, not treated as a match) and
  the case where a matched array contains non-string elements (converted to `""`, not
  dropped — array length preserved).
- `ClaimMappingConfig.for_realm/1` and `default/1`'s realm-threading behavior (design doc
  §4.1, OQ-1).
- A `StreamData` property test — see "Property test rationale" below.

## Test cases

### `test/letflow/oidc/claim_mapping_test.exs`

**`map_verified_claims/3` — defaulting behavior (criterion 2)**

1. **"all optional claims missing: every field defaults per Key Invariant 3"** — calls with
   `claims: %{"sub" => "user-1"}` (only `sub` present) and asserts every field against its
   exact documented default in one assertion: `tenant_id: nil`, `realm:` (config's realm),
   `roles: []`, `email: ""`, `preferred_username: "user-1"` (the subject value, not `""`),
   `display_name: nil`. This is the single most direct test of criterion 2's exact wording.
2. **"preferred_username defaults to the subject value, not a blank string"** — isolates
   this specific rule (the one default that is *not* `""`/`nil`/`[]`, easy to get wrong by
   copy-pasting the `email`-shaped default): claims missing `preferred_username` entirely,
   asserts `preferred_username == subject` for two different subject values, proving the
   default tracks whatever `subject` actually is, not a hardcoded string.
3. **"email missing -> \"\""**, **"tenant_id missing -> nil"**, **"display_name missing ->
   nil"**, **"roles missing -> []"** — one focused test per field, each supplying every
   *other* optional claim (so a field defaulting only because the whole map was empty can't
   be mistaken for the field defaulting because that specific path was absent).
4. **"a present-but-wrong-JSON-type claim value defaults exactly like a missing one, for
   each of the four string-shaped fields"** — design doc §5's cross-field pattern ("missing
   path -> default; path resolves to wrong type -> same default, never an error") is the
   part of Key Invariant 3 the acceptance-criterion text only implies via
   `resolve_optional_string_claim/3`'s existence. Tests `email`, `tenant_id`,
   `preferred_username`, and `display_name` each set to a non-string value (integer, list,
   map, boolean — one per field, varied) and asserts the same default as the missing-claim
   case, not an error and not the raw wrong-typed value leaking through.
5. **"combination: some optional fields present, some missing"** — a claims map with
   `email` and `roles` present but `tenant_id`, `preferred_username`, `display_name`
   absent; asserts the present fields are read correctly *and* the absent fields still get
   their individual defaults in the same call — proving defaulting is per-field
   independent, not all-or-nothing.
6. **"all optional claims present with valid values: no defaulting occurs"** — the
   converse of case 1, full happy-path claims map, asserts every field reflects the claim
   value verbatim (not a default) — without this, cases 1-5 alone couldn't rule out a bug
   where a field defaults unconditionally regardless of what's in `claims`.
7. **"realm always comes from config, never from claims, even if claims contains a
   `\"realm\"` key"** — claims map includes a `"realm" => "attacker-supplied"` key (not
   configured as any claim path); asserts `IdentityContext.realm` equals `config.realm`,
   proving `realm` is never claim-derived (design doc §6: "N/A — always supplied by the
   caller's `ClaimMappingConfig.realm`, never claim-derived, never defaulted").

**`resolve_roles/2` short-circuit behavior (design doc §7.3, REVIEWER's finding)**

8. **"first configured roles path that resolves to a list wins"** — `roles_claim_paths:
   ["realm_access.roles", "roles"]`, claims has both paths present as lists with different
   contents; asserts the first path's list is returned, not the second's.
9. **"a path that resolves to a non-list value is skipped, not treated as an error or a
   match — the next path in the list is tried"** — first path resolves to a string (wrong
   type, not a list), second path resolves to a real list; asserts the second path's list
   wins, proving the "resolves but wrong type" case falls through to the next candidate
   rather than short-circuiting on the wrong-typed value or erroring.
10. **"no configured path resolves to a list at all -> []"** — every path in
    `roles_claim_paths` either absent from claims or resolves to a non-list value; asserts
    `roles == []`.
11. **"non-string elements inside a matched roles array become empty strings, array length
    preserved"** — matched path's list is `["admin", 42, "user", nil, %{}]`; asserts result
    is `["admin", "", "user", "", ""]` (length 5, non-strings converted not dropped) per
    design doc §7.3's citation of Zig's `switch (item) { .string => |s| s, else => "" }`.

**`map_verified_claims/3` — sub-missing error case (criterion 3)**

12. **"nil subject returns {:error, :sub_claim_missing}"** — `subject: nil`, claims
    otherwise fully populated (proving the error fires on subject alone, not because other
    claims were also missing).
13. **"empty-string subject returns {:error, :sub_claim_missing}"** — `subject: ""`, same
    fully-populated claims, same assertion — the second half of criterion 3's "no sub"
    case per the design doc's OQ-2 resolution (nil and "" both trigger the error).
14. **"a present, non-empty subject never triggers sub_claim_missing, even when every other
    claim is absent"** — claims `%{}` (nothing but what the test itself doesn't add) with a
    real subject string; asserts `{:ok, %IdentityContext{}}` is returned, not an error —
    the converse of 12/13, proving the error path is specifically and only about `subject`,
    not a general "claims map looks sparse" heuristic.

**`resolve_claim_path/2` — path resolution (design doc §5's `resolveJsonPath` citation)**

15. **"single-segment path resolves a top-level key"**.
16. **"multi-segment dotted path resolves a nested value"** — e.g. `"realm_access.roles"`
    against `%{"realm_access" => %{"roles" => [...]}}`.
17. **"a path that hits a non-map value partway through resolves to nil, does not raise"**
    — e.g. path `"a.b.c"` against `%{"a" => %{"b" => "not-a-map"}}` (segment `"b"` resolves
    to a string, then segment `"c"` can't be looked up on a string); asserts `nil` is
    returned, and implicitly (by the test not crashing) that no exception was raised.
18. **"a completely absent top-level path resolves to nil"**.
19. **"an absent nested path (parent map exists, child key doesn't) resolves to nil"**.

**`ClaimMappingConfig.for_realm/1` / `default/1`**

20. **"for_realm/1 returns the configured entry for a realm present in application
    config"** — using `config/test.exs`'s `"bpm-default"` entry; asserts every field
    matches what's configured (`config/test.exs` fixture is the same one the running app
    already uses — real config, not a test-only stub).
21. **"for_realm/1 falls back to default/1 for a realm with no config entry"** — a realm
    string guaranteed absent from `config/test.exs` (e.g. `"unconfigured-realm"`); asserts
    the returned config equals `ClaimMappingConfig.default("unconfigured-realm")` exactly.
22. **"default/1 threads the given realm into the returned struct's realm field, not Zig's
    literal empty string"** — design doc §4.1/OQ-1's deliberate deviation; asserts
    `ClaimMappingConfig.default("some-realm").realm == "some-realm"` for two different
    realm arguments, proving the value is threaded through, not hardcoded.

### `test/letflow/oidc/claim_mapping_property_test.exs`

23. **Property: "for any claims map containing a non-empty string sub, map_verified_claims/3
    never raises and always returns {:ok, %IdentityContext{}} with the seven-field shape
    intact"** — see "Property test rationale" below.

## Property test rationale

This project's established precedent (`test/letflow/process_instance_test.exs`) uses
`StreamData` for a closed state/transition set — not the shape `ClaimMapping` has (there's
no state machine here). But REQ-017's own SECURITY-REVIEWER/REVIEWER sign-off rests
specifically on the claim that `resolve_claim_path/2`'s map-walk **never raises**, regardless
of what shape the `claims` map or its nested values take (design doc §5: "never raises";
§9's zero-I/O call graph). That is exactly the kind of guarantee a fixed set of hand-picked
examples proves only at the specific points chosen, while a property test proves it across
the whole space of malformed/adversarial claim shapes StreamData can generate — arbitrary
nesting, arbitrary value types (numbers, booleans, nested maps, nested lists, `nil`) sitting
where a map was expected. Given the function's safety-critical role (it is the boundary
between attacker-controlled JWT claims and the rest of the identity pipeline REQ-018/021
build on), this is judged worth the investment: one property test, generating random
`claims` maps whose values are drawn from a recursive generator (maps, lists, strings,
integers, booleans, `nil`, mixed), always paired with a valid non-empty string `sub`, and
asserting the call **never raises** and **always** returns `{:ok, %IdentityContext{}}` with
all seven struct fields set to the right static types (`is_binary/1` for `email`/
`preferred_username`/`realm`/`external_user_id`, `is_list/1` for `roles`, `is_binary/1` or
`is_nil/1` for `tenant_id`/`display_name`). This gives ongoing regression protection for the
"never raises on malformed claims" guarantee specifically — a guarantee REVIEWER confirmed
holds today by reading the code, but that a future edit (e.g. someone replacing
`resolve_claim_path/2`'s `Map.get/2` with `Map.fetch!/2` while refactoring) could silently
break without any example-based test catching it if the example fixtures happen to avoid
the exact malformed shape that would trip the new bug. Not adding a second property for the
`roles_claim_paths` short-circuit rule specifically — cases 8-11 above already give that
rule direct, readable, exact-value coverage (property tests are better suited to "never
raises" / "shape invariant" style guarantees than to pinning an exact expected output,
which is what the short-circuit rule needs).
