# Test Spec: REQ-018 — JIT user provisioning (createOrGetJitOidcUser equivalent)

**Requirement:** REQ-018 (`docs/requirements.yaml`, stage S1) — port the JIT
(just-in-time) user-provisioning orchestration from `src/oidc/jit_provisioning.zig`
together with the actual upsert from `src/identity/registry.zig`'s
`createOrGetJitOidcUser` (lines ~843-912) into `Letflow.Identity.provision_oidc_user/3`,
operating on REQ-015's `users` schema (`Letflow.Identity.User`), keyed on
`(tenant_id, external_realm, external_id)`.

**Requirement's acceptance criteria (verbatim):**
1. "calling the provisioning function twice with the same (tenant_id, external_realm,
   external_id) returns the same user_id both times, with created: true only on the
   first call — demonstrated with an actual test or iex session, not just described"
2. "the inserted row has password_hash set to the fixed OIDC-only marker and
   auth_source: :oidc"
3. "a simulated concurrent-insert race (two calls racing before either commits) is
   handled by the re-select fallback without raising an unhandled exception — either
   demonstrated or the code path is inspected and cited explicitly if concurrency can't
   be simulated in this environment"
4. "@moduledoc cites src/oidc/jit_provisioning.zig and src/identity/registry.zig's
   createOrGetJitOidcUser as the ported source"

**Test tier:** unit + integration. `Letflow.Identity.provision_oidc_user/3` and
`Letflow.Identity.User.jit_changeset/2` both touch `Letflow.Repo` (real Postgres via
`Letflow.DataCase`'s sandboxed connection) — this is not a pure-function module the way
REQ-017's `ClaimMapping` is. `Letflow.Oidc.JitProvisioningConfig`'s `for_realm/1`,
`default/1`, and `default_roles/1` ARE pure (config-read or plain struct logic, no
`Repo` call) and are tested separately, `async: true`, with no DB dependency.

## Scope test

Real application-executable Elixir logic: `lib/letflow/identity.ex` (upsert
orchestration + private algorithm), `lib/letflow/oidc/jit_provisioning_config.ex`
(config struct + 3 functions), `lib/letflow/identity/user.ex`'s `jit_changeset/2`. Not
docs-only, not build-config. Full TEST-DESIGN-VALIDATOR / TEST-RUNNER chain applies.

## Files

- `test/letflow/identity_test.exs` — `provision_oidc_user/3` (criteria 1, 2, 3, plus
  the jit-disabled and username-collision cases the design flags as important).
- `test/letflow/oidc/jit_provisioning_config_test.exs` — `JitProvisioningConfig.for_realm/1`,
  `default/1`, `default_roles/1`.

## Test cases

### Acceptance criterion 1 — idempotency

1. **First call creates, second call with the identical `(tenant_id, realm,
   external_user_id)` triple returns the same `user.id` with `created: false`** — see
   `identity_test.exs:"calling provision_oidc_user/3 twice with the same identity
   returns the same user.id, created: true then false"`. This is the direct acceptance
   demonstration: proves the select-first branch (design §3.3 step 1) actually
   short-circuits the second call rather than attempting (and colliding on) a second
   insert. Would fail if the second call minted a new row, returned a different id, or
   reported `created: true` again.
2. **Idempotency holds across three consecutive calls, not just two** — see
   `identity_test.exs:"three consecutive calls all resolve to the same user.id"`. Guards
   against an off-by-one implementation that only special-cases "the second call" rather
   than genuinely converging to a stable row. Would fail if any of calls 2 or 3 produced
   a different id or an unexpected `created: true`.

### Acceptance criterion 2 — fixed literals on the inserted row

3. **`password_hash == "__OIDC_ONLY__"` and `auth_source == :oidc` on a freshly created
   row, read back from Postgres (not just the in-memory reply)** — see
   `identity_test.exs:"the inserted row has the fixed OIDC-only password_hash and
   auth_source: :oidc"`. Re-selects the row via `Letflow.Repo.get/2` after the call,
   matching this project's existing "persistence test" convention
   (`process_instance_test.exs`'s "every successful transition is persisted to
   Postgres") — proves the value actually landed in the database, not merely in the
   changeset's local struct. Would fail if `password_hash`/`auth_source` were left
   caller-overridable or the literal were misspelled/wrong-cased.
4. **A caller cannot override `password_hash` or `auth_source` by supplying them via the
   `IdentityContext`/attrs path** — see `identity_test.exs:"password_hash and
   auth_source are not caller-overridable"`. `IdentityContext` has no `password_hash`
   field at all, so this is exercised indirectly: the test constructs the identity
   context and asserts the persisted row still carries the fixed literals regardless of
   what's in context. Guards the changeset-internal-fixed-value design decision (design
   §5) — would fail if a future change threaded a caller-supplied value through
   `cast/3` instead of `put_change/3`.

### Acceptance criterion 3 — concurrent-insert race

5. **Two genuinely concurrent calls racing into the `INSERT ... ON CONFLICT` path for
   the identical `(tenant_id, realm, external_user_id)` triple**: no unhandled exception
   escapes either `Task`, both return `{:ok, _}`, exactly one has `created: true`, both
   resolve to the same `user.id`, and exactly one row exists in the database afterward —
   see `identity_test.exs:"a genuine concurrent race between two tasks resolves to
   exactly one created row, both callers succeed"`. Built per design §9's exact guidance:
   two `Task.async/1`-spawned processes, each `Ecto.Adapters.SQL.Sandbox.allow/3`'d onto
   the test's own sandboxed connection (manual mode, configured in
   `test/test_helper.exs` for this run), synchronized on a barrier
   (`Task.async` + a shared `Agent`-free `send`/`receive` rendezvous — see the test file
   for the exact mechanism) so both tasks complete their own select-first step before
   either attempts the insert, then both proceed into `Repo.insert/2` at effectively the
   same time. This is the one acceptance criterion that a naive two-sequential-calls test
   (which would only exercise criterion 1's idempotency path, never touching the
   `ON CONFLICT`/re-select branch at all) cannot satisfy — see design §9's explicit
   warning about this trap. Would fail if the re-select-on-conflict logic raised
   `Ecto.ConstraintError` (i.e. if the implementation used a naive "insert, catch
   unique-constraint" pattern instead of `on_conflict: :nothing`), or if both tasks
   reported `created: true`, or if two rows ended up in the database for the same
   identity.
6. **Inspection-only: the `conflict_target`'s predicate genuinely matches the migration's
   partial index.** Per design §9 ("a compile-time/migration-time property, not something
   a passing test row-count alone proves"), this is confirmed by direct inspection of
   `lib/letflow/identity.ex`'s `insert_or_fetch/3`, cross-checked against
   `priv/repo/migrations/20260816000004_create_users.exs`'s index definition — see
   "Inspection-only findings" below. Not a runtime assertion; recorded here so the
   traceability table has an explicit entry for this design-flagged check rather than
   silently omitting it.

### Acceptance criterion 4 — moduledoc citations

7. **Inspection-only, not a runtime test.** `lib/letflow/identity.ex`'s `@moduledoc`
   is checked by direct reading, not an ExUnit assertion that greps the source file for a
   substring (an assertion reading a module's own `@moduledoc` string and checking it
   contains a citation would be checking the file against itself — same reasoning
   REQ-016/REQ-017's specs already applied to their own citation criteria). See
   "Inspection-only findings" below.

### Design-flagged coverage beyond the 4 acceptance criteria

8. **`jit_config.enabled == false` short-circuits to `{:error, :jit_disabled}` with no DB
   write** — see `identity_test.exs:"jit_config.enabled == false returns {:error,
   :jit_disabled} without writing to the database"`. Exercises design §2.2 step 1 (the
   precondition check before any `Repo` call). The "no DB write occurs" half is verified
   by querying `Letflow.Identity.User` by the test's unique external identity afterward
   and asserting zero rows exist — not merely trusting the return value. Would fail if
   the disabled-check were skipped, reordered after the insert attempt, or if a row got
   written despite the error return.
9. **Cross-tenant `username` collision (design §4.4/OQ-3, explicitly recommended by
   §9): two different tenants, same `preferred_username`, the second tenant's
   provisioning call fails with a changeset error naming `username`** — see
   `identity_test.exs:"two different tenants with the same preferred_username: the
   second JIT provisioning call fails with a username uniqueness changeset error"`. Pins
   the known, design-acknowledged limitation (global, not tenant-scoped, unique index on
   `users.username`) as documented shipped behavior rather than an undiscovered surprise.
   Would fail if a future change silently mangled the username to avoid the collision
   (the pinned behavior would then no longer reproduce) or if the collision instead raised
   an unhandled `Ecto.ConstraintError` (would mean the `unique_constraint(:username)`
   declaration was dropped from the changeset, an INV-8 regression).
10. **`display_name` nil-fallback to `preferred_username`** — see
    `identity_test.exs:"display_name nil in the identity context falls back to
    preferred_username on the persisted row"`. Exercises design §4.3's explicitly-cited
    fallback rule (`identity_ctx.display_name orelse identity_ctx.preferred_username`,
    ported from `jit_provisioning.zig` line 359's sync-path rule applied here to the
    create path). Would fail if a future change stored `nil`/raised instead of falling
    back, or if the fallback source were wrong (e.g. falling back to `external_user_id`
    instead of `preferred_username`).
11. **`display_name` provided (non-nil) is stored verbatim, not overridden by the
    fallback** — see `identity_test.exs:"display_name present in the identity context is
    stored verbatim"`. The converse of case 10 — proves the `||` fallback is genuinely
    conditional on `nil`, not an unconditional overwrite. Would fail if the
    implementation always used `preferred_username` regardless of whether `display_name`
    was supplied.
12. **`external_identity_collision` fallback branch — inspection-only, not a runtime
    test.** Design §9 states this branch ("re-select after conflict finds nothing") is
    "deliberately-unreachable-in-normal-operation" and is reachable only by a genuine
    three-way race (two concurrent inserts conflict, and then a *third* process deletes
    the row before the re-select) that is not reproducible as a deterministic test in
    this environment without directly invoking the module's private functions (which
    `provision_oidc_user/3`'s public contract does not expose, and adding a
    test-only public seam purely to reach an intentionally-defensive branch would be
    exactly the kind of implementation-shape-driven busywork this project's test-design
    guidance warns against). Verified by direct code inspection instead — see
    "Inspection-only findings" below. This matches the task's own instruction: state
    explicitly rather than inventing fake coverage.

## Test cases — `JitProvisioningConfig` (not a REQ-018 acceptance criterion by number,
but named directly in the design and needed for `provision_oidc_user/3`'s own inputs)

13. **`for_realm/1` returns the configured entry for a realm present in
    `config :letflow, :oidc_jit_provisioning`** — see
    `jit_provisioning_config_test.exs:"for_realm/1 returns the configured entry for a
    realm present in application config"`. Uses the already-configured `"bpm-default"`
    entry (`config/test.exs`). Would fail if the config-read mapped the wrong keys or
    silently fell back to defaults despite a configured entry existing.
14. **`for_realm/1` falls back to `default/1` for an unconfigured realm** — see
    `jit_provisioning_config_test.exs:"for_realm/1 falls back to default/1 for a realm
    with no config entry"`. Would fail if an unconfigured realm raised (e.g. a bare
    `Map.fetch!/2`) instead of falling back, or returned a struct that doesn't match
    `default/1`'s own output.
15. **`default/1` threads the given `realm` argument into the returned struct** — see
    `jit_provisioning_config_test.exs:"default/1 threads the given realm into the
    returned struct's realm field"`. Would fail if `realm` were hardcoded/ignored.
16. **`default_roles/1`: empty `default_roles` on the config falls back to
    `["VIEWER"]`; non-empty `default_roles` is returned unchanged** — see
    `jit_provisioning_config_test.exs:"default_roles/1 empty -> [VIEWER], non-empty ->
    unchanged"`. Both branches in one test (paired assertions), matching design §6.1's
    exact rule. Would fail if either branch used the wrong fallback value or if a
    non-empty list were incorrectly replaced.

## Inspection-only findings (not runtime assertions)

- **AC4 — moduledoc citations.** Read `lib/letflow/identity.ex` lines 1-15 directly: the
  `@moduledoc` states `provision_oidc_user/3` (below) ports the JIT (just-in-time)
  user-provisioning orchestration from `src/oidc/jit_provisioning.zig` together with the
  actual upsert from `src/identity/registry.zig`'s `createOrGetJitOidcUser` (lines
  ~843-912)" — both source files named explicitly, satisfying AC4 as written.
- **Case 6 — `conflict_target` predicate match.** `lib/letflow/identity.ex`'s
  `insert_or_fetch/3` passes `conflict_target: {:unsafe_fragment, "(external_realm,
  external_id) WHERE external_id IS NOT NULL"}` to `Repo.insert/2`. This textually
  matches `priv/repo/migrations/20260816000004_create_users.exs`'s
  `unique_index(:users, [:external_realm, :external_id], where: "external_id IS NOT
  NULL", name: :users_external_identity_partial_index)` — same two columns, same WHERE
  predicate. Test case 5 (the genuine concurrent race) is the runtime evidence that this
  `conflict_target` is not merely textually plausible but actually functions as the
  `ON CONFLICT` target under a real race (if it targeted the wrong index/predicate, the
  race would either raise `Ecto.ConstraintError` on the losing task, or the two
  concurrent inserts would both succeed and leave two rows — case 5's assertions rule out
  both).
- **Case 12 — `external_identity_collision` fallback.** `lib/letflow/identity.ex`'s
  `re_select_on_conflict/2`: after the insert path signals "no genuinely-inserted row"
  (via the `Repo.get(User, id)` existence check — see implementation note below), it
  re-selects by `(tenant_id, external_realm, external_id)`; if that also returns `nil`,
  returns `{:error, :external_identity_collision}`. This is a plain `case` match with an
  explicit `nil ->` branch returning a tagged error tuple, not a fallthrough or a raise —
  satisfies INV-8 (no unhandled crash) by inspection. The branch is structurally
  unreachable under any interleaving this test suite can construct (it requires the
  freshly-inserted-by-us row to vanish between our own insert attempt and our own
  re-select, i.e. a concurrent delete of a row whose id only this process has ever held),
  consistent with design §9's own framing of it as a defensive-only branch.

**Implementation note surfaced during test-writing (not a defect, recorded for
traceability):** the design doc (§3.3) anticipated `Repo.insert/2` with
`on_conflict: :nothing` + `returning: true` signaling a suppressed insert via `id: nil`
on the returned struct. The actual implementation (`lib/letflow/identity.ex`'s
`insert_or_fetch/3`, comment at lines ~100-114) found empirically that this schema's
client-generated `binary_id` primary key means Ecto pads the returned struct from
changeset-local data even when the `RETURNING` clause yields zero rows, so `id` is never
`nil` in either case — the implementation instead does a `Repo.get(User, id)` existence
check to distinguish a genuine insert from a suppressed one. Test case 5 (the real
concurrent race) is written against the actual implementation's observable behavior
(`{:ok, _}` from both tasks, exactly one `created: true`, one row in the DB) rather than
against the design doc's anticipated internal signal, so this divergence does not weaken
the test — it is exactly the kind of behavior a real race is needed to pin down, per
design §9's own caution that "a test could pass 'by accident'" without one.

## Fixture isolation

Every test constructs its own `tenant_id` (`Ecto.UUID.generate()`), `realm`
(interpolated with a unique suffix, e.g. `"realm-#{System.unique_integer([:positive])}"`),
and `external_user_id` (`Ecto.UUID.generate()` or a unique-integer-suffixed string) —
no shared hardcoded identity across tests, matching this project's established
`Ecto.UUID.generate()`-per-test convention (`process_instance_test.exs`,
`row_approval_test.exs`) and `test_developer_guide.md`'s "no test pollution" principle.
The two-tenant collision test (case 9) explicitly creates two distinct tenant UUIDs
scoped to that one test, not shared with any other test.
