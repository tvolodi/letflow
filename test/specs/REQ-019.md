# Test Spec: REQ-019 — Tenant<->realm binding (OIDC-12/ADP-04b equivalent)

**Requirement:** REQ-019 (`docs/requirements.yaml`, stage S1) — port
`src/oidc/realm_tenant_binding.zig`'s `resolveTenantByRealm`/`resolveRealmByTenant` as
`Letflow.Identity` functions operating on REQ-015's `tenants` schema, enforce the
one-to-one tenant<->realm invariant (each tenant has at most one `idp_realm_id`, each
`idp_realm_id` maps to at most one tenant, `idp_realm_id` immutable after creation,
default tenant pinned to `idp_realm_id = "bpm-default"`), and port adp-04a's
realm-ownership guard as a function REQ-021's future pipeline will call before REQ-018's
JIT provisioning.

**Requirement's acceptance criteria (verbatim):**
1. "resolveTenantByRealm(idp_realm_id) and resolveRealmByTenant(tenant_id) both work
   against REQ-015's tenants table, tested with the seeded default tenant (bpm-default)"
2. "attempting to bind a second tenant to an already-bound idp_realm_id is rejected
   (unique index or explicit changeset validation), not silently overwritten"
3. "attempting to change an existing tenant's idp_realm_id via the normal update
   changeset is rejected or the changeset simply omits idp_realm_id from its allowed
   fields — whichever approach is taken, it's stated explicitly in the moduledoc"
4. "a realm-ownership guard function exists that rejects a (tenant_id, external_realm)
   pair where external_realm is not the realm bound to tenant_id"

**Test tier:** unit + integration. `Letflow.Identity.resolve_tenant_by_realm/1`,
`resolve_realm_by_tenant/1`, `verify_realm_ownership/2`, and
`Letflow.Identity.Tenant.create_changeset/3`/`update_changeset/2` all touch
`Letflow.Repo` (real Postgres via `Letflow.DataCase`'s sandboxed connection) or produce
`Ecto.Changeset` structs meant to be persisted — not pure functions the way
REQ-017's `ClaimMapping` is.

## Scope test

Real application-executable Elixir logic: `lib/letflow/identity.ex` (three new
`Repo`-touching functions) and `lib/letflow/identity/tenant.ex` (two new changeset
functions plus two private validation helpers). Not docs-only, not build-config. Full
TEST-DESIGN-VALIDATOR / TEST-RUNNER chain applies.

## Files

- `test/letflow/identity_test.exs` — extended (same file as REQ-018's tests, same
  `Letflow.Identity` context module, matching this project's one-test-file-per-context
  convention). New `describe` blocks added; REQ-018's existing tests are untouched.

## What "seeded default tenant (bpm-default)" means here

Per the design doc (`lib/letflow/design/req019-tenant-realm-binding.md` §4, §11): no
`priv/repo/seeds.exs` exists and this requirement does not add one. Confirmed by direct
search (repeated here, not just trusted from the design doc): no `.ex`/`.exs` file in
this repo inserts a `tenants` row anywhere. "Seeded" therefore means a
TEST-DESIGNER-constructed fixture, built per-test via `Tenant.create_changeset/3` +
`Repo.insert/1` with `slug: "bpm-default"`, `idp_realm_id: "bpm-default"`, inside each
test's own sandboxed transaction (`Ecto.Adapters.SQL.Sandbox` rolls back per test per
`test/support/data_case.ex`, confirmed by reading that file — so a hardcoded
`"bpm-default"` slug/realm string used identically across many tests does not collide,
since no test's insert is ever visible to another test's transaction). This is
distinguished from the *collision-rejection* tests (AC2), which deliberately use unique,
per-test-generated realm/slug strings (never the literal `"bpm-default"`) so that two
tenants *within the same test* can be asserted to collide with each other, without also
depending on/colliding with any other test's use of the same fixture pattern.

## Test cases

### Acceptance criterion 1 — `resolve_tenant_by_realm/1` / `resolve_realm_by_tenant/1`

1. **Both functions resolve the seeded default-tenant fixture correctly, in both
   directions** — see `identity_test.exs:"resolve_tenant_by_realm/1 resolves the
   seeded default tenant (bpm-default) by its idp_realm_id"` and
   `identity_test.exs:"resolve_realm_by_tenant/1 resolves the seeded default tenant's
   (bpm-default) idp_realm_id by its tenant id"`. Builds the fixture described above
   inside the test, then calls `resolve_tenant_by_realm("bpm-default")` and asserts the
   returned tenant's `id` matches the fixture's `id`; separately calls
   `resolve_realm_by_tenant(tenant.id)` and asserts `{:ok, "bpm-default"}`. Directly
   satisfies AC1's explicit "tested with the seeded default tenant (bpm-default)"
   wording — this is not incidental coverage, it is the literal criterion. Would fail if
   either function queried the wrong column, returned the wrong tenant, or silently
   swallowed a real match into `{:error, :not_found}`.
2. **`resolve_tenant_by_realm/1` not-found path** — see `identity_test.exs:"
   resolve_tenant_by_realm/1 returns {:error, :not_found} for an unknown realm
   string"`. Calls the function with a realm string guaranteed not to exist (a
   uniquely-suffixed literal, not `"bpm-default"`), asserts `{:error, :not_found}`.
   Would fail if the function raised instead of returning a typed error, or returned
   `{:ok, nil}`/some other non-error shape for a genuine miss.
3. **`resolve_realm_by_tenant/1` not-found path** — see `identity_test.exs:"
   resolve_realm_by_tenant/1 returns {:error, :not_found} for an unknown tenant_id"`.
   Calls the function with `Ecto.UUID.generate()` (a well-formed UUID matching no row),
   asserts `{:error, :not_found}`. Would fail if the function raised
   (`Ecto.Query.CastError` or similar) or returned an incorrect success shape.
4. **`resolve_realm_by_tenant/1`'s `{:ok, nil}` divergence for a tenant with no bound
   realm** — see `identity_test.exs:"resolve_realm_by_tenant/1 returns {:ok, nil} for a
   tenant that exists but has no bound realm"`. Design doc §5.2 names this as a
   deliberate divergence from the literal ported Zig behavior (which would treat a null
   `idp_realm_id` as a persistence failure) — worth pinning explicitly per this
   project's practice of testing documented divergences from the ported source, not just
   the literal acceptance-criterion text. Creates a non-default tenant with
   `idp_realm_id: nil` (`oidc_mode: :disabled` so the conditional-required rule doesn't
   block creation), asserts `{:ok, nil}`, not `{:error, :not_found}` and not a crash on
   the `nil` field. Would fail if the function conflated "no realm bound" with "no
   tenant found," or raised on the nil field.

### Acceptance criterion 2 — one-to-one collision rejection

5. **A second tenant cannot bind to an already-bound `idp_realm_id`** — see
   `identity_test.exs:"creating a second tenant with an already-bound idp_realm_id is
   rejected, not silently overwritten"`. Creates tenant A with a unique
   `idp_realm_id: "realm-<n>"`, persists successfully. Attempts to create tenant B with
   the identical `idp_realm_id`, asserts `{:error, %Ecto.Changeset{}}` with an error
   specifically on `:idp_realm_id` (via `errors_on/1`, matching REQ-018's existing
   helper), and separately asserts only one row exists in `tenants` for that
   `idp_realm_id` afterward (re-queried from Postgres, not trusted from the in-memory
   changeset). This is the direct acceptance demonstration for AC2 — would fail if the
   collision instead raised an unhandled `Ecto.ConstraintError` (meaning
   `unique_constraint(:idp_realm_id, ...)` was missing or misnamed against the
   migration's actual partial-index name), or if tenant B were silently persisted
   (overwriting/duplicating the binding).
6. **The collision is a typed changeset error, not a raised exception** — folded into
   test case 5 above via `assert {:error, %Ecto.Changeset{}} = ...` rather than a
   `try/rescue`: if `unique_constraint/2` were absent, `Repo.insert/1` would raise
   `Ecto.ConstraintError` and this assertion's pattern match itself would fail with an
   unhandled exception, which ExUnit reports as a test failure either way — so this
   single assertion already discriminates "typed error" from "raised exception" without
   needing a separate case.
7. **Two tenants with genuinely distinct `idp_realm_id` values both persist
   successfully** — see `identity_test.exs:"two tenants with distinct idp_realm_id
   values both persist successfully"`. The converse of case 5: proves the unique index
   is scoped to the actual `idp_realm_id` value, not overly broad (e.g. rejecting any
   second tenant regardless of realm). Would fail if a change accidentally made the
   uniqueness check tenant-count-based rather than value-based.

### Acceptance criterion 3 — `idp_realm_id` immutability via `update_changeset/2`

8. **`update_changeset/2` never casts `idp_realm_id`, even when explicitly present in
   the attrs map** — see `identity_test.exs:"update_changeset/2 does not cast
   idp_realm_id even when present in attrs"`. Builds and persists a tenant with a known
   `idp_realm_id`, then calls `Tenant.update_changeset(tenant, %{idp_realm_id:
   "attempted-new-realm", display_name: "New Name"})`. Asserts
   `Ecto.Changeset.get_change(changeset, :idp_realm_id) == nil` (the field was never
   cast at all — the correct observable outcome per design doc §11, distinct from "a
   validation error is present on the field," which would be the wrong assertion for a
   field that's structurally absent from `cast/3`'s field list). Also asserts
   `changeset.valid?` (an unrelated, permitted field change alongside the ignored one
   doesn't make the changeset invalid) and that `display_name`'s change IS present
   (proving the changeset itself works, not just that it happens to reject
   everything). Would fail if a future edit added `:idp_realm_id` back to
   `update_changeset/2`'s `cast/3` list.
9. **Persisting that changeset via `Repo.update/1` leaves `idp_realm_id` unchanged in
   the database** — see `identity_test.exs:"persisting update_changeset/2 with an
   attempted idp_realm_id change leaves the original idp_realm_id unchanged in the
   database"`. Continues case 8: calls `Repo.update/1` on the changeset, then
   re-selects the row from Postgres via `Repo.get/2` (not trusting the in-memory struct
   the update returned) and asserts `idp_realm_id` still equals the original value, not
   `"attempted-new-realm"`. This is the acceptance-criterion-defining assertion — a test
   that only checked the in-memory changeset (case 8) without this re-select could pass
   even if some other code path re-introduced the field later; re-selecting from
   Postgres is what actually proves immutability end-to-end, matching this project's
   established persistence-test convention
   (`process_instance_test.exs`/`identity_test.exs`'s existing `Repo.get/2` re-select
   pattern). Would fail if `idp_realm_id` were somehow changed at the DB level despite
   case 8's changeset-level check passing.

### Acceptance criterion 4 — realm-ownership guard, every branch

10. **Match: `verify_realm_ownership/2` returns `:ok` when `external_realm` is exactly
    the tenant's bound realm** — see `identity_test.exs:"verify_realm_ownership/2
    returns :ok when external_realm matches the tenant's bound idp_realm_id"`. Would
    fail if the function never returned `:ok` at all (e.g. an inverted comparison) or if
    it required exact-tenant-and-realm equality in a way subtly different from a plain
    string match (e.g. case-insensitive when it shouldn't be).
11. **Mismatch: a bound-but-different realm is rejected** — see
    `identity_test.exs:"verify_realm_ownership/2 returns {:error,
    :realm_tenant_mismatch} when external_realm does not match the tenant's bound
    realm"`. Tenant is bound to realm X; guard called with realm Y (X != Y). Asserts
    `{:error, :realm_tenant_mismatch}`. This is the direct SECURITY-REVIEWER-flagged
    fail-open trace turned into a real test — SECURITY-REVIEWER's step02c handoff traced
    this branch by hand and found no fail-open path; this test is what makes that a
    standing, re-runnable check rather than a one-time manual read. Would fail if the
    function ever returned `:ok` for a non-matching realm (the exact fail-open shape a
    security guard must never exhibit).
12. **Tenant not found** — see `identity_test.exs:"verify_realm_ownership/2 returns
    {:error, :not_found} for a tenant_id that matches no row"`. Calls the guard with
    `Ecto.UUID.generate()` (matches no row) and any realm string. Asserts
    `{:error, :not_found}` — distinct from `{:error, :realm_tenant_mismatch}` per design
    §6.1 case 1. Would fail if the function crashed on a missing tenant (e.g. an
    unguarded struct-field access) or conflated "no such tenant" with "realm mismatch."
13. **Tenant with `idp_realm_id: nil` — the SECURITY-REVIEWER-flagged edge case** — see
    `identity_test.exs:"verify_realm_ownership/2 returns {:error,
    :realm_tenant_mismatch}, not :ok and not a crash, for a tenant with no bound
    realm"`. Creates a non-default tenant with `idp_realm_id: nil` (`oidc_mode:
    :disabled` at creation), calls
    `verify_realm_ownership(tenant.id, "some-external-realm")`. Asserts
    `{:error, :realm_tenant_mismatch}` — explicitly NOT `:ok` (a `nil ==
    "some-external-realm"` comparison must not somehow both-be-falsy their way to a
    pass) and NOT `{:error, :not_found}` (the tenant genuinely exists). This is the
    second half of the fail-open trace SECURITY-REVIEWER did by hand
    (`step02c-security-review.json`'s `scrutiny_point_answers`, "Does
    verify_realm_ownership/2 have any path where a mismatched or nil realm could be
    treated as a pass (fail-open)?") — without this test, a future refactor of the
    `case` clause matching `{:ok, _mismatched_or_nil}` could accidentally split that
    clause and mishandle the nil sub-case with no test catching it. Would fail if the
    nil-realm case were ever treated as a pass, or if it raised instead of returning a
    typed error.

### Default-tenant pinning validation (design §3.2/§4, not separately numbered in
REQ-019's AC list but explicitly named in the requirement description's "default tenant
is pinned to idp_realm_id = 'bpm-default'" clause, and in the design's own §11 testing
guidance)

14. **`create_changeset/3` with `slug: "bpm-default"` and a non-`"bpm-default"`
    `idp_realm_id` is invalid** — see `identity_test.exs:"create_changeset/3 rejects
    slug bpm-default paired with a different idp_realm_id"`. Asserts
    `changeset.valid? == false` and an error is present on `:idp_realm_id`. Would fail
    if the default-tenant pinning check were absent or only checked presence, not the
    specific required value.
15. **`create_changeset/3` with `slug: "bpm-default"` and `idp_realm_id:
    "bpm-default"` is valid** — see `identity_test.exs:"create_changeset/3 accepts slug
    bpm-default paired with idp_realm_id bpm-default"`. The positive counterpart to case
    14 — proves the pinning rule doesn't reject the one value it's supposed to require.
    Would fail if the validation were inverted (rejecting the correct value) or if some
    unrelated required-field check blocked an otherwise-correct default-tenant creation.
16. **`create_changeset/3` with `slug: "bpm-default"` and `idp_realm_id` entirely
    omitted is invalid** — see `identity_test.exs:"create_changeset/3 rejects slug
    bpm-default with idp_realm_id omitted entirely"`. Distinguishes "wrong value present"
    (case 14) from "no value present at all" — SECURITY-REVIEWER's step02c handoff
    specifically confirmed the `validate_change/3` + `validate_required/2` combination
    catches both the wrong-value and the omitted-value sub-cases; this test pins the
    omitted-value sub-case as a standing regression check rather than leaving it
    verified only by a one-time manual security read. Would fail if
    `validate_required/2` were dropped from `validate_default_tenant_pinning/1`'s
    default-tenant branch (since `validate_change/3` alone does not fire for an absent
    field).

### `oidc_mode`-conditional `idp_realm_id`-required rule (design §3.2, empirically
demonstrated by ELIXIR-DEV in Step 2a per the task's own instruction to turn that into a
committed test)

17. **`oidc_mode: :enabled`, non-default tenant, `idp_realm_id` omitted -> invalid** —
    see `identity_test.exs:"create_changeset/3 requires idp_realm_id for a non-default
    tenant when oidc_mode is :enabled"`. Would fail if the conditional-required rule
    were dropped or the condition were inverted.
18. **`oidc_mode: :disabled`, non-default tenant, `idp_realm_id` omitted -> valid** —
    see `identity_test.exs:"create_changeset/3 allows a non-default tenant with no
    idp_realm_id when oidc_mode is :disabled"`. The converse of case 17 — proves the
    requirement is genuinely conditional on `oidc_mode`, not an unconditional
    `validate_required(:idp_realm_id)` that would incorrectly block OIDC-disabled tenant
    creation (design §3.2's explicit "does NOT unconditionally require idp_realm_id"
    framing). Would fail if `idp_realm_id` were required regardless of `oidc_mode`.
19. **`oidc_mode: :enabled`, non-default tenant, `idp_realm_id` present -> valid** — see
    `identity_test.exs:"create_changeset/3 accepts a non-default tenant with
    idp_realm_id present when oidc_mode is :enabled"`. Confirms the required-ness rule
    doesn't have an unrelated side effect that blocks an otherwise-correct, fully-populated
    non-default tenant.

## Fixture isolation

Every test that is not specifically about the default-tenant fixture (cases 1, 4-ish
context, 14-19 all use `"bpm-default"` deliberately as the value under test) uses a
unique, per-test `idp_realm_id`/`slug` generated via
`System.unique_integer([:positive, :monotonic])`, matching `identity_test.exs`'s
existing `unique_realm/1` helper convention (extended here with a `unique_slug/1`
sibling). The collision tests (cases 5-7) explicitly construct two distinct tenants
scoped to that one test only. Every test runs inside `Letflow.DataCase`'s per-test
sandboxed transaction (rolled back after the test), so the repeated literal
`"bpm-default"` across cases 1 and 14-19 does not collide across tests, matching
REQ-018's own established sandbox-isolation reasoning restated in "What 'seeded default
tenant' means" above.
