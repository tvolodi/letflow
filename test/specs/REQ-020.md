# Test Spec: REQ-020 — Per-tenant role registry (TenantRoleStore/IDN-05 equivalent)

**Requirement:** REQ-020 (`docs/requirements.yaml`, stage S1) — port
`src/identity/role_registry.zig`'s `TenantRoleStore` (`list_roles`, `upsert_role`) and
`resolveRoleInTx` as `Letflow.Identity.RoleRegistry` functions operating on REQ-015's
`tenant_role`/`groups` schema.

**Requirement's acceptance criteria (verbatim):**
1. "list_roles/1 returns [] (not an error) against an empty tenant_role table, and
   returns all rows sorted by name when populated"
2. "upsert_role/2 with a non-existent group_id returns an error tuple rather than
   inserting a dangling reference"
3. "upsert_role/2 called twice with the same name and a different group_id updates the
   existing binding rather than creating a duplicate row"
4. "resolve_role_in_tx/2 (or equivalent inside-an-existing-transaction call) returns nil
   on any lookup failure (unknown name, table/connection issue) rather than raising"
5. "@moduledoc cites src/identity/role_registry.zig and states explicitly that this
   module has no coupling to the OIDC token-verification pipeline"

**Test tier:** unit + integration. `Letflow.Identity.RoleRegistry.list_roles/0`,
`upsert_role/2`, and `resolve_role_in_tx/1` all touch `Letflow.Repo` (real Postgres via
`Letflow.DataCase`'s sandboxed connection) — not pure functions.

## Scope test

Real application-executable Elixir logic: `lib/letflow/identity/role_registry.ex` (a new
context module: `list_roles/0`, `upsert_role/2`, `resolve_role_in_tx/1`, plus private
name-validation logic) and `lib/letflow/identity/tenant_role.ex` (a new `changeset/2`
function). Not docs-only, not build-config. Full TEST-DESIGN-VALIDATOR / TEST-RUNNER
chain applies.

## Files

- `test/letflow/role_registry_test.exs` — **new file**, not an extension of
  `test/letflow/identity_test.exs`. See "Module/file placement" below for why.

## Module/file placement — why a separate test file

Checked how `test/letflow/` is currently organized before deciding
(`test/letflow/row_approval_test.exs`, `parallel_approval_test.exs`,
`process_instance_test.exs`, `application_test.exs`, `identity_test.exs`): one test file
per production module/context, named after it (`identity_test.exs` <->
`lib/letflow/identity.ex`, not `lib/letflow/identity/tenant.ex` or `user.ex` even though
those are also touched — the file mirrors the top-level *context* module, not every
schema file it uses).

`Letflow.Identity.RoleRegistry` is a deliberately separate top-level context module from
`Letflow.Identity` — not a set of functions added to it. This is not a file-organization
convenience; it is the design's own explicit decision
(`lib/letflow/design/req020-role-registry.md` §1, reasons 1-4): REQ-020's own
description names the module explicitly, R-Co's own source keeps `role_registry.zig`
separate from `registry.zig`, and — most load-bearing for testing — the coupling
boundary (AC5) is *structural* specifically because `RoleRegistry` has no `alias
Letflow.Oidc.*` and never appears in the same module as `Letflow.Identity`'s
OIDC-pipeline functions (`provision_oidc_user/3`, `resolve_tenant_by_realm/1`, etc.).

Putting `RoleRegistry`'s tests inside `identity_test.exs` would blur exactly the
boundary the design goes out of its way to keep structural: that test file already
`alias`es `Letflow.Oidc.IdentityContext`/`JitProvisioningConfig` for REQ-018's tests,
and mixing `RoleRegistry` tests into the same file would put role-registry test code in
a file that imports OIDC-pipeline types for unrelated tests — the test-file mirror of
the exact coupling risk the design's §1 reason 3 identifies for the *production* code.
A separate `test/letflow/role_registry_test.exs` (mirroring `role_registry.ex`'s own
module boundary, matching this project's established one-file-per-context-module
pattern) is therefore the better match, and this file never aliases `Letflow.Identity`
or any `Letflow.Oidc.*` module — confirmed directly by inspection of the file's alias
list.

## Test cases

### Acceptance criterion 1 — `list_roles/0`

1. **Empty table returns `[]`, not an error** — see
   `role_registry_test.exs:"returns [] (not an error) against an empty tenant_role
   table"`. Calls `list_roles/0` against a fresh sandboxed transaction with no rows
   inserted. Would fail if the function raised on an empty result set or returned
   something other than a bare `[]` (e.g. wrapped in `{:ok, []}`).
2. **Populated table returns all rows sorted by `name` ascending, insertion order
   deliberately scrambled** — see `role_registry_test.exs:"returns all rows sorted by
   name ascending, proving the ORDER BY is real"`. Inserts three roles via
   `upsert_role/2` in the order zeta -> alpha -> mid (deliberately NOT alphabetical, and
   NOT reverse-alphabetical either, so neither "insertion order" nor "reverse insertion
   order" could accidentally satisfy the assertion). Asserts the returned list, filtered
   to just these three names, comes back as `[alpha, mid, zeta]`. This is the specific
   design point called out in the task: with insertion order zeta/alpha/mid, a query
   that silently relied on primary-key/insertion order instead of a genuine `ORDER BY
   name` would return `[zeta, alpha, mid]` — visibly different from the expected
   `[alpha, mid, zeta]` — so this test is not vacuously satisfied by an accidentally-
   correct insertion order. **Empirically verified**: ran this test against the real
   implementation; the actual SQL logged was `SELECT ... FROM "tenant_role" AS t0 ORDER
   BY t0."name"`, and the assertion passed with the scrambled insertion order, confirming
   the `ORDER BY` clause is real and doing the sorting (not insertion order coincidentally
   matching).

### Acceptance criterion 2 — `upsert_role/2`, non-existent `group_id`

3. **A syntactically-valid but nonexistent `group_id` returns `{:error,
   :group_not_found}` and inserts no row** — see `role_registry_test.exs:"a
   syntactically-valid but nonexistent group_id returns {:error, :group_not_found} and
   inserts no row"`. Calls `upsert_role(name, Ecto.UUID.generate())` where the generated
   UUID matches no `groups` row. Asserts the return value AND separately re-queries
   `tenant_role` by `name` to assert zero rows exist afterward — not just the return
   tuple, per the task's explicit instruction to check the row count/absence, not only
   the return value. Would fail if the function inserted a dangling row before/despite
   the existence check (e.g. if the pre-check were accidentally skipped or raced past),
   or if it returned a different error atom / raised the DB-level foreign-key violation
   as an unhandled `Ecto.ConstraintError` instead of the typed `:group_not_found`.

### Acceptance criterion 3 — `upsert_role/2`, update not duplicate

4. **Called twice with the same name and a different, valid `group_id` updates the
   binding — both the returned `group_id` and the row count are checked** — see
   `role_registry_test.exs:"called twice with the same name and a different group_id
   updates the binding, no duplicate row"`. Creates two real `Group` rows (group_a,
   group_b). Calls `upsert_role(name, group_a.id)`, asserts the returned row's
   `group_id == group_a.id`. Calls `upsert_role(name, group_b.id)` with the SAME name,
   asserts the returned row's `group_id == group_b.id` (proving the second call's value
   is reflected, not silently ignored). Then re-queries `tenant_role` by `name` directly
   from Postgres (not trusting the in-memory reply) and asserts exactly one row exists,
   and that row's `group_id` is `group_b.id`. Would fail if `upsert_role/2` created a
   second row instead of updating (duplicate-row bug — the `unique_index(:tenant_role,
   [:name])` + `on_conflict:` mechanism not actually wired correctly), or if the
   `on_conflict: [set: [group_id: group_id]]` clause were missing/wrong and the existing
   row's `group_id` were left unchanged after the second call (stale-value bug).

### Acceptance criterion 4 — `resolve_role_in_tx/1`, "never raises"

5. **Bound name resolves to the correct `group_id`** — see
   `role_registry_test.exs:"returns the bound group_id for a name that exists"`. Would
   fail if the lookup returned the wrong field, `nil` for a genuinely-bound name, or
   raised.
6. **Unbound/unknown name resolves to `nil`** — see
   `role_registry_test.exs:"returns nil for an unbound/unknown name"`. Calls with a
   name guaranteed not to exist. Would fail if the function raised on a miss (it
   shouldn't — `Repo.get_by/2` itself returns `nil` for no match, no `rescue` needed for
   this specific path) or returned something other than `nil` (e.g. `{:error,
   :not_found}`, which would break the "never returns an error tuple" contract).
7. **Called from inside an existing `Repo.transaction/1` callback (the function's
   documented usage per the design's §5 "ambient transaction" decision) still resolves
   correctly** — see `role_registry_test.exs:"called from inside an existing
   Repo.transaction/1 callback (its documented usage), still resolves correctly"`.
   Wraps the call in `Repo.transaction(fn -> RoleRegistry.resolve_role_in_tx(name) end)`
   and asserts the transaction succeeds with the correct `group_id`. This is the direct
   test of the design's most novel decision (§5, §11 OQ-2): `resolve_role_in_tx/1` takes
   no connection/transaction argument because Ecto's transaction context is ambient to
   the calling process — this test proves that claim is actually true in this codebase,
   not just asserted in the design doc. Would fail if the ambient-transaction assumption
   were wrong (e.g. if Ecto's sandbox/connection model here required an explicit
   connection argument to participate in the same transaction).
8. **The "never raises" contract's rescue path, genuinely exercised** — see
   `role_registry_test.exs:"a query-level error that would otherwise raise resolves to
   nil, not an unhandled exception"`. This is the test case the task explicitly asked to
   reason through rather than skip; see "AC4 rescue-path testability" below for the full
   reasoning and empirical verification (a mutation test: removing the `rescue` clause
   makes exactly this test fail with `Ecto.Query.CastError`, and no other test in the
   file changes status).

### Beyond the bare acceptance criteria — name validation, 3 rejection modes

9. **Empty name rejected** — see `role_registry_test.exs:"rejects an empty name"`.
   `upsert_role("", group.id)` asserts `{:error, :invalid_role_name}`. Would fail if the
   empty-string check were dropped from `validate_role_name/1`.
10. **Name longer than 128 codepoints rejected** — see `role_registry_test.exs:"rejects
    a name longer than 128 codepoints"`. Uses `String.duplicate("a", 129)`. Asserts
    `{:error, :invalid_role_name}`. Paired with test 11 below (the boundary itself,
    128, is accepted) so the off-by-one direction of the `<=` vs. `<` comparison is
    pinned, not just "some long string is rejected somewhere."
11. **Name of exactly 128 codepoints accepted (boundary case)** — see
    `role_registry_test.exs:"accepts a name of exactly 128 codepoints (the boundary
    itself is valid)"`. Uses `String.duplicate("a", 128)`, a real `Group` fixture,
    asserts `{:ok, %TenantRole{name: ^exactly_128}}`. Would fail if the length check
    used `< 128` instead of `<= 128` (i.e. `String.length(name) > @max_name_codepoints`
    with `@max_name_codepoints = 128`, which is what the implementation actually uses —
    this test would catch an accidental off-by-one in either direction).
12. **Name containing a control character rejected** — see
    `role_registry_test.exs:"rejects a name containing a control character"`. Uses a
    name embedding `<<0x01>>` (a real ASCII control character, `0x01`, inside the
    control-character range `0x00-0x1F`/`0x7F` the design's §4.1 specifies). Asserts
    `{:error, :invalid_role_name}`. Would fail if the control-character regex
    (`~r/[\x00-\x1F\x7F]/u`) were absent or mistyped to not cover this codepoint.

### Beyond the bare acceptance criteria — `group_id` invalid-UUID-format rejection

13. **A `group_id` that is not a syntactically valid UUID string is rejected distinctly
    from the not-found case, with no row inserted** — see
    `role_registry_test.exs:"rejects a group_id that is not a syntactically valid UUID,
    distinct from the not-found case"`. Calls `upsert_role(name, "not-a-uuid")`.
    Asserts `{:error, :invalid_group_id}` — a different atom from test case 3's
    `{:error, :group_not_found}` — and separately re-queries `tenant_role` to confirm no
    row was inserted. This is deliberately a separate test case from AC2's
    not-found test (case 3) per the task's explicit instruction, since the two error
    atoms represent genuinely different failure modes (malformed input vs. well-formed
    but absent) and the design (§4.2) treats them as a distinct pre-DB-round-trip gate.
    Would fail if malformed input were misclassified as `:group_not_found` (i.e. if the
    `Ecto.UUID.cast/1` pre-validation step were skipped and the malformed string reached
    `Repo.get(Group, group_id)` directly — which would actually raise
    `Ecto.Query.CastError` rather than cleanly returning either error atom, since
    `Repo.get/2` is not itself exception-tolerant for a non-UUID-shaped `binary_id`
    argument the way `Ecto.UUID.cast/1` is; this test would surface that as an unhandled
    exception rather than a clean assertion failure, which is still a failing test
    either way).

## AC4 rescue-path testability — reasoning and empirical verification

The task instructions ask this design to address AC4's "never raises" clause with more
than the two obvious cases (bound name, unbound name) — specifically to either exercise
the `rescue` path genuinely, or state explicitly what was tried and why full coverage
isn't practical.

**What was tried and used:** rather than mocking or breaking the DB connection (judged
impractical at this level — `Letflow.DataCase`'s sandbox doesn't expose an easy hook to
simulate "connection drops mid-query" without either a mock (forbidden by DIRECTIVE T-1)
or reaching into Postgrex/DBConnection internals, which would be fragile and unrelated
to what this function's contract actually needs to prove), this spec instead found a
**real, non-mocked way to trigger an exception from inside `resolve_role_in_tx/1`'s own
query**: passing a value of the wrong Elixir type for the `name` parameter (a tuple,
`{:not, :a, :string}`, where the schema's `name` field is `:string`) causes
`Ecto.Query.CastError` to be raised by Ecto's own query-building/execution machinery
when it tries to cast that value for the `where: t0.name == ^name` clause — a genuine
error path, not a simulated one, and one that plausibly represents the broader class of
"malformed input reaches the query and something goes wrong before/during execution"
that the `rescue` clause exists to guard against (the design's own §4.3 names
`Ecto.QueryError`/`DBConnection.ConnectionError`/"the catch-all `rescue _ -> nil`" as
the target class — this test exercises that catch-all against a real member of the
"something raised during the query" family, even though it isn't specifically a
connection-level failure).

**This does not cover the specific "table/connection issue" sub-case literally** (a
dropped connection, pool exhaustion) — that sub-case remains untested at this level for
the reasons above (no mocking, and simulating a real connection failure against a live
sandboxed Postgres connection mid-test is not practical without infrastructure this
project doesn't have). This is stated explicitly rather than silently claimed as full
coverage.

**Empirical verification that this test is load-bearing (not vacuous):** temporarily
removed the `rescue _ -> nil` clause from `lib/letflow/identity/role_registry.ex`'s
`resolve_role_in_tx/1` and re-ran `mix test test/letflow/role_registry_test.exs`.
Result: **12/13 passed**, with exactly one failure — `resolve_role_in_tx/1 (acceptance
criterion 4) a query-level error that would otherwise raise resolves to nil, not an
unhandled exception` — failing with the actual raised exception:

```
** (Ecto.Query.CastError) deps/ecto/lib/ecto/repo/queryable.ex:504: value `{:not, :a, :string}`
in `where` cannot be cast to type :string in query: ...
    (letflow 0.1.0) lib/letflow/identity/role_registry.ex:74: Letflow.Identity.RoleRegistry.resolve_role_in_tx/1
```

No other test in the file changed status. The `rescue` clause was then restored
(confirmed via `git diff --stat` showing no diff against the committed version) and the
full suite re-run, confirming **13/13 passed** again. This confirms test case 8 would
genuinely fail if the implementation lost its "never raise" behavior — it is not a
vacuous assertion.

## AC5 — `@moduledoc` content requirement, no runtime test

REQ-020's fifth acceptance criterion ("`@moduledoc` cites `src/identity/role_registry.zig`
and states explicitly that this module has no coupling to the OIDC token-verification
pipeline") is a **documentation-content requirement**, not application behavior in the
ExUnit sense — there is no runtime code path whose correctness this could assert against
beyond `grep`-ing the module's own docstring for expected substrings, which the task's
own framing (and this project's established anti-pattern guidance on manufactured
busywork gates) correctly flags as not real coverage: a test asserting
`String.contains?(@moduledoc, "role_registry.zig")` would pass or fail based solely on
whether the string literal is present, proving nothing about behavior and trivially kept
"green" by copy-pasting the required substrings without them being true. AC5 is
therefore judged **more appropriately verified by direct inspection** — which this spec
does here, and which RELEASE-VALIDATOR should re-confirm independently rather than trust
this spec's claim:

Inspected `lib/letflow/identity/role_registry.ex` lines 1-17 directly. Confirmed:
- Line 3 cites `src/identity/role_registry.zig` by name (`role_registry.zig`'s
  `TenantRoleStore`, `resolveRoleInTx`), plus `src/design/idn05-role-registry.md`.
- Lines 10-16 state, in prose sentences (not merely by omission of an `alias` line):
  "This module has **no coupling to the OIDC/claim-mapping pipeline**: it does not
  `alias` or call any `Letflow.Oidc.*` module, and it does not call or get called by
  `Letflow.Identity`'s OIDC-pipeline functions... It is a standalone,
  workflow-engine-facing role registry... not part of token verification or identity
  resolution."

Both required moduledoc elements are present as of this inspection. This is a one-time
inspection result, not a standing regression check — a future edit could silently remove
this prose without any test catching it, which is the accepted, explicitly-stated
tradeoff for a documentation-content criterion per this project's own guidance against
inventing busywork tests.

## Fixture isolation

Every test builds its own unique `name` (via `unique_name/1`, using
`System.unique_integer([:positive, :monotonic])`, matching `identity_test.exs`'s
established convention) and its own real `Group` row(s) (via `insert_group!/0`) inside
its own sandboxed transaction. `tenant_role.name` carries a table-wide unique index
(REQ-015's migration, confirmed in the design doc §8) — since all tests in this file run
`async: true`, using a shared/hardcoded name across tests could genuinely collide even
under the sandbox (unlike `identity_test.exs`'s deliberate, scoped reuse of the literal
`"bpm-default"` string, which is safe there specifically because sandboxed transactions
never see each other's rows — the same protection applies here, but this file avoids any
shared literal name regardless, since there is no analogous "seeded default" concept for
role names to justify reusing one). No test depends on another test's data or on
execution order.
