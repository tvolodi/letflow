# Test Spec: REQ-021 — Auth Plug pipeline (auth.zig/tenant_status.zig equivalent)

**Requirement:** REQ-021 (`docs/requirements.yaml`, stage S1) — wire REQ-016's OIDC
verification, REQ-017's claim mapping, REQ-019's tenant<->realm resolution + ownership
guard, and REQ-018's JIT provisioning into one request-scoped Plug pipeline
(`Letflow.Plugs.AuthPipeline`), plus a separate write-pause Plug
(`Letflow.Plugs.TenantStatus`) porting `tenant_status.zig`.

**Requirement's acceptance criteria (verbatim):**
1. "a request with a valid OIDC bearer token (or a test double standing in for
   ueberauth_oidcc's verification result, if a real Keycloak issuer isn't reachable in
   this environment — state explicitly which was used) flows through verify -> tenant
   resolution -> realm-ownership guard -> JIT provisioning and ends with an auth context
   (user_id, tenant_id, roles) available to the next plug in the chain"
2. "a request with a missing or malformed bearer token is rejected with 401 before
   tenant resolution or JIT provisioning runs"
3. "a write request (POST/PUT/PATCH/DELETE) against a tenant whose status is migrating
   is rejected with 503 and a Retry-After header; a GET/HEAD request against the same
   tenant passes through"
4. "a request whose token's realm does not match the resolved tenant's bound realm is
   rejected, not silently JIT-provisioned under the wrong tenant"
5. "moduledoc explicitly states this plug supersedes REQ-103 (never built) as Letflow's
   first real auth plug, and names which router.ex routes (if any) it is mounted in
   front of"

**Test tier:** unit + integration. Both plug modules are exercised via `Plug.Test.conn/3`
+ direct `call/2` invocation against a real, sandboxed Postgres connection
(`Letflow.DataCase`) — no route is mounted behind them yet (per the design doc §8), so
there is no `Letflow.Router`-level HTTP test; the plugs are tested directly, matching
`docs/guides/test_developer_guide.md`'s "unit tests of a single... module" tier and the
design doc §8's own framing ("modules exist and are tested; NOT wired into router.ex's
live plug pipeline yet").

**State used:** which verification adapter — explicitly the **test double** path named
by AC1's own parenthetical, per `lib/letflow/design/req021-auth-plug-pipeline.md` §3.2:
`config/test.exs` already wires `config :letflow, :oidc, token_verifier:
Letflow.Oidc.TokenVerifierDouble` (ELIXIR-DEV's double, reused as-is for AC1/AC2's
simplest cases), plus a second, TEST-DESIGNER-authored double,
`Letflow.Oidc.ConfigurableTokenVerifierDouble` (`test/support/`), used **directly**
(passed explicitly to test helpers, never wired into `config :letflow, :oidc`) for the
harder-to-reach branches (arbitrary realms, a token with no `sub` claim) that
`TokenVerifierDouble`'s one fixed sentinel token can't produce. No real Keycloak call is
made anywhere in this suite — see "Why a second double" below.

## Scope test

Real application-executable Elixir logic: `lib/letflow/plugs/auth_pipeline.ex` and
`lib/letflow/plugs/tenant_status.ex` (two new `Plug` behaviour modules with real
verification/DB/business logic), plus `lib/letflow/oidc/token_verifier.ex` (a new
behaviour) and `lib/letflow/oidc/token_verifier/oidcc.ex` (a real adapter). Not
docs-only, not build-config. Full TEST-DESIGN-VALIDATOR / TEST-RUNNER chain applies.

## Why a second double (`ConfigurableTokenVerifierDouble`)

`Letflow.Oidc.TokenVerifierDouble` (ELIXIR-DEV's, already SECURITY-REVIEWER/REVIEWER-
approved as part of the implementation) recognizes exactly one fixed sentinel raw token
(`"valid-test-token"`), mapped to one fixed claims map: realm `bpm-default`, subject
`test-subject-001`. That is sufficient for:
- AC1's happy path (needs exactly one valid-token shape)
- AC2's missing/malformed-header path (never reaches the verifier at all)
- the generic "invalid token string" 401 case (any non-sentinel string already returns
  `{:error, :invalid_test_token}`)

It is **not** sufficient for:
- testing the unknown-realm 401 branch with a realm that provably matches no seeded
  tenant (need a token claiming an arbitrary, test-chosen realm string)
- testing the `sub_claim_missing` branch (`TokenVerifierDouble`'s one claims map always
  has a `sub`)
- testing the JIT-disabled 403 branch against a specific, test-controlled realm (need
  a realm whose `config :letflow, :oidc_jit_provisioning` entry can be distinguished by
  fixture without touching global test config, which no realm currently configured for
  `bpm-default` allows — see `JitProvisioningConfig.for_realm/1`'s fallback: an
  unconfigured realm's `default/1` is `enabled: true`, so a *disabled* realm needs its
  own distinct realm string that this suite controls without mutating
  `config/test.exs`)

Per the design doc §3.2's own explicit delegation ("module name and exact fixture-claims
shape left to TEST-DESIGNER... consistent with this project's convention of test doubles
living under `test/support/`"), this spec adds
`Letflow.Oidc.ConfigurableTokenVerifierDouble` — **stateless, derives every claim from
the raw token string itself** (no `Application.put_env/3`, no `Agent`/process-dictionary
state), so it is safe under `async: true` (concurrently-running tests using different
token strings never share or race over mutable state). See the module's own moduledoc
for its full recognized-token grammar. This module is never wired into
`config/test.exs`'s `:token_verifier` key — it is passed to `AuthPipeline`/`TenantStatus`
tests only by constructing calls that don't go through `Application.fetch_env!` at all
(the plug always resolves the verifier from config, so tests using this double call the
verifier's `verify_bearer_token/2` result indirectly by first confirming what claims a
given token string would produce, then, where a realm/JIT config needs to be
distinguished per-test, configuring that realm's JIT/claim-mapping fixture entries
directly — see "JIT-disabled realm fixture" below for the one place this requires adding
a config entry, done once at suite-compile time in `config/test.exs`, not mutated
per-test).

## JIT-disabled realm fixture

To exercise the `:jit_disabled` -> 403 branch without any per-test global-config
mutation, `config/test.exs` needs one additional, permanently-configured realm entry
under `config :letflow, :oidc_jit_provisioning` with `enabled: false` — a realm string
reserved for this purpose (`"jit-disabled-test-realm"`), never used by any other test's
tenant fixtures. **This is the one piece of `config/test.exs` this spec adds** (a static,
compile-time config entry, not a runtime mutation): appending one entry to the existing
`%{"bpm-default" => %{...}}` map. This is additive only — the existing `"bpm-default"`
entry (and everything `identity_test.exs`/`claim_mapping_test.exs` already rely on) is
unchanged.

## Test cases

### Acceptance criterion 1 — valid token flows through the full pipeline

1. **A valid bearer token flows through verify -> tenant resolution -> realm-ownership
   guard -> JIT provisioning and attaches `conn.assigns[:auth_context]` with `user_id`,
   `tenant_id`, `roles`** — see
   `auth_pipeline_test.exs:"a valid bearer token flows through the full pipeline and
   attaches user_id/tenant_id/roles to conn.assigns[:auth_context]"`. Seeds a tenant
   bound to realm `bpm-default` (matching `TokenVerifierDouble`'s fixed claims), sends a
   `POST` request with `Authorization: Bearer valid-test-token`, asserts
   `conn.halted == false`, `conn.assigns[:auth_context].tenant_id == tenant.id`,
   `conn.assigns[:auth_context].roles == ["VIEWER"]` (the double's fixed
   `realm_access.roles` claim), and `conn.assigns[:auth_context].user_id` is a
   real, freshly-provisioned `Letflow.Identity.User` id — re-queried directly from
   Postgres (`Repo.get(User, user_id)`, not trusting the in-memory assign) to confirm
   the row actually exists with `auth_source: :oidc`. Would fail if any pipeline step
   were skipped, mis-ordered, or if the assign key/shape didn't match §5.1's spec.
2. **A second request with the same token resolves to the same `user_id` (idempotent
   JIT lookup, not a duplicate insert)** — see
   `auth_pipeline_test.exs:"a second request with the same valid token resolves to the
   same user_id, not a duplicate row"`. Calls the plug twice against the same seeded
   tenant. Would fail if the pipeline re-provisioned a new user on every request instead
   of reusing REQ-018's idempotent upsert.

### Acceptance criterion 2 — missing/malformed token rejected before any DB/JIT work

3. **No `Authorization` header at all -> 401, halted, no tenant/JIT work runs** — see
   `auth_pipeline_test.exs:"no Authorization header at all is rejected 401 before any
   tenant resolution or provisioning runs"`. Sends a request with no header at all
   (deliberately *not* seeding any tenant matching any realm). Asserts `conn.status ==
   401`, `conn.halted == true`, and the JSON body's `error == "unauthorized"`. Proves the
   ordering claim by construction: since no tenant/realm/JIT config is set up to match
   *any* value this request could plausibly resolve to, a 401 here can only be coming
   from step 1's short-circuit — if tenant resolution or JIT provisioning had somehow run
   anyway, they would either crash (no matching config) or the test's own separate
   row-count assertion (below) would catch a stray write.
4. **Malformed header (wrong prefix, e.g. `"Token abc"` instead of `"Bearer abc"`) ->
   401** — see `auth_pipeline_test.exs:"a malformed Authorization header (wrong scheme
   prefix) is rejected 401"`. Matches R-Co's case-sensitive RFC 6750 check (design §4.2).
5. **Empty token after the `"Bearer "` prefix -> 401** — see
   `auth_pipeline_test.exs:"an empty token after the Bearer prefix is rejected 401"`.
   Sends `Authorization: Bearer ` (trailing space, empty token). Pins the
   `byte_size(token) > 0` guard in `extract_bearer_token/1`.
6. **Lowercase `"bearer "` prefix (wrong case) is rejected, not accepted** — see
   `auth_pipeline_test.exs:"a lowercase bearer prefix is rejected 401 (case-sensitive per
   RFC 6750)"`. Directly pins the case-sensitivity the design doc §4.2 states explicitly
   as matching R-Co's own check — would fail if a case-insensitive match were
   accidentally used instead.
7. **A syntactically well-formed but unverifiable token (any string other than the
   double's one valid sentinel) -> 401** — see `auth_pipeline_test.exs:"a well-formed but
   invalid/unverifiable bearer token is rejected 401"`. Proves step 1b's verifier-failure
   branch specifically (distinct from step 1a's header-shape branch above).
8. **No user row exists in the database after any of the above rejections** — folded
   into test cases 3-7 above via a shared assertion pattern (each test independently
   re-queries `Letflow.Identity.User` and `Letflow.Identity.Tenant` counts before/after
   and asserts no row was inserted by the rejected request) rather than a separate test,
   since "no row was written" is a property of each rejection case individually, not a
   distinct scenario.

### Acceptance criterion 3 — tenant-status write-pause

9. **`POST` against a `:migrating` tenant -> 503, halted, `Retry-After: 30` header, JSON
   body `error: "tenant_migrating"`** — see
   `tenant_status_test.exs:"a POST request against a :migrating tenant is rejected 503
   with a Retry-After header"`. Seeds a tenant with `status: :migrating`, builds a `conn`
   with `conn.assigns[:auth_context][:tenant_id]` pre-set (simulating `AuthPipeline`
   having already run, per the design's "runs after AuthPipeline" calling convention,
   §6.1), calls `TenantStatus.call/2` directly. Asserts `conn.status == 503`,
   `conn.halted == true`, `Plug.Conn.get_resp_header(conn, "retry-after") ==
   ["30"]`.
10. **`PUT`/`PATCH`/`DELETE` against the same `:migrating` tenant are each independently
    rejected 503** — see `tenant_status_test.exs`'s
    `"the tenant-status write-pause rejects every write method (PUT, PATCH, DELETE)"`
    test, parameterized over the three remaining write methods via `for` inside one
    test (not just `POST`, since `@write_methods` is a 4-element list and only testing
    one element wouldn't pin the other three being included). Would fail if
    `@write_methods` in the implementation dropped or misspelled any of `PUT`/`PATCH`/
    `DELETE`.
11. **`GET` against the same `:migrating` tenant passes through unchanged, no 503** —
    see `tenant_status_test.exs:"a GET request against a :migrating tenant passes
    through unchanged"`. Asserts `conn.halted == false` and `conn.status == nil` (the
    plug never touched the response at all — not just "not 503").
12. **`HEAD` against the same `:migrating` tenant also passes through** — see
    `tenant_status_test.exs:"a HEAD request against a :migrating tenant also passes
    through unchanged"`. `HEAD` is explicitly named in the acceptance criterion
    alongside `GET` — tested as its own case since it is a distinct method value from
    `GET`, not implied by testing `GET` alone.
13. **A write request against an `:active` tenant passes through, no 503** — see
    `tenant_status_test.exs:"a POST request against an :active tenant passes through
    unchanged"`. Proves the check is status-conditional, not "reject every write
    unconditionally" (a test suite that only ever sent write requests against migrating
    tenants couldn't distinguish a real status check from an "always reject writes" bug).
14. **`GET`/write requests never issue a DB query at all for a non-write method** — see
    `tenant_status_test.exs:"a GET request issues no Ecto query at all (method
    short-circuit, no DB round-trip)"`. Uses `Ecto.Adapters.SQL.Sandbox`'s telemetry-free
    approach is unavailable without extra deps, so this is verified instead by
    `:telemetry.attach/4` on `[:letflow, :repo, :query]` (Ecto's standard telemetry
    event, emitted by every `Letflow.Repo` call including `Repo.get/2` — no extra
    dependency needed, `ecto_sql` emits this by default) around a `GET` call, asserting
    zero events fired. Would fail if `call/2`'s method-guard clause were removed and
    every request fell through to the DB-querying clause regardless of method.

### Acceptance criterion 4 — realm-ownership guard rejects mismatch, no JIT under wrong tenant

15. **`verify_realm_ownership/2`, called with the plug's exact argument shape, rejects a
    tenant that does not own the claimed realm** — see
    `auth_pipeline_test.exs:"the realm-ownership guard rejects a tenant that does not own
    the token's claimed realm, called with the exact arguments AuthPipeline itself
    passes"`. This is the direct, deterministic reproduction of the scenario ELIXIR-DEV's
    own self-verification script (`scratch/req021_demo.exs`, step 3) already
    demonstrated is the only reachable way to exercise this guard's rejection branch
    given the current implementation — see "AC4 test strategy" below for the full
    structural reasoning for why this is the correct test shape (not a full end-to-end
    plug call). Seeds `tenant_a` bound to realm `R`, and a second `tenant_b` bound to a
    *different* realm. Calls `Letflow.Identity.verify_realm_ownership(tenant_b.id, R)` —
    the exact call `AuthPipeline.guard_realm_ownership/2` makes internally when its
    `tenant.id` argument doesn't own its `realm` argument. Asserts `{:error,
    :realm_tenant_mismatch}`, and separately confirms (by row-count query) that calling
    `Letflow.Identity.provision_oidc_user/3` was never invoked as a consequence (this
    spec does not call `provision_oidc_user/3` at all in this test — its absence from the
    test body, combined with the row-count assertion staying at zero throughout, is the
    proof that nothing this test didn't explicitly call could have written a row).
16. **No user row is created under `tenant_b` when the guard would reject** — see
    `auth_pipeline_test.exs:"no user row is created under the wrong tenant when the
    realm-ownership guard would reject"`, folded into test case 15's own body: after
    asserting the `{:error, :realm_tenant_mismatch}` result, queries
    `Letflow.Identity.User` filtered to `tenant_id: tenant_b.id` and asserts `[] ==`
    the result. This is the literal "not silently JIT-provisioned under the wrong
    tenant" clause of AC4, checked as a real database fact, not just the return value.
17. **The plug's own call order guarantees the guard runs before provisioning** — see
    `auth_pipeline_test.exs:"AuthPipeline's call/2 never reaches JIT provisioning when
    the realm-ownership guard fails"`. This test targets the ordering property directly
    at the plug level (not just the `Letflow.Identity` function level, cases 15-16
    above): constructs the scenario where `resolve_tenant_by_realm/1` itself resolves to
    a tenant whose bound realm the guard then independently re-confirms mismatches — using
    a `bpm-default`-claiming token (`TokenVerifierDouble`'s sentinel) but explicitly
    seeding NO tenant bound to `bpm-default` at all, so `resolve_tenant_by_realm` returns
    `{:error, :not_found}` and the pipeline never reaches the guard step in the first
    place (this is AC2's territory structurally, folded in here as the plug-level
    negative-space check: whatever the failure mode, no row is ever written under any
    tenant when resolution/ownership fails). Combined with cases 15-16's direct
    `Letflow.Identity`-level proof of the guard's own rejection behavior, this
    establishes both "the guard, called correctly, rejects the wrong pairing" and "the
    plug never writes a user row when any pre-provisioning step fails" — see "AC4 test
    strategy" below for why these two together are the strongest coverage achievable
    without either mocking or a non-deterministic concurrency test.

### `sub_claim_missing` branch (beyond the bare acceptance criteria, same 401 collapse)

18. **A verified token with no `sub` claim -> 401, no user row created** — see
    `auth_pipeline_test.exs:"a verified token with no sub claim is rejected 401, no user
    row created"`. Uses `ConfigurableTokenVerifierDouble`'s `"no-sub-token:" <> realm`
    token shape (seeds a tenant bound to that realm first). Exercises
    `map_claims/2`'s `{:error, :sub_claim_missing}` branch, distinct from every prior
    401 case (this one reaches step 4a before failing, later than cases 3-7 and 15-17).

### JIT-disabled realm (403, distinct from every 401 case)

19. **A verified token for a realm whose JIT config has `enabled: false` -> 403, no user
    row created** — see `auth_pipeline_test.exs:"a verified token for a realm with JIT
    provisioning disabled is rejected 403, no user row created"`. Seeds a tenant bound to
    `"jit-disabled-test-realm"` (the fixture realm added to `config/test.exs`, see "JIT-
    disabled realm fixture" above). Uses `ConfigurableTokenVerifierDouble`'s
    `"realm-token:jit-disabled-test-realm"` token shape. Asserts `conn.status == 403`,
    JSON body `error == "forbidden"`, and confirms no `Letflow.Identity.User` row exists
    for that tenant afterward. Distinguishes this design-specified 403 (§4.5) from every
    401 rejection above — would fail if `:jit_disabled` were accidentally collapsed into
    the generic 401 branch instead of matched separately.

### Acceptance criterion 5 — moduledoc content, no runtime test

REQ-021's fifth acceptance criterion ("moduledoc explicitly states this plug supersedes
REQ-103... and names which router.ex routes... it is mounted in front of") is a
documentation-content requirement, not application behavior in the ExUnit sense — same

verified by **direct inspection** here, for TEST-DESIGN-VALIDATOR/RELEASE-VALIDATOR to

- Lines 23-31: "**Not mounted in front of any route today.** All 3 of `Letflow.Router`'s

## AC4 test strategy — why not a full end-to-end plug-level race

`Letflow.Plugs.AuthPipeline.call/2`'s `with` chain (lines 56-64 of
`lib/letflow/plugs/auth_pipeline.ex`) binds `realm` once (from the verified token's `iss`
claim) and passes that same, single `realm` value to both `resolve_tenant/1` (which calls
`Letflow.Identity.resolve_tenant_by_realm/1`, a direct `Repo.get_by(Tenant, idp_realm_id:
realm)` equality lookup) and `guard_realm_ownership/2` (which calls
`Letflow.Identity.verify_realm_ownership/2`, itself re-querying via
`resolve_realm_by_tenant/1`, another `idp_realm_id`-keyed lookup on the SAME tenant id
`resolve_tenant/1` just returned). Both queries key off the identical `idp_realm_id`
column value for the identical `realm` string within the same single-request call
sequence — **given a snapshot of consistent database state, these two lookups cannot
structurally disagree**: whichever tenant `resolve_tenant_by_realm(realm)` finds is, by
definition of that same lookup, bound to `realm`; re-querying that tenant's bound realm
moments later (absent an actual concurrent write racing between the two calls) returns
the same value.

This was independently confirmed by ELIXIR-DEV's own self-verification script
(`scratch/req021_demo.exs`, step 3, lines 54-73), which reaches the identical conclusion
and demonstrates the guard's rejection by calling
`Letflow.Identity.verify_realm_ownership/2` directly against a deliberately
wrong-tenant/right-realm pairing rather than trying to force the full plug's `with` chain
into disagreeing with itself.

**What this means for coverage:** the acceptance criterion is about the *guard's
behavior* (does it reject a mismatched pairing, and does that rejection prevent JIT
provisioning) — not about proving the two DB reads can disagree under normal operation
(they can't, by construction, and that's a *good* property of this design, not a gap).
Test cases 15-17 above prove:
1. The guard function, called with the exact argument shape `AuthPipeline` uses
   internally, correctly rejects a mismatched `(tenant_id, realm)` pairing (case 15).
2. No user row is written as a side effect of that rejection (case 16).
3. At the full-plug level, no request that fails resolution/ownership ever reaches
   `provision_oidc_user/3` — checked as a real database fact (zero rows) across every
   failure-path test in this file, not asserted from the return value alone (case 17 and
   the row-count assertions folded into cases 3-7).

**What is explicitly NOT covered, stated rather than silently omitted:** a genuine
concurrent write landing between `resolve_tenant/1`'s read and `guard_realm_ownership/2`'s
re-read within a single request — a true TOCTOU race on the same tenant row. Reproducing
this deterministically would require either (a) instrumenting `AuthPipeline.call/2`
itself to pause mid-`with`-chain (out of scope — the design doc's own `with` chain has no
seam for a test to inject a pause without changing production code), or (b) a
best-effort, timing-dependent `Task`-based race (accepted for REQ-018's genuinely
input-symmetric concurrent-insert race in `identity_test.exs`, but not attempted here
because, unlike that case, there is no way to guarantee the racing write actually lands
inside the ~microsecond window between these two specific reads without an explicit sync
point inside the plug itself — a "best effort" race here could easily pass for reasons
unrelated to the guard actually working, which would be a worse, misleading test than
having none). This gap is judged acceptable because `Letflow.Identity.verify_realm_ownership/2`'s
own re-query-not-trust design (explicitly re-querying rather than accepting a
caller-supplied realm, per its own moduledoc) is exactly the defense a genuine race
would need, and that mechanism is directly tested here (case 15) — what's untested is
only the specific timing window's non-occurrence in the full plug flow, which the
structural argument above shows cannot occur under any non-racing scenario, and which
open question OQ-12/OQ-14 in the design doc already flag as a class of not-fully-defended
edge case at this stage of the project.

## Fixture isolation

Every test builds its own unique tenant `slug`/`idp_realm_id` (via
`System.unique_integer([:positive, :monotonic])`-suffixed strings, matching
`identity_test.exs`'s established `unique_realm/1`/`unique_slug/1` convention — reused
directly in this file's own helper functions) and its own real `Tenant` row(s) inside its
own sandboxed transaction, except where a test deliberately uses the fixed
`"bpm-default"` realm (required because `Letflow.Oidc.TokenVerifierDouble`'s one
sentinel token always claims that exact realm) — safe under the sandbox's per-test
transaction isolation (rolled back after each test, never visible across tests), the
same reasoning `identity_test.exs`'s own "bpm-default" fixture reuse already documents.
Every test that needs the `"jit-disabled-test-realm"` fixture realm creates its own,
independently-slugged tenant bound to that realm — the realm string itself is shared
across any tests using it (since it must match the one static `config/test.exs` entry),
but each test's tenant row is distinct, and `Repo.get_by(Tenant, idp_realm_id: ...)`
would only ever be ambiguous if two tenants were bound to the identical realm string at
once — the partial unique index on `idp_realm_id` (REQ-015's migration) makes that
