# Test Spec: REQ-022 — Schema-per-tenant provisioning mechanism (tenant_schemas registry + provisioning function)

**Requirement:** REQ-022 (`docs/requirements.yaml`, stage S2) — build the tenant_schemas
registry, `Letflow.TenantProvisioning.provision_tenant_schema/1`, and
`Letflow.TenantProvisioning.replay_migrations/2`, resolving the deferral
`lib/letflow/design/identity-schema.md` §1 flagged.

**Requirement's acceptance criteria (verbatim):**
1. "priv/repo/migrations gains a tenant_schemas migration (public/default schema) that
   applies cleanly via mix ecto.migrate, with columns for at minimum tenant_id and
   schema_name"
2. "a provision_tenant_schema/1-equivalent function exists that issues a real CREATE
   SCHEMA and records the mapping in tenant_schemas, demonstrated against at least one
   non-default tenant schema name"
3. "a migration-replay function exists that re-applies priv/repo/migrations/ against a
   specific tenant schema via Ecto's prefix: option, demonstrated by confirming at
   least one table exists under the provisioned schema's own information_schema, not
   just under public"
4. "the moduledoc/description explicitly states, as an open question rather than a
   silent decision, whether REQ-015's users/groups/tenant_role migrations are
   retrofitted to use :prefix now or remain in public schema"

**Test tier:** unit + integration. `schema_name_for_tenant/1` is pure (no I/O);
`provision_tenant_schema/1`, `replay_migrations/2`, and `Registration.changeset/2` all
touch `Letflow.Repo` (real Postgres, per DIRECTIVE T-1 — no mocked database).

## The Sandbox-incompatibility investigation (why this file isn't a plain DataCase file)

The design doc (`lib/letflow/design/req022-tenant-schema-provisioning.md` §6,
"Testing environment caveat") flagged, without resolving, that `Ecto.Migrator`'s own
moduledoc (`deps/ecto_sql/lib/ecto/migrator.ex`, read directly) states migrations
"cannot run dynamically during test under `Ecto.Adapters.SQL.Sandbox`, as the sandbox
has to share a single connection across processes to guarantee the changes can be
reverted," and left resolving this to TEST-DESIGNER at Step 3.

**Empirically reproduced before writing the real test:** a throwaway probe test called
`replay_migrations/2` from inside `Letflow.DataCase`'s normal sandboxed checkout.
Result — a real, reproducible failure, not a hypothetical:

```
PROBE replay_migrations result: {:error,
 {:migration_failed,
  %DBConnection.ConnectionError{
    message: "could not checkout the connection owned by #PID<0.641.0> (...).
    When using the sandbox, connections are shared, so this may imply another
    process is using a connection. Reason: connection not available and request
    was dropped from queue after 766ms. ...",
    severity: :error,
    reason: :queue_timeout
  }}}
```

Root cause, traced directly in `deps/ecto_sql`: with no `:migration_lock` config key
set for `Letflow.Repo` (confirmed absent from `config/test.exs`), `Ecto.Migrator`
defaults to the `:table_lock` strategy (`deps/ecto_sql/lib/ecto/adapters/postgres.ex`
`lock_for_migrations/3`/`do_lock_for_migrations(:table_lock, ...)`), which itself
completes on the single sandboxed connection fine — but the *overall* migration-run
sequence still genuinely needs a second connection at some point during `run/4`'s
lock/versions/apply cycle, and DataCase's sandboxed pool only ever hands this test
process its one owned connection. Whether or not every internal step could
theoretically share one connection, the actual observed behavior against this
project's real `deps/ecto_sql` version is: it doesn't, and hangs/times out queuing for
a second one.

**Fix, matching the design doc's own suggestion:** for the two describe blocks that
call `Ecto.Migrator` (directly or via `replay_migrations/2`), switch `Letflow.Repo` to
Sandbox `:auto` mode for that block's `setup`, instead of relying on the ambient
manual/checkout pattern. Per `Ecto.Adapters.SQL.Sandbox.mode/2`'s own moduledoc
(`deps/ecto_sql/lib/ecto/adapters/sql/sandbox.ex`, read directly): "Whenever you
change the mode to `:manual` or `:auto`, all existing connections are checked in" —
this checks in the test's already-checked-out sandboxed connection and makes every
subsequent `Repo` call use a real, ad hoc, committing connection instead. These
specific tests are therefore **not** rolled back automatically; they clean up the real
schema/rows/`schema_migrations` bookkeeping they create in `on_exit/1` instead.

**Why switching the mode mid-test doesn't corrupt another concurrently running test's
sandboxed connection** (the exact risk that same moduledoc's warning describes):
confirmed directly from Elixir's own installed `ex_unit` source
(`ex_unit/lib/ex_unit/runner.ex`, `async_loop/4`, read directly, not assumed) that
ExUnit fully drains and waits for every `async: true` module to finish
(`0 = running |> Enum.reduce(...) |> map_size()` at line 124-127) before starting any
`async: false` (sync) module, and runs sync modules strictly one at a time (the
`for pair <- sync_modules do ... wait_until_available ... end` loop at lines 132-135
never spawns the next sync module until the previous one's `:DOWN` is received). This
project already has four other `async: false` test files
(`process_instance_test.exs`, `parallel_approval_test.exs`,
`plugs/auth_pipeline_test.exs`, `plugs/auth_pipeline_configurable_verifier_test.exs`),
confirming `async: false` is an established, accepted pattern here, not a novel
divergence. Because ExUnit's `async` setting is module-wide (not settable per test),
`test/letflow/tenant_provisioning_test.exs` is `async: false` for its *entire* module,
even though only two of its describe blocks actually need the `:auto`-mode switch —
there is no other test file's connection to disturb at the moment those blocks' setup
runs, since no other test file is executing concurrently with a sync module by
construction.

`provision_tenant_schema/1` itself needs no such treatment — confirmed empirically
(the probe above succeeded for the provisioning half, only `replay_migrations/2`
failed): it only ever uses one connection (one `Repo.transaction/1`, two `Repo.query!`
calls inside it), so its own tests run under DataCase's ordinary sandboxed
(rolled-back) transaction with no special handling.

## Test cases

### Acceptance criterion 1 — `tenant_schemas` migration + `Registration.changeset/2`

1. **The migration applied cleanly, with at least `tenant_id` and `schema_name`
   columns** — see `tenant_provisioning_test.exs:"the migration applied cleanly:
   tenant_schemas exists in public with at least tenant_id and schema_name columns"`.
   Every test in this file already implicitly proves the migration applied (DataCase's
   checkout would fail outright otherwise), but this test goes further and queries
   `information_schema.columns` directly for `tenant_schemas`, asserting `tenant_id`,
   `schema_name`, `migrations_applied_at`, and `provisioned_at` are all present. Would
   fail if the migration were missing, misnamed, or dropped a required column.
2. **`changeset/2` requires both `tenant_id` and `schema_name`** — see
   `tenant_provisioning_test.exs:"changeset/2 requires both tenant_id and
   schema_name"`. Would fail if either `validate_required` entry were dropped.
3. **A second row for the same `tenant_id` violates the `unique_constraint` on
   `tenant_id`** — see `tenant_provisioning_test.exs:"a second row for the same
   tenant_id violates the unique_constraint on tenant_id"`. This is the DB-level
   invariant `provision_tenant_schema/1`'s own idempotency (test case 8 below) is
   built on — this test isolates and pins it directly at the changeset/migration layer,
   independent of the provisioning function. Would fail if the migration's
   `unique_index(:tenant_schemas, [:tenant_id])` or the changeset's
   `unique_constraint(:tenant_id)` were removed or misnamed.
4. **A `schema_name` already used by a different tenant violates the
   `unique_constraint` on `schema_name`** — see `tenant_provisioning_test.exs:"a
   schema_name already used by a different tenant violates the unique_constraint on
   schema_name"`. Defense-in-depth per the design doc §2 (practically unreachable via
   `provision_tenant_schema/1` itself, since `schema_name` is deterministically derived
   from `tenant_id`, but the DB-level constraint and its changeset mapping are real,
   independently-testable surface). Would fail if `unique_index(:tenant_schemas,
   [:schema_name])` or `unique_constraint(:schema_name)` were removed or misnamed.
5. **A `tenant_id` with no matching `tenants` row violates the
   `foreign_key_constraint`, no row inserted** — see `tenant_provisioning_test.exs:"a
   tenant_id with no matching tenants row violates the foreign_key_constraint, no row
   inserted"`. Would fail if `references(:tenants, ...)` were dropped from the
   migration or `foreign_key_constraint(:tenant_id)` were dropped from the changeset
   (in which case this would surface as an unhandled `Ecto.ConstraintError` instead of
   a clean changeset error, itself still a failing test either way).

### Acceptance criterion 2 — `provision_tenant_schema/1`

6. **Issues a real `CREATE SCHEMA`, confirmed via `information_schema.schemata`
   directly (not the return value), and records the `tenant_schemas` row** — see
   `tenant_provisioning_test.exs:"issues a real CREATE SCHEMA (confirmed via
   information_schema.schemata, not just the return value) and records the
   tenant_schemas row"`. Queries `information_schema.schemata` directly, per this
   file's task instruction not to trust the function's own `{:ok, _}` return as proof.
   Would fail if the schema were never actually created (e.g. a stubbed/no-op DDL
   call) even if the function still returned an `{:ok, _}`-shaped value.
7. **Idempotent: calling it twice for the same tenant returns the identical
   `Registration` row, schema still created only once** — see
   `tenant_provisioning_test.exs:"calling it twice for the same tenant is idempotent:
   identical Registration row, schema still created only once"`. Asserts both calls'
   `id` match and a direct `COUNT(*)` against `tenant_schemas` for that `tenant_id` is
   exactly 1. Would fail if the second call raised (constraint violation not
   converted to idempotent success) or produced a second, duplicate row.
8. **A syntactically valid but unknown `tenant_id` returns `{:error, :tenant_not_found}`
   and leaves no orphan schema or row behind (the atomicity invariant)** — see
   `tenant_provisioning_test.exs:"a syntactically valid but unknown tenant_id returns
   {:error, :tenant_not_found} and leaves no orphan schema or row behind"`. This is the
   test the dispatching task specifically called out: ELIXIR-DEV's Step 2a handoff
   demonstrated this manually once, against a real dev DB, via a throwaway scratch
   script that was then deleted — a one-time manual demo does not guarantee this
   invariant holds against any future change to this function, so it needs to be an
   always-run automated test. Confirms `schema_exists?` is `false` *before* the call
   (so the later assertion isn't vacuous), calls `provision_tenant_schema/1` with a
   fresh `Ecto.UUID.generate()` matching no real `tenants` row, then re-confirms
   `schema_exists?` is still `false` and `Repo.get_by(Registration, ...)` is `nil`.
   **Empirically verified this test is load-bearing, not vacuous:** temporarily
   mutated `provision_tenant_schema/1` to issue `CREATE SCHEMA` *before* opening
   `Repo.transaction/1` (i.e. moved it outside the transaction/rollback boundary — the
   exact class of bug this invariant guards against), and re-ran this test. Result:
   this exact test failed —
   ```
   1) test provision_tenant_schema/1 (acceptance criterion 2) a syntactically valid
      but unknown tenant_id returns {:error, :tenant_not_found} and leaves no orphan
      schema or row behind
      Expected false or nil, got true
      code: refute schema_exists?(would_be_schema_name)
   ```
   — no other test in the file changed status (13/14 passed, exactly this one
   failing). The mutation was then reverted and `git diff --stat
   lib/letflow/tenant_provisioning.ex` confirmed a clean revert (no diff against the
   committed version) before the full suite was re-run, confirming 14/14 passed again.
9. **A syntactically invalid `tenant_id` returns `{:error, :invalid_tenant_id}`
   without touching the database** — see `tenant_provisioning_test.exs:"a
   syntactically invalid tenant_id returns {:error, :invalid_tenant_id} without
   touching the database"`. Would fail if the `schema_name_for_tenant/1` short-circuit
   were removed and a malformed string reached `Repo.query!`/`Ecto.UUID` casting
   raising an unhandled exception instead of a clean typed error.

### Acceptance criterion 3 — `replay_migrations/2`

10. **A tenant with no `Registration` row returns `{:error, :tenant_not_provisioned}`,
    never invoking `Ecto.Migrator`** — see `tenant_provisioning_test.exs:"returns
    {:error, :tenant_not_provisioned} for a tenant_id with no Registration row, never
    invoking Ecto.Migrator"`. This branch returns before ever reaching `Ecto.Migrator`
    (`tenant_provisioning.ex:161-163`'s `nil -> {:error, :tenant_not_provisioned}`), so
    it needs none of the `:auto`-mode treatment above and runs under DataCase's
    ordinary sandboxed transaction. Would fail if `replay_migrations/2` instead tried
    to provision on the fly or otherwise reached `Ecto.Migrator.run/4` for an
    unregistered tenant.
11. **Replays `test/support/req022_migration_fixture.ex` into the tenant's own
    schema, confirmed via that schema's own `information_schema`, and NOT under
    `public`** — see `tenant_provisioning_test.exs:"replays
    test/support/req022_migration_fixture.ex into the tenant's own schema, confirmed
    via that schema's own information_schema, and NOT under public"`. This is AC3's
    literal wording, satisfied exactly as specified: `SELECT EXISTS (...)  FROM
    information_schema.tables WHERE table_schema = $1 AND table_name = $2` is queried
    twice — once scoped to the tenant's own provisioned schema (asserted `true`), once
    scoped to `public` (asserted `false`, via `refute`) — positively proving the table
    landed under the tenant's schema *because of* `:prefix`, not by some accidental
    default. Also asserts `migrations_applied_at` was stamped non-nil after a
    successful replay. Would fail if `:prefix` were dropped from the
    `Ecto.Migrator.run/4` call, or if `mark_migrations_applied/1` were removed.

### Acceptance criterion 4 — `@moduledoc` open-question content, no runtime test

REQ-022's fourth acceptance criterion ("the moduledoc/description explicitly states,
as an open question rather than a silent decision, whether REQ-015's
users/groups/tenant_role migrations are retrofitted to use :prefix now or remain in
public schema") is a **documentation-content requirement**, not application behavior
in the ExUnit sense. Following the established project precedent
(`test/specs/REQ-020.md`'s AC5 handling, and the WF-02 Step 3 workflow doc's own
explicit warning against "a test with no real executable behavior to fail against" —
the manufactured-busywork anti-pattern `core-directives.md` and
`docs/agents/workflows/WF-02_requirement_implementation.md` both flag), this is
**verified by direct inspection** here rather than a `String.contains?(@moduledoc,
...)`-style runtime assertion, which would prove nothing about behavior and would be
trivially kept "green" by copy-pasting the required substrings without them being
true.

Inspected `lib/letflow/tenant_provisioning.ex` lines 27-50 directly. Confirmed the
required content is present, verbatim in substance:
- Line 27: `## Open question (REQ-022 acceptance criterion 4 — not resolved here)` —
  explicitly framed as an open question, not a silent decision.
- Lines 29-39: states REQ-015's `users`/`groups`/`tenant_role` tables "currently live
  in the public default schema," that "this requirement does not retrofit those three
  tables to live under each tenant's own schema," and that whether they "*should*
  eventually be retrofitted behind `:prefix`... is left open for a future requirement
  to decide explicitly — not assumed either way by this module."

This is a one-time inspection result, not a standing regression check — a future edit
could silently remove this prose without any test catching it, which is the accepted,
explicitly-stated tradeoff for a documentation-content criterion per this project's own
guidance against inventing busywork tests. RELEASE-VALIDATOR should re-confirm this
independently rather than trust this spec's claim, same as REQ-020's precedent asks.

## Fixture isolation and cleanup

Every test that inserts a `Tenant` uses `insert_tenant!/0`, which generates a
per-test-unique `slug` via `System.unique_integer([:positive, :monotonic])`, matching
`identity_test.exs`'s established convention — no shared hardcoded tenant row across
tests. Every `Registration` row inserted directly (AC1's changeset tests) uses
`unique_schema_name/1`, likewise per-test-unique, avoiding any reliance on this file's
`async: false` setting for isolation between tests (each test's data would collide
under a hypothetical future `async: true` refactor otherwise, even though today's
serial execution would also happen to avoid it).

The two describe blocks that switch to Sandbox `:auto` mode (see the investigation
section above) are **not** protected by DataCase's transaction rollback — each
registers an `on_exit/1` that explicitly `DROP SCHEMA ... CASCADE`s the real schema it
created and deletes the real `tenant_schemas`/`tenants` rows (or, for the guard-pattern
block, deletes its `schema_migrations` bookkeeping row by its deliberately implausible
`999_999_999` version number, chosen to avoid any collision with a real
timestamp-based `priv/repo/migrations/` version). **Verified empirically**: ran
`test/letflow/tenant_provisioning_test.exs` twice consecutively (14 passed both times)
and then queried the real test database directly —

```sql
SELECT nspname FROM pg_catalog.pg_namespace WHERE nspname LIKE 'tenant_%';   -- 0 rows
SELECT version FROM public.schema_migrations WHERE version = 999999999;      -- 0 rows
SELECT count(*) FROM public.tenant_schemas;                                  -- 0
SELECT count(*) FROM public.tenants WHERE slug LIKE 'req022-%';              -- 0
```

confirming no orphan Postgres schema, no orphan `schema_migrations` bookkeeping row,
and no residual `tenant_schemas`/`tenants` rows survive a run.
