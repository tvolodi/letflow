# Test Spec: REQ-023 — Event-store schema & migrations

**Requirement:** REQ-023 — "Event-store schema/migrations (events, instance_sequence,
event_payload_store, events_archive, idempotency sidecar, instance_projections)"
**Test tier:** unit + integration
**Design artefact:** `lib/letflow/design/req023-event-store-schema.md`
**Implementation under test:** `lib/letflow/event_store/*.ex` (six `Ecto.Schema`
modules), `priv/repo/migrations/20260816120001..120006_*.exs` (six migrations), and
`Letflow.TenantProvisioning.tenant_scoped_migrations/0`.

---

## WF-02 Step 3 scope test — verdict: **YES, in scope**

Step 3 opens with a scope test: does Step 2a's `artifacts_out` contain
**application-executable surface**, or is it docs-only / build-config-only?

**Verdict: YES — there is real executable surface, by a wide margin.** Re-derived from
the artefacts themselves, not inherited from the dispatching handoff:

- `lib/letflow/event_store/` ships **six `Ecto.Schema` modules** with `schema/2`
  declarations, composite/natural primary keys, `Ecto.Enum` fields, `read_after_writes`
  fields, and seven changeset functions carrying `validate_required/2`,
  `validate_length/3`, `validate_number/3`, `unique_constraint/3` and
  `foreign_key_constraint/2` calls. These are pure functions with observable behaviour:
  `Event.insert_changeset(%Event{}, attrs)` returns a different value for valid and
  invalid `attrs`, and `InstanceProjection.terminal?/1` is a total function over a
  closed status set. All of that is directly assertable.
- `priv/repo/migrations/20260816120001..120006_*.exs` each contain a **load-bearing
  conditional** — `if prefix() do ... end` — whose two branches produce materially
  different database state. That is control flow, not a declaration.
- `Letflow.TenantProvisioning.tenant_scoped_migrations/0` changed materially: it went
  from returning `[]` to returning six entries, and it gained a
  `Code.ensure_loaded?/1`-guarded `Code.require_file/1` side effect
  (`ensure_migration_module_loaded!/2`). Its output is now the default
  `migration_source` of `replay_migrations/2`, so it drives real DDL against real
  tenant schemas.

None of this resembles the `mix.exs`/`.formatter.exs`/`config/*.exs` category the scope
test exists to skip: nothing here is a build/project declaration verified by running the
command it declares. Every acceptance criterion below has a runnable assertion that
fails if the criterion is violated. Steps 3b and 4 therefore proceed normally.

## Test files

| File | Tier | `async` | Touches DB? |
|---|---|---|---|
| `test/letflow/event_store/schemas_test.exs` | unit (pure) | `true` | no |
| `test/letflow/event_store/migrations_test.exs` | integration | `false` | yes — real tenant schemas |

`migrations_test.exs` is `async: false` for the same empirically-established reason
`test/letflow/tenant_provisioning_test.exs` is: `Ecto.Migrator` genuinely needs a second
database connection beyond the one `Letflow.DataCase`'s sandbox checks out, so the
Migrator-touching describe blocks switch `Letflow.Repo` to `Ecto.Adapters.SQL.Sandbox`
`:auto` mode and clean up the real schemas/rows they create in `on_exit/1` rather than
relying on transaction rollback. ExUnit drains every `async: true` module before running
any sync module and runs sync modules one at a time, so the `:auto` switch cannot
disturb another module's connection. `schemas_test.exs` is `async: true` and is safe
there: it performs no I/O beyond `Code.fetch_docs/1` and attaches no global
`:telemetry` handler — deliberately avoiding a second instance of the `async: true` +
global-handler mistake `docs/issues/ISS-0011.yaml` records.

## Test cases

### Acceptance criterion 1 — six migrations, all `:prefix`-scoped, replay cleanly

1. **All six REQ-023 migrations are registered and replay into a provisioned tenant
   schema, and none of their tables appears in `public`** — see
   `migrations_test.exs:"replay_migrations/2 applies every registered tenant-scoped
   migration and all six event-store tables land in the tenant's own schema, never in
   public"`.
   *Why it exists:* this is the criterion's own wording turned into an executable
   check, and it is the only test that exercises the whole REQ-022 → REQ-023 seam end to
   end (`provision_tenant_schema/1` → `replay_migrations/2` → `Ecto.Migrator` with
   `prefix:` → six real `CREATE TABLE`s). The `refute` half is what proves `:prefix` is
   actually doing the work: a migration that ignored `:prefix` and wrote to the default
   schema would still make the `assert` half pass in a naive "does the table exist"
   check, so the test positively asserts the tables are **absent** from `public` too.
   Also asserts `Registration.migrations_applied_at` was stamped, which is the
   REQ-022-side observable that the replay ran to completion rather than partially.

2. **Every migration's column set matches its `Ecto.Schema` module's field list,
   table by table** — see `migrations_test.exs:"each event-store table's real column set
   in the tenant schema matches its Ecto.Schema module's field list exactly"`.
   *Why it exists:* "applies cleanly" is necessary but not sufficient — a migration can
   apply cleanly and still disagree with the schema module that reads it, which surfaces
   much later as a runtime `Postgrex` error in REQ-025. This test cross-checks the two
   independently-authored halves against each other (`__schema__(:fields)` versus
   `information_schema.columns`) for all six tables at once, so drift in either
   direction fails immediately. It is deliberately an equality assertion, not a subset
   assertion: an extra column in either half is drift too.

3. **The six REQ-023 migration modules are all present in
   `tenant_scoped_migrations/0`** — see `migrations_test.exs:"tenant_scoped_migrations/0
   registers all six REQ-023 event-store migrations"`.
   *Why it exists:* `req022-tenant-schema-provisioning.md` §4 states both halves are
   mandatory and independent: a guarded-but-unregistered migration is inert forever
   (never selected by `replay_migrations/2`, so no tenant schema ever gets the table)
   while a registered-but-unguarded one corrupts `public`. Test 6 below covers the guard
   half; this covers the registration half, so dropping either is caught.

### Acceptance criterion 2 — `events`' PK is `(event_id, created_at)`

4. **The physical primary key of `events` in a provisioned tenant schema is exactly
   `["event_id", "created_at"]`, in that order** — see `migrations_test.exs:"events'
   physical primary key in the tenant schema is (event_id, created_at), in that order,
   not a bare event_id"`.
   *Why it exists:* this is the criterion read literally, against the database rather
   than against the migration source text. Column *order* is asserted, not just
   membership, because `(created_at, event_id)` would satisfy a set-equality check while
   being the wrong index for the partitioning retrofit 0003 Decision C point 2(a)
   exists to preserve. The test also explicitly `refute`s the bare `["event_id"]` shape
   the criterion names as the thing to avoid, and asserts `events_archive` carries the
   same composite shape (the archive is the same row).

5. **`Letflow.EventStore.Event.__schema__(:primary_key)` is `[:event_id, :created_at]`**
   — see `schemas_test.exs:"Event's primary key is the composite (event_id, created_at),
   not a bare event_id"`.
   *Why it exists:* the migration and the schema module can disagree. Test 4 pins the
   database; this pins the Elixir side, so a schema module that reverted to
   `@primary_key {:event_id, :binary_id, autogenerate: true}` fails even though the
   database is still correct. It additionally pins `__schema__(:autogenerate) == []` and
   `__schema__(:autogenerate_id) == nil`: design INV-EV-5 requires REQ-025 to mint one
   `event_id` and one `created_at` and bind the same values into `events`,
   `event_idempotency` and `event_payload_store`, which silently breaks if either PK
   component ever gains `autogenerate`.

### Acceptance criterion 3 — no UPDATE path on `events`; moduledoc states the invariant

6. **`Letflow.EventStore.Event`'s own public API is exactly `[insert_changeset: 2]`** —
   see `schemas_test.exs:"Event's own public API is exactly insert_changeset/2 — no
   update_changeset/2, no generic changeset/2, no other update path"`.
   *Why it exists:* this is the structural form of the criterion and is far stronger
   than grepping the moduledoc prose. It is written as an *exact set* equality over
   `Event.__info__(:functions)` (with the `__`-prefixed functions `Ecto.Schema`
   generates filtered out), not as a blacklist of the two names the criterion happens to
   mention, so a future `revise_changeset/2`, `correct/2` or `touch/1` fails the test
   just as `update_changeset/2` would. The criterion says "no `update_changeset/2` **or
   any function that issues an UPDATE**"; only an exact-set assertion covers the second
   half.

7. **`ArchivedEvent`, `InstanceSequence`, `StoredPayload` and `IdempotencyRecord`
   likewise expose only `insert_changeset/2`** — see `schemas_test.exs:"the four other
   append-only event-store schemas likewise expose only insert_changeset/2"`.
   *Why it exists:* the immutability invariant is not `events`-only — `events_archive`
   holds the same immutable fact (`ArchivedEvent`'s moduledoc says so), `instance_sequence`
   must be incremented under a row lock rather than by a read-modify-write changeset
   (design INV-EV-4), and a claimed idempotency key must never be re-pointed. Covering
   them here means the invariant is enforced across the whole directory rather than at
   one file.

8. **`InstanceProjection` deliberately *does* expose `update_changeset/2`** — see
   `schemas_test.exs:"InstanceProjection deliberately DOES expose update_changeset/2 —
   the contrast that proves tests 6 and 7 discriminate"`.
   *Why it exists:* a test that asserts "no module in this directory has
   `update_changeset/2`" would pass just as happily against a directory where nobody
   ever writes changesets at all. This is the negative control: `instance_projections`
   is derived state (0003 Decision C point 3, design INV-EV-9) and legitimately carries
   an update path, so tests 6 and 7 are proven to be measuring something real rather
   than being vacuously true.

9. **`Event`'s moduledoc states the immutability invariant and cites 0003 Decision C
   point 1** — see `schemas_test.exs:"Event's moduledoc states the append-only
   immutability invariant and cites 0003 Decision C point 1"`.
   *Why it exists:* the criterion demands this specific text, so it is tested — but as
   the weaker half, paired with test 6's structural assertion, never as a substitute for
   it. Read via `Code.fetch_docs/1` (the compiled `Docs` chunk) rather than by reading
   the `.ex` file as a string, so the test asserts on what the module actually publishes
   and cannot be satisfied by a matching comment somewhere else in the file. Whitespace
   is normalised before matching so that re-wrapping a moduledoc paragraph is not a test
   failure, while deleting or weakening the claim is.

### Acceptance criterion 4 — unique index on `idempotency_key`; moduledoc supersession

10. **`uq_event_idempotency_key` exists as a real `CREATE UNIQUE INDEX` on
    `event_idempotency(idempotency_key)` in the tenant schema** — see
    `migrations_test.exs:"the idempotency sidecar carries a real unique index on
    idempotency_key"`.
    *Why it exists:* the criterion's first clause, checked against `pg_indexes` in the
    provisioned schema. `pg_indexes` (not `information_schema.table_constraints`) is the
    right source: Ecto's `create unique_index(...)` emits `CREATE UNIQUE INDEX`, not
    `ALTER TABLE ... ADD CONSTRAINT UNIQUE`, so the constraint views do not list it at
    all and a test written against them would pass vacuously.

11. **Neither `events` nor `events_archive` carries any unique index mentioning
    `idempotency_key`** — see `migrations_test.exs:"neither events nor events_archive
    carries a unique index on idempotency_key — the sidecar is the single enforcement
    point"`.
    *Why it exists:* this is the executable form of the word "supersedes" in the
    criterion. The moduledoc claim (test 13) is prose; this is the structural fact the
    prose describes. Two competing sources of truth for one invariant is the failure
    mode design INV-EV-3 exists to prevent, and R-Co reached the same end state by
    *removing* those two indexes at `1147_par01_events_partitioning.sql`. Without this
    test, someone could "helpfully" add `unique_index(:events, [:idempotency_key])` back
    and every other test here would still pass.

12. **A duplicate `idempotency_key` insert into a provisioned tenant schema is rejected,
    and surfaces as a changeset error rather than a raw `Postgrex` crash** — see
    `migrations_test.exs:"a second row claiming the same idempotency_key is rejected by
    uq_event_idempotency_key"`.
    *Why it exists:* tests 10 and 11 assert the index *exists* and is *unique*; this
    asserts it actually *bites* against real Postgres through the real
    `IdempotencyRecord.insert_changeset/2` path with `prefix:` threaded through, which is
    exactly how REQ-025's append will hit it. It also pins the error *shape*
    (`{:error, changeset}` with `idempotency_key: ["has already been taken"]`), proving
    the `unique_constraint/3` declaration names the right index — a mismatch between the
    declared constraint name and the real index name turns this into an
    `Ecto.ConstraintError` crash instead, which the assertion catches.

13. **`IdempotencyRecord`'s moduledoc states it supersedes `event_store.md`'s Open
    Question #1** — see `schemas_test.exs:"IdempotencyRecord's moduledoc states it
    supersedes event_store.md's Open Question #1 two-phase check"`.
    *Why it exists:* the criterion's second clause, demanded verbatim. Same
    `Code.fetch_docs/1` + whitespace-normalisation approach and same
    weaker-half-of-a-pair framing as test 9 — the structural claim it describes is
    already covered by test 11.

14. **`IdempotencyRecord.insert_changeset/2` declares the `uq_event_idempotency_key`
    unique constraint** — see `schemas_test.exs:"IdempotencyRecord.insert_changeset/2
    declares the uq_event_idempotency_key unique constraint by name"`.
    *Why it exists:* a pure, no-I/O counterpart to test 12 that pins the index *name*
    the changeset is wired to. Test 12 needs a provisioned tenant schema to run; this one
    fails in milliseconds with a precise message if the name drifts, which is where the
    failure is actually easiest to read.

### Acceptance criterion 5 — `instance_projections` scope statement

15. **`InstanceProjection`'s moduledoc states its schema is event-store scope while its
    meaningful population is EE-01/S3 scope** — see `schemas_test.exs:"InstanceProjection's
    moduledoc scopes the schema to the event store and its population to EE-01/S3"`.
    *Why it exists:* this criterion is purely a moduledoc claim — there is no structural
    fact to prefer over it, because "this table's population is somebody else's job" is
    not expressible as a column constraint. So this is the one place where a doc-text
    assertion is the primary evidence rather than the weaker half of a pair, and it is
    used only because the criterion explicitly demands that text. It asserts all three
    load-bearing sentences (schema scope, population scope, and the "do not read this
    migration as instance-engine work landing early" warning) rather than one keyword.

16. **`instance_projections` and `instance_sequence` have `instance_id` as their natural
    primary key, and `instance_projections` carries only the event-store-scope columns**
    — see `migrations_test.exs:"instance_projections and instance_sequence use
    instance_id as their natural primary key"` and case 2's column-set equality.
    *Why it exists:* the structural half of criterion 5's scope boundary. If a future
    change let S3's engine-owned columns (`definition_id`, `correlation_key`,
    `current_nodes`, `variables`, `error_detail`, `completed_at`, `cancelled_at`) leak
    into this migration, the moduledoc claim in test 15 would become false while still
    passing — case 2's exact column-set equality catches exactly that.

17. **`InstanceProjection.terminal?/1` is `true` for `:completed`/`:cancelled` only** —
    see `schemas_test.exs:"terminal?/1 is true for :completed and :cancelled only —
    :error is NOT terminal"`.
    *Why it exists:* design INV-EV-10 and `event_store.md:292` (Key invariant 10) name
    exactly CANCELLED and COMPLETED; treating `:error` as terminal would silently block
    appends to recoverable instances in REQ-025. The function is total over the closed
    status set declared in the `Ecto.Enum`, so the test enumerates the whole set from
    `__schema__(:type, :status)` rather than hand-listing four atoms — a future fifth
    status then fails this test until someone decides deliberately whether it is
    terminal.

### Beyond the five acceptance criteria — carried forward from the gates that passed

18. **Every entry in `tenant_scoped_migrations/0` is a real no-op under a nil prefix
    (`req022-tenant-schema-provisioning.md` §4's guard pattern)** — see
    `migrations_test.exs:"every migration registered in tenant_scoped_migrations/0 creates
    nothing in public when run with no :prefix (§4 guard pattern)"`.
    *Why it exists:* REVIEWER raised this during REQ-022's own Step 2d review and it was
    recorded in `test/specs/REQ-022.md` case 14 as not-yet-writable, because
    `tenant_scoped_migrations/0` returned `[]` — there was nothing to iterate. REQ-023 is
    the first requirement to populate that list, so it becomes writable here, and this is
    the highest-value test in this step: it mechanically enforces §4 for **every future**
    tenant-scoped migration instead of relying on each future ELIXIR-DEV having read the
    design doc. The mechanism matters: each registered module is run through
    `Ecto.Migrator.run/4` with **no `:prefix` option at all** (the exact shape of a plain
    `mix ecto.migrate` bootstrap) under a synthetic, never-before-applied probe version,
    so Migrator genuinely executes `change/0` instead of skipping it as already-applied;
    the test then asserts `public`'s table set is byte-identical to the snapshot taken
    before the run. Asserting the returned version list is what proves the migration ran
    rather than being skipped — without it the test would pass vacuously against a
    already-recorded real version. The test also asserts the manifest is non-empty, so it
    can never silently revert to the vacuous state it was in during REQ-022.

19. **Each manifest entry's version equals the numeric prefix of the file it was loaded
    from, and that file exists** — see `migrations_test.exs:"each registered migration's
    version matches the numeric prefix of the file it was actually loaded from"`.
    *Why it exists:* REVIEWER found this pairing entirely unguarded — the manifest's
    version integer and its filename string are two independent literals, so a
    wrong-but-unique version number (say `20260816120009` next to
    `20260816120001_create_events.exs`) would be caught by nothing: the module still
    loads, `replay_migrations/2` still succeeds, and the version recorded in the tenant's
    `schema_migrations` silently stops corresponding to any real file. The test reads
    `module_info(:compile)[:source]` — the path the module was *actually* loaded from,
    which is the load-bearing fact, not a re-derivation of the filename convention — and
    asserts its basename is `"<version>_<underscored module suffix>.exs"` and that the
    file exists in the priv directory `tenant_scoped_migrations/0` itself resolves
    (`Application.app_dir(:letflow, "priv")`). Versions are additionally asserted unique
    and strictly ascending, matching the manifest's own stated ordering contract.

20. **`event_payload_store`'s composite FK to `events` is `ON DELETE RESTRICT`, and it
    really blocks the delete** — see `migrations_test.exs:"deleting an events row that
    has an event_payload_store row is blocked by ON DELETE RESTRICT (design OQ-2's
    deliberate signal)"`.
    *Why it exists:* REVIEWER explicitly flagged that this restrict-failure must not be
    "fixed" into a CASCADE — it is the *designed* signal for open question OQ-2 (how
    large payloads survive archival), and under CASCADE REQ-026's archive operation would
    silently destroy the side-table payload of every archived large event, leaving
    archived events unreadable (design INV-EV-12). This test **asserts** the restrict
    behaviour and changes nothing, so that a future well-meaning flip to
    `on_delete: :delete_all` fails here loudly rather than being discovered as data loss
    in REQ-026. It also proves the composite FK is wired to both columns, since the
    payload row is inserted with the event's own `(event_id, created_at)` pair.

## Determinism, isolation and cleanup

- **No wall-clock dependence.** Every timestamp used as data is a fixed literal
  (`~U[2026-01-02 03:04:05.000000Z]` and friends), never `DateTime.utc_now/0`. Nothing
  asserts on elapsed time or on "now". The one place a real clock value is read is the
  `Registration.migrations_applied_at` assertion in case 1, which asserts only that the
  field is a `%NaiveDateTime{}` (i.e. was stamped), never a particular value.
- **No unseeded randomness.** Per-test unique values come from `Ecto.UUID.generate/0`
  (unique by construction, never compared against a fixed expectation) and
  `System.unique_integer([:positive, :monotonic])` (a VM counter, not an RNG) — the same
  two mechanisms `identity_test.exs` and `tenant_provisioning_test.exs` already use. No
  test hand-rolls a seed or calls `:rand`.
- **Per-test unique fixtures, no shared hardcoded IDs.** `insert_tenant!/0` generates a
  unique `slug` per call, so each test gets its own tenant, its own
  `tenant_<32 hex>` physical schema and its own `Registration` row. No identifier is
  shared between tests. Fixed literals are used only for values whose *uniqueness is
  irrelevant* and which live inside a schema no other test can see.
- **Every created schema is dropped.** Each `:auto`-mode describe block registers an
  `on_exit/1` that runs `DROP SCHEMA ... CASCADE` for the schema it provisioned and
  deletes its own `tenant_schemas` and `tenants` rows — these tests genuinely commit, so
  transaction rollback does not apply to them. The §4 guard block additionally deletes
  the synthetic probe versions it wrote into `public.schema_migrations`, and drops a
  stray public table only if (a) its name is one of the six event-store table names and
  (b) it was not present in the snapshot taken before that test ran — so the cleanup can
  never destroy pre-existing state, and only ever fires in the failure case the test is
  designed to detect.
- **Self-sufficiency.** No test reads state another test wrote. Every DB-touching test
  provisions everything it needs in its own `setup`, and the pure tests read only
  compiled module metadata.
- **No secrets or connection strings.** No test file contains a hostname, port, username
  or password; all database access goes through `Letflow.Repo`, configured in
  `config/test.exs`.
- **No `@tag :skip`, no `TODO`.** Every test case listed above is runnable and runs.
