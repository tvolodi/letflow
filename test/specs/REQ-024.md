# Test Spec: REQ-024 — Event type registry (registry.zig, ES-05)

**Requirement:** REQ-024 (`docs/requirements.yaml`, stage S2) — port
`src/event_store/registry.zig` (ES-05) as `Letflow.EventStore.Registry`:
`register_type/2`, `validate_payload/3`, `get_type/2`, the `event_type_registry`
migration, and `Letflow.EventStore.Registry.JsonSchema` (a hand-rolled validator
implementing R-Co's own supported keyword subset).

**Requirement's acceptance criteria (verbatim):**
1. "priv/repo/migrations gains an event_type_registry migration (schema-per-tenant
   per REQ-022) applying cleanly"
2. "register_type/2 rejects a second registration with the same (name,
   schema_version) with a distinct, testable error, not a generic changeset failure"
3. "validate_payload/2 against a payload missing a required field returns a failure
   result whose detail names the specific field_path (JSON Pointer form) and
   constraint, not just a boolean false"
4. "get_type/1 against an unregistered name returns an explicit
   :unknown_event_type-shaped error rather than nil or an exception"
5. "the moduledoc names the JSON Schema validation library choice as an explicit
   open question for CODE-DESIGNER, not a silently made decision"

(AC3/AC4's literal arities, `/2` and `/1`, diverge in the shipped code to `/3` and
`/2` respectively — `tenant_id` threading, a real interface decision CODE-DESIGNER
made explicitly at design time, not a silent deviation. See
`lib/letflow/design/req024-event-type-registry.md` section 4 and
`Letflow.EventStore.Registry`'s own moduledoc. Every test below calls the actual
shipped arity.)

**Test tier:** unit + integration. `Letflow.EventStore.Registry.JsonSchema.validate/2`
is pure (no I/O) — tested standalone. `register_type/2`, `validate_payload/3`,
`get_type/2`, and the migration itself all touch `Letflow.Repo` (real Postgres, per
DIRECTIVE T-1 — no mocked database).

## Module/file placement — why two separate test files, one per production module

Checked how existing tests are organized before deciding: this project's established
convention is one test file per top-level module/context
(`identity_test.exs` ↔ `Letflow.Identity`, `role_registry_test.exs` ↔
`Letflow.Identity.RoleRegistry`, matching `test/specs/REQ-020.md`'s own placement
reasoning). `Letflow.EventStore.Registry.JsonSchema` is exactly this shape: a
structurally separate module (`lib/letflow/event_store/registry/json_schema.ex`) with
its own moduledoc, its own zero-I/O contract, and (per the design doc section 2) a
placement rationale distinct from `Registry` itself (nested under `Registry` only
because it currently has exactly one consumer, not because it's the same concern).
Testing it in the same file as the DB-backed `Registry` functions would force the
whole file to carry `Letflow.DataCase`'s Postgres/Sandbox dependency even for
`JsonSchema`'s tests, which need none of it — matching this project's existing
precedent of never mixing a pure validator's tests into a DB-backed context module's
test file.

## `Letflow.EventStore.Registry.JsonSchema.validate/2` — per-keyword coverage
(supports acceptance criterion 3)

Per `lib/letflow/design/req024-event-type-registry.md` section 1.1's keyword table
and `json_schema.ex`'s own moduledoc, the validator supports exactly 8 keyword
families: `type`, `minimum`/`maximum`, `minLength`/`maxLength`, `enum`, `required`,
`properties`, `items`, `additionalProperties` (literal `false` only) — plus the
"unsupported keywords are permitted and inert" contract and RFC 6901 pointer
construction. `json_schema_test.exs` has one describe block per family (mirroring
`graph_test.exs`'s one-describe-per-CHK convention), each with a minimal
failing-example fixture asserting the exact violation list, plus:

- A fully-valid-payload-against-a-combined-schema happy path, and the empty-schema
  `{}` fully-permissive case.
- **`type`**: single-string-type mismatch; type-array (`["string","null"]`) both
  matching and non-matching; all 7 type names round-tripped against their own runtime
  shape; the type-mismatch cascade-avoidance short-circuit (a mismatch stops sibling
  checks at that same level but not sibling subtrees); an unrecognized type-name
  string and a malformed (non-string/non-list) `type` value both treated permissively,
  not raised.
- **`minimum`/`maximum`**: below-minimum, above-maximum, and the `>=`/`<=` (not
  `>`/`<`) boundary cases; non-numeric values guarded, not raised.
- **`minLength`/`maxLength`**: below-minLength, above-maxLength, boundary cases, and
  — the sharpest test in this group — a codepoint-vs-byte-count distinction using
  `"café"` (4 codepoints, 5 UTF-8 bytes) against `maxLength: 4`, which must pass under
  a correct codepoint-based `String.length/1` implementation and would incorrectly
  fail under a byte-count one.
- **`enum`**: value absent from the list, value present, deep-equality (not identity)
  for a map value, and a malformed (non-list) `enum` value treated permissively.
- **`required`**: single missing field with its exact `field_path`; multiple missing
  fields each getting their own violation (not just the first); a present-but-falsy
  field (`false`) not flagged missing; `required` on a non-map value guarded (not
  raised) at a nested level; a malformed (non-list) `required` value treated
  permissively.
- **`properties`**: recursive nested-field violation with a correctly joined
  `field_path`; an absent (non-required) property not recursed into at all; a
  malformed (non-map) `properties` value treated permissively.
- **`items`**: each array element validated against the single subschema with a
  correctly indexed `field_path`; multiple invalid elements each independently
  indexed; tuple-form `items` (a list of subschemas) explicitly NOT implemented
  (matching R-Co); empty array trivially passes.
- **`additionalProperties`**: literal `false` flags unlisted keys; only listed keys
  present produces no violation; the keyword absent entirely means no enforcement;
  `true` or the subschema form are both NOT enforced (only literal `false` is
  implemented, matching R-Co exactly).
- **Unsupported keywords are permitted and inert**: a schema keyword-salad of `$ref`,
  `pattern`, `format`, `allOf`/`anyOf`/`oneOf`/`not`, `patternProperties`,
  `dependencies`, `title`, `description` — a payload that would violate several of
  these IF enforced is accepted, proving they are genuinely inert end-to-end, not just
  "the test happened not to trigger them." A made-up, unknown keyword is also
  silently ignored.
- **RFC 6901 pointer construction**: the document root renders as `"/"` (not `""`);
  a field name containing `~` escapes to `~0`; a field name containing `/` escapes to
  `~1`; nested + indexed pointers (`properties` then `items`) compose correctly.
- **Reports every violation, not just the first** (ES-05's own requirement): a
  3-simultaneous-violation payload returns all 3. The `required`-before-`properties`
  ordering is asserted directly (`hd(failures(result))`) because it is structurally
  guaranteed by `object_violations/3`'s own fixed call order
  (`required_violations ++ properties_violations ++ additional_properties_violations`,
  `json_schema.ex` lines 126-130); the relative order between two different sibling
  keys within the same `"properties"` map is asserted via `MapSet` rather than a
  pinned list order, since that ordering falls out of Elixir `Map` iteration (not a
  list), which is not part of this module's documented contract even though it is, in
  practice, stable on the current BEAM for small maps — see the "Map-iteration-order
  caution" note below.

### Map-iteration-order caution (why some assertions use MapSet, others a strict list)

`json_schema.ex`'s `properties_violations/3` iterates `schema["properties"]` (an
Elixir `Map`, decoded from a schema literal or, in production, from `Jason.decode/1`)
via `Enum.filter/2` + `Enum.flat_map/2`. Elixir's `Map` type does not, by language
specification, guarantee iteration order — the observed order for small maps (stable,
sorted-by-key-term-order on the current BEAM) is an implementation detail, not a
contract `json_schema.ex` itself makes. Tests in this file are therefore careful to
assert on **list order only where the algorithm's actual control flow guarantees it**
(the fixed per-level check sequence: `type` → `enum` → numeric → string → object
[`required` → `properties` → `additionalProperties`] → array; and iteration over
JSON-array-turned-Elixir-`List` values, e.g. `required`'s name list or `items`'
element list, which Elixir `List`s do preserve in order) — and use an
order-independent `MapSet` comparison wherever multiple violations arise from
iterating sibling keys within the same schema `Map`. One test (`"a type mismatch does
not stop sibling subtrees from being checked"`) does assert a specific two-key
`Map`-iteration order (`"a"` before `"b"`) as a **convenience assertion, verified
empirically to hold** (`mix test` run directly, not assumed) rather than a claimed
contract — if this ever becomes a source of flakiness under a future Elixir/OTP
version change, loosening it to a `MapSet` comparison (as the 3-violation test already
does) is the correct fix, not evidence of a real behavioral regression.

## `Letflow.EventStore.Registry` (DB-backed) — `registry_test.exs`

### Sandbox-`:auto`-mode requirement (why this file needs the same treatment as
`tenant_provisioning_test.exs`)

`event_type_registry` is created by a **tenant-scoped** migration (guarded by
`if prefix() do ... end` — it never exists under `public`). It only comes into being
for a given tenant once `Letflow.TenantProvisioning.replay_migrations/2` has actually
run for that tenant's schema, and `replay_migrations/2` internally calls
`Ecto.Migrator.run/4`, which — per the investigation `test/specs/REQ-022.md` already
documents in full (Ecto.Migrator's own moduledoc, empirically reproduced there) —
cannot run inside `Letflow.DataCase`'s normal single-sandboxed-connection transaction.
Every test needing a real, queryable `event_type_registry` table therefore goes
through a shared `provisioned_tenant/1` setup helper (used via `setup
:provisioned_tenant` in each describe block that needs it) that:

1. Switches `Letflow.Repo` to Sandbox `:auto` mode (real, ad hoc, committing
   connections — not rolled back).
2. Inserts a real `Tenant` row.
3. **Registers `on_exit/1` cleanup immediately**, before calling
   `provision_tenant_schema/1`/`replay_migrations/2` — see "A real bug this file's own
   first draft had" below for why this ordering specifically matters.
4. Calls `TenantProvisioning.provision_tenant_schema/1` then
   `TenantProvisioning.replay_migrations/2` (using the real, shipped
   `tenant_scoped_migrations/0` default — not a test-only fixture list, so what's under
   test is the actual production migration path).

`async: false` for the whole module, for the identical reason
`tenant_provisioning_test.exs` is `async: false` — see that file's moduledoc for the
full ExUnit-source-level proof (`async_loop/4`'s draining of all `async: true` modules
before any `async: false` module starts, and strict one-at-a-time execution among
`async: false` modules) that this file relies on rather than re-deriving.

### A genuine functional gap this file hit and worked around (not a shipped-code bug)

Empirically discovered while first running this file (before any workaround): every
test using `provisioned_tenant/1` failed with

```
{:error, {:migration_failed, %Ecto.MigrationError{
  message: "module Letflow.Repo.Migrations.CreateEventTypeRegistry is not an Ecto.Migration"
}}}
```

This is exactly the gap ELIXIR-DEV's own Step 2a handoff already flagged
(`handoffs/WF02-REQ024-20260816/step-02a-elixir-dev.json`, issue 1):
`priv/repo/migrations/*.exs` files are not part of `:test`'s `elixirc_paths`, and
`Ecto.Migrator`'s directory scan only `Code.compile_file/1`'s a migration file when it
decides that specific version still needs to run. Once version `20260816163103` is
recorded in `schema_migrations` (true for any test database that has run
`mix ecto.migrate` even once — the migration's own no-op-under-`public` guard pattern
still lets it "complete" and get recorded), the module
`Letflow.Repo.Migrations.CreateEventTypeRegistry` is never loaded into that `mix test`
run's BEAM VM at all, so `Ecto.Migrator.run/4`'s explicit `[{version, module}]` form
(what `tenant_scoped_migrations/0`, and hence `replay_migrations/2`, actually uses)
fails to resolve the bare module atom.

**Fix applied, mirroring the exact technique ELIXIR-DEV's own handoff already used for
its manual AC1 demonstration** ("Worked around ... via an explicit `Code.require_file/2`
of the migration ... not a change to any shipped file"): `registry_test.exs` explicitly
`Code.require_file/1`s the real migration file (path resolved via `Path.expand/2` from
`__DIR__`, not a hardcoded absolute path) before calling `replay_migrations/2`.
`Code.require_file/1` caches by path, so calling this once per test (many times across
this file's run) is cheap and idempotent — it does not redefine the module on repeat
calls. This is a **test-file-scoped workaround only**; no shipped file (`lib/`,
`priv/`) was touched to make this pass, and the real migration file's real content is
what's exercised — not a stand-in fixture — so `replay_migrations/2`'s actual shipped
default is still what's under test. The underlying gap remains open production risk
(a `:dev`/`:prod` server process calling `replay_migrations/2` for a newly-onboarded
tenant would hit the identical error) — already flagged by ELIXIR-DEV for a future fix
(an Application-boot-time require loop, or switching `replay_migrations/2` to a
directory-scoped `Migrator.run` call); not re-filed as a duplicate issue here, since
it's already visible in `handoffs/WF02-REQ024-20260816/step-02a-elixir-dev.json`'s
`issues` list for ORCH/REVIEWER to route to a follow-up fix.

### A real bug this file's own first draft had, found and fixed during test
development (documented so the fix's reasoning isn't lost)

The first draft of `provisioned_tenant/1` registered its `on_exit/1` cleanup callback
**after** calling `provision_tenant_schema/1` and `replay_migrations/2`. Because
Sandbox `:auto` mode commits real data immediately (no transaction rollback), a
failure in either of those two calls (which is exactly what happened during the
migration-loading gap above, before it was fixed) left a real, committed orphan
`Tenant` row (and, if it got that far, a real orphan schema) in the test database with
no `on_exit/1` ever registered to clean it up. Since `System.unique_integer/1`'s
counter resets per `mix test` invocation (a fresh BEAM VM each run), the *next*
`mix test` run would generate the identical `"req024-N"` slug sequence and collide
with the still-present orphan row from the previous failed run — empirically observed
directly (`Ecto.InvalidChangesetError`, `slug: ["has already been taken"]`) on the
second test run attempt.

**Fix**: `on_exit/1` is now registered immediately after the `Tenant` row itself
commits, before `provision_tenant_schema/1`/`replay_migrations/2` run — so a failure
in either of those later steps still triggers cleanup of whatever got created so far.
`drop_schema!/1`'s `DROP SCHEMA IF EXISTS` and `Repo.delete_all/1`'s zero-matching-rows
case both tolerate "never got that far" cleanly. The orphan data this bug produced
during development was manually cleaned up (a one-off `scratch/`-scoped script,
deleted afterward — matches this project's file-placement convention for one-off
verification scripts) and confirmed clean via a direct
`pg_catalog.pg_namespace`/`tenants` query before any final test run counted here.
**Verified empirically, twice**: ran the full project suite (`mix test`) twice
consecutively after this fix — 234/234 passed both times — then queried
`pg_catalog.pg_namespace` directly for any `tenant_%`-prefixed schema: zero rows,
confirming no orphan Postgres schema survives a run (matching
`tenant_provisioning_test.exs`'s own established double-run-plus-direct-query
verification convention).

## Test cases

### Acceptance criterion 1 — the `event_type_registry` migration

1. **Applies cleanly for a real provisioned tenant: the table exists under the
   tenant's own schema with the expected columns, and does NOT exist under `public`**
   — see `registry_test.exs`, describe `"event_type_registry migration (acceptance
   criterion 1)"`. `provisioned_tenant/1`'s own `replay_migrations/2` call already
   implicitly proves the migration applies cleanly (a migration error would fail
   `setup` itself for every test in scope); this test goes further and confirms the
   specific table/column shape directly via `information_schema`, matching REQ-022's
   own established verification pattern (`tenant_provisioning_test.exs`'s "the
   migration applied cleanly" test). Would fail if the migration were missing,
   misnamed, dropped a required column, or (the tenant-scoping check specifically) if
   the `if prefix() do ... end` guard were removed and the table leaked into `public`.

### Acceptance criterion 2 — `register_type/2`

2. **A new `(name, schema_version)` registration succeeds and is genuinely persisted**
   — re-selected from Postgres directly (not trusting the in-memory reply), matching
   `process_instance_test.exs`'s/`identity_test.exs`'s established persistence-check
   convention.
3. **Registering the exact same `(name, schema_version)` twice returns
   `{:error, :duplicate_event_type_version}`, not a generic changeset failure** — AC2's
   own literal wording, satisfied exactly as specified (sequential, not concurrent —
   see test case 8 below for the concurrent case). Would fail if the pre-check
   (design doc section 4.1 step 4) were removed or returned a bare
   `{:error, %Ecto.Changeset{}}` instead of the distinct atom.
4. **Registering a version lower than the current maximum returns the distinct
   `{:error, :schema_version_not_monotonic}`, not `:duplicate_event_type_version`** —
   a genuine Letflow-specific tightening beyond R-Co (design doc section 4.1's
   callout); this test pins that the two failure modes ("this exact row already
   exists" vs. "this row doesn't exist but is out of order") return genuinely
   different, distinguishable atoms, not the same one.
5. **Registering a strictly greater version than the current maximum succeeds** — the
   positive case paired with test 4, confirming the monotonicity check's boundary
   direction (`>` required, not `>=`/`<`).
6. **Changeset-level rejections**: empty name, name > 128 characters, `schema_version
   == 0`, and an explicit `nil` `json_schema` — each asserted as a genuine
   `%Ecto.Changeset{valid?: false}` with the specific field's error present (via
   `errors_on/1`, matching this project's established changeset-error-inspection
   helper from `tenant_provisioning_test.exs`/`identity_test.exs`). The `json_schema`
   case deliberately uses an **explicit `nil`** rather than `Map.delete/2` — see the
   in-file comment: `EventType`'s field carries `default: %{}` (design doc section 5),
   so omitting the key entirely leaves the struct's own non-nil default in place and
   `validate_required/2` never fires; only an explicit `nil` value actually reaches
   and is caught by `validate_required/2`. A non-map `json_schema` value is asserted
   separately, confirming `Ecto.Type.cast/2` on the `:map` field type subsumes R-Co's
   `InvalidJsonSchema` structural check (design doc section 4.1 step 2's own note),
   with no bespoke atom needed.
7. **A `tenant_id` with no `Registration` row returns `{:error, :tenant_not_provisioned}`,
   no changeset attempted** — rework iteration 1's fix (design doc section 4, the
   arity/tenant-scope-resolution correction). Uses a fresh `Ecto.UUID.generate()`
   directly, no `provisioned_tenant/1` setup needed (mirrors
   `tenant_provisioning_test.exs`'s own "unprovisioned tenant" test, which similarly
   needs no `:auto`-mode treatment since this branch returns before ever reaching a
   second connection).
8. **Beyond AC2's literal (sequential) wording — the DB-level unique-index backstop,
   genuinely exercised under real concurrency**: ELIXIR-DEV's own Step 2a handoff
   explicitly flagged this path as unexercised ("`insert_with_monotonicity_check/2`'s
   DB-level unique-constraint backstop path ... was not exercised by this handoff's
   manual demonstration ... Flagging for TEST-DESIGNER at Step 3 to consider a
   concurrency-race test if practical"). This test forces two concurrent
   `register_type/2` calls, for the **identical** `(name, schema_version)`, to both
   pass a barrier (mirroring `identity_test.exs`'s own `provision_oidc_user/3`
   concurrent-race test pattern: both tasks `send(parent, {:ready, self()})` then
   block on a `:go` message, released only after both have announced readiness) before
   either calls `register_type/2` — maximizing the chance both read
   `current_max == 0` before either commits, so **only the table's own
   `unique_index(:event_type_registry, [:name, :schema_version])` — not the
   application-level pre-check, which both calls pass — decides the winner**. Unlike
   `identity_test.exs`'s version (which needs `Sandbox.allow/3` to share the parent's
   single connection under `:shared` mode), this test runs under `:auto` mode (already
   active via `provisioned_tenant/1`), so each spawned `Task` gets its own real,
   independent Postgres connection automatically — genuine concurrency, no explicit
   connection-sharing plumbing needed. Asserts: exactly one task got `{:ok, %EventType{}}`,
   the other got exactly `{:error, :duplicate_event_type_version}` (never a raw,
   leaked `%Ecto.Changeset{}` — proving `unique_violation?/2`'s constraint-name
   matching works under a genuine race, not just the sequential pre-check path), and a
   direct Postgres `COUNT(*)` confirms exactly one row exists afterward regardless of
   which task "won". **Verified stable, not flaky**: ran this test file with 5
   different `--seed` values consecutively — 28/28 passed every time (see "Test
   execution evidence" below).

### Acceptance criterion 3 — `validate_payload/3`

`Letflow.EventStore.Registry.JsonSchema`'s own per-keyword behavior is exhaustively
covered independently (see above) — these DB-backed tests exist to prove
`validate_payload/3`'s own wiring (event-type lookup by name/tenant, JSON decoding,
the root-level malformed/non-object short-circuit), not to re-derive every keyword.

9. **A payload missing a required field returns a failure naming the specific
   `field_path` (JSON Pointer) and constraint** — AC3's own literal wording, satisfied
   exactly as specified: `%ValidationFailure{field_path: "/order_id", constraint:
   "required"}`, not a boolean.
10. **`minLength`, `enum`, and `type`-mismatch violations each produce their own
    distinct constraint name** — 3 further keyword examples via the real DB-backed
    path (name lookup → schema fetch → `JsonSchema.validate/2` → error wrapping),
    confirming the wiring, not re-testing the keywords' internal logic (already
    exhaustive in `json_schema_test.exs`).
11. **An unsupported-but-inert keyword (`$ref` and `pattern` together) present in a
    registered schema does not cause a payload that would otherwise violate `pattern`
    (if enforced) to be rejected** — the "permitted and inert" contract demonstrated
    end-to-end through the real DB-backed path, not just inside the pure validator in
    isolation (which `json_schema_test.exs` already covers more exhaustively for every
    inert keyword).
12. **A fully valid payload against a well-formed, real registered schema returns
    `:ok`** — the DB-backed happy path.
13. **Malformed (non-parseable) JSON** is reported as `field_path: "/"`,
    `constraint: "type"`, `actual:` the raw payload string — design doc section 4.2
    step 1's collapsed structural-guard + malformed-JSON-fallback case.
14. **Syntactically valid JSON that decodes to a non-object root (a JSON array)** is
    reported identically (`field_path: "/"`, `constraint: "type"`) — the "payload must
    always be a JSON object" platform invariant, enforced in `Registry` (not
    `JsonSchema`), matching R-Co's own module boundary exactly (design doc section
    4.2's note).
15. **An unregistered event type returns `{:error, :unknown_event_type}`**, propagated
    unchanged from `get_type/2`'s own error (ES-05: unregistered event types are
    always rejected).
16. **Validates against the most recently registered `schema_version`, not an earlier
    one** — registers v1 (permissive) then v2 (requires a field v1 doesn't), and
    confirms an empty payload is rejected against v2's constraint, not silently
    accepted under v1's schema — proving `validate_payload/3` genuinely uses the
    `ORDER BY schema_version DESC LIMIT 1` row, matching R-Co's actual real behavior
    (design doc section 4.2's own note that R-Co has no exact-version parameter
    either).
17. **A `tenant_id` with no `Registration` row returns `{:error, :tenant_not_provisioned}`**
    — rework iteration 1's fix, propagated through `validate_payload/3`'s internal
    `get_type/2` delegation (design doc section 4's "does not duplicate this lookup
    itself" note) rather than a second, independent resolution.

### Acceptance criterion 4 — `get_type/2`

18. **An unregistered name returns `{:error, :unknown_event_type}` — never `nil`,
    never an exception** — AC4's own literal wording. Both an explicit
    `refute match?(nil, ...)` and the positive `{:error, :unknown_event_type}`
    assertion are present, so this would fail equally whether the implementation
    regressed to returning bare `nil` or started raising instead.
19. **A registered name with a single version returns that version.**
20. **A registered name with multiple versions returns the highest `schema_version`**
    — registers `1`, `2`, `5` in strictly increasing order (monotonicity is enforced —
    see test 4/5 above; version registration order must itself be increasing), proving
    "highest" means numerically highest, not "most recently inserted" or "row count."
21. **A `tenant_id` with no `Registration` row returns `{:error, :tenant_not_provisioned}`**
    — rework iteration 1's fix, `get_type/2`'s own direct resolution step (design doc
    section 4.3 step 1), not delegated from elsewhere.
22. **Tenant isolation**: an event type registered for one tenant's schema is
    genuinely invisible to a second, independently provisioned tenant
    (`{:error, :unknown_event_type}` from tenant B's own `get_type/2` call, while
    tenant A's own call still resolves it) — beyond the bare acceptance criteria, but
    directly confirms the schema-per-tenant mechanism (AC1) is actually doing its job
    for reads, not just for the migration's own table-existence check.
