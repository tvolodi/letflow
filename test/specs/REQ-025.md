# Test Spec: REQ-025 — Event append (`Letflow.EventStore.append/2`)

**Requirement:** REQ-025 (`docs/requirements.yaml` lines 1042–1099, stage S2,
`depends_on: [REQ-023, REQ-024]`) — verbatim acceptance criteria:

1. "appending to a terminated instance (status CANCELLED or COMPLETED in
   instance_projections) returns an error and writes zero rows across all
   five involved tables, demonstrated by an actual test or iex session
   against a real Postgres, not just described"
2. "two concurrent appends to the same instance_id never receive the same
   sequence_number -- demonstrated with an actual concurrent test (e.g.
   Task.async_stream racing two appends) or, if concurrency can't be
   exercised in this environment, the FOR UPDATE-equivalent locking code
   path is cited explicitly"
3. "appending twice with the same idempotency_key returns is_duplicate: true
   on the second call and does not insert a second events row, verified
   against the idempotency sidecar table REQ-023 defines"
4. "a payload that fails REQ-024's validate_payload/2 results in zero rows
   written to events, instance_sequence, or instance_projections -- no
   partial state"
5. "a payload over 4096 bytes is split into events.payload's $ref pointer
   form plus an event_payload_store row, verified by reading both rows back
   after append"
6. "every row append/1(2) writes (events, instance_sequence,
   instance_projections, the idempotency sidecar) has tenant_id equal to the
   tenant whose schema the write targeted, derived internally -- not equal
   to a caller-supplied tenant_id when the two are deliberately made to
   disagree in a test, which must fail loudly (not silently attribute to the
   wrong tenant) rather than succeed"

**Plus a 7th, load-bearing case** introduced by REVIEWER's Step 2d ruling on
the design doc's OQ-5 (`lib/letflow/design/req025-event-append.md` §9,
§6.2.1 M1): `append/2` never originates an `instance_projections` row — a
missing row for the target `instance_id` is a distinct failure,
`{:error, :instance_not_started}`, not folded into the terminated-instance
case. Not literally one of the 6 numbered criteria above, but explicitly
called out by the design doc and ELIXIR-DEV's shipped code
(`lib/letflow/event_store.ex`'s `active_instance_guard/3`) as new,
REVIEWER-expected behavior.

**Test tier:** unit+integration (real Postgres via `Letflow.DataCase`, no
mocked DB per `docs/guides/test_developer_guide.md` DIRECTIVE T-1).

## Fixture strategy — read this before the test cases below

Per the design doc's §9 OQ-5 resolution and §11's closing paragraph:
`append/2` is update-only for `instance_projections` — it **never** creates
that row. **Every test below that needs `append/2` to reach its transactional
phase pre-seeds the target instance's `instance_projections` row via a direct
`Repo.insert(prefix: schema_name)` in test setup, never via `append/2`
itself.** This is the REVIEWER-confirmed test strategy named in the design
doc §6.2.1's own text ("a test fixture's direct `Repo.insert` against
`instance_projections`, bypassing `append/2` entirely").

Each test provisions its own tenant (real `CREATE SCHEMA` + real
`tenant_scoped_migrations/0` replay, mirroring
`test/letflow/event_store/registry_test.exs`'s and
`test/letflow/tenant_provisioning_test.exs`'s established
`provisioned_tenant/1` pattern) — every test therefore starts from a
genuinely empty schema, so "zero rows in table X" assertions below check the
whole table under that tenant's prefix, not a per-instance filter.

## Test cases

1. **AC1 — terminated instance, both `:completed` and `:cancelled`** — see
   `test/letflow/event_store_test.exs` `"terminated instance (AC1)"` describe
   block. Proves `active_instance_guard/3`'s terminal-status branch aborts
   the whole `Multi` before any write: `events`/`instance_sequence`/
   `event_idempotency`/`event_payload_store` all stay at 0 rows, and the
   pre-seeded `instance_projections` row is provably untouched (same
   `last_event_seq`/`updated_at` before and after), not just "still exists."

2. **AC2 — concurrent appends never collide on `sequence_number`** — see
   `"concurrent appends (AC2)"`. Two real, concurrently-running `Task`s call
   `append/2` against the identical pre-seeded `instance_id`, each with its
   own distinct `idempotency_key` (so neither collapses into the other via
   the idempotency path, which would make the sequence-number assertion
   vacuous). Exercises the real `SELECT ... FOR UPDATE`-equivalent lock in
   `lock_and_increment_sequence/3` (design doc §6.2.2) against genuine lock
   contention, not a hand-wave — this environment does have a working
   Postgres + `Task`, so the design doc's citation-only fallback isn't
   needed. Asserts both calls succeed, their `sequence_number`s differ, and
   exactly 2 `events` rows exist afterward.

3. **AC3 — duplicate `idempotency_key`** — see `"idempotency (AC3)"`. Same
   `idempotency_key` reused on a second `append/2` call returns
   `is_duplicate: true` and the **same** `event_id`/`sequence_number` as the
   first call; exactly one `events` row and one `event_idempotency` row exist
   afterward (proving M3's "zero net rows anywhere on a duplicate," a
   strictly stronger property than AC3's literal "no second events row").

4. **AC4 — payload fails `Registry.validate_payload/3`** — see `"invalid
   payload (AC4)"`. A payload missing a JSON-Schema-required field is
   rejected with `{:error, {:payload_validation_failed, _}}`. This path runs
   entirely in the pre-transaction phase (design doc §6.1 P4, before
   `Repo.transaction/2` is ever called) — no `instance_projections` row is
   pre-seeded for this test at all, which is itself part of what the test
   proves: a Registry failure never even reaches M1's guard, so
   `:instance_not_started` never fires here even though no row exists.
   Confirms 0 rows in all five tables.

5. **AC5 — oversized payload (> 4096 bytes)** — see `"oversized payload
   (AC5)"`. A payload whose raw byte length exceeds 4096 is stored as
   `events.payload == %{"$ref" => event_id}`, with the real payload +
   original `byte_size` in a matching `event_payload_store` row, read back
   directly from Postgres (not trusted from the in-memory reply).

6. **AC6 — tenant_id derivation and isolation**, three sub-cases (see
   `"tenant_id (AC6)"`):
   a. `events` and `instance_projections` rows carry `tenant_id` equal to
      the tenant the append's `:prefix` resolves to (computed independently
      via `Letflow.TenantProvisioning.tenant_id_for_schema_name/1` in the
      test, not merely re-asserting the value the fixture itself chose).
   b. `instance_sequence` and `event_idempotency` (which the shipped schema
      confirms carry **no** `tenant_id` column at all — design doc §9 OQ-1)
      are instead checked for schema-prefix reachability: a row created
      under tenant A's `:prefix` is readable via `Repo.get(..., prefix:
      schema_a)` and **not** readable via the identical query against a
      second, genuinely-provisioned tenant B's `:prefix` — a real
      cross-tenant isolation check, not merely "the row exists somewhere."
   c. `attrs` carrying a caller-supplied `:tenant_id` key that disagrees
      with the target schema's own tenant is rejected outright with
      `{:error, :tenant_id_not_accepted}` — not silently stripped, not
      silently honored — and writes zero rows anywhere (this rejection runs
      at design doc §6.1 P0, before anything else).

7. **`:instance_not_started` (load-bearing, beyond the 6 numbered ACs)** —
   see `"instance_not_started (new failure mode)"`. Calling `append/2`
   against an `instance_id` with no pre-existing `instance_projections` row
   returns `{:error, :instance_not_started}` (a distinct tag from
   `:instance_terminated`) and writes zero rows anywhere.
