# Test Spec: REQ-026 — Event read paths, archive, and platform sentinels

**Requirement:** REQ-026 (`docs/requirements.yaml`, stage S2, `depends_on: [REQ-025]`)
— verbatim acceptance criteria:

1. "read/2 against an instance with N appended events (via REQ-025) returns exactly
   those N events in ascending sequence_number order, with any large payload
   transparently resolved from event_payload_store"
2. "read/2 against an instance_id with no events returns an explicit not-found error,
   not an empty list"
3. "read_global/1 with after_global_seq set returns only events with a strictly
   greater global_seq, demonstrated across at least two instances' interleaved events"
4. "calling archive/1 twice in a row moves the same rows the first time and zero
   additional rows the second time (idempotent), verified by row counts before/after
   each call"
5. "event_retention_policies exists (via this requirement's own migration) with
   columns id/event_type(unique)/policy(default keep_forever)/keep_days/keep_count/
   created_at/updated_at and the
   chk_retention_policy/chk_keep_days/chk_keep_count CHECK constraints, matching
   R-Co's 003_event_archive.sql shape"
6. "archive/1 against an event_type with an explicit event_retention_policies row
   uses that policy's keep_days/keep_count instead of the global retention_days
   fallback, demonstrated with a policy row that would move a different set of rows
   than the global default would"
7. "the three platform sentinel constants exist and are accessible from the context
   module, each documented as citing src/event_store/platform.zig"

**Plus, per this run's own briefing** (not one of the 7 numbered criteria, but
explicitly named as load-bearing coverage): the flip side of criterion 2 — an
instance that DID have events but had them all archived must return a legitimate
`{:ok, []}`, not `:instance_not_found` (design doc §4.2's own stated reason this case
is real, not vacuous); `up_to_sequence` taking precedence over `up_to_timestamp` when
both are given (ES-06); `read_global/1`'s limit clamping (`0` → default 100, values
outside `1..1000` clamped); `archive/1` never touching
`instance_projections`/`instance_sequence` (INV-AR-2); and the
`event_payload_store` `ON DELETE RESTRICT` ordering — `archive/1` must delete the
payload sidecar row before the `events` row for an event with an externalized
payload, or the delete raises `Ecto.ConstraintError`.

**Test tier:** unit+integration (real Postgres via `Letflow.DataCase`, no mocked DB
per `docs/guides/test_developer_guide.md` DIRECTIVE T-1).

**Design doc:** `lib/letflow/design/req026-event-read-archive-platform-sentinels.md`.
**Implementation:** `lib/letflow/event_store.ex` (extended),
`lib/letflow/event_store/retention_policy.ex` (new),
`priv/repo/migrations/20260817181240_create_event_retention_policies.exs` (new).

## File split

Acceptance criteria 1–4, 6, 7 plus the extra coverage above live in
`test/letflow/event_store_test.exs` (extending REQ-025's existing file, same module —
`read/2`/`read_global/1`/`point_in_time/3`/`archive/1`/the sentinels all live on
`Letflow.EventStore`, the same module `append/2` does). Acceptance criterion 5 (the
`event_retention_policies` table/schema/CHECK-constraint shape itself) lives in a new
file, `test/letflow/event_store/retention_policy_test.exs`, mirroring the existing
`schemas_test.exs`/`migrations_test.exs` split for REQ-023's six tables and, more
directly, `test/letflow/definitions/pack_update_migration_test.exs`'s precedent for a
**GLOBAL** table's own test file (`event_retention_policies` is GLOBAL, design doc
§6 — no `:prefix`, one row per `event_type` platform-wide).

## Fixture strategy — read this before the test cases below

Continues `event_store_test.exs`'s existing pattern (`provisioned_tenant/1`: real
`CREATE SCHEMA` + tenant-scoped migration replay, Sandbox `:auto` mode because
`Ecto.Migrator` needs a second real connection the DataCase sandbox can't hand out).

**New for REQ-026:** several tests need events with a `created_at` in the
deliberate past — `append/2` always stamps `DateTime.utc_now()`, and no test in this
project may depend on wall-clock time (`docs/guides/test_developer_guide.md`
principle 3), so waiting for a real event to "age" is not an option. Those tests
seed `Event`/`InstanceSequence` rows **directly** via `Event.insert_changeset/2` /
`InstanceSequence.insert_changeset/2` + `Repo.insert!/2`, bypassing `append/2`
entirely — the same direct-seeding idiom `migrations_test.exs`'s own `ON DELETE
RESTRICT` test already uses, and the same idiom the design doc §8.5 explicitly
names as the intended test-seeding strategy for `RetentionPolicy` rows (no
CRUD/management API is built by this requirement — `insert_changeset/2` is the only
public write surface). `seed_event!/7`, `seed_instance_sequence!/3`,
`seed_stored_payload!/4`, and `seed_retention_policy!/1` in `event_store_test.exs`
are that idiom, factored out for reuse. `seed_retention_policy!/1` registers its own
`on_exit/1` cleanup, since `event_retention_policies` is GLOBAL and this file's
tests run under Sandbox `:auto` mode (a real commit, not the ordinary rolled-back
transaction).

`retention_policy_test.exs` needs none of this: `event_retention_policies` is
created by the ordinary `mix ecto.migrate --quiet` step `mix test`'s own alias
already runs, so that file uses the perfectly ordinary `Letflow.DataCase` sandboxed
transaction, `async: true` — every row is rolled back automatically.

Choosing a "past enough to be archive-eligible relative to whenever the test
happens to run" timestamp (the AC6 `keep_days` narrower-than-global test) uses a
relative offset from `DateTime.utc_now()` computed once at the start of that test
and used immediately — this is not a wall-clock *dependency* (nothing sleeps, no
assertion's pass/fail depends on how much real time elapses during the test run);
it is a deterministic fixture-construction step, necessary because `archive/1`'s
own eligibility predicate is itself relative to "now" by design. Every other test
below uses a fixed absolute literal (`~U[2020-01-01 00:00:00.000000Z]` and similar),
matching this project's established convention
(`test/letflow/event_store/schemas_test.exs`'s `@fixed_created_at`).

## Test cases

### Acceptance criterion 1 — `read/2` returns exactly N events, ascending order, `$ref` resolved

1. `"3 events appended via append/2 (one with an oversized payload) are all returned, in order, with the oversized payload resolved"`
   (`event_store_test.exs`, describe `"read/2 returns exactly N appended events, ascending sequence_number, $ref resolved (AC1)"`)
   — proves the primary path: N real `append/2` calls (the criterion's own literal
   "via REQ-025" wording), one of them an oversized (>4096-byte) payload split into
   `$ref` form. Asserts `read/2` returns exactly 3 events, in the exact
   `sequence_number` order they were assigned, and the oversized event's payload
   comes back as the real resolved map, never `%{"$ref" => _}`.

2. `"rows inserted out of sequence_number order are still returned ascending -- proves a real ORDER BY"`
   — a deliberately stronger, complementary case: since `append/2`'s own sequence
   assignment is monotonically increasing per call, test 1 alone cannot distinguish
   "the query has a real `ORDER BY sequence_number ASC`" from "rows happened to come
   back in insertion order." This test seeds 3 events directly with
   `sequence_number` `3, 1, 2` (in that literal insertion order) and asserts `read/2`
   still returns `[1, 2, 3]` — would fail immediately if the `ORDER BY` clause were
   ever dropped.

### Acceptance criterion 2 — not-found vs. legitimately-empty

3. `"an instance_id with no instance_sequence row (never appended to) returns {:error, :instance_not_found}, never {:ok, []}"`
   (describe `"read/2: not-found vs. legitimately-empty (AC2)"`) — the criterion's
   literal case.

4. `"an instance that had events, now fully archived, returns {:ok, []} -- NOT :instance_not_found"`
   — the flip side this run's briefing calls out explicitly, and the design doc §4.2
   itself states is the reason a two-step lookup (existence check, then the real
   read) is mandatory rather than a stylistic choice: seeds one event, archives it
   (via a real `archive/1` call, not a hand-wave), confirms the `events` row is gone
   but the `instance_sequence` row survives (INV-AR-2), and asserts `read/2` returns
   `{:ok, []}` — proving these two "zero results" cases are genuinely distinguished,
   not silently collapsed into one.

### Acceptance criterion 3 — `read_global/1` strict `after_global_seq` lower bound, interleaved instances

5. `"events from two instances, appended interleaved (A1 B1 A2 B2), filter to exactly the strictly-greater-global_seq subset"`
   (describe `"read_global/1: after_global_seq strict lower bound, interleaved instances (AC3)"`)
   — appends `A1, B1, A2, B2` (alternating instances), confirms an unfiltered
   `read_global/1` call returns all four in that exact `global_seq` order (proving
   ordering is global, not per-instance), then confirms
   `after_global_seq: A1's global_seq` returns exactly `[B1, A2, B2]` — the *strictly*
   greater subset, with an explicit `refute` that `A1` itself leaks back in (guards
   against an off-by-one `>=` bug).

### Acceptance criterion 4 — `archive/1` idempotency

6. `"3 eligible events: first call moves all 3, second call (immediately after) moves 0"`
   (describe `"archive/1 idempotency (AC4)"`) — seeds 3 old events, asserts
   `events`/`events_archive` row counts before either call (3/0), after the first
   call (`moved_count: 3`, counts 0/3), and after an immediate second call
   (`moved_count: 0`, counts unchanged at 0/3) — the criterion's literal "verified by
   row counts before/after each call."

### Acceptance criterion 6 — an explicit policy row overrides the global fallback

7. `"a keep_forever policy on one event_type excludes it from an archive/1 call that would otherwise (via the global fallback) have archived it too"`
   (describe `"archive/1 honors an explicit event_retention_policies row over the global fallback (AC6)"`)
   — two old events of two different `event_type`s; a `keep_forever` policy row for
   only one of them. `archive/1` with a global `retention_days` that would (absent
   the policy) have archived both moves exactly 1 row — the policy'd type survives.

8. `"contrast: the same two-event-type setup with NO policy row moves both -- proving the policy row above genuinely changed the eligible set"`
   — the same two-event-type age/fallback setup as test 7, with **no** policy row at
   all: `archive/1` moves both (`moved_count: 2`). Exists specifically so test 7's
   `moved_count: 1` reads as "the policy changed the outcome," not "this fallback
   configuration happens to only ever archive 1 row regardless" — the acceptance
   criterion's own "a different set of rows than the global default would" clause,
   made explicit as its own assertion rather than left implicit.

9. `"a keep_days policy narrower than the global fallback archives its event_type sooner than the global default would"`
   — the inverse direction: an event 10 days old, global `retention_days: 30` (which
   alone would NOT archive it), but a `keep_days: 5` policy row for its type (which
   DOES make it eligible) — `archive/1` moves it. Demonstrates a policy can widen
   eligibility, not just narrow it, matching design doc §7.1 rule 2's literal
   "eligible iff created_at < now - keep_days days (that row's OWN keep_days, not
   the global retention_days parameter)."

### Acceptance criterion 7 — platform sentinel constants

10. `"platform_instance_id/0, platform_actor_id/0, platform_tenant_id/0 are accessible, valid UUIDs, and pairwise distinct"`
    (describe `"platform sentinel constants (AC7)"`) — all three are callable public
    functions (not private module attributes, per design doc §3's own "accessible,
    not raw module attributes" framing), each a syntactically valid `Ecto.UUID`, and
    pairwise distinct.

11. `"each accessor's own @doc cites src/event_store/platform.zig"`
    — reads the compiled `Docs` chunk via `Code.fetch_docs/1` (never the `.ex` file
    as a string, so it asserts on what the module actually publishes, matching
    `schemas_test.exs`'s established idiom) and asserts each of the three accessors'
    published `@doc` text contains the literal string `"src/event_store/platform.zig"`
    — the criterion's own "each documented as citing src/event_store/platform.zig."

### Extra coverage — `up_to_sequence` precedence over `up_to_timestamp` (ES-06)

12. `"an up_to_timestamp far in the past that would (if applied) exclude every event is silently ignored once up_to_sequence is also given"`
    (describe `"read/2: up_to_sequence takes precedence over up_to_timestamp when both given (ES-06)"`)
    — a deliberately adversarial case: `up_to_timestamp` set to a date decades before
    any real event, which if actually ANDed in (or if it wrongly won) would return
    `[]`. Getting `[seq1, seq2]` back instead is only possible if `up_to_sequence`
    won outright, per design doc §4.3's "wins outright, not additionally ANDed in."

13. `"point_in_time/3 does not strip a caller-supplied up_to_sequence -- the ordinary precedence rule still applies"`
    — `point_in_time/3` called with both a far-future `timestamp` (which alone would
    include everything) and an explicit `up_to_sequence`; asserts the narrower
    `up_to_sequence` filter still applies, per design doc §4.5's "opts` here still
    accepts `up_to_sequence` (not stripped)."

### Extra coverage — `read_global/1` limit clamping (design §5.2)

14. `"limit: 0 defaults to 100, NOT a literal LIMIT 0 (which would return zero rows)"`
    (describe `"read_global/1 limit clamping (design §5.2)"`) — a strong test: a raw
    SQL `LIMIT 0` returns exactly zero rows, so getting all 3 seeded events back
    directly disproves "0 passed through literally" and proves it was actually
    replaced with a default ≥3 (per design doc §5.2, 100).

15. `"a negative limit is clamped to the floor of 1, not passed through as a literal negative LIMIT"`
    — 3 events seeded, `limit: -5` returns exactly 1 event with `has_more: true` —
    proves the floor-of-1 clamp (a literal negative `LIMIT` would raise a Postgres
    error, never silently return 1 row, so this also proves the clamp runs before
    the query, not that Postgres happened to tolerate the raw value).

16. `"a limit far above 1000 does not error and returns only the events that exist"`
    — `limit: 5000` against 3 events returns exactly 3, `has_more: false`. A lighter
    smoke test than 14/15 (proving the exact 1000 ceiling would need >1000 seeded
    rows, disproportionate to what any acceptance criterion requires — flagged, not
    silently skipped: this is the one clamp direction this spec does not pin to the
    exact boundary value).

### Extra coverage — `archive/1` never touches `instance_projections`/`instance_sequence` (INV-AR-2)

17. `"an archive/1 call that moves a row leaves instance_projections and instance_sequence provably untouched"`
    (describe `"archive/1 never touches instance_projections or instance_sequence (INV-AR-2)"`)
    — captures both rows' full contents before an `archive/1` call that genuinely
    moves a row, and asserts byte-for-byte struct equality afterward (not just "still
    exists" — a changed `updated_at` would be a real, if narrow, violation this
    catches that a mere row-count check would not).

### Extra coverage — `event_payload_store` `ON DELETE RESTRICT` ordering (design §7.3 phase 2)

18. `"an event with an externalized ($ref) payload archives cleanly (no FK violation), archived payload is fully resolved"`
    (describe `"archive/1 deletes event_payload_store before events (ON DELETE RESTRICT ordering, design §7.3 phase 2)"`)
    — seeds an event whose `payload` is a `$ref` pointer plus its matching
    `event_payload_store` sidecar row (mirroring `append/2`'s real oversized-payload
    shape), then calls `archive/1`. `event_payload_store`'s FK to `events` is
    `ON DELETE RESTRICT` (`20260816120004_create_event_payload_store.exs`) — if
    `archive/1`'s phase 2 ever deleted the `events` row before the sidecar row, this
    call would raise `Ecto.ConstraintError` instead of succeeding. Also asserts the
    archived row's payload is the fully-resolved map, never a `$ref` pointer
    (design INV-AR-3/§7.4's OQ-2 resolution).

### Acceptance criterion 5 — `event_retention_policies` table/schema/CHECK constraints

All in `test/letflow/event_store/retention_policy_test.exs`:

19. `"event_retention_policies exists under the public schema"` /
    `"its real column set matches exactly: id, event_type, policy, keep_days, keep_count, created_at, updated_at"` /
    `"the schema module's field list agrees with the real column set"` /
    `"the schema module pins no @schema_prefix -- GLOBAL, not per-tenant (design §6)"`
    (describe `"acceptance criterion 5 -- table existence and column shape"`) — the
    table exists, its real (information_schema-derived) column set matches the
    criterion's literal list exactly (not a subset), the schema module's own field
    list agrees (so a schema/migration drift is caught, same idiom as
    `migrations_test.exs`'s "column set matches Ecto.Schema module's field list
    exactly" test), and no compile-time `@schema_prefix` is pinned (GLOBAL, design §6).

20. `"a second row for the same event_type is rejected by uq_retention_policy_event_type"` /
    `"two different event_type rows both insert cleanly"`
    (describe `"acceptance criterion 5 -- event_type uniqueness"`) — the criterion's
    literal "event_type (unique)," exercised against real Postgres through the real
    `insert_changeset/2` + `unique_constraint/3` path (proves the declared
    constraint name and the real index name agree — a drift between them would raise
    `Ecto.ConstraintError` instead of returning `{:error, changeset}`, the same
    "declared vs. real name" idiom `migrations_test.exs`'s idempotency-key test uses).

21. `"insert_changeset/2 with no :policy key produces a changeset whose data already carries :keep_forever (struct-level default), and it persists that value"` /
    `"the DATABASE column itself defaults to 'keep_forever' -- a raw insert that omits policy entirely still reads back keep_forever"`
    (describe `"acceptance criterion 5 -- policy defaults to keep_forever"`) — two
    independent halves of "default keep_forever": the `Ecto.Schema` struct default
    (what every ordinary insert through this codebase's own changeset sees), and the
    migration's own `default: "keep_forever"` DDL (a raw SQL `INSERT` that
    specifies no `policy` column at all, bypassing the struct/changeset default
    entirely — the only way to prove the DB-level default independently of the
    app-level one).

22. `"policy=keep_days with keep_days=nil is rejected by chk_keep_days"` /
    `"policy=keep_forever with keep_days set is rejected by chk_keep_days"` /
    `"policy=keep_days with a positive keep_days and no keep_count inserts cleanly"` /
    `"policy=keep_days with a non-positive keep_days is rejected at the app layer already (validate_number/3), never reaching the DB"`
    (describe `"acceptance criterion 5 -- chk_keep_days"`) — the exact case this
    run's briefing names ("policy=keep_days with keep_days=null"), its mirror-image
    (a policy value that must have `keep_days` NULL but doesn't), the valid baseline,
    and confirmation that the app-level `validate_number/3` check (redundant by
    design, per design doc §8.3) catches the "present but non-positive" sub-case
    before it would even reach the DB constraint.

23. `"policy=keep_count with keep_count=nil is rejected by chk_keep_count"` /
    `"policy=keep_forever with keep_count set is rejected by chk_keep_count"` /
    `"policy=keep_count with a positive keep_count and no keep_days inserts cleanly"`
    (describe `"acceptance criterion 5 -- chk_keep_count"`) — the `keep_count`
    mirror of test 22's three DB-level cases (this run's other named example:
    "keep_count set when policy=keep_forever").

24. `"an invalid policy string bypassing Ecto.Enum (raw SQL) is rejected by chk_retention_policy"` /
    `"keep_forever with both keep_days and keep_count NULL inserts cleanly (the baseline valid shape)"`
    (describe `"acceptance criterion 5 -- chk_retention_policy"`) — since
    `Ecto.Enum` already refuses any atom outside the three legal values at the
    changeset layer, the only way to reach `chk_retention_policy` itself is a raw
    SQL insert bypassing the schema entirely — this test does exactly that and
    asserts the real Postgres error message names `chk_retention_policy` by name.

25. `"RetentionPolicy's own public API is exactly insert_changeset/2"`
    (describe `"no update/delete API is built by this requirement (design §8.5)"`)
    — structural guard, same idiom as `schemas_test.exs`'s equivalent test for
    `Event`/`ArchivedEvent`/etc: no update or delete function exists on this module,
    matching design doc §8.5's explicit statement that a CRUD/management API is a
    later requirement's scope, not this one's.
