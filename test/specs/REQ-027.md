# Test Spec: REQ-027 — Definition core schema (`process_definitions` + `instance_definition_snapshots`)

**Requirement:** REQ-027 (`docs/requirements.yaml`, stage S2) — add the two core
definition tables R-Co's `src/design/definition.md` documents, as
`priv/repo/migrations/` migrations plus `Ecto.Schema` modules, using REQ-022's
schema-per-tenant `:prefix` mechanism.

**Requirement's acceptance criteria (verbatim from `docs/requirements.yaml`):**

1. "priv/repo/migrations gains process_definitions and instance_definition_snapshots
   migrations, both schema-per-tenant via REQ-022's :prefix mechanism, applying cleanly"
2. "process_definitions has a unique index on (name, version) and a partial unique index
   on name WHERE status = 'active'"
3. "process_definitions has a nullable stage column and a partial index on stage WHERE
   stage IS NOT NULL, per definition.md's PD-07 section
   (migrations/014_definition_stage.sql)"
4. "instance_definition_snapshots.definition_id references process_definitions.id with no
   ON DELETE CASCADE, and the moduledoc states this is deliberate per PD-08"
5. "both Ecto.Schema modules' @moduledoc cite R-Co src/design/definition.md
   (PD-01/PD-07/PD-08 sections) as the ported source"

**Test tier:** unit + integration. The `Ecto.Schema` modules' changesets, enum mappings
and moduledocs are pure (no I/O) and tested standalone; the migrations, indexes,
index predicates, column nullability, column defaults and the foreign key's referential
action are asserted against **real Postgres** (DIRECTIVE T-1 — no mocked database), read
back out of the live system catalog after REQ-022's provision-then-replay mechanism has
applied both migrations into a real per-test tenant schema.

divert (REQ-013's `mix.exs` alias). Nothing here is verified by "run the command and
quote the output"; every criterion is a structural fact of a live schema.

## Files

- `test/letflow/definitions/schemas_test.exs` — **new file**. Pure, `async: true`, no
  `Letflow.Repo` and no `Ecto.Adapters.SQL.Sandbox` dependency anywhere in it: it reads
  only compiled module metadata (`__schema__/1`, `__info__/1`, `Ecto.Enum` reflection)
  and the compiled `Docs` chunk via `Code.fetch_docs/1`. Matches
  `test/letflow/event_store/schemas_test.exs`'s established shape for REQ-023, and
  `test/letflow/definitions/graph_test.exs`'s for REQ-028.
- `test/letflow/definitions/migrations_test.exs` — **new file**. DB-touching,
  `async: false`, `use Letflow.DataCase`. Matches
  `test/letflow/event_store/migrations_test.exs` exactly, including the reason it cannot
  run inside DataCase's rolled-back sandbox transaction: `Ecto.Migrator` needs a second
  genuinely independent connection (it locks `schema_migrations`), which a sandboxed pool
  will not hand out, so these describe blocks switch the sandbox to `:auto` and clean up
  in `on_exit/1` instead of relying on rollback.
- `test/letflow/event_store/migrations_test.exs` — **modified, one attribute + one line**,
  per Step 2d carry-forward (c). See "Carry-forward (c)" below. No assertion in that file
  is changed.

### Why `async: true` on one file and `async: false` on the other

`docs/issues/ISS-0011.yaml` records a pre-existing flake caused by an `async: true`
module attaching a **global** `:telemetry` handler. `schemas_test.exs` attaches no
telemetry handler and issues zero `Repo` calls, so it cannot repeat that mistake;
`migrations_test.exs` genuinely commits to a shared database and is `async: false` for
the whole module (ExUnit's `async` setting is module-wide), which is what makes the
`:auto`-mode switch safe.

### Cleanup discipline (the database is shared)

Every test that creates a tenant schema registers its `on_exit/1` cleanup **before** the
work that could fail, so the schema, its `Registration` row and its `Tenant` row are
dropped on the failure path as well as the passing one. No test creates anything in
`public`.

## Test cases

### Acceptance criterion 1 — both migrations, schema-per-tenant via `:prefix`, applying cleanly

1. **`replay_migrations/2` applies both REQ-027 migrations and both tables land in the
   tenant's own schema** —
   `migrations_test.exs`: *"replay_migrations/2 applies both REQ-027 migrations and both
   definition tables land in the tenant's own schema"*.
   "Applying cleanly" is asserted as `{:ok, versions}` from the real replay, not as an
   absence of exceptions. The companion guarantee — that neither REQ-027 table lands in
   `public` — is **not** owned by this test: under `TenantProvisioning.replay_migrations/2`,
   `Ecto.Migration.__prefix__/1` sets each table's runtime prefix from the migrator's own
   `:prefix` option regardless of what the migration's own `prefix: prefix()` calls
   declare, so a `refute table_exists_in_schema?("public", table)` assertion in this
   describe block could never observe a failure and was removed (ISS-0029/GH#87) rather
   than kept as false coverage. The real, load-bearing owner of the `:prefix`-guard
   property is `test/letflow/event_store/migrations_test.exs`'s section-4 guard test,
   *"every migration registered in tenant_scoped_migrations/0 creates nothing in public
   when run with no :prefix (§4 guard pattern)"* (~line 484): it runs each registered
   migration with **no** `:prefix` at all — the one condition under which the guard can
   actually fail — and asserts `public` gains nothing.
2. **Both migrations are registered in `tenant_scoped_migrations/0`** —
   `migrations_test.exs`: *"tenant_scoped_migrations/0 registers both REQ-027 definition
   migrations"*. REQ-022 §4 makes registration and guarding two independent mandatory
   halves: a guarded-but-unregistered migration is inert forever (no tenant schema ever
   gets the table) and no other test in this file would notice, because they all run
   through `replay_migrations/2` which only ever sees registered migrations.
3. **Each table's real column set equals its `Ecto.Schema` module's field list** —
   `migrations_test.exs`: *"each definition table's real column set in the tenant schema
   matches its Ecto.Schema module's field list exactly"*. "Applies cleanly" is necessary
   but not sufficient: a migration can apply cleanly and still disagree with the module
   that reads it, which surfaces much later as a runtime `Postgrex` error in REQ-030 /
   REQ-033. Equality, not subset — an extra column on either side is drift too.
4. **Neither schema module pins a compile-time `@schema_prefix`** —
   `schemas_test.exs`: *"neither definition schema module pins a compile-time
   @schema_prefix (design INV-DEF-7)"*. A compile-time prefix would defeat the
   per-tenant mechanism criterion 1 is about, and would do so silently: every test that
   passes `prefix:` explicitly would still pass.

### Acceptance criterion 2 — unique index on `(name, version)` **and** partial unique index on `name WHERE status = 'active'`

5. **`uq_definition_version` is a real UNIQUE index over exactly `(name, version)`, in
   that order, and carries no `WHERE` clause** — `migrations_test.exs`: *"uq_definition_version
   is a total UNIQUE index over exactly (name, version)"*. Read from `pg_indexes`, not
   from `information_schema.table_constraints`: Ecto emits `CREATE UNIQUE INDEX` rather
   than `ALTER TABLE ... ADD CONSTRAINT`, so the constraint views do not list it at all
   and a test written against them would pass vacuously. The "no `WHERE`" half matters
   because a partial variant of this index would enforce a strictly weaker rule while
   still being named and still being unique.
6. **A duplicate `(name, version)` insert is rejected, as `{:error, changeset}` and not as
   a raised `Ecto.ConstraintError`** — `migrations_test.exs`: *"a second definition with
   the same (name, version) is rejected by uq_definition_version"*. Asserts the index
   actually bites through the real `create_changeset/2` path with `:prefix` threaded
   through. The error *shape* is part of the assertion: if the changeset's declared
   constraint name and the real index name ever drift apart, this raises instead of
   returning a changeset, and REQ-030's error contract silently breaks.
7. **`uq_active_definition` is a real UNIQUE index over exactly `(name)` whose predicate
   names `status` and the literal the enum actually dumps** — `migrations_test.exs`:
   *"uq_active_definition is a PARTIAL unique index over (name) whose predicate matches
   the literal Ecto.Enum actually dumps for :active"*. See "Carry-forward (a)" below —
   this is the load-bearing half.
8. **Behavioural: a second `active` definition with the same name is rejected by
   `uq_active_definition`** — `migrations_test.exs`: *"a second definition activated under
   a name that already has an active definition is rejected by uq_active_definition
   (PD-03)"*.
9. **Discriminator: two `draft` definitions sharing a name coexist** — same test as 8.
   Without this the partial index would be indistinguishable from a total unique index on
   `name`, and a test suite that only checked "duplicates are rejected" would pass against
   the wrong index entirely.
10. **Both changesets declare both unique constraints by index name** —
    `schemas_test.exs`: *"create_changeset/2 and update_changeset/2 both declare
    uq_definition_version and uq_active_definition by index name"*. Fails in milliseconds
    with a precise message where test 6 fails end-to-end against Postgres.

### Acceptance criterion 3 — nullable `stage` column **and** partial index on `stage WHERE stage IS NOT NULL`

11. **`stage` is physically nullable in the live catalog, and an omitted stage really
    lands as SQL `NULL`** — `migrations_test.exs`: *"stage is a nullable column and an
    omitted stage lands as SQL NULL, which is what idx_def_stage's predicate depends on"*.
    Both halves are needed: `is_nullable = 'YES'` is the criterion's literal wording, and
    the round-trip through a real insert is what proves `idx_def_stage`'s
    `WHERE stage IS NOT NULL` predicate is meaningful rather than matching every row.
12. **`idx_def_stage` exists, is a **non-unique** partial index over exactly `(stage)`,
    and its predicate is `stage IS NOT NULL`** — `migrations_test.exs`: *"idx_def_stage is
    a non-unique PARTIAL index over (stage) predicated on stage IS NOT NULL"*. The
    non-unique half is asserted explicitly: a unique index here would silently forbid two
    definitions sharing a stage label, which PD-07 (open-ended free-text labels)
    explicitly permits.
13. **`stage` is optional at the schema layer and carries no enum/allowed-value
    validation** — `schemas_test.exs`: *"stage is castable, optional on both changesets,
    and validated only for length — no enum, per PD-07"*. PD-07's "no enum validation is
    applied (stage labels are open-ended text)" is a claim about behaviour, so it is
    asserted by feeding an arbitrary label through the changeset and requiring it to be
    accepted, not by reading the source.

### Acceptance criterion 4 — FK to `process_definitions.id` with **no** `ON DELETE CASCADE`, deliberate per PD-08

14. **`pg_constraint.confdeltype` for the FK is `'a'` (NO ACTION), not `'c'` (CASCADE)** —
    `migrations_test.exs`: *"the snapshot FK's referential action in the live catalog is
    NO ACTION ('a'), not CASCADE ('c')"*. See "Carry-forward (a)" below — this is the
    other load-bearing half. The same test pins the constraint's name, its referencing
    column, its referenced table (in the tenant's own schema) and its referenced column,
    so "the FK exists at all and points where PD-08 says" cannot be assumed.
15. **Behavioural: deleting a referenced definition is rejected and the snapshot survives
    intact** — `migrations_test.exs`: *"deleting a definition that has a snapshot row is
    rejected, and the snapshot survives with its captured graph (PD-08)"*. Under CASCADE
    this delete would succeed and destroy exactly the rows the table exists to preserve.
    Per Step 2d carry-forward (e), this test asserts the **rejection** — the designed
    PD-08 behaviour — and changes nothing; `on_delete: :nothing` is not to be "fixed" into
    a CASCADE.
16. **A dangling `definition_id` is rejected as `{:error, changeset}`** —
    `migrations_test.exs`: *"a snapshot referencing a nonexistent definition is rejected as
    {:error, changeset}, not a raised error"*. Proves the FK exists and that the name the
    changeset declares matches Ecto's real default constraint name, which is what lets
    REQ-033 return `DefinitionNotFound` rather than crashing.
17. **The snapshot moduledoc states the absence is deliberate per PD-08** —
    `schemas_test.exs`: *"InstanceDefinitionSnapshot's moduledoc states the missing ON
    DELETE CASCADE is deliberate per PD-08"*. Read through `Code.fetch_docs/1`, so it
    asserts on what the module actually publishes — a matching sentence in an ordinary
    `#` comment elsewhere in the file would not satisfy it.
18. **The snapshot module exposes no update or delete path (write-once, INV-DEF-6)** —
    `schemas_test.exs`: *"InstanceDefinitionSnapshot's own public API is exactly
    create_changeset/2"*, with `ProcessDefinition`'s two-function API asserted alongside as
    the negative control that proves the assertion discriminates.

### Acceptance criterion 5 — both moduledocs cite `definition.md` (PD-01/PD-07/PD-08)

19. **Both moduledocs cite `src/design/definition.md` and all three named sections** —
    `schemas_test.exs`: *"both definition schema modules' moduledocs cite R-Co's
    src/design/definition.md and its PD-01, PD-07 and PD-08 sections"*. Asserted via
    `Code.fetch_docs/1` on the compiled `Docs` chunk, not by grepping the `.ex` file as a
    string. Deliberately pattern-matches the "documented" shape, so a module whose
    moduledoc was deleted (`:none`) or hidden (`:hidden`) raises rather than passing

20. **Both moduledocs carry the requirement's explicitly mandated scope note** —
    `schemas_test.exs`: *"both moduledocs carry REQ-027's mandated 'schema only' scope

## Carry-forward instructions from Steps 1b, 2c and 2d

### (a) Two silent-correctness invariants converted into exit-code gates

Both of these would ship **green** if wrong. Neither is observable from a passing suite
that does not specifically look for it.

**(a.1) The FK's referential action.** `on_delete: :nothing` emits *no* `ON DELETE`
clause at all, so nothing in the DDL text says "NO ACTION" and nothing in
`information_schema` distinguishes it from a cascade without being asked. Test 14
therefore reads `pg_constraint.confdeltype` from the live catalog and asserts it is the
byte `'a'`, with an explicit companion assertion that it is not `'c'`, so a failure reads
against the criterion's own wording. Observed ground truth from a real replay into a
provisioned schema:

```
["instance_definition_snapshots_definition_id_fkey", "f", "a", "a",
 "<tenant_schema>.process_definitions", "definition_id", "id"]
```

**(a.2) The partial unique index's predicate, and the enum case it depends on.** PD-03's
single-active-per-name invariant lives entirely in `uq_active_definition`'s
`WHERE status = 'active'` predicate. If the `Ecto.Enum` ever dumped a different case than
that literal — e.g. R-Co's own uppercase `ACTIVE`, which the sibling
`Letflow.EventStore.InstanceProjection` really does use — the index would match **zero
rows**, PD-03 would be silently unenforced, every existing test would still pass, and
nothing would raise. Test 7 closes this three ways:

- it reads `pg_indexes.indexdef` and asserts the predicate really is present and really
  names `status`;
- it derives the expected literal from `Ecto.Enum.mappings(ProcessDefinition, :status)`
  rather than hard-coding `'active'`, so a case change on **either** side — enum or
  migration — fails the assertion. Postgres renders the predicate as
  `WHERE ((status)::text = 'active'::text)`, so the assertion is made against the
  extracted predicate substring rather than the criterion's literal SQL fragment;
- test 8 is the behavioural companion: two `draft` rows sharing a name coexist, the first
  is activated by the guarded single-statement `UPDATE` REQ-030 will use, and activating
  the second is rejected by a `:unique_violation` whose `constraint` field is asserted to
  be exactly `"uq_active_definition"`. Under a zero-row-matching index that second update
  would simply **succeed**, which is precisely the silent failure being gated.

`schemas_test.exs` carries the pure half: `Ecto.Enum.dump_values/2` for `:status` is
`["draft", "active", "deprecated", "archived"]` and every dumped value equals its own
`String.downcase/1`.

### (b) The `graph` default is written twice as independent literals

`priv/repo/migrations/20260816193001_create_process_definitions.exs:82` and
`lib/letflow/definitions/process_definition.ex:98` each spell out
`%{"nodes" => [], "edges" => []}` independently, with nothing keeping them in sync — the
same hazard class as (a). *"the DB column default for graph and the schema module's
struct default are the same value"* in `migrations_test.exs` inserts a row by raw SQL
that omits `graph` entirely (so the **database** default is what fills the column), reads
it back through `Letflow.Definitions.ProcessDefinition`, and asserts it equals
`%Letflow.Definitions.ProcessDefinition{}.graph`. It also asserts the column has a
default at all, so "both sides are empty" cannot pass vacuously. The struct-side literal
is pinned independently in `schemas_test.exs`.

### (c) `test/letflow/event_store/migrations_test.exs`'s §4 guard-test cleanup extended

That test runs every migration returned by `tenant_scoped_migrations/0` with **no**
`:prefix` and asserts nothing appears in `public`. Its assertion coverage is already
complete for REQ-027 — it iterates the manifest, which now returns nine entries including
REQ-027's two — but its `on_exit/1` defensive cleanup only knew the six event-store table
names, so a REQ-027 guard regression would leave a stray `public.process_definitions`
and `public.instance_definition_snapshots` behind in a database shared with a
concurrently running worktree. A `@later_tenant_scoped_tables` attribute now adds those
two names to the cleanup list. In the passing case this is a no-op, because a correctly
guarded migration creates nothing in `public` at all. **No assertion in that file was
changed.**

### (d) The migration files were not reformatted

`mix format --check-formatted` fails on the two migration files for ISS-0016's reason
alone: `.formatter.exs` excludes `priv/repo/migrations/**`, and the parentheses
`mix format` would add to the `add`/`create` calls are *less* idiomatic than the shipped
house style. The project gate exits 0 as-is. This step touched neither migration.

### (e) `on_delete: :nothing` was not flipped to CASCADE

The delete rejection **is** the designed PD-08 behaviour, and ISS-0024 records that
REQ-033's own acceptance-criterion wording invites exactly this mistake. Test 15 asserts
the rejection; it changes nothing. No test in this run modifies a migration or a schema
module.

## Determinism and isolation

- **No wall-clock dependence.** Every timestamp in both files is a fixed literal
  (`~U[2026-01-02 03:04:05.000000Z]`, `~N[2026-01-02 03:04:05.000000]`). No
  `DateTime.utc_now/0` anywhere.
- **No unseeded randomness.** Uniqueness comes from `Ecto.UUID.generate/0` and
  `System.unique_integer([:positive, :monotonic])` — a VM counter, not an RNG and not a
  clock.
- **Per-test unique fixtures.** Every DB-touching test gets its own `Tenant`, its own
  physical Postgres schema and its own `Registration` row; no identifier, name or id is
  shared between tests.
- **Self-sufficient.** No test depends on another having run first. The pure file has no
  shared mutable state at all.
- **No hardcoded secrets or connection strings.** Both files reach the database only
  through `Letflow.Repo`, which reads `config/test.exs`.
- **No `@tag :skip`, no `TODO`.**
