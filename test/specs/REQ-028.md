# Test Spec: REQ-028 — Graph structural validator (graph.zig, PD-02)

**Requirement:** REQ-028 (`docs/requirements.yaml`, stage S2) — port
`src/definition/graph.zig`'s `validateGraph()` as a pure Letflow function
(`Letflow.Definitions.Graph.validate_graph/1`), implementing all 8 named
structural checks (CHK-01..CHK-08, 9 distinct violation codes since CHK-01
produces 2), per `lib/letflow/design/req028-graph-structural-validator.md`
(the gate-approved design this implementation follows).

**Requirement's acceptance criteria (verbatim):**
1. "a graph satisfying all 8 checks returns {valid: true, violations: []}"
2. "each of the 8 named checks (CHK-01 through CHK-08) has at least one
   explicit failing-example test demonstrating its specific violation code is
   returned, not just a generic invalid-graph test"
3. "a graph violating 3 of the 8 checks simultaneously returns all 3
   violations in one call, not just the first encountered (Key invariant 5)"
4. "a cycle that passes through an EXCLUSIVE_GATEWAY or PARALLEL_GATEWAY node
   is explicitly permitted (not flagged as CYCLE_WITHOUT_GATEWAY), and a
   self-loop is explicitly rejected, each with its own test"
5. "the function signature and its call sites confirm zero Repo/database
   calls anywhere in its call graph"

**Test tier:** unit only. `Letflow.Definitions.Graph.validate_graph/1` and its
entire call graph are pure functions over plain structs — no `Letflow.Repo`,
no I/O of any kind (moduledoc §"Purity (AC5)", design doc §8/§10). This is a
simpler, faster test suite than REQ-022's (no `Letflow.DataCase`, no
`Ecto.Sandbox`, no Postgres).

## Scope test

Real application-executable Elixir logic: `lib/letflow/definitions/graph.ex`
(new module — `Letflow.Definitions.Graph` struct, `Node`/`Edge`/`Violation`
nested structs, `validate_graph/1`, and 8 private check functions plus the
DFS cycle-detection helper). Not docs-only, not build-config. Full
TEST-DESIGN-VALIDATOR / TEST-RUNNER chain applies.

## Test cases

### Acceptance criterion 1 — a fully valid graph

1. **A realistic, 5-node, 5-edge graph (START → HUMAN_TASK → EXCLUSIVE_GATEWAY
   → {SERVICE_TASK → END, back to HUMAN_TASK}) returns exactly `{valid: true,
   violations: []}`** — see `graph_test.exs:"a realistic, multi-node,
   multi-edge, fully valid graph returns valid: true, violations: []"`. Hand
   traced against the actual DFS algorithm (design doc §6.3) before writing:
   the gateway-routed back-edge `n3 → n2` is a genuine cycle (n2 is on
   `on_stack` when the DFS reaches it via n3), permitted because `n3` is an
   `EXCLUSIVE_GATEWAY`; every node satisfies its type's connectivity rule
   (§5's CHK-04 detail). Would fail if any of the 8 checks had a false
   positive on a genuinely well-formed graph (e.g. an off-by-one in the
   isolated-node connectivity computation, or the gateway exemption not
   actually suppressing the cycle violation).

### Acceptance criterion 2 — each of the 9 violation codes, isolated

Every fixture below is deliberately minimal and constructed so that **only**
the named check fires — hand-traced against the actual DFS/connectivity
algorithms in `lib/letflow/design/req028-graph-structural-validator.md` §5/§6
before being written, not guessed and then patched until green. Each
assertion checks the exact `codes(result)` list (not just "violations is
non-empty"), so a test would fail both if the code were wrong AND if any
unexpected extra violation appeared.

2. **CHK-01, `:missing_start_node`** — see `graph_test.exs:"zero START nodes
   -> :missing_start_node, and only that code"`. Zero START nodes; an
   `EXCLUSIVE_GATEWAY` ↔ `END` cycle (permitted, since a gateway is one of the
   two endpoints) keeps CHK-06 clean, and the mutual edge gives both nodes
   their required connectivity, keeping CHK-04 clean. Would fail if the
   `count == 0` branch of `check_start_node/1`'s `cond` were removed or
   miswired.
3. **CHK-01, `:multiple_start_nodes`** — see `graph_test.exs:"more than one
   START node -> :multiple_start_nodes, and only that code"`. Two START
   nodes, each independently satisfying its own outgoing-edge requirement to
   a shared END. Also asserts the exact message text (`"Found 2 START nodes;
   exactly one is required"`), pinning the count interpolation. Would fail if
   the `count > 1` branch were dropped, or if `:missing_start_node` fired
   instead (it wouldn't, since `count == 0` is false here — this test also
   indirectly confirms the two `cond` branches don't both fire).
4. **CHK-02, `:missing_end_node`** — see `graph_test.exs:"zero END nodes ->
   :missing_end_node, and only that code"`. START → HUMAN_TASK ↔
   EXCLUSIVE_GATEWAY, no END anywhere; the HUMAN_TASK/GATEWAY back-edge is
   permitted (gateway endpoint) so CHK-06 stays clean. Would fail if
   `check_end_node/1`'s `Enum.any?` check were inverted or removed.
5. **CHK-03, `:dangling_edge`** — see `graph_test.exs:"an edge whose target
   matches no node id -> :dangling_edge, and only that code"`. A valid
   `n1 → n2` edge alone already satisfies START's outgoing and END's incoming
   requirements; a second edge's dangling target (`"ghost"`, matching no real
   node) is the only defect. Also asserts the exact message text, pinning the
   "target" wording (vs. the sibling "source" wording CHK-03 also supports
   per design doc §5, not separately exercised here since both share one
   violation code and one code path shape). Would fail if the target-existence
   `MapSet.member?` check were dropped or inverted.
6. **CHK-04, `:isolated_node`** — see `graph_test.exs:"a node with zero edges
   -> :isolated_node, and only that code"`. A HUMAN_TASK node with literally
   zero edges referencing it, while START/END satisfy their own connectivity
   entirely via a separate edge. Would fail if the "other node type needs both
   incoming and outgoing" branch of `check_isolated_nodes/1`'s `case` were
   dropped or its logic inverted.
7. **CHK-05, `:duplicate_node_id`, alongside the unavoidable companion
   `:isolated_node`** — see `graph_test.exs:"a repeated node id ->
   :duplicate_node_id, alongside the unavoidable companion :isolated_node"`.
   **This fixture is not "impure" by oversight — it is provably the true
   minimal violation set for CHK-05 under this algorithm**, reasoned through
   explicitly here rather than silently forced to look clean:

   Design doc §6.1 point 1 / §7.2 states node-id → index resolution is
   **first-match-wins** (`Map.put_new/3` over an indexed fold, porting
   `graph.zig`'s own `nodeIndex`/`nodeExists` linear-scan-first-match
   semantics). Consequently, **any** edge naming a duplicated id always
   resolves to the *first* occurrence — the second (higher-index) occurrence
   structurally can never receive incoming/outgoing edge attribution via its
   own shared id, regardless of node type. Every one of the 7 node types
   requires at least one side of connectivity (START needs outgoing, END
   needs incoming, every other type needs both — design doc §5's CHK-04
   detail) — so the second occurrence of *any* duplicated id is therefore
   *always* also flagged `:isolated_node`, for every possible node-type
   choice. Every alternative construction was hand-traced before settling on
   this one (see "CHK-05 fixture-design exploration" below) and each one
   independently confirmed the same unavoidable companion violation, or
   introduced additional unwanted violations (a spurious cycle, or a second
   `:isolated_node` for the first occurrence too) — this fixture is the
   genuinely minimal one.

   Fixture: `n1` (id `"x"`, `START`, the first/only-reachable occurrence of
   `"x"`), `n2` (id `"x"`, `END`, the unreachable duplicate), `n3` (id `"y"`,
   `END`, existing only so the one edge has somewhere real to point besides
   `"x"`, and independently satisfying CHK-02's "at least one END" — which
   `n2` would also have satisfied, since CHK-02 counts by `node_type`, not
   `id`). One edge, `"x" → "y"`. Traced: `node_index = {"x" => 0, "y" => 2}`;
   `n1` (index 0) gets its required outgoing via the edge; `n3` (index 2) gets
   its required incoming; `n2` (index 1, the duplicate) gets neither and is
   flagged isolated. `check_duplicate_node_ids/1` flags index 1 against its
   earlier match at index 0. No cycle (the single edge is acyclic). Exactly 2
   violation codes, in fixed check order (`:duplicate_node_id` from CHK-05 at
   check-list position 3, `:isolated_node` from CHK-04 at position 7). Also
   asserts the exact `:duplicate_node_id` message text (`"Duplicate node ID
   'x'"`). Would fail if the "compare against every earlier node" scan in
   `check_duplicate_node_ids/1` were broken (e.g. comparing against all nodes
   instead of only earlier ones, which would double-count), or if the
   first-match-wins `node_index` construction were changed to
   last-match-wins (which would silently swap which occurrence gets the
   isolated flag, not eliminate it).

8. **CHK-06, `:cycle_without_gateway`** — see `graph_test.exs:"a 2-node cycle
   between two non-gateway nodes -> :cycle_without_gateway, and only that
   code"`. `START → HUMAN_TASK ↔ SERVICE_TASK → END`; the `HUMAN_TASK ↔
   SERVICE_TASK` back-edge involves neither endpoint being a gateway type, so
   it's rejected. Every node's connectivity requirement is independently
   satisfied by the 4 edges present, so nothing else fires. Would fail if the
   gateway-exemption check in `dfs_visit/6`'s back-edge branch were inverted
   (permitting non-gateway cycles) or if the back-edge detection itself
   (`MapSet.member?(on_stack, v)`) were broken.
9. **CHK-07, `:node_limit_exceeded`** — see `graph_test.exs:"501 nodes,
   otherwise a fully-connected acyclic chain -> :node_limit_exceeded, and
   only that code"`. A 501-node linear chain (`start → m1 → m2 → ... → m499 →
   end`, generated programmatically by `linear_chain_graph/1`) — every
   middle node has exactly one incoming and one outgoing edge, START has
   outgoing, END has incoming, no cycle, no duplicate ids, no dangling edges,
   500 edges (well under the 2000 edge limit). Also asserts the exact message
   text (`"Node count 501 exceeds the maximum of 500"`). Would fail if
   `@max_nodes` were changed, or if the `count > @max_nodes` comparison used
   the wrong operator (`>=` would flag exactly 500 as a false positive,
   independently distinguishable from this test since this fixture uses 501,
   one past the boundary — this test targets the code being returned at all,
   not the exact boundary; the boundary itself is not separately tested here,
   which is a deliberate scope choice — REQ-028's own acceptance criteria
   name the *code*, not the exact off-by-one boundary).
10. **CHK-08, `:edge_limit_exceeded`** — see `graph_test.exs:"2001 parallel
    edges between 2 otherwise-valid nodes -> :edge_limit_exceeded, and only
    that code"`. 2 nodes (`START`, `END`), 2001 identical parallel edges
    between them (generated by `many_parallel_edges_graph/1`). Duplicate
    edges between the same pair are harmless to every other check — CHK-03/04
    only care about existence, and CHK-06's DFS visits the target node once
    regardless of how many parallel edges point to it (subsequent identical
    edges hit the "already visited, not on stack" cross/forward-edge branch,
    not a new back-edge), confirmed by hand-tracing the DFS over the repeated
    successor list before writing this fixture. Also asserts the exact
    message text. Would fail if `@max_edges` were changed or the comparison
    operator were wrong.

### Acceptance criterion 3 — 3 simultaneous violations, one call

11. **A graph with no START, no END, and a 2-node non-gateway cycle returns
    all 3 violation codes together, in the fixed check order, not just the
    first encountered** — see `graph_test.exs:"a graph violating 3 checks at
    once returns all 3 violation codes, in fixed check order"`. `HUMAN_TASK ↔
    SERVICE_TASK`, both nodes independently fully connected via the 2-edge
    cycle, no START, no END anywhere. Asserts **both** the exact ordered list
    (`[:missing_start_node, :missing_end_node, :cycle_without_gateway]`,
    exploiting the fixed check-order guarantee from design doc §7.1 for a
    stronger check than an unordered comparison would give) **and**
    (redundantly, for a second, order-independent view) the `MapSet` equality
    of the same 3 codes, **and** `length(result.violations) == 3` to rule out
    any unexpected 4th violation. Design doc §7.2 explicitly proves these 3
    checks are independent of each other's outcome — none needs another to
    "clean up" the input first — so a correct implementation genuinely can
    (and must) report all 3 at once. **Empirically verified this test is
    load-bearing, not vacuous** — see "Mutation test" below.

### Acceptance criterion 4 — gateway cycles permitted; self-loops on
non-gateway nodes rejected; self-loop-on-gateway corollary locked in

12. **A cycle through a `PARALLEL_GATEWAY` node is explicitly permitted** —
    see `graph_test.exs:"a cycle passing through a PARALLEL_GATEWAY node is
    explicitly permitted"`. Deliberately uses `PARALLEL_GATEWAY` (not
    `EXCLUSIVE_GATEWAY`, already exercised by AC1's clean-graph fixture and
    test case 2's `:missing_start_node` fixture) so both members of
    `@gateway_types` are independently proven to trigger the exemption, not
    just one hardcoded atom. Asserts the **full** result is `{valid: true,
    violations: []}` — not merely "no `:cycle_without_gateway` present" —
    proving the cycle is genuinely permitted and the graph is otherwise
    entirely clean, not that the cycle violation happened to be masked by
    some other unrelated defect. Would fail if the gateway-exemption
    `MapSet.member?(gateway_set, u) or MapSet.member?(gateway_set, v)` check
    only tested one of the two atoms in `@gateway_types`, or tested neither.
13. **A self-loop on a non-gateway node (`HUMAN_TASK`) is explicitly
    rejected** — see `graph_test.exs:"a self-loop on a non-gateway node is
    explicitly rejected"`. `START → HUMAN_TASK`, `HUMAN_TASK → HUMAN_TASK`
    (self-loop), `HUMAN_TASK → END`. The self-loop edge alone provides both
    the incoming and outgoing connectivity credit HUMAN_TASK needs (it is its
    own source and target), so CHK-04 stays clean and the only violation is
    the self-loop cycle itself. Also asserts the message names the same node
    on both sides (`"node 'h' to node 'h'"`), pinning that this is genuinely
    the `u == v` self-loop case in `dfs_visit/6`'s back-edge branch, not a
    coincidental 2-node cycle. This is the literal test REQ-028's acceptance
    criterion 4 names.
14. **A self-loop ON an `EXCLUSIVE_GATEWAY` node is accepted — the non-obvious
    corollary, locked in as a regression test** — see `graph_test.exs:"a
    self-loop ON an EXCLUSIVE_GATEWAY node is accepted (design doc §6.4
    corollary, not a self-loop special case)"`. Design doc §6.4 states this
    explicitly: `dfs_visit/6` has **no distinct "self-loop" rule** — a
    self-loop is simply the back-edge case where `u == v`, so the identical
    "either endpoint is a gateway" test applies whether or not the two
    endpoints happen to be the same node; this falls directly out of the
    ported algorithm, not a new behavior invented for this test. This is
    flagged in the design specifically because it's a non-obvious corollary
    no other acceptance criterion exercises — worth a standing regression
    test now that ELIXIR-DEV and REVIEWER already discussed it explicitly
    (rather than leaving it as a one-off demo-script observation with nothing
    to catch a future accidental "fix" that special-cased self-loops
    unconditionally). Asserts the full clean result (`{valid: true,
    violations: []}`), same rigor as test case 12.

### Beyond REQ-028's bare acceptance criteria — REVIEWER's Step 2d suggestion

15. **A node whose only edge is dangling on the far end produces BOTH
    `:dangling_edge` (CHK-03) and `:isolated_node` (CHK-04) in the same
    call** — see `graph_test.exs:"a node's sole edge dangling on its target
    produces both :dangling_edge and :isolated_node"`. Not itself one of
    REQ-028's 4 numbered acceptance criteria — added per REVIEWER's Step 2d
    non-blocking note (`handoffs/WF02-REQ028-20260816/step-03-test-designer.json`
    `task.description`) that this traced-but-implicit interaction (design doc
    §5's CHK-04 detail: "a dangling edge contributes no connectivity to
    either side") is a real design decision worth locking in explicitly, not
    just left as an inference from reading the code. Fixture: `s → fin`
    entirely satisfies START/END connectivity on its own; `h`'s *only* edge
    (`h → "ghost"`) has a dangling target, so — per `check_isolated_nodes/1`'s
    `with {:ok, source_idx} <- ..., {:ok, target_idx} <- ... else :error ->
    {outgoing, incoming}` structure — `h` receives **neither** outgoing credit
    (despite being the edge's valid `source`) **nor** incoming credit,
    because the `with` short-circuits on the target's failed resolution before
    crediting anything. Asserts the exact 2-code ordered list
    (`[:dangling_edge, :isolated_node]`, CHK-03 at check-list position 6, CHK-04
    at position 7). Would fail if `check_isolated_nodes/1` were changed to
    credit a dangling edge's *valid* endpoint even when the other endpoint is
    dangling (a plausible-looking "fix" that would actually contradict the
    design's own documented semantics).

## CHK-05 fixture-design exploration (why test case 7's shape is the true minimum)

Before settling on test case 7's 3-node/1-edge fixture, several alternative
constructions were hand-traced and rejected, each for a concrete, reasoned
cause — recorded here so a future reader doesn't re-derive the same dead ends:

- **Two nodes sharing an id, zero edges at all:** both occurrences end up
  isolated (the first occurrence *also* gets no edge credit with zero edges
  present) — 2 `:isolated_node` violations instead of 1, plus
  `:duplicate_node_id` = 3 codes, not minimal.
- **Two nodes sharing an id, connected to each other via an edge naming that
  shared id as both source and target:** first-match-wins resolves *both*
  endpoints to the same (first) index, producing a self-loop in the adjacency
  graph on a non-gateway node — this additionally triggers
  `:cycle_without_gateway`, a third, unrelated code.
- **Both occurrences the same node type, both START:** additionally triggers
  `:multiple_start_nodes` from CHK-01 (which counts by `node_type`, unrelated
  to id equality) — a third code, and for a different reason than CHK-05 is
  supposed to be isolating.
- **The duplicated id assigned to a node type requiring only one side of
  connectivity, hoping the "unused" side is naturally satisfied for the
  duplicate too:** doesn't work — the duplicate occurrence never receives
  *any* edge attribution regardless of type (proven generally in test case
  7's write-up above), so this doesn't avoid the companion violation for any
  type choice; it only changes *which* single-sided rule the duplicate fails.

Every path leads to either the same unavoidable `[:duplicate_node_id,
:isolated_node]` minimum, or to a strictly larger violation set — confirming
test case 7's fixture is genuinely the smallest achievable under this
algorithm, not an accident of insufficient effort.

## Mutation test — AC3's never-short-circuit invariant is genuinely load-bearing

Per the task instruction to empirically prove at least one test actually
catches a regression (mutation testing, following the REQ-020/REQ-022
precedent), `validate_graph/1`'s composition (`lib/letflow/definitions/graph.ex`,
originally `|> Enum.flat_map(& &1.(graph))`) was temporarily mutated to
short-circuit at the first check that returns any violation:

```elixir
|> Enum.reduce_while([], fn check, acc ->
  case check.(graph) do
    [] -> {:cont, acc}
    found -> {:halt, acc ++ found}
  end
end)
```

This simulates exactly the class of bug Key invariant 5 / AC3 exists to
prevent — "just the first encountered" instead of "every violation,
unconditionally." Re-ran `mix test test/letflow/definitions/graph_test.exs`.
Result: **12/15 passed, 3 failures** — not only test case 11 (the AC3 test
itself), but also test cases 7 and 15 (the CHK-05 companion-violation test and
REVIEWER's dangling+isolated test), since both of those also assert 2
simultaneous violation codes and are equally exposed by the same mutation:

```
1) test REVIEWER suggestion: dangling-only edge also isolates its source node
   a node's sole edge dangling on its target produces both :dangling_edge and :isolated_node
   Assertion with == failed
   code:  assert codes(result) == [:dangling_edge, :isolated_node]
   left:  [:dangling_edge]
   right: [:dangling_edge, :isolated_node]

2) test validate_graph/1 — acceptance criterion 2: CHK-05 (duplicate node id)
   a repeated node id -> :duplicate_node_id, alongside the unavoidable companion :isolated_node
   Assertion with == failed
   code:  assert codes(result) == [:duplicate_node_id, :isolated_node]
   left:  [:duplicate_node_id]
   right: [:duplicate_node_id, :isolated_node]

3) test validate_graph/1 — acceptance criterion 3
   a graph violating 3 checks at once returns all 3 violation codes, in fixed check order
   Assertion with == failed
   code:  assert codes(result) == [:missing_start_node, :missing_end_node, :cycle_without_gateway]
   left:  [:missing_start_node]
   right: [:missing_start_node, :missing_end_node, :cycle_without_gateway]
```

The other 12 tests (every fixture asserting exactly 1 violation code) kept
passing unchanged, exactly as expected — the mutation only changes behavior
once 2+ checks would fire. The mutation was then reverted; `git diff --stat
lib/letflow/definitions/graph.ex` showed an empty diff (clean revert against

## Fixture isolation

Every test builds its own graph value from scratch via the `node/2`/`edge/3`/
`graph/2` helpers — no shared mutable state, no database row, no
`System.unique_integer/1`-style uniqueness needed at all (unlike every
DB-backed test file in this project) since these are plain in-memory structs
scoped entirely to each test's own local variables. `async: true` is safe
because there is no shared resource (Postgres connection, ETS table, file)
across tests. No test depends on wall-clock time, unseeded randomness, or
another test's execution order.
