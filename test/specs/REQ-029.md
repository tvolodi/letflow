## Acceptance criterion 1 — each of the 7 node types

> "each of the 7 node types has at least one explicit test: HUMAN_TASK missing role,
> SERVICE_TASK missing endpoint, SERVICE_TASK invalid timeout (0 and >300000), TIMER
> missing/invalid duration, TIMER P0D explicitly accepted, and START/END/gateway types
> accepting no attributes"

| # | Test case | Why this exists (not just the criterion restated) |
|---|---|---|
| 1 | `HUMAN_TASK role` describe: `attributes: nil -> :missing_role` | Proves CHK-09 fires on the "no attributes map at all" case, the most common real shape (a node with no `attributes` key at all in the decoded JSON), not just the more obvious "role present but blank" case. |
| 2 | `role absent, blank, whitespace-only, or non-string all trigger the same single code` (4-way loop) | Design doc §4.1 states there is "exactly one trigger condition, not a separate code per sub-case" for CHK-09 — this locks that claim in as a test, not just a comment. Includes a non-string value (`42`) specifically because `blank_or_missing_string?/2`'s `is_binary` guard is the line a naive re-implementation (e.g. one that only checks for `nil`/`""`) would get wrong. |
| 3 | `a non-empty, non-whitespace role -> valid: true, violations: []` | Negative-of-the-negative: without this, a bug that always returns `:missing_role` regardless of input would still pass tests 1–2. |
| 4 | `SERVICE_TASK endpoint` describe: `attributes: nil -> :missing_endpoint (alongside :invalid_timeout)` | Traced against the real code: `attributes: nil` means `timeout_ms` is *also* absent, so CHK-10 and CHK-11 both fire — asserting only `[:missing_endpoint]` here would be a wrong expectation (confirmed by running the test against the real implementation first: it failed with `[:missing_endpoint, :invalid_timeout]`, corrected the test to match, see "regression note" below). This test doubles as an SERVICE_TASK instance of the never-short-circuit invariant. |
| 5 | `endpoint absent, blank, or whitespace-only -> :missing_endpoint` (3-way loop, `timeout_ms` supplied and valid) | Isolates CHK-10 alone by supplying a valid `timeout_ms`, so the assertion `codes(result) == [:missing_endpoint]` is a real single-code check, not accidentally passing because of test 4's two-code shape. |
| 5a | `endpoint absent but service_id non-blank -> no :missing_endpoint` (ISS-0104/GH#334, fixed 2026-08-20) | CHK-10's `"service_id"` alternative (design doc §4.1a): a `route_kind: :catalog_service` (service-id-only) SERVICE_TASK node must pass graph validation — before this fix it never could, since CHK-10 required `"endpoint"` unconditionally. |
| 5b | `both endpoint and service_id absent/blank -> :missing_endpoint still fires` (3-way loop) | Proves `"service_id"` is an *alternative* satisfying condition, not a bypass of CHK-10 altogether — a node with neither key present must still fail. |
| 5c | `both endpoint and service_id non-blank -> no :missing_endpoint` | Confirms the two keys are not mutually exclusive from CHK-10's point of view — `route_kind`'s own service_id-wins-when-both-present precedent (REQ-056 design doc §5.1) does not make an `endpoint`-and-`service_id` combination a CHK-10 violation. |
| 6 | `timeout_ms: 0 -> :invalid_timeout` | AC1's explicit "0" boundary case — `0 < 1`, the lower boundary of the `1..300_000` inclusive range. |
| 7 | `timeout_ms: 300001 -> :invalid_timeout` | AC1's explicit ">300000" case — the exact off-by-one above the upper boundary; catches a `<=` vs `<` mistake at the top end. |
| 8 | `timeout_ms: 1 and 300000 are both valid` (2-way loop) | The mirror image of 6/7 — proves the range is inclusive at both ends, not exclusive. Without this, an implementation using `> 0 and < 300_000` (excluding both boundaries) would still pass 6/7 alone. |
| 9 | `timeout_ms missing, or a float/numeric-string -> :invalid_timeout` (3-way loop) | Design doc §2 pins "no type coercion" as a deliberate contract (`is_integer/1`, not `is_number/1` or a string-parse fallback). `1000.0` and `"1000"` are exactly the two coercion temptations a less careful implementation might accept; this test exists specifically to catch that regression, not to restate AC1. |
| 10 | `TIMER duration_iso8601`: `attributes: nil, or missing key -> :invalid_duration` (2-way loop) | AC1's "TIMER missing... duration" case, both of the two ways a duration can be structurally absent (no map at all vs. an empty map). |
| 11 | `P0D is explicitly accepted as a zero-delay timer` | AC1's explicit "TIMER P0D explicitly accepted" case — traced through the scan-forward parser by hand (design doc §4.3): `date_part = "0D"`, one token, no `T`, satisfies the "at least one token" rule. This is the single most load-bearing individual test case in this spec, since `P0D` is the one duration string every other plausible ISO-8601 parser variant (e.g. one that rejects an all-zero duration as "empty") would get wrong. |
| 12 | `other well-formed durations are accepted: P1Y2M3D, PT1H30M, P1DT12H` (3-way loop) | Exercises the multi-token date-only case, the time-only (`T` present, empty date part) case, and the combined date+time case — three structurally distinct branches of `valid_duration_remainder?/1`, all hand-traced against the real code before writing (see "Traces" below). |
| 13 | `malformed durations are rejected` (7-way loop: no leading `P`, zero tokens, empty time part, `.`-fractional, `,`-fractional, wrong unit order, missing digits) | AC1's "TIMER... invalid duration" case, generalized to every distinct rejection branch the scan-forward parser has (design doc §4.3's own "Examples for TEST-DESIGNER" list) rather than one arbitrarily-chosen invalid string — a parser that gets any one of these 7 branches wrong (e.g. accidentally allows `.` through, or doesn't enforce unit ordering) fails this test. |
| 14 | `START/END/EXCLUSIVE_GATEWAY/PARALLEL_GATEWAY require nothing`: 4 types × 3 attribute variants (`nil`, `%{}`, an arbitrary/malformed-looking map) | AC1's "START/END/gateway types accepting no attributes" case. The third variant (`%{"role" => "", "anything" => "goes"}`) is deliberately a map that *would* trigger `:missing_role` if this were a HUMAN_TASK node — proving these 4 types are exempt by node-type filtering, not merely "happened not to have a role key set." |

**Also included (matching REQ-028's own "AC1: fully valid graph" and "never
short-circuits" precedent, not separately named in REQ-029's AC list but necessary to
demonstrate the checks compose correctly):**
- `a SERVICE_TASK missing both endpoint and a valid timeout_ms produces both
  violations, in fixed check order` — the never-short-circuit invariant (design doc
  §3), the same shape as REQ-028's CHK-05 test.
- `a realistic multi-node graph with one valid node per applicable type returns valid:
  true, violations: []` — proves the whole function composes to a clean pass on a
  realistic input, not just that each check individually can return `[]`.

## Acceptance criterion 2 — EXCLUSIVE_GATEWAY default edge with a condition

> "an EXCLUSIVE_GATEWAY edge with both a non-null condition and is_default: true is
> rejected"

**Test case:** `is_default: true with a non-null condition is rejected -- CHK-14 and
CHK-15 both fire`.

**Why this exists, precisely (not just "it's rejected"):** the design doc (§5.1)
states this scenario deliberately produces **two** violation codes, not one —
`:unexpected_edge_condition` (CHK-14, "every edge that isn't a non-default gateway
outgoing edge must have a null condition" — this edge is default, so it falls into
"every other edge") and `:default_with_condition` (CHK-15, the unscoped
is_default/condition conflict rule). A test that only asserted `result.valid == false`
would pass even if a future refactor collapsed these into one code or dropped one of
them; asserting the **exact ordered code list**
(`[:unexpected_edge_condition, :default_with_condition]`) is what actually pins the
two-codes-not-one behavior AC2 (read alongside the design doc) requires. Traced by
hand against `check_gateway_condition_presence/1` (CHK-13, does not fire — this edge
*is* default so it's excluded from CHK-13's scope), `check_non_gateway_condition_absence/1`
(CHK-14, fires), `check_default_condition_conflict/1` (CHK-15, fires),
`check_single_default_edge/1` (CHK-16, does not fire — only one default edge from this
gateway), and `check_cel_syntax/1` (CHK-17, does not fire — the condition
`"status == \"approved\""` is syntactically valid CEL) before writing the assertion.

## Acceptance criterion 3 — two default edges on one gateway

> "an EXCLUSIVE_GATEWAY with two edges both marked is_default: true is rejected"

| Test case | Why this exists |
|---|---|
| `two edges from the same gateway both marked is_default: true -> exactly one :multiple_default_edges violation (the 2nd)` | AC3 literally. Also asserts the violation names the *second* edge (`e2`) and the gateway (`gw`) — proves the "first is legal, only subsequent ones are flagged" rule (design doc §5.3), not just "some violation happened." A naive implementation that flags *every* default edge including the first (N violations for N defaults, not N-1) would still make `result.valid == false` true but would fail this exact-code-list assertion. |
| `three default edges from the same gateway -> two violations (N occurrences -> N-1, mirrors CHK-05's convention)` | Strengthens the N-1 claim beyond the minimal N=2 case — an implementation that special-cases "exactly 2" (e.g. flags only the last one, or hardcodes "flag index 1") would pass the 2-edge test but fail this one. Also asserts violations are in declaration order (`e2` before `e3`). |
| `exactly one default edge among several non-default (conditioned) edges on a gateway is legal` | The required "happy path" a real definition author needs to hit — proves the rule doesn't over-fire on the legal, common case (one default edge alongside conditioned non-default edges from the same gateway). Without this, a bug that flags *any* default edge (even the first, alone) would go undetected by the two failing-case tests above. |

## Acceptance criterion 4 — `valid_cel_syntax?/1`

> "isValidCelSyntax-equivalent rejects at least one structurally invalid expression and
> accepts at least one structurally valid one, with an explicit test noting it performs
> no evaluation"

| Test case | Why this exists |
|---|---|
| `accepts structurally well-formed expressions` — `"status == \"approved\""` and `"amount > 100 && region in [\"US\", \"EU\"]"` | Two accept cases, not one: the first has no brackets at all (only a quoted string), the second has both nested brackets and multiple quoted strings — exercising the bracket-stack and quote-tracking logic together, not just the "no delimiters at all" trivial case. |
| `rejects structurally invalid expressions` — trailing bare operator (`"status == "`), unclosed paren (`"(status == \"approved\""`), unterminated string (`"\"unterminated"`), leading bare operator (`"&& status"`), empty string, whitespace-only string | Six reject cases, one per distinct failure branch of the algorithm (design doc §6 steps 1, 2, and 4) — a change that fixes one branch (e.g. bracket matching) while silently breaking another (e.g. the bare-operator check) is caught by whichever of these six still exercises the broken branch, where a single reject-case test would not distinguish which branch broke. |
| `performs no evaluation -- a well-formed expression referencing a variable that could never exist is still accepted` — `"this_variable_does_not_exist_anywhere == 42"` returns `true` | This is the literal test AC4 asks for by name (design doc §6's own worked example). It exists to positively demonstrate the "no evaluation" property, which is otherwise an absence (of behavior) that's easy to silently break by later adding a variable-resolution step — this test would immediately start failing (return `false` or raise) if that ever happened. |
| (integration) `validate_edge_conditions/1 — CHK-17: invalid CEL syntax on a present condition` — a non-default gateway edge with `"amount >"` produces exactly `[:invalid_cel_syntax]` | Proves `valid_cel_syntax?/1` is actually *wired into* `check_cel_syntax/1` inside `validate_edge_conditions/1`, not merely correct in isolation — a caller that forgot to call `valid_cel_syntax?/1` from CHK-17 (or called it but ignored the result) would pass every `valid_cel_syntax?/1`-only test above yet fail this one. |

## Acceptance criterion 5 — extra undeclared attributes ignored

> "extra undeclared attributes on a node do not cause a violation, demonstrated by an
> explicit test"

**Test case:** `extra keys alongside a valid role/endpoint/timeout never cause a
violation` — a HUMAN_TASK node with `"role"` plus two unrelated extra keys
(`"unexpected_key"`, `"another"`), and a SERVICE_TASK node with `"endpoint"`/
`"timeout_ms"` plus two unrelated extra keys (one of them itself a nested map, to prove
the extra value's *shape* doesn't matter either) — both nodes in the same graph,
asserting `valid: true, violations: []`.

**Why this exists:** the design doc (§2) states this property is true "by
construction, not by an explicit allow-list/ignore-list mechanism" — i.e. there is no
code path that specifically permits extra keys, they're simply never read. A
regression here would most likely come from someone adding a defensive "reject unknown
keys" check later without realizing AC5 forbids it; this test would immediately catch
that. The nested-map extra value (`"nested" => %{"a" => 1}`) specifically guards
against a naive implementation that iterates *all* map values looking for something
(e.g. a badly-scoped `Enum.all?` over `Map.values/1`) rather than reading only the
named keys.

## Regression note — one assertion caught and corrected against real output

The first draft of the "SERVICE_TASK endpoint: attributes: nil" test asserted
`codes(result) == [:missing_endpoint]`. Running it against the real implementation
failed with `left: [:missing_endpoint, :invalid_timeout]` — correct on reflection:
`attributes: nil` means `timeout_ms` is absent too, so CHK-11 also fires. The test was
corrected to assert `[:missing_endpoint, :invalid_timeout]` and a second, separate test
was added (`endpoint absent, blank, or whitespace-only -> :missing_endpoint`, supplying
a valid `timeout_ms`) to isolate CHK-10 alone. This is recorded here as evidence the
test suite was actually run and its output actually read during design, per
`core-directives.md`'s "no speculation" rule — not asserted to be correct without
checking.
