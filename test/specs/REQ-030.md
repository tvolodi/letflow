# Test Spec: REQ-030 — Definition store CRUD (`Letflow.Definitions` create/get_by_id/get_active_by_name/list/activate/deprecate/archive)

**Requirement:** REQ-030 (`docs/requirements.yaml`, stage S2, `depends_on: [REQ-027, REQ-028, REQ-029]`)
— verbatim acceptance criteria (re-verified directly against `docs/requirements.yaml`
lines 1408–1417, 9 criteria, not 8 or 4 as some earlier summaries in this run's history
said):

1. "create/1 with a graph that fails REQ-028's validateGraph() writes zero rows and
   returns the collected violations, not a generic error"
2. "two concurrent create/1 calls with identical (name, version) result in exactly one
   success and one duplicate-error, demonstrated with an actual concurrent test or the
   ON CONFLICT code path cited explicitly if concurrency can't be exercised"
3. "activate/1 on a DRAFT definition atomically deprecates any prior ACTIVE version of
   the same name in the same transaction, verified by reading both rows after the call"
4. "activate/1 called twice on the same already-ACTIVE definition returns the
   no-op/AlreadyActive result both times, never an error"
5. "every one of the 4 forbidden-transition cells in definition.md's authoritative
   state transition table (e.g. ACTIVE->ARCHIVED directly, DRAFT->ARCHIVED directly)
   is tested and rejected"
6. "activate/1's signature includes a nil-able/optional service-scope-validation hook
   parameter that REQ-031 wires in, documented explicitly in the moduledoc as the
   SVC-03 integration point"
7. "get_active_by_name/1 against a name with an ACTIVE version returns that definition;
   against a name with only DRAFT/DEPRECATED/ARCHIVED versions (no ACTIVE row) returns
   a not-found error, not the most recent non-active row"
8. "list/1 with a stage filter returns only rows whose stage column exactly matches the
   filter value, combinable with a simultaneous name and/or status filter in the same
   call (verified with an explicit test using all three filters together)"
9. "a row written by create/1 has tenant_id equal to the tenant whose schema the write
   targeted, derived internally -- not equal to a caller-supplied tenant_id when the
   two are deliberately made to disagree in a test, which must fail loudly (not
   silently attribute to the wrong tenant) rather than succeed"

**AC5's "4" vs the real table's "9" -- not silently resolved either way.** AC5's own
text says "4 forbidden-transition cells" but names only 2 examples by name
(`ACTIVE->ARCHIVED`, `DRAFT->ARCHIVED`). `lib/letflow/design/req030-definition-store-crud.md`
§6.1 read `definition.md:558-570`'s authoritative 4x4 transition table directly and
counted **9** off-diagonal `✗` (forbidden) cells, not 4 — CODE-DESIGN-VALIDATOR and
SECURITY-REVIEWER both independently re-confirmed this count during their own gate
passes (per this run's task briefing). The design doc's own §6.1 states plainly: "the
enforcement mechanism rejects the complete, correct set of 9 forbidden cells regardless
of which count TEST-DESIGNER's coverage ends up targeting." This spec tests **all 9**,
each as its own named test case — not 4, and not a generic loop that could silently
skip one.

**Plus one regression case beyond the 9 numbered criteria:** design doc §6.2's
documented "genuine cross-row race" and SECURITY-REVIEWER's filed, REVIEWER-accepted,
non-blocking finding — `activate/2`'s TOCTOU between two *different* DRAFT rows sharing
the same `name`, activated concurrently. Cheap to demonstrate given AC2's test already
sets up the `Task.async` machinery, so included rather than skipped.

**Test tier:** unit+integration (real Postgres via `Letflow.DataCase`, no mocked DB per
`docs/guides/test_developer_guide.md` DIRECTIVE T-1). No state-machine property test
(`ExUnitProperties`) is added here: REQ-030's status transitions are a small, fully
enumerable closed set (4 states, 3 legal edges, 9 forbidden cells) already covered
exhaustively by AC5's 9 explicit example-based tests — a `StreamData` property test
generating random `[activate, deprecate, archive]` sequences would exercise the exact
same 9 cells non-exhaustively per run instead of deterministically covering all of
them, so the example-based approach is the stronger, not weaker, choice here (contrast
with `test/letflow/process_instance_test.exs`, whose 20-step action sequences over 4
actions genuinely need a property test because hand-enumerating all reachable states
is impractical at that size).

## Fixture strategy — read this before the test cases below

Mirrors `test/letflow/definitions/snapshot_store_test.exs`'s and
`test/letflow/event_store_test.exs`'s established `provisioned_tenant/1` pattern: each
test provisions its own tenant (real `CREATE SCHEMA` via
`TenantProvisioning.provision_tenant_schema/1`, real
`TenantProvisioning.replay_migrations/2`, which includes REQ-027's
`process_definitions` migration). `Ecto.Adapters.SQL.Sandbox` is switched to `:auto`
mode (not the normal rolled-back sandbox transaction) because `Ecto.Migrator` needs its
own real DB connection the sandbox can't hand out — same reasoning as those two files'
own moduledocs. `async: false` for the whole module, for the same reason those two
files are `async: false`.

**File organization**: `test/letflow/definitions_test.exs` (REQ-041) is `async: true`
and deliberately pure — no `Repo` connection anywhere in that file. Every one of
REQ-030's 7 functions does real database I/O, so none of REQ-030's behavioral coverage
belongs there. This mirrors the split already established for this same context
module: `pack_update_migration_test.exs` and `snapshot_store_test.exs` both live under
`test/letflow/definitions/` as separate DB-backed files rather than folded into the
top-level pure file. `test/letflow/definitions/store_test.exs` (this spec's primary
file) follows `snapshot_store_test.exs`'s exact pattern (`process_definitions` is a
per-tenant-schema table, like `instance_definition_snapshots`, not a GLOBAL table like
REQ-041's three tables). Two pure, doc-content assertions for AC6 and part of AC9 (the
moduledoc text itself, not the runtime behavior) were added to the existing
`test/letflow/definitions_test.exs` instead, next to REQ-041's own moduledoc-content
tests, reusing that file's established `normalized_moduledoc/1` helper — no DB
connection needed for a doc-content string check.

Every test uses `unique_name/1` (`System.unique_integer/1`-suffixed) for every
definition `name` and a fresh `Ecto.UUID.generate()` for every `created_by` — no
shared or hard-coded identifiers, no test depends on another test's data or on
execution order, no wall-clock dependency anywhere.

`valid_graph/0` is the minimal graph passing all three of `Graph.validate_graph/1`,
`.validate_node_attributes/1` and `.validate_edge_conditions/1` (one START node with an
outgoing edge to one END node with an incoming edge). The three `graph_*` fixtures used
by AC1's tests each deliberately fail exactly one specific, named check in `graph.ex`
(confirmed by direct reading of the check implementations, not guessed) — see
`store_test.exs`'s moduledoc "Fixture graphs" section for the full reasoning.

## Test cases

### AC1 — `create/2` writes zero rows and returns collected violations on graph validation failure

See `test/letflow/definitions/store_test.exs`, describe block
`"create/2 (AC1) -- graph validation failure writes zero rows"`:

1. `"a graph missing an END node (validate_graph/1, P7) is rejected with {:error, {:graph_validation_failed, violations}} and writes zero rows"`
   — the literal AC1 case: `validate_graph/1` itself (P7) rejects the graph. Asserts
   the specific `:missing_end_node` violation code (not a generic error) and a direct
   row-count query confirming zero rows landed.
2. `"a structurally-valid graph with a HUMAN_TASK missing 'role' (validate_node_attributes/1, P8) is rejected and writes zero rows"`
   — proves the pipeline's P8 phase (`validate_node_attributes/1`) also gates
   `create/2`, closing the gap the design doc's §0/§4.1 flags explicitly: REQ-030's own
   `requirements.yaml` description text names only one of REQ-029's two validators by
   name. Asserts `:missing_role` is present AND no structural violation code is present
   (proving P7 passed and P8 specifically is what caught it, not a coincidental
   structural failure).
3. `"a structurally-valid graph with an unexpected non-gateway edge condition (validate_edge_conditions/1, P9) is rejected and writes zero rows"`
   — same reasoning for P9 (`validate_edge_conditions/1`), the third and last
   pre-write validation phase.

### AC2 — concurrent identical `(name, version)` creates: exactly one success, one duplicate-error

See describe block `"create/2 (AC2) -- concurrent identical (name, version) creates"`,
test `"exactly one succeeds, the other gets :duplicate_name_version, exactly one row lands"`.
A **real** concurrent test: two `Task.async/1` processes call `Definitions.create/2`
with byte-identical `attrs` against the same schema simultaneously (not sequentially
awaited), backed by real, separate Postgres connections since `provisioned_tenant/1`
switches `Ecto.Adapters.SQL.Sandbox` to `:auto` mode (real connection-pool checkout,
`pool_size: System.schedulers_online() * 2` per `config/test.exs`, confirmed >= 2).
Asserts exactly one `{:ok, _}` and exactly one `{:error, :duplicate_name_version}` among
the two results, and a direct row-count query confirming exactly one row landed —
citing the `ON CONFLICT` code path was the acceptance criterion's own named fallback
for when concurrency "can't be exercised," which does not apply here since it can be.

### AC9 — `tenant_id` is always derived internally, never a caller-supplied value

See describe block `"create/2 (AC9) -- tenant_id always derived internally, never caller-supplied"`:

1. `"a created row's tenant_id equals the tenant whose schema was written into"` — the
   positive case: a definition created with no `tenant_id` key in `attrs` at all still
   gets the correct `tenant_id`, both in the returned struct and re-read from Postgres.
2. `"a disagreeing atom :tenant_id key is rejected with :tenant_id_not_accepted, writes zero rows"`
   — the literal AC9 negative case: `attrs` deliberately carries a `:tenant_id` value
   that disagrees with the real tenant. Asserts the typed
   `{:error, :tenant_id_not_accepted}` (fails loudly, per AC9's own wording) and zero
   rows written — never a silent attribution to the wrong tenant.
3. `"attrs containing a string \"tenant_id\" key is also rejected with {:error, :tenant_id_not_accepted}, and writes zero rows"`
   — the string-keyed variant of the same guard (`reject_key/4` checks both forms).

Part of AC9 is a pure moduledoc-content check, not a runtime behavior — see "Moduledoc
checks" below.

### AC3 — `activate/2` on DRAFT atomically deprecates any prior ACTIVE of the same name

See describe block `"activate/2 (AC3) -- deprecates prior ACTIVE of the same name atomically"`,
test `"a second DRAFT activation deprecates the first ACTIVE version, both rows re-read from Postgres"`.
Creates and activates definition 1 (name `X`, version `1.0.0`) → ACTIVE. Creates and
activates definition 2 (same name `X`, version `2.0.0`). **Re-reads both rows from
Postgres after the second `activate/2` call** (not just trusting the in-memory reply):
definition 1's re-read status must be `:deprecated`, definition 2's must be `:active`,
and a direct `COUNT(*) WHERE name = X AND status = 'active'` query must equal exactly
1 — proving the atomic deprecate-then-activate pair, not merely that both calls
individually "succeeded."

### AC4 — `activate/2` twice on already-ACTIVE: no-op both times, never an error

See describe block `"activate/2 (AC4) -- idempotent no-op on ACTIVE, never an error"`,
test `"calling activate/2 repeatedly on an already-ACTIVE definition always returns the AlreadyActive no-op, never an error"`.
Calls `activate/2` three times in sequence on the same definition (first call is the
real activation, `already_active: false`; the next two are repeats). Asserts every
call returns `{:ok, %{already_active: _, definition: %{status: :active}}}` — literally
never an `{:error, _}` shape on any call, matching AC4's "never an error, on every
call" wording (not just "the first repeat"). Confirms exactly one row stays ACTIVE for
that name throughout.

### AC5 — all 9 forbidden-transition cells, individually tested and rejected

See describe block `"AC5 -- all 9 forbidden-transition cells, tested individually"`.
The authoritative table (design doc §6.1, citing `definition.md:558-570` directly) has
these 9 off-diagonal `✗` cells:

| # | Cell | Test |
|---|---|---|
| 1 | DRAFT → DEPRECATED | `"cell DRAFT -> DEPRECATED: deprecate/2 on a DRAFT row returns {:error, :invalid_status_transition}, status unchanged"` |
| 2 | DRAFT → ARCHIVED | `"cell DRAFT -> ARCHIVED: archive/2 on a DRAFT row returns {:error, :invalid_status_transition}, status unchanged"` |
| 3 | ACTIVE → DRAFT | `"cell ACTIVE -> DRAFT: activate/2, deprecate/2, archive/2 on an ACTIVE row never yield status :draft"` |
| 4 | ACTIVE → ARCHIVED | `"cell ACTIVE -> ARCHIVED: archive/2 on an ACTIVE row returns {:error, :invalid_status_transition}, status unchanged"` |
| 5 | DEPRECATED → DRAFT | `"cell DEPRECATED -> DRAFT: activate/2, deprecate/2, archive/2 on a DEPRECATED row never yield status :draft"` |
| 6 | DEPRECATED → ACTIVE | `"cell DEPRECATED -> ACTIVE: activate/2 on a DEPRECATED row returns {:error, :not_draft}, status unchanged"` |
| 7 | ARCHIVED → DRAFT | `"cell ARCHIVED -> DRAFT: activate/2, deprecate/2, archive/2 on an ARCHIVED (terminal) row never yield status :draft"` |
| 8 | ARCHIVED → ACTIVE | `"cell ARCHIVED -> ACTIVE: activate/2 on an ARCHIVED row returns {:error, :not_draft}, status unchanged"` |
| 9 | ARCHIVED → DEPRECATED | `"cell ARCHIVED -> DEPRECATED: deprecate/2 on an ARCHIVED row returns {:error, :invalid_status_transition}, status unchanged"` |

**Why cells 3, 5, 7 (the `X -> DRAFT` cells) are shaped differently.** None of
`activate/2`, `deprecate/2`, `archive/2` ever sets an *existing* row's status to
`:draft` — `create/2` is the only writer of `:draft`, and it only ever `INSERT`s a
fresh row (design doc INV-DS-4: enforced "by construction," not by an explicit
rejection branch). There is therefore no direct function call that *attempts*
`ACTIVE -> DRAFT`/`DEPRECATED -> DRAFT`/`ARCHIVED -> DRAFT` for a test to invoke and
assert an error atom against. Each of these 3 tests instead drives a row to the
relevant starting status and calls **all three** of `activate/2`, `deprecate/2`,
`archive/2` against it (using 3 independent fixture rows so a legitimate transition by
one function doesn't consume the row before the next function is tried), asserting
that **none** of the three ever leaves the row's re-read status as `:draft` — the
strongest statement obtainable about a transition target with no code path to attempt
it directly. This was flagged as a genuine, design-doc-acknowledged ambiguity (§6.1,
§9 OQ-1: "the ambiguity is in how many test cases AC5 anticipates... not in what the
design must enforce") rather than silently resolved by picking an arbitrary subset.

**Bonus, folded in at no extra cost:** cells 5 and 7's fixtures also each include a
self-transition rejection (`DEPRECATED -> DEPRECATED` via `deprecate/2` inside cell 5's
test, `ARCHIVED -> ARCHIVED` via `archive/2` inside cell 7's test) — these are diagonal
"—" cells in the authoritative table (not counted among the 9), but the design doc's
own §6.1 function-by-function breakdown treats them as real rejections worth pinning,
and they come for free from the same fixture rows.

### AC6 — the `service_scope_validator` hook is a real parameter with real effect

See describe block `"activate/2 (AC6) -- service_scope_validator hook takes effect"`:

1. `"a hook returning :ok lets activation proceed and is called with the graph and tenant_id"`
   — asserts activation succeeds, and (via `assert_receive`/`refute_received` on a
   message the hook closure sends to the test process) that the hook was called
   **exactly once**, with a real `%Letflow.Definitions.Graph{}` struct (not the raw map)
   and the real tenant's `tenant_id` — the hook's documented 2-arity contract.
2. `"a hook returning {:error, reason} aborts activation as {:service_scope_violation, reason}, stays DRAFT"`
   — asserts the exact `{:error, {:service_scope_violation, reason}}` wrapping, that the
   definition's re-read status is still `:draft` (nothing written), and that zero rows
   are ACTIVE for that name.
3. `"the hook is never called on the already-ACTIVE no-op path"` — supplies a hook that
   `raise`s if invoked at all, activates an already-ACTIVE definition, and asserts the
   call still succeeds as a no-op (proving the hook was never reached — a raise would
   have propagated and failed the test).
4. `"the hook is never called on a rejected non-draft transition"` — same
   raise-if-called technique, against a DEPRECATED definition; asserts `{:error, :not_draft}`
   without the hook ever firing.

Part of AC6 is a pure moduledoc-content check — see "Moduledoc checks" below.

### AC7 — `get_active_by_name/2`

See describe block `"get_active_by_name/2 (AC7)"`:

1. `"a name with an ACTIVE version returns that definition"` — the positive case.
2. `"a name with only a DRAFT version (never activated) returns {:error, :not_found}"`
   — no ACTIVE row exists at all.
3. `"a name whose only version was activated then deprecated returns {:error, :not_found} -- never the most recent non-active row"`
   — the sharper AC7 case: a DEPRECATED row genuinely exists for this name (confirmed
   by a direct re-read and a row-count assertion before calling `get_active_by_name/2`,
   so a buggy "fall back to most recent" implementation would have something concrete
   to wrongly return), yet the function must still return `{:error, :not_found}`.

### AC8 — `list/2`'s stage filter is exact-match, combinable with name/status filters

See describe block `"list/2 (AC8) -- stage filter exact-match, combinable with other filters"`,
test `"stage filter matches exactly, excludes a longer same-prefix stage, combines via AND"`.
Creates 4 definitions in one tenant: two with `stage: "prod"` (one DRAFT, one ACTIVE),
one with `stage: "production"` (same prefix, different value), one with no stage at
all. Asserts `list(%{stage: "prod"})` returns both `"prod"` rows and excludes both the
`"production"` row (the substring/exact-match distinction AC8 turns on) and the
no-stage row. Then asserts `list(%{stage: "prod", status: :active})` returns exactly
the one ACTIVE `"prod"` row, and `list(%{stage: "prod", status: :draft, name: <exact name>})`
returns exactly the one matching row — all three filters combined in a single call, as
AC8 explicitly requires ("verified with an explicit test using all three filters
together").

### Moduledoc checks (AC6 doc-content half, AC9 doc-content half)

See `test/letflow/definitions_test.exs`, describe blocks
`"moduledoc -- AC6: activate/2's service_scope_validator hook is documented as the SVC-03 integration point (REQ-030)"`
and `"moduledoc -- AC9 (doc-content half): tenant_id is always derived, never accepted (REQ-030)"`.
Pure, database-free tests reading `Letflow.Definitions`' compiled moduledoc via
`Code.fetch_docs/1` (reusing the file's existing `normalized_moduledoc/1` helper, built
for REQ-041's own moduledoc checks), asserting the text names `:service_scope_validator`,
`SVC-03`, `REQ-031`, the hook's 2-arity `:ok | {:error, term()}` contract, the
`:tenant_id_not_accepted` error atom, the "never accepts a `:tenant_id`" statement, and
`tenant_id_for_schema_name` (the derivation function) — matching AC6's explicit
"documented explicitly in the moduledoc" requirement.

### Regression — `activate/2`'s cross-row TOCTOU (design doc §6.2, non-blocking finding)

See describe block `"Regression -- activate/2 cross-row TOCTOU (design doc §6.2)"`,
test `"concurrent activation of two DRAFT rows sharing a name never yields a double-ACTIVE state"`.
Two **different** DRAFT rows sharing the same `name` are activated concurrently via
`Task.async/1` (same real-concurrency machinery as AC2's test). Asserts every result is
either a genuine success or the documented `{:error, {:transaction_failed, _reason}}`
fallback (never a different, unexpected error shape, never a raised exception escaping
the test) and, regardless of exactly which interleaving occurred (inherently
timing-dependent), that the DB's `uq_active_definition` partial unique index left
**exactly one** row ACTIVE for that name — never a corrupted double-ACTIVE state. This
run's actual execution (captured in this run's `mix test` log) did trigger the real
race: the second transaction's `UPDATE` genuinely raised a Postgres unique-violation,
caught and converted to `{:error, {:transaction_failed, exception}}` exactly as the
design doc describes — not merely a theoretical possibility this test happens to pass
vacuously against.
