# Test Spec: REQ-031 — Service scope activation validator (`Letflow.Definitions.ServiceScopeValidator`, SVC-03)

**Requirement:** REQ-031 (`docs/requirements.yaml`, stage S2, `depends_on: [REQ-030]`) —
verbatim acceptance criteria (re-read directly against `docs/requirements.yaml`
lines 1460–1465, 5 criteria):

1. "given an injected lookup returning a global-scope service, a SERVICE_TASK referencing
   it passes validation for any tenant_id"
2. "given an injected lookup returning a tenant-scoped service owned by tenant A, a
   SERVICE_TASK referencing it fails validation when activated by tenant B, with a
   violation detail naming the node_id and the service ref_id"
3. "given an injected lookup returning 'not registered' for a service_id, validation
   fails with a distinct not-registered violation reason, distinguishable from the
   owned-by-another-tenant case"
4. "REQ-030's activate/1 is demonstrated calling this validator via its nil-able hook
   when a lookup implementation is supplied, and skipping the check entirely when the
   hook is nil (matching R-Co's own optional-field default)"
5. "the moduledoc explicitly names the ServiceCatalog/PluginRegistry dependency gap and
   which future stage each belongs to, rather than implying real catalog integration
   exists today"

**Design source:** `lib/letflow/design/req031-service-scope-validator.md` (gate-approved,
survived one CODE-DESIGN-VALIDATOR rework cycle). §5's two branch tables are this
module's exact spec; §5's two "why the asymmetry is preserved" notes and INV-SSV-5/
INV-SSV-9 are the two deliberate, faithfully-ported R-Co asymmetries this spec gives
their own named test cases, per this run's task briefing (one of the two triggered the
rework cycle — the single most scrutinized/fragile part of this module).

**Test tier:** unit (pure, no I/O — `Letflow.Definitions.ServiceScopeValidator` has zero
`Repo`/`Ecto` dependency, INV-SSV-4) + integration (real Postgres, for AC4's `activate/2`
hook-wiring demonstration, per `docs/guides/test_developer_guide.md` DIRECTIVE T-1). No
property test: `validate/3`'s branch tables are a small, fully enumerable closed set (2
functions × 5 rows each = 10 branches) already covered exhaustively by example-based
tests below — the same reasoning `test/specs/REQ-030.md` gives for skipping a property
test on its own small enumerable transition table, in contrast to
`test/letflow/process_instance_test.exs`'s genuinely-large action-sequence space.

## Fixture strategy — read before the test cases below

**Pure unit tests** (`test/letflow/definitions/service_scope_validator_test.exs`):
`async: true`, no `Letflow.DataCase`, no `Repo` — mirrors
`test/letflow/definitions/graph_test.exs`'s established shape exactly (pure module under
test, `use ExUnit.Case, async: true`, hand-built `Graph`/`Node` fixtures, no tenant
provisioning). `Lookup` structs are built inline per test with anonymous functions
returning a canned `{:ok, %{scope: ..., owner_tenant_id: ...}}` / `{:error,
:not_registered}` result — this is exactly why the design doc picked a struct-of-
functions over a config-resolved `@behaviour` (design doc §3.1): a different return
value per test case, no `Application.put_env/3` cross-test coupling, safe under this
file's own `async: true`.

**Integration test for AC4** (`test/letflow/definitions/store_test.exs`, new describe
block appended after the existing REQ-030 `"activate/2 (AC6)"` block): REQ-030's own AC6
tests in that file already prove `activate/2`'s hook mechanism takes effect, but they use
a hand-rolled anonymous 2-arity closure as the "hook," not the real, merged
`Letflow.Definitions.ServiceScopeValidator.build/1` output — AC4 specifically asks for
*this* validator, wired through `build/1`, to be demonstrated as the real hook value.
Reuses `store_test.exs`'s existing `provisioned_tenant/1`/`create!/2`/`reread!/2`/
`count_active_by_name/2` helpers and `Sandbox :auto` + `async: false` convention (same
file, no new fixture machinery needed) rather than duplicating tenant-provisioning setup
in a new file. Every test uses `unique_name/1` and a fresh tenant per
`provisioned_tenant/1` — no shared or hard-coded identifiers, no execution-order
dependency, no wall-clock dependency.

**Malformed-lookup / short-circuit fixtures**: hand-built `Lookup` structs whose
`service_lookup`/`plugin_lookup` functions either return an out-of-contract value (to
prove fail-closed, SECURITY-REVIEWER's OQ-1 concern) or `raise` if called a second time
(to prove `Enum.reduce_while/3` genuinely halts after the first violation, not merely
that the returned violation happens to be the first one — the same "prove it, don't
assert around it" technique `store_test.exs`'s AC6 block already uses for "the hook is
never called on the no-op path").

## Test cases

### AC1 — global-scope service passes for any tenant_id

See `service_scope_validator_test.exs`, describe block
`"validate/3 -- AC1: global-scope service passes for any tenant_id"`:

1. `"a SERVICE_TASK referencing a global-scope service_id passes for tenant A"` — the
   literal AC1 case, one `tenant_id`.
2. `"the same global-scope service_id passes for a completely different tenant B, same
   Lookup, unchanged"` — proves the pass is genuinely scope-driven (global means "any
   tenant," not a coincidence of one particular tenant_id matching something), per design
   doc §5's service branch table row 2 note that `owner_tenant_id` is never inspected for
   a `:global` result.

### AC2 — tenant-scoped service owned by tenant A fails for tenant B, violation names node_id + ref_id

See describe block `"validate/3 -- AC2: tenant-scoped service owned by tenant A fails for tenant B"`:

1. `"a SERVICE_TASK referencing a service owned by tenant A fails when validated as tenant B, violation names the exact node_id and service ref_id"`
   — asserts `{:error, %Violation{node_id: ^expected_node_id, kind: :service, ref_id:
   ^expected_service_id, reason: :service_not_available_to_tenant}}`, i.e. both identity
   fields AC2 requires ("naming the node_id and the service ref_id") are asserted against
   the exact fixture values, not merely that *some* violation was returned.
2. `"the same tenant-scoped service passes when validated as its own owning tenant A"`
   — the necessary positive control: without this, a validator that always failed
   tenant-scoped services regardless of owner would vacuously satisfy case 1 above.

### AC3 — not-registered is a reason DISTINCT from owned-by-another-tenant, not just a different string

See describe block `"validate/3 -- AC3: not-registered is a distinct, comparable reason from owned-by-another-tenant"`:

1. `"a not-registered service_id fails with reason :service_not_registered"` — the literal
   AC3 case.
2. `"the not-registered reason and the owned-by-another-tenant reason are distinct, comparable atom values -- not merely different message strings"`
   — the sharper AC3 requirement, tested literally: runs both scenarios (not-registered,
   and owned-by-another-tenant) and asserts `violation_1.reason != violation_2.reason`
   AND `is_atom(violation_1.reason) and is_atom(violation_2.reason)` AND
   `violation_1.reason == :service_not_registered` AND `violation_2.reason ==
   :service_not_available_to_tenant` — pinning that these are two members of a small
   closed atom set (`==`/pattern-match distinguishable), not two arbitrary strings that
   happen to render differently, which is exactly what the design doc §3.2 says a plain
   `reason: []const u8` string (R-Co's own shape) would NOT guarantee.

### AC4 — `activate/2` calls this validator via its hook when supplied, skips when nil (real, merged `activate/2`, real Postgres)

See `store_test.exs`, new describe block `"activate/2 (REQ-031 AC4) -- ServiceScopeValidator.build/1 wired as the real hook"`:

1. `"a Lookup causing a violation is wired via ServiceScopeValidator.build/1 and blocks activation with the real Violation struct"`
   — builds a real `Lookup` whose `service_lookup` returns `{:error, :not_registered}`,
   passes `service_scope_validator: ServiceScopeValidator.build(lookup)` to
   `Definitions.activate/2` against a definition whose graph has a SERVICE_TASK node
   referencing that `service_id`. Asserts `{:error, {:service_scope_violation,
   %ServiceScopeValidator.Violation{reason: :service_not_registered, ref_id: ^service_id,
   node_id: ^node_id}}}` — the full, real `Violation` struct surfacing unchanged through
   `activate/2`'s wrap (design doc §6's "reason... unwrapped and passed through verbatim"
   claim, exercised for real rather than trusted from the design doc's prose). Confirms
   the definition's re-read status is still `:draft` and zero rows are ACTIVE for that
   name — nothing written on a blocked activation.
2. `"the identical graph activates successfully when the hook is omitted entirely -- the nil-skip path is a genuine skip, not an accidentally-permissive lookup"`
   — same exact graph/service_id/tenant (which WOULD fail if the hook ran, per case 1
   above) activated a second time with no `:service_scope_validator` key in `opts` at
   all. Asserts real success (`{:ok, %{definition: %{status: :active}}}`) — this is the
   design doc §6's own "demonstration shape for TEST-DESIGNER" note, executed literally:
   proving AC4's "skipping the check entirely when the hook is nil" is genuine (the same
   graph that fails when the hook runs must succeed when it doesn't), not merely that an
   omitted hook happens not to error.
3. `"a Lookup permitting the reference is wired via build/1 and activation succeeds"`
   — the positive integration case: a `Lookup` whose `service_lookup` returns
   `{:ok, %{scope: :global, owner_tenant_id: nil}}`, wired the same way, activation
   succeeds — proves `build/1`'s closure is not merely "always blocks," closing the gap a
   test suite containing only case 1 would leave.

### AC5 — moduledoc names the ServiceCatalog/PluginRegistry gap and their owning stages

See `service_scope_validator_test.exs`, describe block
`"moduledoc -- AC5: ServiceCatalog/PluginRegistry dependency gap is named, with owning stages"`
— pure, database-free, reads `Letflow.Definitions.ServiceScopeValidator`'s compiled
moduledoc via `Code.fetch_docs/1` (this file's own local `normalized_moduledoc/1` helper,
matching the same pattern independently established in `definitions_test.exs`,
`promotion_review_test.exs` — each test file defines its own copy rather than sharing one
across files, confirmed by direct comparison of both):

1. `"the moduledoc names ServiceCatalog as the real service-registry dependency and attributes it to stage S6"`
2. `"the moduledoc names PluginRegistry as the real plugin-dispatch dependency and attributes it to stage S3"`
3. `"the moduledoc states this module does NOT implement or depend on either dependency today"` —
   the "rather than implying real catalog integration exists today" half of AC5's wording,
   tested as its own assertion rather than assumed to follow from the two stage-naming
   assertions above.

## Additional coverage flagged by the design/review process (not incidental)

### Asymmetry 1 (INV-SSV-5) — plugin not-registered passes, service not-registered fails

See describe block `"validate/3 -- asymmetry 1 (INV-SSV-5): plugin not-registered passes, service not-registered fails"`:

1. `"a not-registered plugin_handler passes validation (no violation)"` — own named test,
   not folded into AC3's service-side not-registered test. This is one of the two most
   scrutinized design decisions in this requirement (design doc §5's "why the first
   asymmetry is preserved" note, citing R-Co's `checkPluginHandler` line 220-222
   verbatim) — pinned explicitly so a future change collapsing the two branches together
   is caught immediately.
2. `"the identical not-registered condition on the service side (not plugin) still fails -- confirms the asymmetry is real, not a validator that just never fails on 'not registered'"`
   — direct contrast in the same test, both checked against the same kind of Lookup
   result shape, so the asymmetry is demonstrated by contrast rather than merely
   asserting the plugin side alone (which alone wouldn't rule out a broken validator that
   never fails on `:not_registered` for either kind).

### Asymmetry 2 (INV-SSV-7 vs. INV-SSV-9) — nil `owner_tenant_id` on tenant scope: violation for service, pass for plugin

See describe block `"validate/3 -- asymmetry 2 (INV-SSV-7 vs INV-SSV-9): nil owner_tenant_id is a violation for service, a pass for plugin"`:

1. `"a tenant-scoped service lookup with owner_tenant_id: nil is a violation (:service_not_available_to_tenant, 'scope data is inconsistent')"`
   — pins INV-SSV-7's exact reason atom AND exact message text (design doc §5 service
   table row 4's verbatim template), not just "some error."
2. `"the identically-shaped tenant-scoped PLUGIN lookup with owner_tenant_id: nil is a PASS -- the exact inverse of the service-side case above"`
   — pins INV-SSV-9, the CODE-DESIGN-VALIDATOR-rework-triggering decision (per this run's
   task briefing) — its own named test case, not incidentally covered by any other
   assertion, with the contrast to case 1 made explicit in the test's own name and body
   (same malformed-shape input, opposite outcome by kind).

### First-violation-wins / short-circuit semantics

See describe block `"validate/3 -- first-violation-wins: Enum.reduce_while/3 genuinely halts, proven not just asserted"`:

1. `"a graph with 2 violating SERVICE_TASK nodes returns only the FIRST node's violation, and the second node's lookup function is never called"`
   — two SERVICE_TASK nodes, in graph order, both referencing not-registered
   `service_id`s. The SECOND node's `service_lookup` function `raise`s unconditionally if
   invoked. Asserts the returned violation's `node_id` matches the FIRST node only, and
   (since a raise inside `Enum.reduce_while/3`'s callback would propagate and fail the
   test with that exception, not silently pass) the test passing at all is itself proof
   the second lookup was never called — the same "prove it, don't assert around it"
   technique `store_test.exs`'s existing AC6 block already established for
   `activate/2`'s hook (`exploding_validator`), applied here to `validate/3`'s own
   internal short-circuit.
2. `"a violation on the service check for a node short-circuits before that same node's plugin check runs"`
   — one SERVICE_TASK node with BOTH a violating `service_id` AND a `plugin_handler`
   attribute present; the `plugin_lookup` function `raise`s unconditionally if invoked.
   Confirms the `with` chain in `check_node/3` (service check before plugin check, design
   doc §5 step 2b before 2c) halts at the first `{:error, _}` within a single node too,
   not only across nodes.

### Malformed/garbage lookup results fail closed (SECURITY-REVIEWER OQ-1)

See describe block `"validate/3 -- malformed Lookup results fail closed, never silently pass (SECURITY-REVIEWER OQ-1)"`:

1. `"a service_lookup returning a completely out-of-contract value raises rather than silently passing"`
   — `service_lookup` returns `:not_a_valid_result_shape_at_all` (neither `{:ok, _}` nor
   `{:error, :not_registered}`). Asserts `validate/3` raises (`FunctionClauseError` or
   `CaseClauseError`, matched loosely via `assert_raise` on the base `RuntimeError` chain
   or explicitly on both concrete exception modules) rather than returning `:ok` — proving
   the "fail closed, never fail open" property OQ-1 and REVIEWER's Step 2d sign-off both
   rely on, exercised directly rather than trusted from the design doc's prose.
2. `"a plugin_lookup returning a completely out-of-contract value also raises rather than silently passing"`
   — same proof, mirrored for the plugin side (the two sides have independent clause sets
   in the implementation, so this is not redundant with case 1 — a bug fixing only one
   side's exhaustiveness would leave the other silently permissive).

### Nodes with no service_id/plugin_handler, and non-SERVICE_TASK nodes, are skipped (not misclassified)

See describe block `"validate/3 -- nodes with no service_id/plugin_handler attribute, and non-SERVICE_TASK nodes, are skipped"`:

1. `"a SERVICE_TASK node with attributes: nil contributes no violation and is skipped entirely"`
   — ports the design doc §5 step 2a / `.zig` line 65 case (`check_node/3`'s first clause
   head). Uses a `Lookup` whose both functions `raise` if called at all, so the test
   passing at all proves the node was truly skipped, not that its lookups happened to
   pass.
2. `"a SERVICE_TASK node with attributes present but neither 'service_id' nor 'plugin_handler' keys contributes no violation"`
   — same raise-if-called technique, `attributes: %{"other_key" => "value"}`.
3. `"a SERVICE_TASK node whose service_id attribute is an empty string, or not a string at all, is skipped for that key (INV-SSV-3)"`
   — three sub-cases in one test: `""`, `123` (non-string), and a missing key entirely,
   each confirmed to perform no `service_lookup` call (raise-if-called `Lookup`).
4. `"a non-SERVICE_TASK node (e.g. HUMAN_TASK) carrying a service_id-shaped attribute is never inspected at all"`
   — a `HUMAN_TASK` node with `attributes: %{"service_id" => "some-service"}` and a
   raise-if-called `Lookup`; the graph walk's own `Enum.filter(&(&1.node_type ==
   :SERVICE_TASK))` (design doc §5 step 1) means this attribute is never read regardless
   of its shape — proves node-type filtering happens before attribute inspection, not
   that this particular attribute value happens to be treated as absent.
