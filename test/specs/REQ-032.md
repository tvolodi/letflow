## Acceptance criterion 1 — a well-formed interface passes validation and is persisted unchanged

> "a SUB_PROCESS node with a well-formed interface (valid inputs/outputs, well-formed
> json_schema on each entry) passes validation and is persisted unchanged as part of the
> node's attributes"

| # | Test case | Why this exists (not just the criterion restated) |
|---|---|---|
| 1 | `sub_process_interface_test.exs` — `nil (the interface attribute absent entirely) is valid, not a violation` | AC1's boundary companion: `interface` is documented **optional** — this locks in that the single case across CHK-01..18 where "attribute entirely absent" is legal, not a violation, actually holds, distinguishing it from the `_NOT_OBJECT` tests below where the attribute IS present with the wrong shape. |
| 2 | `sub_process_interface_test.exs` — `valid inputs/outputs with well-formed json_schema on each entry -> zero violations, expected parsed shape` | The literal AC1 demonstration: two `inputs` entries (one with `required` explicitly `true`, exercising a non-default value) and one `outputs` entry, asserting the **exact** returned `{parsed, []}` shape (not just `violations == []`) — catches a bug that silently drops or mis-shapes an otherwise-valid entry while still reporting zero violations. |
| 3 | `sub_process_interface_test.exs` — `an interface with both 'inputs' and 'outputs' absent (empty object) is well-formed` | The other AC1-adjacent boundary: `interface: {}` (present, but neither key given) is legal per design doc §7.1's chosen default, not a `_INPUTS_NOT_ARRAY`/`_OUTPUTS_NOT_ARRAY` violation. |
| 4 | `graph_test.exs` — `a SUB_PROCESS node with a well-formed interface passes validation, and its attributes are returned/persisted unchanged` | The **integration** half of AC1, which the pure sibling-module tests above can't reach: drives the exact same interface through `Graph.validate_node_attributes/1` (the real CHK-18 call path a definition-creation flow would use) and asserts both `%{valid: true, violations: []}` **and** that the `Node`'s own `attributes` map, captured before the call, is bit-identical after — the concrete demonstration of design doc §5.4's "never mutates or re-serializes what it validates; the original `attributes` map is what gets persisted" claim. A future change that made CHK-18 return a transformed/re-serialized attributes value (violating §5.4) would fail this test even though it might still report `valid: true`. |
| 5 | `graph_test.exs` — `a SUB_PROCESS node with no 'interface' attribute at all is valid` | AC1's "optional attribute" case at the integration level, mirroring test 1 above but through the real `Graph.validate_node_attributes/1` call path rather than the bare `parse_interface/2` call. |

## Acceptance criterion 2 — each of the 6 named violation codes

> "each of the 6 named violation codes has at least one explicit failing-example test"

All 6 are tested directly against `parse_interface/2` (bare `interface_value` terms, no
`Graph.t()` needed), in `sub_process_interface_test.exs`:

| Code | Test case | Why this exists |
|---|---|---|
| `SUB_PROCESS_INTERFACE_NOT_OBJECT` | `interface_value present but not a JSON object -> :sub_process_interface_not_object, and only that code` (5-way loop: string, integer, `true`, `false`, list) | Covers every non-map JSON type distinctly — a naive implementation that only checks `is_binary`/`is_list` (missing booleans or integers) would pass a narrower single-example test but fail this one. Also asserts the violation message names the node id. |
| `SUB_PROCESS_INTERFACE_INPUTS_NOT_ARRAY` / `_OUTPUTS_NOT_ARRAY` | Two isolated tests (`'inputs' present but not a JSON array -> ...`, `'outputs' present but not a JSON array -> ...`) plus `both 'inputs' and 'outputs' non-array at once -> both codes fire, never-short-circuit` | The two isolated tests prove each code fires independently and alone (not the other one too); the combined test locks in design doc §5.3 step 3b's explicit "can both fire on the same `interface_value`, never-short-circuit" rule — an implementation that stopped after the first non-array key would pass the two isolated tests but fail this one. |
| `SUB_PROCESS_INTERFACE_ENTRY_INVALID` | `every distinct entry-shape defect -> :sub_process_interface_entry_invalid, and only that code` (8-way loop: non-map entry, empty map, blank name, whitespace-only name, non-string name, missing `json_schema`, non-map `json_schema`, non-boolean `required`) + `an entry that fails the shape check is excluded from the parsed entry list` | The 8-way loop exercises every distinct branch of design doc §5.3.1 point 1's `_ENTRY_INVALID` trigger condition (the "or" chain) individually — a change that fixed/broke any one branch (e.g. stopped trimming whitespace before the blank check) would be caught by whichever loop iteration exercises that branch, where one hand-picked example would not distinguish which branch broke. The exclusion test locks in the "excluded from parsed output" half of §5.3 point f. |
| `SUB_PROCESS_INTERFACE_SCHEMA_INVALID` | `shape-valid entry with a malformed json_schema -> ..., entry still included in parsed output` | Proves both the code fires **and** the entry is still returned in the parsed list (design doc §5.3.1 point 2 — deliberately different inclusion behavior from `_ENTRY_INVALID`, since the tuple shape itself is valid). A regression that treated `_SCHEMA_INVALID` like `_ENTRY_INVALID` (excluding the entry) would fail only this test, not the `_ENTRY_INVALID` ones. |
| `SUB_PROCESS_INTERFACE_DUPLICATE_NAME` | `a name repeated within 'inputs' -> ..., N occurrences -> N-1 violations` (3 occurrences), `a name repeated within 'outputs' -> ...`, `the same name in both 'inputs' and 'outputs' is NOT a duplicate`, `an entry excluded for _ENTRY_INVALID never participates in duplicate-name detection` | 3 occurrences (not 2) strengthens the "N-1, not N" claim past the minimal case, mirroring REQ-029's own 3-default-edges precedent — an implementation that special-cased exactly 2 duplicates would pass a 2-occurrence test but fail this one. The inputs/outputs-independence test is the literal "worth covering" item from this run's brief and REQ-032's own text ("duplicate name **within** inputs or **within** outputs" — not across). The last test locks in design doc §5.3.2's "only entries that parsed a reliable name are dedupe candidates" scoping rule. |

**Integration-level wiring proof (not a duplicate of the above — a distinct failure mode
it alone catches), `graph_test.exs`:**
- `a SUB_PROCESS node with a malformed interface -> the delegate's violation appears in
  validate_node_attributes/1's result` — proves CHK-18 is actually wired into the check
  list and its result concatenated, not merely that the delegate is correct in
  isolation (same "wiring" shape as REQ-029's own CHK-17 precedent in this file).
- `two SUB_PROCESS nodes, each with a distinct violation -> both surface,
  never-short-circuit, node ids attributed correctly` — proves CHK-18 iterates every
  SUB_PROCESS node in the graph (not just the first) and correctly attributes each
  violation's message to its own node id.
- `a non-SUB_PROCESS node carrying an 'interface'-shaped attribute is never checked by
  CHK-18` — proves the type filter is real, not accidental (a HUMAN_TASK node with a
  malformed `"interface"` key present is never flagged, since CHK-18 only applies to
  SUB_PROCESS nodes).

## Acceptance criterion 3 — unsupported-but-inert json_schema keywords are accepted

> "an interface entry's json_schema containing an unsupported-but-recognized-as-inert
> keyword (e.g. $ref or pattern) is accepted, not rejected, per spc-01's 'permitted and
> inert' rule"

| Test case | Why this exists |
|---|---|
| `the design doc §6 worked example ($ref/pattern on a nested schema) is accepted` | The exact worked example the design doc gives TEST-DESIGNER (§6) — ties `$ref`/`pattern` on a **nested** schema (inside `properties`) together with every supported keyword (`type`, `properties`, `required`, `additionalProperties`) all validating together, proving unsupported keywords don't interfere with supported-keyword validation elsewhere in the same schema. |
| `a schema consisting entirely of unsupported keywords is accepted (nothing left to fail)` | The degenerate case: a schema with **zero** supported keywords must still return `true` (`Enum.all?` over an empty filtered list), not `false` by some accidental "must have at least one recognized keyword" requirement nowhere stated in the design. |
| `end-to-end: an interface entry whose json_schema uses only inert unknown keywords produces zero violations` | Confirms AC3 holds through the full `parse_interface/2` path (not just `validate_schema_shape/2` in isolation) — proves an entry isn't independently flagged `_ENTRY_INVALID` or `_SCHEMA_INVALID` just because its schema is "unusual." |

## Acceptance criterion 4 — the 32-level recursion depth cap

> "a json_schema nested beyond the 32-level recursion cap is rejected as malformed"

Built as an **exact** 32-deep (accepted) / 33-deep (rejected) boundary pair, per this
run's brief and design doc §6's precise depth-numbering convention (entry's own
top-level schema = depth 1; a call at `depth > 32` returns `false` immediately) — not
just "very deep."

`nested_schema/1` (`sub_process_interface_test.exs`) builds this via `"items"`
recursion: `nested_schema(1) = %{"type" => "string"}` (a leaf, depth-1, no recursion);
`nested_schema(n) = %{"items" => nested_schema(n - 1)}` for `n > 1`. Hand-traced in the
test file's own helper comment: `validate_schema_shape(nested_schema(n), 1)` makes its
**deepest** recursive call at `depth = n` (each `"items"` descent increments depth by
1, starting the top-level call at depth 1) — so `nested_schema(32)`'s deepest call is at
depth 32 (`32 > 32` is false, accepted) and `nested_schema(33)`'s deepest call is at
depth 33 (`33 > 32` is true, rejected, and that `false` propagates back up through every
enclosing `is_map`/`Enum.all?` check).

| # | Test case | Why this exists |
|---|---|---|
| 1 | `a schema nested exactly 32 levels deep is accepted -- the maximum accepted depth` | The exact upper boundary the design doc pins as still-legal — an off-by-one implementation (`depth >= 32` instead of `depth > 32`) would wrongly reject this. |
| 2 | `a schema nested 33 levels deep is rejected -- one level beyond the cap` | The exact one-level-over boundary — an off-by-one the other direction (`depth > 33`) would wrongly accept this. Tests 1 and 2 together pin the cap to the single correct value; either alone would leave an off-by-one undetected. |
| 3 | `depth > 32 rejects immediately regardless of schema content, even an otherwise-trivial schema` | Exercises design doc §6 step 1 (the depth guard itself) directly and independently of the recursive-building helper — a call already past the cap must reject even `%{}` or a trivially valid `%{"type" => "string"}`, proving the guard runs *before* any content inspection, not as a fallback after content already failed some other check. |
| 4 | `end-to-end: an entry with a 33-deep json_schema -> :sub_process_interface_schema_invalid` | Confirms AC4 holds through the full `parse_interface/2` path — the entry is still included in the parsed output (same rule as the `_SCHEMA_INVALID` describe block), proving depth-cap rejection is reported through the same code as any other schema malformation, not a distinct 7th code. |
| 5 | `end-to-end: an entry with a 32-deep json_schema produces zero violations` | The end-to-end mirror of test 1 — proves the boundary holds through the real call path a SUB_PROCESS node's interface entry would actually take, not just the bare `validate_schema_shape/2` call. |

## Also covered per the design's own algorithm detail (this run's brief, beyond the 5 named ACs)

- **`required` defaulting to `false` when absent** — `sub_process_interface_test.exs`:
  `an entry with no 'required' key parses with required: false` and, as a negative
  control, `an entry with 'required': true is not overridden by the default` (proves the
  default only applies when the key is *absent*, not that `required` is unconditionally
  forced to `false`).
- **Duplicate-name detection scoped separately per list** — covered under AC2 above
  (`the same name in both 'inputs' and 'outputs' is NOT a duplicate`).
- **The full supported-keyword set, each accepted at least once** — `validate_schema_shape/2
  -- the full supported-keyword set` describe block: a table-driven test over all 11
  keyword/value-form combinations (`type`, `minimum`, `maximum`, `minLength`,
  `maxLength`, `enum`, `required` (the schema-meta-keyword, not the entry-tuple field —
  labeled explicitly to avoid the naming collision design doc §6 flags), `properties`,
  `items`, and `additionalProperties` in both its boolean and schema-object forms) —
  each individually accepted. Extended one step further than the brief's minimum ask: a
  second table-driven test asserts each of the same keywords **rejects** a malformed
  value, so a keyword whose validation rule is accidentally missing entirely (always
  returns `true` regardless of value) is also caught — the accept-only table alone
  cannot distinguish "correctly validates" from "never actually checks this keyword."
