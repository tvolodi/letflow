# Test Spec: REQ-033 — Definition snapshot store (`Letflow.Definitions.SnapshotStore`)

**Requirement:** REQ-033 (`docs/requirements.yaml` lines 1506–1553, stage S2,
`depends_on: [REQ-027]`) — verbatim acceptance criteria:

1. "create/2 against a valid definition_id inserts a snapshot row whose graph
   matches the source process_definitions row's graph at the moment of the
   call"
2. "create/2 called twice with the same instance_id is idempotent (no error,
   no second row) OR returns a distinct SnapshotAlreadyExists-equivalent
   error -- pick one behavior and state which in the moduledoc, since
   definition.md's own text supports the idempotent reading for an EE-01
   retry"
3. "get_by_instance_id/1 against an instance_id with no snapshot returns a
   not-found error, not nil silently"
4. "deleting a process_definitions row that an instance_definition_snapshots
   row references is rejected by the database (foreign_key_violation), and
   the snapshot row remains present and unmodified -- per PD-08's
   no-ON-DELETE-CASCADE design (REQ-027); a snapshot is never removed as a
   side effect of deleting its source definition"
5. "the moduledoc explicitly states the EE-01 instance-start integration
   point is S3 scope, not built here"

**Plus two load-bearing cases beyond the 5 numbered criteria:**

- **REVIEWER's explicit Step 2d recommendation** (design doc §4.3, §9 OQ-2):
  a `create/3` retry for an already-snapshotted `instance_id`, called with a
  **different** `definition_id` than the original call, is silently
  discarded — first-writer-wins, the original snapshot is returned unchanged,
  no error. REVIEWER confirmed this design choice at Step 2d and specifically
  asked for a test pinning this exact behavior (distinct from the
  same-`definition_id` retry case AC2 already covers), so a future change
  that "fixes" this into an error/mismatch-detection path is a deliberate
  decision, not an accidental regression nobody notices.
- **INV-8 UUID-cast guards**, added by ELIXIR-DEV as a documented deliberate
  divergence from the design doc's literal §4.3 text (`snapshot_store.ex`
  moduledoc, "Deliberate divergence..." section): `create/3`'s
  `instance_id`/`definition_id` and `get_by_instance_id/2`'s `instance_id`
  are each validated via `Ecto.UUID.cast/1` before any query runs. A
  malformed value (non-UUID string, `nil`, a struct) must return a typed
  `{:error, :invalid_instance_id}` / `{:error, :invalid_definition_id}`,
  never raise `Ecto.Query.CastError`. `opts[:prefix]` missing/blank must
  return `{:error, :missing_prefix}`, also without raising.

**Test tier:** unit+integration (real Postgres via `Letflow.DataCase`, no
mocked DB per `docs/guides/test_developer_guide.md` DIRECTIVE T-1).

## Fixture strategy — read this before the test cases below

Mirrors `test/letflow/event_store_test.exs`'s and
`test/letflow/definitions/migrations_test.exs`'s established
`provisioned_tenant/1` pattern: each test provisions its own tenant (real
`CREATE SCHEMA` via `TenantProvisioning.provision_tenant_schema/1`, real
`TenantProvisioning.replay_migrations/1`), so every test starts from a
genuinely fresh, empty tenant schema. `Ecto.Adapters.SQL.Sandbox` is switched
to `:auto` mode (not the normal rolled-back sandbox transaction) because
`Ecto.Migrator` needs its own real DB connection the sandbox can't hand out —
same reasoning as `event_store_test.exs`'s and `migrations_test.exs`'s own
moduledocs. `async: false` for the whole module, for the same reason those
two files are `async: false`.

Every test inserts its own `process_definitions` row(s) directly via
`ProcessDefinition.create_changeset/2` + `Repo.insert!/2` (never through a
not-yet-built REQ-030 CRUD layer) and uses a fresh `Ecto.UUID.generate()` for
every `instance_id`/`definition_id` — no shared or hard-coded identifiers, no
test depends on another test's data or on execution order.

## Test cases

1. **AC1 — a valid `create/3` call copies the source definition's graph at
   the moment of the call** — see `test/letflow/definitions/snapshot_store_test.exs`
   `"create/3 (AC1)"` describe block, test `"create/3 inserts a snapshot row whose graph, name and version match the source process_definitions row"`.
   Inserts a `process_definitions` row with a distinctive, non-default graph,
   calls `create/3`, and asserts both the in-memory reply's `graph` and a
   fresh `Repo.get/3` re-select of the `instance_definition_snapshots` row
   equal the source row's graph exactly (also `definition_name`/
   `definition_ver`) — proving the copy, not just "some row got created."

2. **AC2 — same-`instance_id` retry is idempotent: no error, no second row**
   — see `"create/3 idempotency (AC2)"`, test
   `"a second create/3 call with the SAME instance_id and SAME definition_id returns the pre-existing snapshot, inserts zero additional rows"`.
   Calls `create/3` twice with identical arguments, asserts both calls return
   `{:ok, snapshot}` with the same `snapshotted_at` (proving the second call
   did not re-insert and get a fresh timestamp), and asserts the table's row
   count for that `instance_id` stays at exactly 1.

3. **REVIEWER-recommended — differing-`definition_id` retry is silently
   discarded (first-writer-wins), not an error** — see
   `"create/3 idempotency (AC2)"`, test
   `"a second create/3 call with the SAME instance_id but a DIFFERENT definition_id is silently discarded -- the original snapshot is returned unchanged, no error"`.
   Inserts two distinct `process_definitions` rows, calls `create/3` first
   with `definition_id_1`, then again with the same `instance_id` but
   `definition_id_2`. Asserts the second call still returns `{:ok, snapshot}`
   (not an error of any shape), and that the returned/re-selected snapshot's
   `definition_id`/`definition_name`/`definition_ver`/`graph` all still match
   the **first** definition, never the second — pinning exactly the design
   doc's §9 OQ-2 / §4.3 "no `:instance_id_conflict`-shaped error" decision
   that REVIEWER confirmed at Step 2d.

4. **AC3 — `get_by_instance_id/2` on a miss returns a typed error, never
   `nil`** — see `"get_by_instance_id/2 (AC3)"`, test
   `"get_by_instance_id/2 for an instance_id with no snapshot returns {:error, :snapshot_not_found}, never nil"`.
   Calls `get_by_instance_id/2` with a freshly generated `instance_id` that
   was never passed to `create/3`, and asserts the literal
   `{:error, :snapshot_not_found}` tuple — a regression to `nil` (e.g. an
   incautious `Repo.get/3` return threaded straight through) fails this test
   immediately since `nil` does not match the asserted pattern.

5. **AC4 — deleting a referenced `process_definitions` row is rejected by
   the database, snapshot survives unmodified** — see
   `"AC4 -- delete-rejection is not SnapshotStore's own code"`, test
   `"deleting a process_definitions row referenced by a snapshot raises Ecto.ConstraintError (foreign_key_violation) and the snapshot survives, byte-for-byte"`.
   Per the design doc §7, this exercises `Repo.delete/2` directly against the
   `process_definitions` row (not any `SnapshotStore` function — none exists
   to call), asserts it raises `Ecto.ConstraintError` naming the FK
   `instance_definition_snapshots_definition_id_fkey`, and then re-selects
   the snapshot via `get_by_instance_id/2` and asserts it is
   `{:ok, snapshot}` with every field unchanged from before the failed
   delete attempt.

6. **AC5 — moduledoc states the EE-01 integration point is S3 scope, not
   built here** — see `"AC5 -- moduledoc scope statement"`, a pure,
   database-free test reading `Code.fetch_docs/1` on
   `Letflow.Definitions.SnapshotStore` (mirroring
   `test/letflow/definitions/schemas_test.exs`'s `normalized_moduledoc/1`
   helper) and asserting the moduledoc text names EE-01, states the
   integration point is S3 scope, and states it is "not built here" in
   substance — a doc-content check per the requirement's own wording, not a
   runtime assertion.

7. **INV-8 guards — malformed `instance_id`/`definition_id`/`opts[:prefix]`
   each return a typed error, never raise** — see
   `"INV-8 UUID-cast and prefix guards"` describe block, covering:
   - `create/3` with a non-UUID-string `instance_id` → `{:error, :invalid_instance_id}`
   - `create/3` with a non-UUID-string `definition_id` → `{:error, :invalid_definition_id}`
   - `create/3` with a struct-shaped `instance_id` (e.g. a `%Date{}`) →
     `{:error, :invalid_instance_id}`, not a raised `Protocol.UndefinedError`
     or `Ecto.Query.CastError`
   - `create/3` with `opts` missing `:prefix` entirely, and with
     `prefix: ""` → both `{:error, :missing_prefix}`
   - `get_by_instance_id/2` with a malformed `instance_id` →
     `{:error, :invalid_instance_id}`
   - `get_by_instance_id/2` with `opts` missing `:prefix` →
     `{:error, :missing_prefix}`

   Each case additionally asserts the offending call writes zero rows (where
   applicable) — a pre-transaction guard that raised or silently proceeded
   to attempt a query would be caught either by the raised exception
   surfacing in the test itself, or by a nonzero row count.
