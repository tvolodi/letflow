# Test Spec: REQ-034 — Definition export/import (`export_import.zig`, PD-09)

**Requirement:** REQ-034 (`docs/requirements.yaml`, stage S2, `depends_on: [REQ-030]`)
**Design:** `lib/letflow/design/export_import.md` (validated by CODE-DESIGN-VALIDATOR)
**Implementation:** `lib/letflow/definitions/export_import.ex`
(`Letflow.Definitions.ExportImport`, `export/2`, `import/3`) — passed
SECURITY-REVIEWER and REVIEWER (Step 2d) before this test-design step began.
**Test tier:** integration (real Postgres via `Letflow.DataCase`, no mocked DB, per
`docs/guides/test_developer_guide.md` DIRECTIVE T-1). Both `export/2` and `import/3`
do real database I/O (`export/2` reads via `Definitions.get_by_id/2`, `import/3`
writes via `Definitions.create/2`) — nothing in this module is pure, so no
`async: true`/no-DB split like `definitions_test.exs` uses for REQ-041/parts of
REQ-030 applies here.

**Verbatim acceptance criteria (from `docs/requirements.yaml`, `id: REQ-034`):**

1. "export/1 on an existing definition produces a document whose graph field
   round-trips byte-for-byte comparable back through import/1's graph field"
2. "import/1 always assigns a new id distinct from the source document's id field,
   even when the source id happens to already exist as a definition in the target
   tenant"
3. "import/1 on a document with a graph that fails REQ-028's validateGraph() is
   rejected the same way REQ-030's create/1 rejects an invalid graph directly -- no
   bypass path"
4. "import/1 on a document whose bpm_export_schema_version is not
   \"bpm/definition/v1\" is rejected with a distinct unknown-schema-version error"

**Naming note:** the requirement text says `export/1`/`import/1`; the shipped,
CODE-DESIGN-VALIDATOR-passed signatures are `export/2` (`id`, `opts`) and `import/3`
(`document`, `imported_by`, `opts`) — `opts` (for tenant `:prefix`) and the required
`imported_by` parameter (design doc §4.3, OQ-3: `ExportDocument` carries no creator
identity, `create/2` requires `:created_by`) are additions the design doc flags
explicitly, not a naming mismatch worth re-litigating here.

**Per REVIEWER's Step 2d non-blocking note (recorded in this run's handoff chain):**
`import_error()`'s `create_error()` branch nominally includes `:tenant_id_not_accepted`
and `:initial_status_not_draft`, but neither is reachable through `import/3`'s own
`create_attrs()` builder (design doc §4.3 step I1: no `:tenant_id` key, no `:status`
key are ever built) — there is no code path by which `import/3` could produce either.
Not covered here; a test asserting against an unreachable branch would be manufactured
coverage, not real coverage.

## Fixture strategy

Mirrors `test/letflow/definitions/store_test.exs`'s established `provisioned_tenant/1`
pattern exactly (same helper, copied per that file's own precedent of each DB-backed
test file owning its own private fixtures rather than sharing a test-support module):
each test provisions its own tenant (real `CREATE SCHEMA` via
`TenantProvisioning.provision_tenant_schema/1`, real
`TenantProvisioning.replay_migrations/2`). `Ecto.Adapters.SQL.Sandbox` is switched to
`:auto` mode because `Ecto.Migrator` needs its own real DB connection the sandbox
can't hand out. `async: false` for the whole module, same reasoning as
`store_test.exs`/`snapshot_store_test.exs`.

Every test uses `unique_name/1` (`System.unique_integer/1`-suffixed) for every
definition `name` and a fresh `Ecto.UUID.generate()` for every `created_by`/
`imported_by` — no shared or hard-coded identifiers, no test depends on another
test's data or on execution order, no wall-clock dependency anywhere.

`valid_graph/0` is the same minimal structurally-valid graph `store_test.exs` uses
(one START with an outgoing edge to one END with an incoming edge).
`graph_with_task_and_extra_metadata/0` is a richer, still-valid graph (adds a
`HUMAN_TASK` node with a nested `attributes` map carrying both the required `"role"`
key and an unrelated `"note"` key) — used only by AC1, to prove the round trip
preserves a full nested map value, not just top-level keys or the keys `graph.ex`'s
own validators happen to read. `graph_missing_end_node/0` (same fixture shape as
`store_test.exs`'s) deliberately fails `validate_graph/1`'s CHK-02 check — used by
AC3.

## Test cases

### AC1 — `export/2`'s document graph and `import/3`'s imported-row graph round-trip byte-for-byte

See `test/letflow/definitions/export_import_test.exs`, describe block
`"export/2 + import/3 (AC1) -- graph round-trips byte-for-byte"`, test `"the source
row's graph, export/2's document graph, and the imported row's re-read graph are all
structurally equal"`.

Creates a definition (in one tenant) with `graph_with_task_and_extra_metadata/0`,
exports it (into a *second*, independently-provisioned tenant's `import/3` call — the
two tenants are unrelated, proving the round trip isn't accidentally relying on any
same-schema shortcut), then asserts Elixir structural (`==`) equality across the full
chain design doc §5 INV-EI-3 states: source row's persisted `graph` == `export/2`'s
`document.graph` == `import/3`'s returned `imported.graph` == the imported row's
`graph`, **re-read directly from Postgres** (not just the in-memory struct
`import/3` returns) — this last re-read is deliberate: it proves fidelity survives
the real jsonb encode/decode round trip, which a test that only checked the returned
struct could miss if, say, `create/2`'s insert path silently normalized the value on
write without the returned struct reflecting it.

Why this test exists: `graph` is a map value that passes through two separate `cast`
boundaries (`export/2`'s struct-copy into `ExportDocument`, `import/3`'s
`create/2`-delegated `Ecto.Changeset.cast` into `:graph`) and one Postgres jsonb
round trip — any of the three is a plausible place for a naive implementation to
silently reorder keys, coerce types, or drop nested data; this test would fail if any
of them did.

### AC2 — `import/3` always assigns a new id, distinct from `document.id`, even under a real id collision

See describe block `"import/3 (AC2) -- always assigns a fresh id, distinct from
document.id"`, two tests:

1. `"the imported row's id differs from the exported document's id (basic case,
   different tenant)"` — the plain case: export from tenant A, import into tenant B,
   assert `imported.id != document.id`. Establishes the baseline before the sharper
   edge case below.

2. `"the imported row's id differs from document.id even when document.id already
   exists as a definition in the target tenant, and the pre-existing row is left
   untouched"` — the literal AC2 edge case. Exports a definition from tenant A (so
   `document.id` is a real, specific UUID), then, in tenant B (the *target* tenant for
   the import), directly inserts a pre-existing `process_definitions` row **whose id is
   set to that exact same UUID** (`document.id`), under an unrelated name/version so
   the later `import/3` call can't accidentally fail on the unrelated
   `uq_definition_version` constraint instead of exercising the id-collision path.
   Confirms the collision precondition is real (`count_by_id(target_schema,
   document.id) == 1` before the import call — something concrete actually occupies
   that id, not merely a hypothetical). Calls `ExportImport.import/3` and asserts:
   - `imported.id != document.id` (the id-collision id was not reused);
   - `count_by_id(target_schema, document.id) == 1` **after** the import too — the
     pre-existing collision row was not overwritten, duplicated, or removed;
   - the re-read collision row's `name`/`version` are unchanged from what was inserted
     before the import — not silently merged with the imported document's content;
   - the imported row lands under its own freshly-assigned id, re-read directly from
     Postgres, carrying the **source document's** `name`/`graph` — a genuinely
     separate row, not a same-id update.

   **Why a direct `Repo.insert!` fixture, not `create/2`.** `create/2`'s
   `create_changeset/2` never casts `:id` (confirmed directly,
   `lib/letflow/definitions/process_definition.ex`) — there is no way to make `create/2`
   itself produce a row under a caller-chosen id, so the only way to construct a real
   "this id already exists" precondition is to insert one directly.
   `insert_row_with_id!/4` builds `%ProcessDefinition{id: id}` (the struct's primary
   key pre-set to the caller-chosen, non-nil id) and passes it through
   `ProcessDefinition.create_changeset/2` before `Repo.insert!/2`.
   `@primary_key {:id, :binary_id, autogenerate: true}` only autogenerates a fresh id
   when the field is nil at insert time (confirmed by direct reading of
   `process_definition.ex` and by this test itself actually passing — the inserted
   row's id doesn't get silently replaced) — a pre-set non-nil id is preserved through
   `Repo.insert!/2` unchanged. Verified empirically, not just reasoned about: this
   run's actual `mix test` execution (below) shows the collision row landing under
   the exact requested id and the assertions against it passing.

### AC3 — `import/3` rejects an invalid graph identically to a direct `create/2` call — no bypass path

See describe block `"import/3 (AC3) -- an invalid graph is rejected identically to a
direct create/2 call, no bypass"`, test `"import/3 and a direct create/2 call built
from the same attrs return the identical rejection, both write zero rows"`.

Builds one `ExportDocument` whose `graph` is `graph_missing_end_node/0` (fails
`validate_graph/1`'s CHK-02, the same fixture shape `store_test.exs`'s AC1 coverage
uses for REQ-030's own `create/2`). Then builds `direct_attrs` that mirror **exactly**
what design doc §4.3 step I1 says `import/3` itself constructs internally (`name`,
`version`, `description`, `graph`, `created_by` — no `:id`, no `:tenant_id`, no
`:status`), and calls `Definitions.create/2` with those attrs directly, alongside
calling `ExportImport.import/3` with the `ExportDocument`. Asserts:

- both calls return `{:error, {:graph_validation_failed, violations}}` (not some other
  shape);
- the returned `violations` lists are **identical** between the two calls (not just
  "both errored" — the exact same violation codes/messages), and the full two return
  values (`import_result == direct_result`) are asserted equal;
- both calls wrote zero rows (`count_by_name/2` == 0 for the shared name).

This is the strongest available proof of "no bypass path" (INV-EI-2): if `import/3`
ran any validation logic of its own — even logic that happened to reach the same
verdict via a different path — a coincidental difference in violation ordering,
message text, or an extra/missing violation would fail this test's equality
assertion. Only a genuine pass-through to the exact same `create/2` call survives it.

### AC4 — a schema-version mismatch is rejected with a distinct `{:error, {:unknown_schema_version, actual}}`

See describe block `"import/3 (AC4) -- a schema-version mismatch is rejected with a
distinct unknown-schema-version error"`, test `"an otherwise-fully-valid document with
a mismatched schema version is rejected distinctly, not as a create_error(), writes
zero rows"`.

Builds an `ExportDocument` with `bpm_export_schema_version: "bpm/definition/v0"` (a
plausible prior-version string, not an arbitrary garbage value) but an **otherwise
fully valid** body — `valid_graph/0`, a fresh unique name, a valid version string.
This is deliberate: if the schema-version gate (design doc §4.3 step I0) were skipped
or bypassed and the document reached `create/2` anyway, it would **succeed** (valid
graph, valid attrs) rather than merely fail differently — so this test would catch
both "gate skipped and document silently imported" and "gate skipped and document
rejected by the wrong error shape," not just the latter.

Asserts the exact return value `{:error, {:unknown_schema_version, "bpm/definition/v0"}}`
(not just a loose pattern match), an explicit `refute match?({:error,
{:graph_validation_failed, _}}, result)` naming the specific `create_error()` shape
this document would otherwise plausibly trigger if the gate were bypassed, and zero
rows written for that name.

## Coverage check

- [x] AC1 — 1 test, full round-trip chain (source row -> `document.graph` ->
      `imported.graph` -> re-read-from-Postgres `graph`), using a graph rich enough
      (nested `attributes` map, an unrelated extra key) to catch a shallow-copy bug.
- [x] AC2 — 2 tests: the baseline case, and the literal collision edge case (a real
      pre-existing row under `document.id` in the target tenant, proven not
      overwritten/duplicated).
- [x] AC3 — 1 test, `import/3` vs. a direct `create/2` call built from the exact attrs
      `import/3` itself constructs, asserting the two return values are identical, not
      just both errors.
- [x] AC4 — 1 test, an otherwise-fully-valid document (so the gate is the only thing
      that could reject it) rejected with the exact distinct tuple, structurally
      unreachable as a `graph_validation_failed`.
- [x] No test depends on wall-clock time or unseeded randomness — all identifiers are
      `System.unique_integer/1`-suffixed or `Ecto.UUID.generate()`.
- [x] No shared/hardcoded fixtures — every test provisions its own tenant(s); no test
      reads another test's data or depends on execution order.
- [x] No hardcoded secrets/connection strings — DB config comes from
      `config/test.exs` (already-existing, not touched by this change).
- [x] Both `create_error()` variants unreachable through `import/3` (
      `:tenant_id_not_accepted`, `:initial_status_not_draft`) deliberately not
      covered, per REVIEWER's Step 2d note — see above.
