# Test Spec: REQ-035 — Promotion reviews schema (`promotion_reviews`, PRM-04 Type C part)

**Requirement:** REQ-035 (`docs/requirements.yaml`, stage S2, `depends_on: [REQ-022]`) —
add `priv/repo/migrations/20260816200001_create_promotion_reviews.exs` and
`lib/letflow/definitions/promotion_review.ex` (`Letflow.Definitions.PromotionReview`),
using REQ-022's schema-per-tenant `:prefix` mechanism. Schema only — REQ-037's
transition functions and REQ-036's plan/digest computation are explicitly out of
scope (design doc `lib/letflow/design/req035-promotion-reviews-schema.md` §1).

**Requirement's acceptance criteria (verbatim from `docs/requirements.yaml`):**

1. "priv/repo/migrations gains a promotion_reviews migration (schema-per-tenant per
   REQ-022) applying cleanly, with status as an Ecto.Enum over exactly the 6 named
   values"
2. "the partial unique index on (tenant_id, plan_digest) WHERE status IN
   ('pending_review', 'approved') exists and is demonstrated to reject a second
   pending_review insert with the same (tenant_id, plan_digest) while a first is still
   pending_review or approved"
3. "row_version defaults to 1 and the schema module documents it as an
   optimistic-locking column, not a plain counter"
4. "the moduledoc flags def_type's open-ended text-vs-CHECK-constraint choice and the
   PER_TENANT-vs-GLOBAL classification as explicit open questions, per prm-04's own
   Open Question 1 and this requirement's description"

**Test tier:** unit + integration, following REQ-027's established split. The
`Ecto.Schema` module's changeset, enum reflection and moduledoc are pure (no I/O) and
tested standalone; the migration, its two indexes, index predicates, column
nullability/defaults and the partial unique index's actual rejection/acceptance
behaviour are asserted against **real Postgres** (`docs/guides/test_developer_guide.md`
DIRECTIVE T-1 — no mocked database), after REQ-022's provision-then-replay mechanism
has applied the migration into a real per-test tenant schema.

## What is and isn't DB-enforced (read before AC1's tests)

`status` is declared `Ecto.Enum` in the schema (`lib/letflow/definitions/promotion_review.ex`)
but the migration column is a plain `:string` (`varchar(255)`) with **no** `CHECK`
constraint (`priv/repo/migrations/20260816200001_create_promotion_reviews.exs:61`, and
its own header comment says so explicitly). This means:

- **Enforced:** a `cast/3` (or any changeset built through `Ecto.Changeset.cast/3` on
  `:status`) rejects a 7th value that is not one of the 6 named atoms/strings — this is
  `Ecto.Enum`'s `Ecto.Type` callback behaviour, entirely in-process, never touching the
  database.
- **NOT enforced:** a raw SQL `INSERT`/`UPDATE` that bypasses the schema entirely can
  write an arbitrary string into the `status` column — Postgres itself has no rule
  against it. This suite states this explicitly and demonstrates it once (rather than
  silently leaving it unverified), so nobody later reads AC1 as if the *database*
  guarantees the enum, when only the application layer does.

## Files

- `test/letflow/definitions/promotion_review_test.exs` — **new file**. Pure,
  `async: true`, no `Letflow.Repo`/`Ecto.Adapters.SQL.Sandbox` dependency: reads only
  compiled module metadata (`__schema__/1`, `__info__/1`, `Ecto.Enum` reflection) and
  the compiled `Docs` chunk via `Code.fetch_docs/1`. Matches
  `test/letflow/definitions/schemas_test.exs`'s established shape.
- `test/letflow/definitions/promotion_review_migration_test.exs` — **new file**.
  DB-touching, `async: false`, `use Letflow.DataCase`, switches the sandbox to `:auto`
  mode for the same reason `test/letflow/definitions/migrations_test.exs` and
  `test/letflow/event_store/migrations_test.exs` do: `Ecto.Migrator` needs a second,
  genuinely independent connection (it locks `schema_migrations`), which a sandboxed
  pool will not hand out. Cleans up in `on_exit/1`, registered before anything that can
  fail.

### Cleanup discipline (the database is shared)

Every test that provisions a tenant schema registers its `on_exit/1` cleanup **before**
the work that could fail, so the schema, its `Registration` row and its `Tenant` row are
dropped on the failure path as well as the passing one. No test writes to `public`.

## Test cases

### Acceptance criterion 1 — migration applies cleanly, schema-per-tenant, `status` is an `Ecto.Enum` over exactly the 6 named values

1. **`replay_migrations/2` applies the REQ-035 migration and `promotion_reviews` lands
   in the tenant's own schema, never in `public`** —
   `promotion_review_migration_test.exs`: *"replay_migrations/2 applies the REQ-035
   migration and promotion_reviews lands in the tenant's own schema, never in public"*.
   The `public` half is what actually proves `:prefix` is doing the work — a migration
   that ignored `:prefix` would still satisfy a naive "does the table exist" check.
2. **The migration is registered in `tenant_scoped_migrations/0`** —
   `promotion_review_migration_test.exs`: *"CreatePromotionReviews is registered in
   tenant_scoped_migrations/0"*. REQ-022 §4: a guarded-but-unregistered migration is
   inert forever — no other test in this file would notice, since they all go through
   `replay_migrations/2`, which only sees registered entries.
3. **The real column set in the tenant schema equals `PromotionReview.__schema__(:fields)`
   exactly** — `promotion_review_migration_test.exs`: *"promotion_reviews' real column
   set matches PromotionReview.__schema__(:fields) exactly"*. Equality, not subset — an
   extra or missing column on either side is drift that surfaces later as a runtime
   `Postgrex` error in REQ-037.
4. **`Ecto.Enum.values/2` reflects exactly the 6 named atoms, in the requirement's
   order, and `Ecto.Enum.dump_values/2` shows they already dump lowercase** —
   `promotion_review_test.exs`: *"PromotionReview's status enum is exactly the 6 named
   values from REQ-035, and dumps lowercase"*. The lowercase half matters concretely
   here: both index predicates (`WHERE status IN ('pending_review', 'approved')` /
   `WHERE status IN ('applied', 'superseded')`) are written as lowercase string
   literals — if the enum ever dumped a different case, both partial indexes would
   silently stop matching any row and nothing would raise.
5. **A raw `cast/3` on `:status` rejects a 7th, unnamed value; accepts each of the 6**
   — `promotion_review_test.exs`: *"casting :status directly rejects a value outside
   the 6 named enum values, and accepts each of the 6"*. `insert_changeset/2` itself
   deliberately never casts `:status` (design §5.1, INV-PR-3 — a newly-inserted review
   is always `:pending_review`), so this criterion's "rejected by the changeset" half is
   tested by casting `:status` directly through `Ecto.Changeset.cast/3`, which is where
   `Ecto.Enum`'s actual type-level enforcement lives, exercised precisely because that
   enforcement point is otherwise invisible from `insert_changeset/2`'s own test
   coverage.
6. **`status` carries no DB-level `CHECK` constraint — a raw SQL write of an
   out-of-enum string succeeds** — `promotion_review_migration_test.exs`: *"status
   carries no DB-level CHECK constraint -- a raw SQL write of an out-of-enum string
   succeeds"*. Exists so AC1 is not silently overclaimed as DB-enforced when only the
   application layer enforces it (see "What is and isn't DB-enforced" above) — this is
   the negative control for test 5.

### Acceptance criterion 2 — the partial unique index rejects a second live review, accepts one once the first is no longer live

7. **`uq_promotion_review_active_digest` is a real UNIQUE index over exactly
   `(tenant_id, plan_digest)` whose predicate names `status` and both literal values**
   — `promotion_review_migration_test.exs`: *"uq_promotion_review_active_digest is a
   PARTIAL unique index over (tenant_id, plan_digest) predicated on status IN
   (pending_review, approved)"*. Read from `pg_indexes`, not
   `information_schema.table_constraints`: `create unique_index(...)` emits `CREATE
   UNIQUE INDEX`, which the constraint views do not list at all.
8. **A second `pending_review` insert with the same `(tenant_id, plan_digest)` while
   the first is still `pending_review` is rejected as `{:error, changeset}`, not a
   raised `Ecto.ConstraintError`** — `promotion_review_migration_test.exs`: *"a second
   pending_review insert with the same (tenant_id, plan_digest) is rejected while the
   first is still pending_review"*. The error *shape* is part of the assertion:
   `insert_changeset/2`'s declared constraint name must match the real index name, or
   this raises instead of returning a changeset — exactly the error contract REQ-037's
   `insert_review/1` will depend on.
9. **The same rejection holds when the first row's status is `approved`, not just
   `pending_review`** — same test file: *"a second insert with the same
   (tenant_id, plan_digest) is also rejected while the first is approved"*. The
   predicate is `IN ('pending_review', 'approved')`, not just `= 'pending_review'` —
   without this case a test suite that only checked the `pending_review` half would
   pass against a strictly narrower (wrong) predicate.
10. **Once the first row's status moves to a value outside `{pending_review, approved}`
    (e.g. `rejected`, via `Repo.update_all` since REQ-037's transition functions don't
    exist yet), a second insert with the same `(tenant_id, plan_digest)` succeeds** —
    same test file: *"a second insert with the same (tenant_id, plan_digest) succeeds
    once the first review is no longer pending_review or approved"*. This is the
    discriminator design §4.3 calls for explicitly: without it, a bare unconditional
    unique index on `(tenant_id, plan_digest)` (wrong — would forbid ever re-submitting
    a superseded/rejected digest) would be indistinguishable from the correct partial
    index by every other test in this file.
11. **A second insert with a *different* `plan_digest` for the same tenant while the
    first is still pending succeeds** — same test file: *"a second pending_review
    insert with a different plan_digest for the same tenant succeeds"*. Discriminates
    the index's actual key: proves `plan_digest` is really part of the uniqueness
    scope, not just `tenant_id` alone.
12. **`insert_changeset/2` declares `uq_promotion_review_active_digest` by index name
    on `[:tenant_id, :plan_digest]`** — `promotion_review_test.exs`: *"insert_changeset/2
    declares uq_promotion_review_active_digest by index name on
    [:tenant_id, :plan_digest]"*. Pins the pure half of test 8/9's error-shape
    guarantee — fails in milliseconds with a precise message where 8/9 would fail
    end-to-end against Postgres.

### Acceptance criterion 3 — `row_version` defaults to 1, documented as optimistic-locking

13. **The DB column default for `row_version` is `1`, read back from a raw insert that
    omits the column entirely** — `promotion_review_migration_test.exs`: *"the DB
    column default for row_version is 1, from a raw insert that omits it"*. A raw SQL
    insert (not a changeset insert) is used deliberately: a changeset-mediated insert
    would send the schema module's own struct default and could never detect a
    disagreement between the migration's DB default and the schema's default — the same
    hazard REQ-027's `graph` default carry-forward exists to catch.
14. **A freshly built `%PromotionReview{}` struct's `row_version` is `1`** —
    `promotion_review_test.exs`: *"a freshly built PromotionReview struct's row_version
    default is 1"*. The schema-module-side half of the pair with test 13.
15. **`insert_changeset/2` never casts `:row_version`, even when an attacker-supplied
    attrs map includes it** — `promotion_review_test.exs`: *"insert_changeset/2 does
    not cast :row_version even when attrs supply one"*. If this were ever castable, a
    caller could insert a review with an arbitrary starting `row_version`, undermining
    REQ-037's `WHERE row_version = $expected` concurrency guard from row zero.
16. **The moduledoc states `row_version` is an optimistic-locking column, not a plain
    counter, with the exact contract text design §7.1 mandates** —
    `promotion_review_test.exs`: *"PromotionReview's moduledoc documents row_version as
    an optimistic-locking column, not a plain counter"*. Read through
    `Code.fetch_docs/1`, so it asserts on what the module actually publishes.

### Acceptance criterion 4 — moduledoc flags both open questions

17. **The moduledoc states `def_type`'s open-ended text-vs-CHECK-constraint choice as
    an explicit open question, citing prm-04's Open Question 1** —
    `promotion_review_test.exs`: *"PromotionReview's moduledoc flags def_type's
    open-ended text-vs-CHECK-constraint choice as an open question"*.
18. **The moduledoc states the PER_TENANT-vs-GLOBAL classification is not independently
    confirmed, citing the `events`/`1147_par01_events_partitioning.sql` precedent it is
    measured against** — `promotion_review_test.exs`: *"PromotionReview's moduledoc
    flags the PER_TENANT-vs-GLOBAL classification as an unconfirmed open question"*.

### Beyond the bare acceptance criteria — cheap, real, not busywork

19. **`plan_digest` format validation actually rejects a malformed digest** (too short,
    too long, uppercase hex, non-hex characters) and accepts a genuine 64-char lowercase
    hex string — `promotion_review_test.exs`: *"insert_changeset/2 rejects a plan_digest
    that is not exactly 64 lowercase hex characters"*. This is REQ-036's PRM-03
    idempotency anchor (design §3, `plan_digest` row) — a validation gap here would let
    a malformed digest silently defeat the partial unique index's real-world purpose
    without ever tripping a DB error, since the column itself is an unconstrained
    `varchar(255)`.
20. **Every field `insert_changeset/2`'s spec requires really is required, and
    `def_type` really is optional with its default preserved** —
    `promotion_review_test.exs`: *"insert_changeset/2 requires tenant_id, plan_digest,
    def_id, serialised_plan and requested_by, and treats def_type as optional"*. Design
    §5.1 is explicit that `def_type` is deliberately excluded from
    `validate_required/2` (it carries a non-nil column default) — this is exactly the
    kind of one-field exception that's easy to get backwards by copy-pasting a
    `validate_required` list from a sibling module.
21. **`insert_changeset/2` never casts `:approved_by`, `:approved_at` or
    `:superseded_by`, even when attrs supply them** —
    `promotion_review_test.exs`: *"insert_changeset/2 does not cast approved_by,
    approved_at or superseded_by"*. Same reasoning as test 15 — these are REQ-037
    transition-owned fields; a newly-inserted review must not be insertable as already
    approved/superseded.
22. **`PromotionReview` exposes no `update_changeset/2` — its only public function is
    `insert_changeset/2`** — `promotion_review_test.exs`: *"PromotionReview's own
    public API is exactly insert_changeset/2 -- no update_changeset (design §5.1)"*.
    Design §5.1 is explicit that a changeset-mediated update path here would reintroduce
    the lost-update race `row_version`'s manual guard exists to prevent — this is a
    structural regression guard, not a restatement of the criterion.

## Determinism and isolation

- **No wall-clock dependence.** No `DateTime.utc_now/0` anywhere in either file.
- **No unseeded randomness.** Uniqueness comes from `Ecto.UUID.generate/0` (for actor
  and tenant identifiers — a generator, not an assertion target) and
  `System.unique_integer([:positive, :monotonic])` (a VM counter). `plan_digest` test
  values are `:crypto.hash(:sha256, "<fixed prefix>-#{unique_integer}") |>
  Base.encode16(case: :lower)` — deterministic given the counter, never
  `:rand`/`:crypto.strong_rand_bytes/1`.
- **Per-test unique fixtures.** Every DB-touching test gets its own `Tenant`, its own
  physical Postgres schema, its own `Registration` row, and its own `plan_digest`; no
  identifier is shared between tests.
- **Self-sufficient.** No test depends on another having run first.
- **No hardcoded secrets or connection strings.** Both files reach the database only
  through `Letflow.Repo`, which reads `config/test.exs`.
- **No `@tag :skip`, no `TODO`.**
