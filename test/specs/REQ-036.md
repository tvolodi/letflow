# Test Spec: REQ-036 — Promotion plan computation, conflict preflight, and plan digest

**Requirement:** REQ-036 (`docs/requirements.yaml` lines 1639–1714, stage S2)
**Design:** `lib/letflow/design/promotion_plan.md` (validated by CODE-DESIGN-VALIDATOR)
**Implementation:** `lib/letflow/definitions/promotion_plan.ex`,
`lib/letflow/definitions/promotion_conflict.ex`,
`lib/letflow/definitions/promotion_digest.ex`
**Test tier:** unit + integration (real Postgres via `Letflow.DataCase` for
`PromotionPlan`/`PromotionConflict`; pure unit tests for `PromotionDigest`)

**Verbatim acceptance criteria (from `docs/requirements.yaml`):**

1. `compute_promotion_plan/5` against a target tenant with no existing version of
   `process_key` marks every produced entry `change_kind: added`
2. `compute_promotion_plan/5` against byte-identical source and target definitions
   returns the empty-plan error, not a `PromotionPlan` with an empty entries list
3. `compute_promotion_plan/5` against a `source_tenant_id` that is itself a
   production tenant returns the invalid-promotion-source error before reading any
   `process_definitions` row
4. `reject_if_conflicts/4` with `target_active_version > base_version` returns a
   rejection detail naming the conflicting definition; with
   `target_active_version <= base_version` (including the target having zero rows)
   returns no conflict
5. `compute_plan_digest/1` called twice on plans with identical content but
   differently-ordered map keys produces the identical digest, demonstrated by an
   explicit test constructing the same entries in two different key orders
6. `verify_digest/2` uses a constant-time comparison, not `Kernel.==/2` or
   `:erlang.=:=/2` directly on the two strings, and this choice is stated in the
   moduledoc

## Fixture convention

`PromotionPlan`/`PromotionConflict` tests use this codebase's established per-test
tenant-schema-fixture convention (`test/letflow/definitions/snapshot_store_test.exs`'s
`provisioned_tenant/1`, also `migrations_test.exs`): each test provisions its own
real tenant schema(s) via `TenantProvisioning.provision_tenant_schema/1` +
`TenantProvisioning.replay_migrations/1`, `async: false`, Sandbox `:auto` mode +
manual `on_exit/1` cleanup (an `Ecto.Migrator` run needs a second real DB connection
the sandbox can't hand out). No shared or hardcoded tenant/process-key identifiers —
every fixture uses a fresh `Ecto.UUID.generate()` / `System.unique_integer/1`.
`PromotionDigest` is pure (no `Letflow.Repo` dependency at all), so its tests use
plain `ExUnit.Case, async: true` with bare map literals, matching `graph_test.exs`'s
precedent for a zero-I/O module.

**`opts[:permission_checker]` has no built-in default** (`Keyword.fetch!/2` — design
§9.1) — every `compute_promotion_plan/5` call in `promotion_plan_test.exs` passes it
explicitly (`allow/0`/`deny/0` helpers), never relying on a nonexistent default.

**AC3's fixture is the design's own stated limitation, not a test gap.** The real
`default_tenant_classifier/1` classifies every tenant as `:test` (design §9.2) —
there is no tenant "kind" column anywhere in this codebase to build a real
production-tenant fixture against. The AC3 test injects `opts[:tenant_classifier]`
explicitly, returning `:production` for its fixture tenant, per the design's own
explicit instruction that this is how AC3 must be exercised until a real
tenant-kind column exists.

## Test cases

### `promotion_plan_test.exs`

1. **AC1 — empty target, all 5 dimensions** — `target has no process_definitions row
   at all -- every entry across all 5 dimensions is :added, before is nil
   everywhere`. Exists to prove the "empty-target fallout" (design §3.3) is not a
   special-cased branch but a mechanical consequence of the generic before/after
   rule for every one of the 5 diff dimensions at once (graph_node, graph_edge,
   variable_schema, service_binding, module_ref) — a test covering only 1 or 2
   dimensions could pass while a regression broke a dimension it didn't exercise.
   Also pins the exact `{type_rank, id}` sort order (design §2.5) via a full,
   order-sensitive list equality — not just an unordered set check.
2. **AC1 variant — draft (non-active) target row** — `a target row exists for
   process_key but is NOT active (still :draft) -- treated identically to no
   target row at all`. Exists because `fetch_active/2` filters on `status: :active`;
   a naive implementation that read ANY row by name (ignoring status) would pass
   the "genuinely no row" case above but silently fail this one — this is the test
   that would catch that specific regression.
3. **AC2 — byte-identical plan** — `identical ACTIVE graphs at source and target --
   returns {:error, :empty_plan}, never {:ok, %{entries: []}}`. Exists to
   distinguish the two representations the acceptance criterion explicitly calls
   out as different: an empty-entries success tuple vs. a typed error. Asserts the
   full `{:error, :empty_plan}` term, not just `elem(result, 0) == :error`.
4. **AC3 — production-tenant source, ordering proof** — `source_tenant_id classified
   :production -- {:error, :invalid_promotion_source}, even with a malformed
   target_tenant_id`. Exists to prove step ordering (design §3.2 steps 1–2 run
   before step 3's schema resolution), not just that the error is eventually
   returned: a malformed `target_tenant_id` is deliberately passed so that if the
   implementation regressed to resolve tenant schemas before checking
   `tenant_classifier`, this test would instead observe `{:error,
   :invalid_tenant_id}` and fail.
5. **AC3 companion — default classifier never fires** — `source_tenant_id
   classified :test (the real default classifier) is never rejected on this
   ground`. Exists to prove AC3's check is a real conditional or the default
   behavior would falsely reject every ordinary promotion.
6. **permission_checker gate** — `permission_checker returning false --
   {:error, :forbidden}, even with a malformed target_tenant_id` (proves this is
   the very first check, per design §3.2 step 1) and `omitting
   opts[:permission_checker] entirely raises KeyError -- no silent
   allow-everything default`. Exists because a silently-defaulting
   `permission_checker` would be strictly worse than a crash (design's own
   moduledoc reasoning) — this test locks in the crash-not-silently-allow contract
   the "Critical details" of this run's task explicitly flagged.
7. **invalid_tenant_id** — `a malformed source_tenant_id (after
   permission_checker/tenant_classifier both pass) returns {:error,
   :invalid_tenant_id}`. Exists to cover the 4th member of `compute_error()` that
   none of the 6 numbered ACs individually names.
8. **Diff mechanics beyond AC1** — `overlapping definitions produce a mix of
   :added, :modified and :removed entries, and byte-identical units produce no
   entry`. AC1 only exercises the all-`:added` empty-target case; this test proves
   `:modified`/`:removed` and the "no entry when before == after" rule (design
   §3.4) actually work, and pins the `before` = target / `after` = source
   convention (design §2.2) explicitly by asserting which side's value lands in
   which field.

### `promotion_conflict_test.exs`

9. **AC4 — conflict** — `target_active_version > base_version -- a rejection
   detail naming the conflicting definition`. Asserts every field of
   `conflict_detail()` individually (`process_key`, `target_definition_id`,
   `target_active_version`, `base_version`), not just that an error occurred.
10. **AC4 — equal versions** — `target_active_version == base_version -- no
    conflict`. Exists because `<=` (per the acceptance criterion's own wording)
    includes equality — a naive strict `>` reimplementation as `>=` would fail
    only this case among the three boundary tests.
11. **AC4 — lesser version** — `target_active_version < base_version -- no
    conflict`.
12. **AC4 — zero rows** — `target has zero rows for process_key -- no conflict,
    even against base_version "0"`. Exists because the acceptance criterion names
    "including the target having zero rows" explicitly — `"0"` is chosen
    deliberately as the most conflict-prone possible `base_version`, so this test
    cannot pass by accident (e.g. by a version comparison that happens to treat
    absent-target as `"0" <= "0"`).
13. **AC4 — multiple pairs, one conflicts** — `only the conflicting pair is named,
    non-conflicting pairs contribute nothing`. Exists to prove the per-pair
    filtering (design §4.2 step 3) doesn't leak non-conflicting pairs into the
    result list.
14. **AC4 — multiple pairs, all conflict** — `one detail per pair, in input
    order`. Exists to prove the design's own explicit resolution of "supports
    multiple process_key conflicts as a list" (design §4.2) — index-aligned lists,
    order preserved — actually holds when more than one pair conflicts
    simultaneously, not just when exactly one does.
15. **AC4 — multiple pairs, zero conflicts** — `ZERO conflicts across all of them
    -- :ok`. Exists as the explicit "aggregate is :ok only when *no* pair
    conflicts" case named by this run's task briefing, distinct from case 12's
    single-pair zero-rows scenario.
16. **List-length-mismatch guard** — both directions (`process_key` longer;
    `base_version` longer), each against a deliberately UNPROVISIONED
    `target_tenant_id`. Exists to prove the guard clause (design §4.2 step 1)
    short-circuits before any `TenantProvisioning`/`Repo` call — a genuine DB read
    against a schema that was never created would raise, not return the clean
    error tuple these tests assert, so a passing test is itself the proof of
    short-circuiting, not merely an assertion about it.
17. **invalid_tenant_id** — malformed `target_tenant_id` with equal-length lists
    (guard does not fire) — covers the 3rd member of `conflict_error()`.
18. **`version_greater?/2` — numeric case (design §9.4)** — `"10"` vs `"9"`,
    chosen specifically because lexicographic and numeric comparison DISAGREE on
    this pair (`"10" < "9"` byte-wise, `10 > 9` numerically). Exists to prove the
    numeric branch is genuinely taken, not merely that *some* comparison finds a
    conflict — a lexicographic-only implementation would pass every other version
    test in this file but fail this one specifically.
19. **`version_greater?/2` — non-numeric case (design §9.4)** — `"beta"` vs
    `"alpha"` (conflict) and the reverse `"alpha"` vs `"beta"` (no conflict) in
    the same test. Exists to prove the lexicographic fallback is genuinely
    direction-sensitive, not a fallback that always/never reports a conflict for
    non-numeric input.
20. **`version_greater?/2` — partial-numeric-prefix edge case** — `"12abc"` vs
    `"9"`. Exists to pin the exact `with {target_int, ""} <- Integer.parse(...)`
    contract (design §9.4/implementation): a numeric PREFIX with a non-empty
    remainder must NOT be treated as a clean integer parse. A regression using
    `Integer.parse/1`'s returned integer directly (ignoring the remainder) would
    incorrectly find `12 > 9` and report a conflict; this test asserts `:ok`
    instead, per the correct lexicographic-fallback reading (`"12abc" < "9"`
    byte-wise).

### `promotion_digest_test.exs`

21. **AC5 — key-order independence, example 1** — a single-entry plan (with a
    nested `after` map) built as two independently-written literals with keys in
    different order at every level. Exists as the first of the two required
    independently-constructed examples.
22. **AC5 — key-order independence, example 2** — a two-entry plan with a
    3-level-deep nested map (`before.meta.owner`), independently constructed with
    a different key order at every level, including the deepest nesting. Exists
    as the second required example — deliberately different content/shape from
    example 1 (not a copy-pasted variant) so the two examples don't share a single
    code path through `canonicalize/1`'s map-recursion branch.
23. **Content-sensitivity sanity check** — differing content produces a different
    digest. Exists so cases 21/22 can't vacuously pass against a `compute_plan_digest/1`
    that ignores its input entirely (e.g. a stubbed constant return).
24. **Digest format** — 64-char lowercase hex. Exists to pin the literal
    `Base.encode16(case: :lower)` output shape the acceptance criteria describe.
25. **Array-order significance** — reordering the `entries` LIST (not map keys)
    changes the digest. Exists to pin the load-bearing distinction design §2.5/§5.1
    draw between object-key sorting (AC5, order-independent) and array-element
    order (deliberately NOT sorted, order-significant) — a `canonicalize/1` that
    accidentally sorted lists too would silently break `PromotionPlan`'s own
    `{type_rank, id}` determinism contract without any AC5 test catching it, since
    AC5's own fixtures use single- or few-entry lists that could pass even if list
    sorting were happening.
26. **`nil` values are not dropped** — a `nil`-valued key changes the digest
    versus that key being entirely absent. Exists because the requirement
    (`docs/requirements.yaml`) explicitly names "null values included not
    omitted" as a canonicalization requirement — a `canonicalize/1` that quietly
    filtered `nil` values (a common accidental behavior of some JSON-encoding
    helpers) would pass every other digest test in this file but fail this one.
27. **AC6 — `verify_digest/2` true/false against a plan** — correct digest
    verifies true; a same-length wrong digest verifies false.
28. **AC6 — `verify_digest/2` digest-vs-digest form** — `plan_or_digest` already a
    binary in digest shape compares directly, without recomputing anything.
29. **AC6 — differently-sized comparison raises, not silently false** — confirmed
    directly (not assumed) via a scratch `elixir -e` invocation during test design
    that OTP's real `:crypto.hash_equals/2` raises `ArgumentError` on
    differently-sized binaries rather than returning `false`. Exists to pin this
    exact, non-obvious real behavior as a regression guard — a future "safety"
    rewrite that swapped in a manual byte-by-byte compare would silently change
    this contract from raise to `false`, and this test would catch that.
30. **AC6 — moduledoc states the constant-time-comparison choice** — asserts the
    moduledoc contains both `:crypto.hash_equals/2` and the literal phrase "never
    `Kernel.==/2` or `:erlang.=:=/2` directly on the two digest strings", matching
    AC6's own wording almost verbatim. A doc-content check (`Code.fetch_docs/1`),
    same technique as `snapshot_store_test.exs`'s AC5 test.
