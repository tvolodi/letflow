# Test Spec: REQ-037 — Promotion review state machine and base promote

**Requirement:** REQ-037 (`docs/requirements.yaml`, stage S2,
`depends_on: [REQ-035, REQ-036]`)
**Design:** `lib/letflow/design/promotion_review_state_machine.md` (validated by
CODE-DESIGN-VALIDATOR; rework iteration 1 fixed `insert_review/2`'s `tenant_id`
derivation per SECURITY-REVIEWER's BLOCKER)
**Implementation:** `lib/letflow/definitions/promotion_review_store.ex`,
`lib/letflow/definitions/promotion.ex`
**Test tier:** unit + integration (real Postgres via `Letflow.DataCase` for both
modules — neither is pure, both write/read `process_definitions` and/or
`promotion_reviews`)

**Verbatim acceptance criteria (from `docs/requirements.yaml`):**

1. `insert_review/1` followed by a second `insert_review/1` with the identical
   `(tenant_id, plan_digest)` while the first is still `pending_review` returns the
   duplicate-review error, not a second row
2. `approve_review/4` called by the same principal recorded as `requested_by` is
   rejected with a self-approval error before any row is updated
3. `approve_review/4` with a `plan_digest` not matching the stored value is
   rejected with a digest-mismatch error, distinct from the self-approval and
   invalid-transition errors
4. two concurrent `approve_review/4` calls on the same `review_id`: exactly one
   succeeds (row_version optimistic-lock check), the other gets the
   invalid-transition error from the zero-rows-affected
   `WHERE row_version = $expected` clause
5. a rejected review can be transitioned to `superseded` via `supersede_review/2`
   (→ `/3`, design §1.2 arity resolution) — the NEW edge prm-04 adds, demonstrated
   explicitly, not left untested as if `rejected` were terminal
6. every one of the 7 permitted edges in prm-04's table has an explicit passing
   test, and at least 2 non-edges (e.g. `rejected -> approved`,
   `pending_review -> applied`) have explicit rejecting tests

**Also covered per this run's task briefing (not a bare `acceptance_criteria`
line, but load-bearing per the rework-iteration design and the task's explicit
demand):**

- `insert_review/2`'s post-rework `tenant_id` derivation: `opts[:prefix]`, never
  `args.plan.target_tenant_id` (design §2.3, INV-PRM04-6, the fix that closed
  SECURITY-REVIEWER's BLOCKER)
- `promote_definition/3`'s basic success path, with `opts[:permission_checker]`
  supplied explicitly on every call (no built-in default, same convention as
  REQ-036's `promotion_plan_test.exs`)

## Fixture convention

Both test files use this codebase's established per-test tenant-schema-fixture
convention (`test/letflow/definitions/promotion_plan_test.exs`/
`promotion_conflict_test.exs`, REQ-036's most recent precedent): each test
provisions its own real tenant schema(s) via
`TenantProvisioning.provision_tenant_schema/1` +
`TenantProvisioning.replay_migrations/1`, `async: false`, Sandbox `:auto` mode +
manual `on_exit/1` cleanup (an `Ecto.Migrator` run needs a second real DB
connection the ordinary sandboxed connection can't hand out). No shared or
hardcoded tenant/process-key/review identifiers — every fixture uses a fresh
`Ecto.UUID.generate()` / `System.unique_integer/1`.

`promotion_review_store_test.exs` needs only ONE provisioned tenant per test
(every `PromotionReviewStore` function writes to a single tenant's
`promotion_reviews`, scoped entirely by `opts[:prefix]`). `promotion_test.exs`
needs TWO (source + target), mirroring `promotion_plan_test.exs`'s own two-tenant
pattern, since `promote_definition/3` reads the source's active
`process_definitions` row and writes the target's.

**AC4's concurrency test reuses `test/letflow/event_store_test.exs`'s own
established `Task.async` + `{:ready, pid}`/`:go` barrier idiom verbatim** — the
exact mechanism `lib/letflow/design/promotion_review_state_machine.md` §4 spells
out step by step specifically so this run would not need to invent one. Sandbox
`:auto` mode (already required for schema provisioning) means each spawned
`Task` gets its own real, independent Postgres connection, which is what makes
the race genuinely concurrent rather than serialized through a shared
connection.

**`opts[:permission_checker]` is supplied explicitly on EVERY `promote_definition/3`
call in `promotion_test.exs`** — it has no built-in default (`Keyword.fetch!/2`,
design §3.2, reusing `PromotionPlan.promotion_opts()`'s own no-default stance).
`opts[:event_appender]` is likewise supplied explicitly on every call that is
meant to reach it — it is a new, equally no-default opt this design adds (design
§5 OQ-1: no working `EventStore.append/2` call site exists yet for a
definition-level event).

## Test cases

### `promotion_review_store_test.exs`

1. **AC1 — duplicate review** — `a second insert_review/2 with the identical
   (tenant_id, plan_digest) while the first is pending_review -> :duplicate_review,
   not a second row`. Exists to prove the partial unique index
   (`uq_promotion_review_active_digest`) is mapped to the typed
   `{:error, :duplicate_review}` atom (never a leaked changeset), and that the
   collision holds even when the second call supplies a *different*
   `requested_by` — the index is on `(tenant_id, plan_digest)` only, so a naive
   implementation that also compared `requested_by` would wrongly let this
   second call through.
2. **AC1 boundary — duplicate index only covers pending_review/approved** —
   `a duplicate (tenant_id, plan_digest) is accepted again once the first row is
   no longer pending_review/approved (rejected)`. Exists to prove the duplicate
   check is not a blanket "ever existed" check — the partial index's own
   `WHERE status IN ('pending_review', 'approved')` predicate is what AC1 is
   really pinned against, not an accidental total ban on repeats.
3. **`insert_review/2` tenant_id derivation** — `a plan.target_tenant_id that
   disagrees with opts[:prefix]'s real tenant is ignored -- the stored row's
   tenant_id is the prefix's tenant`. Exists specifically because this is the
   exact bug class SECURITY-REVIEWER's BLOCKER caught in this run's first design
   iteration (INV-1 addendum) — a plan carrying a mismatched
   `target_tenant_id` must never leak into the stored `tenant_id` column. Also
   confirms, via a fresh `Repo.get!/3` (not just the in-memory reply), and
   confirms the plan's own copy of the disagreeing value is still stored
   verbatim inside `serialised_plan` (proving the disagreement was genuine, not
   an accidental match).
4. **`insert_review/2` tenant_id derivation, failure path** — `opts[:prefix]
   pointing at a schema name with no valid reverse tenant_id ->
   {:error, :invalid_schema_name}, no row written`. Exists to prove the
   `TenantProvisioning.tenant_id_for_schema_name/1` failure path short-circuits
   before any changeset/DB call is attempted (design §2.3 step 3).
5. **`insert_review/2` digest re-verification** — `a digest that does not match
   plan.entries -> {:error, :digest_mismatch}, no row written`. Exists because
   `insert_review/2` adds this re-verification as a design addition beyond
   REQ-037's literal text (design §2.3 step 1, defending
   `PromotionDigest`'s own INV-PRM-5) — a caller passing a `digest` not actually
   derived from `plan` must never be allowed to persist a wrong `plan_digest`.
6. **AC2 — self-approval, before any row update** — `actor_id == requested_by ->
   {:error, :self_approval_forbidden}, and the row is provably unchanged
   afterwards`. Exists to prove both halves of AC2's wording: the correct error
   atom, AND that no `UPDATE` was ever issued — re-reads the row fresh from
   Postgres and checks `row_version`/`status`/`approved_by`/`approved_at` are
   all untouched, not just trusting the function's return value.
7. **AC2 — gate ordering** — `self-approval is rejected even when the supplied
   plan_digest is ALSO wrong -- self-approval gate runs first, digest gate never
   reached`. Exists to pin the design's explicit "no gate short-circuits past an
   earlier one... in this exact order" requirement (design §2.4) as an
   observable behavior, not just a comment — if gate ordering ever flipped,
   this call would instead return `:digest_mismatch`, and this test would catch
   that regression.
8. **AC3 — digest mismatch, distinct atom** — `a plan_digest not matching the
   stored value -> {:error, :digest_mismatch}, a different actor than
   requested_by`. Exists to prove the exact atom AC3 demands, and explicitly
   asserts `elem(result, 1) != :self_approval_forbidden` and
   `!= :invalid_transition` side by side, per AC3's own "distinct from" wording
   — not just implicitly distinct because they're different pattern matches in
   different tests. Also confirms the row was not mutated (row_version/status
   unchanged).
9. **AC4 — concurrency, Task.async barrier** — `two concurrent approve_review/4
   calls on the same review_id: exactly one :ok, exactly one
   {:error, :invalid_transition}`. Exists to prove the row_version-guarded
   `UPDATE`'s race behavior genuinely, not simulated sequentially — reuses
   `event_store_test.exs`'s exact barrier idiom (see "Fixture convention"
   above) so both calls are parked at a `receive do :go end` barrier before
   either issues its `approve_review/4` call, then released simultaneously.
   Asserts the deterministic outcome shape (exactly one `:ok`, exactly one
   `:invalid_transition` — never `:ok`/`:ok` or error/error), then re-reads the
   row fresh (outside either `Task`) to confirm `row_version == 2` (exactly one
   increment, not two, proving the loser's `UPDATE` truly affected zero rows
   rather than succeeding and being silently overwritten by the winner).
10. **AC6 / edge 1 — pending_review -> approved** — `edge 1/7:
    pending_review -> approved, via approve_review/4`. One of the 7 explicit
    per-edge passing tests AC6 demands.
11. **AC6 / edge 2 — pending_review -> rejected** — `edge 2/7:
    pending_review -> rejected, via reject_review/3`.
12. **AC6 / edge 3 — approved -> applied** — `edge 3/7: approved -> applied, via
    mark_review_applied/2`.
13. **AC6 / edge 4 — approved -> failed** — `edge 4/7: approved -> failed, via
    mark_review_failed/2`.
14. **AC6 / edge 5 — applied -> superseded** — `edge 5/7: applied -> superseded,
    via supersede_review/3`.
15. **AC6 / edge 6 — failed -> superseded** — `edge 6/7: failed -> superseded,
    via supersede_review/3`.
16. **AC5 + AC6 / edge 7 — rejected -> superseded, the NEW edge** — `edge 7/7
    (acceptance criterion 5, the NEW edge): rejected -> superseded, via
    supersede_review/3 -- rejected is NOT terminal`. Exists specifically to
    satisfy AC5's explicit demand that this edge not be "left untested as if
    rejected were terminal" — labeled with both AC numbers in its own test name
    and surrounding comment so neither criterion reads as silently folded into
    the other without acknowledgement.
17. **AC6 — non-edges, identical `:invalid_transition` atom** — `rejected ->
    approved (illegal) and pending_review -> applied (illegal) both return
    exactly {:error, :invalid_transition}`. Exists to prove INV-PRM04-1's
    "same atom regardless of which illegal edge was attempted" claim as an
    observable fact, not an assumption — computes both results independently
    then asserts `Enum.uniq([result_a, result_b]) == [{:error, :invalid_transition}]`,
    a single assertion that would fail if the two illegal edges ever diverged
    into different error shapes. The `rejected -> approved` half deliberately
    uses a DIFFERENT actor than `requested_by`, so it genuinely exercises the
    status pre-check rather than being masked by the self-approval gate, which
    runs first.
18. **Beyond AC6 — superseded is truly terminal** — `superseded is a true
    terminal state: supersede_review/3 on an already-superseded row ->
    {:error, :invalid_transition} too`. A 3rd non-edge, cheap and real: proves
    `superseded` is not a member of any function's `allowed_source_statuses`
    (design §2.1), not just asserted by the two required non-edges above.
19. **Beyond the bare ACs — `:review_not_found`** — `every transition function
    returns {:error, :review_not_found} for an id that does not exist in this
    tenant's schema`. Exercises the generic `transition/6` mechanism's shared
    step-1 guard across all five UPDATE-based functions in one test, cheap
    coverage of a real, reachable error path every one of them shares.

### `promotion_test.exs`

20. **Basic success path** — `version-pointer move (deprecate old active,
    activate new target row) + event-append, both succeed`. Exists to prove
    `promote_definition/3`'s full 10-step algorithm end to end against real
    Postgres: the freshly-inserted target row lands `:active`, carries the
    source row's copied fields (`version`/`description`/`stage`/`graph`), the
    source row itself is untouched, and the injected `event_appender` receives
    the exact `DEFINITION_PROMOTED` event-attrs shape design §3.2 step 9
    specifies (`event_type`, `actor_id`, `review_id`,
    `source_tenant_id`/`target_tenant_id`, `source_definition_id`/
    `target_definition_id`, `process_key`) under the TARGET tenant's prefix.
21. **Basic success path — pre-existing active target row is deprecated** — `a
    pre-existing ACTIVE target row for the same process_key is deprecated as
    part of the same swap`. Exists to prove the "deprecate before activate"
    half of PD-03's ordering (design §3.2 step 8(a)) is real, not just the
    "activate the new row" half — a regression that only ever inserted+activated
    without deprecating the old row would still pass test 20 (which starts with
    no prior target row) but would fail this one.
22. **`opts[:permission_checker]` — forbidden, fail-closed** —
    `permission_checker returning false -> {:error, :forbidden}, before any
    process_definitions read`. Deliberately uses two UNPROVISIONED tenant ids
    (no `CREATE SCHEMA` ever ran for either) — if the permission check did not
    genuinely run before any schema resolution/read, the next step would raise
    against Postgres instead of cleanly returning `{:error, :forbidden}`, so a
    passing test here proves the ordering, not just the final atom.
23. **`opts[:permission_checker]` — no built-in default** — `omitting
    opts[:permission_checker] entirely raises KeyError -- no silent
    allow-everything default`. Mirrors `promotion_plan_test.exs`'s identical
    convention check for `PromotionPlan.compute_promotion_plan/5`.
24. **`opts[:event_appender]` — no built-in default** — `omitting
    opts[:event_appender] entirely raises KeyError -- no silent no-op default`.
    Exists because this design deliberately adds `event_appender` with no
    default specifically so ENV-03's event-append half can never look silently
    "done" when it structurally cannot run yet (design §5 OQ-1) — this test
    pins that the function fails loudly, not silently, when the opt is
    omitted.
25. **`opts[:event_appender]` — failure propagates, no compensating rollback**
    — `an event_appender returning {:error, _} propagates unchanged, after the
    version-pointer move has already committed`. Exists to pin the real,
    explicitly-stated gap design §3.2 step 9/§5 OQ-1 names: the transaction
    (steps 7-8) is NOT nested with the event-append, so a failing
    `event_appender` does not roll back the already-committed pointer move.
    Asserts the target tenant genuinely has exactly 1 active
    `process_definitions` row after the failure — proving the write really did
    commit, not just that the function returned an error tuple.
26. **`opts[:tenant_classifier]` — production source rejected** —
    `source_tenant_id classified :production -> {:error,
    :invalid_promotion_source}`. Mirrors `promotion_plan_test.exs`'s identical
    AC3 fixture convention (the real `default_tenant_classifier/1` always
    returns `:test`, so a production-tenant fixture requires an injected
    classifier — this is the design's own stated limitation, not a test gap,
    restated from REQ-036's test spec).
27. **`:source_definition_missing`** — `the source tenant has no ACTIVE row for
    process_key -> {:error, :source_definition_missing}`. Exists because this
    is a NEW error case design §3.2 step 5 adds beyond
    `PromotionPlan.compute_error()`'s set — `promote_definition/3` has nothing
    to copy if the source has since been deactivated/archived, so this must be
    a hard failure, not a silent no-op write; this test proves it actually is
    one against real Postgres (both tenants provisioned, genuinely empty).
