# Test Spec: REQ-038 — Promotion rollback (`Letflow.Definitions.rollback_definition_version/4`, `rollback.zig`, PRM-08)

**Requirement:** REQ-038 (`docs/requirements.yaml`, stage S2, `depends_on: [REQ-030, REQ-037]`) —
verbatim acceptance criteria (re-read directly against `docs/requirements.yaml` lines
1814–1819, 5 criteria):

1. "rolling back to a version with status SUPERSEDED (that was previously ACTIVE) succeeds
   and flips the pointer: the target becomes ACTIVE and the former ACTIVE becomes
   SUPERSEDED"
2. "rolling back to a version whose status has never been ACTIVE or SUPERSEDED for this
   process_key returns the version-never-active error, no rows changed"
3. "rolling back to the currently-ACTIVE version returns the already-active error, no rows
   changed, no event appended"
4. "a successful rollback appends exactly one DEFINITION_VERSION_ROLLED_BACK event and
   updates any applied/approved promotion_reviews row for the former-active definition to
   superseded"
5. "a caller lacking the platform.admin-equivalent permission is rejected before any row is
   read or locked"

**Design source:** `lib/letflow/design/req038-promotion-rollback.md` (gate-approved, survived
one CODE-DESIGN-VALIDATOR rework cycle on §6/§7's `promotion_reviews` supersede-lookup — the
original design blanket-superseded every `applied`/`approved` row sharing a process_key, which
would have corrupted unrelated audit history; the rework replaced it with the
exactly-one-match safe default this spec tests explicitly below). REVIEWER's own sign-off
(`handoffs/WF02-REQ038-20260817/step-02d-reviewer.json`) independently re-verified the guard
order, the cardinality-branching lookup's three branches, and the `:deprecated` status-enum
mapping directly against the shipped code — this spec's test cases are written against that
same shipped code (`lib/letflow/definitions.ex`'s `rollback_definition_version/4` and its 5
private helpers, `lib/letflow/definitions/promotion_review_store.ex`'s widened
`supersede_review/3`), not against the design doc's prose alone.

**Test tier:** unit+integration (real Postgres, DIRECTIVE T-1 — no mocked database). This
function is transactional/DB-driven throughout (row locking, guarded updates, a real
`promotion_reviews` lookup), so every test provisions a real tenant schema; there is no pure,
I/O-free slice of this function worth testing in isolation the way `ServiceScopeValidator`'s
`validate/3` was (REQ-031). No property test: the guard/status space here is a small,
enumerable closed set (3 `process_definitions` statuses × a handful of guard branches, 3
cardinality branches for the review lookup), already covered exhaustively by the example-based
cases below — the same reasoning `test/specs/REQ-030.md`/`test/specs/REQ-031.md` give for
skipping a property test on their own small enumerable transition tables, in contrast to
`test/letflow/process_instance_test.exs`'s genuinely large action-sequence space.

## Fixture strategy — read before the test cases below

**File:** `test/letflow/definitions/rollback_test.exs`, `Letflow.Definitions.RollbackTest`,
`use Letflow.DataCase, async: false`. `rollback_definition_version/4` lives directly on
`Letflow.Definitions` (not a submodule, design §1), so this file follows
`test/letflow/definitions/store_test.exs`'s established `provisioned_tenant/0` + Sandbox
`:auto` + `async: false` convention exactly (`Ecto.Migrator` needs a second real DB connection
the ordinary sandboxed connection can't hand out). Only ONE tenant schema per test — rollback
is single-tenant (design §4.1/OQ-2), unlike `promotion_test.exs`'s two-tenant fixtures.

`two_version_history!/2` builds a process_key with two versions using the REAL, already-merged
`Definitions.create/2` + `Definitions.activate/2` (never a raw `Repo.insert!`/`Repo.update_all`
bypassing the real state machine) — `activate/2`'s own already-shipped deprecate-then-activate
swap (REQ-030) leaves v1 `:deprecated` and v2 `:active`, the ordinary, already-shipped shape of
"a process_key with rollback-eligible history."

`promotion_reviews` fixtures (`review_pending!/3`, `review_approved!/3`, `review_applied!/3`)
mirror `promotion_review_store_test.exs`'s own `insert_review_fixture!`/`approved_review!`
helpers — every row is created via the real `PromotionReviewStore` transition functions.
Each review's `entries` carries a fresh `System.unique_integer/1`-tagged node id so its
`plan_digest` is always unique — required so two reviews for the SAME process_key (the exact
scenario the ambiguous-match test needs) don't collide on `uq_promotion_review_active_digest`
(`(tenant_id, plan_digest)` while `pending_review`/`approved`).

Several tests pass an `exploding_event_appender/0` (`raise`s if invoked) specifically to PROVE
a guard short-circuited before Step 3 (the event-append) ever ran, not merely to assert it did
— the same "prove it, don't assert around it" technique `store_test.exs`'s AC6 block and
`test/specs/REQ-031.md`'s short-circuit tests already established in this codebase. Every test
uses `unique_process_key/1` (`System.unique_integer/1`-suffixed) — no shared or hard-coded
identifiers, no execution-order dependency, no wall-clock dependency.

## Test cases

### AC1 — rollback to a SUPERSEDED (`:deprecated`) version that was previously ACTIVE flips the pointer both ways

See describe block `"rollback_definition_version/4 -- AC1: rollback to a SUPERSEDED version
flips the pointer"`:

1. `"rolling back from v2 (active) to v1 (deprecated, previously active) succeeds and flips
   both rows"` — the literal AC1 case. Builds a real two-version history via
   `two_version_history!/2`, rolls back to v1, asserts every `rollback_result()` field
   (`definition_id`, `version`, `rolled_back_from_version`, `event_id`,
   `superseded_review_id`), re-reads BOTH rows from Postgres (not the in-memory reply) to
   confirm v1 is now `:active` and v2 is now `:deprecated`, asserts the event payload's
   `event_type`/`process_key`/`from_version`/`to_version`/`actor_id` fields match exactly, and
   asserts exactly one event message was sent (`refute_receive` a second copy) — the AC4 "exactly
   one event appended" (INV-RB-6) half of this scenario, proven in the same test rather than
   left implicit.
2. `"after rollback, get_active_by_name/2 returns the rolled-back-to row (status-enum reuse
   correctness)"` — proves a definition rolled back to `:active` is queryable through the SAME
   public API (`Definitions.get_active_by_name/2`, REQ-030) a normally-`activate/2`'d row would
   be, not a special/divergent state. Exists because the design's §3 status-enum mapping
   (`SUPERSEDED -> :deprecated`) is only sound if the resulting `:active` row is genuinely
   indistinguishable from any other active row in every other function's eyes.

### AC2 — target version never ACTIVE/SUPERSEDED returns version-never-active, no rows changed

See describe block `"rollback_definition_version/4 -- AC2: version never ACTIVE/SUPERSEDED ->
version_never_active"`:

1. `"target row is still DRAFT (never activated) -> version_never_active, active row
   untouched"` — the literal AC2 case: a second version exists but was never activated. Pins
   `updated_at` on the still-active row equal before/after the call (not just `status`
   unchanged — a no-op double-write that happened to restore the same status would still fail
   an `updated_at` comparison), and confirms the draft row's own status is untouched too.
2. `"target_version has no row at all -> version_never_active"` — target_version was never
   even created as a row (distinct code path from "row exists with wrong status" — both must
   independently reach the `target_row == nil` branch).
3. `"target row is ARCHIVED -- INV-RB-4 excludes :archived from the eligible rollback-target
   set"` — the design's own OQ-1 decision, tested directly rather than trusted from prose: an
   `:archived` row (reachable only via prior activation, same structural argument R-Co's own
   `{ACTIVE, SUPERSEDED}` rationale makes for `:deprecated`) is still rejected as
   version-never-active, because the eligible set is deliberately `{:active, :deprecated}`
   only, not "any status reachable only via prior activation."

### Guard ordering — 3 guard cases checked in the correct order (would catch a reordering)

See describe block `"rollback_definition_version/4 -- guard order: process_key_not_found wins
over version_never_active"`. This is the concrete "would catch a reordering" test the task
briefing asked for: a scenario where two guard conditions could plausibly both apply, proving
which one the code actually checks first.

1. `"no row is currently ACTIVE (all deprecated) -> process_key_not_found, even though a
   DEPRECATED row matches target_version"` — v1 is activated then deprecated (via the real
   `Definitions.deprecate/2`), leaving NO row `:active` for this process_key, while a
   `:deprecated` row that would satisfy the target-row lookup's own status filter
   (`[:active, :deprecated]`) genuinely exists. If guard evaluation order were reversed (target-
   row lookup before the current-active check), this call would find that row and proceed
   toward a swap against `current_active == nil` — a defect. The actual `cond do` order (§5 step
   2b before 2d) must reject this as `process_key_not_found` instead, exactly R-Co's own "No
   current ACTIVE row -- process_key may simply never have been promoted" unification. This is
   the sharpest possible ordering test: it is the one fixture shape where the two guards'
   answers would genuinely differ if evaluated in the other order.
2. `"process_key with zero rows at all -> the identical process_key_not_found error"` — the
   OTHER half of R-Co's unification (both "process_key never existed" and "every version already
   deprecated" collapse to the same error atom), tested as its own case so a regression that
   split them into two different errors is caught.

### AC3 — rollback to the currently-ACTIVE version returns already-active, no rows changed, no event appended

See describe block `"rollback_definition_version/4 -- AC3: rolling back to the currently-ACTIVE
version -> already_active"`:

1. `"target_version == current active version -> already_active, event_appender never called,
   row unchanged"` — passes `exploding_event_appender/0` (raises if invoked); the test only
   passes because the already-active guard (§5 step 2c) fires and returns via `Repo.rollback/1`
   before Step 3 is ever reached — proving, not asserting, "no event appended." `updated_at`
   pinned before/after, same technique as AC2 case 1.

### AC5 — permission guard checked before any row is read or locked

See describe block `"rollback_definition_version/4 -- AC5: permission guard runs before any row
is read or locked"`:

1. `"permission_checker returning false -> forbidden, proven to run before any
   process_definitions read"` — uses `TenantProvisioning.schema_name_for_tenant/1` (confirmed
   pure, no I/O — design §4.1's own note) to derive a well-formed schema name that decodes to a
   real tenant_id WITHOUT ever calling `provision_tenant_schema/1` — no `CREATE SCHEMA` ever ran.
   If the permission guard did not run before any `Repo` call, the very next step (locking
   `process_definitions` rows under this nonexistent Postgres schema) would raise a Postgrex
   undefined-schema error instead of cleanly returning `{:error, :forbidden}`. Additionally
   passes `exploding_event_appender/0`, proving the guard also short-circuits before Step 3.
   Mirrors `promotion_test.exs`'s own "neither tenant is provisioned" technique — the
   established pattern in this codebase for proving this exact ordering claim, not a new
   mechanism.
2. `"omitting opts[:permission_checker] raises KeyError -- no silent allow-everything
   default"` — INV-RB-2.
3. `"omitting opts[:event_appender] raises KeyError -- no silent no-op default"` — INV-RB-2,
   the other hook.

### AC4 + the cardinality-branched `promotion_reviews` lookup (INV-RB-10) — the single most scrutinized part of this requirement

See describe block `"rollback_definition_version/4 -- AC4 + cardinality-branched
promotion_reviews lookup (INV-RB-10)"`. This is a named, explicit test group per the task
briefing: this exact lookup triggered CODE-DESIGN-VALIDATOR's only rework cycle on this run
(the original design blanket-superseded every match, which would have corrupted unrelated
audit rows for any process_key promoted more than once — not a rare edge case, the *ordinary*
state of the table per design §6).

1. `"zero matching promotion_reviews rows -> superseded_review_id: nil, not an error"` — a
   review exists for a COMPLETELY DIFFERENT process_key (not just "no reviews at all"),
   proving the lookup is genuinely scoped by process_key, not "any row happens to exist in this
   tenant." Confirms the rollback still succeeds (`{:ok, _}`) with `superseded_review_id: nil`
   — AC4's own text: "zero matching rows is acceptable, not an error."
2. `"exactly one APPLIED promotion_reviews row for the process_key is superseded, superseded_by
   == the rollback's event_id"` — the literal AC4 case. Re-reads the review row from Postgres
   (not the in-memory reply) to confirm `status == :superseded`, `superseded_by ==
   result.event_id` (the EXACT event_id from this rollback, not merely "some UUID"), and
   `row_version` incremented by exactly 1 (the guarded-update contract `PromotionReviewStore`
   already establishes).
3. `"exactly one APPROVED promotion_reviews row -- the 7->8 edge REQ-038 widened on
   supersede_review/3 -- is superseded the same way"` — the sharpest possible test of this
   requirement's OWN edit to `promotion_review_store.ex` (widening `allowed_source_statuses`
   from `[:applied, :failed, :rejected]` to include `:approved`). A review is left at
   `:approved` (never advanced to `:applied`) — exactly the real orchestrator race design §7
   names (`promote_definition/3` committed, `mark_review_applied/2` hasn't run yet or failed
   independently) — and rollback still supersedes it correctly. Without this test, the ENTIRE
   reason REQ-038 needed to touch `promotion_review_store.ex` at all would be unverified.
4. `"MORE THAN ONE matching row -> superseded_review_id: nil, ZERO rows mutated (not first, not
   most recent -- none)"` — the exact defect CODE-DESIGN-VALIDATOR's Rework 1 blocked on,
   tested as its own case: two eligible reviews (one `:applied`, one `:approved`) for the SAME
   process_key. Asserts `superseded_review_id == nil` AND re-reads BOTH rows from Postgres,
   confirming BOTH retain their original `status`, `row_version`, and `superseded_by == nil` —
   proving literally zero mutation, not "the first one" or "the most recent one," which a
   test asserting only `superseded_review_id == nil` without re-reading both rows would not
   distinguish from a silent wrong-row mutation.

### Event-append-after-commit window (design §4.2/§5 step 3, §8 OQ-3, INV-RB-7)

See describe block `"rollback_definition_version/4 -- event-append-after-commit: swap is
committed before event_appender runs"`. REVIEWER's own handoff explicitly flagged this as MORE
security-sensitive for rollback than for the equivalent `promote_definition/3` tradeoff
(rollback is disproportionately likely to run during incident response, and has no second
bookkeeping call like `mark_review_applied/2` to independently surface a gap) — this test
demonstrates the ordering is real, not merely asserted, per the task briefing.

1. `"a fresh read from a separate connection, taken inside event_appender, already observes the
   swap"` — the supplied `event_appender` closure spawns a genuinely separate BEAM
   process/connection (`Task.async`, via `reread_statuses_via_separate_connection/3`) that
   re-reads BOTH rows directly from Postgres at the exact moment the closure runs, and reports
   what it observed back to the test process. Sandbox mode is `:auto` (real commits, no
   wrapping transaction, via `provisioned_tenant/0`), so this is a real, independent
   connection — not the same connection that ran TX1. Asserts the target row already reads
   `:active` and the former-active row already reads `:deprecated` at that moment, proving TX1
   had already durably committed before `event_appender` was ever invoked, using the same
   technique `RELEASE-VALIDATOR` used for REQ-030 (fresh read from a separate call, not the
   same BEAM process that just wrote it).

### `opts[:event_appender]` error propagation — the disclosed OQ-3 tradeoff, pinned so it doesn't silently change shape

See describe block `"rollback_definition_version/4 -- event_appender {:error, _} propagates
after the swap already committed"`:

1. `"an event_appender error propagates as this function's own result; the swap is NOT rolled
   back"` — mirrors `promotion_test.exs`'s identical test for `promote_definition/3`. Confirms
   `{:error, reason}` propagates unchanged AND the pointer swap (re-read from Postgres) remains
   committed — the accepted, disclosed tradeoff (design §8 OQ-3, REVIEWER's sign-off), not
   silently reworked into a different behavior later without a test catching it.

### Status-enum reuse correctness — double rollback (can you roll back twice in a row?)

See describe block `"rollback_definition_version/4 -- status-enum reuse correctness: a row
deprecated via rollback's own swap is still eligible for a subsequent rollback"`:

1. `"rolling back twice in a row, alternating between two versions, both succeed"` — rolls back
   v2 -> v1, then immediately rolls back v1 -> v2 again. The second call's guard logic (§5 step
   2d's `status in [:active, :deprecated]` eligibility check) must recognize v2 — now
   `:deprecated` via THIS module's OWN swap on the first call, not via the original `activate/2`
   promotion path — as a legitimate rollback target. Directly exercises the task briefing's own
   framing: "a prior-ACTIVE row that becomes `:deprecated` via THIS path should be correctly
   handled by REQ-038's own... guard logic on a SUBSEQUENT rollback." Asserts both rollbacks'
   full result shape and re-reads both rows from Postgres after each call.
