# Test Spec: REQ-039 — Sandbox pool and fixture loader (`sandbox_pool.zig` + `fixture_loader.zig`)

**Requirement:** REQ-039 (`docs/requirements.yaml:1822-1873`, stage S2) — build
`Letflow.SandboxPool` (`claim/1,2`, `release/1,2`, on-demand ephemeral Postgres-schema
provisioning under a hard concurrency quota) and `Letflow.SandboxPool.FixtureLoader`
(`load_fixtures_only/3`, allowlist-gated TRUNCATE-then-INSERT fixture loading).

**Requirement's acceptance criteria (verbatim, `requirements.yaml:1867-1872`):**
1. "claim/1 against an empty pool immediately succeeds and returns a sandbox_id +
   schema_name for a real, freshly-created Postgres schema"
2. "claim/1 when max_concurrent_sandboxes slots are all in use blocks until either a
   slot frees or the wait window elapses, returning SandboxUnavailable in the latter
   case"
3. "release/1 on a claimed sandbox drops its schema (verified: the schema no longer
   appears in information_schema.schemata after release) and frees its quota slot for
   a subsequent claim/1"
4. "load_fixtures_only/3 with a table_name not in the allowlist returns
   InvalidTableName without issuing any SQL against that table name"
5. "load_fixtures_only/3 loading the same fixtures twice against the same
   sandbox_schema (simulating a retry) leaves the same final row set both times, via
   the TRUNCATE-before-insert step"
6. "the moduledoc names the process-per-instance-vs-row-based-state open question
   explicitly and states it is left for CODE-DESIGNER, per this requirement's
   description and stage-2-event-store-definitions.md's Early findings section"

**Test tier:** unit + integration. `Letflow.SandboxPool` is a GenServer whose entire
behaviour is DB-mediated (`claim`/`release` provision/drop real Postgres schemas);
`Letflow.SandboxPool.FixtureLoader.load_fixtures_only/3` is a stateless function that
also touches `Letflow.Repo` on every non-error path. Both are exercised against real
Postgres, per DIRECTIVE T-1 — no mocked database anywhere in either test file.

## Scope test

Real application-executable Elixir logic: `lib/letflow/sandbox_pool.ex` (new GenServer
+ client API) and `lib/letflow/sandbox_pool/fixture_loader.ex` (new stateless module),
per `lib/letflow/design/req039-sandbox-pool-fixture-loader.md`. Not docs-only, not
build-config. Full TEST-DESIGN-VALIDATOR / TEST-RUNNER chain applies.

## The Sandbox-incompatibility investigation — not re-derived, reused directly

`SandboxPool.claim/1,2` calls `Ecto.Migrator.run/4` internally (to scaffold every
`Letflow.TenantProvisioning.tenant_scoped_migrations/0` table into the freshly
`CREATE SCHEMA`'d sandbox, per the design doc §4.4 step 4d/§4.6). This is the *exact*
failure mode `test/letflow/tenant_provisioning_test.exs` already hit and solved for
`replay_migrations/2` — that file's moduledoc and its
`describe "replay_migrations/2 -- successful replay (acceptance criterion 3)"` block
document the full empirical investigation (a real, reproduced
`DBConnection.ConnectionError`/`:queue_timeout` under the default shared-connection
sandbox mode; root cause traced directly into `deps/ecto_sql`; the `:auto`-mode fix;
and the ExUnit-source-level argument for why switching `Letflow.Repo`'s sandbox mode
mid-test cannot corrupt any other concurrently running test file's connection). Both
of this REQ-039 spec's test files reuse that fix directly rather than re-deriving it:
each file's `setup` block switches `Letflow.Repo` to Sandbox `:auto` mode for *every*
test up front (not just a subset of describe blocks, unlike
`tenant_provisioning_test.exs`), because in both new files practically every test
either calls `claim/1,2` directly or (in `fixture_loader_test.exs`'s case) needs a
schema `claim/1,2` produced. Both files are `async: false` for the whole module, for
the identical reason (see the cited moduledoc's ExUnit-source-level argument, which
does not depend on which specific test file is doing the switching).

**Consequence:** neither new file relies on DataCase's automatic rollback. Every real
Postgres schema either file creates is dropped explicitly — via `release/1,2`'s own
`DROP SCHEMA` on the normal path, plus a defensive `on_exit/1`
`DROP SCHEMA IF EXISTS ... CASCADE` fallback registered immediately after every
successful claim (a no-op when `release/1,2` already ran; a safety net when a test
body doesn't reach that point, e.g. a test that asserts an error before ever
releasing).

## Why each file starts its own uniquely-named `SandboxPool` instance, not the
## application's singleton

Per the design doc §4.2/§4.7 **INV-SP-7**, `start_link/1`'s `:name` option exists
specifically so a test can start an independent pool instance with its own small
`:max_concurrent`, deterministically exercising acceptance criterion 2's
quota-exhausted/blocking-wait behaviour without contending for, or being polluted by,
the application's own singleton `Letflow.SandboxPool` (`config/test.exs` pins that
singleton's quota to `max_concurrent_sandboxes: 1` specifically so *that* slot stays
available and cheap for whatever other future test needs it — e.g. a REQ-040 test
exercising the real end-to-end assertion-rerun orchestration against the default pool
— not so every SandboxPool test in this project has to serialize against one global
slot). Both `sandbox_pool_test.exs` and `fixture_loader_test.exs` define a local
`start_pool!/1` helper that starts a pool under a fresh, `System.unique_integer/1`-
suffixed atom name and stops it in `on_exit/1`.

## Test cases

### Acceptance criterion 1 — `claim/1,2` against an empty pool

1. **Immediately succeeds, returns a real, freshly-created Postgres schema** — see
   `sandbox_pool_test.exs:"immediately succeeds and returns a sandbox_id + schema_name
   for a real, freshly-created Postgres schema"`. Asserts the returned `sandbox_id` is
   a valid UUID, `schema_name` matches the exact `^sandbox_[0-9a-f]{32}$` shape the
   design commits to (§4.4 step 4b), and — the core AC1 assertion — queries
   `information_schema.schemata` directly (not the function's own return value) to
   confirm a real Postgres schema exists. Also confirms INV-SP-3 (design doc §4.7):
   `process_definitions` and `instance_definition_snapshots` already exist inside the
   freshly claimed schema, proving the migration-replay scaffolding step actually ran.
   Would fail if `claim/1,2` returned a well-shaped struct without actually issuing
   `CREATE SCHEMA`, or if the `Ecto.Migrator.run/4` step were dropped.
2. **Two immediate claims against a pool with room for both produce two distinct
   schemas** — see `sandbox_pool_test.exs:"two immediate claims against a pool with
   room for both produce two distinct schemas"`. Beyond AC1's bare statement, pins
   that repeated claims don't collide or reuse state. Would fail if `sandbox_id`/
   `schema_name` generation weren't genuinely fresh per claim.

### Acceptance criterion 2 — `claim/1,2`, quota exhausted, both required paths

3. **A queued waiter is served once the held slot frees (the blocking-then-success
   path)** — see `sandbox_pool_test.exs:"a queued waiter is served once the held slot
   frees, before its wait window elapses"`. `max_concurrent: 1`; the first claim
   consumes the only slot; a `Task.async` second `claim/2` call (2s wait window) is
   confirmed to have genuinely parked in the pool's `:waiting` queue (polled via
   `:sys.get_state/1` + bounded retry, matching this project's established
   `parallel_approval_test.exs` polling idiom — removes the race between "the waiter's
   call reached the pool's mailbox" and "the test releases the held slot", rather than
   assuming a fixed sleep is long enough) *before* the held slot is released. Only
   after that confirmation does the test call `release/2`, then asserts the waiter's
   `Task.await/2` resolves to `{:ok, %SandboxClaim{}}` with a schema distinct from the
   one that was released. Would fail if a freed slot were never handed off to a queued
   waiter (design doc §4.4 step 5), or if the hand-off produced the same, already-
   dropped schema.
4. **When no slot frees within the wait window, `{:error, :sandbox_unavailable}` and
   the held claim is untouched (the real timeout path)** — see
   `sandbox_pool_test.exs:"when no slot frees within the wait window, returns
   {:error, :sandbox_unavailable} and the held claim is untouched"`. `max_concurrent:
   1`; the held slot is never released; a second `claim/2` call uses a small,
   deliberate `max_wait_ms` of 150ms (not REQ-039's real-world 60s default, per this
   spec's task instruction to keep any unavoidable real timeout small) and is asserted
   to return `{:error, :sandbox_unavailable}` only after genuinely waiting out that
   window — nothing in this test frees the slot early, so the assertion cannot pass via
   the release-driven hand-off path tested in case 3. Also confirms the held claim's
   schema still exists afterward (the timed-out waiter didn't corrupt pool bookkeeping
   or drop the wrong schema). Would fail if `handle_info({:claim_timeout, ...}, ...)`
   (design doc §4.4 step 6) were missing or replied with the wrong error.
5. **`max_wait_ms <= 0` against an exhausted pool rejects immediately, never
   queueing** — see `sandbox_pool_test.exs:"max_wait_ms <= 0 against an exhausted pool
   rejects immediately without ever queueing"`. Directly pins design doc §4.4 step 3's
   "already elapsed by definition" short-circuit — asserts both the immediate
   `{:error, :sandbox_unavailable}` reply and that the pool's `:waiting` queue length is
   still 0 afterward (would have been 1 had this path incorrectly fallen through to the
   queueing branch).

### Acceptance criterion 3 — `release/1,2`

6. **Drops the schema for real (confirmed via `information_schema.schemata`) and frees
   the quota slot for a subsequent `claim/1`** — see `sandbox_pool_test.exs:"drops the
   schema for real (confirmed via information_schema.schemata) and frees the quota
   slot for a subsequent claim/1"`. `max_concurrent: 1`; confirms the slot is genuinely
   fully consumed before release (`claim(0, pool)` returns `{:error,
   :sandbox_unavailable}`, so the later "frees the slot" assertion isn't vacuous);
   calls `release/2`; the core AC3 assertion queries `information_schema.schemata`
   directly (not the return value) and asserts the schema no longer appears; then
   confirms a fresh `claim/2` immediately succeeds against the now-freed slot, with a
   distinct `sandbox_id`/`schema_name` from the first. Would fail if `DROP SCHEMA`
   were skipped, or if the `active` map entry weren't removed on a successful release
   (design doc §4.5 step 4).
7. **An unknown `sandbox_id` returns `{:error, :not_found}`** — see
   `sandbox_pool_test.exs:"an unknown sandbox_id returns {:error, :not_found} without
   touching any schema"`. Beyond AC3's bare statement but directly tied to `release/1,2`'s
   own error taxonomy (design doc §7) — would fail if an unrecognized `sandbox_id`
   instead raised or silently returned `:ok`.

### Acceptance criterion 4 — `load_fixtures_only/3`, allowlist rejection (the
### SQL-injection boundary)

8. **A `table_name` outside the allowlist returns `{:error, :invalid_table_name}`, and
   no SQL runs against ANY table in the batch, including allowlisted ones** — see
   `fixture_loader_test.exs:"a table_name outside the allowlist returns
   {:error, :invalid_table_name}, and no SQL runs against ANY table in the batch,
   including allowlisted ones"`. Claims a real sandbox; the fixtures batch mixes one
   `process_definitions` row (which, on its own, would insert cleanly) with one
   `not_on_the_allowlist` row. Asserts the whole call returns
   `{:error, :invalid_table_name}`, then queries `process_definitions` in that schema
   directly and asserts **zero** rows landed — proving INV-FL-2 (design doc §5.5): the
   validation pass rejects the whole batch *before* any mutation runs, not just before
   the offending table's own mutation. Would fail if the allowlist check ran per-table
   inside the mutation loop instead of as a whole-batch pre-pass (in which case this
   test would find 1 row, not 0).
9. **Every fixture already violating the allowlist (no allowlisted table involved at
   all)** — see `fixture_loader_test.exs:"every fixture already violating the
   allowlist (no allowlisted table involved at all) is likewise rejected, no SQL
   issued"`. Simpler complementary case to case 8, using a plausible-looking but
   never-allowlisted table name (`users`) to confirm the allowlist is a real
   allowlist, not merely a denylist of one known-bad name.
10. **An invalid `sandbox_schema` shape is rejected before any table-name check** —
    see `fixture_loader_test.exs:"an invalid sandbox_schema shape is rejected before
    any table-name check, returning {:error, :invalid_schema_name}"`. Deliberately does
    **not** claim a real sandbox — INV-FL-1 (design doc §5.5, the hardening this design
    adds beyond R-Co's own source) means a syntactically wrong `sandbox_schema` must be
    rejected purely from its shape, with zero DB round trips. Not itself one of
    REQ-039's 6 numbered criteria, but directly exercises the schema-name-validation
    step the design added specifically because `load_fixtures_only/3` (unlike Zig's
    same-file-caller-trust version) has no type-level guarantee its caller always
    passes a value `SandboxPool.claim/1,2` actually produced.

### Acceptance criterion 5 — `load_fixtures_only/3`, idempotent retry via
### TRUNCATE-before-insert

11. **Loading the identical fixtures twice leaves the identical final row set both
    times** — see `fixture_loader_test.exs:"loading the identical fixtures twice
    leaves the identical final row set both times"`. This is AC5's literal wording,
    satisfied directly: two fixture rows (fixed `id`s `id_a`/`id_b`, `id` is
    `process_definitions`' primary key) are loaded once, and the actual row set is
    read back via a real `SELECT ... ::text` query (not trusting the `:ok` return
    value) and compared against `[id_a, id_b]`. The identical fixtures list is then
    loaded a **second** time (simulating a retry), and the row set is read back and
    compared again. This is a genuinely load-bearing assertion, not vacuous: without
    the TRUNCATE-before-insert step (design doc §5.4 step 5a), the second call would
    either raise a primary-key conflict on the already-present `id`s (surfacing as
    `{:error, :insert_failed}`, not `:ok`) or, if `id` weren't the primary key,
    silently double the row count to 4 — asserting both `:ok` *and* exactly
    `[id_a, id_b]` after the second call rules out both failure modes at once.
12. **A changed retry (same table, different row content) replaces the prior load's
    rows entirely** — see `fixture_loader_test.exs:"a changed retry (same table,
    different row content) replaces the prior load's rows entirely"`. Complements case
    11 with the sharper failure mode a *content-identical* retry can mask: loads one
    row, confirms it, then loads a *different* row into the same table/schema and
    confirms the first row's `id` is now **gone**, not merely joined by the second —
    directly proving the TRUNCATE step ran on the second call rather than the second
    call simply happening to also succeed.
13. **An empty fixtures list is a no-op** — see `fixture_loader_test.exs:"an empty
    fixtures list is a no-op: :ok, no rows inserted, no prior rows disturbed"`. Ports
    `fixture_loader.zig:51`'s no-op semantics: seeds one row, then calls
    `load_fixtures_only/3` with `[]` and confirms the seeded row is untouched (not
    truncated away) — pins that an empty batch issues no TRUNCATE either, not just no
    INSERT.

### Acceptance criterion 6 — `@moduledoc` open-question content, no runtime test

REQ-039's sixth acceptance criterion ("the moduledoc names the
process-per-instance-vs-row-based-state open question explicitly and states it is left
for CODE-DESIGNER...") is a **documentation-content requirement**, not application
behavior in the ExUnit sense — identical in kind to REQ-022's acceptance criterion 4
(`test/specs/REQ-022.md`'s own handling, itself following `test/specs/REQ-020.md`'s
AC5 precedent) and this project's explicit warning (`core-directives.md`,
`docs/agents/workflows/WF-02_requirement_implementation.md`) against manufacturing a
`String.contains?(@moduledoc, ...)`-style test that would prove nothing about whether
the content is actually true and would stay trivially "green" under a copy-pasted
substring. This is **verified by direct inspection** instead.

Inspected `lib/letflow/sandbox_pool.ex` lines 13-30 directly (the `@moduledoc`'s
`## Process-per-instance vs. row-based state (REQ-039's open question, resolved here)`
section). Confirmed the required content is present, in substance:
- Explicitly names the open question, citing both sources REQ-039's own text and this
  criterion require: `stage-2-event-store-definitions.md`'s "Early findings" section
  (process-vs-row) and `sandbox_pool.zig`'s own moduledoc ("The pool records every
  active claim in a process-local table").
- States plainly that CODE-DESIGNER (not ELIXIR-DEV, and not this module silently
  deciding on its own) resolved it, and cites the exact design-doc location (§2) where
  that resolution lives.
- Summarizes the actual resolution (single supervised `GenServer`, chosen for the
  blocking-quota-arbitration property) and why it's *not* one process per claimed
  sandbox, matching design doc §2.3's reasoning rather than asserting a conclusion
  with no argument behind it.

This is a one-time inspection result, not a standing regression check — a future edit
could silently remove this prose without any test catching it, which is the accepted,
explicitly-stated tradeoff for a documentation-content criterion per this project's own
guidance against inventing busywork tests. RELEASE-VALIDATOR should re-confirm this
independently rather than trust this spec's claim, same as REQ-022/REQ-020's precedent
asks.

## Fixture isolation and cleanup

Every claimed sandbox schema in both files carries a fresh `Ecto.UUID.generate()`-
derived name (`SandboxPool`'s own provisioning sequence, design doc §4.4 step 4b) — no
shared hardcoded schema name across tests. Every pool instance is started under a
`System.unique_integer/1`-suffixed atom name (`start_pool!/1` in both files), so no
test's pool contends with another test's or with the application's own singleton.
Every `process_definitions` fixture row in `fixture_loader_test.exs` uses a fresh
`Ecto.UUID.generate()` `id` and a `System.unique_integer/1`-suffixed `name`
(`valid_process_definition_json/1`).

**Verified empirically, matching `test/specs/REQ-022.md`'s own precedent:** ran both
new test files together 5 times consecutively (seeds `0`, `1`, `2`, plus two runs with
ExUnit's own random seed — 13 passed every time, 65/65 total) and queried the real test
database directly after the final run:

```sql
SELECT nspname FROM pg_catalog.pg_namespace WHERE nspname LIKE 'sandbox_%';  -- 0 rows
```

confirming no orphan Postgres schema survives a run. (One earlier ad hoc run during
drafting left 2 orphan schemas from unrelated pre-existing debris in the shared test
database, discovered and dropped before this verification sequence began — not
reproduced across any of the 5 clean, consecutive runs that followed, ruling out a
leak in this file's own `on_exit/1` cleanup.)
