# Test Spec: REQ-040 — Promotion assertion re-run orchestration (`Letflow.Definitions.apply_promotion_assertion_rerun/6`, `assertion_rerun.zig`, PRM-06/07)

**Requirement:** REQ-040 (`docs/requirements.yaml:1875-1937`, stage S2, `depends_on: [REQ-039, REQ-037]`,
both `done`) — verbatim acceptance criteria (`requirements.yaml:1930-1936`, 6 criteria):

1. "calling apply_promotion_assertion_rerun/6 twice with the same (review_id, plan_digest) returns
   the cached outcome on the second call and claims no second sandbox, verified by sandbox claim
   count"
2. "a sandbox loaded via REQ-039 receives ONLY the artifact's fixtures[] rows, demonstrated by
   confirming no pre-existing tenant data appears in the sandbox schema"
3. "an assertion replay that fails records status = failed with a non-empty failing_assertion_ids
   list; a passing replay whose teardown itself fails records status = teardown_failed with
   assertions_failed = 0 -- both distinct outcomes tested explicitly"
4. "the moduledoc explicitly states the apply pipeline gate condition is assertions_failed == 0,
   not status == passed, citing the teardown_failed green-gate case"
5. "a simulated teardown failure appends a PROMOTION_ASSERTION_TEARDOWN_FAILED event via REQ-025's
   append and does not change a passing run's outcome from green to failed"
6. "the moduledoc names the crash-safety/guaranteed-teardown open question explicitly, per this
   requirement's description and stage-2-event-store-definitions.md's Early findings"

**Design source:** `lib/letflow/design/req040-promotion-assertion-rerun.md` (gate-approved, survived
one CODE-DESIGN-VALIDATOR rework cycle adding required moduledoc text, no algorithm change).
REVIEWER's own sign-off (`handoffs/WF02-REQ040-20260817/step-02d-reviewer.json`) independently
re-verified the idempotency idiom, the double-run self-consistency (not oracle) comparison,
`fail_closed_counts/1`'s `max(assertions_total, 1)` guarantee, the try/rescue span's structural
scope, and a byte-for-byte match of the design §13.1/§13.2 moduledoc/`@doc` prose against the
shipped text — this spec's test cases are written against that same shipped code
(`lib/letflow/definitions.ex`'s `apply_promotion_assertion_rerun/6` and its private helpers), not
against the design doc's prose alone.

**Test tier:** unit+integration (real Postgres, DIRECTIVE T-1 — no mocked database, no mocked
`SandboxPool`). This function is transactional/DB-driven and orchestrates a real REQ-039
`SandboxPool`/`FixtureLoader` throughout, so every DB-touching test provisions a real tenant schema
and claims real ephemeral sandbox schemas. No property test: the status/outcome space here is a
small, enumerable closed set (4 statuses × a handful of guard/precedence branches), already covered
exhaustively by the example-based cases below — the same reasoning `test/specs/REQ-038.md` gives for
its own small enumerable transition table.

## Fixture strategy — read before the test cases below

**Files:**
- `test/letflow/definitions/promotion_assertion_rerun_test.exs` — all DB-backed acceptance-criteria
  coverage (AC1, AC2, AC3, AC5, plus the flagged extra coverage below). `Letflow.Definitions.PromotionAssertionRerunTest`, `use Letflow.DataCase, async: false`. `apply_promotion_assertion_rerun/6`
  lives directly on `Letflow.Definitions` (design §1), and internally calls `Ecto.Migrator.run/4`
  (via `SandboxPool.claim/2`'s own provisioning sequence, REQ-039), so this file follows
  `rollback_test.exs`'s/`sandbox_pool_test.exs`'s established `provisioned_tenant/0` (switches
  `Letflow.Repo` to Sandbox `:auto` mode internally) + `start_pool!/1` (an isolated,
  uniquely-named `SandboxPool` instance per test, never the application singleton) + `async: false`
  convention exactly — not a new mechanism.
- `test/letflow/definitions_test.exs` — AC4 and AC6, the two pure documentation-content criteria,
  added as two new describe blocks reusing that file's own already-established
  `normalized_moduledoc/1` helper (`Code.fetch_docs/1`, whitespace-normalized) against
  `Letflow.Definitions` itself — mirrors that file's own REQ-030/REQ-042 moduledoc-content blocks
  exactly, per this run's own task briefing pointing at that precedent. No new test file needed for
  these two criteria; `Letflow.Definitions`' moduledoc is already the established target other
  requirements' doc-content checks in that file assert against.

**Every test creates its own tenant (`provisioned_tenant/0`) and its own isolated `SandboxPool`
instance (`start_pool!/1`, `System.unique_integer/1`-suffixed name)** — no shared or hard-coded
identifiers, no test depends on another test's data or execution order, no wall-clock dependency
(`rng_seed` is a fixed literal, `fixed_rng_seed/0`, never derived from `System.os_time`).

**`opts[:event_appender]` is supplied explicitly on every DB-touching call** (`Keyword.fetch!/2`,
no built-in default, design §3/§9) — mirrors `rollback_test.exs`'s `recording_event_appender/1`
(records what it was called with by sending a message to the test process) and
`exploding_event_appender/0` (raises if invoked — proves, not merely asserts, that a path never
calls it).

**Three claim-count/mid-flight-observation techniques, used because `apply_promotion_assertion_rerun/6`
runs synchronously start-to-finish and never returns control mid-call:**

1. **Idempotency claim-count proof (AC1) — pool-quota exhaustion, not tracing.** A pool started with
   `max_concurrent: 1`. Call 1 claims, replays, releases (pool returns to 0/1 active). The test then
   claims the pool's own single slot directly (`SandboxPool.claim(0, pool)`), fully exhausting it.
   Call 2 (same `(review_id, plan_digest)`, `max_wait_ms: 0`, an `exploding_event_appender/0`) must
   still return the cached `{:ok, result}` — if the idempotent-hit path incorrectly attempted a
   second `SandboxPool.claim/2` for any reason, that call would immediately fail
   `{:error, :sandbox_unavailable}` against the exhausted pool (deterministic, since `max_wait_ms: 0`
   never queues) and propagate as this function's own `{:error, _}` return, failing the test. This
   is the "sandbox pool with a known small `max_concurrent_sandboxes` quota" proof technique named in
   this run's own task briefing.
2. **Mid-replay sandbox inspection (AC2, and the two "release it out from under the function" tests
   below) — a custom `opts[:assertion_evaluator]` as the one available mid-call injection point.**
   Since `assertion_evaluator` runs (twice per assertion) between Step 3 (fixture load) and Step 5
   (release), a custom evaluator can read the pool's own live state via `:sys.get_state/1` (the same
   primitive `sandbox_pool_test.exs`'s own `wait_until_waiter_queued/2` already uses in this
   codebase) to learn the currently-claimed `sandbox_id` — reliable because each test's dedicated
   pool never has more than one claim in flight at a time (the whole call is synchronous, single
   BEAM process). From there a test can either read the sandbox schema's own real Postgres row set
   directly (AC2), or call the REAL `SandboxPool.release/2` itself, once, from inside the evaluator
   (the two teardown-failure tests below) — genuinely triggering the exact `{:error, :not_found}`
   `finish_replay/8`'s own subsequent Step 5 release call then observes, with no mocking of
   `SandboxPool` anywhere.
3. **Real-exception injection (try/rescue span) — a custom `assertion_evaluator` that raises.**
   Since `assertion_evaluator` runs inside `run_replay_span/8`'s own `try` body, a `raise` from a
   custom evaluator is a genuine, unhandled exception at exactly the point design §2.3's `try/rescue`
   decision exists to catch — no manufactured stand-in for "an exception happened here."

## Test cases

### AC1 — idempotent replay, cached outcome, NO second sandbox claim

See describe block `"apply_promotion_assertion_rerun/6 -- AC1: idempotent replay returns the cached
outcome and claims no second sandbox"`:

1. `"calling twice with the same (review_id, plan_digest) returns the cached outcome on the second
   call, proven via a fully-exhausted pool quota that a second real claim would have to fail
   against"` — the literal AC1 case, using technique 1 above. Asserts call 1's full result shape
   (`idempotent_hit: false`, real `sandbox_id`, `run_id`), re-reads the row from Postgres (not the
   in-memory reply) to confirm persistence, then asserts call 2 (`idempotent_hit: true`) returns the
   IDENTICAL `run_id`/`sandbox_id`/`status`/counts as call 1, with the pool fully exhausted and an
   `exploding_event_appender/0` in place — proving both "no second claim" (INV-AR-4) and "no
   `event_appender` call on the idempotent-hit path" (design §7.1: `teardown_event_appended: true`,
   "nothing attempted this call") in the same test.

### AC2 — the claimed sandbox receives ONLY `artifact.fixtures[]`, never organic tenant data

See describe block `"apply_promotion_assertion_rerun/6 -- AC2: the claimed sandbox receives ONLY
artifact.fixtures[], never organic tenant data"`:

1. `"a process_definitions row that already exists in the PRODUCTION tenant schema does not appear
   in the sandbox; only the artifact's own fixture row does"` — seeds a real, unrelated
   `process_definitions` row directly in the target tenant schema (via `Definitions.create/2`, the
   real state-machine function, never a raw insert) BEFORE calling
   `apply_promotion_assertion_rerun/6`, then builds `artifact.fixtures` with a single, DIFFERENT
   `process_definitions` fixture row. Using technique 2, a custom `assertion_evaluator` reads the
   claimed sandbox's own `process_definitions` table directly (a real Postgres query against the
   sandbox schema, not the production tenant schema) while the sandbox still exists (before Step 5's
   release drops it) and reports the row set back to the test process. Asserts the sandbox's row set
   is EXACTLY `[fixture_id]` — the organic tenant-schema row's id is absent — proving INV-AR-2
   empirically, not merely by reading `FixtureLoader.load_fixtures_only/3`'s own source.

### AC3 (first half) — a failing replay records `status = :failed` with a non-empty `failing_assertion_ids`

See describe block `"apply_promotion_assertion_rerun/6 -- AC3 (first half): a failing replay records
status = :failed with a non-empty failing_assertion_ids list"`:

1. `"a single assertion with an empty payload replays consistently (both runs agree) but is still
   counted failed, per the placeholder's own empty-payload-fails rule"` — one assertion,
   `payload: ""`. The default evaluator returns `{:ok, "{}"}` on both replay passes (byte-identical,
   so this is NOT the non-determinism path — isolates the "empty payload = fail" rule specifically,
   design §6.1 step h). Asserts `status == :failed`, `assertions_total == 1`, `assertions_passed ==
   0`, `assertions_failed == 1`, `failing_assertion_ids == [assertion.id]`, and re-reads the row from
   Postgres to confirm persistence.

### AC3 (second half) + AC5 — a passing replay whose own teardown fails is `:teardown_failed` with `assertions_failed = 0`, and the `PROMOTION_ASSERTION_TEARDOWN_FAILED` event is appended without demoting the run

See describe block `"apply_promotion_assertion_rerun/6 -- AC3 (second half) + AC5: a passing replay
whose own teardown fails records status = :teardown_failed with assertions_failed = 0, and appends
PROMOTION_ASSERTION_TEARDOWN_FAILED without demoting the run to :failed"` — this is deliberately one
describe block covering both criteria, since PRM-07 AC2's green-gate case (AC3's second clause) and
the "does not change a passing run's outcome from green to failed" clause (AC5) are the same
underlying behavior, verified by the same fixture:

1. `"a passing single-assertion replay whose sandbox release fails (forced via a real, unmocked
   SandboxPool.release/2 call from inside the evaluator) records status = :teardown_failed,
   assertions_failed = 0, and appends exactly one PROMOTION_ASSERTION_TEARDOWN_FAILED event"` — one
   passing assertion (non-empty payload). Using technique 2's release variant
   (`evaluator_releasing_sandbox_once/1`), the sandbox is genuinely released mid-replay so
   `finish_replay/8`'s own Step 5 `SandboxPool.release/2` call gets a real `{:error, :not_found}` —
   not a stub. Asserts `status == :teardown_failed`, `assertions_passed == 1`, `assertions_failed ==
   0` (the real replay genuinely found zero failures — INV-AR-6), `teardown_error != nil`,
   `teardown_event_appended == true`, and that `recording_event_appender/1` received EXACTLY one
   `{:event_appended, attrs, prefix}` message with `attrs.event_type ==
   "PROMOTION_ASSERTION_TEARDOWN_FAILED"`, `attrs.run_id == result.run_id`, `attrs.sandbox_id ==
   result.sandbox_id`, `attrs.error` a human-readable string — this IS the literal AC5 scenario ("a
   simulated teardown failure appends a PROMOTION_ASSERTION_TEARDOWN_FAILED event... and does not
   change a passing run's outcome from green to failed": `assertions_failed` stayed `0`, `status`
   became `:teardown_failed`, never `:failed`).

### INV-AR-6 companion — a FAILING replay whose teardown also fails stays `:failed`, never promoted to `:teardown_failed`

See describe block `"apply_promotion_assertion_rerun/6 -- INV-AR-6 companion: a FAILING replay whose
teardown also fails stays :failed, never becomes :teardown_failed"` — not itself one of the 6 named
acceptance criteria, but the OTHER half of the same precedence rule AC3/AC5 exercise (design §7.5's
`recordTeardownFailure`-port: a teardown failure never *demotes* an already-failed run into the
differently-named `:teardown_failed` status), flagged because a broken precedence implementation
that always used `:teardown_failed` regardless of `pre_teardown_status` would still pass every AC3/
AC5 test above:

1. `"a failing single-assertion replay (empty payload) whose sandbox release ALSO fails stays
   :failed, not :teardown_failed -- the PROMOTION_ASSERTION_TEARDOWN_FAILED event is still
   appended"` — same `evaluator_releasing_sandbox_once/1` technique, this time with an empty-payload
   (failing) assertion. Asserts `status == :failed` (NOT `:teardown_failed`), `assertions_failed ==
   1`, and that the teardown-failure event was still appended (design §7.5: "called exactly once,
   regardless of whether `pre_teardown_status` was `:passed` or `:failed`" — the eventing decision is
   independent of the status-precedence decision).

### Double-run self-consistency check (not an oracle comparison) — the extra coverage this run's task briefing specifically flagged

See describe block `"apply_promotion_assertion_rerun/6 -- double-run self-consistency check (not an
oracle comparison)"`. Constructed per the task briefing's own instruction: "construct a
fixture/assertion shape that would genuinely produce different results across runs" — confirmed
constructible against the current stub-level evaluator (the evaluator is fully test-controlled via
`opts[:assertion_evaluator]`; no PRM-05 real engine is needed to make an evaluator that is *itself*
non-deterministic across two calls, which is exactly the class of bug this check exists to catch,
per design §6.1/§11 OQ-4):

1. `"an evaluator whose result genuinely differs between the two same-seed replay passes (a
   'metadata.nonce' field that increments per call) is counted failed, with its id in
   failing_assertion_ids, when the differing field is NOT declared in non_deterministic_fields"` —
   `evaluator_with_changing_nonce/0` returns JSON with a `metadata.nonce` field that increments on
   every invocation (a per-process call counter, deliberately NOT reading `injection`'s
   `frozen_clock_ms`/`rng_seed` — modeling an evaluator that reads some OTHER non-deterministic
   source the frozen-seed reset does not, and cannot, protect against). A non-empty
   `assertion.payload` is used specifically so the ONLY way this test can fail is the byte-level
   mismatch path (design §6.1 step g), not the separate empty-payload-fails rule (step h) — isolates
   the double-run check from AC3 (first half)'s own failure mode. Asserts `status == :failed`,
   `failing_assertion_ids == [assertion.id]`.
2. `"the SAME non-determinism, once its dot-path IS declared in non_deterministic_fields, is
   stripped before comparison and the assertion passes"` — identical evaluator and artifact, except
   `non_deterministic_fields: ["metadata.nonce"]`. Asserts `status == :passed`, proving
   `strip_non_deterministic_fields/2`'s dot-path removal (design §6.1 step f) is what makes the
   difference between these two tests, not some other confound — the only variable changed between
   test 1 and test 2 is `non_deterministic_fields`.

### `fail_closed_counts/1` — infrastructure failures never leave `assertions_failed == 0` or a row stuck at `:running`

See describe block `"apply_promotion_assertion_rerun/6 -- fail_closed_counts/1: infrastructure
failures never leave assertions_failed == 0 or a row stuck at :running"` — the extra coverage this
run's task briefing flagged as R-Co's own disclosed reference-implementation bug (a stuck `running`
row) that this design deliberately closes:

1. `"a sandbox-claim failure (pool fully exhausted, max_concurrent: 0) records status = :failed with
   assertions_failed == 1 (the real assertion's own id), sandbox_id nil, and a real terminal
   completed_at -- never left at :running"` — `SandboxPool.claim/2` is guaranteed to fail immediately
   (`max_concurrent: 0`, `max_wait_ms: 0`). Re-reads the row from Postgres (not trusting the
   function's own `{:error, :sandbox_unavailable}` return, which carries no row data) to confirm the
   row was actually written to a terminal state, not left at its `:running` default.
2. `"the same sandbox-claim failure against a ZERO-assertion artifact still records assertions_failed
   == 1 (never 0), via the '__infrastructure_failure__' sentinel id (design §11 OQ-2)"` — the sharp
   edge case `fail_closed_counts/1`'s own `max(assertions_total, 1)` clause exists for: an artifact
   with `assertions: []` has no real assertion id to blame, so the design's own synthetic sentinel is
   used instead of leaving the column at its literal `0` default. This is the single test that would
   fail first if `max(assertions_total, 1)` were ever simplified back to a bare `assertions_total`.
3. `"a fixture-load failure (a fixtures[] row naming a table outside FixtureLoader's allowlist)
   records status = :failed with assertions_failed >= 1, and the claimed sandbox is still genuinely
   released (schema dropped) despite the failure"` — `artifact.fixtures` includes one
   `%FixtureRow{table_name: "not_on_the_allowlist", ...}`, guaranteeing
   `FixtureLoader.load_fixtures_only/3` returns `{:error, :invalid_table_name}` (REQ-039's own
   already-tested behavior, reused as a fault-injection point here rather than re-derived). Beyond
   the fail-closed accounting, this test's second half confirms `handle_fixture_load_failure/7`'s own
   release-before-fail-closed-write contract empirically: queries `information_schema.schemata`
   directly for the row's own `sandbox_id`-derived schema name and asserts it no longer exists.

### try/rescue crash safety — proven, not just asserted

See describe block `"apply_promotion_assertion_rerun/6 -- try/rescue crash safety: a raised
exception mid-replay is caught, not propagated, and produces a fail-closed terminal row"` — the extra
coverage this run's task briefing flagged: technique 3 above, a genuine raised exception, not a
simulated stand-in:

1. `"an assertion_evaluator that raises mid-replay results in {:error, {:transaction_failed,
   exception}} to the caller (never a crash), a best-effort sandbox release (schema actually
   dropped), and a :failed row with fail-closed counts (never left at :running)"` —
   `evaluator_raising/0` (`raise "simulated evaluator crash"`) is passed as
   `opts[:assertion_evaluator]`. Asserts the call returns (does not crash the test process)
   `{:error, {:transaction_failed, %RuntimeError{message: "simulated evaluator crash"}}}` — pattern
   matching the exact exception struct, not merely `{:error, _}`. Re-reads the row (via
   `review_id`, since no `run_id` is returned on this path) and asserts `status == :failed`,
   `assertions_failed == 1`, `teardown_error =~ "assertion rerun crashed: simulated evaluator
   crash"`, `completed_at != nil`, `sandbox_id != nil` (the claim succeeded before the exception
   fired). Independently confirms `safe_release/2`'s own best-effort release genuinely ran by
   querying `information_schema.schemata` for the sandbox's own schema name and asserting it no
   longer exists — proving the `rescue` clause's cleanup attempt actually worked, not merely that
   the function returned a plausible-looking error tuple.
