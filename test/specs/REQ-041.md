## Scope-test verdict

Real executable surface exists: a new context module with two public functions
(`compute_pack_update_plan/5`, `classify_artefact/3`), three new `Ecto.Schema`/
changeset modules, and three new migrations that create real tables. Proceeds to the
full test-design procedure — not routed to RELEASE-VALIDATOR as docs-only.

## Key structural fact this suite must not assume away

Unlike every other S2 requirement so far, these three tables are **GLOBAL**
(public/default schema) — REQ-022's schema-per-tenant provision-then-replay fixture
machinery (`test/letflow/definitions/promotion_review_migration_test.exs`'s `:auto`
sandbox mode + on-exit schema drop) is **not needed**. Because these tables carry no
`:prefix` and are not registered in `Letflow.TenantProvisioning.tenant_scoped_migrations/0`,
they were already created by the ordinary `mix ecto.migrate --quiet` step `mix test`'s
alias runs before the suite starts (confirmed by running `MIX_ENV=test mix ecto.migrate
--quiet` directly — no errors, all three migrations already applied). A test can
therefore use a plain `Letflow.DataCase` connection — the normal per-test sandboxed
transaction, `async: true` — and query `information_schema`/`pg_indexes` directly. This
is the one deliberate divergence from `promotion_review_migration_test.exs`'s pattern,
called out explicitly rather than silently copied.

## Test cases

1. **AC1 (migrations land in public schema, applying cleanly)** — see
   `test/letflow/definitions/pack_update_migration_test.exs`:
   - `"all three tables exist under table_schema = 'public'"` — proves via
     `information_schema.tables` that each table is actually reachable in the public
     schema, not merely assumed from the migration's absence of a `prefix:` option.
   - `"none of the three REQ-041 migration modules is registered in
     tenant_scoped_migrations/0"` — proves the GLOBAL classification is structural, not
     accidental: a registered-but-unguarded migration would still (by luck) create the
     table in public on first apply, so this is the test that actually distinguishes
     "deliberately GLOBAL" from "someone forgot the guard AND forgot to register it,"
     which would otherwise look identical to a naive existence check.
   - `"each table's real column set in the public schema matches its Ecto.Schema
     module's field list exactly"` — "applies cleanly" is necessary but not sufficient;
     a migration can apply without error and still disagree with the schema module that
     reads it (this is the drift-detector convention every prior REQ-027/REQ-035
     migration test in this project uses).

2. **AC2 (no matching base row classifies `:conflict`, not `:unchanged` or an error)** —
   see `pack_update_migration_test.exs`, describe block "AC2":
   - `"an artefact with no matching solution_pack_artefact_bases row, and no
     solution_pack_installs row at all, classifies :conflict via
     compute_pack_update_plan/5"` — theirs/incoming differ, no base row exists at all
     (not even a fixture insert). Directly exercises PRM-09 AC5's "cannot prove no
     modification" language, and proves the function returns `{:ok, plan}` (not an
     error tuple, not a crash) with `classification: :conflict`.
   - `"...even when theirs and incoming happen to be identical"` — the sharper case:
     without a base row, `classify_artefact/3`'s contract is that `nil` is never
     treated as equal to anything, including itself by coincidence. A weaker
     implementation that special-cased "theirs == incoming, call it unchanged" would
     pass the first test above but fail this one — this is the test that catches that
     specific mistake.

3. **AC3 (base==theirs!=incoming → clean_update; base==incoming!=theirs → local_only;
   base==theirs==incoming → unchanged)** — two layers:
   - Pure layer, `test/letflow/definitions_test.exs`, describe "classify_artefact/3 —
     AC3": four direct unit tests against `classify_artefact/3` itself (the three named
     outcomes plus the both-differ conflict case from the design's truth table row 4),
     with no DB fixtures — the fastest, most direct proof of the algorithm's own logic.
   - Integration layer, `pack_update_migration_test.exs`, describe "AC3": the same four
     outcomes reproduced through the full `compute_pack_update_plan/5` orchestration
     with a real `solution_pack_artefact_bases` row as the base — proves the DB lookup
     wiring (not just the pure comparison) produces the right classification end to
     end. Kept as two layers rather than one because a bug in `fetch_base/4`'s query
     (e.g. wrong composite key) would make the pure-layer test pass while the real
     behavior is broken — exactly the gap an integration test exists to close.

4. **AC4 (`has_unresolved_conflicts` true iff ≥1 conflict lacks a resolution row)** —
   see `pack_update_migration_test.exs`, describe "AC4":
   - conflict artefact, no resolution row → `has_unresolved_conflicts: true`,
     `resolved: false`.
   - same conflict artefact, a matching `pack_update_resolutions` row inserted →
     `has_unresolved_conflicts: false`, `resolved: true`.
   - two conflict artefacts, only one resolved → `has_unresolved_conflicts` stays
     `true` — proves the flag is an `Enum.any?`, not an `Enum.all?`/count check that
     could be fooled by partial resolution.
   - a resolution recorded against a *different* `target_version` does not resolve the
     conflict — proves `pack_update_resolutions`' per-attempt `target_version` scoping
     (design §3.3, OQ-5) is actually enforced in the lookup, not just documented.
   - zero conflict-classified artefacts (all `:unchanged`) → `has_unresolved_conflicts:
     false` vacuously — the trivial case the design's formula explicitly calls out.

5. **AC5 (moduledoc flags GLOBAL-vs-PER_TENANT as unresolved beyond REQ-041's scope)**
   — see `test/letflow/definitions_test.exs`, describe "AC5": reads
   `Letflow.Definitions.SolutionPackInstall`'s published moduledoc via
   `Code.fetch_docs/1` (the compiled `Docs` chunk, not the `.ex` source text — so a
   matching comment elsewhere would not satisfy it) and asserts it states the GLOBAL
   classification, names the open question explicitly ("OPEN QUESTION, explicitly not
   resolved here"), and defers it to a future REVIEWER/decision-record follow-up rather
   than proposing a general rule itself.

## Beyond the bare acceptance criteria — cheap, real, not busywork

- **Real DB-level FK enforcement** (`pack_update_migration_test.exs`, describe "real DB
  foreign key"): each of the three tables' `tenant_id` rejects a value matching no real
  `tenants` row, via `assert_raise Ecto.ConstraintError`, mirroring this project's own
  `tenant_role_test.exs`/`user_test.exs` FK-assertion pattern. This is the one place
  REQ-041's design explicitly says a real cross-table FK is *possible* (both tables
  share the public schema) where every other S2 per-tenant table's design explicitly
  omits it — worth confirming the FK is actually wired, not just declared in the
  migration text.
- **Each table's own unique index rejects a real duplicate insert**
  (`uq_solution_pack_install_active`, `uq_solution_pack_artefact_base`,
  `uq_pack_update_resolution`) — these are exactly the lookup keys AC2/AC3/AC4's
  queries depend on; if any of the three unique-constraint names in the changeset
  disagreed with the real index name, `Repo.insert` would raise `Ecto.ConstraintError`
  instead of returning `{:error, changeset}` everywhere a caller expects the latter —
  the same class of drift REQ-035's own migration test exists to catch.

## Explicitly out of scope (not tested here)

- SOL-01/02/03's install/export path (does not exist).
- REQ-036's `compute_plan_digest/1` / canonical-JSON normalization (does not exist;
  REQ-041's own contract is that callers supply already-canonical text — see design
  §5.4/OQ-1).
- Apply-time rejection of a plan with `has_unresolved_conflicts: true` (a later
  requirement's job — REQ-041 only computes and exposes the flag).
- The REVIEWER-noted O(n) per-artefact DB-lookup performance characteristic — a future
  optimization note, not a behavior requirement.
