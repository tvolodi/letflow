# Test Spec: REQ-042 — Definition full-text search (`store.zig`'s `Store.search()`, PD-10)

**Requirement:** REQ-042 (`docs/requirements.yaml:2000-2050`, stage S2, `depends_on: [REQ-030]`)
**Design:** `lib/letflow/design/search.md`
**Shipped code:** `lib/letflow/definitions.ex` — `Letflow.Definitions.search/2` (added to
the existing context module, no new file, no new migration, no new schema).
**Test tier:** unit+integration (real Postgres, no mocks — DIRECTIVE T-1) for AC1–AC5;
pure doc-content check for AC6.

## Scope-test verdict

Real executable surface exists: a new public function (`search/2`) on an existing
context module, backed by a real `Ecto.Query` against a real table
(`process_definitions`). Proceeds to the full test-design procedure — not routed to
RELEASE-VALIDATOR as docs-only.

## Fixture strategy

Mirrors `test/letflow/definitions/store_test.exs`'s established `provisioned_tenant/1`
pattern exactly (real `CREATE SCHEMA` via `TenantProvisioning.provision_tenant_schema/1`,
real `TenantProvisioning.replay_migrations/2`, Sandbox `:auto` mode + manual `on_exit/1`
schema drop, `async: false` for the whole module) — `process_definitions` is a
per-tenant-schema table, same as REQ-030's CRUD functions this file's sibling already
covers. Every test provisions its own fresh tenant schema, so even the AC1 test's
requirement for a definition literally named `"invoice"` causes no cross-test collision:
no other test in the suite shares that tenant schema. Every other identifier (`version`,
`created_by`, and any name not literally mandated by an acceptance criterion) uses
`unique_name/1` (`System.unique_integer/1`-suffixed) or a fresh `Ecto.UUID.generate()` —
no shared or hard-coded identifiers beyond what AC1 itself requires, no test depends on
another test's data or on execution order, no wall-clock dependency.

AC6 (moduledoc content) needs no database at all — it is a pure `Code.fetch_docs/1`
check on the compiled `Letflow.Definitions` module, added to
`test/letflow/definitions_test.exs` alongside that file's existing
`normalized_moduledoc/1`-based checks (REQ-030's AC6/AC9, REQ-041's AC5), rather than
invented as a new pattern.

## Test cases

1. **AC1 (ranking order)** — `test/letflow/definitions/search_test.exs`, describe
   "search/2 (AC1) — ranking order": creates three definitions in one tenant — one named
   exactly `"invoice"`, one named `"invoice-approval"`, and one named unrelated to the
   query but with a `description` containing the word "invoice" — then calls
   `Definitions.search("invoice", prefix: schema_name)` and asserts (a) each of the
   three returned ranks is exactly `3.0`/`2.0`/`1.0` respectively, matching the design's
   closed 3-valued rank domain (INV-SR-5), and (b) the three appear in that exact
   relative order in the returned list — proving both the rank *values* and the
   `ORDER BY rank DESC` behavior, not just one or the other (a query that computed the
   right ranks but forgot to order by them would pass a rank-only check and fail this
   one).

2. **AC2 (empty query error)** — describe "search/2 (AC2) — empty query is a distinct
   error, not an empty list": `Definitions.search("", prefix: schema_name)` returns
   exactly `{:error, :query_empty}`. Exists specifically to rule out the tempting-but-wrong
   implementation that treats "no query" the same as "no match" and returns `{:ok, []}`
   — the acceptance criterion's own wording ("not an empty result list") names this
   exact confusion.

3. **AC3 (query too long)** — describe "search/2 (AC3) — a query over 512 bytes is a
   distinct error from the empty-query error":
   - a 513-byte query returns exactly `{:error, :query_too_long}`, structurally distinct
     from AC2's `{:error, :query_empty}` (asserted via `refute error == {:error,
     :query_empty}` in the same test, so a regression collapsing both checks into one
     shared error atom is caught here, not just by two tests that happen to each pass in
     isolation).
   - **boundary case, beyond the bare acceptance criterion but cheap and real**: a
     query of exactly 512 bytes does **not** error — proves the design's `> 512` (not
     `>= 512`) comparison is actually implemented as written (design §4 V1); an
     off-by-one here would silently reject legitimate 512-byte queries and this is the
     one test that would catch it.

4. **AC4 (no match → empty list, not an error)** — describe "search/2 (AC4) — no
   matching name or description anywhere returns an empty list, not an error": creates a
   couple of unrelated definitions, then searches for a token guaranteed not to appear
   in any fixture (`"nonexistent-<unique-integer>"`), asserts the result is exactly
   `{:ok, []}` — not `{:error, _}` of any shape.

5. **AC5 (pagination)** — describe "search/2 (AC5) — limit/offset paginate the ranked
   result", two test cases:
   - **default limit (20)**: creates 25 definitions whose names all share one
     per-test-unique token, calls `search(token, prefix: schema_name)` (no `:limit`/
     `:offset` — exercises the stated default of 20) then
     `search(token, prefix: schema_name, offset: 20)`; asserts page 1 has exactly 20
     results, page 2 has exactly 5, the two pages' definition-id sets are disjoint, and
     their union is exactly the 25 created ids — the two-successive-calls-cover-every-row
     contract the acceptance criterion names literally.
   - **explicit limit**: creates 15 definitions sharing a second per-test-unique token,
     calls `search(token, prefix: schema_name, limit: 10, offset: 0)` then
     `search(token, prefix: schema_name, limit: 10, offset: 10)`; same disjoint-union
     assertion, this time proving a caller-supplied `:limit` (not just the default) is
     actually honored — the first pagination case alone couldn't distinguish "the
     default 20 works" from "any :limit value is silently ignored and 20 is always
     used," this one closes that gap.

6. **AC6 (moduledoc states no new migration/table, citing PD-10)** — reading
   `lib/letflow/definitions.ex`'s moduledoc directly (done as part of this test-writing
   pass, quoted below) confirms the required text is present verbatim:

   > `search/2` (REQ-042) adds definition full-text search over `process_definitions`'
   > `name`/`description` columns via `ILIKE` ranking, ported from `store.zig`'s
   > `Store.search()` per `src/design/definition.md`'s PD-10 section. **PD-10 states
   > explicitly that search lives inside the existing store -- no new Zig source file or
   > SQL migration is required**, and this port adds zero new `priv/repo/migrations/`
   > files and zero new indexes (no `idx_def_name`, no GIN/`tsvector` index) -- the query
   > runs against `process_definitions` exactly as REQ-027 shipped it.

   In addition to this direct read, `test/letflow/definitions_test.exs` gains a runnable
   doc-content test (describe "moduledoc -- AC6: search/2 states no new migration/table
   was added, citing PD-10 (REQ-042)") asserting `Code.fetch_docs/1`'s compiled output
   for `Letflow.Definitions` contains the PD-10 citation, the "no new Zig source file or
   SQL migration is required" claim, the `src/design/definition.md` source citation, and
   the "zero new `priv/repo/migrations/` files"/"zero new indexes" boundary statements —
   so a future edit that weakens or deletes this paragraph fails a real test, not just an
   agent's one-time manual read.

## Explicitly out of scope (not tested here)

- The `GET /api/v1/definitions/search` HTTP endpoint and its `limit > 100` → 422
  rejection — S4 (api-surface) scope, does not exist yet (design §1's scope table).
- Any `tsvector`/GIN-index-backed search path — deliberately never built (design §1, §9
  INV-SR-1).
- SQL-injection safety (INV-SR-2) is a code-construction property (bound `^value`
  parameters, no raw `Repo.query!`), confirmed by direct reading of `definitions.ex`'s
  `where_search_match/2`/`select_with_rank/3`/`order_by_rank/3` (all `fragment/1` calls
  with `?`-placeholders bound to `^`-pinned values or column refs, zero string
  interpolation into SQL text) rather than by a dedicated injection-attempt test — no
  acceptance criterion asks for one, and a query string containing `%`/`_`/`'` behaves as
  ordinary `ILIKE` metacharacters/safe bound text either way (design §6), not a
  distinct behavior worth its own test case.
- `status`/`stage` filtering combined with search — REQ-042's acceptance criteria name no
  such combination; `search/2`'s design deliberately has no status/stage parameter.
