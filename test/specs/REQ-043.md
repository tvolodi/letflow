## Flagged limitation — acceptance criterion 3's second half (Instruction Precedence, `core-directives.md`)

REQ-043 ships **schema only**: `Letflow.Engine.Token`/`Letflow.Engine.Task` have exactly
two structural changesets each (`insert_changeset/2`, `advance_changeset/2` /
`complete_changeset/2`) and **no context-module function with a public `attrs` parameter a
caller could reach** — that is explicitly REQ-045/051/062's job (design §1's scope table,
§4.3 point 2, §5.3 point 2). The design doc's own §6 point 2 states this in so many words:

> "this requirement's schema modules structurally support that contract (by requiring
> `tenant_id` in their cast list) but **cannot themselves enforce the 'never
> caller-supplied' half**, since REQ-043 builds no public function a caller could pass
> attrs into. Flagged explicitly for REQ-045/051/062's own CODE-DESIGNER to carry forward,
> not silently assumed automatic."

Contrast with `EventStore.append/2` (REQ-025), which is a real context-module boundary and
does reject a caller-supplied `:tenant_id` outright — `event_store_test.exs`'s AC6 test
("attrs carrying a caller-supplied `:tenant_id` key is rejected outright with
`{:error, :tenant_id_not_accepted}`") is exactly this criterion's literal shape, and it is
satisfiable there because that function exists. No equivalent function exists yet for
`Token`/`Task`. Writing a test asserting `Token.insert_changeset/2` or
`Task.insert_changeset/2` *rejects* a disagreeing `tenant_id` today would assert something
false about the actual code (confirmed by direct read of both changesets and both
migrations: `tenant_id` carries no FK, no check constraint, no changeset-level comparison
against anything — see `docs/agents/instructions/core-directives.md`'s "No Speculation").

**Resolution, per Instruction Precedence (a `docs/migration/decisions/` gap is not
silently resolved in either direction; this is not a decision-record conflict but the same
"don't fabricate what isn't there" principle applies):** three tests in
`test/letflow/engine/migrations_test.exs`'s "tenant_id" `describe` block cover this
criterion as honestly as the shipped code allows:

1. The **positive** case — a row inserted with `tenant_id` correctly derived via
   `tenant_id_for_schema_name/1` stores and reads back exactly that value (the "derived
   internally" half, literally).
2. **Storage-level isolation** — a row is reachable only under its own tenant's `:prefix`,
   never another provisioned tenant's, proving schema-per-tenant does real isolation work
   independent of the `tenant_id` column's own (currently unenforced) correctness.
3. An **honest negative test** pinning today's real behavior: a `tenant_id` that disagrees
   with the target schema is **currently accepted, not rejected** — asserted explicitly as
   a known, deliberate, and already-flagged gap, not as something this test claims is
   correct. This test is written so it **fails the moment someone adds enforcement without
   updating it** — a deliberate tripwire, not permission to leave the gap.

This is filed as a MINOR issue on this run's handoff (`result.issues`), recommending
REQ-045's own TEST-DESIGNER write the literal "rejects a disagreeing `tenant_id`"
regression test once `Letflow.Engine`'s real context-module function exists to reject it.

## Test cases

### Acceptance criterion 2 — `uq_instance_correlation` partial unique index

1. **A second `instance_projections` row with the same `(definition_id, correlation_key)`
   is rejected as `{:error, changeset}` with `correlation_key: ["has already been taken"]`,
   not a raw `Postgrex`/`Ecto.ConstraintError` crash** — see
   `migrations_test.exs:"a second row with the same (definition_id, correlation_key) is
   rejected with {:error, changeset}, not a raw Postgrex crash"`.
   *Why it exists:* the criterion's own wording, made executable against real Postgres
   through the real `insert_changeset/2` → `unique_constraint(:correlation_key, name:
   :uq_instance_correlation)` path — exactly the path a future EE-01 write hits. The error
   *shape* matters as much as the rejection: a declared constraint name that drifted from
   the real index name would surface as an uncaught `Ecto.ConstraintError` instead, which
   this assertion would catch.

2. **Any number of rows with a NULL `correlation_key` for the same `definition_id` all
   succeed** — see `migrations_test.exs:"any number of rows with a NULL correlation_key
   for the same definition_id are all permitted -- the partial predicate is doing real
   work"`.
   *Why it exists:* the criterion's second clause, literally. Without the index's `WHERE
   correlation_key IS NOT NULL` predicate, three NULL-correlation_key rows under the same
   `definition_id` would violate a naive (non-partial) unique index — this test would fail
   loudly if the partial predicate were ever dropped from the migration.

3. **The same `correlation_key` is fine under a *different* `definition_id`** — see
   `migrations_test.exs:"the same correlation_key is fine under a different definition_id
   -- uniqueness is scoped to the pair, not to correlation_key alone"`.
   *Why it exists:* proves the index is scoped to the *pair*, not to `correlation_key`
   alone — a plausible, wrong implementation (`unique_index(:instance_projections,
   [:correlation_key], ...)`) would still pass test 1 and fail only here.

4. **`uq_instance_correlation` and `idx_proj_definition` exist as real indexes with the
   designed shape** (unique vs. plain, correct columns, correct partial predicate,
   `idx_proj_status` from REQ-023 untouched) — see `migrations_test.exs:"uq_instance_correlation
   and idx_proj_definition exist as real indexes with the designed shape"`.
   *Why it exists:* the structural fact tests 1–3 rely on indirectly; also guards
   REQ-023's own `idx_proj_status` against accidental collateral damage from this
   requirement's migration.

### Acceptance criterion 3 — `tenant_id` internal derivation (tasks/tokens)

5. **A `Token`/`Task` row inserted with `tenant_id` derived via
   `tenant_id_for_schema_name/1` stores and reads back exactly that value** — see
   `migrations_test.exs:"a Token/Task row inserted with tenant_id derived via
   tenant_id_for_schema_name/1 stores and reads back exactly that value"`.
   *Why it exists:* the criterion's "derived internally" half, demonstrated the same way
   `event_store_test.exs`'s AC6 test does — the expected `tenant_id` is computed
   independently of the fixture's own tenant, so a derivation bug would produce a real
   assertion failure, not a tautology.

6. **A row is reachable only under its own tenant's `:prefix`** — see
   `migrations_test.exs:"a Token row written under one tenant's schema is reachable only
   under that tenant's own :prefix, never another provisioned tenant's"`.
   *Why it exists:* schema-per-tenant isolation, independent of whatever the `tenant_id`
   column itself says — the storage-level half of "never misattributes."

7. **Honest pin of today's real behavior: a disagreeing `tenant_id` is currently accepted,
   not rejected** — see `migrations_test.exs:"TODAY, without a context-module enforcement
   point, a caller-supplied tenant_id that disagrees with the target schema is accepted,
   not rejected -- a documented, flagged gap (design §6 point 2), not this test asserting
   that is correct"`.
   *Why it exists:* see "Flagged limitation" above. This is the closest a truthful test can
   get to the criterion's literal "fails loudly" ask, given REQ-043's schema-only scope —
   written as a tripwire against REQ-045+ silently forgetting to add enforcement, not as a
   claim that the current state is acceptable long-term.

### Acceptance criterion 4 — `tasks.status` restricted to exactly PENDING/COMPLETED/CANCELLED

8. **The closed value set is exactly `[:pending, :completed, :cancelled]`, dumping
   uppercase** — see `schemas_test.exs:"the closed value set is exactly [:pending,
   :completed, :cancelled]"` and `"the dump mapping is uppercase, matching R-Co's own
   stored strings exactly"`.
   *Why it exists:* the criterion's first half, pure and fast — `Ecto.Enum.values/2` and
   `Ecto.Enum.mappings/2` read the closed set directly off the compiled schema rather than
   guessing at it.

9. **`complete_changeset/2` rejects a status atom outside the closed set** (`:status` is
   not even castable by `insert_changeset/2` — asserted explicitly so this test fails
   loudly if that cast list ever changes without updating the assumption) — see
   `schemas_test.exs:"a status atom outside the closed set is rejected by cast, not
   silently coerced"`.
   *Why it exists:* "accepts only" has two readings — the closed *set* (test 8) and the
   *rejection* of anything outside it (this test). `Ecto.Enum`'s `cast/1` legitimately
   rejects at the changeset layer, pure and fast — no DB round-trip needed to prove this
   half.

10. **The raw DB column value is the literal uppercase string `"PENDING"`** — see
    `migrations_test.exs:"a Task row's raw status column is the uppercase string
    \"PENDING\""`.
    *Why it exists:* tests 8–9 are pure and cannot see what Postgres actually stores —
    `Ecto.Enum` would decode any dump string back to the same atom on read, making a
    struct-level assertion blind to a casing regression. This queries the raw column
    directly (bypassing the schema's own `load/1`) to corroborate what the pure tests
    predict. Paired with an equivalent `tokens.status` lowercase test
    (`migrations_test.exs:"a Token row's raw status column is the lowercase string
    \"active\""`) so a future harmonization "fix" (INV-EE43-4 forbids it) fails loudly on
    whichever table it touches.

### Acceptance criterion 5 — `current_nodes` (JSONArray) round-trips through real Postgres

11. **A non-empty list of maps round-trips exactly, in order, through a real insert +
    re-select** — see `migrations_test.exs:"a non-empty list of maps round-trips exactly,
    in order"`.
    *Why it exists:* the criterion's own wording, literally — this is the one property a
    pure unit test of `JSONArray`'s callbacks cannot prove (that Postgrex's real jsonb
    encode/decode round-trips correctly through a type whose `type/0` reports `:map`).

12. **Omitting `current_nodes` stores and re-reads the schema-level default `[]`** — see
    `migrations_test.exs:"omitting current_nodes stores and re-reads the schema-level
    default []"`.
    *Why it exists:* the empty-array default is the common case (every instance starts
    with `current_nodes: '[]'` per EE-01 §1a) and exercises a different code path (the
    struct's own default rather than a cast value) than test 11.

13. **`JSONArray.cast/1`/`load/1`/`dump/1` each accept a `list()` and reject a `map()`
    (and, for `cast/1`, a scalar)** — see `test/letflow/event_store/json_array_test.exs`,
    all four `describe` blocks.
    *Why it exists:* the pure, fast, isolated counterpart to tests 11–12 — pins the three
    callbacks' exact behavior in milliseconds, including the negative direction (a JSON
    *object* value, which is exactly what the built-in `:map` type *would* have accepted
    and `JSONArray` must not silently allow through — that would reintroduce the
    corruption risk `current_nodes: %{}` would represent for a column documented as
    holding a JSON array).

14. **`JSONArray.type/0` reports `:map`** — see `json_array_test.exs:"reports :map --
    identical jsonb wire encoding to a plain :map field"`.
    *Why it exists:* pins the specific design choice (§2.4/OQ-3's resolution) that makes
    this a minimal, narrowly-scoped type rather than a new wire encoding — a regression to
    a different `type/0` would silently change the column's Postgres-side type mapping.

### Acceptance criterion 6 — all three migrations apply cleanly, schema-per-tenant

15. **`tokens` and `tasks` land in the tenant's own schema, never in `public`** — see
    `migrations_test.exs:"tokens and tasks land in the tenant's own schema, never in
    public"`.
    *Why it exists:* the `refute ... "public"` half is what proves `:prefix` is actually
    doing the work — a migration that silently ignored `:prefix` would still satisfy a
    naive "does the table exist" check.

16. **`tokens`' and `tasks`' real column sets match their `Ecto.Schema` modules' field
    lists exactly; `instance_projections`' seven new columns exist and its full column set
    matches `InstanceProjection`'s extended field list** — see
    `migrations_test.exs:"tokens' and tasks' real column sets match their Ecto.Schema
    module's field list exactly"` and `"instance_projections' seven new engine-owned
    columns exist and the full column set matches InstanceProjection's extended field
    list"`.
    *Why it exists:* "applies cleanly" is necessary but not sufficient — a migration can
    apply cleanly and still disagree with the schema module that reads it, which would
    surface later as a runtime `Postgrex` error in REQ-045+. Equality, not subset, matching
    `event_store/migrations_test.exs`'s established discipline for the same reason.

17. **All three REQ-043 migration modules are registered in `tenant_scoped_migrations/0`,
    in the required order (`tokens` before `tasks`, both after the `instance_projections`
    `ALTER`)** — see `migrations_test.exs:"the three REQ-043 migration modules are
    registered in tenant_scoped_migrations/0, tokens before tasks, both after the
    instance_projections ALTER"`.
    *Why it exists:* `req022-tenant-schema-provisioning.md` §4: a guarded-but-unregistered
    migration is inert forever; a registered-but-unguarded one corrupts `public`. This
    covers the registration half and the FK-driven ordering constraint design §4.2/§7
    states explicitly (`tasks.token_id` requires `tokens` to already exist).

18. **Each of the three REQ-043 migrations, run with no `:prefix`, creates nothing in
    `public`** — see `migrations_test.exs:"each of the three migrations, run with no
    :prefix, creates nothing in public"` (the §4 guard-pattern `describe` block).
    *Why it exists:* the "no-op under no `:prefix`" half of the criterion, literally —
    each registered module is run through `Ecto.Migrator.run/4` with **no `:prefix`
    option at all** (the exact shape of a plain `mix ecto.migrate` bootstrap) under a
    synthetic, never-before-applied probe version, so Migrator genuinely executes
    `change/0` instead of skipping it as already-applied. Scoped to just REQ-043's three
    modules (rather than relying solely on `event_store/migrations_test.exs`'s broader,
    full-manifest version of this same test) so this spec's own coverage claim for
    criterion 6 does not depend on an unrelated file continuing to exist unchanged —
    though that file's test does also, automatically, now cover these same three entries
    as a second, corroborating layer, since it iterates the full
    `tenant_scoped_migrations/0` list.

## Determinism, isolation and cleanup

- **No wall-clock dependence.** No test in this run uses `DateTime.utc_now/0` for anything
  compared or asserted on; `migrations_test.exs`'s one `DateTime.utc_now/0` call (inside
  `Task.insert_changeset/2`'s test of a `completed_at` value that's deliberately NOT cast)
  is used only as an arbitrary present-ish value, never compared for elapsed time.
- **No unseeded randomness.** Every per-test unique value comes from `Ecto.UUID.generate/0`
  (unique by construction) or `System.unique_integer([:positive, :monotonic])` (a VM
  counter) — the same two mechanisms every other test file in this project uses. No test
  hand-rolls a seed or calls `:rand`.
- **Per-test unique fixtures, no shared hardcoded IDs.** `migrations_test.exs`'s
  `provisioned_tenant/0` provisions a brand-new tenant, physical schema and `Registration`
  row per call — called once per test (never shared across a `describe` block), matching
  `event_store_test.exs`'s established per-test isolation rather than
  `event_store/migrations_test.exs`'s per-`describe`-block sharing.
- **Every created schema is dropped.** `provisioned_tenant/0`'s `on_exit/1` drops the
  physical schema and deletes its own `tenant_schemas`/`tenants` rows; the §4 guard block
  deletes its synthetic probe versions from `public.schema_migrations` and drops only
  tables that are (a) new since the snapshot taken at test start, so cleanup can never
  touch pre-existing state.
- **Self-sufficiency.** No test reads state another test wrote; every DB-touching test
  provisions everything it needs in its own body, and the pure tests read only compiled
  module metadata.
- **No secrets or connection strings.** No test file contains a hostname, port, username or
  password; all database access goes through `Letflow.Repo`, configured in
  `config/test.exs`.
- **No `@tag :skip`, no `TODO`.** Every test case listed above is runnable and runs.
