# Test Spec: REQ-044 — Pure transition kernel skeleton (transition.zig EE-02)

**Requirement:** REQ-044 (`docs/requirements.yaml`, stage S3) — port the core value
types and top-level dispatch of `transition.zig`'s `transition()` as a pure Letflow
module, per `lib/letflow/design/req044-transition-kernel.md` (the gate-approved design
`lib/letflow/engine/{token.ex,instance_state.ex,transition.ex}` implement).

**Requirement text (verbatim, from this run's handoff `context.requirement_text.REQ-044`):**

> Port the core value types and top-level dispatch of `src/engine/transition.zig`'s
> `transition()` as a pure Letflow module -- no `Ecto.Repo` call, no I/O, no clock
> read. Builds `lib/letflow/engine/{token.ex,instance_state.ex,transition.ex}`.
> Determinism is load-bearing (EE-02 AC2, XC-04 kernel determinism): identical inputs
> always produce identical outputs, demonstrated by an explicit test rather than
> asserted. An unknown/unrecognised event type returns an error result, and a state
> whose token sits on a `node_id` absent from the snapshot graph returns an error
> result naming the offending `node_id` -- neither raises or crashes. A token entering
> a `HUMAN_TASK` node adds that node to `pending_task_nodes`, while tokens entering
> `START`, `END`, `EXCLUSIVE_GATEWAY` and `PARALLEL_GATEWAY` nodes do not -- each of
> the five node-type cases has its own explicit test. The moduledoc states explicitly
> that Zig's `std.json.ObjectMap` allocator-ownership contract is deliberately not
> ported. The module reuses REQ-028's existing graph structs from
> `lib/letflow/definitions/graph.ex` rather than defining a second copy.

**REQ-044's own 6 acceptance criteria, as parsed from the paragraph above (matching the
design doc §13 traceability table exactly):**

1. **AC1 — purity.** `transition/3`'s function signature and its entire call graph
   contain zero `Repo` calls, zero HTTP/file access, and zero
   `DateTime.utc_now`/`System.system_time` reads, confirmed by inspection and stated
   in the moduledoc.
2. **AC2 — determinism.** Calling `transition/3` twice with the identical (snapshot,
   state, event) triple returns `==`-equal results, demonstrated by an explicit test
   rather than asserted.
3. **AC3 — the two error paths.** An unknown/unrecognised event type returns an error
   result; a token on a `node_id` absent from the snapshot graph returns an error
   result naming the offending `node_id`; neither raises or crashes.
4. **AC4 — the 5-way dispatch.** A token entering `HUMAN_TASK` adds that node to
   `pending_task_nodes`; tokens entering `START`, `END`, `EXCLUSIVE_GATEWAY`, and
   `PARALLEL_GATEWAY` do not — each of the five node-type cases has its own explicit
   test.
5. **AC5 — moduledoc text.** The moduledoc states explicitly that Zig's
   `std.json.ObjectMap` allocator-ownership contract is deliberately not ported.
6. **AC6 — struct reuse.** The module reuses REQ-028's existing graph structs from
   `lib/letflow/definitions/graph.ex` rather than defining a second copy.

**Test tier:** unit + property. `Letflow.Engine.Transition.transition/3` and its
entire call graph are pure functions over plain structs — no `Letflow.Repo`, no I/O of
any kind (moduledoc's own "Purity (AC1)" section; design doc §8/§11). Same simpler,
faster test shape as REQ-028's `graph_test.exs` (no `Letflow.DataCase`, no
`Ecto.Sandbox`, no Postgres) — plus one `StreamData` property test for AC2, since the
requirement text itself calls determinism out as load-bearing and asks for an explicit
test, not just an inline assertion inside an example test.

## Test cases

### Acceptance criterion 2 — determinism (load-bearing, property test)

1. **`transition/3` called twice with the identical `(definition_snapshot,
   instance_state, event)` triple always returns `==`-equal results** — see
   `transition_test.exs:"calling transition/3 twice with the identical (snapshot,
   state, event) triple always returns == -equal results"`. A `StreamData` property
   test (`world_generator/0`), not a single hand-picked example, following
   `test/letflow/process_instance_test.exs`'s established
   `use ExUnitProperties`/`check all(... <- generator(), max_runs: N)` shape (the
   `docs/guides/test_developer_guide.md` §4 pattern this codebase already uses for its
   one other state-machine module). Chosen over a plain example test specifically
   because the requirement text itself singles determinism out as load-bearing and
   asks for a demonstration, not an assertion buried inside another test.

   **Generator design, so the property actually exercises every dispatch path, not
   just the happy one:** `world_generator/0` builds a graph from a small (≤4-node)
   pool of node ids (`@node_id_pool`), each node's type drawn uniformly from all 8
   `node_type()` variants (so `:START`/`:END`/`:HUMAN_TASK` real dispatch,
   `:EXCLUSIVE_GATEWAY`/`:PARALLEL_GATEWAY` stubs, and the `:SERVICE_TASK`/`:TIMER`/
   `:SUB_PROCESS` catch-all are all represented); a random set of edges and tokens
   drawn from that same pool *plus* a `"ghost-node"`/`"ghost-token"` value deliberately
   excluded from the real pools (guaranteeing reliable, non-flaky coverage of the
   `:unknown_node_id`/`:unknown_token_id` error branches on a meaningful fraction of
   runs, not left to chance); and an event that is usually a well-formed
   `{:advance_token, token_id}` but sometimes a wrong-tag tuple or not a tuple at all
   (`event_gen/0`'s `StreamData.frequency/1` weighting), covering
   `:unknown_event_type` too. `node_ids` deliberately uses plain `list_of/2`, not
   `uniq_list_of/2` — duplicate node ids are a legal input to a function that never
   itself validates graph structure (that's REQ-028's job, upstream of this pure
   kernel), and requiring uniqueness against this small a domain also risks
   `StreamData.TooManyDuplicatesError` at low generation sizes (hit once during actual
   development of this generator — see "Generator design note" below). `max_runs: 150`
   (above `stream_data`'s own 100-run default) since this generator's branching is
   wide enough to want more samples for confidence. Would fail if any dispatch branch
   read anything **not** part of its own arguments (a hidden module attribute computed
   at compile time in an order-dependent way, an `:ets`/process-dictionary read, or —
   the change this test is actually designed to catch — an accidental `System.unique_integer/1`
   or similar non-argument input smuggled into a future edit of any `dispatch_*`
   function).

### Acceptance criterion 3 — the two error paths, plus one defensive addition

2. **An unrecognized event tag returns `{:error, {:unknown_event_type, event}}`, never
   raises** — see `transition_test.exs:"a tuple with an unrecognized tag returns
   {:error, {:unknown_event_type, event}}, not a crash"`. Would fail if the final
   catch-all clause of `transition/3`'s own top-level `case` were removed (which would
   instead raise `CaseClauseError`) or if it returned the wrong tuple shape.
3. **A non-tuple event value (a bare atom, a string, an integer, a map, a list) also
   returns the same named error shape, not a crash** — see
   `transition_test.exs:"a non-tuple event value also returns {:error,
   {:unknown_event_type, event}}, not a crash"`. Exercises 5 distinct term shapes in
   one loop, proving the catch-all clause's pattern is a genuine bare-variable match
   (`event -> {:error, {:unknown_event_type, event}}`), not merely "any 2-tuple with
   an unrecognized first element." Would fail if the catch-all clause were narrowed to
   only match tuples.
4. **A token positioned on a `node_id` absent from `definition_snapshot.nodes` returns
   `{:error, {:unknown_node_id, node_id}}`, naming the exact offending id** — see
   `transition_test.exs:"a token positioned on a node_id absent from the snapshot
   returns {:error, {:unknown_node_id, node_id}}"` and the companion test asserting the
   exact id `"some-specific-node-42"` is echoed back verbatim (`"the error names the
   exact offending node_id, not a generic message"`). Would fail if the node lookup
   used a bang function (`Enum.find!/2`, raising instead of returning `nil`) or if the
   error tuple's payload were a generic atom instead of the real `node_id`.
5. **Defensive addition beyond the literal AC text (design doc §7.3): an event naming
   a `token_id` absent from `instance_state.tokens` returns `{:error,
   {:unknown_token_id, token_id}}`, not a crash** — see `transition_test.exs:"an event
   naming a token_id absent from instance_state.tokens returns {:error,
   {:unknown_token_id, token_id}}, not a crash"`. Not literally named by AC3 (which
   only names the event-type and node-id lookups), but the design doc explicitly flags
   this as part of the same "never raise" totality bar and asks TEST-DESIGNER to cover
   it anyway (design doc §7.3, quoted: "TEST-DESIGNER should still write a test for
   this case even though it is not literally named by an acceptance criterion"). Would
   fail if the token lookup used a bang function or silently matched the wrong token.

### Acceptance criterion 4 — each of the five node-type dispatch cases, its own test

Per AC4's literal wording ("each of the five node-type cases has its own explicit
test"), every one of the 5 cases below is its own `describe` block with at least one
dedicated test — not one shared parametrized test covering all 5 at once.

6. **`:START` (case 1/5) — advances the token onto the target of its first outgoing
   edge in declaration order; `pending_task_nodes` unchanged** — see
   `transition_test.exs:"advances the token onto the target of its first outgoing edge
   in declaration order; pending_task_nodes unchanged"`. Two outgoing edges from the
   `:START` node (`e1 -> "a"`, `e2 -> "b"`), asserting the token moves to `"a"` (`e1`,
   declared first) not `"b"` — locks in design doc §6.1's declaration-order tie-break,
   not just "it moved somewhere." A second test
   (`"other tokens in the instance are left untouched, and list order is preserved"`)
   proves `replace_token/2` only touches the matching token, in place, without
   reordering the list. A third test (`"a START node with no outgoing edge at all
   returns a named error rather than raising (defensive totality)"`) locks in the
   `nil`-branch fallback design doc §6.1 itself flags as defensive. Would fail if the
   edge-selection picked the *last* matching edge instead of the first, if
   `replace_token/2` dropped or duplicated an unrelated token, or if a `:START` node
   with zero outgoing edges raised instead of returning `{:error, {:unknown_node_id,
   _}}`.
7. **`:END` (case 2/5) — removes the token; `pending_task_nodes` unchanged; also
   satisfies the handoff's item 6 ("END node transition moves instance toward
   `:completed` status")** — see `transition_test.exs:"the last live token reaching
   END is removed and status becomes :completed"` and `"a token reaching END while
   another token is still live: removed, status stays unchanged (multi-token case,
   design doc §12.2)"`. The first test is REQ-044's own achievable case (a single live
   token reaching `:END` — the only shape this requirement's own dispatch can ever
   produce, per design doc §12.2's own note that the true multi-token rule isn't fully
   exercisable until REQ-051's `PARALLEL_GATEWAY` split exists); the second
   demonstrates the "moves *toward* `:completed`, not *to* it unconditionally" wording
   using a token that was never actually reachable via this requirement's own dispatch
   (constructed directly on the fixture, not produced by a prior `transition/3` call)
   specifically to prove the `remaining_tokens == []` branch condition itself, not
   just the single-token collapse. Would fail if `status` were set to `:completed`
   unconditionally on any `:END` arrival, or if the token weren't actually removed
   from `tokens`.
8. **`:HUMAN_TASK` (case 3/5) — token stays put; `pending_task_nodes` gains the exact
   token** — see `transition_test.exs:"the token stays at the HUMAN_TASK node, and
   pending_task_nodes gains this exact token"`. Asserts `new_state.pending_task_nodes
   == [tok]` using the same `Token.t()` value (not a rebuilt copy) — design doc §6.3's
   own "the same `Token.t()` value... is appended" wording, and that `new_state.tokens`
   is unchanged (the token does not move). A second test
   (`"pending_task_nodes accumulates -- an existing entry is preserved, the new token
   appended after it"`) proves append semantics, not replace/overwrite semantics.
   Would fail if the dispatch moved the token's position, replaced
   `pending_task_nodes` instead of appending, or appended a reconstructed token
   missing some field.
9. **`:EXCLUSIVE_GATEWAY` (case 4/5, stub) — named error, `pending_task_nodes`
   unchanged** — see `transition_test.exs:"returns the named
   :gateway_not_yet_implemented error, never {:ok, ...}"`. Asserts the exact
   `{:error, {:gateway_not_yet_implemented, :EXCLUSIVE_GATEWAY, node_id}}` shape (never
   `{:ok, ...}`, ruling out an accidental silent no-op success) — see the note directly
   below this list for how "`pending_task_nodes` unchanged" is meaningfully proven on
   an error-returning path. Would fail if this stub ever returned `{:ok, ...}` or a
   different error tag.
10. **`:PARALLEL_GATEWAY` (case 5/5, stub) — same shape as case 4, its own dedicated
    test** — see `transition_test.exs:"returns the named
    :gateway_not_yet_implemented error, never {:ok, ...}"` (the `:PARALLEL_GATEWAY`
    `describe` block, a separate test from case 4's). Would fail under the same
    conditions as case 4, verified independently so a bug in one gateway's stub
    wouldn't be masked by the other's passing.

**A note on "`pending_task_nodes` unchanged" for the two gateway stubs (cases 4 and
5):** unlike `:START`/`:END`/`:HUMAN_TASK`, the gateway stubs never return `{:ok,
new_state, _}` at all — there is no new `InstanceState` value for
`pending_task_nodes` to have changed *on*. Each gateway test therefore asserts two
things together: (a) the exact `{:error, {:gateway_not_yet_implemented, ...}}` shape
(ruling out a hidden, mistaken `{:ok, ...}` success path that *would* need its own
`pending_task_nodes` check), and (b) that the original `state` variable the test built
still shows `pending_task_nodes == []` afterward — true by Elixir's own immutability
guarantee once (a) is confirmed, but asserted explicitly so a reader sees the property
demonstrated, not merely inferred from language semantics.

### Beyond REQ-044's bare 6 acceptance criteria

11. **The catch-all for the 3 remaining `node_type()` variants (`:SERVICE_TASK`,
    `:TIMER`, `:SUB_PROCESS`) plus one bogus atom, all returning a named error, never
    raising** — see `transition_test.exs:"SERVICE_TASK, TIMER, SUB_PROCESS, and an
    unrecognized node_type atom all return a named error, never raise"`. Not itself
    one of REQ-044's 6 numbered ACs (only the 5-way dispatch is named), but design doc
    §6.6 explicitly flags this catch-all as necessary for `transition/3`'s own "never
    raises" totality bar over *every* value `Node.t().node_type` can hold — a partial
    `case` with no catch-all would raise `FunctionClauseError`/`CaseClauseError` on any
    of these 4 remaining possibilities, which is exactly the class of bug AC3's "never
    raises" language exists to rule out generally, even though AC3's own literal text
    only names the event-type/node-id lookups. Cheap to add, matching REQ-028's own
    precedent (`graph_test.exs`'s "Beyond REQ-028's bare acceptance criteria" section)
    of testing a flagged-but-not-numbered design decision as a standing regression
    test. Would fail if any of these 4 nodes-type values raised instead of returning
    `{:error, {:node_type_not_yet_implemented, node_type, node_id}}`.

### Struct-shape sanity (`instance_state_test.exs`, `token_test.exs`)

12. **`InstanceState`'s documented defaults (`status: :active`, `tokens: []`,
    `variables: %{}`, `pending_task_nodes: []`) and its one `@enforce_keys` field
    (`instance_id`)** — see `instance_state_test.exs`. Not itself a REQ-044 acceptance

    defaults holding — a silent default change (e.g. `status: :active` becoming `nil`)

    any default value changed, or if `instance_id` stopped being enforced.
13. **`Token`'s documented defaults (`branch_id: nil`, `waiting_child_instance_id:
    nil`) and its two `@enforce_keys` fields (`node_id`, `token_id`)** — see
    `token_test.exs`. Same rationale as case 12, for the sibling struct.

## Generator design note — `StreamData.TooManyDuplicatesError` hit and fixed during
development, not left as a flaky test

While first writing `world_generator/0`, `node_ids` was generated with
`StreamData.uniq_list_of/2` (requiring distinct node ids). Running `mix test
test/letflow/engine/` surfaced a real, reproducible failure:

```
1) property transition/3 -- determinism (acceptance criterion 2, load-bearing) ...
   ** (StreamData.TooManyDuplicatesError) too many (10) non-unique elements were
   generated consecutively. ...
   MapSet.new(["n1", "n2", "n3"])
```

`@node_id_pool` only has 4 elements, and `StreamData`'s generation-size scaling can
shrink the effective sampling space further at small sizes — asking for uniqueness
against that small a domain is exactly the failure mode `uniq_list_of/2`'s own
documentation warns about ("try to make sure to not make the uniqueness function
return values out of a small value space"). Fixed by switching to plain `list_of/2`
(duplicate node ids are legal input to `transition/3` regardless — it never validates
graph structure itself, that's REQ-028's job). Re-ran: 0 failures, confirmed clean
across multiple re-runs with different random seeds (`mix test test/letflow/engine/
--seed 0`, `--seed 12345`, and the default random seed each ran clean). This is
reported here per this project's "no test depends on... unseeded randomness" bar and
in the spirit of the REQ-028 spec's own "Mutation test" section — an empirical record
that the property test's own construction was itself debugged against a real failure,
not assumed correct on the first try.

## AC5 — moduledoc text, verified by direct reading, not a grep-based ExUnit test

Per this handoff's own instruction (matching the general anti-busywork warning in
`docs/agents/workflows/WF-02_requirement_implementation.md` Step 3: "a grep-based check
is NOT appropriate... manufactured busywork, not real coverage"), AC5's "the moduledoc
states explicitly that Zig's `std.json.ObjectMap` allocator-ownership contract is
deliberately not ported" is a **prose-content** criterion, not application behavior. An
ExUnit test asserting `String.contains?(@moduledoc, "some substring")` would not
demonstrate anything beyond "the string is present" — a decorative check that adds no
real regression protection an attentive reader wouldn't already get from reading the
module directly, and is exactly the kind of manufactured coverage this project's
guidance warns against.

Direct reading confirms `lib/letflow/engine/instance_state.ex`'s `@moduledoc` (lines
10-23) carries the exact verbatim paragraph design doc §9 specifies, under the heading
`## Variable storage: no ObjectMap allocator-ownership equivalent (REQ-044)` — matched
word-for-word against design doc §9's block. RELEASE-VALIDATOR should re-confirm this
by direct reading, per the same precedent.

## AC6 — struct reuse, verified structurally, not by a dedicated runtime test

Design doc §1: "No new `DefinitionGraph`/`GraphNode`/`GraphEdge`/`NodeType`-equivalent
type is declared anywhere under `lib/letflow/engine/`." This has already been confirmed
directly by CODE-DESIGN-VALIDATOR and REVIEWER reading the implementation. There is no
runtime behavior that would distinguish "genuinely reuses `Letflow.Definitions.Graph.t()`"
from "defines an identically-shaped lookalike struct" other than the module name itself
— a fact settled more directly by reading `lib/letflow/engine/transition.ex`'s `alias`
list and `@spec`s than by any ExUnit assertion. It is, however, verified
**incidentally and structurally** by every single test in `transition_test.exs`: every
fixture constructs and passes a real `%Letflow.Definitions.Graph{}` /
`%Letflow.Definitions.Graph.Node{}` value into `transition/3`, and `transition/3`'s own
function head pattern-matches on `%Graph{} = definition_snapshot`
(`lib/letflow/engine/transition.ex:123`) — if `Transition` depended on some other,
duplicate graph struct type under `lib/letflow/engine/`, every test in this file would
fail to compile or dispatch at all, not merely fail an assertion. See
`transition_test.exs`'s own closing comment block for this same note inline.

## Fixture isolation

Every test builds its own graph/token/instance-state value from scratch via the
`node/2`/`edge/3`/`graph/2`/`token/2`/`instance_state/2` helpers — no shared mutable
state, no database row, no `System.unique_integer/1`-style uniqueness needed (same
reasoning as `graph_test.exs`, REQ-028) since these are plain in-memory structs scoped
entirely to each test's own local variables. `async: true` is safe because there is no
shared resource across tests. No test depends on wall-clock time; the one property
test uses `StreamData`'s own seeded generation (seeded from `ExUnit.configuration()[:seed]`,
itself deterministic per `--seed`), not hand-rolled/unseeded randomness.
