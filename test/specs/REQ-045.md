# Test Spec: REQ-045 — Instance start and engine execution shell (EE-01)

**Requirement:** REQ-045 (`docs/requirements.yaml`, stage S3). Design:
`lib/letflow/design/req045-instance-start-engine-shell.md`. Implementation:
`lib/letflow/engine.ex` (`Letflow.Engine.create/2` — the design's own §3 reconciles
the requirement text's informal "create/1" wording to the real two-argument
`create(attrs, opts)` shape, matching every other REQ-025/030-style context module).
Also touches `lib/letflow/definitions/graph.ex` (`Graph.from_map/1`, new public
function) and `lib/letflow/tenant_provisioning.ex` (`maybe_seed_platform_event_types/2`,
seeds the `"INSTANCE_STARTED"` `event_type_registry` row so `EventStore.append/2`
can ever succeed for this event type — design §9 OQ-3a).

## Scope test

Real application-executable Elixir logic: `Letflow.Engine.create/2` (new context
module, `lib/letflow/engine.ex`), `Letflow.Definitions.Graph.from_map/1` (new public
function), `Letflow.TenantProvisioning`'s new seeding step. Not docs-only, not
build-config. Full TEST-DESIGN-VALIDATOR / TEST-RUNNER chain applies.

## Test tier and file

DB-backed integration test: `Letflow.Engine.create/2`'s entire algorithm is I/O —
resolves a real `process_definitions` row, calls `SnapshotStore.create/3` (real
insert), and runs a real `Ecto.Multi` against `instance_projections`/`tokens`/`events`.
Follows `test/letflow/definitions/store_test.exs`'s and
`test/letflow/definitions/snapshot_store_test.exs`'s established `Letflow.DataCase`,
`provisioned_tenant/1`, `async: false` pattern (Ecto.Migrator needs a second real DB
connection the Sandbox can't hand out). New file: `test/letflow/engine_test.exs`,
mirroring `lib/letflow/engine.ex`'s own top-level placement (not nested under
`test/letflow/engine/`, which holds only the pure REQ-043/044 modules with no `Repo`
dependency — this module has a real one).

## Fixture graphs

Every fixture definition is inserted via `Definitions.create/2` + `Definitions.activate/2`
(REQ-030) rather than a raw `Repo.insert!/2`, so each test exercises `create/2`
against a definition that genuinely passed REQ-028/029's structural/attribute
validation — the same discipline `store_test.exs` already established.

- `graph_start_end/0` — `START -> END` directly. First non-START node is `:END`
  (design §9 OQ-1a's second success case): `create/2` should succeed, `current_nodes`
  ends up `[]` (the token is removed on `:END` arrival, per REQ-044's own dispatch),
  and `instance_projections.status` becomes `:completed` in the same call.
- `graph_start_human_task_end/0` — `START -> HUMAN_TASK("role": "approver") -> END`.
  First non-START node is `:HUMAN_TASK`: `create/2` should succeed, `current_nodes ==
  ["task"]`, and a `tokens` row lands at `"task"`.
- `graph_start_gateway_end/0` — `START -> EXCLUSIVE_GATEWAY -> END` (with the gateway's
  own required attributes so the graph is otherwise structurally valid). First
  non-START node is `:EXCLUSIVE_GATEWAY`: since REQ-050/051 shipped and `activate/3`
  now loops to a stable resting state (design §9 OQ-1a, superseded —
  `WF02-REQ045-20260818` rework), `create/2` succeeds — `current_nodes == []`,
  `instance_projections.status == :completed` — exactly like `graph_start_end/0`, the
  gateway's default edge to `:END` having auto-advanced within the same call.
- an inline `SERVICE_TASK` fixture (`START -> SERVICE_TASK -> END`) — the real,
  current capability gap: no requirement has shipped a `:SERVICE_TASK` dispatch
  clause yet, so `create/2` must fail with
  `{:error, {:activation_failed, {:node_type_not_yet_implemented, :SERVICE_TASK, _}}}`
  and write nothing (except the benign snapshot orphan, same as before).

## Test cases

### Acceptance criterion 1 — snapshot before event, correct row shape

1. **`create/2` against an ACTIVE definition inserts an `instance_projections` row
   (`status: :active` transiently visible at the DB level is not itself asserted —
   only the final committed state is — since REQ-044's own dispatch for a
   `HUMAN_TASK` first node keeps status `:active`), variables seeded from
   `initial_variables`, a `tokens` row at the post-`:START` position, and an
   `instance_definition_snapshots` row** — `graph_start_human_task_end/0` fixture,
   asserts every field of the returned `create_result()` map plus a direct re-select
   of all three tables. Would fail if any of the three writes were skipped, or if
   `variables`/`current_nodes` didn't reflect the real post-dispatch state.
2. **The snapshot row is written strictly before the `INSTANCE_STARTED` event** —
   demonstrated by forcing the `Ecto.Multi` (event append) to fail (an unregistered
   `actor_id` that fails `EventStore.append/2`'s own FK) and confirming the snapshot
   row survives as an orphan while `instance_projections`/`tokens`/`events` all have
   zero rows for that `instance_id` — the exact ordering design §5/§9 OQ-4 states is
   the deliberate, accepted shape (a snapshot orphan is benign; a Multi failure rolls
   back the Multi's own three writes, never the already-committed snapshot). Would
   fail if the snapshot call ran inside the same transaction as the Multi (in which
   case it would roll back too) or after the Multi instead of before.
3. **A definition whose first non-START node is `:END` completes in the same call**
   — `graph_start_end/0` fixture: `current_nodes == []`, `status: :completed` on the
   re-selected `instance_projections` row, zero `tokens` rows survive (REQ-044's own
   `:END` dispatch removes the token before this module's own `Ecto.Multi` even
   builds the `tokens` insert — confirmed by reading `activate/3`'s call to
   `Transition.transition/3` running before `persist/7`). Confirms AC1's "token on
   the START node" language is superseded by the real end-state `transition/3`
   produces, not a literal claim the token is left sitting on `:START` (checked
   directly against `lib/letflow/engine.ex` and the design doc per this run's own
   instruction not to assume).

### Acceptance criterion 2 — non-ACTIVE definition rejected, zero rows

4. **`create/2` against a DRAFT definition returns a distinct not-active error and
   writes zero rows** across `instance_projections`, `instance_definition_snapshots`
   and `events`. Would fail if the status check were skipped or if any row leaked
   through before the check.
5. **Same, for a DEPRECATED definition.**
6. **Same, for an ARCHIVED definition.** Three separate tests (not one parametrized
   loop silently collapsing the distinction) since each status is reached via a
   different real transition path (`create` only vs. `create -> activate -> deprecate`
   vs. `... -> archive`), confirming the rejection isn't accidentally specific to one
   transition history.

### Acceptance criterion 3 — `initial_variables` edge cases, three explicit tests

7. **`initial_variables: nil` is rejected with `{:error, :invalid_initial_variables}`,
   writes zero rows.**
8. **`initial_variables` set to a list is rejected the same way, writes zero rows.**
9. **`initial_variables: %{}` (empty map) is accepted** — `create/2` succeeds, the
   resulting `instance_projections.variables == %{}`. Each of the three is its own
   test per the AC's literal "three explicit tests" wording. Would fail if the
   `is_map/1 and not is_struct/1` guard were loosened to accept a list, or tightened
   to reject `%{}`.

### Acceptance criterion 4 — duplicate correlation key, nil correlation key

10. **A second `create/2` with the same `(definition_id, correlation_key)` returns
    `{:error, :duplicate_correlation_key}` and writes no second `instance_projections`
    row** (count stays 1) — also confirms no orphan `tokens`/`events` row was left by
    the rejected second call (the whole Multi rolls back together). Would fail if the
    unique-constraint violation weren't mapped to the distinct atom, or if partial
    rows from the failed second call survived.
11. **Two `create/2` calls with `correlation_key: nil` both succeed** — the partial
    unique index (`WHERE correlation_key IS NOT NULL`) never fires for `nil`. Would
    fail if a naive non-partial unique constraint were used instead.

### Design §9 OQ-1a, superseded (`WF02-REQ045-20260818` rework) — activation now loops
to a stable resting state instead of assuming a fixed hop count

12a. **A definition whose first non-START node is `:EXCLUSIVE_GATEWAY` (default edge
    to `:END`) now completes `create/2` in the same call**: `current_nodes == []`,
    `instance_projections.status == :completed`, zero `tokens` rows — exactly like
    `graph_start_end/0`'s own AC1 test case, demonstrating `activate/3`'s
    `advance_until_stable/3` loop correctly re-hops past the gateway to `:END`'s own
    dispatch instead of stopping short with the token stranded at `"gw"`'s target.
    Would fail if the loop stopped after a fixed hop count instead of a real stability
    check.

### Real, current capability boundary — not a literal REQ-045 AC, but the only way to
demonstrate AC1's "token ends up wherever `transition/3` actually moves it" for a
definition whose first node genuinely can't be dispatched by any shipped requirement

12b. **A definition whose first non-START node is `:SERVICE_TASK` fails `create/2`
    outright** with `{:error, {:activation_failed, {:node_type_not_yet_implemented,
    :SERVICE_TASK, _}}}`, and writes zero rows across all three tables (the snapshot
    row is the one exception — see design §5 step 7/§9 OQ-4: the snapshot call runs,
    and commits, before the pure `activate/3` dispatch that fails; this is the same
    deliberate "benign orphan" shape as test case 2 above, so this test asserts the
    snapshot DOES exist while the other three tables have zero rows, rather than
    asserting "zero rows everywhere"). Would fail if `create/2` accidentally succeeded
    for an unsupported node type, or crashed instead of returning a typed error.

### Acceptance criteria 5, 6, 7 — moduledoc content assertions

Same pattern as `test/letflow/engine/schemas_test.exs`'s `normalized_moduledoc/1`
helper (read via `Code.fetch_docs/1`, whitespace-collapsed) — a prose-content
criterion, not application behavior; a `String.contains?` check here still adds real
regression protection (catching an accidental deletion/weakening of the required
statement) without being a decorative restatement, since these three ACs are
themselves worded as "the moduledoc states X."

13. **AC5 — the moduledoc states which of `process_instance.ex`/
    `instance_supervisor.ex` is superseded vs. generalized**, and whether
    `Letflow.Events.TransitionEvent` is retired or kept, with the REQ-046 pointer.
14. **AC6 — the moduledoc names the process-vs-row open question explicitly**,
    states it is resolved for EE-01's own scope only, cites
    `stage-3-instance-engine.md`'s second Early finding, and states the answer may
    differ for REQ-056/057.
15. **AC7 — the moduledoc states `POST /api/v1/instances` is S4 scope** and that this
    requirement builds a context-module function only.

### `actor_id`/`idempotency_key` missing-value behavior (OQ-3b/INV-8)

16. **`create/2` with `attrs` missing `:actor_id` returns
    `{:error, {:event_append_failed, :missing_actor_id}}`** (never raises), plumbed
    straight through from `EventStore.append/2`'s own typed error — confirms `Map.get/2`
    is used, not `Map.fetch!/2`, on this externally-reachable field (REVIEWER-confirmed
    intentional typed-error behavior, not a gap). Also confirms zero rows survive
    across `instance_projections`/`tokens` (the Multi's M3 step fails, rolling back
    M1/M2 too), leaving only the benign snapshot orphan — same shape as test cases 2
    and 12b.

### WF02-REQ045-20260818 addendum — worklist rework coverage gap (REVIEWER Step 2d re-review)

REVIEWER PASSed the `advance_until_stable/4`/`tokens_needing_dispatch/3` worklist
rework (superseding the old fixed-2-hop dispatch) but flagged a non-blocking
coverage gap: zero `:PARALLEL_GATEWAY` split/join coverage (multiple tokens in
flight simultaneously — the exact scenario the worklist loop's multi-token
bookkeeping exists for) and zero hop-limit-exceeded coverage. New fixtures:
`graph_start_parallel_split_join_end/0`, `graph_start_parallel_split_human_tasks/0`,
`graph_start_gateway_cycle_never_exits/0`.

17. **A split whose 2 branches both lead directly to the matching join (no
    intermediate node in either branch — mirrors
    `test/letflow/engine/parallel_gateway_test.exs`'s own split/join fixture shape)
    completes `create/2` in the same call**: `status: :completed`, `current_nodes ==
    []`, zero `tokens` rows survive (both split-derived tokens are consumed by the
    join, and the join's own merged token is then consumed by `:END`, all within one
    `create/2` call). Would fail if the worklist loop failed to re-queue either
    split-derived token, or failed to re-queue the join's newly-fired merged token.
18. **A split whose 2 branches each stop at their own `:HUMAN_TASK` leaves exactly 2
    live tokens, one per branch** (`graph_start_parallel_split_human_tasks/0` — the
    join/`:END` portion of this graph exists only so `find_matching_join/2` succeeds
    structurally; it is never reached, since neither branch ever leaves its
    `:HUMAN_TASK`). Chosen per task step 2b's own guidance: the simplest graph shape
    that lets `create/2` actually observe a multi-token split result without
    inventing a same-call join `create/2` wasn't designed to reach. Asserts
    `result.current_nodes`/`projection.current_nodes` are `["task_a", "task_b"]`
    (sorted), `token_count == 2`, both `tokens` rows' `node_id`s match, and both
    rows have distinct `branch_id`s (confirming 2 genuinely independent tokens, not
    one duplicated). **This test currently fails against the implementation as
    written** — see "Bug found by this test" below; it is deliberately left in the
    suite failing rather than removed or weakened, per this project's core
    directive against reporting untested work as done.
19. **A `CHK-06`-permitted 2-gateway cycle (`gw1 <-> gw2`, neither ever satisfying
    its exit condition) that never reaches a resting state returns
    `{:error, {:activation_failed, {:hop_limit_exceeded, token_id}}}`**, writing
    zero rows except the benign snapshot orphan. This is a **real integration test
    of the actual hop bound**, not a fabricated stand-in: `graph.ex`'s CHK-06 cycle
    check explicitly permits a cycle when at least one endpoint of the closing
    back-edge is a gateway node, so a definition exercising this test's exact shape
    could genuinely reach `create/2` in production. Confirmed by direct trace of
    `graph.ex`'s `check_cycles/1` (self-loop-through-a-gateway is also
    CHK-06-permitted, but doesn't work here: `tokens_needing_dispatch/3` treats a
    token landing back on its own prior `node_id` as "stayed put," the same rule
    that stops `:HUMAN_TASK` re-dispatch, so a 1-node self-loop never re-queues and
    the loop ends after 1 hop — two distinct gateway node_ids are required for the
    hop count to keep climbing toward the `length(graph.nodes) * 4 + 10 == 26`
    bound). Would fail if the hop bound were miscounted or the loop's termination
    condition were wrong in a way that let a genuine non-terminating case loop
    forever instead of erroring.

#### Bug found by this test run (test case 18) — not fixed by TEST-DESIGNER, reported for ELIXIR-DEV/ISSUE-FIXER

`lib/letflow/engine.ex`'s `insert_token_records/4` (design doc §6 step 10, M2) has
exactly 2 clauses:

```elixir
defp insert_token_records(_repo, _instance_id, [], _prefix), do: {:ok, []}
defp insert_token_records(repo, instance_id, [%Token{} = token], prefix) do ...
```

There is no clause for a list of 2+ tokens. Any `create/2` call whose activation
loop ends with more than one live token — the exact `:PARALLEL_GATEWAY` split
landing on 2+ `:HUMAN_TASK` branches this WF02-REQ045-20260818 addendum was
commissioned to cover — raises `FunctionClauseError` inside the `Ecto.Multi.run/3`
callback (M2), violating this codebase's own "never raise" totality discipline
(`transition.ex`'s moduledoc, restated project-wide). Actual failure, captured by
running `mix test test/letflow/engine_test.exs` against the code as merged to this
branch (commit `e4512ef` + this addendum's own test-only changes):

```
1) test create/2 -- :PARALLEL_GATEWAY split/join (REVIEWER-flagged gap, WF02-REQ045-20260818) a split whose 2 branches each stop at their own HUMAN_TASK leaves 2 live tokens, one per branch (Letflow.EngineTest)
   ** (FunctionClauseError) no function clause matching in Letflow.Engine.insert_token_records/4
   Attempted function clauses (showing 2 out of 2):
       defp insert_token_records(_repo, _instance_id, -[]-, _prefix)
       defp insert_token_records(repo, instance_id, -[%Letflow.Engine.Token{} = token]-, prefix)
```

Per this run's own instructions and the project's core directives, TEST-DESIGNER
does not implement the fix (that's ELIXIR-DEV's scope, likely via ISSUE-FIXER
diagnosis first) and does not weaken or remove this test to make the suite green —
doing so would hide a genuine, currently-reachable multi-token bug behind a passing
suite. Test case 18 is left in `test/letflow/engine_test.exs`, currently RED, as
the reproducing regression test for that fix.
