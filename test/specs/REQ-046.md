# Test Spec: REQ-046 — Retirement of `process_instance.ex`; retention of `instance_supervisor.ex`

**Requirement:** REQ-046 — verbatim acceptance criteria from `docs/requirements.yaml`:

1. `lib/letflow/process_instance.ex` is either deleted (with every test referencing it
   migrated or removed, and `mix test` passing) or retained with a moduledoc paragraph
   stating explicitly why it survives alongside REQ-045's engine and what its remaining
   role is.
2. `lib/letflow/instance_supervisor.ex` either starts REQ-045's definition-driven
   instances or is retired explicitly with a recorded reason — it is not left in the
   supervision tree supervising a superseded module.
3. `mix test` passes with the actual output quoted, after the change — no test is
   deleted merely to make the suite green without stating why in the commit or
   moduledoc.
4. The resulting supervision tree preserves real supervised isolation (killing one
   instance's process, if processes are used, does not affect another), demonstrated
   by a test or explicitly stated as not-applicable if REQ-045 resolved to a row-based
   engine.

**Test tier:** unit+integration

**Scope-test verdict (see run notes for full reasoning):** REQ-046 is fundamentally a
deletion/retirement requirement. Most of AC1/AC3/AC4 are already fully proven by (a) the
existing full suite passing with `process_instance.ex`, `transition_event.ex`, and
`process_instance_test.exs` gone — nothing broken by the deletion — and (b)
`test/letflow/engine_test.exs` (REQ-045) already covering the replacement
definition-driven start path, and `test/letflow/parallel_approval_test.exs` already
covering the surviving supervised-isolation guarantee AC4 asks for (cited by name in
`lib/letflow/design/req046-process-instance-retirement.md` §6). No new test is written
to re-prove those — that would duplicate coverage that already exists under a different
file, not add real protection.

**Genuine new surface identified:** `lib/letflow/router.ex` was edited by this
requirement (§6a of the design doc) — three routes removed (`POST /instances`,
`POST /instances/:id/actions`, `GET /instances/:id`), `GET /health` and the catch-all
404 retained. No test anywhere in `test/` exercised `Letflow.Router` before this
requirement (confirmed by grep — `test/letflow/plugs/*_test.exs` test individual plug
modules, not the composed router's route dispatch; `test/specs/REQ-021.md`'s one hit is
prose, not code). `docs/guides/test_developer_guide.md` §2 explicitly names
`Letflow.Router` end-to-end testing as a coverage target once such tests exist ("see
REQ-107's precedent" — REQ-107 is not yet implemented, so no prior test file to extend).
This is real, previously-uncovered, low-cost-to-test behavior: AC1's compile-integrity
concern (no remaining reference to a deleted symbol) and the router's own post-change
contract (exactly `/health` live, everything else 404s) are both directly assertable via
`Plug.Test`, matching the established `Plug.Test`-based convention already used in
`test/letflow/plugs/tenant_status_test.exs`.

## Test cases

1. `GET /health` still returns `200` with `{"status": "ok"}` — proves the one retained
   route is unaffected by the route removals — see
   `test/letflow/router_test.exs:"GET /health returns 200 and status ok"`.
2. `POST /instances` (the removed create-instance route) now returns `404` via the
   catch-all, not a `Plug.Conn.WrapperError`/500 from calling an undefined remote
   function — proves the route was cleanly removed, not left dangling against a deleted
   module (AC1's compile-integrity concern, made concrete at the HTTP layer) — see
   `test/letflow/router_test.exs:"POST /instances now falls through to 404"`.
3. `POST /instances/:id/actions` (the removed action route) returns `404` — same proof
   for the second removed route — see
   `test/letflow/router_test.exs:"POST /instances/:id/actions now falls through to 404"`.
4. `GET /instances/:id` (the removed read route) returns `404` — same proof for the
   third removed route — see
   `test/letflow/router_test.exs:"GET /instances/:id now falls through to 404"`.
5. An arbitrary unknown path still returns `404` — regression guard confirming the
   catch-all itself (unmodified by this requirement) still behaves as before — see
   `test/letflow/router_test.exs:"an arbitrary unknown route still 404s"`.

Each of cases 2-4 is a test that would have failed loudly against the pre-REQ-046
router (it would have raised trying to call the now-deleted
`Letflow.InstanceSupervisor.start_instance/1` / `Letflow.ProcessInstance.*` functions,
not returned 404) — so this is real regression coverage for the deletion, not a
tautological "test that the code does what the code does."

## Why no new test for `process_instance.ex` / `transition_event.ex` / `instance_supervisor.ex` directly

- `process_instance.ex` and `transition_event.ex` are deleted outright — there is no
  executable surface left to test *against*; the only meaningful assertion ("these
  symbols no longer exist / nothing references them") is what `mix compile
  --warnings-as-errors` and the full `mix test` run already demonstrate by succeeding.
- `instance_supervisor.ex` is reduced to a bare `start_link/1` + `init/1` (unchanged
  code, per design §2) plus a new moduledoc. It is already exercised implicitly on every
  single test run: it is a permanent child of `Letflow.Application`'s supervision tree,
  so if it failed to start (or crashed) the entire suite would fail to boot, not just a
  hypothetical dedicated test. A dedicated `instance_supervisor_test.exs` asserting "it
  starts with zero children" would only re-prove what `DynamicSupervisor.init/1`'s own
  documented semantics already guarantee — not real new coverage.
