# Test Spec: REQ-047 — Task activation persistence (EE-03)

**Requirement:** REQ-047 (`docs/requirements.yaml`, stage S3) — port
`InstanceStore.applyTransition()` as the persistence orchestration layer that turns
REQ-044's pure transition output into committed rows. Design:
`lib/letflow/design/req047-task-activation-persistence.md`. Implementation:
`lib/letflow/engine/task_activation.ex` (new module) + `lib/letflow/engine.ex`
(extended `persist/7`), both PASSed by SECURITY-REVIEWER and REVIEWER.

**Test tier:** unit (pure, `Letflow.Engine.TaskActivation`'s own functions +
`Letflow.Engine.Transition`'s dispatch clauses directly) + integration (real Postgres,
`Letflow.Engine.create/2` end to end, extending `test/letflow/engine_test.exs`'s own
established fixtures/helpers).

## Test cases

1. `newly_pending_tokens/2` returns only tokens whose `token_id` is new relative to the
   "previous" list — proves the diff-by-`token_id` set-difference design (§5.1) is
   exactly that, not e.g. full-struct equality or an off-by-one on which list is
   authoritative. See `test/letflow/engine/task_activation_test.exs`:
   `"newly_pending_tokens/2"` describe block.

2. `resolve_assignee/1` reads `assignee_ref` from `attributes["role"]` and
   `assignee_type` from `attributes["assignee_type"]`, defaulting the latter to `nil`
   when absent, with **zero** group-membership checking — proves AC4's "group with no
   members still gets a task" is true because this function never looks at membership
   at all, not because a membership check happened to pass. Same describe block, cases
   for both attribute-present and attribute-absent.

3. `insert_attrs/4` builds the six-key attrs map, with the `node.label -> node.id`
   fallback for a `nil` label (§4.2/OQ-2) — proves `tasks.node_name`'s `null: false`
   constraint can never be violated by a structurally-valid-but-unlabeled node, and that
   `:status` is never included (so the schema's `default: :pending` is what makes every
   row PENDING, not something this function sets itself — INV-EE47-2).

4. `token_id_to_record_id/2` zips two same-order lists into a `token_id => record.id`
   map — proves the FK-resolution mechanism (§3) actually produces the right pairing,
   not just "some map."

5. Four explicit unit tests, one per node type (`:START`, `:END`, `:EXCLUSIVE_GATEWAY`,
   `:PARALLEL_GATEWAY`), each calling `Transition.transition/3` directly (REQ-044's own
   pure kernel, no DB) and then `TaskActivation.newly_pending_tokens/2` on the
   before/after `pending_task_nodes` lists, asserting the diff is `[]`. This is the
   acceptance criterion's own required distinction between "verifying" and "merely
   assuming" the transition function's guarantee — it exercises the real dispatch
   clauses (REQ-044/050/051's shipped code) rather than trusting the design doc's
   citation that only `dispatch_human_task/3` ever appends. A regression in any of these
   four dispatch clauses (e.g. someone mistakenly wiring `:EXCLUSIVE_GATEWAY` to also
   append to `pending_task_nodes`) would fail this test even though it would not fail
   any REQ-044/050/051 test (their own tests check routing/token movement, not this
   module's own "is a task row warranted" question).

6. `cancel_pending_timers/2` returns `:ok` unconditionally, and its `@doc` states the
   SCH-03 hook naming and S6 ownership verbatim in substance — a moduledoc/doc-content
   assertion (matching `engine_test.exs`'s own AC5/AC6/AC7 precedent for
   structural/documentation acceptance criteria that have no other runtime behavior to
   assert on today).

7. Integration: a `create/2` call whose first non-`START` node is `:HUMAN_TASK` results
   in exactly one `tasks` row, `status: :pending`, with the right `instance_id`,
   `node_id`, `node_name`, `assignee_type`, `assignee_ref` — proves AC1 end to end
   through the real `Ecto.Multi`, not just that `insert_attrs/4` builds the right map in
   isolation (case 3 above proves the map; this proves the map actually gets written).
   See `test/letflow/engine_test.exs`, describe `"create/2 (REQ-047 AC1)..."`.

8. Integration: forcing the `:event` Multi step to fail (missing `:actor_id`, the same
   forced-failure technique `test/letflow/engine_test.exs`'s own REQ-045 atomicity test
   already uses) against a `HUMAN_TASK`-first graph leaves **zero** rows in `tasks`,
   `instance_projections`, and `tokens` — proves the task-row insert genuinely
   participates in the same `Repo.transaction/1` as the other three writes, not a
   separate transaction of its own that could survive the rollback. This is the test
   that would fail if `:task_records` were ever accidentally wired to its own
   `Repo.transaction/1` instead of `Multi.run/3` on the caller's `multi`.

9. Four integration tests, one per node type, asserting `create/2` against a graph whose
   first non-`START` node is that type ends with zero `tasks` rows — the DB-level
   companion to case 5, proving the whole pipeline (not just the pure diff) produces no
   row for these four types. Reuses `engine_test.exs`'s own existing
   `graph_start_end/0` (START+END), `graph_start_gateway_end/0` (EXCLUSIVE_GATEWAY),
   `graph_start_parallel_split_join_end/0` (PARALLEL_GATEWAY split+join) fixtures.

10. Integration: a `HUMAN_TASK` node whose `attributes["assignee_type"]` is `"GROUP"`
    and whose `attributes["role"]` (→ `assignee_ref`) names a group with no members
    (nothing in this schema's tables backs any group/membership concept at all, so
    "no members" is simply "not validated against anything") still produces exactly one
    `PENDING` task row, no error — proves AC4 end to end, not just at the pure
    `resolve_assignee/1` layer (case 2).

11. Integration: a `create/2` call whose first non-`START` node is `:END` sets
    `instance_projections.status` to `:completed`, creates zero `tasks` rows, and (via
    case 6's moduledoc assertion) documents the SCH-03 hook — proves AC5's three parts
    together against the real `persist/7`/`finalize_instance_projection/4` path.

## Coverage check

- [x] AC1 (exactly one PENDING tasks row, same-transaction) — cases 3, 7
- [x] AC2 (forced event-append failure -> zero tasks/instance_projections/tokens) —
      case 8
- [x] AC3 (START/END/EXCLUSIVE_GATEWAY/PARALLEL_GATEWAY -> zero tasks rows, each its own
      explicit test, verifying not assuming) — cases 5, 9
- [x] AC4 (group with no members still gets a PENDING task) — cases 2, 10
- [x] AC5 (END -> COMPLETED, no task, documented SCH-03/S6 hook) — cases 6, 11
- [x] Closed state/transition set touched (the 5-way `Transition` dispatch) — covered by
      direct-dispatch unit tests (case 5), not merely a property test, matching
      `transition_test.exs`'s own established mix of a determinism property plus
      explicit per-dispatch-clause example tests; no new property test is added by this
      spec because REQ-044's own `transition_test.exs` already owns the
      determinism/statespace property coverage for these dispatch clauses — this
      requirement's own new surface (`TaskActivation`) is a pure diff/mapping layer with
      no additional state machine of its own to property-test.
