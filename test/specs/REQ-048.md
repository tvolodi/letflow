# Test Spec: REQ-048 — Task completion (EE-04, `Letflow.Engine.complete_task/3`)

**Requirement:** REQ-048 (`docs/requirements.yaml`, stage S3) — `Letflow.Engine.complete_task/3`
completes a `PENDING` `Letflow.Engine.Task`: merges `attrs.output_variables` into the
instance's live variables, evaluates the completed `:HUMAN_TASK` node's own outgoing
edge(s) via `Letflow.Engine.Transition`'s `{:complete_task, token_id}` dispatch, activates
any newly-reached `:HUMAN_TASK` node(s), flips the task row to `COMPLETED`, and appends
exactly one `TASK_COMPLETED` event — all inside one `Ecto.Multi`. Row-level `SELECT ...
FOR UPDATE` locking on `tasks` and `instance_projections` serializes concurrent
`complete_task/3` calls on the same `task_id`.

**Design doc:** `lib/letflow/design/req048-task-completion.md`
**Implementation read directly (not the design doc alone — one deviation from the design
was found and fixed during implementation):** `lib/letflow/engine.ex`'s `complete_task/3`
and its private `run_complete_task/6` Multi chain; `lib/letflow/engine/transition.ex`'s
`dispatch_task_completion/4` and `really_conditioned?/1`; `lib/letflow/engine/task_activation.ex`'s
`append_multi_from_existing_records/6`.

**Test tier:** unit+integration (real Postgres via `Letflow.DataCase`/sandbox `:auto`,
matching `test/letflow/engine_test.exs`'s own established pattern for this module — no
meaningful pure-layer split, `complete_task/3`'s whole algorithm is I/O) plus one pure
unit test (moduledoc-content check, AC5).

## Implementation detail load-bearing for these tests

`Registry.validate_payload/3` (called inside `EventStore.append/2`, which `complete_task/3`'s
M9 step calls for the `TASK_COMPLETED` append) requires `"TASK_COMPLETED"` to already be a
registered `event_type_registry` row for the tenant, or the whole call fails with
`{:error, :unknown_event_type}` — this is explicitly named as OQ-6 in the design doc §10/§13
("inherited not new" — the same pre-existing pattern `"INSTANCE_STARTED"` already required for
REQ-045, and `test/letflow/event_store_test.exs`'s own `register_event_type!/2` fixture already
established this pattern for REQ-025's tests). Every test below that calls
`Engine.complete_task/3` registers a permissive `"TASK_COMPLETED"` event type
(`%{"type" => "object"}` schema — accepts any JSON object) via `Registry.register_type/2`
immediately after tenant provisioning, mirroring `event_store_test.exs`'s own
`register_event_type!/2` helper.

## Test cases

1. **AC1 + `really_conditioned?/1` fix** — `complete_task/3` on a `PENDING` task at a
   `HUMAN_TASK` node with a single, ordinary, unconditioned outgoing edge (no `condition`,
   no `is_default`) merges `output_variables`, flips the task row to `COMPLETED` with
   `completed_at`/`completed_by` set, activates the next `HUMAN_TASK` node as a new
   `PENDING` task row, updates `instance_projections.current_nodes`/`variables`, and
   appends exactly one `TASK_COMPLETED` event — verified by reading `tasks`,
   `instance_projections`, and `events` back after one call.
   See `test/letflow/engine_complete_task_test.exs:"AC1 — completing a PENDING task ..."`.
   **Why this exists, beyond restating the AC:** the implementation's own comment in
   `transition.ex` documents that reusing the design's originally-specified
   `is_default`-only edge partition made *this exact scenario* — the ordinary
   single-unconditioned-edge `HUMAN_TASK` completion, not an edge case — fail with
   `{:error, {:no_matching_edge, ...}}` on every call, because an edge with `condition: nil`
   was wrongly bucketed as "conditioned" and then evaluated as `Expr.evaluate_condition(nil,
   _)` (always `false`). `really_conditioned?/1`'s fix (treat `condition: nil`/`""` as a
   default/fallback candidate, same as `is_default: true`) is what makes this test pass at
   all — the test fails deterministically against the pre-fix partition logic, so it is
   real regression coverage for that fix, not incidental.

   **Status as of this writing: this test currently FAILS against the shipped
   implementation** (`assert length(tasks) == 2` observes `1`) — not because of a test
   bug, but because it caught a second, independent, BLOCKER-severity defect while
   verifying AC1: `TaskActivation.newly_pending_tokens/2`'s `token_id`-only diff never
   creates a `tasks` row for `task_b` when the same token continues directly from
   `task_a` to `task_b` (no gateway/split involved) — the instance's `tokens`/
   `instance_projections` rows correctly advance to `task_b`, but no `PENDING` task
   exists there for anyone to ever complete. Filed as `docs/issues/ISS-0057.yaml`
   (GitHub #202). This is intentional, verified coverage, not a mistake to "fix" by
   loosening the assertion — TEST-RUNNER/ELIXIR-DEV should treat this test's failure as
   the reproduction case for ISS-0057, and this test should turn green once that issue
   is fixed, not before.

2. **AC1 — instance completes when the next node is `:END`** — completing a `PENDING`
   task whose single outgoing edge leads straight to `:END` flips the instance to
   `:completed` (`instance_projections.status`), leaves zero live `tokens` rows, and still
   appends exactly one `TASK_COMPLETED` event. Exists to prove AC1's "activates the next
   node" language also covers the terminal case correctly (a `:HUMAN_TASK -> :END` shape
   is a materially different final-state assertion than AC1's own two-task-chain case
   above — an instance reaching `:completed` reconciles `instance_projections` and removes
   the token row entirely, both of which are new code paths `run_complete_task/6`'s M10
   step exercises differently than the "next node is another `HUMAN_TASK`" case).
   See `test/letflow/engine_complete_task_test.exs:"AC1 — completing the last PENDING ..."`.

3. **AC2a — `output_variables: %{}` succeeds.** An empty map is a structurally valid
   `output_variables` value (`fetch_output_variables/1`'s `is_map/1` guard accepts it);
   proves the empty-map case is not mistakenly treated the same as "missing."
   See `test/letflow/engine_complete_task_test.exs:"AC2 — output_variables: %{} succeeds..."`.

4. **AC2b — `output_variables: nil` returns a distinct, typed error.** `nil` fails
   `fetch_output_variables/1`'s `is_map/1` guard and returns
   `{:error, :invalid_output_variables}` before any I/O — proves the pre-transaction
   validation path rejects `nil` specifically (not merely "any error"), and rejects it
   *before* touching the database (zero task-row mutation, checked explicitly).
   See `test/letflow/engine_complete_task_test.exs:"AC2 — output_variables: nil is rejected..."`.

5. **AC3a — a non-existent `task_id` returns `{:error, :task_not_found}`.**
   See `test/letflow/engine_complete_task_test.exs:"AC3 — a non-existent task_id ..."`.

6. **AC3b — an already-`COMPLETED` task returns `{:error, {:task_not_pending, :completed}}`,
   a distinct, separately pattern-matchable shape from AC3a's `:task_not_found`.** Completes
   the same task twice in sequence; the second call must not be confused with "not found" —
   proves `fetch_and_lock_task/3`'s two failure branches (`nil` vs. `%Task{status: status}`)
   are exercised and produce genuinely different tagged tuples, not one shared generic
   "can't complete this task" error.
   See `test/letflow/engine_complete_task_test.exs:"AC3 — completing an already-COMPLETED ..."`.

7. **AC4 — two concurrent `complete_task/3` calls on the same `task_id` result in exactly
   one success and one `{:error, {:task_not_pending, :completed}}`.** Two Elixir processes
   (`Task.async/1`, real separate Postgres connections — sandbox mode is `:auto` for this
   fixture, same as `engine_test.exs`'s own `provisioned_tenant/0`, not the shared-connection
   `:manual` sandbox mode) both call `Engine.complete_task/3` for the same `task_id` at
   essentially the same time. `fetch_and_lock_task/3`'s `SELECT ... FOR UPDATE` forces the
   second transaction to block until the first commits or rolls back, then re-reads the row
   and sees `status: :completed` — proving the row lock, not luck, is what prevents a
   double-completion. Asserts the outcome multiset is exactly `[{:ok, _}, {:error,
   {:task_not_pending, :completed}}]` in either order (order is legitimately
   nondeterministic — whichever process's transaction commits first), and that exactly one
   `TASK_COMPLETED` event and one `COMPLETED` task row exist afterward (not two).
   See `test/letflow/engine_complete_task_test.exs:"AC4 — two concurrent complete_task/3 ..."`.

8. **AC5 — the moduledoc states the S4 scope boundary.** A pure, no-DB test reading
   `Letflow.Engine`'s compiled moduledoc (`Code.fetch_docs/1`) and asserting it names both
   HTTP status-code mapping and IDN-03 assignee authorization as S4/out-of-scope. This is a
   documentation-content assertion, not a request-mapping test (no HTTP surface exists in
   this stage to test against) — it exists so a future edit that quietly removes or waters
   down the scope-boundary statement is caught by a real failing test, not left to be
   discovered by a later stage design incorrectly assuming this function already does
   assignee authorization.
   See `test/letflow/engine_complete_task_test.exs:"AC5 — moduledoc states the S4 scope..."`.
