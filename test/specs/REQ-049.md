# Test Spec: REQ-049 — Variable scoping and merge (instance.zig mergeVariables, EE-09)

**Requirement:** REQ-049 (`docs/requirements.yaml`, stage S3) — port `instance.zig`'s
`mergeVariables()` as a pure `Letflow.Engine.VariableMerge.merge/3`, per
`lib/letflow/design/req049-variable-merge.md` (the gate-approved design
`lib/letflow/engine/variable_merge.ex` implements).

**Requirement text (verbatim, from this run's handoff `context.requirement_text.REQ-049`):**

> Variable scoping and merge (instance.zig mergeVariables, EE-09). Merging a key absent
> from the instance map inserts it with no VARIABLE_OVERWRITTEN event; merging a key
> already present overwrites it AND produces exactly one VARIABLE_OVERWRITTEN event
> carrying the key, the old value and the new value -- two explicit tests. Merging an
> empty map is a no-op producing zero events and leaving the variable map unchanged.
> Merging a value that a registered variable schema rejects leaves the variable map
> unchanged, transitions the instance to ERROR (returns {:rejected, unchanged_variables,
> events}), and produces an EXECUTION_ERROR event -- verified by reading the variable map
> back and confirming it did not absorb the rejected value. Schema validation goes
> through REQ-024's validate_payload/3 rather than a second JSON Schema implementation --
> verified by inspection (this module doesn't call it directly; the design's
> caller-composition contract is what satisfies this AC). Variables merged by a task
> completion are visible to a gateway condition evaluated later in the same completion,
> demonstrated by an explicit test rather than argued. Also: whole-batch all-or-nothing
> rejection semantics (REVIEWER-confirmed to match the design) needs its own explicit
> test.

**REQ-049's 5 acceptance criteria, as parsed from the paragraph above (matching the
design doc §14 traceability table):**

1. **AC1 — insert vs. overwrite.** A key absent from the instance map is inserted with
   no `VARIABLE_OVERWRITTEN` event; a key already present is overwritten and produces
   exactly one `VARIABLE_OVERWRITTEN` event carrying the key, the old value, and the new
   value. Two explicit tests, per the requirement text's own wording.
2. **AC2 — empty-map no-op.** Merging an empty map produces zero events and leaves the
   variable map unchanged.
3. **AC3 — rejection.** A value a registered variable schema rejects leaves the variable
   map unchanged, transitions the instance to ERROR (via `{:rejected, unchanged_variables,
   events}`), and produces an `EXECUTION_ERROR` event — verified by reading the variable
   map back, not merely by the return tuple's shape.
4. **AC4 — `validate_payload/3` reuse.** Schema validation goes through REQ-024's
   `validate_payload/3` rather than a second JSON Schema implementation — verified by
   inspection, since `merge/3` itself never calls it (the design's caller-composition
   contract, design doc §7, is what satisfies this AC).
5. **AC5 — CEL visibility.** Variables merged by a task completion are visible to a
   gateway condition evaluated later in the same completion — demonstrated by an
   explicit test rather than argued.

**Also required, named separately by the requirement text and the handoff:** the
whole-batch all-or-nothing rejection semantics (design doc §3.2, REVIEWER-confirmed)
needs its own explicit test, distinct from the plain AC3 rejection test.

**Test tier:** unit. `Letflow.Engine.VariableMerge.merge/3` is a pure function over
plain maps and tagged tuples — no `Letflow.Repo`, no I/O of any kind (moduledoc's own
"Purity" section; design doc §10). Same simpler, faster test shape as
`test/letflow/engine/transition_test.exs` (REQ-044) — no `Letflow.DataCase`, no
`Ecto.Sandbox`, no Postgres. No property test: unlike `Transition.transition/3`'s
open-ended `(graph, state, event)` input space, `merge/3`'s algorithm (design doc §3.1)
has few enough branches (new-key insert, overwrite-pass, first-rejection-wins) that
targeted example tests give complete branch coverage without needing randomized input
generation to find edge cases a hand-picked set would miss.

## Test cases

### Acceptance criterion 1 — insert (no event) vs. overwrite (exactly one event)

1. **A brand-new key is inserted into `new_variables` and produces zero events** — see
   `variable_merge_test.exs:"a brand-new key is inserted into new_variables and
   produces zero events"`. Would fail if `merge/3` ever emitted a
   `:variable_overwritten` event for a key that was never present in
   `current_variables`, or failed to actually add the new key to the returned map.
   A second test (`"inserting several new keys at once still produces zero events"`)
   confirms this holds for a multi-key insert batch too, not just a single key.
2. **Overwriting a key already present replaces its value and produces exactly one
   `{:variable_overwritten, key, old_value, new_value}` event** — see
   `variable_merge_test.exs:"overwrites the value and produces exactly one
   variable_overwritten event with key, old value, and new value"`. Asserts the full
   3-field event payload (key `"count"`, old value `1`, new value `2`), not just that
   *an* event occurred — would fail if the event carried the wrong old/new value, was
   missing, or was duplicated. A second test
   (`"overwriting two keys at once produces exactly one event per overwritten key, none
   for inserts"`) mixes two overwrites and one insert in the same call, confirming the
   insert path emits nothing while each overwrite emits exactly one event, in
   deterministic sorted-key order (design doc §3.1 step 1) — would fail if event count
   didn't scale 1:1 with overwritten keys, or if insert keys leaked a spurious event.

### Acceptance criterion 2 — empty incoming map is a no-op

3. **Merging `%{}` returns the *same* `current_variables` value (identity, not merely
   `==`-equal) and zero events** — see `variable_merge_test.exs:"returns the exact
   same current_variables value unchanged, with zero events"`. Checking identity
   (design doc §9's "no copy divergence") rather than just structural equality is
   deliberate: it would still catch a bug where `merge/3` reconstructed an
   equal-but-different map via an unnecessary `Enum.reduce/3` pass over an empty key
   list — behaviourally invisible via `==` alone in this specific test, but a genuine
   deviation from the "falls out of the general algorithm with no special case"
   design intent (§9). A second test confirms the boundary case of an already-empty
   `current_variables` merged with `%{}` stays `%{}`.

### Acceptance criterion 3 — rejection: unchanged map, `{:rejected, ...}`, one `EXECUTION_ERROR` event

4. **A rejected overwrite value leaves `current_variables` byte-for-byte unchanged,
   returns `{:rejected, unchanged_variables, events}`, and produces exactly one
   `execution_error` event carrying key/rejected-value/reason/failures** — see
   `variable_merge_test.exs:"rejects the batch, leaves current_variables byte-for-byte
   unchanged, and produces exactly one execution_error event"`. Follows the
   requirement text's own verification method literally: reads
   `Map.get(unchanged_variables, "amount")` back and asserts it is still `10` (the old
   value), not `-5` (the rejected value) — proving the map did not silently absorb the
   rejected value, not merely trusting the return tuple's tag. Would fail if the
   rejected value were merged anyway, if the map identity/values diverged, or if the
   `execution_error` event's fields didn't match design doc §5's shape exactly.
5. **A `variable_validations` entry for a *new* (non-overwrite) key is silently
   ignored — `new_keys` are never looked up, even when a `{:rejected, _}` entry exists
   for one** — see `variable_merge_test.exs:"a variable_validations entry for a new
   (non-overwrite) key is silently ignored -- new_keys are never looked up"`. Locks in
   design doc §3.1 step 3's explicit carve-out (AC1's insert path is unconditional, no
   schema exception). Would fail if a future change accidentally applied
   `variable_validations` lookups to `new_keys` too, silently blocking legitimate
   first-time variable writes.

### Whole-batch all-or-nothing rejection semantics — its own explicit test (REVIEWER-confirmed, design doc §3.2)

6. **A batch with one valid new key and one rejected overwrite key: neither lands** —
   see `variable_merge_test.exs:"a batch with both a valid new key and a rejected
   overwrite key: neither lands"`. This is the test the handoff calls out by name,
   distinct from the plain AC3 rejection test above: it proves the *otherwise
   unproblematic* new-key insert in the same batch is also discarded, not just the
   rejected key itself — the load-bearing distinction design doc §3.2 draws between
   "all-or-nothing" and "partial-merge-then-halt." Would fail if `merge/3` applied
   `new_keys` inserts before running the validation pass (a partial-merge
   implementation would pass the plain AC3 test above but fail this one).
7. **A batch with one valid overwrite and one rejected overwrite: the valid overwrite
   is NOT partially applied, and no stray `variable_overwritten` event leaks out** —
   see `variable_merge_test.exs:"a batch with both a valid overwrite and a rejected
   overwrite: the valid one is NOT partially applied"`. Asserts both that
   `unchanged_variables["status"]` is still `"pending"` (not `"approved"`) and that
   `events` contains *only* the one `execution_error` event, not a mixture of
   `variable_overwritten` and `execution_error`. Would fail under a partial-merge
   implementation that processes `overwrite_keys` in order and stops only once it
   hits the rejected one, having already committed the earlier valid overwrite.
8. **First-failure-wins ordering (design doc §3.3): when two overwrite keys would
   both be rejected, the lexicographically smallest key's failures are the ones
   reported, and only those** — see `variable_merge_test.exs:"first-failure-wins
   ordering (design doc §3.3): the lexicographically smallest rejected key is
   reported"`. Uses two keys (`"alpha"`, `"zeta"`) whose sort order and insertion
   order deliberately differ from the map's natural iteration order, so the test
   would only pass if `merge/3` genuinely sorts before scanning (design doc §3.1 step
   1) rather than relying on incidental `Map` iteration order. Would fail if the scan
   picked a different key, combined both keys' failures into one event, or depended
   on non-deterministic map ordering (this test would flake, not just fail, under
   that bug).

### AC2's "no schema registered" branch and `nil`/`%{}` equivalence (design doc §2, §3.1 step 3)

9. **An overwrite key with no entry at all in `variable_validations` is treated as
   `:ok`** — see `variable_merge_test.exs:"an overwrite key with no entry in
   variable_validations at all is treated as :ok"`. Directly exercises AC2's "(or
   where no variable schema is registered)" wording — a `variable_validations` map
   that has an entry for some *other* key but nothing for the key actually being
   merged.
10. **`variable_validations: nil` is equivalent to `variable_validations: %{}`** — see
    `variable_merge_test.exs:"variable_validations: nil is equivalent to
    variable_validations: %{}"`. Compares the two calls' full return values for
    equality rather than asserting on a single field, catching a divergence anywhere
    in the result (event list, map contents, or result tag) design doc §2 states
    should not exist.
11. **An explicit `:ok` outcome behaves identically to an absent entry** — see
    `variable_merge_test.exs:"an explicit :ok outcome for an overwrite key behaves
    identically to an absent entry"`. Would fail if a future change accidentally
    special-cased the explicit-`:ok` branch differently from the default-`:ok`
    branch (design doc §3.1 step 3 states they are the same outcome).

### Acceptance criterion 4 — `validate_payload/3` reuse (code-inspection, not a runtime test)

**Not a runtime-testable criterion, following the `transition_test.exs` AC1/AC5/AC6
precedent for structural properties.** Design doc §7 resolves this literally:
`merge/3` cannot call `Letflow.EventStore.Registry.validate_payload/3` directly (it
performs `Repo` I/O and needs `event_type`/`tenant_id` arguments `merge/3`'s own
`(current_variables, incoming_variables, variable_validations)` signature does not
carry) — the design instead has the *caller* invoke `validate_payload/3` before
calling `merge/3`, to produce the `variable_validations` map `merge/3` consumes (§7,
§7.1, §7.2). This AC is therefore satisfied by:

- **Code inspection:** `lib/letflow/engine/variable_merge.ex`'s moduledoc states this
  explicitly ("`merge/3` never runs schema validation itself... by calling
  `Letflow.EventStore.Registry.validate_payload/3` (REQ-024) before invoking
  `merge/3`, not a second JSON Schema implementation"), and the module's own `alias`
  list (`alias Letflow.EventStore.Registry.ValidationFailure`) references only the
  *struct*, never the `validate_payload/3` function.
- **The grep check design doc §10 specifies**, independently re-run here:

  ```bash
  grep -n "Repo\.\|Logger\.\|DateTime\.\|System\.os_time\|System\.system_time\|HTTPoison\|Req\.\|File\.\|:rand\.\|:crypto\.\|Registry\.validate_payload\|Registry\.get_type\|Registry\.register_type" lib/letflow/engine/variable_merge.ex
  ```

  returns 4 matches when actually re-run against the current implementation, at
  lines 26, 56, 63, and 106 — **all four inside doc strings** (the `@moduledoc`'s own
  prose describing what `merge/3` does *not* call, and the `@typedoc` for
  `validation_outcome`, both explaining the caller-composition contract in words; line
  63 is the grep command's own example invocation quoted inside the moduledoc, which
  trivially self-matches). None fall inside `merge/3`'s or `find_rejection/2`'s actual
  function bodies (lines 153–193) — read directly, confirming neither function
  contains a real call to `Registry.validate_payload/3`, `Repo`, `Logger`, a clock
  read, or any other I/O. The design doc's own grep recipe (§10) does not distinguish
  prose mentions from real call sites, so its literal "must return zero matches" bar is
  not met by the actual file — flagged here as a MINOR inaccuracy in the design's
  stated verification method (not a purity violation in the implementation itself,
  confirmed by the direct code read) so it can be corrected at the source rather than
  silently worked around. Satisfies AC4's substance (REQ-024's actual validator, not a
  reimplementation, is what ultimately decides `:ok` vs. `:rejected` for every key —
  just from outside this pure kernel) without a manufactured ExUnit assertion that
  would only ever restate the module's own source text back at itself.
  `variable_merge_test.exs` tests 4, 6, 7, and 8 above all
  exercise `merge/3` with hand-constructed `variable_validations` maps carrying real
  `Letflow.EventStore.Registry.ValidationFailure` structs (REQ-024's own type, reused
  verbatim, never re-shaped) — confirming the *data shape* half of AC4 at runtime,
  even though the *call site* half is inspection-only by design.

### Acceptance criterion 5 — CEL visibility: merged variables observed by a later step in the same completion

12. **The returned `new_variables` map, threaded into a fresh `InstanceState`, is
    immediately readable with no deferred/async step** — see
    `variable_merge_test.exs:"the returned new_variables map, threaded into a fresh
    InstanceState, is immediately readable with no deferred/async step"`. Composes
    `merge/3`'s output directly into a second read (`composed_state.variables[...]`)
    within the same test process/call sequence — no message pass, no process
    boundary, no persistence round-trip in between — demonstrating design doc §11's
    "visibility is guaranteed by construction" claim rather than merely restating it.
13. **The composed `InstanceState` carrying the merged variables is itself accepted
    by `Transition.transition/3` (REQ-044) in the same call sequence, with the merged
    value confirmed present at the exact point a gateway evaluator would read it** —
    see `variable_merge_test.exs:"the composed InstanceState carrying the merged
    variables is itself accepted by Transition.transition/3 in the same call
    sequence"`. This is the "merge-then-observe" half of the composition test design
    doc §11 asks for explicitly, completable now; **the full "the gateway's CEL
    condition itself reads the merged value" half is not yet completable** —
    `EXCLUSIVE_GATEWAY` dispatch is still a REQ-050 stub (`transition.ex`'s own
    `:gateway_not_yet_implemented` error, design doc §11's own flagged forward
    dependency, confirmed directly against `transition_test.exs`'s
    `":EXCLUSIVE_GATEWAY node dispatch (5-way case 4/5, stub..."` tests) — there is no
    CEL-condition-reading code path to observe yet. This test therefore asserts (a)
    the composed state carrying the merged value is accepted and dispatched by
    `transition/3` without error about the composition itself (only the named stub
    error, proving the call succeeded structurally), and (b) the merged value is
    still directly readable on that same composed state immediately afterward. Once
    REQ-050 lands, this test should be extended (not replaced) to assert the
    gateway's actual CEL evaluation result depends on the merged value — flagged here
    so that extension isn't lost track of, matching design doc §11's own forward-
    dependency note.
