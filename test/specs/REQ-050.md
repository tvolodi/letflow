## Why each test case exists (not a restatement of the AC)

### AC1 — declared-order, second-edge-first-match

Proves the dispatch does not simply take "the first true" by accidental list-scan
order equal to array position, but genuinely walks `conditioned_edges` in
`definition_snapshot.edges`' declared order and stops at the first `true`. A 3-edge
gateway where edge 1 evaluates false, edge 2 evaluates true, edge 3 would also
evaluate true (so a bug that evaluates all edges and picks the "last true" or scans in
reverse would be caught) — the fixture asserts specifically edge 2's target is taken,
never edge 1's or edge 3's.

### AC2 — default declared first, evaluated last

Proves `default_edge` is structurally excluded from the ordering loop regardless of
its position in `definition_snapshot.edges` — the design's core claim in §5.1/§5.3.
The fixture declares the default edge *before* two false-evaluating conditioned
edges, so a naive "first declared edge wins if default" implementation would
incorrectly take the default early; this test only passes if the default is
genuinely considered last.

### AC3 — runtime-erroring condition treated as false, not an instance error

Distinguishes "a condition raised" from "no condition matched" — two different code
paths in a naive implementation, one uniform outcome in the real design (§5.2
catch-false). Two example conditions: an undefined-variable reference, and a
type-mismatch (ordering comparison between a string and a number). Both must fall
through to the *next* edge rather than propagate an error out of
`dispatch_exclusive_gateway/4` — proven by placing a real, later-declared,
true-evaluating edge after the erroring one and asserting *that* edge's target wins.

### AC4 — no match, no default → structured ERROR naming node_id and evaluated_conditions

Proves the exact failure tuple shape (`{:error, {:no_matching_edge, node_id,
evaluated_conditions}}`) and its contents: `node_id` is the gateway's own id, and
`evaluated_conditions` names every conditioned edge (its `edge_id`, original CEL
`condition` string, and `result: false`) in declared order — not a generic/opaque
error a caller couldn't diagnose from.

### AC5 — exactly one edge followed

Every passing-case test above additionally asserts `new_state.tokens` contains
exactly one token whose `node_id` equals the expected target, and that no other token
was created/duplicated — asserted directly (list equality / length), not inferred
from "the test didn't fail."

### AC6 — unsupported CEL feature → catch-false, at least 2 distinct expressions

Proves `hasCelUnsupportedFeatures()`'s ported boundary is honored end-to-end through
the gateway, not just inside `Expr` in isolation (that's also covered directly in
`expr_test.exs`). Two distinct unsupported expressions used here: a macro call
(`has(variables.x)`) and the ternary operator (`variables.a ? variables.b :
variables.c`) — both must evaluate to `false` (fall through), never raise or error
the instance.

### AC7 — each of the 4 CEL→expr rewrites tested directly

`expr_test.exs` tests `translate_cel_to_expr/1` directly, one example per rewrite rule
(prefix strip, `&&`→`and`, `||`→`or`, `!`→`not ` with `!=` passing through unchanged),
independent of gateway dispatch — proves the translation is correct in isolation, not
just as an emergent property of an end-to-end gateway test (which could mask a bug if
two rewrite bugs happened to cancel out).

### AC8 — zero I/O, deterministic

`expr_test.exs`'s moduledoc/grep note plus an explicit repeated-call-equality check
(not a property test — `Expr`'s functions are simple enough that one direct
"same input twice, same output" assertion plus the existing grep/`mix xref` method
from the design doc §7 is sufficient, matching REQ-044's own AC1 code-inspection
precedent). `transition_test.exs`'s existing `world_generator/0` property test already
covers determinism for the composed `transition/3` call graph including
`:EXCLUSIVE_GATEWAY` dispatch — not duplicated here.

### AC9 — the two pre-existing stub-error tests fixed

`transition_test.exs`'s old "returns the named :gateway_not_yet_implemented error"
`:EXCLUSIVE_GATEWAY` test and `variable_merge_test.exs`'s AC5 composed-dispatch
assertion both asserted the now-superseded stub tuple. Both are updated in this same
change (not left red) — REVIEWER (Step 2d) confirmed this fallout is the correct,
expected consequence of REQ-050 legitimately superseding REQ-044's stub.
