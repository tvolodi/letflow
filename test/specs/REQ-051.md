# Test Spec: REQ-051 — Parallel gateway split and join (transition.zig EE-06/EE-07)

**Requirement:** REQ-051 (`docs/requirements.yaml`, stage S3) — port `transition.zig`'s
`PARALLEL_GATEWAY` split (EE-06) and join (EE-07) branches into REQ-044's transition
dispatch, per `lib/letflow/design/req051-parallel-gateway-split-join.md` (the
gate-approved design `lib/letflow/engine/{join_counter.ex,instance_state.ex,
transition.ex}` implement).

**Requirement text (verbatim, from this run's handoff `context.requirement_text.REQ-051`):**

> Port `src/engine/transition.zig`'s `PARALLEL_GATEWAY` branches (EE-06 split / EE-07
> join) into REQ-044's transition dispatch. See
> `lib/letflow/design/req051-parallel-gateway-split-join.md` for the full design and
> `lib/letflow/engine/transition.ex` for the implementation.

**7 acceptance criteria, copied verbatim from this run's handoff `task.acceptance_criteria`:**

1. A `PARALLEL_GATEWAY` with 3 outgoing edges produces exactly 3 tokens with 3 distinct
   `branch_id`s in one `transition/3` call.
2. A join with 3 expected branches does not fire when 2 tokens have arrived and does
   fire when the 3rd arrives, asserted at both points.
3. A join whose branch count is 3 but where 1 branch was cancelled via the EE-08
   (`{:cancel_branch, branch_id}`) path fires when the remaining 2 active tokens
   arrive — it does not wait for the cancelled branch, demonstrated by an explicit test.
4. When every branch of a split is cancelled before any reaches the join, the join
   node is cancelled and the instance status becomes `:cancelled`.
5. Tokens arriving at a join in two different orders produce the identical post-join
   state, and the join fires exactly once in both orderings.
6. A variable key produced with different values on two parallel branches resolves
   through REQ-049's merge policy with a `:variable_overwritten` event, not through a
   second collision rule defined in this module.
7. `test/letflow/engine/transition_test.exs:348`'s obsolete REQ-044-stub assertion is
   retired/rewritten to match the new, correct `:pass_through` behavior for a
   zero-edge `PARALLEL_GATEWAY` node.

**Test tier:** unit (example-based). `Letflow.Engine.Transition.transition/3`,
`Letflow.Engine.JoinCounter`, and `Letflow.Engine.InstanceState` are pure functions
over plain structs — no `Letflow.Repo`, no I/O of any kind (moduledoc's own "Purity"
section; design doc §9). Same shape as `test/letflow/engine/transition_test.exs`
(REQ-044) — `async: true`, no `Letflow.DataCase`/`Ecto.Sandbox`. No property test is
added here: REQ-044's `transition_test.exs` already carries the one load-bearing
determinism property that exercises `:PARALLEL_GATEWAY`'s dispatch entry point (via
its `node_type_gen/0` pool) across the whole module including this requirement's new
code paths; the 7 criteria above are each a specific, hand-picked scenario (3-way
split, wait/fire boundary, cancellation exclusion, all-cancelled, order-independence,
merge reuse) that a generic random-graph property would not reliably hit, so
example-based tests are the right tool per the guide's own "pure functions first /
tests are specifications" principles.

## Test cases

1. **AC1 (3-way split → 3 distinct branch_ids)** — `parallel_gateway_test.exs`,
   `"a 3-outgoing-edge split produces exactly 3 tokens with 3 distinct branch_ids in
   one transition call"`. Builds a split node with 3 outgoing edges into 3 branch
   nodes converging on one join, advances the token positioned on the split, and
   asserts the resulting `tokens` list has exactly 3 entries whose `branch_id`s form a
   3-element `MapSet` (proves distinctness, not just count) and whose `node_id`s match
   the 3 branch targets. Exists because AC1 is a distinctness claim, not merely a count
   claim — a buggy implementation that derived the same `branch_id` for every child
   token would still produce "3 tokens" and pass a naive count-only assertion.

2. **AC2 (join wait/fire boundary)** — `parallel_gateway_test.exs`, `"a join with 3
   expected branches does not fire on the 2nd arrival and fires on the 3rd, asserted
   at both points"`. Pre-seeds `instance_state.join_counters` with a 3-branch
   `JoinCounter` (2 branches already `received`, matching "2 tokens have arrived"),
   then drives the 3rd branch's token through `transition/3` and asserts `{:ok,
   new_state, [{:parallel_join_fired, ...}]}` with the join cohort removed from
   `join_counters` and a new merged token present. A second, separate assertion
   drives only the 2nd of 3 arrivals (0 pre-seeded) and asserts `{:ok, new_state, []}`
   (no pending event — `:wait`) with the cohort still present, `received_from_branches`
   correctly grown. Exists because AC2 explicitly requires the negative case ("does
   not fire when 2 have arrived") to be asserted, not just the positive terminal case
   — a test that only checked the 3rd arrival could pass even if the join fired
   prematurely on the 2nd.

3. **AC3 (join excludes a cancelled branch)** — `parallel_gateway_test.exs`, `"a join
   whose branch count is 3 but where 1 branch was cancelled fires when the remaining 2
   active tokens arrive, not waiting for the cancelled branch"`. Splits into 3
   branches, cancels one via `{:cancel_branch, branch_id}` (asserting `:wait`, no fire
   yet — 1 of 2 remaining branches has not arrived), then advances the two remaining
   branch tokens in turn and asserts the join fires on the *second* remaining arrival
   (not needing all 3 original branches, only the 2 still-active ones). Exists because
   this is the specific rule `join_outcome/1`'s `still_outstanding` set exists to
   express — a naive count-based join (`received_count == expected_count`) would never
   fire here since only 2 of 3 tokens ever arrive.

4. **AC4 (all-cancelled → join+instance cancelled)** — `parallel_gateway_test.exs`,
   `"when every branch of a split is cancelled before any reaches the join, the join
   is cancelled and the instance status becomes :cancelled"`. Splits into 3 branches,
   cancels all 3 via 3 separate `{:cancel_branch, _}` calls, and asserts: the first two
   cancellations return `{:ok, _, []}` with `status: :active` still (per `join_outcome/1`'s
   `:wait` since not yet all cancelled — for the first — and per the "0 received"
   `:cancel_join` guard only tripping once the *last* expected branch resolves), the
   final cancellation returns `{:ok, new_state, [{:parallel_join_cancelled, ...}]}`
   with `new_state.status == :cancelled` and the cohort removed from `join_counters`.
   Exists because this is EE-07 AC4's own literal wording, and because it is the one
   case that must produce `:cancel_join` rather than `:fire` — distinguished from AC3
   above only by whether `received_from_branches` is empty at the moment the last
   branch resolves (design doc §4.1), so this test's fixture deliberately arranges
   *zero* branches to ever arrive, unlike AC3's fixture where 2 do.

5. **AC5 (order-independence + exactly-once firing)** — `parallel_gateway_test.exs`,
   `"tokens arriving at a join in two different orders produce identical post-join
   state, and the join fires exactly once in both orderings"`. Runs the same 3-branch
   split/join scenario twice from the same initial split result, feeding the 3
   `{:advance_token, _}` events in one order (`[0, 1, 2]`) in one run and a different
   order (`[2, 0, 1]`) in the other, and asserts: (a) the final `InstanceState.t()`
   values from both orderings are `==`-equal (order-independence — same `tokens`,
   `join_counters`, `variables`, `status`), (b) exactly one of the 3 calls in each
   ordering returns a `[{:parallel_join_fired, ...}]` pending event, the other two
   returning `[]` (exactly-once firing — not two fires, not zero), and (c) a 4th
   `transition/3` call in each ordering, replaying the already-fired 3rd branch's now
   stale `branch_id` again, returns `{:error, {:unknown_branch_id, _}}` rather than
   constructing a second merged token — the concrete mechanism (§4.3's "cohort no
   longer exists after the first fire") that makes exactly-once true, not merely
   coincidentally observed once. Exists because AC5 names two independent properties
   (order-independence, exactly-once) that a join implementation could satisfy one of
   without the other (e.g., a naive "fire on every arrival once `received_count >=
   expected_count`" bug would still be order-independent but would fire multiple
   times if a stale event replayed) — both are asserted explicitly, not inferred from
   each other.

6. **AC6 (REQ-049 merge reuse, not a second collision rule)** — `parallel_gateway_test.exs`,
   two-part test:
   - `"dispatch_parallel_gateway's join-fire path calls VariableMerge.merge/3 — no
     second collision rule exists in transition.ex"` — a code-inspection assertion
     (matching REQ-044/REQ-049's own `grep`-based precedent for structural claims),
     reading `lib/letflow/engine/transition.ex`'s source and asserting it contains the
     literal call site `"VariableMerge.merge("` exactly once, and that no other
     function name matching `merge` or `overwrite` is defined in that file — proving
     "no second collision rule defined in this module" at the source level, not merely
     by behavioral coincidence.
   - `"a variable key set to different values on two parallel branches produces a
     :variable_overwritten event through REQ-049's own merge/3, and the join-fire
     itself performs no second overwrite"` — a runtime test. Simulates branch A's own
     task completion writing `%{"x" => "a"}` into `instance_state.variables` via a
     direct `VariableMerge.merge/3` call (representing REQ-047's future orchestration
     layer invoking REQ-049 at an ordinary task completion, per design doc §12.5's
     "collisions are actually resolved earlier, at whichever branch's own
     task-completion call happens to invoke merge/3 second" reading), asserting that
     call's own event list is `[]` (new key, no collision yet). Then simulates branch
     B's task completion writing `%{"x" => "b"}` via a second direct `merge/3` call,
     asserting **that** call's event list is `[{:variable_overwritten, "x", "a", "b"}]`
     — the collision event, produced by REQ-049's own function, not by anything in
     `transition.ex`. Finally advances both branch tokens through the join and asserts
     the resulting `{:parallel_join_fired, _, _, _, merge_events}` pending event's own
     `merge_events` field is `[]` (§4.3 step 1's no-op call, since `incoming_variables`
     is always `%{}` at the join) and `new_state.variables["x"] == "b"` (the value
     already settled by the branches' own merge calls, left untouched by the join).
     Exists because AC6's literal wording ("resolves ... with a VARIABLE_OVERWRITTEN
     event, not through a second collision rule defined in this module") is precise
     about *where* the event comes from — this test proves the event's origin is
     REQ-049's `merge/3`, called from ordinary branch-level variable writes, and that
     the join-fire's own `VariableMerge.merge/3` call (§4.3 step 1) never manufactures
     a second, redundant overwrite event for the same key.

7. **AC7 (retire the obsolete REQ-044-stub test)** — `transition_test.exs`, the
   `describe "transition/3 -- :PARALLEL_GATEWAY node dispatch..."` block at line ~347
   is rewritten: `"a zero-edge PARALLEL_GATEWAY (no in-edges, no out-edges) is
   classified :pass_through and returns {:error, {:unknown_node_id, node_id}}, not the
   retired :gateway_not_yet_implemented stub"`. Exists because the old assertion
   (`{:error, {:gateway_not_yet_implemented, :PARALLEL_GATEWAY, "gw"}}`) is now false
   against the shipped implementation — `gateway_role/2` classifies a 0-in/0-out node
   `:pass_through` (design doc §3), and the `:pass_through` dispatch path, finding no
   outgoing edge to advance onto, returns `{:error, {:unknown_node_id, node.id}}`
   (mirroring `:START`'s own no-outgoing-edge defensive path). Running this exact
   rewritten test against the pre-REQ-051 code (REQ-044-era `dispatch_parallel_gateway/4`,
   which unconditionally returned the stub error for every input) would fail — proving
   this is a genuine behavior change being locked in, not busywork.
