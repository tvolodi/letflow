## AC1 — cancelling an ACTIVE instance: all open tasks CANCELLED, one INSTANCE_CANCELLED
event, instance status CANCELLED, all committed together

**Requirement text:** "cancelling an ACTIVE instance sets every open task to CANCELLED,
appends exactly one INSTANCE_CANCELLED event, and sets the instance status to CANCELLED —
all committed together, verified by reading tasks, instance_projections and events back."

**Test case:** `AC1 -- cancelling an ACTIVE instance with 2 open tasks` /
`"cancels both tasks, the live token, sets the instance CANCELLED, appends one event"`.
Starts an instance on a 2-branch `PARALLEL_GATEWAY` split (`task_a`/`task_b`, both
`HUMAN_TASK`) so there are 2 concurrently-open `tasks` rows and 2 live `tokens` rows, then
calls `cancel_instance/3` once. Asserts, by reading the real rows back (not from the
in-memory `{:ok, result}` alone): both `tasks` rows are `:cancelled` with `cancelled_at`
set, both `tokens` rows are `:cancelled`, `instance_projections.status == :cancelled` with
`cancelled_at` set, and exactly one `INSTANCE_CANCELLED` `events` row exists whose payload
`cancelled_task_ids`/`cancelled_token_ids` name exactly those 2 tasks/tokens.

**Why this exists:** the AC's own text requires proving 3 separate table writes landed
*together* — a test that only checked the returned `{:ok, result}` map (built purely from
in-memory values, §"Result assembly" of the design) would pass even if the `Ecto.Multi`
silently failed to persist one of the three tables; only re-reading `tasks`,
`instance_projections`, and `events` independently proves the commit was real and complete.
Using 2 tasks (not 1) also proves M4's `Enum.reduce_while` loop over `open_tasks` handles
more than a single row, not just the trivial one-row case.

## AC2 — already-terminal instance: distinct conflict error, writes nothing; zero-open-tasks
ACTIVE instance still appends INSTANCE_CANCELLED

**Requirement text:** "cancelling an already-CANCELLED or already-COMPLETED instance
returns a distinct conflict error and changes nothing; cancelling an ACTIVE instance with
zero open tasks still appends INSTANCE_CANCELLED."

**Test cases** (3, `describe "AC2 ..."`):

1. `"cancelling an already-CANCELLED instance returns a distinct conflict error, writes
   nothing more"` — cancels once (`:ok`), then cancels again: asserts
   `{:error, {:instance_already_terminal, :cancelled}}`, and that `task_count`/`event_count`
   are unchanged from their post-first-cancel values (the second call's own M1/M4/M5 must
   never have run any write, since M3 short-circuits before them, design §7's own ordering
   rationale).
2. `"cancelling an already-COMPLETED instance returns a distinct conflict error, writes
   nothing"` — completes the instance's one task via `complete_task/3` (driving the
   instance to `:completed`, `graph_human_task_end`), then calls `cancel_instance/3`:
   asserts `{:error, {:instance_already_terminal, :completed}}`, zero `INSTANCE_CANCELLED`
   events, and the task's own status remains `:completed` (not overwritten to `:cancelled`).
3. `"an ACTIVE instance with zero open tasks still appends exactly one INSTANCE_CANCELLED
   event and sets the instance CANCELLED"` — starts a single-`HUMAN_TASK` instance, then
   forces the zero-open-tasks-while-still-ACTIVE state directly via `Repo.update!/1` on the
   `tasks` row (bypassing `complete_task/3` entirely, so `instance_projections.status`
   stays `:active` while `tasks` has zero `:pending` rows) — a deliberate, disclosed test
   fixture for a state the design's own INV-EE52-4 names as reachable (M1 may return `[]`).
   Calls `cancel_instance/3`: asserts `:ok`, `cancelled_task_ids == []`, exactly one
   `INSTANCE_CANCELLED` event, `instance_projections.status == :cancelled`.

**Why these exist:** case 1/2 are the two distinct, separately-pattern-matchable conflict
tuples INV-EE52-2 requires — a test asserting only "returns an error" without matching the
exact `status` atom inside the tuple would not catch a regression that collapsed both cases
into the same generic error. Case 3 is the edge case M3's ordering rationale (§7) explicitly
calls out — M6/M7 must be unconditional even when M1/M5's locked sets are both empty; a
naive implementation might (incorrectly) skip the event append when `open_tasks == []`,
silently violating INV-EE52-4, and this test would fail against that regression while
passing against the correct implementation.

## AC3 — after cancellation, a further `EventStore.append/2` call is rejected by the real
active-instance guard

**Requirement text:** "after cancellation, a further append via REQ-025's append/1 is
rejected by its existing active-instance guard — demonstrated against the real event store
rather than asserted from the code."

**Test case:** `"a further EventStore.append/2 call for the same instance after
cancellation returns {:error, {:instance_terminated, :cancelled}}"`. Cancels a real
instance, then calls `Letflow.EventStore.append/2` directly (not through `Engine`) with a
fresh, permissively-registered event type and the same `instance_id`. Asserts
`{:error, {:instance_terminated, :cancelled}}` — the exact tuple
`EventStore.active_instance_guard/3` (M1 of `append/2`'s own `Ecto.Multi`) produces for a
terminal-status `instance_projections` row.

**Why this exists:** the design's own §6/§9 states this codebase deliberately does *not*
duplicate `append/2`'s own terminal-status guard inside `cancel_instance/3` for this
purpose — it relies on `append/2`'s real, already-shipped guard to reject a post-cancel
append. A test that merely inspected `cancel_instance/3`'s source for "does it call
`terminal?/1`" would not prove the *downstream* guard actually still fires end-to-end
against real Postgres state that `cancel_instance/3` itself produced; only a real second
`append/2` call against the just-cancelled instance proves this.

## AC4 — cancellation racing a task completion: exactly one winner, one distinct conflict
loser, run concurrently

**Requirement text:** "a cancellation racing a task completion on the same instance
resolves with exactly one winner and a distinct conflict error for the loser, run
concurrently rather than sequentially."

**Test case:** `"exactly one of cancel_instance/3 and complete_task/3 commits, the other
gets a distinct conflict"`. Starts a single-`HUMAN_TASK`-then-`END` instance (that task is
the instance's only open task — design §7.1's own worked, deterministic case). Launches
`cancel_instance/3` and `complete_task/3` on that same task truly concurrently via
`Task.async`/`Task.await_many` (real, separate Postgres connections under Sandbox `:auto`,
mirroring `engine_complete_task_test.exs`'s own AC4 exactly — not two sequential calls).
Asserts the disjunction design §7.1 traces precisely: exactly one result is `{:ok, _}`, and
the other is *one of* `{:error, {:instance_already_terminal, :completed}}` (cancel lost) or
`{:error, {:task_not_pending, :cancelled}}` (complete lost) — and that whichever tuple
appears is internally consistent with the final persisted state (if `cancel_instance/3`
won, `instance_projections.status == :cancelled` and the task is `:cancelled`; if
`complete_task/3` won, `instance_projections.status == :completed` and the task is
`:completed`).

**Why this exists:** this is the one AC the requirement text itself insists be run
concurrently, not sequentially — a sequential simulation (call one, then the other) would
never exercise the actual row-lock queueing (`FOR UPDATE` on the `tasks` row) that makes
the outcome deterministic-but-genuinely-raced, and would trivially always produce the same
winner every run, hiding a lock-ordering regression that only manifests under real
contention. Using `Task.async`/real Sandbox `:auto` connections (not the shared-connection
`:manual` sandbox mode) is load-bearing — under `:manual` mode the two calls would be
serialized by the test's own connection ownership, not by Postgres's own row lock, and the
race would never actually happen.

## AC5 — REQ-051's join-path cancellation and a direct `cancel_instance/3` call reach the
same persisted state

**Requirement text:** "an instance cancelled via REQ-051's all-branches-cancelled join path
and one cancelled by a direct cancel_instance call reach the same persisted state (status,
task statuses, appended event), compared explicitly."

**Test case:** `"Transition's own :cancel_join outcome and cancel_instance/3's own
persisted status agree on the identical :cancelled atom"`. Two independent halves, compared
explicitly in one test (design §4's own "agreement by construction" reasoning, since no
code path in this codebase persists `Transition`'s `:cancel_join` result today — design §4,
§0 access-gap notes, and OQ-2):

1. **Pure half, no DB:** builds a minimal `%Letflow.Engine.InstanceState{}` carrying one
   outstanding `Letflow.Engine.JoinCounter` (`expected_from_branches: MapSet.new(["b1"])`,
   `received_from_branches`/`cancelled_branches` both empty) and one live `Token` on branch
   `"b1"`, then calls
   `Letflow.Engine.Transition.transition(%Graph{}, state, {:cancel_branch, "b1"})` directly
   — this is `dispatch_cancel_branch/3`'s `:cancel_join` branch (the "last outstanding
   branch cancelled, zero already received" case, `join_outcome/1`'s own `:cancel_join`
   clause), matching design §7.1's cited `req051` §3.4 mechanism exactly. Asserts the
   returned `InstanceState.status == :cancelled`.
2. **Real half, real DB:** starts a genuine instance and calls `Engine.cancel_instance/3`
   against it (same fixture shape as AC1, single-task variant). Asserts the persisted
   `instance_projections.status == :cancelled` read back from Postgres.
3. Both halves' asserted values are the identical Elixir atom `:cancelled` — the test
   states this explicitly (`assert pure_status == :cancelled` and
   `assert persisted_status == :cancelled`, then `assert pure_status == persisted_status`)
   rather than merely asserting each independently, so the comparison called for by the AC
   text is actually performed, not merely implied by two separate assertions landing in the
   same test.

**Why this exists:** design §4/OQ-2 already discloses that this AC's "agreement" cannot
today be proven by exercising one single shared code path (no requirement persists
`Transition`'s `:cancel_join` result) — the two halves are provably the *only* two ways
this codebase can produce a `:cancelled` instance-state value at all, so comparing their
outputs directly is the strongest test this codebase's current shape supports, and is
exactly what design §4's own reasoning instructs TEST-DESIGNER to build. A test that
skipped the pure half (asserting only that `cancel_instance/3` sets `:cancelled`) would
leave `req051`'s own `:cancel_join` logic completely unexercised by any test in the
codebase — this test also closes that pre-existing gap (§4's own note: "`req051`'s own
`:cancel_join` pure logic remains untested by any real caller until a future requirement
closes that gap" — this AC's own comparison test is that exercise, even though no
*production* caller wires it yet).

## AC6 — moduledoc names SCH-03 (S6) and REQ-056 as explicit, undone scope, not implying
EE-08 is fully covered

**Requirement text:** "the moduledoc names the SCH-03 timer-cancellation hook (S6) and the
in-flight SERVICE_TASK abandonment hook (REQ-056) as explicitly out of scope, rather than
implying EE-08 is fully covered."

**Test case:** `"names SCH-03/S6 timer cancellation and REQ-056 SERVICE_TASK abandonment as
explicit, undone gaps"`. Reads `Letflow.Engine`'s real moduledoc via `Code.fetch_docs/1`
(matching `engine_test.exs`'s own `normalized_moduledoc/1` helper, reused verbatim) and
asserts it names `"SCH-03"`, `"S6"`, `"SERVICE_TASK"`, `"REQ-056"`, and the explicit-gap
phrase `"Neither exists in Letflow yet, and `cancel_instance/3` performs neither."`.

**Why this exists:** a moduledoc that silently omitted these two hooks would read as
implying `cancel_instance/3` fully implements EE-08 (timers and in-flight service calls
included) — this is a documentation-content AC, but it is exactly the kind of regression a
future edit could silently reintroduce (deleting this paragraph while touching the
moduledoc for an unrelated reason); asserting on the literal substance (not just "the
string SCH-03 appears somewhere") catches that.

## AC7 — moduledoc states the `ParallelApproval`/`ApprovalSupervisor` disposition
concretely

**Requirement text:** "the moduledoc states concretely whether
lib/letflow/parallel_approval.ex and Letflow.ApprovalSupervisor are deleted or
retained-with-a-stated-reason, and mix test passes with the actual output quoted after the
change."

**Test case:** `"states ParallelApproval and ApprovalSupervisor are deleted, with the
REQ-046-contrast reason, and both modules are actually gone"`. Two parts in one test:

1. Moduledoc assertion (same `Code.fetch_docs/1` technique as AC6): asserts the moduledoc
   states both are `"**deleted**"`, names `"PARALLEL_GATEWAY"` as the superseding mechanism,
   and states the `Letflow.InstanceSupervisor`/REQ-046 contrast reason ("unlike
   `Letflow.ProcessInstance`'s own retirement").
2. **Concrete, not merely textual, verification that the deletion is real**:
   `Code.ensure_loaded(Letflow.ParallelApproval)` and
   `Code.ensure_loaded(Letflow.ApprovalSupervisor)` both return `{:error, :nofile}` — the
   modules genuinely do not exist in the compiled codebase, not merely "the moduledoc says
   so."

**Why this exists:** a moduledoc claim ("both are deleted") is trivially untrustworthy on
its own — this AC's own text pairs "states whether deleted" with a call for real proof
(historically, in this codebase, "mix test passes with real output quoted"). The
`Code.ensure_loaded/1` check is TEST-DESIGNER's own executable proxy for that same
"actually verify, don't just assert from prose" discipline: it fails for real if a future
change reintroduces either module without updating the moduledoc's own claim, or vice
versa. (The literal "run `mix test`, quote its actual output" half of this AC is TEST-
RUNNER's job per WF-02 Step 4, not built into this test file — design doc §14's own
traceability table states this explicitly: "`mix test` execution/quoting is
ELIXIR-DEV's/TEST-RUNNER's job, not this design's.")
