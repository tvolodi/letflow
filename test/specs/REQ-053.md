# Test spec: REQ-053 — State reconstruction by event replay (EE-11)

**Requirement:** REQ-053 (`docs/requirements.yaml`), stage S3.
**Design:** `lib/letflow/design/req053-state-reconstruction.md`.
**Implementation:** `lib/letflow/engine/reconstruction.ex`, `Letflow.Engine.Reconstruction.reconstruct_instance/2`.
**Test code:** `test/letflow/engine/reconstruction_test.exs`.

Scope test (WF-02 Step 3): `reconstruct_instance/2` is real, executable Elixir logic (two
merged Postgres queries, a full replay fold through `Transition.transition/3`, and an
opt-in `Ecto.Multi`-free write-back under `FOR UPDATE NOWAIT`) — this requirement has
executable surface, so the full test-design procedure applies.

Conventions matched: `test/letflow/engine_cancel_instance_test.exs`'s own
`provisioned_tenant/0` (Sandbox `:auto`, `async: false`, real Postgres per
`docs/guides/test_developer_guide.md` DIRECTIVE T-1), its own event-type registration
fixture pattern, and its `Task.async`/message-passing concurrency shape (AC5's lock
holder below). Instances are built through the real `Letflow.Engine.create/2` and
`complete_task/3` calls, not hand-constructed `events` rows, everywhere the design
doesn't require a lower-level fixture (AC4's zero-event snapshot-only instance, AC4's
EXECUTION_ERROR event, and AC6's unrecognized-event-type event are the 3 places a
direct `SnapshotStore.create/2`/`EventStore.append/2` call is unavoidable, since no
`Engine` function ever produces those states).

## AC1 — N-event instance reconstructs field-for-field equal to its projection

**Requirement text:** "an instance with N appended events reconstructs to an
InstanceState equal field-for-field (tokens, variables, task set, status) to its
persisted instance_projections row."

**Test case:** `AC1 -- multi-event instance reconstructs equal to its persisted
projection` / `"3 durable events (STARTED + 2 TASK_COMPLETED) reconstruct to matching
tokens/variables/status/tasks"`. Builds a 3-task sequential instance (`t1 -> t2 -> t3`),
completes `t1` and `t2` (each appending a `TASK_COMPLETED` event with its own
`output_variables`), leaving `t3` pending — 3 durable events total. Reconstructs and
compares against the design doc §6 definition: `current_nodes` node-id multiset vs.
`instance_projections.current_nodes`, `variables` vs. the projection's `variables`,
`status` vs. the projection's `status`, and the task set
(`instance_state.pending_task_nodes`'s node-ids) vs. the `tasks` table's own
`:pending`-status rows.

**Why this exists:** N=1 event (bare `INSTANCE_STARTED`) would never exercise the
`TASK_COMPLETED` replay clause's variable-merge/token-position-match logic at all — a
regression there would slip past a trivial-N test. N=3 forces two separate
`TASK_COMPLETED` replays to fold correctly in sequence.

**Result: this test currently FAILS against the shipped implementation** — not a test
bug. `instance_state.pending_task_nodes` accumulates every `HUMAN_TASK` node a token
has ever visited across the *entire* replay fold (`t1`, `t2`, `t3`), because
`Transition.dispatch_human_task/3`'s own contract is "the only dispatch clause that
ever appends to `pending_task_nodes`" and nothing ever removes from it
(`lib/letflow/engine/transition.ex` comments at both the append site and the
`{:complete_task, _}` dispatch site confirm this is deliberate, pre-existing REQ-044
kernel behavior). In the *live* system this is harmless: `Engine.complete_task/3`
starts each call from a fresh, single-hop `InstanceState` whose `pending_task_nodes`
only ever holds that one call's newly-activated node, so it only ever signals "insert
one new `tasks` row" and never accumulates across calls. `Reconstruction.replay/3`, by
contrast, threads one `InstanceState` through the *entire* event log in one fold, so
`pending_task_nodes` there is a running historical log of every task node ever
activated (`["t1", "t2", "t3"]`), not the currently-open set (`["t3"]`) — a design/
implementation gap between `req053-state-reconstruction.md` §6 (which directs this
exact `pending_task_nodes`-vs.-`tasks`-table comparison) and the pre-existing REQ-044
kernel semantics it was built on top of, undetected until a genuinely multi-hop (N>1
`TASK_COMPLETED`) replay is exercised. Flagged here rather than weakened: this is a
real correctness gap in `reconstruct_instance/2`'s task-set field for any instance with
more than one completed task, not a fixture mistake. Needs ISSUE-FIXER/ELIXIR-DEV
follow-up — see this file's own "Known open finding" section below.

## AC2 — projection deleted entirely, reconstruction still correct (ground truth is the log)

**Requirement text:** "deleting the instance_projections row entirely and then
reconstructing still produces the correct state, proving reconstruction does not read
the projection as an input."

**Test case:** `AC2 -- deleting instance_projections entirely still reconstructs the
correct state` / `"reconstruction succeeds with the right state after the projection
row is gone"`. Builds the same 3-task partially-completed instance, deletes its
`tasks`/`tokens`/`instance_projections` rows (FK-safe order), confirms the projection
row is truly gone, then reconstructs and asserts the exact expected status/variables/
token position — values it could only have gotten from the event log, since the
projection (and every row `write_back` would otherwise read) no longer exists.

**Why this exists:** a reconstruction that silently fell back to reading
`instance_projections` when present (INV-RC-2's own violation) would still pass a test
that only checked "does it error", or one built with the projection present. Deleting
the row first is the only way to prove the read path never touches it.

## AC3 — events spanning `events` and `events_archive` reconstruct identically

**Requirement text:** "an instance whose events span both events and events_archive
(some rows moved by REQ-026's archive/1) reconstructs to the identical state it had
before archival."

**Test case:** `AC3 -- events partly archived, some appended after, reconstruct to the
correct merged state` / `"reconstructing across events/events_archive matches the
unbroken pre-archival log"`. Reconstructs the 3-event instance once (capturing the
pre-archival state), backdates its events and archives all 3 (`EventStore.archive/1`,
matching `event_store_test.exs`'s own backdating pattern — `retention_days: 0` is
documented as "archive nothing via the fallback", not "archive everything now", so
backdating plus a small positive `retention_days` is required to actually move rows),
reconstructs again and asserts the token positions/variables/status are unchanged by
the pure storage relocation, then completes the instance's last task (a 4th event that
lands live, while the first 3 stay archived) and reconstructs a third time — proving
the merge across both tables produces the fully-correct final state (`COMPLETED`, all 4
variables, zero live tokens), not just an already-archived-only or already-live-only
log.

**Why this exists:** REQ-026's `read/2` deliberately does not span `events_archive`
(design doc §1) — this requirement's own `read_full_log/2` is new code with its own
merge-and-sort logic; a bug there (e.g. dropping archived rows, or ordering the merge
by table instead of `sequence_number`) would only surface once an instance genuinely
has events in both tables at once, which the single-archival-pass test alone would
miss without the final "append a new live event after archiving" step.

## AC4 — zero-events seed state; EXECUTION_ERROR reconstructs to status ERROR

**Requirement text:** "an instance with zero events reconstructs to token-on-START,
empty variables, status ACTIVE; an instance whose log contains an EXECUTION_ERROR event
reconstructs to status ERROR."

**Test cases** (2, separate `describe` blocks):

1. `AC4 -- zero-events instance seeds token-on-START/empty-variables/ACTIVE` /
   `"reconstructs a snapshot-only, zero-event instance to the seed state"`. Creates an
   active definition and calls `SnapshotStore.create/2` directly for a fresh
   `instance_id`, without ever calling `Engine.create/2` — mirroring the
   snapshot-committed/event-append-crashed window design doc §4/§5.1 names as the one
   case where a zero-event instance is still real and reconstructible. Asserts
   `event_count == 0`, `status == :active`, `variables == %{}`, and the one token sits
   on `"start"`.
2. `AC4 -- a log containing EXECUTION_ERROR reconstructs to status ERROR` /
   `"reconstructs status :error with the payload's variable snapshot"`. Starts a normal
   instance, then appends an `EXECUTION_ERROR` event directly via
   `EventStore.append/2` (no `Engine`-level function ever produces this event type, so
   this is the only way to construct the scenario) carrying its own `variables`
   snapshot. Asserts `status == :error` and that `variables` come from the event's own
   payload, not from whatever the instance's variables were immediately before.

**Why these exist:** case 1 is the seed-state construction path (§5.2) — never
exercised by any event fold at all, so it needs its own direct test independent of
`fold_events/3`. Case 2 proves the two event types (`INSTANCE_CANCELLED`/
`EXECUTION_ERROR`) that design doc §5.3 states are *not* routed through
`Transition.transition/3` are still replayed correctly by their own direct-state-mutate
clauses.

## AC5 — write-back: read-only by default, opt-in write, lock contention is distinct

**Requirement text:** "reconstruction without write-back leaves instance_projections
byte-identical (verified by reading the row before and after); reconstruction with
write-back updates it, and a concurrent lock holder causes a distinct lock-contention
error rather than a silent overwrite."

**Test cases** (4, separate `describe` blocks):

1. `AC5 -- reconstruction without write-back never mutates instance_projections` —
   reads the projection row, calls `reconstruct_instance/2` with no `write_back` key
   (default `false`), reads the row again, asserts every field is unchanged.
2. `AC5 -- write_back: true updates instance_projections to the reconstructed state` —
   first corrupts the live row (`variables`/`current_nodes` forced to obviously-wrong
   values) so the assertion proves an actual write happened rather than coincidentally
   matching an already-correct row, then calls `reconstruct_instance/2` with
   `write_back: true` and asserts the row now matches the replayed state, including
   `last_event_seq` sourced from the merged log's own last `sequence_number` (design
   doc §7's own stated field, with no `InstanceState` equivalent).
3. `AC5/OQ-4 -- write_back: true inserts a fresh row when the projection was deleted` —
   design doc §7's own extension (not literally named by any AC, per OQ-4): deletes the
   projection row first, then write-back inserts a brand-new row rather than erroring,
   asserting `definition_id` is correctly sourced from the instance's snapshot and
   `correlation_key` is `nil` (the documented, disclosed information loss on that path
   — moduledoc divergence 2).
4. `AC5 -- a concurrent lock holder causes lock-contention, never a silent overwrite` —
   a real second Postgres connection (`Task.async`, Sandbox `:auto`) opens its own
   transaction and takes a plain `FOR UPDATE` lock on the projection row, signals the
   test process once it holds the lock, and only releases it after the main call
   returns. `reconstruct_instance/2` called with `write_back: true` while that lock is
   held asserts `{:error, {:lock_contention, ^instance_id}}`, and that the row is
   unchanged afterward (no silent overwrite once the lock releases and the caller has
   already returned an error).

**Why these exist:** case 1/2 are the two literal halves of the AC — a test asserting
only "no error" would not catch a regression that quietly performed a write on the
default path, or one that silently no-op'd instead of writing when asked. Case 4 is the
one scenario in this whole suite that cannot be proven without genuine inter-process
concurrency — `write_back/3`'s `FOR UPDATE NOWAIT` behavior is only observable when a
*different* connection is actually holding the row lock at the moment `write_back/3`'s
own lock attempt runs; a single-process test can never produce that condition.

## AC6 — 3 separately pattern-matchable errors, each with its own test

**Requirement text:** "instance-not-found, lock-contention and replay-failed are three
separately pattern-matchable errors, each with its own test."

**Test cases** (3, separate `describe` blocks):

1. `AC6 -- :instance_not_found for an id with no events and no snapshot` — a random
   UUID with no snapshot and no events anywhere; asserts
   `{:error, :instance_not_found}` exactly.
2. `AC6 -- {:lock_contention, instance_id} is its own distinct error shape` — the same
   concurrent-lock mechanics as AC5 case 4, run again independently (a fresh instance,
   its own lock-holder task) so this AC has its own standalone, runnable test rather
   than only being covered incidentally by AC5's.
3. `AC6 -- {:replay_failed, {:unrecognized_event_type, _, _}} for a persisted unknown
   event type` — appends a `"BOGUS_EVENT_TYPE"` event (a type outside the closed
   4-type set §1 confirms is currently the only one ever produced) directly via
   `EventStore.append/2`, and asserts the exact `{:replay_failed,
   {:unrecognized_event_type, "BOGUS_EVENT_TYPE", event_id}}` shape (INV-RC-3 — never
   silently skipped).

**Why these exist:** the requirement text explicitly calls for 3 *separate* tests, not
one test asserting 3 different calls loosely — each test here pattern-matches the exact
tuple shape (not just `{:error, _}`), which is what would actually catch a regression
that collapsed two of the three into the same generic shape.

## AC7 — moduledoc records the NFR-04 bound as documented context only

**Requirement text:** "the moduledoc records R-Co's NFR-04 bound (10,000 events under 5
seconds) as documented context and states explicitly that Letflow has not adopted an
NFR requirement for it."

**Test case:** `AC7 -- moduledoc states NFR-04 as R-Co context Letflow has not adopted`
/ `"names the 10,000-events/5-seconds bound and explicitly disclaims it as a Letflow
AC"`. Fetches the real, compiled moduledoc via `Code.fetch_docs/1` (not a string
grepped from the source file — proves the doc actually compiles into the module, not
just exists in the `.ex` text) and asserts it contains `"NFR-04"`, `"10,000 events"`,
`"5 seconds"`, `"Letflow has not adopted an NFR requirement"`, and the explicit
no-tuning disclaimer.

**Why this exists:** a moduledoc that merely mentioned "10,000 events" without also
stating Letflow never adopted it as its own AC would risk a later reader treating it as
a live Letflow performance requirement (and, worse, a later benchmark "fixing" this
module against a target it was never scoped to meet) — the test checks both halves are
actually present, not just the numeric bound.

## Known open finding (from this test run, not a fixture bug)

`mix test test/letflow/engine/reconstruction_test.exs --seed 0` — **12 passed, 1
failed.** The 1 failure is AC1's test, and it is a real finding, not a test-authoring
mistake: see AC1's "Result" paragraph above. `instance_state.pending_task_nodes`
accumulates every historically-activated `HUMAN_TASK` node across a multi-`TASK_COMPLETED`
replay instead of reflecting the currently-open set, so the design doc §6-mandated
task-set comparison against the `tasks` table's `:pending` rows fails for any instance
with more than one completed task. This is left failing rather than weakened or
removed, per this project's "tests are specifications" principle — routes to
ISSUE-FIXER for root-cause diagnosis and a fix in either
`lib/letflow/engine/reconstruction.ex` (filter `pending_task_nodes` down to the
currently-open set before returning) or a correction to
`lib/letflow/design/req053-state-reconstruction.md` §6 if the intended fix is instead a
different definition of "task set."
