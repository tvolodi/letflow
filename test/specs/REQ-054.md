# Test Spec: REQ-054 — Instance state snapshots (`SnapshotWriter`) + snapshot-aware replay

**Requirement:** REQ-054 (stage S3) — port `snapshot_writer.zig` as
`Letflow.Engine.SnapshotWriter` (`take_snapshot/4`, `maybe_take_snapshot/4`,
`latest_snapshot/2`) plus its `instance_state_snapshots` migration/schema, and extend
REQ-053's `Letflow.Engine.Reconstruction.reconstruct_instance/2` so it replays from the
latest snapshot instead of always from sequence 1 when one exists. See
`lib/letflow/design/req054-instance-state-snapshots.md` for the full design; acceptance
criteria verbatim from `handoffs/WF02-REQ054-20260819/step-03-test-designer.json`.

**Test tier:** unit + integration (real Postgres throughout, `Letflow.DataCase`,
DIRECTIVE T-1 — no mocked database).

**Code under test (post-rework, commit `c356fe0` on this branch):**
`lib/letflow/engine/snapshot_writer.ex`, `lib/letflow/engine/instance_state_snapshot.ex`,
`priv/repo/migrations/20260821000001_create_instance_state_snapshots.exs`,
`lib/letflow/engine/reconstruction.ex` (the REQ-054 modification —
`select_replay_source/2`, `read_full_log/3`, `seed_state_for_replay/3`), and the three
new call sites in `lib/letflow/engine.ex` (`maybe_snapshot_after_create/4`,
`maybe_snapshot_after_complete_task/2` both clauses, `maybe_snapshot_after_set_instance_error/3`).

## Test cases

1. **Migration applies cleanly, no `tenant_id` column** — `AC1 -- instance_state_snapshots migration applies cleanly under tenant provisioning, no tenant_id column` in
   `test/letflow/engine/snapshot_writer_test.exs`. Why this test exists: `provisioned_tenant/0`
   already runs every tenant-scoped migration via `TenantProvisioning.replay_migrations/2`
   as a side effect of every other test in this file — this case exists to make that
   coverage explicit and add the one assertion no other test makes: querying
   `information_schema.columns` directly proves the shipped column set (no `tenant_id`,
   per Decision 0006 D2 / INV-ISS-4) rather than merely trusting the migration file's own
   prose comment.

2. **`take_snapshot/4` round-trips `InstanceState` field-for-field (INV-ISS-3)** —
   `AC2 -- take_snapshot/4 followed by latest_snapshot/2 round-trips every InstanceState field` and
   `AC2 -- round-trips a token's nil branch_id/waiting_child_instance_id, not just present values`.
   Why: the serialise/deserialise pair (§2.2 of the design doc) is hand-written struct↔map
   conversion with no `Ecto.Type` backing it — a typo in either direction (e.g. a swapped
   key, a missed `nil` case) would silently corrupt every future snapshot-sourced
   reconstruction. This is also the correctness precondition AC4's both-paths-agree test
   depends on: if the round-trip itself were lossy, AC4 could pass or fail for the wrong
   reason.

3. **`maybe_take_snapshot/4` cadence, default 1000 and configurable** —
   `AC3 -- default interval 1000: no row below it, exactly one row at it` and
   `AC3 -- configurable interval: no row below it, exactly one row at it`. Why: the
   requirement's own text singles out "default 1000, configurable" as the acceptance bar;
   testing only the configurable path would leave the literal default constant
   (`@default_interval` in `snapshot_writer.ex`) unverified, and testing only 1000 would
   leave the `opts[:interval]` override path unverified. Both cases call
   `maybe_take_snapshot/4` with hand-picked `sequence_number` values against a real FK'd
   instance — no 1000-event loop needed, since the cadence check is a pure row-based
   arithmetic comparison (§6 of the design doc, option 1) with no dependency on how many
   real events actually exist.

4. **Both-paths-agree — the single most important test (INV-ISS-1)** —
   `AC4 -- snapshot-sourced reconstruction agrees with full-replay reconstruction of an identical history`.
   Why: this is the correctness bar the design doc itself names as non-negotiable — "a
   snapshot that diverges from full replay is worse than no snapshot at all." Built as two
   real instances sharing the same graph and the same sequence of real
   `Engine.complete_task/3` calls: instance A gets a real snapshot taken mid-way (via
   `SnapshotWriter.take_snapshot/4`, not a stub) and then one more real event past it;
   instance B never gets a snapshot row at all, forcing `select_replay_source/2` to return
   `{:full_replay, 1}` for real. `reconstruct_instance/2`'s results are compared node-id
   multiset / variables / status / pending-task-node-set, per REQ-053 design §6's own
   equality definition (token_id/branch_id are freshly minted every replay regardless of
   seed, so raw struct `==` is never the right comparison here — matches
   `reconstruction_test.exs`'s own `assert_state_matches_projection/2` precedent). The test
   additionally asserts `event_count`: 1 for the snapshot-sourced instance (only the event
   after the snapshot's `sequence_number` is folded) vs. 4 for the full-replay instance —
   proving the snapshot path was genuinely exercised, not merely that the two final states
   coincidentally matched despite both taking the same (full-replay) path.

5. **Moduledoc distinguishes the two snapshot tables, and names the open question** —
   `AC5 -- moduledoc distinguishes instance_state_snapshots from instance_definition_snapshots` and
   `AC5 -- moduledoc names the cadence-counter placement as an open question`. Why: the
   design doc calls this out explicitly as "a silent data-model error" risk (the two table
   names are one word apart) and separately requires the cadence-counter open question be
   surfaced, not silently defaulted — both are doc-content requirements the shipped
   moduledoc (`lib/letflow/engine/snapshot_writer.ex:1-107`) already satisfies in prose;
   asserting on it, mirroring `reconstruction_test.exs`'s own AC7 NFR-04 doc-content test
   precedent, guards against a future edit silently dropping either explanation.

6. **`engine.ex` wiring — real end-to-end, not `maybe_take_snapshot/4` tested in isolation**
   — `AC6 -- real create/complete_task/set_instance_error calls never write a snapshot below the real threshold` and
   `AC6 -- the exact same call path writes a row once its real threshold condition holds`.
   Why, and an open finding surfaced rather than silently worked around: REQ-028's
   structural validator caps any one graph at `@max_nodes 500`
   (`lib/letflow/definitions/graph.ex:158`), so a single instance's own event sequence
   (`INSTANCE_STARTED` + one `TASK_COMPLETED` per distinct `HUMAN_TASK` node) can never
   legitimately reach 1000 — the literal default `maybe_take_snapshot/4` interval — through
   `create/2`/`complete_task/3` alone; `set_instance_error/2`'s own eligibility check
   (`execution_error.ex` `check_eligibility/1`) additionally rejects a second call once an
   instance is already `:error`, closing off "call it 999 times" as a workaround too. This
   is a genuine, load-bearing interaction between REQ-028's cap and REQ-054's hardcoded
   default that this test design surfaces for REVIEWER/CODE-DESIGNER rather than silently
   routing around with a manufactured always-passing test. Given that constraint, this
   requirement's AC6 is covered by two real (non-mocked) sub-tests instead: (a) driving
   `Engine.create/2`, `Engine.complete_task/3` (both the plain-completion and, separately,
   `Engine.set_instance_error/2`) through their real call sites and confirming via
   `SnapshotWriter.latest_snapshot/2` that no row is written while genuinely under
   threshold — proving the wiring is live and correctly evaluates its real arguments on
   every call, not dead code; and (b) taking the `InstanceState` a real `Engine.complete_task/3`
   call actually produced and passing it through the identical `SnapshotWriter.maybe_take_snapshot/4`
   function `engine.ex`'s own call sites invoke, with a real, small `interval` override
   (a legitimate, documented part of `cadence_opts()`, not a stub), to prove that same
   function genuinely writes a row once its threshold condition holds — bridging the gap
   between "wiring never fires by accident" (a) and "the write half of the contract really
   works" (already covered in isolation by test case 3) using data a real engine flow
   produced.
