# Test Spec: REQ-055 — Concurrent instance isolation guarantees (EE-12)

**Requirement:** REQ-055 (stage S3) — verify concurrent operations across distinct
instances never corrupt each other's state, concurrent operations on the SAME instance
resolve deterministically to exactly one winner, no global/table-level lock is held
across instance boundaries anywhere in the engine's write paths, and (conditionally)
supervised-process isolation.

**Design doc:** `lib/letflow/design/req-055-concurrent-instance-isolation.md`

**Test tier:** unit+integration (real Postgres, real concurrent processes via
`Task.async`/`Task.await_many` — no mocked database, no mocked concurrency)

## Test cases

1. **AC1 — 100 concurrent task completions across 100 distinct instances**
   (`test/letflow/engine_concurrency_test.exs`, `describe "AC1 -- 100 concurrent task
   completions across 100 distinct instances"`). Proves cross-instance isolation under
   real overlapping load, not just single-pair concurrency: 100 instances are started
   sequentially, then all 100 `complete_task/3` calls are launched via `Task.async`
   *before any is awaited*, so they genuinely overlap in-flight against real Postgres
   connections (sandbox mode `:auto`, not the shared-connection mode other test files
   use — a shared connection would serialize the calls at the connection layer and the
   test would pass for the wrong reason, per design §3.1). Exists because AC2 alone
   (two calls, same instance) cannot show that instance A's completion never touches
   instance B's rows — only a genuinely wide concurrent batch across *distinct*
   instances exercises that. Assertions: (a) every result is `{:ok, %{instance_status:
   :completed}}` — a real Postgres deadlock or a mis-scoped lock causing spurious
   `:task_not_pending` would break this; (b) each instance's own `InstanceProjection`
   holds only its own instance-tagged `output_variables` value, catching cross-instance
   variable-map corruption a naive shared-state bug would produce; (c) a loose
   wall-clock proxy (`Task.await_many` total time < ~30x one independently-measured
   single completion) — this is deliberately loose to avoid CI flakiness, but fails
   decisively (near 100x) against an accidentally-reintroduced global mutex/singleton
   serialization point, which no per-row-lock assertion can otherwise catch from
   ExUnit.

2. **AC2 — two concurrent task completions on the SAME instance**
   (`describe "AC2 -- two concurrent task completions on the SAME instance"`). Proves
   the opposite property from case 1: same-instance concurrency must NOT both succeed —
   `fetch_and_lock_task/3`'s `FOR UPDATE` lock (design §2.1 L1) must serialize the two
   transactions so exactly one commits `:completed` and the other observes the typed
   conflict `{:error, {:task_not_pending, :completed}}`. Exists to prove the lock
   actually does its job under real contention, not merely that the code path exists
   (the sequential-call version of this same scenario is already covered by
   `engine_complete_task_test.exs`'s AC4 case — this one specifically requires both
   `Task.async` calls launched before either is awaited, since a sequential
   launch-then-await pattern would never actually contend on the lock and would prove
   nothing about concurrency, per REQ-055's own acceptance text explicitly ruling out
   sequential execution as sufficient). Also asserts exactly one `TASK_COMPLETED` event
   exists afterward — proves the losing transaction's rollback was complete, not a
   partial/duplicate write.

3. **AC4 — reconstruction matches projection for all instances after the concurrent
   run** (`describe "AC4 -- reconstruction matches projection for all instances
   after the concurrent run"`). Reuses case 1's 100-instance concurrent completion, then
   calls `Letflow.Engine.Reconstruction.reconstruct_instance/2` (REQ-053, unmodified)
   once per instance and compares its `status`/`variables`/token-node-id-multiset
   against that same instance's own live `InstanceProjection`. Exists because AC1's own
   assertions read only `instance_projections` — a bug that corrupted the *event log*
   itself (as opposed to the projection) during the concurrent write burst would pass
   AC1's checks but fail this one, since reconstruction rebuilds state purely from the
   event log (`INV-RC-2`), never from `instance_projections`. Checked per-instance in a
   loop (not once in aggregate) so a single corrupted instance among the 100 fails with
   its own `instance_id` visible in the failure output.

4. **AC5 — not applicable, stated explicitly, no test case.** REQ-045 resolved the
   running-instance shape to row-based state (a plain transactional context module),
   not a supervised `:gen_statem`/`DynamicSupervisor`-per-instance process (design §1,
   confirmed directly from `lib/letflow/engine.ex`'s and
   `lib/letflow/instance_supervisor.ex`'s own moduledocs) — there is no per-instance
   process to kill, so AC5's process-kill scenario cannot be exercised. Per REQ-055's
   own acceptance text ("state that this half is not applicable rather than silently
   skipping it") and this project's design-gate rule against silent "TBD" omission,
   this is stated as a `@moduledoc` paragraph in `test/letflow/engine_concurrency_test.exs`
   itself, cross-referencing design doc §1/§2.6, rather than left unaddressed. AC3 (the
   moduledoc lock-inventory addition) is verified directly by inspection of
   `lib/letflow/engine.ex`'s new EE-12 moduledoc section already added at Step 2a — not
   by a separate test case here, since AC3's own deliverable *is* documentation, not
   executable behavior; its content is derived from and consistent with the same L1
   lock this file's AC2 case exercises under real contention.
