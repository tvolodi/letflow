# Test Spec: REQ-056 — Service task configuration, retry classification and dispatch contract

**Requirement:** REQ-056 (`docs/requirements.yaml`, stage S3) — see `lib/letflow/design/service_task.md`
for the full approved design this test suite verifies against. Acceptance criteria verbatim:

1. `parse_config_from_node_attributes` returns a config with `timeout_ms` defaulting to 30000
   and `retry_limit` defaulting to 3 when the node omits them, and records the
   `BothUrlAndServiceIdProvidedUrlIgnored` warning (not an error) when both `url` and
   `service_id` are present.
2. An HTTP 3xx is classified as a failure and is never followed as a redirect, and an HTTP 429
   is classified as a retriable failure — two explicit tests, since both are easy to get
   backwards.
3. Each of the 7 failure kinds has an explicit test mapping an input condition to that kind, and
   `is_retriable_failure`/`decide_failure` are tested at `attempt_index` below, equal to, and
   above `retry_limit`.
4. `compute_service_task_backoff_ms` grows exponentially with `attempt_index` and is clamped at
   the cap, verified across at least 4 successive attempt indices without any sleeping.
5. A 2xx response whose body is a JSON object merges into instance variables via REQ-049's
   merge; a 2xx response whose body is a JSON array or a bare string does not merge and routes
   to REQ-061's ERROR path — two explicit tests.
6. A URL template rendering to an empty string is rejected at activation and routes to the
   ERROR path rather than dispatching a request.
7. The moduledoc states explicitly that the HTTP transport and the `service_catalog` lookup are
   injectable interfaces, names OBS-05's DLQ (S6) as the unbuilt destination for exhausted
   retries, and confirms no partial DLQ was built here.
8. An exhausted-retry outcome (`decide_failure` returning give-up) is demonstrated routing into
   REQ-061's `set_instance_error` rather than writing its own ERROR transition, confirmed by
   inspection and by test — this closes REQ-061's own AC8 obligation, deferred forward because
   REQ-056 did not exist when REQ-061 was built.

**Test tier:** unit + integration (real Postgres for AC5(b)/AC6/AC8's routing demonstrations)

## Why AC5/AC6/AC8 need an integration test, not just a shape assertion

`Letflow.Engine.ServiceTask` is deliberately caller-less (design doc §1, §6): it never calls
`Letflow.Engine.set_instance_error/2` itself — no dispatch-orchestration loop exists yet. So
"routes to REQ-061's ERROR path" cannot be proven by reading the module alone; it has to be
demonstrated by actually composing the two pieces: build the `standalone_error_attrs()` map with
`ServiceTask.build_empty_url_error_attrs/1` or `ServiceTask.build_service_task_give_up_error_attrs/1`,
then hand it to the real `Letflow.Engine.set_instance_error/2` against a real, Postgres-backed
instance fixture, and assert the instance actually lands in `:error` status with an
`EXECUTION_ERROR` event recorded. A test that only asserts the *shape* of the returned map (e.g.
`assert Map.has_key?(attrs, :error_type)`) would pass even if `set_instance_error/2` silently
rejected the map for some unrelated reason — it would prove nothing about the two pieces actually
composing. `test/letflow/engine_execution_error_test.exs` (REQ-061's own suite) established this
"build attrs, call `set_instance_error/2` against a real tenant schema, read the projection and
event back" pattern; this suite reuses it directly.

## Test cases

1. **AC1 — defaults + warning.** `parse_defaults_test/0`: a node with only `endpoint` set gets
   `timeout_ms == 30_000`, `retry_limit == 3`, `warnings == []`. A node with both `endpoint` and
   `service_id` gets `warnings == [:both_url_and_service_id_provided_url_ignored]` and still
   returns `{:ok, _}` (never `{:error, _}`) — proves the "warning, not error" wording. See
   `test/letflow/engine/service_task_test.exs` `describe "AC1"`.
2. **AC1 — explicit overrides not defaulted.** A node supplying `timeout_ms`/`retry_limit`
   explicitly gets those values back unchanged (guards against a test that would pass even if
   the function ignored the node's own values and always returned the defaults).
3. **AC1 — missing url and service_id is a hard parse error**, not silently defaulted — proves
   `route_kind` derivation actually branches on presence/absence rather than always picking one.
4. **AC2 — 3xx is a failure, never a redirect.** `classify_failure_kind({:http, 301, nil})`
   returns `:http_redirect_3xx` (a failure_kind, not `{:success, _}`), and
   `is_retriable_failure(:http_redirect_3xx) == false`. Fails if the classifier were backwards
   (e.g. treated 3xx as retriable-success).
5. **AC2 — 429 is a retriable failure.** `classify_failure_kind({:http, 429, nil})` returns
   `:rate_limited_429`, and `is_retriable_failure(:rate_limited_429) == true`. Fails if 429 were
   mis-classified as `:http_non_2xx` (non-retriable) — the exact backwards mistake AC2 warns
   about.
6. **AC3 — all 7 failure kinds, one test per kind**, each asserting the exact input ->
   `failure_kind()` mapping from design doc §5.2: `:timeout`, `:network`,
   `:request_build_error`, `:http_non_2xx` (e.g. a 500), `:http_redirect_3xx` (e.g. 301),
   `:rate_limited_429`, `:invalid_2xx_body` (2xx with an array body, a bare string body, and an
   undecodable body — three sub-cases, since AC5 also needs this).
7. **AC3 — `decide_failure/3` boundary at `attempt_index` below/equal/above `retry_limit`**, for
   a retriable kind (`:timeout`) with `retry_limit = 3`: `attempt_index = 2` -> `:retry` (below),
   `attempt_index = 3` -> `:give_up` (equal), `attempt_index = 4` -> `:give_up` (above). A
   parallel case for a non-retriable kind (`:invalid_2xx_body`) at `attempt_index = 0` (below any
   reasonable limit) still gives up immediately — proves step 1 of the algorithm (retriability
   gates before the boundary check) is not bypassed.
8. **AC4 — exponential growth + cap, no sleep.** `compute_service_task_backoff_ms/3` called at
   `attempt_index` 0, 1, 2, 3 with `base_ms: 100, cap_ms: 10_000` asserts the literal sequence
   `100, 200, 400, 800` (exponential, no jitter) in one synchronous test with zero
   `Process.sleep/1` calls anywhere. A second case with a low cap (`cap_ms: 500`) asserts
   `attempt_index: 5` returns exactly `500`, not an uncapped `3200` — proves the clamp fires.
9. **AC5(a) — 2xx JSON object classifies as success and merges via REQ-049.**
   `classify_failure_kind({:http, 200, ~s({"a":1})})` returns `{:success, %{"a" => 1}}`; that
   decoded map is then fed directly into `Letflow.Engine.VariableMerge.merge/3` as
   `incoming_variables`, asserting the real merge produces `{:ok, %{"a" => 1}, []}` against
   an empty `current_variables` — proves the classifier's success output is actually
   merge-shaped, not just asserted in isolation.
10. **AC5(b) — 2xx JSON array/bare string does not merge, routes to ERROR (integration).**
    Two sub-cases (array body, bare-string body) each: `classify_failure_kind` returns
    `:invalid_2xx_body`; `is_retriable_failure(:invalid_2xx_body) == false`;
    `decide_failure(:invalid_2xx_body, 0, 3) == :give_up`; then
    `ServiceTask.build_service_task_give_up_error_attrs/1`'s output is handed to a real
    `Letflow.Engine.set_instance_error/2` call against a provisioned tenant/instance, and the
    instance is confirmed to land in `:error` status with one `EXECUTION_ERROR` event recorded
    whose `error_type` is `"service_task_retries_exhausted"`. See
    `test/letflow/engine/service_task_test.exs` `describe "AC5(b)/AC8 -- give-up routes to set_instance_error/2"`.
11. **AC6 — empty rendered URL rejected at activation, routes to ERROR (integration).**
    `validate_rendered_url("")`, `validate_rendered_url("   ")`, and `validate_rendered_url(nil)`
    all return `{:error, :empty_rendered_url}`; a non-blank URL returns `:ok` (guards against a
    vacuously-always-rejecting implementation). Then
    `ServiceTask.build_empty_url_error_attrs/1`'s output is handed to a real
    `Letflow.Engine.set_instance_error/2` call, and the instance is confirmed to land in
    `:error` status with one `EXECUTION_ERROR` event whose `error_type` is
    `"service_task_url_rendered_empty"`.
12. **AC7 — moduledoc content, asserted as real ExUnit assertions on the compiled moduledoc
    string** (not grep): asserts the moduledoc contains "INJECTABLE" applied to both the HTTP
    transport and the `service_catalog` lookup, names "OBS-05", "S6", and states the DLQ/retry
    queue/discard/sweep was not built here.
13. **AC8 — exhausted-retry give-up demonstrated end to end (integration), distinct scenario
    from AC5(b).** A *retriable* kind (`:timeout`) reaching `attempt_index == retry_limit`
    produces `decide_failure(:timeout, 3, 3) == :give_up`; `build_service_task_give_up_error_attrs/1`'s
    output (with `last_failure_kind: :timeout`) is handed to a real `set_instance_error/2` call,
    and the instance lands in `:error` with the event's `reason` text containing "retries
    exhausted" (distinguishing it from AC5(b)'s "not retriable" reason text, per design doc §4's
    `cause_text` branch) — proves both give-up causes reach the identical sink function, per
    design doc §6's routing statement, and confirms by inspection (§ "by inspection" note below)
    that no separate/bespoke ERROR-transition code exists.

### "By inspection" component of AC7/AC8

`lib/letflow/engine/service_task.ex` was read in full (see design doc §0 sourcing, and this
run's own reading of the file): it contains no `Letflow.Repo` reference, no
`Ecto.Multi` construction, no call to `ExecutionError.append_multi/3`, and exactly one function
(`build_service_task_give_up_error_attrs/1`) producing a `standalone_error_attrs()`-shaped map
for every `:give_up` cause — confirming AC8's "no separate ERROR transition" claim structurally,
not just by test. The integration tests above additionally confirm this composes correctly at
runtime.
