# Test Spec: REQ-057 — Plugin handler interface and registry contract (EXT-03)

**Requirement:** REQ-057 (`docs/requirements.yaml`, stage S3) — port `plugin_interface.zig`
and `plugin_registry.zig`'s stable interfaces: the handler contract
(`Letflow.Engine.PluginInterface`, `lib/letflow/engine/plugin_interface.ex`) and the
registration/freeze/resolution table (`Letflow.Engine.PluginRegistry`,
`lib/letflow/engine/plugin_registry.ex`). Full design (gate-approved, 1 rework
iteration): `lib/letflow/design/req057-plugin-interface-registry.md`.

**Test tier:** unit (pure, `async: true`) for `PluginInterface`'s `invoke/2,3` and
`build_error_args/3`, and for `PluginRegistry`'s registration/resolution logic (via a
real, restarted OTP singleton, `async: false` — see rationale below) + unit+integration
(`Letflow.DataCase`, real Postgres) for the design doc §7.1 end-to-end routing
demonstration.

## Acceptance criteria (verbatim) and their test cases

1. **"A registered handler is invoked with a context carrying instance_id,
   definition_id, node_id, node_type, instance variables, node config and trace_id, and
   returning COMPLETE with output variables merges them via REQ-049's merge."**
   - `plugin_interface_test.exs` `"ExecutionContext -- carries all seven named fields
     (AC1)"` — proves the struct's shape and `@enforce_keys` (also proves a missing
     required field is structurally impossible to construct, exercising the same
     contract from the failure side).
   - `plugin_interface_test.exs` `"invoke/2 -- a COMPLETE outcome is returned unchanged
     (AC1)"` — proves `invoke/2` passes a handler's `{:complete, output_variables}`
     through verbatim.
   - `engine_plugin_error_routing_test.exs` `"AC1 -- a handler's COMPLETE outcome merges
     via REQ-049's VariableMerge.merge/3"` — the full, real chain: a genuine
     `Letflow.Engine.create/2` instance, a fixture handler, `invoke/2`, then
     `VariableMerge.merge/3` called with `invoke/2`'s own `output_variables` unchanged
     (design doc §8's "no adapter" claim, proven rather than asserted).

2. **"A handler returning ERROR routes the instance to REQ-061's EE-10 ERROR path with
   the handler's reason string preserved in the EXECUTION_ERROR event."**
   - `plugin_interface_test.exs` `"invoke/2 -- a deliberate ERROR outcome preserves the
     handler's reason string (AC2)"` — proves `invoke/2` never rewrites/truncates a
     handler's own reason string.
   - `engine_plugin_error_routing_test.exs` `"AC2/AC8 -- a handler ERROR outcome routes
     into REQ-061's set_instance_error/2"` — design doc §7.1's exact 7-step sequence: a
     real instance, a fixture ERROR handler, `invoke/2` → `build_error_args/3` → a real
     `Letflow.Engine.set_instance_error/2` call, then an independent re-fetch of the
     `instance_projections` row AND the appended `EXECUTION_ERROR` event, asserting the
     reason string survived the whole chain byte-for-byte.

3. **"A handler that raises, and a handler that exits, are BOTH treated as ERROR
   outcomes rather than propagating -- two explicit tests, since a bare try/rescue
   passes the first and fails the second."**
   - `plugin_interface_test.exs` `"invoke/2 -- a handler that raises is treated as ERROR,
     not propagated (AC3)"` — a handler that `raise`s; asserts `invoke/2` returns
     `{:error, reason}` (never raises to its own caller) and the test process itself
     stays alive to make the assertion (a bare `try/rescue` would already pass this one
     — see the next test for why it isn't sufficient).
   - `plugin_interface_test.exs` `"invoke/2 -- a handler that exits is ALSO treated as
     ERROR, not propagated (AC3)"` — a **separate** handler that calls `exit/1`; this is
     the test a bare `try/rescue` would fail (an `exit` never runs a `rescue` clause) —
     its passing is exactly what proves `invoke/2`'s `Task.Supervisor` +
     `Task.yield/2` mechanism, not a `try/rescue`, is what's actually wired in.
   - `engine_plugin_error_routing_test.exs` `"AC3 (routing half) -- a raising handler's
     crash also reaches set_instance_error/2"` — confirms a crash's `{:error, _}`
     outcome routes through the identical §7.1 chain a deliberate `ERROR` does, not a
     separate/different path.
   - Supplementary (same function, real shipped branches, not independently-named ACs):
     `"invoke/2 -- a handler returning a value outside its own outcome() contract"` (the
     `{:ok, other}` defensive branch, design doc §2.4.1 step 3, OQ-3) and `"invoke/3 --
     a handler that does not respond within opts[:timeout_ms]"` (the timeout branch) —
     included because both are real, reachable branches of the exact function AC3 is
     about, at negligible cost.

4. **"Each of the registration errors (duplicate node_type, invalid node_type, nil
   handler, incompatible API version, registration after freeze) is a distinct
   pattern-matchable error with its own test."**
   - `plugin_registry_test.exs`, one `describe` block per error, each asserting the
     exact distinct atom: `"register_plugin_handler/1 -- registry_frozen (AC4)"` (tested
     directly against the live, always-post-boot-frozen singleton — no restart needed),
     `"-- nil_handler (AC4)"`, `"-- invalid_node_type (AC4)"`, `"--
     incompatible_api_version (AC4)"`, `"-- duplicate_node_type (AC4)"` (plus a sibling
     test proving the SAME `handler_key` under two DIFFERENT scopes is explicitly NOT a
     duplicate, per design doc §6.1 step 6). See "Why plugin_registry_test.exs restarts
     a real OTP child" below for why five of these six are triggered via a boot-time
     seed list rather than a live post-boot call.

5. **"A tenant-scoped registration without an owner_tenant_id and a global registration
   with one are both rejected with their own distinct errors, and resolution for tenant
   B does not return tenant A's tenant-scoped handler."**
   - `plugin_registry_test.exs` `"register_plugin_handler/1 --
     tenant_scoped_plugin_requires_owner_id (AC5)"` and `"--
     global_plugin_must_not_have_owner_id (AC5)"` — the two distinct SVC-02 scoping
     errors.
   - `plugin_registry_test.exs` `"resolve_plugin_handler_for_tenant/2 -- cross-tenant
     isolation (AC5)"` — `"tenant B's lookup never returns tenant A's tenant-scoped
     registration"` (the literal AC5 non-leak assertion: tenant A's registration seeded,
     tenant B's lookup returns `{:error, :not_registered}`, tenant A's own lookup still
     finds it) and `"tenant-scoped wins for its own tenant, but a DIFFERENT tenant still
     gets the global fallback"` (design doc §5.2's two-step precedence order, both
     branches). A third test covers the trivial "nothing registered at all" baseline.

6. **"A plugin registered for a node_type that also has a built-in handler shadows the
   built-in, demonstrated by an explicit test."**
   - `plugin_registry_test.exs` `"resolve_node_handler_kind/1 -- plugin precedence over
     a real built-in (AC6)"` — `"HUMAN_TASK resolves :builtin before registration,
     :plugin after -- the built-in is shadowed"`. Uses `"HUMAN_TASK"` specifically, not
     `"SERVICE_TASK"` — design doc §0's own confirmed read of `Transition.dispatch_node/4`
     found `HUMAN_TASK` is one of the 5 node types with a REAL built-in dispatch clause
     today, while `SERVICE_TASK` has none (a plugin registered there would be the *first*
     handler, not a demonstration of shadowing an existing one). A second test confirms
     an unregistered key resolves `:builtin`, the control case the shadowing test's
     "before" half already implies but this makes explicit for a key that's never
     touched by any seed list in this file.

7. **"The moduledoc states that the WASM plugin host is S5 scope and that S3 supports
   only in-process Elixir behaviour implementations, and names the registry-storage
   mechanism as an open question left for CODE-DESIGNER."**
   - `plugin_registry_test.exs`, `describe "moduledoc -- ..."` blocks, using
     `Code.fetch_docs/1` + a normalized-whitespace substring match — the same technique
     `engine_execution_error_test.exs`'s own REQ-061 AC6 moduledoc tests already
     establish as this project's precedent for a structural/textual AC. Checks both
     `Letflow.Engine.PluginInterface`'s and `Letflow.Engine.PluginRegistry`'s
     moduledocs for the S5/WASM-scope sentence and the in-process-only support
     statement, and `PluginRegistry`'s moduledoc specifically for the storage-mechanism
     section. **Note on wording:** by the time CODE-DESIGNER's design doc shipped, the
     storage-mechanism question was no longer literally "open" — design doc §4.2
     resolved it (a supervised `GenServer` owning a private ETS table), flagging it at
     §10 OQ-1 as a candidate for a `docs/migration/decisions/` record rather than as
     still-undecided. `PluginRegistry`'s moduledoc documents that resolved mechanism in
     detail (a `## Storage mechanism` section), which is what these tests check for —
     asserting literal "open question" text against an implementation that correctly
     resolved the question before shipping would be testing stale requirement wording
     against code that did its job, not a real defect.

8. **"A handler ERROR outcome is demonstrated routing into REQ-061's set_instance_error
   rather than writing its own ERROR transition, confirmed by inspection and by test --
   this closes REQ-061's own AC obligation, deferred forward because REQ-057 did not
   exist when REQ-057 was built."**
   - **Inspection half:** `plugin_interface_test.exs` `"build_error_args/3 -- the pure
     outcome() -> error_args() mapper (AC8)"` includes `"is the only function this
     module defines that constructs an ExecutionError.error_args() value (INV-PR-10)"`
     — a runnable, mechanical stand-in for "confirmed by inspection": lists every
     function `PluginInterface` exports and asserts `build_error_args/3` is the only
     one whose name mentions "error", so a future addition of a second, competing
     error-constructing function would fail this test rather than pass silently. The
     shape-correctness half of the mapper (`"maps context + reason + meta to the exact
     error_args() shape REQ-061 expects"` and the `actor_id: nil` case) is tested in the
     same `describe` block.
   - **Test half:** `engine_plugin_error_routing_test.exs` `"AC2/AC8 -- a handler ERROR
     outcome routes into REQ-061's set_instance_error/2"` — design doc §7.1's literal
     7-step sequence, reproduced exactly: a real `Letflow.Engine.create/2` instance
     (step 1), a fixture handler (step 2), a hand-built `ExecutionContext` pointing at
     the real instance (step 3), `invoke/2` (step 4), `build_error_args/3` (step 5), a
     real `Letflow.Engine.set_instance_error/2` call (step 6), and an independent
     re-fetch of both the `instance_projections` row and the appended `EXECUTION_ERROR`
     event (step 7) — this is the same test listed under AC2 above; AC2 and AC8 are
     closed by the identical demonstration, per design doc §7.1's own framing.

## Why `plugin_registry_test.exs` restarts a real OTP child instead of using a
## per-test isolated instance

`Letflow.Engine.PluginRegistry` is a single, named-singleton `GenServer`
(`lib/letflow/application.ex`) owning a single, fixed-named ETS table
(`Letflow.Engine.PluginRegistry.Table` — a module attribute, not parameterized by
process name, unlike `Letflow.SandboxPool`'s own `:name`-option precedent
`sandbox_pool_test.exs` uses for the same isolation problem). `init/1` also freezes the
registry automatically the instant a boot's seed list finishes processing successfully
(design doc §6.4), so there is no way to start a second, independently-seeded instance
of this module without first stopping the live one (which would otherwise crash on
`:ets.new/2`'s `:named_table` collision), and no way to reach a live, post-boot,
still-unfrozen instance at all. `plugin_registry_test.exs` therefore restarts the real,
application-supervised child (`Supervisor.terminate_child/2` +
`Supervisor.delete_child/2` + `Supervisor.start_child/2` with a test-chosen seed list),
asserts against the result, and restores the default (empty) registry via `on_exit/1`
before the next test runs — `async: false` for the whole file, since this mutates a
node-wide singleton. This is why `nil_handler`/`invalid_node_type`/the two SVC-02
scoping errors/`incompatible_api_version`/`duplicate_node_type` are all triggered via a
deliberately malformed **seed list** (causing `init/1` to `{:stop, ...}`, which
`Supervisor.start_child/2` surfaces as a structured error) rather than via a live
post-boot `register_plugin_handler/1` call — `registry_frozen` is the one error
reachable directly, since the live default instance is always already frozen.

## Coverage check

- [x] Every acceptance criterion (1–8) above has ≥1 runnable test case listed, with no
      `@tag :skip`.
- [x] No test depends on wall-clock time or unseeded randomness — the one
      time-adjacent test (`invoke/3`'s timeout branch) uses a deliberately short,
      test-controlled `timeout_ms:` against a handler that sleeps far longer, which is
      deterministic (always times out) rather than wall-clock-dependent.
- [x] No closed state/transition set is introduced by this requirement in the sense
      `test_developer_guide.md` §4 means for `process_instance_test.exs`-style property
      testing — `PluginRegistry`'s registration-error union (AC4/AC5) is a fixed set of
      independently-triggerable, non-sequential checks (design doc §6.1's explicit,
      ordered `with` chain), not a multi-step state machine with a legal/illegal
      transition graph; each error already has its own explicit example test above,
      which is the shape `test_developer_guide.md` §2's "Unit/example tests" tier
      describes for exactly this case.
- [x] Fixtures use per-test unique data (`unique_key/1` uses
      `System.unique_integer([:positive, :monotonic])`, `Ecto.UUID.generate()` for every
      tenant/actor id) — no shared hardcoded IDs, no cross-test pollution.
- [x] Every test is self-sufficient (no dependency on execution order) — the OTP-restart
      helper's `on_exit/1` restoration runs after each test regardless of pass/fail,
      independently of every other test in the file.
- [x] No hardcoded secrets/connection strings anywhere in these files.
