# Test Spec: REQ-058 — Lua script execution audit persistence path

**Requirement:** REQ-058 (LUA-07), stage S3. See
`handoffs/WF02-REQ058-20260818/step-01-code-designer.json` `context.requirement_text`
for the full verbatim text and `lib/letflow/design/req058-lua-script-audit.md` §11 for
the acceptance-criteria traceability table this spec mirrors.

**Test tier:** unit + integration (real Postgres via `Letflow.DataCase`, no state
machine/closed transition set here, so no property test — `LuaScriptAudit` is a single
`with`-chain function, not a `Letflow.ProcessInstance`-shaped module per
`test_developer_guide.md` §4's scoping).

**Module under test:** `Letflow.Engine.LuaScriptAudit.execute_script_for_audit/6`
(`lib/letflow/engine/lua_script_audit.ex`).

**Test-double strategy:** no real Lua runtime exists (S5, unstarted). Every test
supplies an inline module `use`ing `@behaviour Letflow.Engine.LuaScriptAudit.Executor`,
following `test/letflow/definitions/service_scope_validator_test.exs`'s
"raise-if-called" double idiom for proving a dependency was genuinely never invoked,
plus an `Agent`-backed call-recorder double for the one case (AC3) that must positively
observe zero calls without relying on a raise (a raise proves "not called on this
control-flow path," an explicit counter proves "the call count is exactly zero" — using
both fixture styles across the suite covers each AC with the strongest available
technique for that case).

## Test cases

1. **Success path (AC2)** — a test-double executor returns a manifest hash matching the
   supplied `registered_hash`; asserts `{:ok, %AuditRecord{...}}` with the right
   `instance_id`/`manifest_hash`/`actor_id`, then independently re-reads the row via
   `Repo.get/3` and `Repo.all/2` (scoped to the tenant's `:prefix`) to confirm exactly
   one row landed and its stored columns match what was passed in — not just trusting
   the function's own return value. See
   `test/letflow/engine/lua_script_audit_test.exs` describe
   `"execute_script_for_audit/6 success path"`.
   Exists because: AC2 explicitly requires "verified by reading the row back" — a test
   asserting only the return tuple would pass even if the insert silently used the
   wrong `:prefix` or wrong column values.

2. **`instance_id` rejected before the executor is touched (AC3)** — two sub-cases,
   `instance_id: nil` and `instance_id: "not-a-uuid"` (malformed, non-UUID string),
   each against a raise-if-called executor double *and* a separate `Agent`-counted
   double; asserts `{:error, :invalid_instance_id}` and that the executor's callback
   count is exactly zero. See describe `"instance_id validated before executor
   invocation"`.
   Exists because: AC3's entire point is an *ordering* guarantee — a test that only
   checks the return value (without instrumenting the executor) cannot distinguish
   "validated first" from "validated after a wasted executor call," which is exactly
   the invariant INV-LSA-1 promises.

3. **Manifest-hash mismatch (AC4)** — a test-double executor returns
   `{:ok, %{manifest_hash: "actual-hash"}}` against `registered_hash: "different-hash"`;
   asserts `{:error, {:manifest_hash_mismatch, "different-hash", "actual-hash"}}` (the
   distinct, pattern-matchable 3-tuple, not a bare atom) and that zero rows exist in
   `lua_script_execution_audit` for that tenant schema afterward. See describe
   `"manifest hash mismatch"`.
   Exists because: AC4 requires both a *distinct* error shape (not conflated with
   `:invalid_instance_id` or a generic `:error`) and a *write-nothing* guarantee — the
   requirement text's own framing is that silently recording a mismatched hash as if
   trusted defeats the entire feature's purpose (INV-LSA-2).

4. **Missing/nil/empty `:prefix` fails closed (AC7 / INV-LSA-6)** — three sub-cases:
   `opts` with no `:prefix` key at all, `prefix: nil`, and `prefix: ""`; each against a
   raise-if-called executor double; asserts `{:error, :missing_prefix}`, that the
   executor is never invoked, and (via `Repo.all/2` scoped to a real provisioned
   tenant schema) that zero rows exist anywhere reachable. See describe `"missing or
   blank :prefix fails closed"`.
   Exists because: this behavior was added during INV-1 rework specifically because an
   earlier version of this fail-closed guard did not exist; the handoff explicitly
   calls out that it "must have its own test" rather than being incidentally covered
   by the AC2 happy path (which always supplies a valid prefix).

5. **Migration applies cleanly to a provisioned tenant schema (AC1)** — mirrors
   `test/letflow/engine/migrations_test.exs`'s established `provisioned_tenant/0`
   pattern (real `CREATE SCHEMA`, real `TenantProvisioning.replay_migrations/2`
   replay, `:auto`-mode sandbox, per-test schema drop in `on_exit/1`): asserts the
   `lua_script_execution_audit` table exists in the tenant's own schema and *not* in
   `public`, its column set matches `AuditRecord.__schema__(:fields)` exactly, the
   `idx_lua_script_execution_audit_instance` index exists, and the migration module is
   registered in `TenantProvisioning.tenant_scoped_migrations/0`. See describe
   `"migration applies to a provisioned tenant schema"`.
   Exists because: per the design doc §0/§6.3, a migration file with the `if prefix()
   do` guard that is *not* also registered in `@tenant_scoped_migration_manifest` is
   inert forever — this is the concrete, executable check that both halves are
   actually wired together, not just present as separate files.

6. **`mix.exs`/moduledoc guardrails (AC5, AC6)** — `Mix.Project.config()[:deps]`
   carries no dependency whose name matches a Lua/NIF-shaped pattern; the compiled
   module's `@moduledoc` (`Code.fetch_docs/1`) contains the S5-scope-deferral
   substance ("S5", `stage-5-scripting-plugins.md`) and the narrowness substance
   ("SERVICE_TASK", "supersedes"/"superseded"). See describe `"mix.exs and moduledoc
   guardrails"`.
   Exists because: AC5/AC6 are prose requirements on the moduledoc/dependency list, not
   on `execute_script_for_audit/6`'s runtime behavior — without a mechanical check, a
   future edit could silently strip the narrowness statement or add a Lua dependency
   and no other test in this file would catch it.
