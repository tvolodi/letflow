# Test Spec: REQ-059 — Dependency pin resolution, recording and inheritance
# (`pin_resolver.zig`, PIN-01/02/03/04)

**Requirement:** REQ-059 (stage S3). See `docs/requirements.yaml` REQ-059 entry for the
full verbatim text and `lib/letflow/design/req059-pin-resolver.md` §10 for the
acceptance-criteria → design-element traceability table this spec mirrors, one level
down to acceptance-criteria → test-case.

**Test tier:** pure-function unit tests (`Letflow.Engine.PinResolver` is a stateless
module of pure functions plus one Repo-reading call via
`Letflow.Engine.Reconstruction.read_full_log/3`, matching REVIEWER's own N/A finding on

per DIRECTIVE T-1) for every claim that can only be observed end to end (the actual
`INSTANCE_STARTED` payload shape, zero-row-write on failure, a genuine two-instance

**Modules under test:** `Letflow.Engine.PinResolver` (`lib/letflow/engine/pin_resolver.ex`)
and `Letflow.Engine.create/2`'s REQ-059 integration in `lib/letflow/engine.ex`
(`start_instance/5`'s new call order).

**Files:**

## Test-double strategy

Every lookup is an inline `%Letflow.Engine.PinResolver.Lookup{}` struct built per test,
following `test/letflow/definitions/service_scope_validator_test.exs`'s established
idiom for this codebase's injectable-lookup pattern:
- a **raise-if-called** lookup proves a call genuinely never happened (a passing test
  under a coincidentally-permissive stub could not distinguish "skipped" from "called
  and happened to succeed");
- a **`:counters`/`Agent`-backed call-counting** lookup proves an exact call count
  (needed for AC7's "issues zero reads" claim, and for the halt-on-first-unresolved-ref
  ordering claim) — a raise proves "not reached on this path," a counter proves "reached
  exactly N times," and REQ-059's own ACs need both techniques across different cases.

## Test cases

### AC1 — deterministic ordering, byte-identical serialized output

1. **Sort order is `{kind, ref}` ascending regardless of node order** — a graph whose
   `SUB_PROCESS`/`SERVICE_TASK` nodes are listed out of the expected final order;
   asserts the returned `pins` list's `ref`/`kind` sequence is
   `catalog_entry < module < variable_schema`, `ref` ascending within a kind. See
   `pin_resolver_test.exs` describe `"resolve/4 -- AC1: deterministic {kind, ref}
   ordering, byte-identical serialized output"`.
2. **Two resolutions of the same inputs produce byte-identical `Jason.encode!/1` output**
   — REQ-059's own AC1 wording, calls `resolve/4` twice against the identical
   graph/definition/lookup and asserts both `pins_1 == pins_2` and
   `Jason.encode!(pins_1) == Jason.encode!(pins_2)`.
3. **Duplicate `service_id` references across two `SERVICE_TASK` nodes produce exactly
   one entry** (§4.1's dedupe-by-ref rule).

Exists because: AC1 is explicitly about a *reproducibility* guarantee, not merely "some
order exists" — a test asserting only that the list is non-empty, or checking one
resolution's shape, would pass even if `sort_pins/1` were nondeterministic (e.g. keyed
by insertion order under a hash-map iteration that happened to look stable in one run).

### Overrides are verified against the lookup, never trusted verbatim

Revised 2026-08-20, GH#298 / ISS-0079,
`lib/letflow/design/iss-0079-pin-override-verification.md` — feeds AC1's own "source"
field; supersedes this section's original claim that overrides bypass the lookup entirely,
which was the defect that design fixed.

4. **A matching override — its `version` equal to what the lookup currently reports for
   that ref — is accepted, `source: :override`, with `resolved_id`/`version` taken from the
   lookup's own fresh result, never from the caller** (there is no `resolved_id` field on an
   override at all any more — R-Co's actual wire shape has none either).
5. **An override whose `version` does not match the lookup's current answer** returns
   `{:error, {:unresolved_pin_override, ref}}`, and the pin set is not partially built.
6. **An override naming a `{kind, ref}` the graph does not reference at all** (a stray) is
   the same error, checked once every real ref has already resolved successfully.
7. **A ref that fails to resolve at all reports its own `unresolved_catalog_ref`/
   `unresolved_module_ref`, never `unresolved_pin_override`**, even when an override was
   supplied for that exact ref — base resolvability is checked before override verification.
8. **`kind: module` overrides are verified the same way as `catalog_entry`, not
   special-cased to always fail** — a module override that verifies successfully is
   accepted; one under a lookup that can never resolve a module (e.g. `default_lookup/0`)
   fails as `unresolved_module_ref` with no special case needed to produce that outcome.

### AC5 halt-on-first-unresolved (also feeds AC2's "zero rows" via the integration test)

9. **An unresolvable `catalog_entry` ref halts immediately** — `{:error,
   {:unresolved_catalog_ref, ref}}`, and a `:counters`-backed lookup proves a *second*
   ref's `catalog_lookup` call never happens (the graph has two unresolvable refs; only
   the first is ever looked up).
10. **An unresolvable `module` ref returns the distinct `{:error, {:unresolved_module_ref,
    ref}}`** — a different tagged tuple from case 9, confirming the two error shapes
    really are distinguishable, not just differently worded.
11. **A halt on the module-ref step never reaches the (always-present) variable_schema
    lookup** — proves the whole-function halt, not just a per-kind halt.

Exists because: PIN-01's design (§4.1) states resolution "halts entirely," never
returning a partial list — a test that only checks the final error value cannot
distinguish "halted before ever calling the second lookup" from "called it, discarded
the result, and returned the first error anyway," which matters because the discarded
call could have side effects in a real (non-test) lookup implementation.

### PIN-02 AC4 — zero catalog/module refs still record exactly one `variable_schema` entry

12. **A graph with no `SERVICE_TASK`/`SUB_PROCESS` nodes at all still produces exactly
    one `pinned_version`, `kind: :variable_schema`** — a raise-if-called catalog/module
    lookup proves the zero-refs case never spuriously calls either.
13. **A reference attribute that is absent, `nil`, empty-string, or non-string
    contributes nothing** (mirrors `ServiceScopeValidator`'s own INV-SSV-3 non-empty-string
    gate, reused per the design's §1 citation) — still exactly one `variable_schema` entry.

Exists because: AC4's literal wording is "still records exactly one variable_schema
entry" — the "unconditionally" claim is only proven by a test that supplies a graph
genuinely producing zero catalog/module pins, not by a test that happens to also have
a `SERVICE_TASK` node (which would leave "zero-refs" case unexercised).

### AC3 — initial variable validation reuses REQ-024's validator, lists every failing field

14. **`nil` `variable_json_schema` is `:ok` unconditionally** — the `default_lookup/0`
    case, whatever the variables are.
15. **Variables violating multiple constraints are rejected listing EVERY failing
    field** — a schema with two independent violations (`required` + `minimum`);
    asserts `length(failures) == 2` and that each specific `field_path`/`constraint`
    pair is present, not just that *some* error occurred.
16. **Conforming variables pass against a real resolved schema.**
17. (integration) **The same violating-variables case end to end through `Engine.create/2`**
    — a custom `pin_lookup` supplying a real JSON Schema via `attrs[:pin_lookup]`,
    asserting `{:error, {:variable_schema_violation, failures}}` with both failing
    fields present AND zero rows written (projection/snapshot/event) — proving the
    reordering (design doc §3 step 3, before `create_snapshot/3`) holds at the real
    `Engine.create/2` call site, not just at `validate_initial_variables/2`'s own unit
    level.

Exists because: AC3 explicitly says "listing each failing field" (plural) — a test
supplying only a single-constraint schema could pass even if the implementation
short-circuited after the first `ValidationFailure`, which would be indistinguishable
from `JsonSchema.validate/2`'s real collecting behavior on a single-violation input.

### AC2 — a failed resolution writes zero rows anywhere (integration, real Postgres)

18. **An unresolvable `service_id` (the `default_lookup/0` a caller supplying no
    `pin_lookup` gets) returns `{:error, {:unresolved_catalog_ref, ref}}` and leaves
    `instance_projections`/`instance_definition_snapshots`/`tokens`/`events` all at
    zero rows** — read back all four counts independently after the call, not just
    trusting the return tuple.
19. **The already-shipped "resolvable pin, later activation failure" case is
    unaffected by the reordering** — a `SERVICE_TASK` node with a *resolvable*
    `service_id` (custom `pin_lookup`) still reaches `create_snapshot/3` (the benign
    1-row snapshot orphan `test/letflow/engine_test.exs:580`'s own pre-existing test
    documents) before `activate/3`'s own, REQ-059-independent
    `:node_type_not_yet_implemented` dispatch failure. This is the *contrast* case that
    proves case 18's zero-snapshot-rows result comes specifically from pin resolution
    failing *before* `create_snapshot/3`, not from some unrelated always-zero
    invariant.

**No integration-level "unresolvable `module_ref`" counterpart exists.**
`Letflow.Definitions.Graph`'s own `@node_type_map` (`graph.ex:203-211`) does not include
`"SUB_PROCESS"` at all yet — a `"SUB_PROCESS"` node built through `Definitions.create/2`'s
real JSON-graph path silently becomes `:unknown_node_type`, not `:SUB_PROCESS`, so
`PinResolver`'s own `node.node_type == :SUB_PROCESS` filter can never match a
real-pipeline-built node. This is confirmed by having written and run exactly that test
first: it failed with `{:activation_failed, {:node_type_not_yet_implemented,
:unknown_node_type, "sub"}}`, not the expected `unresolved_module_ref`, proving
`resolve/4`'s `module` branch is unreachable through the real pipeline today — a
Graph-level gap one layer beneath REQ-059's own already-documented SCOPE GAP
(service_catalog/PLC-01 not existing), not something REQ-059 introduces or is
responsible for fixing. The module_ref halt-on-unresolved behavior (case 10 above) is
still fully covered at the pure-function level against a hand-built
`%Node{node_type: :SUB_PROCESS}` struct, which is the only way to construct one today.
`docs/anti-patterns.md` is a candidate location for this finding if a future requirement
adds real `SUB_PROCESS` support and rediscovers the same gap.

### AC4 — `INSTANCE_STARTED` payload carries `pinned_versions`; no separate pin table

20. **A zero-refs definition's real `INSTANCE_STARTED` event payload carries exactly one
    `pinned_versions` entry, `kind: "variable_schema"`, and no `pin_conflicts` key at
    all (root instance)** — read via `Reconstruction.read_full_log/3` against the real
    tenant schema after a real `Engine.create/2` call, not asserted against a return
    value alone.
21. **No `priv/repo/migrations/*.exs` file creates a pin-shaped table** — a filesystem
    grep across every migration file for a `create table(...)` call whose table name
    matches `pin`, asserting the list is empty. This is the concrete, mechanical check
    for PIN-02 AC3's "no separate pin table exists anywhere in
    `priv/repo/migrations`" — a prose-only reading of the requirement could not catch a
    future migration silently reintroducing one.

### AC6 — child instance pin inheritance and conflict recording (integration)

22. **A child started from a parent with a differing pin inherits the PARENT's version
    and records the conflict** — uses the *always-present* `variable_schema` pin (not a
    `SERVICE_TASK`/`SUB_PROCESS` reference, sidestepping the Graph-level gap noted
    above) as the shared `{kind, ref}` both parent and child genuinely produce for the
    same definition: the parent is created with `pin_overrides` fixing its
    `variable_schema` version to `"parent-v1"`; the child is created with
    `attrs[:parent_instance_id]` set to the parent's real `instance_id` and no override
    of its own (so its own resolution produces `"unversioned"`, the `default_lookup/0`
    value). Reads the child's real `INSTANCE_STARTED` payload and asserts
    `pinned_versions` carries `version: "parent-v1"`, `source: "inherited"`, and
    `pin_conflicts` carries the one conflict record with `child_resolved_version:
    "unversioned"`/`inherited_version: "parent-v1"`. Also asserts the *parent's own*
    payload has no `pin_conflicts` key at all (root instance).
23. **A child agreeing with its parent's pin has zero conflicts, but `pin_conflicts: []`
    is still present** — distinguishing "child, zero conflicts" from "root, no parent"
    by payload shape alone, per design doc §7's explicit rule.

Exists because: this is the one REQ-059 AC that requires genuinely threading two real
instances' event logs together (`parent_pins/2` → `PinResolver.reconstruct_effective_pins/2`
against the parent's *actual* appended `INSTANCE_STARTED` event) — a pure
`apply_inheritance/2` unit test (also present, see below) proves the merge algorithm is
correct in isolation, but not that `Engine.create/2`'s own `attrs[:parent_instance_id]`
wiring (`engine.ex`'s `parent_pins/2` helper) actually reaches it end to end.

### AC7 — replay derives pins from events only, zero catalog/module reads (integration + pure)

24. **`reconstruct_effective_pins/2`, called after a real `create/2` whose own
    `pin_lookup` is call-counted (`Agent`-backed), never increments that counter** — the
    counter sits at `1` after `create/2` itself (the one unconditional
    `variable_schema_lookup` call every instance makes); calling
    `reconstruct_effective_pins/2` afterwards leaves the counter unchanged, since that
    function's own 2-arity signature (`instance_id`, `opts`) has no `Lookup.t()`
    parameter to reach the counter through at all — the strongest available proof, per
    the design doc §6's own note that AC7 "is satisfied by construction."
25. **`reconstruct_effective_pins/2` on an instance with no events returns `{:error,
    :instance_not_found}`.**
26. (pure) **`merge_effective_pins/2` with zero rebind events mirrors the base set
    exactly**; **a single rebind event updates only the matching `{kind, ref}` entry**,
    leaving `kind`/`resolved_id`/`source` on every other entry untouched; **ALL rebind
    events are folded in order, not just the most recent** (design doc §6 OQ-2 — an
    earlier rebind of one ref is not lost by a later, unrelated rebind of a different
    ref).

### AC5 — `PinMissing` error, no fallback (runtime + inspection)

27. **`pin_for/3`**: a present `{kind, ref}` is found; an absent one returns
    `{:error, {:pin_missing, kind, ref}}` naming the exact kind/ref, never a substitute
    value; an empty pins list never raises.
28. **Inspection-based**: the raw source of `lib/letflow/engine/pin_resolver.ex` is
    split at `"def merge_effective_pins("` (the first function, in file order, after
    `resolve/4`'s own body) and everything from that point on (`merge_effective_pins/2`,
    `reconstruct_effective_pins/2`, `apply_inheritance/2`, `pin_for/3`) is asserted to
    contain neither the substring `"catalog_lookup"` nor `"module_lookup"` anywhere.
    A second assertion counts the literal occurrences of `lookup.catalog_lookup` and
    `lookup.module_lookup` across the *whole* file and asserts each is exactly `1` —
    the one legitimate call site inside `resolve/4` itself.

Exists because: AC5 literally says "confirmed by inspection," not just "confirmed by
running some inputs through it" — a purely behavioral test (however many cases) can
only ever sample the input space; it cannot prove the negative "no code path anywhere
does X" the way a source-text assertion can. Case 28 is the load-bearing evidence for
that negative claim; case 27 is the ordinary behavioral coverage of the one function
this whole guarantee is actually about.

### PIN-04 AC2/AC3 — `apply_inheritance/2` (pure)

29. `parent_pins == nil` (root instance) → `own_pins` unchanged, `[]` conflicts.
30. A parent pin absent from `own_pins` is added, `source: :inherited`, no
    `source_event_id` on the fresh entry (it's a read-side-only field per the design's
    own type distinction), no conflict.
31. Matching versions on both sides → kept as-is, no conflict ("agreement is not
    inheritance," design doc §7).
32. Differing versions → **inherited wins**, `source: :inherited`, and a `conflict()`
    record naming both `child_resolved_version`/`inherited_version` correctly (not
    swapped — this is REQ-059's own text calling out "easy to get backwards").
33. Inheritance wins even over a child's own `:override` source (design doc §7 OQ-6 —
    no override exception, the literal reading of "inheritance wins").
34. The merged result is re-sorted per `resolve/4`'s own `{kind, ref}` ordering after
    inherited additions (inherited entries must not break AC1's ordering guarantee).

### AC8 — moduledoc names the SCOPE GAP, cites ISS-0672/GH-306

35. The moduledoc names `service_catalog`, attributes it to stage S6; names `PLC-01`,
    states it is unscoped; cites `ISS-0672` and `GH-306`; states unresolvable
    references return typed errors rather than a stub. Uses
    `service_scope_validator_test.exs`'s established `normalized_moduledoc/1` helper
    (`Code.fetch_docs/1` + whitespace normalization) — a local copy per that file's own
    established convention of not sharing one across test files.
