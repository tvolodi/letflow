## Event-type registration (ISS-0071/GH#257)

Per REVIEWER's finding on this run (`handoffs/WF02-REQ060-20260819/step-02d-reviewer.json`),
`EventStore.append/2` rejects any event type not already registered via
`Registry.register_type/2`, and no production code path registers
`"INSTANCE_PINS_REBOUND"` — the same pre-existing gap `"TASK_COMPLETED"`/
`"INSTANCE_CANCELLED"` already have. `provisioned_tenant/0` below registers
`"INSTANCE_PINS_REBOUND"`, `"INSTANCE_CANCELLED"` (needed for the AC3 CANCELLED case)
and `"EXECUTION_ERROR"` (needed for the AC3 ERROR case) itself, exactly mirroring
`test/letflow/engine_cancel_instance_test.exs:63-97`'s established
`register_event_type!/2` pattern. `"INSTANCE_STARTED"` is auto-seeded by
`TenantProvisioning.replay_migrations/2` and needs no explicit registration.

## Pin fixture strategy

`Letflow.Definitions.Graph`'s own node-type map has no dispatchable `SERVICE_TASK`/
`SUB_PROCESS` implementation yet (REQ-059's own test suite already documents this —
`test/letflow/engine_test.exs:1006-1020`), so a `catalog_entry`/`module` pin can never
survive a real `Engine.create/2` call through the public pipeline: pin resolution
would succeed, but the subsequent node-activation step always fails first
(`:node_type_not_yet_implemented`), aborting the whole `Ecto.Multi` and leaving no
instance to rebind against. Every fixture below therefore rebinds the `variable_schema`
pin (`kind: :variable_schema`, `ref: definition.name`) — the one pin kind every
instance carries unconditionally (PIN-02 AC4) — using `pin_overrides` at `Engine.create/2`
time to fix its starting version deterministically. This does not narrow AC coverage:
`PinRebind.rebind_pins/3`'s own per-entry logic (`resolve_entries_against_effective_pins/2`,
`compute_changed_entries/2`) is generic over `kind` — it never branches on it — so
exercising it against `:variable_schema` entries exercises the same code path a
`:catalog_entry`/`:module` entry would.

## Test cases

### AC1 — exactly one event, correct payload shape, no-op entries omitted

**Requirement text:** "a valid rebind on a running instance appends exactly one
INSTANCE_PINS_REBOUND event carrying ref, prior_version, new_version, actor and reason
for each CHANGED entry, and an entry whose requested version already matches
contributes no payload entry."

1. **A single changed entry appends exactly one event whose payload's `entries` list
   has exactly one member carrying `kind`, `ref`, `prior_version`, `new_version`,
   plus top-level `actor` and `reason`** — read the event back via
   `Reconstruction.read_full_log/3`, not just trust `rebind_pins/3`'s return value,
   since the return value and the durable payload are built by separate code
   (`interpret_rebind_result/3` vs. `append_pins_rebound_event/6`) and could drift.
2. **A no-op entry (requested version == current version) still returns `{:ok, %{changed:
   []}}}`, still appends exactly one event, but that event's payload `entries` list is
   empty** — proves "contributes no payload entry" is a per-entry filter, not "the whole
   rebind is skipped when nothing changed" (design doc §9 OQ-3, restated in the
   moduledoc's M6 comment: "exactly one event is always appended on a successful, valid,
   in-range rebind call").

Exists because: a test that only checks the returned `changed` list could pass even if
`append_pins_rebound_event/6` accidentally included unchanged entries in the durable
payload (a real bug: a future `PinResolver.merge_effective_pins/2` reader would then see
a spurious version-that-never-changed entry) — reading the raw event payload is the only
way to catch that.

### AC2 — UnknownPinRef rejects the WHOLE request, zero writes, even with individually-valid entries

**Requirement text:** "a rebind naming a ref absent from the current effective pin set
returns a distinct UnknownPinRef error and applies NONE of the entries — verified by
reading the effective pin set back and confirming it is unchanged, including for the
entries that were individually valid."

3. **A request with one individually-valid entry (real ref, differing version) ordered
   BEFORE one entry naming a ref absent from the effective pin set** returns
   `{:error, {:unknown_pin_ref, kind, ref}}`; `PinResolver.reconstruct_effective_pins/2`
   read back afterwards shows the ORIGINAL version for the valid entry's ref (not the
   requested new version), and the raw event log has zero `INSTANCE_PINS_REBOUND`
   events (`event_count/1`-style row count, not just "no error was silently absorbed").

Exists because: `resolve_entries_against_effective_pins/2` processes entries via
`Enum.reduce_while/3` in list order — placing the valid entry first is the only way to
prove the module does a full pre-pass across every entry (or otherwise correctly
aborts before any write) rather than "committing" earlier entries as it goes and only
failing to reach the invalid one; reading the pin set back (not just checking the
return tuple) is what "applies NONE" actually means operationally.

### AC3 — InstanceNotRebindable, all three terminal statuses tested individually

**Requirement text:** "a rebind against a COMPLETED, CANCELLED or ERROR instance
returns a distinct InstanceNotRebindable error, with each of the three statuses
tested."

4. **COMPLETED** — a `START -> END` graph completes inside `Engine.create/2` itself
   (`graph_start_end/0`, mirrors `engine_test.exs:407-423`'s own fixture); rebind
   returns `{:error, {:instance_not_rebindable, :completed}}`.
5. **CANCELLED** — an active instance is cancelled via `Engine.cancel_instance/3`
   (REQ-052); rebind returns `{:error, {:instance_not_rebindable, :cancelled}}`.
6. **ERROR** — an active instance is moved to `:error` via `Engine.set_instance_error/2`
   (REQ-061); rebind returns `{:error, {:instance_not_rebindable, :error}}`.

Exists because: `check_rebind_eligibility/1` is a hand-written three-way `case`, not a
reuse of `InstanceProjection.terminal?/1` (which excludes `:error` — REVIEWER's own
sign-off note) — a test suite that only exercised COMPLETED/CANCELLED (the set
`terminal?/1` itself would accept) could not catch a regression that silently switched
`check_rebind_eligibility/1` back to calling `terminal?/1`. Each status gets its own
test rather than one parameterized case so a single regression's failing status is
immediately nameable from the test name alone.

### AC4 — missing/empty reason, empty entries list, malformed entry: three distinct errors

**Requirement text:** "a rebind with a missing or empty reason, an empty entries list,
and a malformed entry each return a distinct invalid-input error."

7. **Missing `:reason` key** returns `{:error, :invalid_reason}`.
8. **Empty-string / all-whitespace `:reason`** returns the SAME `{:error, :invalid_reason}`
   (design doc §4 M0.3 collapses both into one atom — asserted explicitly so a reader
   does not expect two different atoms).
9. **Missing `:entries` key** returns `{:error, :empty_entries}`.
10. **Empty `:entries` list (`[]`)** returns the SAME `{:error, :empty_entries}`.
11. **A malformed entry (missing `:version` key)** returns
    `{:error, {:malformed_entry, 0, :missing_or_unexpected_keys}}` — index-tagged.
12. **A malformed entry (invalid `:kind` value)** returns
    `{:error, {:malformed_entry, 0, {:invalid_kind, "bogus"}}}` — a second, distinctly-
    shaped malformed-entry reason, proving `:malformed_entry` itself is not a single
    hardcoded reason.

Exists because: AC4's own wording ("each return a distinct invalid-input error") is a
three-way distinctness claim (`:invalid_reason` vs. `:empty_entries` vs.
`{:malformed_entry, ...}`) — a test checking only one of the three could not catch a
regression that collapsed two of them onto the same atom. Cases 8/10 close the "missing
vs. empty are the same condition" half of the claim, which cases 7/9 alone do not cover.

### AC5 — post-rebind effective pin set, and reconstruction from the event log alone

**Requirement text:** "after a rebind, REQ-059's effective pin set reflects the new
versions and REQ-053's reconstruction derives the same set from INSTANCE_STARTED plus
INSTANCE_PINS_REBOUND, with no catalog read."

13. **`PinResolver.reconstruct_effective_pins/2` called after a successful rebind
    returns the NEW version for the rebound ref**, `source` and other fields otherwise
    intact.
14. **The same result is independently reproducible by hand from the raw event log**:
    read `INSTANCE_STARTED` and `INSTANCE_PINS_REBOUND` via
    `Reconstruction.read_full_log/3` directly, call `PinResolver.merge_effective_pins/2`
    on the two extracted payload lists manually, and assert the result equals case 13's
    `reconstruct_effective_pins/2` result — demonstrating the effective set really is a
    pure fold over exactly those two event types (design doc / moduledoc's own
    "Reconstruction/PinResolver reuse" claim), not some other, undocumented data path.
15. **`rebind_pins/3`'s own `rebind_attrs()` typespec and pre-transaction argument
    handling accept no catalog/module lookup of any kind** (confirmed by inspection —
    `attrs` has exactly `:entries`/`:reason`/`:actor_id`/`:idempotency_key`, no
    `:pin_lookup` field, unlike `Engine.create/2`'s own `attrs[:pin_lookup]`) — the
    "zero catalog reads" half of AC5 is a structural property, not merely an observed
    absence of calls in one run; stated explicitly here rather than left implicit.

Exists because: REQ-059's own AC7 test (`engine_test.exs:1185-1222`) proves "zero
catalog reads" for `create/2` via a call-counting `Lookup` stub — no such stub is
possible for `rebind_pins/3` because it never accepts a `Lookup` at all, so this spec
proves the equivalent claim the only way available: by tracing the exact two event
types the effective set is rebuilt from and confirming no lookup parameter exists to
call through in the first place.

### AC6 — lock contention surfaces as ConcurrentModification; moduledoc names ERROR as PIN-05's "FAILED"

**Requirement text:** "lock contention surfaces as a distinct ConcurrentModification
error rather than blocking, and the moduledoc states that ERROR (not a non-existent
FAILED status) is the terminal status PIN-05's text refers to."

16. **A real second Postgres connection holds a plain `FOR UPDATE` lock on the
    instance's `instance_projections` row; a concurrent `rebind_pins/3` call against
    the SAME instance returns `{:error, {:concurrent_modification, instance_id}}`
    immediately (not after blocking)** — genuine two-`Task.async`-process race, Sandbox
    mode `:auto` (real, separate connections), mirroring
    `test/letflow/engine/reconstruction_test.exs`'s `with_locked_projection/3` and
    `test/letflow/engine_execution_error_test.exs`'s AC5 concurrency shape exactly. The
    test asserts the call returns promptly (bounded `Task.await/2` timeout well under
    the lock holder's own hold duration) as the "rather than blocking" half of the
    claim, and confirms the row's `variables`/`current_nodes` are unchanged afterwards
    as the "no silent overwrite" half.
17. **Moduledoc inspection**: `Code.fetch_docs(Letflow.Engine.PinRebind)` contains
    `PIN-05's own requirement text says "FAILED"`, `` `ERROR` is the status PIN-05's
    text means ``, and `` counts as **terminal for rebind purposes specifically** `` —
    mirrors `engine_test.exs`'s own `normalized_moduledoc/1` idiom (whitespace-collapsed
    substring match) for AC5/AC6/AC7 moduledoc-content assertions there.

Exists because: a unit-level assertion that `lock_projection_nowait/2`'s rescue clause
maps `%Postgrex.Error{postgres: %{code: :lock_not_available}}` to
`{:concurrent_modification, id}` would prove the mapping is correct in isolation but
NOT that Postgres actually raises `lock_not_available` (SQLSTATE `55P03`) for this
exact query/lock combination against this exact schema — only a genuine two-connection
race against the real `instance_projections` table proves the whole path end to end,
matching this codebase's own established precedent for every other NOWAIT claim
(`reconstruction_test.exs`'s AC5, `engine_execution_error_test.exs`'s AC5). The
moduledoc check is a separate, deliberately literal assertion because AC6's own wording
names a specific documentation obligation, not just a behavioural one — a test that only
verified the behavior could pass even if a later edit accidentally deleted or garbled
the naming-mismatch explanation.
