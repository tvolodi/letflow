## CONFIRMED GAP — read this before any AC below

While building AC1/AC4's tests, direct execution against real Postgres (not the design
doc's own claims) showed `complete_task/3`'s rewired REQ-050 call site does not actually
intercept the realistic case. Traced precisely, confirmed by both code read and running
code:

1. `dispatch_task_completion_hop_chain/5`'s own rewired `{:no_matching_edge, ...}` clause
   (`lib/letflow/engine.ex` ~line 1157) only fires for a no-match on the **completing
   task's own** outgoing edges (`Transition.dispatch_task_completion/4`, dispatched for
   the literal `{:complete_task, token_id}` event). A no-match discovered on a **later**
   hop — e.g. an `:EXCLUSIVE_GATEWAY` one hop downstream of the completing task, which is
   REQ-050's own actual scenario and the shape any real process definition would use — is
   discovered by `advance_until_stable/4`'s own internal worklist loop instead
   (`{:advance_token, token_id}` events), a separate code path whose `{:error, reason}` is
   wrapped `{:error, {:activation_failed, reason}}` (line 383) and returned completely
   **unrewired** — the transaction still aborts, exactly the pre-REQ-061 bug.
2. The one scenario where the rewired clause *does* fire directly (a `:HUMAN_TASK` whose
   own edges fail to resolve) is structurally unreachable through the public API:
   `Letflow.Definitions.create/2` runs `Graph.validate_edge_conditions/1` (CHK-19,
   `check_human_task_fallback_edge/1`) before any row is written, which rejects a
   `:HUMAN_TASK` with a really-conditioned edge and no fallback — confirmed directly by
   calling `Graph.validate_edge_conditions/1` on such a graph
   (`%{valid: false, violations: [%{code: :human_task_no_fallback_edge, ...}]}`). A
   zero-outgoing-edges `:HUMAN_TASK` is independently rejected by `validate_graph/1`'s
   `check_isolated_nodes/1` (`:isolated_node`).
3. `merge_output_variables/5` (REQ-049's own call site) calls `VariableMerge.merge(current,
   output, nil)` — the third argument, `variable_validations`, is a literal `nil` always.
   `VariableMerge.merge/3`'s `find_rejection/2` can only produce `{:rejected, ...}` when a
   key's own `variable_validations` entry is `{:rejected, failures}`; with `validations`
   always `%{}`, that branch is unreachable. `merge_output_variables/5` is also `defp` —
   confirmed via `Letflow.Engine.module_info(:exports)` (empty for that name) — so it
   cannot be unit-tested directly either.

**Net effect:** neither of REQ-061's own two "currently-shippable" callers (REQ-049,
REQ-050) is actually reachable end-to-end through `Engine.complete_task/3`'s public API
for a realistic process definition. REVIEWER's AC4 sign-off ("2 of 2 currently-shippable
callers wired") assumed both were reachable; this test-design pass found that assumption
false for both. **This is a confirmed defect in the shipped `complete_task/3` rewiring,
not a gap in the shared sink itself** — `ExecutionError.append_multi/3` and
`Engine.set_instance_error/2` (the sink and its standalone entry point) work correctly
and are both fully, genuinely reachable via the public API; every test below that needs a
real EE-10 trigger uses `set_instance_error/2` for that reason, with `AC4a` isolating and
demonstrating the `complete_task/3`-specific defect on its own.

Flagged in this run's handoff `result.issues` for ORCH to route (recommended: back to
CODE-DESIGNER/ELIXIR-DEV for `complete_task/3`'s own rewiring — the fix likely needs
`advance_until_stable/4`'s own `{:error, reason}` branch to route the `{:no_matching_edge,
...}` case into `ExecutionError.append_multi/3` too, not just the first hop's).

## AC1 — EXECUTION_ERROR event carries error type, affected node/field, reason, variables

**Requirement text:** "an EXECUTION_ERROR event carries error type, affected node or
field, a human-readable reason, and the instance variable map as it stood at the moment
of the error -- all four verified by reading the event payload back."

**Test case:** `AC1 -- set_instance_error/2 appends one EXECUTION_ERROR event` /
`"the event payload carries error_type, affected, reason, and the variable snapshot"`.
Starts an instance, calls `Engine.set_instance_error/2` with a REQ-050-shaped
`error_type: :no_matching_gateway_edge`/`affected: {:node, "gw"}` payload, then reads the
`EXECUTION_ERROR` event row back directly from `events` (not the in-memory `{:ok, result}`
alone) and asserts all four AC1 fields: `error_type`, `affected` (`%{"kind" => "node",
"node_id" => "gw"}`), `reason` (contains the gateway id and "no outgoing edge matched"),
and `variables` (the exact snapshot map passed in, read back verbatim). Also cross-checks
`instance_projections.error_detail` carries the same `error_type`/`affected`.

**Why this case, not `complete_task/3` directly:** the CONFIRMED GAP above means a
`complete_task/3`-driven trigger for this exact scenario does not reach
`ExecutionError.append_multi/3` at all today — testing the payload shape via
`set_instance_error/2` (the one genuinely reachable public entry point into the same sink)
is the honest way to prove AC1 holds for the sink itself, which is what AC1 is actually
about (payload shape), not about which caller reached it.

## AC2 — status flip and EXECUTION_ERROR append commit together (atomicity)

**Requirement text:** "the status flip to ERROR and the EXECUTION_ERROR append commit
together: forcing the append to fail leaves the instance status unchanged, verified by
reading both back."

**Test case:** `AC2 -- forcing the EXECUTION_ERROR append to fail leaves status
unchanged` / `"an unregistered EXECUTION_ERROR event type rolls back the whole
transaction"`. A tenant that never registers `"EXECUTION_ERROR"` in
`event_type_registry` forces `EventStore.append/2`'s own `Registry.validate_payload/3`
call to fail with `:unknown_event_type` inside `ExecutionError.append_multi/3`'s
`:execution_error_event` step — which, per `Ecto.Multi`'s own documented semantics, aborts
and rolls back the entire enclosing transaction. Asserts, read back independently:
`instance_projections.status` is still `:active` (not `:error`), `error_detail` is `nil`,
and the tenant's `events` row count is unchanged. Proves INV-EE61-1/INV-EE61-5 (the event
step runs before the projection-update step, same transaction) rather than assuming it
from the code's own ordering comment.

## AC3 — an instance in ERROR rejects task completion with a distinct conflict

**Requirement text:** "an instance in ERROR rejects task completion with a distinct
conflict error and remains in ERROR afterwards."

**Test case:** `AC3 -- complete_task/3 against an ERROR instance` / `"returns {:error,
{:instance_not_active, :error}}, instance and task untouched"`. Per the design doc §6,
this is already-shipped REQ-048 behavior (`fetch_and_lock_instance_projection/3`'s own M2
check, unmodified by REQ-061) — this test exists to confirm that claim against real code,
not to exercise new logic. Uses `set_instance_error/2` to reach `:error` (independent of
the AC4a defect, since `set_instance_error/2` doesn't depend on the broken
`complete_task/3` rewiring), then calls `complete_task/3` against the instance's own still-
`:pending` task. Asserts the distinct third-element conflict shape
(`{:instance_not_active, :error}`, distinguishable from `:completed`/`:cancelled`), that
the instance is still `:error` afterward, and that the task row is untouched
(`status: :pending`) — the rejected call performed zero writes.

## AC4 — REQ-049 and REQ-050 both route through the shared sink (interim scope, per
REVIEWER's sign-off) — see the CONFIRMED GAP above for what this test design actually
found

**Requirement text:** "at least the two currently-shipped calling paths (REQ-049 schema
violation, REQ-050 gateway no-match) are demonstrated routing into
set_instance_error/append_multi rather than writing their own ERROR transition, confirmed
by test."

**Test case A (the confirmed defect, stated plainly):** `AC4a -- CONFIRMED GAP: REQ-050's
realistic downstream-gateway no-match` / `"complete_task/3 still aborts unrewired, zero
ERROR state persisted"`. Starts an instance on `task(HUMAN_TASK) -> gw(EXCLUSIVE_GATEWAY)`
where `gw`'s own edges can never match and carry no default — the realistic shape REQ-050
itself describes. Completes `task`; asserts the return value is the **pre-REQ-061** shape
(`{:error, {:activation_failed, {:no_matching_edge, "gw", _}}}`), not the promised
`{:error, {:instance_execution_error, :no_matching_gateway_edge, _}}`, and that
`instance_projections.status` stays `:active`, `error_detail` stays `nil`, the `events`
count is unchanged, and the task stays `:pending`. This test passes today because it
correctly documents the *actual* shipped behavior — it is not an assertion that AC4 is
satisfied for this scenario.

**Test case B (what does hold — the shared-sink claim, isolated from the trigger
mechanism):** `AC4b -- REQ-049's and REQ-050's own error_args() shapes, same sink
function` / `"set_instance_error/2 commits status:error identically for both error_type
values"`. Builds the exact `error_args()` shapes `merge_output_variables/5`'s own
rejection clause (`lib/letflow/engine.ex` lines 1093-1106) and
`dispatch_task_completion_hop_chain/5`'s own rewired clause (lines 1157-1170) would each
construct — verbatim, field for field — and passes each through
`Engine.set_instance_error/2` on its own instance. Both commit `status: :error` with the
correct `error_type` in both the projection and the `EXECUTION_ERROR` event payload, and
`ExecutionError.__info__(:functions)` confirms `append_multi/3` (the one function both
calls necessarily route through, since `set_instance_error/2`'s own body calls nothing
else to reach `ERROR`) exists as a single arity-3 export. This is the one part of AC4's
"same code path, not two implementations" claim that is genuinely checkable given the
confirmed gap: the **sink** is unified even though neither trigger reaches it via
`complete_task/3` today.

## AC5 — two concurrent EE-10 triggers on one instance: exactly one commits, one rejected

**Requirement text:** "two concurrent operations both triggering EE-10 on the same
instance result in exactly one committed EXECUTION_ERROR and one rejection, run
concurrently rather than sequentially."

**Test case:** `AC5 -- two concurrent set_instance_error/2 calls target the same
instance` / `"exactly one commits EXECUTION_ERROR, the other observes
{:instance_already_error, _}"`. Two `Task.async` processes, each its own Postgres
connection (Sandbox `:auto`, matching `engine_cancel_instance_test.exs`'s own AC4 race
precedent), call `Engine.set_instance_error/2` against the **same** `instance_id`
simultaneously. Asserts exactly one `{:ok, _}` and exactly one `{:error,
{:instance_already_error, _}}` among the two results, that
`instance_projections.status` ends `:error`, and that exactly one `EXECUTION_ERROR` event
was ever appended (INV-EE61-3) — the loser wrote nothing. This exercises the general
row-lock-queueing mechanism `ExecutionError.append_multi/3`'s own `:execution_error_
eligibility` step implements (design doc §3), the part of AC5 that is genuinely reachable;
the design doc's own §5.5 traces a `complete_task/3`-specific version of this same race,
which inherits AC4a's defect and cannot itself be exercised end to end today.
