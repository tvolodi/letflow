## STATUS (post rework iteration 1) — read this before any AC below

Test-design's original pass (see git history of this file for the prior "CONFIRMED GAP"
text) found that `complete_task/3`'s rewired REQ-050 call site did **not** intercept the
realistic downstream-gateway scenario. That finding was real and is now fixed:

1. `dispatch_task_completion_hop_chain/5`'s rewired `{:no_matching_edge, ...}` clause
   originally only fired for a no-match on the **completing task's own** outgoing edges
   (`Transition.dispatch_task_completion/4`). A no-match discovered on a **later** hop —
   e.g. an `:EXCLUSIVE_GATEWAY` one hop downstream of the completing task, which is
   REQ-050's own actual scenario and the shape any real process definition would use — is
   discovered inside `advance_until_stable/4`'s own internal worklist loop instead, whose
   `{:error, reason}` is wrapped `{:error, {:activation_failed, reason}}`. That branch was
   previously returned unrewired, aborting the transaction (the pre-fix bug).
2. **Fixed in commit `d91e97d`** ("fix(REQ-061 rework 1): route downstream-hop
   no_matching_edge into ExecutionError sink"): `dispatch_task_completion_hop_chain/5`
   (`lib/letflow/engine.ex`, inside the `case advance_until_stable(...)` block) gained a
   clause matching `{:error, {:activation_failed, {:no_matching_edge, node_id,
   evaluated_conditions}}}` — the exact shape `advance_until_stable/4`'s internal loop
   produces for a downstream gateway no-match. That clause now builds the same
   `error_args()` shape (`error_type: :no_matching_gateway_edge`, `affected: {:node,
   node_id}`, the evaluated conditions, the variable snapshot) and returns `{:ok,
   {:execution_error, error_args}}`, routing it into the same `ExecutionError.
   append_multi/3` sink as every other EE-10 trigger, instead of aborting the `Multi`.
3. `merge_output_variables/5` (REQ-049's own call site) still calls
   `VariableMerge.merge(current, output, nil)` — the third argument,
   `variable_validations`, is a literal `nil` always, so `VariableMerge.merge/3`'s
   `find_rejection/2` can never produce `{:rejected, ...}`. This is a **separate,
   pre-existing gap in already-shipped REQ-049 code** (not introduced or touched by
   REQ-061), filed as `docs/issues/ISS-0063.yaml` (GitHub #212) and explicitly out of
   scope for REQ-061's own rework, per REVIEWER's sign-off in
   `handoffs/WF02-REQ061-20260819/step-02d-reviewer-rework1.json`. `merge_output_
   variables/5` is also `defp` — confirmed via `Letflow.Engine.module_info(:exports)`
   (empty for that name) — so it cannot be unit-tested directly either; it remains
   demonstrable only indirectly, via `ExecutionError.append_multi/3` fed the same
   `error_args()` shape (test `AC4b`).

**Net effect:** REQ-050's downstream-gateway no-match scenario is now genuinely fixed and
demonstrated end-to-end through `Engine.complete_task/3`'s public API — test `AC4a`
(`test/letflow/engine_execution_error_test.exs`) asserts the fixed behavior: `complete_
task/3` returns `{:error, {:instance_execution_error, :no_matching_gateway_edge, {:node,
"gw"}}}`, the instance projection lands in `status: :error` with `error_detail` set, an
`EXECUTION_ERROR` event is durably appended (`interpret_complete_result/1` maps the
committed `{:execution_error, _}` `Multi` outcome to this distinct error tuple for the
caller — the transaction as a whole commits, it does not roll back), and the task itself
stays `:pending` (ERROR is non-terminal; `TASK_COMPLETED` never fires on this path).
REQ-049's call site (`merge_output_variables/5`) remains genuinely unreachable via
`complete_task/3` today, for the separate reason in point 3 above — that gap is tracked in
`ISS-0063`, not this requirement's scope. `ExecutionError.append_multi/3` and `Engine.
set_instance_error/2` (the shared sink and its standalone entry point) work correctly and
are both fully, genuinely reachable via the public API; tests below that need a real
EE-10 trigger not tied to a specific caller use `set_instance_error/2` for that reason.

## AC1 — EXECUTION_ERROR event carries error type, affected node/field, reason, variables

**Requirement text:** "an EXECUTION_ERROR event carries error type, affected node or
field, a human-readable reason, and the instance variable map as it stood at the moment
of the error -- all four verified by reading the event payload back."

**Test case:** `AC1 -- set_instance_error/2 appends one EXECUTION_ERROR event` /
`"the event payload carries error_type, affected, reason, and the variable snapshot"`.
Starts an instance, calls `Engine.set_instance_error/2` with a REQ-050-shaped
`error_type: :no_matching_gateway_edge`/`affected: {:node, "gw"}` payload, then reads the
`EXECUTION_ERROR` event row back directly from `events` (not the in-memory `{:ok, result}`
alone) and asserts all four AC1 fields: `error_type`, `affected` (`%{"kind" => "node",
"node_id" => "gw"}`), `reason` (contains the gateway id and "no outgoing edge matched"),
and `variables` (the exact snapshot map passed in, read back verbatim). Also cross-checks
`instance_projections.error_detail` carries the same `error_type`/`affected`.

**Why this case, not `complete_task/3` directly:** AC1 is about the sink's payload shape,
not about which caller reached it, so it is tested directly against `set_instance_error/2`
(the sink's own standalone entry point) rather than via a specific caller — `AC4a` below
separately demonstrates the same payload shape end to end through `complete_task/3` for
REQ-050's real trigger.

## AC2 — status flip and EXECUTION_ERROR append commit together (atomicity)

**Requirement text:** "the status flip to ERROR and the EXECUTION_ERROR append commit
together: forcing the append to fail leaves the instance status unchanged, verified by
reading both back."

**Test case:** `AC2 -- forcing the EXECUTION_ERROR append to fail leaves status
unchanged` / `"an unregistered EXECUTION_ERROR event type rolls back the whole
transaction"`. A tenant that never registers `"EXECUTION_ERROR"` in
`event_type_registry` forces `EventStore.append/2`'s own `Registry.validate_payload/3`
call to fail with `:unknown_event_type` inside `ExecutionError.append_multi/3`'s
`:execution_error_event` step — which, per `Ecto.Multi`'s own documented semantics, aborts
and rolls back the entire enclosing transaction. Asserts, read back independently:
`instance_projections.status` is still `:active` (not `:error`), `error_detail` is `nil`,
and the tenant's `events` row count is unchanged. Proves INV-EE61-1/INV-EE61-5 (the event
step runs before the projection-update step, same transaction) rather than assuming it
from the code's own ordering comment.

## AC3 — an instance in ERROR rejects task completion with a distinct conflict

**Requirement text:** "an instance in ERROR rejects task completion with a distinct
conflict error and remains in ERROR afterwards."

**Test case:** `AC3 -- complete_task/3 against an ERROR instance` / `"returns {:error,
{:instance_not_active, :error}}, instance and task untouched"`. Per the design doc §6,
this is already-shipped REQ-048 behavior (`fetch_and_lock_instance_projection/3`'s own M2
check, unmodified by REQ-061) — this test exists to confirm that claim against real code,
not to exercise new logic. Uses `set_instance_error/2` to reach `:error` (independent of
the AC4a defect, since `set_instance_error/2` doesn't depend on the broken
`complete_task/3` rewiring), then calls `complete_task/3` against the instance's own still-
`:pending` task. Asserts the distinct third-element conflict shape
(`{:instance_not_active, :error}`, distinguishable from `:completed`/`:cancelled`), that
the instance is still `:error` afterward, and that the task row is untouched
(`status: :pending`) — the rejected call performed zero writes.

## AC4 — REQ-049 and REQ-050 both route through the shared sink (interim scope, per
REVIEWER's sign-off) — see STATUS above for the current, fixed state

**Requirement text:** "at least the two currently-shipped calling paths (REQ-049 schema
violation, REQ-050 gateway no-match) are demonstrated routing into
set_instance_error/append_multi rather than writing their own ERROR transition, confirmed
by test."

**Test case A (REQ-050, now fixed and demonstrated end to end):** `AC4a -- REQ-050's
realistic downstream-gateway no-match` / `"complete_task/3 routes it into ExecutionError.
append_multi/3: EXECUTION_ERROR appended, status :error"`. Starts an instance on
`task(HUMAN_TASK) -> gw(EXCLUSIVE_GATEWAY)` where `gw`'s own edges can never match and
carry no default — the realistic shape REQ-050 itself describes, discovered a hop
downstream of the completing task via `advance_until_stable/4`'s internal loop. Completes
`task`; asserts `Engine.complete_task/3` returns `{:error, {:instance_execution_error,
:no_matching_gateway_edge, {:node, "gw"}}}` — the fixed shape, per `interpret_complete_
result/1`'s leading clause mapping a committed `{:execution_error, _}` `Multi` outcome to
this tuple, distinct from the pre-fix raw `{:error, {:activation_failed, ...}}` abort —
that `instance_projections.status` is `:error` with `error_detail != nil`, that exactly
one new event was appended and its payload's `error_type` is `"no_matching_gateway_edge"`,
and that the task itself stays `:pending` (the `Multi` as a whole commits — ERROR is a
durable, non-terminal state — but `TASK_COMPLETED` never fires on this path). This proves
AC4's REQ-050 half is genuinely satisfied end to end, not merely at the shared-sink level.

**Test case B (the shared-sink claim, isolated from the trigger mechanism):** `AC4b --
REQ-049's and REQ-050's own error_args() shapes, same sink function` / `"set_instance_
error/2 commits status:error identically for both error_type values"`. Builds the exact
`error_args()` shapes `merge_output_variables/5`'s own rejection clause
(`lib/letflow/engine.ex` ~lines 1093-1106) and `dispatch_task_completion_hop_chain/5`'s
own rewired clause (~lines 1157-1180, per commit `d91e97d`) would each construct —
verbatim, field for field — and passes each through `Engine.set_instance_error/2` on its
own instance. Both commit `status: :error` with the correct `error_type` in both the
projection and the `EXECUTION_ERROR` event payload, and `ExecutionError.__info__
(:functions)` confirms `append_multi/3` (the one function both calls necessarily route
through, since `set_instance_error/2`'s own body calls nothing else to reach `ERROR`)
exists as a single arity-3 export. This isolates REQ-049's own remaining gap (still
unreachable via `complete_task/3`, per `ISS-0063`, STATUS above) from the sink itself,
which is unified and correct for both error types regardless of which caller reaches it.

## AC5 — two concurrent EE-10 triggers on one instance: exactly one commits, one rejected

**Requirement text:** "two concurrent operations both triggering EE-10 on the same
instance result in exactly one committed EXECUTION_ERROR and one rejection, run
concurrently rather than sequentially."

**Test case:** `AC5 -- two concurrent set_instance_error/2 calls target the same
instance` / `"exactly one commits EXECUTION_ERROR, the other observes
{:instance_already_error, _}"`. Two `Task.async` processes, each its own Postgres
connection (Sandbox `:auto`, matching `engine_cancel_instance_test.exs`'s own AC4 race
precedent), call `Engine.set_instance_error/2` against the **same** `instance_id`
simultaneously. Asserts exactly one `{:ok, _}` and exactly one `{:error,
{:instance_already_error, _}}` among the two results, that
`instance_projections.status` ends `:error`, and that exactly one `EXECUTION_ERROR` event
was ever appended (INV-EE61-3) — the loser wrote nothing. This exercises the general
row-lock-queueing mechanism `ExecutionError.append_multi/3`'s own `:execution_error_
eligibility` step implements (design doc §3), the part of AC5 that is genuinely reachable;
the design doc's own §5.5 traces a `complete_task/3`-specific version of this same race,
which inherits AC4a's defect and cannot itself be exercised end to end today.
