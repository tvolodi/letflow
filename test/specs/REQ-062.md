# REQ-062 — SPC-01 sub-process runtime half (test spec)

**Design:** `lib/letflow/design/req062-sub-process-runtime.md`
**Implementation:** `lib/letflow/engine/sub_process.ex` (new module), plus changes to
`lib/letflow/engine/transition.ex` (`:SUB_PROCESS` dispatch, `{:sub_process_completed,
token_id}`), `lib/letflow/engine.ex` (`advance_until_stable/4`'s widened return,
`prepare_sub_process_children/5`, `prepare_sub_process_children_for_completion/7`, the
two `append_sub_process_*_multi` Multi-composition points), `lib/letflow/engine/
reconstruction.ex` (`SUB_PROCESS_COMPLETED` replay clause), and the
`add_sub_process_parent_columns` migration (`instance_projections.parent_instance_id`/
`parent_token_id`).

**Test files:**

* `test/letflow/engine/sub_process_test.exs` — pure-layer coverage: `Letflow.Engine.
  SubProcess.build_child_initial_variables/2` (input filter), `build_parent_merge_
  variables/2` (output filter), `to_error_args/6` (failure → `details.code` mapping),
  `Letflow.Engine.Transition`'s two new `:SUB_PROCESS` dispatch clauses, and the AC5
  GH-428 struct-update regression. No `Letflow.Repo` dependency, `async: true`.
* `test/letflow/engine_sub_process_test.exs` — DB-integration coverage: real child
  creation via `Letflow.Engine.create/2`, real completion propagation via
  `Letflow.Engine.complete_task/3`, all four SPC-01 failure modes, EE-08 (cancel
  non-cascade), and AC6 (create/2 unreachability). `Letflow.DataCase`, `async: false`.
* `test/letflow/engine/transition_test.exs` — one existing test was **stale** (it
  asserted `:SUB_PROCESS` still fell into the generic `node_type_not_yet_implemented`
  catch-all, which this requirement's own `:SUB_PROCESS` dispatch clause makes false);
  fixed to drop `:SUB_PROCESS` from the catch-all list, plus one new regression test
  locking in that `:SUB_PROCESS` genuinely left the catch-all.
* `test/letflow/engine/reconstruction_test.exs` — one new test exercising
  `apply_event/3`'s `SUB_PROCESS_COMPLETED` replay clause (added this same branch as a
  rework-1 fix) end to end.

## Why each test case exists (not a restatement of the AC)

| AC | Test case(s) | Why this test, specifically |
|---|---|---|
| AC1 (filtered inputs) | `sub_process_test.exs` "`build_child_initial_variables/2` -- AC1" (5 cases: filters, `inputs: []` → `%{}`, absent optional omitted, absent required errors on the *first* declared entry, schema-violating present entry errors); `engine_sub_process_test.exs` "AC1" (real DB path) | The pure tests isolate each of the filter's 4 distinct branches (a naive implementation could pass a single "happy path" example while still leaking an unnamed variable, or falling back to EXT-05 on `inputs: []` instead of `%{}` — the design doc explicitly flags this as a deliberate, non-obvious choice). The DB test proves the filtered map is what a real `create/2` call actually persists onto the child's own `instance_projections.variables` row, not just what the pure function *would* return in isolation — a wiring bug between `SubProcess` and `Letflow.Engine`'s own Multi-building code would pass the pure test and fail this one. |
| AC2 (no interface → full copy) | `sub_process_test.exs` "AC2" pure case; `engine_sub_process_test.exs` "AC2" DB case | Symmetric to AC1's own two-level split, for the same reason: an implementation that always filters (even with `interface == nil`) would look correct against a filtered-input-only test suite but silently break every pre-REQ-062 SUB_PROCESS node with no declared interface (EXT-05, already-shipped behavior this requirement must not regress). |
| AC3 (4 failure modes, zero-children / no-partial-merge) | `sub_process_test.exs` pure error-shape cases for all 4; `engine_sub_process_test.exs` 4 dedicated describe blocks, one per failure code, each asserting the DB-observable consequence (`instance_projection_count` unchanged / `child_projections(...) == []` for the 2 activation failures; `parent_projection.variables == parent_initial_variables` unchanged for the 2 completion failures) | The AC's own wording ("ZERO child instances created", "unmodified, no partial merge") is a claim about persisted rows, not about the pure function's return value — a pure-only test could not distinguish "the function correctly signals failure" from "the caller correctly refuses to write anything on that signal". Each of the 4 codes gets its own DB test rather than one parameterized loop, because each fires from a genuinely different call site (2 from `prepare_child_activation/4`'s activation-time filter, 2 from `append_completion_multi/6`'s completion-time filter) with different DB-observable evidence to check. |
| AC4 (filtered outputs, unnamed child var absent from parent) | `sub_process_test.exs` "`build_parent_merge_variables/2` -- AC4" pure cases; `engine_sub_process_test.exs` "AC4" DB case, plus asserting the persisted `SUB_PROCESS_COMPLETED` event's own `output_variables` payload also excludes the unnamed variable | The DB test's extra event-payload assertion exists because the design doc (§3.4 point 4) states the event payload carries the *same* filtered `merge_variables` map used for the merge — a regression that filtered correctly for the live merge but accidentally persisted the child's raw, unfiltered map into the event log would pass a `variables`-only assertion and fail this one; a future `Reconstruction` replay would then leak the unnamed variable back in on any reconstruct call, silently reopening AC4 through the back door. |
| AC5 (`waiting_child_instance_id` set/cleared/preserved, GH-428 regression) | `sub_process_test.exs` "AC5 -- GH-428 regression" pure test (the actual regression demonstration: an unrelated `PARALLEL_GATEWAY` split on a sibling token, asserting the waiting token is byte-for-byte unchanged); `engine_sub_process_test.exs` "AC5" DB case (set while running / cleared on completion, against real `tokens` rows) | The GH-428 regression is specifically about the *pure* struct-update discipline (design doc §1.1) — R-Co's own bug was a manual field-by-field struct copy in Zig that silently dropped a field never mentioned by the copying code. The only way to catch a Letflow reintroduction of that exact bug class is a pure test that drives a transition **unrelated to the SUB_PROCESS token at all** and checks the SUB_PROCESS token survives untouched — a DB-level test alone could not distinguish "preserved because the code is correct" from "preserved because this particular DB test never happened to touch the field", since the DB test's own completion call is the code path that's *supposed* to clear the field, not accidentally drop it. Splitting the two — a pure regression test for "never accidentally dropped by an unrelated hop" and a DB test for "correctly set/cleared by the *related* hop" — covers both halves of the AC precisely. |
| AC6 (child creation unreachable via public `create/2`) | `sub_process_test.exs` moduledoc-inspection test (quotes the exact "internal-only" claim); `engine_sub_process_test.exs` "AC6" functional test (a caller-supplied `parent_instance_id` in `create/2`'s own `attrs` is silently ignored — the resulting instance's `parent_instance_id` column stays `nil`) | Pure code inspection alone (confirming `create_attrs()`'s type has no `parent_instance_id` key) proves the *documented* contract but not that a forged extra map key can't sneak through anyway — Elixir maps don't reject unrecognized keys at the call boundary the way a strict schema would. The functional test closes that gap: even a caller that actively tries to forge the parent link gets ignored, not honored. |
| AC7 (cancel does not cascade to child, EE-08) | `engine_sub_process_test.exs` "AC7" | The design doc (§7) argues this is true *by construction* of already-shipped, unmodified code (`cancel_instance/3`'s existing `instance_id`-scoped queries) — exactly the kind of claim the design doc itself says "is not obviously true without a test exercising it." A real cancel call against a real parent+running-child pair is the only way to demonstrate it rather than assume it. |
| AC8 (all 4 failure modes route into `set_instance_error`, not a bespoke ERROR transition) | `sub_process_test.exs` "`to_error_args/6` -- AC8" pure test (all 4 codes share `error_type: :subprocess_interface_violation`, never 4 distinct top-level atoms); the same 4 DB tests under AC3 above each additionally assert `projection.error_detail["error_type"] == "subprocess_interface_violation"` and exactly one `EXECUTION_ERROR` event (never a distinct event type) | This closes REQ-061's own deferred AC obligation (REQ-061 named `set_instance_error`'s shared-sink contract before REQ-062 existed to exercise a real caller of it beyond REQ-049/050). Reusing the AC3 DB tests rather than writing 4 more from scratch avoids duplicating an entire fixture/setup for a claim that's already observable in the same transaction — the AC3 tests already assert the DB-row consequence; adding the `error_type`/event-type assertions to the same test bodies is direct, not indirect, evidence for AC8. |

## Beyond the bare AC list

* `transition_test.exs`'s fixed catch-all test and its new companion test are
  regression coverage for a **real, would-otherwise-go-undetected break**: before this
  fix, the pre-existing test asserted behavior REQ-062's own implementation
  deliberately changed (`:SUB_PROCESS` moving out of the catch-all) — an unfixed stale
  assertion is not "extra coverage", it is a false claim about current behavior that
  the WF-02 Step 3 "Unblock Everything" directive requires fixing as part of this run,
  not filing as a separate issue (it is squarely inside this requirement's own changed
  surface, `lib/letflow/engine/transition.ex`).
* `reconstruction_test.exs`'s new test is REQ-053's own replay contract (EE-11)
  extended to a 5th persisted event type this requirement introduces
  (`SUB_PROCESS_COMPLETED`) — not itself one of REQ-062's 8 named ACs, but explicitly
  named in the design doc's moduledoc-finding list as this branch's own rework-1 fix,
  and the task instructions for this run call it out by name ("a small addition to
  `test/letflow/engine/reconstruction_test.exs` exercising the new
  `SUB_PROCESS_COMPLETED` replay clause").
