# Test Spec: REQ-063 — Identity tables move behind per-tenant schema (Decision 0006 D1)

**Requirement:** REQ-063 (`docs/requirements.yaml`, stage S3) — relocate
`users`/`groups`/`tenant_role` from Postgres's `public` schema into each tenant's own
schema via `:prefix`. Full design (approved through security + idiom gates):
`lib/letflow/design/req063-identity-tables-schema-per-tenant.md`.

**Requirement's acceptance criteria (verbatim, from the handoff's
`context.requirement_text`):**

1. "users/groups/tenant_role each exist inside at least two distinct provisioned tenant
   schemas (information_schema.tables check, and the same query false for public
   post-cutover)"
2. "each of the three migrations carries the prefix()-truthiness guard (a plain mix
   ecto.migrate creates ZERO of the three tables in public)"
3. "two users with the same username can be created in two different tenant schemas
   without conflict, a duplicate within one schema still conflicts"
4. "the same (external_realm, external_id) pair cannot be bound to two tenants
   (rejected by tenants_idp_realm_id_partial_index)"
5. "existing public rows are copied into the correct per-tenant schema before public
   tables drop, row-count equality plus a spot-check"
6. "AuthPipeline's full flow (token -> realm -> tenant -> per-schema user
   lookup/JIT provisioning) passes end to end against a per-tenant users table"

Criteria 1 and 2 (the migrations themselves — real `CREATE SCHEMA`/`information_schema`
checks and the guard's plain-`mix ecto.migrate`-no-op behavior) were already
demonstrated by ELIXIR-DEV's own Step 2a verification against real Docker Postgres
(handoff `handoffs/WF02-REQ063-20260818/step-02a-elixir-dev.json`) and are structurally
re-proven by every test in this spec that provisions a tenant schema and confirms the
three identity tables land there (any test using `replay_migrations/2` fails outright
if the guard were broken, since a broken guard would create the tables under `public`
instead and the tenant-schema-scoped queries below would find nothing). This spec's own
new coverage focuses on criteria 3–6, which needed genuine runtime proof beyond
ELIXIR-DEV's own manual/exploratory verification, plus fixing the ~39 pre-existing tests
this schema move broke.

**Test tier:** integration only. Every identity table (`users`/`groups`/`tenant_role`)
now requires a real, provisioned Postgres schema to exist at all — there is no
pure-function surface left to unit-test in isolation here.

## Scope test

Real application-executable Elixir logic across `lib/letflow/identity.ex`,
`lib/letflow/identity_migration.ex`, `lib/letflow/plugs/auth_pipeline.ex`, three new
tenant-scoped migrations, and one guarded drop migration. Not docs-only, not
build-config. Full TEST-DESIGN-VALIDATOR / TEST-RUNNER chain applies.

## Two workstreams

### Workstream 1 — fix the ~39 pre-existing test failures

ELIXIR-DEV's own Step 2a `mix test` run reported 722/761 passing, 39 failing, every one
confined to exactly the two categories the design's own §7 item 4 predicted in advance:
fixtures inserting directly into the now-relocated `public` `users`/`groups`/
`tenant_role` tables (which the drop migration already removed on this branch), and
call sites still using the old `provision_oidc_user/3` arity (now `/4`, per design
§5b). This is expected fallout from the schema move, not a regression.

**Files touched, each with a why:**

- `test/letflow/identity_test.exs` — every `provision_oidc_user/4` test now provisions
  a real tenant schema (`TenantProvisioning.provision_tenant_schema/1` +
  `replay_migrations/2`) and passes `prefix: schema_name` explicitly, per the design's
  new required-arg `opts :: [prefix: String.t()]`. Converted from `async: true` to
  `async: false` for the whole module (ExUnit's `async` is module-wide) because
  `replay_migrations/2` needs `Ecto.Adapters.SQL.Sandbox.mode(Letflow.Repo, :auto)` —
  `Ecto.Migrator` cannot run under the sandbox's single shared connection
  (`lib/letflow/design/req022-tenant-schema-provisioning.md` §6's testing-environment
  caveat, already flagged for TEST-DESIGNER by that design doc). The REQ-018
  acceptance-criterion-3 concurrent-race test needed special handling — see "The
  concurrent-race test: two real connections vs. the original design's one shared
  connection" below, which is also where ISS-0047 (a genuine, separate, pre-existing
  bug this rewrite surfaced) is explained.
- `test/letflow/plugs/auth_pipeline_test.exs` and
  `test/letflow/plugs/auth_pipeline_configurable_verifier_test.exs` — every tenant
  fixture now also provisions and migrates a real schema (not just a bare `tenants`
  row), since `AuthPipeline.provision_user/3` internally derives the schema via
  `TenantProvisioning.schema_name_for_tenant/1` and calls `Identity.provision_oidc_user/4`
  with it — without a real schema, JIT provisioning would fail with `relation "users"
  does not exist`. `auth_pipeline_test.exs` converted to `async: false` for the same
  `:auto`-mode reason as `identity_test.exs`;
  `auth_pipeline_configurable_verifier_test.exs` was already `async: false` (for an
  unrelated reason — the global `Application.put_env/3` config swap) so only its
  fixture helper changed.
- `test/letflow/identity/user_test.exs`, `test/letflow/identity/group_test.exs`,
  `test/letflow/identity/tenant_role_test.exs` — these three files insert bare
  `%User{}`/`%Group{}`/`%TenantRole{}` structs directly via `Repo.insert/1` (no
  changeset, no single call site to thread a `prefix:` option through — see design's
  own §7 item 4 note that these fixtures need special handling). Fixed via `SET
  search_path TO "<tenant_schema>", public` issued once per test on the sandboxed
  connection, pointing every subsequent *unprefixed* `Repo` call at the provisioned
  tenant schema automatically — see "Why `SET search_path`, not `prefix:`" below for
  why this is the correct mechanism here, not a workaround.
- `test/letflow/role_registry_test.exs` — same `SET search_path` mechanism.
  `Letflow.Identity.RoleRegistry` was deliberately NOT modified by REQ-063 (out of
  scope — its own design doc, `lib/letflow/design/req020-role-registry.md`, already
  documented that it takes zero tenant/prefix arguments, anticipating a future
  per-request `SET search_path` mechanism Letflow "has not built yet"). REQ-063 made
  that gap concrete: `RoleRegistry`'s unprefixed queries now find nothing in `public`
  at all. Converted from `async: true` to `async: false` for the `:auto`-mode
  requirement.

**Why `SET search_path`, not `prefix:`, for the four direct-struct-insert files.**
`Repo.insert/1` on a bare struct (`user_test.exs`/`group_test.exs`/
`tenant_role_test.exs`) and every `RoleRegistry` public function
(`role_registry_test.exs`) have no per-call `opts`/`prefix:` parameter to pass —
`RoleRegistry` was explicitly left that way by REQ-020's own design (see above), and a
bare-struct `Repo.insert/1` has no changeset-level opts to thread either. Verified
directly against real Postgres before writing these files: `SET search_path TO
"<schema>", public` issued on the sandboxed connection is a transaction-scoped write
like any other on that connection — automatically reverted by `Letflow.DataCase`'s
normal rollback (no manual GUC cleanup needed) for the three struct-insert files, which
stay on the ordinary sandboxed-and-rolled-back path once the schema itself has been
provisioned via a preceding `:auto`-mode step. This is not a novel technique invented
for testing only — it is the exact mechanism `lib/letflow/design/req020-role-registry.md`
already names as the target production architecture ("Tenant isolation is provided by
the per-tenant schema... The schema search path must be set... before any query
executes") that Letflow has "not built yet" at the request-pipeline level; using it here
proves the tenant-schema tables behave correctly under that mechanism today, ahead of
that pipeline-level work landing.

**The concurrent-race test: two real connections vs. the original design's one shared
connection, and ISS-0047.** `identity_test.exs`'s REQ-018 acceptance-criterion-3 test
(two `Task`s racing into `provision_oidc_user/4` for the identical identity) originally
used `Ecto.Adapters.SQL.Sandbox` `:manual` mode + `Sandbox.allow/3`
(`lib/letflow/design/req018-jit-provisioning.md` §9's exact guidance), which routes both
spawned `Task`s through the *same* underlying sandboxed connection/transaction (nested
savepoints) — not two genuinely independent Postgres connections. This test now also
needs `provisioned_tenant!/0`'s `:auto`-mode migration replay first. A first draft tried
running the race itself under `:auto` mode too (two real, independent connections) —
this reliably (not flaky; reproduced on 3 consecutive runs) surfaced a genuine,
separate, pre-existing bug: `Letflow.Identity.insert_or_fetch/4`'s `on_conflict:
:nothing` only covers the `(external_realm, external_id)` conflict target, not the
separate `username` unique index, so a true two-connection race on an identical
identity (which also shares a username, as this test deliberately constructs) can raise
a `username`-uniqueness `Ecto.Changeset` error instead of resolving via the intended
re-select fallback. This is **not** a REQ-063 regression — REQ-063 only added
`prefix:`-threading and never touched `insert_or_fetch/4`'s conflict-handling logic;
the gap is inherited from REQ-018's original implementation and was never previously
exercised as a genuine cross-connection race because `Sandbox.allow/3` always
serialized the two attempts at the Postgres session level. Filed as
`docs/issues/ISS-0047.yaml` / GitHub issue #176, not fixed inline (fixing
`lib/letflow/identity.ex` is ELIXIR-DEV's lane, not TEST-DESIGNER's, and REQ-063's own
acceptance criteria do not require it). The test itself was restored to the original
`:manual` mode + `Sandbox.allow/3` mechanism (after using `:auto` mode only for the
up-front schema/migration provisioning step, then switching back), which genuinely
proves REQ-018's original acceptance criterion 3 — that claim remains true and is not
weakened by this rewrite.

### Workstream 2 — new coverage for REQ-063's own acceptance criteria

| Acceptance criterion | Test case | Why this test exists (not just a restatement) |
|---|---|---|
| 3a — "two users with the same username can be created in two different tenant schemas without conflict" | `identity_test.exs` `describe "provision_oidc_user/4 — username collision..."` `"two users with the same username in TWO DIFFERENT tenant schemas both succeed"`; `user_test.exs` `"two users with the SAME username in TWO DIFFERENT tenant schemas both succeed"` | Proves the index's *meaning* genuinely changed from global-unique to per-tenant-unique (Decision 0006 §3.1) — the column-level `unique_index(:users, [:username])` definition is byte-identical to the pre-REQ-063 migration (design §2.3 point 3), so only a real cross-schema insert (not a migration-file diff) can demonstrate the behavior actually changed. Two variants: one through the full `provision_oidc_user/4` JIT path (proves the application-level flow), one through a direct `Repo.insert/1` (isolates the DB constraint itself from JIT-provisioning logic, matching the existing `user_test.exs` file's own direct-insert convention). |
| 3b — "a duplicate within one schema still conflicts" | `identity_test.exs` `"two users with the same username in the SAME tenant schema: the second JIT provisioning call fails..."`; `user_test.exs` `"two users with the same username: the second raises a constraint error"` (pre-existing, now schema-scoped) | Without this negative case, the 3a tests alone would not distinguish "the index still enforces uniqueness, just now per-schema" from "the index was silently dropped/broken by the schema move" — both must be true together for the acceptance criterion's own "without conflict... still conflicts" contrast to hold. |
| 4 — "the same (external_realm, external_id) pair cannot be bound to two tenants (rejected by tenants_idp_realm_id_partial_index)" | `identity_test.exs` `describe "Tenant.create_changeset/3 — one-to-one collision rejection"` `"creating a second tenant with an already-bound idp_realm_id is rejected, not silently overwritten"` — **pre-existing test, unchanged by this run** | `tenants_idp_realm_id_partial_index` lives on the `tenants` table, which Decision 0006 D3 keeps permanently in `public` — REQ-063 never touches it, so this test needed no fixture change and already proves the exact mechanism the acceptance criterion names. Re-verified passing after every other fixture change in this run (not merely assumed unaffected) — see the full-suite run below. No new test was needed or written for this criterion; listed here so the traceability table has an explicit row rather than a silent gap. |
| 5 — "existing public rows are copied into the correct per-tenant schema before public tables drop, row-count equality plus a spot-check" | `identity_migration_test.exs`, `describe "IdentityMigration.copy_tenant/2 and copy_all_tenants/0"` — 4 tests: full copy + preserved ids (spot-check), idempotent re-run, multi-tenant aggregate counts (row-count equality across `copy_all_tenants/0`'s summary vs. each schema's actual row count), and the orphaned-`tenant_role` abort path | ELIXIR-DEV's own Step 2a handoff did this same proof manually against live Postgres (insert-copy-inspect, once, by hand, then reset the DB) — not a committed, repeatable test. These four tests turn that manual proof into permanent, real-Postgres-backed coverage: preserved-id spot-check (a specific row's `id` survives the copy unchanged, per design §4's "client-generated binary_id primary key... preserved verbatim"), aggregate row-count equality across two tenants at once (not just one, so the per-tenant partitioning is genuinely exercised), and the one failure mode the design explicitly calls out as needing to never be silently dropped (an orphaned `tenant_role`). |
| 5 (guard) — drop migration's guard-skip behavior on an uncopied row | `identity_migration_test.exs`, `describe "DropLegacyPublicIdentityTables migration guard"` — 3 tests: skip-on-uncopied-row (all three tables survive, not just the one with the gap), proceed-once-fully-copied, and idempotent re-run-after-success | ELIXIR-DEV's own Step 2a handoff demonstrated this exact skip/proceed behavior manually against live Postgres ("deliberately inserting an uncopied row... confirmed the guard correctly SKIPPED the drop... ran mix letflow.copy_identity_tables... confirmed the drop proceeded") — this is TEST-DESIGNER's job (per the handoff's own task description) to turn into a real, repeatable ExUnit test rather than trust the one-time manual demonstration. Runs the actual shipped migration file (`Code.require_file/1`'d, not a stand-in fixture) via `Ecto.Migrator.run/4` directly against throwaway-recreated `public.*` tables (see that file's own moduledoc for why recreation is needed — this branch's own `mix ecto.migrate` already ran the real drop once, so the tables must be reconstructed to exercise the guard at all). |
| 6 — "AuthPipeline's full flow (token -> realm -> tenant -> per-schema user lookup/JIT provisioning) passes end to end against a per-tenant users table" | `auth_pipeline_test.exs`, `"a valid bearer token flows through the full pipeline and attaches user_id/tenant_id/roles..."` and `"a second request with the same valid token resolves to the same user_id, not a duplicate row"` — both pre-existing tests, fixtures updated | These two tests already exercised the full token→realm→tenant→JIT-provisioning flow before REQ-063; the only change needed was making the tenant fixture provision a real schema so the per-schema `users` lookup/insert this criterion asks about has somewhere real to happen. ## What is verified by inspection, not a new runtime test

- **Acceptance criteria 1 and 2** (migration shape/guard) — already demonstrated by
  ELIXIR-DEV's Step 2a real-Postgres verification, and structurally re-proven by every
  test above that successfully provisions+replays a tenant schema and finds the three
  identity tables there (a broken guard would make every such test fail with "relation
  does not exist" against the tenant schema, since the tables would have landed in
  `public` instead). No standalone migration-guard unit test was added for REQ-063's
  own three `create table` migrations, matching the precedent
  `tenant_provisioning_test.exs`'s and `event_store/migrations_test.exs`'s own guard
  tests already set for the *general* pattern (REQ-063's migrations follow that
  pattern byte-for-byte, confirmed by direct inspection of the three migration files —
  each carries the identical `if prefix() do ... end` structure).
- **Acceptance criterion 4** — pre-existing, unmodified, re-confirmed passing (see
  table above).
