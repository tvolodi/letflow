# Test Spec: REQ-064 — Drop `tenant_id` from schema-isolated tables (Decision 0006 D2)

**Requirement:** REQ-064 (`docs/requirements.yaml`, stage S3) — drop `tenant_id` from
ten schema-isolated business tables: `events`, `events_archive`,
`instance_projections`, `process_definitions`, `tokens`, `tasks`,
`promotion_reviews`, `promotion_assertion_runs`, `users`, `groups`. Full design
(approved through security + idiom gates):
`lib/letflow/design/req064-drop-tenant-id.md`.

**Requirement's acceptance criteria (verbatim, from the handoff's
`context.requirement_text`):** none of the ten tables has a `tenant_id` column,
confirmed via `information_schema.columns` in a provisioned tenant schema; the four
D3 tables (`tenant_schemas`, `solution_pack_installs`, `solution_pack_artefact_bases`,
`pack_update_resolutions`) still have `tenant_id` WITH their FK intact, confirmed the
same way plus a test that a bad `tenant_id` is still rejected; the
`promotion_assertion_runs` idempotency contract still holds under the simplified
single-column index (same key twice in one tenant schema yields one row, same key in
a different tenant schema yields a separate row); the `promotion_reviews`
`plan_digest` uniqueness still holds per-tenant under the simplified index; no `lib/`
module references a `tenant_id` field on any of the ten tables (grep-confirmed); and
`TenantProvisioning.tenant_id_for_schema_name/1` itself still exists and is still
tested; every moduledoc that described `tenant_id` on a dropped-from table has been
updated; `mix test` is green with no skipped/excluded tests.

**Test tier:** integration only. Every affected table is reachable only via a real,
provisioned Postgres tenant schema — there is no pure-function surface to unit-test
here in isolation.

## Scope test

Real application-executable Elixir logic: ten Ecto migrations
(`priv/repo/migrations/20260820000001..000010`), ten schema-module edits
(`lib/letflow/engine/{token_record,task}.ex`,
`lib/letflow/event_store/{event,archived_event,instance_projection}.ex`,
`lib/letflow/definitions/{process_definition,promotion_review,promotion_assertion_run}.ex`,
`lib/letflow/identity/{user,group}.ex`), and 14 call-site edits across
`lib/letflow/definitions.ex`, `lib/letflow/event_store.ex`,
`lib/letflow/definitions/promotion_review_store.ex`. Not docs-only, not
build-config. Full TEST-DESIGN-VALIDATOR / TEST-RUNNER chain applies.

## Two workstreams

### Workstream 1 — fix the pre-existing test-compile/test-run failures

ELIXIR-DEV's own Step 2a report and ORCH's independent grep found ~20 files that fail
to compile because they build struct literals / attrs maps / query filters with a
`tenant_id:` key against the ten schemas this requirement just stripped it from. This
is the expected, designed fallout of the field removal — the same shape as REQ-063's
own ~39-test fallout in this same codebase (`test/specs/REQ-063.md`). A first
mechanical pass fixed the 20 named files; the actual `mix test` run this spec is based
on additionally surfaced **5 more files never named in the original 20** whose
breakage has the identical root cause (a `tenant_id:` reference against one of the ten
schemas) but were missed by the original grep because they either fail at runtime
(`Ecto.QueryError`/`KeyError` inside a test body, not a compile error) rather than at
compile time, or live outside the `test/letflow/definitions|engine|event_store|identity`
glob the original grep swept:

- `test/letflow/plugs/auth_pipeline_test.exs`
- `test/letflow/plugs/auth_pipeline_configurable_verifier_test.exs`
- `test/letflow/definitions/store_test.exs`
- `lib/letflow/identity_migration.ex` (**production code**, not a test file — see
  below)
- `lib/letflow/definitions/promotion_assertion_run.ex` (a stale moduledoc sentence,
  not a test file)

Per `core-directives.md`'s Unblock-Everything rule, all of these are fixed here as
part of "resolve any problem that blocks full completion of the current task," not
filed as separate issues — they are direct fallout of REQ-064's own field removal, not
an unrelated defect merely noticed in passing.

**Mechanical fixture fixes (no change in test intent, `tenant_id:` key or reference
dropped from a struct literal/attrs map/query filter/`for` list):**

- `test/letflow/definitions/{export_import,migrations,promotion_conflict,promotion_plan,
  promotion_review_migration,schemas,snapshot_store}_test.exs`
- `test/letflow/engine/migrations_test.exs`
- `test/letflow/event_store/{migrations,schemas}_test.exs`
- `test/letflow/identity/tenant_role_test.exs` (only its `insert_group!/1` helper's
  `%Group{tenant_id: ...}` literal)
- `test/letflow/role_registry_test.exs` (its `insert_group!/1` helper, same pattern)
- `test/letflow/plugs/auth_pipeline_configurable_verifier_test.exs`'s and
  `auth_pipeline_test.exs`'s `user_count_for_tenant/1,2` helpers — both built a
  `User |> where(tenant_id: ^tenant_id) |> ...` query filter, a **runtime**
  `Ecto.QueryError` (not a compile error), which is why these two files were not in
  ORCH's original compile-error-only grep. Fixed by dropping the `where(tenant_id:
  ...)` clause entirely — counting all rows under `prefix: schema_name` is already
  tenant-scoped, since the schema boundary is the only tenant identifier left.

**Tests whose entire purpose was proving something about the now-removed column
(restructured or deleted, not mechanically patched — each preserves the underlying
acceptance-criterion intent where one still exists):**

- `test/letflow/identity/group_test.exs` — its one test, `"a group can reference a
  tenant_id with no matching tenants row (no DB-level FK enforced)"`, existed solely
  to prove `groups.tenant_id` carried no FK. That claim is moot once the column is
  gone entirely (there is nothing left to have-or-lack an FK). **Deleted**, not
  patched — patching would leave a test asserting on a field that no longer exists on
  a struct.
- `test/letflow/identity/user_test.exs` — same situation, same fix: `"a user can
  reference a tenant_id with no matching tenants row (no DB-level FK enforced)"`
  **deleted**.
- `test/letflow/event_store_test.exs`'s `describe "tenant_id (AC6)"` block — its test
  "events and instance_projections rows carry tenant_id equal to the tenant :prefix
  resolves to" asserted `event_tenant_id == expected_tenant_id` and
  `projection.tenant_id == expected_tenant_id` directly on `Event`/`InstanceProjection`
  structs. **Restructured, not deleted** — the underlying spirit of AC6 (an event and
  its projection are correctly attributed to the tenant whose `:prefix` wrote them,
  not some other tenant) is still true and still worth proving; it is now expressed as
  schema-prefix reachability instead of a field comparison: the row is found via
  `Repo.get_by(..., prefix: schema_name)` in its own tenant's schema and genuinely
  `refute`d in a second, independently provisioned tenant's schema.
- `test/letflow/definitions/promotion_test.exs` — `review_for/2`'s in-memory
  `%PromotionReview{tenant_id: plan.target_tenant_id, ...}` literal (field dropped;
  the struct itself no longer has anywhere to put that value) and
  `assert target_row.tenant_id == target_tenant_id` on a `%ProcessDefinition{}` row
  (assertion dropped outright — its meaningful half, "the row landed in the target
  tenant's own schema," is already proven by the preceding
  `Repo.get!(ProcessDefinition, id, prefix: target_schema)` succeeding at all; a
  wrong-schema write would have raised `Ecto.NoResultsError` there already).
  `insert_definition!/2`'s stray unused `tenant_id: Ecto.UUID.generate()` in its base
  attrs map dropped too (it was never read by anything, `ProcessDefinition` never cast
  it even before this requirement — REQ-063-era fixture debt, not new).
- `test/letflow/definitions/promotion_review_store_test.exs`'s `describe "insert_review/2
  -- tenant_id is derived from opts[:prefix], never from plan.target_tenant_id"` —
  **restructured, not deleted**. The real claim it proved (which tenant a row lands in
  is decided by `opts[:prefix]`, never by trusting `plan.target_tenant_id`) is exactly
  as true and exactly as worth proving post-REQ-064 — the mechanism just changed from
  "assert the stamped tenant_id column" to "assert the row is reachable in the
  prefix's own schema." Renamed to `describe "insert_review/2 -- prefix validity is
  still checked, even though no tenant_id is stamped"`; the disagreeing-target-tenant
  test drops its two `.tenant_id` field assertions and replaces them with
  `Repo.get!(PromotionReview, review.id, prefix: schema_name)` (proves the row is
  where the prefix said it should be) while keeping its `serialised_plan` JSON-payload
  assertion unchanged (that part was never about the dropped column). The
  `invalid_schema_name` test in the same `describe` block needed no change — it never
  referenced `tenant_id` at all.
- `test/letflow/definitions/store_test.exs`'s `describe "create/2 (AC9) -- tenant_id
  always derived internally, never caller-supplied"` — its first test asserted
  `definition.tenant_id == tenant_id` on a `%ProcessDefinition{}`. Not in ORCH's
  original 20-file list (found only by actually running the suite, confirming the
  handoff's own warning that this class of breakage needed real verification, not
  just a grep-and-patch pass). **Restructured**: renamed to "a created row is
  reachable under its own tenant's schema and NOT under a different tenant's schema,"
  proves the same underlying claim (a row belongs to the tenant whose schema it was
  written into) via `refute Repo.get(ProcessDefinition, definition.id, prefix:
  other_schema_name)` against a second, independently provisioned tenant — a stronger
  proof than the original field-equality check, since it positively demonstrates
  cross-tenant unreachability rather than merely reading back a column. The
  `describe` block's other two tests (`:tenant_id_not_accepted` rejection of an atom
  or string `"tenant_id"` key in caller-supplied attrs) needed no change — that
  rejection is enforced by `Letflow.Definitions.create/2`'s own attrs-key guard, not
  by the schema having a `tenant_id` field to reject into, so it is unaffected by the
  column's removal.
- `test/letflow/engine/schemas_test.exs` — beyond mechanical struct-literal/attrs-map/
  `for`-list fixes on `Token`/`Task` (same pattern as the other schema-changeset
  files), one moduledoc-content test asserted a **now-false claim**:
  `test "states tenant_id is never populated from caller-supplied attrs by this
  schema's own contract (design §4.3 point 5)"` checked `doc =~ "never a value taken
  from external caller input"` — the exact phrase from `Task`'s OLD moduledoc section
  (`## tenant_id is never caller-supplied`), which this requirement's own §5.2 already
  replaced with `## No tenant_id column (Decision 0006 D2)`. Left unfixed, this test
  would have kept passing-for-the-wrong-reason if the two phrases had accidentally
  overlapped, or failed for a reason unrelated to a real regression — either way it
  was no longer testing anything true. Renamed to `"states the tenant_id column was
  dropped by Decision 0006 D2 and must not be re-added"`, now asserts
  `doc =~ "No \`tenant_id\` column (Decision 0006 D2)"` and `doc =~ "Do not re-add a
  \`tenant_id\` field to this schema"` — the actual current moduledoc text, verified
  directly against `lib/letflow/engine/task.ex`.

**Production-code fixes (not test files, but blocking the suite — Unblock-Everything):**

- `lib/letflow/identity_migration.ex` — `copy_groups/2`, `copy_users/2`,
  `copy_tenant_roles/2`'s inner query all filter via
  `fragment("? = ?", g.tenant_id, ^tenant_id)` against the **legacy public**
  `groups`/`users` tables (correctly still `tenant_id`-bearing — REQ-063's own drop
  migration for these hasn't run yet at the point this module executes, see the
  module's own moduledoc). Before this requirement, `g.tenant_id`'s type information
  came from `Letflow.Identity.Group`'s own `field(:tenant_id, Ecto.UUID)` declaration,
  letting Ecto cast `^tenant_id` to `uuid` for the comparison. Once REQ-064 removed
  that field declaration, the fragment lost its only source of type info for the
  pinned value, and Postgrex started sending the raw string form of the UUID instead
  of its 16-byte binary encoding — `** (DBConnection.EncodeError) Postgrex expected a
  binary of 16 bytes, got "<uuid-string>"`, a genuine runtime bug reachable by any real
  call to `IdentityMigration.copy_tenant/2`, not merely a test-fixture artifact. Fixed
  by adding explicit type info to the fragment's pinned parameter:
  `fragment("? = ?", g.tenant_id, type(^tenant_id, Ecto.UUID))` (three occurrences).
  This is exactly the kind of "subtle bug hiding behind what looked like a mechanical
  fixture fix" the handoff's own briefing warned to watch for, citing REQ-063's
  Sandbox-pooling precedent — found only by actually running
  `test/letflow/identity_migration_test.exs` against real Postgres, not by
  inspection.
- `lib/letflow/definitions/promotion_assertion_run.ex` — a moduledoc sentence still
  claimed `insert_changeset/2` "casts only the four columns present at
  idempotency-claim time (`tenant_id`, `review_id`, `idempotency_key`,
  `plan_digest`)" — stale since the changeset itself (§4 point 8 of the design) had
  already dropped `tenant_id` from its `cast/3` list. Not caught by the requirement's
  own "grep for 'never caller-supplied'/'intra-schema column'" check (different
  wording), but a real accuracy drift the requirement's own acceptance criteria
  ("every moduledoc that described tenant_id on a dropped-from table has been
  updated") cover in spirit. Fixed to read "casts only the three columns... (`tenant_id`
  was a fourth column here until Decision 0006 D2 dropped it, see the migration
  file's own header)".

### Workstream 2 — new coverage for REQ-064's own acceptance criteria

All new tests live in `test/letflow/req064_tenant_id_removal_test.exs`.

| Acceptance criterion | Test case | Why this test exists (not just a restatement) |
|---|---|---|
| `promotion_assertion_runs` idempotency, same key/same tenant schema -> one row | `describe "promotion_assertion_runs idempotency contract..."` `"the same idempotency_key twice within ONE tenant schema resolves to exactly one row..."` | Proves the `on_conflict: :nothing` + `conflict_target: [:idempotency_key]` idiom (design §2.3, `claim_or_fetch_assertion_run/5`'s own real call shape) genuinely suppresses a second insert and leaves exactly one row — a broken/missing index would let both inserts land, silently doubling idempotency-anchor rows. |
| `promotion_assertion_runs` idempotency, same key/different tenant schema -> two rows | Same describe block, `"the same idempotency_key in a DIFFERENT tenant schema produces a SEPARATE row..."` | The genuinely load-bearing half of this acceptance criterion: proves the simplified single-column `[:idempotency_key]` index (down from `[:tenant_id, :idempotency_key]`) did NOT accidentally become globally unique across every tenant schema at once — the two inserts must both win, in their own schemas, or a regression here would silently merge two unrelated tenants' idempotency anchors. |
| `promotion_reviews` `plan_digest` uniqueness, same digest/same tenant schema -> rejected | `describe "promotion_reviews plan_digest uniqueness..."` `"a duplicate plan_digest within ONE tenant schema is rejected"` | Same reasoning as the assertion-runs positive case, for the simplified `[:plan_digest]` index (down from `[:tenant_id, :plan_digest]`) and `uq_promotion_review_active_digest`'s partial-index predicate. |
| `promotion_reviews` `plan_digest` uniqueness, same digest/different tenant schema -> both succeed | Same describe block, `"the same plan_digest in a DIFFERENT tenant schema succeeds..."` | The cross-tenant-isolation half — proves the simplified index enforces uniqueness only within a schema, not globally; a regression collapsing this to a global constraint would make the second insert fail where it must succeed. |
| A bad/nonexistent `tenant_id` is still rejected by a D3 table's FK | **Not duplicated** — `test/letflow/definitions/pack_update_migration_test.exs`'s `describe "real DB-level foreign key: tenant_id references tenants.id on all three GLOBAL tables"` `"solution_pack_installs rejects a tenant_id matching no tenants row"` already exists and already proves exactly this, pre-dating this requirement. Re-verified passing after every migration/schema-module edit this run made (see the full-suite run below) — the D3 tables' migrations/schema modules were, per design §1, untouched by this requirement, so this existing test needed no edit and is not duplicated here. Listed in this table so the traceability mapping has an explicit row rather than a silent gap, matching `test/specs/REQ-063.md`'s own precedent for a pre-existing, unmodified, re-verified test. |
| `information_schema.columns` confirms all ten D2 tables lack `tenant_id` | `describe "information_schema.columns..."` two tests, `"all ten D2 tables genuinely lack tenant_id, in a real provisioned tenant schema"` and the same check against a **second**, independently provisioned schema | Direct, real-Postgres proof at the column-catalog level, not inferred from a struct's compiled field list (which could theoretically diverge from what actually got migrated if a migration silently failed to apply). The second-schema variant guards against "passed only because this one schema's replay happened to skip the drop migrations" — a flake this codebase has hit before with tenant-scoped migration manifests (`tenant_scoped_migrations/0`'s own moduledoc cites this exact class of bug). Each test also asserts the table itself has a nonzero column count first, so an accidentally-empty/missing table can't produce a false pass by vacuously satisfying "lacks tenant_id." |
| `information_schema.columns` confirms all four D3 tables still have `tenant_id` | Same describe block, `"all four D3 tables genuinely still have tenant_id, in public"` | The direct negative-space check this requirement's own acceptance criteria explicitly ask for — proves D3 was genuinely untouched, not merely "no migration file mentions it," at the same level of rigor as the D2-absence checks above. |
| `TenantProvisioning.tenant_id_for_schema_name/1` itself still exists and is tested | **Not duplicated** — `test/letflow/event_store_test.exs:534`'s `"events and instance_projections rows carry tenant_id equal to the tenant :prefix resolves to"` (post-REQ-064 restructure, Workstream 1 above) already asserts `{:ok, expected_tenant_id} = TenantProvisioning.tenant_id_for_schema_name(schema_name)` as a genuine round-trip check, unaffected by this requirement (only the function's *stamping call sites* were removed, not the function itself — design §1). No new test needed; confirmed by direct inspection this session, not assumed. |
| No `lib/` moduledoc still says "never caller-supplied"/"intra-schema column" about a dropped-from table | Verified by direct `grep -rn` this session (not a runtime test — nothing to assert against inside `mix test` for a doc-text claim spanning the whole `lib/` tree). Every hit for either phrase is either unrelated (`definitions.ex`'s `base` value, `sandbox_pool.ex`'s `schema_name`) or already correctly past-tense (`identity/user.ex:10`, "`tenant_id` **was** an intra-schema column... until Decision 0006 D2... dropped it"). | Confirms REVIEWER's Step 2d PASS held, rather than trusting that gate blindly, per this handoff's own instruction. |
