# Test Spec: REQ-066 — `Letflow.Api.Error` / `Letflow.Api.Response`

**Requirement:** REQ-066 (stage S4) — port `src/api/errors.zig` and
`src/api/response.zig` as the single response/error contract every S4 route emits.
**Test tier:** unit + integration (`Plug.Test`-driven conn threading, plus one
router-level end-to-end case for INV-5).
**Design:** `lib/letflow/design/req066-api-error-response.md`.
**Test files:**

- `test/letflow/api/error_test.exs` — pure unit tests for the Problem Details builder.
- `test/letflow/api/response_test.exs` — conn-threading tests for the response helpers,
  including the two security-invariant cases and the moduledoc contract case.

## 0. Scope test (WF-02 Step 3)

**IN SCOPE — the answer is YES.** This requirement produced real
application-executable Elixir surface: `lib/letflow/api/error.ex` (222 lines of
application logic — a struct, ten constructors, a serialiser) and
`lib/letflow/api/response.ex` (181 lines — fourteen conn-threading functions plus a
private trace-id precedence resolver). Neither is project/build configuration; both
are called from `lib/letflow/router.ex` at runtime. The full Step 3 procedure
therefore applies, and the handoff routes on to TEST-DESIGN-VALIDATOR (Step 3a) and
TEST-RUNNER (Step 4) rather than skipping to RELEASE-VALIDATOR.

## 1. Measured runtime facts these tests assert against

These are the values ELIXIR-DEV measured at runtime and REVIEWER independently
re-confirmed. The tests assert them literally; they are **not** idealised guesses,
and a test asserting the idealised value instead would fail.

| Fact | Asserted value | Why it is not the "obvious" value |
|---|---|---|
| Success `Content-Type` | `application/json; charset=utf-8` | `Plug.Conn.put_resp_content_type/2` appends the charset. A bare `"application/json"` assertion fails. |
| Error `Content-Type` | `application/problem+json; charset=utf-8` | Same charset suffix; also a deliberate divergence from R-Co, which serves problem bodies as `application/json`. |
| `no_content/1` | 204, `""` body, **no** `content-type` header at all | `send_resp/3` without `put_resp_content_type/2` leaves the header list empty — asserted as `[] == get_resp_header(conn, "content-type")`, not as some default type. |
| `rate_limited` title | `Too Many Requests` | Not `Rate Limited`. Verbatim from `errors.zig`'s `problemRateLimited`, not Title-Cased from the `rate-limited` slug. |
| `internal` title | `Internal Server Error` | Not `Internal Error`. Verbatim from `errors.zig`'s `problemInternalError`. |
| `unprocessable` slug | `unprocessable-entity` | Slug and function name differ; the slug follows `errors.zig`. |
| `type` base URI | `https://bpm.example.com/problems/` | Nothing in `config/*.exs` sets `:problems_base_uri` (REVIEWER grepped all five config files), so `Application.compile_env/3`'s default is what is actually compiled in. |
| `trace_id` precedence | non-empty `problem.trace_id` → `conn.assigns[:trace_id]` → `""` | Three branches, matching `errors.zig:54`. All three are covered by their own test. |

## 2. Test cases

### AC1 — every constructor produces type/title/status/detail, `type` absolute

*"Letflow.Api.Error produces a JSON body containing type, title, status and detail for
every status constructor ported, with type an absolute URI, verified by a test per
constructor."*

One test per ported constructor (ten of them), in
`test/letflow/api/error_test.exs`, `describe "problem constructors"`:

1. `bad_request/1 builds the 400 document` — 400 / `bad-request` / `Bad Request`.
2. `unauthorized/1 builds the 401 document` — 401 / `unauthorized` / `Unauthorized`.
3. `forbidden/1 builds the 403 document` — 403 / `forbidden` / `Forbidden`.
4. `not_found/0 builds the 404 document` — 404 / `not-found` / `Not Found`, fixed detail.
5. `conflict/1 builds the 409 document` — 409 / `conflict` / `Conflict`.
6. `unsupported_media_type/1 builds the 415 document` — 415 / `unsupported-media-type`.
7. `unprocessable/1 builds the 422 document` — 422 / `unprocessable-entity`.
8. `rate_limited/1 builds the 429 document` — 429 / `rate-limited` / **`Too Many Requests`**.
9. `internal/0 builds the 500 document` — 500 / `internal-error` / **`Internal Server Error`**, fixed detail.
10. `service_unavailable/1 builds the 503 document` — 503 / `service-unavailable`.

Each of the ten goes through one shared assertion helper that (a) serialises via
`Error.serialise/1` and decodes the real JSON body rather than inspecting the struct,
so the test proves the *wire* contract and not merely the in-memory shape;
(b) asserts all four RFC 9457 fields are present with their exact expected values;
and (c) asserts `type` parses as an **absolute** URI — `URI.parse/1` yields a
`scheme` and a non-empty `host`, and the string begins with the configured base.
The absolute-URI check is a separate assertion rather than folded into the string
equality because AC1 names it as its own obligation: a future change to
`:problems_base_uri` that set a relative path would still satisfy a
`type == base <> slug` equality while violating the criterion.

Supporting cases in the same file (why each exists, beyond restating AC1):

11. `trace_id defaults to an empty string` — `errors.zig`'s `ProblemDetails` carries a
    `""` default that the requirement text calls out explicitly. Without this case, a
    constructor that omitted the field entirely (so the key never reached the JSON
    body) would pass all ten cases above, because they do not look at `trace_id`.
12. `serialise/1 escapes quotes and backslashes in detail` — the design (§0.1) records
    that `errors.zig` interpolates `detail` raw and therefore emits invalid JSON for a
    detail containing a quote, and that Jason fixing this must not be "fixed" back.
    This case pins that improvement: it round-trips a detail containing `"` and `\`
    and asserts the decoded value equals the input exactly.
13. `serialise/1 emits all five RFC 9457 keys` — guards the `@derive {Jason.Encoder,
    only: [...]}` list. Dropping a field from `only:` would silently shrink the wire
    contract while every field-value assertion above still passed on the survivors.

### AC2 — Content-Type split, asserted from the response header

*"an error response carries Content-Type: application/problem+json and a success
response carries application/json, each verified by asserting the response header
rather than by inspection."*

In `test/letflow/api/response_test.exs`:

14. `ok/2 sends 200 with the JSON content type` — asserts
    `get_resp_header(conn, "content-type") == ["application/json; charset=utf-8"]`.
15. `not_found/1 sends the problem content type` — asserts
    `["application/problem+json; charset=utf-8"]`.
16. `every error helper sends problem+json` — walks all ten wrappers in one test and
    asserts the header on each. This exists because AC2's guarantee is about the
    *class* of error responses, not one representative: a wrapper that bypassed
    `send_problem/2` and set its own content type would pass case 15 and fail here.

Every one of these reads `Plug.Conn.get_resp_header/2` on the returned conn — the
actual header the client receives — never `conn.resp_headers` inspection by eye or a
struct-field peek.

### AC3 — 500 detail invariant across exception types (INV-4)

*"a 500 produced from an unexpected exception has a detail string that is identical
across two different underlying exception types, demonstrated by a test — no exception
message, module name, SQL fragment, or stack trace reaches the body."*

Tested per the design (§0.3) by calling `internal_error/1` **directly from a rescue
clause**, not by triggering a live crash through a `Plug.ErrorHandler`: no catch-all
error handler is wired in this requirement, and inventing a crash path would be
testing a mechanism that does not exist yet.

17. `a rescued RuntimeError yields the fixed 500 body` — raises a `RuntimeError` whose
    message carries a fake secret and a fake SQL fragment, rescues it, calls
    `Response.internal_error/1`, and asserts the body equals the fixed expected
    document.
18. `a rescued ArgumentError yields the fixed 500 body` — the same shape with a
    different exception type and a completely different distinctive message.
19. `two exception types give byte-identical 500 bodies` — the criterion's actual
    claim. Produces both bodies inside one test and asserts `body_a == body_b` on the
    raw strings. Cases 17 and 18 alone would not prove this if the expected literal
    were itself wrong; this case compares the two real outputs to each other.
20. `no seeded exception material leaks into the body` — the leak-detection half of
    INV-4, distinct from the identical-across-types half: two bodies could be identical
    to each other and *both* leak the same shared secret.

    **The seeded values must reach an input the function actually observes**, or every
    `refute` is trivially true against every possible implementation and asserts
    nothing (this is what rework 1 corrected: the first version bound the rescued
    exception to `_e`, discarded it, and passed a bare `conn(:get, "/")`, so eight of
    the ten forbidden substrings were values the code under test never saw).
    `internal_error/1` is arity-1 and conn-only, so **the conn is that input**, and
    `leaky_conn/2` loads every field a leaking implementation could plausibly reach
    for: the rescued exception struct, `Exception.message(e)`, `to_string(e.__struct__)`
    and the formatted `__STACKTRACE__` as assigns; a fake Postgres DSN and a debug-flag
    string as request headers; and the secret plus the SQL fragment in the request path
    and query string. `:trace_id` is deliberately *not* assigned — `send_problem/2`
    legitimately reflects that assign into the body, so seeding it would prove nothing.

    Forbidden substrings, each verified reachable-in-principle before being kept —
    shared by both cases: `hunter2` and `db.internal` (DSN header), `SELECT` and
    `tenant_id` (query string), `Elixir.` (the `:error_type` assign is
    `"Elixir.RuntimeError"` / `"Elixir.ArgumentError"`), `stacktrace` (the assign key,
    and the `x-debug-flags` header value); plus, per case only, that case's own
    exception message and module name. Nothing is refuted against a body whose call
    could not have produced it.

    The searched surface is the raw body **plus every decoded JSON string value**:
    `Jason` escapes the quotes in the ArgumentError message on the way out, so a raw
    `String.contains?/2` on the body alone would miss that leak (measured: raw-body
    match `false`, decoded-surface match `true`).

20b. `a fully seeded conn yields the same bytes as a bare conn` — the same claim stated
    positively and at maximum strength: the body produced from the fully seeded conn is
    byte-identical to the one produced from a bare `conn(:get, "/")`. This catches
    reflection of *any* conn field into the detail, not only the enumerated substrings.

### AC4 — 404 byte-identical for never-existed vs. cross-tenant (INV-5)

*"the 404 problem document produced for a resource that never existed and the one
produced for a resource belonging to another tenant are byte-identical, demonstrated
by a test comparing the two serialised bodies."*

21. `never-existed and cross-tenant 404s are byte-identical` — builds two conns that
    differ in everything a handler could plausibly branch on (different request paths,
    and the cross-tenant conn additionally carrying `:tenant_id` and
    `:requested_tenant_id` assigns naming a *different* tenant), sends both through
    `Response.not_found/1`, and asserts the two `resp_body` **strings** are equal —
    byte equality of the serialised bodies, not merely `assert both.status == 404`,
    which is what the handoff explicitly calls out as insufficient.
22. `the router catch-all emits the same 404 body` — the structural half of the
    guarantee. `lib/letflow/router.ex`'s `match _` routes through
    `Response.not_found/1`, so this drives two *unmatched routes* through the real
    router end to end and asserts their bodies are byte-identical to each other and
    to the direct `Response.not_found/1` body. Without this case, AC4 would be proven
    only for direct calls, and a future route that hand-rendered its own 404 would go
    undetected — which is exactly the failure mode INV-5 exists to prevent.

Both cases use fixed literal UUID strings rather than `Ecto.UUID.generate()`, so
nothing in this file depends on randomness (see AC8).

### AC5 — 201 for creation, 204 empty for deletion

*"Letflow.Api.Response's success helpers set 201 for creation and 204 with an empty
body for deletion, each verified by a test asserting the status and (for 204) that the
body is empty."*

23. `created/2 sends 201 with the encoded body` — asserts `status == 201` and that the
    body decodes back to the map passed in (so the helper is not silently dropping the
    body while getting the status right).
24. `no_content/1 sends 204 with an empty body` — asserts `status == 204` and
    `resp_body == ""` (literal empty string, not "falsy" or "small").
25. `no_content/1 sets no content-type header` — a 204 carries no representation, and
    the moduledoc states this explicitly. Asserted as `[] ==
    get_resp_header(conn, "content-type")`. This is the measured behaviour, and it is
    the case most likely to be broken by a well-meaning later refactor that funnels
    `no_content/1` through `send_json/3`.
26. `send_json/3 honours an arbitrary status` — `send_json/3` is the shared primitive
    behind `ok/2` and `created/2` and is the function `Letflow.Router` now delegates
    to; a test at 202 proves it is genuinely status-parameterised rather than
    incidentally correct at the two statuses its wrappers use.

### Trace-id precedence (requirement text: the `""`-defaulting trace id field)

27. `an explicit non-empty trace_id wins` — branch 1 of `errors.zig:54`: a problem
    document that already carries a trace id keeps it even when `conn.assigns` names a
    different one. Asserted with *both* set to different values, so a naive
    implementation that always preferred the conn would fail.
28. `conn.assigns[:trace_id] is used when the document is empty` — branch 2.
29. `trace_id falls back to an empty string` — branch 3: neither source set. Guards
    against `nil` reaching the JSON body as `null` instead of `""`.

### AC6 — moduledoc states the translation and the divergence

*"the moduledoc states the Zig-to-Elixir translation explicitly: that response.zig's
HandlerResult struct is replaced by conn-threading functions, and whether Letflow's
problem+json content type diverges from R-Co's."*

30. `the Response moduledoc records the translation and divergence` — reads the
    compiled documentation chunk with `Code.fetch_docs/1` (the real artefact a reader
    or `mix docs` sees, not the source file text) and asserts the moduledoc mentions
    `HandlerResult`, that it is not ported as a struct, that functions take and return
    a conn, that `application/problem+json` is used, and that this **diverges** from
    R-Co. Asserting on `Code.fetch_docs/1` rather than on file contents means the test
    still holds if the file is moved or reformatted, and fails if the moduledoc is
    deleted during a later refactor — which is the actual risk AC6 guards.

### Additional guard cases (not required by any single AC, but load-bearing)

31. `serialise/1 escapes control characters in detail` (error_test) — the other half of
    the escaping story from case 12: a raw newline inside a JSON string literal is
    invalid JSON outright, so this is a stricter check than the quote/backslash case.
32. `send_problem/2 sends at the document's status` (response_test) — `send_problem/2`
    is the primitive every wrapper funnels through; it must send at the *document's
    own* status rather than one the sending function picks.
33. `every wrapper sends a full problem document` (response_test) — complements AC1's
    builder-level coverage by proving each `Response` wrapper actually routes through
    the corresponding `Error` constructor instead of emitting a bare status.
34. `Error records the same translation notes` (response_test) — AC6's obligations
    restated on `Letflow.Api.Error`, which is where a reader looking up the problem
    document shape lands first.

## 3. AC7 — combined describe + test name lengths

*"every combined describe+test name is under 200 characters."*

`docs/anti-patterns.md` records four separate occurrences in this project of ExUnit's
255-character `describe <> test` limit being exceeded, each one a compile-time
`SystemLimitError` that failed the **entire** suite rather than a single test.

All 35 names across both files were measured after writing, and **re-measured after
rework 1** (a script that extracts every `describe`/`test` string and reports
`length(describe <> " " <> test)`). The longest combined name is **81 characters**, the
case added in rework 1:

    internal_error and INV-4 a fully seeded conn yields the same bytes as a bare conn

The next longest is 75 (`serialisation contract serialise/1 escapes quotes and
backslashes in detail`), then 71 twice. 81 is well under the 200-character ceiling this
handoff sets and under a third of ExUnit's hard limit. All requirement and spec citations are `#`
comments above the tests, never inside a name string.

## 4. AC8 — determinism

No test in either file reads the wall clock, calls `DateTime.utc_now/0`,
`:rand`, `Ecto.UUID.generate/0`, or any other unseeded source. The two UUIDs used in
the INV-5 cases are fixed literals chosen precisely so the "different request path"
variation stays deterministic. Both files are `async: true` and share no state — no
database is touched, since both modules under test are pure/conn-threading with no
Ecto dependency (`Letflow.DataCase` is deliberately not used, matching
`test/letflow/router_test.exs`'s precedent for DB-free surface).
