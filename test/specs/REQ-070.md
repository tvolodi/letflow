# Test Spec: REQ-070 — Router Decomposition

**Requirement:** REQ-070 (stage S4) — Replace `lib/letflow/router.ex`'s flat route
table with the decomposed structure (`ApiPipeline` + sub-router stubs) that the rest
of S4 mounts into. GET /health preserved byte-compatibly. Shared middleware declared
in exactly one place. Unmatched routes return RFC 9457 404.

**Test tier:** unit + file-inspection (`Plug.Test`-driven conn routing, plus
source-assertion and grep-based structural invariant checks).

**Design:** `lib/letflow/design/req070-router-decomposition.md`.

**Test file:** `test/letflow/router_test.exs` (REQ-070 tests added to the existing
REQ-046 module; the existing module already uses plain `ExUnit.Case, async: true` with
no Ecto sandbox, making it the correct home for all six ACs).

---

## 1. Acceptance criteria and test mapping

### AC1 — GET /health returns 200 + `{"status":"ok"}` with no DB dependency

**Criterion:** `GET /health` returns HTTP 200 with JSON body `{"status":"ok"}` and
requires no Ecto connection.

**Why this test exists:** The health endpoint serves as the deploy/redeploy-test.sh
liveness probe. It must work even when the database is unavailable. The test documents
this by running inside a plain `ExUnit.Case` module that never calls
`Ecto.Adapters.SQL.Sandbox.checkout/1` — if the handler ever adds a DB call, that call
will crash or block rather than silently pass, making the missing sandbox observable.

**Test case:**
`describe "REQ-070 AC1" / "GET /health returns 200 without Ecto.Sandbox checkout"`

- Calls `GET /health` via `Plug.Test.conn/2` + `Letflow.Router.call/2`
- Asserts `conn.status == 200`
- Asserts `Jason.decode!(conn.resp_body) == %{"status" => "ok"}`

### AC2 — Sub-router isolation: mount `Letflow.Routers.Identity` directly

**Criterion:** A sub-router can be called independently of `Letflow.Router` and
`Letflow.Plugs.ApiPipeline`. Calling it directly still produces valid RFC 9457 404
responses with the correct `Content-Type`.

**Why this test exists:** The decomposition is only useful if each sub-router is a
self-contained `Plug` that compiles and runs independently. A test that mounts the
top-level router and sends a request to `/api/v1/identity/…` does not prove isolation
— the top-level router's middleware might provide something the sub-router silently
depends on. Calling `Letflow.Routers.Identity.call/2` directly (no ApiPipeline, no
authentication middleware) proves the stub truly has no hidden upstream dependency.

**Test case:**
`describe "REQ-070 AC2" / "Letflow.Routers.Identity compiles and handles requests independently of the top-level router"`

- Calls `conn(:get, "/some-path") |> Letflow.Routers.Identity.call(@identity_opts)`
- Asserts `conn.status == 404`
- Asserts `get_resp_header(conn, "content-type") |> hd() =~ "application/problem+json"`

### AC3 — Unrouted path returns RFC 9457 404 via top-level router

**Criterion:** Any request whose path is not `/health` and not under `/api/v1` receives
HTTP 404 with `Content-Type: application/problem+json` and a body containing all four
RFC 9457 required members (`type`, `title`, `status`, `detail`).

**Why this test exists:** The old format was `{"error":"not_found"}` (application/json).
The new contract is RFC 9457 (application/problem+json). This test guards both the
Content-Type header (the Letflow divergence from R-Co documented in
`Letflow.Api.Response`'s moduledoc) and the body shape (four required RFC 9457 fields).
The existing "unknown route still 404s" test already checks the full body value via
`@not_found_body`; these tests add the missing Content-Type assertion and make the
RFC 9457 field presence explicit.

**Test cases:**
`describe "REQ-070 AC3" / "Content-Type is application/problem+json"`

- Calls `GET /nonexistent-path-xyz` via the top-level router
- Asserts `get_resp_header(conn, "content-type") |> hd() =~ "application/problem+json"`

`describe "REQ-070 AC3" / "body contains all four RFC 9457 required members"`

- Asserts `Map.has_key?(body, "type")`, `"title"`, `"status"`, `"detail"`

### AC4 — Plug.Parsers and AuthPipeline each declared in exactly one lib/ file

**Criterion:** The shared middleware elements that must not be duplicated across
sub-routers each have exactly one registration call in `lib/`.

**Why this test exists:** The requirement's core invariant is "shared middleware chain
declared in exactly one place." A future developer adding a sub-router might copy the
`plug(Plug.Parsers, ...)` boilerplate from `api_pipeline.ex`, unknowingly duplicating
the middleware chain. This test makes that error immediately visible at test runtime.

The test searches for the *invocation form* (`"plug(Plug.Parsers,"` and
`"plug(Letflow.Plugs.AuthPipeline)"`) rather than the bare module name, because:
- `"Plug.Parsers"` appears in `safe_json_parser.ex` and `content_type.ex` (module doc
  references), which would cause false positives.
- `"AuthPipeline"` appears in 6 files (auth_pipeline.ex definition + 5 doc references).

**Test cases:**
`describe "REQ-070 AC4" / "Plug.Parsers invoked in exactly one lib/ file"`

- `Path.wildcard("lib/**/*.ex")`, filters for `"plug(Plug.Parsers,"` substring
- Asserts `length(matches) == 1` and `hd(matches) =~ "api_pipeline"`

`describe "REQ-070 AC4" / "AuthPipeline plug registered in exactly one lib/ file"`

- Filters for `"plug(Letflow.Plugs.AuthPipeline)"` substring
- Asserts `length(matches) == 1` and `hd(matches) =~ "api_pipeline"`

### AC5 — router.ex lists all 11 deferred routes and states readiness not-ported

**Criterion:** `lib/letflow/router.ex`'s moduledoc table names all 11 deferred
sub-router modules and explicitly states that the readiness endpoint is not ported.

**Why this test exists:** The deferred-route table and the readiness note are the
primary documentation of what S4 does NOT yet implement. If `router.ex` is later
edited and one of the 11 names is accidentally removed or misspelled, this test will
fail immediately, flagging that the documentation is out of sync with the decision
record. Source-assertion tests for prose documentation are the only way to enforce
that structured information stays present across edits.

**Test cases:**
`describe "REQ-070 AC5" / "all 11 deferred sub-router module names are listed"`

- Reads `lib/letflow/router.ex` as text at runtime
- Asserts each of the 11 deferred module names appears as a substring

`describe "REQ-070 AC5" / "readiness endpoint is documented as not ported"`

- Asserts `String.contains?(source, "not ported")`

### AC6 — router.ex references decision record and amendment date

**Criterion:** `lib/letflow/router.ex` references `0001-web-framework.md` and the
`2026-08-20` amendment date, tying the implementation to its decision record.

**Why this test exists:** Decision record traceability — if the file is regenerated
or wholesale-replaced without preserving the decision record reference, this test
fails. This catches "clean slate" rewrites that lose the provenance comment.

**Test cases:**
`describe "REQ-070 AC6" / "router.ex references 0001-web-framework.md"`

- Asserts `String.contains?(source, "0001-web-framework.md")`

`describe "REQ-070 AC6" / "router.ex references the 2026-08-20 amendment date"`

- Asserts `String.contains?(source, "2026-08-20")`

## 2. What these tests do NOT cover (and why)

- **Integration through `ApiPipeline` to sub-routers:** That is the concern of REQ-073
  through REQ-082 (the per-sub-router requirement set). Testing `GET /api/v1/identity/…`
  end-to-end here would require the authentication middleware to pass, which is a
  REQ-113/114 concern.
- **`GET /health` under load or concurrent requests:** Performance and concurrency
  testing is out of scope for ExUnit unit tests.
- **`ApiPipeline`'s middleware order beyond Plug.Parsers + AuthPipeline:** The order of
  the remaining plugs (`TenantStatus`, `:match`, `:dispatch`) is covered by
  `test/letflow/plugs/tenant_status_test.exs` and the `api_pipeline` sub-router tests.
