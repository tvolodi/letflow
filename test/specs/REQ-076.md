# REQ-076 — Identity routes 4/4: API tokens, role registry, tenant onboarding

Design doc: `lib/letflow/design/req076-identity-tokens-roles-onboarding.md`.

Requirement text (context.requirement_text, verbatim intent): ship API-token
issue/list/revoke, the role-registry HTTP routes, and tenant self-service onboarding,
matching R-Co's `identity.zig`/`onboarding.zig` behavior where it is actually load-bearing
(INV-1, INV-4, INV-5).

Eight acceptance criteria (verbatim from `task.acceptance_criteria`), each mapped below to
the concrete test case(s) that would fail if the criterion were violated.

---

## AC1 — plaintext returned once, subsequent GET has no token field (INV-4)

> creating an API token returns the plaintext exactly once in the 201 body, and a
> subsequent GET of that token returns metadata with no token field, demonstrated by two
> tests

**Why this needs two tests, not one:** the 201 body and the later GET body are built by two
different response-shape functions (`token_created_map/2` vs `token_map/1`) — a bug that
accidentally reused `token_created_map/2` for the list/get path, or that persisted the
plaintext and let a later query re-derive it, would only be caught by asserting the GET
path's *absence* of the field, not just the 201 path's presence.

- `Letflow.Routers.IdentityTest` `"POST /tokens returns 201 with a plaintext token field
  matching the lf_tok_ shape (AC1a)"` — asserts the 201 body's `"token"` key is a non-empty
  string matching `~r/^lf_tok_[0-9a-f]{64}$/`.
- `Letflow.Routers.IdentityTest` `"GET /tokens after creation has no token field and no
  value equal to the plaintext anywhere in the response (AC1b)"` — creates a token, then
  `GET /tokens`, decodes the JSON body, asserts no key named `"token"` exists on any item
  and asserts the raw response body string does not contain the captured plaintext
  substring (belt-and-suspenders, catches a plaintext leaking under a differently-named
  key too).
- Same pair repeated against `DELETE /tokens/:id`'s response body (design §7.1's own "or
  `DELETE ... ; GET`" alternative — both are exercised here since they're cheap once the
  fixture exists).

## AC2 — persisted row never equals the plaintext in any column (INV-4)

> the persisted token record does not contain the plaintext in any column, verified by
> querying the row and asserting no column equals the returned plaintext

**Why a full-struct sweep, not just `token_hash`:** the criterion says "no column," not
"the hash column specifically" — a naive test that only checked `token_hash != plaintext`
would miss a bug that accidentally also wrote the plaintext into, e.g., `name` (which is
caller-invisible in the response but still a real on-disk leak).

- `Letflow.IdentityTest` `"create_token/3 — the persisted row's own columns never equal the
  plaintext, checked across every field (AC2)"` — re-selects the row via `Repo.get!/3`
  (never trusts the in-memory `{:ok, %{token: token}}` reply) and asserts every value in
  `Map.from_struct(persisted)` is `!= plaintext`.

## AC3 — plaintext in no log line, no error body (INV-4)

> the token plaintext appears in no log line and no error body, verified by capturing logs
> across a successful creation and a deliberately failed one

- `Letflow.Routers.IdentityTest` `"a token's plaintext never appears in captured logs or in
  either response body, across a successful creation and a deliberately failed one (AC3)"`
  — `ExUnit.CaptureLog.capture_log/1` wraps (a) a successful `POST /tokens` and (b) a
  second `POST /tokens` for the same user with an already-known-bad `roles` entry (outside
  the five-role allow-set), both against a token generated in-test so its plaintext value
  is known ahead of time to search for; asserts `refute log =~ plaintext` and
  `refute resp_body =~ plaintext` for both requests.

## AC4 — revoked token rejected 401 on the very next request, no sleep/cache-flush

> a revoked token is rejected with 401 on the very next request, demonstrated by a test
> that revokes and immediately retries with no sleep or cache flush

**Why two tests (primitive + HTTP):** `verify_api_token/2`'s own live-lookup mechanism is
the actual guarantee, but nothing calls it over HTTP without `Letflow.Plugs.AuthPipeline`'s
new API-token branch (design §3.5) — a primitive-only test could pass while the HTTP wiring
was broken/missing, which is exactly what CODE-DESIGN-VALIDATOR's rework instruction
(design §3.4) flagged as the AC4 gap in attempt 1.

- `Letflow.IdentityTest` `"verify_api_token/2 — a revoked token is rejected on the very
  next verification call, no sleep (AC4 primitive)"`.
- `Letflow.ApiTokenAuthPipelineTest` `"a revoked API token is rejected with 401 on the very
  next HTTP request through the real Letflow.Router pipeline, no sleep or cache flush
  (AC4)"` — mints a token via `Identity.create_token/3`, makes a real request through
  `Letflow.Router.call/2` (full `AuthPipeline` + `TenantStatus` + `Routers.Identity` chain)
  with `Authorization: Bearer <plaintext>` + `X-Tenant-Slug: <tenant.slug>`, asserts 200,
  calls `Identity.revoke_token/2`, repeats the identical request, asserts 401 — same
  `plaintext`, same headers, no `Process.sleep/1`, no cache-clear call between the two.

## AC5 — tenant isolation (INV-1)

> a token created in tenant A cannot authenticate a request for tenant B's resources

- `Letflow.IdentityTest` `"verify_api_token/2 — a token minted under tenant A's schema
  cannot verify against tenant B's schema (AC5, INV-1)"` — creates a token under tenant A's
  `prefix:`, asserts it verifies under tenant A's own prefix, asserts `{:error, :invalid}`
  (row genuinely absent, not a status check) under tenant B's prefix.
- `Letflow.ApiTokenAuthPipelineTest` `"a tenant-A-minted token sent with tenant B's
  X-Tenant-Slug header is rejected 401, not authenticated as a tenant-B user (AC5, INV-1,
  HTTP level)"` — same token, same plaintext, `X-Tenant-Slug` pointed at tenant B instead of
  tenant A; asserts 401 through the real pipeline.

## AC6 — `handleUpsertRole`'s constraint matches R-Co's actual behaviour

> handleUpsertRole's constraint on role names matches R-Co's actual behaviour, with the
> observed constraint named in the moduledoc and a test covering both an accepted and a
> rejected role name

Design §5.1 confirms by direct read of `role_registry.zig` that R-Co's constraint is
**format-only** (non-empty, ≤128 Unicode codepoints, no ASCII control characters) — no
check against the five-value `auth.Role` enum. `Letflow.Identity.RoleRegistry.upsert_role/2`
(REQ-020, unchanged) already enforces exactly this. The moduledoc statement lives on
`Letflow.Routers.Identity` (§9a) — see that module's "Role registry constraint" section.

- `Letflow.Identity.RoleRegistryTest` `"a role name outside the five auth.Role enum values
  (e.g. CUSTOM_APPROVER) is accepted — format-only constraint, no enum-membership check
  (REQ-076 AC6 accept case)"` — the load-bearing new case: `"CUSTOM_APPROVER"` is not one of
  `PLATFORM_ADMIN`/`PROCESS_DESIGNER`/`PROCESS_OPERATOR`/`TASK_WORKER`/`AGENT_RUNNER`, and
  is accepted anyway.
- Reject case: already covered by this file's pre-existing "upsert_role/2 — name validation
  rejection modes" describe block (empty name, >128 codepoints, control character) — that
  coverage is REQ-020's own, reused here rather than duplicated, since AC6 asks for "a"
  rejected name, not a new rejection mode.
- `Letflow.Routers.IdentityTest` `"POST /roles accepts a role name outside the five-role
  enum and returns 200, not 201 (AC6, OQ-5)"` — router-level companion proving the HTTP
  status code design §10 OQ-5 flags (200, matching R-Co's own upsert semantics).

## AC7 — GET onboarding by unknown hostname is indistinguishable from exists-but-not-caller's (INV-5)

> GET onboarding by an unknown hostname returns a response indistinguishable from one for a
> hostname whose tenant exists but is not the caller's, demonstrated by comparing the two
> responses

Design §8.4 resolves the population this protects: a caller **lacking** `:TenantsManage`
(every non-PLATFORM_ADMIN caller) — `Authorization.evaluate_access/2` denies before any
`Repo` call runs, for either hostname, so the two responses are byte-identical 403s with
equal (zero) DB round trips either way.

- `Letflow.Routers.OnboardingTest` `"GET /onboarding?hostname= for a never-bound hostname
  and for a hostname bound to a real other tenant are byte-identical 403s for a caller
  lacking :TenantsManage (AC7, INV-5)"` — full HTTP dispatch via `Letflow.Router.call/2`
  with a `PROCESS_DESIGNER`-only API token (lacks `:TenantsManage`); asserts both responses
  are 403 with identical `resp_body`.

## AC8 — onboarding creates a tenant via `Letflow.TenantProvisioning`, not a second path

> onboarding creates a tenant via Letflow.TenantProvisioning rather than a second
> provisioning path, confirmed by inspection and stated in the moduledoc

Inspection: `lib/letflow/routers/onboarding.ex`'s `provision_and_bind/4` calls
`TenantProvisioning.provision_tenant_schema/1` then `TenantProvisioning.replay_migrations/2`
— the identical two-call sequence `Letflow.Routers.Tenants`'s `POST /tenants` handler uses
(REQ-075 §7.1); no other schema-creation code path exists in `Letflow.Routers.Onboarding` or
`Letflow.Identity.create_onboarding/1`. Stated in `Letflow.Routers.Onboarding`'s moduledoc
("One tenant-provisioning path, not two").

- `Letflow.Routers.OnboardingTest` `"POST /onboarding actually provisions a real, queryable
  Postgres schema for the new tenant via the shared TenantProvisioning path (AC8)"` — full
  HTTP dispatch via `Letflow.Router.call/2` with a `PLATFORM_ADMIN` token; asserts 201, then
  queries `information_schema.tables` directly against the schema name derived from the
  returned `tenant_id`, proving the schema/migration side effect actually happened (same
  proof pattern REQ-075 §7.1 AC4 already established) rather than merely that a `tenants`
  row exists.

## AC9 — idempotent partial-provisioning recovery entry point (ISS-0230, SCOPE EXTENSION, run `WF02-REQ076-20260822`)

> a tenant left half-provisioned by a replay failure is recoverable by an idempotent
> recovery entry point this requirement adds in its own orchestration layer -- never as a
> function inside Letflow.TenantProvisioning that calls both primitives, per req022 section
> 3.2's No implicit chaining invariant -- demonstrated by a test that forces
> replay_migrations/2 to fail, asserts the tenants row survived with migrations_applied_at
> NULL and no rollback occurred, then invokes the recovery entry point and asserts the
> schema is fully migrated with migrations_applied_at set and exactly one tenant_schemas
> row, then invokes the SAME entry point a second time against the now-healthy tenant and
> asserts it returns success and leaves the state unchanged (still exactly one
> tenant_schemas row, no error, no duplicate schema) -- the second invocation is what
> demonstrates idempotence and is not optional (ISS-0230)

**Why one test covering the whole sequence, not several smaller ones:** the acceptance
criterion is a single causal chain (a real failure -> survival -> repair -> convergence ->
re-invocation -> unchanged convergence) where the second invocation's assertions only mean
anything in light of the state the first invocation already produced. Splitting it into
independent tests would let each one pass in isolation while an ordering/interaction bug
(e.g. the recovery entry point silently depending on being called exactly once) went
undetected. This mirrors `test/letflow/tenant_provisioning_test.exs`'s own established style
(one real-Postgres, non-DataCase-sandboxed test per acceptance criterion's causal chain).

**Failure mechanism, not invented here:** reuses the exact precedent
`test/letflow/tenant_provisioning_test.exs`'s `replay_migrations/2` tests already
established — `replay_migrations/2`'s optional second argument (`migration_source`) accepts
a `[{version, module}]` list overriding the default production manifest; passing a module
whose `change/0` raises makes `Ecto.Migrator.run/4` raise, which `replay_migrations/2`'s own
`try/rescue` (confirmed at `lib/letflow/tenant_provisioning.ex:325-326`) converts into a
clean `{:error, {:migration_failed, exception}}` rather than crashing the test process — the
same clean-failure contract `WF03-ISS0230-20260822` measured against real Postgres and
recorded in `Letflow.TenantProvisioning`'s own moduledoc. A new fixture,
`test/support/req076_broken_migration_fixture.ex`, provides the raising `change/0` (kept
separate from `test/support/req022_migration_fixture.ex`, which deliberately no-ops and must
keep succeeding for REQ-022's own tests).

**Why the recovery call itself uses the real default manifest, not the broken fixture:**
`Letflow.TenantOnboarding.provision_and_migrate/1` always calls `replay_migrations/2` at
arity 1 (design §11.2.1 step 2) — the recovery entry point converges the tenant onto the
real shipped migration manifest, never a caller-supplied one. The test's own call to
`TenantOnboarding.recover_provisioning/1` therefore exercises this exact real-manifest
behavior, not a second broken-fixture replay.

- `Letflow.TenantOnboardingTest`, describe `"AC9: recover_provisioning/1 (ISS-0230)"`, test
  `"recovers a half-provisioned tenant and is idempotent on a second call"` — real-Postgres
  test (name kept short per ISS-0030's 255-char combined-atom limit; full rationale here) (matching `tenant_provisioning_test.exs`'s `Sandbox.mode(..., :auto)` +
  manual `on_exit/1` cleanup pattern, `async: false`, since `Ecto.Migrator.run/4` needs a
  second live connection the DataCase sandbox transaction cannot supply):
  1. Inserts a real `Tenant` row and calls `TenantProvisioning.provision_tenant_schema/1`
     directly (real `CREATE SCHEMA`).
  2. Calls `TenantProvisioning.replay_migrations/2` with the broken fixture as the
     `migration_source` argument; asserts `{:error, {:migration_failed, _}}`.
  3. Asserts survival: `Repo.get(Tenant, tenant.id)` still returns the tenant row (no
     rollback), `Repo.get_by(Registration, tenant_id: tenant.id).migrations_applied_at ==
     nil`, and exactly one `Registration` row exists for that `tenant_id`.
  4. Calls `TenantOnboarding.recover_provisioning(tenant.id)`; asserts `{:ok, %Registration{
     migrations_applied_at: %NaiveDateTime{}}}`.
  5. Asserts full convergence: a real production table (`onboarding_registry` — chosen
     because it is a `public`-schema, always-migrated table whose presence is orthogonal to
     tenant-scoped migrations, so this assertion instead spot-checks a genuinely
     tenant-scoped table created by the real manifest, `users`, under the tenant's own
     schema via `information_schema.tables`), still exactly one `Registration` row, and
     `Repo.get(Tenant, tenant.id).status == :active` (AC10's status-flip, confirmed here
     too since AC9's own recovery path is what performs it).
  6. Calls `TenantOnboarding.recover_provisioning(tenant.id)` a **second** time (mandatory
     per the acceptance criterion's own text); asserts `{:ok, %Registration{}}` again, still
     exactly one `Registration` row (no duplicate), and `status` still `:active` — the
     second call's success with unchanged cardinality is what demonstrates idempotence.

## AC10 — the `:migrating` tenant-status decision across onboarding (ISS-0230, SCOPE EXTENSION, run `WF02-REQ076-20260822`)

> the tenant status a half-provisioned tenant carries between creation and successful
> replay is decided explicitly and stated in the moduledoc, and BOTH request directions
> against a tenant in that state are asserted by tests -- a write (POST) and a read (GET) --
> because Letflow.Plugs.TenantStatus gates write methods only and passes GET/HEAD through
> with no DB query at all (tenant_status.ex @write_methods; REQ-071 AC4 tests), so a
> :migrating half-provisioned tenant would still serve reads against an empty schema; the
> moduledoc must state what a read receives and why that is acceptable, and the resulting
> rule must not be a second status rule conflicting with TenantStatus (ISS-0230)

**Decision under test (design §12.1/§12.2, stated in `Letflow.TenantOnboarding`'s
moduledoc):** reuse `:migrating` verbatim, zero changes to `Letflow.Plugs.TenantStatus`.
Both directions are tested against a tenant that is genuinely HTTP-reachable while
`:migrating` — an already-fully-provisioned `TenantFixture.provisioned_tenant!/1` tenant
administratively flipped back to `:migrating` via `Tenant.status_changeset/2` — per the
design's own argument (§12.2) that the truly-empty-schema state cannot carry a real,
`AuthPipeline`-accepted credential at all (both authentication mechanisms query a
tenant-schema table that does not exist until migration completes), so it cannot be the
subject of an authenticated HTTP test in the first place. Testing the reachable state is
therefore the correct demonstration of "what a read/write against `:migrating` actually
does," not a weaker substitute for the unreachable one.

**Why two tests, not one:** the write and read paths hit two different branches of
`TenantStatus.check_tenant_status/2` (`conn.method in @write_methods and tenant.status ==
:migrating` vs. the `true -> conn` pass-through) — a regression in either branch alone
(e.g. `@write_methods` accidentally including `GET`, or the write branch's guard being
dropped) would only be caught by a test exercising that specific method.

- `Letflow.Routers.OnboardingScopeExtensionTest` `"AC10 write: POST /identity/tokens against
  a :migrating tenant with a real, valid token is rejected 503 by TenantStatus's existing
  write-pause, unchanged (AC10, ISS-0230)"` — full HTTP dispatch via `Letflow.Router.call/2`
  (real `AuthPipeline` -> `TenantStatus` -> `Letflow.Routers.Identity` chain) with a real
  API token minted for a `PLATFORM_ADMIN` user of a `provisioned_tenant!/1` tenant, then that
  tenant flipped to `:migrating`; asserts `conn.status == 503` and the decoded body's
  `"error"` field is `"tenant_migrating"` — the same TenantStatus rejection shape REQ-071's
  own tests already pin, demonstrating no second, REQ-076-specific status rule was added.
- `Letflow.Routers.OnboardingScopeExtensionTest` `"AC10 read: GET /identity/tokens against
  the same :migrating tenant with the same token passes through unchanged and serves
  existing data (AC10, ISS-0230)"` — same tenant/token, `GET` instead of `POST`; asserts
  `conn.status == 200` and the decoded body has an `"items"` key — proving `TenantStatus`'s
  documented write-pause/read-pass-through split holds for a `:migrating` tenant regardless
  of how it entered that status (creation-time `:migrating` per this extension, or an
  administrative flip, are indistinguishable to `TenantStatus`, which is exactly the design's
  "not a second status rule" requirement).

## Isolation / no-pollution notes

Every test below builds its own unique tenant (`TenantFixture.provisioned_tenant!/1` with a
distinct `slug_prefix`), unique hostname (`System.unique_integer/1`-suffixed), and unique
user — no shared hardcoded tenant/hostname/user values, matching this codebase's established
`test_developer_guide.md` "no test pollution" convention. No test depends on wall-clock time
beyond `DateTime.utc_now/0`-relative offsets (e.g. "1 second in the future" / "1 second in
the past" for `expires_at`), and no test depends on unseeded randomness — the plaintext
token value itself is real crypto-random output, but every assertion about it treats it as
an opaque captured value, never a value the test tries to predict.
