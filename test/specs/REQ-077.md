Test file: `test/letflow/routers/req077_promotion_pipeline_test.exs`.

Design doc: `lib/letflow/design/req077-promotion-pipeline-routes.md` (§12 is the
test-specification section this file implements directly; every `describe` block below
cites the design section it covers).

All ten routes (R1-R10) are live on this branch — REQ-140 (platform-event-appender)
shipped and ELIXIR-DEV wired the real `Letflow.EventStore.PlatformEvents` appenders into
R7/R8/R9/R10 (confirmed by reading `lib/letflow/routers/promotions.ex`,

## AC1 — "each of the six route modules has at least one end-to-end test through the
real router ... with promotion_review.zig's five handlers each covered individually"

Ten `describe "AC1: ..."` blocks, one per route (R1-R10), each dispatching directly
against the real sub-router (`Letflow.Routers.Promotions.call/2`,
`.Definitions.call/2`, `.Tenants.call/2`) and asserting both HTTP status and the exact
`Map.keys/1` set of the JSON body against the literal allowlist named in design §7.
R1/R4/R5/R6/R7 (`promotion_review.zig`'s five handlers) each get their own dedicated
test, satisfying the "covered individually" clause explicitly. R2 (`promotions.zig`),
R3 (`promotion_read.zig`), R8 (`promotion_assertion.zig`) each get their own test too, so
all six R-Co source modules are covered per design §1's own module→route mapping.

Dispatch mechanism is sub-router dispatch with `conn.assigns.auth_context` set by hand
— design §12.0's own SETTLED decision, matching the established precedent from
REQ-073/074/075's own router test files (`tenants_test.exs`, `identity_test.exs`).
`Letflow.Plugs.Authorize` is a real, live plug in the dispatch chain (mounted by `use
Letflow.Api.AuthorizedRouter`) and resolves `conn.assigns.scoped_opts` itself from the
hand-set `auth_context` — no test sets `scoped_opts` directly.

R7's test additionally re-reads the target tenant's ACTIVE `process_definitions` row
after a real submit→approve→apply flow, proving the version pointer actually moved (not
just that the HTTP layer returned 200). R9's test does the same for the rollback
target. R10's test does the same for the newly-created target-tenant row.

## AC2 — assertion-run idempotency (REQ-040's contract)

`describe "AC2: repeat POST .../run-assertions is idempotent"`. Two real POSTs with the
identical `(review_id, plan_digest, artifact)` triple through the real router, real
`Letflow.SandboxPool` claim/replay/release, asserting:
- `r1.status == r2.status`
- `r1.resp_body == r2.resp_body` (byte-identical — no `trace_id` in a success body, per
  design §8.1, so no stripping is needed)
- `Repo.aggregate(from(r in PromotionAssertionRun, where: r.review_id == ^review_id),
  :count, prefix: <target schema>) == 1` — the AC's own named check.

Why this actually exercises the mechanism and not a vacuous no-op: the artifact/fixture
payload is a real, well-formed `PromotionArtifact` JSON body (one assertion with a
non-empty payload, one valid `process_definitions` fixture row satisfying every NOT NULL
column) so the first call performs a genuine sandbox claim + fixture load + replay, not
an early validation-error short-circuit.

## AC3 — per-tenant `plan_digest` uniqueness (REQ-064's contract)

`describe "AC3: ..."`. Two independent tenant pairs (`source_a`/`target_a`,
`source_b`/`target_b`), each source given an active definition with the **same graph
content** (different `process_key` strings — deliberate, since `compute_plan_digest/1`
hashes only `plan.entries`, design §8.2, so the digests coincide despite the different
process keys, proving the property is really about entry content, not a name match).
Submits from each tenant pair, asserts:
- both 201
- `plan_digest` equal across the two responses
- `review_id` different
- `Repo.aggregate(PromotionReview, :count, prefix: <schema>)` is exactly **1** for
  **each** tenant's own schema separately (never a combined/global count — a global
  count of 2 would also pass while proving nothing about isolation, design §12.3's own
  warning).

## AC4 — approving an already-applied review

`describe "AC4: ..."`, two tests:

1. Drives a review to `:applied` through the real HTTP routes (submit → approve →
   apply), captures the target's ACTIVE `process_definitions` row (id + version) before
   a second approve attempt, then asserts the second approve is 409 with the exact
   literal detail (`"review is not in a state that permits this transition"`), the
   review row is still `:applied`, and the target definition's `id`/`version` are
   byte-identical before/after — this is AC4's own three-part wording, verified
   directly against real rows, not inferred from the HTTP status alone.
2. **Gate-ordering pin** (design §5.3/§6.1/§12.4's own explicit requirement): the
   original requester attempting to approve their OWN already-`:applied` review gets
   **403** (self-approval), not 409 — because `approve_review/4`'s self-approval gate
   runs before its status pre-check. This is a real regression trap: if a future change
   reordered those two gates, this test (not merely the first one) would catch it,
   since the first test uses a non-requester actor and would still see 409 either way.

## AC5 — four explicit cross-tenant tests (INV-5)

`describe "AC5: ..."`, one `setup` block builds tenant A's review once; four `test`s
(R4/R5/R6/R7) each call tenant B against A's review id AND against a freshly generated,
never-issued UUID, asserting both are 404 and their JSON bodies are byte-identical after
stripping `trace_id` (the field that legitimately differs per request, matching the
convention `test/letflow/routers/onboarding_test.exs:223` already established). A fifth
test (not AC5-required, named because design §5.2/§3.2 call it out as belonging to the
same set) does the same for a malformed non-UUID id.

## Design §12.7 — the 6-status × 3-operation matrix (§6.2)

`describe "design §6.2/§12.7: ..."`, six tests, one per `PromotionReview.status()`
value, seeded via `PromotionReviewStore`'s own transition functions directly (design
§12.7's own prescribed shape) rather than driving every state through HTTP. The
`:pending_review` row needs three independent seeded reviews (approve and reject both
mutate the row on success, so a shared row would corrupt the next column's
precondition); the other five rows are single-review-reused-across-all-three-columns,
safe because a 409 never mutates the row.

The `:approved` row's `apply` column (the matrix's third 200 cell) is **deliberately not
re-driven here** — it needs a real target-tenant-eligible source `process_definitions`
row to actually reach 200, and that exact path is already covered end-to-end by the
"AC1: R7" and both "AC4" tests. Re-deriving it a third time with a synthetic
(non-persisted) plan would only ever hit `:source_definition_missing` → 409, which is a
different cell's mechanism, not this one's.

## Design §12.8 — the `:Unknown`/PLATFORM_ADMIN-only pinning test

`describe "design §12.8: ..."`, four tests:
1. All ten path templates from design §1 resolve to
   `Authorization.endpoint_policy_key/2 == :Unknown` — pins the fallthrough so a later
   addition of a real clause for any of these paths is forced to be a deliberate,
   visible change (the test fails immediately) rather than a silent re-gating.
2. Every non-`PLATFORM_ADMIN` role, including holding no role at all, is `Deny403` on
   `:Unknown`.
3. `PLATFORM_ADMIN` is `Allow` on `:Unknown`.
4. One end-to-end denial through the real router: a `PROCESS_DESIGNER` caller gets 403
   with the exact `"insufficient permissions"` detail on `POST /promotions/plan`, and
   the response body has no `entries` key at all (full-body proof no plan data leaked
   past the gate).

## Design §12.9 — full-stack smoke test

`describe "design §12.9: ..."`, one test dispatching through `Letflow.Router.call/2`
(the whole pipeline — `Plug.Parsers`, trace-id assignment, `AuthPipeline` with a real
`Bearer valid-test-token`, `TenantStatus`, the `/promotions` forward, the sub-router's
own match/dispatch) rather than a sub-router. This is the one gap sub-router dispatch
cannot close on its own (every other test in this file hand-sets `auth_context`, so none
of them would catch a real disagreement between `AuthPipeline`'s claim→roles mapping and
what the rest of the suite assumes). Asserts 403, `auth_context.roles == ["VIEWER"]`
(the token double's real, pinned output), and no plan data in the denial body. Mirrors
`test/letflow/plugs/api_pipeline_integration_test.exs`'s own established
`insert_tenant_for_realm!/1` fixture pattern exactly, reused rather than reinvented.
