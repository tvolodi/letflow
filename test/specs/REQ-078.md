# Test spec: REQ-078 — Supporting routes (audit, definition validation, tenant config,
# solution packs, pin rebind, metrics)

Design: `lib/letflow/design/req078-supporting-routes.md`. Traceability table: design §18
(T-01..T-19), extended here with the two INV-5 cross-tenant-404 cases the design's own §18.2
closing paragraph calls out as still needed at handoff time. All tests live in
`test/letflow/routers/req078_supporting_routes_test.exs`.

## AC1 — each of the six modules has ≥1 end-to-end test through the real router

Why: proves the mount points in design §2.7 actually work and the response shape matches
§6.2/§7.3/§12.1/§8.3/§10.4/§11.5 — not just that the context function compiles.

* `GET /api/tenant-config` is dispatched through `Letflow.Router` itself (not a sub-router),
  because the thing under test is precisely that it is reachable with **no** `Authorization`
  header at all — the one property only the top-level router can prove (design §2.4).
* The other five are dispatched directly against their owning `Plug.Router` sub-module with
  `conn.assigns[:auth_context]` set by hand, matching the established convention in
  `test/letflow/routers/tenants_test.exs` and `identity_test.exs` (their own moduledocs record
  the same choice, for the same reason: each sub-router's own handlers read
  `conn.assigns.auth_context` directly, so nothing under test depends on how that assign got
  populated — the full `AuthPipeline` bearer-token dance is REQ-021/025's own coverage, not
  this requirement's). Every request still goes through real `Plug.Router` `match`/`dispatch`,
  a real handler, and a real backing context function against real Postgres.

## AC2 — audit list is tenant-isolated; caller without `:AuditRead` gets 403

Two tenants seeded with events in the same timestamp window; requesting as tenant A must
return only A's events (never a B `event_id`), proving `read_global/1`'s `:prefix` scoping
(design §5, §6.1) rather than an application-level filter that could be bypassed. A
`TASK_WORKER`-only caller (holds no `:AuditRead` per `authorization.ex`'s matrix) must get 403
with zero events disclosed.

## AC3 — pack export/install never cross a tenant boundary

Export as A naming one A id and one B id must 422 (`{:error, {:definition_not_found, _}}` —
the B id is invisible in A's schema, design §8.3 INV-1) rather than ever returning a B
artefact. Install as A, then read `process_definitions` back with `prefix: <B schema>` and
assert zero new rows there — the only rows are in A's own schema.

## AC4 — the validate endpoint adds no rule of its own

T-12a/T-12b per design §18.2: a valid graph must report `"findings" => []` at 200 AND agree
(zero violations) with calling `Graph.validate_graph/1`/`validate_node_attributes/1`/
`validate_edge_conditions/1` directly on the same `%Graph{}`. An invalid graph (missing END
node) must 422 with `"errors"` equal to the concatenation of the three direct-validator calls'
violations, mapped through the same two-key shape, in the same order. This is what actually
proves the route is a pure composition and not a second, possibly-drifting, rule.

## AC5 — metrics is per-tenant-scoped

Tenant A seeded with 1 active instance, tenant B with 7. Request as A must report
`instances.active == 1` and the body must contain no value equal to 7 or 8 (B's own figure or
a platform-wide total) anywhere. Separately, `Code.fetch_docs/1` on `Letflow.Routers.Metrics`
must contain the phrase `"PER-TENANT-SCOPED"` — the verbatim moduledoc obligation design §11.3
requires.

## AC6 — the `validation.zig` distinction is stated

`Code.fetch_docs/1` on `Letflow.Routers.Definitions`'s moduledoc must name both
`routes/validation.zig` (this endpoint) and `src/api/validation.zig` (REQ-068's
`Letflow.Api.Validation`), so a reader cannot conflate the two.

## AC7 — metrics moduledoc states no subsystem is built

`Code.fetch_docs/1` on `Letflow.Routers.Metrics` must contain both "No metrics subsystem is
built here" and "S6 observability".

## AC8 — pack install's `variable_schemas` write is single-path and tenant-scoped

T-17: install a pack carrying one `variable_schemas` entry as tenant A; read `variable_schemas`
back with `prefix: <A schema>` (row present, `json_schema` decoded correctly) and with
`prefix: <B schema>` (zero rows) — proves both the write-only-into-caller's-schema half of AC3
and the "writes those rows" half of AC8 in the same assertion pair.

T-18: install a pack whose `schema_content` is `"[1,2]"` (a top-level non-object, i.e. not a
well-formed JSON Schema document) must 422, and must leave **zero** `variable_schemas` rows AND
**zero** `process_definitions` rows in A — proving the whole `Ecto.Multi` transaction rolled
back rather than partially committing the definition it had already inserted.

T-19 (mechanical, design §18.1): (a) no file under `lib/letflow/routers/` contains a `Repo.`
call (INV-RT-1, re-verified here rather than only trusted from REVIEWER's pass); (b) no file
under `lib/letflow/routers/` contains `VariableSchema.changeset`, `Repo.insert`, `Repo.insert_all`
or `Ecto.Multi.insert`; (c) across all of `lib/`, the only call site combining a
`VariableSchema.changeset` build with an insert (`Repo.insert`/`insert_all`/`Ecto.Multi.insert`)
is inside `lib/letflow/definitions.ex`'s `register_variable_schemas/3`.

## INV-5 (not itself a numbered AC, but confirmed by REVIEWER/SECURITY-REVIEWER as required)

Rebind-pins and definition-validate both act on an existing resource id; a caller from tenant A
naming an id that genuinely exists, but in tenant B's schema, must get the same 404 (no detail)
as a genuinely nonexistent id — design §4.4. Added here because no test enforced this at
handoff despite both gates having confirmed the code does it.
