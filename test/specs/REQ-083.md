## 1. Acceptance-criteria -> test-case mapping

### AC1 — all three handlers tested end-to-end through the real router; list and
inbox cursor-paginated across at least two pages

**Why this test exists, not just a restatement of the criterion:** the design (§5)
specifies `/tasks/inbox` must be declared textually before `/tasks/:id` so
`Plug.Router`'s first-match-wins semantics don't swallow the literal `"inbox"` segment
as `id = "inbox"` — a real, checkable ordering bug class, not a style note. The
pagination cases exist because `list_tasks/2`'s cursor mechanism (§3.1 points 5-9) is
the one place this requirement's own SQL diverges from a naive "just add a LIMIT" read
— an off-by-one in the `page_size + 1`/`has_next` computation would silently either
drop the last row or double-return the boundary row across a page split, which only a
real two-page test (not a single-page "does it return items" test) can catch.

* `describe "AC1: GET /tasks/:id basic end-to-end"` — one task inserted, fetched by id,
  status 200 asserted, spot-checked fields (`id`, `node_id`, `status`).
* `describe "AC1: GET /tasks paginates across at least two pages"` — two tasks,
  `page_size=1`; page 1 has 1 item + a `next_cursor`; page 2 (following that cursor) has
  the other item + `next_cursor: nil`; the two pages' ids are disjoint and their union is
  exactly the two inserted tasks (catches both a dropped row and a duplicated boundary
  row).
* `describe "AC1: GET /tasks/inbox paginates across at least two pages"` — identical
  page-split assertion, through `/inbox` instead of `/`, for an operator caller (whose
  inbox is deliberately the whole tenant queue per design §5.3 point 2) — proves the
  *same* cursor mechanism is genuinely reused by both endpoints, not two independent
  (and possibly divergently-buggy) copies.

### AC2 — inbox for user X returns tasks assigned directly, via a group, via a role;
never a task assigned only to a different user Y — four explicit assertions

**Why this test exists:** this is the requirement's own named security-relevant
scoping dimension (an inbox leaking another user's task within the same tenant is a
real authorisation defect, per the requirement text, even though it's not a
cross-tenant leak). The design (§3.4) states plainly that R-Co's own shipped
`listCursor` SQL has **no ROLE arm at all** — this codebase's `resolve_principal_scope/2`
is a genuine *extension* beyond what was ported from R-Co, so the ROLE case is not
"probably fine because R-Co already does it" — it needed a first real test.

* `describe "AC2: GET /tasks/inbox scoping for a task-worker-only caller"` — one test,
  four separate `assert`/`refute` calls (not folded into a single set-equality check, so
  a future regression that drops exactly one of the three inclusion arms — or widens
  exclusion — points at the specific failing line rather than an opaque list diff):
  1. `assert task_direct.id in returned_ids` (assignee_type "USER", assignee_ref ==
     caller's own user_id)
  2. `assert task_via_group.id in returned_ids` (assignee_type "GROUP", assignee_ref ==
     a group id the caller is a member of)
  3. `assert task_via_role.id in returned_ids` (assignee_type "ROLE", assignee_ref == a
     role name bound, via `TenantRole.group_id`, to that same group)
  4. `refute task_other_user.id in returned_ids` (assignee_type "USER", assignee_ref ==
     a different user Y's id)

**Extra assurance on the reworked ROLE path (not itself a named AC, but load-bearing
for §3.4's rework-1 fix):**

* `describe "AC2 extra assurance: a role held only in a DIFFERENT tenant does not leak
  into this tenant's inbox"` — seeds tenant B with a role named identically
  (`"approver"`) to one that does *not* exist for the caller in tenant A, and a task
  assigned to that tenant-B role. Asserts the caller's tenant-A inbox contains their own
  same-tenant directly-assigned task and never the tenant-B role-assigned task. This
  exercises exactly the `:prefix`-scoped `Ecto.Query` against `Letflow.Identity.TenantRole`
  SECURITY-REVIEWER's Step 2c gate required (`resolve_principal_scope/2`, design §3.4
  point 2) — a same-named role in a different tenant schema is the one scenario an
  accidentally-unscoped query (the original, rejected design) would have silently
  leaked through, since `TenantRole.name` collisions across schemas are otherwise
  invisible to a query that isn't schema-qualified.

### AC3/INV-5 — a task id belonging to another tenant returns the identical response to
a nonexistent id

**Why this test exists:** `get_task/2` (§3.2) is specified to resolve both cases
through the exact same code path with no branch that could distinguish them — the test
proves this structurally by asserting on both the status code AND the raw response
body bytes, not merely "both are 404" (two different 404 bodies would still pass a
status-only check but would leak the fact that *some* tenant owns the resource, which
is exactly what INV-5 forbids).

* `describe "AC3/INV-5: GET /tasks/:id cross-tenant id is indistinguishable from a
  nonexistent id"` — `resp_cross_tenant.status == 404`,
  `resp_cross_tenant.status == resp_never_existed.status`, AND
  `resp_cross_tenant.resp_body == resp_never_existed.resp_body`.

### AC4/INV-1 — tenant A sees no tenant B task, even with identically-named nodes

**Why this test exists:** seeding both tenants with a node literally named
`"shared_node"` is the only way to rule out an accidental pass from two tenants simply
never colliding on any field by chance — if isolation were broken by, say, a missing
`prefix:` opt on one query branch, an identically-named-node test is what would catch
it; two arbitrarily-different-named tasks would not.

* `describe "AC4/INV-1: GET /tasks tenant isolation with identically-named nodes"` —
  both tenants seeded with a task on `node_id: "shared_node"`; tenant A's `GET /tasks`
  returns exactly tenant A's own task id, never tenant B's.

### AC5/INV-2 — explicit field allowlist, full key-set assertion

**Why this test exists:** the design (§5.5) specifies hand-built response maps, never a
`Jason.Encoder`/struct-wholesale encoding — a regression that accidentally re-enabled
wholesale struct encoding (or added a field to the map without updating this test)
would still pass a "contains these N expected keys" check; only a full
`Map.keys(...) |> Enum.sort() == [...]` assertion catches an extra, unintended key
(e.g. `form_schema`, `completed_by`, or a future `claimed_by`) leaking into the
response.

* `describe "AC5/INV-2: response allowlists"` —
  * `GET /tasks` item shape: `Map.keys(item) |> Enum.sort()` for every item in the page
    equals the full nine-key list (`assignee_ref`, `assignee_type`, `created_at`, `id`,
    `instance_id`, `node_id`, `node_name`, `status`, `token_id`).
  * `GET /tasks/:id` shape: full ten-key list (the same nine plus `correlation_key`,
    `updated_at`), plus explicit `refute Map.has_key?/2` for `claimed_by`,
    `form_schema`, `output_variables`, `completed_by`, `completed_at`, `cancelled_at` —
    the design's own OQ-1/OQ-7 named exclusions, checked individually so a future reader
    diffing this test against the design's exclusion list sees each one enumerated, not
    only implied by the key-set's absence.

### AC7 — a caller without TasksRead gets 403 on all three endpoints

**Why this test exists:** all three routes fold through the same
`with_authorized_scope/4` helper (§5.1) and the same `:TasksRead` permission chain —
the test proves this by exercising all three endpoints, not just one, since a future
change to one handler's own dispatch (e.g. accidentally short-circuiting before the
authorization check) would only be caught by testing that specific route. Two role
shapes are tested: no roles at all, and a real recognized role
(`AGENT_RUNNER`, `role_allows?/2` grants it zero permissions) that exists but genuinely
lacks `TasksRead` — distinguishing "unauthenticated-shaped" denial from "authenticated,
wrong role" denial.

* `describe "AC7: a caller without TasksRead gets 403 on all three endpoints"` — four
  tests: `GET /tasks`, `GET /tasks/inbox`, `GET /tasks/:id` each with `roles: []`, plus
  `GET /tasks` with `roles: ["AGENT_RUNNER"]`.

## 2. Additional coverage (not independently named by an AC, but load-bearing for the
design's own explicitly-stated behavior)

* **Route-match ordering** — `GET /tasks/inbox` is served as the inbox, not
  misinterpreted as `GET /tasks/:id` with `id = "inbox"` (design §5, a real ordering
  requirement, not a style note — see AC1's rationale above).
* **Validation (400/422)** — `status=bogus` -> 400, `instance_id=not-a-uuid` -> 400, a
  malformed `:id` path segment -> 400 (this router's own established 400-for-malformed-
  input convention, §5.2 point 2 — a **deliberate divergence from R-Co's own 422** for
  these three fields, stated explicitly in the design so a reader porting from R-Co's
  behavior doesn't "fix" this back to 422), and `cursor=not-a-valid-cursor!!!` -> 422
  (this router's *own* convention for cursor errors specifically — kept separate from
  the `identity_test.exs` precedent, which asserts 400 for an invalid cursor on
  `/users`, because `Letflow.Routers.Tasks.handle_list_result/2` maps `:invalid_cursor`
  to `Response.unprocessable/2`, not `Response.bad_request/2` — copying the Identity
  router's 400 here would have produced a test that fails against the real
  implementation, so this test asserts what this router actually specifies, not what a
  sibling router does).
* **`assignee_id` filter (design §5.2 point 3)** — an `:all`-scope caller (operator)
  supplying `?assignee_id=` narrows results to that user only.
* **INV-2** — a task-worker-only caller's `GET /tasks` scope is never widened by a
  caller-supplied `assignee_id` naming a *different* user — the row-filter guarantee
  `AllowWithRowFilter` exists to enforce, tested directly rather than only inferred from
  AC2's inbox test (which never exercises `GET /tasks` with an `assignee_id` param at
  all).
* **Status filter** — `status=COMPLETED` excludes a `PENDING` task.
* **404 for a genuinely nonexistent id** (not merely the cross-tenant case AC3 covers).
* **Unmatched sub-path** returns the RFC 9457 404 problem document (matches
  `Letflow.Routers.Tasks`'s own `match _ do Response.not_found(conn) end` catch-all).

## 3. Fixtures — no wall-clock or unseeded-randomness dependency

`insert_task!/2` builds the mandatory FK chain (`instance_projections` ->
`tokens` -> `tasks`, per `priv/repo/migrations/20260818110003_create_tasks.exs`'s two
`references/2` columns) directly via each schema's own `insert_changeset/2`, with
`Ecto.UUID.generate/0` for every id — no `System.system_time/1`-derived or
otherwise-unseeded value anywhere. `inserted_at`/`updated_at` (the pagination sort key)
come from each row's own real insert time (`timestamps/1`), which is what the
two-tasks-in-sequence pagination tests rely on for their strict ordering — this is
real, observed DB state at assertion time, not a mocked or frozen clock.
