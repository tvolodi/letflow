# Test Spec: REQ-085 — Task routes 2/2, write path (`Letflow.Tasks`, `Letflow.Engine`, `Letflow.Routers.Tasks`)

**Requirement:** REQ-085 (stage S4). Ports `src/api/routes/tasks.zig`'s `handleComplete`
(L341, EE-04), `handleClaim` (L551), `handleAssign` (L628), `handleReassign` (L736) — the
write half of the 7-handler file REQ-083 already split. `handleComplete` is the engine
entry point (output variables merge, token advances) — it must never write the `tasks`
row directly. Claim/assign/reassign are authorisation-sensitive beyond REQ-069's
`TasksAssign` permission: claiming a task assigned to a different user or to a group the
caller does not belong to must fail even within the same tenant. Two simultaneous claims
of the same task must result in exactly one winner. SECURITY (INV-1, INV-5, INV-8). Full
text: `docs/requirements.yaml` REQ-085.

**Design:** `lib/letflow/design/req085-task-routes-write.md` — §1 resolves claim as
atomic conditional self-assignment against `assignee_type`/`assignee_ref` (no
`claimed_by` column); §2 resolves claim's permission gate to `:TasksComplete`, not
`:TasksAssign`; §3.1 establishes `SELECT ... FOR UPDATE` + `Ecto.Multi`, the same
concurrency idiom `Letflow.Engine.complete_task/3` already uses, as the sole locking
mechanism for claim/assign/reassign.

**Implementation:** `lib/letflow/tasks.ex` (`claim_task/3`, `assign_task/4`,
`reassign_task/4`), `lib/letflow/routers/tasks.ex` (`handle_complete/3`, `handle_claim/3`,
`handle_assign/3`, `handle_reassign/3`), `lib/letflow/engine/task.ex`
(`assignment_changeset/2`, additive), `lib/letflow/api/authorization.ex`
(`endpoint_policy_key("POST", "/tasks/:id/claim")`, additive).

**Test tier:** integration (`Letflow.DataCase`, real Postgres, real tenant-schema
provisioning via `Letflow.TenantFixture`) — dispatched directly against
`Letflow.Routers.Tasks.call/2`, extending REQ-083's own `tasks_test.exs` file (same
dispatch mechanism, same fixture-helper shape) rather than a parallel file, since this
requirement extends the same router module and context module REQ-083 already built.

**Test file:** `test/letflow/routers/tasks_test.exs` (extended, not a new file).

## 1. Acceptance-criteria -> test-case mapping

### AC1 — completing a task advances the owning instance (output variables in
instance variables, token moved), asserted through the real router, not only the 200

**Why this test exists, not just a restatement of the criterion:** the single most
damaging way to get this route wrong (per the requirement's own text) is a handler that
flips the `tasks` row to `COMPLETED` without driving the engine transition, leaving the
owning instance permanently stalled. A test asserting only `conn.status == 200` cannot
distinguish "the instance actually advanced" from "the row was flipped and nothing else
happened" — the whole point of this AC is to prove the router is wired to
`Letflow.Engine.complete_task/3` (REQ-048) and not a shortcut around it.

* `describe "REQ-085 AC1: POST /tasks/:id/complete advances the owning instance"` — a
  real instance is started via `Letflow.Engine.create/2` (START -> HUMAN_TASK -> END),
  its pending task completed through the real router with a body containing an output
  variable. Assertions: the response body's `variables`/`current_nodes`/
  `instance_status` fields (not just `conn.status`); a direct `Repo.get!` of the
  `instance_projections` row (status `:completed`, `variables` includes the merged
  output, `current_nodes == []`); a direct read of the `tasks` row (`status ==
  :completed`, `output_variables` populated); and that no token remains `:active` at the
  old node — the token genuinely moved, not merely a status flip.

### AC2 — `handleComplete` contains no direct write to the `tasks` table; grep for
`Repo.` in the module returns no hit

**Why this test exists:** this project already has a precedent for exactly this
structural check (`test/letflow/routers/req078_supporting_routes_test.exs`'s own
`"no Repo. call anywhere under lib/letflow/routers/"` test, using a
`strip_comments_and_docs/1` helper so prose mentions of `Repo.` inside the module's own
`@moduledoc` — which this router's moduledoc has several of, describing the very
invariant this test checks — don't produce a false positive). Reusing that precedent
here is cheaper and more directly traceable to the acceptance criterion's own literal
wording ("confirmed by grep for `Repo.` in the module returning no hit") than inventing
a new mechanism.

* `describe "REQ-085 AC2/INV-TW85-2: handleComplete routes to the engine, never writes
  tasks directly"` — reads `lib/letflow/routers/tasks.ex`, strips `@moduledoc`/`@doc`
  blocks and `#` comments, asserts the stripped source contains no `"Repo."` substring.

### AC3 — completing an already-completed task and completing an already-cancelled
task each return a 409-class problem document and produce no second transition — two
explicit tests

**Why these tests exist:** `complete_task/3`'s row-lock discipline (EE-12) is the only
mechanism preventing a double-transition; a test that only checks the HTTP status
without also reading the task/instance rows before and after would not actually verify
"no second transition" — a bug that let a second transition through while still somehow
returning 409 (e.g., a transition that ran but whose result was mis-mapped to 409) would
pass a status-only test and fail a real user. Both the `COMPLETED` and `CANCELLED`
starting states are tested explicitly since they are two distinct values of the same
error tuple's `status` field, and the design's own §5.5.1 table treats them identically
— a regression that broke only one of the two would not be caught by testing just one.

* `describe "REQ-085 AC3: completing a non-PENDING task returns 409 with no second
  transition"` — two tests, one task forced to `:completed` and one forced to
  `:cancelled` (via a direct `Ecto.Changeset.change/2` fixture write, since REQ-085's own
  functions never write `:status` themselves — there is no "real" way to reach this state
  other than via `Letflow.Engine.complete_task/3`, which is exactly the function under
  test, so the fixture must bypass it). Each asserts `conn.status == 409` and that the
  task row's `status`/`output_variables`/`completed_by`/`updated_at` and the instance
  projection's `status`/`variables` are byte-identical before and after the request.

### AC4 — two concurrent claims of the same task produce exactly one success and one
deterministic non-500 rejection, demonstrated by a test running both concurrently

**Why this test exists:** the design's entire justification for reusing
`complete_task/3`'s row-lock idiom (§3.1) instead of R-Co's bare `UPDATE...WHERE` is that
it produces this exact guarantee under genuine concurrency — a serial "call claim, then
call claim again" test would never exercise the row-lock's blocking behavior at all and
would pass even if `claim_task/3` used no locking whatsoever. This test therefore
launches two `Task.async` bodies before awaiting either, matching
`test/letflow/engine_concurrency_test.exs` (REQ-055)'s own established pattern for real
concurrent-write tests in this codebase (`Letflow.TenantFixture.provisioned_tenant!/1`
already puts `Ecto.Adapters.SQL.Sandbox` in `:auto` mode, so each `Task.async` body gets
its own independent Postgres connection rather than being serialized through one shared
sandbox connection).

* `describe "REQ-085 AC4: two concurrent claims of the same task"` — one unassigned
  task, two different caller user ids, two `Task.async` router dispatches to
  `POST /:id/claim` launched before either is awaited. Asserts the two response statuses
  are exactly `[200, 409]` sorted (never `[200, 200]`, never a `500`), and that the
  task's final `assignee_ref` matches whichever caller received the `200`.

### AC5 — claiming a task assigned to a different user, and claiming one assigned to a
group the caller does not belong to, are both rejected with no state change — two
explicit tests

**Why these tests exist:** these are the two branches of `claim_task/3`'s decision table
(design §3.4) that reject *before* any write is attempted — a bug that let either branch
fall through to a write (e.g., an inverted membership check) would silently let a caller
steal another user's or another group's task. Asserting "no state change" (not just the
409 status) is what would catch that specific bug class; a status-only assertion would
not.

* `describe "REQ-085 AC5: claim rejected with no state change"` — two tests: (1) a task
  assigned `USER`/`other_user`, claimed by a different caller — asserts 409 and that
  `assignee_type`/`assignee_ref` are unchanged; (2) a task assigned `GROUP`/`group.id`,
  claimed by a caller deliberately never added as a member of that group — same
  assertions.

### AC6 — a task id belonging to another tenant returns the same response as a
nonexistent id, on all four verbs, with no state change in any case

**Why this test exists:** INV-1/INV-5's "same response" guarantee is only meaningful if
checked byte-for-byte (status *and* body), not merely "both are some 4xx" — a
distinguishing error message would itself leak that the id exists in another tenant's
schema. All four verbs are exercised in one test (a `for` loop over
`{verb, body}` pairs) rather than four separate tests, since the underlying mechanism
(§4 of the design) is structurally identical for all four — one row-lookup that
resolves to `{:error, :task_not_found}` regardless of which tenant's schema is queried —
and a shared loop keeps the fixture (`task_b`, `nonexistent_id`) obviously identical
across all four checks rather than risking four independently-drifting copies.

* `describe "REQ-085 AC6/INV-TW85-4: a cross-tenant task id behaves identically to a
  nonexistent id"` — tenant B's task, and a freshly-generated nonexistent id, are both
  submitted to tenant A's router for `complete`/`claim`/`assign`/`reassign`. For each
  verb: asserts both responses are `404`, asserts the two responses' `status` and
  `resp_body` are identical. After all four verbs, reads tenant B's own row directly and
  asserts it is completely unchanged (`status == :pending`, `assignee_type == nil`,
  `assignee_ref == nil`).

### AC7 — a caller without `TasksComplete` cannot complete and a caller without
`TasksAssign` cannot assign or reassign, with the absence of state change verified in
each case

**Why these tests exist, and why there are four not two:** the design's own §2 resolves
claim's permission gate to `:TasksComplete` (the same gate `complete` uses), which is
*not* literally named by AC7's own text (AC7 names `complete` only) — the design
explicitly instructs adding a claim-specific 403 assertion rather than assuming AC7's
text already covers it, since a reader could otherwise mistakenly believe claim needs no
dedicated test. `AGENT_RUNNER` (a recognized role that `role_allows?/2` grants zero
permissions to, the same role REQ-083's own AC7 test in this file already uses) is the
role without `TasksComplete`; `TASK_WORKER` (confirmed at design §0 to hold
`:TasksComplete` but not `:TasksAssign`) is the role that must still be denied `assign`/
`reassign` — using it rather than a no-roles-at-all caller additionally proves the gate
is permission-specific, not merely "any caller with fewer than all permissions is
denied everything."

* `describe "REQ-085 AC7: permission gates deny with no state change"` — four tests:
  `AGENT_RUNNER` denied `complete` (403, task status unchanged); `AGENT_RUNNER` denied
  `claim` (403, `assignee_type` unchanged); `TASK_WORKER` denied `assign` (403,
  `assignee_type` unchanged); `TASK_WORKER` denied `reassign` (403, `assignee_ref`
  unchanged).

## 2. Additional coverage (design-flagged, not literally named by a single AC)

The design's own AC-traceability table (§9) and error-union tables (§5.5.2-§5.5.4) name
several branches that no single AC above exercises directly. `describe "REQ-085:
assign/reassign happy paths and error branches"` covers:

* `assign_task/4`'s happy path (unassigned task -> `USER`/target, response body and row
  both asserted).
* `assign_task/4`'s `:already_assigned` branch (already-assigned task, no state change).
* `reassign_task/4`'s happy path (already-assigned task -> new `USER`/target,
  unconditional overwrite).
* `reassign_task/4`'s `:not_currently_assigned` branch (unassigned task, no state
  change).
* `claim_task/3`'s `:not_claimable` branch — a task whose `assignee_type` is none of
  `USER`/`GROUP`/`ROLE` (`"BOGUS"`), which the schema's own `assignee_type :string`
  field (no DB-level enum constraint) makes constructible as a fixture even though no
  real write path in this codebase ever produces it.
* `claim_task/3`'s idempotent-no-op branch (OQ-2 in the design) — re-claiming a task
  already claimed by the same caller succeeds with 200, no error.
* `claim_task/3`'s `ROLE` grant branch — a task assigned to a role the caller holds via
  group membership, claimed successfully and rewritten to `USER`/caller.
* Malformed-UUID 400s on `assign` and `complete`.
* Missing/empty `user_id` 422s on `assign` and `reassign` (`Letflow.Api.Validation`'s
  existing field-constraint pipeline).
