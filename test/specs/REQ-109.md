## AC1 — migration guarded by `if prefix() do` **and** registered in the manifest, applying cleanly

**Test:** `variable_schema_test.exs`, `describe "AC1 — migration applies to a fresh tenant schema"`.

Both halves are proved by execution rather than by reading the migration source:

* **Manifest half.** `TenantProvisioning.replay_migrations/1` runs *only* the
  `@tenant_scoped_migration_manifest` list (`tenant_provisioning.ex:238-263`), so
  asserting `20_260_821_000_002 in applied_versions` is direct evidence the manifest
  entry exists — a source grep would only prove the tuple is typed there, not that the
  runner picks it up.
* **Apply half.** `Repo.all(VariableSchema, prefix: schema_name)` returns `[]` against
  the freshly provisioned schema (the table exists and is empty), then a seeded row is
  read back with every AC2-named column populated.

**Why this test exists:** a tenant-scoped migration can fail in two independent ways —
missing `if prefix() do` (it would land in `public`), or missing from the manifest (it
would never run for any tenant). Reading the file catches neither at runtime. A
follow-on assertion also confirms the table is absent from `public`, which is what the
`if prefix() do` guard is for.

## AC2 — the columns, and a duplicate `(definition_id, variable_key)` rejected by an actual insert

**Test:** `describe "AC2 — columns and the unique constraint"`, six tests.

1. A seeded row reads back with `definition_id`, `variable_key`, `json_schema`,
   `description` and a non-nil `created_at` (the DB default fires — `created_at` is
   `read_after_writes: true`).
2. A second `Repo.insert` of the same pair through `VariableSchema.changeset/2`
   returns `{:error, changeset}` with the `uq_variable_schema_definition_key`
   constraint mapped onto `:definition_id`.
3. A second insert of the same pair as a **raw struct** (no changeset, so no constraint
   declaration to catch the 23505) raises `Ecto.ConstraintError` with
   `constraint == "uq_variable_schema_definition_key"` and `type == :unique`.

**Why (2) and (3) both exist:** (2) proves the changeset declares the constraint under
the migration's actual index name — a wrong `name:` there silently degrades to an
unhandled raise. (3) proves the constraint is enforced by *Postgres* and pins the index
name Postgres actually rejected against, independently of what the changeset declares.
Together they are the "actual failing insert, not reading the migration source" AC2
asks for. A further test inserts a *different* `variable_key` for the same
`definition_id` and succeeds, proving the constraint is on the pair rather than on
`definition_id` alone.

### AC2's FK clause — `definition_id (FK to process_definitions(id))`

Two more tests, added after TEST-DESIGN-VALIDATOR's first-pass FAIL found the FK
clause had no runnable coverage (dropping `references(...)` from the migration left
every other test green):

4. **Catalog form.** `foreign_keys_on/2` — copied from
   `test/letflow/definitions/migrations_test.exs:160-186`, the established helper for
   this assertion class — asserts **exactly one** FK on `variable_schemas` in the
   provisioned schema, with `column == "definition_id"`,
   `referenced_column == "id"`, `referenced_table == "#{schema_name}.process_definitions"`
   and `on_delete == "r"`, plus an explicit `refute … == "c"`.
5. **Failing-insert form.** A row whose `definition_id` is a fresh
   `Ecto.UUID.generate()` matching no `process_definitions` row raises
   `Ecto.ConstraintError` with `type == :foreign_key` and
   `constraint == "variable_schemas_definition_id_fkey"`, and writes nothing.

**Why both:** (5) is the "actual failing insert" AC2's own wording prefers, but it
proves only that *some* FK exists. The load-bearing property is *which*
`process_definitions` the FK resolves to — a tenant-scoped migration whose FK bound to
`public.process_definitions` would be a cross-schema reference under INV-1 and would
still pass (5). Only (4) can catch that, which is why `migrations_test.exs:551-552`
carries a custom failure message on exactly that assertion. (4) is also the *only*
runnable check on `on_delete: :restrict`: that choice is a stated, reasoned divergence
from R-Co's `ON DELETE CASCADE` committed to in the migration header (design §2.2), and
`confdeltype` is the sole place a referential action is observable — no DDL text
distinguishes `:restrict` from a cascade.

## AC3 — the single most important test: rejection driven through the real `complete_task/3`

**Test:** `engine_variable_schema_merge_test.exs`,
`describe "AC3 — a violating overwrite through complete_task/3"`.

A `variable_schemas` row `("amount", %{"type" => "number"})` is seeded for the
instance's definition; the instance starts with `initial_variables: %{"amount" => 100}`
so `"amount"` is an **overwrite candidate**; `Engine.complete_task/3` is then called
with `output_variables: %{"amount" => "not-a-number"}`.

Asserted:

* the call returns
  `{:error, {:instance_execution_error, :variable_schema_rejected, {:field, "amount"}}}`;
* `instance_projections.variables` is still `%{"amount" => 100}` — the rejected value
  was **not** merged (`merge/3`'s two-phase semantic, R-Co ISS-202);
* `instance_projections.status == :error`;
* **exactly one** `EXECUTION_ERROR` event, whose payload carries
  `error_type == "variable_schema_rejected"`,
  `affected == %{"kind" => "field", "key" => "amount"}` (the offending
  `variable_key`), a `reason` naming `amount`, and the pre-merge variable snapshot;
* no `TASK_COMPLETED` event, and the task row stays `:pending`.

**Why this test exists — and why it is the requirement's whole point.**
`test/letflow/engine_execution_error_test.exs`'s AC4b reaches the identical
`error_args()` shape through `Engine.set_instance_error/2`, with an in-line comment
saying "Currently unreachable via complete_task/3." That shortcut was legitimate
*because* `merge_output_variables` hardcoded `variable_validations: nil`
(`req049-variable-merge.md` §7.3 sanctioned it), so `merge/3`'s `{:rejected, …}` branch
could never fire in production. REQ-109 removes that hardcoded `nil`. This test is the
only artefact in the suite that proves the removal worked: it never calls
`set_instance_error/2`, and it fails against pre-REQ-109 code, where the same
completion returns `{:ok, _}` and merges the string.

**This was verified by execution, not asserted.** With `merge_output_variables/7`'s
`VariableSchema.variable_validations/5` call temporarily replaced by a stub returning
`{:ok, nil}` — the exact pre-REQ-109 behaviour — the file's result went from
`5 passed` to `3/5 passed`: AC3 and AC6 both failed with
`left: {:error, {:instance_execution_error, :variable_schema_rejected, {:field, "amount"}}}`
against `right: {:ok, …}`. `lib/letflow/engine.ex` was restored to HEAD immediately
afterwards (`git checkout --`, working tree confirmed clean apart from the new test
files). AC4/AC5's three tests correctly stayed green under the stub — they assert
behaviour REQ-109 must *not* change.

## AC4 — a conforming overwrite still merges, status unchanged, token advances

**Test:** `describe "AC4 — a conforming overwrite still merges"`.

Same seeded schema, but on the two-human-task graph and with a conforming value
(`250`). Asserted by reading `instance_projections` and `events` back:
`variables == %{"amount" => 250}`, `status == :active` (unchanged — the two-task graph
is used precisely so completion does not drive the instance to `:completed`, which
would make "status unchanged" untestable), `current_nodes == ["task_b"]` and a
`task_b` task row exists (the token advanced), zero `EXECUTION_ERROR` events.

**Behaviour differing from the AC's wording, deliberately tested as-implemented:** AC4
says "appends a `VARIABLE_OVERWRITTEN` event." There is no such event row. REQ-048's
INV-EE48-5 (`engine.ex:2221-2224`) embeds merge outcomes as
`payload["merged_variable_events"]` inside the single `TASK_COMPLETED` event and
"never appended as their own separate rows". The test asserts the real artefact —
`%{"event" => "variable_overwritten", "key" => "amount", "old_value" => 100,
"new_value" => 250}` inside `TASK_COMPLETED`'s payload — and additionally asserts
zero events named `VARIABLE_OVERWRITTEN` exist, so the divergence is pinned rather
than glossed. Writing the AC's literal assertion would have failed against correct
code.

## AC5 — two explicit tests: no row merges untouched; a brand-new key is never validated

**Tests:** `describe "AC5 — an overwrite candidate with no row"` and
`describe "AC5 — a brand-new key is never validated"`, plus a unit-level companion in
`variable_schema_test.exs`.

* **No row.** A schema *is* seeded, but for a different key (`"other"`), so the table
  is non-empty and the query genuinely runs — this is stronger than an empty table,
  which would pass even if `fetch_schemas/3` returned `%{}` unconditionally. The
  overwrite of `"amount"` with a value that would violate `"other"`'s schema merges
  untouched, no `EXECUTION_ERROR`. This pins §6.2 / INV-VS-4's *omission* rule.
* **Brand-new key.** A schema is seeded **for `"amount"`**, the instance starts
  *without* `"amount"`, and the completion inserts `"amount" => "not-a-number"`. The
  completion **succeeds** and the violating value is stored.

  **This asserts the implemented behaviour, not R-Co's.** R-Co's Phase 1
  (`instance.zig:2390-2430`) validates every key that has a schema and only then checks
  collision; Letflow validates overwrite candidates only
  (`req049-variable-merge.md` §3.1 step 3, design §11.1 OQ-1). That divergence is a
  real open defect tracked as **ISS-0077 / GH#300**; REQ-109 is built to AC5 as
  written, so the test pins AC5's semantics and carries an in-line pointer to
  ISS-0077. When ISS-0077 is decided the other way, this test is the one that must
  change, and the comment says so.
* **Unit companion** (`variable_schema_test.exs`): `variable_validations/5` with
  `current = %{"a" => 1}`, `incoming = %{"b" => 2}` and a row seeded for `"b"` returns
  `{:ok, %{}}` — and does so against a repo double that raises on any call, proving
  INV-VS-2's "zero queries when the candidate set is empty" at the same time.

## AC6 — cross-tenant isolation (INV-1)

**Test:** `describe "AC6 — a tenant-A row has zero effect in tenant B"`.

Two tenant schemas are provisioned. Tenant A's definition is created through
`Definitions.create/2` + `activate/2`; tenant B's is inserted with the **same `id`**,
name, version and graph, then activated — so the completion really is identical in the
`(definition_id, variable_key, violating value)` triple the AC names, and the only
difference between the two runs is which schema holds the row.

The `variable_schemas` row is seeded **only in A**. Rows are read back in both schemas
first (`A` has exactly one, `B` has none) before either completion runs, per the AC's
"verified by reading the rows back". Then the identical completion is **rejected in A**
(status `:error`, one `EXECUTION_ERROR`) and **succeeds in B** (variables merged to the
violating value, zero `EXECUTION_ERROR`).

**Why this test exists:** the only thing separating the two is the `prefix:` on
`fetch_schemas/3`'s single `repo.all/2`. Dropping that `prefix:` resolves to Ecto's
default (`public`) schema — a cross-tenant read under INV-1. Because `definition_id`
is not itself a tenant-scoped identifier (design §7), reusing it across schemas is the
sharpest possible form of the test: an id-based-only isolation would leak.

## AC7 — fail-closed prefix, with a distinct error and **no query issued**

**Test:** `describe "AC7 — fail-closed prefix guard"`, four tests, built on a
`NeverQueriedRepo` module defined in the test file whose every callback **raises**.

* `variable_validations/5` and `fetch_schemas/3` each return
  `{:error, :missing_prefix}` for a missing key, `nil`, `""` and a non-binary.
* "Issues no query" is **proved, not argued**: every one of those calls is made with
  `NeverQueriedRepo`, which raises on `all/1` and `all/2`. Reaching a query is a test
  failure by construction. (This reuses SECURITY-REVIEWER's own 2b technique.)
* **The ordering is pinned explicitly.** `variable_validations(NeverQueriedRepo, id,
  %{}, %{}, prefix: nil)` — nothing whatsoever to validate — still returns
  `{:error, :missing_prefix}` rather than the `{:ok, %{}}` empty-candidate fast path.
  Design §4.5 makes step 1 precede step 3 deliberately; an implementation that
  reordered them would still pass every other AC7 assertion, so this test is the only
  guard on that ordering.
* `{:error, :invalid_definition_id}` for a `nil`/malformed `definition_id` is covered
  in the same style (design §6.4) — a distinct, pattern-matchable member of the closed
  `error_reason()` union, also with zero queries.

## `changeset/2` — first consumer

**Test:** `describe "changeset/2 — REQ-109's tests are its first consumer"`.

`changeset/2` has zero callers in `lib/` (design §3.2 — REQ-078/REQ-082 will be the
production consumers). Two small tests pin what the seeding path depends on: the three
required fields, and that `json_schema` is cast as a map. Deliberately *not* asserted:
that `json_schema` is a well-formed JSON Schema document — the moduledoc states
outright that it does not check this (design §11.3 OQ-3), so asserting it would
certify a guarantee that does not exist.

## `validations_for/3` — non-map stored schema (unit only, **scoped**, ISS-0089 / GH#306)

**Test:** `describe "validations_for/3 unit — a non-map json_schema"`.

`validations_for/3`'s `{:ok, _not_a_map}` branch omits the key and logs a warning
(design §6.3). The test calls `validations_for/3` **directly with a hand-built
`schemas` map** and says so in the test name and in a block comment.

**It does not, and must not, claim to cover the production failure mode.**
`fetch_schemas/3` — the branch's only production caller — selects `json_schema` as a
typed `:map` field, so Ecto's `:map` loader runs first and returns `:error` for every
non-object jsonb value, which Ecto turns into a raise at load time. Verified by
execution: `Ecto.Type.load(:map, %{"a" => 1})` → `{:ok, …}` while
`Ecto.Type.load(:map, [1, 2] | "str" | 42 | true)` → `:error`. The branch is therefore
**unreachable from production** (ISS-0089 / GH#306). Seeding a non-map row and
asserting graceful skipping would certify a defence the production path bypasses, so
that test is not written. What *is* written is an honest unit test of a pure function's
own documented contract, which is worth having for whoever wires REQ-078/REQ-082.

| AC8–AC13 | Documentation/source-state criteria whose own wording specifies verification by reading the named file or by `grep`. Assertions on moduledoc prose are brittle string checks, not coverage. |
| A non-map `json_schema` seeded in the DB and read through `fetch_schemas/3` | Unreachable — Ecto's `:map` loader raises first (ISS-0089 / GH#306). Covered as a pure-function unit test only, explicitly scoped. |
| Brand-new keys being *validated* | They are not, by design (AC5) and by defect (ISS-0077 / GH#300). The test pins the actual behaviour. |
| The registration / INSERT path | Out of scope by the requirement's own text; REQ-078/REQ-082 own it. Rows are seeded directly. |

| `{:variable_schema_lookup_failed, reason}` end-to-end | No reachable trigger — see below. Covered as a unit test of the lookup instead. |

### `{:variable_schema_lookup_failed, reason}` has no reachable end-to-end trigger

Attempted at TEST-DESIGN-VALIDATOR's (non-blocking) suggestion, then withdrawn on
evidence. `engine.ex:1671` maps a lookup error to this tuple and it is a clause of
`complete_task/3`'s `@spec` at `:1263`, but **both** members of
`VariableSchema.error_reason()` are structurally unreachable from `complete_task/3`:

* **`:missing_prefix`** — `complete_task/3` resolves the tenant via
  `TenantProvisioning.tenant_id_for_schema_name/1` (`engine.ex:1315`) *before*
  `run_complete_task/6` is entered, so a nil/empty prefix is rejected several steps
  earlier and never reaches the merge step.
* **`:invalid_definition_id`** — `instance_projection.ex:113` types `definition_id` as
  a nullable `Ecto.UUID`, but the **column** is `null: false` and typed `uuid`
  (`20260818110001_alter_instance_projections_add_engine_columns.exs:71`). Verified by
  execution: forcing it via `Repo.update_all` raises
  `Postgrex.Error ERROR 23502 (not_null_violation)` rather than producing the state.
  A malformed non-UUID value is rejected by the column type for the same reason.

So the guard is correct defence-in-depth against a state the schema forbids — the same
class as ISS-0089/GH#306's non-map `json_schema` branch, and handled the same way: a
unit assertion on the pure lookup (`fetch_schemas/3` → `{:error, :invalid_definition_id}`,
in the AC7 block) rather than a DB-seeded test certifying a path production cannot
take. The reasoning is recorded as a block comment in
`engine_variable_schema_merge_test.exs` where the test would have gone, and reported to
ORCH for forward filing.
