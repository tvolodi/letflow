# Test Spec: REQ-118 — CORS support on the Letflow side for the browser-origin SPA

**Requirement:** REQ-118 — verbatim acceptance criteria from `docs/requirements.yaml`:

1. CORS headers are emitted for cross-origin requests to the API, with the
   allowed-origin list read from application config rather than hardcoded.
2. The default configuration does NOT include a wildcard origin, and a test asserts
   that an unlisted origin is rejected.
3. Preflight (OPTIONS) handling is either implemented with a test, or explicitly
   documented as unnecessary with the reason stated — not left ambiguous.
4. A test exercises a cross-origin request end-to-end through the router rather than
   unit-testing the plug in isolation.
5. No change is made under `web/` — confirmed by `git diff`.

**Test tier:** unit+integration (router-level `Plug.Test`, DB-free)

**Implementation under test:** `lib/letflow/plugs/cors.ex` (new `Letflow.Plugs.Cors`
plug), mounted in `lib/letflow/router.ex` ahead of `plug(:match)`/`plug(:dispatch)`.
Design doc: `lib/letflow/design/req118-cors.md` (CODE-DESIGN-VALIDATOR-approved).
SECURITY-REVIEWER and REVIEWER have both already PASSed the implementation this spec
tests.

**Test file:** `test/letflow/plugs/cors_test.exs` — a dedicated per-plug file (not
appended to `test/letflow/router_test.exs`), matching
`test/letflow/plugs/tenant_status_test.exs`'s precedent of a focused per-plug test
file that still dispatches through real request handling rather than calling the plug
module directly. Every case here calls `Letflow.Router.call(conn, @opts)` — never
`Letflow.Plugs.Cors.call/2` in isolation — per AC4's explicit requirement.

## Test cases

### AC1 + AC4 — CORS headers emitted for a matched origin, config-driven, through the router

1. `GET /api/tenant-config` with `origin: http://localhost:5173` (a compiled-in
   default origin) gets `access-control-allow-origin: http://localhost:5173` echoed
   back, dispatched through `Letflow.Router` — proves headers are emitted for a real
   cross-origin request to the SPA's actual login-bootstrap endpoint, not just a
   synthetic route.
2. `GET /health` with the same allowed origin gets the header too, and the route's
   existing `200` + `{"status":"ok"}` body is unaffected — proves the plug adds
   headers without disturbing the wrapped route's own contract.
3. `GET /health` with `origin: http://127.0.0.1:4173` (the second compiled-in default
   — Playwright's built-SPA preview server) is also matched — proves both documented
   default origins work, not just the first.
4. A matched-origin response carries `vary: origin` — proves the cache-correctness
   header from design §1 is actually present, not just documented.

### AC1 — allowed-origin list is genuinely config-driven, not hardcoded

5. `Application.put_env(:letflow, :cors_allowed_origins, [custom_origin])` (cleaned up
   via `on_exit`) is set to a value disjoint from `@default_origins`. A request from
   `custom_origin` (never in the compiled-in default) is now accepted, and a request
   from `http://localhost:5173` (previously accepted by default) is now rejected. This
   is the only test that actually distinguishes "reads `Application.get_env/3` at
   request time" from "the two hardcoded defaults happen to match the two dev
   origins" — every other case in this file would pass identically against a version
   of the plug with the origin list hardcoded as a literal instead of read from
   config, so this case is what makes AC1's "from application config rather than
   hardcoded" clause a real, falsifiable assertion rather than an unverified claim.

### AC2 + AC4 — unlisted origin is rejected (no wildcard default)

6. `GET /health` with `origin: http://evil.example.com` (unlisted, and not matched by
   any wildcard since none exists) gets **no** `access-control-allow-origin` response
   header (`get_resp_header(conn, "access-control-allow-origin") == []`) — this is
   the concrete assertion AC2 requires. Per design §0.5, rejection is header omission,
   not a distinct HTTP status, so this test does not assert on `conn.status` for this
   case.
7. The same unlisted-origin request still gets its normal `200`/body from `/health` —
   proves rejection is silent (no CORS headers) rather than an active block, matching
   the design's explicit reasoning that non-browser callers (curl, server-to-server)
   must not be denied by a mechanism that only informs browsers.
8. An unlisted-origin request to an unrouted path still 404s normally (not halted
   early by the CORS plug) — proves the plug's "no halt for an unmatched origin"
   invariant.

### AC3 + AC4 — preflight (OPTIONS) is implemented and tested

9. An `OPTIONS /api/v1/anything` request with `origin: http://localhost:5173` and
   `access-control-request-method: POST` gets `204`, an empty body, and all four
   preflight response headers (`access-control-allow-origin`, `vary`,
   `access-control-allow-methods`, `access-control-allow-headers`,
   `access-control-max-age`) with the exact values from design §1's preflight table —
   proves preflight is fully implemented, not merely documented as unnecessary.
10. The same preflight response is confirmed to be neither the router's 404 catch-all
    nor a normal-route `200` — proves the request is short-circuited by the CORS plug
    itself (before `plug(:match)`/`plug(:dispatch)` runs), not accidentally matching
    some other path.
11. An `OPTIONS` request with a matched origin but **no**
    `access-control-request-method` header is NOT treated as a preflight (falls
    through to the normal 404 catch-all) — proves the preflight detection is the
    documented `method == "OPTIONS" and access-control-request-method present`
    conjunction, not `method == "OPTIONS"` alone.
12. An `OPTIONS` preflight from an **unlisted** origin is not short-circuited with
    `204` and carries no CORS headers — proves the preflight short-circuit itself
    respects the allowlist rather than answering every `OPTIONS` request
    unconditionally.

### Regression — no `Origin` header (same-origin / non-browser caller)

13. `GET /health` with no `Origin` header at all returns `200` + the pre-existing JSON
    body (matching `router_test.exs`'s own `GET /health` assertion) and carries no
    CORS headers whatsoever — proves this change is invisible to same-origin and
    non-browser callers, the majority of Letflow's existing traffic.

### Invariant pin — `access-control-allow-credentials` is never emitted

14–16. Three cases (matched-origin actual request, matched-origin preflight,
unlisted-origin request) each assert `get_resp_header(conn,
"access-control-allow-credentials") == []`. This pins SECURITY-REVIEWER's
already-passed check (design §0.1: the SPA never uses cookie/credentialed CORS) with
an executable test, so a future change cannot silently reintroduce the header without
a test failing first.

## AC5 — no change under `web/`

Not testable by an ExUnit test (there is no executable surface under `web/` to assert
against for "no change was made" — it's a diff-scope fact, not application behavior).
Confirmed instead via `git diff --stat -- web/` returning empty, same verification
method the design doc itself specifies (§4 AC5 row). ELIXIR-DEV's implementation
handoff and REVIEWER's pass both already confirm this; TEST-DESIGNER re-confirms:

```

(no output)
```

## Why this proves real coverage, not tautological restatement

Case 5 (AC1) is the load-bearing one: every other case in this file would still pass
against a hypothetical buggy implementation that hardcoded
`["http://localhost:5173", "http://127.0.0.1:4173"]` as a literal list inside
`origin_allowed?/1` instead of calling `Application.get_env/3` — the observable
request/response behavior would be identical for every origin this file otherwise
exercises. Case 5 is specifically constructed to diverge from that hypothetical: it
uses an origin the hardcoded list would never contain, and asserts a previously-listed
origin stops working once the config value changes to exclude it. Cases 6-8 (AC2) are
similarly falsifiable against a wildcard-default implementation — a `["*"]` or
missing-check version would incorrectly emit the header for `evil.example.com`, which
these tests would catch. Cases 9-12 (AC3) would fail against an unimplemented or
partially-implemented preflight path (e.g. one that short-circuits every `OPTIONS`
request unconditionally, or one that never halts and instead falls through to
`:dispatch`), so they are real regression coverage for preflight specifically, not a
restatement of "this route returns 204."
