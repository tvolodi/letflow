# Test Spec: REQ-124 — Mobile tenant-config bootstrap (`GET /api/mobile/tenant-config`)

**Requirement:** REQ-124 (`docs/requirements.yaml`, stage S9) — MOB-2
(`docs/mobile/requirements.md`), the gate for the entire mobile tier per
`docs/mobile/build-order.md` phase M-0. Adds `GET /api/mobile/tenant-config`, returning
`{realm_url, locales, default_locale, branding, environment_kind}` **without** a bearer
token, so the mobile app can discover which realm to authenticate against before it
holds any token. Resolves two gaps: (a) implements the previously-stub
`Letflow.Routers.MobileTenantConfig`; (b) mounts it ahead of
`Letflow.Plugs.ApiPipeline`/`Letflow.Plugs.AuthPipeline` (which has no bypass), the same
mechanism `Letflow.Routers.TenantConfig` (REQ-078) already uses.

**Design:** `lib/letflow/design/req124-mobile-tenant-config.md`.

**Handoff acceptance criteria (verbatim, `handoffs/WF02-REQ124-20260822/step-03-test-designer.json`):**
1. "GET /tenant-config [/api/mobile/tenant-config] returns the five specified fields
   for a known tenant slug with no Authorization header, demonstrated by a test that
   sends no token"
2. "a test asserts that the endpoint exposes no field beyond the five specified -- an
   exact-shape assertion (sorted key-set equality), not a subset check"
3. "the behaviour for an unknown tenant slug is tested and shown byte-identical to the
   default/missing-slug branch"
4. "every other route under Letflow.Plugs.ApiPipeline still requires authentication,
   proven by a test that would fail if the exemption were pipeline-wide (e.g. GET
   /api/v1/tenants with no token -> 401)"
5. "Letflow.Identity.safe_get_tenant_by_slug/2's exception-swallowing behavior is
   tested (raises inside get_tenant_by_slug/1 -> {:error, :lookup_failed}, never
   propagates)"

**Test tier:** integration (router, real Postgres via `Letflow.DataCase`) for AC1-4,
unit (real Ecto exception, no mocking) for AC5.

## Scope test

Real application-executable Elixir logic: `lib/letflow/routers/mobile_tenant_config.ex`
(new `Plug.Router` sub-module, handler, response allowlist, realm resolution),
`lib/letflow/identity.ex`'s `safe_get_tenant_by_slug/2` (new public function, shared
never-raise wrapper), and `lib/letflow/router.ex`'s new `forward/2` mount line. Not
docs-only, not build-config. Full TEST-DESIGN-VALIDATOR / TEST-RUNNER chain applies.

## Files

- `test/letflow/routers/mobile_tenant_config_test.exs` — new file, router-dispatched
  tests for the new endpoint. `test/letflow/routers/tenant_config_test.exs` does not
  exist as a standalone file (REQ-078's `GET /api/tenant-config` coverage lives inside
  `test/letflow/routers/req078_supporting_routes_test.exs`'s AC1 describe block) — that
  file's `GET /api/tenant-config` case (dispatched through `Letflow.Router.call/2`, no
  `Authorization` header, sorted-key-set assertion) is the style this new file follows.
- `test/letflow/identity_test.exs` — extended with one new `describe` block for
  `safe_get_tenant_by_slug/2` (AC5), independent of the pre-existing REQ-018/REQ-019
  describe blocks in the same file, matching this project's one-test-file-per-context
  convention.

## Dispatch strategy

Every router-layer test dispatches through `Letflow.Router` itself
(`Letflow.Router.call/2`), never directly against
`Letflow.Routers.MobileTenantConfig`'s own `Plug.Router`. The property under test —
reachability with no `Authorization` header — can only be proven through the real
top-level mount chain (`Letflow.Router` -> `forward("/api/mobile/tenant-config", ...)`,
declared before `/api/v1`, outside `ApiPipeline`/`AuthPipeline`). No test ever calls
`put_req_header(conn, "authorization", ...)` with a real value; one test (AC5's second
case) deliberately attaches a *garbage* header to prove the route never inspects it at
all, not even to reject it.

## Test cases

### Acceptance criterion 1 — 5-field response, no Authorization header, known slug

1. **Known slug with `idp_realm_id` set resolves to a 200 with `realm_url` reflecting
   the resolved realm, no `Authorization` header sent** — see
   `mobile_tenant_config_test.exs:"200, realm_url reflects the resolved tenant's
   idp_realm_id, exactly the 5 documented keys and no others"` (describe "AC1/AC3").
   Inserts a `tenants` row via `Tenant.create_changeset/3` with a unique
   `idp_realm_id`, dispatches `GET /api/mobile/tenant-config?slug=<slug>` through
   `Letflow.Router.call/2` with a bare `Plug.Test.conn/2` (asserted via
   `get_req_header(conn, "authorization") == []` before the call), asserts `200` and
   `body["realm_url"] =~ "/realms/#{realm_id}"`. Would fail if the route were still
   mounted behind `AuthPipeline` (401 instead of 200), if it 404'd, or if `realm_url`
   fell through to the default despite a resolvable slug.
2. **The route is reachable through the real router mount with genuinely no
   Authorization header** — see `mobile_tenant_config_test.exs:"no Authorization
   header is required to reach this route -- reachable through the real Letflow.Router
   mount, not dispatched directly against the sub-router"`. A second, narrower
   assertion isolating exactly the AC1 wording ("no Authorization header ... sends no
   token") from the shape assertion in case 1, dispatched the same way. Would fail if a
   future change moved this forward declaration after `/api/v1` (making it require
   auth) since `Letflow.Router.call/2` is the real dispatch path, not a bypass.

### Acceptance criterion 2 — exact-shape assertion

3. **Exact 5-key sorted-set equality, not a subset check** — folded into case 1:
   `assert Map.keys(body) |> Enum.sort() == ["branding", "default_locale",
   "environment_kind", "locales", "realm_url"]`. This is a hard equality on the full
   key set, not `assert_subset` or a `Map.has_key?` chain on a few keys — it would fail
   if a 6th key (tenant id, slug, display_name, status, or anything else derivable from
   `%Letflow.Identity.Tenant{}`) ever leaked into the response body, which is exactly
   the failure mode INV-2's "adding a sixth key is a security change" moduledoc
   statement warns against. It would equally fail if any of the 5 required keys were
   missing.

### Acceptance criterion 3 — unknown-slug behaviour, byte-identical to default/missing-slug

4. **A slug with `idp_realm_id: nil` falls through to the default realm** — see
   `mobile_tenant_config_test.exs:"a slug with nil idp_realm_id falls through to the
   default realm"` (describe "AC4"). Inserts a resolvable tenant whose
   `idp_realm_id` is `nil`, asserts `200` and `body["realm_url"] =~
   "/realms/bpm-default"`. Would fail if a nil-realm hit were treated as "resolved" and
   surfaced a non-default (nil-derived, likely malformed) `realm_url`.
4b. **A slug with a genuinely-persisted EMPTY-STRING `idp_realm_id` (not `nil`) also
   falls through to the default realm** — see `mobile_tenant_config_test.exs:"a slug
   with an EMPTY-STRING idp_realm_id (not nil) also falls through to the default
   realm"`. Distinguished deliberately from case 4: `Ecto.Changeset.cast/4`'s default
   `:empty_values` normalizes an incoming `idp_realm_id: ""` param to `nil` before
   persistence, so a naive fixture using the normal changeset path cannot produce a row
   whose `idp_realm_id` is a real, persisted empty string — this test uses
   `Ecto.Changeset.put_change/3` (which bypasses that normalization) to force one, then
   asserts `tenant.idp_realm_id == ""` before dispatching, so the fixture is verified to
   actually exercise the `realm_id != ""` half of
   `resolve_realm_id/1`'s guard clause (`lib/letflow/routers/mobile_tenant_config.ex`),
   not silently collapse into the already-covered nil case. Would fail if that guard
   clause's `!= ""` check were ever dropped, letting an empty-string realm id leak
   into `realm_url` as `".../realms/"` (a malformed URL).
5. **Unknown slug, nil-realm slug, missing `?slug=`, and empty `?slug=` all produce the
   exact same response body** — see `mobile_tenant_config_test.exs:"an unknown slug, a
   nil-idp_realm_id slug, and a missing ?slug= param all produce the BYTE-IDENTICAL
   response body"`. This is the direct acceptance demonstration for AC3's "byte-identical"
   wording: four independently-dispatched requests (miss, nil-realm hit, no param, empty
   param) are compared with plain `==` on the decoded body maps, not a
   field-by-field/subset comparison — any divergence anywhere in the 5-key shape fails
   this test. This is the endpoint's anti-enumeration property (design §4/INV-5-flavored):
   an unauthenticated caller with a wordlist cannot distinguish "this slug does not
   exist" from "this slug exists but has no realm bound" from "no slug was supplied at
   all." Would fail if any one of the four branches diverged in status, key set, or any
   field's value.

### Acceptance criterion 4 — the exemption is route-specific, not pipeline-wide

6. **`GET /api/v1/tenants` with no `Authorization` header still returns 401** — see
   `mobile_tenant_config_test.exs:"GET /api/v1/tenants with no Authorization header
   still returns 401 -- proves ApiPipeline/AuthPipeline is unchanged"` (describe "AC5").
   The literal example named in the handoff's AC4 text. Dispatches through the same
   `Letflow.Router.call/2` used by every other test in this file — proving the
   unauthenticated exemption is scoped to the two `Letflow.Router`-level `forward/2`
   declarations (`/api/tenant-config`, `/api/mobile/tenant-config`), not something that
   leaked into `Letflow.Plugs.ApiPipeline`/`Letflow.Plugs.AuthPipeline` itself. This is
   the test that would fail if REQ-124 had (incorrectly) implemented AC1 by adding a
   bypass/allowlist branch inside `AuthPipeline` rather than mounting a second,
   independent route ahead of it, per the design's explicit rejection of exactly that
   approach.
7. **A garbage `Authorization` header on the mobile route itself changes nothing** —
   see `mobile_tenant_config_test.exs:"GET /api/mobile/tenant-config itself is
   unaffected by AuthPipeline even when called with a garbage Authorization header"`.
   Complements case 6 from the other direction: proves this route doesn't merely
   *tolerate* a missing header, it never inspects the header at all (mounted entirely
   outside `AuthPipeline`), so a syntactically-present-but-worthless bearer token is
   just as irrelevant as no header. Would fail if a future refactor accidentally routed
   this endpoint's request through any part of `AuthPipeline`'s token-parsing path
   (which would either reject the bogus token with 401, or behave inconsistently
   depending on header presence).

### Global (non-per-tenant) field coverage — locales/default_locale/branding/environment_kind never vary by slug

8. **A known-slug response and the default-fallback response agree on every field
   except `realm_url`** — see `mobile_tenant_config_test.exs:"a resolvable known-slug
   response and the default-fallback response agree on every field except realm_url"`.
   Directly demonstrates the handoff's explicit instruction that these four fields "are
   identical across every branch (only realm_url varies)": compares two structurally
   different branches (a resolvable known slug vs. the default fallback) field-by-field,
   asserting `realm_url` differs while `locales`/`default_locale`/`branding`/
   `environment_kind` are identical. Would fail if any of the four "global" fields were
   accidentally derived from the resolved tenant (e.g. a future change that tried to key
   `environment_kind` off `Tenant.status`).

### Never-error rule — every branch is 200, never 404/500

9. **Every branch tested above (cases 1, 4, 5, 8) already asserts `200`** — no separate
   test needed per branch; the never-error rule is verified as a side effect of every
   positive-path assertion in this file, matching how `req078_supporting_routes_test.exs`
   verifies `Letflow.Routers.TenantConfig`'s identical rule (no branch there gets a
   dedicated "and it's not a 500" test either — the 200 assertion on every case *is* the
   coverage).
10. **An unmatched sub-path under the mount 404s cleanly, not a 500** — see
    `mobile_tenant_config_test.exs:"an unmatched sub-path under the mount still returns
    a clean response, not a 500"` (describe "never-error rule"). This is the one
    genuinely different path this module can take (`match _ do Response.not_found(conn)
    end`), distinguished explicitly from the "GET /" bootstrap path, which the moduledoc
    and design both pin to *always* 200. Would fail if a routing change caused this
    sub-path to raise instead of falling through to the router's own `match _` clause.

### Moduledoc content check (design §7 requirement, folded here rather than a separate spec)

11. **Moduledoc names the shared wrapper and the non-disclosure boundary** — see
    `mobile_tenant_config_test.exs:"moduledoc documents the shared wrapper by name"`.
    Confirms `Letflow.Routers.MobileTenantConfig`'s moduledoc literally names
    `Letflow.Identity.get_tenant_by_slug/1` (the delegate) and contains "never disclose"
    (the disclosure-boundary heading) — a light content check that the design §7
    moduledoc-outline requirement (restated reasoning, not a cross-reference-only doc)
    was actually followed, mirroring `req078_supporting_routes_test.exs`'s own AC5-AC7
    moduledoc-content assertions for sibling modules.

### Acceptance criterion 5 — `Identity.safe_get_tenant_by_slug/2` exception-swallowing

12. **A genuine hit resolves exactly like `get_tenant_by_slug/1`** — see
    `identity_test.exs:"a genuine hit resolves exactly like get_tenant_by_slug/1"`
    (describe "safe_get_tenant_by_slug/2 — exception-swallowing"). Baseline: the wrapper
    must not change behaviour on the success path. Would fail if the wrapper's `rescue`
    clause somehow shadowed a legitimate result.
13. **A genuine miss returns `{:error, :not_found}`, same as the unwrapped function** —
    see `identity_test.exs:"a genuine miss returns {:error, :not_found}, same as
    get_tenant_by_slug/1"`. Distinguishes "not found" from "lookup failed" — the two
    error atoms the wrapper's type signature (`{:error, :not_found | :lookup_failed}`)
    names separately. Would fail if the wrapper collapsed a genuine miss into
    `:lookup_failed` (which would be a different, worse anti-enumeration property than
    intended — see design §4 point 2's "none of them functions as an existence oracle,"
    which relies on distinguishing these at the `Identity` layer even though the
    *router* layer intentionally re-collapses them into one default response).
14. **A raise inside `get_tenant_by_slug/1` is swallowed into `{:error, :lookup_failed}`,
    never propagates** — see `identity_test.exs:"a raise inside get_tenant_by_slug/1 is
    swallowed into {:error, :lookup_failed}, never propagates"`. This is the literal
    acceptance criterion. Passing a non-binary `slug` (`12_345`, an integer) to
    `safe_get_tenant_by_slug/2` makes Ecto's own query planner raise `Ecto.QueryError`
    at query-execution time inside the underlying `Repo.get_by(Tenant, slug: slug)` call
    — confirmed against this project's vendored Ecto dependency
    (`deps/ecto/lib/ecto/query/planner.ex`: `"value \`#{inspect(v)}\` cannot be dumped
    to type #{...}"` -> `raise Ecto.QueryError`). This is a **real** exception raised
    from inside the function under test, not a simulated/mocked one — the raise happens
    because the parameter genuinely cannot be dumped to the `:string` column type, the
    same class of failure a real DB-level type error would produce. Would fail if
    `safe_get_tenant_by_slug/2`'s `rescue` clause were removed or narrowed to a specific
    exception type that doesn't match `Ecto.QueryError`.
15. **`get_tenant_by_slug/1` itself (unwrapped) DOES raise for the same input — proves
    the rescue is load-bearing, not a no-op** — see `identity_test.exs:"get_tenant_by_slug/1
    itself (unwrapped) DOES raise for the same bad input -- proves the rescue in
    safe_get_tenant_by_slug/2 is load-bearing, not a no-op"`. Companion to case 14:
    without this test, case 14 alone couldn't distinguish "the rescue clause correctly
    caught a real exception" from "this input never actually raises anything, so the
    rescue clause is dead code that happens to never fire." `assert_raise
    Ecto.QueryError, fn -> Identity.get_tenant_by_slug(12_345) end` pins that the
    identical input, called WITHOUT the wrapper, genuinely raises — making case 14's
    passing result meaningful.
16. **The warning log names the context label and the slug, never the exception itself
    (INV-4)** — see `identity_test.exs:"the warning log names the context_label and the
    slug, and never the exception itself (INV-4)"`. Uses `ExUnit.CaptureLog.capture_log/1`
    to capture the `Logger.warning/1` call inside the `rescue` clause, asserts the log
    contains the caller-supplied `context_label` (`"req124-log-test"`) and the
    `inspect/1`-rendered slug (`"98765"`), and asserts it does NOT contain `"QueryError"`
    or `"cannot be dumped"` (substrings that would appear if the exception's own message
    were logged). Directly demonstrates the function's own `@doc`'s explicit "never the
    exception itself (INV-4: it can carry connection strings and query text)" claim,
    turning a one-time code-read claim into a standing regression check. Would fail if a
    future edit changed `Logger.warning/1`'s call to interpolate `inspect(exception)` or
    `Exception.message(exception)` instead of the caller-supplied `slug`/`context_label`.

## Fixture isolation

Every `tenants` row inserted by `mobile_tenant_config_test.exs` uses a unique,
per-test slug (`Letflow.TenantSlugFixture.unique_slug/1`) and, where set, a unique
`idp_realm_id` (`System.unique_integer([:positive, :monotonic])`-suffixed) — no test
shares a literal slug/realm with another, and no test depends on execution order.
`identity_test.exs`'s new `describe` block reuses that file's own pre-existing
`unique_slug/1`/`unique_realm/1`/`insert_tenant!/2` helpers, unchanged. Every test in
both files runs inside `Letflow.DataCase`'s per-test sandboxed (rolled-back)
transaction — no `Letflow.TenantFixture` `:auto`-mode/schema-provisioning machinery is
needed anywhere in this spec, since the endpoint under test only ever reads the global
`tenants` table.
