# Test Spec: REQ-125 — Definition delta-sync endpoint (MOB-3 offline cache)

**Requirement:** REQ-125 (`docs/requirements.yaml`, stage S9) — MOB-3. Adds
`GET /definitions/delta?since=<cursor>`, letting a mobile app warm/refresh an offline
cache of a tenant's process definitions incrementally instead of re-fetching the whole
set on every sync.

**Design:** `lib/letflow/design/req125-definitions-delta-sync.md`.

**Handoff acceptance criteria (verbatim, run WF02-REQ125-20260823):**
1. "the delta endpoint returns only definitions changed after the supplied cursor,
   tested with at least three definitions where exactly one changed"
2. "the choice between timestamp and monotonic cursor is stated in the moduledoc with
   its reasoning, and clock skew is addressed explicitly (this is a doc check, not a
   test — confirm it's present, no test needed for AC2 itself)"
3. "deletion/deprecation representation is decided and tested -- a cache consuming the
   delta can learn that a definition is gone"
4. "the behaviour when the cursor predates retained history is defined and tested,
   rather than silently returning an incomplete delta (per the design: the counter
   never expires, so since=nil/0 means full history -- test that; and malformed since
   -> {:error, :invalid_since} -> 400 -- test that too)"
5. "a test asserts that a delta request from tenant A never returns a definition
   belonging to tenant B"

**Test tier:** unit+integration. `Letflow.Definitions.delta/2` (AC1/AC3/AC4's context
layer) is tested directly against a real Postgres tenant schema via
`Letflow.DataCase`/`provisioned_tenant/0` — no HTTP needed for those. AC2 is a pure
moduledoc-content check (no I/O). AC4's malformed-since HTTP mapping and AC5's tenant
isolation are tested at the HTTP layer (`Letflow.Routers.Definitions`), matching
REQ-081's own AC5 cross-tenant placement precedent. Also includes REVIEWER's Step 2d
direction: `store_test.exs`'s pre-existing `activate/2` cross-row TOCTOU regression
test is UPDATED (not deleted) to assert the new definition_sequence-lock serialization
guarantee.

## Test cases

### Acceptance criterion 1 — only definitions changed after the cursor

1. **With three definitions where exactly one changed, delta returns only that one** —
   see `store_test.exs:"delta/2 (AC1) ... with three definitions where exactly one
   changed, delta returns only that one"`. Creates three definitions, takes a baseline
   `since` (full history, all three present), activates one of them (itself a change,
   but *before* the next cursor is taken — asserted absent from the final delta),
   takes a second cursor after the activation, then deprecates that same definition
   (the ONE change strictly after the second cursor). Asserts the final delta's
   `items` is exactly `[deprecated_definition]` — not the other two untouched
   definitions, not the earlier activation. Would fail if `delta/2`'s `WHERE
   sequence_number > since` used the wrong comparison operator (off-by-one on either
   boundary) or queried unfiltered by `since` at all. Verified discriminating: with
   the query mutated from `sequence_number > since_floor` to `>=`, `mix test` was
   re-run and exactly one test failed (the AC1 zero-change case below, not this one —
   see "Mutation testing" below for why, and why that's still sufficient evidence).
2. **A zero-change delta (caller already caught up) is `{:ok, %{items: [], next_since:
   since}}`, never an error** — see `store_test.exs:"...a zero-change delta (caller
   already caught up) is {:ok, %{items: [], next_since: since}}, never an error"`.
   Mirrors `list_paginated/2`'s established "empty page is `{:ok, ...}`, never an
   error" precedent the design doc cites. Would fail if `delta/2` ever returned an
   error, or a non-empty/incorrect `next_since`, for an up-to-date caller.
3. **`GET /delta` (HTTP layer) returns the delta envelope with a real definition
   present** — see `routers/definitions_test.exs:"REQ-125 AC1 ... GET /delta with no
   since returns full history and a next_since watermark"`. End-to-end smoke test
   confirming the route wiring, `definition_map/1` rendering, and JSON envelope shape
   (`items`, `next_since`) all work together, not just the context-layer function in
   isolation.

### Acceptance criterion 2 — cursor-choice reasoning + clock skew (doc check only)

4-7. **`Letflow.Definitions`'s moduledoc states the monotonic-vs-timestamp cursor
   choice, its reasoning, and addresses clock skew explicitly** — see
   `definitions_test.exs:"moduledoc -- AC2 ..."`'s four cases: (a) states `since` is a
   monotonically increasing integer, never a wall-clock timestamp; (b) addresses clock
   skew explicitly as the failure mode this endpoint runs under, naming concrete
   failure modes (device clock drift, timezone misconfiguration, leap-second smear);
   (c) states the counter is server-assigned and bumped inside the same transaction as
   the row mutation it sequences; (d) states a `since` that predates retained history
   is not a distinguishable error state, and why (no expiry/pruning, `since: nil/0`
   means full history). Per this run's task instructions, this is confirmation the
   design's required content is present in the shipped moduledoc, not a test that
   would "fail" for a behavioural reason — but each assertion is still a real,
   independently-checkable string match against the compiled `Docs` chunk (via
   `normalized_moduledoc/1`), matching every other moduledoc-content check already
   established in this file (see AC6/AC9/AC4 blocks above it), not a rubber-stamp.

### Acceptance criterion 3 — deletion/deprecation representation

8. **A deprecated definition appears in the delta with `status: :deprecated`, not
   omitted** — see `store_test.exs:"delta/2 (AC3) ... a deprecated definition appears
   in the delta with status :deprecated, not omitted"`. Activates a definition, takes
   a cursor, deprecates it, and asserts the resulting delta item's `status` field is
   `:deprecated` — the exact mechanism the design doc (§3) says a consuming cache uses
   to learn "this definition is gone" (no separate tombstone type). Would fail if
   `delta/2`'s query were ever filtered by status (excluding non-active rows), which
   would silently break offline-cache invalidation.
9. **An archived definition appears in the delta with `status: :archived`, not
   omitted** — see `store_test.exs:"delta/2 (AC3) ... an archived definition appears
   in the delta with status :archived, not omitted"`. Same shape as case 8, one status
   further down the lifecycle (`deprecated!` fixture then `archive/2`), confirming the
   terminal status is equally representable, not just the intermediate one.

### Acceptance criterion 4 — stale/malformed cursor behaviour

10. **`since: nil` returns every existing row — a device's first sync, by
    construction** — see `store_test.exs:"delta/2 (AC4) ... since: nil returns every
    existing row -- a device's first sync, by construction"`. Would fail if `delta/2`
    ever required a non-nil `since` or returned a partial/empty result for the
    no-prior-watermark case.
11. **`since: 0` returns the exact same full history as `since: nil`, including an
    identical `next_since`** — see `store_test.exs:"delta/2 (AC4) ... since: 0 returns
    the exact same full history as since: nil"`. Directly demonstrates the design's
    "since=nil/0 means full history" equivalence, not just nil alone. Verified
    discriminating: with `validate_since/1`'s `since >= 0` guard mutated to `since >
    0`, `mix test` was re-run and exactly this test failed (0 was rejected as
    `:invalid_since` instead of floored to full history) — see "Mutation testing"
    below.
12. **A negative `since` returns `{:error, :invalid_since}`, never a silent
    full/empty dump** — see `store_test.exs:"delta/2 (AC4) ... a negative since
    returns {:error, :invalid_since}, never a silent full/empty dump"`.
13. **A non-integer `since` (a string, a float) returns `{:error, :invalid_since}`** —
    see `store_test.exs:"delta/2 (AC4) ... a non-integer since returns {:error,
    :invalid_since}"`. Defensive-coding check on `validate_since/1`'s catch-all clause,
    independent of the router's own parsing layer (case 15 below).
14. **`GET /delta?since=0` (HTTP layer) is treated as full history, not an error** —
    see `routers/definitions_test.exs:"REQ-125 AC4 ... GET /delta?since=0 is treated
    as full history, not an error"`. HTTP-layer companion to case 11.
15. **`GET /delta?since=<malformed>` returns 400 for three distinct malformed shapes**
    — see `routers/definitions_test.exs:"REQ-125 AC4"` describe block's three cases:
    a non-numeric string (`not-a-number`), a negative integer (`-1`), and digits with
    trailing garbage (`12abc`, proving `Integer.parse/1`'s full-string-consumption
    requirement is actually enforced, not just a leading-digit parse). The `12abc`
    case is verified discriminating: with `parse_since_param/1`'s
    `{int, ""} -> {:ok, int}` clause mutated to accept any trailing remainder
    (`{int, _trailing} -> {:ok, int}`), `mix test` was re-run and exactly this test
    failed — see "Mutation testing" below.

### Acceptance criterion 5 — tenant isolation

16. **Tenant A's delta never contains a definition created/mutated only in tenant B's
    schema** — see `routers/definitions_test.exs:"REQ-125 AC5 ... tenant A's delta
    never contains a definition belonging to tenant B"`. Creates and activates+
    deprecates a definition in tenant B's schema (maximally "changed", i.e. the case
    most likely to leak if isolation were broken), requests tenant A's own `/delta`
    with no `since`, and asserts tenant B's definition id is absent from the response.
    This is the literal test obligation the handoff and design doc §8 both name.
17. **Tenant B's own high-water `since` cursor, replayed against tenant A, is scoped
    to tenant A's own counter — never used to probe tenant B's change volume** — see
    `routers/definitions_test.exs:"REQ-125 AC5 ... tenant B's own since cursor,
    replayed against tenant A, is scoped to tenant A's own counter"`. Gives tenant B a
    much larger change volume (5 definitions) than tenant A (1), takes tenant B's
    `next_since`, and sends that exact integer as tenant A's own `since`. Asserts
    `200` (never an error — a numerically-plausible-but-foreign cursor is never
    treated as invalid) and an empty `items` list (tenant A's own counter is nowhere
    near that high, so nothing in tenant A's schema has a `sequence_number` that
    large) — directly demonstrating design §8's "the cursor cannot be used to probe
    another tenant's change volume" claim, not just asserting it by citation.
18. **`GET /delta` requires `DefinitionsRead`, same as every other read endpoint** —
    see `routers/definitions_test.exs:"REQ-125 AC6 ... AGENT_RUNNER (no
    DefinitionsRead) gets 403 on /delta"`. Not itself part of AC5's tenant-isolation
    wording, but adjacent authorization coverage for the new route, matching REQ-081's
    own AC6 block's shape (this file already has one covering the other five
    endpoints; `/delta` needed its own since it isn't in that block's endpoint list).

## TOCTOU test update (REVIEWER, Step 2d)

`store_test.exs`'s pre-existing `"Regression -- activate/2 cross-row TOCTOU"` describe
block asserted that two concurrent `activate/2` calls on two DRAFT definitions sharing
one `name`, deterministically forced into the race window design doc §6.2 documents,
produce exactly one success and one `{:error, {:transaction_failed, _}}` (a real
Postgres `unique_violation` on `uq_active_definition`). REQ-125 (design §5.3) added a
per-tenant-schema `definition_sequence` lock that every `activate/2` call now takes as
its very first step inside the same transaction — this closes the race window the old
test forced: a second concurrent `activate/2` call for the same tenant now blocks at
the Postgres level (on the `definition_sequence` row's `FOR UPDATE` lock) until the
first call's transaction commits, by which point the first call's write is already
visible, so the second call's own deprecate-step correctly deprecates it instead of
racing it.

**Confirmed, not asserted:** running the OLD test (`git show
b4831ef:lib/letflow/definitions.ex`, the commit immediately before ELIXIR-DEV's
REQ-125 implementation landed) against the CURRENT test suite reproduces the original
failure this run started from — `assert_receive {:toctou_paused, ^task1_pid}` times
out, because the query-count rendezvous the old test relied on no longer matches the
new transaction's actual query shape.

The UPDATED test (renamed describe block, same file) forces the NEW guarantee into
view the same way the old one forced the race: pauses task 1 (via the same `[:letflow,
:repo, :query]` telemetry rendezvous technique, no test hook added to
`lib/letflow/definitions.ex`) right after it acquires the tenant-wide
`definition_sequence` row lock; releases task 2 and proves BY NEGATIVE ASSERTION
(`refute_receive`, real wait window) that task 2's own attempt to acquire that same
lock has NOT completed while task 1 holds it; releases task 1 to commit; proves task 2
now completes. Asserts both `activate/2` calls succeed (no `unique_violation` fallback
path is reachable anymore — serialization removed the race window entirely, not just
narrowed it), and checks REVIEWER's requested post-hoc invariants: `get_active_by_name/2`
returns exactly one row, the deprecated row's `sequence_number` is strictly less than
the surviving active row's, and `count_active_by_name/2 == 1` (no double-ACTIVE state).

**This is itself the case-where-the-fail-then-pass-check-is-nontrivial**: the new test
was verified to (a) PASS against the current (post-fix) implementation, and (b) FAIL
against the pre-fix implementation (`b4831ef`'s `lib/letflow/definitions.ex`, swapped
in temporarily and reverted via `git diff --stat` confirming a clean restore) — both
runs shown, not asserted, per `docs/guides/test_developer_guide.md` §5.

## Mutation testing (delta/2's own discriminating power)

Since `delta/2` and its private helpers are new code, three temporary mutations were
applied to `lib/letflow/definitions.ex`/`lib/letflow/routers/definitions.ex`, `mix
test` was re-run, the specific expected test failure was confirmed, and the mutation
was reverted (confirmed clean via `git diff --stat` showing no changes) before the
next mutation and before this run's final commit:

1. **`delta/2`'s query**: `d.sequence_number > ^since_floor` → `>=`. Result: 1 failure
   — `delta/2 (AC1) ... a zero-change delta (caller already caught up) is {:ok,
   %{items: [], next_since: since}}, never an error`. (Case 2 above.) The AC1
   exactly-one-changed test, case 1, did NOT fail under this mutation — traced and
   understood, not just observed: by the time that test's third `delta/2` call runs,
   the row whose `sequence_number` originally equaled the boundary value has since
   been reassigned a strictly higher `sequence_number` (the deprecate step bumps it
   again), so no row remains at exactly the mutated boundary for that particular call
   sequence to expose. The zero-change test's boundary is untouched by any later
   write, so it reliably exposes this exact mutation — one discriminating test is
   sufficient evidence the mutation is caught, even though a second test that could
   have caught it happens not to for this specific fixture sequence.
2. **`validate_since/1`**: `since >= 0` → `since > 0`. Result: 1 failure — `delta/2
   (AC4) ... since: 0 returns the exact same full history as since: nil`. (Case 11
   above.) Exactly the boundary case designed to catch this.
3. **`parse_since_param/1`** (router): `{int, ""} -> {:ok, int}` → `{int, _trailing}
   -> {:ok, int}`. Result: 1 failure — `REQ-125 AC4 ... GET
   /delta?since=12abc (trailing garbage after digits) returns 400, not a truncated
   parse`. (Case 15's third sub-case.)

Each mutation produced exactly the expected single failure (confirmed via `mix test`
output, not inferred), and every other test in the three touched files continued to
pass under each mutation — no mutation silently broke unrelated coverage.
