# Test Spec: REQ-126 — Version-pinned form references on task payloads (MOB-3 pinning)

**Requirement:** REQ-126 (stage S9). Adds `form_id`/`form_version` to every task
payload returned by `GET /tasks`, `GET /tasks/inbox`, `GET /tasks/:id` (the three
REQ-083 read routes), so a client (SPA or mobile app) can render the exact pinned
form version and never silently fall back to the currently-active one. Full text in
`docs/requirements.yaml`'s REQ-126 entry.

**Design:** `lib/letflow/design/req126-form-version-pinning.md` — `form_id ==
task.node_id`; `form_version == instance_definition_snapshots.definition_ver`,
looked up by `task.instance_id` via a `left_join`. No new schema, no new pin
machinery (§2.3 states the relationship to `Letflow.Engine.PinResolver` explicitly,
in `Letflow.Tasks`'s moduledoc, per acceptance criterion 2).

**Implementation:** `lib/letflow/tasks.ex` (`get_task/2`, `list_tasks/2`,
`get_form_version/2`), `lib/letflow/routers/tasks.ex` (`task_list_item_map/2`,
`task_detail_map/3`, and the read/write route handlers that call them).

**Test tier:** integration (`Letflow.DataCase`, real Postgres, real tenant-schema
provisioning via `Letflow.TenantFixture`), dispatched directly against
`Letflow.Routers.Tasks.call/2` — matching REQ-083's/REQ-085's own established
convention in this same file.

**Test file:** `test/letflow/routers/tasks_test.exs` (extended, not replaced — new
`describe` blocks under a `REQ-126` heading, added fixture helpers
`graph_human_task_end_v2/0` and `active_definition_named!/4`, and the two
`@task_list_item_keys`/`@task_detail_keys` module attributes widened to the new,
intentional 11-key/13-key shape).

## 1. Acceptance-criteria -> test-case mapping

### AC1 — task payloads returned by the task read routes carry `form_id` and
`form_version`, asserted against the actual response body

**Why this test exists, not just a restatement of the criterion:** the design
routes `form_version` through two structurally different code paths depending on
which handler answers the request — `get_task/2`'s own `left_join` for
`GET /tasks/:id`, and `list_tasks/2`'s separately-added `left_join` for
`GET /tasks`/`GET /tasks/inbox` (§4.1 vs §4.2) — sharing no query between them. A
test against only one of the two paths would not catch a regression that fixed one
`left_join` and left the other one stale (e.g. a copy-paste of the join that
selects the wrong column, or a widened `select` tuple whose shape one call site
forgot to destructure). Testing both the detail route and the list route closes
that gap.

* `describe "REQ-126 AC1: task payloads returned by the read routes carry form_id/form_version"`:
  * `GET /tasks/:id` — starts a real instance via `Letflow.Engine.create/5` from an
    active `v1.0.0` definition whose graph has a `HUMAN_TASK` node named `"task"`
    (`start_instance_with_pending_task!/2`, REQ-085's own established fixture — the
    only path that produces a genuine `instance_definition_snapshots` row, unlike
    `insert_task!/2`'s direct-`Repo.insert!` fixture which has no such row and
    would only ever exercise the `nil`-fallback case). Asserts
    `body["form_id"] == "task"` (the activated node's own id) and
    `body["form_version"] == "1.0.0"` (the version the instance started from).
  * `GET /tasks` — same fixture; asserts the corresponding list item (matched by
    `id`) carries the same `form_id`/`form_version` pair, proving `list_tasks/2`'s
    independently-added `left_join` produces the same answer as `get_task/2`'s.

### AC2 — the relationship to `Letflow.Engine.PinResolver` is stated in the
moduledoc

**No test written for this criterion.** This is a documentation acceptance
criterion with no independently executable behavior — REQ-083's own AC6 in this
same file set the precedent for treating a "moduledoc states X" criterion as
non-testable-by-ExUnit and confirming it by direct inspection instead. Confirmed
directly against the shipped module (not a handoff summary): `lib/letflow/tasks.ex`
lines ~43-56 (the "## Form version pinning (REQ-126, MOB-3)" section) state, in
substance, that `PinResolver` pins external/mutable-catalog references needing an
active `resolve/4` step, that a form reference has no such external catalog (it is
already inside the definition's own already-immutable snapshot row), and that this
requirement therefore adds a new read rather than new pin machinery — matching
design §2.3 and satisfying AC2's own wording ("reusing its mechanism where it
applies, and saying why where it does not"). If a future reviewer disagrees that
this reading is correct, that is a REVIEWER/CODE-DESIGN-VALIDATOR-level
documentation-quality question, not something an ExUnit assertion can adjudicate.

### AC3 — the pinned version reflects the version pinned when the task was
created, proven by a test that changes the form after task creation and asserts
the payload still names the original version

**Why this test exists:** this is the requirement's central anti-regression case —
the design's own §7.2 names the exact scenario, because the most natural *wrong*
implementation (a live `process_definitions` lookup by process name, joined
through `instance_projections`/the definition id instead of through the frozen
snapshot row) would pass every other test in this file (including AC1's) while
silently answering the *current* active version instead of the *pinned* one — the
exact MOB-3 failure this requirement exists to prevent. Only a test that actually
promotes a second version after the task exists can distinguish the two
implementations.

* `describe "REQ-126 AC3: form_version reflects the version pinned when the task
  was created, not a later promotion"` — follows design §7.2's five numbered steps
  verbatim:
  1. `active_definition_named!/4` creates+activates a definition named
     `process_name` at version `"1.0.0"`, graph `graph_human_task_end/0` (a
     `HUMAN_TASK` node id `"task"`).
  2. `Letflow.Engine.create/5` starts an instance from v1 — writes the
     `instance_definition_snapshots` row (`definition_ver: "1.0.0"`) and activates
     a `tasks` row for `"task"`.
  3. `active_definition_named!/4` again, same `process_name`, version `"2.0.0"`,
     a graph with the `"task"` node's `attributes` changed
     (`graph_human_task_end_v2/0`) — `Definitions.activate/2`'s own PD-03 contract
     atomically deprecates v1 in the same transaction, which the test confirms
     directly (`v1_reloaded.status == :deprecated`) so the scenario is provably
     "the process's live version really did change," not merely "a second,
     inactive definition row exists somewhere."
  4. `GET /tasks/:id` for the task created in step 2.
  5. Asserts `body["form_version"] == "1.0.0"` and, explicitly,
     `refute body["form_version"] == "2.0.0"` — the second assertion is redundant
     with the first only if `"1.0.0" != "2.0.0"` continues to hold, which is true
     here but is written out anyway so a reader sees the negative case named, not
     only implied.

### AC4 — the SPA's existing behaviour is unchanged: `web/`'s test suite passes
unmodified against the new payload shape

**Why this is a run-the-suite criterion, not a new SPA test:** REQ-126 does not
ask the SPA to consume `form_id`/`form_version` — only to tolerate two additive,
unconsumed response keys. The design (§6.3) already establishes *why* this cannot
fail: the SPA's `RawTask`/`Task` type boundary
(`web/src/api/tasks.ts`'s `normalizeTask`) is a plain, non-`.strict()` TypeScript
interface spread, and `web/tsconfig.app.json` sets no
`exactOptionalPropertyTypes` — nothing in that boundary can fail to compile or run
because of two new, unread keys. Proving it means running the real suite, not
writing a new assertion that would just restate the type-boundary argument in
prose.

* Ran `cd web && npm install --no-audit --no-fund` (no `node_modules` present in
  this worktree) then `npm test`
  (`vitest run --passWithNoTests --exclude tests/e2e/** --exclude tests/guards/**`,
  `web/package.json`'s own `"test"` script). No `web/` source or test file was
  touched by this change.

### AC5 — a test asserts the field is present rather than null for a task whose
definition pins a form, so an unimplemented path cannot pass as a satisfied one

**Why this is a separate test from AC1, not folded into it:** AC1 asserts *which*
values `form_id`/`form_version` carry (`== "task"`, `== "1.0.0"`); AC5 is
specifically a presence guard, per the design's own §7.3 framing — an
implementation that always emits `form_id: nil, form_version: nil` (e.g. a
`left_join` that was added but never wired into the response map, or a response
map that hardcodes `nil` "for now") would fail AC1 immediately, but making AC5
independently named and independently assertable matters because it is the
criterion TEST-DESIGN-VALIDATOR is told to check for explicitly, and a dedicated,
narrowly-scoped `refute is_nil(...)` test is the most direct, least-interpretable
proof of it — it cannot be satisfied by an implementation that coincidentally gets
AC1's exact string values right for the wrong reason (e.g. a hardcoded string
matching the test's own fixture data) while returning `nil` in every other
scenario, since it is checked on the very same real-engine fixture AC1 and AC3 use,
not a special-cased one.

* `describe "REQ-126 AC5: form_id/form_version are present rather than null for an
  ordinarily-created task"` — same real-engine fixture as AC1's detail case;
  `refute is_nil(body["form_id"])`, `refute is_nil(body["form_version"])`.

**Not covered (design's own explicit "MAY," not one of the five ACs):** the
`left_join`-miss fallback case (§5/§7.3 — a `tasks` row with no matching
`instance_definition_snapshots` row, "structurally near-impossible" by
construction since `TaskActivation` never runs before `SnapshotStore.create/3`).
Deliberately not fixtured here — INV-8's non-crash behavior for that case is a
nice-to-have the design explicitly does not require TEST-DESIGNER to cover, and
constructing it would mean bypassing the FK chain `insert_task!/2` already
enforces (`instance_id` with no matching snapshot row, inserted directly via
`Repo.insert!/2`), which is real but off-the-happy-path fixture work with no
acceptance criterion behind it.

## 2. Incidental fix required to keep REQ-083's own existing tests green

`Letflow.Routers.TasksTest`'s pre-existing `@task_list_item_keys`/
`@task_detail_keys` module attributes (used by the REQ-083 "AC5/INV-2: response
allowlists" `describe` block) encoded the *old*, pre-REQ-126 9-key/11-key response
shape. Running the full file against the already-shipped REQ-126 implementation
(before this change) failed both of those pre-existing tests —

```
left:  [..., "form_id", "form_version", ...]   # actual response
right: [...]                                    # old allowlist, missing both keys
```

— confirming the implementation really does add the two keys (this is exactly
AC1's assertion, independently corroborated by an unrelated test's failure) and
that the allowlist needed updating to the new, intentional 11-key/13-key shape.
This is **not** a weakening of REQ-083's own test: the allowlist still asserts an
*exact* key set (`Map.keys(...) |> Enum.sort() == ...`), it merely now names the
two keys REQ-126 deliberately, additively introduced, matching
`lib/letflow/routers/tasks.ex`'s own "Response allowlists" doc comment update for
this requirement.
