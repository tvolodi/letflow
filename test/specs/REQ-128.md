# Test Spec: REQ-128 — Add Keycloak to the dev stack with a Letflow realm and a real issuer

**Requirement:** REQ-128 (`docs/requirements.yaml`, stage S4) — add a `keycloak` service
to `docker-compose.yml` with realm import from a tracked realm file
(`priv/keycloak/realms/bpm-default.json`), a new `config/keycloak_port.exs`
per-workspace host-port resolver, and point `config/dev.exs`/`config/test.exs`'s
`:oidc` issuer at the real local Keycloak instead of the
`https://placeholder-keycloak.invalid/...` placeholder.

**Design doc:** `lib/letflow/design/req128-keycloak-dev-stack.md`, CODE-DESIGN-VALIDATOR
PASSed, corrected post-PASS (2026-08-22) to keep the realm named `bpm-default` rather
than renaming it to `letflow-default` — see that doc's "Correction after
CODE-DESIGN-VALIDATOR PASS" section, which is authoritative over the earlier body text.
That doc's own "Test-designer scope" section (the section this spec implements) states
this requirement introduces no new `lib/letflow/` runtime logic — it is docker-compose
config, a static JSON realm fixture, and Elixir config files — and directs TEST-DESIGNER
to a narrower-than-usual scope: check whether `config/db_port.exs` (the existing,
identical-shape sibling to the new `config/keycloak_port.exs`) has a dedicated unit
test, and match whatever that answer is; check whether this repo has any existing
docker/integration-tagged test convention and, only if one exists, add a smoke test
behind it; and do not, in any case, write a test that requires Docker/Keycloak running
for `mix test` to pass.

**Correction (post-TEST-DESIGN-VALIDATOR FAIL, 2026-08-22):** the "no new
`lib/letflow/` runtime logic" framing above, copied from the design doc's Test-designer
scope section, turned out to be incomplete. Commit `52cb063` on this branch
(`feature/WF02-REQ128-20260822`) added a real conditional to
`lib/letflow/application.ex`'s `start/2`:

```elixir
provider_configuration_opts: %{
  quirks: %{allow_unsafe_http: Keyword.get(oidc_config, :allow_unsafe_http, false)}
}
```

`config/dev.exs` and `config/test.exs` set `allow_unsafe_http: true` (the local
Keycloak container serves its discovery document over plain HTTP, no TLS termination
in front of it — oidcc's discovery parser otherwise rejects a non-HTTPS
`userinfo_endpoint` outright). `config/prod.exs` deliberately does **not** set the
key, so `Keyword.get/3`'s `false` default is the only thing holding a real deployed
issuer to oidcc's safe HTTPS-only discovery validation. That is one bit of real,
new, `lib/letflow/` runtime logic gated entirely on which config file is loaded — and
prior to this correction, nothing in `test/` guarded it: a future accidental
`allow_unsafe_http: true` added to `config/prod.exs` would have shipped a
production issuer with relaxed HTTPS validation and `mix test` would have stayed
green with zero signal. TEST-DESIGN-VALIDATOR's FAIL on the original version of this
spec caught exactly this gap. Test case 3 below adds the one regression test this
actually needed — not zero, as the original "no runtime logic" framing concluded, and
not a broad new suite either; `application.ex`'s only other REQ-128-adjacent change
(reading `:allow_unsafe_http` off `oidc_config` at all) is otherwise pure
config-plumbing already exercised indirectly by every `mix test` run booting
`Letflow.Application` against `config/test.exs`'s `allow_unsafe_http: true`, per
`test/letflow/application_test.exs`'s pre-existing tests.

**Requirement's acceptance criteria (verbatim, from `docs/requirements.yaml`):**
1. "docker compose up -d starts Keycloak and it reaches a healthy state, with the actual
   healthcheck output quoted"
2. "the realm's discovery document is fetched successfully over HTTP from the configured
   issuer, quoted in the result -- proving the issuer is real and reachable, not merely
   written down"
3. "the realm defines all five roles from Letflow.Api.Authorization (PLATFORM_ADMIN,
   PROCESS_DESIGNER, PROCESS_OPERATOR, TASK_WORKER, AGENT_RUNNER), verified by reading
   them back from the running Keycloak rather than from the JSON file"
4. "the seeded operator account holds PROCESS_OPERATOR and NOT PLATFORM_ADMIN, asserted
   explicitly"
5. "a token obtained from the running Keycloak carries a flat top-level `roles` claim,
   demonstrated by decoding a real token and quoting the payload"
6. "Oidcc.ProviderConfiguration.Worker starts against the real issuer and reaches a ready
   state instead of retrying, evidenced from a running node"
7. "the Keycloak host port follows the repo's per-workspace .env pattern rather than
   being hardcoded"
8. "the chosen default host port is not 8081 and is not any port already mapped in
   R-Co's docker-compose.yml, verified by reading that file and quoting its ports:
   entries -- not by checking whether R-Co happens to be running"
9. "config/prod.exs is unchanged and the result states why"

**Why none of these acceptance criteria produce a `mix test` unit/integration test:**
Every one of the nine criteria above is a live-instance verification against a running
Keycloak container — "starts... and reaches a healthy state", "fetched successfully over
HTTP", "verified by reading them back from the running Keycloak", "a token obtained from
the running Keycloak", "evidenced from a running node". None describes behavior of
Elixir code under `lib/letflow/` that a unit test could assert against; all nine are
executed and evidenced by ELIXIR-DEV directly (docker healthcheck output, a curl of the
discovery document, Keycloak Admin REST API reads, a decoded JWT, `iex` inspection of
`Oidcc.ProviderConfiguration.Worker`) per the design doc's "Verification plan" section,
which explicitly states this is "not a new test suite; TEST-DESIGNER's scope below is
narrower." Writing an ExUnit test that spun up Docker/Keycloak to re-assert these would
either (a) require Docker/Keycloak present for `mix test` to pass — forbidden by this
requirement's own scope note and by `config/test.exs` policy — or (b) mock/stub Keycloak
entirely, which would only prove the mock returns what it was told to return, not that a
real Keycloak instance behaves this way. Neither is real coverage.

## Test case 1: `config/keycloak_port.exs` — no dedicated unit test file (matches
`config/db_port.exs`'s existing precedent)

**Check performed:** `grep -rn "db_port" test/` was run against this worktree before
deciding anything. It returns only incidental references inside
`test/reports/*.yaml` run-history reports (prose quoting `LETFLOW_DB_PORT` values used
during past runs) and zero matches under `test/letflow/`, `test/letflow_web/`, or
`test/support/`. `config/db_port.exs` — the file `config/keycloak_port.exs` mirrors
exactly (same three-tier precedence: env var → untracked `.env` → hardcoded default;
same `Integer.parse/1` guard; same raise-with-usage-message on a bad value; see both
files' identical structure) — has never had a dedicated ExUnit test file in this repo's
history.

**Why this is not "no coverage," and why inventing one now would be wrong:** the design
doc's Test-designer scope explicitly asks to mirror `db_port.exs`'s existing precedent
rather than invent a new one, and the reason that precedent makes sense holds for
`keycloak_port.exs` too — the file's actual logic (env-var override → dotenv-file parse
→ default, with an integer guard) already runs, unmocked, as a value used by every
`mix test` invocation, since `config/test.exs` evaluates it via `Code.eval_file/1` at
config-load time (before any test process starts) to compute the `:oidc` issuer URL. A
parse failure or a malformed `.env` value is not a silent bug path here: it raises
immediately at config-eval time with the file's own descriptive error message, which
means `mix test` itself would fail loudly (config load error, not a passing/failing
ExUnit test) before a single test could run, for either file. Adding an ExUnit unit
test around a function that is not exposed as a callable unit (it is a script evaluated
via `Code.eval_file/1`, not a module with an importable function) would mean either (a)
duplicating its body into a test-callable form — testing a copy, not the shipped file —
or (b) shelling out to re-evaluate the real file under controlled env vars, which is
extra machinery this repo has deliberately not built for its first instance
(`db_port.exs`) and the design doc directs matching that choice, not diverging from it.

**Conclusion:** no test file added for `config/keycloak_port.exs`, matching
`config/db_port.exs`'s existing (lack of) coverage exactly, per explicit design-doc
instruction to check first and match rather than invent.

## Test case 2: no docker/integration-tagged smoke test — no such convention exists in
this repo today

**Check performed:** `grep -rln "@moduletag :docker" test/`, `grep -rln "@tag :docker"
test/`, and a broader `grep -rln ":docker" test/` (in case of a differently-cased or
differently-spelled tag) were all run against this worktree. All three returned zero
matches. No test file anywhere under `test/` currently gates any test behind a
Docker/integration/live-service tag of any name (`:docker`, `:integration`, `:live`, or
similar patterns were also checked and found absent).

**Why this means no smoke test is added:** the design doc's Test-designer scope is
conditional — "if this repo has any existing docker/integration-tagged test convention
[...] add a smoke test gated behind that tag" — and explicit that the negative branch
is "do NOT invent a docker-in-CI dependency where none exists today." Since the grep
above confirms no such convention exists, adding one here would be inventing new test
infrastructure (a new tag, a new opt-in test-running convention, a new expectation for
whoever eventually runs `mix test --include docker` or equivalent) as a side effect of
this configuration-only requirement — exactly what the design doc instructs against.
This is a documented decision, not an oversight: a future requirement that wants
Docker-gated smoke tests as a first-class repo convention should introduce that
convention deliberately (tag name, `test_helper.exs` wiring, CI/local documentation)
rather than have it appear as a one-off inside REQ-128's scope.

**Conclusion:** no smoke test added. `mix test` and `scripts/test_parallel.sh` continue
to require no Docker/Keycloak present, exactly as before this requirement, unchanged by
this requirement's own implementation (`config/test.exs` still uses
`Letflow.Oidc.TokenVerifierDouble`, confirmed unchanged by
`lib/letflow/design/req128-keycloak-dev-stack.md`'s scope point 4).

## Test case 3: `lib/letflow/application.ex`'s `allow_unsafe_http` default is held to
`config/prod.exs` specifically, not just the currently-loaded env

**What's under test:** `lib/letflow/application.ex`'s `start/2` (commit `52cb063`)
computes
`Keyword.get(oidc_config, :allow_unsafe_http, false)` and feeds it to
`Oidcc.ProviderConfiguration.Worker`'s `provider_configuration_opts.quirks.allow_unsafe_http`.
This is real conditional runtime logic — the design doc's "no new `lib/letflow/`
runtime logic" premise, taken at face value, missed it (see the "Correction" note
above). `config/dev.exs` and `config/test.exs` both set `allow_unsafe_http: true`
deliberately (local Keycloak serves discovery over plain HTTP);
`config/prod.exs` deliberately omits the key so the `Keyword.get/3` `false`
default applies to a real deployed issuer. The invariant worth protecting is
narrow and specific: **`config/prod.exs` must never set `allow_unsafe_http: true`.**

**Why the existing `test/letflow/application_test.exs` tests don't already cover
this:** every existing test in that file reads `Application.fetch_env!(:letflow, :oidc)`
— the *currently loaded* config, which under `mix test` is always
`config/test.exs`'s (`allow_unsafe_http: true`, by design). None of them ever loads
`config/prod.exs`'s source, so none could catch a regression specific to that file.

**Test added:** `test/letflow/application_test.exs`, one new test appended to the
existing `Letflow.ApplicationTest` module (not a new file — this module already
covers `application.ex`'s OIDC-worker wiring end to end, so a `prod.exs`-specific
assertion about the same wiring's config input belongs alongside it rather than in a
new file):

```elixir
test "config/prod.exs's :oidc config does not set :allow_unsafe_http, so application.ex's Keyword.get default (false) holds a real production issuer to safe HTTPS-only discovery validation" do
  prod_config_path = Path.expand("../../config/prod.exs", __DIR__)

  config = Config.Reader.read!(prod_config_path)
  oidc_config = Keyword.fetch!(config[:letflow], :oidc)

  refute Keyword.has_key?(oidc_config, :allow_unsafe_http),
         "config/prod.exs must not set :allow_unsafe_http -- doing so would relax " <>
           "oidcc's HTTPS-only discovery validation for a real production issuer " <>
           "(see lib/letflow/application.ex's provider_configuration_opts comment)"
end
```

It loads `config/prod.exs` directly via `Config.Reader.read!/2` — independent of
`MIX_ENV` and of whatever env happens to be loaded in the test VM — rather than via
`Application.get_env`/`fetch_env`, which would read the currently-loaded (`test`)
env and prove nothing about `prod.exs`. No Docker, no real Keycloak, no network:
pure config-file parsing.

**Proof this is a real regression test, not one that only ever runs against
already-correct code:** temporarily adding `allow_unsafe_http: true` to
`config/prod.exs`'s `:oidc` block and re-running just this test fails it
(`Keyword.has_key?/2` returns `true`, `refute` fails) with the message above;
reverting the edit passes it again. This was verified locally as part of writing
the test (edit → `mix test test/letflow/application_test.exs` → 1 failure with the
expected message → revert → 4 passed) before this spec was finalized.

**Result:** `MIX_ENV=test "/c/Program Files/Elixir/bin/mix" test
test/letflow/application_test.exs` — 4 tests, 0 failures (3 pre-existing + this one).
`MIX_ENV=test "/c/Program Files/Elixir/bin/mix" compile --warnings-as-errors` — clean,
no warnings.

## Summary

Two of the design doc's Test-designer scope conditions were checked against the
actual state of this repo and came back negative for new test-code obligations:
`db_port.exs` has no dedicated unit test to mirror, and no docker-tagged test
convention exists to attach a smoke test to. Those two remain correctly
uncovered by design.

The doc's third premise — "no new `lib/letflow/` runtime logic" — was wrong:
`lib/letflow/application.ex`'s `allow_unsafe_http` default (commit `52cb063`) is real
conditional logic gating production HTTPS-only discovery validation, previously
unguarded by any test. Test case 3 above closes that gap with exactly one regression
test, appended to the existing `test/letflow/application_test.exs`, verified to fail
against a mutated `config/prod.exs` and pass against the real one. REQ-128's nine
`docs/requirements.yaml` acceptance criteria remain live-instance verifications
executed and evidenced directly by ELIXIR-DEV per the design doc's "Verification
plan" section — this test targets the one piece of `lib/letflow/` logic those criteria
don't already cover, not a restatement of any of the nine.
