# Test Spec: REQ-131 — Implement REQ-130's authorization mechanism and make it mandatory router-wide

**Requirement:** REQ-131 (stage S4). Builds `Letflow.Plugs.Authorize` +
`Letflow.Api.AuthorizedRouter` (REQ-130's chosen mechanism) and migrates all 53
pre-existing call sites across identity/audit/definitions/instances/onboarding/tenants/
tasks onto it, plus wires promotion.ex and metrics.ex, deleting every router-local
`with_authorized_scope/4`/`with_authorization/4` helper. Full text:
`docs/requirements.yaml` REQ-131.

**Design:** `lib/letflow/design/req130-authorization-generalization.md`.

**Implementation:** `lib/letflow/plugs/authorize.ex`, `lib/letflow/api/authorized_router.ex`,
every router under `lib/letflow/routers/` (commit `7e2f602`).

**Test tier:** unit (`Letflow.Plugs.AuthorizeTest`, DB-free) + integration
(`Letflow.Routers.IdentityTest`, `Letflow.Api.AuthorizationEnforcementTest`,
`Letflow.Plugs.ApiPipelineIntegrationTest`, `Letflow.RouterTest`,
`Letflow.Routers.InstancesTest`, real Postgres via `Letflow.TenantFixture`).

**Role:** TEST-DESIGNER, WF-02 Step 3 coverage-verification pass. ELIXIR-DEV already
wrote `test/letflow/api/authorization_enforcement_test.exs` and updated three
pre-existing test files as part of the implementation commit; SECURITY-REVIEWER and
REVIEWER already passed the branch including those tests. This pass independently
re-derives AC-to-test coverage for all 10 ACs rather than trusting ELIXIR-DEV's own
claim, per this project's central redundancy principle
(`docs/migration/decisions/0004-humanless-pipeline.md`), and fills the two real gaps it
found.

## 1. Acceptance-criteria -> test-case mapping

Each row names the file:test-name(s) that prove the AC, and whether the coverage was

### AC1 — a request with a valid token but insufficient role receives 403 as an RFC
9457 problem document via `Letflow.Api.Response`, asserted on both body shape and
Content-Type, exercised against a real identity.ex route

**Gap found and filled.** Pre-existing identity.ex 403 tests (`AC4: permission-denial
on the three write routes...` etc.) asserted only `conn.status == 403` — none asserted
body shape or `Content-Type`. `test/letflow/router_test.exs`'s REQ-070 AC3 block asserts
RFC 9457 shape/Content-Type but only for the top-level 404, not a 403 on a real
identity.ex route.

* Added: `test/letflow/plugs/authorize_test.exs` —
  `"insufficient role on a real policy key -> 403, problem+json Content-Type, RFC 9457
  body shape"` (`describe "AC1: a Deny403 sends an RFC 9457 problem document"`). Uses
  policy key `:UsersManage` (a real identity.ex route's own declared key) with role
  `TASK_WORKER`, asserts `Content-Type: application/problem+json`, and the decoded body's
  `status`/`type`/`title`/`detail` members plus the literal `detail` text
  `Letflow.Plugs.Authorize` sends.

### AC3 — mechanism wired into every router mounted under `Letflow.Plugs.ApiPipeline`
(7 wired + promotion.ex + metrics.ex), such that a new route is authorized without its
author adding it themselves

**Already covered — no gap.** `test/letflow/api/authorization_enforcement_test.exs`'s
`@routers` list walks all 10 routers (7 wired + `Letflow.Routers.Promotion` +
`Letflow.Routers.Metrics`, plus SolutionPacks) via each router's own compiled
`__authz_routes__/0`, and a separate test
(`"Letflow.Routers.Promotion declares zero routes (genuine stub, REQ-077 not yet
shipped)"`) confirms promotion.ex is a real zero-route stub, not silently unwired. The
"without the author adding it themselves" half is structural: `Letflow.Api.AuthorizedRouter`
`plug`s `Letflow.Plugs.Authorize` unconditionally at `use`-time (confirmed by reading
`lib/letflow/api/authorized_router.ex`), so a bare `get`/`post`/etc. route on any of
these routers still passes through it — proven at runtime by AC4/AC5's tests below.

### AC4 — an enforcement artefact exists that FAILS when a route carries no policy key

**Gap found and filled — the "ongoing, not just one-time" half.**
`authorization_enforcement_test.exs`'s own moduledoc states its structural walk
"cannot see" a route declared with no policy key at all (it is never accumulated into
`__authz_routes__/0`), and explicitly defers that runtime case to
`test/letflow/api/authorize_plug_test.exs` — **a file that does not exist anywhere in
this codebase** (confirmed by a filesystem search before writing this spec). So the only
evidence AC4's runtime behavior held was ELIXIR-DEV's one-time manual demo during
implementation (temporarily adding an unguarded route, quoting the failure, reverting
it) — nothing ran it on every subsequent `mix test`.

* Added: `test/letflow/plugs/authorize_test.exs`,
  `describe "AC4/AC5: a route with no policy key (:Unknown) is fail-closed-EXCEPT-PLATFORM_ADMIN"`
  — dispatches directly to `Letflow.Plugs.Authorize.call/2` with no `:policy_key` private
  key set at all (the exact shape a policy-key-less route produces), asserting a
  non-admin caller is denied 403. This runs on every `mix test`, closing the "ongoing"
  gap the deferred/missing file left open.

### AC5 — an unmatched (method, path) denies for every role EXCEPT PLATFORM_ADMIN, with
a test asserting both halves

**Gap found and filled — the PLATFORM_ADMIN-allow half was entirely untested.** The
non-admin-denial half was already indirectly covered (`test/letflow/plugs/
api_pipeline_integration_test.exs`'s REQ-071 AC2/AC4 tests hit an unmatched route with
an unrecognized `"VIEWER"` role and observe 403), but **no test anywhere in this
codebase exercised the PLATFORM_ADMIN-allowed half** of the same `:Unknown` branch —
confirmed by grepping `test/` for `PLATFORM_ADMIN.*allow`/`:Unknown` and reading
`test/letflow/api/authorization_test.exs` in full (it tests `roles_from_strings/1`
exhaustively but has no case at all for `evaluate_access/2`'s `:Unknown` branch).

* Added: same `describe` block as AC4 above —
  `"no :policy_key private key, PLATFORM_ADMIN -> allowed through, not halted,
  scoped_opts assigned"` proves the admin-allow half, and
  `"no :policy_key private key, non-admin role -> 403"` /
  `"no :policy_key private key, no roles at all -> 403"` cover the denial half directly
  at the plug (in addition to the pre-existing indirect router-level evidence), so both
  halves of AC5 are now asserted in one file, matching the AC's own "asserting both
  halves" wording.

### AC6 — a token carrying an unrecognized role string is treated as holding no role,
not as holding an unknown-but-accepted one

**Already covered at the function level — reinforced at the plug level.**
`test/letflow/api/authorization_test.exs`'s `describe "roles_from_strings/1 —
untrusted-input conversion (§0.2)"` (pre-existing, unchanged by REQ-131 since that
function itself was not touched) already exhaustively proves unrecognized strings are
dropped, never defaulted to an accepted role. `Letflow.Plugs.Authorize.call/2` calls
that same function directly (`lib/letflow/plugs/authorize.ex:105`), and
`api_pipeline_integration_test.exs`'s REQ-071 AC2 test is indirect end-to-end evidence
(an unrecognized `"VIEWER"` role is denied identically to holding no role at all).

* Added (belt-and-suspenders, at the plug boundary rather than only the underlying
  function): `test/letflow/plugs/authorize_test.exs`,
  `describe "AC6: an unrecognized role string is dropped, not accepted-unknown"` — two
  tests proving a caller holding only unrecognized role strings is denied byte-identically
  to a caller holding no roles at all, and that mixing a recognized-but-insufficient role
  with unrecognized strings evaluates only the recognized one.

### AC8 — the mechanism's position in the pipeline matches the design, and a test
demonstrates it runs after `AuthPipeline` has populated `auth_context`

**Already covered — no gap.**
`test/letflow/plugs/api_pipeline_integration_test.exs`'s REQ-071 AC2 test sends a
request through the real `Letflow.Router` -> `Letflow.Plugs.ApiPipeline` ->
`AuthPipeline` -> `TenantStatus` -> `Letflow.Routers.Identity` chain and asserts
`conn.assigns.auth_context` is populated (`tenant_id`/`roles`/`user_id`) AND that the
request reached a real `Letflow.Plugs.Authorize` decision (403, not 401/500) — which is
only possible if `AuthPipeline` ran first. `test/letflow/plugs/authorize_test.exs`'s
`describe "ordering: this plug requires auth_context already populated"` (added this
pass) complements this from the other direction: calling `Authorize.call/2` with no
`auth_context` assigned at all yields 500 before any authorization decision is made,
proving the plug cannot silently proceed if `AuthPipeline` is skipped or misordered.
