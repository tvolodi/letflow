# Test Spec: REQ-132 — Row scoping for `AllowWithRowFilter` on `GET /tasks`

**Requirement:** REQ-132 (stage S4). `Letflow.Api.Authorization` returns three decision
kinds; REQ-131 made `Allow`/`Deny403` real, but the third — `AllowWithRowFilter` — was
computed and then ignored on the task read path. This requirement applies it: for
`:TasksList` with a task-worker-only role, `evaluate_access/2` returns
`kind: :AllowWithRowFilter, task_scope: {:own_user_and_groups, ctx.user_id}` — a
groups-inclusive scope (own-assigned tasks AND tasks assigned to groups the caller
belongs to), never narrowed to `assignee_id == user_id` alone. The row scope must come
from that `task_scope` tuple only — never from a request-supplied `assignee_id` query
param, which must not be able to widen the caller's own scope. Needs SECURITY-REVIEWER
(INV-2). Full text in this run's handoff `context.requirement_text`.

**Design:** `lib/letflow/design/req132-row-scoping.md`. Its central finding (§12, Open
question 1): **the row-scoping mechanism is already fully implemented and shipped**
(landed under REQ-083/REQ-130/REQ-131) — `Letflow.Routers.Tasks.build_list_assignee_scope/3`
(`lib/letflow/routers/tasks.ex:186-204`) pattern-matches `decision.task_scope` before
ever inspecting a caller-supplied `assignee_id`, and `Letflow.Tasks.filter_by_assignee_scope/2`
(`lib/letflow/tasks.ex:613-634`) builds the groups-inclusive `WHERE`. Zero new `lib/`
code this run — confirmed independently by ELIXIR-DEV, SECURITY-REVIEWER, and REVIEWER
(all PASS). The design's own §12 Open question 2 is the actual gap this step closes:
existing coverage in `test/letflow/routers/tasks_test.exs` exercised this mechanism only
for `GET /tasks/inbox` (AC2 describe blocks, lines ~401-473) plus a **user-only**
`assignee_id`-widening test for `GET /tasks` (INV-2, lines ~690-712, no group fixture) —
none of REQ-132's five ACs, all worded around `GET /tasks` specifically, had a `GET
/tasks`-targeted test with the full four-task-shape fixture set (own / member-group /
other-user / non-member-group) the criteria describe.

**Implementation:** `lib/letflow/routers/tasks.ex` (`build_list_assignee_scope/3`,
`handle_list/3`), `lib/letflow/tasks.ex` (`filter_by_assignee_scope/2`,
`resolve_principal_scope/2`, `list_tasks/2`) — all pre-existing, unmodified by this run.

**Test tier:** integration (`Letflow.DataCase`, real Postgres, real tenant-schema
provisioning via `Letflow.TenantFixture`), dispatched directly against
`Letflow.Routers.Tasks.call/2` — same convention as the rest of this file.

**Test file:** `test/letflow/routers/tasks_test.exs` (new `describe` blocks added
alongside the existing REQ-083/REQ-085 ones, immediately after the existing INV-2
`GET /tasks` test at the original lines ~690-712).

## 1. Acceptance-criteria -> test-case mapping

### AC1 — a TASK_WORKER listing tasks receives exactly the `{:own_user_and_groups,
user_id}` scope's rows and no others, against seeded third-user/member-group/
non-member-group data

**Why this test exists:** the requirement text is explicit that the scope is
**groups-inclusive**, not `assignee_id == user_id` — a regression that silently
narrowed `filter_by_assignee_scope/2`'s `{:principal, _}` clause back to a plain
user-id-equality `WHERE` (the "intuition about what 'own rows' means" the requirement
text warns against) would still pass a test that only seeds a directly-assigned task.
Seeding all four shapes in one test — own task, member-group task, a different user's
task, and a non-member-group task — means a regression in any one of the three `WHERE`
arms (own / group-member / group-non-member exclusion) fails a specific, individually
named assertion rather than an aggregate count.

* `describe "REQ-132 AC1: GET /tasks for a TASK_WORKER-only caller returns exactly the
  {:own_user_and_groups, user_id} scope"` —
  `test/letflow/routers/tasks_test.exs` (new block, immediately following the existing
  INV-2 describe block) —
  1. `assert task_own.id in returned_ids` (directly assigned, `assignee_type: "USER"`,
     `assignee_ref == user_x`)
  2. `assert task_via_member_group.id in returned_ids` (`assignee_type: "GROUP"`,
     `assignee_ref` == a group `user_x` is a member of)
  3. `refute task_other_user.id in returned_ids` (`assignee_type: "USER"`,
     `assignee_ref` == a different user `user_y`)
  4. `refute task_via_non_member_group.id in returned_ids` (`assignee_type: "GROUP"`,
     `assignee_ref` == a group `user_x` is deliberately NOT a member of)

### AC2 — a caller supplying `?assignee_id=<different user>` does not receive that
user's rows

**Why this test exists:** this is the requirement's own named attack scenario — the
query parameter and the row filter "want to feed the same Ecto where clause." The
existing `INV-2` test (line ~690, pre-existing, unmodified) already covers this with a
user-only fixture; this new test is **meaningfully distinct**, not a duplicate, because
it adds a group-task fixture and asserts the caller's own scope (own task + group task)
is still fully intact alongside the attack's exclusion — proving the malicious
`assignee_id` neither substitutes for nor narrows the `{:own_user_and_groups, _}` scope,
only that it fails to widen it. A regression that accidentally cleared the whole result
set on any `assignee_id` presence (rather than truly ignoring it) would pass the
pre-existing INV-2 test (which never checks a positive inclusion) but fail this one.

* `describe "REQ-132 AC2: assignee_id widening attack with a group-task fixture"` —
  `test/letflow/routers/tasks_test.exs` —
  1. `refute task_y.id in returned_ids` (the attack itself: naming `user_y` via
     `?assignee_id=` must not surface `user_y`'s task)
  2. `assert task_own.id in returned_ids` (own scope intact)
  3. `assert task_via_group.id in returned_ids` (group scope intact)

### AC3 — a role whose decision is a plain allow (`task_scope: :all`) still sees the
unfiltered set

**Why this test exists:** the pre-existing coverage of `GET /tasks` with
`PLATFORM_ADMIN` (AC1/AC4 pagination and isolation tests, REQ-083) never seeded tasks
assigned to *different* users/groups than the caller — those tests' tasks are all
unassigned (`assignee_type: nil`), so they cannot distinguish "unfiltered" from "the
row filter happens to match everything because nothing is assigned to anyone else." This
test closes that specific gap: three tasks, assigned to two different users and a group
none of which is the (roleless-for-assignment) `PLATFORM_ADMIN` caller, are all still
returned — proving the row-filter mechanism engages **only** on the
`{:own_user_and_groups, _}` decision shape and never applies by default.

* `describe "REQ-132 AC3: GET /tasks for a plain-:Allow role (task_scope: :all) stays
  unfiltered"` — `test/letflow/routers/tasks_test.exs` — all three of `task_a`, `task_b`
  (different users), `task_group` (a group) are asserted present in one `PLATFORM_ADMIN`
  listing.

### AC4 — the row scope is derived from the `AccessDecision`'s `task_scope` tuple in
code, never from any request-supplied value

**Not a runnable test — verified by code reading**, per this requirement's own
`context.requirement_text` framing ("verifiable by reading the query construction") and
already performed independently by ELIXIR-DEV, SECURITY-REVIEWER, and REVIEWER (all
PASS, per this run's own dispatch notes) plus the design doc itself (§2, §5, §11
INV-2). The concrete structural evidence, re-confirmed here rather than merely cited:

* `Letflow.Routers.Tasks.build_list_assignee_scope/3`'s first clause
  (`lib/letflow/routers/tasks.ex:186-204`) matches on `decision.task_scope`, binds its
  own `assignee_id` parameter as `_assignee_id` (structurally unread — no branch inside
  the clause inspects it), and derives `user_id` from the tuple `evaluate_access/2`
  returned (itself sourced from `ctx.user_id`, never a request-observed value).
* Clause ordering means a `:AllowWithRowFilter` decision can never fall through to the
  `assignee_id`-reading clauses (clauses 2/3, only reachable when `task_scope == :all`).
* AC1/AC2's own tests above are the runnable evidence that this reading holds in
  practice, but AC4 itself — "derived from the tuple, never from any request-supplied
  value, verifiable by reading" — is satisfied by the code reading, not by a test
  assertion that could not distinguish "correct by construction" from "correct by
  coincidence of this run's fixtures."

### AC5 — REQ-072 tenant scoping still applies underneath the row filter, proven by a
test where the other user's tasks belong to another tenant

**Why this test exists:** mirrors the existing "AC2 extra assurance" cross-tenant test
for `/inbox` (line ~440, role-name collision), but targets `GET /tasks` with the
simplest possible cross-tenant proof: the **same** `user_id` has a task directly
assigned in a second tenant's schema. If tenant scoping were ever dropped from
`resolve_principal_scope/2`'s group query or from `list_tasks/2`'s own `Repo.all`
`:prefix` opt, this is the one fixture shape that would catch it even though the
row-filter's own `user_id`-matching logic would otherwise consider the tenant-B task a
legitimate match — proving the `:prefix` scoping is structurally independent of, and
applied underneath, the `{:own_user_and_groups, _}` narrowing.

* `describe "REQ-132 AC5: GET /tasks -- REQ-072 tenant scoping still applies underneath
  the row filter"` — `test/letflow/routers/tasks_test.exs` —
  1. `assert task_in_a.id in returned_ids` (tenant A's own group task)
  2. `refute task_in_b.id in returned_ids` (tenant B's task, same `user_id`, directly
     assigned — must not leak across the schema boundary)
