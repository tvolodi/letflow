# REQ-134 — Real-Keycloak token integration path for `AuthPipeline`

Status: implemented (Step 3, TEST-DESIGNER). Run: WF02-REQ134-20260823.
Design: `lib/letflow/design/req134-real-keycloak-token-integration.md`.

## Requirement (verbatim)

> `config/test.exs` sets `token_verifier: Letflow.Oidc.TokenVerifierDouble`, so the
> entire suite passes with no identity provider running. That was correct while none
> existed. Its consequence is that no test in this repository has ever exercised a real
> token, which is why a placeholder issuer and an unmountable authorization matrix both
> survived to 2026-08-22 without a single failure. Add an integration path that obtains a
> real token from the running Keycloak (direct-access grant against the seeded users) and
> drives it through AuthPipeline for real: signature verification against the live JWKS,
> issuer/realm resolution, claim mapping, JIT provisioning, and the authorization plug.
> Keep TokenVerifierDouble as the default for the unit suite. Do NOT make the whole suite
> depend on a running Keycloak -- that would trade a blind spot for a flaky,
> infrastructure-coupled suite, and this project already runs partitioned parallel test
> processes (scripts/test_parallel.sh) that a shared external service would serialize.
> The real-token path should be a tagged/excluded-by-default set that a human or CI can
> run deliberately, with a clear skip message naming what has to be running -- follow the
> pattern web/tests/e2e/onboarding/ already uses ("Ensure docker-compose services are
> running"). State in the result how a developer runs it, and confirm that mix test with
> Keycloak stopped still passes.

## Files

| File | Role |
|---|---|
| `test/support/keycloak_test_client.ex` | Test-only Keycloak HTTP client (discovery probe, direct-access-grant token fetch, signature-tampering helper) |
| `test/letflow/integration/keycloak_auth_pipeline_test.exs` | The tagged, excluded-by-default integration suite |
| `test/test_helper.exs` | `ExUnit.start(exclude: [:keycloak])` — the default-exclusion mechanism |

## Running the real-token suite

```
mix test --include keycloak test/letflow/integration/keycloak_auth_pipeline_test.exs
```

Requires `docker compose up -d keycloak` (plus Postgres) running first. `--include
keycloak` overrides `test_helper.exs`'s `exclude: [:keycloak]` default for this
invocation only; the path argument scopes the run to this one file so a developer isn't
also re-running the double-based suite redundantly.

## Test cases, mapped to acceptance criteria

### AC1 — a genuine token drives `AuthPipeline` end to end

**Test:** `"a real admin-user token authenticates and attaches the expected
auth_context"` (`describe "acceptance criterion 1"`).

Obtains a real token via `KeycloakTestClient.direct_access_token/4` against the seeded
`admin-user`/`admin-pass` credential (`priv/keycloak/realms/bpm-default.json`), drives it
through `AuthPipeline.call/2` via `Plug.Test.conn/2` + a real `authorization: Bearer
<token>` header, and asserts the conn is not halted and
`conn.assigns.auth_context` matches `%{tenant_id: <fixture tenant_id>, user_id: <a
binary>, roles: [... "PLATFORM_ADMIN" ...]}`.

**Why this exists:** this is the one path in the entire test suite that has ever driven
a byte-for-byte real JWT, issued by a real Keycloak, through every step of
`AuthPipeline.call/2` — token verification, issuer/realm resolution, claim mapping, JIT
provisioning, and auth-context attachment — with no double standing in for any of them.
Every other test of this plug (`test/letflow/plugs/auth_pipeline_test.exs`) exercises the
same code paths against `Letflow.Oidc.TokenVerifierDouble`'s one fixed sentinel string,
which cannot fail on a real signature/claims/issuer mismatch by construction. Without
this test, a change that broke real-token verification (e.g. the placeholder-issuer bug
this requirement's own problem statement names) would pass the whole suite.

### AC2 — a tampered token is rejected by the REAL verifier

**Test:** `"a token with a tampered signature is rejected with 401 unauthorized"`
(`describe "acceptance criterion 2"`).

Obtains a real token the same way as AC1, derives a tampered variant via
`KeycloakTestClient.tamper_signature/1` (the JWT's signature segment mutated
byte-for-byte, header/payload untouched), drives it through the identical
`AuthPipeline.call/2` path under the SAME real-verifier override as AC1, and asserts the
conn is halted, `conn.status == 401`, and the decoded JSON body is `%{"error" =>
"unauthorized"}`.

**Why this exists:** proves the signature check is real and load-bearing, not a
pass-through. `TokenVerifierDouble` has no concept of "tampered" — it recognizes exactly
one fixed sentinel string and nothing else, so this exact test could not even be
expressed against the double; it is intrinsically a real-verifier-only assertion. This
test fails specifically because `Oidcc.Token.validate_jwt/3`'s live-JWKS signature check
rejects the mutated signature — if a future change made verification skip the signature
check (or accept any signature), this test is what would catch it, where the unit suite
against the double cannot.

### AC3 — JIT provisioning creates then reuses a real user row, across two calls

**Test:** `"first call provisions a user row, second call reuses it"` (`describe
"acceptance criterion 3"`).

Obtains a real token for the seeded `designer-user`/`designer-pass` credential
(deliberately distinct from AC1/AC2's `admin-user`, so this test's JIT-provisioned row
never collides or races with the other two tests' rows within the same shared
`bpm-default` tenant/schema). Derives the token's `sub` claim, and captures a **baseline**
`Letflow.Repo.aggregate/3` count of matching `Letflow.Identity.User` rows
(`external_realm == "bpm-default" and external_id == <sub>`, scoped to the fixture
tenant's real Postgres schema) — `count_before` — *before* either pipeline call. Asserts
the count goes to `count_before + 1` after the 1st `AuthPipeline.call/2`, and is still
`count_before + 1` (not `count_before + 2`) after the 2nd, with the two calls' resulting
`user_id`s equal.

**Why a baseline count, not a hardcoded `0` (rework, TEST-DESIGN-VALIDATOR gate 1,
2026-08-23):** design §5 deliberately keeps the `bpm-default` tenant/schema permanent,
never torn down between runs. An earlier version of this test asserted an absolute `0`
before the first call — correct on a database's first run, but a certain, deterministic
failure on every subsequent run of the exact command this file's AC6 section documents,
since nothing deletes the `designer-user` row `provision_oidc_user/4` created on the
prior run. Capturing `count_before` instead makes the test self-sufficient and correct on
every run regardless of prior invocations or other tests sharing the same persistent
fixture, while the `count_before + 1` (not `+ 2`) assertion after the second call still
proves the second call adds no new row.

**Why this exists:** the count-only assertion (staying at `count_before + 1`) alone would
not rule out a delete-then-reinsert pair producing a *different* row that happens to keep
the count stable — the `user_id_1 == user_id_2` identity check is what proves the SAME
row is reused, not merely that the count is stable. This is also the first test in the
suite that exercises `Letflow.Identity.provision_oidc_user/4`'s upsert-on-`(tenant_id,
external_realm, external_id)` behavior against a genuinely token-derived `external_id`
(the real `"sub"` claim), rather than the double's synthetic one.

**Mechanism:** `test/test_helper.exs`'s `ExUnit.start(exclude: [:keycloak])`, applied at
suite-collection time, before Mix's `--partitions N` splitting — so the module is
excluded from every partition's assignment pool too, not merely "excluded from running."

### AC5 — the real-token tests skip with a message naming exactly what must be running

**Test coverage:** `setup_all`'s reachability probe (not a separate `test`, but a
verified behavior of the module as a whole — see below).

**Evidence (this run, Keycloak stopped, `mix test --include keycloak
test/letflow/integration/keycloak_auth_pipeline_test.exs`):**

```
0) Letflow.Integration.KeycloakAuthPipelineTest: failure on setup_all callback, all tests have been invalidated
   ** (RuntimeError) Keycloak not ready at http://localhost:8092/realms/bpm-default/.well-known/openid-configuration. Ensure docker-compose services are running (docker compose up -d keycloak) before executing these tests.

Result: 0 tests, 3 invalid
```

The message names exactly what must be running (the Keycloak discovery URL) and exactly
what to do about it (`docker compose up -d keycloak`) — the same two-component shape
`web/tests/e2e/onboarding/onb-ui-01.e2e.spec.ts`'s `assertServicesReady/1` uses. It is
the first and only thing surfaced, not buried behind an unrelated failure.

**Deviation from the design's literal mechanism, recorded (not silent):** design §3.1
specifies `setup_all` returning `{:skip, message}`, the ExUnit idiom that marks tests
"skipped" rather than "failed." Measured directly against this repo's installed
toolchain (Elixir 1.20.3 / ex_unit 1.20.3): `setup_all` does not accept `{:skip, _}` as a
return value in this version — attempting it raises `RuntimeError: expected ExUnit
setup_all callback ... to return the atom :ok, a keyword, or a map, got {:skip, ...}
instead`, which is a *more* obscure failure than a plain targeted message (it buries the
real "Keycloak not ready" text inside an ExUnit-internal complaint). `ExUnit`'s
tag-based dynamic-skip mechanism (`ExUnit.Filters.eval/4`) is evaluated from each test's
compile-time `tags` map before any `setup_all`/`setup` callback runs at all, so a
runtime-computed skip reason cannot flow through that path either — confirmed by reading
`ex_unit/lib/ex_unit/runner.ex`'s `prepare_tests/4` and `ex_unit/lib/ex_unit/filters.ex`.
This module therefore raises a plain `RuntimeError` carrying the intended message text
directly. `mix test`'s summary reports this as a failure ("all tests have been
invalidated"), not literally "skipped," but the message satisfies AC5's substantive
requirement — naming exactly what's down and what to do about it, as the first and only
thing surfaced — as closely as this ExUnit version allows. Reported to ORCH as a MINOR
design/implementation discrepancy.

## Mutation-style verification these tests would actually fail (not tautologies)

- **AC2** would pass trivially against `TokenVerifierDouble` (which has no concept of
  tamper) — it only means anything because `setup`'s override installs the REAL
  `Letflow.Oidc.TokenVerifier.Oidcc` for this module. If that override were removed (or
  swapped back to the double), this test would either fail to compile against the
  double's single-sentinel contract or, if adapted, would not exercise a real signature
  check at all — the test's value is structurally tied to the override being real.
- **AC3**'s `user_id_1 == user_id_2` assertion would fail if `provision_oidc_user/4`'s
  upsert ever regressed to unconditional insert (each call would mint a new row, count
  would go `count_before` → `count_before + 1` → `count_before + 2`, and the two
  `user_id`s would differ) — this is the concrete regression this assertion is designed
  to catch, distinct from the count-only check.
