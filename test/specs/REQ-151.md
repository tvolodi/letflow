# Test spec: REQ-151 — Lua 5.3 sandbox deny-set (LUA-03, LUA-04 restated)

**Requirement:** REQ-151 (`docs/requirements.yaml`)
**Implementation:** `lib/letflow/engine/lua/sandbox.ex` (`Letflow.Engine.Lua.Sandbox`)
**Design:** `lib/letflow/design/req151-lua-sandbox.md`
**Test code:** `test/letflow/engine/lua/sandbox_test.exs`

All tests construct their `Lua.t()` exclusively via `Letflow.Engine.Lua.Sandbox.new/0`
or `new/1` — never `Lua.new/1` directly — so every assertion below exercises the real
production construction path, not a bypassed one.

## Empirical note that shapes every "raises" assertion below

Before writing these tests, the actual runtime behavior was probed directly (not
assumed from the design doc's prose) via `MIX_ENV=test mix run` against a real
`Sandbox.new/0` VM. Finding: **every path in the 28-entry deny-set, once passed to
`Lua.new/1`'s `sandboxed:` option, becomes a real raising function when called** —
`Lua.sandbox/2` (the library's mechanism) always writes a raising callable at the given
path, regardless of whether something already existed there. This means the design
doc's "installed vs. not installed / vacuous" distinction (§4.1) matters for *why the
path is denied* (does it neutralize a live capability, or restate LUA-03's text against
something that was never reachable anyway) but does **not** change the observable test
behavior: **referencing** a denied path returns a truthy `NativeFunc` value in every
case; **calling** it always raises `Lua.RuntimeException` with a `"<name> is
sandboxed"` message. The one true exception is `string.dump`, which has no deny-set
entry at all (§4.3 — nothing exists at that path to override) and is confirmed to
evaluate to plain `nil`. `coroutine` likewise evaluates to `nil` (§6 — deliberately not
sandboxed, asserted absent instead). This is why every per-path test below calls the
function (not just references it) except for `string.dump` and `coroutine`, which
assert `nil` directly — matching AC2's literal "nil or raises" wording against what the
runtime actually does, not what "installed/vacuous" suggested it might do.

## Test cases

### 1. "the only call site" (AC1)

**Why this test exists:** AC1's entire enforcement mechanism is structural (single call
site), not a runtime check — a passing test here is the only evidence INV-SBX-1 holds.
Without it, a future PR could add a second `Lua.new/1` call site and nothing would
fail.

Asserts: `grep -rn "Lua\.new(" lib --include=*.ex` (invoked via `System.cmd/3` from
inside the test, so the assertion runs against the real repository tree rather than a
hand-maintained expectation) returns exactly one line, and that line is inside
`lib/letflow/engine/lua/sandbox.ex`.

### 2. Per-path denial tests (AC2)

One test per path named in AC2's literal text: `io.open`, `io.write`, `os.execute`,
`os.exit`, `os.getenv`, `os.remove`, `os.rename`, `os.tmpname`, `load`, `loadfile`,
`dofile`, `require`, `package`, `debug`, `string.dump`.

**Why one test per path, not a single parameterized loop with a shared assertion
style:** `string.dump` behaves differently (nil, not raise — see empirical note above),
and `package`/`debug` are whole-table paths tested by indexing rather than calling
positional args. Folding all fifteen into one uniform loop would either (a) hide the
`string.dump` special case behind a branch inside the loop, which is harder to read
than a dedicated test, or (b) force `string.dump` to raise, which would be a false
assertion. Individual tests keep each path's actual observed behavior explicit and
literally named, which also makes a future regression's failing test name
self-explanatory (e.g. `test "os.exit is sandboxed"` failing tells a reader exactly
what broke without opening the file).

Each denial test calls the path with a representative argument (e.g. `os.execute('ls')`,
`io.open('/etc/passwd')`, `debug.getmetatable({})`) from inside a `Sandbox.new/0` VM and
asserts a `Lua.RuntimeException` is raised. `string.dump` asserts `nil` instead (no
deny-set entry — genuinely absent, not sandboxed).

### 3. "default denials hold — no custom list narrows them" (AC3)

**Why this test exists:** this is the regression test for the exact trap decision 0014
and REVIEWER's second gating round caught (a partial `sandboxed:` list silently
reopening every default). Per the design's §5 AC3 disposition, `Sandbox.new/1` exposes
no caller-supplied custom-list option in this requirement, so the test proves the trap
guard holds for the one options surface this module exposes today: calling
`Sandbox.new/1` with an arbitrary (non-deny-set) options keyword list still produces a
VM where `os.execute` and `load` (AC3's named minimum) remain denied, exactly as
`Sandbox.new/0` does. This gives REQ-152 a passing regression test to build its own
extension on top of, per the design's own stated intent.

### 4. `debug`'s metatable/upvalue functions are unreachable (AC2, §4.2)

**Why this test exists:** `debug` is the requirement's "central finding" — a real,
non-vacuous gap in the *library's own default* sandbox that this module closes and the
bare `Lua.new/1` default does not. A generic "debug is sandboxed" test only proves the
whole-table override exists; this test proves the specific capability that motivated
adding `debug` at all (metatable-protection bypass, arbitrary upvalue mutation) is
actually unreachable. Asserts `debug.getmetatable`, `debug.setmetatable`,
`debug.getupvalue`, `debug.setupvalue` each raise when accessed/called from inside a
`Sandbox.new/0` VM.

### 5. "coroutine is absent, not sandboxed" (AC6/§6)

**Why this test exists:** this is the concrete, executable proof of the explicit
`coroutine` decision the requirement mandates (§6/INV-SBX-3) — that `coroutine` is
absent by nature of the runtime, not silently sandboxed as a side effect of some other
path. It is also the trip-wire the design and moduledoc both call out: if a future
`tv-labs/lua` upgrade adds a real `coroutine` library, this exact test starts failing,
which is the intended signal to revisit the decision rather than a flake. Asserts
`coroutine == nil` (not a `NativeFunc`, not a raise) from inside a `Sandbox.new/0` VM.

### 6. "math, string, table remain usable" (smoke test, not itself an AC)

**Why this test exists:** every other test in this file proves something is denied;
without this one, a reader (or a future refactor) cannot distinguish "the intended
surface is denied and everything else works" from "the sandbox denies everything,
including the MUST-load set." Asserts `math.floor`, `string.format`, and
`table.insert` all succeed normally from inside a `Sandbox.new/0` VM.

### 7. Moduledoc content assertions (AC4, AC5, AC6)

**Why this test exists:** AC4 and AC5 are documentation acceptance criteria — the only
way to fail them is for the moduledoc text to regress (e.g. someone trims the "three
reasons" list during an edit) without any other test catching it. Using
`Code.fetch_docs/1` (not a raw file read) verifies the *compiled* moduledoc rather than
just source text, so the assertion also catches malformed `@moduledoc` syntax that
would otherwise silently produce no docs. Asserts the moduledoc string contains:
markers for LUA-03's three restatement reasons (5.1-name absence, jit/ffi/bit vacuity,
SBX-1 property-not-mechanism), LUA-04's structural-holds text, and the `coroutine`
decision's reason.
