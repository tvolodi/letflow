## What this requirement delivers

REQ-153 provides a concrete `Letflow.Engine.Lua.Executor` module that implements
`@behaviour Letflow.Engine.LuaScriptAudit.Executor` using tv-labs/lua (adopted in REQ-148).
It also resolves `script_ref`'s previously-opaque `term()` type to a concrete binary
(the Lua source text itself), and proves LUA-02's per-invocation isolation invariant.

## Acceptance criteria and test mapping

### AC1 — Module exists and implements the Executor behaviour

**Criterion:** A module implementing `@behaviour Letflow.Engine.LuaScriptAudit.Executor`
exists under `lib/`.

**Why:** If the behaviour is not declared, Elixir will not enforce callback completeness and
the module could silently drift from the contract REQ-058 defined.

**Tests:**
- `describe "behaviour implementation (AC1)"` → `test "Executor implements the Letflow.Engine.LuaScriptAudit.Executor behaviour"` — reads `module_info(:attributes)` and checks `:behaviour` is listed.
- `test "execute_with_manifest/2 is exported"` — confirms the callback is actually exported.

### AC2 — `lib/letflow/engine/lua_script_audit.ex` is unmodified

**Criterion:** The seam module REQ-058 built must not be changed by REQ-153. Decision 0014 (d)

**Tests:**

### AC3 — Global isolation: absence asserted through the executor (LUA-02)

**Criterion:** A global set in execution 1 must be absent in execution 2 through the same
executor module.

**Why this matters for test design:** `execute_with_manifest/2` discards the Lua return
value (it only returns `{:ok, %{manifest_hash: ...}}`). Asserting `{:ok, _}` on
`"return MY_GLOBAL"` would be vacuous — both `nil` and `42` would yield `{:ok, _}`, so
the test would pass even if state leaked.

**Correct approach:** Use Lua's `error()` to signal leakage. If `MY_GLOBAL` is present and
non-nil, the script calls `error(...)`, which becomes a `Lua.RuntimeException`, which the
executor catches and returns as `{:error, _}`. Asserting `{:ok, _}` therefore proves
absence: the test would fail if leakage occurred.

**Tests:**
- `describe "global isolation (AC3)"` → `test "a global written in execution 1 is absent in execution 2"` — sets `MY_GLOBAL = 42` in exec 1, then in exec 2 asserts `{:ok, _}` on a script that `error()`s if `MY_GLOBAL ~= nil`.

---

### AC4 — Distinct state: no reset-and-reuse path

**Criterion:** Each invocation obtains a fresh, distinct Lua state; no state is reset or
reused between calls.

**Why:** A reset-and-reuse implementation (e.g., clearing globals on a cached state) might
pass a simple global-absence check but still share underlying VM state in subtle ways.
The correct proof is through the executor itself.

**Tests:**
- `describe "distinct state (AC4)"` → `test "a table mutated in execution 1 is pristine in execution 2"` — mutates `T` in exec 1 through the executor, then in exec 2 asserts `{:ok, _}` on a script that `error()`s if `T ~= nil`. Proves table state does not bleed across invocations through the executor, not just at the `Sandbox.new()` level.

### AC5 — INV-LSA-1 via real executor: invalid `instance_id` → `{:error, :invalid_instance_id}`

**Criterion:** `LuaScriptAudit.execute_script_for_audit/6` with the real `Executor` module
(not a test double) must short-circuit with `{:error, :invalid_instance_id}` for invalid
instance IDs, writing zero executor calls and zero audit rows.

**Why:** This verifies the ordering guarantee in `lua_script_audit.ex`: the executor is
never invoked for an invalid instance. Using the real executor (not a double) confirms the
real wiring, not just the test-double wiring from REQ-058.

**Tests:**
- `describe "INV-LSA-1 with real executor (AC5)"`:
  - `test "nil instance_id short-circuits..."` — passes `nil` as instance_id.
  - `test "malformed instance_id short-circuits..."` — passes a non-UUID string.

### AC6 — INV-LSA-2 via real executor: manifest hash mismatch

**Criterion:** When the executor's reported `manifest_hash` differs from `registered_hash`,
`execute_script_for_audit/6` returns `{:error, {:manifest_hash_mismatch, registered, actual}}`
and writes no audit row.

**Why:** This verifies the hash-check invariant with a real executor computing a real
SHA-256. Using a test double could mask a wiring failure between the executor's reported
hash and `lua_script_audit.ex`'s comparison.

**Tests:**
- `describe "INV-LSA-2 with real executor (AC6)"` → `test "a registered_hash that does not match..."` — computes the real SHA-256 of a script, then passes a deliberately wrong hash, and asserts the mismatch error shape.

**Criterion:** The executor module's moduledoc must document that `script_ref` is a binary

## Test changes made by TEST-DESIGNER

**AC3 and AC4 were inadequate in the original test file.** Both tests asserted `{:ok, _}`
on scripts that return a value, but `execute_with_manifest/2` discards Lua return values.
A broken implementation (leaking state) would have also returned `{:ok, _}`, making the
assertions vacuous.

**Fix applied:** Both tests now use Lua's `error()` function to signal leakage. The
executor catches `Lua.RuntimeException` and returns `{:error, _}`, so `{:ok, _}` is only
possible when the state is actually absent. This is the canonical way to assert absence
of side-effects when the Lua return value is not propagated by the executor API.
