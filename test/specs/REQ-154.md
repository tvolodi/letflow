## Acceptance Criteria Coverage

### AC-1 — Budget is configurable; smaller budget halts a loop sooner than larger

**Test:**
```
describe "instruction budget (REQ-154)"
  test "AC-1: smaller budget halts sooner than larger budget on the same loop"
```

**Location:** `test/letflow/engine/lua/executor_test.exs`, `describe "instruction budget (REQ-154)"`

**What it tests:**

Runs `"for i = 1, 5000 do end"` (a loop guaranteed to exceed 500 instructions but
complete within 50 000) twice via the 3-arity `execute_with_manifest/3` overload, once
with `max_instructions: 500` and once with `max_instructions: 50_000`.

- With 500: asserts `{:error, {:budget_exceeded, 500}}` — the loop is cut short.
- With 50 000: asserts `{:ok, %{manifest_hash: _}}` — the loop completes normally.

**Why this proves AC-1:** The budget is passed in as a call-site argument; neither value
is a hardcoded literal in `executor.ex`. The test drives two different numeric values and
observes different outcomes, proving the budget is configurable. The 500-instruction
threshold is much smaller than 5000 loop iterations, so the difference in outcome is not
accidental.

### AC-2 — Unbounded `while true do end` terminates under a configured budget

**Test:**
```
describe "instruction budget (REQ-154)"
  test "AC-2: while true do end terminates with budget_exceeded rather than hanging"
```

**Location:** `test/letflow/engine/lua/executor_test.exs`, `describe "instruction budget (REQ-154)"`

**What it tests:**

Runs `"while true do end"` with `max_instructions: 1000` and asserts:

```elixir
assert {:error, {:budget_exceeded, 1000}} =
         Executor.execute_with_manifest("while true do end", "h", max_instructions: 1000)
```

**Why this proves AC-2:** An unbounded loop never exits on its own. If the budget
mechanism did not work, the test process would hang until the test suite timeout killed
it. The assertion completing successfully (ExUnit imposes a per-test timeout) proves the
VM interrupted the loop. The specific `max_instructions: 1000` argument also exercises
AC-1's configurability on a degenerate input.

### AC-3 — Budget exhaustion is a structured, pattern-matchable error

**Test:**
```
describe "instruction budget (REQ-154)"
  test "AC-3: budget_exceeded is a structured error, not a bare string or atom"
```

**Location:** `test/letflow/engine/lua/executor_test.exs`, `describe "instruction budget (REQ-154)"`

**What it tests:**

Captures the result of running `"while true do end"` under a 500-instruction budget and
asserts:

```elixir
assert {:error, {:budget_exceeded, _limit}} = result
```

**Why this proves AC-3:** The pattern `{:error, {:budget_exceeded, _limit}}` is distinct
from every other error arm the function produces:

| Other arms | Pattern |
|---|---|
| Lua runtime error (non-budget) | `{:error, msg}` where `msg :: String.t()` |
| Compiler error | `{:error, msg}` where `msg :: String.t()` |
| Non-binary script ref | `{:error, :invalid_script_ref}` |

A test matching `{:error, _}` would pass for all four; this test cannot. The `_limit`
sub-binding also confirms the limit is carried in the tuple (required for caller
diagnostics).

### AC-4 — `pcall`-caught budget exhaustion returns `{:ok, %{manifest_hash: _}}`

**Test:**
```
describe "instruction budget (REQ-154)"
  test "AC-4: pcall-caught budget exhaustion returns {:ok, _} -- layer-1 pcall-catchable"
```

**Location:** `test/letflow/engine/lua/executor_test.exs`, `describe "instruction budget (REQ-154)"`

**What it tests:**

Runs the following script with `max_instructions: 1000`:

```lua
local ok, err = pcall(function() while true do end end)
return ok, tostring(err)
```

and asserts:

```elixir
assert {:ok, %{manifest_hash: _}} =
         Executor.execute_with_manifest(script, "h", max_instructions: 1000)
```

**Why this asserts `{:ok, %{manifest_hash: _}}` — the REQ-148 spike OQ-2(a) answer:**

REQ-148 spike question OQ-2(a) asked: "what happens when a Lua script calls `pcall` over
its own budget-exhausting inner loop?" The spike answer confirmed:

> `pcall` returns `[false, "instruction budget exceeded"]`, the inner loop stops, and
> `Lua.eval!/2` returns normally. There is no continuation hazard (the Elixir-level host
> sees a normal return). However, the script does receive control back after pcall.

`Lua.eval!/2` returning normally means the `execute_with_manifest` `try` block does NOT
enter any `rescue` arm. The hash is computed and `{:ok, %{manifest_hash: …}}` is
returned.

This is **documented layer-1 behavior**: `:max_instructions` is in-band and
pcall-catchable. A hostile script can wrap its loop in `pcall` and survive the budget.
Layer 2 (REQ-155) plugs this gap with a host-enforced, non-catchable `Process.exit/2`
kill. This test therefore **asserts the limitation explicitly** rather than treating it
as a bug, and is the correct test per AC-4's wording ("assert what a script that pcalls
its own budget exhaustion does, matching REQ-148's spike answer (a)").

### AC-6 — `@moduledoc` states INV-2 and INV-4 do not port, and why

**Verification method:** Source-text check on `executor.ex`.

**Location:** `lib/letflow/engine/lua/executor.ex` `@moduledoc`, section "What R-Co had, and why it does not port"

**What the moduledoc must state (verified by reading `executor.ex`):**

1. **INV-2 non-port reason** — present: *"INV-2 does not port because the threat it
   guarded against does not exist in this runtime."* Explanation: `:max_instructions` is
   wired into `Lua.new/1` at construction time and not reachable from Lua globals, so
   the `_G.__limiter__ = nil` bypass that INV-2 defended against is impossible.

2. **INV-4 non-port reason** — present: *"INV-4 does not port because this runtime has
   no hook API and needs none."* Explanation: `tv-labs/lua` enforces `:max_instructions`
   via its own internal VM counter; the tight-loop interruption that `LUA_MASKCOUNT`
   solved is REQ-155's problem, addressed by preemptive BEAM scheduling.

No new test is needed; the moduledoc text is the artifact and is already present.

## Notes on Mutation / Pre-Fix Failure

AC-1 through AC-4 are new tests for new code (ELIXIR-DEV implemented `execute_with_manifest/3`
as part of this requirement). The "pre-fix failure is that the code did not exist" rule
therefore applies per `docs/agents/workflows/WF-03_issue_resolving.md`.

However, this is **WF-02** (requirement implementation), not WF-03 (regression). The
WF-02 obligation is that the new tests exercise real application logic. The tests are
behaviorally verified: AC-2 in particular would hang forever (failing via ExUnit
timeout) if the VM integration were broken. The structured-error tests (AC-1, AC-3) would
fail against a naive `{:error, "budget exceeded"}` string return. The pcall test (AC-4)
would fail if a `rescue` arm incorrectly caught the normal return from `Lua.eval!/2`.
