# REQ-155 Test Spec: Out-of-Band Host-Enforced Wall-Clock Kill (LUA-10, Layer 2)

This spec reflects the tests actually shipped in
`test/letflow/engine/lua/executor_test.exs`, under the `describe "wall-clock timeout
(REQ-155)"` block (T1–T8 below, plus the moduledoc-content tests for AC-5/6/7). See
`lib/letflow/design/req155-lua-wallclock-kill.md` for the design these tests exercise —
in particular §4 (supervised-task mechanism), §5 (error shape), §6 (blindness to
in-band state), and §9 (original acceptance criterion mapping).

All tests target `Letflow.Engine.Lua.Executor.execute_with_manifest/3`, using the
3-arity overload so each test can set its own `:max_instructions` and `:timeout_ms`
independent of Application config. `config/test.exs` sets a short default
`:lua_wallclock_timeout_ms` for any incidental `/2`-arity use, but no REQ-155 test
below relies on it.

**Deviation from the original T2 design (documented here per WF-02 Step 3):** this
spec originally proposed a T2 script that (a) sets a small `:max_instructions` budget,
(b) `pcall`s a first unbounded loop so the in-band budget error is caught, then (c)
re-enters a *second* unbounded `while`/`for` loop rather than returning. That script
does not actually exercise layer-2 necessity against the `tv-labs/lua` runtime shipped
in this repo: ELIXIR-DEV verified empirically (scratch probes against
`Letflow.Engine.Lua.Sandbox`/`Lua.eval!` directly, and confirmed independently by
SECURITY-REVIEWER and REVIEWER reading the vendored runtime source) that this
runtime's `:max_instructions` counter is permanently exhausted once tripped — any
further `while`/`for` iteration re-raises `{:budget_exceeded, _}` almost immediately,
which layer 1 alone already terminates. That version of the test would pass or fail
identically whether layer 2 (the outer wall-clock kill) were present or removed, so it
would not be the two-layer proof decision 0014 requires. The shipped T2 substitutes a
`goto`-based loop (`::top:: goto top`) after the `pcall`, which this runtime's
instruction-budget check does not instrument at all (confirmed empirically: it hangs
indefinitely with no `:max_instructions` error). This is a real, host-relevant escape
hatch — it demonstrates LUA-10's own point that a hostile or buggy script can always
find an in-band construct the counter does not cover, and only a host-external,
non-cooperative kill can bound it. The rest of the design (mechanism, error shape,
supervisor, moduledoc content) is unaffected by this substitution.

## T1 — Timeout is configurable and observably different at two values

**Maps to:** AC-1

**Test:** `"AC-1: a shorter configured timeout terminates measurably sooner than a longer one"`

Runs the same wall-clock-hanging script (`while true do end`, no `pcall`, no budget
dependency — isolates the timeout parameter alone) twice: once with `timeout_ms: 100`
and once with `timeout_ms: 600`, both with a very large `:max_instructions` so the
in-band budget layer plays no role. Asserts the short call returns
`{:error, {:wallclock_timeout, 100}}` and the long call returns
`{:error, {:wallclock_timeout, 600}}` — proving the returned value tracks the
`:timeout_ms` opt, not a hardcoded constant. Additionally asserts, via `:timer.tc/1`,
that the short call's measured wall-clock elapsed time stays well under 400ms (a
4x margin over the configured 100ms, chosen to absorb CI scheduling jitter without
weakening the assertion) and that the long call's elapsed time exceeds the short
call's — establishing that elapsed wall-clock time, not just the returned tuple, also
tracks the configured value.

**Why this test exists:** AC-1 requires proof that the timeout is a real configured
parameter rather than a constant baked into the implementation; asserting on two
different configured values in the same run (rather than trusting a single hardcoded
default) is the only way to rule out a hidden constant.

## T2 — Wall-clock timeout still fires when the script has trapped its own instruction-budget exhaustion and continues looping via a construct the budget counter does not instrument

**Maps to:** AC-2. This is decision 0014's required two-layer test; it must fail if
layer 2 is removed or bypassed.

**Test:** `"AC-2: wall-clock timeout still fires when the script traps its own budget error and loops again via a construct the instruction budget does not instrument"`

Runs:

```lua
local ok, err = pcall(function() while true do end end)
-- budget error caught and ignored here; script deliberately keeps running
-- instead of returning, via a construct :max_instructions does not check.
::top::
goto top
```

with `max_instructions: 200, timeout_ms: 300`. Asserts the call returns
`{:error, {:wallclock_timeout, 300}}` — not `{:ok, _}}`, not
`{:error, {:budget_exceeded, _}}` — proving the outer host-enforced kill is what ends
the call, independent of what the script did with its own in-band error (it caught
and ignored the budget error via `pcall`) and independent of the fact that
`:max_instructions` never fires again for the `goto` loop at all.

**Why this test exists:** it is decision 0014's specific two-layer proof. Without a
script that both (a) demonstrably observes and discards its own budget error and (b)
continues running via a path invisible to `:max_instructions`, a test could pass
against layer 1 alone and never actually exercise layer 2. The `goto` construct is
what makes (b) true against this runtime — see the deviation note above.

## T3 — The script's execution process is actually terminated, not merely abandoned

**Maps to:** AC-3

**Test:** `"AC-3: the task's process is dead and no longer tracked by the supervisor after a timeout"`

Snapshots `Task.Supervisor.children(Letflow.Engine.Lua.TaskSupervisor)` before issuing
a call that hangs on `while true do end` with `timeout_ms: 150`, asserts the call
returns `{:error, {:wallclock_timeout, 150}}`, sleeps 50ms to allow the already
brutally-killed task's `:DOWN` bookkeeping to settle inside the supervisor, then
asserts the post-call children set is identical (as a sorted list) to the pre-call
snapshot. `Letflow.Engine.Lua.TaskSupervisor` is used only by this executor and only
within this test file (confirmed: no other test file references it), so this
before/after comparison is not exposed to interference from unrelated concurrent
`async: true` test modules, and tests within one `ExUnit.Case` module run one at a
time by default, so it is not exposed to interference from other tests in this same
file either.

**Why this test exists:** proves the kill is real — that the calling process did not
merely give up waiting while the Lua evaluation quietly kept running in the
background as an orphaned process.

## T4 — Wall-clock timeout error is a distinct, pattern-matchable shape

**Maps to:** AC-4 (timeout arm)

**Test:** `"AC-4: wallclock_timeout does not match budget_exceeded, a bare string, or invalid_script_ref"`

Runs a script that never finishes within `timeout_ms: 100` (no budget dependency).
Asserts the return matches `{:error, {:wallclock_timeout, 100}}` specifically, and
`refute`s three specific negative matches: `{:error, {:budget_exceeded, _}}}`,
`{:error, msg} when is_binary(msg)`, and `{:error, :invalid_script_ref}`.

## T5 — Instruction-budget error remains its own distinct shape (regression guard)

**Maps to:** AC-4 (budget arm, distinguishing companion to T4)

**Test:** `"AC-4 regression guard: budget_exceeded is unaffected by a generous timeout and stays distinct"`

Runs `while true do end` with `max_instructions: 500, timeout_ms: 5_000` (a timeout
generous enough that the wall-clock mechanism plays no role in the outcome). Asserts
the return matches `{:error, {:budget_exceeded, 500}}` specifically, and `refute`s the
same three shapes as T4 in reverse (this result does not match `{:wallclock_timeout,
_}}`, a bare string, or `:invalid_script_ref`).

**Why T4 and T5 exist as a pair:** each alone would only prove its own arm exists;
together they prove a future change cannot accidentally merge the two tagged-tuple
shapes into one (e.g. by reusing one atom for both) without a test noticing on both
sides.

## T6 — Execution runs under the named supervisor

**Maps to:** AC-5

**Tests:** `"AC-5: the running script is a child of Letflow.Engine.Lua.TaskSupervisor while in flight"` and `"AC-5: moduledoc names Letflow.Engine.Lua.TaskSupervisor and justifies not reusing PluginTaskSupervisor"`

The first test starts a hanging call (`timeout_ms: 300`) via `Task.async/1` from the
test process, waits for a `:started` signal plus a 50ms settle window, then asserts
`Task.Supervisor.children(Letflow.Engine.Lua.TaskSupervisor) != []` — proving the
script genuinely runs as a supervised child while in flight, not merely that the
supervisor is registered. It then awaits the in-flight call's own timeout so the test
does not leak a process. The second test is a documentation-content check: it asserts
the moduledoc mentions both `Letflow.Engine.Lua.TaskSupervisor` (the supervisor used)
and `Letflow.Engine.PluginTaskSupervisor` (the one it is not reusing), which is the
mechanical proxy for "the moduledoc names the supervisor and justifies not reusing
the other one."

## T7 — Moduledoc restates LUA-10 as layer 2 and the non-interchangeability rationale

**Maps to:** AC-6

**Test:** `"AC-6: moduledoc restates LUA-10 as layer 2 of the LUA-08/LUA-10 pair"`

A documentation-content test asserting the moduledoc contains all of: `"LUA-10"`,
`"layer 2"`, `"enforced by the host"`, `"cooperate"`, and — closing a gap found during
Step 3 review, where the first four substrings alone could pass even if the moduledoc
never stated the "neither is met without both" clause — the literal substring
`"Neither LUA-08 nor LUA-10 is met"` (matching the moduledoc's actual sentence: "...
pair**. Neither LUA-08 nor LUA-10 is met until both layers have landed together —").

## T8 — Moduledoc carries forward the BEAM-node-kill / `System.halt/0` limitation

**Maps to:** AC-7

**Test:** `"AC-7: moduledoc discloses the BEAM-node-kill / System.halt/0 limitation"`

A documentation-content check asserting the moduledoc contains `"System.halt/0"` and
`"BEAM node"` — closing a gap found during Step 3 review, where the original
assertion (`moduledoc =~ "NOT"`) could pass on any unrelated negation anywhere in the
moduledoc and never actually verify it attached to the BEAM-node-kill disclosure — and
additionally the exact substring `"does **NOT** cover a hard kill of the BEAM node"`,
matching the moduledoc's actual sentence, tying the negation directly to its subject.
