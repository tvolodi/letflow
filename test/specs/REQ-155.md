# REQ-155 Test Spec: Out-of-Band Host-Enforced Wall-Clock Kill (LUA-10, Layer 2)

Prose test-spec skeleton only. No test code. See
`lib/letflow/design/req155-lua-wallclock-kill.md` for the design these tests exercise —
in particular §4 (supervised-task mechanism), §5 (error shape), §6 (blindness to
in-band state), and §9 (acceptance criterion mapping, T1–T8 below correspond to that
table's rows).

All tests target `Letflow.Engine.Lua.Executor.execute_with_manifest/3`, using the
3-arity overload so each test can set its own `:max_instructions` and `:timeout_ms`
independent of Application config.

---

## T1 — Timeout is configurable and observably different at two values

**Maps to:** AC-1

Runs the same wall-clock-hanging script twice in the same test run: once with a short
configured `:timeout_ms` and once with a materially longer one, both against a script
whose Lua source is an unconditional infinite loop (no `pcall`, no budget dependency —
isolates the timeout parameter alone). Asserts the short-timeout call returns
`{:error, {:wallclock_timeout, short_value}}` and does so in wall-clock time consistent
with the short value (bounded above by some reasonable margin over `short_value`, not
by the long value). Asserts the long-timeout call, given a large enough `:max_instructions`
budget instead so its own script terminates in-band before the long timeout ever
matters, is used as the comparison point, or alternatively both calls use the same
infinite-loop script and the test asserts the short call's wall-clock duration is
strictly less than the long call's configured timeout — establishing that the returned
`timeout_ms` value in the error and the actual elapsed wall-clock time both track the
`:timeout_ms` opt supplied at the call site, not a hardcoded constant.

## T2 — Wall-clock timeout still fires when the script has trapped its own instruction-budget exhaustion and continues looping

**Maps to:** AC-2. This is decision 0014's required two-layer test; it must fail if
layer 2 is removed or bypassed.

Runs a script whose Lua source: (a) sets a small `:max_instructions` budget via the
call's opts; (b) wraps a first unbounded loop in the Lua equivalent of a protected call
so the in-band budget-exceeded error is caught rather than propagated; (c) upon
catching it, enters a second unbounded loop rather than returning. Configures a
`:timeout_ms` that is comfortably longer than the time the first loop takes to exhaust
its budget, but still short enough for the test to run quickly. Asserts the call
returns `{:error, {:wallclock_timeout, timeout_ms}}` — not `{:ok, _}`, not
`{:error, {:budget_exceeded, _}}` — proving the outer host-enforced kill is what ends
the call, independent of what the script did with its own in-band error. A variant of
this test with REQ-154's layer alone (i.e. calling the pre-REQ-155 code path, or
asserting on a mock that never wraps the evaluation in a supervised task) should be
described as the negative control this test is designed to catch, even though only the
positive (post-REQ-155) assertion is runnable against the shipped code.

## T3 — The script's execution process is actually terminated, not merely abandoned

**Maps to:** AC-3

After a call that produces `{:error, {:wallclock_timeout, _}}` (using the same kind of
unconditionally-looping script as T1/T2), asserts that the supervised task's process is
no longer running. Per the design's §9 OQ-2, the primary mechanism is querying
`Task.Supervisor.children/1` on `Letflow.Engine.Lua.TaskSupervisor` and asserting no
child remains that corresponds to the just-timed-out call (allowing for the possibility
that other, unrelated concurrent calls in the same test run may have their own
children — the assertion must be scoped to the specific task under test, not merely
"the supervisor has zero children"). If the implementation exposes the task's pid by
some test-observable means (see design OQ-2), an equivalent `Process.alive?/1` check on
that pid returning `false` after the call returns satisfies the same intent. Either way,
this test's purpose is to prove the kill is real — the calling process did not simply
give up waiting while the Lua evaluation quietly kept running in the background.

## T4 — Wall-clock timeout error is a distinct, pattern-matchable shape

**Maps to:** AC-4 (timeout arm)

Runs a script that never finishes within a short configured `:timeout_ms` (no budget
dependency). Asserts the return matches `{:error, {:wallclock_timeout, timeout_ms}}`
specifically — a match against `{:error, {:wallclock_timeout, _}}` succeeds, a match
against `{:error, {:budget_exceeded, _}}` does not, a match against a bare
`{:error, _ :: String.t()}` (checked via `is_binary/1` on the second element) does not,
and a match against `{:error, :invalid_script_ref}` does not.

## T5 — Instruction-budget error remains its own distinct shape (regression guard)

**Maps to:** AC-4 (budget arm, distinguishing companion to T4)

Runs a script that exhausts a small configured `:max_instructions` budget without
trapping the error itself, using a `:timeout_ms` generous enough that the timeout
mechanism plays no role in this call. Asserts the return matches
`{:error, {:budget_exceeded, limit}}` specifically, and that the same negative matches
as T4 hold in reverse (this shape does not match `{:wallclock_timeout, _}}`,
a bare string, or `:invalid_script_ref`). Exists so a future change cannot
accidentally merge the two tagged-tuple shapes into one without a test noticing.

## T6 — Execution runs under the named supervisor

**Maps to:** AC-5

During a long-running (but not necessarily timed-out) call, asserts that
`Task.Supervisor.children/1` on `Letflow.Engine.Lua.TaskSupervisor` reports at least one
child while the call is in flight, and confirms via the module's moduledoc content (a
documentation/text assertion, not a runtime one) that the supervisor is named and its
selection over `Letflow.Engine.PluginTaskSupervisor` is justified in prose.

## T7 — Moduledoc restates LUA-10 as layer 2 and the non-interchangeability rationale

**Maps to:** AC-6

A documentation-content test (or a manual/documentation-review check performed by
TEST-DESIGNER, depending on how strictly this is made machine-checkable) confirming
`Letflow.Engine.Lua.Executor`'s moduledoc text states: this requirement restates LUA-10
as layer 2 of the LUA-08/LUA-10 pair; LUA-10's "enforced by the host / not relying on
Lua to cooperate" clause is what forbids satisfying it with `:max_instructions` alone;
and neither LUA-08 nor LUA-10 is met without both layers landed together.

## T8 — Moduledoc carries forward the BEAM-node-kill / `System.halt/0` limitation

**Maps to:** AC-7

A documentation-content check confirming the moduledoc states, in substance, that a
hard kill of the BEAM node itself or a call to `System.halt/0` is NOT covered by this
mechanism — matching the limitation already disclosed in
`lib/letflow/engine/plugin_interface.ex`'s moduledoc.
