# Test Spec: REQ-156 — Configurable Memory Limit for Lua Script Execution

**Design:** `lib/letflow/design/req156-lua-memory-limit-impl.md`
**Sibling specs:** `test/specs/REQ-154.md` (in-band budget), `test/specs/REQ-155.md`
(wall-clock kill) — REQ-156's tests must exercise all three arms together where noted.

This is a prose skeleton: test names and what each one asserts, in words. No test code.

---

## T1 — Memory limit is configurable per execution, not hardcoded

**Asserts:** two calls to `execute_with_manifest/3` in the same test run, one with a
small configured `:max_heap_words` and one with a materially larger configured
`:max_heap_words`, both running the same allocating script. The call with the smaller
limit terminates (returns `{:error, :memory_limit_exceeded}`) measurably sooner than
the call with the larger limit — the same "two different configured limits, driven from
the same test, without `Application.put_env` round-tripping" pattern REQ-154's T1 and
REQ-155's T1 already use for their own configured values. The test quotes real `mix
test` output showing both calls' outcomes and relative timing (or the larger-limit
call's outcome differing from the smaller-limit call's, e.g. completing successfully
where the smaller limit failed, if that is the more reliable way to demonstrate the
limit is load-bearing rather than a no-op).

**Maps to:** AC-1.

---

## T2 — Large allocation under a small configured limit terminates cleanly (LUA-09's own acceptance criterion, at the scale it names)

**Asserts:** a Lua script that attempts an allocation on the order of magnitude LUA-09's
own acceptance text names ("1 GB"), run under a small configured `:max_heap_words`
(sized so that, converted to bytes via `:erlang.system_info(:wordsize)`, it corresponds
to roughly the "16 MB" LUA-09 names), returns `{:error, :memory_limit_exceeded}` rather
than: hanging (the test must have its own outer bound, e.g. an `assert_receive`-style
timeout or a hard-coded test timeout well above the configured `:timeout_ms`, so a
regression that removes the memory-kill path fails the test instead of hanging the test
suite), exhausting the test node's memory, or returning `{:ok, _}`. The test must not
choose a smaller scale "for convenience" — the design's §8 mapping (AC-2) requires the
scale LUA-09 itself names.

**Maps to:** AC-2.

---

## T3 — Memory-limit error is pattern-distinguishable from the instruction-budget error and the wall-clock-timeout error

**Asserts:** three calls in one test, each configured to deterministically trigger one
of the three resource-limit arms:

1. A script that exhausts a small `:max_instructions` budget without pcall-trapping it
   → `{:error, {:budget_exceeded, limit}}`.
2. A script that blocks (e.g. an unbounded loop, or the same host-blocking pattern
   REQ-155's own T2 uses) under a small `:timeout_ms`, with `:max_heap_words` left `nil`
   or large enough not to interfere → `{:error, {:wallclock_timeout, timeout_ms}}`.
3. A script that allocates aggressively under a small `:max_heap_words` (as in T2)
   → `{:error, :memory_limit_exceeded}`.

A single `case`/pattern-match construct in the test asserts all three outcomes are
distinct and none is confusable with either of the other two — i.e., the test does not
merely assert three separate `assert` calls each in isolation, but demonstrates the
three shapes cannot unify under one pattern.

**Maps to:** AC-3.

## T4 — Implemented mechanism matches REQ-149's recommendation

**Asserts:** this is primarily a design/code-review-level criterion (verified by
CODE-DESIGN-VALIDATOR and REVIEWER reading the moduledoc and implementation against
`req149-lua-memory-limit.md` §3), not a runtime-observable behavior distinct from T1–T3.
If a test is written for it at all, it should assert the moduledoc's REQ-156 section
(per design §7) is present and contains the required statements (e.g. a test reading
`Code.fetch_docs/1` for the module and asserting the moduledoc string contains the
LUA-09 clause-satisfaction language and the decision-0014-OQ-1 rejection language) —
mirroring how REQ-154/155's own moduledoc-content criteria were tested, if a
docstring-content test exists for those; otherwise this criterion is satisfied by
inspection during REVIEWER's gate rather than by an automated test.

**Maps to:** AC-4.

## T5 — Moduledoc states LUA-09 restatement and clause satisfaction, in those words

**Asserts:** the module's `@moduledoc` (retrieved via `Code.fetch_docs/1` or an
equivalent introspection mechanism, matching whatever pattern REQ-154/155's own
moduledoc-content tests use, if any) contains: a statement that this restates LUA-09;
an explicit statement that "terminate the script" is satisfied; an explicit statement
that "fail gracefully" is NOT satisfied; and a reference to `:max_heap_size` (or
equivalent) as the mechanism.

**Maps to:** AC-5.

## T6 — `:max_instructions` is never used as a memory proxy, and the moduledoc records the rejection

**Asserts two things:**

1. **Static/code-level:** no code path in `Letflow.Engine.Lua.Executor` reads
   `max_heap_words` when computing, adjusting, or validating `max_instructions`, or vice
   versa — the two options are independently threaded through `opts` and independently
   applied (`max_instructions` to `Sandbox.new/1`, `max_heap_words` to the `spawn_opt`
   call per design §5). This may be asserted by inspection (REVIEWER gate) rather than
   a runtime test, since it is a negative claim about the absence of a code path.
2. **Moduledoc content:** the `@moduledoc` states that `:max_instructions` was
   considered and rejected as a memory-limit proxy, citing decision 0014's OQ-1.

**Maps to:** AC-6.

## Coverage notes for TEST-DESIGNER

- T2 and T3's third case both allocate aggressively under a small `:max_heap_words`;
  they may share a helper script/fixture, but each test must independently assert its
  own specific outcome shape rather than relying on the other having run first.
- Per design §5.4, `Task.Supervisor.children/1` on `Letflow.Engine.Lua.TaskSupervisor`
  is **not** a valid way to observe a memory-limited execution's process (it is not
  registered there) — do not reuse REQ-155's T3-style supervisor-registry assertion
  technique for a memory-limited case. REQ-156's own AC-2 only requires the *return
  value* to be a structured error, which does not need process-registry introspection.
- Any test that intentionally allocates at the "1 GB" scale must still complete quickly
  in practice, because the small configured `:max_heap_words` limit is expected to kill
  the process almost immediately after allocation begins — the scale describes the
  script's *attempted* allocation, not an amount the test actually waits to see
  allocated.
- No test in this spec should hardcode a literal timeout/budget/heap-word value as a
  module attribute shared across tests in a way that defeats AC-1's "two different
  configured limits" requirement — each relevant test must pass its own explicit value
  through `execute_with_manifest/3`'s `opts`.
