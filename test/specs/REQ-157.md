# Test spec: REQ-157 — Capability model and capability check at every gated host-function call site (LUA-05, LUA-06)

**Requirement:** REQ-157 (`docs/requirements.yaml`)
**Implementation:** `lib/letflow/engine/lua/capabilities.ex` (new),
`lib/letflow/engine/lua/platform.ex` (extended)
**Design:** `lib/letflow/design/req157-lua-capability-model.md`
**Test code:** `test/letflow/engine/lua/capabilities_test.exs` (new),
`test/letflow/engine/lua/platform_test.exs` (extended)

This was originally a skeleton only (CODE-DESIGNER, Step 1) naming each planned test per
acceptance criterion. ELIXIR-DEV (Step 2a) then wrote the actual `capabilities_test.exs`
(11 cases) and extended `platform_test.exs` (28 REQ-157 + carried-over REQ-152 cases,
39 total across both files) against this skeleton and the design doc's §9 table.
TEST-DESIGNER (Step 3) reconciled this document against the real, shipped test cases
below — the planned-test descriptions were updated where implementation details differed
from the original plan, and one coverage gap was found and closed (see "Coverage gap
found and closed at Step 3" below).

## Construction convention

Tests that need a real production sandbox construct their `Lua.t()` via
`Letflow.Engine.Lua.Sandbox.new/0` (never `Lua.new/1` directly), matching REQ-151/152's
convention. Tests that need a specific, non-default (or non-empty) grant set call
`Letflow.Engine.Lua.Platform.install/2` directly against a fresh `Sandbox.new/0` VM,
since `Sandbox.new/1` itself only ever calls the empty-grant-set `install/1` (design §1.1)
and is not modified by this requirement.

## Planned test cases

### 1. `Capabilities` unit tests (support AC2–AC6; no Lua VM involved)

- `test/letflow/engine/lua/capabilities_test.exs`
  - `new/0` returns an empty grant set; `has?/2` on it is `false` for any capability.
  - `new/1` builds a grant set from a list; `has?/2` is `true` for each listed capability
    and `false` for one not listed.
  - `add/2` returns a new grant set containing the added capability; the original grant
    set passed in is unchanged (pure, non-mutating).
  - `check/3` returns `:ok` when the grant set has the required capability.
  - `check/3` returns `{:error, %{function: _, required: _, granted: _}}` — all three
    keys present — when the grant set lacks the required capability; `required` matches
    the capability passed in, `function` matches the function-name atom passed in,
    `granted` matches `MapSet.to_list/1` of the grant set passed in (including the empty-
    list case for an empty grant set).
  - `check/3` returns `:ok` unconditionally when `required = :none`, regardless of grant
    set content (including an empty grant set) — proves the ungating mechanism itself,
    independent of any Lua wiring.
  - `check!/3` returns `:ok` on grant; raises `Lua.RuntimeException` on denial (asserted
    via `assert_raise`), carrying the same three fields somewhere on the raised struct.
  - `service_capability/1` returns the exact string `"service:call:" <> svc_id` for
    several `svc_id` values (including one containing a colon, to prove no unexpected
    escaping/parsing is applied).

### 2. Closed-set enumeration (AC1)

- `platform_test.exs`: a script run against a real `Letflow.Engine.Lua.Sandbox.new/0` VM
  enumerates the `platform` table's keys (mechanism per design §11 OQ-3 — `pairs`, or the
  substituted mechanism ELIXIR-DEV records if `pairs` does not work as expected) and
  asserts the result is exactly the 8 names from design §4.1's table
  (`call_service`, `read_variable`, `write_variable`, `log`, `emit_event`,
  `get_instance_state`, `now`, `fail`) — no more, no fewer, order not asserted.
- `platform_test.exs`: a source-level guard reads `lib/letflow/engine/lua/platform.ex`'s
  text and asserts exactly one occurrence of the `Lua.set!(lua, [:platform,` call-site
  pattern (the single fold, design §4.1/§10 INV-CAP-1) — guards against a future
  hand-added 9th `Lua.set!` call that would bypass the capability matrix entirely.

**Why both are needed:** the enumeration test alone would not catch a 9th function added
via some mechanism other than the matrix fold (e.g. a second, hand-written `Lua.set!`
call elsewhere in the file) if that alternate mechanism happened to also produce exactly
8 *currently listed* names — it only catches a discrepancy once a 9th name is actually
visible. The source-level guard catches the structural violation (a second call site
existing at all) independent of what names it happens to install today.

### 3. Per-function capability-denial tests (AC2) — one case per gated function, six total

- `platform_test.exs`, against `Platform.install(Sandbox.new(), Capabilities.new())`
  (empty grant set), each case rescues the raised `Lua.RuntimeException` and asserts
  `exception.original[:function]`, `[:capability_required]`, and `[:capabilities_granted]`
  are all present and match the row's own matrix entry (not merely `assert_raise
  Lua.RuntimeException` with no field check):
  - `platform.read_variable(...)` → `capability_required == "variable:read"`.
  - `platform.write_variable(...)` → `capability_required == "variable:write"`.
  - `platform.log(...)` → `capability_required == "audit:log"`.
  - `platform.emit_event(...)` → `capability_required == "event:emit"`.
  - `platform.get_instance_state(...)` → `capability_required == "instance:read"`.
  - `platform.call_service("any-service")` → `capability_required ==
    "service:call:any-service"`.

**Why these tests exist:** AC2 is LUA-06's own acceptance criterion, applied
individually — a single "some function is gated" test would not prove each of the six
independently checks capabilities before executing; a bug that accidentally skipped the
check for one function would only be caught by testing each function by name.

**Coverage gap found and closed at Step 3:** the version of these six tests originally
written by ELIXIR-DEV asserted only `assert_raise Lua.RuntimeException`, with no check
of the raised exception's fields. Every one of the six gated functions' stub bodies
(`run_stub(:not_yet_implemented, ...)`) *also* unconditionally raises
`Lua.RuntimeException` regardless of whether the capability check ran — so a bug that
skipped `Capabilities.check!/3` entirely for one row would still produce a raise
indistinguishable from a genuine denial under a bare `assert_raise`. This was confirmed
by mutation-testing the shipped code directly: temporarily short-circuiting the
`check!/3` call for `write_variable` (`if row.name != :write_variable do
Capabilities.check!(...) end`) and running `mix test
test/letflow/engine/lua/platform_test.exs` left **all 27 tests in that file passing**
(`Result: 27 passed`) — the gap was real, not hypothetical. Adding the
`capability_required`/`capabilities_granted`/`function` field assertions above to all
six per-function cases closes it: re-running the same mutant against the updated tests
produces exactly one failure (`Result: 26/27 passed`, `write_variable`'s case, with
`capability_required` observed as `nil` instead of `"variable:write"`), and reverting
the mutant restores `39 passed` across both files. See
`test/letflow/engine/lua/platform_test.exs`'s "REQ-157: per-function capability-denial
tests" `describe` block for the comment recording this same mutation-testing rationale
in the test file itself.

### 4. Structured denial fields (AC3)

- `platform_test.exs`: a dedicated `read_variable` case (`describe "REQ-157: structured
  denial fields (AC3)"`) rescues the raised `Lua.RuntimeException` and asserts all three
  fields are present and correct on `exception.original`: the function name
  (`:read_variable`), the required capability (`"variable:read"`), and the granted
  capabilities (`[]`, the empty grant set used).

**Why this test exists:** AC2's tests (as originally written) proved only that a raise
happens; this test proves the raise carries LUA-06's three explicitly named fields, not
merely a generic error message. Since Step 3's gap-closing change (§3 above) now asserts
these same three fields on all six per-function denial cases, this dedicated case is
retained as a redundant, explicitly AC3-labeled example rather than removed — the
per-function cases fully subsume it, but it stays as the direct citation for AC3 in
isolation.

### 5. `call_service` denial without any grant (AC4)

- `platform_test.exs`: `platform.call_service("billing")` against an empty grant set
  raises; the rescued exception's required-capability field equals exactly
  `"service:call:billing"` (not the bare `"service:call"`).

**Why this test exists:** AC4 is LUA-05's own acceptance criterion, verbatim
(`platform.call_service('X')` without `service:call:X` returns a structured error) — this
test is the direct, literal instantiation of that example.

### 6. `call_service` grant is parameterised, not blanket (AC5)

- `platform_test.exs`: grant set built via
  `Capabilities.new(["service:call:alpha"])`; `platform.call_service("alpha")` succeeds
  past the gate (reaches the stub's own non-capability raise, not a capability-denial
  raise — distinguished per design §4.3/§9); `platform.call_service("beta")`, same grant
  set, still raises a *capability denial* (not the stub's raise), with required-capability
  field `"service:call:beta"` and granted field `["service:call:alpha"]`.

**Why this test exists:** AC5 is the requirement's most specific anti-regression
target — a blanket `"service:call"` capability implementation (rather than one
parameterised per service id) would pass AC4 alone but incorrectly let a single grant
authorise every service. This test is the one that would catch that specific wrong
implementation.

### 7. `now` and `fail` callable with an empty capability set (AC6)

- `platform_test.exs`: against `Platform.install(Sandbox.new(), Capabilities.new())` (or
  plain `Sandbox.new/0`, since `install/1` already uses an empty grant set per design
  §4.4):
  - `platform.now()` returns its normal value (an ISO 8601 string) with no raise at all —
    proves no capability gate exists on this path, not merely that the gate happens to be
    satisfied.
  - `platform.fail()` raises — but the raised exception is the stub's own explicit-failure
    raise (design §4.3), NOT a capability-denial raise: asserted by checking the
    capability-denial-specific fields (e.g. `capability_required`) are absent from the
    raised exception, distinguishing "denied by capability check" from "the stub itself
    always raises."

**Why this test exists:** AC6 explicitly guards against a wrong implementation that adds
a gate to either function "by symmetry" with the other six (design §5's binding
statement) — a test that merely calls both and expects *some* result would not catch a
regression that added a capability requirement to `now`, since a granted call would
still "work." Asserting `now` never raises at all, and that `fail`'s raise is not a
capability-shaped one, are what actually distinguish "ungated" from "gated but granted."

### 8. Moduledoc content (AC7)

- `platform_test.exs`: `Code.fetch_docs/1` on `Letflow.Engine.Lua.Platform`'s moduledoc
  asserts the presence of: the 8-row capability matrix (function name → required
  capability, in substance), the `now`/`fail` ungated rationale, and the "a test that
  expects a gate on either is reading the matrix wrong" binding statement (design §5).

**Why this test exists:** AC7 requires documentation content that no other test in this
suite verifies — a passing denial/enumeration test proves the *mechanism* works, not that
the matrix and its rationale are legibly recorded for a future implementer (REQ-159/160)
or reviewer, which is what AC7 is actually asking for.

### 9. Regression guard — REQ-152's existing `platform.now` behavior is unchanged

- `platform_test.exs`: REQ-152's own existing test cases (ISO 8601 parseability via
  `DateTime.from_iso8601/1`, exact-value injection via a fixed `TimeSource`) are re-run
  unmodified against the refactored `install/2`-based wiring (design §4.3's "refactor,
  not behavior change" claim for `now`) — not a new acceptance criterion, but a guard
  against this requirement silently breaking REQ-152's already-accepted behavior while
  moving `now`'s installation into the capability-matrix fold.

### 10. `mix test` / `mix compile --warnings-as-errors` (AC8)

Not asserted by a test in this file — TEST-RUNNER's Step 4 responsibility, real output
quoted there, same convention as REQ-151/152's specs.

## No wall-clock or unseeded-randomness dependence

None of the above tests depend on wall-clock time except test 9's carry-over regression
cases, which (per REQ-152's own spec) use a hardcoded `DateTime.t()` literal via a fixed
`TimeSource`, never `DateTime.utc_now/0` in an assertion. No test in this file uses
`:rand` or any other unseeded source.
