# Test spec: REQ-158 — Capability manifest, load-time validation, and the hash fed to LuaScriptAudit (LUA-07)

**Requirement:** REQ-158 (`docs/requirements.yaml`)
**Implementation:** `lib/letflow/engine/lua/manifest.ex`, `lib/letflow/engine/lua/executor.ex`
**Design:** `lib/letflow/design/req158-lua-manifest-validation.md`
**Test code:** `test/letflow/engine/lua/manifest_test.exs` (pure, `async: true`),
`test/letflow/engine/lua/manifest_executor_audit_test.exs` (real Postgres, `async: false`)

**Reconciled by TEST-DESIGNER, Step 3, against the actually-shipped tests.** This
document originally described a skeleton written before implementation (CODE-DESIGNER,
Step 1). Since then: (a) ELIXIR-DEV built the real test files against it; (b) a rework
round found and fixed a real hash-collision bug (SECURITY-REVIEWER: the original
raw-separator byte scheme — `0x00`/`0x0A` — collided under delimiter injection, e.g.
`capabilities: ["a\nb", "c"]` hashing identically to `capabilities: ["a", "b", "c"]`)
and added two regression tests for it; (c) the fix changed the hash's byte layout from
raw separators to **length-prefixed framing** (each field prefixed by its own 32-bit
big-endian byte length) — this document's §2–3 below are updated to describe that
current scheme, not the superseded one; (d) TEST-DESIGNER's own mutation-testing pass
(§10 below) found and closed one further coverage gap: no test compared
`compute_hash/2`'s output against an independently-computed digest, so a mutation
shrinking the length prefix from 32 bits to 16 bits, or reordering the three
concatenated segments, passed every test in this file undetected. A new test closes
that gap (§2, "golden/independent-reimplementation" case). (e) REVIEWER's flagged
non-blocking documentation gap (neither `manifest.ex`'s moduledoc nor `executor.ex`'s
`script_ref` `@typedoc` steered future callers toward the manifest-carrying map shape
over the legacy bare-binary shape) is addressed by a one-sentence addition to each, and
two new moduledoc/typedoc-content tests assert the addition is present (§9).

## Construction convention

Tests build a `Letflow.Engine.Lua.Manifest.t()` directly as a plain struct literal (no
factory module needed at this size) with a `script_id` and a `capabilities` list. Tests
that need a `Letflow.Engine.Lua.Capabilities.grant_set()` for comparison use
`Letflow.Engine.Lua.Capabilities.new/1`, matching REQ-157's own test convention. No
database, no `Repo`, no Ecto sandbox is needed anywhere in this file — every function
this requirement adds is pure (design §3.1, INV-MAN-1/INV-MAN-2).

## Planned test cases

### 1. `Manifest` struct and shape validation (supports AC1, AC5; no execution involved)

- `test/letflow/engine/lua/manifest_test.exs`
  - `validate_shape/1` returns success for a manifest with a non-empty string
    `script_id` and a list of string capabilities.
  - `validate_shape/1` returns a distinct, pattern-matchable shape error when
    `script_id` is missing, `nil`, or not a string.
  - `validate_shape/1` returns a distinct, pattern-matchable shape error when
    `capabilities` is not a list, or contains a non-string element.

### 2. Hash determinism and canonicalization (AC5)

- `compute_hash/2` called twice with the identical manifest and identical script source
  produces the identical hex string both times.
- `compute_hash/2` is insensitive to the *order* of the manifest's `capabilities` list —
  two manifests differing only in the listed order of the same set of capability
  strings produce the identical hash (proves the canonicalization/sort step in the
  design's §4.2 byte layout is actually applied, not merely documented).
- `compute_hash/2` is insensitive to *duplicate* entries in `capabilities` — a manifest
  listing a capability twice produces the identical hash to the same manifest listing it
  once (proves the design's de-duplication-through-`MapSet` canonicalization step).
- `compute_hash/2` produces a lowercase hex string of the length expected for a SHA-256
  digest (64 hex characters), matching the format `lib/letflow/engine/lua/executor.ex`
  already produces for its own script-source hash today.

### 3. Hash sensitivity — the "modified manifest is rejected" mechanism, in isolation (AC1, AC5)

- `compute_hash/2` produces a *different* hash when `capabilities` gains an additional
  capability string, all else (`script_id`, `script_source`) held fixed.
- `compute_hash/2` produces a *different* hash when `capabilities` loses a capability
  string, all else held fixed.
- `compute_hash/2` produces a *different* hash when `script_id` changes, all else held
  fixed (proves two different scripts with identical capabilities and identical source
  text do not collide onto the same manifest hash).
- `compute_hash/2` produces a *different* hash when even a single byte of
  `script_source` changes, all else held fixed (proves the manifest-covering hash did
  not lose the original script-content sensitivity the bare-source hash already had).
- **(added, rework 1, SECURITY-REVIEWER regression)** `compute_hash/2` does NOT collide
  a capability string containing an embedded LF (`"a\nb"`) with the equivalent
  split-list capabilities (`"a"`, `"b"`) — the exact collision the original
  raw-`0x0A`-separator scheme produced, now closed by length-prefixed framing.
- **(added, rework 1)** `compute_hash/2` does NOT create an analogous collision when a
  literal NUL (`0x00`) byte appears inside `script_id` or `script_source` — proving the
  fix is general (length-prefixing, not merely picking a different separator byte).
- **(added, TEST-DESIGNER Step 3, mutation-testing gap)** `compute_hash/2`'s output
  matches an digest independently reconstructed in the test from the moduledoc's own
  documented byte layout (32-bit big-endian length prefix on each field, in the
  documented field order), using `:crypto.hash/2` directly rather than any of
  `Manifest`'s own helpers. **Why this test was added:** every other sensitivity test
  above only ever compares `compute_hash/2` against itself on two different inputs, so
  none of them can detect a mutation that changes the hash's *absolute* value in a way
  that preserves all of those *relative* properties — verified directly: a mutant
  shrinking the 32-bit length prefix to 16 bits, and a mutant reordering the three
  concatenated segments, both left every other test in this file passing, and both are
  caught only by this test.

**Why these tests exist:** AC5 requires the hash algorithm and covered bytes to be
stated precisely enough that "modified manifest is rejected" is well-defined; these
tests are the direct, mechanical proof that the stated byte layout (moduledoc, current
length-prefixed scheme) is actually sensitive to every field it claims to cover,
insensitive to the one reordering/duplication case it claims not to be, immune to the
delimiter-injection collision class SECURITY-REVIEWER found against the earlier
raw-separator scheme, and matches its documented exact byte layout rather than merely
some internally-self-consistent formula.

### 4. Load-time rejection of a manifest modified after registration (AC1 — LUA-07's own acceptance criterion)

- `validate_at_load/3`, given a manifest and script source, first computes the hash that
  would have been recorded at registration time (i.e. calls `compute_hash/2` on the
  *original*, unmodified manifest+source pair and treats that as `registered_hash`).
  Then the same script source is validated again against a manifest that has since been
  modified (one additional capability string added, `script_id` and `script_source`
  unchanged) — asserted to return the distinct mismatch error
  (`{:error, {:manifest_mismatch, registered_hash, computed_hash}}`), with
  `computed_hash` different from `registered_hash`.
- `validate_at_load/3`, given a manifest and script source that have NOT changed since
  the `registered_hash` was computed from them, returns `{:ok, manifest_hash}` with
  `manifest_hash` equal to `registered_hash`.
- `validate_at_load/3` short-circuits on a shape-invalid manifest (design §3.1 step 1)
  — asserted by passing a manifest that fails `validate_shape/1` (e.g. `nil` `script_id`)
  and confirming the result is `{:error, {:invalid_manifest, _}}`, distinct from a
  hash-mismatch error, and that no hash was computed as part of producing that result.

**Why these tests exist:** AC1 is LUA-07's own literal acceptance text ("Modified
manifest without re-registration is rejected") — the first case above is the direct,
literal instantiation of it: a manifest edited after its `registered_hash` was captured
must be rejected on the next load-time check, with no re-registration step having
occurred.

### 5. Rejection happens before any script text executes (AC2)

- A test double (a bare Elixir function or a small recording agent, not a Lua
  interpreter) stands in for "script execution" and records whether it was invoked. The
  test drives the *calling convention* design §3.2 describes: call `validate_at_load/3`
  first; only if it returns `{:ok, _}` does the test proceed to "execute" (invoke the
  recording double). With a deliberately modified manifest (as in test 4's first case),
  the test asserts `validate_at_load/3` returns `{:error, {:manifest_mismatch, _, _}}`
  AND that the recording double was never invoked — i.e., zero executions were attempted
  as a consequence of the rejection.
- A variant of the same test, using a real `Letflow.Engine.Lua.Executor` +
  `Letflow.Engine.LuaScriptAudit.execute_script_for_audit/6` call in place of the bare
  recording double, with a Lua script whose body would produce an observable side effect
  if it ran (e.g. a script that would otherwise return a specific sentinel value or raise
  a specific, distinguishable error if `Lua.eval!/2` were ever reached) — asserting that
  when `validate_at_load/3` is called first and rejects, the calling test code never
  reaches the point of invoking `execute_script_for_audit/6` at all, so neither that
  sentinel value nor that specific error is ever observed. This is the literal
  instantiation of AC2's own wording ("a script whose body would set an observable side
  effect produces none when its manifest is invalid").

**Why these tests exist:** AC2 is explicitly about *ordering*, not merely about
`validate_at_load/3` returning an error value in isolation — a design or implementation
that computed the right error but only after already running the script would satisfy
every other test in this file while failing AC2's actual point. These tests exist
specifically to catch that failure mode.

### 6. The manifest hash flows into `LuaScriptAudit`'s audit row on a successful execution (AC3)

- Using a real `Letflow.Engine.Lua.Executor` and a test `Letflow.Engine.LuaScriptAudit`
  invocation (per the design §5.3.1 coordinated `executor.ex` change, once that change
  has landed — this test is written against the post-change behavior, not the
  pre-REQ-158 bare-script-source hash): compute `manifest_hash` via
  `Manifest.validate_at_load/3` for an unmodified manifest+script pair, then call
  `LuaScriptAudit.execute_script_for_audit/6` passing that same `manifest_hash` as the
  `registered_hash` argument. Assert the call succeeds (`{:ok, %AuditRecord{}}`) and that
  the inserted `AuditRecord`'s `manifest_hash` field equals the value
  `Manifest.compute_hash/2` produced for that manifest+script pair — proving the value
  this module computes is the value that ends up recorded, end to end, not merely equal
  in isolation.
- A negative companion: if this test is run before the `executor.ex` coordinated change
  (design §5.3.1) lands, it is expected to fail, and that failure is itself the intended
  signal that the coordinated change has not yet been made — this test is not expected
  to pass against an unmodified `executor.ex`.

**Why this test exists:** AC3 explicitly requires this be "proven end to end rather than
in isolation" — a unit test of `Manifest.compute_hash/2` alone (tests 2–3 above) proves
the hash function's own properties, but not that the value actually reaches the audit
row through the real `Executor` → `LuaScriptAudit` path.

### 7. A hash mismatch still yields `LuaScriptAudit`'s own error, and INV-LSA-2 is fed, not bypassed (AC4)

- Call `LuaScriptAudit.execute_script_for_audit/6` directly with a `registered_hash`
  that does NOT match what the real `Executor` will compute for the given script (e.g.
  an arbitrary, deliberately wrong hex string, or the hash of a *different* manifest+
  script pair than the one actually being executed). Assert the result is
  `{:error, {:manifest_hash_mismatch, registered_hash, actual_hash}}` — `LuaScriptAudit`'s
  own existing error shape, unchanged — and assert no `AuditRecord` row was inserted
  (e.g. by counting rows before and after, or asserting the repo query for that
  `instance_id` returns nothing).
- The same assertion repeated for a case where `Manifest.validate_at_load/3` was called
  first and itself returned `{:ok, _}` (i.e., the load-time gate passed), but the
  `registered_hash` value passed on to `execute_script_for_audit/6` is nonetheless wrong
  (e.g. a stale value from a prior manifest version, simulating a race between load-time
  validation and execution) — proving `Letflow.Engine.Lua.Manifest`'s own successful
  gate result does not, and cannot, suppress or substitute for `LuaScriptAudit`'s
  independent post-execution check.

**Why these tests exist:** AC4 is specifically about *not bypassing* INV-LSA-2 — a test
that only ever exercises the happy path (test 6) would not catch an implementation that
accidentally routes around `LuaScriptAudit.verify_manifest_hash/2` (e.g. by having
`Manifest` its own comparable "success" path short-circuit the call). These tests
directly exercise the mismatch path through the unmodified `LuaScriptAudit` code and
assert its own, unchanged error shape and unchanged no-row-written behavior.

### 8. Moduledoc content (AC5, AC6)

- `Code.fetch_docs/1` on `Letflow.Engine.Lua.Manifest`'s moduledoc asserts the presence
  of: the hash algorithm name (SHA-256) and encoding (lowercase hex), the exact ordered
  list of covered fields and the **current** length-prefixed framing (32-bit big-endian
  length prefix per field, per the moduledoc's post-rework-1 "Framing" section) — not
  the superseded raw-separator scheme, though a second test below confirms the
  moduledoc still explains *why* that earlier scheme was replaced — and the R-Co
  `manifest.zig` provenance statement (design §2.4) — that the file is absent from this
  checkout and no field is claimed "deliberately dropped" as a result.
- A second test asserts the moduledoc's "Framing" section still explains, in substance,
  why the raw `0x00`/`0x0A` separator scheme was replaced (mentions both separator byte
  values and "delimiter-injection") — this is deliberately kept as *history*, not
  current-algorithm documentation, so a future reader does not rediscover the same
  vulnerability by "simplifying" the framing back to separators.

**Why this test exists:** AC5 and AC6 both require specific, precise moduledoc content
that no functional test in this file otherwise verifies — a passing hash/gate test
proves the mechanism works, not that its exact covered-bytes claim and its
source-provenance caveat are legibly recorded for a future reviewer. Splitting the
"current algorithm" and "historical vulnerability" assertions into two tests also means
a moduledoc edit that accidentally deletes the *current* framing description (while
leaving the historical explanation intact, or vice versa) is caught precisely, not
papered over by one loosely-worded combined assertion.

### 9. Documentation gap fix — steering future callers toward the manifest-carrying `script_ref` shape (REVIEWER, non-blocking)

REVIEWER flagged that neither `manifest.ex`'s moduledoc nor `executor.ex`'s
`script_ref` `@typedoc` textually steered a future caller toward the
manifest-carrying map shape (`%{manifest: Manifest.t(), script_source: binary()}`)
over the legacy bare-`binary()` shape kept only for ~40 pre-existing test call sites.
TEST-DESIGNER (Step 3) added one sentence to each:

- `manifest.ex`'s moduledoc now states a caller constructing a
  `Letflow.Engine.Lua.Executor.script_ref()` value "should prefer" the map shape,
  naming the bare-binary shape "legacy."
- `executor.ex`'s `script_ref` `@typedoc` now carries the identical steer inline,
  next to the type definition callers actually read.

Two tests assert this text is present and does not regress silently:
- `test/letflow/engine/lua/manifest_test.exs`, "moduledoc steers future callers toward
  the manifest-carrying map shape..." — asserts `manifest.ex`'s moduledoc contains
  `"should prefer"` and `"legacy"`.
- `test/letflow/engine/lua/manifest_test.exs`, "Executor's script_ref @typedoc also
  steers toward the manifest-carrying map shape..." — reads `Executor`'s type docs via
  `Code.fetch_docs/1`'s `type_docs` component and asserts the same two phrases plus
  `"manifest"` are present in the `script_ref` type's own doc string, not merely
  somewhere else in the module.

**Why these tests exist:** REVIEWER's finding was non-blocking prose, not a functional
defect — without a test, a later edit could silently drop the steering language again
with nothing to catch it.

### 10. Mutation-testing summary (TEST-DESIGNER, Step 3 discipline)

Three mutations were tried directly against the shipped `lib/letflow/engine/lua/manifest.ex`
(each applied, `mix test` run, result recorded, then reverted and `mix test` re-run to
confirm a clean baseline before and after):

1. **Hash-comparison always `:ok`** (`validate_at_load/3`'s `if computed_hash ==
   registered_hash` replaced with `if true`): caught immediately — 3 of 28 then-existing
   tests failed (the two `validate_at_load/3` mismatch-shape tests and the AC2
   never-invoked test whose assertion depends on the mismatch actually firing).
2. **Ordering: `compute_hash/2` called before `validate_shape/1`** inside
   `validate_at_load/3` (instead of after, short-circuiting on shape error first):
   caught — the "a shape-invalid manifest short-circuits..." test failed, because
   `compute_hash/2`'s own `is_binary(script_id)` guard raises a `FunctionClauseError`
   on the `nil` `script_id` fixture that test uses, before the shape check ever runs.
3. **Length-prefix framing: 32-bit shrunk to 16-bit**, and, separately, **the three
   concatenated segments reordered**: **NOT caught** by any test that existed before
   this Step 3 pass — all 28 tests still passed under both mutants, because every
   sensitivity/determinism/collision test in this file only ever compares
   `compute_hash/2`'s output against itself on two different inputs, never against an
   independently-computed expected value. **Gap closed** by the new
   "matches an independently-reconstructed digest..." test in §2 above, verified to
   fail under both mutants and pass against the real, unmutated code.

## No wall-clock or unseeded-randomness dependence

None of the tests in either file depend on wall-clock time or on `:rand` or any other
unseeded source. Every hash and comparison in `manifest_test.exs` is over fixed,
literal test-authored manifest/script-source values. `manifest_executor_audit_test.exs`
uses `Ecto.UUID.generate()` for `instance_id`/`actor_id` values, matching the existing
`lua_script_audit_test.exs` convention — this is used only to obtain unique identifiers
for otherwise-deterministic assertions, not as an input any assertion's outcome depends
on being a particular value.

## Test isolation

`manifest_test.exs` needs no isolation beyond ExUnit's own `async: true` default: every
function under test is pure (no `Repo`, no process state, no shared mutable data).

`manifest_executor_audit_test.exs` provisions a fresh, uniquely-slugged tenant and a
real Postgres schema per test via its own `provisioned_tenant/0` helper (mirroring
`test/letflow/engine/lua_script_audit_test.exs`'s established shape): each test creates
its own `Tenant` row, calls `TenantProvisioning.provision_tenant_schema/1` and
`replay_migrations/2` to create and migrate a real, uniquely-named schema, and registers
an `on_exit/1` callback that drops that schema (`DROP SCHEMA IF EXISTS ... CASCADE`) and
deletes the tenant's `Registration`/`Tenant` rows — so a test's real-Postgres side
effects cannot leak into another test's run even under `async: false`'s serialized
execution, and cannot accumulate across repeated `mix test` runs. Verified: both tests
in this file each call `provisioned_tenant/0` independently rather than sharing
state via `setup`, so a mid-file failure in one test's assertions still runs its own
`on_exit/1` cleanup and does not affect the other test's freshly-provisioned schema.
