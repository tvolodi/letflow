## Construction convention

Following REQ-157's own spec convention: tests needing the real production sandbox
construct via `Letflow.Engine.Lua.Sandbox.new/0`. Tests needing a specific execution
context (this requirement's new concern) call `Letflow.Engine.Lua.Platform.install/3`
directly against a fresh `Sandbox.new/0` VM, since `Sandbox.new/1` itself only ever
calls the empty-context `install/1` (design §2.3.1) and is not modified by this
requirement.

## Planned test cases

### 1. `Letflow.Engine.LuaNumberMarshalling` unit tests (support AC5, AC6)

- `to_lua/1` returns an integer argument unchanged.
- `to_lua/1` returns a float argument unchanged, including a whole-number float (e.g.
  the value that prints as `3.0`), asserting the result is still recognizably a float
  (not collapsed to an integer) via `is_float/1`.
- `to_lua/1` returns `nil` unchanged.
- `from_lua/1` returns an integer, a whole-number float, and `nil` unchanged — mirror of
  the three `to_lua/1` cases above, proving both directions are identity for the numeric/
  `nil` cases per REQ-150 §2.1/§2.2.
- A non-numeric, non-`nil` value (a string, a boolean, a map) passed to either function
  is returned unchanged — proves neither function does anything beyond the numeric/`nil`
  cases REQ-150 §3 assigns it.

### 2. `platform.read_variable` — current value or nil (AC1)

- `platform_test.exs`: with an execution context whose `variables` map has a key set to
  a string value, calling `platform.read_variable` with that key's name returns the
  string value.
- Same setup, calling `platform.read_variable` with a name absent from `variables`
  returns Lua `nil`.
- Calling `platform.read_variable` with a non-string argument (e.g. a number or a table)
  returns Lua `nil` rather than raising (design §4.1 step 1).

### 3. `platform.read_variable` — number-marshalling round trip (AC6)

- An execution context's `variables` map contains one integer-valued entry and one
  whole-number-float-valued entry (e.g. values that print as `3` and `3.0`
  respectively). `platform.read_variable` for each name returns a Lua value whose
  `math.type` matches the stored Elixir type exactly: `"integer"` for the integer entry,
  `"float"` for the float entry — proving `LuaNumberMarshalling.to_lua/1` is actually
  applied on this call path (REQ-150 §2.2/§2.3), not merely available and unused.

### 4. `platform.read_variable` — capability denial (AC4)

- Against `Platform.install/3` called with an empty grant set (and any execution
  context), calling `platform.read_variable` raises a Lua error; the rescued
  exception's structured fields show `required` equal to `"variable:read"` — same
  three-field assertion style REQ-157's own per-function denial tests use, applied here
  to confirm the capability requirement is unchanged from REQ-157's matrix (design §4.3).

### 5. `platform.get_instance_state` — valid instance, scoped to self (AC3)

- A real `InstanceProjection` row is inserted (via the project's normal test-fixture
  path, under an explicit tenant prefix), and an execution context is built with that
  same `prefix` **and** `instance_id` equal to that row's id (design §5.1 — the
  script-supplied argument must equal `execution_context.instance_id`).
  `platform.get_instance_state` called with that same id returns a Lua table whose
  `status` field matches the row's status string and whose `variables` field matches the
  row's `variables` map, each numeric leaf passed through the same round-trip assertion
  style as test 3 above.

### 6. `platform.get_instance_state` — structured errors, not raises (AC3)

- Calling `platform.get_instance_state` with a non-UUID-shaped argument returns a
  two-value Lua result whose first value is `nil` and whose second value is a table
  with `reason` equal to `"invalid_id"` — and no exception is raised. Checked even when
  `execution_context.instance_id` is set, proving the malformed-argument check (design
  §5.2 step 2) runs before the self-scope check (step 3).
- Calling `platform.get_instance_state` with a well-formed UUID that differs from
  `execution_context.instance_id` returns `nil` plus a `reason` of `"forbidden"` — no
  exception raised. Two sub-cases, both asserting the identical `"forbidden"` outcome
  (design §5.1/§5.3 — the response must not let a script distinguish the two), both
  implemented as `"a real same-tenant sibling instance AND a nonexistent instance id both
  return the IDENTICAL forbidden result"`:
  - the other id belongs to a real `InstanceProjection` row in the **same** tenant
    schema (proves same-tenant cross-instance reads are rejected by default, not merely
    cross-tenant ones);
  - the other id is well-formed but names no row anywhere.
  A separate test, `"no Repo.get/3 (no [:letflow, :repo, :query] telemetry event) fires
  for a same-tenant sibling id"` (ADDED by TEST-DESIGNER — see "Mutation testing" below),
  independently proves the "no `Repo` call attempted at all" half of this claim via a
  `:telemetry.attach/4` counter on `[:letflow, :repo, :query]`, the same idiom
  `test/letflow/api/context_test.exs` already uses for the same purpose. The two
  sub-cases above only ever asserted the *return value*; this test is the one that
  asserts the *absence of a database round trip*.
- Calling `platform.get_instance_state` with `instance_id` equal to
  `execution_context.instance_id`, where that id does not correspond to any row under
  the execution context's `prefix` (e.g. the row was deleted after the context was
  built), returns `nil` plus a `reason` of `"not_found"` — no exception raised. This is
  the only path that reaches step 4/`Repo.get/3` and still misses.
- Calling `platform.get_instance_state` under the empty-context sentinel (`prefix ==
  nil`) returns `nil` plus a `reason` of `"no_execution_context"`, with no `Repo` call
  attempted (assertable via a fixture that would raise if the repo were ever queried, or
  by inspecting that no query telemetry event fires).

### 7. `platform.get_instance_state` — capability denial (AC4)

- Same shape as test 4, asserting `required` equal to `"instance:read"`.

### 8. `platform.log` — structured entry with correlation IDs (AC2)

- An execution context is built with distinct, recognizable values for `script_identity`,
  `instance_id`, and `trace_id`. Calling `platform.log("info", "a message", nil)` (or
  with a small table for `context`) produces exactly one captured `Logger` entry (via
  `ExUnit.CaptureLog` or an injected backend, matching whatever mechanism this project's
  existing `Logger`-emitting tests use) whose metadata carries all three values —
  asserted **individually** (three separate assertions, one per field), per REQ-159's own
  acceptance text ("all three asserted individually").
- The emitted entry's message body contains the script-supplied `message` text
  unchanged.
- A `context` argument containing a table (not just a scalar) is present on the emitted
  entry's metadata in some inspectable form — proves `context` is not silently dropped.

### 9. `platform.log` — level mapping and malformed input

- `platform.log` called with each of `"debug"`, `"info"`, `"warn"`, `"error"` produces a
  `Logger` entry at the corresponding Elixir `Logger` level (`"warn"` mapping to
  `:warning`).
- `platform.log` called with an unrecognized level string produces an `:info`-level
  entry whose metadata carries the original unrecognized string under a distinct
  metadata key, rather than raising or silently discarding the level (design §6.1 step
  2).
- `platform.log` never raises regardless of argument shape (a non-string `message`, a
  missing `context` argument) — a smoke test calling it with several malformed argument
  combinations and asserting no exception propagates.

### 10. `platform.log` — capability denial (AC4)

- Same shape as test 4, asserting `required` equal to `"audit:log"`.

### 11. Matrix/stub-tag regression guards

- A source-level or introspection-based check that the `@capability_matrix`'s
  `required` value for each of `read_variable`, `get_instance_state`, `log` is still
  exactly `"variable:read"` / `"instance:read"` / `"audit:log"` respectively —
  regression guard for design §7.2's "required unchanged, stub tag only" claim.
- A check that `write_variable`, `call_service`, `emit_event` still raise the
  `:not_yet_implemented` stub error (unchanged by this requirement) — proves this
  requirement did not accidentally touch REQ-160's rows.
- A check that `now` and `fail` remain callable with an empty grant set and are
  unaffected by the new `execution_context` parameter (regression guard against
  design §7.3's claim that the other 5 rows ignore it).

### 12. `install/1`/`install/2` backward compatibility

- Every pre-existing REQ-157 test that calls `Platform.install/1` or `Platform.install/2`
  (not the new `install/3`) continues to pass unmodified — in particular, the six
  per-function capability-denial tests and the `now`/`fail` ungated tests, none of which
  should require any change to keep passing (design §2.3.1).
- A *granted* call to `read_variable`/`get_instance_state`/`log` made through
  `Platform.install/2` (not `install/3`) — i.e. with the empty execution-context
  sentinel — is observable and structured, not a crash: `read_variable` returns `nil`,
  `get_instance_state` returns the `"no_execution_context"` structured error, `log`
  still emits an entry with `nil` correlation fields (design §4.2, §5.2 step 1, §6.2).

## No wall-clock or unseeded-randomness dependence

Confirmed by direct reading of both test files: no test reads `DateTime.utc_now/0`,
`System.os_time/0`, or any unseeded `:rand`/`Enum.random` call. `platform_test.exs`'s
`platform.now()` tests (REQ-152, not this requirement) inject a fixed `TimeSource` double
rather than reading the real clock. All fixture identifiers in the REQ-159 sections
(`Ecto.UUID.generate/0`, tenant slugs via `Letflow.TenantSlugFixture.unique_slug/1`) are
used only as fixture identifiers/labels, never as assertion targets — matching this
document's original intent.

## Test isolation — real-Postgres fixtures

`provisioned_tenant/0` (mirroring `test/letflow/event_store_test.exs`'s own idiom)
provisions a real tenant schema per test via `Ecto.Adapters.SQL.Sandbox.mode(Repo,
:auto)` (required because tenant provisioning runs in its own process/transaction
outside the calling test's sandboxed connection) and registers an `on_exit` callback that
drops the schema and deletes the `tenants`/`registrations` rows it created, keyed by that
test's own generated `tenant.id` — no shared fixture state across tests, no fixed/reused
tenant id, and cleanup runs unconditionally via `on_exit` even on test failure. Every
`get_instance_state` test that needs a real row calls `seed_projection!/3` with its own
locally-generated `instance_id`, so no two tests can collide on the same row.
`async: false` at the module level (already required by the pre-existing REQ-152
`Platform.now/0` application-env tests) additionally rules out any cross-test
interleaving hazard from the `Ecto.Adapters.SQL.Sandbox.mode(..., :auto)` call, which
is itself process-global for the duration of the test that makes it.

## Mutation testing (TEST-DESIGNER, WF-02 Step 3)

Both mutations named in this run's task brief were applied directly to the shipped
source, run against the real test suite, observed, then reverted and reconfirmed clean.

**1. `get_instance_state`'s self-instance-only check — equality swapped for `true`.**
`do_get_instance_state/3`'s `if instance_id == execution_context.instance_id do ... end`
was changed to `if true do ... end` (unconditionally treating every argument as the
caller's own instance). Result: 1 test failed out of 56 —
`"a real same-tenant sibling instance AND a nonexistent instance id both return the
IDENTICAL forbidden result"` caught it (both ids incorrectly returned real state instead
of `"forbidden"`). Reverted; 64 passed again.

**2. Same check — reordered to run AFTER the `Repo` call, rather than before it.**
`do_get_instance_state/3` was changed to call `fetch_instance_state/3` unconditionally
first, and only apply the `instance_id == execution_context.instance_id` check
afterward to decide whether to return the real result or substitute `"forbidden"`. This
preserves every RETURN VALUE the existing tests asserted — 56/56 passed unchanged,
confirming a genuine gap: no test verified the "no `Repo` call attempted at all" half of
the design's own claim (design §5.1, moduledoc "Only a match reaches `Repo.get/3`").
**Gap closed**: added `"no Repo.get/3 (no [:letflow, :repo, :query] telemetry event)
fires for a same-tenant sibling id"` to `platform_test.exs`, using the same
`:telemetry.attach/4` counter idiom `test/letflow/api/context_test.exs` already uses.
Re-applying the same reordering mutation against the new test suite: 56/57 passed, the
new test the sole failure. Reverted; 57 passed again (see quoted output below).

**3. `LuaNumberMarshalling.to_lua/1` — round float to 1 decimal place.** Added a clause
`def to_lua(value) when is_float(value), do: Float.round(value, 1)`. Result: 65/65
passed unchanged — NOT a real gap, because every float value exercised by the existing
suite (`3.0`, `2.5`) is already exact at 1 decimal place, so this particular mutation is
coincidentally invisible to this test suite without being a genuine identity violation
for those specific inputs. Followed up with two mutations that ARE genuine identity
violations (below) to confirm coverage rather than concluding a gap from a
coincidentally-unobservable mutation.

**4. `LuaNumberMarshalling.to_lua/1` — coerce a whole-number float to an integer.**
Added `def to_lua(value) when is_float(value) and value == trunc(value), do:
trunc(value)`. Result: 63/65 passed — 2 failures: the unit test
`"returns a float unchanged, including a whole-number float -- still is_float/1"` and
the platform round-trip test both caught it. Reverted; 65 passed again.

**5. `LuaNumberMarshalling.from_lua/1` — coerce an integer to a string.** Added
`def from_lua(value) when is_integer(value), do: Integer.to_string(value)`. Result:
64/65 passed — 1 failure: `"returns an integer unchanged"` caught it. Reverted; 65
passed again.

**Conclusion:** mutations 1, 2, 4, 5 are all caught (2 required adding a new test, as
detailed above); mutation 3 is a false lead (coincidentally-invisible against this
suite's specific float fixture values, not a genuine identity violation for those
values) and does not indicate a real gap given 4 and 5 independently confirm both
functions' identity guarantee is exercised for both integer and float subtypes in both
directions.
