call_service, emit_event (LUA-11 write half, LUA-12)

**Requirement:** REQ-160 (`docs/requirements.yaml`)
**Implementation:** `lib/letflow/engine/lua/platform.ex` (extended)
**Design:** `lib/letflow/design/req160-lua-host-api-write.md`

section below the existing REQ-159 divider)

This is a pre-implementation skeleton, written by CODE-DESIGNER (WF-02 Step 1), for

## Construction convention

Same as REQ-159's spec: tests needing a specific execution context call
`Letflow.Engine.Lua.Platform.install/3` directly against a fresh
`Letflow.Engine.Lua.Sandbox.new/0` VM, granting whichever capability the test needs via
`Letflow.Engine.Lua.Capabilities.new/1`.

## Planned test cases

### 1. `platform.write_variable` — stages without applying (AC1's own acceptance text)

- Calling `platform.write_variable("x", 1)` inside a script, then reading back
  `Letflow.Engine.Lua.Platform.take_staged_writes/0` from the *same* process the script
  ran in, returns `%{"x" => 1}` — proving the write reached the staging buffer.
- A `write_variable` call whose first argument is not a string is a no-op: the staged
  buffer is unaffected (still whatever it was before the call), and the call itself
  returns without raising.
- `write_variable` never calls `Letflow.Repo` — asserted the same way REQ-159's own
  "no `Repo` call attempted" property was asserted for `get_instance_state`'s forbidden
  arm (a telemetry-handler-based assertion, per that spec's own mutation-testing
  addendum, or an equivalent mechanism TEST-DESIGNER selects).

### 2. `platform.write_variable` — discarded on every failure arm (AC1)

Four sub-cases, each asserting the identical outcome — the staged-writes buffer, once
retrieved via a mechanism equivalent to `take_staged_writes/0`, never reflects a write
a failed script attempted, and (since `owned_modules` does not yet wire this buffer
into `Letflow.Engine.Lua.Executor`, design §2.5 OQ-1) each sub-case is proven at the
layer this requirement actually owns: the process that ran the failing script exits
(or its evaluation raises) without ever having its buffer read out by anything:

- **Raised script error.** A script calls `platform.write_variable("x", 1)` and then
  raises a Lua runtime error (e.g. calls a denied global, or an explicit script-level
  error). The evaluating call returns an error tuple; nothing in the test process ever
  observes `%{"x" => 1}` reaching any variable-state representation, because nothing
  ever calls `take_staged_writes/0` on that process's behalf following an error return.
- **REQ-154's instruction budget.** A script calls `write_variable` then enters a loop
  that exhausts a small, explicitly configured `:max_instructions` budget. Same
  assertion shape as above: the write was staged inside the process, the process
  returned an instruction-budget error, and the write is never observed anywhere else.
- **REQ-155's wall-clock kill.** A script calls `write_variable` then blocks (e.g. an
  infinite loop that does not trip the instruction budget within the configured
  wall-clock timeout). The supervising `Task` is killed via
  `Task.shutdown(task, :brutal_kill)`. Assert the write is never observed anywhere: the
  killed process's memory, including its process dictionary, is gone, and no other
  process ever read it before the kill (this is the design's own §2.2 proof, restated
  here as a concrete test rather than only an argument).
- **REQ-156's memory limit.** A script calls `write_variable` then attempts a large
  allocation under a small configured `:max_heap_words` limit, triggering the BEAM's
  own `max_heap_size` kill. Same assertion shape as the wall-clock case.

### 3. `platform.write_variable` — multiple writes accumulate, then apply atomically on success (AC2)

- A script calls `write_variable` three times with three distinct names, then completes
  successfully (no error, no kill). `take_staged_writes/0`, read from the same process
  immediately after the script's normal completion, returns a map containing all three
  key/value pairs — none missing, none stale.
- A script writes the same name twice with two different values, then completes
  successfully. `take_staged_writes/0` returns only the second (last) value for that
  name — proving "last write wins" (design §2.4), not both, not neither.
- **Atomicity, not merely eventual application.** Using `Letflow.Engine.VariableMerge.merge/3`
  directly against the staged-writes map `take_staged_writes/0` returned (current
  variables `%{}`, no validations), assert the single `merge/3` call's return is the
  whole `{:ok, new_variables, events}` tuple with all three keys present in
  `new_variables` — there is no intermediate call, no partial map, and no way for a
  test (or any other process) to observe a state with only one or two of the three keys
  applied, because `merge/3` is a single, non-yielding function call (design §2.6).

### 4. `platform.write_variable` — capability denial

- Against `Platform.install/3` called with an empty grant set, calling
  `platform.write_variable` raises a Lua error whose structured fields show `required`
  equal to `"variable:write"` — same three-field assertion style as every other gated
  function's denial test (REQ-157/159 precedent).

### 5. `platform.call_service` — round trip through a registered service (AC3, LUA-12's own text)

- Configure a test double implementing `Letflow.Engine.Lua.Platform.ServiceCaller`
  (via `Application.put_env(:letflow, :lua_platform_service_caller, <double module>)`)
  that returns `{:ok, %{"status" => "ok", "count" => 3}}` for a known `service_id`.
  Granting `"service:call:<that service_id>"`, calling
  `platform.call_service(service_id, {...})` from inside a script and reading the
  returned table's fields inside the script (e.g. via a second `platform.log` call
  echoing them, or returning them as the script's own result) shows the exact values
  the double returned — proving the response is both a real Lua table (LUA-12's own
  "MUST be returned as Lua table") and actually readable from the script, not merely
  returned as an opaque host value.
- The double receives the decoded, `from_lua/1`-converted payload the script passed —
  asserted by having the double itself assert on its received arguments (or by a
  test-only capturing double), proving the payload actually round-trips through the
  host, not merely that some table comes back.

### 6. `platform.call_service` — number-marshalling round trip (AC6)

- A double returns a response map containing one integer-valued and one
  whole-number-float-valued field. The script reads both back via `math.type` (mirrors
  REQ-159's own read-direction round-trip test, applied here to `call_service`'s
  response instead of `read_variable`'s value) and asserts `"integer"`/`"float"`
  respectively — proving `LuaNumberMarshalling.to_lua/1` runs on this call path.
- A script passes one integer-valued and one whole-number-float-valued argument as part
  of `call_service`'s payload; the double captures what it received and asserts the
  Elixir-side types are `integer()`/`float()` respectively (not collapsed) — proving
  `from_lua/1` runs on the write direction of this same call.

### 7. `platform.call_service` — service failure returns structured error, not a raise (AC4, part 1)

- Configure the double to return `{:error, :downstream_unavailable}` for a granted
  `service_id`. Calling `platform.call_service` from the script does **not** raise —
  the call returns normally, and the script observes a `nil` first value and a second
  value that is a table with a `reason` field derived from `:downstream_unavailable`.
  Assert explicitly that no `Lua.RuntimeException`/`Lua.CompilerException` propagates
  out of the evaluating call for this case.

### 8. `platform.call_service` — missing capability DOES raise (AC4, part 2)

- Against `Platform.install/3` called with a grant set that does **not** include
  `"service:call:<the id the script names>"` (either empty, or granting a
  *different* service's capability — proving the parameterisation is per-service, not
  all-or-nothing), calling `platform.call_service` raises a Lua error whose structured
  `required` field equals `"service:call:<the id the script names>"`. This test and
  test 7 above must be two distinct test cases in the same file, each asserting the
  opposite of what the other asserts (raises vs. returns), per REQ-160's explicit "both
  behaviours must be tested and must differ" text.

### 9. `platform.emit_event` — capability denial and successful emission (AC5)

- Against an empty grant set, calling `platform.emit_event` raises a Lua error whose
  structured `required` field equals `"event:emit"`.
- With `"event:emit"` granted and a populated execution context (`instance_id`,
  `prefix`, `actor_id` all set to real, fixture-created values under an explicit
  tenant prefix), and an `event_type` pre-registered in that tenant's
  `Letflow.EventStore.Registry` with a schema the test's payload satisfies, calling
  `platform.emit_event(event_type, payload, idempotency_key)` from a script returns
  Lua `true`, and a subsequent, independent read of the tenant's event stream (e.g.
  `Letflow.EventStore.read_global/1`, or a direct query against the `events` table
  under that prefix) shows exactly one row matching `event_type`/`instance_id`/
  `actor_id`/`idempotency_key` — proving the event is genuinely "observable by the
  host," not merely that the Lua call returned successfully.

### 10. `platform.emit_event` — no execution context / malformed arguments (design §5.3 steps 1–2)

- With `Platform.install/2` (empty execution context) and `"event:emit"` granted,
  calling `platform.emit_event` returns `nil` plus a table with `reason` equal to
  `"no_execution_context"` — no `Letflow.EventStore.append/2` call is attempted (an
  assertion mechanism equivalent to REQ-159's own Repo-call-avoidance test, applied to
  `EventStore.append/2` instead of `Repo.get/3`).
- With a populated execution context, calling `platform.emit_event` with a non-string
  `event_type` or a non-string `idempotency_key` returns `nil` plus a table with
  `reason` equal to `"invalid_arguments"` — no `EventStore.append/2` call attempted.

### 11. `platform.emit_event` — host-side append failure returns structured error, not a raise

- With a populated execution context and `"event:emit"` granted, calling
  `platform.emit_event` with an `event_type` that has no registered schema for that
  tenant returns `nil` plus a table whose `reason` reflects
  `Letflow.EventStore.append/2`'s own `:unknown_event_type` error — asserted not to
  raise, mirroring test 7's "service failure does not raise" shape for the third of
  this requirement's three write-path functions.

### 12. Tenant-prefix discipline (AC7)

- A grep-style or code-inspection-based assertion (mirroring `VariableMerge`'s own
  "grep-checkable" recipe convention) that no call site inside `write_variable`'s or
  `call_service`'s implementation ever references `Letflow.Repo` at all, and that
  `emit_event`'s one `Letflow.EventStore.append/2` call site always passes
  `prefix: execution_context.prefix` textually, never a value built from `event_type`,
  `payload`, or `idempotency_key`.
- Functionally: constructing two execution contexts that differ only in `prefix`
  (pointing at two distinct, real tenant schemas, each with the *same* `event_type`
  registered and satisfiable), and asserting `platform.emit_event` called under each
  context writes its event into the correspondingly different tenant's `events` table —
  never the other one — proving the prefix actually governs which schema receives the
  row, not merely that no crash occurs.

### 13. Number-marshalling module identity (AC6)

- `write_variable`'s staged value for an integer- and a whole-number-float-valued
  script argument, read back via `take_staged_writes/0`, are `is_integer/1`/`is_float/1`
  true respectively (not collapsed) — proving `LuaNumberMarshalling.from_lua/1` (the
  same module/function REQ-159 already created and REQ-160 reuses, per REQ-150 §2.1) is
  actually applied on this call path, not a second, independently-written conversion.

### 14. Compile/test gate (AC8)

- `mix compile --warnings-as-errors` passes with the REQ-160 changes applied.
- `mix test` passes, quoting the real pass count for `platform_test.exs`'s REQ-160
  section, at TEST-RUNNER's Step 4.

## Resolution of open items (TEST-DESIGNER, Step 3)

- **Test 2's four failure-arm sub-cases** are proven at the `Platform` layer, per
  design §2.5's own consequence paragraph, not by driving `Executor` directly: the
  structural guard "`platform.ex`'s source has zero call sites of `take_staged_writes()`
  other than its own `@spec`/`def` lines" (already present, ELIXIR-DEV's own
  self-verification test) proves `take_staged_writes/0` is **never** invoked from
  inside this module on ANY path — success, raised error, instruction-budget
  exhaustion, wall-clock kill, or memory-limit kill alike, since none of those paths is
  distinguished by this module's own code at all. This single structural assertion is
  therefore sufficient for every one of the four sub-cases uniformly (design §2.2's own
  proof: nothing escapes a non-normal-return path because nothing ever reads the buffer
  out on one). Driving the real `Executor`/REQ-155/156 kill mechanisms end-to-end is
  left to a future `Executor`-focused requirement (design OQ-1) once that module
  actually calls `take_staged_writes/0`.
- **Test 9/11/12's tenant fixture**: resolved by reusing `provisioned_tenant/0`,
  `seed_projection!/3`, and a new `register_event_type!/2` fixture that mirrors
  `event_store_test.exs`'s own `register_event_type!/2` convention (permissive
  `{"type" => "object"}` JSON schema) — see the REQ-160 section of
  `test/letflow/engine/lua/platform_test.exs`.

### Net result

- 3 real gaps found (mutations 4 and 6, plus mutation 4 covering both `call_service`
  and `emit_event`'s capability-gate-precedes-body property) — closed by 3 new tests:
  - `REQ-160: call_service -- missing capability raises...` → "a MISSING capability
    means the ServiceCaller spy is never invoked at all"
  - `REQ-160: emit_event -- capability denial...` → "a MISSING capability means
    EventStore.append/2 is never reached (Repo-query spy)"
  - `REQ-160: structural guard -- LuaNumberMarshalling call sites are genuinely
    present` → "every REQ-160 numeric-crossing call site routes through
    LuaNumberMarshalling.from_lua/1 or .to_lua/1 by name"
- 4 mutations were already caught by ELIXIR-DEV's own 82 tests (last-write-wins,
  clear-after-read, call_service never-raises, emit_event prefix discipline) — no
  action needed beyond confirming the catch.
- Final test file: `test/letflow/engine/lua/platform_test.exs`, **85 tests**, all
  passing against the real (unmutated) implementation.
