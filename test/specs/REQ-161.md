## Construction convention — this requirement needs a MONITORED PROCESS, not a bare `Lua.eval!/2` call

Unlike REQ-159/160's tests (which call `Lua.eval!/2` synchronously in the test's own
process, because none of those functions ever terminate the calling process), every
test in this spec that actually exercises `platform.fail`'s termination MUST run the
script inside a separately spawned, monitored process — `Task.async/1` +
`Task.yield/2`, or `spawn_monitor/1` directly — mirroring
`test/letflow/engine/lua/executor_test.exs`'s own REQ-155/156 harness pattern (design
§2.3, §4). Calling `platform.fail` from inside the TEST process's own synchronous
`Lua.eval!/2` call would terminate the test process itself (design §2.3's `exit/1`
semantics apply to whatever process is running the script, with no exception for a
test runner) — this is a correctness property to exploit for observation, not a bug
to work around by calling it differently.

Every test below spawns via `Task.async(fn -> ... end)` unless noted, and observes
the outcome via `Task.yield(task, timeout)` (returning `{:exit, reason}` on a
crashed task) or a direct `Process.monitor/1` + `assert_receive {:DOWN, ...}`, per
design §2.4/§4.

## Planned test cases

### 1. `pcall`-wrapped `platform.fail` still yields SCRIPT_FAILED and does not run to completion (AC1 — the central regression-catching test)

This is the one test decision 0014's LUA-15 restatement requires by name, and it must
fail if the uninterceptable mechanism (design §2, §3.2 step 3) is ever replaced by an
ordinary `raise`.

- A script does: calls `platform.fail("give up", {code = 1})` wrapped in `pcall`,
  and if the `pcall` call itself somehow returns (it must not), sets a marker
  variable and calls `platform.log("info", "reached past pcall")` to prove
  continuation would have been observable if it happened.
- Run inside a `Task.async/1`. `Task.yield(task, 1_000)` MUST return `{:exit,
  {:script_failed, %{reason: "give up", details: _}}}` — **not** `{:ok, _}` — and
  the task's process MUST be dead (`Process.alive?(task.pid) == false`).
- Assert the `platform.log("info", "reached past pcall")` call never happened — no
  log entry captured with that message (via whatever log-capture mechanism
  `platform_test.exs` already uses for `log` assertions elsewhere, e.g.
  `ExUnit.CaptureLog` or the REQ-159 log-capture convention already in the test
  file).
- **This test must be written so that reverting `do_fail/1`'s `exit/1` call (design
  §3.2 step 3) back to a `raise Lua.RuntimeException` (the prior stub, design §1.2)
  makes it fail** — with a plain raise, `Task.yield/2` would return `{:ok, _}`
  (the task completing normally after its own internal `pcall` caught the raise),
  the marker log WOULD appear, and the assertions above would not hold. This
  regression-sensitivity is itself part of what TEST-DESIGNER must verify before
  calling the test complete (e.g. by confirming this exact failure mode manually
  against a local revert, noted in the test file's own comments if TEST-DESIGNER
  chooses to).

### 2. Structured failure carries `reason`/`details`, readable by the host (AC2)

- A script calls `platform.fail("validation failed", {field = "email", code = 422})`
  with no `pcall` wrapper at all (the plain, unwrapped call — the common case).
  Run inside a `Task.async/1`; `Task.yield/2` returns `{:exit, {:script_failed,
  %{reason: "validation failed", details: details}}}` where `details` is the decoded,
  number-marshalled Elixir map `%{"field" => "email", "code" => 422}` (design §3.2
  step 2 — `Lua.decode!/2` + `LuaNumberMarshalling.from_lua/1` applied, matching
  `call_service`'s/`emit_event`'s established payload-decoding convention, REQ-160
  §4.4 step 2/§5.3 step 3).
- A script calls `platform.fail("no details")` with only one argument. Assert
  `details` is `nil` (design §3.2 step 2, missing-argument default).
- A script calls `platform.fail()` with zero arguments. Assert `reason` is the
  literal string `"script called platform.fail with no reason"` (design §3.2 step
  1's no-argument default) and `details` is `nil`.
- A script calls `platform.fail(42, "not a table")` — a non-binary `reason` and a
  non-table `details`. Assert `reason` renders via `inspect/1` (design §3.2 step 1)
  as `"42"`, and `details` is the plain string `"not a table"` unchanged (not
  decoded, since it is not a table reference).

### 3. SCRIPT_FAILED is pattern-match-distinguishable from a stand-in SCRIPT_ERROR shape (AC3)

REQ-162 (the real SCRIPT_ERROR requirement) does not exist yet, so this test uses a
**stand-in** shape for the "future" side of the comparison, matching design §3.3's own
comparison table — TEST-DESIGNER should annotate the stand-in clearly as
provisional/representative, not as REQ-162's actual final shape:

- A script that deliberately calls `platform.fail("boom", nil)`, run inside a
  `Task.async/1`, yields `{:exit, {:script_failed, %{reason: "boom", details:
  nil}}}`.
- A script that raises an ordinary uncaught Lua error (e.g. calls a sandboxed
  function without `pcall`, or does `error("uncaught bug")`), run the same way
  (inside `Task.async/1`, no `platform.fail` involved at all), yields `{:ok,
  {:error, %Lua.RuntimeException{}}}` from `Lua.eval!/2`'s own return — the task
  completes **normally** (design §3.3 row 2, "Observed via": a normal function
  return, not a process exit) with an `{:error, _}` value inside it, never an
  `{:exit, _}` from `Task.yield/2` at all.
- A single `case`/pattern-match block asserts: `{:script_failed, %{reason: _,
  details: _}}` matches the first outcome's exit reason; the SAME pattern does
  **not** match the second outcome (which isn't even an exit reason — it's a
  normally-returned `{:error, %Lua.RuntimeException{}}` term) or a bare `:killed`
  atom (from a third sub-case: a script that triggers REQ-155's wall-clock kill via
  an infinite loop with no `platform.fail` call, yielding a `:DOWN`/`{:exit, :killed}`
  reason with no `:script_failed` tag and no `reason`/`details` fields at all).
- Explicitly assert the two outcome shapes are NOT structurally identical: the
  `:script_failed` outcome is a 2-tuple with a map second element carrying
  `reason`/`details`; the crash outcome carries no such tuple at all (a
  `Lua.RuntimeException` struct with entirely different fields); the `:killed`
  outcome is a bare atom with no payload whatsoever. Three distinct shapes, one
  `case` statement, three distinct match results.

### 4. `platform.fail` is callable with an EMPTY capability set (AC4)

- Calling `Letflow.Engine.Lua.Platform.install/3` with
  `Letflow.Engine.Lua.Capabilities.new()` (the empty grant set — no capabilities
  granted at all) and running a script that calls `platform.fail("x", nil)` still
  yields `{:script_failed, %{reason: "x", details: nil}}` on `Task.yield/2` — the
  call is never denied, no `Lua.RuntimeException` about a missing capability is ever
  raised for this call. Mirrors REQ-157's own "a test that expects a gate on `now`
  or `fail` is reading the matrix wrong" text directly.
- Read `Letflow.Engine.Lua.Platform.capability_matrix/0` and assert the `:fail` row's
  `required` field is exactly `:none` (a structural assertion on the matrix data
  itself, not merely a behavioral one) — same style as REQ-157's own matrix-shape
  tests.

## Cross-cutting notes for TEST-DESIGNER

- **Do not test through `Executor.execute_with_manifest/2,3`** for the
  pattern-matchability assertions (tests 1 and 3) — design §4 establishes that
  `executor.ex`'s existing `handle_yield_result/3` stringifies every non-timeout
  exit reason (including `{:script_failed, _}`) into an opaque string via
  `format_exit_reason/1`/`inspect/1`, so the pattern-match distinction these tests
  need to prove is only observable at the raw `Task.yield/2`/`:DOWN` level, called
  directly against `Letflow.Engine.Lua.Sandbox`/`Letflow.Engine.Lua.Platform`, not
  through `Executor`. This mirrors REQ-160 §2.5/§9's own layering discipline
  (proving a property at the layer that actually owns it).
- Every `Task.async/1` used in this spec's tests must have its resulting task
  process confirmed dead (`Process.alive?/1` false, or an explicit `:DOWN`
  reception) wherever the test's point is that the script "does not run to
  completion" — a bare `Task.yield/2` result alone does not, by itself, prove the
  process actually terminated (it proves the *caller* observed a result, which is
  necessary but let TEST-DESIGNER add the liveness check explicitly per test 1's
  own AC1 wording, "does NOT run to completion").
- No test in this spec should assert on `format_exit_reason/1`'s specific string
  output — that function is owned by `executor.ex`, not this requirement, and
  design §4/OQ-2 explicitly leaves whether it should special-case `:script_failed`
  as future, undecided work.
