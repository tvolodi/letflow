# Test spec: REQ-162 — uncaught Lua runtime errors captured as structured SCRIPT_ERROR (LUA-16 restated)

**Requirement:** REQ-162 (`docs/requirements.yaml`)
**Implementation:** `lib/letflow/engine/lua/executor.ex` (extended — `run_script/3`'s
`rescue e in Lua.RuntimeException` clause gains a `:script_error` branch;
`handle_yield_result/3` gains one pass-through clause)
**Design:** `lib/letflow/design/req162-lua-script-error-capture.md`
**Test code:** `test/letflow/engine/lua/executor_test.exs` (extended, a new REQ-162
section) plus one test in `test/letflow/engine/lua/platform_test.exs` or a new
`test/letflow/engine/lua/script_error_test.exs` for the §4.2 capability-state test
(TEST-DESIGNER's call which file, per its own conventions) that must bypass
`Sandbox.new/1`'s hardcoded empty grant set — see case 6 below.

This is a pre-implementation skeleton, written by CODE-DESIGNER (WF-02 Step 1), for
TEST-DESIGNER (Step 3) to reconcile against the actual implementation, following the
convention REQ-159/160/161's own test specs used.

## Construction convention

Unlike REQ-161's tests, SCRIPT_ERROR is produced by a normal `{:error, _}` return
from `run_script/3` — the process does **not** exit. Every test below can call
`Letflow.Engine.Lua.Executor.execute_with_manifest/3` (or, for case 6, construct the
`Lua.t()` directly per design §4.2) synchronously in the test's own process; no
`Task.async`/monitor scaffolding is needed for this requirement specifically, unlike
REQ-161's.

## Planned test cases

### 1. An uncaught runtime error produces a structured SCRIPT_ERROR carrying a stack trace and capability state, both asserted individually (AC1)

- Run a script whose body is `local x = 1 // 0` (no `pcall`) through
  `execute_with_manifest/3` with a real `budget`/`timeout_ms`/`max_heap_words`.
- Assert the return is `{:error, {:script_error, script_error}}` where `script_error`
  is a map.
- Assert `script_error.stack_trace` is a non-empty list (design §3, §6.1) — assert
  it independently of the `capabilities` assertion below, per AC1's "both asserted
  individually" wording (two separate `assert` calls, not one combined pattern
  match that would pass even if one field were wrong-shaped but present).
- Assert `script_error.capabilities` is a list (empty, per §4.1's inherited wiring
  gap — assert it equals `[]` here specifically, and cite design §4.1 in a test
  comment so a future reader does not mistake this for a bug when case 6 below
  proves the field is correctly wired once a non-empty grant set is supplied).

### 2. Moduledoc states which restatement branch holds and the mechanism/citation; a test asserts the corresponding value (AC2)

- Not a runtime-assertable criterion on its own for the "moduledoc states X" half —
  TEST-DESIGNER/REVIEWER read `executor.ex`'s `## REQ-162` moduledoc section (design
  §13) directly and confirm it names branch (a), the
  `exception.original.state.instruction_count` mechanism, and cites REQ-148 §5/OQ-2(c)
  by section.
- The corresponding assertable half: run the `1 // 0` script from case 1 and assert
  `script_error.instruction_count` matches `{:consumed, n}` where `n` is a
  non-negative integer (design §2.2) — not `{:configured_budget, _}` — proving
  branch (a) fires for the exercised exception type in practice, not just in the
  moduledoc's prose claim.

### 3. Instruction count is never zero-filled or silently omitted (AC3)

- Reusing case 1/2's result: assert `script_error.instruction_count` is exactly a
  2-tuple with head `:consumed` or `:configured_budget` — assert the map's
  `instruction_count` key is present (`Map.has_key?/2`) and its value pattern-matches
  one of the two tags; assert directly that it is never a bare integer `0` and never
  a bare integer at all (`refute is_integer(script_error.instruction_count)`), which
  would be the exact zero-fill-shaped mistake design §2.3/§3 forbids.
- A second case forces branch (b): construct a `Lua.RuntimeException` wrapping a
  `%Lua.VM.InternalError{}` directly (bypassing `Lua.eval!/2` — `InternalError`
  structurally has no `:state` field, design §2.3) and call the SCRIPT_ERROR shaping
  function on it directly with a known `budget`; assert the result is exactly
  `{:configured_budget, budget}` — proving the fallback path, not just asserting its
  existence in prose.

### 4. The division-by-zero test uses a Lua-5.3-raising form, and the moduledoc records the substitution (AC4)

- The `1 // 0` script (case 1) IS this test — no separate case needed structurally,
  but assert additionally that `script_error.message` contains the substring
  `"divide by zero"` (the exact wrapped `Lua.VM.RuntimeError` message text, design
  §8, `executor.ex` line 3789's `value: "attempt to divide by zero"`), tying the
  test concretely to the specific raise site this design cites.
- A companion case: run `local x = 1 / 0` (float division, no `pcall`). Assert this
  does **NOT** raise at all — `execute_with_manifest/3` returns `{:ok, %{manifest_hash:
  _}}` with the script's `x` evaluating to `inf` internally (not independently
  observable through this function's return shape, so this case only needs to assert
  the call succeeds rather than erroring) — proving the literal LUA-16 criterion's
  assumed form does not fire in this runtime, motivating the substitution the
  moduledoc must record.
- TEST-DESIGNER/REVIEWER confirm `executor.ex`'s `## REQ-162` moduledoc section
  states the substitution and cites `1/0`'s non-raising behavior as the reason.

### 5. SCRIPT_ERROR is pattern-match-distinguishable from all 4 other real arms, one test (AC5)

Drive `execute_with_manifest/3` five separate times, once per arm, asserting each
result independently in the same test function:

1. A normal script (`return 1`) with a generous budget/timeout/no heap limit →
   `{:ok, %{manifest_hash: hash}}`, `hash` a binary.
2. A tight `max_instructions` budget against a `while true do end` loop with no
   `pcall` → `{:error, {:budget_exceeded, budget}}`.
3. A hanging script (e.g. a blocking `receive`-equivalent or a very long loop) with a
   short `timeout_ms` → `{:error, {:wallclock_timeout, timeout_ms}}` (REQ-155's
   existing test fixture/pattern, reused).
4. A memory-hungry script (e.g. `string.rep("x", <<large>>)`) with a small
   `max_heap_words` → `{:error, :memory_limit_exceeded}` (REQ-156's existing test
   fixture/pattern, reused).
5. The `1 // 0` script from case 1, generous budget/timeout/no heap limit →
   `{:error, {:script_error, %{} = script_error}}`.

Assert all five results in one test via a single `case`/`cond` per result (or five
explicit `assert match?/2` calls) so the five patterns are demonstrated genuinely
mutually exclusive, not just individually true. `{:script_failed, _}` is not
included in this same in-process test (per design §9 row 1, it is observed via a
process exit, not a return value of `execute_with_manifest/3`) — cite REQ-161's own
test spec case 1/3 for where that arm's distinguishability is actually exercised, and
note in a test comment that this is why SCRIPT_FAILED is the one arm proven
elsewhere, not a gap in this test.

### 6. Capability state is read from REQ-157's capability set, not re-derived (AC6)

Per design §4.2, this cannot be proven through `execute_with_manifest/3` today (its
sandbox is hardwired to the empty grant set via `Sandbox.new/1`). This test instead:

- Constructs a `Lua.t()` via `Lua.new(sandboxed: Letflow.Engine.Lua.Sandbox.deny_set()
  |> Enum.map(fn {path, _reason} -> path end))`, piped through
  `Letflow.Engine.Lua.Platform.install(lua, Letflow.Engine.Lua.Capabilities.new(["variable:read"]))`
  — an explicit **one-capability** grant set, bypassing `Sandbox.new/1`'s hardcoded
  1-arity `install/1` call (design §4.2).
- Runs `local x = 1 // 0` against that state via `Lua.eval!/2` directly, in a
  `try/rescue e in Lua.RuntimeException` block in the test itself.
- Calls the SCRIPT_ERROR shaping function directly (the private/public function
  `run_script/3`'s new branch delegates to — TEST-DESIGNER names it per the actual
  implementation) with `e` and the same `Capabilities.new(["variable:read"])` value.
- Asserts the resulting `script_error.capabilities` is exactly `["variable:read"]` —
  proving the shaping function reads the grant set it is given rather than
  re-deriving an empty or reconstructed list.

### 7. Stack trace excludes host filesystem paths and Elixir module internals (AC7)

- Reusing case 1's `script_error.stack_trace`: assert every frame's `source` value
  (when non-nil) does not contain `"/"` and does not start with `"Elixir."`; assert
  every frame's `name` value (when non-nil) does not start with `"Elixir."` or
  contain the literal substring `"Lua.VM."` (design §6.1, §6.3).
- A second case exercises the untyped/fallback branch (design §6.2): construct a
  `Lua.RuntimeException` wrapping a plain Elixir exception (e.g. `%RuntimeError{message:
  "boom"}`, not a `Lua.VM.*` struct) directly, call the shaping function on it, and
  assert `script_error.stack_trace == []` and `script_error.message` equals the
  fixed placeholder string (design §6.2) rather than containing `"boom"` or any
  Elixir-internal detail.
