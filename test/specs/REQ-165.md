# REQ-165 Test Spec: Adopt `wasmex` behind a mandatory process boundary, with a pinned Rust toolchain in CI

This is a prose skeleton for TEST-DESIGNER — no test code is written here (WF-02 Step 1
is design, not test authoring). See `lib/letflow/design/req165-wasmex-process-boundary.md`
for the full design these tests exercise: §1 (dependency/build), §2 (Rust toolchain
pin), §3 (handler module + trivial guest), §4 (process-boundary proof), §5 (hang
timeout), §7 (moduledoc content). Fixtures referenced below
(`priv/wasm_fixtures/req165_trivial.wat`, `priv/wasm_fixtures/req165_hang.wat`) are
specified verbatim in that design's §3.3/§5 and must be created exactly as given there
— they are not literal test code, they are WAT source data the tests load.

All tests target `Letflow.Engine.Wasm.PluginHandler`, dispatched exclusively through
`Letflow.Engine.PluginInterface.invoke/2,3` — no test calls
`Letflow.Engine.Wasm.PluginHandler.handle_node/1` directly, per that behaviour's own
moduledoc ("never call this directly").

---

## T1 — Trivial guest executes and returns `{:complete, map}`

**Design ref:** §3 (module structure), §3.2 (internal flow), §3.3 (trivial guest).

Build an `ExecutionContext` (whatever minimal field values the test's own context
builder needs; `node_config`/`variables` are not exercised by the trivial guest and may
be empty maps) pointed at the default (non-hang) guest, call
`PluginInterface.invoke(Letflow.Engine.Wasm.PluginHandler, context)`, and assert the
result matches `{:complete, %{"answer" => 42, "executed_in_pid" => _pid}}` — proving
both that the guest actually ran (the `"answer"` value the fixture's `answer` export
returns) and that the outcome conforms to `PluginInterface`'s existing `outcome()` type
with no new tag introduced.

## T2 — Guest invocation runs in a different process from the caller (AC4)

**Design ref:** §4 in full.

Capture `self()` as `test_pid` before calling `invoke/2`. Destructure the returned
`{:complete, %{"executed_in_pid" => handler_pid}}`. Assert `handler_pid != test_pid`.
Also assert `Process.alive?(test_pid)` immediately after, as a positive check that
nothing about the call harmed the calling process. This is the acceptance criterion's
own named technique ("comparing `self()` captured inside the handler against the test
process pid") and needs no `wasmex` internals.

## T3 — Hanging guest is terminated by the supervised-task timeout, surfaces as `{:error, reason}` (AC5)

**Design ref:** §5 in full.

Build an `ExecutionContext` pointed at the hang fixture (`req165_hang.wat`, an
unconditional-loop guest with no fuel bound). Call `PluginInterface.invoke(handler,
context, timeout_ms: 100)` — a short outer bound, deliberately shorter than
`wasmex`'s own default 5-second call-level timeout, so the assertion exercises
`PluginInterface`'s own `Task.yield/2` + `Task.shutdown(:brutal_kill)` mechanism, not
`wasmex`'s internal interrupt. Assert the result matches `{:error, reason}` and that
`reason` contains `"did not respond within 100ms"` (the exact string
`handle_yield_result/4`'s existing `nil` clause produces). Assert no exception or exit
propagates to the test process — satisfied structurally by the test being able to make
this assertion at all, immediately, with no `rescue`/`catch` wrapping the call.

## T4 — `mix.exs` includes `wasmex`, and the native build actually succeeds (AC1)

**Design ref:** §0, §1.

Not a `mix test` case — a build-verification step ELIXIR-DEV runs and quotes real
output for, per the requirement's own instruction ("Run `mix deps.get` and `mix
compile` and quote the real output"). Must be run with `WASMEX_BUILD=true` set (per
§0/§1's finding that `wasmex` uses `rustler_precompiled` and could otherwise satisfy a
bare `mix compile` via a downloaded precompiled artifact without ever invoking
`cargo`/`rustc`). The quoted output must show an actual native compilation step (a
`cargo build`/`Compiling wasmex` style line), not merely dependency resolution.

## T5 — Rust toolchain pin is honoured in CI (AC2)

**Design ref:** §2 in full.

Not a `mix test` case — verified by (a) the `.tool-versions` diff adding the `rust
1.97.1` line, (b) the `.github/workflows/ci.yml` diff adding the Rust-setup step that
reads that pin via a shell step feeding `dtolnay/rust-toolchain@stable`'s `toolchain:`
input, plus `WASMEX_BUILD: true` on the backend-gate step, and (c) a real CI run
(quoted, not asserted) showing the Rust setup step executing and the backend gate step
compiling `wasmex` natively.

Optionally, if ELIXIR-DEV extends `mix letflow.check_toolchain` per the design's §2
(adding `"rust"` to `@recognised_tools`): a unit test on that task exercising the new
row analogous to the shipped Elixir/OTP row tests (a `rust` line present and matching →
`OK`; a `rust` line present and mismatched → the drift warning block; `rustc` not
found on `PATH` → the new not-found failure mode, never raising). This task remains
advisory — no exit-code assertion should ever expect it to fail the build.

## T6 — `plugin_interface.ex` is unmodified (AC6)

**Design ref:** §6.

Not a `mix test` case — a `git diff --stat` check scoped to this requirement's own
commit range against `lib/letflow/engine/plugin_interface.ex`, expected to produce no
output, exactly as `req163`/`req164`'s own out-of-scope-path confirmations did.

## T7 — Moduledoc restates WASM-01's mechanism clause and states its acceptance criterion is met (AC7)

**Design ref:** §7.1.

A `moduledoc =~ ...` style content test against
`Letflow.Engine.Wasm.PluginHandler`'s compiled moduledoc, asserting it names: Rust NIF
(not the C API), a runtime-loaded shared library (not a statically linked platform
binary), and a statement that WASM-01's own acceptance criterion ("no external Wasm
runtime dependency at deploy time") is met as literally worded. Plus a second,
separate test/deployment check (mechanics an implementation decision, per the design's
§9 OQ-D1) asserting no external Wasm runtime process or dependency is required — e.g.
introspecting the loaded NIF module, or asserting no external `wasmtime`/`wasmer`
binary/service is configured.

## T8 — Moduledoc discloses the residual native-crash risk (AC8)

**Design ref:** §7.2.

A `moduledoc =~ ...` style content test, the same technique
`test/letflow/engine/lua/executor_test.exs:506`'s AC-5 test already uses for an
analogous disclosure, asserting the moduledoc states: a Wasmtime/NIF-layer crash can
take down the entire BEAM node, no supervisor recovers it, and the process boundary
bounds hangs and guest traps but not native crashes — in the same disclosed-and-
uncovered terms `Letflow.Engine.PluginInterface`'s own moduledoc already uses.

## T9 — `mix test` and `mix compile --warnings-as-errors` both pass (AC9)

Not a new test — the existing full-suite/compile-gate obligation every requirement
carries, run and quoted for real by ELIXIR-DEV/TEST-RUNNER after T1-T8 are implemented.
