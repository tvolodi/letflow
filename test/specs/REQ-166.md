# REQ-166 Test Spec: WASM module ABI validation and rejection at registration (WASM-02)

This is a prose skeleton for TEST-DESIGNER — no test code is written here (WF-02 Step 1
is design, not test authoring). See
`lib/letflow/design/req166-wasm-module-abi-validation.md` for the full design these
tests exercise: §1 (verified `wasmex` introspection API), §3 (entry point/types), §4
(never-invocable proof), §5 (algorithm + required-export table), §6 (traceability).

All tests target `Letflow.Engine.Wasm.ModuleRegistry.register/1` directly — this is a
registration-time entry point, not something dispatched through
`Letflow.Engine.PluginInterface.invoke/2,3` (that dispatches invocation, a separate
concern per the design's §2.1).

Fixtures: each test compiles its own WAT source inline (a short string literal per
case, per the design §5.2's table) rather than reading a shared `.wat` file from
`priv/wasm_fixtures/` — unlike REQ-165's trivial/hang guests, each ABI-validation case
needs a distinct, deliberately-malformed export section, so one fixture per test
(inline WAT text passed straight to `register/1`, which itself calls
`Wasmex.Module.compile/2` — no `File.read!/1` needed) keeps each case self-contained and
easy to read next to its assertion.

---

## T1 — A module missing `execute` is rejected with a structured error naming `execute` (AC1)

**Design ref:** §5.1 stage 1 steps 2–5, §3 `registration_error()`/`export_defect()`.

Compile (inline WAT, via `register/1`) a module that exports `init`, `deinit`,
`get_capabilities`, `alloc`, and `memory` with the exact required signatures (§5.2
table) but omits `execute` entirely. Assert `register/1` returns
`{:error, {:invalid_abi, defects}}` where `defects` contains `{:missing, "execute"}`
and no other defect (this fixture is conforming in every other respect, so this is also
an implicit check that a correct export isn't mis-flagged).

## T2 — A module missing EACH of the other required exports is likewise rejected (AC2)

**Design ref:** §5.2 (full required-export table), §5.1 step 5 (per-export, not
stop-on-first).

One test case per remaining required export — `init`, `deinit`, `get_capabilities`,
`alloc`, `memory` — each built the same way as T1 (conforming in every export except
the one under test) and each asserted to produce `{:error, {:invalid_abi, defects}}`
with `defects` containing exactly `{:missing, <that export's name>}` (or, for `memory`,
also accepting `{:wrong_kind, "memory", :memory, _}` as the design allows if a fixture
substitutes a non-memory export named `"memory"` instead of omitting it — pick one
shape per case and document which). A validator that only checks `execute` (the design's
own stated risk, per the requirement's acceptance-criteria wording) must fail at least
one of these five cases.

Also include one signature-mismatch case distinct from a missing-export case (the
design's `{:wrong_signature, ...}` variant): a module exporting `execute` with
`(param i32) -> i32` (wrong arity) instead of `(param i32 i32) -> i32`, asserting
`defects` contains `{:wrong_signature, "execute", expected: {[:i32, :i32], [:i32]},
actual: {[:i32], [:i32]}}` — proving the validator checks signatures, not just names
(the design's own §1.3 finding that a present-but-wrong-shape export is a distinct,
detectable case from an absent one).

## T3 — Rejection happens at registration, never at invocation: a non-conforming module is never invocable (AC3)

**Design ref:** §2.1, §4 (re-derived structural proof, two-stage), §3.1 (`RegisteredModule`
opacity + start-then-stop decision).

**Note on the design's rework:** the design's `register/1` DOES call
`Wasmex.start_link/1` (as stage 2, §2.2/§5.1) — a prior version of both the design and
this spec assumed the opposite and asserted a grep-based "never calls `start_link/1`"
check. That check is no longer valid and must not be reintroduced; the "never invocable"
property is now proven by the opaque-type/single-constructor argument below (assertion
2), not by "the instantiation function is never called."

Assertions:

1. Register a non-conforming module that fails stage 1 (reuse T1's fixture, missing
   `execute`). Assert the return is `{:error, {:invalid_abi, _defects}}` and that no
   `Wasmex.Module.t()`/`registered_module()` value is observable anywhere in the
   result — there is no field of the error tuple a caller could extract and hand to
   `Wasmex.start_link/1`. Also assert (e.g. via a test-local counter/mock, or simply by
   the absence of any process crash/log line the instantiation-attempt task would leave)
   that stage 2 never runs for this fixture — a stage-1 failure returns before any
   instantiation attempt (§5.1 stage 1 step 5).
2. Register a module that passes stage 1 but fails stage 2 (a module with a real,
   unresolved `wasi_snapshot_preview1`/`path_open` import per req163 §4's named surface,
   otherwise exporting everything stage 1 requires). Assert the return is
   `{:error, {:instantiation_failed, defect}}` where `defect` is either
   `{:unresolved_import, "wasi_snapshot_preview1", "path_open"}` (the parsed shape, per
   §5.1 stage 2 step 7) or, if the exact message-parse doesn't match, the
   `{:crashed, _}` fallback — and, either way, that no `registered_module()` value is
   observable in the result. This is the test that exercises req163 §4's instantiation-
   based rejection directly, and the fixture REQ-167's own test can reuse per the
   design's §7 open-question note.
3. A structural/type-level check rather than a runtime one: confirm (by reading
   `lib/letflow/engine/wasm/module_registry.ex`'s compiled source, or a
   `mix compile --warnings-as-errors` run) that `RegisteredModule` is declared `@opaque`
   and that `register/1` is the only function in the module constructing
   `%RegisteredModule{}` — i.e. the rejection path provably cannot produce a value a
   caller could route to invocation, not merely "doesn't in this test run." (Grepping
   for the literal struct-construction syntax `%RegisteredModule{` and asserting it
   appears exactly once in `module_registry.ex`, inside `register/1`'s success branch,
   is an acceptable substitute if the project's tooling has no readier assertion for
   "only constructed in one place.")

## T4 — A conforming module registers successfully and is then invocable (AC4)

**Design ref:** §3 `register/1`'s `{:ok, registered_module()}` branch, §3.1.

Compile (inline WAT) a module exporting all five required functions with exact
required signatures plus `memory`, matching req163 §3.1/§3.2 exactly (this can be the
same fixture shape T1 built for its "conforming baseline," extended with a real
`execute` export this time). Assert `register/1` returns `{:ok, %RegisteredModule{}}`
(match loosely on the opaque struct's tag, not its internal fields, since the design
marks `registered_module()` `@opaque`). Then prove "invocable": pass the registered
module's underlying compiled module/bytes to `Wasmex.start_link/1` directly in the test
(this test is allowed to reach into the struct for this one assertion even though
production code may not, per Elixir's `@opaque` being a Dialyzer-level discipline, not
a runtime access control) and assert `{:ok, pid}` — i.e. the same bytes that failed in
T1–T3's variants succeed here, and successful registration is not merely "no error" but
"a Wasmtime instance can actually be started from what was returned."

## T5 — Moduledoc names the export contract and cites REQ-163 (AC5)

**Design ref:** §2.3.

Not a `mix test` case — a doc-content check: read
`Letflow.Engine.Wasm.ModuleRegistry`'s `@moduledoc` (via `Code.fetch_docs/1` or a direct
source read) and assert it names all five required exports (`init`, `execute`,
`deinit`, `get_capabilities`, `alloc`), names `memory`, states the two-stage gate
(static check, then real instantiation attempt), and contains a citation to both
`req163-wasm-abi-choice.md` §3.1/§3.2 (export contract) and §4 (instantiation-failure
rejection), per the design's §2.3 content list.

## T6 — `mix test` and `mix compile --warnings-as-errors` both pass (AC6)

**Design ref:** §6 row 6.

Not a design-level test case — an ELIXIR-DEV/CI obligation: run both commands and quote
real output. `--warnings-as-errors` is specifically relevant here because the design's
§4 "never invocable" proof leans on `RegisteredModule` being `@opaque`; a build that
silently accepted an opacity violation elsewhere in `lib/letflow/` would undermine that
proof, so this AC is not merely "tests pass" but "the opacity discipline itself
compiles clean."
