# REQ-167 Test Spec: WASM import whitelist derived from the manifest, and filesystem access denied by default (WASM-06, WASM-07 restated)

This is a prose skeleton for TEST-DESIGNER — no test code is written here (WF-02 Step 1
is design, not test authoring). See
`lib/letflow/design/req167-wasm-import-whitelist.md` for the full design these tests
exercise: §1 (verified `wasmex` `imports:` API + live crash-shape probes), §3
(entry-point types), §5 (algorithm), §6 (placeholder registry), §7 (WASM-07 moduledoc
content), §9 (traceability).

All tests target `Letflow.Engine.Wasm.CapabilityGate.build_import_table/1` and
`.start_instance/2` directly — this is a standalone mechanism, not dispatched through
`Letflow.Engine.PluginInterface.invoke/2,3` or gated behind
`Letflow.Engine.Wasm.ModuleRegistry.register/1` (design §0's decoupling decision — a
future dispatch-integration requirement wires the three together).

Fixtures: each test compiles its own WAT source inline, the same convention
`test/specs/REQ-166.md` establishes — one short WAT string literal per case, passed
straight to `start_instance/2` (which itself calls `Wasmex.Module`/`Wasmex.start_link`
internally; no `File.read!/1` needed). The two registry entries this design defines
(design §6) are `"var:read"` → `"env"`/`"read_variable"` and `"service:call"` →
`"env"`/`"platform_call_service"`, both `(i32,i32)->i32` (`(i32)->i32` for
`read_variable`, per §6's table) — tests should build manifests as literal
`%{capabilities: [...]}` maps rather than a shared fixture module.

## T1 — A module declaring only `var:read` and importing `platform_call_service` FAILS TO INSTANTIATE (AC1)

**Design ref:** §5.2 step 3, §1.2 probe 1 (live-verified crash shape), §6 (registry).

Build `manifest = %{capabilities: ["var:read"]}`. Compile (inline WAT) a module that
imports `"env"`/`"platform_call_service"` `(i32,i32)->i32` (the exact signature §6's
table gives it) and otherwise contains no other imports. Call
`CapabilityGate.start_instance(bytes, manifest)`. Assert the return is
`{:error, {:instantiation_denied, {:unresolved_import, "env", "platform_call_service"}}}`
(or, if the live crash-message parse doesn't match exactly as it did in this session's
live probe, the `{:crashed, _}` fallback — assert whichever the actual implementation
produces, but assert it is a **structured** error, never a bare string or an uncaught
exception/exit reaching the test process). Also assert the test process itself survives
(no linked `:EXIT` propagates) — the same containment property
`req166-wasm-module-abi-validation.md`'s T3/AC5-equivalent test already establishes for
`ModuleRegistry.register/1`; confirm the calling test process is a non-trapping caller
(`Process.info(self(), :trap_exit) == {:trap_exit, false}`) immediately before the call,
mirroring REQ-166's own mutation-pass fix (test/specs/REQ-166.md's "AC5" entry) so this
containment claim rests on a caller shape matching production.

## T2 — The import table is built from the manifest as a whitelist: an ungranted host function is absent, asserted by inspecting the table (AC2)

**Design ref:** §1.3 (why inspection targets the built map, not a live instance), §5.1,
§5.2 step 4.

This is a **pure function** test — no `Wasmex` call, no instantiation.

1. `manifest = %{capabilities: ["var:read"]}`. Call
   `CapabilityGate.build_import_table(manifest)`. Assert the returned map's `"env"`
   namespace (if present at all) does **not** have a `"platform_call_service"` key —
   `refute Map.has_key?(Map.get(table, "env", %{}), "platform_call_service")`. Assert it
   **does** have a `"read_variable"` key.
2. Symmetric case: `manifest = %{capabilities: ["service:call"]}`. Assert
   `"platform_call_service"` **is** present and `"read_variable"` is **not**.
3. `manifest = %{capabilities: []}`. Assert the returned table has neither key (and, per
   design §5.1 step 3, is `%{}` or namespace-empty — assert whichever exact empty shape
   the implementation returns, documented in a comment since no AC fixes it beyond "the
   host function is absent").
4. `manifest = %{capabilities: ["var:read", "service:call"]}`. Assert **both** keys are
   present — proves the filter is additive per-capability, not exclusive/single-choice.

## T3 — A module attempting filesystem access under the core-module ABI is rejected, using REQ-163's named surface (AC3)

**Design ref:** §5.2 step 5, §1.2 probe 4, §7 point 2.

Compile (inline WAT) a module importing `"wasi_snapshot_preview1"`/`"path_open"` with
the real 9-parameter/1-result WASI Preview 1 signature `req163-wasm-abi-choice.md` §4
gives: `(param i32 i32 i32 i32 i32 i64 i64 i32 i32) (result i32)`. Call
`CapabilityGate.start_instance(bytes, manifest)` for **at least two** manifests: (a)
`%{capabilities: []}` (nothing granted) and (b) `%{capabilities: ["var:read",
"service:call"]}` (everything this registry can grant, granted) — assert **both** return
`{:error, {:instantiation_denied, {:unresolved_import, "wasi_snapshot_preview1",
"path_open"}}}` (or the `{:crashed, _}` fallback per T1's note), proving denial is
unconditional on manifest content, not merely true for an empty one. Also assert the
literal string `"wasi:filesystem/types"` (WASM-07's own literal, unreplaced acceptance
text) never appears anywhere in the fixture, the manifest, or the assertion — a comment
in the test should say why, citing this design's §7 point 2, so a future reader does not
"fix" the test to use the literal name.

## T4 — Moduledoc restates WASM-07 correctly (AC4, AC5, AC6)

**Design ref:** §7 (all three points).

Not a `mix test` case against `start_instance/2`'s behavior — a doc-content check: read
`Letflow.Engine.Wasm.CapabilityGate`'s `@moduledoc` (via `Code.fetch_docs/1` or a direct
source read) and assert it states, at minimum:

1. That `wasi:filesystem/types` is NOT the surface tested (AC4's first clause).
2. What IS tested instead, naming `wasi_snapshot_preview1`/`path_open` (or the namespace
   generally) (AC4's second clause).
3. Why asserting the literal component-model name under a core-module runtime would be a
   false pass — the "rejected as unrecognized regardless of filesystem policy" reasoning
   (AC4's third clause).
4. That this module restates WASM-07: intent implemented, concrete name ABI-dependent,
   replaced per REQ-163 (AC5).
5. Whether an explicit filesystem-grant path exists today — asserting the moduledoc says
   **no**, plainly, per this design's §7 point 3 (AC6). A moduledoc that merely fails to
   mention a grant path (silence) does not satisfy this AC — TEST-DESIGNER should assert
   on the presence of an explicit "no such path exists" statement, not merely the absence
   of a false claim.

## T5 — The whitelist is provably exhaustive: a module importing anything not in `@known_imports` at all (not just the two known capability-gated names) is denied regardless of manifest

**Design ref:** §4 (structural "never granted beyond the whitelist" argument), §5.1 step 3.

A module importing a host function with a name the registry has never heard of at all
(e.g. `"env"`/`"totally_unregistered_function"`, distinct from both `read_variable` and
`platform_call_service`) is denied identically to T1/T3, for **every** manifest,
including the maximally-permissive `%{capabilities: ["var:read", "service:call"]}"` one —
because §5.1's construction can never produce a table entry for a descriptor that does
not exist in `@known_imports` regardless of what the manifest grants. This is the test
that most directly proves §4's structural argument (not merely "the two named cases from
the acceptance criteria happen to be denied") — a validator that special-cased only
`platform_call_service`/`path_open` by name (rather than implementing the generic
whitelist mechanism) would pass T1 and T3 but fail this test.

## Notes for TEST-DESIGNER on fixture authoring

- Every fixture WAT module needs at minimum a `(memory (export "memory") 1)` export to
  be a well-formed core module per `req163-wasm-abi-choice.md` §3.2, even though this
  design's tests do not exercise the plugin ABI's four named exports at all (this
  requirement's tests are about imports, not exports) — omit `init`/`execute`/`deinit`/
  `get_capabilities`/`alloc` entirely; `CapabilityGate.start_instance/2` does not require
  or check for them (that is `ModuleRegistry`'s job, not exercised here).
- The `Task.Supervisor.async_nolink/2` + `Task.yield/2` boundary
  (`Letflow.Engine.Wasm.CapabilityGateTaskSupervisor`) must already be started under
  `Letflow.Application`'s supervision tree for any of these tests to run without a
  separate ad hoc supervisor — confirm this in the test setup rather than assuming it,
  the same way REQ-166's suite depends on `ModuleRegistryTaskSupervisor` already being
  live.
- Callbacks for `read_variable`/`platform_call_service` in test fixtures' expected
  `import_table()` values should be trivial stubs (e.g. one that always returns a
  constant `:i32`) — no test in this spec ever calls either function through a
  successfully-instantiated instance, since presence/absence and instantiation
  success/failure are both observable without invoking the granted function.
