# REQ-168 Test Spec: WASM linear memory isolation and host-side validation of every guest pointer/length pair (WASM-08)

This is a prose skeleton for TEST-DESIGNER — no test code is written here (WF-02 Step 1
is design, not test authoring). See
`lib/letflow/design/req168-wasm-memory-isolation.md` for the full design these tests
exercise: §1 (live-verified `wasmex` `Wasmex.Memory` behavior, including the
node-crash finding), §2 (bounds-check algorithm), §4 (`MemoryGuard` public contract),
§5 (this design's own test strategy, which this spec expands into concrete cases), §6
(moduledoc content), §8 (traceability).

All tests target `Letflow.Engine.Wasm.MemoryGuard.check_bounds/3`,
`.read/4`, and `.write/4` directly — no REQ-171/172 host function exists yet
(design §5's stated reason), so there is no real host-function call path to test
through. `check_bounds/3` needs no `Wasmex` handle at all (pure arithmetic); `read/4`/
`write/4` need a real `Wasmex.Memory.t()` handle obtained from
`priv/wasm_fixtures/req168_memory.wat` (design §5.1) via `Wasmex.start_link/1` →
`Wasmex.store/1` → `Wasmex.memory/1`, the same three-call pattern this design's own
live-verification probes used.

**⚠️ Mandatory safety constraint, restated from design §5.4 — read before writing any
test in this file.** Never call `MemoryGuard.read/4`, `MemoryGuard.write/4`, or any
`Wasmex.Memory` function directly with an `offset`/`length` value at or above
approximately `2^40`. Design §1.4 live-reproduced a real `SIGABRT` (process exit code
134, "Aborted (core dumped)") at that magnitude against this exact dependency version —
a test that exercises this path for real, rather than against `check_bounds/3`'s pure
arithmetic (safe at any magnitude), would abort the test runner's own OS process
mid-suite. Every large-magnitude case below (T3's third case) targets `check_bounds/3`
only.

## T1 — `check_bounds/3` accepts every valid case (baseline, not itself an AC but needed so T2/T3's rejections are meaningful)

**Design ref:** §2 steps 3-4 (the exact boundary conditions), §5.2's table.

1. Fully in-bounds: `offset=0, length=10, memory_size=65536` → `:ok`.
2. Ends exactly at the boundary: `offset=65526, length=10, memory_size=65536` → `:ok`.
3. Zero-length read exactly at the end-of-memory boundary: `offset=65536, length=0,
   memory_size=65536` → `:ok` (design §2 step 3's explicit note that `offset ==
   memory_size` is not itself rejected when `length == 0`).

## T2 — `check_bounds/3` rejects each of the three named malformed-input shapes (AC3 — WASM-08's own acceptance criterion)

**Design ref:** §2 in full (the exact algorithm), §1.3 (why this can't rely on
`wasmex`'s own check alone for magnitude reasons even though `wasmex` also rejects
these specific "moderate" cases cleanly).

1. **Offset beyond memory size.** `offset=65537, length=1, memory_size=65536` →
   `{:error, {:offset_out_of_range, 65537, 65536}}`.
2. **Length running past the memory end.** `offset=65530, length=100,
   memory_size=65536` → `{:error, {:length_exceeds_memory, 65530, 100, 65536}}`.
3. **An offset+length pair that would overflow a fixed-width check** — the case design
   §1.4 found `wasmex`'s own Rust-side allocation path does NOT handle safely at this
   magnitude (a real `SIGABRT`, live-reproduced). Per the safety constraint above, this
   test calls **`check_bounds/3` only**, never `read/4`/`write/4`, never any
   `Wasmex.Memory` function: `offset=9_223_372_036_854_775_808,
   length=9_223_372_036_854_775_808, memory_size=65536` →
   `{:error, {:length_exceeds_memory, 9_223_372_036_854_775_808,
   9_223_372_036_854_775_808, 65536}}`, asserting the returned tuple's numeric fields
   are the exact input values (proving Elixir's bignum arithmetic computed
   `offset + length` exactly, with no wraparound, at a magnitude that would wrap or
   abort in a fixed-width-integer implementation).
4. **Defensive: negative offset.** `offset=-1, length=1, memory_size=65536` →
   `{:error, {:invalid_argument, :offset, -1}}`.
5. **Defensive: non-integer length.** `offset=0, length="10", memory_size=65536` →
   `{:error, {:invalid_argument, :length, "10"}}`.

## T3 — Live: `read/4`/`write/4` against a real `Wasmex.Memory` handle, malformed pointer yields a structured error, BEAM node/process stay up (AC2 — WASM-08's own acceptance criterion, in its literal "host crash" framing)

**Design ref:** §4 (`read/4`/`write/4` specs), §1.3 (confirms these specific live calls
are safe to make — all within the range `wasmex`'s own NIF already bounds-checks
cleanly), §1.6 (why `read/4`/`write/4` must pattern-match `{:error, _}` regardless of
the callee's own `@spec`).

Setup: start a real instance from `priv/wasm_fixtures/req168_memory.wat`, obtain
`store`/`memory` via `Wasmex.store/1`/`Wasmex.memory/1`.

1. **Valid round-trip (sanity).** `write(store, memory, 0, "hi")` → `:ok`;
   `read(store, memory, 0, 2)` → `{:ok, "hi"}`.
2. **Malformed pointer via `read/4`, offset beyond size.** Fetch the real size first
   (`Wasmex.Memory.size/2`), then call `read(store, memory, size + 1000, 10)`. Assert
   the return is `{:error, {:invalid_pointer, {:offset_out_of_range, _, _}}}`. Assert
   `Process.alive?(self())` immediately after (the calling test process received no
   exit signal). Assert `Process.whereis(Letflow.Engine.PluginTaskSupervisor) |>
   Process.alive?/1` (the application's supervision tree, an available proxy for "the
   node stayed up," is untouched).
3. **Length running past memory end via `read/4`.** `read(store, memory, size - 1,
   1000)` → `{:error, {:invalid_pointer, {:length_exceeds_memory, _, _, _}}}`. Same
   process/supervisor liveness assertions as case 2.
4. **Malformed pointer via `write/4`, offset beyond size.** `write(store, memory,
   size + 1, "x")` → `{:error, {:invalid_pointer, {:offset_out_of_range, _, _}}}`. Same
   liveness assertions.
5. **Non-trapping caller precondition** (mirrors `req166`/`req167`'s identical
   mutation-tested assertion): confirm `Process.info(self(), :trap_exit) ==
   {:trap_exit, false}` immediately before each of cases 2-4, so the "no exit signal
   propagated" claim rests on a caller shape matching production, not an
   artificially-hardened test process.

## T4 — Per-instance memory isolation (AC4)

**Design ref:** §1.5 (live-verified finding this test restates as a permanent
regression test).

Start two `Wasmex` instances from the **identical** `req168_memory.wat` bytes; obtain
each instance's own `store`/`memory` handle independently. `write(store_a, mem_a, 0,
<<99>>)`. Assert `read(store_b, mem_b, 0, 1) == {:ok, <<0>>}` (the second, untouched
instance reads back a zero byte — no leak). Assert `read(store_a, mem_a, 0, 1) ==
{:ok, <<99>>}` (the first instance still sees its own write, confirming the isolation
assertion isn't trivially true because neither instance's memory is readable at all).

## T5 — Moduledoc content (AC5)

**Design ref:** §6 (required moduledoc prose, citing
`req165-wasmex-process-boundary.md` §7.2 verbatim).

Not a behavioral test — a doc-content check, mirroring
`test/letflow/engine/lua/executor_test.exs:506`'s and
`req165-wasmex-process-boundary.md` §7.2's own `moduledoc =~ ...` technique. Read
`Letflow.Engine.Wasm.MemoryGuard`'s `@moduledoc` (via `Code.fetch_docs/1`) and assert it
states, at minimum:

1. That this validation bounds host-side dereferences only (what it prevents: the host

   real current memory).
2. That it does **NOT** bound a fault inside Wasmtime's own native code/runtime itself
   — the residual class `req165-wasmex-process-boundary.md` §7.2 already discloses.
   Assert the moduledoc's wording is recognizably the same disclosure (e.g. contains
   "does NOT bound a fault" and "Wasmtime" and "native code" — TEST-DESIGNER should pick
   the exact substring match against ELIXIR-DEV's actual final prose, not this spec's
   paraphrase).

## Notes for TEST-DESIGNER on fixture authoring

- `priv/wasm_fixtures/req168_memory.wat` (design §5.1) needs only a `(memory (export
  "memory") 1)` export and one placeholder function export — it does not need to
  satisfy the plugin ABI's five required exports (`init`/`execute`/`deinit`/
  `get_capabilities`/`alloc`); `ModuleRegistry.register/1`'s export-shape check is not
  exercised by this requirement's tests at all.
- `Letflow.Engine.PluginTaskSupervisor` must already be running under
  `Letflow.Application`'s supervision tree for T3's liveness assertions to check
  something real — confirm this in test setup rather than assuming it, matching
  `req167`'s identical note for `CapabilityGateTaskSupervisor`.
- No new `Task.Supervisor` is introduced by this design (design §3) — `MemoryGuard`'s
  own calls are made directly, not wrapped in a monitored task, because §1.3 already
  confirms every value this design's own `check_bounds/3` lets through falls inside the
  range `wasmex`'s NIF handles cleanly. Do not add a `Task.Supervisor.async_nolink/2`
  wrapper inside `MemoryGuard` itself — doing so would silently contradict this design's
  own stated reasoning without a design amendment.
- Re-running this spec's T2 case 3 and T3 cases against the actual installed `wasmex`
  dependency is safe (T2 case 3 never calls `wasmex` at all; T3's magnitudes are all
  "moderate," confirmed live-safe in design §1.3) — nothing in this spec requires
  re-running the dangerous `2^40`-scale probe scripts under `scratch/` as part of the
  shipped test suite; those scripts exist only as this design's own verification record.
