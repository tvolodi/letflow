# REQ-169 Test Spec: WASM fuel budget and linear-memory cap per invocation (WASM-09, WASM-10)

This is a prose skeleton for TEST-DESIGNER — no test code is written here (WF-02 Step 1
is design, not test authoring). See
`lib/letflow/design/req169-wasm-fuel-and-memory-cap.md` for the full design these tests
exercise: §1 (live-verified `wasmex`/Wasmtime fuel and `StoreLimits` behavior,
including the memory-cap-does-not-trap divergence), §2 (what the finding changes about
the design), §4 (`Letflow.Engine.Wasm.ResourceLimits`'s public contract), §5 (this
design's own test strategy, which this spec expands into concrete cases), §6 (required
moduledoc content), §7 (the divergence statement), §9 (traceability).

All tests target `Letflow.Engine.Wasm.ResourceLimits.build_store/1`, `.arm_fuel/2`,
`.classify_call_result/1`, and `.memory_grew_within_cap?/3` directly, dispatching guest
calls through the existing, unmodified `Letflow.Engine.PluginTaskSupervisor` (mirroring
`PluginHandler`'s own dispatch pattern) — no REQ-171/172 host function exists yet
(design §3's stated reason), so there is no real host-function call path to test
through.

**⚠️ Read design §1.6/§2/§7 before writing T3 below.** WASM-10's literal acceptance
wording ("traps cleanly") does **not** match live-verified behavior: `memory.grow`
beyond `StoreLimits.memory_size` returns an ordinary `{:ok, [-1]}` success, never a
trap or error. T3's assertions below are written against the real, live-verified
behavior. Do not "fix" T3 to assert a trap that design §1.6 shows does not occur —
that would silently paper over a documented, ORCH-facing finding.

## T1 — `build_store/1` produces a fuel-enabled, limit-attached Engine/Store pair (setup precondition for every other test)

**Design ref:** §4 `build_store/1`, §1.1/§1.5 (mechanism this wraps).

1. `build_store(%{fuel_budget: 1_000, memory_cap_bytes: 65_536})` → `{:ok, {engine,
   store}}`; assert `Wasmex.StoreOrCaller.set_fuel(store, 10) == :ok` (proves
   `consume_fuel: true` was really set on the `Engine` this `Store` was built from —
   design §1.3's canary property exercised positively here).
2. A malformed `StoreLimits`-adjacent input (e.g. a negative `memory_cap_bytes`, if
   `Wasmex.StoreLimits`/`Wasmex.Store.new/2` itself rejects it cleanly rather than
   crashing — confirm which by direct live call before writing this case, per design
   §1's own discipline of never asserting a shape that wasn't actually run) — asserted
   against whichever clean `{:error, build_defect()}` shape TEST-DESIGNER's own
   pre-write live check confirms; do not assume design §4's `build_defect()` variants
   are exhaustive without checking.

## T2 — AC1 + AC5: fuel metering genuinely bounds an infinite loop and is genuinely enabled

**Design ref:** §1.1, §1.3, §4 `arm_fuel/2`/`classify_call_result/1`, §5.2.

1. Using `priv/wasm_fixtures/req169_hang.wat`'s `"hang"` export: `build_store(%{
   fuel_budget: 1_000, memory_cap_bytes: 65_536})`, `arm_fuel(store, 1_000)`, dispatch
   via a supervised task with a generous outer timeout (e.g. 5s — must be long enough
   that the *fuel* mechanism is what terminates the call, not the outer task bound).
   Assert the task completes within that bound (not a `:timeout`/`nil` outer outcome)
   and `classify_call_result/1` applied to the raw `Wasmex.call_function/4` result
   returns `:fuel_exhausted`.
2. **AC5's own scenario, direct.** Build an `Engine` with `consume_fuel: false`
   directly (bypassing `build_store/1`, to simulate what a hypothetical future
   regression in that function would produce) and a `Store` from it; assert
   `arm_fuel(store, 1_000)` returns `{:error, {:fuel_not_configured, _}}` — proving the
   canary fires rather than silently letting the guest run unbounded.
3. **Mutation-driven addition candidate (WF-02 Step 3, TEST-DESIGNER should verify
   this actually distinguishes a real mutant, not merely assert it):** a control case
   using the identical `"hang"` fixture with `consume_fuel: false` throughout (no
   `arm_fuel/2` call attempted, matching what an un-canaried regression would let
   through) and only a short *outer* task timeout — assert the outer task genuinely
   times out (`:timeout`/`nil`), proving fuel, not the outer boundary, was what
   terminated case 1's call.

## T3 — AC3: memory-cap behavior, asserted honestly against the live-verified `-1`-return shape, NOT a trap

**Design ref:** §1.5/§1.6 (the divergence itself), §2 item 3, §4 `memory_grew_within_cap?/3`, §5.4, §7.

Using `priv/wasm_fixtures/req169_grow.wat`'s `"grow_by"` export (starts at 1 page, own
declared max 10 pages):

1. `build_store(%{fuel_budget: 100_000, memory_cap_bytes: 2 * 65_536})` (2-page cap).
   Fetch `size_before = Wasmex.Memory.size/2`. Dispatch `grow_by(1)` (reaches the cap
   exactly): assert the raw return is `{:ok, [1]}` (memory.grow's own "previous page
   count" convention) and `classify_call_result/1` on it is `:ok`.
2. Fetch `size_before_2` (now 2 pages). Dispatch `grow_by(5)` (would reach 7 pages,
   exceeding the cap): assert the raw return is **exactly** `{:ok, [-1]}` — the test's
   own inline comment must state this is a success shape per Wasm's own
   growth-failure convention, not an error, per design §1.6. Assert
   `classify_call_result/1` on this same raw value is `:ok` (design §4's contract:
   nothing else to classify it as).
3. Fetch `size_after_2` (`Wasmex.Memory.size/2`, same instance, after step 2's call).
   Assert `size_after_2 == size_before_2` (the real, physical memory did not grow at
   all despite the guest's request — the actual security guarantee). Assert
   `memory_grew_within_cap?(size_before_2, size_after_2, 2 * 65_536) == :within_cap`.
4. **Sanity/control: identical `grow_by(5)` call against a `Store` built with NO
   memory cap at all** (`build_store` with a `memory_cap_bytes` large enough to be a
   practical no-op, e.g. `10 * 65_536`, or a direct `Wasmex.Store.new(nil, engine)`
   call if design's `build_store/1` requires a cap argument — confirm which against
   the shipped `config()` type): assert the grow **succeeds** (`{:ok, [1]}`, page
   count actually increases), proving case 2's failure was caused by the cap, not by
   some unrelated fixture limitation.

## T4 — AC2: fuel resets per invocation

**Design ref:** §1.2, §4 `arm_fuel/2`'s "before every call" contract, §5.3.

Using `priv/wasm_fixtures/req169_counting.wat`'s `"count_forever"` export (writes its
loop counter to memory offset 0 on every iteration, per design §1.4's technique) and
one `Store` reused across two invocations:

1. `build_store/1`, `arm_fuel(store, 500)`, dispatch `"count_forever"`: assert
   `classify_call_result/1` is `:fuel_exhausted`; read memory offset 0 (4 bytes,
   little-endian i32) as `counter_1`.
2. `arm_fuel(store, 500)` **again** (fresh budget, same value), dispatch
   `"count_forever"` a second time: assert `:fuel_exhausted` again; read the counter
   again as `counter_2`. Assert `counter_2 == counter_1` (byte-for-byte identical
   iteration count — design §1.2's live reproduction found identical backtrace
   offsets across repeats, so exact equality, not "roughly equal," is the correct
   assertion and should be asserted as such).
3. **The discriminating negative case, mutation-grade (WF-02 Step 3, TEST-DESIGNER
   should include this — it is what actually catches "forgot to reset" bugs, not
   just steps 1-2 above).** Repeat step 1 fresh (`arm_fuel(store, 500)`, dispatch,
   read `counter_a`), then dispatch `"count_forever"` a **second** time on the same
   `store` **without** calling `arm_fuel/2` again: assert `classify_call_result/1` is
   still `:fuel_exhausted` (0 fuel remaining traps immediately) and the resulting
   counter, `counter_b`, is **strictly less than** `counter_a` (starved — got
   essentially zero budget, not the full 500). This is design §1.2's own live-
   reproduced "omission genuinely starves invocation N+1" finding, restated as a
   permanent regression test; without this case, a `arm_fuel/2` that silently no-ops
   on its second call within a test run could still pass steps 1-2 by accident if the
   implementation happened to reset fuel via some other unintended path.

## T5 — AC4: both knobs are configurable, and the tighter one binds sooner

**Design ref:** §1.4/§1.5, §4 `config()`, §5.5.

1. **Fuel.** Dispatch `req169_counting.wat`'s `"count_forever"` under
   `fuel_budget: 20` and, separately (fresh `Store` each), `fuel_budget: 2_000`.
   Assert both classify as `:fuel_exhausted`. Assert the memory counter under the
   tighter budget is strictly less than under the looser budget (design §1.4's live
   values, 3 vs 250, may be asserted as exact regression values in addition to the
   inequality, since Wasmtime's own fuel accounting is deterministic per §1.2).
2. **Memory.** Using `req169_grow.wat`'s `"grow_by"` export, repeatedly call
   `grow_by(1)` against a `memory_cap_bytes: 2 * 65_536` store until the first `-1`
   result, counting successful grows; repeat against `memory_cap_bytes: 5 * 65_536`.
   Assert the tighter cap's successful-grow count is strictly less than the looser
   cap's (design §1.5's live values, 1 vs 4, may be asserted as exact regression
   values in addition to the inequality).

## T6 — AC6: fuel-exhaustion, memory-cap, and a future wall-clock timeout are pattern-match distinguishable

**Design ref:** §4 `call_classification()`, §5.6.

1. `classify_call_result/1` on a captured fuel-exhaustion raw result (from T2) returns
   `:fuel_exhausted`.
2. `classify_call_result/1` on a captured guest-authored-trap raw result (a small
   dedicated fixture whose guest code deliberately executes `unreachable`, distinct
   from a fuel trap — design §1.6's own guest-self-check pattern, or any simpler
   `unreachable`-only fixture) returns `{:trap, msg}` where `msg` does **not** contain
   the substring `"fuel"`.
3. Assert `classify_call_result/1` on T3's memory-cap-hit raw result (`{:ok, [-1]}`)
   is `:ok`, not `:fuel_exhausted` and not `{:trap, _}` — confirming by construction
   that a memory-cap breach and a fuel exhaustion can never collide under this
   function's classification.
4. Assert neither `:fuel_exhausted` nor any `{:trap, _}` value can structurally equal
   (`===`) `Letflow.Engine.PluginInterface`'s own existing timeout-error shape
   (`{:error, "...did not respond within " <> _}`, from `handle_yield_result/4`'s
   `nil` clause, REQ-165, unmodified) — a static/structural assertion (the shapes are
   different Elixir term types: an atom, a 2-tuple with a `:trap` tag, vs a 2-tuple
   with an `:error` tag wrapping a string prefix), not a live invocation of a
   not-yet-built REQ-170 mechanism.

## Mutation-driven strengthening pass (WF-02 Step 3, TEST-DESIGNER, 2026-08-28)

Per the ORCH handoff's own enumerated acceptance criteria, six specific mutations of
`lib/letflow/engine/wasm/resource_limits.ex` were applied locally (one at a time,
running `mix test test/letflow/engine/wasm/resource_limits_test.exs` after each, then
reverting to a byte-identical copy of the pre-mutation file before the next), plus one
additional mutation of the AC7 moduledoc-content check per the handoff's explicit
"confirm the AC7 test is not trivially satisfiable" item. Findings:

1. **`new_engine/1` hardcoded to `consume_fuel: false`** (AC5's central concern) — caught
   immediately: 7 of the (then-)9 tests fail, because `arm_fuel/2` now returns
   `{:error, {:fuel_not_configured, _}}` for every store built via `build_store/1`. No
   gap; no new test needed.
2. **`arm_fuel/2` turned into an unconditional `:ok` no-op**, never calling
   `Wasmex.StoreOrCaller.set_fuel/2` — caught: 6 of 9 tests fail, and critically the
   **AC2 reset test itself** fails specifically (`first_count > 0` becomes `first_count
   == 0`, not merely a "wrong budget value" mismatch), satisfying the handoff's own
   discriminating condition. No gap; no new test needed.
3. **`classify_call_result/1`'s `@fuel_exhausted_substring` loosened from
   `"all fuel consumed by WebAssembly"` to bare `"fuel"`** — **NOT caught**: all 9
   original tests stayed green, because none of the fixtures' real trap/error strings
   happen to contain the bare word "fuel" outside the canonical phrase. Genuine gap.
   Added two new tests directly exercising `classify_call_result/1`'s pure string logic
   (no wasmex fixture needed): one asserting an incidental "...fuel-adjacent..." trap
   message classifies as `{:trap, _}` (not `:fuel_exhausted`), and a control case
   confirming the canonical phrase still classifies as `:fuel_exhausted`. Re-ran the
   mutation afterward — the new test now fails exactly as expected (1/11 red, the new
   test); reverted the mutation, both new tests pass (11/11 green) against the real
   implementation.
4. **`memory_grew_within_cap?/3`'s `<=` mutated to `<`** — caught: the existing AC3
   "attempting to grow beyond the cap" test already exercises the exact boundary
   (`size_after == memory_cap_bytes`, since the guest reaches the cap exactly before
   the capped attempt), so it fails specifically on this mutation (`:capped` instead of
   `:within_cap`). No gap; no new test needed.
5. **`store_limits/1` mutated to pass `memory_size: nil`** (unbounded) instead of
   `config.memory_cap_bytes` (AC3/AC4's central memory-cap concern) — caught: 2 tests
   fail, including AC4's "tighter cap permits strictly fewer successful grows" test
   (both counts become equal/large once the cap is gone). No gap; no new test needed.
6. **AC7 moduledoc-content check specificity** — the handoff asked to confirm this
   isn't trivially satisfiable by an accidental substring match. Constructed an
   adversarial moduledoc (kept in isolation just long enough to observe the result,
   then reverted) that plants the exact three matched fragments (`"DIVERGENCE"`,
   `"WASM-10"`, `does **NOT** trap`) inside an unrelated sentence about "unrelated
   retries," with no mention of `memory.grow`/`StoreLimits.memory_size` at all — **NOT
   caught**: all three original assertions still passed (11/11 green at that point, the
   3-item classify_call_result gap already having been closed). Genuine gap. Added a
   second AC7 test requiring: the mechanism terms (`memory.grow`,
   `StoreLimits.memory_size`) to actually appear, a proximity regex anchoring the "does
   NOT trap" claim within 200 chars of `StoreLimits.memory_size` (so the claim can't be
   floating free in an unrelated sentence), the design-doc filename
   (`req169-wasm-fuel-and-memory-cap.md`) and decision `"0014"` citation (mirroring
   `test/specs/REQ-168.md` T5 item 3's identical citation-strengthening technique per
   this spec's own T7.4 note), and the underlying security-property sentence
   (`physically, unconditionally bounds`). Re-ran the adversarial mutation afterward —
   the new test fails exactly as expected (11/12 red); reverted, 12/12 green against
   the real implementation.

**Every mutation above was reverted before moving to the next**, confirmed by `diff`
against a byte-identical pre-mutation copy of `resource_limits.ex` after the final
revert (`IMPLEMENTATION FULLY REVERTED`). `resource_limits.ex` itself was never left
modified at any point this pass concluded. All 12 tests (9 original + 3 new) pass
against the real, unmodified implementation; `mix compile --warnings-as-errors`
succeeds cleanly.

No genuine implementation defect was found during this pass — all six assigned
mutations either were already caught by the existing suite, or are now caught by the
two added tests (three new `test` blocks total: one `classify_call_result/1`
false-positive test, one `classify_call_result/1` control case, one AC7 citation/
proximity test).

## Notes for TEST-DESIGNER on fixture authoring

- `priv/wasm_fixtures/req169_hang.wat`, `req169_counting.wat`, and `req169_grow.wat`
  (design §5.1) are all new, permanent fixtures — none needs to satisfy the plugin
  ABI's five required exports (`init`/`execute`/`deinit`/`get_capabilities`/`alloc`);
  `ModuleRegistry.register/1`'s export-shape check is not exercised by this
  requirement's tests at all, exactly as REQ-168's tests did not exercise it either.
- `Letflow.Engine.PluginTaskSupervisor` must already be running under
  `Letflow.Application`'s supervision tree for every dispatch in this spec — confirm
  this in test setup rather than assuming it, matching `req167`/`req168`'s identical
  note.
- **Never assert AC3's literal "traps cleanly" wording as written.** Design §1.6/§7
  found this does not match live-verified behavior. A test asserting a trap for the
  memory-cap case would fail against the real, correct implementation — TEST-DESIGN-
  VALIDATOR should reject any such assertion as a spec-vs-reality mismatch, not accept
  it as stronger coverage.
- Reading a loop counter back from linear memory after a fuel-exhaustion trap (T4, T5
  item 1) relies on the `Store`/`Memory` handle remaining valid and readable after a
  trapped call returns — already confirmed live by this design (§1.4) and consistent
  with REQ-168's own established finding that a `Store` remains usable after a call
  returns, trap or not.
