# REQ-170 Test Spec: WASM per-invocation wall-clock timeout enforced across the process boundary (WASM-11)

See `lib/letflow/design/req170-wasm-wallclock-timeout.md` (gate-approved) for the full
design these tests exercise: §1 (live-verified `wasmex` v0.15.1 behavior, including the
decision-0014-falsifying finding that a hung guest is never interrupted and its Store
never becomes usable again), §2 (what this changes about WASM-11's literal text), §3
(split coverage answer: AC3 needs zero new code, AC1/AC4 need a small `PluginHandler`
extension, AC5 needs a new small classifier), §4 (`Letflow.Engine.Wasm.CallTimeout`'s
public contract and the `PluginHandler` extension), §5 (test strategy this spec
implements), §6 (required moduledoc content), §8 (OQ-5 filing).

**⚠️ SAFETY NOTE, do not violate:** none of these tests reproduce design §1.5's
32-concurrent-hang worker-pool-saturation scenario. That scenario durably occupies
`wasmex`'s shared, node-global native thread pool for the remainder of any test run it
is part of and would corrupt every other WASM test's own timing assumptions. It is
recorded as a one-time, this-design-session live-verified result only (§1.5, §8), not
an automated regression test.

All tests exercise the real, unmodified `Letflow.Engine.PluginInterface.invoke/2,3` ->
`Letflow.Engine.Wasm.PluginHandler.handle_node/1` entry point (no bypass), except AC2,
which is specifically about `wasmex`'s own documented claim in isolation and so targets
`Wasmex.call_function/4` directly, per the design's own §5.3 instruction.

## CI-hang-footprint reduction pass (WF02-REQ170-20260828, ORCH final-ci-fix handoff)

PR #691's CI (`mix letflow.check` -> plain `mix test`, a single non-partitioned BEAM
process) failed on one of two duplicate runs of the identical commit (9 failures) while
the other passed cleanly (0 failures). Root cause, structurally confirmed (not a guess):
this requirement's own tests dispatch genuinely-hanging guests through the REAL
`PluginInterface.invoke -> PluginHandler.handle_node -> Wasmex.start_link/1` entry
point. Per the design doc's own finding (§1.1-1.4), a genuinely-hung `wasmex` call is
**never** interrupted — it permanently occupies one thread of `wasmex`'s shared,
node-global Tokio native worker pool with no BEAM-side reclaim mechanism. Across
`call_timeout_test.exs` and `plugin_handler_test.exs`'s REQ-170 blocks, this accumulated
~8 permanently-leaked native threads over one sequential `mix test` run, exhausting the
shared pool before later WASM test files ran in the same OS process on a CI runner with
few cores — the exact cascading failure observed.

Two changes reduce this footprint without weakening any AC's live coverage:

1. `call_timeout_test.exs`'s "AC5" describe block: the first test ("a real captured
   wall-clock-timeout PluginInterface outcome ... classifies as :wall_clock_timeout")
   dispatched its own live hang against `node_config["timeout_ms"] => 300` — the exact
   same mechanism (inner wasmex-level `GenServer.call` timeout -> `PluginInterface`
   `{:exit, reason}` -> `classify/1`) that `plugin_handler_test.exs`'s "REQ-170 AC1"
   test already proves live, including its own `CallTimeout.classify(result) ==
   :wall_clock_timeout` assertion. Converted to a synthetic `outcome()` value —
   `{:error, reason}` with `reason` captured verbatim from one real run of that exact
   call shape (`scratch/req170_capture_outcome.exs`, git-ignored). This removes one
   leaked native thread with zero coverage loss: AC1 still proves the mechanism live.
   The block's *second* test (outer `Task.yield/2` timeout shape) is kept live — it is
   the only live end-to-end proof that `classify/1` correctly recognizes the OUTER
   timeout's string shape (`plugin_handler_test.exs`'s "REQ-170 AC3" test exercises the
   same outer-boundary mechanism but does not call `classify/1`), so it stays per AC1
   of this fix's own mandate ("keep AT LEAST ONE live, end-to-end proof per distinct
   mechanism").
2. `plugin_handler_test.exs`'s "REQ-170 AC4" describe block: consolidated from two
   tests / three live calls (300ms, 2_000ms, then a separate 7_000ms test) to one test
   / two live calls (300ms, 7_000ms). A pair straddling wasmex's own hardcoded 5,000ms
   default proves BOTH properties AC4 needs in the same two calls: (a) the shorter
   value binds sooner (the ordering claim), and (b) `timeout_ms` is threaded through to
   `Wasmex.call_function/4` rather than silently dropped (M6's own closing-test
   guarantee: if dropped, both calls collapse to ~5,000ms and `long_elapsed_ms > 6_000`
   fails). M6's re-applied-mutation guarantee (table above) still holds against the
   consolidated test — re-verified locally after the consolidation (see WF-02
   Step 3/TEST-DESIGNER's `mix test` output for this run below).

Net effect: `call_timeout_test.exs`'s live-hang count drops from 3 to 2 (AC2's own
direct-`Wasmex.call_function/4` test, kept — this is the sole proof of the raw
`wasmex`-documented-claim finding and cannot be made synthetic; plus AC5's remaining
outer-timeout live test). `plugin_handler_test.exs`'s REQ-170-block live-hang count
drops from 5 to 4 (AC1: 1, AC3: 1, AC4 consolidated: 2 — REQ-165's own pre-existing,
unmodified "AC5: a hanging guest is terminated by the outer task timeout" test, 1 more
live hang, is untouched: it is a different, already-shipped requirement's own coverage,
out of scope for this REQ-170 test-file fix). Total genuinely-hanging calls across both
files: ~9 (recount at per-call granularity; the handoff's own count is an estimate) down
to 7 — every one of REQ-170's 7 real acceptance criteria (AC1-AC7) still has at least
one live, end-to-end test proving the real mechanism, per this fix's own hard
constraint; the reduction stops there rather than trading away that constraint to chase
the "roughly half" target number.
