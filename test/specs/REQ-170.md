# REQ-170 Test Spec: WASM per-invocation wall-clock timeout enforced across the process boundary (WASM-11)

See `lib/letflow/design/req170-wasm-wallclock-timeout.md` (gate-approved) for the full
design these tests exercise: §1 (live-verified `wasmex` v0.15.1 behavior, including the
decision-0014-falsifying finding that a hung guest is never interrupted and its Store
never becomes usable again), §2 (what this changes about WASM-11's literal text), §3
(split coverage answer: AC3 needs zero new code, AC1/AC4 need a small `PluginHandler`
extension, AC5 needs a new small classifier), §4 (`Letflow.Engine.Wasm.CallTimeout`'s
public contract and the `PluginHandler` extension), §5 (test strategy this spec
implements), §6 (required moduledoc content), §8 (OQ-5 filing).

**⚠️ SAFETY NOTE, do not violate:** none of these tests reproduce design §1.5's
32-concurrent-hang worker-pool-saturation scenario. That scenario durably occupies
`wasmex`'s shared, node-global native thread pool for the remainder of any test run it
is part of and would corrupt every other WASM test's own timing assumptions. It is
recorded as a one-time, this-design-session live-verified result only (§1.5, §8), not
an automated regression test.

All tests exercise the real, unmodified `Letflow.Engine.PluginInterface.invoke/2,3` ->
`Letflow.Engine.Wasm.PluginHandler.handle_node/1` entry point (no bypass), except AC2,
which is specifically about `wasmex`'s own documented claim in isolation and so targets
`Wasmex.call_function/4` directly, per the design's own §5.3 instruction.
