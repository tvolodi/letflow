# REQ-170 Test Spec: WASM per-invocation wall-clock timeout enforced across the process boundary (WASM-11)

This is a prose skeleton for TEST-DESIGNER — no test code is written here (WF-02 Step 1
is design, not test authoring). See
`lib/letflow/design/req170-wasm-wallclock-timeout.md` for the full design these tests
exercise: §1 (live-verified findings, including that `wasmex`'s documented
interrupt-and-keep-Store claim does NOT hold), §2 (what that changes about WASM-11's
literal text and this requirement's actual deliverable), §3 (AC3 is already fully
covered by unmodified `PluginInterface` code; AC1/AC4/AC5 need small new code), §4
(`Letflow.Engine.Wasm.CallTimeout`'s public contract, and the small `PluginHandler`
extension), §6 (required moduledoc content), §7/§8 (the divergence and OQ-5 filing
statements), §10 (traceability).

**⚠️ Read design §1/§2/§7 before writing T1/T2 below.** WASM-11's literal text
("Exceeding the timeout MUST INTERRUPT EXECUTION") does **not** match live-verified
behavior: the underlying guest execution is never actually terminated, only the
caller's wait is bounded. Do not "fix" T1's assertions to claim guest-execution
termination that design §1/§2 show does not occur — that would silently paper over a
documented, ORCH-facing finding more severe than any prior WASM requirement's own
divergence.

Unlike REQ-166–169 (which test `ResourceLimits`/`CapabilityGate`/`MemoryGuard`
directly, bypassing dispatch, because no host function wires them into a real call path
yet), `PluginHandler` **is** already wired into a real, dispatchable
`Letflow.Engine.PluginInterface.invoke/2,3` path (REQ-165/057). Tests here go through
the real entry point (`PluginInterface.invoke/2,3`), not a bypass, except where §5.3
explicitly calls for testing `wasmex` in isolation.

## T1 — AC1/AC5 (design §5.2): a guest blocked in a host call is bounded by the configured timeout; the caller-facing error is classifiable as `:wall_clock_timeout`

**Design ref:** §4.2 `CallTimeout.classify/1`, §4.3 `PluginHandler`'s new `node_config["timeout_ms"]`, §5.2.

1. Build an `ExecutionContext` (`Letflow.Engine.PluginInterface.ExecutionContext`) with
   `node_config: %{"wasm_fixture" => "wasm_fixtures/req170_hang.wat", "export" =>
   "hang", "timeout_ms" => 500}`. Call
   `Letflow.Engine.PluginInterface.invoke(Letflow.Engine.Wasm.PluginHandler, context)`
   — the real, unmodified, production entry point. Assert the call returns within a
   small bound around 500ms (well under `PluginInterface`'s own `@default_timeout_ms`
   30,000ms) and the result is `{:error, reason}` with `reason` a binary.
2. Assert `Letflow.Engine.Wasm.CallTimeout.classify(result) == :wall_clock_timeout` on
   the same captured result.
3. **Required test comment** (design §5.2 item 3): note explicitly that this proves the
   *caller's* wait was bounded and it received a structured error — it does NOT prove,
   and this design does not claim, that the underlying guest WebAssembly execution was
   actually terminated (design §1.4 live-verified it is not, for a non-cooperating
   guest under this `wasmex` version).

## T2 — AC2 (design §5.3): `wasmex`'s own documented interrupt-and-keep-Store claim, tested directly against real `wasmex`, and found NOT to hold

**Design ref:** §1.1, §1.2, §7.

1. Direct against `Wasmex.start_link/1` + `Wasmex.call_function/4` (not through
   `PluginHandler` — this AC is specifically about `wasmex`'s own claim in isolation).
   Start a guest from `priv/wasm_fixtures/req170_hang.wat`. Call
   `Wasmex.call_function(pid, "hang", [], 500)`. **Assert this raises/exits** (wrap in
   `catch :exit, reason -> reason end` or an equivalent `assert_raise`/`catch_exit`
   idiom) rather than returning `{:error, _}` — the real, live-verified behavior per
   design §1.1, quoted there with the exact crash shape
   (`{:timeout, {GenServer, :call, [...]}}`).
2. **Required test comment**: cite design §1.1/§7 explicitly — this assertion is
   written against the real, live-verified divergence from `wasmex`'s own
   documentation, not against the documented claim, per this project's established
   "test the real behavior, state the divergence" discipline (`req169` §5.4 item 4
   precedent).
3. A second assertion in the same test (or a closely related one): after the crash in
   step 1, attempt a **second** call on the **same** `pid` with a bounded wait (e.g.
   2–5 seconds, not the full 30 seconds design §1.2 used — this is a regression test,
   not a full reproduction of every live-verification bound). Assert this second call
   also does not return a clean result within that bound (it should also time out/exit)
   — proving the "Store stays available for subsequent calls" half of the documented
   claim is equally false. **Do not assert `Process.alive?(pid) == true` as proof the
   Store "is available"** — design §1.2/§1.4 show liveness of the BEAM process is not
   the same as the Store being usable; assert against an actual second call's outcome.

## T3 — AC3 (design §5.4): the outer supervised task terminates the invocation independently of `wasmex`'s own timeout

**Design ref:** §1.6, §3 (zero new production code for this half — exercises existing, unmodified `PluginInterface.invoke/2,3`).

1. Build an `ExecutionContext` with `node_config: %{"wasm_fixture" =>
   "wasm_fixtures/req170_hang.wat", "export" => "hang", "timeout_ms" => 60_000}` (an
   inner `wasmex`-level bound deliberately much LONGER than the outer bound below).
   Call `Letflow.Engine.PluginInterface.invoke(Letflow.Engine.Wasm.PluginHandler,
   context, timeout_ms: 500)` (driving the OUTER bound via `invoke/3`'s existing
   `invoke_opts()`). Assert the call returns within roughly 500ms, not 60,000ms, and
   the result is `{:error, reason}`.
2. **Prove independence concretely**, per the handoff's own "assert the task process is
   dead" instruction: reproduce `invoke/3`'s own dispatch (`Task.Supervisor.async_nolink/2`
   under `Letflow.Engine.PluginTaskSupervisor` + `Task.yield/2`) directly in this test
   (rather than through the opaque `invoke/3` wrapper) so the task's `pid` is
   observable; assert `Task.yield(task, 500) == nil` and, after calling
   `Task.shutdown(task, :brutal_kill)`, assert `Process.alive?(task.pid) == false`.
3. `Letflow.Engine.Wasm.CallTimeout.classify/1` on the captured `{:error, reason}`
   returns `:wall_clock_timeout` (this scenario hits `PluginInterface`'s existing `nil`
   clause, the second of the two shapes `classify/1` must recognize per design §4.2).

## T4 — AC4 (design §5.5): the timeout is configurable, and the tighter of two values binds sooner

**Design ref:** §4.2 `CallTimeout.config()`, §4.3 `PluginHandler`'s new `"timeout_ms"` `node_config` key, §5.5.

1. Dispatch `req170_hang.wat`'s `"hang"` export twice through
   `PluginInterface.invoke/2,3` → `PluginHandler`, once with
   `node_config["timeout_ms"] = 300` and once with `node_config["timeout_ms"] =
   2_000`. Both use `PluginInterface`'s default outer bound (30,000ms) unchanged —
   deliberately never firing in this test, isolating the inner knob as what's under
   test (design §5.5's own reasoning: the inner value is what genuinely,
   deterministically governs elapsed time, per §1.1's finding, not `wasmex`'s
   documented-but-nonfunctional interrupt).
2. Measure real wall-clock elapsed time for each call (`System.monotonic_time/1`
   around each `invoke/2` call). Assert both return `{:error, _}`. Assert the 300ms
   case's elapsed time is strictly less than the 2,000ms case's, each within a generous
   tolerance band (this is real wall-clock scheduling/timing, not `wasmex`'s own
   deterministic fuel accounting — do NOT assert exact millisecond equality/values,
   unlike REQ-169's fuel-count tests; design §5.5 states this explicitly).

## T5 — AC5 (design §5.6): the timeout error is distinguishable by pattern match from REQ-169's fuel-exhaustion and memory-cap errors

**Design ref:** §4.2 `CallTimeout.classification()`, §4.4 (two independent distinguishing properties), §5.6.

1. Reuse T1's or T3's captured `PluginInterface.outcome()` (a wall-clock-timeout
   `{:error, reason}`) and REQ-169's own `req169_hang.wat` + `ResourceLimits.build_store/1`
   + `ResourceLimits.arm_fuel/2` sequence (reused directly per REQ-169's own gate-approved
   design, not re-derived) to produce a fuel-exhaustion raw `Wasmex.call_function/4`
   result.
2. Assert `Letflow.Engine.Wasm.CallTimeout.classify/1` on the wall-clock case is
   `:wall_clock_timeout`, and `Letflow.Engine.Wasm.ResourceLimits.classify_call_result/1`
   on the fuel case is `:fuel_exhausted`.
3. Assert `:wall_clock_timeout !== :fuel_exhausted` and, more generally per design
   §4.4's type-shape argument, that no value `CallTimeout.classify/1` can ever produce
   (`:wall_clock_timeout | :not_timeout`) can equal any value
   `ResourceLimits.classify_call_result/1` can ever produce (`:fuel_exhausted | {:trap,
   binary()} | :ok`) — assertable directly since the two result sets share no common
   member by construction.
4. Assert the two underlying raw strings are mutually exclusive substrings: the
   wall-clock reason's `"{:timeout, {GenServer, :call,"` substring does not appear in
   the fuel reason's `"all fuel consumed by WebAssembly"` string, and vice versa (both
   directions, via `String.contains?/2`).

## T6 — AC6 (design §5.7): moduledoc discipline — OQ-5 not settled here; the design session's own findings are stated, not absorbed

**Design ref:** §6 (required moduledoc content), §8 (full OQ-5 filing), §5.7.

1. A `moduledoc =~ ...`-style assertion (mirroring `req165`/`req168`/`req169`'s own
   precedent) confirming `Letflow.Engine.Wasm.CallTimeout`'s moduledoc contains: (a) a
   phrase stating OQ-5 (scheduler safety under real load) is NOT settled by this
   requirement and names what would settle it (a load spike plus S6 thresholds); (b) a
   phrase referencing the node-wide native-worker-pool-exhaustion finding as filed
   evidence (design §8).
2. **Do not attempt to reproduce design §1.5's 32-concurrent-hang saturation scenario
   as an automated `mix test` case** (design §5.7 states why explicitly: it takes over
   a minute and durably occupies `wasmex`'s shared, node-global native thread pool for
   the remainder of the test run, corrupting every other WASM test's own timing
   assumptions). That finding is a live-verified, one-time, this-design-session result,
   reproducible via `scratch/req170_timeout_probe.exs` outside the normal suite, not a
   suite-embedded regression test. If TEST-DESIGNER judges a smaller-scale, suite-safe
   version of this scenario is feasible (e.g. saturating with a small fixed number of
   hangs well under `System.schedulers_online()`, on a separate `Task.Supervisor`
   instance scoped to the test, verifying no cross-test pool leakage), that is a
   reasonable addition — but it is not required by this design, and must not replace T6
   item 1's moduledoc-content assertion.
