# REQ-171 Test Spec: WASM host API 1/2 — read path (`read_variable`, `log`, `now`, `uuid`) at parity with Lua (WASM-12 read half)

This is a prose skeleton for TEST-DESIGNER — no test code is written here (WF-02 Step 1
is design, not test authoring). See `lib/letflow/design/req171-wasm-host-api-read.md`
for the full design these tests exercise: §1 (live-verified `wasmex` callback
mechanics, binding on every test's own call shape), §2 (number marshalling reuse),
§3 (`uuid`'s decision), §4 (`CapabilityGate` extension, `@known_imports` real rows),
§5 (`HostApi`'s per-function algorithms and the shared buffer protocol), §9 (this
spec's own source table, reproduced and expanded below).

All tests target `Letflow.Engine.Wasm.HostApi`'s `do_read_variable/6`, `do_log/8`,
`do_now/3`, `do_uuid/3` (either directly, for cases that need no live `wasmex`
instance — design §9's T13 — or through a real running instance via a new fixture,
`priv/wasm_fixtures/req171_host_api.wat`, design §9), and
`Letflow.Engine.Wasm.CapabilityGate.build_import_table/1,2`. No test targets
`lib/letflow/engine/lua/platform.ex` directly except as the **other half** of a
parity comparison (design §9's "dual-drive strategy") — this requirement does not
modify that file, and no test should.

**⚠️ Read design §1 before writing any test that installs an import callback.** A
callback for a single-`:i32`-result import must return a **bare integer**, never
`[integer]` — wrapping it yourself double-wraps (design Finding 2, live-verified).
A callback must **never raise** (design Finding 3, live-verified: a raising callback
and a return-type mismatch both collapse into the same opaque
`{:error, "Error during function excecution..."}` shape from
`Wasmex.call_function/4` — there is no way to distinguish "my callback has a bug"
from "the guest tripped a real Wasm trap" from this string alone, so every
`HostApi.do_*` function under test must be independently proven never to raise on
its own, not merely trusted because the top-level call returned cleanly).

## T1 — AC1 + AC2 (found case): `read_variable` returns the current value for a set variable, parity with Lua

**Design ref:** §5.2 (buffer protocol), §5.3 (`do_read_variable` algorithm), §9
(parity strategy).

1. Build a fixed `execution_context()`-equivalent with `variables: %{"balance" =>
   42}` (an integer — reused by T9 below for the subtype check) on both sides: a
   `Letflow.Engine.Lua.Platform.execution_context()` with the same `variables` map,
   and a `Letflow.Engine.Wasm.HostApi.execution_context()` with the same map.
2. **Lua side:** `Sandbox.new/1` + `Platform.install/3` with that context + an empty
   grant set covering `"variable:read"`; `Lua.eval!(lua, "return platform.read_variable('balance')")`
   → decode the Lua return value.
3. **WASM side:** `CapabilityGate.build_import_table/2` with a manifest granting
   `"var:read"` and that same `execution_context`; `Wasmex.start_link/1` against
   `priv/wasm_fixtures/req171_host_api.wat` with that import table;
   `Wasmex.call_function(pid, "call_read_variable", [name_ptr, name_len, out_ptr,
   64])` where `name_ptr`/`name_len` address a `"balance"` UTF-8 data segment the
   fixture declares — assert the `i32` return is `>= 0` and `<= 64` (fits the
   buffer); read the guest's own memory at `out_ptr` for that many bytes via
   `Wasmex.Memory.read_binary/4` (from the test process, not from inside a
   callback — no re-entrancy concern per design §9); `Jason.decode!/1` those bytes.
4. Assert the Lua-decoded value and the WASM-decoded (JSON-decoded) value are
   `===` equal — same input, same observable outcome, ABI differs only in
   encoding (AC1).

## T2 — AC2 (not-present case): `read_variable` returns the chosen not-present representation for an unset variable

**Design ref:** §5.2, §5.3 step 3.

1. Same setup as T1 but `variables: %{}` (or a key the guest does not request).
2. WASM side: assert the `i32` return is exactly `-1` (design §5.2's chosen
   not-present sentinel) and that the guest's `out_ptr` buffer was not written
   (assert via a canary byte pattern pre-written to the buffer that must survive
   unchanged).
3. Lua side, same context: `platform.read_variable('missing')` returns Lua `nil` —
   assert this too, as the parity anchor AC2 requires ("matching the Lua side's nil
   semantics").

## T3 — AC3: `log` emits a structured entry carrying script/module identity, instance ID, and trace ID, each asserted individually

**Design ref:** §5.4.

1. Fixed `execution_context` with distinct, easily-asserted values for
   `script_identity`, `instance_id`, `trace_id` (e.g. three different UUIDs/strings,
   chosen so a test asserting the wrong field against the wrong value would fail —
   do not reuse the same value for two fields).
2. Drive `env.log` through `priv/wasm_fixtures/req171_host_api.wat`'s
   `call_log/6` export with `level = "info"`, a chosen `message`, and
   `context_len = 0` (no context).
3. Capture the emitted `Logger` entry's metadata (a custom `:logger` handler
   attached for the test, or an equivalent structured-capture mechanism — confirm
   which this project's existing test helpers already use, e.g. check
   `test/support/` before inventing a new one) and assert, **individually**, that
   `metadata[:script_identity]`, `metadata[:instance_id]`, `metadata[:trace_id]`
   each equal the exact value set in step 1 (AC3's own wording: "asserted
   individually" — one failing assertion per field, not one combined equality
   check against a map literal, so a future regression in exactly one field is
   pinpointed by which assertion fails).
4. Repeat with `context_len > 0` (a JSON object written into guest memory) and
   assert `metadata[:context]` decodes to the same map.
5. Repeat with malformed level bytes (invalid UTF-8) and malformed context JSON,
   asserting the call still completes (`results: []`, no error surfaced to the
   guest) and the degrade-gracefully metadata keys design §5.4 steps 2/3 specify
   appear.

## T4 — AC1: `log` semantic parity with Lua (`do_log/3`, LUA-13)

**Design ref:** §5.4, §9.

1. Same fixed `execution_context` on both sides (mirrors T1's dual-drive
   structure).
2. Lua side: `platform.log("info", "<message>", {key = "value"})`; WASM side:
   `env.log` with the same level/message and a JSON-encoded `{"key": "value"}`
   context.
3. Assert both emit a `Logger` entry at `:info` level with the same message text
   and the same `context` metadata value (decoded, since Lua carries it as a
   decoded Elixir term via `Lua.decode!/2` and WASM carries it as `Jason.decode!/1`
   output — both should equal `%{"key" => "value"}`).

## T5 — AC2/(design §9 T5): invalid-argument (`-2`) case, all three buffer-returning functions

**Design ref:** §5.2's third return range.

1. For each of `read_variable`, `now`, `uuid`: call with an `out_ptr`/`out_cap` pair
   whose end (`out_ptr + out_cap`) exceeds the guest's actual declared memory size
   (`priv/wasm_fixtures/req171_host_api.wat`'s single-page declaration, 65,536
   bytes — choose an `out_ptr` near that boundary and an `out_cap` that overflows
   it).
2. Assert the `i32` return is exactly `-2` and no write occurred (canary-byte
   check, as in T2).
3. For `read_variable` specifically, also test an out-of-bounds `name_ptr`/
   `name_len` pair (with a valid `out_ptr`/`out_cap`) — assert `-2` there too, and
   that `execution_context.variables` was never consulted (a spy/counter on the
   map access, or simply: use a `variables` map that would answer `>= 0` if reached,
   to prove the `-2` path short-circuits before the lookup).

## T6 — AC4: `now` parity against a fixed injected clock

**Design ref:** §5.5 ("calls `Letflow.Engine.Lua.Platform.now/0` directly").

1. `Application.put_env(:letflow, :lua_platform_time_source, <a TestDouble module
   returning one fixed `DateTime.t()`>)` in `setup`, `Application.delete_env/2` (or
   restore) in `on_exit`.
2. Lua side: `platform.now()` → the fixed ISO 8601 string.
3. WASM side: `env.now` via the fixture's `call_now/2` export → decode the
   returned buffer bytes as UTF-8.
4. Assert both strings are **exactly equal**, byte-for-byte (not merely "both
   parse to the same instant" — design §5.5's whole point is that `do_now/0`
   calls the *same* `Platform.now/0` code path, so exact string equality is the
   correct, strongest assertion, not a looser `DateTime.compare/2` check).
5. Also assert the returned string round-trips through `DateTime.from_iso8601/1`
   without error (AC4's "parseable as... ISO 8601 UTC instant" wording, satisfied
   independently of step 4's exact-match check).

## T7 — AC5: `HostApi` moduledoc states the `uuid`/Lua-matrix asymmetry and records the decision taken

**Design ref:** §3.

1. Read `Letflow.Engine.Wasm.HostApi`'s compiled moduledoc (e.g.
   `Code.fetch_docs/1` or a direct source-text check on `host_api.ex`) and assert
   it contains language naming: (a) that `uuid` has no counterpart in
   `platform.ex`'s 8-row Lua capability matrix, and (b) the explicit decision
   taken (implemented as a WASM-side addition, not presented as Lua parity) —
   a substring/regex assertion against the moduledoc text, not a behavioral test.

## T8 — `uuid` produces well-formed, unique values

**Design ref:** §3, §5.6.

1. Two successive `env.uuid` calls (via the fixture's `call_uuid/2` export) each
   return `36` for the `i32` result (fixed-length canonical UUID string, design
   §3's "always exactly 36 bytes" claim) with a valid `out_cap`.
2. Decode both buffers as UTF-8; assert each matches a canonical UUID v4-shaped
   regex and the two values are **not equal** to each other (uniqueness, the
   minimum bar for "not silently constant").

## T9 — AC6: number-marshalling subtype round-trip

**Design ref:** §2.

1. `variables: %{"count" => 5, "ratio" => 5.0}` (deliberately same numeric
   magnitude, different subtype, mirroring REQ-150's own subtype-preservation
   test shape).
2. `env.read_variable("count")` → decode the JSON buffer via `Jason.decode!/1` →
   assert `is_integer/1` is true and the value equals `5`.
3. `env.read_variable("ratio")` → assert `is_float/1` is true and the value
   equals `5.0` (not silently promoted/demoted to `5`).
4. Assert `Letflow.Engine.LuaNumberMarshalling.to_lua/1` is the actual function
   `do_read_variable` calls (a direct unit test of `HostApi`'s own source, or —
   if source-inspection is awkward — a targeted case where `to_lua/1`'s identity
   behavior is the only thing that could make step 2/3 pass: e.g. confirm no
   coercion happens even for a value that would tempt a naive implementation to
   "helpfully" convert, per `LuaNumberMarshalling`'s own moduledoc warning).

## T10 — AC7: capability gating comes from `CapabilityGate`'s whitelist, no second model

**Design ref:** §4.1–§4.4.

1. A manifest **without** `"var:read"` → `build_import_table/2`'s output has no
   `env.read_variable` entry (structural check on the returned map), **or**
   (equivalently, an end-to-end check) instantiating
   `priv/wasm_fixtures/req171_host_api.wat` (which imports `env.read_variable`)
   against that table fails instantiation with an unresolved-import defect naming
   `env`/`read_variable` — mirrors REQ-167's own AC1/AC3 test shape
   (`capability_gate.ex`'s own moduledoc).
2. A manifest **with** `"var:read"` → the entry is present and a real call
   succeeds (ties back into T1).
3. Same two cases for `"audit:log"` / `env.log`.

## T11 — AC7 (the `:none`-gated rows): `now`/`uuid` work with an EMPTY capability grant set

**Design ref:** §4.1, §4.4.

1. A manifest with `capabilities: []` (nothing granted at all) still produces a
   `build_import_table/2` output containing `env.now` and `env.uuid` entries, and
   both succeed when called through a real instance — proving the `:none`
   sentinel's structural inclusion (design §4.2's "always included" filter rule),
   not merely that *some* manifest happens to grant them.
2. The same empty-grant manifest's output does **not** contain `env.read_variable`
   or `env.log` (the two capability-gated rows) — a guest importing those still
   fails instantiation, distinguishing "ungated by design" from "gated but the
   test manifest happens to grant everything."

## T12 — AC8: no `Letflow.Repo` call anywhere in `HostApi`

**Design ref:** §5.1 (INV-HOSTAPI-1), §9.

1. `grep -rn 'Letflow\.Repo' lib/letflow/engine/wasm/host_api.ex` → zero hits.
   Structural, mirrors `memory_guard.ex`'s own AC1 grep-based test shape and
   `req168`'s own precedent for this project's convention of a real repo-search
   check standing in for (not merely supplementing) a behavioral assertion when
   the property is "this code path never reaches a particular dependency at all."

## T13 — Finding 3's binding requirement: no `HostApi.do_*` function ever raises, called directly with hostile arguments

**Design ref:** §1 Finding 3, §5.1 (INV-HOSTAPI-2), §9.

1. Call `do_read_variable/6`, `do_log/8`, `do_now/3`, `do_uuid/3` directly (no
   running `Wasmex` instance needed for the argument-validation branches — mirrors
   `MemoryGuard.check_bounds/3`'s own "callable with fabricated integers alone"
   design) with: negative offsets, offsets/lengths whose sum overflows a plausible
   `memory_size` (Elixir bignums, so no literal overflow — but a size far larger
   than any real guest's memory, exercising `MemoryGuard`'s own arithmetic path
   indirectly through `HostApi`), a `context` argument shaped as something other
   than the documented `wasmex_callback_context()` map for the pure/non-memory-
   touching branches only (do not fabricate a fake `Wasmex.Memory.t()`/
   `Wasmex.StoreOrCaller.t()` — those must come from a real instance per T1's
   setup; this test's own scope is the argument-validation branches that run
   *before* any `MemoryGuard` call, e.g. `read_variable`'s not-yet-reached name
   lookup once bounds fail).
2. Assert every call returns the design's own documented sentinel (`-1`/`-2`, or
   `nil` for `log`) — never raises, never exits, never crashes the calling test
   process.

## Fixture: `priv/wasm_fixtures/req171_host_api.wat`

Per design §9: exports `memory` (at least 1 page) and one guest function per host
function under test, each a thin re-export forwarding its own arguments verbatim to
the corresponding `env.*` import:

- `call_read_variable(name_ptr, name_len, out_ptr, out_cap) -> i32`
- `call_log(level_ptr, level_len, message_ptr, message_len, context_ptr, context_len) -> ()`
- `call_now(out_ptr, out_cap) -> i32`
- `call_uuid(out_ptr, out_cap) -> i32`

Also declares fixed data segments for the literal strings T1/T3/T4/T9's scenarios
need (e.g. `"balance"`, `"count"`, `"ratio"`, an `"info"` level string, a sample
message) at documented, stable offsets, so tests can address them without computing
offsets at runtime.
