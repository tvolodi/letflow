## Acceptance criteria → tests

### AC "ONE shared scenario definition... WASM-12's own acceptance criterion"

Not a new mechanism here — `test/support/host_api_parity.ex` (`Letflow.Test.
HostApiParity`) already implements the single named registry (7 scenarios:
`read_variable`, `log`, `now`, `uuid`, `write_variable`, `call_service`, `fail`).
`host_api_write_test.exs`'s "WASM-12: the shared parity harness..." describe block
calls `assert_parity/1` once per scenario (7 tests) plus an **exhaustiveness guard**
comparing `HostApiParity.scenarios/0`'s key set against
`CapabilityGate.known_host_functions/0`'s set — two independently-derived sets, never
a second hand-written literal list, so a future 8th `@known_imports` row without a
matching scenario fails this test by construction (design §8.4). Why this exists: the
harness could otherwise silently drift out of sync with `@known_imports` as new host
functions ship.

### AC "a guest that writes variables and then FAILS leaves instance variable state
unchanged, asserted separately for each failure arm"

Five tests in "write_variable: discard on every failure arm": guest trap
(`req172_write_then_trap.wat`), fuel exhaustion
(`req172_write_then_fuel_exhaustion.wat` + `ResourceLimits.arm_fuel/2`), memory cap
(`req172_write_then_memory_cap_fail.wat`, a guest that observes the `-1` sentinel and
reacts with its own `platform.fail` call, per design §3.4's honest restatement — no
host-provided memory-cap failure signal exists), wall-clock timeout
(`req172_write_then_hang.wat`, `@tag :wasm_hang`, direct `Wasmex.call_function/4`
with an explicit short timeout wrapped in `try/catch :exit`, mirroring
`call_timeout_test.exs`'s own AC2 pattern), and `fail`
(`req172_write_then_fail.wat`). Each test reads the Wasmex instance's OWN process
dictionary directly via `Process.info(pid, :dictionary)` (this file's private
`staged_writes/1` helper, mirroring `PluginHandler`'s own `fail_signal/1`) to confirm
the write really reached the staging buffer BEFORE asserting
`HostApi.take_staged_writes/0` — called from the TEST process, a process wholly
distinct from whichever process ran the guest — observes `%{}`. This mirrors
`platform_test.exs`'s own REQ-160 cross-process discipline exactly: process
dictionaries are per-process by construction, so this is a direct observation of
discard, not an inference. Why per-arm, not one combined test: each arm uses a
genuinely different WASM-level mechanism (trap vs. fuel vs. reactive fail vs. leak vs.
deliberate fail) and design §2.3/§9.1 states the wall-clock arm's guarantee
(abandonment) is not the same MECHANISM as the other four (destruction), even though
the OBSERVABLE guarantee is identical — collapsing them into one test would hide that
distinction.

A sixth test in this describe block ("a genuine guest trap is distinguishable from
fail") reuses `req172_write_then_trap.wat` and asserts `fail_signal(pid) == :none`
after a real trap — proving trap and `fail` are told apart by the presence/absence of
the pdict signal, not merely asserted for `fail` in isolation (mirrors
`platform_test.exs`'s own AC3 distinguishability discipline).

### AC "a guest that writes several variables and succeeds applies all of them with no
observable partial state"

"write_variable: staging, accumulation, and the -2 malformed-value case" describe
block: single write retrievable; several writes accumulate with last-write-wins on a
duplicate key (`%{"a" => 3, "b" => 2}` from three calls); empty buffer when never
called; malformed value JSON → `-2`, nothing staged; integer/float subtype round
-trip via `LuaNumberMarshalling.from_lua/1`. "No partial state" is proven the same way
`platform.ex`'s own REQ-160 test proves it: `stage_write/2` is a single,
non-yielding `Map.put/3` call per write — there is no intermediate call, no
observable half-applied map.

### AC "call_service returns a structured error... a missing capability fails per
REQ-167 -- the two behaviours asserted distinctly"

"call_service: structured service failure vs. missing-capability instantiation
denial" describe block: (1) a service-side failure produces a well-formed
`{"ok": false, "error": {"reason": ...}}` envelope, `n >= 0` — never a trap; (2) a
manifest lacking `"service:call"` fails at INSTANTIATION
(`{:error, {:instantiation_denied, {:unresolved_import, "env",
"platform_call_service"}}}`) via `CapabilityGate.start_instance/2`, with a
`SpyServiceCaller` double proving the real `ServiceCaller.call/2` body is never
invoked at all (`refute_received {:spy_called, _, _}`) — mirrors
`platform_test.exs`'s own mutation-testing-motivated `SpyServiceCaller` precedent.
These are two structurally different call shapes (instantiation failure vs. a normal
call return), asserted in two separate tests, never folded into one.

### AC "a guest that attempts to catch or ignore its own fail STILL yields a failed
outcome and does not run to completion"

`req172_fail_then_continue.wat` (new fixture): calls `fail`, then — unreachable in
practice — would call `write_variable` with a distinguishable marker and return the
literal `777`. The test asserts `Wasmex.call_function/4` never returns `{:ok, [777]}`,
that the fail-signal is present, and that `staged_writes(pid) == %{}` (the marker
write never ran). This is the WASM analogue of REQ-161's `pcall`-wrapped-continuation
test — core WebAssembly has no `pcall`/`catch` at all, so the adversarial shape is
"what would run next if fail returned", not a literal `pcall` translation.

### AC "any semantic difference... enumerated explicitly in the moduledoc"

Five tests in "AC6: every non-ABI semantic difference is enumerated in the
moduledoc", one per design §9 entry (9.1 wall-clock abandonment, 9.2 malformed-name
arm has no WASM equivalent, 9.3 `var:write`/`variable:write` token divergence, 9.4
`call_service` capability granularity, 9.5 `fail`'s structurally different
mechanism). **All five currently FAIL against the shipped `host_api.ex` — see
"Known gap" below.**

## Known gap found by this pass — NOT fixed by TEST-DESIGNER

`lib/letflow/engine/wasm/host_api.ex`'s moduledoc restates decision 0014 (4), the
capability source, the tenant boundary, number marshalling, `uuid`'s asymmetry, the
callback ABI, the shared buffer protocol, and the four invariants — but does **not**
enumerate design §9's five non-ABI semantic differences (wall-clock abandonment,
malformed-name arm, `var:write`/`variable:write` token divergence, `call_service`
granularity, `fail`'s structurally different mechanism). Design §11's own AC6 text is
explicit: "an unlisted one means the requirement is unmet." This is a genuine
acceptance-criterion gap in the implementation that passed SECURITY-REVIEWER/REVIEWER
(neither gate checks moduledoc-content completeness against a design's own §9), not a
test-design defect — the five failing tests above are the correct, intended signal.
Not fixed here because editing `lib/letflow/engine/wasm/host_api.ex` (implementation)
is outside TEST-DESIGNER's role; flagged for ORCH to route back to CODE-DESIGNER/
ELIXIR-DEV. All five differences are already fully and correctly stated in the design
doc's own §9 — closing this gap is expected to be a moduledoc-only addition, no
behavioral change.

## Mutation-testing pass (TEST-DESIGNER, 2026-08-28)

Per this project's standard discipline: mutated the shipped `host_api.ex`/
`capability_gate.ex` locally (never committed), confirmed the suite's reaction,
reverted every mutation, and re-verified via `md5sum`/`git diff --stat` (empty) after
every revert.

1. **`stage_write/2` loses accumulation** (`Process.put(@staged_writes_pdict_key,
   %{name => value})` instead of `Map.put(current, name, value)`). **Caught**: both
   "several writes accumulate, last-write-wins" and "round-trips an integer AND a
   whole-number float" failed immediately (2 failures). Reverted; `md5sum` confirmed
   byte-identical to pre-mutation.

2. **`do_fail/5` skips `stash_fail_signal/2`** (calls `exit/1` with no prior stash).
   **Caught, decisively**: 8 failures across every fail-dependent test in this file
   (default/explicit/invalid-UTF-8 reason tests, both fail discard-arm tests, the
   AC5 uninterceptability test, the parity harness's own `fail` scenario, and one
   AC6 moduledoc test that happens to also require the mechanism). Confirms `do_fail/
   5`'s uninterceptable-AND-distinguishable mechanism (design §2.2) is genuinely
   load-bearing, not merely asserted. Reverted; `md5sum` confirmed byte-identical.

3. **`capability_gate.ex`'s `platform_call_service` row widened from
   `"service:call"` to `:none`** (collapses AC4's structural distinctness — a missing
   grant would no longer deny instantiation at all). **Caught** by both this file's
   own "a missing service:call capability fails at instantiation" test AND five
   pre-existing `capability_gate_test.exs` tests (AC1/AC2's own whitelist tests).
   Reverted; `git diff --stat` against `lib/letflow/engine/wasm/` empty afterward.

4. **`@default_fail_reason` changed from the documented fallback string to `"no
   reason given"`**. **Caught**: the "a missing reason/details pair... defaults to
   the documented fallback string" test failed immediately (plus, incidentally, one
   AC6 moduledoc test that also asserts this substring). Reverted; `md5sum` confirmed
   byte-identical.
