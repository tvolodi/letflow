## Blocking finding (discovered during this step, reported to ORCH for routing)

**`ModuleVersionRegistry.register_version/3` cannot register ANY WASM module that
declares a host-function import — regardless of what capability manifest is
supplied — which blocks the design's own SS8.2/SS8.4 test scenario at its very
first step.**

Root cause, live-verified (not speculation): `register_version/3` delegates its
stage-1/2 validation verbatim to `Letflow.Engine.Wasm.ModuleRegistry.register/1`
(design SS3/SS5, "reused as-is"). That function's stage 2 (`module_registry.ex`'s
private `instantiate/2`) always calls `Wasmex.start_link(%{bytes: bytes})` with
**no `imports` key at all** — and `wasmex.ex:229`'s own `imports = Map.get(opts,
:imports, %{})` confirms the default is an **empty** import table, never one derived
from any manifest. Per `req163-wasm-abi-choice.md`'s own decision (cited in
`module_registry.ex`'s moduledoc), an unresolved import at this stage-2 attempt is
rejected identically to a missing/malformed export — this is `ModuleRegistry`'s
documented, intentional behaviour, not a crash. The consequence for REQ-173: since
`register_version/3` never builds a manifest-derived import table before calling
`ModuleRegistry.register/1`, **every** module declaring `env.platform_call_service`,
`env.write_variable`, or any other host import is rejected at registration with
`{:error, {:instantiation_failed, {:unresolved_import, "env", <name>}}}`, before
`activate/2` or `invoke/4` ever run. This is not specific to the two capabilities
design SS8.3 chose (`"service:call"`/`"var:write"`) — a `:none`-gated import (e.g.
`now`, always granted) is rejected identically, since stage 2 does not consult
capabilities or manifests at all.

This was previously unverified because no test exercised `register_version/3` with
a real host-importing fixture before this step: `ELIXIR-DEV`'s own handoff
(`step-02a-elixir-dev.json`) explicitly deferred "new tests" to this step, and
`REVIEWER`'s one FAIL round on this requirement (`step-02a-elixir-dev-fix1.json`)
was about a missing documentation citation, not a functional re-run of SS8.4's
scenario. Empirically confirmed here: see the
`describe "blocking finding: ..."` block below.

**Consequence for what can be tested end-to-end today:** because the design's own
SS8.1 controllable-gate mechanism requires the guest to make a real host call to
park (there is no other way to hold an `invoke/4` call open without a guest-side
host call), and any host-importing module is rejected at registration, **AC1
("held invocation... a guest blocked in a controllable host call"), AC4's
in-flight half ("released only after its last in-flight invocation completes"),
and AC5 (capability isolation of an actually-in-flight invocation) cannot be
exercised end-to-end through the public `register_version/3` → `activate/2` →
`invoke/4` path with the shipped implementation.** This is reported as a finding
for ORCH to route (likely a CODE-DESIGNER/ELIXIR-DEV fix making
`register_version/3` build a real, manifest-derived import table for its own
proving instantiation, rather than delegating that stage verbatim to
`ModuleRegistry.register/1`), not silently worked around.

## Test design given the finding

Per this project's TDD/red-test discipline (a correctly-written test that fails
against a genuine implementation defect is coverage, not noise — WF-02 Step 4 routes
a failure caused by "this run's own implementation" back to `ELIXIR-DEV`, exactly
the mechanism this defect needs), this suite is split three ways:

1. **The literal design SS8.4 scenario**, written EXACTLY per the design's
   prescribed mechanism (real `req173_v1_gated.wat`/`req173_v2_gated.wat`, the
   blocking service-caller gate, one overlapping scenario proving AC1-AC5
   together). This test is expected — and confirmed — to fail at its very first
   step (`register_version/3` for `req173_v1_gated.wat`) for the reason above. It
   is kept, not deleted or weakened, because it correctly encodes WASM-14/AC5 and
   needs no edit once the blocking finding is fixed — it will simply start passing.
2. **Capability-free companion fixtures** (`req173_v1_capless.wat`/
   `req173_v2_capless.wat` — zero imports, same ABI/return-literal shape as the
   gated pair) give genuine, currently-passing coverage of every part of
   WASM-14/AC2/AC3 that does not require an actually-held-open invocation, plus
   the "nothing to wait for" half of AC4 (design SS6 trigger point 2 — a version
   with `ref_count` already 0 at activation time releases immediately).
3. **AC5's design SS8.4 step 14 "defense in depth" check** (the two manifests are
   disjoint, verified directly via `CapabilityGate.build_import_table/2`) needs no
   WASM execution at all, so it is unaffected by the finding and is included in
   full.

## Acceptance criteria → tests

### AC1 — "a test holds an invocation open... activates a new module version
DURING it... the held invocation completes normally against the OLD version's
observable behaviour... overlap real rather than sequential"

`describe "design SS8.4: the one overlapping scenario ..."` — the one test
implements design SS8.4 steps 1-14 verbatim: registers/activates
`req173_v1_gated.wat` under `"service:call"`, starts invocation A asynchronously,
synchronously waits (`Req173BlockingServiceCaller.await_parked/1` — never a sleep)
until the guest is genuinely parked inside `platform_call_service`, THEN registers
and activates `req173_v2_gated.wat`, runs invocation B, releases the gate, and
asserts invocation A completes with `{:ok, v1_id, [111]}`. **Currently fails** at
the first `register_version/3` call — see "Blocking finding" above; the assertions
for AC1 proper are unreached. This is the correct, permanent test for AC1; it needs
no change once the blocking finding is fixed.

### AC2 — "an invocation started AFTER the activation observes the NEW version"

Two tests: the blocked SS8.4 scenario (step 9, unreached today for the same
reason), and — independently, passing today —
`"activating a second version supersedes the first; a new invocation observes the
new version and its own distinct literal (AC2/AC3, non-overlapping case)"`, which
registers/activates `req173_v1_capless.wat`, invokes it (`{:ok, v1_id, [111]}`),
then registers/activates `req173_v2_capless.wat` and asserts the next invocation
returns `{:ok, v2_id, [222]}`. This proves version resolution genuinely re-reads
`current_version_id` at each fresh checkout, independent of the concurrency
mechanism itself (which the blocked test above additionally covers for the
*overlapping* case, once fixed).

### AC3 — "the two module versions used are observably different in output"

The `req173_v1_gated.wat`/`req173_v2_gated.wat` pair differs in three independent,
cross-checkable ways (design SS8.2): which capability each needs to instantiate,
whether the invocation blocks, and the returned literal (111 vs. 222) — mirrored in
the capless pair for the tests that can actually run. The blocked SS8.4 scenario's
step 13 (`assert result_a != result_b`) states this explicitly per the design; the
passing `"activating a second version..."` test demonstrates the same
distinguishability (`[111]` vs. `[222]`) for the non-overlapping case.

### AC4 — "the prior version's resources are released only after its last
in-flight invocation completes, not at activation time"

Two halves, per design SS6's two trigger points:
- **Trigger point 2 ("nothing to wait for")** — passing today:
  `"design SS6 trigger point 2: activating away from a version whose ref_count is
  already 0 releases it IMMEDIATELY..."` registers/activates
  `req173_v1_capless.wat` (never invoked, `ref_count` stays 0), then
  registers/activates `req173_v2_capless.wat`, and asserts `version_status/2` for
  v1 flips straight to `:released` — proving release fires inside `activate/2`
  itself when there is nothing in flight, with no further external action.
- **Trigger point 1 (an in-flight invocation held across activation)** — this is
  exactly the half design SS8.4 steps 8/12 assert (superseded, NOT released, while
  A is parked; released immediately after A's own release call) and is currently
  unreached — see "Blocking finding."

Mutation-tested (see below): inverting the release predicate's `ref_count == 0`
check is caught by the trigger-point-2 test above.

### AC5 — "when the new version's manifest declares a DIFFERENT capability set, an
in-flight invocation of the prior version keeps the prior version's capability set,
and the new invocation gets the new one"

- **Dynamic, in-flight proof** (design SS8.4 steps 9/11/14) — unreached today, same
  root cause; the blocked test asserts both invocation A's success (proving it kept
  `"service:call"` after v2's activation stripped it from "current") and invocation
  B's success (proving it got `"var:write"` despite A still being in flight on the
  stripped-of-that-grant prior version).
- **Static "defense in depth" proof** (design SS8.4 step 14) — passing today,
  independent of the blocking finding:
  `describe "AC5 defense in depth: v1_manifest/v2_manifest are disjoint..."` calls
  `CapabilityGate.build_import_table/2` directly on each manifest and asserts
  `v1_manifest` grants `platform_call_service` only, `v2_manifest` grants
  `write_variable` only — pinning that the manifests themselves are as disjoint as
  design SS8.3 claims, independent of `invoke/4`'s own code.

### AC6 — "`mix test` / `mix compile --warnings-as-errors` pass with real output
quoted"

`mix compile --warnings-as-errors` passes cleanly (quoted in the handoff). `mix
test` for this suite is 16/17 — the one failure is the design SS8.4 scenario,
failing for the documented, verified reason above (a genuine pre-existing

new test, and the full pre-existing `test/letflow/engine/wasm/` suite, passes

## Error-path and idempotency coverage (not separately named as an AC, but part of
`invoke/4`/`activate/2`/`current_version/1`/`version_status/2`'s own declared
contract, design SS3)

- `current_version/1`/`activate/2`/`version_status/2`/`invoke/4` for an unknown
  `module_name` each return their own declared `{:error, {:unknown_module, _}}` (or
  `{:unknown_module, _}` for `version_status/2`, which is not error-wrapped per its
  own spec).
- `activate/2` for a known module but an unregistered `version_id` returns
  `{:error, {:unknown_version, module_name, version_id}}`.
- `invoke/4` against a module with no active version returns
  `{:error, {:no_active_version, module_name}}`.
- A no-op activation (re-activating the already-current version) is idempotent —
  does not disturb `current_version/1` or release the version.
- A brand-new, registered-but-never-activated version reports `:superseded` (not
  `:active`) from `version_status/2` — design SS2's `status_for/2` never treats an
  unactivated version as current.

## Mutation testing performed (this project's discipline for a brand-new module —
see `docs/agents/workflows/WF-03_issue_resolving.md`'s "When the pre-fix failure is
'the code under test does not exist'")

Since `ModuleVersionRegistry` is an entirely new module, the ordinary
fail-before-fix/pass-after-fix check is vacuous (every test would simply raise
`UndefinedFunctionError` against a nonexistent module). Per that section's
"mutate the shipped logic instead" requirement, four mutants were applied, in
place, one at a time, against `lib/letflow/engine/wasm/module_version_registry.ex`
(baseline `md5sum`: `40eed577159b3d9276d4fb7442c0ca75`), each run against
`test/letflow/engine/wasm/module_version_registry_test.exs`'s full 17 tests
(baseline 16/17 passed — the one pre-existing failure is the blocked SS8.4
scenario), then reverted and the revert verified (`md5sum` back to baseline, `git
status --porcelain`/`git diff --stat` empty) before moving to the next:

| # | Mutant | Result | Caught by |
|---|---|---|---|
| 1 | `activate/2`'s `handle_call` clause set `current_version_id: previous_id` instead of `current_version_id: version_id` (activation silently no-ops) | **12/17** (4 new failures) | "activate/2 makes a version current...", "activating a second version supersedes the first...", "a no-op activation is idempotent...", design SS6 trigger-point-2 test |
| 2 | `apply_release_predicate/2`'s guard inverted: `entry.ref_count != 0` instead of `== 0` | **15/17** (1 new failure) | "design SS6 trigger point 2: activating away from a version whose ref_count is already 0 releases it IMMEDIATELY..." |
| 3 | `run_call/6`'s success branch hardcoded `{:ok, 999, result}` instead of `{:ok, snapshot.version_id, result}` | **14/17** (2 new failures) | "activate/2 makes a version current, and a later invocation resolves to it...", "activating a second version supersedes the first..." |
| 4 | `checkout`'s `handle_call` swapped the `:unknown_module`/`:no_active_version` error tuples between its two failure clauses | **14/17** (2 new failures) | "invoke/4 against a module with no active version", "invoke/4 against a wholly unknown module_name" |

Each mutant was demonstrably caught by a *different* new test (or set of tests),
targeting a distinct trap: activation not taking effect, premature release,
misreported version identity on success, and misclassified registry errors — not
one incidental assertion catching all four. Revert verified after each mutant
(shown per-mutant in the handoff's quoted output) and again at the end of the
whole session.
