## What this requirement's decision means for test scope

The design (§2) declines to adopt instance pooling for WASM-13. §3 records
**INV-174-1**: per-invocation isolation already holds *by construction*, not by a
reset mechanism, because both scoped call sites (`ModuleVersionRegistry.invoke/4` and
`PluginHandler.run_guest/3`) call `Wasmex.start_link/1` with no `:store` option, so
`wasmex` allocates a brand-new `Store` (and therefore zero-initialized linear memory)
on every single invocation. There is no reset mechanism, no pool, no superseded-version
exclusion, and no p50 benchmark to test (design §4.5 explains why each of those is N/A
under a decline). The only property this requirement's acceptance criteria require a
test for is INV-174-1 itself, independently for both call sites (design §4, opening
paragraph: "the two paths use different instantiation call sites... a single test
covering only one would leave the other's isolation unverified").

## Fixture note: `req174_memory_write.wat` needed the plugin ABI too

The design's §4.1 sketch specified only `memory` + `write_marker` + `read_marker`.
Live-running Test A against that shape failed at `register_version/3`'s first call
with `{:error, {:invalid_abi, [missing: "init", missing: "execute", missing: "deinit",
missing: "get_capabilities", missing: "alloc"]}}` — `ModuleVersionRegistry.
register_version/3` delegates to `ModuleRegistry.register/1`, which (per REQ-166,
independent of any manifest or capability) requires all five plugin-ABI exports on
*any* module, not just ones declaring imports. `req173_v1_capless.wat` established
this exact precedent (its own comment documents the same requirement). The fixture was
extended with the same five constant-returning, zero-import ABI exports
`req173_v1_capless.wat` uses, alongside the original `write_marker`/`read_marker`
pair — `PluginHandler.run_guest/3` never calls `ModuleRegistry.register/1` at all, so
Test B does not depend on these exports existing, but both tests share the one fixture
file per the design's intent.

## Discriminating-power verification (mutation-testing discipline)

Per this project's history of test-design flaws that looked right but would pass
regardless of the property under test, the `[0]`-not-`[1]` assertion shape was
empirically verified to actually discriminate a real isolation violation, using a
throwaway script (not committed, no production code under `lib/letflow/engine/wasm/`
touched — confirmed via `git diff --stat -- lib/letflow/engine/wasm/` showing no
output before and after) that called the real `wasmex` NIF directly:

1. **First attempt — sharing only a `Wasmex.Store` across two separate
   `Wasmex.start_link/1` calls** (one instance for `write_marker`, a second,
   freshly-instantiated one for `read_marker`, both given the same `Store` struct):
   `read_marker` returned `0`, not `1`. This showed that a shared `Store` alone,
   without a shared `Instance`, does not leak linear memory in this `wasmex` version —
   each `Wasmex.Instance` gets its own memory allocation from the module's memory
   section at instantiation, even against a reused `Store`. (This refines, for the
   record, decision 0014(e)'s framing of the risk as purely "Store reuse" — the
   mechanism that actually leaks is instance/pid reuse, not Store reuse alone; §1.2 of
   the design already establishes that the shipped call sites never pass a `:store` key
   at all, so this refinement does not change the design's conclusion.)
2. **Second attempt — reusing the SAME instance (`pid`) for both calls**, i.e.
   `write_marker` then `read_marker` invoked via `Wasmex.call_function/4` against one
   single `Wasmex.start_link/1`-started process, with no restart between them: real
   output —
   ```
   write_marker result (single shared instance): 0
   read_marker result (SAME instance/pid reused across the two calls): 1
   ```
   This confirms the assertion shape used in both committed tests (`[0]`, not `[1]`)
   would fail loudly (observe `[1]`) under a real instance-reuse defect — exactly the
   shape a hand-built, naively-implemented pool could introduce by handing the same
   `pid` to two invocations without a reset step. The tests are not a tautology; they
   have real discriminating power against the specific defect class this requirement's
   decision record exists to avoid.

## What this requirement does NOT need to test, and why

Per design §4.5: no memory-reset-mechanism test (none exists — pooling declined), no
superseded-version-exclusion test (only meaningful for an adopted pool that reuses
instances — REQ-173's existing hot-reload tests already cover the only
version-currency property that exists in a no-pooling design), no p50-latency
benchmark (WASM-13's own acceptance criterion is a property of an *adopted* pool
amortising cost against a baseline; with pooling declined, every invocation *is* the
baseline, so there is no comparison to record).
