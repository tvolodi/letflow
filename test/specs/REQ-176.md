# Test Spec: REQ-176 — DLQ schema and `Letflow.Dlq` core entry lifecycle

**Requirement:** REQ-176 (stage S6, queue task 351, GH#696). Design authority:
`lib/letflow/design/req176-dlq-core.md` (commit 1959adf). Implementation authority:
`lib/letflow/dlq.ex`/`lib/letflow/dlq/entry.ex`/
`priv/repo/migrations/20260829000001_create_dlq_entries.exs` (commit b5a028d), already
passed SECURITY-REVIEWER and REVIEWER (REVIEWER filed ISS-0353, a deferred, non-blocking
idiom gap in `insert_changeset/2`'s cast list — not exercised by any test here since it
is not exploitable through `enqueue/2`'s pre-sanitized attrs).

Acceptance criteria (verbatim from the Step 3 handoff):

1. the `dlq_entries` table lives inside each tenant's Postgres schema with a
   `tenant_id` column retained, matching decision 0003 Decision B's pattern —
   verified by inspecting the migration
2. `enqueue/1` creates an entry with status `"pending"`, `retry_count` 0, and a
   `created_at` timestamp; `list/2` is tenant-scoped, demonstrated by an entry
   enqueued under tenant A being absent from a `list/2` call scoped to tenant B
3. `retry/2` on a `"pending"` or `"retrying"` entry transitions it to `"retrying"`,
   appends a `retry_history` entry with `attempt_no`/`attempted_at`/`outcome`/
   `error_message` field names matching `DlqRetryAttempt` exactly, and increments
   `retry_count`; `retry/2` on a `"resolved"` or `"discarded"` entry returns a
   conflict error and leaves status, retry_count and retry_history unchanged — four
   tests, one per starting status
4. `discard/2` on a `"pending"` or `"retrying"` entry transitions it to
   `"discarded"`; `discard/2` on an already `"resolved"` or `"discarded"` entry
   returns a conflict error rather than silently succeeding
5. `list/2` filters by `entry_type` and by `status` independently, each
   demonstrated narrowing a result set that contains rows of more than one value,
   and supports cursor pagination: given more rows than one page, the first page's
   `next_cursor`, passed back in, returns the next distinct page with no repeated or
   skipped ids
6. no route or controller file is added or modified, confirmed by `git diff --stat`
   scoped to this requirement's commits
7. `mix test` and `mix compile --warnings-as-errors` both pass with real output
   quoted

**Test tier:** unit+integration (`Letflow.DataCase`, real Postgres, real tenant
schema provisioning via `Letflow.TenantFixture`) — no route exists yet (REQ-178's
scope), so every test calls `Letflow.Dlq`'s functions directly, mirroring
`test/letflow/definitions/promotion_test.exs`'s established pattern for a
context-module-only test with no HTTP layer in front of it.

**Test file:** `test/letflow/dlq_test.exs`.

## 1. Acceptance-criteria -> test-case mapping

### AC1 — migration: schema-per-tenant, `tenant_id` retained

**Why this test exists, not just a restatement:** the design's own isolation claim
(the Postgres schema, not the `tenant_id` column, is the actual boundary) is only
checkable by querying `information_schema` directly against a real provisioned tenant
schema — reading the migration source is a static claim, this proves the column and
the schema-scoping both exist as shipped, and that no `dlq_entries` table leaked into
`public`.

* `describe "AC1: dlq_entries migration -- schema-per-tenant with tenant_id retained"`
  — provisions a real tenant, queries `information_schema.columns` for the tenant's
  own schema and asserts `tenant_id`/`id`/`status` are present, then queries
  `information_schema.tables` scoped to `public` and asserts no `dlq_entries` row
  exists there.

### AC2 — `enqueue/2` initial state + `list/2` tenant scoping

**Why these tests exist:** `enqueue_attrs()`'s own type excludes `status`/
`retry_count`/`retry_history`/`created_at`/`tenant_id` as caller-settable keys (design
§3.1) — the test proves the *defaults* the function itself injects are exactly what
the acceptance criterion names, not merely that *some* row got inserted. The
tenant-scoping test exists because `list/2` issues exactly one query scoped by
`opts[:prefix]` with no query-level `tenant_id` filter at all (design §3.2) — the
Postgres schema is the entire isolation mechanism, so a regression that dropped the
`prefix:` option from `Repo.all/2` would leak (or 500 on) every other tenant's rows;
only a real two-tenant test can catch that class of bug.

* `describe "AC2: enqueue/2 initial state"` — one entry enqueued, in-memory reply and
  a fresh `Repo.get!/3` reload both asserted: `status == :pending`, `retry_count ==
  0`, `retry_history == []`, `created_at` is a real `DateTime.t()`.
* `describe "AC2: list/2 is tenant-scoped"` — one entry enqueued under tenant A;
  `list/2` scoped to tenant B returns `[]`; `list/2` scoped to tenant A returns
  exactly that entry.

### AC3 — `retry/2`'s four starting-status cases

**Why these tests exist:** the state machine is exhaustive over `DlqStatus`'s four
values (design §3.4) and the `:pending`/`:retrying` cases are specified to have the
*same effect* despite different starting states — a single happy-path test would miss
a regression that special-cased one of the two. The two conflict tests exist because
`retry/2`'s contract is "the row is read but not written" — asserting only the error
shape would miss a regression that still mutated `retry_count`/`retry_history` before
returning the error.

* `describe "AC3: retry/2 from :pending"` — asserts the transition to `:retrying`,
  `retry_count == 1`, and the appended `retry_history` entry's key set is exactly
  `[:attempt_no, :attempted_at, :error_message, :outcome]` (not merely "contains
  attempt_no"), plus `attempt_no == 1`, `outcome == "failed"`, `error_message == nil`,
  `attempted_at` a binary (ISO-8601 string, not a raw `DateTime.t()`).
* `describe "AC3: retry/2 from :retrying"` — calls `retry/2` twice; asserts the second
  call still lands on `:retrying` (not e.g. rejected as a no-op transition),
  `retry_count == 2`, and both `retry_history` entries present with `attempt_no` 1
  and 2 respectively. (`retry_history` elements decode from Postgres jsonb as
  string-keyed maps on any element that made a DB round-trip and only the entry
  freshly appended this call stays atom-keyed in the in-process return value — this
  is `{:array, :map}`'s ordinary non-`embeds_many` behavior per design §2.2, not a
  defect, so the test normalizes both key shapes before comparing values.)
* `describe "AC3: retry/2 from :resolved"` — forces `:resolved` directly (no public
  function in this module ever produces that state, design §3: only
  enqueue/list/get/retry/discard exist), asserts
  `{:error, {:invalid_state, :resolved}}`, and asserts a fresh reload's `status`,
  `retry_count`, `retry_history` are byte-for-byte the pre-call values.
* `describe "AC3: retry/2 from :discarded"` — reaches `:discarded` through the public
  `discard/2` API (no forced state needed here), asserts
  `{:error, {:invalid_state, :discarded}}` and the same unchanged-fields guarantee.

### AC4 — `discard/2`'s terminal transitions + already-terminal conflicts

**Why these tests exist:** "calling discard twice never silently succeeds" (design
§3.5) is exactly the kind of idempotency claim that a naive `UPDATE ... SET status =
'discarded'` (with no starting-state guard) would violate without any test noticing —
the second-call test specifically re-calls `discard/2` on an already-`:discarded` row
via the *same public function*, not a forced state, to prove the guard is real.

* `describe "AC4: discard/2 from :pending"` — transitions to `:discarded`.
* `describe "AC4: discard/2 from :retrying"` — reaches `:retrying` via `retry/2`
  first, then `discard/2` transitions to `:discarded`; asserts `retry_count`/
  `retry_history` are untouched by `discard/2` (design §3.5's "only `status`
  changes").
* `describe "AC4: discard/2 from :resolved"` — forces `:resolved`, asserts
  `{:error, {:invalid_state, :resolved}}`, unchanged `retry_count`.
* `describe "AC4: discard/2 from :discarded (twice)"` — calls `discard/2`, then calls
  it again on the same id; the *second* call asserts
  `{:error, {:invalid_state, :discarded}}`.

### AC5 — `list/2`'s independent `entry_type`/`status` filters + cursor pagination

**Why these tests exist:** "independent" is the acceptance criterion's own word —
proving it requires a result set that genuinely contains more than one value of each
filtered column, then asserting the filter narrows to exactly the matching subset (a
single-value fixture could pass by accident even if the `WHERE` clause were dropped
entirely, matching Mutation D/E below). The pagination test exists because `list/2`'s
keyset mechanism (design §3.2) is the one place this requirement's own SQL is more
than "just add a LIMIT" — an off-by-one or a missing tie-breaker column would either
drop or duplicate a row at the page boundary, which only a real multi-page test with a
set-equality check (not just "does page 2 return something") can catch.

* `describe "AC5: list/2 filters by entry_type and status independently"` — three
  tests: `entry_type` narrows a 3-distinct-type result set to one; `status` narrows a
  2-distinct-status (`:pending`/`:retrying`) result set to one each; both filters
  combined together narrow to exactly the one row matching both.
* `describe "AC5: list/2 cursor pagination"` — three entries, `page_size: 1`; walks
  all three pages via each page's own `next_cursor`, asserts `next_cursor` is present
  on pages 1-2 and `nil` on page 3, and asserts the *union* of all three pages' ids
  has no duplicates and equals exactly the three inserted ids (catches both a dropped
  row and a duplicated boundary row).

### AC6 — no route or controller file added or modified

**Why these tests exist:** REQ-176's own explicit scope boundary (design §0) says no
route/controller exists yet (REQ-178's scope) — this is a structural, not behavioral,
claim, so it is checked structurally rather than invented as a fake behavioral
assertion. Two independent checks, since they catch different regressions: the
commit-scoped `git diff --stat` check would catch a future amendment to the b5a028d
commit itself, while the working-tree check would catch a file added later (by another
commit) that a commit-scoped diff wouldn't see.

* `describe "AC6: no route or controller file was added by REQ-176 (commit b5a028d)"`
  — `git show --stat --format= b5a028d`'s changed-file list contains no path matching
  `routers/` or `controller`; separately, `lib/letflow/routers/dlq.ex` does not exist
  in the working tree and `Letflow.Routers.Dlq` does not load.

### AC7 — `mix test`/`mix compile --warnings-as-errors` pass

Not a test-file criterion — verified directly by running both commands and quoting
real output (see the TEST-DESIGNER handoff report for the actual command output).

## 2. Mutation-testing discipline (performed, not merely claimed)

Per `docs/agents/workflows/WF-02_requirement_implementation.md` Step 3, each mutation
below was applied to the real shipped implementation, confirmed **not** caught by the
pre-existing suite (this module has zero other test-file references anywhere in the
codebase per `grep -rl "Letflow.Dlq\\b"`, so `test/letflow/support/tenant_fixture_test.exs`
— the only pre-existing test that touches `dlq_entries` at all, via its table-count
oracle — stands in for "the whole pre-existing suite" and was run and confirmed green
under every mutation below), then confirmed caught once this file's tests were
restored, then reverted with `md5sum`/`git diff --stat` confirming a byte-identical
revert:

1. **AC2 (enqueue defaults):** `enqueue/2`'s injected `status`/`retry_count` flipped
   from `:pending`/`0` to `:retrying`/`1`. Not caught by the pre-existing suite,
   caught by 5 of this file's tests. Reverted, `md5sum` confirmed.
2. **AC2 (tenant scoping):** `list/2`'s `Repo.all(query, prefix: prefix)` changed to
   `Repo.all(query)` (drops the tenant-scoping option). Not caught by the pre-existing
   suite, caught by 5 of this file's tests. Reverted, `md5sum` confirmed.
3. **AC3 (retry conflict guard):** `apply_retry/2`'s
   `when status in [:pending, :retrying]` guard removed (matches any status). Not
   caught by the pre-existing suite, caught by the `:resolved`/`:discarded` conflict
   tests. Reverted, `md5sum` confirmed.
4. **AC4 (discard conflict guard):** `apply_discard/2`'s same guard removed. Not
   caught by the pre-existing suite, caught by the `:resolved`/twice-`:discarded`
   conflict tests. Reverted, `md5sum` confirmed.
5. **AC5 (entry_type filter):** `filter_by_entry_type/2` made a no-op regardless of
   its argument. Not caught by the pre-existing suite, caught by both the
   `entry_type`-only and combined-filter tests. Reverted, `md5sum` confirmed.
6. **AC5 (cursor seek predicate):** `filter_by_list_cursor/2`'s tuple comparison
   changed from `<` to `<=` (re-includes the boundary row, producing a repeated id
   across pages). Not caught by the pre-existing suite, caught by the pagination test.
   Reverted, `md5sum` confirmed.
7. **AC1 (migration column):** the `tenant_id` column removed from the migration.
   Not caught by the pre-existing suite (its oracle checks table *count*, not
   per-table columns), caught by 9 of this file's tests including the dedicated AC1
   test. Reverted, `md5sum` confirmed.
8. **AC6 (structural):** a dummy `lib/letflow/routers/dlq.ex` file added. Caught by
   the working-tree-existence half of the AC6 test. Deleted afterward, `git status`
   confirmed clean.
