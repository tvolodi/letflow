# Test Spec: REQ-177 — DLQ landing hooks (SERVICE_TASK exhaustion + instance ERROR)

**Requirement:** REQ-177 (stage S6, queue task 352, GH#697). Design authority:
`lib/letflow/design/req177-dlq-hooks.md` (commit 4070492). Implementation authority:
`lib/letflow/engine.ex`'s `land_service_task_exhaustion/2` (Hook A) and
`lib/letflow/engine/execution_error.ex`'s `:execution_error_dlq_landing` `Multi` step
(Hook B) (commits fdb096a/8206de9), already passed SECURITY-REVIEWER and REVIEWER.

This spec covers the acceptance criteria not already covered by ELIXIR-DEV's own
regression test (`test/letflow/engine_execution_error_test.exs`'s combining-mark
truncation test, which addresses the INV-8 codepoint-vs-grapheme truncation finding
only) and by that same file's pre-existing AC2/AC3 coverage of Hook B's own ERROR-path
landing and same-transaction atomicity. This document's own two test files are:

- `test/letflow/engine_dlq_landing_test.exs` (new) — Hook A's own exhaustion/
  non-exhaustion split, and the AC4 non-effects test.
- `test/letflow/engine_execution_error_test.exs` (pre-existing, unmodified by this
  handoff) — Hook B's AC2/AC3 coverage and the truncation regression, cross-referenced
  below rather than duplicated.

Acceptance criteria (verbatim from the Step 3 handoff):

1. a SERVICE_TASK dispatch driven to retry-exhaustion (`attempt_index == retry_limit`)
   produces exactly one `dlq_entries` row via `enqueue/1`, with `entry_type` `"event"`,
   `instance_id` set, and `full_reason` naming the classified failure kind — read back
   from the database, not asserted from the caller's own return value
2. an instance driven to ERROR via REQ-061's execution-error path produces exactly one
   `dlq_entries` row via `enqueue/1`, with `entry_type` `"event"`, `instance_id` set,
   and `full_reason` equal to the persisted EXECUTION_ERROR event's own `reason` field
3. the ERROR-path DLQ landing is in the same transaction as REQ-061's status flip and
   event append: forcing the DLQ insert to fail leaves the instance status, the
   EXECUTION_ERROR event, and the DLQ table all unchanged, verified by reading all
   three back
4. a test explicitly asserts that calling REQ-176's `retry/2` against one of these two
   entries transitions the DLQ entry to `"retrying"` but does NOT re-invoke the
   original SERVICE_TASK dispatch and does NOT change the instance's own status away
   from ERROR — naming both non-effects, not just the one effect that does happen
5. the moduledoc for both hook sites names REQ-176's `retry/2`
   no-op-beyond-the-DLQ-entry behavior as a deferred follow-up (naming what would need
   to exist for it to do more) rather than leaving it unremarked
6. no file outside the two named hook call sites and their tests is modified,
   confirmed by `git diff --stat`
7. `mix test` and `mix compile --warnings-as-errors` both pass with real output quoted

**Test tier:** unit+integration (`Letflow.DataCase`, real Postgres, real tenant schema
provisioning via `Letflow.TenantFixture`), mirroring
`test/letflow/engine_execution_error_test.exs`'s and `test/letflow/dlq_test.exs`'s own
established pattern for this class of test. No route/controller exists yet for
`Letflow.Dlq` (REQ-178's scope) or for a SERVICE_TASK dispatch orchestrator (no
requirement yet) — every test calls `Letflow.Engine`/`Letflow.Dlq` functions directly.

## 1. Acceptance-criteria -> test-case mapping

### AC1 — Hook A: genuine exhaustion lands exactly one DLQ row, read back from the DB

**Why this test exists, not just a restatement:** the design's own boundary condition
(§3) is subtle — Hook A must fire on `is_retriable_failure(kind) == true and
attempt_index >= retry_limit`, and must NOT fire merely because
`ServiceTask.decide_failure/3` would return `:give_up` (which also covers the
immediately-non-retriable case). A test that only calls the function and checks its
own `{:ok, _}` return proves nothing about what got persisted — the requirement's own
wording is explicit that the row must be read back independently.

- `test/letflow/engine_dlq_landing_test.exs`, describe `"Hook A -- genuine SERVICE_TASK
  retry exhaustion lands a DLQ entry"`:
  - `"attempt_index == retry_limit with a retriable failure kind produces exactly one
    dlq_entries row"` — calls `land_service_task_exhaustion/2` with
    `last_failure_kind: :timeout` (retriable), `attempt_index: 3`, `retry_limit: 3`
    (the literal boundary the AC names), then queries `Letflow.Dlq.Entry` by
    `instance_id` directly (not the function's own `{:ok, result}`) and asserts
    `entry_type == "event"`, `instance_id` set, `full_reason` names `"timeout"` and
    `"retries exhausted"`.
  - `"attempt_index above retry_limit (>=, not strictly ==) still counts as
    exhaustion"` — `attempt_index: 5`, `retry_limit: 3`, confirms the `>=` reading
    the design doc gives for the AC's `==` wording.

**Mutation-testing performed:** flipped `attempt_index >= retry_limit` to
`attempt_index > retry_limit` in `land_service_task_exhaustion/2`. The pre-existing
suite (`engine_execution_error_test.exs`, `dlq_test.exs`, `service_task_test.exs` — 66
tests) still passed with the mutant in place. The first test above
(`attempt_index == retry_limit`) failed under the mutant, as expected (3/5 passed in
this file). Reverted; `md5sum lib/letflow/engine.ex` before/after:
`a81217ec39c883b1c0f0ed3bd120f462` both times; `git diff --stat` empty for the file.

### Non-exhaustion companion (AC1's own negative case, named in the handoff's task)

**Why this test exists:** without it, a regression that makes Hook A fire
unconditionally (e.g. dropping the `is_retriable_failure` check) would pass AC1's own
positive test and go undetected — this is the test that actually pins the boundary
from the other side.

- describe `"Hook A -- non-exhaustion companion does not land a DLQ entry"`:
  - `"a non-retriable failure kind returns {:error, :not_exhaustion} and lands
    nothing"` — `last_failure_kind: :http_non_2xx`, `attempt_index: 0`,
    `retry_limit: 3`. Asserts `{:error, :not_exhaustion}`, zero `dlq_entries` rows,
    and the instance projection stays `:active` (neither `Dlq.enqueue/2` nor
    `set_instance_error/2` was called).
  - `"a retriable kind below retry_limit (not yet exhausted) also lands nothing"` —
    `last_failure_kind: :rate_limited_429`, `attempt_index: 1`, `retry_limit: 3`. Same
    assertions.

**Mutation-testing performed:** replaced the guard with
`attempt_index >= retry_limit or attempt_index >= 0` (always true — simulates
dropping the retriable-kind check entirely). Pre-existing suite (66 tests) still
passed. Both non-exhaustion tests above failed under the mutant (3/5 passed in this
file). Reverted; `md5sum lib/letflow/engine.ex` matches the pre-mutation value again;
`git diff --stat` empty.

### AC2/AC3 — Hook B's ERROR-path landing and same-transaction atomicity

Already covered by `test/letflow/engine_execution_error_test.exs`'s pre-existing

### AC4 — `retry/2` is a landing-only no-op: both non-effects named explicitly

**Why this test exists, not just a restatement:** `Letflow.Dlq.retry/2` was already
tested (REQ-176, `dlq_test.exs`) for its own state-machine transition in isolation.
What is new here is the **cross-module** claim: that calling it against a
REQ-177-landed entry has no observable effect on the *instance* it came from. A test
that only asserts the entry's own status transition would not prove the absence of
coupling — the acceptance criterion is explicit that both non-effects must be named,
not just the one effect that does happen.

- describe `"AC4 -- Dlq.retry/2 against a Hook-A-landed entry is a no-op beyond the
  entry itself"`:
  - Lands an entry via `land_service_task_exhaustion/2` (the instance is now `:error`).
    Calls `Dlq.retry/2` against it. Asserts:
    - the one effect: `retried_entry.status == :retrying`, `retry_count == 1`.
    - non-effect 1: `instance_projections.status` is still `:error` after the call
      (read back independently, before/after), and `error_detail` is byte-for-byte
      unchanged.
    - non-effect 2: the durable event log gained **zero** new events (a real
      re-dispatch would be expected to produce at least one observable event), and no
      second `dlq_entries` row was landed for the instance — `retry/2` touched only
      the one row's own columns.

**Mutation-testing performed:** since no SERVICE_TASK transport exists yet to inject a
call-count double into (design doc §9 OQ-1), and `Letflow.Dlq`/`Letflow.Engine`'s
shipped code has no coupling between `retry/2` and the instance's own status to begin
with, the mutant here **simulates the regression this test guards against**: a
temporary edit to `Letflow.Dlq`'s private `apply_retry/2` (in `lib/letflow/dlq.ex`,
reverted immediately after measurement, never committed) that additionally flips
`instance_projections.status` to `:active` on a successful retry — exactly the kind of
accidental future coupling AC4 exists to catch. The pre-existing suite
(`dlq_test.exs` + `engine_execution_error_test.exs`, 26 tests) still passed with the
mutant in place (neither file asserts on `instance_projections.status` after a
`retry/2` call). The AC4 test above failed under the mutant (4/5 passed in this file).
Reverted; `md5sum lib/letflow/dlq.ex` before/after: `e59d76b211e7de196f92e15816e2afb1`
both times; `git diff --stat` empty for the file. `lib/letflow/dlq.ex` is not modified
in this handoff's final diff — confirmed by `git status --short` showing only the new
test file as untracked.
