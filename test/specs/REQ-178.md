# Test Spec: REQ-178 — `Letflow.Routers.Dlq` route/controller layer

**Requirement:** REQ-178 (stage S6, queue task 353, GH#698). Design authority:
`lib/letflow/design/req178-dlq-routes.md`. Implementation authority:
`lib/letflow/routers/dlq.ex` plus the one `forward("/dlq", ...)` line in
`lib/letflow/plugs/api_pipeline.ex`, already passed SECURITY-REVIEWER (Step 2c) and
REVIEWER (Step 2d, see `handoffs/WF02-REQ178-20260829/step-03-test-designer.json` for
the full sign-off summary).

Test file: `test/letflow/routers/dlq_test.exs`. Uses `Letflow.DataCase` (real Postgres)
and `Letflow.TenantFixture` for real provisioned tenant schemas, matching
`test/letflow/routers/tasks_test.exs`'s own established idiom for this class of router
test — direct `Letflow.Routers.Dlq.call/2` dispatch, `conn.assigns[:auth_context]` set
directly (bypassing `AuthPipeline`), same cross-tenant-identical-404 idiom.

Acceptance criteria (verbatim from the Step 3 handoff):

1. `GET /api/v1/dlq` returns a body shaped exactly `{items: [...], next_cursor:
   string|null}`, and each item's field names match `DlqEntry`'s, verified against
   `web/src/types/api.ts` rather than a hand-invented shape.
2. `GET /api/v1/dlq` honors `status`, `source_type`, `search`, `cursor` and
   `page_size` independently, each with its own test demonstrating the filter
   narrows the result set.
3. `POST /api/v1/dlq/:id/retry` and `.../discard` both require the `DlqOperate`
   permission — a caller holding no role with that permission receives 403, and a
   caller from a different tenant naming a real id belonging to tenant A receives
   404, never 403.
4. `POST /api/v1/dlq/:id/retry` and `.../discard` against a non-existent id return
   404, and against an id already `"resolved"` or `"discarded"` return a
   409-shaped conflict rather than a generic 500.
5. the list endpoint is tenant-scoped (a fixture entry in another tenant never
   appears), and the route module's moduledoc states explicitly that R-Co's
   `dlq.zig` was not inspected and that `web/src/api/dlq.ts`/`web/src/types/api.ts`
   were the binding contract instead.

## Test cases and rationale

### AC1 — list shape (`describe "AC1: GET /dlq returns {items, next_cursor}..."`)

One test enqueues a single entry and asserts the top-level body has exactly the two
keys `items`/`next_cursor` (not three, no `has_more` — design §7 OQ-1 was deliberately
resolved against emitting it), and that the one item's key set is exactly the 18-key
allowlist `dlq_entry_json/1` builds — not a subset/superset check, so a silently
dropped or silently added field is caught. Exists because the design explicitly calls
out two divergences from the naive "just mirror `CursorPage<T>`" reading (§7 OQ-1,
OQ-2); a presence-only assertion would not catch either regressing back to the naive
shape.

### AC2 — independent filters (`describe "AC2: GET /dlq filters"`)

Six... actually five tests (`status`, `source_type`, `search`, `instance_id`,
`page_size`) — `cursor` is exercised as part of the `page_size` test since a cursor is
only meaningful once a first page exists. Each test seeds at least two entries with
different filterable values and asserts the filtered call returns only the matching
row(s), proving narrowing rather than merely "the endpoint doesn't error." The
`source_type` test specifically exists to catch a regression of the one field-rename
this router performs (`source_type` query param -> `entry_type` `Letflow.Dlq.list/2`
key) reverting to a same-name passthrough, which would silently produce an
always-empty-or-always-full result depending on direction.

### AC3 — permission gate and cross-tenant-404 (`describe "AC3: retry/discard require DlqOperate"`)

Three tests, matching the task's explicit "three distinct tests" framing:

1. `POST retry` with a `TASK_WORKER`-only caller (a real role that does **not** hold
   `DlqOperate` per the real `role_allows?/2` matrix, not an invented role) -> 403,
   plus no state change on the entry.
2. `POST discard`, same shape, -> 403, no state change.
3. A `PLATFORM_ADMIN` caller in tenant A naming a real id that only exists in tenant
   B's schema -> 404 for both retry and discard, identical response bytes to a
   genuinely-nonexistent id, and the tenant-B row is left untouched. This is the one
   test proving "never 403" for the cross-tenant case specifically (a caller who
   *does* hold the permission, so a wrongly-scoped tenant check that leaked into a
   403 branch would be caught here, whereas the no-permission tests above could not
   catch it).

### AC4 — not-found vs terminal-state (`describe "AC4: ..."`)

Four tests, one per {retry, discard} x {not-found, terminal}:

* not-found tests use a freshly generated UUID that was never inserted -> 404.
* terminal tests force an entry to `:resolved` (retry) or drive it to `:discarded`
  via the real `discard/2` (discard) and then re-call the same operation -> 409, with
  the entry's `status`/`retry_count` asserted unchanged afterward. These exist
  specifically because `Letflow.Dlq`'s own `@spec`s enumerate no `Ecto.Changeset.t()`
  branch (design §6) — a regression that let a `{:invalid_state, _}` tuple fall
  through to `Response.internal_error/1` (500) would only be caught by a test that
  actually drives that exact tuple, not by a happy-path test.

### AC5 — tenant scoping (`describe "AC5: GET /dlq is tenant-scoped"`)

One test: an entry enqueued under tenant A is absent from tenant B's list call. Exists
at the router layer (not just `Letflow.Dlq`'s own AC2 coverage in
`test/letflow/dlq_test.exs`) to prove the router itself threads
`conn.assigns.scoped_opts` through rather than, say, a hardcoded or caller-suppliable
prefix.

### Moduledoc contract-source statement (`describe "moduledoc states R-Co's dlq.zig..."`)

One structural test reading the compiled moduledoc via `Code.fetch_docs/1` and
asserting it names `dlq.zig`, the phrase "not inspected", and both
`web/src/api/dlq.ts` and `web/src/types/api.ts`. This is a documentation
acceptance criterion, not application behavior, but it is still a real regression
guard: a future edit that quietly strips this disclosure would fail this test.

## Mutation testing performed

Each mutation below was applied to `lib/letflow/routers/dlq.ex`, confirmed to fail the
named test(s), then reverted; `git diff` against the pre-mutation file was confirmed
empty (byte-identical) after every revert.

1. **Filter removal** — `entry_type: non_empty(Map.get(query, "source_type"))` ->
   `entry_type: nil`. Result: `AC2 ... source_type narrows the result set` failed
   (14/15 passed). Reverted.
2. **404-status flip** — `handle_write_result({:error, :not_found}, conn)` changed
   from `Response.not_found(conn)` to `Response.ok(conn, %{})`. Result: both AC4
   not-found tests plus the AC3 cross-tenant-404 test failed (12/15 passed) — the
   cross-tenant test also depends on this exact branch since a cross-tenant id
   resolves to the same `{:error, :not_found}` tuple. Reverted.
3. **409-status flip** — `handle_write_result({:error, {:invalid_state, _}}, conn)`
   changed from `Response.conflict(conn, ...)` to `Response.ok(conn, %{})`. Result:
   both AC4 terminal-state tests failed (13/15 passed). Reverted.
4. **Permission-check bypass** — the retry route's declared policy key changed from
   `authz_post "/:id/retry", :DlqReadRetryDiscard` to `authz_post "/:id/retry",
   :TasksList` (an existing, unrelated policy key whose required permission,
   `:TasksRead`, `TASK_WORKER` *does* hold). Result: `AC3 ... POST /dlq/:id/retry ->
   403 for a caller with no role holding DlqOperate` failed (14/15 passed).
   Reverted.

All four mutations were confirmed to fail only the test(s) they targeted (not a
wider collapse), and `lib/letflow/routers/dlq.ex` is confirmed byte-identical to its
pre-mutation state after the full sequence (`diff` produced no output; `git status`
shows no modification to the file, only the new test file as untracked).
