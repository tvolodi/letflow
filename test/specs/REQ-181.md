# Test Spec: REQ-181 — Webhook subscriptions core CRUD

**Requirement:** REQ-181 (`docs/requirements.yaml`) — `Letflow.Webhooks` context module
(`create/2`, `list/1`, `update/3`, `delete/2`, private `get/2`) plus
`Letflow.Webhooks.Subscription` schema/migration, per
`lib/letflow/design/req181-webhooks-core.md`. No route/controller yet (REQ-182's scope).

**Requirement's acceptance criteria (verbatim, from
`handoffs/WF02-REQ181-20260829/step-03-test-designer.json`):**
1. "the webhook_subscriptions table lives inside each tenant's Postgres schema with a
   tenant_id column retained, matching decision 0003 Decision B's pattern — verified by
   inspecting the migration"
2. "create/2 with no secret supplied generates one, stores only a hashed form in the
   database, and returns the plaintext exactly once as hmac_secret_once in its return
   value; a subsequent list/1 or get of the same subscription never includes the
   plaintext secret or an hmac_secret_once key at all — two explicit tests"
3. "update/3 accepts %{status: \"PAUSED\"} and, separately, %{is_active: false}, and
   both result in a subscription that subsequently reads back as status \"PAUSED\" —
   reconciling WebhookSubscription's dual status/is_active representation to one stored
   state"
4. "list/1 is tenant-scoped, demonstrated by a subscription created under tenant A being
   absent from a list/1 call scoped to tenant B"
5. "delete/2 removes the subscription such that a subsequent list/1 no longer includes
   it, and a second delete/2 of the same id returns a not-found error rather than a
   duplicate success"
6. "no route or controller file is added or modified, confirmed by git diff --stat
   scoped to this requirement's commits"

**Test tier:** integration. Every function under test touches `Letflow.Repo` against a
real, per-test-provisioned tenant Postgres schema (`Letflow.DataCase`, real `CREATE
SCHEMA` via `Letflow.TenantFixture.provisioned_tenant!/1`) — same shape as
`test/letflow/dlq_test.exs`. `async: false`, matching every other tenant-fixture test
file in this codebase (real schema creation/teardown against one shared instance).

## A real implementation bug found and fixed during this step

While writing AC2's coverage, `create!/2`'s insert failed with a Postgres
`not_null_violation` on `created_at` — `Letflow.Webhooks.Subscription.insert_changeset/2`
was passing `created_at` in the attrs map but its `cast/3` whitelist did not include
`:created_at`, so `cast/3` silently dropped it before the changeset ever reached
`Repo.insert/1`, and the column has no DB-side default. This is a real bug in reviewed,
merged code, not a test-authoring mistake — REVIEWER had approved `insert_changeset/2`
without exercising the actual insert path end-to-end. Fixed in commit `3046e44` (adds
`:created_at` to `insert_changeset/2`'s `cast/2` fields and `validate_required/2` list;
`lib/letflow/design/req181-webhooks-core.md` §2.4 corrected to match) and re-approved by
REVIEWER at commit `5337911`. All test cases below are written and verified against the
fixed code.

## Test cases

### Acceptance criterion 1 — schema-per-tenant, `tenant_id` retained

1. **The `webhook_subscriptions` table exists inside the tenant's own Postgres schema,
   carries `id`/`tenant_id`/`status`/`secret_hash` columns, and does not exist in
   `public`** — see `webhooks_test.exs:"the table exists in the tenant's own schema,
   carries a tenant_id column, and is absent from public"`. Queries
   `information_schema.columns`/`information_schema.tables` directly against the
   provisioned tenant schema and against `public`, rather than trusting the migration
   file's source text — proves the migration's actual effect, not just its intent.
   Would fail if the migration were scoped to `public` instead of the tenant prefix, or
   if `tenant_id` were dropped from the table (schema-per-tenant alone would make the
   column technically redundant, but decision 0003 Decision B explicitly retains it —
   this test pins that retention as a standing check).

### Acceptance criterion 2 — `create/2` secret handling: hash-only storage, plaintext once

2. **No secret supplied — `create/2` generates one, stores only the SHA-256 hash,
   returns `hmac_secret_once`** — see `webhooks_test.exs:"no secret supplied --
   generates one, stores only the SHA-256 hash, returns hmac_secret_once"`. Asserts the
   returned plaintext is a non-empty string, independently recomputes the SHA-256 hash
   of that plaintext and asserts it equals the persisted `secret_hash` (not merely "some
   hash exists" — the *correct* hash of the *actual* returned plaintext), asserts
   `secret_hash != plaintext` (guards against a no-op "hash" that just echoes the
   input), and re-selects the row from Postgres via `Repo.get!/3` to confirm the hash
   persisted, not just present on the in-memory struct. Would fail if `create/2` stored
   the plaintext directly (mutation-tested below — see "Mutation testing"), used a
   different/broken hash algorithm, or returned a plaintext not matching what was
   hashed.
3. **A subsequent `list/1` of the same subscription carries no plaintext and no
   `hmac_secret_once` key at all** — see `webhooks_test.exs:"a subsequent list/1 of the
   same subscription carries no plaintext and no hmac_secret_once key"`. Lists the
   subscription back via `list/1`, asserts `Map.has_key?(Map.from_struct(listed),
   :hmac_secret_once)` is false (the schema struct structurally cannot carry that key —
   this assertion would fail to compile-time-guarantee anything if the schema ever grew
   such a field) and that `listed.secret_hash != plaintext` while `listed.secret_hash ==
   subscription.secret_hash` (the hash read back matches what `create/2` returned, not a
   different/corrupted value). This is the direct acceptance demonstration for AC2's
   second half — would fail if `list/1` ever joined in or otherwise surfaced the
   plaintext.

### Acceptance criterion 3 — `update/3`'s status/is_active reconciliation

4. **`%{status: "PAUSED"}` results in `status: :PAUSED` with `paused_at` set, persisted**
   — see `webhooks_test.exs:"%{status: \"PAUSED\"} results in status PAUSED on
   readback"`. Asserts the returned struct's `status`/`paused_at`, then re-selects from
   Postgres to confirm persistence. Would fail if the status write were skipped or
   `paused_at` were left `nil`.
5. **`%{is_active: false}` results in the identical stored state as case 4** — see
   `webhooks_test.exs:"%{is_active: false} results in status PAUSED on readback"`. Same
   assertions, different input shape — this is the literal AC3 reconciliation
   requirement: two different caller-facing representations must converge to one stored
   `status`. Would fail if `is_active: false` took a different code path that left
   `status` at `:ACTIVE` or omitted `paused_at`.
6. **Agreeing pair `%{status: "PAUSED", is_active: false}` reconciles to `PAUSED`** —
   see `webhooks_test.exs:"agreeing pair %{status: \"PAUSED\", is_active: false} results
   in PAUSED"`. Proves both keys can be supplied together without conflict when they
   agree.
7. **Agreeing pair `%{status: "ACTIVE", is_active: true}` reconciles to `ACTIVE` and
   clears `paused_at`** — see `webhooks_test.exs:"agreeing pair %{status: \"ACTIVE\",
   is_active: true} results in ACTIVE and clears paused_at"`. Pauses first, then
   resumes via the agreeing pair, asserts `paused_at` is `nil` afterward — the converse
   of cases 4-6, proving the reconciliation isn't PAUSED-only. Would fail if resuming
   left a stale `paused_at` timestamp (mutation-tested below).
8. **Disagreeing pair `%{status: "ACTIVE", is_active: false}` returns
   `{:error, :invalid_status}` and does not write** — see `webhooks_test.exs:
   "disagreeing pair %{status: \"ACTIVE\", is_active: false} returns invalid_status and
   does not write"`. Re-selects from Postgres afterward to confirm `status` is
   unchanged — proves the reconciliation check happens *before* any write (design
   §3.3's "resolves ... to a single target atom before touching the database"), not
   that it merely returns an error while still mutating the row.
9. **Single-key `%{status: "ACTIVE"}` alone resolves to `ACTIVE`** — see
   `webhooks_test.exs:"single key %{status: \"ACTIVE\"} alone results in ACTIVE"`.
10. **Single-key `%{is_active: true}` alone resolves to `ACTIVE`** — see
    `webhooks_test.exs:"single key %{is_active: true} alone results in ACTIVE"`. Cases
    9-10 confirm the single-key paths (as opposed to the dual-key agreement paths in
    cases 6-8) both work independently — would fail if `reconcile_status/1`'s
    single-key clauses were removed or miswired.

### Acceptance criterion 4 — `list/1` is tenant-scoped

11. **A subscription created under tenant A is absent from tenant B's `list/1`** — see
    `webhooks_test.exs:"a subscription created under tenant A is absent from tenant B's
    list/1"`. Provisions two separate real tenant schemas, creates a subscription only
    under tenant A, asserts tenant A's `list/1` returns exactly that one subscription
    and tenant B's `list/1` returns `[]`. This is the literal AC4 demonstration — would
    fail if `list/1` somehow queried across schemas or `Repo`'s `prefix` option were
    dropped.

### Acceptance criterion 5 — `delete/2` removes the row; second delete is not-found

12. **After `delete/2`, `list/1` excludes the row, and a second `delete/2` of the same
    id returns `{:error, :not_found}`, not a duplicate success** — see
    `webhooks_test.exs:"list/1 excludes the deleted subscription, and deleting again
    returns not_found"`. Single test covering both halves of AC5 in sequence: delete
    once (assert `{:ok, deleted}` with matching id), list (assert `[]`), delete again
    (assert `{:error, :not_found}`). Would fail if delete were non-destructive, if
    `list/1` still returned the deleted row, or if a second delete against an
    already-absent row fabricated a success (mutation-tested below).

### Acceptance criterion 6 — no route/controller file added

13. **Neither `Letflow.Webhooks` nor `Letflow.Webhooks.Subscription` contains
    Plug/Router-shaped constructs** — see `webhooks_test.exs:"neither Letflow.Webhooks
    nor Letflow.Webhooks.Subscription references Plug/Router-shaped constructs"`.
    Direct source-text check for `use Plug.Router`, `use ...Web, :controller`, and a
    `get "/..."` route macro call, run against the actual files in the working tree
    (not trusted from a design doc's claim). Would fail if either file grew a route.
14. **No webhook-named router file exists in `lib/letflow/routers`** — see
    `webhooks_test.exs:"no router file for webhooks exists anywhere in lib/letflow/
    routers"`. Lists the actual directory contents and filters for a `webhook`-matching
    filename, asserting none exist. This directly (and more durably than a one-time `git
    diff --stat` read) satisfies AC6's underlying intent: no route/controller file for
    this requirement, checked against the current working tree rather than a specific
    commit range that would go stale.

## Mutation testing (webhooks.ex, `lib/letflow/webhooks.ex`)

Performed by TEST-DESIGNER against the current, REVIEWER-approved
`lib/letflow/webhooks.ex` (commit `5337911`), each mutation applied then reverted
individually, revert confirmed via `git diff 5337911 -- lib/letflow/webhooks.ex
lib/letflow/webhooks/subscription.ex` (empty after all mutations):

1. **Skip the hash step — store the plaintext directly as `secret_hash`** (`insert_attrs`
   in `create/2`: `secret_hash: secret_hash` -> `secret_hash: plaintext`). Result: 2 of
   14 tests failed (`Result: 12/14 passed`) — both AC2 tests (case 2 and case 3 above),
   exactly as expected, since case 2 independently recomputes the expected hash and case
   3 checks `secret_hash != plaintext`.
2. **Flip a status-reconciliation branch** — in `apply_status_update/3`'s
   `%Subscription{status: :ACTIVE}, :PAUSED` clause, changed the target write from
   `%{status: :PAUSED, paused_at: current_timestamp()}` to `%{status: :ACTIVE,
   paused_at: nil}` (silently makes pausing a no-op). Result: 3 of 14 tests failed
   (`Result: 11/14 passed`) — all three AC3 pause-path tests (cases 4, 5, 6 above).
3. **Make `delete/2` succeed twice on the same id** — changed `delete/2` from `with
   {:ok, subscription} <- get(id, opts) do Repo.delete(...) end` to a `case` that maps
   `{:error, :not_found}` to a fabricated `{:ok, %Subscription{id: id}}`. Result: 1 of
   14 tests failed (`Result: 13/14 passed`) — the AC5 test (case 12 above), which
   asserts `{:error, :not_found}` on the second delete.

**Gap found, not silently worked around:** a fourth candidate mutation — removing the
`lock("FOR UPDATE")` clause from `fetch_and_lock_subscription/3` (`update/3`'s row-lock
step) — was applied and run, and **all 14 tests still passed** (`Result: 14 passed`,
unchanged). This is a genuine coverage gap: nothing in this suite exercises concurrent
`update/3` calls against the same row, so the row lock's actual purpose (preventing a
lost-update race under concurrent writers) is unverified by this test file. Reverted
immediately (confirmed via the same `git diff` check as the other three). This is
recorded here rather than fixed in this pass because a genuine concurrent-access test
(two processes racing inside overlapping transactions) is a materially larger piece of
work than the mutation-driven unit checks above, and is flagged for
TEST-DESIGN-VALIDATOR to weigh — either accept the gap as a follow-up
(`Letflow.Dlq.retry/2`/`discard/2`, which established this same lock-then-check idiom,
appears to have the same gap in `test/letflow/dlq_test.exs`, so this would not be a new
double standard) or require it closed before this handoff passes.
