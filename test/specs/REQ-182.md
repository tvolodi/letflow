# Test Spec: REQ-182 — `Letflow.Routers.Webhooks` route/controller layer

**Requirement:** REQ-182 (stage S6, queue task 355, GH#700). Design authority:
`lib/letflow/design/req182-webhooks-routes.md`. Implementation authority:
`lib/letflow/routers/webhooks.ex` plus the pre-existing
`endpoint_policy_key("PATCH", "/webhooks/subscriptions/:id")` clause in
`lib/letflow/api/authorization.ex` and the `forward("/webhooks", ...)` line in
`lib/letflow/plugs/api_pipeline.ex`, already passed CODE-DESIGN-VALIDATOR,
SECURITY-REVIEWER, and REVIEWER (see
`handoffs/WF02-REQ182-20260829/step-03-test-designer.json`).

Test file: `test/letflow/routers/webhooks_test.exs`. Mirrors
`test/letflow/routers/dlq_test.exs`'s (REQ-178) established idiom for this class of
router test: `Letflow.DataCase` (real Postgres), direct
`Letflow.Routers.Webhooks.call/2` dispatch, `conn.assigns[:auth_context]` set
directly (bypassing `AuthPipeline`), `Letflow.TenantFixture.provisioned_tenant!/1`
for real tenant schemas, same cross-tenant-identical-404 idiom, `async: false`.

Acceptance criteria (verbatim from the Step 3 handoff):

1. `POST /api/v1/webhooks/subscriptions` with no secret supplied returns a 2xx
   response whose body includes `hmac_secret_once` carrying the plaintext secret
   exactly once; a subsequent `GET`/list of the same subscription never includes
   the plaintext secret or an `hmac_secret_once` field at all — two explicit
   tests.
2. `PATCH /api/v1/webhooks/subscriptions/:id` accepts `{status: "PAUSED"}` and,
   separately, `{is_active: false}`, and both result in a subscription that
   subsequently reads back as `PAUSED` via `GET`/list.
3. every subscription route requires the `WebhooksManage` permission from
   REQ-069's matrix — a caller lacking it receives 403, and a caller from a
   different tenant naming a real subscription id belonging to tenant A receives
   404, never 403.
4. `GET /api/v1/webhooks/subscriptions` returns `{items: [...]}` with each item's
   `target_url`, `event_types`, `status` and `created_at` present, matching
   `webhooksApi.list`'s consumer shape.
5. `DELETE /api/v1/webhooks/subscriptions/:id` removes the subscription such that
   a subsequent list no longer includes it, and a second `DELETE` of the same id
   returns 404 rather than a duplicate success.
6. the route module's moduledoc states explicitly that R-Co's `webhooks.zig` was
   not inspected in this batch (unreachable from the drafting environment) and
   that `web/src/api/dlq.ts` / `web/src/types/api.ts` were the binding contract
   instead.

## Test cases and rationale

### AC1 — `hmac_secret_once` on create, absent on read (`describe "AC1: ..."`)

Two tests:

1. `POST /subscriptions` -> 201, body has a non-empty string `hmac_secret_once`
   and no `secret_hash` key. Exists to prove the plaintext is actually surfaced
   once (a regression that dropped the splice entirely, or emitted an empty
   string, would pass a weaker "status is 2xx" check but fail this one).
2. A subsequent `GET /subscriptions` list of the same subscription: the item has
   neither `hmac_secret_once` nor `secret_hash` nor `secret` keys, and — the
   strongest form of this check — the raw response body string does not contain
   the plaintext value returned by the earlier create call at all. This last
   assertion exists specifically to catch a regression where the plaintext
   leaked under some other, unexpected key name rather than the three obvious
   ones checked by key absence.

### AC2 — PATCH status/is_active reconciliation (`describe "AC2: ..."`)

Two tests, one per input shape (`{status: "PAUSED"}`, `{is_active: false}`),
each independently creating a subscription, PATCHing it, and verifying both the
PATCH response body and a subsequent list call read back `"PAUSED"`. Two
separate tests (not one parameterized test) exist because the design (§3.3)
states the router does no reconciliation of its own — `Letflow.Webhooks.update/3`'s
`reconcile_status/1` is the single place that logic lives — so a regression that
broke one input path (e.g., only threading `status` through and silently
dropping `is_active`, or vice versa) needs a test per path to be caught; a test
that only ever exercised one shape would leave the other's wiring unverified.

### AC3 — permission gate and cross-tenant-404 (`describe "AC3: ..."`)

Five tests:

1–4. One 403 test per route (`GET`/`POST`/`PATCH`/`DELETE`) using `TASK_WORKER` —
a real role that does **not** hold `WebhooksManage` per the real `role_allows?/2`
matrix (confirmed by reading `lib/letflow/api/authorization.ex` directly, not
assumed). The `PATCH`/`DELETE` tests additionally assert no state change
occurred on the 403 branch, matching `dlq_test.exs`'s own precedent for proving
the plug denies before any handler body runs. Four separate tests (not one)
exist because the task explicitly asks for "at least list+create+update+delete"
coverage — a single combined test could not localize which specific route
regressed if only one lost its authorization check.
5. A `PLATFORM_ADMIN` caller in tenant A naming a real id that only exists in
   tenant B's schema -> 404 for both PATCH and DELETE, identical response bytes
   to a genuinely-nonexistent id, and tenant B's row is left untouched. This is
   the one test proving "never 403" for the cross-tenant case specifically (a
   caller who *does* hold the permission, so a wrongly-scoped tenant check that
   leaked into a 403 branch would be caught here, whereas the no-permission
   tests above could not catch it) — mirrors `dlq_test.exs`'s AC3 test 3
   verbatim in structure.

### AC4 — GET list shape (`describe "AC4: ..."`)

One test: creates a subscription with an explicit `target_url` and
`event_types`, then asserts the list body is exactly `{"items": [...]}` (no
extra top-level keys, matching design §5's "exactly-one-key map" requirement)
and that the one item's `target_url`, `event_types`, `status`, and `created_at`
are all present with the expected real values (not merely "the key exists" —
`target_url`/`event_types` are asserted equal to what was submitted, `status` to
`"ACTIVE"`, `created_at` to `is_binary/1`).

### AC5 — DELETE removes; second DELETE is 404 (`describe "AC5: ..."`)

Two tests:

1. `DELETE` -> 204, and a subsequent list excludes the deleted subscription.
2. Two sequential `DELETE`s of the same id: first -> 204, second -> 404. This
   exists specifically to catch a regression that made `delete/2`'s error
   handling fall through to some other status (e.g., a second 204, which the
   design explicitly calls "structurally impossible" but which this test
   verifies rather than assumes) — matching the task's explicit "not a
   duplicate success" framing.

### AC (moduledoc) — R-Co `webhooks.zig` non-inspection is documented

One structural test reading the compiled moduledoc via `Code.fetch_docs/1` and
asserting it mentions `webhooks.zig`, the phrase `"not inspected"`, and both
`web/src/api/dlq.ts` and `web/src/types/api.ts` — matching
`dlq_test.exs`'s own moduledoc-disclosure test verbatim in structure, adapted to
REQ-182's contract-source statement (design §0/§7).

## Mutation-testing confirmation

Per WF-02 Step 3's mutation-driven mandate, four mutants were applied to
`lib/letflow/routers/webhooks.ex`, each run against this suite, and each
reverted (confirmed via `git diff` showing a clean working tree afterward):

1. **PATCH's `:not_found` branch flipped to `Response.ok(conn, %{})`** (200
   instead of 404) — caught: 12/13 passed, 1 failure (the AC3 cross-tenant test,
   which asserts `patch_conn.status == 404`).
2. **GET list's policy key changed from `:WebhookSubscriptionsManage` to
   `:DefinitionsRead`** (a permission `TASK_WORKER` genuinely holds, per
   `role_allows?(:TASK_WORKER, ...)`) — caught: 12/13 passed, 1 failure (the AC3
   "GET -> 403 for TASK_WORKER" test). Note: an earlier attempt that replaced
   `authz_get` with a plain, key-less `get` route was *not* caught, because
   `Letflow.Plugs.Authorize`'s fail-closed-except-`PLATFORM_ADMIN` behavior for
   an `:Unknown` policy key still denies `TASK_WORKER`; the policy-key-swap
   mutation above was chosen instead because it actually grants access to a
   caller the real policy would deny, which is the failure mode AC3 exists to
   catch.
3. **`handle_list/1` spliced a fabricated `hmac_secret_once` value onto every
   list item** — caught: 12/13 passed, 1 failure (the AC1 "list never includes
   hmac_secret_once" test).
4. **PATCH's `is_active` key dropped from the narrowed `attrs` map** (only
   `status` threaded through) — caught: 12/13 passed, 1 failure (the AC2
   "`{is_active: false}` reads back as PAUSED" test).

All four mutants were reverted via `git checkout -- lib/letflow/routers/webhooks.ex`;
`git diff lib/letflow/routers/webhooks.ex` shows no changes afterward, and the full
suite (`mix test test/letflow/routers/webhooks_test.exs`) passes 13/13 against the
unmutated file.
