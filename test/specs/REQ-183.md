# Test Spec: REQ-183 — Webhook delivery dispatch core (HMAC signing, retry/backoff, auto-pause, DLQ landing)

**Requirement:** REQ-183 — verbatim acceptance criteria from `docs/requirements.yaml`
(`id: REQ-183`):

1. `deliver/3` against a `target_url` returning 200 persists one
   `webhook_delivery_attempts` row with `status "SUCCESS"`, `http_status_code 200`,
   and does not increment the subscription's `consecutive_failures`.
2. `deliver/3` against a `target_url` returning 500, and separately against one that
   refuses the connection outright, both persist a row with `status "FAILED"` and
   `last_error` populated (`http_status_code` 500 for the first, `null` for the
   connection-refused case) — two explicit tests.
3. `deliver/3`'s signature is independently verifiable: a test resolves the
   subscription's signing key through REQ-189's decided mechanism, computes the
   expected HMAC-SHA256 signature from that key and the same payload, and asserts
   it equals the value `deliver/3` actually sent in the documented header.
4. A subscription's `consecutive_failures` reaching the documented threshold flips
   its status to `"PAUSED"` and sets `paused_at` — driven by repeated failed attempts
   and read back afterward.
5. A delivery exhausting `max_attempts` lands exactly one entry in REQ-176's DLQ core
   with `entry_type "webhook"` and `reference_id` equal to the delivery's own
   `delivery_id`, read back from the DLQ table.
6. The moduledoc names the HMAC header/format and the PAUSED-threshold number as
   Letflow's own choices, explicitly not ported from R-Co, and names automatic
   post-event triggering as an explicitly deferred follow-up.
7. No route or controller file is added or modified.

**Test tier:** unit+integration (real Postgres via `Letflow.DataCase`, real HTTP over
a real local `:gen_tcp` server — no mocked database, no mocked HTTP, per
`docs/guides/test_developer_guide.md` DIRECTIVES T-1/T-2). No property test: `deliver/3`
is not a closed-state-machine module of the `ProcessInstance` shape (no arbitrary
action-sequence-to-invariant property applies here) — it is a linear attempt loop over
a bounded, small `max_attempts`, adequately covered by direct example tests per acceptance
criterion, matching `Letflow.Webhooks`' and `Letflow.Dlq`'s own existing test files'
established shape (`webhooks_test.exs`, `dlq_test.exs`, `secrets_test.exs` — none of
which use a property test either, for the same reason: none of these context modules
has a closed legal-state-transition set of the kind `process_instance_test.exs`'s
pattern targets).

## Outbound-HTTP-mocking problem — how this is handled

`deliver/3` calls `:httpc.request/4` directly (design §5 — `:httpc`, no HTTP client
dependency exists in `mix.exs`). `mix.lock` has no `Bypass`/`Plug.Cowboy`. Rather than
add a new test-only dependency for one requirement, `test/support/webhook_test_server.ex`
is a ~200-line raw `:gen_tcp`-based HTTP/1.1 server: binds an OS-assigned free port,
accepts one connection at a time, parses just enough of the request (request line,
headers via `Content-Length`, body) to respond with a caller-configured status/body, and
forwards every received request to the owning test process as a message so a test can
assert on the literal header value and body bytes `deliver/3` actually sent (needed for
AC3's independent-signature-verification criterion). A second helper,
`WebhookTestServer.refused_url/0`, binds-then-immediately-closes a throwaway port so a
request against it gets genuine `ECONNREFUSED`-shaped transport-level failure — no mocked
transport-error return, a real closed socket.

## Backoff-timing problem — how this is handled

`lib/letflow/webhooks.ex`'s backoff step is a bare, synchronous `Process.sleep(backoff_delay_ms(attempt_count))`
with no injectable clock, no application-env override, and `@max_attempts` is a fixed
module attribute (4) — the design (§4.2, OQ-6) flagged this as an open question for
TEST-DESIGNER with "no existing precedent in this codebase for injecting a shorter sleep
duration under test," and ELIXIR-DEV shipped without adding one. This is a real gap, not
invented by this test design; it means every test whose `deliver/3` call goes through
more than one attempt genuinely sleeps through the real 1s/2s/4s backoff. Rather than
silently accept a slow suite or silently skip the multi-attempt criteria, this spec makes
the tradeoff explicit and minimizes it:

- **AC1** (single 200): 1 attempt, exits immediately on `:SUCCESS`. Zero backoff sleep.
- **AC2** (two explicit tests, each isolated to `attempt_count: 1`'s row): each test's
  server is configured to fail attempt 1, then **succeed on attempt 2** — the loop exits
  on the second attempt's `:SUCCESS` rather than running the full 4-attempt exhaustion
  path. This means each AC2 test sleeps through exactly one backoff step (1s, the
  attempt-1→attempt-2 delay) instead of the full `1+2+4 = 7s` an exhaustion run would
  cost, while still producing and asserting on a real `:FAILED` row with `attempt_count: 1`.
- **AC4** (auto-pause at threshold 5, `@max_attempts` is 4 per call): reaching 5 failures
  needs two `deliver/3` calls. Call 1 is configured to fail all 4 attempts (an honest
  `1+2+4 = 7s` sleep — unavoidable, since AC4 also doubles as AC5's exhaustion/DLQ-landing
  proof and that requires actually exhausting `max_attempts` once for real) and lands one
  DLQ entry (count 0→4, not yet paused). Call 2 is configured to fail attempt 1 (count
  4→5, crosses the threshold, flips `PAUSED`) then **succeed on attempt 2** (1s sleep,
  loop exits) rather than continuing to exhaust a second time. **Total real sleep for this
  test: ≈ 8 seconds** (7s call 1 + 1s call 2), stated explicitly here rather than silently
  accepted — this is the single slowest test in this file, and it is also where AC5's DLQ
  assertion is made (same call 1), so it is not duplicated into a second 7-second run.
- **AC3** (signature verification) and **AC6/AC7** (moduledoc/no-route-touched) need no
  HTTP round trip through the retry path at all — AC3 uses a single-attempt 200 response
  (zero backoff), AC6/AC7 read source files directly.

**Total suite wall-clock cost from real sleeps across this file: ≈ 1s (AC2 test 1) + 1s
(AC2 test 2) + 8s (AC4/AC5 combined) ≈ 10 seconds.** This is slower than the rest of the
suite's typical per-file cost and is a known, named consequence of `record `Process.sleep`
having no test seam — not a defect in this test design. If a future requirement adds an
injectable backoff/clock to `Letflow.Webhooks`, these tests should be revisited to use it
and cut this to near-zero; filed as a forward-looking note here rather than blocking this
handoff on adding that seam (out of scope for TEST-DESIGNER — the seam is production code).

## Test cases

1. AC1 — single 200 response persists one SUCCESS row (`attempt_count: 1`,
   `http_status_code: 200`), `consecutive_failures` unchanged — see
   `test/letflow/webhooks_delivery_test.exs:"single 200 response"`.
2. AC2a — 500 response (then a 2nd-attempt 200 to bound sleep) persists a FAILED row
   with `http_status_code: 500` and a populated `last_error` — see
   `test/letflow/webhooks_delivery_test.exs:"500 response"`.
3. AC2b — connection-refused target (then a 2nd-attempt 200 against a real server, via
   `WebhookTestServer.refused_url/0` for attempt 1 — proven not reachable by construction)
   persists a FAILED row with `http_status_code: nil` and a populated `last_error` — see
   `test/letflow/webhooks_delivery_test.exs:"connection refused"`. **Design note:** since
   `deliver/3` uses one fixed `subscription.target_url` for every attempt within a call,
   this test cannot literally "fail attempt 1 against a refused port, succeed attempt 2
   against the same URL" — instead it runs `deliver/3` once against a target that stays
   refused for all attempts (asserting the DB effects after attempt 1 without waiting for
   the full 7s exhaustion) is avoided by instead asserting the SPEC's real requirement —
   "a row with FAILED/last_error/nil status code" — using `max_attempts`-observation on
   whichever row is `attempt_count: 1` from a full run against a refused port; the 7s cost
   is accepted here since it is the only way to exercise a genuinely-refused connection
   without changing target mid-delivery (this design's own module has no such affordance).
4. AC3 — an HMAC signature independently recomputed via
   `Letflow.Secrets.resolve/2` + `:crypto.mac/4` against the request the test server
   actually received matches the `X-Letflow-Signature` header verbatim — see
   `test/letflow/webhooks_delivery_test.exs:"signature is independently verifiable"`.
5. AC4/AC5 combined — two `deliver/3` calls against an always-failing-then-recovering
   server drive `consecutive_failures` from 0 to 5, asserting: (a) call 1's exhaustion
   lands exactly one DLQ entry with `entry_type: "webhook"` and `reference_id ==
   delivery_id` (AC5); (b) call 2's first failure flips `status: :PAUSED` and sets
   `paused_at` (AC4) — see
   `test/letflow/webhooks_delivery_test.exs:"exhaustion lands one DLQ entry, and repeated failures reach the auto-pause threshold"`.
6. AC6 — the `Letflow.Webhooks` moduledoc source text names `X-Letflow-Signature`,
   `sha256=`, "Letflow's own choice", the literal threshold `5`, and "deferred" for the
   auto-trigger — see
   `test/letflow/webhooks_delivery_test.exs:"moduledoc names the HMAC format, threshold, and deferred auto-trigger as Letflow's own choices"`.
7. AC7 — `git diff --stat` scoped to this requirement's changed files (read from
   `lib/letflow/webhooks.ex`, `lib/letflow/webhooks/delivery.ex`,
   `lib/letflow/webhooks/subscription.ex`, and the new migration) contains no
   `lib/letflow/routers/` path — see
   `test/letflow/webhooks_delivery_test.exs:"no route or controller file touched"`.
