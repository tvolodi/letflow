# Test Spec: REQ-184 — `GET /api/v1/webhooks/subscriptions/:id/deliveries`

**Requirement:** REQ-184 (stage S6, queue task 357, GH#702). Design authority:
`lib/letflow/design/req184-webhook-deliveries-route.md`. Implementation authority:
`lib/letflow/webhooks.ex`'s new `list_delivery_attempts/3` and
`lib/letflow/routers/webhooks.ex`'s new `authz_get "/subscriptions/:id/deliveries"`
clause, `handle_deliveries/2`, `resolve_limit/1`, `delivery_json/1` — already passed
CODE-DESIGN-VALIDATOR, SECURITY-REVIEWER, and REVIEWER (see
`handoffs/WF02-REQ184-20260830/step-02c-security-reviewer.json`,
`step-02d-reviewer.json`).

Test files:

- `test/letflow/webhooks_test.exs` — context-level (`Letflow.Webhooks.list_delivery_attempts/3`
  called directly, no HTTP layer), `describe "REQ-184: ..."` block.
- `test/letflow/routers/webhooks_test.exs` — HTTP-level (`Letflow.Routers.Webhooks.call/2`
  dispatch), `describe "REQ-184 AC*: ..."` blocks.

Both mirror `test/letflow/dlq_test.exs`/`test/letflow/routers/dlq_test.exs`'s
established idiom for this class of test: `Letflow.DataCase` (real Postgres),
`Letflow.TenantFixture.provisioned_tenant!/1` for real tenant schemas, `async: false`.

Acceptance criteria (verbatim from `docs/requirements.yaml`'s REQ-184 entry):

1. `GET .../deliveries` returns `{items: [...]}` with each item's fields matching
   `WebhookDeliveryAttempt` exactly (`delivery_id`, `subscription_id`, `event_type`,
   `status`, `http_status_code`, `attempted_at`, `attempt_count`, `max_attempts`,
   `last_error`).
2. the route honors the `limit` param, demonstrated by a test with more delivery
   attempts than the requested limit returning exactly `limit` items.
3. the route requires the `WebhooksManage` permission from REQ-069's matrix — a
   caller lacking it receives 403.
4. a caller from a different tenant naming a real subscription id belonging to
   tenant A receives 404, never 403, regardless of whether that subscription has
   delivery attempts.
5. a request against a non-existent subscription id returns 404.
6. the route module's moduledoc states explicitly that R-Co's `webhooks.zig` was
   not inspected and that the SPA's already-committed contract was the binding
   source of truth instead.

This spec covers the full set of tests across both files (ELIXIR-DEV's initial pass
plus TEST-DESIGNER's gap-fill — see "Gap analysis" below for exactly which tests are
which).

## Test cases and rationale

### AC1 — response shape, field-by-field (`webhooks_test.exs` router-level)

Two tests (`describe "REQ-184 AC1: ..."`):

1. A `FAILED` delivery with a non-null `http_status_code` and `last_error`: asserts
   `Map.keys(item)` equals exactly the 9-field allowlist (catching both a missing
   field and an accidentally-leaked extra field, e.g. `id` or `tenant_id`), then
   asserts every field against a concrete seeded value (`delivery_id`,
   `subscription_id`, `event_type`, `status`, `http_status_code`, `attempt_count`,
   `max_attempts`, `last_error`), not merely "the key is present." This is the test
   that would catch a regression silently swapping two same-typed fields (e.g.
   `attempt_count`/`max_attempts` transposed) which a "keys present" check alone
   would miss.
2. A `SUCCESS` delivery: asserts `status == "SUCCESS"`, a real `http_status_code`,
   and `last_error == nil` — exists because AC1's field list includes `last_error`
   as nullable, and test 1 alone (which always sets a non-nil `last_error`) would
   never exercise the null-encoding path (`nil` surviving JSON round-trip as `null`,
   not `""` or being dropped).

### AC2 — limit enforcement, ordering, and `resolve_limit/1`'s fallback branches

Context-level (`webhooks_test.exs`, `describe "REQ-184: list_delivery_attempts/3 ..."`):

- Seeds two attempts sharing the same `attempted_at` second (distinguished only by
  `attempt_count`) plus two strictly-older attempts, calls
  `list_delivery_attempts(id, 2, ...)` directly, and asserts the two survivors are
  exactly the two same-second rows, higher `attempt_count` first — this is what
  proves the two-key `[desc: attempted_at, desc: attempt_count]` ordering
  (REVIEWER-affirmed, design §4/OQ-2) rather than an ordering that only happens to
  produce the right *count*.
- A real, in-tenant, zero-delivery-attempt subscription returns `{:ok, []}`, not an
  error (design §1.1's explicit "zero attempts is not an error" requirement).
- A non-existent id returns `{:error, :not_found}`; a malformed (non-UUID) id
  returns `{:error, :invalid_id}` with **no DB round-trip** (asserted by the test
  existing at all against a schema that has no rows to find — a query that reached
  the DB would still correctly return not-found, so this test's real value is
  documented in design §1.1's `get/2` reuse, verified indirectly since `invalid_id`
  is a distinct return value from `not_found`).
- A real subscription id belonging to another tenant returns `{:error, :not_found}`
  even though that other tenant has delivery-attempt rows for it — the exact
  "permission/existence say nothing about cross-tenant visibility" case.

HTTP-level (`routers/webhooks_test.exs`, `describe "REQ-184 AC2: ..."`):

- **Exact-count-under-limit-cutoff** — 5 seeded attempts at strictly decreasing
  `attempted_at` seconds, `?limit=2` returns exactly 2 items, **and** (TEST-DESIGNER
  gap-fill) asserts `Enum.map(items, & &1["delivery_id"])` equals the two most-recent
  deliveries' ids in order — the context-level test above proves the *query*
  orders correctly; this proves `delivery_json/1`'s per-item mapping and
  `Enum.map/2` in `handle_deliveries/2` don't silently reverse or re-sort the
  already-correctly-ordered list on its way to JSON (a regression e.g. swapping
  `Enum.map` for something order-losing would pass the count-only version of this
  test but fail this one).
- **Omitted limit defaults to 20** — 3 seeded attempts, no `limit` param, all 3
  survive (well under 20).
- **(TEST-DESIGNER gap-fill) `resolve_limit/1`'s remaining branches** — four
  parameterized tests (`?limit=abc`, `?limit=0`, `?limit=-1`, `?limit=5abc`), each
  asserting the request still succeeds (200) and all 3 seeded rows survive (proving
  fallback to the default of 20, not a 0-row or 1-row result, and not an error).
  `resolve_limit/1` is a several-branch private function
  (`lib/letflow/routers/webhooks.ex:241-248`: positive-integer-string → value;
  non-positive/non-numeric/trailing-garbage string → default; non-binary (nil) →
  default) that, before this gap-fill, had test coverage of only its nil/absent
  branch (via "omitted limit defaults to 20") and its one valid-positive-integer
  branch (via the exact-count test) — its `_other -> @default` catch-all covering
  zero, negative, non-numeric, and partial-parse ("5abc") inputs was entirely
  untested. This matters because OQ-1 (design §4) is this design's own choice
  (no acceptance criterion demands it) and a plausible-looking alternate
  implementation (e.g. `String.to_integer/1` with a rescue, or a parse that accepts
  `"5abc"` as `5`) could silently diverge from the documented behavior without any
  test catching it.

### AC3 — 403 without `WebhooksManage` (`routers/webhooks_test.exs`)

One test: `TASK_WORKER` — confirmed by reading `lib/letflow/api/authorization.ex:482-483`
directly (`role_allows?(:TASK_WORKER, permission), do: permission in [:DefinitionsRead,
:InstancesRead, :TasksRead, :TasksComplete]` — `:WebhooksManage` is not in this list) —
gets 403. Not an ad-hoc/fake permission: `TASK_WORKER` is one of the five real roles
in `@roles` (`authorization.ex:109`) and this is its real, currently-shipped
permission set, not a role invented for the test.

### AC4 — cross-tenant real id → 404 regardless of attempts (`routers/webhooks_test.exs`)

One test: tenant A's caller holds `PLATFORM_ADMIN` (which *does* hold
`WebhooksManage`, confirmed by `authorization.ex`'s `PLATFORM_ADMIN` catch-all) and
names tenant B's real subscription id, which has a real delivery attempt seeded
against it — gets 404. This is simultaneously the cross-tenant test **and** the
"permission alone doesn't bypass tenant scoping" case the Step 3 task asked about:
a caller *with* proper `WebhooksManage` still can't see another tenant's data,
because the test's role is `PLATFORM_ADMIN`, not a role lacking the permission (that
case is AC3's territory, and combining both into one caller would leave it
ambiguous which check fired). No separate test was needed — this AC4 test already
is that companion case.

### AC5 — non-existent id → 404, distinct from AC4 (`routers/webhooks_test.exs`)

Two tests:

1. A syntactically valid but never-persisted UUID → 404.
2. A syntactically invalid id (`"not-a-uuid"`, not a UUID at all) → 404, never 400
   — this is the `{:error, :invalid_id}` branch (`get/2`'s regex/parse-based UUID
   validation, reused unmodified from REQ-181/182), folded into the same 404
   response as the well-formed-but-absent case per §3.1's two-clause fold. Both are
   real, independent tests (not one parameterized test) because they exercise two
   distinct `Letflow.Webhooks.list_delivery_attempts/3` return values
   (`{:error, :not_found}` vs. `{:error, :invalid_id}`) that the router maps to the
   same HTTP status — a regression that broke only one of the two return-value
   branches (e.g. changed `:invalid_id`'s mapping to 400) would only be caught by
   having both tests present.

### AC6 — moduledoc disclosure (doc-level check, not a runtime test)

Confirmed by reading `lib/letflow/routers/webhooks.ex:17-25` directly: the
moduledoc's "## Contract source" section states verbatim "R-Co's `webhooks.zig` was
**not inspected** while drafting this route layer (REQ-182) or the deliveries route
added on top of it (REQ-184)" and names `web/src/api/dlq.ts` (including
`getDeliveries/2`) and `web/src/types/api.ts`'s `WebhookDeliveryAttempt` type as the
binding contract — this is the same moduledoc REQ-182's own existing runtime test
(`describe "moduledoc states R-Co's webhooks.zig was not inspected ..."`,
`routers/webhooks_test.exs`) already asserts against via `Code.fetch_docs/1`
(checking for `"webhooks.zig"`, `"not inspected"`, and both `web/` file paths) — that
existing test already covers REQ-184's identical AC6 wording since both requirements
share one moduledoc on one module. No new test needed; this is a doc-content
confirmation, not a runtime-test gap.

## Gap analysis (TEST-DESIGNER, Step 3, this pass)

ELIXIR-DEV's initial test pass already fully covered AC1, AC3, AC4, AC5, and AC6 at
a genuine (not superficial) level — see `handoffs/WF02-REQ184-20260830/req184-test-design-gap-analysis.md`
for the full per-AC verification detail. Two real gaps were found and filled in this
pass, both in `test/letflow/routers/webhooks_test.exs`'s `describe "REQ-184 AC2: ..."`
block:

1. The exact-limit-cutoff test asserted only `length(items) == 2`, not which two
   survived or in what order — enhanced in place to assert delivery-id ordering.
2. `resolve_limit/1`'s non-positive/non-numeric/partial-parse fallback branches
   (zero, negative, non-numeric, trailing-garbage) had zero test coverage — four new
   parameterized tests added.

No gap was found in AC1, AC3, AC4, AC5, or AC6 requiring new tests; see the
gap-analysis file above for why each was judged already complete.
