# Test Spec: REQ-186 — Timers schema and scheduler core (SCH-01/02/05/06)

**Requirement:** REQ-186 — verbatim acceptance criteria from
`handoffs/WF02-REQ186-20260829/step-03-test-designer.json` (mirrors
`docs/requirements.yaml`'s REQ-186 entry):

1. the timers table lives inside each tenant's Postgres schema with a
   tenant_id column retained (decision 0003 Decision B), verified by
   inspecting the migration, and carries a partial index on `(fire_at) WHERE
   status = 'pending'`
2. the status CHECK constraint admits exactly pending, fired, cancelled and
   failed — a test attempting to insert a timer with status `'expired'`
   fails at the database level, not only in the changeset
3. the recurrence CHECK constraint is all-or-nothing: a test inserting
   `repeat_expression` without `repeat_interval_us` is rejected by the
   database, and a test inserting all four recurrence columns consistently
   succeeds
4. a timer created with `fire_at` in the past is fired by the first poll
   after it exists, and the appended event carries `fired_late: true`
   together with both the scheduled `fire_at` and the actual firing
   timestamp; a timer created with `fire_at` in the future is NOT fired by
   that same poll — two explicit tests
5. polling twice over the same due timer fires it exactly once: the second
   poll appends no second event and the timers row remains status `'fired'`
   with its original `fired_at`
6. a fire attempt that raises increments `fire_error_count` and leaves the
   timer `'pending'`, AND the remaining due timers in that same poll cycle
   are still attempted — one test asserts both, by making the first of two
   due timers fail and asserting the second still fired
7. a timer reaching the configured max fire retries transitions to
   `'failed'` with `failed_at` set and produces exactly one `dlq_entries`
   row with `entry_type "timer"`, and is not attempted again by subsequent
   polls
8. the poll interval, jitter, max timers per cycle and max fire retries are
   all read from application config with the documented defaults (5000 ms,
   0 ms, 64, 3), demonstrated by a test overriding at least the interval and
   asserting the poller uses the override
9. no route or controller file is added or modified, confirmed structurally
   (no git-history dependency, per this project's own documented
   anti-pattern against hardcoded commit SHAs / squash-merge-fragile git
   checks)
10. `mix test` and `mix compile --warnings-as-errors` both pass with real
    output quoted (TEST-RUNNER's obligation, not re-asserted as an ExUnit
    test here)

**Test tier:** unit + integration (real Postgres via `Letflow.DataCase` /
`Letflow.TenantFixture`, DIRECTIVE T-1 — no mocked database). No property
test: `Letflow.Scheduler`/`Letflow.Scheduler.Timer` is not a named
state-machine module in the `Letflow.ProcessInstance` sense (no
`gen_statem`, no closed legal/illegal transition table driven by an
external action sequence) — its "states" are exactly the four DB-CHECK-
constrained `status` values and the transitions between them are covered
exhaustively by the example tests below (arm → fire, arm → error → fire,
arm → error×N → failed), which is a small enough closed set that per-case
examples give equivalent coverage to a generator here, matching this
guide's own "use a property test when a module has a closed set of legal
states/transitions" guidance without inventing a generator that would not
exercise anything the direct tests don't already.

## Test cases

1. AC1 — table lives in the tenant's own Postgres schema (not `public`),
   carries a `tenant_id` column, and the partial index
   `idx_timers_pending_fire_at` exists with the correct partial predicate —
   see `test/letflow/scheduler_test.exs:"AC1: ..."`. Exists because the
   isolation-boundary contract (schema-per-tenant, decision 0003 Decision B)
   and the poller's one hot-query index are both structural claims about the
   migration, not the context module's behavior — a passing `Scheduler`
   function call proves nothing about whether the index/column actually
   exist, so this is checked directly against
   `information_schema`/`pg_indexes`.
2. AC2 — a raw SQL insert with `status = 'expired'` is rejected with
   `Postgrex.Error`/`check_violation` — see
   `test/letflow/scheduler_test.exs:"AC2: ..."`. Exists because the design
   explicitly requires this to be a DB-level backstop independent of the
   changeset's own `validate_inclusion`-style guard (there is in fact no
   changeset-level status guard at all — `arm_changeset/2` doesn't even cast
   `status`) — this proves the constraint exists and is enforced by
   Postgres itself, not merely documented in a comment.
3. AC3 — two cases: (a) a raw insert with `repeat_expression` set and the
   other three recurrence columns `NULL` is rejected with
   `check_violation`; (b) a raw insert with all four recurrence columns
   consistently populated succeeds — see
   `test/letflow/scheduler_test.exs:"AC3: ..."`. Exists because the
   all-or-nothing shape is a compound, multi-column CHECK that no changeset
   in this requirement's scope validates (REQ-186's own callers never write
   the recurrence quartet) — only a real Postgres round-trip proves the
   constraint's boundary is exactly where the design says it is, including
   the specific "trio without the interval" negative case named in the
   acceptance criterion text.
4. AC4 — two tests: a past-`fire_at` timer is claimed and fired by
   `poll_and_fire/1`'s first call, with the appended `TIMER_FIRED` event's
   payload showing `fired_late: true` and both `scheduled_fire_at` /
   `actual_fired_at` present; a future-`fire_at` timer is not claimed or
   fired by that same call — see
   `test/letflow/scheduler_test.exs:"AC4: ..."`. Exists because SCH-05's
   whole "no separate recovery sweep needed" claim depends on the ordinary
   claim query's `fire_at <= now()` filter doing double duty as both "due
   now" and "was due while nothing was polling" — two hand-picked fixtures
   (one on each side of "now") are the direct falsifier of that claim if the
   comparison were flipped, off-by-one, or `fired_late` were computed
   backwards.
5. AC5 — polling the same due timer twice: the second `poll_and_fire/1` call
   claims zero ids for that timer, no second `TIMER_FIRED` event exists, and
   the timer's `fired_at` is unchanged from the first poll — see
   `test/letflow/scheduler_test.exs:"AC5: ..."`. Exists because idempotency
   here is claimed to fall entirely out of the claim query's own `WHERE
   status = 'pending'` filter (design §5) — a mutation removing or weakening
   that filter, or a mutation that re-fires an already-`"fired"` row, is
   exactly what this test is built to catch.
6. AC6 — two due timers in one tenant schema, the first rigged (via a
   `:meck`-free technique — see helper below) to raise inside its fire
   attempt: asserts the first timer's `fire_error_count` becomes `1` and its
   `status` stays `"pending"`, AND the second timer still ends up `"fired"`
   in the same `poll_and_fire/1` call — see
   `test/letflow/scheduler_test.exs:"AC6: ..."`. Exists because this is the
   literal ISS-303/ISS-0618 regression this design's `try/rescue` boundary
   exists to fix — a mutation that lets one timer's raise propagate and
   abort the whole `Enum.reduce/3` loop is exactly what "the remaining due
   timers ... are still attempted" is asserting against.
7. AC7 — a timer driven through `max_fire_retries()` consecutive raising
   fire attempts ends `"failed"` with `failed_at` set, produces exactly one
   `dlq_entries` row with `entry_type == "timer"` (and `reference_id` equal
   to the timer's own id), and a further `poll_and_fire/1` call does not
   claim it again — see `test/letflow/scheduler_test.exs:"AC7: ..."`.
   Exists because "exactly one" is the load-bearing word: a mutation that
   double-enqueues into the DLQ, or that lets a `"failed"` timer be
   reclaimed by a later poll, is exactly what this test is built to catch.
8. AC8 — overrides `:poll_interval_ms` (and confirms the three other keys'
   documented defaults resolve when unset) via
   `Letflow.Scheduler.poll_interval_ms/0` / `jitter_ms/0` /
   `max_timers_per_cycle/0` / `max_fire_retries/0`, AND a `Poller`-specific
   test starts its own supervised `Letflow.Scheduler.Poller` instance
   (per the Step 3 handoff's own instruction — the Poller is not started
   under the ordinary test supervision tree, `config/test.exs`'s
   `start_scheduler: false`) and asserts the overridden interval actually
   changes the delay used for `Process.send_after/3` between ticks — see
   `test/letflow/scheduler_test.exs:"AC8: config defaults"` and
   `test/letflow/scheduler/poller_test.exs:"AC8: Poller uses config
   override"`. Exists because the accessors' own unit correctness (default
   fallback, override honored) is one claim, and the `Poller` actually
   *reading* those accessors on every tick (not caching them at `init/1`
   time) is a separate claim the design explicitly makes (§3.2 step 1) —
   both need their own falsifier.
9. AC9 — no file under `lib/letflow/api/`, `lib/letflow/routers/`, or `web/`
   is a route/controller for `timers`/`scheduler`; concretely, this test
   walks the actual working-tree file list under those directories (not
   `git diff`/`git log`, avoiding the hardcoded-SHA/squash-merge fragility
   `test/letflow/dlq_test.exs`'s own AC6 test comment documents as this
   project's anti-pattern) and asserts none of them reference
   `Letflow.Scheduler`/`timers` — see
   `test/letflow/scheduler_test.exs:"AC9: ..."`.
