# Test Spec: REQ-187 — Wire TIMER nodes into the engine (SCH-01/SCH-03)

**Requirement:** REQ-187 — verbatim acceptance criteria from
`handoffs/WF02-REQ187-20260829/step-03-test-designer.json` (mirrors
`docs/requirements.yaml`'s REQ-187 entry, and REVIEWER's own added item):

1. AC1/AC7: a token reaching a valid `:TIMER` node arms exactly one
   `'pending'` timers row with `fire_at = arrival + parsed duration_iso8601`;
   cover at least one date-part and one time-part duration string, plus the
   `P0D` edge case.
2. AC2: the timer row and the state-transition event are written in the SAME
   transaction — a test that forces the `:event` step to fail after the
   timer-arm `Multi.merge` step must leave NO timers row behind.
3. AC3: firing a timer (`Scheduler.poll_and_fire/1` / a direct
   `do_fire`/`fire_timer` path) advances the live token off the `:TIMER` node
   along its outgoing edge, including the case where that edge leads
   directly into another dispatch-needing node (`:TIMER` -> `:TIMER`,
   `:TIMER` -> `:EXCLUSIVE_GATEWAY`, `:TIMER` -> `:SUB_PROCESS`) resolving
   fully in one `advance_after_timer_fired/3` call.
4. AC4: completing an instance (the `:completed` path through
   `finalize_instance_projection/5`) cancels its `'pending'` timers via
   `cancel_pending_timers/5`, called from the same, unmoved call site.
5. AC5: `cancel_instance/3` cancels `'pending'` timers in the same
   transaction as the cancellation event; a test forcing a later Multi step
   to fail (e.g. `:event`) must leave any timer seeded for that instance
   still `'pending'` — verifying `run_cancel_instance/5`'s
   `:timer_cancellations` step (positioned between `:open_tasks` and
   `:instance_projection`) rolls back correctly.
6. AC6 (SCH-03): a `'fired'` timer is never mutated by a later cancellation
   (status-guarded `update_all`, `WHERE status = 'pending'`); no `'pending'`
   timer belonging to a terminal instance is ever fired by a later poll.
   Cover the concurrency-shaped edge case at the unit/integration level
   available to TEST-DESIGNER (does not need real concurrent Postgres
   transactions if a deterministic ordering can exercise both branches of
   the race).
7. REVIEWER's own added item — the multi-timer-per-hop-chain guard: a
   `:PARALLEL_GATEWAY` split landing two branches on distinct `:TIMER` nodes
   in the same hop-chain must surface `prepare_timer_arms/4`'s
   `{:error, {:multiple_timers_in_one_hop_chain_not_supported, node_ids}}`
   as a typed, non-raising failure — new, defensive logic beyond the design
   doc's original description
   (`handoffs/WF02-REQ187-20260829/req187-reviewer-report.md`).
8. Purity regression: `transition.ex`'s own grep-based purity check (see its
   moduledoc) is exercised as part of this requirement's test suite.
9. Reconstruction: replaying a persisted `TIMER_FIRED` event
   (`Reconstruction.replay/4`) reproduces the same post-fire `InstanceState`
   the live `advance_after_timer_fired/3` path produces, independently.
10. AC8: no route/controller/migration/`web/` file needed to add this
    coverage.

**Test tier:** unit-adjacent + integration (real Postgres via
`Letflow.DataCase` / `Letflow.TenantFixture`, DIRECTIVE T-1 — no mocked
database). The pure-kernel half of AC1/AC3/AC6 (the `:TIMER` node's
`transition/3` dispatch itself: arrival not caught by the catch-all, the
`{:timer_fired, token_id}` hop, the defensive `:token_not_at_timer` error)
is already covered by `test/letflow/engine/transition_test.exs`'s own
`"transition/3 -- :TIMER entry/fired"` describe block (ELIXIR-DEV's
mechanical update for this requirement) and is **not** repeated here — this
file is the DB-level integration half: real `timers` rows, real `Ecto.Multi`
atomicity, real `Scheduler.poll_and_fire/1`, real `cancel_instance/3`/
`create/2` call sites. `test/letflow/engine/task_activation_test.exs`'s own
`"cancel_pending_timers/5"` describe block proves the function's `@doc`
names SCH-03 and both call sites textually, and explicitly defers the real
DB-level coverage of both call sites to `engine_test.exs` — that coverage
never actually landed there, so this file supplies it (AC4/AC5/AC6).
`test/letflow/scheduler_test.exs`/`scheduler/poller_test.exs` already cover
the scheduler-side arm/claim/fire/retry machinery generically (including
one already-armed-`:TIMER`-node fixture) plus REQ-186's own AC9
route/controller structural scan — this file's own AC8 test is a narrower,
REQ-187-specific complement (the 6 files this requirement touched), not a
duplicate.

No property test: this requirement adds no new closed state/transition
table of its own (`timers.status`'s own 4-value closed set was already
REQ-186's own property/example-test target); the scenarios below are a
small enough closed set of node-type/hop-chain shapes that per-case examples
give equivalent coverage to a generator here.

## Test cases

All in `test/letflow/engine/timer_wiring_test.exs` unless noted.

| # | AC | Test | Why this test, not just a restatement |
|---|----|------|----------------------------------------|
| 1 | AC1 | `"a date-part duration (P1D) arms fire_at = arrival + 86400s"` | Proves `parse_iso8601_duration/1`'s date-part unit table (`D` = 86400s) is actually wired end to end through `prepare_timer_arms/4` into a real committed row, not just unit-tested in isolation in `graph_test.exs`. |
| 2 | AC1 | `"a time-part duration (PT1H) arms fire_at = arrival + 3600s"` | Covers the `T`-separated time-part branch of the same parser (`H` = 3600s) — a different code path inside `parse_iso8601_duration/1` (`[date_part, time_part]` clause) than the date-only test above; a bug isolated to the time-part branch would not be caught by test 1. |
| 3 | AC1 | `"the P0D edge case arms fire_at == arrival (zero-second offset)"` | The explicitly named edge case: `seconds = 0` exercises `DateTime.add(now, 0, :second)` and confirms a "fire immediately" timer is still armed as a real `'pending'` row (not skipped, not treated as invalid) rather than firing synchronously inside `create/2`. |
| 4 | AC2 | `"missing :actor_id fails the event append and leaves zero timers rows"` | Reuses `engine_test.exs`'s own REQ-047 AC2 forced-`:event`-failure technique against a `:TIMER`-first graph — proves the timer-arm `Multi.merge` step and `:event` genuinely share one `Ecto.Multi`/transaction, not merely "usually run together." Without this test, a regression that moved timer-arming into its own separate `Repo.transaction/1` (breaking the atomicity guarantee) would go undetected by test 1-3 alone (mutation-confirmed, see handoff report). |
| 5 | AC3 | `"TIMER -> END: the instance completes and the token is no longer at the TIMER node"` | The base case named in the AC text: fires via the real `Scheduler.poll_and_fire/1` entrypoint (not a lower-level `do_fire`/`fire_timer` call), proving the full poller-to-engine re-entry wiring, and asserts both halves of "advances the token" — the live `TokenRecord` reaches `:completed` AND the `instance_projections` row reaches `:completed`, not just one or the other. |
| 6 | AC3 | `"TIMER -> TIMER -> END: firing the first arms a NEW pending timer for the second, in the same call"` | The AC text's own named "edge leads directly into another dispatch-needing node" case, using `:TIMER -> :TIMER` (the shape design doc §8.4 calls out explicitly: "a `:TIMER` node's outgoing edge can lead directly into another `:TIMER` node"). Proves `advance_after_timer_fired/3`'s own internal `prepare_timer_arms/4` + `build_timer_arms_multi/4` reuse resolves the WHOLE hop-chain (fire A, arm B) inside one call, not just the first hop — also re-checks AC1's own `fire_at = arrival + duration` contract for the re-armed second timer, with "arrival" now being the first timer's own `fired_at` (a fresh clock read at fire time, per design doc §8.4), not the original instance-creation timestamp. |
| 7 | AC4 | `"cancel_pending_timers/5 with reason instance_completed cancels a real pending timer"` | Per design doc §5.2's own scope note, a `:TIMER`-parked token structurally prevents `create/2`'s single hop-chain from ever reaching `:completed` while a sibling timer is pending (confirmed by direct analysis: the only path to `finalize_instance_projection/5`'s `:completed` clause is `create/2`'s own initial hop-chain, and any live `:TIMER`-parked token keeps `remaining_tokens` non-empty). This test therefore exercises the exact real, production `cancel_pending_timers/5` function with the exact params/reason string that call site uses, against a real seeded pending timer — the strongest test available for a call site the design itself documents as unreachable via ordinary flow. |
| 8 | AC4 | `"finalize_instance_projection/5's :completed clause still calls it, unmoved, right after the projection update"` | Source-text structural check (mirrors `engine_cancel_instance_test.exs`'s own AC6/AC7 moduledoc-content-assertion precedent) confirming the call site itself still exists, in the same clause, textually after the `repo.update(prefix: prefix)` call, with the `"instance_completed"` reason string — this is what makes test 7 relevant to the ACTUAL call site rather than a same-shaped-but-disconnected function. |
| 9 | AC5 | `"an ordinary cancel_instance/3 call cancels the instance's pending timer with reason instance_cancelled"` | The organically-reachable half of AC5 (unlike AC4's call site, `cancel_instance/3` genuinely can be called while a `:TIMER`-parked token exists) — a real end-to-end call through the public API, not a direct `TaskActivation` call. |
| 10 | AC5 | `"forcing the :event step to fail (idempotency_key too long) rolls back :timer_cancellations too"` | The AC's own named rollback test. `cancel_instance/3`'s own pre-transaction phase only checks actor_id/idempotency_key presence (not length), so a 256-char idempotency_key reaches `EventStore.append/2`'s own pre-transaction `fetch_idempotency_key/1` check and fails the `:event` Multi step from inside the already-open transaction — proving `:timer_cancellations` genuinely participates in the same all-or-nothing `Ecto.Multi`, not merely running first. |
| 11 | AC5 | `"run_cancel_instance/5's own Multi places :timer_cancellations between :open_tasks and :instance_projection"` | Design doc §6.2's lock-ordering fix (avoiding an AB-BA Postgres deadlock against `Scheduler.fire_timer/2`'s own `timers`-then-`instance_projections` lock order) is NOT observable via any single-process assertion — a reordering back to the "topically obvious" pre-fix spot (grouped with `:task_cancellations`/`:token_cancellations` after `:eligibility`) doesn't change any test-10-observable outcome. This structural/source-position test is what actually catches that regression (mutation-confirmed — test 10 alone does not catch it). |
| 12 | AC6 | `"TIMER -> HUMAN_TASK -> END: firing the timer then cancelling the instance leaves the fired row untouched"` | Direct proof of the status-guarded `UPDATE ... WHERE status = 'pending'`: a real `'fired'` row, produced by a real fire, is left with `cancelled_at: nil`/`cancel_reason: nil` after a real subsequent `cancel_instance/3` call on the same (still-active) instance. |
| 13 | AC6 | `"cancelling the instance first, then attempting to fire its (now-cancelled) timer directly, is a no-op"` | The other direction of the SCH-03 race, as a deterministic stand-in for true concurrency (per the handoff's own "does not need real concurrent Postgres transactions if a deterministic ordering can exercise both branches" allowance): cancels first (making the timer `'cancelled'`), then calls `Scheduler.fire_timer/2` directly against that exact `timer_id` — proving `fire_timer/2`'s own `status != "pending" -> :already_final` guard is what prevents a `'cancelled'` timer from ever producing a `TIMER_FIRED` event, independent of `claim_due_timer_ids/2`'s own `WHERE status = 'pending'` filtering (which would trivially exclude it — this test proves the guard, not just the filter). |
| 14 | new item | `"a PARALLEL_GATEWAY split arming two TIMER nodes at once returns a typed error, never raises"` | REVIEWER's own added regression test. A `:PARALLEL_GATEWAY` split landing 2 branches directly on 2 distinct `:TIMER` nodes, structurally validated (`find_matching_join/2` is satisfied since both branches' own first edge reaches the same join), resolves within `create/2`'s own single hop-chain — exactly `prepare_timer_arms/4`'s own `length(timer_arms) > 1` guard scenario. Wrapped in a `try/rescue` to make "never raises" an explicit, checked assertion rather than an assumption; also asserts zero rows committed anywhere (the whole attempt aborts in `start_instance/5`'s pre-`Multi` `with` chain). |
| 15 | AC8 | `"transition.ex (+ its 2 pure siblings) gain no Repo/clock call"` | Wires the module's own documented grep command (moduledoc "Purity (AC1)" section) into a standing, runnable `mix test` check — previously only code-inspection evidence per `test/specs/REQ-044.md`. Strips each file's own `@moduledoc` heredoc before scanning so the moduledoc's own quoted grep command text (which literally contains the string `"Logger."` as documentation) doesn't self-trigger a false positive. |
| 16 | AC8 (route/controller) | `"none of the 6 files REQ-187 touched are Plug.Router/controller-shaped"` + `"no file under lib/letflow/api/ or lib/letflow/routers/ references advance_after_timer_fired or TIMER_FIRED"` | Complements `scheduler_test.exs`'s own broader AC9 scan (which covers `Letflow.Scheduler`/`"timers"` references generically, REQ-186's own scope) with a REQ-187-specific check naming this requirement's own new engine-level identifiers. No hardcoded commit SHA / git-history dependency, per this project's own documented anti-pattern (`docs/anti-patterns.md`, `dlq_test.exs`'s own AC6 precedent). |
| 17 | new item | `"the live token's post-fire node_id/status matches a pure replay from the event log"` (`Reconstruction.reconstruct_instance/2`) | Proves the design's own "two independent derivations of the same post-`TIMER_FIRED` state" claim (design doc §9) empirically: fires a timer via the live path, then calls the completely independent `Reconstruction` code path against the same instance's event log, and confirms they agree on the live token's final `node_id`/status. |

## Mutation-testing evidence (this file's own coverage, not re-derived by
## TEST-RUNNER)

4 mutations applied to the shipped implementation and confirmed caught by
this file's tests, then reverted (`git diff` confirmed clean against the
committed tree after each revert):

1. **`task_activation.ex`'s `cancel_pending_timers/5`** — removed the
   `and t.status == "pending"` guard from the `update_all`'s `where/3`
   clause. Caught by test 12 (`"TIMER -> HUMAN_TASK -> END: firing the timer
   then cancelling the instance leaves the fired row untouched"`) — the
   fired row's `status` flipped to `"cancelled"` unexpectedly.
2. **`engine.ex`'s `persist/11`** — replaced `prepared_timers` with `[]` in
   the create-path `Multi.merge` step that builds the timer-arm sub-`Multi`
   (skips appending the timer row even though the state-transition event
   still commits). Caught by 11 of 18 tests, most directly tests 1-3 (AC1 —
   zero timers rows ever created) and test 4 (AC2 — trivially "passes" for
   the wrong reason without tests 1-3 also failing, which they did).
3. **`engine.ex`'s `run_cancel_instance/5`** — moved the `:timer_cancellations`
   Multi step back to its topically-grouped, pre-fix position (after
   `:eligibility`, alongside `:task_cancellations`/`:token_cancellations`).
   Caught by test 11 (the dedicated structural lock-ordering test) — no
   other test in this file distinguishes the two positions in a
   single-process run, confirming that structural test is load-bearing on
   its own, not redundant with test 10.
4. **`engine.ex`'s `prepare_timer_arms/4`** — replaced the
   `length(timer_arms) > 1` guard condition with a hardcoded `false`,
   restoring the pre-fix behavior of calling `build_timer_arms_multi/4` with
   more than one timer. Caught by test 14 — `Engine.create/2` raised
   instead of returning the typed error tuple.
