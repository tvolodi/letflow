## Fixture strategy — the gateway/loop graph

`maybe_rearm_timer/3` is invoked from `do_fire/2`'s `with` chain only AFTER
`Letflow.Engine.advance_after_timer_fired/3` succeeds (REQ-187), which requires the
timer's `token_id` to match a live token **currently parked at a `:TIMER` node**
(`Letflow.Engine.Transition.dispatch_timer_fired/4` returns
`{:error, {:token_not_at_timer, ...}}` otherwise). Observing a recurring chain fire
more than once through the real, unmocked engine therefore requires a token that
returns to a `:TIMER` node after every firing.

A bare self-loop (`"loop" -> "loop"`) is rejected by `Letflow.Definitions.Graph`'s
CHK-06 cycle check (`:cycle_without_gateway` — a cycle must pass through a gateway
node). `graph_gateway_loop/1` (both test files) instead uses `START -> gw
(EXCLUSIVE_GATEWAY) -> loop (TIMER) -> gw` — a 2-node cycle through the gateway,
permitted by CHK-06 — plus an always-false conditioned edge `gw -> end` so CHK-02
(an END node must exist) and CHK-04 (every node has the right edge shape) are
satisfied without ever being taken.

Firing the token off `loop` sends it to `gw`, which dispatches back to `loop` in the
same `advance_until_stable/4` worklist. `tokens_needing_dispatch/3`'s own
`previous_node_id` comparison is **local to the current hop** — `advance_until_stable/4`
(engine.ex:847-853) re-derives `previous_tokens` from the `instance_state` immediately
preceding that specific recursive call, not from the chain's original seed state. So
on the `gw -> loop` hop, the previous node id is `"gw"`, the node id genuinely changed
for that hop, and `Letflow.Engine`'s own REQ-187 `prepare_timer_arms/4` auto-rearm
**does fire again** — confirmed empirically (temporary debug count, reverted): across
AC2's 3 real firings this produces 1 initial arm (at instance creation) + 3 per-firing
arms = 4 `repeat_expression IS NULL` `Timer` rows for that chain, not 1.

This is harmless to every assertion in both test files, for three independently
verified reasons:
1. Every test that counts "this chain's rows" filters `not is_nil(t.repeat_expression)`,
   and the REQ-187 auto-rearm arms never set that field (verified directly:
   `resolve_timer_arm_attrs/4` in `lib/letflow/engine.ex` builds only
   `instance_id/timer_type/node_id/fire_at`, no repeat fields).
2. This graph also auto-arms a REQ-187-style duration-based (`duration_iso8601: "P1D"`)
   timer on every hop, each with `fire_at` a day out — deliberately never claimed by
   any poll in these tests.
3. It cannot collide with `maybe_rearm_timer/3`'s own `:scheduler_timer`-named
   `Ecto.Multi` insert step: `Letflow.Engine.advance_after_timer_fired/3` commits its
   own nested `Multi` (containing any REQ-187 side-arm) to completion before
   `maybe_rearm_timer/3` ever runs its own, separate insert — two different `Multi`
   structs, each with their own step name, never merged into one.

This lets each test manually arm its OWN separate `Letflow.Scheduler.Timer` row
(via `Scheduler.create/2`, `node_id: "loop"`, sharing the graph's one real live
`token_id`) with whatever `repeat_expression`/`repeat_interval_us`/`repeat_total`
quartet the acceptance criterion needs, and fire it via the real
`Scheduler.fire_timer/2`/`poll_and_fire/1` entry points — no mocking library exists
in this codebase and none is introduced here.

`repeat_interval_us` is test-controlled independently of what `repeat_expression`'s
string literally says (REQ-188 design §1.1's own OQ-1: parsing the ISO 8601 repeat
grammar into an interval is explicitly out of scope — `repeat_expression` is a
carried-forward audit string only). AC1 needs the literal "+1 hour" value the
acceptance criterion states, so it uses `repeat_interval_us: 3_600_000_000`
verbatim; AC2/AC4 use much smaller intervals (so multiple cycles run instantly,
with no test depending on wall-clock waiting) while still labeling the row with the
AC's own descriptive `repeat_expression` string.

## Mutation testing (see handoff for full output)

Five mutations were applied one at a time to `lib/letflow/scheduler.ex` /
`lib/letflow/scheduler/poller.ex`, each shown to break at least one of the tests
above, then reverted (confirmed via `git diff` showing a clean working tree):

1. Anchor `fire_at` to the actual firing time (`fired_at`) instead of the fired
   timer's own scheduled `fire_at` — caught by AC1a's exact `fire_at` assertion.
2. Remove the `repeat_total` cap check (`new_fired_count >= fired_timer.repeat_total`)
   so re-arming never stops — caught by AC2's row-count-stays-3 assertion.
3. Flip `retention_enabled?/0`'s default to `true` — caught by AC5's
   row-counts-unchanged assertion.
4. Skip the `retention_due?/1` check in `Poller.maybe_run_retention_sweep/2` —
   caught by AC6/AC5's `last_retention_run_at`/row-count assertions.
5. Make `maybe_rearm_timer/3`'s insert fire off a separate `Task.start/1` (its own
   connection, outside `fire_timer/2`'s transaction) instead of the caller's
   `Repo`/prefix — caught by AC1b's forced-rollback assertion.
