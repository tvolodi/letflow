## Test cases

### AC1 — put/2 + resolve/2 round trip; ciphertext column does not contain plaintext

1. `"put/2 followed by resolve/2 returns the identical plaintext, and Secret.ciphertext does not contain the plaintext bytes"` — writes a secret via `Letflow.Secrets.put/2`, reads the row back directly via `Repo.get_by(Secret, ...)`, asserts `ciphertext` (raw binary) does not contain the plaintext as a substring and is not equal to it, then calls `resolve/2` and asserts the returned plaintext is byte-identical to the original. Exists because "round trip returns identical plaintext" and "ciphertext column does not contain the plaintext" are two independent claims — a test asserting only the round trip could pass even if `put/2` degenerated to storing the plaintext directly (e.g. a no-op "encryption" bug) as long as `resolve/2` just read it back; the direct binary inspection of the stored column is what actually proves encryption happened. See `test/letflow/secrets_test.exs:round trip`.
2. `property "put/2 -> resolve/2 round-trips arbitrary binary plaintext without ever storing it verbatim"` — a `StreamData` property over `binary()` plaintext generators (including the empty binary, single-byte, and larger multi-KB binaries, non-UTF8-safe bytes included since `binary()` is not `String.printable?`-constrained), asserting for every generated plaintext: (a) `resolve/2` returns the exact same bytes, (b) the stored `ciphertext` never contains the plaintext as a substring. This generalizes case 1 beyond one hand-picked plaintext — the codebase's own `StreamData` convention (`test/letflow/oidc/claim_mapping_property_test.exs`) is followed for exactly the reason that guide states: standing in for what a fixed example set can't cover across a wide input space. See `test/letflow/secrets_test.exs:property round trip`.

   **REAL DEFECT FOUND, currently causing this property to fail (not a test bug):**
   `Letflow.Secrets.Secret.insert_changeset/2`'s `validate_required/2` call includes
   `:ciphertext` (and every other `:binary` column) in its cast list, and Ecto's
   `validate_required/2` treats an empty binary (`""`, i.e. a 0-byte value) as
   "blank" exactly the same way it treats an empty *string* as blank — so `put/2`
   called with `plaintext: ""` produces a 0-byte `ciphertext` (correct AES-256-GCM
   output for empty input) that the changeset then rejects with
   `ciphertext: {"can't be blank", [validation: :required]}`, and `put/2` returns
   `{:error, changeset}` instead of succeeding. Neither the design doc
   (`lib/letflow/design/req190-secrets-core.md`) nor the requirement text places any
   non-empty constraint on `plaintext :: binary()` — `put_attrs()`'s own `@type` is
   unconstrained `binary()` — so this is a genuine implementation gap, not
   out-of-scope input. Reproduced directly: `mix test test/letflow/secrets_test.exs`
   fails this property deterministically at the empty-binary case (StreamData
   shrinks straight to `""`). TEST-DESIGNER has no authority to edit `lib/`, so the
   property test is left as designed (narrowing it to `min_length: 1` would hide a
   real bug rather than prove coverage) and this finding is reported to ORCH in this
   step's handoff for routing back to ELIXIR-DEV.

### AC2 — put/2's return shape

3. `"put/2 returns exactly {:ok, %{reference:, key_id:, created_at:}} and nothing else"` — asserts via `Map.keys/1` on the returned map (not just presence of the three expected keys) that the key set is exactly `[:created_at, :key_id, :reference]` — a returned map carrying an extra `:plaintext` or `:ciphertext` key alongside the three expected ones would pass a `match?` assertion that samples only the expected keys, but fails this one. See `test/letflow/secrets_test.exs:put return shape`.

### AC3 — tenant-mismatch rejection, non-disclosure, before any query

4. `"resolve/2 with a reference naming a genuinely nonexistent tenant, and one naming a real different tenant, both return the identical {:error, :tenant_mismatch} tuple"` — asserts the two cases return `==`-identical error terms (not just "both fail"), which is what "the error does not disclose whether that secret exists" actually requires: if the two cases returned different error shapes, a caller could distinguish them and learn whether the tenant is real. See `test/letflow/secrets_test.exs:tenant mismatch non-disclosure`.
5. `"resolve/2 rejects a cross-tenant reference without ever issuing a secrets-table query"` — uses `Ecto.Adapters.SQL.Sandbox`'s query-count telemetry is unavailable here without extra plumbing, so this is proven structurally instead: a reference naming a real tenant B is resolved by a caller scoped to tenant A, where tenant B has **zero** secrets of any kind — if `resolve/2` ran a `secrets` query before the tenant check, a row-shaped bug could only manifest as `{:error, :not_found}` (since there's nothing to find) which is observably different from `{:error, :tenant_mismatch}`; asserting the actual returned error is `:tenant_mismatch` (not `:not_found`) demonstrates the tenant check, not a fallthrough table miss, is what actually fired. See `test/letflow/secrets_test.exs:tenant check ordering`.

### AC4 — purpose/consumer matrix

6. `"a :webhook_dispatcher consumer resolves a :webhook_hmac-purpose secret successfully"` — see `test/letflow/secrets_test.exs:purpose matrix`.
7. `"a :webhook_dispatcher consumer resolves a :generic-purpose secret successfully"` — the matrix's other permitted cell; exists separately from case 6 because the design's table (§3.2) is 2x2 and the two `:webhook_dispatcher` rows are logically independent claims — case 6 alone wouldn't rule out a bug that special-cased `:webhook_hmac` correctly but broke the `:generic` permission. See `test/letflow/secrets_test.exs:purpose matrix`.
8. `"a :generic consumer (default, opts[:consumer] omitted) fails to resolve a :webhook_hmac-purpose secret with {:error, :purpose_not_allowed}"` — see `test/letflow/secrets_test.exs:purpose matrix`.
9. `"a :generic consumer resolves a :generic-purpose secret successfully"` — completes the 2x2 matrix; also exercises `opts[:consumer]` being entirely omitted (not passed at all) to prove the stated default. See `test/letflow/secrets_test.exs:purpose matrix`.

### AC5 — unpinned resolves to newest ACTIVE version, not merely newest row

10. `"two versions exist for the same (tenant, namespace, name); the newer one is disabled; an unpinned reference resolves to the OLDER, still-active version's plaintext"` — this is the exact R-Co-defect-correction case the requirement names verbatim. Distinguishes "filters by status in the DB query" from "just orders by created_at DESC and takes the first row regardless of status" — the latter (R-Co's bug) would return the disabled version's plaintext here, which this test would catch by asserting the returned plaintext matches the older version's, not the newer one's. See `test/letflow/secrets_test.exs:unpinned resolves to newest active`.
11. `"a pinned reference (#<key_id>) to the disabled newer version still resolves successfully"` — design §3.2 step 4's stated asymmetry (disabled-but-pinned succeeds); included alongside case 10 so the two resolution modes (pinned vs. unpinned) are each independently proven against the same two-version fixture, not conflated. See `test/letflow/secrets_test.exs:pinned resolves disabled version`.

### AC6 — master-key missing/malformed fails startup (two tests)

**Why an out-of-process subprocess, not an in-VM assertion.** The validation lives
in `config/runtime.exs`, which is evaluated once, before `Letflow.Application.start/2`
runs, as part of the BEAM node's boot sequence — it is not a callable function this
suite's own already-booted node can re-invoke with a different env var value without
restarting the node (`config/test.exs` has already set a valid value by the time any
test process exists, and mutating `Application.get_env/2` after boot would not
re-exercise `config/runtime.exs`'s own `raise` statements, only the module's later
*read* of the already-resolved value via `Application.fetch_env!/2`). Spiked and
confirmed real subprocess behavior before writing these tests (commands and observed
output recorded in the handoff — see below):

- `LETFLOW_SECRETS_MASTER_KEY="" MIX_ENV=test mix run -e "..."` → exit code 1, stderr
  contains the exact "is malformed" message.
- `env -u LETFLOW_SECRETS_MASTER_KEY MIX_ENV=dev mix run -e "..."` → exit code 1,
  stderr contains the exact "is missing" message (note: `MIX_ENV=test` cannot
  exercise the truly-*absent* case because `config/test.exs` itself injects a
  fallback value when absent — by design, so the rest of this suite can boot at
  all — so this one case deliberately uses `MIX_ENV=dev`, which requires no live
  Postgres connection because the `raise` fires during config evaluation, before
  `Letflow.Repo` ever attempts to connect).

12. `"LETFLOW_SECRETS_MASTER_KEY unset fails application boot with a clear 'is missing' error"` — `System.cmd/3` spawns `mix run -e ...` in `MIX_ENV=dev` with the env var explicitly absent from the child's environment, asserts non-zero exit status and that combined output contains the exact "is missing" message. See `test/letflow/secrets_runtime_config_test.exs`.
13. `"LETFLOW_SECRETS_MASTER_KEY set to a malformed value (wrong length) fails application boot with a clear 'is malformed' error"` — same mechanism, `MIX_ENV=test` (test's own DB config still applies here — irrelevant, since boot never reaches `Letflow.Repo`), env var explicitly set to an empty string (also covers "present but empty" as one malformed shape). See `test/letflow/secrets_runtime_config_test.exs`.

These two tests are `@tag :slow` (they shell out to a fresh `mix run`, materially
slower than the rest of the suite) but not `@tag :skip` — DIRECTIVE T-1's "a
requirement whose test cases are entirely skipped stays in_progress" does not apply
to a *tagged-but-run* test; `mix test` runs all tags by default in this project
(confirmed: no `ExUnit.configure(exclude: [:slow])` anywhere in `test/test_helper.exs`).

### AC7 — redaction of the exact key list

14. `"redact_map/1 replaces the value under each of secret, password, token, client_secret, and a key ending in _secret with [REDACTED], keeping every key name"` — one property-shaped example test iterating the exact key list the requirement names (`secret`, `password`, `token`, `client_secret`, plus one `_secret`-suffixed key, e.g. `"my_custom_secret"`), asserting each value becomes `"[REDACTED]"` and every key is still present and unchanged, and a sixth, unlisted key (`"harmless"`) is left untouched — the negative case is included so the test cannot pass by a bug that redacts everything indiscriminately. See `test/letflow/secrets/redaction_test.exs:redact_map exact keys`.
15. `"a log call passing a value under a sensitive key emits [REDACTED] in captured log output, via the real :logger primary filter Letflow.Application registers"` — uses `ExUnit.CaptureLog.capture_log/1` around a real `Logger.info/2` call carrying `%{secret: "sh"}` metadata, asserting the captured output contains `"[REDACTED]"` and does not contain the literal plaintext `"sh"` value under that key. This is the criterion's own literal wording ("asserted against captured log output") — case 14 alone tests the pure function; this one proves the Logger integration wiring (`Letflow.Secrets.LogFilter`, registered in `Letflow.Application.start/2`) actually intercepts a real log call, which is a materially different failure mode (the filter could be correctly implemented but never registered, or registered on the wrong hook). See `test/letflow/secrets/log_filter_test.exs`.

### AC8 — reference-redaction masking

16. `"render_reference/1 masks the key_id segment of a pinned reference, and leaves an unpinned reference unchanged"` — two assertions in one test: `"sec://tenant/acme/webhook/sub-1#7"` → `"sec://tenant/acme/webhook/sub-1#***"`, and `"sec://tenant/acme/webhook/sub-1"` (no `#` segment) → itself, unchanged. Both cases are required by the acceptance criterion's own wording ("asserted on a reference that has a key id and on one that does not"). See `test/letflow/secrets/redaction_test.exs:render_reference`.

### AC9 — webhook HMAC reconciliation end to end

17. `"Letflow.Webhooks.create/2 writes the HMAC secret via Letflow.Secrets.put/2 with a webhook purpose; the subscription's secret_ref/secret_key_id resolve via resolve/2 (consumer: :webhook_dispatcher) to the exact hmac_secret_once plaintext; secret_hash is NULL on the persisted row"` — the full path: create a subscription, capture `hmac_secret_once`, independently resolve `subscription.secret_ref` (pinned via `secret_key_id`, since that's the version this specific creation wrote) as a `:webhook_dispatcher` consumer, assert the resolved plaintext equals `hmac_secret_once` byte-for-byte, then re-read the row directly from Postgres (bypassing the `Ecto.Schema`'s own unmapped-column silence) and assert its raw `secret_hash` column is `NULL`. Exists because this is the one acceptance criterion that spans two modules (`Letflow.Webhooks` and `Letflow.Secrets`) — a unit test of either module alone could pass while the integration between them (the exact `namespace`/`name`/`purpose` `create/2` passes to `put/2`) is wrong in a way that breaks `resolve/2` for a real webhook consumer. See `test/letflow/secrets_test.exs:webhook HMAC reconciliation`.

### AC10 — moduledoc honest-limitation statement

18. `"Letflow.Secrets.Redaction's moduledoc states redaction keys on field NAMES and does not claim content-based detection"` — reads the compiled module's `@moduledoc` via `Code.fetch_docs/1` and asserts it contains the phrase "field NAME" (or equivalent honest-limitation wording) and does not contain an absolute-guarantee claim — a direct check against the actual shipped documentation, not a paraphrase of what the design doc says the moduledoc should contain. See `test/letflow/secrets/redaction_test.exs:moduledoc honesty`.

### AC11 — no route/controller touched

19. `"git diff --stat scoped to this requirement's commits touches no lib/letflow/routers/*.ex file"` — runs `git diff --stat <merge-base>...HEAD -- lib/letflow/routers` via `System.cmd/3` inside the test and asserts empty output, plus a static-source check (mirroring `test/letflow/webhooks_test.exs`'s own AC6 pattern) that `lib/letflow/secrets.ex`, `lib/letflow/secrets/secret.ex`, `lib/letflow/secrets/redaction.ex`, and `lib/letflow/secrets/log_filter.ex` each contain no `use Plug.Router`, no `use ...Web, :controller`, and no route-macro call. This is the acceptance criterion's own literal wording ("confirmed by git diff --stat"), verified programmatically rather than only by a human reading the diff. See `test/letflow/secrets_test.exs:no route or controller touched`.

## webhooks_test.exs staleness fix (not a REQ-190 acceptance criterion, but in this step's scope)

`test/letflow/webhooks_test.exs`'s AC1 and AC2 describe blocks asserted against the
now-removed `secret_hash`-as-plaintext-hash behavior REQ-190 superseded (0016 §F). Per
ELIXIR-DEV's and REVIEWER's/SECURITY-REVIEWER's confirmation that this is expected
fallout from 0016 §F superseding REQ-181's hashed-secret storage (not a regression),
these assertions are updated in place to the new `secret_ref`/`secret_key_id` reality:

- AC1's schema-introspection test: `secret_hash` remains a real column in
  `information_schema.columns` (the migration blanks it, doesn't drop it) — that
  assertion is unchanged and still true. Added assertions that `secret_ref` and
  `secret_key_id` are also present columns, since AC1's own claim ("the table exists ...
  with these columns") is incomplete without them post-REQ-190.
- AC2's "generates one, stores only the SHA-256 hash" test is rewritten to
  "generates one, stores it via the secrets table (secret_ref/secret_key_id), never a
  plaintext-derived hash in secret_hash" — asserts `subscription.secret_ref` is a
  well-formed `sec://tenant/...` string, `subscription.secret_key_id` is a
  `pos_integer()`, and (directly against Postgres, since the `Subscription` struct has
  no field for the column at all) the raw `secret_hash` column value is `NULL` — the
  literal REQ-190 assertion ("no plaintext secret persist[s] in
  webhook_subscriptions"), which is a *strictly stronger* claim than the old
  hash-equality assertion it replaces, not a weakening.
- AC2's "list/1 never exposes plaintext" test's `secret_hash != plaintext` /
  `secret_hash == subscription.secret_hash` assertions (comparing against a field the
  `Subscription` struct no longer has at all) are replaced with: `listed.secret_ref ==
  subscription.secret_ref` and `refute Map.has_key?(Map.from_struct(listed),
  :secret_hash)` (the struct-level non-existence is now itself the assertion, matching
  `Letflow.Webhooks.Subscription`'s own moduledoc claim that no field maps to that
  column at all).
