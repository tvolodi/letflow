# REQ-191 — Service catalog core: acceptance criteria -> test cases

Test file: `test/letflow/service_catalog_test.exs`. Design authority:
`lib/letflow/design/req191-service-catalog-core.md`. Implementation
authority: `lib/letflow/service_catalog.ex`, `lib/letflow/service_catalog/entry.ex`,
`priv/repo/migrations/20260830000001_create_service_catalog.exs`.

## AC1 — scope/owner_tenant_id consistency is a DATABASE-level CHECK

**Criterion:** an insert with `scope = 'global'` and a non-null
`owner_tenant_id` is rejected by the database, and so is one with
`scope = 'tenant'` and a null `owner_tenant_id` — at the DB level, not
merely at the changeset level.

**Tests:**
- `"scope = 'global' with a non-null owner_tenant_id is rejected by the database"`
- `"scope = 'tenant' with a null owner_tenant_id is rejected by the database"`

**Why each exists:** both use a raw `Repo.query/2` SQL `INSERT` that
deliberately bypasses `Entry.insert_changeset/2` (and therefore its
`check_constraint/3` mapping) entirely. If either test went through
`Letflow.ServiceCatalog.register/1` instead, a passing assertion could mean
only that the changeset's own advisory check ran — never that the database
itself enforces anything. Asserting `%Postgrex.Error{postgres: %{code:
:check_violation}}}` directly from the raw connection is the only way a
green test can only mean "the database rejected this," which is exactly
what the acceptance criterion requires ("not changeset-level").

## AC2 — required_auth / timeout_ms are DATABASE-level CHECKs

**Criterion:** `required_auth = 'BASIC'` is rejected by the database, and so
is `timeout_ms = 0` and `timeout_ms = 3_600_001`.

**Tests:**
- `"required_auth = 'BASIC' is rejected by the database"`
- `"timeout_ms = 0 is rejected by the database"`
- `"timeout_ms = 3_600_001 is rejected by the database"`

**Why each exists:** same raw-SQL rationale as AC1. `0` and `3_600_001` are
the two boundary values immediately outside the valid `1..3_600_000` range
— the values most likely to survive a future off-by-one edit to the `CHECK`
clause undetected if only a mid-range value were tested.

## AC3 — get_for_tenant/2's three-way visibility rule

**Criterion:** a global service is visible to any tenant; a tenant-scoped
service is visible to its owner; a tenant-scoped service owned by a
different tenant returns `{:error, :not_found}` — the identical shape a
genuinely missing service returns, never a `:forbidden`/`:unauthorized`
variant.

**Tests:**
- `"a global service is visible to any tenant"`
- `"a tenant-scoped service is visible to its owner"`
- `"a tenant-scoped service owned by a different tenant is NOT_FOUND, not forbidden"`
- `"a real-but-invisible service and a genuinely missing service produce the identical error shape"`

**Why each exists:** REVIEWER's own sign-off note (recorded on the Step 3
handoff) flags that this predicate is now the SOLE tenant-isolation
mechanism for this table (no physical schema separation backstops it) — so
this is treated as load-bearing security coverage, not an ordinary
business-rule check. The fourth test goes beyond "both return the atom
`:not_found`" (which two independently-written branches could satisfy by
coincidence) and asserts the two *result values* are `==` to each other, so
a future change that attaches distinguishing metadata to only one branch
(e.g. a reason code) would be caught here even though each branch's own
atom would still look correct in isolation.

## AC4 — service_id is globally unique across all tenants and both scopes

**Criterion:** registering the same `service_id` for a second, different
tenant fails, even when the first registration is tenant-scoped.

**Test:** `"registering the same service_id for a second, different tenant fails, even when the first is tenant-scoped"`

**Why it exists:** the design deliberately makes `service_id` the table's
primary key so uniqueness is enforced "for free" by the PK rather than a
separate index — this test exercises exactly the case that would break if
someone "fixed" that by adding a tenant-scoped partial unique index instead
(which would incorrectly allow two tenants to each register the same
`service_id`). The test also re-reads the surviving row afterward to
confirm no silent overwrite occurred.

## AC5 — register/1 rejects a non-existent tenant, no row created

**Criterion:** `register/1` with `scope: :tenant` naming a tenant that does
not exist is rejected, and no row is created.

**Test:** `"returns {:error, :tenant_not_found} and creates no row"`

**Why it exists:** this is the one existence check that runs entirely in
Elixir before any insert is attempted (`check_tenant_exists/1`) — a DB-level
FK constraint alone would also reject an insert naming an unknown tenant,
but only after attempting the write; this test's explicit `refute Repo.get`
confirms the pre-insert-check contract the design specifically calls for
("rejected without creating a row"), not merely "eventually rejected."

## AC6 — delete/1's referential guard, structural not substring

**Criterion:** delete of a service referenced by an ACTIVE definition is
refused, naming the referencing definition id(s); delete of an unreferenced
service succeeds; a service id appearing only as a substring inside an
unrelated string in some definition's graph does NOT block delete.

**Tests:**
- `"delete of a service referenced by an ACTIVE definition is refused, naming the referencing definition id"`
- `"delete of an unreferenced service succeeds"`
- `"a service id appearing only as a substring inside an unrelated string does NOT block delete"`
- `"a concurrent delete of the same row is treated as a benign not-found, not a crash"`

**Why each exists:** the third test is the design's own proof-of-correctness
case for diverging from R-Co's `LIKE '%' || service_id || '%'` guard — it
plants the service_id as plain text inside an unrelated `HUMAN_TASK` node's
`"description"` attribute (never as a `SERVICE_TASK` node's own
`"service_id"` attribute) and asserts delete succeeds; a regression back to
a substring/LIKE-based guard would incorrectly block this delete, which is
exactly the mutation-tested case (see below). The fourth test is regression
coverage for the SECURITY-REVIEWER rework this requirement's own handoff
names (an unhandled `Ecto.StaleEntryError`): rather than hoping two
processes race by chance, it deterministically forces the exact race window
`delete_entry/1`'s own comment documents, by holding a real Postgres
row-level lock open in one process while `delete/1` runs concurrently in
another, so the second `DELETE` is guaranteed to run against a row that
vanished between `delete/1`'s own `Repo.get/2` and `Repo.delete/1`.

## AC7 — update_scope/2: narrow refused (naming conflicting tenants), widen always allowed

**Criterion:** narrowing global -> tenant is refused, naming the
conflicting tenant ids, when another tenant's ACTIVE definition references
it; widening tenant -> global is always allowed.

**Tests:**
- `"narrowing global -> tenant is refused, naming the conflicting tenant, when another tenant's ACTIVE definition references it"`
- `"narrowing global -> tenant succeeds when only the assignee tenant itself references it (self-exemption)"`
- `"widening tenant -> global always succeeds, even with other tenants' ACTIVE references"`

**Why each exists:** the second test is not directly named by the
acceptance-criteria list but exercises the design's own stated exemption
("the tenant the service is being assigned to is allowed to already
reference it") — without it, a regression that removed the exemption
entirely (making every narrow refuse whenever any reference exists,
including the assignee's own) would still pass the first and third tests.
The third test deliberately registers an ACTIVE reference from an
*unrelated* tenant before widening, to prove widening's "always" is
unconditional rather than coincidentally true only when no conflicts exist.

## AC8 — ServiceScopeValidator.validate/3 works unchanged with a catalog-backed Lookup

**Criterion:** a definition referencing a service not visible to its tenant
is rejected at activation; one referencing a visible service activates; no
change to `service_scope_validator.ex` itself.

**Tests:**
- `"a definition referencing a service not visible to its tenant is rejected at activation"`
- `"a definition referencing a visible service activates"`

**Why each exists:** both build a `Letflow.Definitions.Graph.t()` directly
(bypassing JSON parsing, since only the algorithm's own input shape matters
here) and call `ServiceScopeValidator.validate/3` with a
`Letflow.ServiceCatalog.scope_validator_lookup/1`-built `Lookup` — proving
the catalog's `Lookup` implementation is wire-compatible with the frozen
validator, not that the validator's own algorithm is correct (that is
`service_scope_validator_test.exs`'s job). `git diff` against
`lib/letflow/definitions/service_scope_validator.ex` was checked directly
(not via an ExUnit assertion, since a diff is a repository-history fact, not
application behavior) and confirmed empty — see the handoff report.

## AC9 — migration + moduledoc state the GLOBAL divergence and cite decision 0003 / REVIEWER sign-off

**Tests:**
- `"the migration header cites decision 0003 and REVIEWER sign-off"`
- `"Letflow.ServiceCatalog's moduledoc cites decision 0003 and REVIEWER sign-off"`

**Why each exists:** a simple content-presence check, as the acceptance
criterion itself only requires the documentation to exist and cite the
right authorities — there is no executable behavior to assert beyond
"the words are there."

## AC10 — SolutionPack's service_catalog_entries hard-fail retained, REQ-192 named

**Tests:**
- `"SolutionPack's moduledoc names REQ-192 as the owner of the service_catalog_entries decision"`
- `"export/3 always emits service_catalog_entries: []"`
- `"install/3 rejects a non-empty service_catalog_entries array with {:error, :unsupported_pack_section}"`

**Why each exists:** the third test re-confirms the existing (unchanged)
`install/3` behavior under REQ-191's own name, per the design's explicit
instruction not to assume REQ-078's original coverage already covers this
outcome under this requirement — it also asserts the transaction never
opened (no `process_definitions` row was written), proving the guard runs
before any write, not merely that the final return value is correct.

## AC11 — no route/controller file added for the service catalog

**Test:** `"lib/letflow/routers/ contains no service-catalog route module"`

**Why it exists:** a structural, git-history-independent check — it lists
`lib/letflow/routers/` and asserts no filename mentions the service
catalog, so this stays true regardless of when or whether some other
requirement (REQ-192) later adds one under a name this test would also need
to be updated for.

## Mutation testing (not a numbered AC, but load-bearing for this handoff)

Per the TEST-DESIGNER task's own instruction, four mutants were applied to
`lib/letflow/service_catalog.ex`, confirmed caught, then reverted (`git diff`
confirmed clean after each revert):

1. **Removed the scope/owner-match branch from `get_for_tenant/2`'s
   visibility `case`** (collapsed the tenant-owner-match and
   different-tenant-owner clauses into one that always returns `{:ok,
   entry}` for any `scope: :tenant` row) — caught by AC3's third and fourth
   tests (2 failures).
2. **Replaced the structural `SERVICE_TASK`/`service_id` `jsonb_array_elements`
   fragment with a plain `LIKE`-style substring fragment** — caught by AC6's
   third test (1 failure).
3. **Removed the tenant-existence check in `register/1`** (`check_tenant_exists/1`
   for `scope: :tenant` now unconditionally returns `:ok`) — caught by AC5's
   test (1 failure).
4. **Removed the `rescue Ecto.StaleEntryError` clause from `delete_entry/1`**
   — caught by AC6's fourth (concurrent-delete-race) test, which crashed
   with the real `Ecto.StaleEntryError` instead of returning `{:error,
   :not_found}` (1 failure, `Task.await` propagated the crash).

`mix test test/letflow/service_catalog_test.exs` was run after each revert
and returned to `26 passed` before the next mutant was applied.
