# REQ-192 test spec — `list_all/1` and `GET /admin/services`'s admin gate

**Scope of this spec, stated up front:** the WF02-REQ192-20260830 Step 3
handoff (`handoffs/WF02-REQ192-20260830/step-03-test-designer.json`) named a
full acceptance-criteria list spanning both new routers
(`Letflow.Routers.Services`, `Letflow.Routers.AdminServices`) and the two new
`Letflow.Api.Error` 409 constructors. **This pass was explicitly re-scoped by
the dispatching agent to a narrower slice**: only `Letflow.ServiceCatalog.
list_all/1`'s own behavior and `Letflow.Routers.AdminServices`'s `GET /`
(list-all) endpoint's authorization gate. `Letflow.Routers.Services`'s
`GET /services`, and `AdminServices`'s `POST`/`PATCH`/`DELETE` routes
(register/update-scope/delete, the two 409 constructors, the `auth_method`
translation, the 404/422 mappings), are **not covered by this spec or by any
test file as of this pass** — they remain open work for a future
test-design pass. This spec covers exactly the four items the re-scoping
instruction named, no more and no less.

Design authority: `lib/letflow/design/req192-service-catalog-routes.md` §5
(the `list_all/1` addition, rework iteration 2) and §13 (the 403 test
pattern this file's router tests follow). Implementation authority:
`lib/letflow/service_catalog.ex:339-405` (`list_all/1`) and
`lib/letflow/routers/admin_services.ex` (the `GET /` handler,
`handle_list/1`).

## 1. `list_all/1` cross-tenant visibility (no tenant/scope filtering)

**Criterion:** unlike `list_for_tenant/2`, `list_all/1` takes no `tenant_id`
argument and applies no `where` clause at all — every row in the table is
returned, regardless of `scope`/`owner_tenant_id`.

**Why this needs its own test, not a restatement:** `list_for_tenant/2`
already returns every `scope: :global` row to any caller, so a test that
only checks "a global row is visible" would pass against *either* function
and would prove nothing distinguishing. The real, load-bearing claim is that
a **tenant-scoped row owned by tenant B** — which `list_for_tenant/2` would
hide from tenant A — is nonetheless returned by `list_all/1` with no
`tenant_id` argument to even ask "hide from whom?". That is the actual
behavioral delta this function exists to provide (design §5's whole
rationale).

**Test cases** (`test/letflow/service_catalog_test.exs`, describe "REQ-192
list_all/1: cross-tenant visibility, no tenant/scope filtering"):

1. `"returns rows across multiple tenants and the global scope in one call -- none filtered out"` — seeds one `:global` entry plus one `:tenant`-scoped entry each for two distinct tenants, calls `list_all/1` once, and asserts all three `service_id`s are present in a single unfiltered result.
2. `"a row list_for_tenant/2 would hide from a given tenant is nonetheless present via list_all/1"` — registers a `:tenant`-scoped entry owned by tenant B, confirms `list_for_tenant/2(params, tenant_a.id)` does **not** return it (the negative control proving the row really is normally hidden), then confirms `list_all/1/1` **does** return it. This is the test that actually distinguishes the two functions, not just documents that both include global rows.

Router-level companion (`test/letflow/routers/admin_services_test.exs`,
describe "GET /admin/services as PLATFORM_ADMIN"): the same cross-tenant
claim re-verified end-to-end through HTTP — two tenant-scoped entries owned
by tenants other than the caller's own are both present in the JSON
response body, with their true `owner_tenant_id` values intact (not just a
200 status, per the Step 3 handoff's explicit instruction not to stop at
status-code-only assertions).

## 2. `SCA:`/`SC:` cursor cross-endpoint isolation (INV-9)

**Criterion:** a cursor minted by `list_for_tenant/2` (prefix `"SC:"`) must
be rejected by `list_all/1`, and vice versa a cursor minted by `list_all/1`
(prefix `"SCA:"`) must be rejected by `list_for_tenant/2` — both as
`{:error, :wrong_endpoint}` at the context-module level, and as `400`
`"invalid cursor"` at the router level (`Letflow.Api.Pagination.
decode_cursor/4`'s `check_prefix/2`, read directly before writing these
tests to confirm the exact error shape: `check_prefix/2` returns `{:error,
:wrong_endpoint}` when the decoded payload doesn't start with the expected
prefix, and `list_all/1`'s/`list_for_tenant/2`'s own `decode_list_cursor`/
`decode_list_all_cursor` helpers pass that atom straight through unchanged;
the router's `handle_list_result/2` then maps any of
`:invalid_cursor`/`:wrong_endpoint`/`:expired` to the identical `400
"invalid cursor"` response, so the HTTP layer cannot distinguish
"wrong-endpoint cursor" from "garbled cursor" — both assertions below are
written against that actual, confirmed shape, not an assumed one).

**Why this needs its own test:** this is a structural security property
(INV-9), not an incidental one — the whole reason `list_all/1` was given a
*different* prefix rather than reusing `"SC:"` was to make a cursor minted
against the tenant-filtered endpoint unusable against the unfiltered one
(and vice versa). A test that never actually replays a cursor across
endpoints would leave this invariant completely unverified even though the
distinct-prefix constant exists in the source.

**Test cases:**

`test/letflow/service_catalog_test.exs`, describe "REQ-192 list_all/1 <->
list_for_tenant/2: SCA:/SC: cursor cross-endpoint isolation (INV-9)":

1. `"a cursor minted by list_for_tenant/2 (SC: prefix) is rejected by list_all/1 with {:error, :wrong_endpoint}"` — mints a real `"SC:"`-prefixed cursor via `list_for_tenant/2`, confirms (by base64url-decoding it) it really does start with `"SC:"`, then replays it against `list_all/1` and asserts the exact `{:error, :wrong_endpoint}` tuple.
2. The mirror image: a `list_all/1`-minted `"SCA:"` cursor replayed against `list_for_tenant/2`.
3. `"SCA: is not merely a longer match of SC:"` — a regression guard against a hypothetical future prefix choice where one prefix is a literal string-prefix of the other (e.g. `"S:"` vs `"SC:"`), which could make `String.starts_with?/2` silently pass in one direction. Confirms today's real prefixes (`"SC:"`/`"SCA:"`) don't have that relationship, so both cross-checks above are genuinely testing rejection, not accidentally passing through a shared-prefix coincidence.

`test/letflow/routers/admin_services_test.exs`, describe "GET /admin/services
INV-9: a list_for_tenant/2-minted (SC:) cursor is rejected":

4. A `list_for_tenant/2`-minted cursor replayed against `GET /admin/services` returns `400` with `detail == "invalid cursor"`.
5. A same-endpoint-minted (`SCA:`) cursor round-trips successfully (`200`) — a positive control proving test case 4's `400` is really about cross-endpoint rejection and not, say, a broken cursor-encoding pipeline that would reject any cursor at all.

## 3. `GET /admin/services` router authorization enforcement

**Criterion:** a non-`PLATFORM_ADMIN` caller (including a caller with no
roles at all, this codebase's proxy for "unauthenticated" — see below) must
be rejected with `403` before `list_all/1` ever runs; a `PLATFORM_ADMIN`
caller must succeed and see cross-tenant data.

**Note on "unauthenticated":** `Letflow.Plugs.Authorize` (read directly
before writing these tests) has no `401` branch at all — its `call/2` only
ever produces `403` (`:Deny403`) or `500` (a missing/malformed
`auth_context`, an infrastructure failure, not an authorization outcome) or
success. Every other router test file in this codebase that exercises this
plug (`tenants_test.exs`, `dlq_test.exs`) represents "unauthenticated" the
same way: an `auth_context` with `roles: []`, dispatched directly (bypassing
`Letflow.Plugs.AuthPipeline`, which is what would normally populate
`auth_context` from a real credential in production). This spec follows
that same, already-established convention rather than inventing a `401`
this plug cannot actually produce.

**Test cases** (`test/letflow/routers/admin_services_test.exs`):

describe "GET /admin/services as a non-PLATFORM_ADMIN caller":
1. `"returns 403 before ever reaching list_all/1 -- no service data leaked in the body"` — full-body assertion against the exact RFC 9457 problem document (matching `tenants_test.exs`'s own full-body-403 idiom), plus explicit `refute`s that the response contains the seeded entry's `service_id` or the string `"items"` — proving the handler never ran, not just that the status code is 403.
2. A caller holding `:ServicesRead`'s backing role (`PROCESS_OPERATOR`) is still denied — the specific "holds a *different*, plausible-sounding permission but not this one" case the design's §3 names explicitly.
3. A caller with `roles: []` (the "unauthenticated" proxy) is denied identically.

describe "GET /admin/services as PLATFORM_ADMIN":
4. Succeeds with `200` and a response body containing rows owned by two different other tenants (not just the caller's own tenant) — covered in full under §1 above; listed here too since it's simultaneously the authorization-success case Step 3 handoff item #3 calls for.

## 4. `list_all/1` standard pagination correctness

**Criterion:** `next_cursor` is set (non-nil) when more rows remain past the
current page, and `nil` once the result set is exhausted — the same
`page_size + 1`-fetch/drop-the-extra-row idiom `list_for_tenant/2` already
uses, reused verbatim by `list_all/1` via the shared `split_list_page/3`
helper.

**Why this needs its own test:** although `list_all/1` shares its pagination
helper with `list_for_tenant/2`, that sharing is exactly what needs
verifying — a bug in how `list_all/1` calls `split_list_page/3` (e.g. an
off-by-one in `page_size + 1`, or passing the wrong prefix so cursor
decoding on the next page fails) would not be caught by any `list_for_tenant/2`
test, since that function is untouched and has its own, separate call site.

**Test cases** (`test/letflow/service_catalog_test.exs`, describe "REQ-192
list_all/1 pagination correctness"):

1. `"next_cursor is non-nil while more rows remain, and nil on the final page"` — registers exactly 3 rows, pages through with `page_size: 2` (page 1: 2 items + non-nil cursor; page 2, using that cursor: 1 item + `nil` cursor), and confirms the union of both pages' `service_id`s exactly matches the 3 registered rows (no duplicate, no drop).
2. `"next_cursor is nil on the first page when the full result set fits within page_size"` — the boundary case where no continuation is needed at all.
