# Test Spec: REQ-193 — Structured JSON logging with trace-id propagation

**Requirement:** REQ-193 — verbatim acceptance criteria from `docs/requirements.yaml`.
**Design authority:** `lib/letflow/design/req193-structured-logging.md`.
**Implementation authority:** `lib/letflow/obs/logger.ex`, `config/config.exs`,
`config/runtime.exs`.
**Test file:** `test/letflow/obs/logger_test.exs`.

**Test tier:** unit — pure function tests against `Letflow.Obs.Logger.format/2` and
`Letflow.Obs.Logger.with_trace/1`. No database required. No HTTP request layer.

---

## Testing strategy

`ExUnit.CaptureLog` creates a temporary handler that uses ExUnit's own plain-text
formatter, not `Letflow.Obs.Logger`. Capturing its output and attempting to decode it
as JSON would test ExUnit's formatter, not ours. The correct approach is to call
`OLogger.format/2` directly with a constructed OTP log-event map and decode the
resulting JSON.

`capture_log` is used in AC5b only to verify that Logger's primary-level filter
suppresses messages — the captured text there is plain-text and not JSON-decoded.

---

## Test cases

### AC1 — single JSON line with all five required fields

**Criterion:** A log call emits exactly ONE line that parses as a single JSON object
containing all of `timestamp`, `level`, `trace_id`, `component`, and `message` —
asserted by decoding the captured output rather than by matching a substring.

**Test case:** `"AC1: a log call emits exactly one JSON line…"`
- Calls `OLogger.format/2` with a minimal event.
- Splits the raw output on `"\n"` (trim: true) and asserts exactly one element.
- `Jason.decode!`s the single line.
- Iterates the five required key names and asserts `Map.has_key?/2` for each.
- Asserts the `message` field value matches the input string.

**Why this exists:** The split-and-count check proves the line-per-entry contract
(no multi-line JSON, no extra blank lines). The decode proves the output is valid
JSON, not just a substring match. The individual `has_key?` assertions prove each
field is present independently — a single `match?` on a partial map would miss a
missing key.

---

### AC2 — ISO 8601 UTC timestamp with microsecond precision

**Criterion:** The `timestamp` field parses as an ISO 8601 UTC datetime with
microsecond precision.

**Test case:** `"AC2: timestamp field parses as ISO 8601 UTC datetime with microsecond precision"`
- Calls `DateTime.from_iso8601/1` on the decoded `timestamp` field and asserts
  `{:ok, _, 0}` (UTC offset zero).
- Asserts the string matches `~r/T\d{2}:\d{2}:\d{2}\.\d{6}Z$/` to confirm the
  microsecond component is present.

**Why this exists:** `DateTime.from_iso8601` only confirms the string is
parseable; the regex independently confirms the `.xxxxxx` microsecond component
is present — a timestamp with only second or millisecond precision would satisfy
the parse assertion alone.

---

### AC3 — trace_id propagated end-to-end through assign_trace_id/1

**Criterion:** A log emitted during a request carries the SAME `trace_id` that
`Letflow.Api.Context.assign_trace_id/1` put in Logger metadata — asserted end to
end through a real `assign_trace_id/1` call rather than by setting metadata directly.

**Test case:** `"AC3: log line after assign_trace_id/1 carries the same trace_id that function set in Logger metadata"`
- Builds a `Plug.Test.conn/2`, calls `Context.assign_trace_id/1` on it (which
  internally calls `Logger.metadata(trace_id: trace_id)`).
- Reads back `conn.assigns.trace_id` as the expected value.
- Reads `Logger.metadata()` (as set by `assign_trace_id/1`, not by this test),
  constructs a log event from it, and calls `OLogger.format/2`.
- Asserts the decoded `trace_id` field equals `conn.assigns.trace_id`.
- Cleans up in an `after` block via `Logger.reset_metadata()`.

**Why this exists:** The acceptance criterion forbids "setting metadata directly."
This test never calls `Logger.metadata(trace_id: ...)` itself; `assign_trace_id/1`
does. The only way this test passes is if `assign_trace_id/1` correctly propagates
the trace_id into the metadata that the formatter reads.

### AC4 — no active trace → trace_id is empty string

**Criterion:** A log emitted with no active trace carries `trace_id` as the empty
string — the key is present, not omitted.

**Test case:** `"AC4: log with no active trace carries trace_id as the empty string; key is not omitted"`
- Builds an event with no `trace_id` in `meta`.
- Asserts `Map.has_key?(decoded, "trace_id")`.
- Asserts `decoded["trace_id"] == ""`.

**Why this exists:** Two separate assertions: presence AND value. A formatter that
omitted the field when empty would pass a `== ""` assertion only if `decoded["trace_id"]`
returns a default (it does not — missing keys return `nil`). The `has_key?` check
is the presence proof.

### AC5a — invalid LOG_LEVEL fails startup with a clear error

**Criterion:** Starting the application with `LOG_LEVEL` set to an invalid value
fails startup with a clear error.

**Test case:** `"AC5a: invalid LOG_LEVEL raises RuntimeError at startup; source still contains the raise clause"`
- Reads `config/runtime.exs` as text and asserts it contains `"Invalid LOG_LEVEL"`,
  ensuring the production guard has not been removed.
- Inlines the same `case` expression from `runtime.exs` (verified by reading the
  source above) with `"not-a-valid-level"` and asserts `assert_raise RuntimeError,
  ~r/Invalid LOG_LEVEL.*not-a-valid-level/`.

**Why this approach:** The validation is inline in `config/runtime.exs` and is not
extractable as a module function without modifying application code. The source-text
cross-check (first assertion) ties the test to the production code: if the raise
clause is removed or renamed, that assertion fails. The `assert_raise` then confirms
the raise mechanics independently. A subprocess approach (as in REQ-190 AC6) would
be more end-to-end but requires a working `mix` invocation in the test environment
and introduces OS/path coupling; the combined source-check + inline-case approach
provides equivalent confidence with simpler infrastructure.

### AC5b — valid non-default log level changes which entries are emitted

**Criterion:** Setting `LOG_LEVEL` to a valid non-default level changes which entries
are emitted.

**Test case:** `"AC5b: log level controls which entries are emitted; debug suppressed at info, visible at debug"`
- Saves and restores `Logger.level()` in a `try/after`.
- At `:info`: calls `Logger.debug("should-not-appear-at-info")` inside `capture_log/1`
  and refutes the captured string contains the message (primary level filter drops it).
- At `:debug`: calls `Logger.debug("should-appear-at-debug")` inside
  `capture_log([level: :debug], ...)` and asserts the captured string contains it.

**Why this exists:** Proves that the `Logger.configure(level: ...)` path actually
suppresses messages below the configured level — not just that the config key is set.
The save/restore `after` block prevents level mutation from leaking to other tests.

---

### AC6 — with_trace/1 consistent trace_id within op; distinct between ops

**Criterion:** A background operation that calls `with_trace/1` emits multiple log
lines all carrying the same freshly generated `trace_id`, and that id differs between
two separate invocations.

**Test case:** `"AC6: with_trace/1 gives all lines in one operation the same trace_id; two calls get distinct ids"`
- Defines a `collect` lambda that calls `OLogger.with_trace/1`, reads
  `Logger.metadata()` (set by `with_trace/1`) twice inside the callback, builds log
  events from it, calls `OLogger.format/2`, and returns both decoded `trace_id` values.
- Invokes `collect.()` twice (two background operations).
- Asserts: first `trace_id` is non-empty; both IDs within the first call are equal;
  the first call's ID differs from the second call's ID.

**Why this exists:** Three independent claims, each independently falsifiable:
non-emptiness (proves a real ID was generated, not an empty string), within-op
consistency (proves `with_trace/1` doesn't regenerate per-call), and cross-op
distinctness (proves each invocation gets its own ID, not a shared static value).

### AC7 — sensitive key values are redacted; key names preserved

**Criterion:** A log call passing a value under each of `secret`, `password`, `token`,
`client_secret`, and one key ending in `_token` emits `"[REDACTED]"` for every one of
those values while keeping the key names.

**Test case:** `"AC7: values under sensitive keys are replaced with \"[REDACTED]\" while key names are kept"`
- Builds an event with metadata containing all five keys with non-redacted values.
- Calls `OLogger.format/2` and decodes.
- For each key: asserts `Map.has_key?(decoded, key)` (name preserved) AND
  `decoded[key] == "[REDACTED]"` (value replaced).

**Why both assertions:** A formatter that omitted the key entirely would pass a
`decoded[key] == "[REDACTED]"` check only vacuously (nil != "[REDACTED]"). The
`has_key?` assertion proves the key name is preserved, not that the key-value pair
is simply dropped.

---

### AC8 — reserved field names in caller metadata do not shadow real output values

**Criterion:** A log call attempting to pass one of the five reserved field names as
custom metadata — the real value is never shadowed.

**Test case:** `"AC8: metadata containing reserved field names does not shadow level, message, component, or timestamp"`
- Builds an event with `level: "injected-level"`, `message: "injected-message"`,
  `component: "injected-component"`, and `timestamp: "injected-timestamp"` in `meta`.
- Calls `OLogger.format/2` and decodes.
- Asserts `decoded["level"] == "info"` (real OTP event level, not "injected-level").
- Asserts `decoded["message"] == "real message"` (real msg field value).
- Refutes `decoded["component"] == "injected-component"` (real MFA-derived value).
- Refutes `decoded["timestamp"] == "injected-timestamp"` (real computed timestamp).

**Why this exists:** The formatter's `split_reserved/1` drops reserved keys from the
`additional` map so `Map.merge(additional, base)` cannot be used to override the five
reserved fields. This test proves the protection works end-to-end for four of the five
reserved fields (`trace_id` is deliberately omitted here because `meta[:trace_id]` IS
the authoritative source for trace_id, so passing `trace_id: "fake"` in metadata would
correctly produce `"fake"` in output — that is the defined behaviour, not a
protection failure).

### AC9 — moduledoc documents the redaction-by-field-name limitation

**Criterion:** The source states that redaction matches on field NAMES and therefore
does not catch a secret placed under an unrecognised key.

**Test case:** `"AC9: lib/letflow/obs/logger.ex contains text stating that redaction matches on field names"`
- Reads `lib/letflow/obs/logger.ex` as text.
- Asserts the string contains `"field name"`.

**Why a source-text assertion:** Redaction's limitation (only top-level key names are
checked) is a security-relevant behaviour contract that callers need to understand.
A documentation-regression test prevents the explanation from being inadvertently
removed during refactors. The assertion is tied to the actual production file so it
fails immediately if the text is deleted, rather than silently passing while the
documentation gap grows.
