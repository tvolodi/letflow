# Test Spec: REQ-197 — `expr.ex` arithmetic, unary negation, and a structured parse-error surface

**Requirement:** REQ-197 (`docs/requirements.yaml`, stage S6) — extends
`lib/letflow/engine/expr.ex` (REQ-050, S3) with binary arithmetic (`+ - * / %`), unary
negation, R-Co's int/float promotion and by-zero semantics, the null-in-comparison-vs-
null-in-arithmetic asymmetry, and a new `parse_strict/1` structured parse-error entry
point — all while leaving `evaluate_condition/2`'s EE-05 catch-false gateway contract
byte-for-byte unchanged, per
`lib/letflow/design/req197-expr-arithmetic-and-errors.md` (the REVIEWER-approved design
`lib/letflow/engine/expr.ex` implements).

**Test tier:** unit only, `async: true`, same reasoning as REQ-050's own spec —
`Letflow.Engine.Expr` is a pure module (no `Letflow.Repo`, no `Ecto.Sandbox`), and
`Letflow.Engine.Transition` (touched only by one new test here, not by REQ-197's
implementation) is already covered by that reasoning in `test/specs/REQ-050.md`.

## Scope test

Real application-executable Elixir logic: `lib/letflow/engine/expr.ex`'s new `eval/2`
clauses (`{:arith, ...}`, `{:neg, ...}`), its revised ordering-comparison clause (the
null-propagation change), and its new `parse_strict/1`/`describe_parse_error/1`
functions. Not docs-only, not build-config. Full TEST-DESIGN-VALIDATOR / TEST-RUNNER
chain applies.

## Why each new test case exists (not a restatement of the AC)

### AC1 — each arithmetic operator, one test per, concrete expected value

Before this step, `+`, `-`, `*`, `%`, non-zero-divisor `/`, and unary `-` had **zero**
test coverage — only `/`'s zero-divisor corner case was exercised (via the
signed-infinity block, which is about IEEE sentinel construction, not ordinary
division). A wrong operator dispatch (e.g. `apply_int_arith/3`'s clauses swapped, or
`apply_float_arith/3`'s `l - r` accidentally written as `r - l`) would compile clean
and pass every other test in the file, since nothing else exercises plain arithmetic.
Each test parses real condition syntax (`Expr.parse("2 + 3")`, not a hand-built AST) so
the new tokenizer/parser levels (§3.1's `parse_additive`/`parse_multiplicative`/
`parse_unary`) are exercised too, not just `eval/2`'s dispatch.

### AC2 — precedence: `+`/`*` grouping, comparison-vs-arithmetic ordering

Proves the grammar actually inserted 2 new precedence levels between comparison and
primary (§2.1), rather than, say, giving `+`/`*` equal precedence or binding arithmetic
looser than comparison. `2 + 3 * 4 == 14` (not `20`) fails if `*` and `+` share a level
evaluated left-to-right; `1 + 1 == 2` evaluating to `true` fails if a bug routed
comparison to bind tighter than `+` (which would instead try to parse `1 + (1 == 2)`,
a type-mismatch error, not `true`). Left-associativity (`3 - 1 - 1 == 1`, not `3`) and
unary-negation right-recursion (`- - 5 == 5`) are the two precedence properties the
design doc's own §2.2 calls out as "load-bearing," each independently reversible by a
single fold-direction or recursion-direction bug that no other test would catch.

### AC3 — int+float promotion, on a case where int arithmetic would differ

`7 / 2.0 == 3.5` directly contrasted against AC1's `7 / 2 == 3` (same operands, only
one made a float) is the minimal pair that actually proves promotion happened — a test
using only float operands (e.g. `1.0 / 2.0`) would pass identically whether or not
`apply_arith/3`'s promotion clause (§4.2 row 4) ever ran, since native float division
would already be correct without it.

### AC4 — int div-by-zero, int mod-by-zero, float div-by-zero → infinity, 3 tests

Int division-by-zero and int modulo-by-zero had zero coverage before this step (only
float division-by-zero was tested, pre-existing). Each is a distinct guard clause in
`apply_int_arith/3` (`:div, l, 0` vs. `:mod, l, 0`) that could regress independently of
the other — e.g. a future refactor collapsing both into one shared helper could
accidentally swap which error tag (`:division_by_zero` vs. `:modulo_by_zero`) fires for
which operator. The float case (dividend `> 0.0`) was already covered by ELIXIR-DEV's
rework and is not duplicated here.

### AC5 — null-in-comparison→null vs. null-in-arithmetic→error, 2 tests

This is REQ-197's single most safety-relevant behavioural change (design doc §4.5): a
regression here would either (a) make a null-valued gateway variable silently start
erroring in ordering comparisons where it used to propagate — reachable today via
`evaluate_condition/2`'s catch-false, so a caller might never notice — or (b) make null
arithmetic silently produce a value instead of erroring, which is the more dangerous
direction since a caller expecting `{:error, ...}` would instead see (and possibly log
or route on) a nonsensical numeric result. Both tests are the design doc's own §4.5
worked examples, transcribed exactly, at the `eval/2` level (not just at
`evaluate_condition/2`'s boundary, where both outcomes look identical — a bare `false`
— which is precisely why the design doc calls out that only the `eval/2`-level tests
make the asymmetry "a real, testable property rather than something that only exists
in prose").

### AC6 — `parse_strict/1`'s structured failure, field by field

`parse_strict/1` was fully implemented (`expr.ex:474-486`, plus its own
position-tracking tokenizer/parser pair) but had **zero** test coverage of any kind
before this step — confirmed by grep. This is the largest coverage gap this step
closed: without a test, a line/column off-by-one (a very easy mistake in
`advance_pos/3`'s reduce-over-charlist accumulator) or a `token_text` field carrying the
wrong substring would ship silently, defeating the entire point of a "structured"
error surface for the future validation/authoring callers the requirement names. The
malformed input chosen (`"amount + "`, a trailing binary operator with no right
operand) is R-Co's own error.zig-style example class (an incomplete expression, not a
tokenizer-level lexical error), and every field of the returned map is asserted
individually. The exact expected values (`column: 10`, `token_text: ""`) were verified
by loading `expr.ex` directly and inspecting its real return value before being
written into the test — not derived from the design doc's algorithm description alone,
since the design doc traces the mechanism but does not hand-compute this exact number.
A second test locks in that `parse_strict/1`'s success path returns byte-identical
`ast()` to `parse/1` for the same input, per its own `@doc` contract.

### AC7 — `evaluate_condition/2` and `transition.ex` unchanged for a bad condition

Two sub-gaps, both closed:
- `evaluate_condition/2`: the design doc's own §5 names an explicit "verification
  obligation... not skipped" — a new test asserting a *deliberately malformed
  arithmetic* expression (not just the pre-existing undefined-variable/type-mismatch
  cases) still collapses to `false` via the unconditional `else _ -> false` clause.
  Added both a parse-time case (trailing operator) and an eval-time case (int division
  by zero), proving the catch-false composition absorbs REQ-197's two new *classes* of
  failure (a new parse-error reason space is not introduced, but a new eval-error
  reason space — arithmetic errors — is), not just the failure modes that existed
  before this requirement.
- `transition.ex`: the pre-existing REQ-050 catch-false tests (undefined-variable,
  type-mismatch) already prove the gateway's composition is unchanged for the failure
  classes that existed before REQ-197, and remain untouched by this step. But none of
  them used an arithmetic condition — a failure class introduced *by* REQ-197 — so
  there was no direct evidence at the `transition.ex` level (as opposed to the
  `expr.ex` level) that REQ-197 didn't require any `transition.ex` change to keep
  working. The new `dispatch_exclusive_gateway` test (int-division-by-zero condition,
  same graph/edge/token-assertion shape as the pre-existing REQ-050 tests it sits next
  to) closes that gap directly.

### AC8, AC9, AC10, AC11 — no test action; confirmed by inspection

- **AC8** (purity grep, quoted in the PR): already covered by the pre-existing
  `describe "purity and determinism (AC8)"` block, which re-implements the moduledoc's
  documented grep as a live ExUnit assertion against the actual file. No gap.
- **AC9** (`now()` not added, moduledoc states why): pure moduledoc prose
  (`expr.ex:35-55`) — confirmed present and accurate by direct reading. No executable
  surface exists for a test to assert against beyond string-matching the moduledoc
  text, which would be a manufactured assertion with no real failure mode (the actual
  enforcement that `now()` isn't callable is structural: no call-syntax grammar exists
  in `expr.ex` at all yet, confirmed by grep for any `"now("`-shaped dispatch clause).
- **AC10** (moduledoc records `benchmark.zig` non-port): pure moduledoc prose
  (`expr.ex:12-20`), inherited from REQ-050 and confirmed still accurate. Same
  reasoning as AC9 — no test added.
- **AC11** (moduledoc records the EXP-102/CEL-cutover correction): the prose half
  (`expr.ex:22-33`) needs no test, same reasoning as AC9/AC10. The behavioural half —
  `@unsupported_call_markers` still rejects everything it rejected before — already has
  real coverage via the pre-existing (REQ-050) `describe "translate_cel_to_expr/1 --
  unsupported CEL feature boundary"` block; confirmed unchanged by inspection (REQ-197
  adds no new identifier/call-syntax token that could collide with an existing marker).
  No gap, no new test.
