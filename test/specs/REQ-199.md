# Test Spec: REQ-199 — Correlated Effect Re-Entry Ordering Subsystem

**Requirement:** REQ-199  
**Module under test:** `Letflow.Ordering` (public API), `Letflow.Ordering.Consumer`,
`Letflow.Ordering.Cursor`, `Letflow.Ordering.Sweeper`, `Letflow.Ordering.Metrics`  
**Test file:** `test/letflow/ordering_test.exs`  
**Status:** All 18 tests pass.

---

## AC1 — Both tables created in tenant schema

**Criterion:** Provisioning a tenant schema creates `effect_completions` and
`correlation_cursors` tables inside that tenant's own Postgres schema.

**Test:** `AC1: tables created in tenant schema`  
Queries `information_schema.tables` for the provisioned schema and asserts both
table names are present. Proves the migrations were applied and created the
correct tables.

---

## AC2 — `insert_completion/2` idempotency on `(correlation_id, sequence_no)`

**Criterion:** Inserting the same `(correlation_id, sequence_no)` pair twice does
not create a duplicate row, and one `run_cycle/2` call appends exactly one
`effect_applied` event for that pair.

**Test:** `AC2: insert_completion/2 idempotency`  
Inserts the same pair twice, asserts row count == 1, runs one cycle, asserts
exactly one `effect_applied` event in the tenant's `events` table with a matching
`correlation_id` in the payload. Proves the `ON CONFLICT DO NOTHING` semantics and
that the downstream event is emitted exactly once.

---

## AC3 — Strict in-order application (ORD-01)

**Criterion:** When effect completions arrive out of order, they are applied in
ascending `sequence_no` order, not arrival order. Each `run_cycle/2` applies at most
the single next-expected sequence; the higher sequence stays `PENDING` until its
predecessor is applied.

**Test:** `AC3: out-of-order delivery is applied in sequence order (ORD-01)`  
Inserts seq 2 before seq 1 for the same correlation. First cycle applies seq 1
(lowest pending, and next expected == 0+1=1). Asserts seq 1 APPLIED, seq 2 PENDING.
Second cycle applies seq 2. Asserts events in the `events` table are ordered by
`sequence_number` with seq 1 first. Proves the `ORDER BY (correlation_id, sequence_no)`
claim and the `sequence_no == applied_seq + 1` guard work together.

---

## AC4 — Non-next sequence stays PENDING

**Criterion:** A completion whose `sequence_no` is not `applied_seq + 1` is claimed
but not applied — `run_cycle/2` returns `:not_next` and the row remains `PENDING`.
No event is appended.

**Test:** `AC4: non-next sequence stays PENDING`  
Inserts seq 3 only (no cursor, so applied_seq=0, next expected=1). Runs one cycle
and asserts result == `:not_next`, status == `:pending`, zero `effect_applied` events.
Proves the M5 order-check in `Consumer.try_apply/2` (design §7.1 M5).

---

## AC5 — Advisory lock + SKIP LOCKED prevent double-apply (ORD-02)

**Criterion:** Two concurrent consumers attempting to apply the same completion
result in exactly one `:applied` and exactly one `:lock_contention` or
`:cursor_race`. The cursor is advanced exactly once to `applied_seq=1`.

**Test:** `AC5: advisory lock + SKIP LOCKED prevent double-apply`  
Inserts seq 1, then launches two `Task.async` calls each calling
`Consumer.try_apply/2` with the same completion struct (with `Sandbox.allow` so
both share the parent's sandbox connection). Asserts `:applied` appears exactly once
in the results and `:lock_contention` or `:cursor_race` appears at least once.
Asserts cursor `applied_seq == 1` afterward. Proves the `FOR UPDATE SKIP LOCKED`
re-lock (M1) and `pg_try_advisory_xact_lock` (M2) prevent double-apply.

---

## AC6 — Cursor row upsert-initialised on first apply

**Criterion:** When no `correlation_cursors` row exists for a correlation, the first
`run_cycle/2` call that applies a completion creates the row with `applied_seq=1`.

**Test:** `AC6: cursor row created on first apply`  
Inserts seq 1 and asserts no cursor row exists before calling `run_cycle/2`.
After calling `run_cycle/2`, asserts the cursor row exists with `applied_seq == 1`.
Proves M3 (upsert-init) and M8 (conditional advance) in `Consumer.try_apply/2`.

## AC7 — Per-correlation isolation

**Criterion:** Two different correlations with seq 1 each are both applicable in
independent `run_cycle/2` calls. Applying one does not interfere with the other.

**Test:** `AC7: two correlations applied independently`  
Inserts seq 1 for two different correlation IDs. Calls `run_cycle/2` twice.
Asserts both completions are `APPLIED`. Proves the `ORDER BY (correlation_id,
sequence_no)` claim cycles through all pending correlations, and each correlation
has its own cursor.

## AC8 — Gap sweeper marks timed-out gaps DEAD with DLQ entry

**Criterion (two tests):**

**Test 1 — sweep eligible:** A completion whose `sequence_no` is **strictly greater
than** `applied_seq + 1` and whose `created_at` is older than `gap_timeout_seconds`
is moved to `DEAD` by `sweep_gaps/2`. Exactly one `dlq_entries` row with
`entry_type="ordering_gap"` is written naming all unapplied sequence numbers.

**Test 2 — no sweep when seq equals next:** A completion with `sequence_no == applied_seq + 1`
(the next expected, no predecessor gap) is NOT swept even when it is older than
`gap_timeout_seconds` — the strictly-greater-than check must be honoured.

**Tests:** `AC8: gap sweeper marks timed-out gaps DEAD` (two tests in the describe)  
Test 1: Sets `gap_timeout_seconds=1`, inserts seq 2 (gap: applied_seq=0, 2 > 0+1=1),
backdates `created_at` 2 hours, calls `sweep_gaps/2`. Asserts status=`:dead` and
one DLQ entry with `unapplied_sequence_numbers=[2]`.  
Test 2: Sets same timeout, inserts seq 1 (applied_seq=0, 1 == 0+1=1, no gap),
backdates same. Calls `sweep_gaps/2`. Asserts seq 1 stays `:pending`.

## AC9 — Gap younger than `gap_timeout_seconds` is not swept

**Criterion:** A completion that IS a gap (seq > applied_seq+1) but whose
`created_at` is within `gap_timeout_seconds` stays `PENDING`.

**Test:** `AC9: fresh gap is not swept before timeout`  
Sets `gap_timeout_seconds=3600`, inserts seq 2 with a fresh `created_at` (age ~0 seconds).
Calls `sweep_gaps/2`. Asserts status == `:pending`. Proves the timeout condition
`EXTRACT(EPOCH ...) > gap_timeout_seconds` in the sweeper.

## AC10 — Connection pool discipline

**Criterion:** Each `run_cycle/2` call acquires a DB connection at transaction open
and releases it at commit or rollback. No connection is held across calls.

**Test:** `AC10: connection pool discipline`  
Inserts seqs 1..5 then calls `run_cycle/2` five times sequentially. Asserts all
return valid cycle results without `DBConnection.ConnectionError`. If a connection
were held between calls, a 1-connection pool would deadlock on the second call.
Proves the pool-discipline invariant in `Consumer`'s module doc.

## AC13 — Per-correlation lag computation

**Criterion (two tests):** `Metrics.compute_all_lags/1` returns
`lag = MAX(sequence_no) - applied_seq` for each correlation that has PENDING rows.
When all rows are applied (no PENDING), the correlation has no entry in the result.

**Test 1:** Inserts seqs 1..5, applies seqs 1 and 2 (cursor at applied_seq=2), calls
`compute_all_lags/1`. Asserts `lag_info.lag == 3` (max(5)-2). Proves the SQL formula
`MAX(sequence_no) - COALESCE(applied_seq, 0)`.

**Test 2:** Inserts seqs 1..3, applies all three, calls `compute_all_lags/1`. Asserts
the correlation has no entry (all PENDING rows were consumed, `WHERE status='PENDING'`
returns nothing). Proves "lag=0" manifests as absence, not as a zero-lag entry.

---

## AC14 — `oldest_pending_age_seconds` is nil (not 0) when no pending rows

**Criterion:** When a correlation has no PENDING rows, `compute_all_lags/1` returns
no entry for it (not an entry with `oldest_pending_age_seconds: 0`). This preserves
the nil-vs-zero distinction: nil means "no pending rows", 0 means "freshly inserted
pending row".

**Test:** `AC14: oldest_pending_age_seconds is nil when correlation has no pending rows`  
Inserts and applies seqs 1..2. Calls `compute_all_lags/1`. Asserts either no entry
exists for the correlation, or any found entry has `oldest_pending_age_seconds == nil`.
Proves the SQL `MIN(ec.received_at)` returns nil when no PENDING rows exist (the
`WHERE status='PENDING'` filter excludes all rows).

## AC15 — Lag threshold crossing emits `ordering_lag_threshold_exceeded` event

**Criterion:** When a correlation's lag exceeds the configured `:lag_threshold`,
`emit_lag_metrics/2` appends an `ordering_lag_threshold_exceeded` platform event
containing `correlation_id`, `lag`, and `oldest_pending_age_seconds` in its payload.

**Test:** `AC15: lag threshold crossed emits ordering_lag_threshold_exceeded event`  
Sets `lag_threshold=1`, inserts seqs 1..3, applies seq 1 (applied_seq=1, lag=2 > 1).
Calls `emit_lag_metrics/2`. Queries `events` for `event_type="ordering_lag_threshold_exceeded"`
with matching `correlation_id`. Asserts at least one event exists with `payload["lag"]==2`
and `payload["oldest_pending_age_seconds"]` key present. Proves `Metrics.write_to_registry/2`
→ `emit_threshold_exceeded_event/4` → `EventStore.append_platform_event/2` wiring.

**NB:** As noted by REVIEWER (NB-4), `emit_threshold_exceeded_event` uses a
timestamp-based idempotency key, emitting once per `write_to_registry/2` call while
above threshold (not once per crossing). This test asserts the event IS appended when
above threshold — it does not assert "exactly once per crossing" since that is not
what AC15 requires.

**Criterion:** None of the three public functions use OTP process state or open
long-lived connections.

within each call).
