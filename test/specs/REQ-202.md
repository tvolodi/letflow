## 1. IMPORTANT — two real implementation defects found while writing this suite

Per this project's "no speculation, run it" directive, this suite was actually executed
against a real Postgres instance (available in this environment via the
`letflow-1-postgres-1` docker container on the port `.env`'s `LETFLOW_DB_PORT` names),
not merely written and assumed to pass. Doing so surfaced **two real, reproducible
defects in the shipped migration/schema**, both traced to the same root cause: an
Ecto-default index/constraint name exceeding **PostgreSQL's 63-byte identifier limit**
(`NAMEDATALEN`), which Postgres silently truncates.

**Defect A — duplicate index name collision blocks EVERY tenant-schema migration
replay.** `priv/repo/migrations/20260830030001_create_repository_artifacts.exs` creates:

```
create unique_index(:artifact_versions, [:artifact_kind, :artifact_name, :version_number], prefix: schema)
create index(:artifact_versions, [:artifact_kind, :artifact_name, desc: :version_number], prefix: schema)
```

Ecto's `default_index_name/1` (`deps/ecto_sql/lib/ecto/migration.ex:1054-1068`) strips
the `desc:`/`asc:` direction wrapper when generating a name
(`column_name({_dir, column}), do: column_name(column)`), so **both** calls above
resolve to the identical default name
`artifact_versions_artifact_kind_artifact_name_version_number_index` (66 chars — itself
already over the 63-byte limit, compounding with defect B below). The second `CREATE
INDEX` therefore fails with Postgres error `42P07 duplicate_table` ("relation ...
already exists") the moment a real tenant schema is provisioned and
`TenantProvisioning.replay_migrations/1` actually applies this migration with a
non-`nil` `prefix()` — confirmed directly: `mix ecto.migrate` against the main/dev
schema reports success trivially (this migration's `if prefix() do` guard is false
there, so the tenant-scoped block never executes), but every one of this suite's
`provisioned_tenant/0` calls, which replay migrations into a **real, newly provisioned
tenant schema**, reproducibly hit this failure with the exact Postgrex error quoted
above. **This means the feature is currently unusable for any real tenant** — not an
edge case.

**Defect B — even past defect A, the unique constraint's name is silently truncated by
Postgres, breaking the concurrency-retry contract (design §4.4).** The full default
name (66 chars) exceeds Postgres's 63-byte identifier limit, so Postgres stores it
truncated to `artifact_versions_artifact_kind_artifact_name_version_number_in` (63
chars, confirmed via the actual `Ecto.ConstraintError` message raised in this suite's
concurrency test). `Letflow.Repository.ArtifactVersion.changeset/2` declares
`unique_constraint([...], name: :artifact_versions_artifact_kind_artifact_name_version_number_index)`
— the **full**, untruncated atom — which never matches Postgres's actual (truncated)
constraint name. The result: a genuine unique-constraint violation (exactly the
"two concurrent writers raced to the same `version_number`" case design §4.4 exists to
handle) is **not** converted into a changeset error at all — it raises an unhandled
`Ecto.ConstraintError` straight out of `Repo.insert/2`, which `Letflow.Repository`'s
`create_with_retries/7` has no `rescue` clause for, so it propagates and crashes the
caller instead of retrying. This defeats the entire retry-on-conflict design the
moduledoc documents as the safety mechanism for concurrent `create/2` calls.

**Verification method (not merely inferred):** temporarily patched the migration's
second `index/3` call with an explicit short `name:` (diagnostic only, reverted before
this handoff — confirmed via `git status --short
priv/repo/migrations/20260830030001_create_repository_artifacts.exs` showing no diff)
to get past defect A in isolation, re-ran `mix ecto.rollback && mix ecto.migrate`, and
re-ran the full suite: 37/38 tests passed, with the sole remaining failure being defect
B's `Ecto.ConstraintError`, reproduced with its exact stacktrace (quoted above) pointing
at `lib/letflow/repository.ex:153` inside `create_with_retries/7`. Both defects are
therefore independently confirmed and root-caused, not merely hypothesized.

**This is not a flaw in this test suite.** The two failures below (in
`test/letflow/repository_test.exs`, described in AC9 and the concurrency section) are
expected to **fail against the current implementation** and should stay failing until
ELIXIR-DEV fixes both index/constraint names to fit within 63 bytes (e.g. an explicit
short `name:` on the plain index, and a matching explicit short constraint name shared
between the migration's `unique_index/3` and the schema's `unique_constraint/3`) and the
fix passes SECURITY-REVIEWER/REVIEWER again. **Recommended: ORCH routes this back to
ELIXIR-DEV for a rework cycle before spending TEST-RUNNER cycles on a run that will
reproducibly fail for this well-understood reason.**

The two directly-affected tests are:
- `test/letflow/repository_test.exs`, `describe "concurrent create/2 calls for a fresh
  (artifact_kind, artifact_name) pair"` — fails immediately with defect B, without the
  diagnostic patch.
- Every other test in `test/letflow/repository_test.exs` that calls
  `provisioned_tenant/0` fails with defect A, without the diagnostic patch, since no
  tenant schema can ever finish replaying this migration.
- `test/letflow/repository/canonicaliser_test.exs` is entirely unaffected (pure module,
  no tenant schema, no DB).

## 2. Test cases

### AC1 — REPO-01 deduplication: byte-identical content → one content row, two version rows
- `repository_test.exs` "two artifacts with byte-identical content share one
  repository_artifacts row and get two artifact_versions rows" — proves dedup is
  keyed correctly and doesn't accidentally happen per-artifact-name instead of
  per-content. Also asserts `byte_size` is measured on the *canonical* form, not the
  raw input, catching a mutant that stores the wrong byte count.
- "differently key-ordered/whitespaced JSON... also dedups to one row" — proves dedup
  goes through the canonicaliser, not a raw-bytes hash.
- "upsert on a content_hash collision does not re-validate content_type/byte_size
  against the existing row (design §4.2 step 3)" — **added in rework 1**, closing a
  TEST-DESIGN-VALIDATOR-confirmed gap: design §4.2 step 3 states explicitly that a
  `content_hash` collision is NOT re-validated against the existing row's
  `content_type`/`byte_size` ("a hash collision implies identical content by
  construction, so there is nothing to reconcile") — no prior test exercised a
  collision where the two writers submit genuinely different `content_type` values.
  Constructs the collision directly: `content_type: "application/json"` +
  `~s({"a":1})` canonicalizes to the byte-identical string (already-sorted single key,
  no whitespace), and `content_type: "application/wasm"` + the same raw bytes is
  hashed by byte identity with zero transformation (§3.5/OQ-3) — so both submissions
  produce the same `content_hash` while carrying different `content_type`s. Asserts:
  the second `create/2` call succeeds with no error; exactly one `repository_artifacts`
  row exists for that hash; that row's `content_type`/`byte_size` are unchanged from
  the first writer (`"application/json"`, not overwritten to `"application/wasm"`);
  and the second call still returns its own `artifact_versions` row (`version_number:
  1` under its own `artifact_name`) referencing the shared `content_hash`.
  Mutation-confirmed: a mutant that made `upsert_content/5` re-validate
  `content_type`/`byte_size` on a hash collision and raise on mismatch was applied to
  `lib/letflow/repository.ex`, re-run against the full suite (39 tests) →
  38/39 passed, with this exact test as the sole failure (`** (RuntimeError) MUTANT:
  content_type/byte_size mismatch on hash collision`); the mutation was then reverted
  (`git checkout -- lib/letflow/repository.ex`, confirmed clean via `git status
  --porcelain lib/`) and the suite re-ran green (39/39).

### AC2 — key-order/whitespace insensitivity of the hash
- `canonicaliser_test.exs` describe "AC2" — three tests: top-level key
  reorder+whitespace, recursive nested-object key sort, and a sanity check that array
  order IS significant (guards a mutant that also "fixes" array order, which would be
  wrong per design §3.4 rule 4).

### AC3 — number normalisation, asserted on canonical bytes
- `canonicaliser_test.exs` describe "AC3" — four tests: `2.0` vs `2` produce identical
  canonical bytes with no decimal point; the exponent form `3.0e2` also normalises to
  plain `300` (guards a mutant that only handles the simple decimal-float case, missing
  exponent notation); a genuinely fractional float (`2.5`) is NOT collapsed to an
  integer (guards a mutant that over-eagerly truncates every float); malformed JSON is
  `{:error, :invalid_json}`.

### AC4 — binary content hashed by byte identity
- `canonicaliser_test.exs` describe "AC4" — three tests: `application/wasm` bytes pass
  through unchanged and hash as plain SHA-256; the SAME differently-ordered-JSON pair
  from AC2 does NOT dedup under a non-JSON content type (`application/schema+json`),
  pinning OQ-3's narrow reading — this is the mutation-catching test: a broken
  implementation that treated any `+json`-suffixed or JSON-shaped content_type as JSON
  would make this test's two canonical forms equal, which the assertion explicitly
  rejects; and `application/json; charset=utf-8` is also rejected as non-exact-match.

### AC5 — separate module, PromotionDigest unmodified, both moduledocs cross-reference
- `canonicaliser_test.exs` describe "AC5" — Canonicaliser's moduledoc names
  `Letflow.Definitions.PromotionDigest`, states it does NOT normalize numbers, and
  states the two must never be merged.
- `repository_test.exs` describe "AC5" — the two modules are distinct with
  non-overlapping public function names (guards against an accidental merge exposing
  both APIs from one module).
- `repository_test.exs` describe "AC6" (third test) — PromotionDigest's own moduledoc
  reciprocally cross-references `Letflow.Repository.Canonicaliser`, satisfying AC5's
  "BOTH... cross-reference each other" clause.
- The "PromotionDigest not modified in behavior" clause is verified by AC6's fixed-digest
  test below, which would fail if `canonicalize/1`'s behavior changed at all.

### AC6 — an existing promotion digest is unchanged by this requirement
- `repository_test.exs` describe "AC6" — `compute_plan_digest/1` over a fixed fixture
  matches a value independently recorded (via `mix run` against this exact fixture,
  before this test was written) — `9c972bf451a45b8aa4ab79a029621b7ad7aab017b572cdb9f1a597ec2d4a0115`.
  A second test confirms `PromotionDigest` still does NOT normalize numbers (`2.0` vs
  `2` still hash differently there), directly guarding against the exact regression
  design §3.2 warns about (accidentally sharing normalization code between the two
  canonicalisers).

### AC7 — DB-level immutability
- `repository_test.exs` "AC7 -- repository_artifacts..." — raw UPDATE and raw DELETE
  against a persisted row are both rejected by a trigger, mirroring
  `test/letflow/audit_test.exs`'s AC1 test shape exactly (going around the Ecto schema
  entirely via `Repo.query!/2`, not `Repo.update/1`).
- `repository_test.exs` "AC7 -- artifact_versions..." — raw UPDATE rejected.

### AC8 — changed content creates a new version, prior version untouched
- `repository_test.exs` describe "AC8" — asserts `version_number` incremented,
  `content_hash` changed, `artifact_id` carried across versions (OQ-4), and — the
  "provably untouched" requirement — the prior version row is **re-fetched from the
  database** (not the in-memory struct returned by the first `create/2` call) and its
  `content_hash`/`version_number` are unchanged; both content rows (old and new hash)
  still exist as two distinct rows.

### AC9 — version history ordering, parent linkage, REQ-067 pagination
- `repository_test.exs` describe "AC9" — seven tests: newest-first ordering with
  `parent_version_id` populated correctly per version (including the null case for the
  first version); page_size-driven pagination across three pages with `next_cursor`
  advancing and finally `nil`; `page_size` 0 and 201 both rejected
  (`:page_size_too_large`, reject-not-clamp); a foreign-endpoint-prefixed cursor
  rejected `:wrong_endpoint`; an ancient-timestamp cursor rejected `:expired`; a
  non-base64 cursor string rejected `:invalid_cursor`; an invalid schema-name prefix
  rejected `:invalid_schema_name` for both `list_versions/4` and `create/2`; and
  `create/2` rejecting invalid JSON with no row written to either table (a
  no-partial-write guarantee).

### AC10 — migration states placement decision and reason
- `repository_test.exs` describe "AC10" — reads the migration file's source and asserts
  (via normalized-whitespace substring match, the same technique
  `promotion_digest_test.exs` already establishes as this codebase's moduledoc-content
  test precedent) that it states PER-TENANT placement, explicitly rules out global, and
  cites Decision B by name. **Judgment call, flagged to TEST-DESIGN-VALIDATOR:** this is
  a static content check on a migration file, not a behavior the running migration
  exhibits — the alternative (no test at all, relying only on human/REVIEWER read-through)
  seemed weaker than a grep-shaped assertion that at least regresses loudly if the
  comment is ever deleted.

### AC11 — migration-058-vs-045 divergence recorded

  `Letflow.Repository.Artifact` (the module the design designates as carrying this

### AC12 — REQ-041 disambiguation

### AC13 — no route/controller added
- `repository_test.exs` describe "AC13" — three tests: no file under
  `lib/letflow/routers/**/*.ex` references `Letflow.Repository`; `lib/letflow/router.ex`

  `lib/letflow/routers/repository.ex` file exists. **Judgment call, flagged to

### AC14 — `mix test`/`mix compile --warnings-as-errors` pass
- Not asserted in test code (TEST-RUNNER's job at Step 4) — see §1 above for why this

### Cross-tenant isolation (not a numbered AC, but explicitly requested)
- `repository_test.exs` describe "cross-tenant isolation" — mirrors
  `audit_test.exs`'s AC4 test shape: a row (and its content row) created in tenant A's
  schema is unreachable via `Repo.get/3`/`Repo.all/2` scoped to tenant B's schema, and
  `list_versions/4` scoped to tenant B returns an empty page for the identical
  `artifact_name` string tenant A used.

### Concurrent `create/2` safety (not a numbered AC, but explicitly requested)
- `repository_test.exs` describe "concurrent create/2 calls..." — real `Task.async`
  concurrency (not simulated), mirroring REQ-085's "two concurrent claims" test shape:
  two writers race to create the FIRST version of a brand-new `(artifact_kind,
  artifact_name)` pair (the case design's own moduledoc calls out as "the first-version
  race a row-lock cannot cover"). Asserts exactly one lands at `version_number` 1, the
  other retries via the unique-constraint-violation path and lands at `version_number`
  2, and both share one `artifact_id`. **This test currently fails against the shipped
  implementation — see Defect B in §1.** It is intentionally left in this suite,
  un-skipped, because a test written to pass only against already-correct code proves
  nothing; this one is already proven to catch the real defect it exists to catch.
