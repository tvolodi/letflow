# Test Spec: REQ-203 — Per-tenant artifact activation, atomic multi-artifact groups, and activation history (REPO-08/09/10)

**Requirement:** REQ-203 (stage S6, `depends_on: [REQ-202, REQ-072, REQ-067]`) — atomic
multi-artifact activation with a real cross-connection observability guarantee,
per-tenant isolation, activation history with a mandatory rationale, REQ-067 cursor
pagination, `resolve/3`'s not-found semantics, and the REQ-195 `audit_entries`
disambiguation.

**Design doc:** `lib/letflow/design/req203-artifact-activation.md` (§4.3 is the central
technical risk this spec gives the most weight to).

**Test tier:** integration (real Postgres, real cross-connection concurrency via
`Task.async`/`Ecto.Adapters.SQL.Sandbox.mode(Letflow.Repo, :auto)` for AC1/AC2 — no
mocked database, no mocked concurrency).

**Test file:** `test/letflow/repository/activation_test.exs`.

## A note on the AC1/AC2 concurrency mechanism

`activate_group/4`'s shipped implementation had no way for a test to hold its
transaction open mid-`Multi` — design §4.3 explicitly anticipates this need
("TEST-DESIGNER must build from this section") and names the exact mechanism:
`Ecto.Adapters.SQL.Sandbox.mode(Letflow.Repo, :auto)` plus a `Task` that pauses inside
the `Multi` at a test-only synchronization point. No such point existed in the shipped
code, so this pass adds a minimal, clearly-marked TEST-ONLY seam to
`lib/letflow/repository/activation.ex`: an optional 5th argument,
`opts \\ []` with `test_pause_after`/`test_pause_fun` keys (see that module's
`@type test_opts` moduledoc for the full rationale). Every non-test call site
(`opts` defaulting to `[]`) reproduces the exact `Multi` pipeline design §4.2
describes with zero behavioral change — verified directly by every other test in this
file, and by `test/letflow/repository_test.exs`'s full 39-test suite, both passing
unmodified. **Flagged for REVIEWER**: this is new surface on a file REVIEWER already
signed off on.

## Test cases

1. **AC1 (part 1) — all-succeed atomic group activation**
   (`describe "AC1 -- atomic multi-artifact activation, all-succeed"`). Activates a
   group of three artifacts in one `activate_group/4` call and asserts all three
   `resolve/3` to their new versions, with one `artifact_activation_history` row each.
   Baseline correctness case the rollback test (below) contrasts against.

2. **AC1 (part 2) — forced-failure rollback, real mid-Multi failure, not a pre-check**
   (`describe "AC1 -- atomic multi-artifact activation, forced-failure rollback"`).
   Two artifacts are activated normally first (establishing a "previous version" for
   the rollback to be observed leaving them at), then a second `activate_group/4` call
   submits new versions for the first two but a **non-existent `version_id`** for the
   third. This is a genuine mid-transaction DB-level failure (an FK violation on
   `artifact_activations.active_version_id`), not the duplicate-artifact pre-check
   (covered separately below) — exercising the actual "N writes in one transaction,
   one fails, all roll back" claim AC1 makes. Asserts: all three `resolve/3` calls
   still return their PRIOR versions (not the submitted new ones for artifacts 1/2,
   whose own upsert steps ran and would have succeeded standalone before the third
   step's FK violation aborted the whole transaction); the `artifact_activation_history`
   row count is unchanged; the `artifact_activation_groups` row count is unchanged
   (the envelope insert rolled back too). **Real finding, noted in the test's own
   comment and this file's moduledoc for REVIEWER**: the current implementation
   surfaces this failure as a RAISED `Ecto.ConstraintError` out of `activate_group/4`,
   not the returned `{:error, {atom(), Ecto.Changeset.t()}}` tuple that function's own
   `@spec` advertises (no `foreign_key_constraint/3` is mapped on the
   `Letflow.Repository.Activation` changeset used by the internal `repo.update` call).
   The transaction still rolls back correctly either way — which is all AC1 itself
   asks for — so this test asserts the actual behavior (`assert_raise
   Ecto.ConstraintError`) rather than papering over the mismatch.

   A companion test in the same `describe` block confirms the duplicate-`(kind,
   name)`-pair pre-check (design §4.2 step 1b) fires **before** any `Multi` step runs
   at all (`{:error, :duplicate_artifact_in_group}`, zero `artifact_activation_groups`
   rows created) — real coverage of a different code path than the FK-failure case
   above, not a substitute for it.

3. **AC2 — REPO-08's observability criterion, tested directly**
   (`describe "AC2 -- concurrent read during an in-flight multi-artifact activation
   observes no mixed state"`). The load-bearing test in this file, built exactly per
   design §4.3's instructions. Three artifacts are first activated to "old" versions.
   Three new versions are created (but not yet activated). `activate_group/4` is
   launched as a `Task` with `test_pause_after: 1` — the TEST-ONLY seam described
   above — so the transaction pauses immediately after artifact 1's own
   `artifact_activations` row has been updated **inside the still-open, uncommitted
   transaction**, before artifacts 2/3 have been touched at all. The main test process
   (`Ecto.Adapters.SQL.Sandbox.mode(Letflow.Repo, :auto)`, a genuinely separate
   connection from the paused `Task`'s) issues `resolve/3` for **all three** artifacts
   during the pause and asserts every one returns its OLD version — including
   artifact 1, whose row has already been internally updated but not committed. This
   is the direct proof of Postgres's MVCC visibility floor design §4.3 argues for: an
   in-progress transaction's writes are invisible to every other transaction
   regardless of internal step order, at any isolation level, so "some artifacts
   already written internally, others not yet touched" produces a UNIFORM externally-
   observed old-state, never a partial one. The test then signals the paused
   transaction to continue, awaits its commit, and re-reads all three, asserting every
   one now returns its NEW version. A broken implementation that (incorrectly) split
   the group across multiple `Repo.transaction/1` calls, or that used
   `Repo.checkout/2` semantics allowing a per-statement commit, would fail this test
   by showing a mix of old/new during the pause window or by hanging (no commit for
   the main process to observe afterward) — this is real coverage, not a vacuous
   commit-then-read check (design §4.3's own explicit warning against that shape).

4. **AC3 — per-tenant isolation (REPO-09)**
   (`describe "AC3 -- per-tenant isolation"`). Two explicit tests, per the acceptance
   criterion's own two-part phrasing: (a) activating `"shared-name"` in tenant B does
   not create or change any row in tenant A's `artifact_activations`
   (`resolve/3` in tenant A still returns `{:error, :not_activated}`, then, after
   activating separately in tenant A, tenant B's own resolution is unaffected); (b)
   the SAME `version_id` (from REQ-202's global content/version store, confirmed
   directly rather than silently assumed) is active in tenant A while tenant B has
   never activated that `artifact_name` at all — proving the UNIQUE index's
   `tenant_id` scoping is what makes "the same version active in one tenant, not
   another" possible at all.

5. **AC4 — UNIQUE (tenant_id, artifact_kind, artifact_name) is a DATABASE constraint**
   (`describe "AC4 -- UNIQUE (tenant_id, artifact_kind, artifact_name) is a
   DATABASE-level constraint"`). After a normal activation, a raw `Repo.insert!/2`
   (not `activate_group/4`) attempts to insert a SECOND `artifact_activations` row for
   the identical `(tenant_id, artifact_kind, artifact_name)` triple with a valid
   changeset (`Activation.changeset/2`'s own `validate_required/2` passes). Since no
   `unique_constraint/3` is declared on that changeset, the raw Postgres UNIQUE
   violation surfaces as `Ecto.ConstraintError` — proving the constraint is enforced
   by the database, not merely avoided by `activate_group/4`'s own upsert logic (which
   this test deliberately bypasses).

6. **AC5 — `previous_version_id` null-then-populated, field-by-field**
   (`describe "AC5 -- previous_version_id null-then-populated across two successive
   activations"`). Two successive single-artifact `activate_group/4` calls against the
   same artifact, with different `activator_user_id`/`rationale` per call so every
   field can be checked independently rather than trivially matching by construction.
   Asserts `history_1.previous_version_id == nil`, `history_2.previous_version_id ==
   v1.version_id`, and every other field (`new_version_id`, `new_version_number`,
   `activator_user_id`, `rationale`, `tenant_id`, `artifact_kind`, `artifact_name`) on
   both rows.

7. **AC6 — nil / empty-string / whitespace-only rationale are all REJECTED**
   (`describe "AC6 -- rationale must be non-blank..."`). Three separate tests (one per
   blank form) asserting `{:error, {:group, changeset}}` with
   `errors_on(changeset).rationale == ["can't be blank"]` — proving
   `validate_required/2`'s trim-leading pipeline (design §2.4) handles all three
   uniformly, not just the `nil` case a naive `is_nil` check would catch. A fourth
   test bypasses the changeset entirely via `Repo.insert_all/3` against
   `artifact_activation_groups` with a raw empty-string `rationale`, asserting the
   DB-level `CHECK (rationale <> '')` constraint rejects it (`Postgrex.Error` matching
   `artifact_activation_groups_rationale_check` — `insert_all/3` has no changeset to
   map the constraint through, so this surfaces as the raw Postgres error, same
   precedent as `test/letflow/repository_test.exs`'s own DB-trigger-immutability
   tests and `test/letflow/event_store/retention_policy_test.exs`'s raw
   CHECK-constraint test).

8. **AC7 — chronological order, REQ-067 cursor pagination, both call shapes**
   (`describe "AC7 -- activation history ordering and REQ-067 cursor pagination"`).
   Seven tests: per-artifact `list_history/4` newest-first ordering; the tenant-wide
   `(nil, nil)` call shape across multiple distinct artifacts, also newest-first;
   `page_size`-bounded pagination across three pages with cursor advancement (mirrors
   `test/letflow/repository_test.exs` AC9's own pagination test shape exactly);
   `page_size_too_large` for both 0 and 201; `wrong_endpoint` for a cursor minted with
   a different prefix (REQ-202's `"RV:"`); `expired` for a cursor minted far in the
   past; `invalid_cursor` for a structurally invalid string.

9. **AC8 — `resolve/3`'s not-found semantics never fall back to an arbitrary version**
   (`describe "AC8 -- resolve/3's not-found semantics never fall back to an arbitrary
   version"`). The critical test creates THREE versions of an artifact but never
   activates any of them, then asserts `resolve/3` returns `{:error, :not_activated}`
   — not `{:ok, v3}` (the latest by `version_number`), which is exactly what a mutant
   silently "falling back to latest" would return instead. **Verified live**: a
   temporary mutation adding exactly that fallback to `resolve/3` was applied, run,
   confirmed to fail this test (and, as a bonus, the AC3 cross-tenant isolation test
   which also relies on strict not-found semantics), and reverted — see this
   run's TEST-DESIGNER handoff for the measured before/after counts. A second test
   confirms the normal case still resolves correctly once activated.

10. **AC9 — ON DELETE RESTRICT prevents deleting a referenced `artifact_versions` row**
    (`describe "AC9 -- ON DELETE RESTRICT prevents deleting a referenced
    artifact_versions row"`). Two tests: deleting a version currently referenced as
    `active_version_id` is rejected (`Ecto.ConstraintError`); deleting a version that
    is no longer the active pointer (superseded by a later activation) but is still
    referenced as `new_version_id`/`previous_version_id` in
    `artifact_activation_history` is ALSO rejected — proving the FK protection covers
    the history trail, not just the current pointer.

11. **Duplicate-artifact-in-group / empty-group rejection** (design's OQ-E
    resolution) and **the `audit_entries` cross-write** (design §7/OQ-F). Separate
    `describe` blocks: `{:error, :duplicate_artifact_in_group}` for a group containing
    the same `(kind, name)` pair twice, with zero partial state created;
    `{:error, :empty_group}` for `[]`; and a direct read-back of `audit_entries` after
    a two-artifact group activation, asserting exactly two rows (one per artifact, not
    one per group, per design's committed granularity), each with correct
    `action`/`resource_type`/`resource_id` (the artifact's own stable `artifact_id`,
    not the activation/history id)/`actor_id`/`tenant_id`/non-nil `after_state`.

12. **AC10 — moduledoc content assertion**
    (`describe "AC10 -- moduledoc states how activation history differs from
    audit_entries"`). Mirrors REQ-202's own AC5/AC6 moduledoc-content-assertion
    precedent: reads `Letflow.Repository.Activation`'s compiled moduledoc via
    `Code.fetch_docs/1` and asserts it mentions `audit_entries`, `REQ-195`,
    `rationale`, `compliance`, hash-chain tamper-evidence, and the "neither table is
    ever deleted or replaced as redundant" statement — not merely that a moduledoc
    exists, but that it says the specific disambiguating things a later reader would
    need to not delete one table as redundant with the other.

13. **AC11 — no route or controller added** (`describe "AC11 -- no route or controller
    file added"`). Structural check per REQ-202's own precedent for this judgment
    call: confirms `lib/letflow_web/router.ex` (if present) does not mention
    `Activation`, and that no `activation_controller.ex` file exists. The authoritative
    check for this criterion remains `git diff --stat` scoped to this requirement's
    commits, as REQ-202's own AC13/AC14 note — this test is a defense-in-depth
    structural sanity check, not a substitute for that diff review.

14. **AC12 — `mix test`/`mix compile --warnings-as-errors`**. TEST-RUNNER's job, not
    this file's. `mix compile --warnings-as-errors` was run directly during this
    pass and produced no output (clean compile, including the new TEST-ONLY seam on
    `Letflow.Repository.Activation.activate_group/5`).

## Real Postgres runs performed during test design

- `mix test test/letflow/repository/activation_test.exs`: **28/28 passed** (final).
  Three real failures were found and fixed while writing this file (not merely
  anticipated): (1) an `Ecto.ConstraintError` assertion for a mid-Multi FK failure
  that the implementation actually raises differently than initially assumed —
  resolved by asserting the real observed exception rather than an invented one; (2)
  a moduledoc substring assertion broken by an embedded newline in the source text —
  resolved with a whitespace-tolerant regex; (3) an `insert_all/3` type/constraint
  mismatch (`NaiveDateTime` vs `DateTime`, and `Ecto.ConstraintError` vs the actual
  `Postgrex.Error` `insert_all/3` produces when bypassing the changeset entirely) —
  resolved by matching the real Postgres behavior.
- `mix test test/letflow/repository_test.exs test/letflow/repository/canonicaliser_test.exs`:
  **39/39 passed**, confirming the TEST-ONLY seam added to `activate_group/4`
  (an optional 5th `opts` argument, defaulting to `[]`) did not disturb REQ-202's own
  suite.
- A temporary mutant (removing `resolve/3`'s strict not-found semantics in favor of
  "latest by version_number") was applied, run, and confirmed to fail exactly the
  tests designed to catch it (2 failures: AC8's own test plus AC3's isolation test),
  then reverted and re-verified green (28/28).
