# REQ-204 Test Specification — SSRF Validation for Webhook `target_url`

**Design authority:** `lib/letflow/design/req204-ssrf-validation.md`  
**Implementation authority:** `lib/letflow/webhooks/url_validator.ex`, `lib/letflow/webhooks.ex`  
**Test files:**
- `test/letflow/webhooks/url_validator_test.exs` — unit tests for `UrlValidator` directly
- `test/letflow/webhooks_test.exs` — integration tests (new describe blocks at the end)

---

## Acceptance criterion → test case mapping

### AC1 — Non-https scheme rejected at `create/2`

**Criterion:** `create/2` with an `"http://"` `target_url` returns `{:error, :target_url_not_allowed}`.

**Why this test:** the scheme check in `check_scheme/1` runs first in the `with`-chain, before
any DB round-trip. Asserting the exact return atom proves the check is wired in and is distinct
from a changeset error (which would be `{:error, %Ecto.Changeset{}}`).

**Tests:**
- `url_validator_test.exs`: `"http:// scheme is rejected"`, `"ftp:// scheme is rejected"`, `"schemeless URL is rejected"`, `"empty string is rejected"`
- `webhooks_test.exs`: `"REQ-204 AC1: http:// scheme rejected with {:error, :target_url_not_allowed}"`

**DB access needed:** No — validation short-circuits before `tenant_id_for_schema_name/1`.

---

### AC2 — Five explicit private-range IP literals rejected at `create/2`

**Criterion:** `create/2` with each of 127.0.0.1, 169.254.169.254, 10.0.0.5, 172.16.0.5,
192.168.0.5 as the `target_url` host returns `{:error, :target_url_not_allowed}`.

**Why these five:** they are the exact five addresses called out in the acceptance criteria.
Each exercises a different blocked subnet clause in `blocked_ipv4?/1`. 169.254.169.254 is
called out explicitly because it is the cloud instance-metadata service address — the
highest-severity SSRF target in this class.

**Why IP literals in `url_validator_test.exs`:** the `validate/1` 1-arity form is safe to call
with IP literals because `check_ip_literal/1` handles them without any DNS call. Confirming the
same atoms are rejected at the `create/2` level ensures the integration wiring is intact.

**Tests:**
- `url_validator_test.exs`: one test per address (5 tests) plus IPv6 literals (::1, fc00::1, fe80::1, IPv4-mapped forms)
- `webhooks_test.exs`: `"REQ-204 AC2"` describe block — one test per address (5 tests)

**DB access needed:** No.

---

### AC3 — Legitimate https target succeeds at `create/2`

**Criterion:** `create/2` with a valid `"https://<public-ip>/hook"` returns `{:ok, %{subscription:_, hmac_secret_once:_}}`.

**Why a literal public IP:** avoids real DNS calls in tests (consistent with T-2 directive spirit)
while still exercising the full create path including `Secrets.put/2` and DB insert.

**Tests:**
- `url_validator_test.exs`: `"public IP literal (no DNS needed) is allowed"`, `"hostname resolving to public IP via injected resolver is allowed"`
- `webhooks_test.exs`: `"REQ-204 AC3: https target with public IP literal creates the subscription and returns hmac_secret_once"`

**DB access needed:** Yes (AC3 in `webhooks_test.exs` only).

---

### AC4 — `deliver/3` blocks DNS rebinding; records FAILED attempt

**Criterion:** a subscription whose `target_url` was valid at creation time is blocked at
delivery time when the IP at that point falls in a private range, and the refusal is recorded
as a FAILED `webhook_delivery_attempts` row rather than performing the outbound POST.

**Why this approach (direct DB update):** `dispatch_http/4` is `defp` and cannot be reached
with an injected resolver via the public `deliver/3` API today (the resolver thread-through was
implemented as `dispatch_http/4` but not surfaced through `deliver/3`). The DB-update approach
is the correct alternative per design §6.2: it creates a subscription with a valid URL (passes
`create/2`), then updates `target_url` directly in the DB (simulating the rebinding event where
the hostname's IP changed), then calls `deliver/3`. The `dispatch_http/4` validation runs at
dispatch time and returns `{:FAILED, nil, "target_url not allowed (SSRF protection)"}`, which
`attempt_loop` records. This is exactly the scenario the design's defence-in-depth is meant to
catch.

**Why this test is slow (~7s):** `deliver/3` retries up to `@max_attempts = 4` times with
real `Process.sleep/1` backoff (1s + 2s + 4s). All four attempts are SSRF-blocked. This is
the same design decision as REQ-183's slow test — see `test/specs/REQ-183.md`'s
"Backoff-timing problem" section. `@tag timeout: 30_000` is applied.

**DNS resolver injection at `url_validator_test.exs` level:** the `"hostname resolving to
169.254.169.254"` and `"loopback 127.0.0.1"` injected-resolver tests in
`url_validator_test.exs` also cover the DNS-rebinding scenario, but at the validator level.
The `webhooks_test.exs` AC4 test adds the additional guarantee that the FAILED attempt row is
persisted and that no POST is performed.

**Tests:**
- `url_validator_test.exs`: `"hostname resolving to 169.254.169.254 at validation time is rejected (DNS rebinding)"`, `"hostname resolving to loopback 127.0.0.1 via injected resolver is rejected"`, `"hostname resolving to private RFC-1918 via injected resolver is rejected"`
- `webhooks_test.exs`: `"REQ-204 AC4: deliver/3 records FAILED attempts and does not POST when target_url is private at dispatch time"`

**DB access needed:** Yes.

---

### AC5 — `dispatch_http/3` does not auto-follow 3xx redirects

**Criterion:** `:httpc.request/4` is called without `autoredirect: true` or `follow_redirect: true`.

**Why source assertion:** the production code does not follow redirects because it does NOT
pass `autoredirect: true` (`:httpc`'s default is `false`). A source-assertion test is the
most direct and robust way to confirm this status quo — it fails immediately and without
network access if someone accidentally adds the option. This pattern is established in this
codebase per `docs/anti-patterns.md`.

**Tests:**
- `webhooks_test.exs`: `"REQ-204 AC5: dispatch_http/3 does not pass autoredirect: true or follow_redirect: true to :httpc"`

**DB access needed:** No.

## Pre-existing regression noted (not TEST-DESIGNER scope)

The existing `Letflow.WebhooksDeliveryTest` tests (REQ-183) use
`Letflow.WebhookTestServer` which returns `"http://127.0.0.1:PORT/hook"` URLs.
With REQ-204's SSRF validation in place:
1. `Webhooks.create(%{target_url: "http://127.0.0.1:PORT/hook"}, ...)` now returns
   `{:error, :target_url_not_allowed}` instead of `{:ok, ...}`, causing
   `create_subscription!/2` to crash.
2. This is a regression introduced by REQ-204's `create/2` URL validation.

This regression is **out of TEST-DESIGNER scope** — it is a gap between ELIXIR-DEV's
implementation and the test-support infrastructure (`WebhookTestServer` needs to be
updated to serve a URL that passes SSRF validation, or a test-only bypass must be
added). ORCH should register an issue for ISSUE-FIXER to address before TEST-RUNNER
runs the full suite.
