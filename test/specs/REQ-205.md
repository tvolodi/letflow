## AC3 — double-seed is a no-op, one test per entity kind

**Pre-check path**: `seed_idempotency_test.exs` has one test per entity kind
(tenant/user/group/definition), each with a direct DB row-count assertion (not
"no error raised") after seeding twice. Sufficient as-is.

**Conflict-branch path (the design's "belt-and-suspenders" TOCTOU fallback)**:
NOT independently triggered by any test, including this session's new ones.
Reasoning recorded explicitly rather than silently skipped: every `seed_*`
function's conflict branch (e.g. `Seed.seed_company/1`'s
`retry_onboarding_lookup/2`, `seed_one_user/2`'s `refetch_user_or_error/2`,
`seed_one_group/3`'s `refetch_group_or_error/2`, `seed_process/3`'s
`refetch_process_or_error/2`) only executes when two callers race between the
module's own pre-check and its `create_*` call — the pre-check itself already
catches every *sequential* re-seed, which is what a real scenario-harness test
run actually does (no concurrent seeding of the same fixture within one test
process). Forcing the race deterministically would require either mocking the
pre-check (`Letflow.Identity`/`Letflow.Definitions` are called directly, not
through an injectable seam — no `Mox`/behaviour indirection exists in this
codebase for these context modules) or a `Task.async`-based timing race, which
is not guaranteed to land inside the actual TOCTOU window on every run and
would make the test's pass/fail outcome timing-dependent — exactly what this
project's `test_developer_guide.md` and this session's instructions forbid
("Don't depend on wall-clock time or unseeded randomness"). **Coverage
substitute**: code-review-level confirmation, done this session — each
conflict branch was read in full (`test/support/simulation/seed.ex` lines
131-145, 194-205, 278-289, 354-364) and confirmed reachable (pattern-matches a
real `{:error, :duplicate_*}` tuple `Letflow.Identity`/`Letflow.Definitions`
already documented as returning) and correctly shaped (re-fetches and returns
the winning row rather than propagating the error). This is real but weaker
evidence than a triggered test — recorded honestly, not counted as equivalent.

## §5 — `{{produces.X}}` template substitution mechanism

Existing coverage (`runner_test.exs`'s AC4 test) only exercises the **entire-string
form** of substitution on a correct reference. TEST-DESIGNER added, all in
`runner_template_and_outcomes_test.exs`:

- **"substring form resolves ... verified in Postgres afterward"** — a second
  api step's `initial_variables.note` field embeds a prior step's produced
  instance id inside a larger string (`"ref:{{produces.first.instance_id}}:end"`,
  the substring form §5 separately specifies from the whole-string form). The
  test does not hardcode the expected substituted value (it's a runtime UUID
  unknowable in advance) — it reads the *actual persisted* `variables.note`
  field back out of Postgres via `Instances.get_by_id/2` and compares it against
  the id captured in the run report. This is why the test exists: a version of
  the harness that only implemented whole-string substitution (a plausible
  half-measure) would leave `note` containing the literal, unsubstituted
  template text, and this test would catch that.
- **"an unresolved produces reference fails closed"** — a step references
  `{{produces.nonexistent_step.some_field}}`, a name that was never produced by
  any prior step. Asserts `:error` with the exact
  `{:unresolved_template, "produces.nonexistent_step.some_field"}` tuple.
- **"a later step referencing a via:gui step's ... produces output fails
  closed"** — see AC5 above; this is the more specific instance of the same
  fail-closed mechanism the design calls out by name.

**Mutation-tested this session**: `resolve_dotted_path/2`'s `:error` branch
(unresolved lookup) was temporarily changed from
`{:error, {:unresolved_template, "produces." <> dotted_path}}` to
`{:ok, "{{produces." <> dotted_path <> "}}"}` — i.e., silently substituting the
literal template text back in, the exact forbidden behavior §5 prohibits. Both
of the new fail-closed tests failed against the mutant (one crashed with
`left: :ok / right: :error` on the step outcome; the other's step_results match
failed since outcome was `:ok` instead of `:error`). Reverted; `mix test
test/letflow/simulation/runner_template_and_outcomes_test.exs` returned to 7/7
passed.

## §6 — the three expected-outcome verification methods aren't "no error raised" stubs

`instance_state`: see AC4 above (mutation-tested).

`task_assigned` and `audit_event` had **zero prior test coverage** — neither
appears in any of ELIXIR-DEV's three existing test files. TEST-DESIGNER added a
match/mismatch pair for each in `runner_template_and_outcomes_test.exs`:

- `task_assigned`: a real `tasks`/`token_records`/`instance_projections` FK
  chain is inserted directly (same fixture-helper shape
  `test/letflow/routers/tasks_test.exs`'s `insert_task!/2` already uses in this
  codebase), assigned to a real seeded user. One test asserts `:pass` when the
  expected assignee matches the persisted `assignee_ref`; a second asserts
  `:fail` (not `:pass`, not an exception) when the expected assignee is a
  fabricated id that doesn't match. The second test is the one that would catch
  a regression to "return `:pass` if the query didn't raise" — a stub of that
  shape would report `:pass` on the mismatch case, which the test asserts
  against directly.
- `audit_event`: driven by a genuine HTTP-dispatched `POST /api/v1/instances`
  call (the same real audit-log write path AC4's precedent already exercises
  end to end, not a directly-inserted row) — one test asserts `:pass` for the
  real `instance.create` row that call produces; a second asserts `:fail` (with
  `observed.matching_entry == nil`) for an `event_type` that never happened.
  Same "would catch a no-error stub" reasoning as `task_assigned`.

**Real gap found and recorded, not fixed here** (out of TEST-DESIGNER's remit —
this is `test/support/simulation/runner.ex` implementation behavior, ELIXIR-DEV's
file): `verify_outcome/2`'s `:audit_event` clause takes `_produces` as an
unused parameter and never runs `args` through `resolve_ref/3`'s `{{produces.X}}`
substitution the way `task_assigned`/`instance_state` do. A scenario cannot
write `"resource_id" => "{{produces.instance.instance_id}}"` in an `audit_event`
expected outcome today — that literal string is sent to `Audit.list_entries/1`
verbatim as `resource_id` and matches nothing, silently. The two `audit_event`
tests above were written to scope by `resource_type`/`event_type` only
(filters that do work) specifically to avoid asserting on the broken path while
still proving the method reads real state. This finding is carried into the
TEST-DESIGNER handoff for ORCH/ELIXIR-DEV; REQ-206/207/208 (which own the real
scenario corpus and will likely want exactly this resource-id-scoped
`audit_event` check) are the ones who would hit this in practice.
