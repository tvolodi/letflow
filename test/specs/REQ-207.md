## AC3 — supplier-quality-deviation-false-positive: reaches end-false-positive specifically

`describe "vortex-supplier-quality-deviation-false-positive"` (lines 716-921 after this
pass's addition). **Gap found and closed this session.**

**What existed before this pass:** the terminal-node check relied solely on the
severity-classification task's own `TASK_COMPLETED` event payload showing
`activated_nodes == []`, reasoned (in the test's own comment, correctly) to mean "no
further real node was reached" — contrasted against the critical scenario's
non-empty `activated_nodes` (`["corrective-action-subprocess"]`) at the equivalent
point.

**Why that alone is not sufficient**, verified by reading the actual dispatch code
this session (`lib/letflow/engine/transition.ex:373-379`,
`dispatch_end/3`): every terminal END node in this codebase produces
`activated_nodes == []` alike — `dispatch_end/3` unconditionally drops the token the
instant it reaches *any* END node, and no event payload appended anywhere under
`lib/letflow/` (confirmed by grepping every `event_type: "..."` append site) ever
records the literal target node id. So `activated_nodes == []` proves "the token
took a one-hop route to *some* END node from false-positive-check" — it is
consistent with the correct route (`end-false-positive`) **and** with a
hypothetical bug that misrouted `false_positive == true` directly to `end-closed`
instead (also one hop, also `activated_nodes == []`). The requirement's own AC3
wording ("verified by querying the actual end node reached") and the design's own
OQ-3 discussion were not actually satisfied by this signal alone, despite the test's
comment correctly diagnosing the *general* limitation of `current_nodes`/
`activated_nodes` for terminal-node identity.

**Fix applied**: added a structural cross-check (lines ~812-844) that asserts
directly against the seeded graph's own edge data — `@simple_supplier_deviation_graph`
is the actual ground truth for "which literal node does the `false_positive == true`
edge out of `false-positive-check` target," since it is the real definition the
instance ran against. The test now:
1. Finds the edge with `source == "false-positive-check"` and
   `condition == "variables.false_positive == true"`.
2. Asserts `edge["target"] == "end-false-positive"`.
3. Asserts (redundantly, for clarity of intent) `edge["target"] != "end-closed"`.

This closes the loop: the dynamic evidence (only `false_positive: true` was set, no
`severity`; `activated_nodes == []`; `status == :completed`) establishes *that* the
false-positive edge fired and led straight to an END node with no further real node,
and the new static assertion establishes *which* END node that edge's own condition
maps to — together they are equivalent to "queried the actual end node reached,"
which no single persisted runtime signal in this codebase can do directly (a real,
confirmed platform gap, not a test-writing shortcut).

**Verified non-vacuous by mutation, this session**: temporarily changed the seeded
graph's `e3` edge target from `"end-false-positive"` to `"end-closed"` and re-ran
the test. Result: `mix test` failed at test setup with a real
`Letflow.Definitions` graph-validation error (`isolated_node` on `end-false-positive`,
since removing its only incoming edge orphans it) — the seeded process definition
itself became invalid, confirming this graph shape is load-bearing. To isolate the
new assertion specifically (independent of that structural side effect), a second
mutation left the graph correct and instead flipped the test's own expected value
(`assert false_positive_edge["target"] == "end-closed"`) — this failed with:

```
1) test vortex-supplier-quality-deviation-false-positive quarantine -> severity
   false-positive; reaches end-false-positive specifically
   Expected the false_positive == true edge to target end-false-positive
   specifically, not end-closed ...; observed target: "end-false-positive"
```

Both mutations reverted; `mix test test/letflow/simulation/req207_vortex_test.exs`
returned to 4/4 passed (quoted above) after revert.

## Test isolation / fixture hygiene

- **Unique tenant per test**: `setup` block calls
  `Letflow.TenantSlugFixture.unique_slug("req207")` (line 248) and runs once per
  test (ExUnit's `setup` semantics, not `setup_all`) — no shared hardcoded tenant/
  slug/id across the 4 describe blocks.
- **No wall-clock/unseeded-randomness dependency**: grepped the module for
  `DateTime.utc_now`, `:rand`, `System.os_time` — no matches. `DateTime.compare/2`
  (AC2's ordering check) compares two real persisted timestamps against each other,
  never against the current clock.
- **Self-sufficient, no cross-test ordering dependency**: `async: false` is required
  for `Sandbox.mode(:auto)` (real Postgres, not a per-test checkout), but each test
  provisions and tears down its own tenant schema independently via the shared
  `setup`/`on_exit` pair — no test relies on state left behind by another.
- **No hardcoded secrets/connection strings**: none present; tokens are generated
  per-test via `Identity.create_token/3`.
