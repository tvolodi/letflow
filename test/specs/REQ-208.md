## Governing context: the join_counters BLOCKER (not this requirement's to fix)

`Letflow.Engine.complete_task/3`'s per-call state rebuild hardcodes
`join_counters: %{}` (`lib/letflow/engine.ex`, `build_instance_state/3`), so a
`PARALLEL_GATEWAY` join can only fire within the same hop-chain as its own split — any
real, separate-call `HUMAN_TASK` completion on a fork branch fails with a real HTTP
500. This is a genuine, pre-existing Engine defect (filed via `result.issues`,
BLOCKER, at Step 2a), not something REQ-208 introduced or can fix within its own
scope. Its consequence for test design: AC1/AC2's fuller claims (committee route,
quorum, disbursement, EO-002's negative assertion via the intended full run) are
**not reachable** by any test — asserting them as PASS would be fabrication, not
coverage. The test module instead asserts the real, truncated disposition and the
real HTTP-500 reproduction as the closed outcome for those scenarios' unreachable
steps. This is the correct test-design response to a genuine platform defect: prove
what is true, not what was designed to be true before the defect was found.

## AC2 — meridian-loan-origination-below-threshold: EO-002 negative assertion

`describe "meridian-loan-origination-below-threshold"` (lines 653-703). Same
BLOCKER truncates this scenario at the identical point (steps 1/2a/2b only); EO-002's
own literal claim (query real task state, confirm the *absence* of any
committee-vote task, not merely infer it from L1/L2 presence) is honestly reported
as not verified by this scenario's own run (module doc + inline comment, lines
682-687) rather than silently assumed to hold.

**Gap found and closed this session**: the `:no_task_of_type` verification method
(design §2.2, the new negative-assertion primitive EO-002 itself calls for) was
implemented in `test/support/simulation/runner.ex` (lines 598-617) and wired into
`ScenarioFixture`'s closed vocabulary, but was **never actually exercised by any
test** — both loan scenarios' `expected_outcomes` are `[]` (truncated before EO-002
could run). New, non-vacuous logic with zero test coverage is exactly the kind of
gap this coverage-verification pass exists to catch; leaving it uncovered would mean
a broken `:no_task_of_type` implementation could ship undetected.

**Fix applied**: rather than fabricate reachability past the BLOCKER on the loan
scenarios (which would misrepresent the defect), the method is instead exercised on
the `meridian-regulatory-compliance-review-bafin` scenario (AC3), which has no
`PARALLEL_GATEWAY` on its exercised path and is therefore unaffected by the
defect — see AC3 below for the concrete test added and its non-vacuousness proof.
This closes the coverage gap on the verification method's own logic without
overstating what the loan scenarios themselves can prove.

## Test isolation / fixture hygiene

- **Unique tenant per test**: `setup` block (line 333, not `setup_all`) calls
  `Letflow.TenantSlugFixture.unique_slug("req208")` fresh for every test; each test
  seeds its own tenant, org structure, definitions, and per-actor tokens
  independently.
- **Self-sufficient teardown**: `on_exit(fn -> teardown(unique) end)` (line 478)
  drops the tenant's schema and deletes its `Registration`/`OnboardingRecord`/
  `Tenant` rows per test — no shared mutable state or cross-test ordering
  dependency (`async: false` is required only for `Sandbox.mode(:auto)` against
  real Postgres, not for test-to-test ordering).
- **No wall-clock/unseeded-randomness dependency**: grepped the module for
  `DateTime.utc_now`, `:rand`, `System.os_time` — no matches.
- **No hardcoded secrets**: tokens are generated per-test via
  `Identity.create_token/3`; no static credential/connection string present.
