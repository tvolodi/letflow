# Test Spec: REQ-209 — Port R-Co's condition-evaluation corpus as an ExUnit regression suite for `Letflow.Engine.Expr`

**Requirement:** REQ-209 (`docs/requirements.yaml`, stage S7) — port R-Co's
`tests/differential/corpus/conditions_v1.json` (15 entries) into a Letflow ExUnit
regression/golden-value suite for `Letflow.Engine.Expr`, since Letflow never had a
second (CEL) evaluator to diff against the way R-Co's `differential_test.zig` did at
its EXP-102 cutover.

**Design:** `lib/letflow/design/req209-expr-differential-corpus-regression.md`.

**Note on how this file came to exist:** ELIXIR-DEV (Step 2a) already wrote the
complete fixture and test — `test/fixtures/simulation/differential_corpus.json` and
`test/letflow/engine/expr_differential_corpus_test.exs` — directly against the
approved design, and REVIEWER (Step 2d) confirmed the test already provides full
per-entry coverage. This TEST-DESIGNER pass is therefore a coverage-completeness
**confirmation** against that existing test, not new authorship. Every criterion below
was independently re-checked this session (fixture byte-diffed against the R-Co
source, test executed, compile re-run) rather than trusted from the prior handoffs'
summaries. **No gap was found** — no new test code was added.

**Requirement's acceptance criteria (verbatim):**
1. "`test/fixtures/simulation/differential_corpus.json` contains all 15 entries from
   R-Co's `tests/differential/corpus/conditions_v1.json` with `condition_id`,
   `condition_text`, `context` and `expected_result` preserved byte-for-byte, verified
   by a count/diff-style check against the count established this session (15)"
2. "a single property-style ExUnit test iterates every corpus entry and asserts
   `Letflow.Engine.Expr`'s `translate_cel_to_expr/1` + evaluate path returns exactly
   `expected_result` given the entry's context bound as `variables` — one test loop,
   not 15 duplicated test bodies"
3. "every corpus entry is accounted for in the suite's own run output as either
   evaluated-and-matched or EXPECTED_UNSUPPORTED with the specific rejected construct
   named — the sum of both categories equals 15, and zero entries are silently absent
   from the suite"
4. "the test module's moduledoc states explicitly that this is a regression/
   golden-value port, not a CEL-vs-expr differential, and cites both R-Co source files
   (`tests/differential/differential_test.zig`,
   `tests/differential/corpus/conditions_v1.json`) and `expr.ex`'s own EXP-102/AC11
   moduledoc section as the reason no second implementation exists to diff against"
5. "if any corpus entry's evaluated result diverges from its `expected_result` on a
   construct `expr.ex`'s own moduledoc claims to support (i.e. a genuine regression,
   not an EXPECTED_UNSUPPORTED case), it is reported to ORCH as a finding per
   `core-directives.md`'s No Issue Left Local-Only rather than silently adjusted or
   excluded"
6. "`mix test` and `mix compile --warnings-as-errors` both pass with real output
   quoted"

**Test tier:** pure unit. `Letflow.Engine.Expr` has no `Letflow.Repo`/`Ecto.Sandbox`
dependency (moduledoc's own "Purity and determinism (AC8)" section) — `async: true`
is correct and matches `expr_test.exs`'s existing precedent.

## Scope test

Real application-executable Elixir logic under test: `lib/letflow/engine/expr.ex`'s
`evaluate_condition/2` (composing `translate_cel_to_expr/1` → `parse/1` → `eval/2`).
The fixture (`differential_corpus.json`) is JSON test data, not app code, but the test
module itself (`expr_differential_corpus_test.exs`) is real ExUnit logic exercising a
real code path. Not docs-only, not build-config. Full TEST-DESIGN-VALIDATOR /
TEST-RUNNER chain applies.

## Criterion-by-criterion confirmation

### AC1 — fixture is a byte-for-byte, 15-entry port

**Confirmed, not assumed.** Ran `diff --strip-trailing-cr` this session between
`test/fixtures/simulation/differential_corpus.json` and R-Co's own
`tests/differential/corpus/conditions_v1.json` (`c:\Users\tvolo\dev\ai-dala\R-Co\`) —
zero content differences (only a CRLF/LF line-ending artifact in the raw `diff`
output, not a substantive difference; every `condition_id`, `source_definition_id`,
`source_definition_version`, `source_gateway_node_id`, `condition_text`, `context`,
and `expected_result` value is identical across all 15 objects, in the same order).
The test itself also asserts the count at runtime: `assert length(@corpus) == 15`
(line 74) — this is the "count/diff-style check" AC1 asks for, running every time the
suite runs, not a one-off manual check that could silently rot. Would fail if a future
edit to the fixture dropped, duplicated, or renumbered an entry.

### AC2 — single property-style loop, not 15 hand-written tests

**Confirmed by direct inspection.** One `test "..."` block (line 73), containing one
`Enum.reduce/3` loop (lines 76-109) over `@corpus`, calling
`Expr.evaluate_condition(condition_text, context)` (line 83) — the same composed
production entry point `Letflow.Engine.Transition.dispatch_exclusive_gateway/4` uses,
not a hand-assembled `translate_cel_to_expr/1` + `parse/1` + `eval/2` chain
reconstructed in test code. This matches the design doc's §6 resolution of
"property-style" (one test, internal loop over a fixed data table) and REVIEWER's own
Step 2d confirmation that this reading was correctly applied. There are no
macro-generated per-entry `test` cases and no 15 separate `test` blocks. Would fail
(as a design/idiom regression) if a future edit expanded this into per-entry `test`
macros — TEST-DESIGN-VALIDATOR and REVIEWER on any future touch to this file should
keep checking for that.

### AC3 — every entry accounted for, sum equals 15, none silently absent

**Confirmed by direct inspection and execution.** The loop's accumulator
(`{evaluated_acc, unsupported_acc}`) increments exactly one of the two counters for
every entry processed (lines 92-108: the `case disposition do` has exactly two
branches, `:evaluated` and `:expected_unsupported`, each incrementing its own counter
and no third/silent branch). After the loop: `assert evaluated_count == 15`,
`assert expected_unsupported_count == 0`, `assert evaluated_count +
expected_unsupported_count == 15` (lines 111-113) — three separate assertions, not
just a single sum check, so a future change that miscounted one category while the sum
happened to still total 15 would still be caught by the individual-count assertions.
Ran `mix test test/letflow/engine/expr_differential_corpus_test.exs` this session:

All three count assertions pass, confirming the 15/0/15 accounting this design doc's

EXPECTED_UNSUPPORTED, in this corpus version). Per-entry `condition_id` and
`condition_text` are embedded in every assertion's failure message (lines 95, 105), so
a future failing entry is identifiable without re-running in isolation. Would fail if
any entry were skipped by the loop (impossible without editing `@corpus` or the loop
itself) or if the two branches' counters could double-count or under-count an entry.

### AC5 — genuine regressions reported, not silently adjusted

**Satisfied by construction, confirmed by inspection — no genuine regression exists to
report.** All 15 corpus entries' `condition_text` strings use only grammar
`expr.ex`'s own moduledoc documents as supported (variable refs, the 6 comparators,
`&&`/`||`/`!`, literals, parenthesized grouping — design doc §4's classification
table, independently re-derivable from the fixture's own `condition_text` values,
none of which contain any `@unsupported_call_markers` substring, a bare `in`, or a
bare `?`). The test's own run (AC3's quoted output above) shows `evaluated_count ==
15` with every one of those 15 assertions passing against `entry["expected_result"]`
— i.e. `Expr.evaluate_condition/2`'s actual output matches every recorded golden value
with zero divergence. Had any entry diverged, the test would fail with the
`condition_id`-labelled message at lines 94-95, which is the trigger point at which a
finding would be filed to ORCH per core-directives.md's No Issue Left Local-Only — no
such divergence occurred this session, so there is nothing to file. The
`@expected_unsupported_ids` MapSet scaffolding (line 71, empty in this corpus version)
exists precisely so that a future corpus version's genuinely-unsupported entry would
be classified deliberately rather than mis-asserted as a silent pass/fail — see design
doc OQ-1 for the mechanics of adding such an entry later.

## Fixture-loading convention (design doc OQ-3, resolved)

The design doc's §5/OQ-3 deferred to whatever convention
`test/fixtures/simulation/fixture_shape_test.exs` already established for JSON
loading, to avoid introducing a second convention. On inspection, that sibling file
loads YAML fixtures (`yaml_elixir`), not JSON — it has no JSON-loading call to match
against, so OQ-3 is moot for this corpus. `expr_differential_corpus_test.exs` uses
`@corpus_path |> File.read!() |> Jason.decode!()` (line 61), which is this project's
standard JSON-decoding call elsewhere in the codebase and produces the string-keyed
map shape §5 documents (`entry["condition_text"]`, `entry["context"]`, etc., all
accessed via `Map.fetch!/2` with string keys at lines 78-81) — consistent, no
divergent convention introduced.
