# Test Spec: REQ-211 — Instance-attachment schema and core upload/download/list context module

**Requirement:** REQ-211 (`docs/requirements.yaml:11999-12142`, stage S6, queue task 394,
GH#774, closes GH#769/ISS-0390). Design authority:
`lib/letflow/design/req211-instance-attachments-core.md`. Implementation authority:
`lib/letflow/repository/attachment.ex`, `lib/letflow/repository/attachments.ex`,
`priv/repo/migrations/20260901000001_add_content_to_repository_artifacts.exs`,
`priv/repo/migrations/20260901000002_create_instance_attachments.exs`, plus the
REQ-202-touching changes `lib/letflow/repository.ex` (`upsert_content/5` -> public
`upsert_content/6`) and `lib/letflow/repository/artifact.ex` (added `content` field).
Already passed SECURITY-REVIEWER and REVIEWER clean.

Acceptance criteria (verbatim from `docs/requirements.yaml`):

1. the `instance_attachments` table lives inside each tenant's Postgres schema with a
   `tenant_id` column retained and `instance_id` required (not nullable), matching
   decision 0003 Decision B's pattern -- verified by inspecting the migration
2. `upload/2` hashes the uploaded bytes independently of any caller-supplied
   `content_type` or `byte_size` field, creates or reuses a `repository_artifacts` row
   keyed by that hash (byte-identity hashing, no canonicalisation), and creates one
   `instance_attachments` row referencing it -- demonstrated by uploading byte-identical
   content under two different `instance_id` values and showing one
   `repository_artifacts` row but two `instance_attachments` rows
3. `byte_size` stored on the `instance_attachments` row is independently measured from
   the actual uploaded byte content, not trusted from any caller-supplied field --
   demonstrated by a test that supplies a mismatched declared size and asserts the
   stored value reflects the real byte count
4. an upload exceeding a stated, concrete size ceiling is rejected before being
   persisted, with neither a `repository_artifacts` row nor an `instance_attachments`
   row created -- demonstrated by an over-limit upload attempt
5. `list/2` is tenant-scoped and filtered by `instance_id`
6. `list/2` supports cursor pagination per REQ-067's existing contract
7. `delete/2` removes the `instance_attachments` row such that a subsequent `list/2` no
   longer includes it, while the underlying `repository_artifacts` content row is left
   untouched and remains referenced if another row shares its hash
8. the moduledoc states per-tenant-schema dedup boundary (Decision B) and
   no-canonicalisation, demonstrated by two tenants uploading byte-identical content
   producing two independent `repository_artifacts` rows
9. the moduledoc names content-scanning/antivirus as a deliberately deferred follow-up
10. no route or controller file is added or modified
11. `mix test` and `mix compile --warnings-as-errors` both pass with real output quoted

**Test tier:** unit+integration (`Letflow.DataCase`, real Postgres, real tenant schema
provisioning via `Letflow.TenantFixture`) -- no route exists yet (REQ-212's scope), so
every test calls `Letflow.Repository.Attachments`'s functions directly.

**Test file:** `test/letflow/repository/attachments_test.exs` (ELIXIR-DEV wrote 15
sanity tests at Step 2a; this pass cross-checked all 11 ACs against them and added 3
gap-closing tests, bringing the file to 18).

## 1. Acceptance-criteria -> test-case mapping

### AC1 — migration: schema-per-tenant, `tenant_id` retained, `instance_id` required

**Gap found and closed.** ELIXIR-DEV's 15 sanity tests never directly demonstrated the
NOT NULL constraint or schema-isolation claim at the DB level -- every existing test
calls `upload/2`, which always supplies `instance_id`, so a migration that silently
made `instance_id` nullable would pass all 15 unnoticed. Closed by adding the same
`information_schema`-inspection idiom `test/letflow/dlq_test.exs`'s own AC1 test already
established for this project (REQ-176), plus a raw-SQL insert proving the NOT NULL
constraint is real at the Postgres level, not merely enforced by the changeset.

* `describe "AC1: instance_attachments migration -- schema-per-tenant, tenant_id
  retained, instance_id required"` — two tests:
  1. provisions a real tenant, queries `information_schema.columns` for the tenant's
     own schema, asserts `tenant_id`/`instance_id`/`content_hash`/`id` are all
     `is_nullable = "NO"`, then queries `information_schema.tables` scoped to `public`
     and asserts no `instance_attachments` row exists there.
  2. a raw `INSERT` (bypassing `Attachment.changeset/2` entirely) that omits
     `instance_id` is asserted to raise `Postgrex.Error` matching
     `null value in column "instance_id"`.

**Verified as a real gap, not manufactured:** mutated the migration
(`add :instance_id, :binary_id, null: false` -> `null: true`), confirmed both new tests
fail (`Result: 16/18 passed`), reverted, confirmed clean.

### AC2 — `upload/2` hashing + dedup + two-rows-from-one-hash

Confirmed **not stale** despite the design's mid-flight rework (the `content`
byte-storage addendum, §2A). The first `upload/2` sanity test
(`test/letflow/repository/attachments_test.exs:43-58`) asserts
`stored_artifact.content == "hello attachment bytes"` -- this reads back the actual
`repository_artifacts.content :bytea` column the migration addendum added, so it
genuinely exercises real byte round-tripping through the reworked schema, not a
pre-rework assumption about a column that doesn't exist. The dedicated AC2 test
(`:60-84`) uploads byte-identical content under two different `instance_id` values and
asserts one `repository_artifacts` row (`Repo.aggregate(Artifact, :count, ...) == 1`)
but two `instance_attachments` rows (`== 2`), with distinct `attachment.id`s and equal
`content_hash`. Adequate as-is -- no gap.

### AC3 — `byte_size` independently measured

**Gap found and closed.** The existing test
(`test/letflow/repository/attachments_test.exs:86-95`) only proves the *correct*
`byte_size` is stored when no caller-supplied size field exists at all (`upload_attrs()`
has no such key) -- it never proves a caller-supplied, *mismatched* size-shaped value is
ignored, which is exactly what AC3's own text asks for ("supplies a mismatched declared
size"). A mutation making `upload/2` read `Map.get(attrs, :byte_size, byte_size(raw_bytes))`
instead of always computing `byte_size(raw_bytes)` passed all 15 pre-existing tests
unnoticed (verified — see §2 mutation 2 below).

* New test: uploads 42 bytes with `attrs` deliberately carrying an extra
  `byte_size: 999_999` key smuggled into the attrs map, asserts the stored
  `attachment.byte_size == 42` (not `999_999`) and the underlying
  `repository_artifacts.byte_size == 42` too.

### AC4 — upload ceiling enforcement

Existing test (`:97-107`) uploads exactly `26_214_401` bytes (one over the 25 MiB
`@max_upload_bytes` ceiling), asserts `{:error, :file_too_large}`, and asserts both
`repository_artifacts` and `instance_attachments` row counts are `0` afterward
(proving rejection happens strictly before any persistence, matching the design's
step-1-before-hashing ordering). Adequate — no gap.

### AC5 — `list/2` tenant-scoped + instance_id-filtered

Existing test (`:127-158`) uses two tenants and two `instance_id` values, checking all
three negative/positive combinations: wrong tenant returns `[]`, right tenant/wrong
instance returns `[]`, right tenant/right instance returns the one row. Adequate — no
gap.

### AC6 — cursor pagination, no repeat/skip

Existing test (`:160-191`) uploads 5 rows, walks a `page_size: 2` first page and second
page via `next_cursor`, asserts each page has exactly 2 items and the two id sets are
disjoint. Adequate — no gap (a 3rd page / full-union check would be marginally
stronger, matching `dlq_test.exs`'s idiom, but the disjointness check already catches
the dominant regression class: a dropped tie-breaker producing a repeated boundary id).

### AC7 — `delete/2` metadata-only-delete

Existing test (`:206-232`) uploads two attachments sharing one hash under the same
`instance_id`, deletes one, asserts `get/2` on the deleted id returns `:not_found`
while the sibling attachment and the shared `repository_artifacts` row (row count `1`)
both survive. Adequate — no gap.

### AC8 — moduledoc dedup-boundary/no-canonicalisation statement + cross-tenant demonstration

Two existing tests cover this: the moduledoc-content test (`:274-286`, string-matches
`"Decision B"`, `"never one shared row"`, `"No canonicalisation is applied..."`,
`"deliberately deferred follow-up"` against the real compiled moduledoc via
`Code.fetch_docs/1`) and the cross-tenant dedup test (`:246-271`, two tenants upload
byte-identical bytes, each tenant's own schema independently holds exactly one
`repository_artifacts` row with the real content, `content_hash` equal across tenants
but never a shared physical row). Adequate — no gap.

### AC9 — content-scanning deferral named in moduledoc

Covered by the same moduledoc-content test above (`assert normalized =~ "deliberately
deferred follow-up"`). Adequate — no gap.

### AC10 — no route/controller file

Verified two independent ways, matching this project's established AC6-shape idiom
(`dlq_test.exs`'s own precedent): (a) the existing structural test
(`:288-298`) globs `lib/letflow/routers/**/*.ex` and asserts none references
`Letflow.Repository.Attachments`; (b) `git status --porcelain` against the real working
tree for this run confirms zero router/controller/plug files were touched by this
requirement's changes at all (only `repository.ex`, `repository/artifact.ex`,
`repository/attachment.ex`, `repository/attachments.ex`, `tenant_provisioning.ex`, two
migrations, and test/support files). Adequate — no gap.

### AC11 — `mix test`/`mix compile --warnings-as-errors` pass

Not a test-file criterion — verified directly:

## 2. Mutation-testing discipline (performed, not merely claimed)

Per `docs/agents/workflows/WF-02_requirement_implementation.md` Step 3, each mutation
below was applied to the real shipped `lib/letflow/repository/attachments.ex` (and, for
mutation 6, the real shipped migration), confirmed against the suite state at the time,
then reverted with a direct re-read / `git status --porcelain` confirming a clean
revert:

1. **AC4 (size-ceiling comparison operator):** `measured_byte_size > @max_upload_bytes`
   flipped to `<`. Caught: `Result: 4/15 passed` (11 failures — every small-file upload
   now rejected). Reverted, confirmed via grep of the operator back to `>`.
2. **AC3 (byte_size trust):** `measured_byte_size = byte_size(raw_bytes)` changed to
   `measured_byte_size = Map.get(attrs, :byte_size, byte_size(raw_bytes))`. **Not
   caught by the pre-existing 15 tests** (`Result: 15 passed` — a real gap, since no
   existing fixture ever supplies a `:byte_size` key). Closed by the new AC3 test
   above; re-applied the same mutation after adding it and confirmed the new test now
   fails (`Result: 17/18 passed`, the new test named explicitly in the failure list).
   Reverted, confirmed clean.
3. **AC5 (tenant-scoping in `list/2`):** `Repo.all(query, prefix: prefix)` changed to
   `Repo.all(query)` (drops the tenant-scoping option — Ecto defaults to the `public`
   schema). Caught: `Result: 13/15 passed` (the AC5 tenant-scoping test and the AC6
   pagination test both failed). Reverted, confirmed clean.
4. **AC7 (delete/2 metadata-only guarantee):** `delete/2` changed to additionally
   attempt `Repo.delete_all` against `Letflow.Repository.Artifact` for the now-orphaned
   `content_hash` after removing the `instance_attachments` row. Caught: `Result:
   13/15 passed` — the AC7 test itself failed with `Postgrex.Error ... repository_artifacts
   is immutable` (REQ-202's own DB-level `BEFORE DELETE` trigger rejected the attempt,
   demonstrating the defense-in-depth the design doc names at §4.5/§6 is real, not
   theoretical). Reverted, confirmed clean.
5. **AC2/AC8 (no-canonicalisation guarantee):** `upload/2` changed to run `raw_bytes`
   through `Letflow.Repository.Canonicaliser.canonicalize_content/2` before hashing
   (falling back to raw bytes on `{:error, _}`), instead of hashing unconditionally.
   Caught: `Result: 14/15 passed` — the existing "does not canonicalise... even when
   content_type is application/json" test failed. Reverted, confirmed clean.
6. **AC1 (migration NOT NULL constraint):** `add :instance_id, :binary_id, null: false`
   changed to `null: true` in
   `priv/repo/migrations/20260901000002_create_instance_attachments.exs`. **Not caught
   by the pre-existing 15 tests** (a real gap, since no existing test inspects the
   column's nullability or attempts a raw insert omitting `instance_id`). Closed by the
   two new AC1 tests above; re-applied the same migration mutation after adding them
   and confirmed both new tests now fail (`Result: 16/18 passed`, both new AC1 tests
   named in the failure list). Reverted, confirmed clean.

All six mutations, plus both revert confirmations, were run against a real Postgres
instance via `mix test` — no mocked database, per DIRECTIVE T-1.

**One flake observed and diagnosed, not a leftover mutation:** immediately after
reverting mutation 2's second application, one full-suite run reported `14/15 passed`
with no failure detail printed (a `--seed 0` rerun and the file's actual source,
re-read and confirmed byte-identical to the pre-mutation version, both showed no
regression); two immediately subsequent runs both reported `15 passed` cleanly. Recorded
here rather than silently discarded, per this project's own evidence discipline, though
it does not indicate a real defect — it is consistent with this suite's known
Windows-Postgres transient-connection flakiness class documented elsewhere in this
project's `core-directives.md`.
