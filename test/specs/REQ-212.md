# Test Spec: REQ-212 — Instance-attachment route surface

**Requirement:** REQ-212 (`docs/requirements.yaml`, stage S6) — route layer atop
REQ-211's `Letflow.Repository.Attachments` core: `POST`/`GET /instances/:id/attachments`
and `GET`/`DELETE /instances/:id/attachments/:attachment_id`.

**Test tier:** unit+integration (real Postgres tenant schema, real `Plug.Parsers`
multipart parse, direct `Plug.Router` dispatch — no mocked DB, no mocked HTTP layer,
per `docs/guides/test_developer_guide.md` DIRECTIVE T-1/T-2).

**Test file:** `test/letflow/routers/req212_attachments_routes_test.exs` (written by
ELIXIR-DEV at Step 2a as sanity coverage; reviewed and extended by TEST-DESIGNER at
Step 3 — see "Gap-check outcome" below).

## Test cases

1. **AC1** — `describe "AC1: POST /instances/:id/attachments"`, test "accepts a real
   multipart upload and returns 201 with the documented shape, no content_hash". Proves
   the 2xx response body carries `id`, `file_name`, `content_type`, `byte_size`,
   `created_at` (plus `instance_id`/`uploaded_by`/`description`) and never
   `content_hash`, and that the row is actually persisted (queried back via
   `Attachments.get/2`). A second test ("a multipart request with no file part returns
   422, not 500") proves the missing-file branch is mapped, not a crash.

2. **AC2** — `describe "AC2: GET /instances/:id/attachments"`, test "returns
   {items, next_cursor} and honors instance-scoping". Proves the response has exactly
   the two keys `items`/`next_cursor` (not a third `count` key, unlike this router's
   other list routes), and that an attachment uploaded to instance Y is absent from a
   list call scoped to instance X even within the same tenant.

3. **AC3** — `describe "AC3: GET /instances/:id/attachments/:attachment_id returns raw
   bytes"`. Proves `conn.resp_body` is byte-for-byte identical to the uploaded content,
   `Content-Type` matches the stored `content_type`, and `Content-Disposition` carries
   the stored `file_name`.

4. **AC4** — `describe "AC4: permission gating -- 403 for a caller with no relevant
   permission"`, four tests, one per route: `POST` (`TASK_WORKER` → 403), `GET` list
   (`AGENT_RUNNER` → 403), `GET` content (`AGENT_RUNNER` → 403), `DELETE`
   (`PROCESS_DESIGNER`, which holds `AttachmentsRead` but not `AttachmentsManage` → 403,
   plus a no-state-change assertion). This exists because AC4's own text requires "one
   explicit test per route," not one combined test — each of the 4 routes has its own
   dedicated case, not a shared parametrized loop that could silently drop a route.

5. **AC5** — `describe "AC5: cross-tenant -> 404, never 403"`, two tests: one covering
   both the attachment-id case (GET content, DELETE against a real attachment belonging
   to another tenant → 404, plus byte-identical response body to a genuinely
   nonexistent id, proving INV-5's no-distinguishing-detail rule) and the instance-id
   case (a real instance id belonging to another tenant → list returns an empty page,
   never that tenant's rows).

6. **AC6** — `describe "AC6: cross-instance, same tenant -> 404"`. Proves an attachment
   that is real and tenant-correct but named via the wrong `:id` path segment 404s for
   both GET content and DELETE, that DELETE against the wrong instance_id does not
   delete the row, and that the same attachment fetched via its real instance_id still
   200s — distinguishing this from the tenant-scoping case in AC5 (a different failure
   mode being asserted, not the same check restated).

7. **AC7** — `describe "AC7: DELETE against an already-deleted or nonexistent
   attachment_id"`. Two tests: DELETE twice against the same id (204 then 404, not a
   duplicate 204), and DELETE against a UUID that never existed (404).

8. **AC8** — `describe "AC8: moduledoc states the required content"`. Fetches
   `Letflow.Routers.Instances`'s compiled moduledoc via `Code.fetch_docs/1` and asserts
   it contains the three required statements verbatim in substance: no existing
   `web/`/R-Co contract, the content-vs-metadata distinction, and that `content_hash` is
   never surfaced.

9. **AC9** — verified by running `mix test test/letflow/routers/req212_attachments_routes_test.exs`
   and `mix compile --warnings-as-errors` directly (see "Verification run" below), not
   by a test case in this file.

## Gap-check outcome (TEST-DESIGNER, WF-02 Step 3)

Cross-checked all 9 ACs against ELIXIR-DEV's 15 sanity tests one at a time. All 9 had a
real, non-vacuous demonstrating test already. One gap was found via mutation testing
(see below), not via the AC cross-check itself, and closed by adding a 16th test.

### Mutation-testing pass

Five targeted mutations were applied to `lib/letflow/routers/instances.ex` and
`lib/letflow/repository/attachments.ex`, one at a time, each run against the full
16-test (at the time of testing, 15 pre-fix) file, then reverted and confirmed via
`git status --porcelain` / grep for the mutation's own marker text:

| # | Mutation | Result (pre-fix, 15 tests) | Caught by |
|---|---|---|---|
| 1 | Removed the cross-instance-same-tenant equality check (`instance_id: ^instance_id` pin) from `fetch_scoped_attachment_content/3`'s GET-content path | 14/15 — **caught** | AC6 test |
| 2 | Hardcoded `Content-Type` to `application/octet-stream` instead of `attachment.content_type` in `send_attachment_content/3` | 14/15 — **caught** | AC3 test |
| 3 | Changed the DELETE route's policy key from `:AttachmentsManage` to `:AttachmentsRead` | 14/15 — **caught** | AC4 DELETE test (`PROCESS_DESIGNER` holds `AttachmentsRead`, so 403 becomes 204/404) |
| 4 | Disabled `upload/2`'s own `@max_upload_bytes` size guard (`if false do {:error, :file_too_large} else ...`) in `Letflow.Repository.Attachments` | **15/15 — survived** | Nothing — gap |
| 5 | Added `"content_hash" => Base.encode16(attachment.content_hash)` to `attachment_json/1`'s allowlist | 13/15 — **caught** | AC1 and AC2 tests' `refute Map.has_key?(resp/item, "content_hash")` |

**Mutation 4 is the one real gap.** The existing "multipart size ceiling" test only
proves `Plug.Parsers`'s own `:length` option rejects an oversized body — it always
intercepts before `Attachments.upload/2` is ever called, so `upload/2`'s own
`@max_upload_bytes` check (REQ-211's authoritative ceiling, and the route design's own
documented "defense in depth" layer for exactly the case where the `Plug.Parsers`
ceiling is ever misconfigured or bypassed) was never independently exercised through
this route. Closed by adding a 16th test, "an oversized upload that reaches upload/2
directly (Plug.Parsers bypassed) is still rejected via upload/2's own
@max_upload_bytes check, 413" — this test constructs a conn with `body_params`
containing an oversized `%Plug.Upload{}` set directly (bypassing `Plug.Parsers`
entirely, the same class of gap a future parser change or an atypical encoding could
open), so the *only* thing that can still reject the request is `upload/2`'s own guard.
Re-ran mutation 4 against the 16-test file: 15/16 — now caught. Reverted, confirmed via
`git status --porcelain` / grep for `if false` (zero hits) and a clean
`mix compile --warnings-as-errors`.

Every mutation was reverted after testing and confirmed clean before moving to the
next.
