acceptance criterion, matching `Letflow.Scheduler`'s own equivalent test file's shape.

**Revision note (this pass, queue task 415 continuation).** The previous revision of this
spec (see git history) described a BLOCKED pre-fix state: no injectable transport/resolver
seam existed, so AC1/AC2's DNS-rebinding case/AC4/half of AC5 could not be tested against
real transport outcomes, and a real `:catalog_service`-routing defect existed. Both gaps have
since been closed in shipped code:

  (`lib/letflow/engine/service_task_dispatcher.ex:328-344`), plus a
  `:service_task_ssrf_validation_enabled` test-only bypass flag (mirroring `Letflow.Webhooks`'
  own `:webhook_ssrf_validation_enabled`) letting a real local `Letflow.WebhookTestServer`
  produce genuine `:advance`/retriable outcomes.
- `do_attempt_dispatch/2` now actually branches on `config.route_kind`, routing
  `:catalog_service` to `catalog_lookup_stub/2` and never to `http_transport/3,4` — proven
  structurally (a live local listener that never receives a connection).

This revision reflects the current, closed state of every acceptance criterion below. Only
one real gap remained by TEST-DESIGN-VALIDATOR's last review: AC2's own explicit

## Acceptance criteria → test cases

1. **A synthetic `:inline_url` row, claimed by `poll_and_dispatch/1`, results in exactly
   one `:httpc.request/4` call and correctly classifies a 2xx JSON-object response as
   `:advance` carrying the decoded body.**

   Covered: `describe "genuine :advance and genuine retriable outcomes via the
   :service_task_ssrf_validation_enabled test seam"`, test "a real 2xx JSON response from a
   real local server advances the row to status advanced" — a real
   `Letflow.WebhookTestServer` returns `{"result":"ok"}`, `attempt_dispatch/2` is called end
   to end (not just `http_transport/3` in isolation), and the row is read back from Postgres
   (`status == "advanced"`, `dispatched_at != nil`), not just the in-memory return value.

2. **A row resolving to a blocked SSRF range (127.0.0.1, 169.254.169.254, DNS-rebinding)
   is rejected by `UrlValidator.validate/2` BEFORE any `:httpc.request/4` call, producing
   `:give_up`.**

   Covered for all three cases:
   - IP literals: `describe "http_transport/3 -- SSRF gate"` — 127.0.0.1,
     169.254.169.254, a non-https scheme, and `classify_failure_kind/1`'s own mapping of the
     block to `:request_build_error`/non-retriable (4 tests), plus
     `describe "attempt_dispatch/2 -- SSRF-blocked URL gives up immediately, never retries"`'s
     first test (the full poll-claim-decide path).
   - **DNS-rebinding (closed this pass):** `describe "http_transport/4 -- DNS rebinding"`
     (2 tests, `test/letflow/engine/service_task_dispatcher_test.exs:470-532`), mirroring
     `url_validator_test.exs`'s own "hostname resolving to 169.254.169.254 at validation
     time is rejected (DNS rebinding)" case:
     - "hostname resolving to 169.254.169.254 at dispatch time is rejected before any HTTP
       call (DNS rebinding)" — calls `http_transport/4` directly with an injected
       `dns_resolver` that maps an arbitrary hostname (`example.com`) to
       `{169, 254, 169, 254}`, asserting `{:request_build_error, :target_url_not_allowed}`.
       This exercises the resolver-consulting path specifically (`example.com` is not an IP
       literal, so `UrlValidator.check_host/2` must call the injected resolver rather than
       short-circuiting through `check_ip_literal/1`) — proving the rebinding check itself,
       not merely a static blocklist match on the literal URL string.
     - "hostname reachable via the real resolver is still rejected once the injected
       resolver reports 169.254.169.254 (listener never connects)" — the structural proof,
       same technique as the `:catalog_service`-routing block: the dispatch URL's host is
       `localhost`, which the OS's real resolver (what `:gen_tcp`/`:httpc` would use if the
       gate were ever bypassed) resolves to `127.0.0.1`, the real address of a live local
       `Letflow.WebhookTestServer`. A genuine connection WOULD succeed here if
       `http_transport/4` fell through to `do_http_transport/3` — but the *injected*
       resolver passed to `UrlValidator.validate/2` is what this function actually consults,
       and it reports the metadata IP instead. `refute_receive
       {:webhook_test_server_request, _}, 200` proves no connection was ever attempted,
       closing the same "outcome-shape-only" gap the `:catalog_service` block's own comment
       describes.

3. **A `:catalog_service` row is rejected with a `:not_registered`-shaped `:give_up`
   outcome regardless of `service_id`, moduledoc states why.**

   Covered: `describe "route_kind: :catalog_service is routed to catalog_lookup_stub/2,
   never http_transport/3"` — two tests. The first is the structural proof: with the SSRF
   gate bypassed (`:service_task_ssrf_validation_enabled` set to `false`) and the row's
   `rendered_url` pointed at a real, live local `Letflow.WebhookTestServer`, the dispatch
   still gives up with `:request_build_error` and `refute_receive
   {:webhook_test_server_request, _}, 200` proves the listener never received a connection —
   i.e. `:catalog_service` truly never reaches `http_transport/3,4` at all, not merely that
   the SSRF gate would have blocked it anyway. The second proves the give-up is immediate and
   non-retrying even with an SSRF-*allowed* `rendered_url` the module never reads.
   `catalog_lookup_stub/2` itself is additionally unit-tested in isolation
   (`describe "catalog_lookup_stub/2"`).

4. **A retriable failure (`:timeout`, `:network`, `:rate_limited_429`) below `retry_limit`
   advances `next_attempt_at` per `compute_service_task_backoff_ms/3` and increments
   `attempt_index`, in the SAME transaction as the claim.**

   Covered: `describe "genuine :advance and genuine retriable outcomes via the
   :service_task_ssrf_validation_enabled test seam"`, test "a connection-refused failure
   reschedules with next_attempt_at advanced via real backoff, attempt_index incremented" —
   uses `Letflow.WebhookTestServer.refused_url/0` for a genuine `ECONNREFUSED`-shaped
   `:network` failure, asserts the row read back from Postgres has `attempt_index == 1`,
   `last_failure_kind == "network"`, and `next_attempt_at` matching
   `compute_service_task_backoff_ms/3`'s own computed delay within a generous jitter
   tolerance (real clock reads either side of real I/O, not a flake-prone exact-equality
   assertion).

5. **A non-retriable failure, or a retriable failure whose `attempt_index` has reached
   `retry_limit`, produces `:give_up` carrying `build_service_task_give_up_error_attrs/1`'s
   exact shape; this module never calls `set_instance_error/2`.**

   Both halves covered:
   - Non-retriable (`:request_build_error`, from an SSRF block or a malformed
     `route_kind`/`method`): `describe "attempt_dispatch/2 -- SSRF-blocked URL gives up
     immediately, never retries"` asserts every field of `error_attrs` (`instance_id`,
     `error_type`, `affected`, `idempotency_key`, `variables`, `details.last_failure_kind`)
     plus the row's own `status`/`last_failure_kind`/`dispatched_at` read back from the
     database.
   - Retriable exhausted at `retry_limit`: `describe "genuine :advance and genuine
     retriable outcomes..."`, test "retry_limit exhausted after repeated connection-refused
     failures gives up with last_failure_kind network" — `retry_limit: 0` against
     `refused_url/0` gives up immediately with `error_attrs.details.retry_limit == 0` and
     `last_failure_kind == "network"`.
   - Never-calls-`set_instance_error/2`: covered by a grep-based source test (checks
     literal call syntax, `"set_instance_error("`, so the moduledoc's own prose mentioning
     the function by name cannot false-positive it).

6. **`Letflow.Engine.ServiceTaskDispatcher.Poller` is its own supervision-tree entry,
   distinct from and alongside `Letflow.Scheduler.Poller`, with its own configurable poll
   interval.**

   Covered via `describe "boot gating"` (5 tests total): the `config/test.exs` flag value
   and `Process.whereis/1 == nil` under test config, plus three tests proving the
   real-environment default (`true`) is genuinely reachable outside test config —
   `config/dev.exs`/`config/prod.exs` read directly via `Config.Reader` (independent of
   `MIX_ENV`) proving neither overrides the flag to `false`; a source-structure test
   confirming `service_task_dispatcher_children()` is appended as its own, separate call
   alongside (not folded into) `scheduler_children()`; and the exact
   `{Letflow.Engine.ServiceTaskDispatcher.Poller, []}` child spec `application.ex` uses
   started under an isolated, test-owned throwaway `Supervisor`, proving it is a real,
   valid, independently-startable child spec, not just source text.

7. **A dispatch row belonging to a non-ACTIVE instance is skipped at claim time, never
   produces `:httpc.request/4`.**

   Covered: `describe "claim_due_dispatch_ids/2"` — one test per non-active status
   (`:cancelled`, `:completed`, `:error`) plus the positive `:active` case, plus
   `next_attempt_at`-in-future and non-`"pending"`-status exclusions, plus a cross-tenant
   isolation test using two independently-provisioned tenant schemas asserting neither
   schema's `claim_due_dispatch_ids/2` call ever returns the other's row id.

8. **SECURITY-REVIEWER sign-off recorded, confirming every dispatch path (both
   `route_kind` values) gates via `UrlValidator.validate/2` before `:httpc.request/4`, per
   INV-9's own checklist item 3.**

   Process artifact (handoff record), not a test-code concern — out of this file's scope.
   The AC3 structural test above independently corroborates the sign-off's claim in code: a
   `:catalog_service` row genuinely never reaches the gated transport at all (a stronger
   property than merely "the gate would have blocked it").

9. **`mix test` and `mix compile --warnings-as-errors` both pass with real output
   quoted.**

   Verified via `mix letflow.check.test` (forces a fresh warnings-as-errors recompile,
   catches a dead-default-argument class of bug a bare `mix test <file>` run can miss — see
   this role's own instructions, ISS-0069) and a full-suite `mix test` run. Both quoted in
   the handoff. One unrelated pre-existing failure (`Letflow.ServiceCatalogTest`, REQ-192
   pagination) was observed and structurally cleared — see handoff report; not attributable
   to this file's changes (neither `lib/letflow/service_catalog.ex` nor
   `test/letflow/service_catalog_test.exs` appear anywhere in this change's diff).
