# Test Spec: REQ-215 — SERVICE_TASK engine wiring (closes ISS-0411 part 2)

**Requirement:** REQ-215 — verbatim acceptance criteria from
`handoffs/WF02-REQ215-20260903/step-00-git-setup.json`:

1. AC1: a definition containing a SERVICE_TASK node whose `route_kind` is
   `inline_url`, dispatched against a real (test-server) HTTPS-shaped
   endpoint returning a 2xx JSON object, starts an instance whose token
   reaches that node, parks (no
   `{:error, {:node_type_not_yet_implemented, :SERVICE_TASK, _}}`), and is
   later advanced past the node once REQ-214's dispatcher resolves it — an
   end-to-end test replacing what all three of `req206_swiftroute_test.exs`,
   `req207_vortex_test.exs`, and `req208_meridian_test.exs` currently elide.
2. AC2: `req208_meridian_test.exs`'s committee-vote/quorum-2-of-3/
   disbursement paths (previously unreached) are reached and pass end to
   end.
3. AC3: the SERVICE_TASK dispatch row and its state-transition event are
   written in ONE transaction — a test that forces the event append to fail
   leaves no `service_task_dispatches` row behind.
4. AC4: a URL template that renders to an empty string is rejected at
   activation via `build_empty_url_error_attrs/1` and routes to
   `Letflow.Engine.set_instance_error/2`'s ERROR path rather than ever
   creating a dispatch row.
5. AC5: cancelling an instance with a still-pending `service_task_dispatches`
   row marks that row cancelled (in practice: `status: "given_up"` +
   `last_failure_kind: "instance_cancelled"`, the verified schema-shape-forced
   decision the design doc records — no `"cancelled"` status value exists in
   this table's own domain) in the same transaction as the instance's own
   status flip, and REQ-214's dispatcher never dispatches a cancelled row.
6. AC6: `lib/letflow/engine/transition.ex` contains no `:httpc`/HTTPoison/
   Req/File call after this change, and its moduledoc names the new
   `pending_event()` variant and which `InstanceState` field carries the
   parked token.
7. AC7: `docs/migration/stage-7-simulation-uat-parity.md`'s REQ-210 REVIEWER
   sign-off entry no longer attributes the Meridian quorum/disbursement gap
   to `join_counters`, and instead correctly names this requirement's own
   fix.
8. AC8: `mix test` and `mix compile --warnings-as-errors` both pass with real
   output quoted — TEST-RUNNER's own responsibility next, not a test this
   suite writes, but every new test here must not break the 3119/3119
   baseline.

Plus REVIEWER/SECURITY-REVIEWER-traced findings the handoff asks for real
regression coverage on (not separately numbered acceptance criteria, but
treated with equal rigor below): the `:advance` outcome's variable-merge
behavior, the `:give_up` outcome's benign-race folding
(`{:instance_terminal, _}` AND `{:instance_already_error, _}`), and the
minimal `{{variables.KEY}}` renderer's basic-substitution/no-worse-than-
substitution behavior.

**Test tier:** unit-adjacent + integration (real Postgres via
`Letflow.DataCase` / `Letflow.TenantFixture`, DIRECTIVE T-1 — no mocked
database), plus one real-HTTP end-to-end tier using
`Letflow.WebhookTestServer` (the same real local `:gen_tcp` listener
`test/letflow/engine/service_task_dispatcher_test.exs` already established
for REQ-214's own genuine-outcome coverage). The pure-kernel half of AC1/AC6
(`dispatch_service_task/3`'s own park-and-emit behavior, not caught by the
catch-all) is already covered by `test/letflow/engine/transition_test.exs`'s
own `"transition/3 -- :SERVICE_TASK entry"` describe block (ELIXIR-DEV's
mechanical update for this requirement) and is **not** repeated here — this
suite is the DB-level integration half: real `service_task_dispatches` rows,
real `Ecto.Multi` atomicity, real activation-time INSERT, real re-entry via
`advance_after_service_task_outcome/4`, real cancellation, and one genuine
end-to-end Meridian scenario run.

No property test: this requirement adds no new closed state/transition table
of its own beyond `service_task_dispatches.status`'s already-REQ-214-tested
3-value set (`pending`/`advanced`/`given_up`, exercised by
`service_task_dispatcher_test.exs`'s own migration/schema sanity tests) — the
scenarios below are a small enough closed set of hop-chain shapes
(create-time, mid-hop-chain, cancellation, empty-URL) that per-case examples
give equivalent coverage to a generator here, matching REQ-187's own
precedent for the structurally identical TIMER wiring requirement.

## Implementation defect found (reported, then fixed)

**`Letflow.Engine.advance_after_service_task_outcome/4`'s `:advance` clause
(`lib/letflow/engine.ex:2478-2485`) used to double-wrap its own success
result. Status: FIXED by ELIXIR-DEV, verified by this suite.**

- Its own `@spec` (`engine.ex:2466-2477`) promises `{:ok, :advanced}`.
- The originally observed return value was `{:ok, {:ok, :advanced}}`.
- Root cause, traced directly: `do_persist_service_task_advance/10`'s own
  success clause (formerly `engine.ex:2750`) returned
  `{:ok, {:ok, :advanced}}` where `{:ok, :advanced}` alone would match the
  `@spec` (compare `handle_success/3`'s TIMER-side analogue, which returns a
  single-wrapped value at the equivalent point). That value flowed up
  through `persist_service_task_advance/10` and
  `advance_service_task_dispatch/4` UNCHANGED.
  `advance_after_service_task_outcome/4`'s own `:advance` clause then
  wrapped it AGAIN: `repo.transaction(fn -> case ... {:ok, result} -> result
  end)` unwraps ONE layer (`result` becomes `{:ok, :advanced}`), then
  `repo.transaction/1` itself wraps the anonymous function's return value in
  a SECOND `{:ok, _}` envelope.
- **Downstream consequence (originally proven by test 22, now the
  regression guard against recurrence):**
  `ServiceTaskDispatcher.poll_and_dispatch/1`'s own
  `call_advance_after_service_task_outcome/3`
  (`service_task_dispatcher.ex:589-601`) pattern-matches on exactly
  `{:ok, :advanced}`/`{:ok, :error_set}`/`{:ok, :already_final}` — neither
  matched `{:ok, {:ok, :advanced}}` — so a REAL `:advance` outcome used to
  CRASH `poll_and_dispatch/1` with a `CaseClauseError`. This was AC1's own
  literal, real end-to-end path ("later advanced past the node once REQ-214's
  dispatcher resolves it," via `poll_and_dispatch/1`) — it did not work at
  all for a genuine `:advance` outcome through the poller's own top-level
  entry point.
- **The fix, applied by ELIXIR-DEV:** `do_persist_service_task_advance/10`'s
  success clause (`engine.ex:2749-2752`) now reads:
  ```elixir
  case repo.transaction(multi) do
    {:ok, _changes} -> {:ok, :advanced}
    {:error, _failed_step, reason, _changes} -> {:error, reason}
  end
  ```
  returning the single-wrapped `{:ok, :advanced}` the `@spec` always
  promised.
- **Verification (this suite, post-fix):** test 22's two cases were
  rewritten from bug-documenting assertions into positive regression
  coverage — the first now calls the real `poll_and_dispatch/1` entry point
  end to end and asserts it completes without raising, correctly folding the
  resolved dispatch into `:advanced` (`%{claimed: 1, advanced: 1, retried:
  0, given_up: 0}`) and leaving the instance `:completed`; the second
  asserts `advance_after_service_task_outcome/4`'s return value now equals
  `{:ok, :advanced}` exactly, with an explicit `refute actual == {:ok, {:ok,
  :advanced}}` as a standing regression guard should the double-wrap ever
  reappear. Every other test in this suite that had been calling
  `ServiceTaskDispatcher.attempt_dispatch/2` directly followed by
  `Engine.advance_after_service_task_outcome/4` (tests 1, 16, and the new
  AC2 Meridian test) was also updated from asserting the old
  `{:ok, {:ok, :advanced}}` shape to asserting the correct `{:ok, :advanced}`
  shape. Full suite result post-fix: `test/letflow/engine/service_task_wiring_test.exs`
  and `test/letflow/simulation/req208_meridian_test.exs` both fully green
  (26/26 in the combined run); see TEST-RUNNER's AC8 report for the
  project-wide `mix test` result.
