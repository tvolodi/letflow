# Test Spec: REQ-216 — Admission-control core (`Letflow.Admission`)

**Requirement:** REQ-216 (`docs/requirements.yaml`, stage S6) — closes part 1 of
ISS-0431/GH#835: a hand-rolled, pure-BEAM global + per-tenant counting semaphore tied
to `pool_size`, implemented as `Letflow.Admission`. Core module only — no HTTP/Poller
wiring (REQ-217/218).

**Test tier:** unit (pure in-memory `GenServer` state machine — no Repo call anywhere
in the module under test, confirmed by reading `lib/letflow/admission.ex` in full, so
no `Letflow.DataCase`/tenant fixture is used, per `docs/guides/test_developer_guide.md`).

**Test file:** `test/letflow/admission_test.exs` (written by ELIXIR-DEV at Step 2,
15 tests, with a real mutation-testing pass already performed and reported in
`handoffs/WF02-REQ216-20260902/step-02-elixir-dev.json`; independently re-verified by
REVIEWER at Step 2d, then independently re-verified again by TEST-DESIGNER at this
step — see "Gap-check outcome" below).

## Test cases

1. **AC1** (`try_acquire(:global)` admits up to `pool_size - reserved_headroom`,
   rejects beyond, both config-driven, cap changes with a `pool_size` override) —
   `describe "AC1: global cap = pool_size - reserved_headroom"`, 3 tests: admits
   exactly the computed cap then rejects; the cap visibly changes between two
   differently-configured instances with no code edit (`pool_size: 3` → cap 1,
   `pool_size: 10` → cap 8); `reserved_headroom` is independently config-driven too
   (`pool_size: 10, reserved_headroom: 8` → cap 2).

2. **AC2** (per-tenant cap enforced independently — A's exhaustion doesn't block B) —
   `describe "AC2: per-tenant caps are independent across tenants"`, one test: tenant A
   exhausts its own share (5 of `floor(10/2)=5`) and is rejected on its 6th attempt,
   while tenant B — tracked from the start, already holding 1 of its own 5 — still
   succeeds on a simultaneous further acquisition.

3. **AC3** (a `{:tenant, _}` acquisition that passes the per-tenant gate is still
   rejected once the GLOBAL cap alone is exhausted, even for a fresh tenant with zero
   per-tenant usage of its own) — `describe "AC3: tenant acquisition also gated by the
   global cap"`, one test: exhausts the global cap (3/3) via `:global` acquisitions
   alone, then asserts a brand-new tenant's very first `{:tenant, _}` attempt —
   `in_use: 0` against its own generous per-tenant cap — is still `{:error, :capacity}`.
   This is the exact "fresh tenant, zero own usage, still rejected because of global
   exhaustion" scenario the requirement's own worked example names; confirmed this is a
   single dedicated test for that composed scenario, not two separate tests
   (tenant-cap-alone, global-cap-alone) that would leave the *composition* itself
   unverified.

4. **AC4** (`release/1` frees exactly one unit of both the global AND, for a
   `{:tenant, _}` ref, the per-tenant budget) — `describe "AC4: release frees exactly
   the budget(s) it was acquired against"`, 3 tests: a `:global` ref's release frees
   exactly one further `:global` slot, not more; a `{:tenant, _}` ref's release frees
   both that tenant's own unit AND the shared global unit (verified by re-acquiring
   against *either* selector afterward, each still bounded to exactly one success);
   `release/1` is idempotent on a ref already released (second `release/1` call on the
   same ref is `:ok`, not a raise) and on a hand-constructed, never-issued ref (also
   `:ok`) — this is the idempotent-release-on-unknown-ref behavior design §2.1
   documents, confirmed present as its own dedicated test, not folded silently into
   another assertion.

5. **AC5** (per-tenant cap = `floor(global_cap / tracked_tenant_count)`, floored at 1;
   `10/3→3`, `2/5→1`) — `describe "AC5: per-tenant cap is an equal fair-share split
   with a floor of 1"`, 3 tests: the requirement's own literal `floor(10/3)=3` example
   (not merely a structurally similar number); the floor-of-1 example with 5 tenants
   against a global cap chosen large enough (9) that the global cap is provably not the
   bottleneck for that assertion; and — the design's own reworked §2.2 invariant, the
   one this design doc required a rework to state explicitly — a dedicated retroactivity
   test: tenant A alone acquires 3 refs under a 1-tenant-tracked split (cap 10, so A's
   cap is `floor(10/1)=10`), two more tenants then each make their own first attempt
   (shrinking A's *next* computed cap to `floor(10/3)=3`, exactly equal to A's current
   `in_use`), A's next attempt is correctly rejected, and — the actual invariant under
   test — **all three of A's already-held refs still `release/1` cleanly** with no
   cap-dependent rejection on release. This is not a generic per-tenant-cap test
   restated; it is the specific "cap shrinks under a live holder, existing refs stay
   valid" scenario, confirmed by direct read of `lib/letflow/admission.ex`'s
   `{:release, ...}` clause (lines 278–300): it does `Map.pop(state.refs, id)` and
   decrements counters, never calling `per_tenant_cap/1` or consulting the current
   tracked-tenant count at all — the release path is structurally incapable of
   rejecting on a shrunk cap, and this test is what actually exercises that path under
   the shrink condition rather than merely trusting the code read.

6. **AC6** (`Letflow.Admission` present in `Letflow.Application`'s supervision tree;
   moduledoc states its ordering-dependency stance) — `describe "AC6: present in the
   live supervision tree, no ordering dependency documented"`, 3 tests: the live
   `Supervisor.which_children(Letflow.Supervisor)` list actually contains a running,
   alive `Letflow.Admission` child (not just a source-code grep of `application.ex`);
   the real, config-derived default instance (started via the application's own
   supervision tree, `server` defaulted to `__MODULE__`) is usable end-to-end
   (`try_acquire/0` + `release/1` against it); the compiled moduledoc text contains the
   literal phrase "ordering dependency".

7. **AC7** (`mix test` and `mix compile --warnings-as-errors` both pass) — verified by
   directly running both commands (see "Verification run" below), not by an in-suite
   assertion.

Additionally, one test outside the AC1–AC7 breakdown: `describe "atomicity (AC3
mutation-testing target)"`, "a rejected `{:tenant, _}` acquisition mutates neither
counter" — reads `:sys.get_state/1` before and after a rejected attempt and asserts
`global_in_use` is unchanged and the tenant's own `in_use` stays `0`. This exists
specifically to make ELIXIR-DEV's own atomicity claim (design §1: "zero mutation on
rejection") independently verifiable by state inspection, not just by black-box
input/output behavior, and is one of the two tests ELIXIR-DEV's own mutation-testing
pass (dropping the global half of the `{:tenant, _}` guard) reported as the tests that
actually catch that specific defect.

## Gap-check outcome (TEST-DESIGNER, WF-02 Step 3)

Cross-checked all 7 ACs (read directly from `docs/requirements.yaml`'s REQ-216 entry,
not from any paraphrase) against the 15 existing tests, one at a time — table above.
All 7 had a real, non-vacuous demonstrating test already in place. Per this step's own
task instructions, four specific risks were checked in detail, beyond the plain AC
cross-check:

- **Fair-share retroactivity invariant (design §2.2)** — genuinely exercised, not just
  a generically-similar per-tenant-cap test. See AC5's third test above and the direct
  code read of the `{:release, ...}` clause confirming the release path has no
  cap-dependent branch at all (so the test's pass is not an accident of a
  coincidentally-permissive implementation — the code structurally cannot fail this
  invariant, and the test independently confirms the observable behavior matches).

- **Idempotent-release-on-unknown-ref (design §2.1)** — genuinely covered: AC4's third
  test calls `release/1` twice on the same ref (second call `:ok`, not a raise) AND
  separately on a hand-constructed `%Admission.Ref{id: make_ref(), pool: :global}` that
  was never issued by `try_acquire/2` (also `:ok`).

- **Crash semantics (moduledoc's claim that a crash resets all counters to empty)** —
  judged NOT to need a dedicated test, and none was added. Reasoning: this is not one
  of REQ-216's 7 acceptance criteria (it is design doc §5 / open question OQ-3,
  explicitly left open there, not acceptance-tested here); and the claim itself —
  "a fresh `init/1` on restart starts from `global_in_use: 0, tenants: %{}, refs: %{}`"
  — is guaranteed by ordinary OTP `:one_for_one` restart semantics (a freshly-restarted
  `GenServer` always re-runs `init/1` from its start-argument, with no persisted state
  carried across the crash) plus a direct read of `init/1` itself (lines 220–231),
  which contains no external state read beyond `Application` config. Actually crashing
  a supervised `GenServer` mid-test and asserting on its post-restart state would add
  real test complexity (locating the child via `Supervisor.which_children/1`, killing
  it, waiting for the restart, re-locating the new pid) to prove a fact that is true by
  construction of `init/1` having no branches that could do otherwise — this would be
  restating the OTP contract as a test, not discriminating correct code from a real
  defect. Not added.

- **Fresh tenant / zero own usage / exhausted-global scenario (requirement's own AC3
  worked example)** — confirmed this exact composed scenario has its own dedicated
  test (AC3's test, see above), not merely two separately-passing tests
  (tenant-cap-in-isolation, global-cap-in-isolation) that would leave the *interaction*
  itself unverified. Read the test body directly to confirm it exhausts `:global`
  first via 3 plain `:global` acquisitions, then makes the tenant's FIRST-EVER attempt
  — genuinely zero prior tenant usage, not merely a low `in_use` count.

**No gap was found.** No test was added — the existing 15-test suite already provides
non-vacuous coverage of all 7 ACs plus each of the four specifically-flagged risk
areas above. This conclusion was reached by direct reading of both the requirement
text (`docs/requirements.yaml`) and the test bodies, not by accepting ELIXIR-DEV's or
REVIEWER's own summaries of their coverage at face value — independently confirmed by
re-reading `lib/letflow/admission.ex`'s actual GenServer callbacks (in particular the
`{:release, ...}` clause, which structurally cannot special-case the retroactivity
scenario, confirming the test's pass reflects the code's actual structure and not
coincidence) and cross-checking against `lib/letflow/design/req216-admission-control-core.md`
§2.2's own worked numeric example (`floor(10/3)=3`), which appears verbatim in the
test file, not merely as a structurally similar number.
