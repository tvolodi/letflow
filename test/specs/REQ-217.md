# Test Spec: REQ-217 — Wire admission control into the HTTP entry path

**Requirement:** REQ-217 (`docs/requirements.yaml`, stage S6) — closes part 2
(PRIMARY surface) of ISS-0431/GH#835: two admission gates (`:global`, mounted
first in `Letflow.Plugs.ApiPipeline`'s chain before `Plug.Parsers`, and
`:tenant`, mounted after `Letflow.Plugs.AuthPipeline` and before
`Letflow.Plugs.TenantStatus`) wired atop REQ-216's core `Letflow.Admission`
semaphore module. On `{:error, :capacity}`, the plug halts and responds via
the existing `Letflow.Api.Response.service_unavailable/2` (REQ-066) with a
config-driven `Retry-After` header. On success, both admission refs are
released exactly once via two independent, non-exclusive mechanisms
(`register_before_send/2` for non-crashing paths, `Plug.ErrorHandler` +
process-dictionary storage for a raise anywhere in the chain).

**Test tier:** mixed — `test/letflow/plugs/admission_test.exs` is plug-level
unit tests (`Letflow.Plugs.Admission.call/2` invoked directly, no full HTTP
dispatch, `async: false` since it touches the real application-supervised
`Letflow.Admission` singleton); `test/letflow/plugs/admission_pipeline_test.exs`
is full end-to-end HTTP tests dispatched through the real
`Letflow.Router.call/2` chain (`Letflow.DataCase`, `async: false`, real
provisioned tenants via `Letflow.TenantFixture`).

**Written by:** ELIXIR-DEV across two implementation passes (step-02, then
step-04's fix for SECURITY-REVIEWER's step-03 double-global-consumption
finding), each independently verified via real mutation testing by
SECURITY-REVIEWER (step-05) and REVIEWER (step-06). This spec is written by
TEST-DESIGNER (step-07) as an independent completeness audit against
REQ-217's authoritative `acceptance_criteria` list — no new test code was
required; coverage was found complete (see "Gap-check outcome" below).

## Test cases, mapped to `docs/requirements.yaml`'s REQ-217 `acceptance_criteria`

1. **AC1** ("global cap forced to 0 → every `/api/v1/*` request 503 +
   Retry-After, `Plug.Parsers` never runs, an oversized body still 503 not
   413") — `admission_pipeline_test.exs`, `describe "AC1: global cap
   exhausted..."`, 2 tests: a normal request that would otherwise pass auth
   is rejected 503 with `Retry-After: 1` before reaching auth or dispatch;
   an oversized body (over `Plug.Parsers`'s own 2 MB `length:` cap) still
   returns 503, not 413 — proving `Plug.Parsers` never ran (had it run, it
   would raise `Plug.Parsers.RequestTooLargeError` → 413 first).

2. **AC2** ("global cap open, one tenant's per-tenant cap forced to 0 → that
   tenant 503, a DIFFERENT tenant (same global cap) succeeds, both in one
   test") — `admission_pipeline_test.exs`, `describe "AC2: per-tenant cap
   exhausted for one tenant does not affect a different tenant"`, 1 test:
   tenant A's own fair share is exhausted directly against the real
   singleton; tenant A's HTTP request gets 503 with `Retry-After: 1`; tenant
   B's simultaneous HTTP request (same global cap, untouched per-tenant
   share) reaches `Letflow.Routers.Identity`'s catch-all 404 — proof it
   passed both gates.

3. **AC3** ("a successfully admitted request that completes normally
   releases both refs exactly once, verified by exhausting the cap, one
   round trip, then a subsequent request succeeds") —
   `admission_pipeline_test.exs`, `describe "AC3"`, 1 test: `global_cap == 1`
   (the design doc §10.1 rework's own re-derived minimum sufficient cap —
   see item 9 below for why 1, not 2, is now correct), two sequential real
   HTTP requests both return 404 (not 503) — only possible if request 1's
   admission refs are genuinely released before request 2 is admitted,
   since the cap has exactly one unit to give.

4. **AC4** ("a downstream handler RAISES → both refs still released, a test
   that forces a raise in a route handler, then a subsequent request still
   succeeds") — `admission_pipeline_test.exs`, `describe "AC4 (Mechanism
   A)"`, 1 test: `GET /users/not-a-uuid` raises `Ecto.Query.CastError`
   inside the matched route handler (after `:dispatch`), which
   `Plug.Router` wraps in `Plug.Conn.WrapperError` and
   `Letflow.Plugs.ApiPipeline`'s `Plug.ErrorHandler` catches; a follow-up
   request with a valid id then succeeds (200), which is only possible if
   `handle_errors/2` genuinely drained and released both admission refs —
   `global_cap == 1` leaves zero slack for a leaked ref.

5. **AC5** ("503 body matches `Response.service_unavailable/2`'s existing
   `Error.service_unavailable/1` shape exactly, per REQ-066's own
   `test/letflow/api/error_test.exs`") — `admission_test.exs`, `describe
   "AC5: 503 body shape..."`, 3 tests: the global-gate rejection asserts
   the same fields `error_test.exs`'s `assert_problem/5` helper checks for
   `service_unavailable/1` (`status == 503`, `title == "Service
   Unavailable"`, `type` ends with `/problems/service-unavailable`,
   `detail` present, `trace_id` key present) plus the `retry-after` header
   and `content-type`; a second test confirms `Retry-After` is read fresh
   from `Application.get_env(:letflow, :admission, [])[:retry_after_seconds]`
   (overridden to `7` with no other code change, header observed as `"7"`)
   rather than hardcoded; a third test confirms the tenant-gate rejection
   uses the identical shape with distinct wording and does not leak the
   tenant schema name into `detail`.

6. **AC6** ("chain order confirmed by reading `api_pipeline.ex`: global
   admission plug first, before `Plug.Parsers`; per-tenant admission plug
   after `AuthPipeline`, before `TenantStatus`") —
   `admission_pipeline_test.exs`, `describe "AC6"`, 1 test: reads the actual
   source file and asserts the byte offsets of each `plug(...)` line are in
   the required order (`global admission < Plug.Parsers < AuthPipeline <
   :release_global_admission < tenant admission < TenantStatus`) — a direct
   assertion against the real, currently-shipped file, not a restatement of
   intent.

7. **AC7** ("`mix test` and `mix compile --warnings-as-errors` both pass,
   real output quoted") — see "Verification run" below.

## Additional coverage beyond the 7 ACs (verified present, not newly added)

- **Disclosed limitation statement**: `lib/letflow/plugs/admission.ex`'s
  moduledoc states explicitly (lines 22–27) that `AuthPipeline`'s own DB
  work is covered only by the global gate, never a per-tenant one, because
  tenant identity does not exist yet at that point in the chain — matching
  the requirement's own explicit instruction to state this in the plug's
  moduledoc rather than silently omit it. `api_pipeline.ex`'s moduledoc
  repeats the same disclosure at its own admission-control section.
- **Both crash-safety mechanisms, each with a dedicated, non-overlapping
  test**: Mechanism A (`register_before_send/2`, non-crashing completion
  only) — `admission_test.exs`, `describe "Mechanism A"`, 1 test: a
  successful global admission's slot is confirmed held, then freed exactly
  when `send_resp/3` runs the registered callback. Mechanism B
  (`Plug.ErrorHandler` + process-dictionary drain, the ONLY reliable
  channel for a raise inside a plug running before `:dispatch`, where
  `conn.assigns` is not visible to `handle_errors/2`'s own pre-pipeline
  `conn` parameter) — `admission_test.exs`, `describe "Mechanism B"`, 2
  tests: the first deliberately passes a bare, pre-pipeline `conn` (not the
  conn carrying both admission-ref assigns) to `handle_errors/2` and proves
  cleanup succeeds only via the process dictionary, exactly reproducing the
  design doc's corrected pre-dispatch-raise trace; the second confirms
  `handle_errors/2` is a safe no-op when nothing was pending. The
  route-handler-raise case (AC4 above, where `conn.assigns` IS reliable
  because `Plug.Conn.WrapperError` carries the fully-downstream conn) is a
  third, genuinely distinct code path, covered separately by
  `admission_pipeline_test.exs`'s AC4 test. All three paths the design
  doc's corrected trace names are therefore independently exercised, not
  collapsed into one.
- **The §10.1 global-release fix and its own regression proof**:
  `admission_pipeline_test.exs`, `describe "REQ-217 rework..."`, 2
  dedicated tests: `global_cap == 1` now admits one full request end to end
  (would have needed `global_cap == 2` under the pre-fix double-consumption
  defect — a literal re-derivation of the design doc §10.4 minimum-cap
  argument); and a second test that, after a `global_cap == 1` request
  completes, confirms the global counter is back to fully free by
  successfully acquiring and releasing one more probe unit — proving no
  more than one global unit was ever held at any instant (since holding
  two simultaneously would have made the sole in-flight request self-reject
  under a cap of 1). SECURITY-REVIEWER's step-05 handoff already
  independently reproduced the mutation (commenting out
  `plug(:release_global_admission)` → 4/8 tests in
  `admission_pipeline_test.exs` fail, all four exactly the
  `global_cap == 1`-dependent tests named above; reverting restores 8/8) —
  not re-run here since two independent parties (ELIXIR-DEV, then
  SECURITY-REVIEWER) already reproduced it and the underlying diff is
  unchanged since.
