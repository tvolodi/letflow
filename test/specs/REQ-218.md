# Test Spec: REQ-218 — Wire admission control into Poller's per-tick tenant sweep

**Requirement:** REQ-218 (`docs/requirements.yaml`, stage S6) — closes part 3
(SECONDARY surface) of ISS-0431/GH#835: each of `Letflow.Scheduler.Poller`'s
six sequential per-tenant operations (the timer poll-and-fire loop plus the
five `maybe_run_*` sweeps) acquires ONE `Letflow.Admission.try_acquire(:global)`
unit for that operation's own single Repo-touching call, and releases it via
an `after` clause guaranteeing cleanup even past the operation's own existing
`rescue`. Only `:global` is ever acquired — Poller never uses REQ-216's
per-tenant semaphore. See `lib/letflow/design/req218-poller-admission-wiring.md`
for the full design.

**Test tier:** unit — `test/letflow/scheduler/poller_test.exs`,
`Letflow.Scheduler.Poller.handle_info/2` called directly as a plain function
(existing file convention, sidesteps the documented `Ecto.Sandbox` ownership
issue for this GenServer), `Letflow.DataCase, async: false`, real
application-supervised `Letflow.Admission` singleton restarted per test via
`test/support/admission_test_helpers.ex`'s `restart_admission!/1`.

**Written by:** ELIXIR-DEV (step-02), 6 describe blocks, independently
verified via real mutation testing (two mutants: bypassing the capacity
check entirely, and moving `release/1` out of the `after` clause while
narrowing a rescue clause — both caught, both reverted and reconfirmed).
REVIEWER (step-03) independently re-verified via 3 foreground runs including
one with a fixed seed. This spec is written by TEST-DESIGNER (step-04) as an
independent completeness audit against REQ-218's authoritative
`acceptance_criteria` list. **One genuine gap was found and fixed** (see
"Gap-check outcome" below) — a 7th describe block was added.

## Test cases, mapped to `docs/requirements.yaml`'s REQ-218 `acceptance_criteria`

1. **AC1** ("global cap forced to 0 (test config override) → a tick over 3
   tenant schemas calls `poll_and_fire/1` ZERO times for any of them, no
   crash, next tick (cap restored) resumes normally — verified by a test
   asserting the mock/spy call count is exactly 0 then exactly 3") —
   `describe "REQ-218 AC1: forced-zero admission cap skips every schema;
   capacity restored resumes normally"`, 1 test. `Letflow.Admission.init/1`
   floors `global_cap` at `max(pool_size - reserved_headroom, 1)` — a
   literal `0` is never reachable, so the test drives `global_cap == 1` and
   holds the sole unit via a probe `try_acquire(:global)` BEFORE the tick,
   guaranteeing every one of that tick's own admission attempts observes
   exhaustion (the "forced-zero-for-the-whole-tick" case the AC actually
   needs). **Mock/spy substitution**: this codebase has no mocking library
   (confirmed via `mix.exs` and this test file's own established
   convention); the design doc's own §7 Q3 explicitly flags AC1's literal
   "mock/spy call count" wording as unsatisfiable here and directs
   TEST-DESIGNER to substitute an equivalent real-effect assertion. The test
   does exactly that: 3 schemas' due timers all remain `"pending"` while the
   probe is held (proving zero `poll_and_fire` calls succeeded, the same
   fact a call-count-== 0 assertion would prove), then all 3 fire on a
   second tick after the probe is released (proving the ZERO count was
   capacity-shaped, not schema-shaped, and that normal operation resumes).
   This substitution is verified sound: a spy call-count of 0 and "zero
   timers advanced past pending" are equivalent observations of the same
   fact (no `poll_and_fire` body ran) for THIS operation, since
   `poll_and_fire/1`'s only externally observable effect for a due timer is
   the timer's own status transition.

2. **AC2** ("global cap forced to admit exactly 1 concurrent unit, a tick
   still processes all 3 tenant schemas' timer poll-and-fire loop to
   completion (sequential acquire/release, not a permanent block)") —
   `describe "REQ-218 AC2: a cap of exactly 1 still drains all schemas
   sequentially within a single tick"`, 1 test: `global_cap == 1`, no probe
   held, 3 schemas' due timers all fire within one tick.

3. **AC3** ("an admission `{:error, :capacity}` for one schema's operation
   within a tick does not prevent a DIFFERENT schema's SAME operation, or
   that SAME schema's OTHER operations, from being attempted later in the
   same tick") — **two independent sub-clauses, each with its own dedicated
   test** (see "Gap-check outcome" below for why both are required):
   - *(a) different schema, same operation* — `describe "REQ-218 AC3: a
     capacity rejection for one schema/operation does not block the rest of
     the same tick"`, 1 test: a real, continuously-looping antagonist `Task`
     contends for the sole global unit against 10 schemas' own
     `poll_and_fire` admission attempts in a single tick, retried up to 5
     times until a genuine partial (not total) skip is observed — proves a
     rejection for schema A's `poll_and_fire` doesn't block schema B's own
     `poll_and_fire` later in the same tick.
   - *(b) same schema, other operations* — `describe "REQ-218 AC3
     (per-schema clause): a rejected schema's other ops still proceed"`, 1
     test (newly added by TEST-DESIGNER — see gap below): the SAME schema's
     `poll_and_fire` is DETERMINISTICALLY rejected (the test process holds
     the sole global unit before `handle_info/2` is even invoked, so the
     tick's very first admission attempt has strictly nothing else that
     could have taken or released the unit first — same-process
     happens-before ordering, no race), then a short-lived helper `Task`
     releases the unit shortly after, so that SAME schema's later retention
     sweep still runs (its old event gets archived) in the SAME tick —
     proving a rejection for schema A's `poll_and_fire` doesn't block schema
     A's OWN retention sweep later in the same tick. 12 filler schemas
     (provisioned once, reused across up to 10 retries) widen the real
     elapsed time between the target's two admission attempts enough for a
     fixed 5ms release delay to land reliably between them; see the
     in-file comment on `ac3b_attempt/3` for the full derivation, including
     why smaller/zero delays and a two-sided antagonist race were both
     tried and rejected as measurably less reliable.

4. **AC4** ("`Letflow.Admission.try_acquire({:tenant, _})` is never called
   anywhere in `lib/letflow/scheduler/poller.ex` — grep-verified") —
   `describe "REQ-218 AC4..."`, 1 test: reads the actual source file and
   asserts it contains no `{:tenant,` substring anywhere — a real,
   automated check (not merely an informal grep quoted in a handoff),
   matching this codebase's own convention of encoding such invariants as
   executable tests (`poller_test.exs`'s own pre-existing "no second
   ticker" test is the same pattern, grepping for `use GenServer`).

5. **AC5** ("an existing per-operation rescue path... still catches its own
   operation's raise with the new acquire/release wrapped around it — a
   test forcing that operation to raise still leaves the admission slot
   released (no leak) and the tick completes") — `describe "REQ-218 AC5..."`,
   1 test: a fully-provisioned, fully-migrated tenant schema minus its
   `effect_completions` table (surgical fault injection, avoids a separate,
   pre-existing, out-of-scope `poll_and_fire/1` raise-safety gap flagged by
   ELIXIR-DEV/REVIEWER for a schema missing its Postgres schema entirely) —
   `maybe_run_ordering_cycle/1`'s own `rescue _ -> :ok` catches the forced
   raise, a DIFFERENT (intact) schema's own timer still fires in the same
   tick (no total-tick poisoning), and a post-tick `try_acquire(:global)`
   still succeeds under `global_cap == 1` (proving the raised call's

## Additional invariant confirmed present (not a numbered AC, but load-bearing)

- **The `after`-based release survives the rescue path, not just the happy
  path**: AC5's test is the one that actually exercises this — it forces a
  genuine raise INSIDE the wrapped operation and confirms via a subsequent
  probe acquisition that the ref was released. A test that only ever forced
  the happy path (acquire → success → release) would leave the `after`
  clause's specific reason for existing (belt-and-suspenders release when
  the operation's own `rescue` doesn't fire, or for rows 1–2 which have no
  inner `rescue` at all) unverified. Confirmed genuinely exercised, not
  vacuous, by reading the test body directly.
- **Global-only enforcement is asserted BY A TEST, not just informally
  grepped by a prior agent**: AC4's test is a real `ExUnit` assertion over
  the actual source file content, executed on every `mix test` run — not a
  one-off grep quoted in a handoff that could silently rot if a later change
  reintroduced a `{:tenant, _}` call. Confirmed this is genuinely automated,
  not merely described as automated.

## Gap-check outcome

TEST-DESIGNER (step-04) read all 6 acceptance criteria directly from
`docs/requirements.yaml` (not paraphrased from a handoff) and cross-checked
each against ELIXIR-DEV's existing 6 describe blocks. **One genuine gap was
found**: AC3's requirement text names TWO independent sub-clauses — "a
DIFFERENT schema's SAME operation" and "that SAME schema's OTHER
operations" — but the existing AC3 test only exercised the first (10
schemas racing an antagonist for the same `poll_and_fire` operation). A
coarser, explicitly-forbidden design (one acquire/release per SCHEMA
covering all six of its operations at once, ruled out by the design doc's
own §1/§3) would still have passed every assertion in that existing test,
since it never looks at more than one operation per schema — meaning the
existing suite did not actually distinguish the shipped per-operation-call
design from that forbidden coarser one. A new test (see AC3(b) above) was
added specifically to close this: it holds one schema's `poll_and_fire`
admission deterministically rejected and confirms that SAME schema's
retention sweep still runs later in the same tick, which the coarser
forbidden design would fail (it would skip ALL six of that schema's
operations together, not just the one active when its shared ref would have
been acquired).

Two smaller, real bugs were found and fixed while building this test (see
the in-file comments on `ac3b_attempt/3` and `clear_pending_events!/1` for
the full account):
1. A first attempt-loop design let a rejected attempt's own seeded event
   stay pending and get swept up together with a LATER attempt's own event
   once retention next succeeded, inflating that later attempt's own
   archived-count delta past the expected `+1` and producing a false
   negative unrelated to the actual admission outcome. Fixed by clearing
   any leftover pending event before each attempt.
2. A first race design (a continuous antagonist contending against BOTH of
   the target schema's own admission attempts at once, mirroring AC3(a)'s
   own pattern) was empirically shown — via temporary diagnostic
   instrumentation, since removed — to be structurally biased: with a sole
   global unit, both of the target's attempts overwhelmingly land on the
   SAME side of the race together far more often than they split, so
   retrying more times did not reliably fix it. Replaced with the
   largely-deterministic hold-before-tick / short-delayed-release design
   described in AC3(b) above, which removes the race from the "is
   `poll_and_fire` rejected" side entirely and leaves only a comfortably
   one-sided margin on the "does retention still succeed" side.

The other 5 ACs (1, 2, 4, 5, 6) already had genuine, non-vacuous test
coverage — confirmed by reading each test body directly, not inferring
coverage from a describe-block title alone.
