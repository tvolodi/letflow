# Test Spec: REQ-219 — Layer `Letflow.Application`'s flat 20-child supervision tree

**Requirement:** REQ-219 (`docs/requirements.yaml`, stage S6) — closes ISS-0425 parts
1 and partial-2: splits `Letflow.Application`'s flat, single-level, 20-child
`Supervisor.start_link/2` call into three named sibling supervisors —
`Letflow.Supervisor.Infrastructure`, `Letflow.Supervisor.Pollers`,
`Letflow.Supervisor.Http` — with an explicit, looser restart-intensity override on
`Pollers` (`max_restarts: 5, max_seconds: 60`) so a sustained per-tick crash-loop in
either poller can no longer exhaust the shared top-level supervisor's restart budget
and take `Letflow.Repo`/Bandit down with it.

**Design doc:** `lib/letflow/design/req219-supervision-layering.md` (rework iteration
2, CODE-DESIGN-VALIDATOR-approved, REVIEWER-approved at Step 2d).

**Test tier:** unit/integration against the real, application-supervised process
tree (`Supervisor.which_children/1`, `Process.whereis/1`, real application
stop/restart) — no `Letflow.DataCase`/tenant fixture, since nothing here touches
`Letflow.Repo`'s row data, only its supervised process identity.

**Test files:**
* `test/letflow/supervisor/infrastructure_test.exs` (new, ELIXIR-DEV, `async: true`)
* `test/letflow/supervisor/pollers_test.exs` (new, ELIXIR-DEV + 1 TEST-DESIGNER
  addition, `async: false`)
* `test/letflow/supervisor/http_test.exs` (new, ELIXIR-DEV + 1 TEST-DESIGNER
  addition, `async: false`)
* `test/letflow/application_test.exs` (retargeted, pre-existing file, ELIXIR-DEV)
* `lib/letflow/scheduler/poller.ex` gained a test-only, double-gated guard clause
  (ELIXIR-DEV) exercised by `pollers_test.exs`'s AC4 test.

This is a WF-02 Step 3 independent TEST-DESIGNER pass over coverage ELIXIR-DEV
already wrote as part of implementation (REVIEWER independently ran and PASSed it at
Step 2d, 3177/3179, 2 pre-existing unrelated failures). This spec re-derives the
AC-to-test map from the current test files directly (not from either prior agent's
summary), and records two coverage gaps found and closed below.

## AC-to-test traceability map (10 ACs, `docs/requirements.yaml` order)

1. **AC1** ("`Letflow.Application.start/2`'s `Supervisor.start_link/2` call takes
   exactly 3 children ...; none of the 20 current leaf children remain directly in
   `Letflow.Application`'s own children list") — `infrastructure_test.exs:23-43`,
   `test "Letflow.Supervisor has exactly 3 top-level children: Infrastructure,
   Pollers, Http"`. `assert ids == [Infrastructure, Pollers, Http]` is list
   *equality*, not membership — this alone already proves the count is exactly 3 and
   that no other id (of the original 20, or anything else) sneaked in; the four
   `refute ... in ids` lines below it are a redundant, explicit spot-check for 4 of
   the 20 former leaf children, not load-bearing on their own.

2. **AC2** ("`Letflow.Supervisor.Infrastructure`'s list index precedes

   `Letflow.Supervisor.Pollers`' own `init/1` runs") —

   top-level `Supervisor.start_link/2` call, with a test-only probe

   fires from inside `Letflow.Supervisor.Pollers.init/1` itself, message-passing the
   `Process.whereis/1` result back to the test process. This has real discriminating
   power against a swapped-order regression (`[Pollers, Infrastructure, Http]`),
   unlike a mechanism that only restarts the already-running `Pollers` child, which
   the design doc's own §4 records as the exact flaw CODE-DESIGN-VALIDATOR caught in
   iteration 1.

## Coverage gaps found and closed (TEST-DESIGNER, this step)

Neither ELIXIR-DEV's implementation summary nor REVIEWER's Step 2d verdict discusses
either gap below; both were found by reading the actual test files against the actual
`requirements.yaml` AC text word-for-word, per this step's mandate to build a fresh
traceability map rather than trust either prior summary.

1. **`Letflow.Supervisor.Http`'s `:start_http` gate was only tested gated OFF, never
   gated ON.** AC6's text requires `Letflow.Supervisor.Http` to "own exactly Bandit"
   — that half of the AC had no test at all; only the "empty when false" half did.
   A live-restart test (flip `:start_http` to `true`, restart the real, already-booted
   `Letflow.Supervisor.Http` singleton) was deliberately rejected: it would actually
   bind Bandit to a real TCP port, reintroducing the exact ISS-0015 port-collision
   hazard `config/test.exs`'s `start_http: false` exists to avoid in this project's
   two-worktree concurrent `mix test` setup. Instead, the new test calls
   `Letflow.Supervisor.Http.init/1` directly — a plain, side-effect-free function call
   per `Supervisor.init/2`'s own documented contract (`{:ok, {flags, child_specs}}`,
   no process started) — with `:start_http` and `:http_port` overridden for the
   assertion's duration only (both restored via `on_exit/1`). Confirms the gated-true
   branch's child spec id is `{Bandit, ref}` (Bandit's own custom `child_spec/1`
   tags its id with a unique reference rather than the bare `Bandit` atom — found by
   running the test and reading the actual failure output, not assumed), and the
   gated-false branch remains `[]`.

2. **`Letflow.Supervisor.Pollers`' "owns exactly [the two Pollers] when gated on" half
   of AC4 had no test asserting the actual child-id list.** The existing crash-loop
   test flips `:start_scheduler` to `true` and restarts the live `Pollers` singleton,
   but immediately induces a crash — nothing asserted the `which_children/1` id list
   `Pollers.init/1` actually produces with one or both gates true. Closed the same
   way as gap 1: a direct, side-effect-free `Letflow.Supervisor.Pollers.init(nil)`
   call with both `:start_scheduler` and `:start_service_task_dispatcher` overridden
   to `true` (restored via `on_exit/1`), asserting the returned child-spec ids equal
   `[Letflow.Scheduler.Poller, Letflow.Engine.ServiceTaskDispatcher.Poller]` in order.
   This is safe to call directly because `Pollers.init/1`'s only other body content
   (`maybe_run_pollers_init_probe/0`) no-ops when `:pollers_init_probe` isn't set in
   `Application` env, which this new test never sets — confirmed by reading
   `lib/letflow/supervisor/pollers.ex:107-117`.

**Out of scope, confirmed not (mis)covered:** REVIEWER's Step 2d PASS flagged a real,
non-blocking finding — a *persistent* (non-self-clearing) per-tick fault could still
cascade through repeated `Pollers`-level exhaustion into the top-level
`Letflow.Supervisor`'s own default restart budget, now filed as ISS-0451. Read
`pollers_test.exs`'s crash-loop test closely (lines 94-113): it deliberately clears
`:force_poller_crash` immediately after observing the first `:DOWN`, specifically so
the test does *not* exercise a second exhaustion cycle — it proves AC5's own text (a
*single* top-level restart event survives), not the persistent-fault scenario
ISS-0451 tracks. Neither gap fix above touches this scenario or implies REQ-219
covers it; ISS-0451 is out of scope for this requirement by design (REVIEWER's own
verdict text).
