# Test Spec: REQ-299 — `Letflow.Entities.Query.Allowlist` becomes per-entity-type

**Requirement:** REQ-299 (`docs/requirements.yaml`) — add a per-entity-type promoted
typed-column accessor to `Letflow.Entities.Query.Allowlist`, reusing REQ-296's
`Letflow.Entities.Definition.DDL.promoted_columns/1` enumeration rather than
re-deriving it, without changing `compiler.ex`'s dispatch logic or breaking the
existing structural-7 shadowing rule. See
`lib/letflow/design/req299-allowlist-per-entity-type.md` (REWORK ITERATION 1) for the
full design, including why AC4 as originally worded is honestly reported as
satisfiable only against `typed_columns/2`'s own output, not against `load/2`'s.

**Requirement's acceptance criteria (as amended, per this run's handoff):**
1. `typed_columns/2` returns entity-type-specific promoted columns in addition to the
   structural 7, proven by a test comparing two entity-type fixtures with different
   promoted columns and asserting their typed-column sets differ accordingly.
2. The promoted-column set returned by `typed_columns/2` matches
   `Letflow.Entities.Definition.DDL.promoted_columns/1`'s own enumeration for the same
   definition — not two independently hand-maintained lists.
3. The shadowing precedence rule is unchanged and still covers the original
   structural-7 case — the existing test(s) asserting a typed column wins over a
   same-named JSONB key still pass (`load/2` itself did not change).
4. `typed_columns/2`'s per-entity-type set includes both a `queried:true` field and an
   FK-derived (`foreign_keys`) column for one fixture ("order": `total_amount` +
   `customer_id`), and neither for a second fixture ("tag": no `queried:true`, no
   `foreign_keys`) — per design §1.2.1's exact fixture pair.
5. `compiler.ex`'s dispatch logic is unmodified (`git diff` verification, not a runnable
   test — confirmed separately by ELIXIR-DEV/REVIEWER, not re-verified here).
6. `mix letflow.check` passes (whole-suite gate — TEST-RUNNER/RELEASE-VALIDATOR's job,
   not asserted by any single test in this file).

**Test tier:** integration. `Allowlist.typed_columns/2` touches `Repo` (real Postgres,
via `Letflow.TenantProvisioning`/`Letflow.Entities.Definitions`) exactly like `load/2`
already does — no mocked database, per `docs/guides/test_developer_guide.md` DIRECTIVE
T-1.

## Why `load/2`'s existing tests needed no changes (AC3)

Per the design's REWORK ITERATION 1, `load/2`'s body was changed to build
`typed_column_entries` from `typed_columns/0`'s fixed 7 keys only — identical to
pre-REQ-299 behavior — specifically so its *runtime output* is provably unchanged, not
merely its function signature. The existing tests in
`describe "AC3 -- typed-column-wins shadowing precedence"` (query_test.exs, e.g. "a
field named 'deleted', also declared as a queried:true JSONB field, resolves to the
typed column") therefore continue to exercise exactly the same code path and are left
verbatim. Re-running them (not re-writing them) is what "AC3 is confirmed" means for
this run.

## Test cases

### Acceptance criterion 1 — `typed_columns/2` differs per entity type

1. **Two entity-type fixtures with different promoted columns produce different
   `typed_columns/2` key sets** — see `query_test.exs:"AC1: typed_columns/2's
   promoted-column key sets differ across two entity-type fixtures with different
   promoted columns"`. Creates an `"order"` entity type (a `queried: true` field
   `total_amount` plus an FK-derived field `customer_id`) and a `"tag"` entity type
   (neither trigger) in the same provisioned tenant schema. Calls
   `Allowlist.typed_columns/2` for both, asserts the two returned key sets are not
   equal, and asserts the exact set difference is `{"total_amount", "customer_id"}`.
   Would fail if `typed_columns/2` ignored `entity_type` and returned a global/cached
   set (the bug this criterion exists to catch), since both fixtures would then return
   identical key sets.

### Acceptance criterion 2 — agreement with `DDL.promoted_columns/1`

2. **`typed_columns/2`'s promoted names equal `DDL.promoted_columns/1`'s own
   enumeration for the identical definition** — see `query_test.exs:"AC2:
   typed_columns/2's promoted names agree exactly with DDL.promoted_columns/1's own
   enumeration for the same definition"`. Builds one raw, atom-keyed definition map (the
   `"order"` fixture's `fields`/`foreign_keys`) and feeds the *same* map value to two
   independent code paths: (a) persists it via `create_active_definition!/2` and reads
   it back through `Allowlist.typed_columns/2` (a real JSON round-trip through
   `entity_definitions.definition_json`), and (b) calls
   `Letflow.Entities.Definition.DDL.promoted_columns/1` on it directly, no JSON
   round-trip. Asserts the promoted-name sets from (a) (after subtracting the
   structural 7) and (b) are exactly equal, and equal the expected
   `{"total_amount", "customer_id"}`. This is a genuine cross-path agreement check, not
   two hand-copied lists — it would fail if `entity_type_typed_columns/1` ever
   re-implemented (and drifted from) `DDL.promotion_trigger/2`'s rule instead of calling
   `DDL.promoted_columns/1` directly.

### Acceptance criterion 3 — shadowing precedence unchanged (re-confirmed, not re-written)

3. **Existing AC3 tests re-run unmodified** — `query_test.exs`'s
   `describe "AC3 -- typed-column-wins shadowing precedence"` block (4 tests, lines
   ~238-303 pre-existing) is left byte-for-byte as-is. TEST-RUNNER re-running the full
   file re-confirms these pass under the current `allowlist.ex`. No new test is added
   for AC3 since the design explicitly kept `load/2`'s behavior identical to
   pre-REQ-299 — a new test here would only duplicate existing coverage, not add any.

### Acceptance criterion 4 — the exact §1.2.1 fixture pair

4. **`typed_columns/2` includes both triggers for "order", neither for "tag"** — see
   `query_test.exs:"AC4: typed_columns/2 includes a queried:true field AND an
   FK-derived field for 'order', and neither for 'tag' (design doc §1.2.1 fixture
   pair)"`. Builds the exact §1.2.1 pair: `"order"` has a `queried: true`, non-FK field
   `total_amount` and a `foreign_keys` entry `{field: "customer_id"}` whose own `fields`
   entry is `queried: false` (isolating the FK trigger from the `queried: true`
   trigger, per the design note); `"tag"` has one field, `queried: false`, no
   `foreign_keys`. Asserts `"order"`'s result contains both `total_amount` and
   `customer_id` alongside the full structural 7, and `"tag"`'s result key set equals
   *exactly* the structural 7 (neither promoted name leaks in). Would fail if either
   promotion trigger (FK-membership or `queried: true`) were dropped from
   `entity_type_typed_columns/1`'s computation, or if `typed_columns/2` leaked one
   entity type's promoted set into another's (the negative "tag" case).

### Error-path coverage (not separately numbered in the amended AC list, but exercised
by `load/2`'s own contract, which `typed_columns/2` mirrors per design §1.2 steps 1-2)

5. **`{:error, :entity_type_not_found}` for an unknown entity type** — see
   `query_test.exs:"typed_columns/2 propagates {:error, :entity_type_not_found} for an
   unknown entity type"`. Would fail if `typed_columns/2` raised instead of returning
   the typed error `fetch_active_definition/2` already produces for `load/2`.
6. **`{:error, :invalid_schema_name}` for a malformed schema name** — see
   `query_test.exs:"typed_columns/2 propagates {:error, :invalid_schema_name} for a
   non-provisioned schema"`. Calls with a string that fails
   `TenantProvisioning.tenant_id_for_schema_name/1`'s format check before any query
   runs. Would fail if the short-circuit were dropped and the call instead attempted a
   query against a non-existent schema.

## Fixture isolation

Each test calls `provisioned_tenant()` (this file's existing helper), which creates a
fresh tenant + schema per test and drops the schema `on_exit`. `"order"`/`"tag"` entity
type names are constants but scoped to that test's own freshly-provisioned schema, so
no cross-test collision exists (matching this file's existing `"customer"`-fixture
convention used throughout the rest of the suite).
