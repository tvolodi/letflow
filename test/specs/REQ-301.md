# Test Spec: REQ-301 — `:localized_text` field type, generated-column-per-locale

**Requirement:** REQ-301 (`docs/requirements.yaml`) — add a `:localized_text`
`Definition.field_type()`, per-definition/per-field `:locales` and `:search_strategy`
attributes, and a generated-column-per-locale promotion mechanism (plain `text` or
`tsvector`, per `docs/migration/decisions/0025-...md` Sub-question 2). See
`lib/letflow/design/req301-localized-text-field-type.md` for the full design (§0's
landmine findings, §4.5's backfill-is-inertness note, §4.6's `Allowlist.load/2` fix, §10's
open questions).

**Test tier:** unit (pure `Definition`/`Validator`/`DDL` functions) + integration
(`Allowlist.typed_columns/2`, `TenantProvisioning.register_column_promotion/4` +
`run_column_promotion/1` against real Postgres, per `docs/guides/test_developer_guide.md`
DIRECTIVE T-1 — no mocked database).

## Scope test

Real application-executable Elixir logic across `lib/letflow/entities/definition.ex`,
`lib/letflow/entities/definition/validator.ex`, `lib/letflow/entities/definition/ddl.ex`,
`lib/letflow/tenant_provisioning.ex`,
`lib/letflow/tenant_provisioning/column_promotion.ex`, and
`lib/letflow/entities/query/allowlist.ex`. Not docs-only, not build-config. Full
TEST-DESIGN-VALIDATOR / TEST-RUNNER chain applies.

## Amended acceptance criteria (per this run's handoff — verbatim)

1. `Definition.field_type()` gains `:localized_text`, proven by a test defining an entity
   with such a field and confirming it validates.
2. A `:localized_text` field's supported-locale set is per-definition (not
   project-wide), proven by two test fixtures declaring different locale sets for two
   different entity types, both validating independently.
3. `:localized_text` CAN be `queried: true`, proven by a test; a plain `:json` field is
   STILL rejected when `queried: true`, proven by re-running/confirming Validator's
   existing `queried_json_violations/1` coverage still passes (Rule 3 unweakened).
4. `queried: true` `:localized_text` produces one generated column per declared locale
   via REQ-296's DDL generator, proven by a test asserting the generated table has a
   column per locale (e.g. `stem_kk`, `stem_ru`).
5. AMENDED: for a `:localized_text` field with `queried: true` and a declared locale
   set, `Allowlist.typed_columns/2` for that entity type returns one entry per
   locale-derived generated column, typed per REQ-302's mechanism, and does NOT include
   the base field name as a separately queryable entry, proven by a test. Compiler/Cursor
   end-to-end reachability is explicitly OUT of scope (deferred to REQ-300).
6. The moduledoc states the plain-text-vs-tsvector mechanism implemented and cites
   REQ-302's decision record/section, without re-deciding the choice, proven by a test
   appropriate to the mechanism (exact/LIKE-style match for plain text, or full-text
   query test for tsvector).
7. A `:localized_text` field NOT marked `queried: true` stays entirely inside
   `field_values`, no generated column created, proven by a test.
8. `git diff` shows no file under `web/` or `docs/frontend/` touched.
9. `mix letflow.check` passes.

Plus (not separately numbered, per REVIEWER's own idiom-gate fix): `DDL.valid_generated_as_expression?/1`'s accept/reject behavior, and
`TenantProvisioning.execute_add_column/3`'s new `ArgumentError`-on-mismatch path for a
malformed `generated_as`.

## Test cases

### AC1 — `:localized_text` field type validates

1. **A definition with a `:localized_text` field (locales declared) validates as `:ok`**
   — `validator_test.exs`, `describe "REQ-301 AC1..."`. Would fail if `:localized_text`
   were absent from `@field_types` (rejected as `:malformed`) or if any new rule
   incorrectly fired against a conforming fixture.

### AC2 — per-definition locale sets

2. **Two entity types declare different locale sets on their own `:localized_text`
   field, each validates independently** — `validator_test.exs`, `describe "REQ-301
   AC2..."`. One fixture declares `["kk", "ru"]`, the other `["en", "fr", "de"]"` — a
   truly global/shared locale-set implementation could not pass both simultaneously
   without collapsing to one set (this test would not distinguish a single hard-coded
   set from a real per-definition one on its own, but combined with the DDL-level AC4
   test below, which asserts the *specific* locale suffixes appear per definition, the
   per-definition claim is fully proven end to end).

### AC3 — `:localized_text` CAN be `queried: true`; `:json` still cannot (Rule 3 unweakened)

3. **A `:localized_text` field with `queried: true` validates with no
   `:queried_json_conflict`** — `validator_test.exs`, `describe "REQ-301 AC3..."`. Would
   fail if Rule 3's guard were accidentally widened to also match `:localized_text`.
4. **A `:json` field with `queried: true` still fails `:queried_json_conflict`** —
   `validator_test.exs`, same `describe` block, re-confirming (not weakening) the
   pre-existing Rule 3 test already in this file. Proves Rule 3's source is unchanged in
   effect, not just unchanged in text.

### Rules 10/11 — new structural rules this requirement adds

5. **`locales` absent/non-list/empty on a `:localized_text` field fails
   `:invalid_localized_text`**, **duplicate locale fails it**, **a
   locale not matching `^[a-z]{2,8}$` fails it**, **`locales` present on a
   non-`:localized_text` field fails it** — `validator_test.exs`, `describe "Rule 10..."`.
   Each is a fixture violating exactly one condition, confirming Rule 10 fires (not some
   other rule) and reports the correct path.
6. **An invalid `search_strategy` atom fails `:invalid_search_strategy`**, **`search_strategy`
   present on a non-`:localized_text` field fails it**, **`search_strategy` absent on a
   `:localized_text` field is valid (defaults to `:plain`)** — `validator_test.exs`,
   `describe "Rule 11..."`.

### AC4 — one generated column per locale

7. **`promoted_columns/1` and `generate_table_ddl/2` produce exactly one column per
   declared locale, named `<field>_<locale>`, for a `queried: true` `:localized_text`
   field** — `ddl_test.exs`, `describe "REQ-301 AC4..."`. Two locales (`kk`, `ru`)
   produce exactly two columns, both with `source_field == "stem"`; the DDL text
   contains both `GENERATED ALWAYS AS` columns and never contains a bare `"stem"`
   column. Would fail if the dispatch collapsed to one column (the ordinary-type path)
   or produced zero.

### AC6 — plain-vs-tsvector mechanism, both shapes

8. **`:plain` (default) generates a `text` column via a JSONB path-extract expression,
   no `to_tsvector` anywhere** — `ddl_test.exs`, `describe "REQ-301 AC6..."`. Asserts
   the exact `generated_as` text and the exact DDL line.
9. **`:fulltext` generates a `tsvector` column via `to_tsvector('simple', coalesce(...,
   ''))`** — same `describe` block. Asserts the exact `generated_as` text and the exact
   DDL line. Together, cases 8/9 are the "test appropriate to the mechanism" AC6 asks
   for — direct assertions against the generated SQL text/column shape, matching the
   design doc §9's stated acceptable form (column-spec-level, not a live full-text
   `@@`-operator query, since that query surface does not exist yet — REQ-300's job).

### AC7 — not `queried: true` stays in `field_values` only

10. **A `:localized_text` field without `queried: true` produces zero promoted columns
    and no trace in the generated DDL** — `ddl_test.exs`, `describe "REQ-301 AC7..."`.
    Would fail if the dispatch promoted a `:localized_text` field unconditionally,
    ignoring the `queried` trigger `0023`/`promotion_trigger/2` already enforces for
    every other field type.

### AC5 (narrowed per the handoff) — `Allowlist.typed_columns/2` exposes locale columns, never the base name

11. **`typed_columns/2` for an entity type with a `queried: true, locales: ["kk", "ru"]`
    `:localized_text` field returns exactly `stem_kk`/`stem_ru` (typed `:string`) among
    its promoted names, and never `stem` itself** — `query_test.exs`, `describe "REQ-301
    AC5..."`. Would fail if `entity_type_typed_columns/1`'s `:source_field` lookup were
    dropped (crashing with `Map.fetch!/2` or falling back incorrectly) or if the base
    field name leaked in as its own entry.
12. **`Allowlist.load/2` does not crash and does not allowlist the base `:localized_text`
    field name under its own bare name, for a `queried: true` field** — same file, same
    `describe` block. This is the §4.6 fix's own regression test: before the fix, this
    exact fixture reaches `Compiler.json_cast_dynamic/2`'s missing `:localized_text`
    clause the moment such a field is resolved through `load/2`'s output; this test
    proves `load/2` itself never returns such an entry in the first place, so `resolve_field/2`
    for the field's own bare name returns `{:error, {:field_not_allowed, _}}` rather than
    a resolvable-but-crash-prone entry.

### `valid_generated_as_expression?/1` and `execute_add_column/3`'s defensive re-validation

13. **Accepts both known shapes (`:plain` and `:fulltext`), rejects a SQL-injection-shaped
    or malformed string** — `ddl_test.exs`, `describe "valid_generated_as_expression?/1"`.
14. **A `ColumnPromotion` row carrying a malformed `generated_as` is rejected at
    `execute_add_column/3` as `{:ddl_failed, %ArgumentError{}}`, the row is marked
    `ddl_failed`, and the malicious column is never created** —
    `column_promotion_test.exs`, `describe "REQ-301 -- execute_add_column/3's defensive
    re-validation..."`. Constructs the row directly (bypassing
    `register_column_promotion/4`, which does not itself validate `generated_as`'s
    shape) to model "a stored row somehow holds an unsafe value," per this function's own
    stated defence-in-depth posture. Would fail if the re-validation guard were removed
    or if the malformed expression were spliced into `ALTER TABLE` unchecked.
15. **A well-formed `generated_as` applied via `register_column_promotion/4` +
    `run_column_promotion/1` (the `ALTER TABLE ... ADD COLUMN` path, not `CREATE
    TABLE`) actually computes its value from a real row's `field_values`** — same file,
    `describe "REQ-301 -- generated_as applies as GENERATED ALWAYS AS ... STORED via
    ALTER TABLE"`. Inserts a row directly via SQL (bypassing
    `Letflow.Entities.Records`/`Record.Validator`, which has no `field_subschema/1`
    clause for `:localized_text` yet — a pre-existing gap outside this requirement's own
    scope per the design doc's own scope fence; not exercised here) and reads the
    generated column back. Would fail if `generated_as_suffix/1` were dropped from the
    `ALTER TABLE` text or if the expression text were mangled in transit.
