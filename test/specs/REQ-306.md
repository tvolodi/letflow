# Test Spec: REQ-306 — Test coverage for `entity_definitions` pack export/install

**Requirement:** REQ-306 — permanent test coverage for REQ-304's export side and
REQ-305's install side of `Letflow.Definitions.SolutionPack`'s `entity_definitions`
pack section, governed by `docs/migration/decisions/0026-solution-pack-entity-definitions-section.md`.

REQ-306 writes no `lib/` code itself. This spec's job is to map REQ-304's and
REQ-305's own MUST acceptance criteria to real, runnable tests — REQ-304's export-side
criteria were already covered by `test/specs/REQ-304.md`/the pre-existing
`test/letflow/definitions/solution_pack_test.exs` describe blocks; this spec adds the
install-side (REQ-305) coverage that never existed as a permanent test (REQ-305's own
completion report — `test/reports/report-20260910-WF02-REQ305-20260910.yaml` —
states explicitly: "no permanent tests yet exist for the new install path itself; that
coverage is queued separately as REQ-306").

**Test tier:** unit+integration (real Postgres via `Letflow.DataCase`, context-module
level — `install/3` has no HTTP route wired yet, same reasoning REQ-304's own spec
gives for `export/4`).

**Test file:** `test/letflow/definitions/solution_pack_test.exs` (extended, not a new
file — see that file's own moduledoc for why it fits: same module, same fixture/tenant
conventions already established there for the export half).

## Test cases (install-side, new in this requirement)

1. **Round-trip.** Real `export/4` call in tenant A, real `install/3` call in a
   DIFFERENT tenant B. Asserts `installed_entity_definitions`'s one entry (source id,
   name, `status: "installed"`), then re-queries the actual Postgres row in tenant B
   via `EntityDefinitions.get_definition_by_name/2` and asserts `definition_json`,
   `display_name`, `logical_shape_version`, and `status` (`:inactive`, confirming
   0026 §2's `:inactive`-only decision) all equal the source row's — not the
   in-memory install result alone. Also asserts the source tenant's own row count is
   unaffected (no accidental double-install).

2. **Name-collision rollback.** Target tenant already has one entity definition. A
   multi-section pack (process definition + variable schema + an entity-definition
   entry carrying byte-identical `definition_json` content to the existing row — so
   `create_definition/2`'s freshly-recomputed `logical_shape_version` genuinely
   collides, not merely a same-`name` coincidence) is installed against that tenant.
   Asserts `{:error, {:persistence, %Ecto.Changeset{}}}`, then queries
   `process_definitions`, `variable_schemas`, `entity_definitions`, and the global
   `solution_pack_installs` table directly — all show zero rows from the failed
   attempt (entity_definitions still shows exactly the one pre-existing row). Proves
   the failure, which occurs on the THIRD transactional step (after the process
   definition was already inserted in the same transaction), still rolls back
   everything already written earlier in that same transaction.

3. **Malformed entry rejection**, one test per shape:
   - missing `"name"` key
   - missing `"definition_json"` key
   - `"definition_json"` present but the wrong type (a string, not an object)

   Each asserts the exact `{:error, :invalid_pack_document}` tuple and
   `entity_definitions` row count `== 0` in the target tenant (parse failure happens
   before any transaction opens, so nothing could have been written).

4. **Old-pack compatibility.** A document is built with `definitions` and
   `variable_schemas` populated but with the `"entity_definitions"` wire key OMITTED
   entirely (`pack_document/1`'s own `Map.fetch/2` branch — verified with
   `refute Map.has_key?(document, "entity_definitions")` before installing). Asserts
   install succeeds exactly as it would have before REQ-305 (`installed_definitions`
   non-empty, `variable_schemas_written == 1`) and `installed_entity_definitions == []`.

## Known latent defect found while writing this spec — filed, not fixed (scope fence)

Writing the round-trip test with a literal `Jason.encode!/1 |> Jason.decode!/1` round
trip (to simulate real HTTP/JSON transport between export and install) raised
`** (Jason.EncodeError) invalid byte 0xEC in <<...>>` on the FIRST real entity
definition exported. Root cause: `packed_entity_definition/1`
(`lib/letflow/definitions/solution_pack.ex`) embeds
`EntityDefinition.logical_shape_version` verbatim —
`field(:logical_shape_version, :binary)`, a raw (non-UTF-8-safe) SHA-256 digest
computed by `Letflow.Entities.Definition.Shape.logical_shape_of/1` via
`Canonicaliser.content_hash/1` — into a pack document `install/3`'s own moduledoc
describes as "the raw decoded JSON body." A raw binary digest is not valid JSON
input; any real HTTP round trip (once a route is wired for `entity_definitions`
export) would either fail to serialize the export response, or fail to have been
valid JSON in the first place for a hand-built client request. This is a real,
reproducible defect in REQ-304's export shape (not a REQ-305 defect — `install/3`'s
own `fetch_string/2` accepts any `is_binary/1` value regardless of UTF-8 validity, so
install itself is not affected once a document reaches it in-process).

**Not fixed here** — REQ-306's scope fence is test code only, under `test/`.
Round-trip test coded around it (`stringify_keys/1`, a recursive atom→string key
converter that does NOT go through `Jason.encode!/1`) so the test still exercises the
key-shape half of the export→install boundary without tripping this unrelated,
separately-reported bug. Reported to ORCH per `docs/agents/protocols/ISSUE_QUEUE.md`
for `register_task` allocation — see this requirement's completion report for the
resulting `issue_ref`/`github_ref`.
