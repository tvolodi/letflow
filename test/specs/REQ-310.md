# REQ-310 — test spec addendum: re-derived disposition for `vortex-entity-list-filter-and-page`

**Scope of this spec.** REQ-310's own route-level coverage lives in its own test
files. This spec covers exactly one thing: the AC4 describe block of
`test/letflow/simulation/req207_vortex_test.exs`, which REQ-310 flipped, and the
honest re-derivation of the scenario's disposition that flip demanded.

This is *not* a new acceptance criterion of REQ-310. It is REQ-207's AC4, whose
recorded disposition REQ-310 rendered factually false and which the file's own
2026-09-11 ⛔ warning block instructed the implementer to re-derive through
TEST-DESIGNER rather than patch inline.

## 2. The re-derived disposition

**Still `:blocked_on_dependency`. Different, narrower, provable reason.**

Old reason (now false): *the entity subsystem has no HTTP surface.*
New reason (true): *the record-**query** route this scenario's six steps need does
not exist yet; it is REQ-311's.*

### Evidence chain

1. The scenario's six `:gui` steps, verbatim from
   `test/fixtures/simulation/vortex/scenarios/entity-list-filter-and-page.yaml`:
   navigate to entity list view · filter `category == 'raw-material'` · filter
   `status == 'active'` · sort by `display_name` asc · page to page 2
   (`page_size: 25`) · verify a cost-figure field is absent for a role without
   cost-figure visibility.

   Every one of the six is a **record read**. None is a definition CRUD call and
   none is a record write.

2. `lib/letflow/design/req308-entity-http-surface.md:182` states it directly:
   *"record reads only happen via `/entities/query`"*. `Letflow.Routers.Entities`'
   own moduledoc repeats it under "No route reads a record by id, and none lists
   records".

3. `Letflow.Entities.Records` is command-only. Its public surface is
   `create_record/2`, `update_record/2`, `delete_record/2` — no read function
   exists to hang a read route off.

4. `Letflow.Routers.Entities.__authz_routes__/0` returns exactly **nine** entries,
   and `POST /query` is not among them. Six are `/definitions/...`; three are
   `/records/...` writes (POST/PUT/DELETE).

5. `Letflow.Api.Authorization.endpoint_policy_key("POST", "/entities/query")`
   returns `:EntitiesQuery` — the permission REQ-309 minted — while no route
   consumes it. A policy key with no route behind it is the exact signature of a
   surface that is *specified and vocabulary-complete but not yet served*.

6. Step 6's field redaction is `Letflow.Entities.Query.FieldGrants`, which
   REQ-311's own description names as the thing REQ-311 wires
   (`redact_page/2` / `redact_joined_page/2`). No shipped route calls it.

### A second, independent blocker (recorded, not conflated)

Even a complete `POST /entities/query` would not make these six steps *execute*
through this harness: `Letflow.Simulation.Runner.run_steps/1` matches
`step.via == :gui` and records `outcome: :deferred_to_s8` unconditionally —
`test/support/simulation/runner.ex:309-318`. GUI steps are never dispatched.

This is deliberately kept as a *separate* evidence line rather than folded into
the primary reason. The primary blocker is a missing route (REQ-311 clears it);
this one is a harness capability (S8 clears it). Conflating them would let the
test survive REQ-311 landing without anyone re-examining it.

## 3. Test cases

### TC-1 — `/entities` IS mounted (positive assertion, replaces old Signal 1)

*Why it exists:* the old test asserted the opposite and is now wrong. Asserting
the mount positively means the file can never again drift back into claiming an
absent subsystem. Fails if the forward is removed.

Asserts `api_pipeline.ex` contains `forward("/entities", to: Letflow.Routers.Entities)`.

### TC-2 — the deferred rows are gone from `router.ex` (replaces old Signal 1's inverse)

*Why:* REQ-310 point 7 removed them outright. Asserting their absence pins that
retirement; a regression that re-added them would mean the mount was reverted.

### TC-3 — exactly the nine routes, and no record-read route (the sharp new signal)

*Why:* this is the assertion that actually carries the disposition. It proves
three things at once — the router is real and compiled (nine routes), definition
CRUD and record writes are served, and **no route reads records**. Checked
structurally against `__authz_routes__/0`, not against source text.

Sub-assertions:
- the route set equals the expected nine exactly (set equality, both directions —
  a tenth route added without updating this test fails here);
- no `{_, "/query", _}` entry exists;
- no `GET` route exists under `/records`;
- `:EntitiesQuery` appears in no route's permission slot.

### TC-4 — the permission exists but nothing consumes it

*Why:* distinguishes "unspecified" from "specified, not yet served" — the precise
state REQ-311 will change. `endpoint_policy_key("POST", "/entities/query")` is
`:EntitiesQuery`, yet TC-3 proved no route carries it.

### TC-5 — `Letflow.Entities.Records` exposes no read function

*Why:* replaces old Signal 3, which checked two file paths that were never the
real ones. This checks the *capability* rather than a filename: if no context
function can read a record, no route can serve one. Uses
`function_exported?/3` over the module's real exports, so a later
`list_records/2` or `get_record/3` trips it.

### TC-6 — the harness defers `:gui` steps (the second blocker, asserted live)

*Why:* proves the second evidence line rather than asserting it in a comment.
Runs `Runner.run/1` on the real fixture and asserts all six step results come
back `:deferred_to_s8`. **This makes the test execute the scenario** — it is no
longer `steps_executed: 0` bookkeeping — while recording the true outcome.

### TC-7 — REQ-311 tripwire (the next flip)

*Why:* the same pending-only mechanism the old test armed against REQ-310, now
re-aimed at REQ-311 (`status: pending`, queue task 598), which is the requirement
that adds `POST /entities/query`. When REQ-311 flips to `done`, this fails with
instructions to re-derive again.

### TC-8 — allowlist tier correction for REQ-309/REQ-310

*Why:* both are now *built* (code on this branch) though `docs/requirements.yaml`
still reads `status: pending` — DOC-UPDATER has not run. The old pending-only tier
meant "filed but unbuilt"; that is no longer true of REQ-310 in either direction
it could be read. They move to the unconditional allowlist with the triage
recorded: REQ-309 shipped permission vocabulary only, REQ-310 shipped the nine
routes — and *REQ-310's arrival is what this rewrite is responding to*, so it is
admitted as triaged-and-acted-on, not waved through.
