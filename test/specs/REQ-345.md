# REQ-345 — Deterministic seeded exam fixture for e2e runs

TEST-DESIGNER coverage for `Mix.Tasks.Letflow.Seed.ExamFixtures` (WF-02 Step 3, no
pre-fix baseline — this is new code, not a WF-03 regression). Test file:
`test/mix/tasks/letflow.seed.exam_fixtures_test.exs`. All tests call
`Mix.Tasks.Letflow.Seed.ExamFixtures.run/1` directly (never a shelled-out `mix`
invocation) against a real, `:auto`-mode Postgres connection, following
`test/mix/tasks/letflow.seed_test.exs`'s own established convention for testing a
task that provisions a real tenant schema (DDL can't run inside
`Ecto.Adapters.SQL.Sandbox`'s per-test transaction).

Below, each row is one REQ-345 acceptance criterion (quoted from
`docs/requirements.yaml`), the test case(s) proving it, and why that specific
assertion — not just a restatement of the criterion — is the thing that would catch
a real regression.

## AC1 — "running the seed path twice ... leaves exactly one copy of EACH of the two
fixture exams AND one copy of the seeded submitted session"

**Test:** `describe "idempotency -- running the task twice"` in the test file, single
test calling `ExamFixtures.run([])` twice then querying `entity_record_latest`
(via `Letflow.Entities.Record.Latest`, the same table `create_record/2` itself
writes to — not a hand-rolled duplicate of the query surface, and not the compiled
`POST /entities/query` surface either, since that route requires an authenticated
HTTP round trip this test doesn't otherwise need) for `exam`, `category`, `question`,
`exam_question_rule` and `session` rows scoped to the two fixture titles/categories.

**Why this exists, not just "assert count == 1":** the implementation's whole claim
is that `create_record/2`'s repeat-`idempotency_key` guarantee (design doc §4a) is
sufficient — it never hand-rolls a "does this exist" check for entity records. A
regression where a future edit swapped a fixed `idempotency_key` for
`Ecto.UUID.generate()` on even ONE of the ~24 writes (the exact anti-pattern the
design doc calls out by name, §4) would silently double that one record on a second
run while every other record stayed singular — asserting each entity_type's count
independently (exam, category, question, rule, session) rather than one aggregate
count is what would catch a single-record regression instead of only a wholesale one.

## AC2 — "two exams are seeded ... a mixed exam carrying one question per supported
type INCLUDING a shorttext question, and a second exam carrying NO shorttext
question ... the seeded type list ... is quoted from a ... result, not merely
asserted in prose"

**Test:** `describe "content correctness"`, first test — resolves the mixed
category's `record_id`, filters `question` records by `category_id == mixed_cat.id`,
asserts `length == 5` AND `Enum.sort(types) == Enum.sort(~w(single multiple
truefalse likert shorttext))`. Second test does the equivalent for the scoreable
exam: `length == 3` and `refute "shorttext" in types`.

**Why this exists:** a fixture that seeded, say, 5 questions but with a duplicate
type (e.g. two `single` and no `likert`) would still satisfy "5 questions" and would
break `web/`'s parity spec (REQ-346) silently much later, in a completely different
requirement's test run. Asserting the exact type SET, not just the count, is the
thing that would catch that class of drift at the source.

## AC3 — scoreable exam's `passing_score_pct` "is fixed, documented ... and quoted"

**Test:** same "content correctness" describe block, second test additionally
asserts `numeric(field(scoreable_exam, "passing_score_pct")) == 60.0` (a tiny local
`numeric/1` helper normalizes `float`/`integer`/`Decimal.t()` — the
`:decimal`-typed field's JSONB round-trip shape is exactly the ambiguity the design
doc's Open Question #1 flags as unresolved by design, so the test must tolerate
whichever concrete Elixir term the validator actually produces rather than assuming
one).

**Why this exists:** REQ-349 (a later, separate requirement) depends specifically on
this exam's `passing_score_pct` value being the fixed `60.0` the moduledoc
documents — a silent drift here (e.g. an edit changing the exam's attrs map without
updating the moduledoc) would not fail any OTHER test in this suite, only REQ-349's,
which is exactly the kind of cross-requirement coupling this test exists to catch
early, at the source.

## AC4 — "the mixed exam's session can only reach status grading_pending with
passed: nil"

**Test:** `describe "session outcome"` — after `ExamFixtures.run([])`, resolves the
seeded session's `record_id` and the seed candidate's `id`, then calls
`Letflow.Exam.Session.submit/3` directly a THIRD time (submit is documented
idempotent) and asserts on the real returned `{:ok, outcome}` map:
`outcome.status == :grading_pending` and `outcome.passed == nil`.

**Why this asserts the real claim, not a proxy for it:** the session's PERSISTED
`entity_record_latest` row stores `"passed" => false`, not `nil`
(`lib/letflow/exam/session.ex:1068`, `outcome.passed || false`) — asserting against
the raw stored field would pass even if the fixture's `Q5` shorttext question were
accidentally dropped and the exam became fully scoreable (which would flip the
stored value to `true`/`false` genuinely, but a naive `!= true` assertion could still
pass by accident). Calling `Session.submit/3` directly exercises
`outcome_from_session/1`'s own `if status == :grading_pending, do: nil, else:
fv(session, "passed")` mapping — the SAME function path the real
`POST /modules/exam/exam-sessions/:id/submit` route calls on every re-submit, and the same one
the design doc's own quoted manual run output (`{"passed":null,...}`) reflects. This
is the assertion that would actually fail if REQ-345's mixed exam ever lost its
shorttext-forces-grading-pending property.

## AC5/AC6/AC7 — real write paths (`Letflow.Entities`/REQ-335's routes), no direct
SQL, no direct write of `score_pct`/`status`/`passed`

Not independently re-tested here — these are static/diff-shape properties (already
checked by SECURITY-REVIEWER/REVIEWER per this run's PASS gates) that a runtime test
cannot distinguish from "wrote the same records via a different code path." AC4's
test above corroborates the *behavioral consequence* of this (the outcome comes from
`Session.submit/3`'s real state machine, not a hand-set value) as far as a runtime
assertion usefully can.

## AC8/AC10 — identifying content (titles/stems) fixed and quotable; question-type
enum inventory

Covered incidentally by AC2's exact-type-set and title-based lookups (the test
looks records up BY the exact literal titles/category names the moduledoc
documents — a typo or drift in either would make every other assertion in the file
fail with "expected exactly one match, got 0", not silently pass against the wrong
record).

## AC11 — "no exam_assignment record, table, or client-side substitute appears
anywhere ... a grep ... is quoted"

**Test:** `describe "no exam_assignment"` — after `ExamFixtures.run([])`, asserts
`Letflow.Entities.Definitions.get_active_definition_by_name("exam_assignment",
schema) == {:error, :not_found}`.

**Why this is the meaningful runtime check, not the grep itself:** the grep is a
static diff check (RELEASE-VALIDATOR/close-out's job, run over source text, not
something an ExUnit test can usefully repeat). What a runtime test CAN prove is the
functional consequence the requirement actually cares about: that no
`exam_assignment` entity type is defined or resolvable in the seeded tenant at
all — proving the gap is genuinely unaddressed by a workaround, not merely absent
from a text search that a differently-named workaround table could dodge.
