## A defect found and fixed while writing these tests

Writing the AC-6 "exactly two round-trips on success" test (and, transitively, AC-9's
and AC-10's success-path tests) required actually driving `Letflow.PublicRead.resolve/2`
to its success branch against a real Postgres-backed `Letflow.PublicRead.Handle` row.
Doing so raised `** (MatchError) no match of right hand side value: ~N[2026-09-14
23:15:56]` inside `DateTime.to_iso8601_iodata/3`, from
`Letflow.PublicRead.resolve_resource/3` (`lib/letflow/public_read.ex`, then line 190).

**Root cause:** `Letflow.PublicRead.Handle`'s schema declares a bare `timestamps()`
(matching the migration's own bare `timestamps()`, `priv/repo/migrations/
20260914000001_create_public_read_handles.exs:35`) — Ecto's default for `timestamps()`
is `:naive_datetime`, not `:utc_datetime_usec`. `handle.inserted_at` is therefore a
`NaiveDateTime.t()`, not a `DateTime.t()`, at every call site — including the design
document's own §6 success-path pseudocode, which specified
`DateTime.to_iso8601(handle.inserted_at)` verbatim. `DateTime.to_iso8601/1`'s first
clause pattern-matches `%DateTime{}` and does not accept a `%NaiveDateTime{}`, so this
crashed on every real success-path resolution — a live 500 on the one response shape
this whole requirement exists to serve correctly, not merely a test-fixture artifact.
The same value was also handed to `projection_module.project/2` inside `handle_meta`,
which `Letflow.PublicRead.Projection`'s own behaviour types as `DateTime.t()` — a second
instance of the identical mismatch, silently correct only for a projection that never
inspects `issued_at`.

**Why this was fixed here rather than only reported:** `docs/agents/instructions/
core-directives.md`'s "Unblock-Everything" section directs "test execution reveals
failures -> determine root cause and fix, do not just report and stop." This defect
directly blocked writing the AC-6/AC-9/AC-10 success-path tests this requirement's own
acceptance criteria require — it is not a tangential finding, it is the exact code path
under test. The fix (matching this codebase's own established naive-datetime-as-UTC
idiom, `Letflow.Routers.Identity`'s private `iso8601/1` helper,
`lib/letflow/routers/identity.ex:796-800`, and the `DateTime.from_naive!(ndt,
"Etc/UTC")` pattern already used in `lib/letflow/identity.ex:1446`,
`lib/letflow/routers/onboarding.ex:263`, `lib/letflow/routers/promotions.ex:783`,
`lib/letflow/routers/tenants.ex:481`) converts `handle.inserted_at` to a real
`DateTime.t()` once, in `resolve_resource/3`, before it is used for either purpose. This
is a MAJOR finding to be reported to ORCH/queued as a regression-class issue per "No
Issue Left Local-Only" (the design document itself carries the same latent bug in its
§6 pseudocode and should be corrected or annotated) — flagged here for
TEST-DESIGN-VALIDATOR and ORCH's attention, not silently absorbed into this diff.

## Notes for TEST-DESIGN-VALIDATOR

- `test/support/public_read_fixture_support.ex` deliberately carries no defaulted
  argument that goes unexercised (ISS-0069): `insert_resource!/2`'s `attrs` and
  `issue_handle!/4`'s `kind`/`opts` defaults are each exercised by at least one call
  site that omits them, verified by grep across every call site in this run's three new
  test files.
- `async: false` is required (not merely stylistic) on all three new DB-backed test
  files, because `PublicReadFixtureSupport.provision_tenant!/0` calls
  `Letflow.TenantFixture.provisioned_tenant!/1` with `template: :replay`, which switches
  `Letflow.Repo` to Sandbox `:auto` mode — empirically confirmed in this run: the first
  attempt at `async: true` produced `{:error, {:migration_failed, %Postgrex.Error{...
  :invalid_schema_name}}}` under concurrent async execution, matching the same
  requirement already stated by `test/letflow/tenant_provisioning/backfill_test.exs`
  and `test/support/tenant_fixture_dispatch_test.exs` for every other `template:
  :replay` call site in this suite.
- `config/test.exs` gained one additional kind registration,
  `"public-read-fixture-mismatch" => Letflow.PublicReadFixtureSupport.Projection`
  (same projection module, different kind string), solely so AC-4's kind-mismatch case
  could be exercised through a real HTTP request rather than a direct `resolve/2` call
  bypassing the router's own `fetch_kind/1` registration check.
