## AC-3 decision: documented grep, not a runtime purity test

Considered an automated regression test (e.g. a `:telemetry` handler counting
`[:letflow, :repo, :query]` events fired during `project/2`, mirroring REQ-352's own
AC-6/AC-7 round-trip-counting mechanism) and decided against it, for a reason specific to
this module rather than a general aversion to runtime checks: `Letflow.Exam.
CertificatePublicProjection.project/2`'s ENTIRE body is two function clauses, a
`Map.get/2`-only literal-map construction, and a private `to_float/1` helper — there is no
`Repo`, `Ecto.Query`, or `Application` alias anywhere in the module for a future edit to
misuse without an editor immediately seeing it (unlike REQ-352's own `resolve_resource/3`,
which threads through a real `Repo.get/3` call and genuinely needs a round-trip-count
mechanism to distinguish "one query" from "two"). A telemetry-based test here would
instrument a code path that structurally cannot emit a query event today, so it could only
ever pass — it would not be a regression-catching mechanism, it would be a test that always
passes by construction, which is exactly the "manufactured busywork" this pipeline's test
design guidance warns against. The grep test written instead
(`test/letflow/exam/certificate_public_projection_test.exs` "purity (documented grep, no
runtime test)") re-verifies the actual absence on THIS run's real source (not merely citing
SECURITY-REVIEWER's own earlier grep as a historical claim), and — because it strips the
moduledoc before matching — does not false-positive on the moduledoc's own legitimate prose
discussion of `Letflow.PublicRead.resolve/2`'s `Repo.get/3` call.
