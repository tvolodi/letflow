# Test Spec: REQ-358 — UAT scenario `scope`/branching schema + schema-validation mix task

**Requirement:** REQ-358 (stage S7). **Run:** `WF02-REQ358-20260916`, WF-02 Step 3.
**Design:** `lib/letflow/design/req358-uat-scope-branching-env.md`.
**Code under test:** `lib/mix/tasks/letflow.check_uat_scenario_schema.ex`
(`Mix.Tasks.Letflow.CheckUatScenarioSchema`) — a new module, `run/1` over a pure core
(`check_file/1` / `check_scenario/2`), following
`Mix.Tasks.Letflow.CheckRequirementsRegistration`'s structural precedent.
**Test file:** `test/mix/tasks/letflow_check_uat_scenario_schema_test.exs`.

## Requirement text

> Extend the UAT scenario YAML schema with a scope field and step-level `when:`
> branching (eq/in/else only). Extend UAT-RUNNER/WF-05 docs with an explicit
> environment target (base URL + credential source). Add a schema-validation mix task
> rejecting malformed scope/branching scenario files with a clear error. Backward
> compatible: every existing scenario file still parses and its non-branching behavior
> is unchanged. The branching construct must be proven sufficient for a login-routing
> example (role=PLATFORM_ADMIN / role=<tenant-role> / unauthenticated, three distinct
> outcomes).

## Scope of this spec

Four surfaces are touched by this requirement (design §1–§4): the schema itself, the
mix task, the UAT-RUNNER/WF-05 doc prose, and the throwaway login-routing fixture. Only
the mix task (`lib/mix/tasks/letflow.check_uat_scenario_schema.ex`) is real,
unit-testable Elixir logic — the doc-prose changes to `.claude/agents/uat-runner.md`
and `docs/agents/workflows/WF-05_uat_run.md` are `.md` with no executable surface (a
prose-mutation test asserting on markdown text would be manufactured busywork, not real
coverage), and are out of scope for this test file. This spec covers AC1 (backward
compatibility), AC2 (malformed rejection), and the schema half of AC4 (branching
sufficiency) — the part of REQ-358 that is genuinely a function of parsed YAML data to
a violations list.

**Not covered here, by design:** AC3/AC4's *runtime* half — UAT-RUNNER actually
evaluating a `when:` branch against a live authenticated session and observing three
distinct outcomes. `check_scenario/2`/`check_file/1` have no branch-evaluation
function at all (confirmed by reading the module in full — its only exported
functions are `run/1`, `check_file/1`, `check_scenario/2`, `render/1`); branch
*evaluation* is UAT-RUNNER's own procedural job reading `.claude/agents/uat-runner.md`
against a real HTTP session, not an Elixir function, so it is not unit-testable. That
gap is real and is closed by a real UAT-RUNNER run against QA, dispatched separately
in this run (not TEST-DESIGNER's job, per the task description).

## Why this suite needs no fail-first-against-pre-fix-code demonstration

REQ-358 is a WF-02 (new-code) requirement, not a WF-03 regression. The
fail-first-against-pre-fix-code / mutation-evidence discipline in
`docs/agents/workflows/WF-03_issue_resolving.md` applies to regression tests, where
there is a real "before" state to compare against. Here the module is genuinely new;
there is no pre-fix version of `check_scenario/2` to run these tests against, and
inventing one would prove nothing beyond "the module exists." Instead, every test case
below is built and reasoned through against a concrete, plausible wrong
implementation — stated per test case — so that each one is a real, falsifiable claim
about the shipped logic rather than a tautology.

## Test cases

### AC1 — backward compatibility

Requirement: "every existing scenario file still parses and its non-branching behavior
is unchanged" — concretely, design §1.2's default rule that `scope` is derived from
`company_id:` when `scope:` is absent, so none of the 29 existing scenario files need
editing.

| Test | Why it exists |
|---|---|
| `F-SCOPE-FROM-COMPANY-ID` | Builds an in-suite fixture with `company_id: "meridian"` and no `scope:` key — the exact shape of all 11 tenant scenario files today. Would fail against an implementation that requires an explicit `scope:` key and never falls back to `company_id:` (the literal bug AC1 exists to prevent). |
| `F-SCOPE-FROM-COMPANY-ID-PLATFORM` | Same, with `company_id: "platform"` — the shape of all 18 platform scenario files. A separate case because a plausible bug hardcodes the fallback for one literal value (e.g. only `"platform"`, or only non-`"platform"` values) rather than deriving from whatever `company_id:` actually holds. |
| `F-SCOPE-EXPLICIT-NO-COMPANY-ID` | An explicit `scope:` with no `company_id:` at all — the forward-looking case design §1.2 names for genuinely new Letflow-native scenarios. Would fail against an implementation that requires `company_id:` unconditionally (treating it as still-mandatory rather than optional-with-fallback). |
| `T-LIVE-MERIDIAN` | Runs `check_file/1` against the real, unedited `test/fixtures/uat/scenarios/meridian/loan-origination-below-threshold.yaml`. This is design §5's own named AC1 evidence mechanism: the real file, zero edits, must resolve clean. Exercises the real `YamlElixir.read_from_file/1` path, not just the pure core. |
| `T-LIVE-PLATFORM` | Same, against `test/fixtures/uat/scenarios/platform/definition-promotion-approved.yaml` — the platform-scenario shape's live counterpart. |
| `F-TOTALITY` (`check_file/1`'s `ok?` agrees with the violations list) | Applied across the three real files this spec reads, so a bug that reports `ok?: true` while still populating `violations` (or vice versa) is caught even though each individual field-level test only checks one of the two. |

### AC2 — malformed rejection

Requirement: "a schema-validation mix task rejecting malformed scope/branching
scenario files with a clear error." One test case per SCHEMA-3..6 rule the design
names (SCHEMA-1/2 are the pre-existing parse/required-field rules, also covered since
the task validates the whole current shape per design §2.3).

| Test | SCHEMA rule | Why it exists |
|---|---|---|
| `F-SCOPE-MISSING` | SCHEMA-3 | Neither `scope:` nor `company_id:` present. The "invisible to classification" case design §1.2 says must never silently default. Fails against an implementation that treats a missing scope as vacuously OK. |
| `F-SCOPE-EMPTY-STRING` | SCHEMA-3 | `scope: ""` — key present, value empty. Would pass an implementation that only checks `Map.has_key?/2` and never non-emptiness. |
| `F-SCOPE-WRONG-TYPE` | SCHEMA-3 | `scope: 42` (non-string). Would pass an implementation that checks presence/truthiness but never `is_binary/1`. |
| `F-REQUIRED-FIELDS-MISSING` | SCHEMA-2 | `id`/`title`/`version` all absent, asserting exactly 3 violations (one per field, not one combined violation) — catches an implementation that stops at the first missing field instead of reporting every one. |
| `F-BOTH-STEPS-AND-BRANCHES` | SCHEMA-4 | A file carrying both top-level `steps:`/`expected_outcomes:` **and** `branches:`. The design is explicit these are mutually exclusive; this is the "ambiguous, which applies first" case that must be rejected outright rather than one silently taking precedence. |
| `F-NEITHER-STEPS-NOR-BRANCHES` | SCHEMA-4 | A file carrying neither step shape at all. Catches an implementation that only checks the "both present" half of the exclusivity rule and treats "neither" as vacuously fine. |
| `F-BRANCHES-EMPTY-LIST` | SCHEMA-5 | `branches: []`. An implementation that treats an empty list as "branches key present, therefore fine" instead of requiring at least one entry would pass this. |
| `F-BRANCH-BAD-OP` | SCHEMA-5 | `when.op: "gt"`. The design is explicit the `when:` vocabulary is deliberately narrow — eq/in/else only, never a relational or boolean operator. This is the guardrail test: an implementation that accepts any string op (or checks a blocklist instead of an allowlist) would let this through. |
| `F-BRANCH-EQ-WITH-LIST-VALUE` | SCHEMA-5 | `op: eq` with a list `value` (the `in` shape used with the wrong operator). Catches an implementation that validates `value`'s presence but not its type/shape per-operator. |
| `F-BRANCH-IN-WITH-EMPTY-LIST` | SCHEMA-5 | `op: in` with `value: []`. An empty membership list can never match anything at runtime; the design requires a non-empty list. |
| `F-BRANCH-MISSING-NAME` | SCHEMA-5 | A branch with no `name` key. `name` is load-bearing for the UAT report (design §1.3: "used only in the UAT report") and for the SCHEMA-6 else-position check's own error message, so a missing name must hard-fail, not default to a blank label. |
| `F-BRANCH-DUPLICATE-NAME` | SCHEMA-5 | Two branches sharing one `name`. Design requires uniqueness within the file — ambiguous which branch a UAT report line naming that value refers to otherwise. |
| `F-BRANCH-EMPTY-STEPS` | SCHEMA-5 | A branch with `steps: []`. A branch with no steps can never actually be run; must be rejected the same way a top-level empty `steps:` would be. |
| `F-ELSE-NOT-LAST` | SCHEMA-6 | An `else` branch that is not the final list entry. Branches are evaluated top-to-bottom and `else` means "nothing earlier matched" — an `else` in the middle would make every branch after it unreachable, a silent authoring bug the design requires catching mechanically. |
| `F-ELSE-MULTIPLE` | SCHEMA-6 | Two `when: else` branches in one file. At most one is allowed per the design; a second is always unreachable (dead) and must be flagged, not silently ignored. |
| `F-PARSE-ERROR` | SCHEMA-1 | An on-disk file that is not valid YAML at all (unterminated flow mapping), read via `check_file/1` so the real `YamlElixir.read_from_file/1` error path is exercised, not simulated. Confirms a parse failure surfaces the underlying decoder message rather than being swallowed. |
| `F-NOT-A-MAPPING` | SCHEMA-1 | An on-disk file whose top-level YAML is a list, not a mapping (parses fine as YAML, wrong shape). Distinct failure mode from a parse error — `check_file/1` has a separate `{:ok, _other}` clause for it. |

### AC4 — branching sufficiency (schema-validation half)

Requirement: "the branching construct must be proven sufficient for a login-routing
example (role=PLATFORM_ADMIN / role=<tenant-role> / unauthenticated, three distinct
outcomes)."

| Test | Why it exists |
|---|---|
| `T-LOGIN-ROUTING-FIXTURE-VALID` | Runs `check_file/1` against the real `test/fixtures/uat/scenarios/_throwaway/login-routing-example.yaml` (design §3's throwaway fixture, already committed as an `artifacts_in`). Proves the exact three-branch shape named in the requirement text — `eq PLATFORM_ADMIN`, `in [TENANT_ADMIN, TENANT_USER]`, `else` — is SCHEMA-1..6-valid using only the eq/in/else vocabulary, no scripting language needed. |
| `F-LOGIN-ROUTING-SHAPE-HERMETIC` | The same three-branch shape, built as an in-suite fixture rather than read from disk. Keeps this property true even if the throwaway file is later relocated or deleted (its own header says TEST-DESIGNER may discard/relocate it), and is a second, independent check of the same claim built from a different data path (`check_scenario/2` directly, not `check_file/1`). |

As stated above, this section covers only the schema-validity half of AC4. The
"three distinct outcomes actually observed against a live session" half is not
unit-testable and is named explicitly, not faked, per the task description's
instruction.

## Verifying each test would actually fail on a violation

Reasoned through against a hypothetical broken implementation for each test above (see
the "Why it exists" column, which states the specific mistake each test would catch):
every AC1 test would go red against an implementation that drops or narrows the
`company_id:` fallback; every AC2 test would go red against an implementation that
under-validates the specific field/shape it targets (missing a type check, an
allowed-operator check, a uniqueness check, or a position check, per row); the AC4
tests would go red against an implementation that rejects a structurally-valid
three-branch `eq`/`in`/`else` file for any reason (e.g. a regression in SCHEMA-5/6).
None of the AC1/AC4 "must validate" tests can pass by construction (they assert
`== []`/`ok? == true` against fixtures whose only defining property is validity), and
none of the AC2 "must reject" tests can pass by construction either (each asserts a
specific `rule` tag and, in most cases, a specific substring of the violation
message) — so a no-op `check_scenario/2` that always returns `[]` fails every AC2
test, and a `check_scenario/2` that always returns a violation fails every AC1/AC4
test. The suite cannot be vacuously green in either direction.
