# Test Spec: REQ-362 — Two-phase visual regression testing

**Requirement:** REQ-362 (stage S7). **Run:** `WF02-REQ362-20260916`, WF-02 Step 3.
**Design:** `lib/letflow/design/req362-visual-regression-testing.md`.
**Code under test:** `web/tests/support/visual-baseline.ts` (baseline persistence:
accept action §2, re-baseline action §4) + Playwright's real built-in
`expect(page).toHaveScreenshot()` (phase-2 pixel-diff, §3), reached through
`web/playwright.config.ts`'s `snapshotPathTemplate` override.
**Test files:**
- `web/tests/unit/visual-baseline.test.ts` (vitest — pure fs/logic, every `npm test` run)
- `web/tests/e2e/req362-visual-regression.e2e.spec.ts` (Playwright — real browser + real
  pixel comparison), two describe blocks (see "Suite structure" below)

## Requirement text (summary)

Phase 1: an agent's existing screenshot-judgment discipline gains a persistence step —
accept a judged-correct screenshot as a durable baseline, keyed to
scenario+step+EO+environment. Phase 2: every later run of an expected outcome that
already has a baseline is mechanically pixel-diffed against it via Playwright's own
built-in comparison, at its default threshold, with **no LLM judgment gate** — any
difference is an unconditional auto-fail. An auto-fail routes through the existing
`ISSUE_QUEUE.md` dual-track mechanism (local + queue + GitHub), carrying both images as
evidence. Re-baselining (accepting a new image over an existing one) requires an
explicit, recorded justification — never a bare accept.

## Suite structure — why two describe blocks in the e2e file, and this file's own finding

`req362-visual-regression.e2e.spec.ts` was originally written by ELIXIR-DEV as the
implementation's real-exercise PROOF (6 tests) against the actual, git-committed
baseline directory (`test/fixtures/uat/visual-baselines/platform/
req362-visual-regression-selfcheck/`) — this satisfied AC-2/AC-3/AC-4/AC-5 for real
during implementation, including a real `register_task` filing now recorded, resolved,
at `docs/issues/ISS-0691.yaml` (`queue_ref: Q-691`, `github_ref: GH-1446`).

**TEST-DESIGNER finding (this run), verified empirically, not assumed:** re-running
that same spec on every CI invocation rewrites the committed sidecar YAML's
`accepted_at`/`rebaselined_at` timestamps every time, because it targets the same
durable evidence directory `git ls-files` shows is tracked. Reproduced directly:
running the spec once left
`test/fixtures/uat/visual-baselines/platform/req362-visual-regression-selfcheck/01-EO-001.local.yaml`
modified in the working tree (`accepted_at` changed from `2026-09-16T11:02:46Z` to
`2026-09-16T11:25:16Z`, `rebaselined_at` similarly) — confirmed via `git diff` before
reverting it with `git checkout --`. A formal suite that runs on every PR's CI and
mutates a committed evidence fixture every time is a genuine defect, not a
hypothetical one — it would either leave CI permanently "dirty" or, worse, get
committed back and erase the historical record of the original real exercise.
Separately confirmed the spec does **not** call `register_task`/file a fresh GitHub
issue on each run (grepped the spec and support module for `register_task`/
`gh issue create` — zero hits; the fail-case test only references the already-filed,
already-resolved `ISS-0691` as a constant) — so there is no GitHub-spam risk, only the
fixture-mutation one.

**Fix applied:**
1. The original describe block is now tagged `{ tag: '@manual' }` and excluded from the
   default `npm run test:e2e` (now `playwright test ... --grep-invert @manual`, see
   `web/package.json`). It is preserved byte-for-byte in behavior — it remains the
   permanent record of the one real exercise — and is run deliberately via the new
   `npm run test:e2e:manual` script.
2. A new, second describe block ("REQ-362 visual regression — formal CI-safe
   regression suite") was added to the same file. It exercises the identical real
   Playwright mechanism (same `toHaveScreenshot()` call, same default threshold, no
   mocking) against a disposable scenario id
   (`req362-visual-regression-ci-formal`/`-no-baseline`) that its own `beforeAll`/
   `afterAll` create and delete — confirmed via `git status --porcelain` before and
   after a run: zero diff, zero untracked residue. It never calls
   `register_task`/files a real GitHub issue (AC-4's real-filing proof stays satisfied
   by the manual block's one-time run).
3. `web/tests/support/visual-baseline.ts` gained a test-only escape hatch
   (`__setBaselineRootForTests`/`__resetBaselineRootForTests`) used by the new vitest
   unit suite to point every `acceptBaseline`/`rebaseline`/`baselineExists` call at a
   fresh `fs.mkdtempSync` directory per test — production code (UAT-RUNNER at runtime)
   never calls it.

## Test cases

### AC-1 — baseline location/naming, keyed to scenario+step+EO+environment, distinct from transient

| Test | File | Why it exists |
|---|---|---|
| `snapshotName returns the [company, scenario, stem.png] segments...` | `visual-baseline.test.ts` | Pins the array-return shape. Would fail against a regression back to a single joined string — the module's own comment documents this as a real, previously-hit bug (Playwright flattens a string `name` into one file instead of a nested path). |
| `baselinePngPath and baselineSidecarPath are keyed to company+scenario+step+EO+environment, zero-padded` | `visual-baseline.test.ts` | Would fail against an implementation that drops zero-padding (`1` instead of `01`), breaking lexical ordering past step 9. |
| `a different environment produces a distinct path` | `visual-baseline.test.ts` | AC-1 explicitly requires environment-keying (design §1.2) — would fail against an implementation that ignores the environment segment and collides `qa`/`local` baselines. |

### AC-2 — phase-1 accept, implemented and exercised for real

| Test | File | Why it exists |
|---|---|---|
| `phase 1: baseline-accept action (AC-2)` | e2e, `@manual` block | The original real exercise: a real page load, a real screenshot, a real `acceptBaseline` call, confirmed against the real committed path. |
| `phase 1: accept establishes a baseline (AC-2)` | e2e, formal block | Same real mechanism, CI-safe disposable directory — this is what runs on every PR. |
| `accepts a first baseline: copies the PNG and writes a sidecar with empty history` | `visual-baseline.test.ts` | Would fail against an implementation that seeds `history` with a phantom entry or omits it, contradicting design §2.3 ("empty on first accept"). |
| `rejects a second accept when a baseline already exists` | `visual-baseline.test.ts` | Design §2.2 step 4: accept must never silently overwrite — that is re-baseline's job, which requires justification. Would fail against an implementation that lets a second accept double as an unconditional overwrite (the exact "backdoor around phase 2" the design forbids), and confirms the rejected call left the original provenance untouched. |

### AC-3 — phase-2 pixel-diff via Playwright's built-in comparison, exercised pass + fail

| Test | File | Why it exists |
|---|---|---|
| `phase 2: pixel-diff against unchanged screen passes` | e2e, `@manual` block | Original real pass-case proof. |
| `phase 2: pixel-diff against a deliberately altered screen fails` | e2e, `@manual` block | Original real fail-case proof — a real DOM mutation (injected banner), a real Playwright comparison failure caught and asserted. |
| `phase 2: unchanged screen compares PASS via the real Playwright mechanism` | e2e, formal block | Same real pass-case, CI-safe. |
| `phase 2: altered screen compares FAIL via the real Playwright mechanism, no issue filed` | e2e, formal block | Same real fail-case, CI-safe, and explicitly does NOT call any issue-filing mechanism (see "Suite structure" above for why that's correct here, not a coverage gap). |

### AC-4 — auto-filed issue lands in local + queue + GitHub, carries both screenshots

| Test | File | Why it exists |
|---|---|---|
| (real exercise, one-time) | `docs/issues/ISS-0691.yaml` | The actual, permanent record: `queue_ref: Q-691`, `github_ref: GH-1446`, `status: resolved`, `affected_files` lists both the new and baseline screenshot paths under `_disputed/ISS-0691/`. This is the "exercised for real" evidence AC-4 requires — re-deriving it via a fresh `register_task` call on every CI run would file a new real GitHub issue every PR, which is the defect this run's fix avoids, not missing coverage. |
| `phase 1: baseline-accept action (AC-2)` … `re-baseline action` (`@manual` block, full sequence) | e2e, `@manual` block | Re-runnable via `npm run test:e2e:manual` if the mechanism itself (not the filing) ever needs re-verifying; mirrors evidence images to `_disputed/ISS-0691/` on each manual run, consistent with the existing record. |

### AC-5 — re-baseline action with mandatory recorded justification, exercised for real

| Test | File | Why it exists |
|---|---|---|
| `re-baseline action with mandatory justification (AC-5)` / `after re-baseline, the ... screen now compares as PASS` | e2e, `@manual` block | Original real exercise: real justification text recorded, sidecar history confirmed, and the mechanism (not just the bookkeeping) proven by a subsequent real PASS comparison. |
| `re-baseline recovers the altered screen to PASS, with a real recorded justification (AC-5)` | e2e, formal block | Same real mechanism, CI-safe. |
| `rejects rebaseline when no baseline exists yet` | `visual-baseline.test.ts` | Symmetric negative case the original spec didn't cover: re-baseline must not silently create a baseline — would fail against an implementation that treats a missing baseline as "just accept it". |
| `rejects a blank/generic justification: %j` (parametrized over `''`, `'ok'`, `'fine'`, `'lgtm'`, `'LGTM'`, `'looks fine now'`, `'Looks Fine'`, `'accept'`, whitespace-only) | `visual-baseline.test.ts` | The original spec only exercised the single literal `'looks fine now'`. Each of these is a plausible real rubber-stamp — would fail against an implementation that special-cases only the one literal string the original test happened to use, missing case-insensitivity, the length check, or the rest of the generic-phrase list. |
| `accepts a real, specific justification and appends (never overwrites) sidecar history` | `visual-baseline.test.ts` | Exercises TWO successive re-baselines. Would fail against an implementation that overwrites `history[0]` on the second call instead of appending (design §4.3's append-only discipline), and independently checks that each entry's `superseded_baseline_hash` is the hash of the PNG that existed immediately before THAT specific overwrite, not a stale or future hash. |
| `rebaseline() rejects a blank/generic justification (AC-5 negative check)` | e2e, `@manual` block | Original negative-path proof, preserved. |

### AC-6 — phase-2 auto-fail is unconditional, no judgment gate, and design states why

| Test | File | Why it exists |
|---|---|---|
| `phase 2: pixel-diff against a deliberately altered screen fails` / `phase 2: altered screen compares FAIL...` | e2e, both blocks | Both fail-case tests assert the comparison fails unconditionally on a real, measurable pixel diff — no agent judgment call intervenes between detection and fail. `lib/letflow/design/req362-visual-regression-testing.md` §3.4 carries the explicit statement-and-reasoning AC-6 additionally requires (design-doc text, not test-code territory). |

### Additional edge-case coverage beyond the original ACs (TEST-DESIGNER judgment, item 4)

| Test | File | Why it exists |
|---|---|---|
| `phase 2 against a key with no accepted baseline yet: Playwright auto-fails and writes the missing reference` + the immediately following confirmation test | e2e, formal block | Design §5's flow puts the phase-1-vs-phase-2 branch decision entirely on `baselineExists()` being checked BEFORE the comparison call — nothing in the design or the original spec proved what happens if that guard is bypassed. Measured for real: `toHaveScreenshot` against a wholly new key does NOT throw a normal, try/catch-catchable error (confirmed by first writing the test with a try/catch, running it, and observing the catch block never fired) — it fails the enclosing test via Playwright's own internal mechanism regardless of surrounding try/catch, and writes the missing reference PNG to disk with **no** sidecar. That asymmetry (a PNG appears at the exact path `acceptBaseline` would also write to, but with none of §2.3's required provenance fields) is the concrete, checkable shape of the hazard the existence-check gate exists to prevent, and is now pinned by a real assertion (`test.fail()`) rather than left undocumented. |
| `a malformed (non-JSON) sidecar surfaces a real parse error on rebaseline` | `visual-baseline.test.ts` | Corrupts an existing sidecar file in place, then calls `rebaseline`. Would fail (silently proceed, or crash uninformatively) against an implementation that doesn't actually read/validate the prior sidecar before appending — confirms `readSidecar`'s `JSON.parse` surfaces a real, catchable error instead. |
| `baselineExists is false for a key whose PNG was never accepted, even if a stray sidecar-shaped file exists` | `visual-baseline.test.ts` | `baselineExists` must key off the PNG (what phase 2 actually compares against), not the sidecar — would fail against an implementation that checks sidecar presence instead, since a sidecar-without-PNG state should never be treated as "baseline exists." |

## Why this requirement needs no fail-first-against-pre-fix-code demonstration

REQ-362 is a WF-02 (new-code) requirement, not a WF-03 regression — there is no
pre-fix version of `visual-baseline.ts` or the e2e mechanism to run these tests
against. Every test case above is instead reasoned against a concrete, plausible wrong
implementation (stated per case in the tables) so each is a real, falsifiable claim
about the shipped logic.
