Stage S7. Verifies `lib/letflow/help/platform.ex` (`Letflow.Help.Platform`),
`lib/letflow/help/platform_help_content.ex` (`Letflow.Help.PlatformHelpContent`), and the
`Letflow.Help.MarkdownSafety` extraction, against
`lib/letflow/design/req365-platform-help-authoring.md` (CODE-DESIGN-VALIDATOR-approved)
and this run's handoff acceptance criteria
(`handoffs/WF02-REQ365-20260918/step-03-test-designer.json`).

Test code: `test/letflow/help/platform_test.exs`. `Letflow.DataCase` (real Postgres, no
mocks, per `docs/guides/test_developer_guide.md` DIRECTIVE T-1). `platform_help_content`

## Acceptance criteria -> test cases

### AC1 — "a platform-scope help-content write path exists, reusing REQ-364's
context-module shape ... not a parallel schema/mechanism"

Not independently re-tested here as its own assertion (it is a structural/design-review
property, already checked by CODE-DESIGN-VALIDATOR/REVIEWER against the design and the
shipped module). What *is* tested is that the module's actual runtime behavior matches
that shape function-by-function — AC3 below covers exactly that, one `describe` block per
function, mirroring `help_test.exs`'s own per-function organization.

### AC2 — "the write path enforces the same sanitization rule REQ-363/364 established for
tenant-scoped content — no separate, weaker validation for the platform path"

- `create_draft/1`: `"rejects a body containing a raw <script> tag"`, `"rejects a title
  containing a raw HTML tag"`, `"rejects a markdown link with a javascript: URL scheme"`,
  `"rejects a markdown image with a data: URL scheme"`. Why: exercises
  `Letflow.Help.MarkdownSafety.validate/2` from the **platform** call site specifically
  (`PlatformHelpContent.validate_common/1`), not merely re-running `help_test.exs`'s
  existing tenant-side coverage — the design's own §5 acceptance-mapping requires this be
  demonstrated for the platform path too. Each would fail if `PlatformHelpContent`'s
  changesets stopped calling `MarkdownSafety.validate/2` (e.g. a copy-paste omission, or a
  weaker/no-op validator swapped in for the platform path) — the exact "second,
  independently-maintained implementation that could drift apart" risk design §5 flags.
- `create_draft/1`: `"allows the design's own safe markdown subset"` — a positive control:
  proves the validator isn't simply rejecting everything (which would make the negative
  tests above vacuous/trivially-true).
- `update_draft/2`: `"rejects raw HTML on update, same as create"` — the validator is
  wired on `update_changeset/2` too, not only `create_changeset/2`; a real, distinct
  changeset function with its own cast/validate pipeline.

### AC3 — "every `Letflow.Help.Platform` function has test coverage"

One `describe` block per function:

- **`create_draft/1`**: creates with `status: :draft`/`confirmed_at: nil`/
  `confirmed_for_definition_version: nil`/`media: []` regardless of extra fields; rejects
  caller-supplied `:status`, `:confirmed_at`, `:confirmed_for_definition_version` (each
  its own test, mirroring `Letflow.Help`'s already-tested "never caller-supplied" rule —
  would fail if a future edit re-added any of these three fields to
  `PlatformHelpContent.create_changeset/2`'s cast list, silently reopening the hole
  `reject_key/4` exists to close); rejects a non-nil `:process_definition_id` with
  `{:error, :process_definition_id_not_supported}` (design §3.3's concrete OQ-2
  resolution — would fail if that rejection were ever silently dropped, letting an
  unvalidated cross-tenant-schema reference through); the two sanitization tests (AC2).
- **`update_draft/2`**: updates title/body while still `:draft`; rejects update
  (`{:error, :not_a_draft}`) once the row is `:live` — would fail if the `ensure_draft/1`
  guard were removed or inverted, letting a published row's content be silently
  overwritten without going through `withdraw/1` first; rejects a non-nil
  `:process_definition_id` on update too (not just create — a real second call site for
  `reject_process_definition_id/1`, not assumed to inherit from the create-path test);
  returns `{:error, :not_found}` for an unknown id.
- **`publish/1`**: moves `:draft -> :live` and sets `confirmed_at` from the real clock —
  asserted by bracketing the call with `DateTime.utc_now()` reads taken *before* and
  *after* the call and asserting the stored value falls between them (`:gt`/`:eq` and
  `:lt`/`:eq` respectively), which would fail if `confirmed_at` were ever taken from
  caller-supplied `attrs` instead of `DateTime.utc_now()` (there is no `attrs` parameter
  on `publish/1` at all — its arity is checked directly, `Function.info(&Platform.publish/1,
  :arity)`, so a future signature change that added one would be caught here even before
  any behavioral test ran); `confirmed_for_definition_version` is `nil` after publish
  (design §3.3 — no version to resolve, since `process_definition_id` is always nil);
  returns `{:error, :not_a_draft}` for an already-`:live` row.
- **`reconfirm/1`**: bumps `confirmed_at` on an already-`:live` row while leaving
  `:title`/`:body` **provably unchanged** — asserted by a direct `==` comparison of the
  pre- and post-reconfirm `title`/`body` values (not merely "no error raised"), which
  would fail if `reconfirm/1` ever started re-applying `attrs`-shaped content changes
  instead of only touching `confirmed_at`; `confirmed_for_definition_version` stays `nil`;
  `reconfirm/1` takes no `attrs` parameter (arity check, same reasoning as `publish/1`);
  returns `{:error, :not_live}` for a `:draft` row; returns `{:error, :not_found}` for an
  unknown id.
- **`withdraw/1`**: moves `:live -> :draft`, after which `update_draft/2` succeeds again
  (proves the round-trip, not just the single transition — would fail if `withdraw/1` set
  `status: :draft` but `update_draft/2`'s own `ensure_draft/1` guard were somehow left
  stale/inconsistent with it); returns `{:error, :not_live}` for an already-`:draft` row;
  returns `{:error, :not_found}` for an unknown id.
- **`get_by_screen/1`**: returns only rows matching the given `screen_id`, proven with a
  second, non-matching row present in the same table at the same time (not merely "the
  query runs") — would fail if the `where` clause were ever dropped or widened.

### AC4 — "`help_content.ex`'s own existing tests still pass unchanged after the
markdown-safety extraction (same behavior, moved location)"

**Not duplicated here.** `test/letflow/help_test.exs` (pre-existing, REQ-364, unmodified
by this change) already exercises `Letflow.Help.HelpContent`'s full sanitization surface
end-to-end (all five bypass classes, the three round-3 fixes, the safe-content positive
controls) via `Letflow.Help.create_draft/2`/`update_draft/3`, which now call
`Letflow.Help.MarkdownSafety.validate/2` (the extracted module) instead of a private
in-file function. `help_test.exs` asserts on `Letflow.Help`'s public behavior/error
messages, not on where the validator's code physically lives, so the extraction is
transparent to it — if the extraction had changed behavior (a different error message, a
dropped check, a crash on a case the old code handled), `help_test.exs` would fail exactly
as it did before the extraction. This is confirmed, not assumed: TEST-RUNNER runs
`test/letflow/help_test.exs` as part of the same `mix test`/`mix letflow.check.test` pass
that runs this file, and its own PASS/FAIL is reported in that run rather than being
re-asserted redundantly here.

## Determinism / isolation

- Every `screen_id` is generated via `unique_screen_id/1`
  (`System.unique_integer/1`-suffixed) — no hard-coded identifier shared across tests.
- No test depends on wall-clock time beyond the bounded before/after bracket pattern
  `help_test.exs` already established for `Help.publish/2`/`reconfirm/2` (real clock
  reads taken by the test itself immediately around the call, not a fixed/sleep-based
  assumption about how long the call takes).
- No unseeded randomness.
- `platform_help_content` is a single shared (non-tenant-scoped) table, so every test runs
  inside `Letflow.DataCase`'s sandboxed transaction (`async: false`, matching
  `help_test.exs`'s own choice) — rolled back automatically after each test, no manual
  cleanup needed and no cross-test row leakage despite the shared table.
