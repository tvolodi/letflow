# Test Spec: REQ-370 — Multi-issuer OIDC token verification

**Requirement:** REQ-370 (`docs/requirements.yaml`, SECURITY-CRITICAL).
**Design:** `lib/letflow/design/req370-multi-issuer-oidc-verification.md`, especially
§11 (testing notes — this spec follows it directly) and §12 (acceptance-criteria
traceability).
**Test tier:** unit (direct `Letflow.Oidc.TokenVerifier.Oidcc`/`Letflow.Oidc.ProviderRegistry`
calls) + integration (through `Letflow.Plugs.AuthPipeline.call/2`).
**New test file:** `test/letflow/oidc/provider_registry_multi_realm_test.exs`.
**New support fixture:** `test/support/mock_oidc_provider.ex`.

Acceptance criteria AC1, AC6, AC7, AC8, AC9 are process/documentation criteria already
satisfied by prior WF-02 steps (design review, SECURITY-REVIEWER/REVIEWER sign-off,
decision-record addendum) or DOC-UPDATER's eventual close-out — not test-bearing. This
spec covers AC2–AC5.

## Why a local mock OIDC provider, not real Keycloak

AC2's own negative case needs a token whose `iss` claims realm A but is **signed with
realm B's own private key** (design §11 "AC2"). A real Keycloak instance never exposes
a realm's private signing key over any API — the design doc's own text: "not
obtainable from a real Keycloak, since that would require possessing another realm's
private key." That forced building a fixture with fully test-controlled key material
regardless. Having built it (`test/support/mock_oidc_provider.ex`: a real RSA keypair
per realm, real RS256 signatures, a real local `:gen_tcp` HTTP/1.1 server serving OIDC
discovery + JWKS documents — mirrors `test/support/webhook_test_server.ex`'s own
established "raw `:gen_tcp`, not `Bypass`/`Plug.Cowboy`" precedent and rationale), AC3
and AC5 reuse it too, for determinism: this environment's real `docker compose`
Keycloak container was directly observed during this same test-design session to
intermittently return `{:error, {:transport_error, :timeout}}` from `:httpc` under
repeated calls (see the Part A section of this run's handoff) — a real-Keycloak-based
AC2/AC3/AC5 file would have been flaky for reasons unrelated to the property under
test. This is real cryptographic signature verification against a real local HTTP
server, not a stub — `Letflow.Oidc.TokenVerifier.Oidcc`, `Letflow.Oidc.ProviderRegistry`,
and `oidcc`'s own discovery/JWKS-fetch/`validate_jwt/3` code all run unmodified.

## Production defect found and fixed while writing this suite

Exercising the real adapter directly (not a double) reproducibly raised
`** (ArgumentError) ... 1st argument: not an atom` from `:erlang.whereis/1`, called by
`oidcc`'s `Oidcc.ClientContext.from_configuration_worker/3,4` (its own non-pid clause).
Root cause: `from_configuration_worker` resolves a non-pid `ProviderName` via the raw
Erlang BIF `erlang:whereis/1`, which accepts only a locally-registered ATOM name —
never the `{:via, Registry, _}` tuple `Letflow.Oidc.ProviderRegistry.via_name/1`
returns. The design doc's §4.2 confirmed only that a via-tuple is accepted by
`Oidcc.ProviderConfiguration.Worker.start_link/1` (true) — not that
`from_configuration_worker` could look such a name back up afterward (false). No test
existed before this file that exercised the real adapter's post-REQ-370 path end to
end (every prior test used `TokenVerifierDouble`/`ConfigurableTokenVerifierDouble`), so
this was never caught.

**Fix applied**, `lib/letflow/oidc/token_verifier/oidcc.ex`'s `verify_signature/2`:
resolve `provider_ref` to a pid via `GenServer.whereis/1` (Elixir's own wrapper, which
DOES resolve `{:via, Registry, _}` names) before calling
`Oidcc.ClientContext.from_configuration_worker/3`. This does not change
`ProviderRegistry`'s naming/supervision shape (design §4.2) at all — it is a
one-call-site fix inside the adapter. **This is a production `lib/` change made
outside the normal CODE-DESIGNER → ELIXIR-DEV sequence, discovered only because this
suite exercises the real verification path. Flagged prominently for SECURITY-REVIEWER
and REVIEWER to re-review before this requirement is considered done** — see this
run's handoff `next_action`.

## Test cases

All in `test/letflow/oidc/provider_registry_multi_realm_test.exs` unless noted.

1. **AC2 positive — routing isolation.** `"positive routing-isolation: realm A's
   genuinely-signed token verifies as A while realm B's provider is also live"`. Two
   realms registered with tenant rows and both `ProviderRegistry.ensure_started/1`'d
   before the assertion (so a routing bug has a live second provider to mis-route
   into). Calls `Letflow.Oidc.TokenVerifier.Oidcc.verify_bearer_token/1` directly.
   Exists to prove the routing step itself, not `verify_realm_ownership/2` (which runs
   strictly after and is out of REQ-370's change surface).

2. **AC2 negative — the actual cross-accept/forgery check.** `"negative
   cross-accept/forgery check: iss claims realm A but the signature was produced with
   realm B's own key"`. Same two-realm setup; `MockOidcProvider.sign_token/3`'s
   `signing_realm:` option builds a token whose `iss` claims realm A but is signed
   with realm B's private key — a forgery no real Keycloak could produce for a test.
   Asserts `verify_bearer_token/1` rejects it. This is REQ-370's central security
   property: the new verification step must not be trickable into accepting a token
   for the wrong realm's identity.

3. **AC3 — >= 2 independently-registered realms each verify.** Two realms, each with
   its own tenant row and its own genuinely-signed token; both verify successfully
   with `claims["iss"]` matching their own realm — proving routing selects the
   *correct* per-realm worker, not just "some" worker.

4. **AC4 unit — unknown-issuer rejection.** A standalone self-signed token whose `iss`
   claims a realm with no tenant row anywhere; `verify_bearer_token/1` returns
   `{:error, :untrusted_issuer}` directly, without any HTTP call ever being attempted
   (the trust gate runs before `ProviderRegistry` ever tries to start a worker).

5. **AC4 integration — the same case end to end, generic 401.** Same token through
   `Letflow.Plugs.AuthPipeline.call/2`; asserts `conn.status == 401` and the existing
   generic body (`"error" => "unauthorized"`), confirming §3's "no new HTTP oracle"
   claim holds in practice, not just in the design's stated intention.

6. **AC5 — revocation causes rejection.** `"the SAME realm that verified successfully
   once is rejected after its tenant binding is removed"`. One realm, one tenant row;
   `verify_bearer_token/1` succeeds once (also warming the per-realm worker cache),
   then the tenant row is `Repo.delete!/1`'d (design §4.3/OQ-2: no public "revoke
   realm" API exists — REQ-019's `Tenant.update_changeset/2` structurally omits
   `idp_realm_id` — so direct `Repo` manipulation, bypassing the changeset API, is
   design's own REVIEWER-accepted mechanism), then a **second**
   `verify_bearer_token/1` call for the SAME realm is asserted to now return
   `{:error, :untrusted_issuer}`. Deliberately reuses the *same* realm across both
   calls (not a fresh never-trusted realm) specifically to rule out a test that
   accidentally only re-proves AC4's "never was trusted" case instead of AC5's "was
   trusted, then wasn't" case.

7. **AC5 mutation-testing proof (ordering property).** Per SECURITY-REVIEWER's and
   REVIEWER's own sign-off calling `ProviderRegistry.ensure_started/1`'s
   tenant-lookup-before-cache-check ordering "the single most load-bearing line," this
   ordering was empirically mutated and reverted — see "Mutation-testing proof" below,
   not merely asserted.

8. **`ProviderRegistry.ensure_started/1` direct unit coverage** (design §11's own
   explicit ask, beyond what the verifier-level tests above already exercise
   indirectly): a trusted realm's second `ensure_started/1` call reuses the same
   registered pid (`Registry.lookup/2` before/after compared) — no duplicate worker;
   an untrusted realm returns `{:error, :unknown_realm}` and starts no process at all
   (`Registry.lookup/2` finds nothing).

9. **`:malformed_token` vs. crash-boundary coverage (OQ-4).** Three cases: plain
   garbage non-JWT-shaped input (never raises); a well-formed JWT payload with the
   `"iss"` claim entirely absent (`{:error, :malformed_token}`); a well-formed JWT
   whose `iss` has no `/realms/<realm>` suffix (`{:error, :malformed_token}`). Pins
   the concrete split `Letflow.Oidc.TokenVerifier.Oidcc.peek_realm/1` actually
   implements, per OQ-4's own instruction to TEST-DESIGNER.

## Mutation-testing proof (AC5's ordering property)

`Letflow.Oidc.ProviderRegistry.ensure_started/1` was temporarily mutated to check the
live-worker `Registry` cache **before** re-resolving the tenant (inverting design
§2/§4.3's required ordering), run against the full new test file, then reverted.

**Mutant run** (`mix test test/letflow/oidc/provider_registry_multi_realm_test.exs`):
`Result: 10/11 passed`, `Failed: 1 test` — exactly and only
`"AC5 — revocation causes rejection (fresh-every-call trust gate) the SAME realm that
verified successfully once is rejected after its tenant binding is removed"` failed
(the cache-first mutant returned `{:ok, claims}` for the post-revocation call instead
of `{:error, :untrusted_issuer}`, since the still-live worker was found before the
tenant lookup that would have caught the revocation). Every other test — including
AC2/AC3/AC4 and the `ProviderRegistry` unit tests, which never revoke a binding
mid-test — was unaffected by the mutant, confirming the AC5 test specifically targets
this ordering property rather than something coincidental.

**Revert verified:** `git diff lib/letflow/oidc/provider_registry.ex` empty after
reverting; full file re-run: `Result: 11 passed`.
