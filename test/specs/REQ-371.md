# Test Spec: REQ-371 — Operator-facing rollback/withdrawal screen

**Requirement:** REQ-371 (`docs/requirements.yaml`).
**Design:** `lib/letflow/design/req371-rollback-withdrawal-screen.md`.
**Test tier:** Vitest unit (component-level, `web/src/pages/definitions/`) +
Playwright e2e (`web/tests/e2e/pipelines/`).

This spec covers the rework requested by TEST-DESIGN-VALIDATOR on branch
`feature/WF02-REQ371-20260919`: AC1 had zero test coverage (no test ever clicked the
button, asserted its visibility conditions, or asserted its absence), and the "Other
version…" manual-entry branch of AC2's UI was covered only by the e2e spec, not
Vitest. AC2–AC7 backend/flow coverage predates this rework and already exists in
`test/letflow/definitions/rollback_test.exs`,
`web/src/api/__tests__/definitionRollback.test.ts`, and
`web/src/pages/definitions/__tests__/DefinitionRollbackPage.test.tsx` — not
re-described here beyond what changed.

## AC1 — "a rollback/withdraw action is reachable from the process detail /
version-history view in web/src for any version the backend accepts, gated to the
same role(s) DefinitionListPage.tsx already uses for destructive definition actions"

**New file:** `web/src/pages/definitions/__tests__/DefinitionListPage.test.tsx`.

The actual gating condition, read directly from `DefinitionListPage.tsx:211`, is
`def.status === 'ACTIVE' && isPlatformAdmin` — narrower than
`DefinitionListPage.tsx`'s own `DESIGNER_ROLES` (`PROCESS_DESIGNER`,
`PLATFORM_ADMIN`) used for Activate/Archive; the button code comment at line 41-44
explains this divergence is deliberate (rollback's backend route is
`PLATFORM_ADMIN`-only). The acceptance criterion's "same role(s)... already uses for
destructive definition actions" phrase does not mean literally identical role list —
it means the button must be visibly gated using the pattern already established on
this page, not silently ungated. Tests assert the concrete, current condition rather
than a guessed/looser one.

Test cases:

1. **TC-REQ371-07a** — `btn-rollback-${id}` renders for an ACTIVE-status row when the
   session has `PLATFORM_ADMIN`. Exists to prove the happy path is wired at all.
2. **TC-REQ371-07b** — `btn-rollback-${id}` is absent for a non-ACTIVE (`DRAFT`) row,
   even as `PLATFORM_ADMIN`. Exists because the button's condition is a compound `&&`
   — a test that only ever supplies an ACTIVE row could pass even if the status check
   were accidentally dropped from the JSX.
3. **TC-REQ371-07c** — `btn-rollback-${id}` is absent for a non-`PLATFORM_ADMIN`
   session (`PROCESS_DESIGNER`), even on an ACTIVE row. Exists because
   `PROCESS_DESIGNER` legitimately sees Activate/Archive on the same row via
   `DESIGNER_ROLES` — this is the specific negative case that would catch a regression
   where rollback was accidentally gated on `hasDesignerRole` instead of
   `isPlatformAdmin`.
4. **TC-REQ371-07d** — clicking the button calls `navigate('/definitions/:id/rollback')`
   with the exact id. Exists to prove "reachable" is a real navigation, not just a
   rendered-but-dead button.

## AC2 (UI sub-case) — "Other version…" manual-entry branch

**Extended file:** `web/src/pages/definitions/__tests__/DefinitionRollbackPage.test.tsx`.

Previously this branch (`DefinitionRollbackPage.tsx`'s `OTHER_VERSION_SENTINEL`
handling, lines 157–199) was exercised only by e2e step 5, not Vitest. Added:

5. **TC-REQ371-07** — selecting `Other version…` swaps the `<select>` for the manual
   `<input data-testid="rollback-target-version-manual">`. Exists to prove the branch
   toggle itself works, independent of what's typed into it.
6. **TC-REQ371-08** — typing into the manual input drives `canContinue` the same way
   the dropdown does (Continue stays disabled until a reason is also filled), and the
   typed value flows into the confirmation dialog's text. Exists to prove
   `targetVersionManual` state is actually read by `targetVersion`/`canContinue`, not
   just stored and ignored.
7. **TC-REQ371-09** — "Choose from the list instead" reverts to the dropdown with an
   empty selection, and re-entering manual mode shows a blank input (not the
   previously-typed value). Exists to prove the cancel handler's
   `setTargetVersionManual('')` actually clears state rather than merely hiding the
   input while the stale value lingers underneath — a bug that would otherwise be
   invisible in the DOM the first time around.

## AC1 end-to-end reachability

**Changed file:**
`web/tests/e2e/pipelines/platform-definition-promotion-rollback.pipeline.e2e.spec.ts`,
step 3. Previously navigated straight to `/definitions/:id/rollback` via URL, which
cannot distinguish "reachable via a real click" from "only reachable by a bookmark."
Step 3 now searches for the definition on `/definitions`, waits for its row, and
clicks `btn-rollback-${definitionIdV2}` before asserting `waitForURL` lands on the
rollback route — the same button asserted directly in TC-REQ371-07a/d above. Step 5
(the never-active-version refusal case) still navigates by URL, since it is testing
the refusal behavior, not reachability, and AC1's claim is already proven by step 3.
