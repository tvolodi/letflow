## Acceptance-criteria -> test-case mapping

### AC1 — undeclared-variable violation names the exact typed variable name and the step/edge it belongs to

**Test**: `semantic_validation_test.exs`, describe `"validate/2 (AC1) -- undeclared
variable reference names the exact typed variable and its edge/step"`, test `"a
gateway edge condition referencing a variable absent from declared_fields produces
:undeclared_variable_reference naming the edge id, source node id, and the exact
typed variable name"`.

**Why this test exists**: this is the core mechanism AC1 requires — the design's own
§2.2 violation shape embeds `edge.id`, `edge.source`, and `hd(path)` **verbatim as
authored** into the message. The test asserts on `edge.id` ("Edge 'e1'"), the source
node id ("EXCLUSIVE_GATEWAY node 'gw'"), and the exact misspelled string
(`'cusotmer_name'`, not a corrected or normalized form) all appearing in the single
produced violation's message, and that the violation code is
`:undeclared_variable_reference`. If the implementation ever dropped the edge/step
identification, or normalized/corrected the typed name before reporting it, this
test would fail.

### AC2 — the violation's suggested nearest declared field name, via a real string-distance measure, one-typo case

**Tests**:
- `semantic_validation_test.exs`, describe `"validate/2 (AC2) -- suggested nearest
  declared field name via real string-distance"`, test `"'cusotmer_name' typed
  against a declared 'customer_name' field suggests 'customer_name' by name in the
  violation message"` — the exact AC2 worked example, asserting the literal substring
  `"nearest declared field: 'customer_name'"` appears in the violation message.
- Same describe, test `"with zero declared fields, no suggestion clause is emitted at
  all"` — proves the `nil`-suggestion path (no fields to suggest) omits the clause
  entirely rather than emitting a placeholder like `"nearest declared field: none"`.
- describe `"levenshtein_distance/2 and nearest_declared_field/2 (AC2) -- real
  edit-distance measure, not a placeholder or first-alphabetical fallback"`, four
  tests:
  - `levenshtein_distance/2` computes real Wagner-Fischer distances for several known
    pairs (`"cusotmer_name"`/`"customer_name"` = 2, `"kitten"`/`"sitting"` = 3,
    identical strings = 0, one string empty = the other's length) — proves it is a
    genuine edit-distance algorithm, not a stub returning a constant.
  - case-sensitivity: `"Customer_Name"` vs `"customer_name"` is 2 substitutions, not
    0 — proves the design's explicit case-sensitivity decision (a case-only typo must
    not be silently treated as "identical").
  - `nearest_declared_field/2` picks the true minimum-distance candidate over a
    farther-but-alphabetically-first one (`"custname"` against
    `["zzz_field", "amount", "customer_name"]` picks `"customer_name"`, not
    `"amount"`) — this is the test that would catch a first-alphabetical-fallback
    regression, which AC2 explicitly forbids.
  - deterministic alphabetical tie-break among equidistant candidates, and `nil` on
    an empty candidate list.

**Why these tests exist**: AC2's own wording explicitly rules out "a placeholder or
first-alphabetical fallback" — the "farther but alphabetically first loses" test is
the one that actually distinguishes a real string-distance measure from a fallback
that happens to produce a plausible-looking answer on the single worked example.

### AC3 — non-comparable type pair (numeric/money vs. text/string, at minimum) produces a violation; the table is stated explicitly in the moduledoc

**Tests**: `semantic_validation_test.exs`, describe `"validate/2 (AC3) -- non-comparable
type-pair produces :incompatible_comparison_operand_types"`, six tests:
- numeric vs. string is flagged (the explicit AC3 floor), asserting the violation
  message names both resolved families (`"(numeric)"`, `"(string)"`) and the CEL
  operator spelling (`"=="`).
- an `:integer`-declared field is also `:numeric` for comparability (money-by-convention,
  no distinct money type — per the design's own re-verification and the moduledoc's
  table).
- two same-family fields (`number` vs `number`) are comparable — no violation. This
  proves the table's **OK** cells are tested too, not only its VIOLATION cells (a test
  suite asserting only "X vs Y is a violation" everywhere could pass even if the
  implementation flagged everything indiscriminately).
- a `field == null` guard is exempt regardless of the field's declared type.
- `array`-typed fields are never comparable, including against their own family (an
  extra table cell beyond the AC3 floor, proving the moduledoc's stated
  "never comparable, including with themselves" claim).
- an operand that is itself undeclared is exempt from the type table (already
  independently reported by the field-existence check on the same edge — no
  redundant second violation).

**Why these tests exist**: AC3 requires both "the violation fires" (floor case) and
"the table is stated explicitly... not left implicit" — the moduledoc states the full
5x5 table in prose; these tests are what proves the moduledoc's claims are actually
what the code does, for both the OK and VIOLATION halves of the table, plus the
documented exemptions (null literal, unresolved operand).

### AC4 — two independent broken rules (one field-existence, one type-compatibility) produce BOTH violations from a single validate/2 call

**Tests**: `semantic_validation_test.exs`, describe `"validate/2 (AC4) -- both violation
classes from a single call when a definition has one of each"`, two tests:
- two separate gateway edges, one with an undeclared-variable condition, one with a
  type-incompatible comparison — a single `validate/2` call returns both violation
  codes (asserted via `Enum.sort/1` equality against both codes, so this would fail if
  either check ever became early-returning/short-circuiting across edges).
- the harder case: a **single edge's single condition** triggers both violation
  classes at once (`"cusotmer_name == \"x\" and amount == customer_name"`) — proves
  the "collects across the whole graph in one pass, `Enum.flat_map/2`, no early
  return anywhere in the call chain" design claim (§1.2) at the finest possible
  granularity, not just across edges.

**Why these tests exist**: AC4's own wording is "the author is never required to fix
one to discover the other" — the only way to actually prove that is a single
`validate/2` call surfacing both codes at once; a test issuing two separate calls
(one per violation) would prove nothing about this requirement.

### AC5 — a definition with zero semantic violations validates cleanly, including after both AC4 violations are corrected in the same test

**Tests**: `semantic_validation_test.exs`, describe `"validate/2 (AC5) -- zero
violations validates cleanly, including after both AC4 violations are corrected"`,
two tests:
- a fresh, fully clean fixture validates to `%{valid: true, violations: []}`.
- **the fix-path test**: starts from the exact AC4 broken definition (one
  field-existence + one type-compatibility violation, asserted broken first), then
  corrects BOTH problems in the same test (`cusotmer_name` -> `customer_name`,
  `amount == customer_name` -> `amount == 100`), and re-validates the corrected graph
  clean in the same test body.

**Why this test exists**: the handoff explicitly calls out that AC5's test must
"start from the broken definition in test 4, correct BOTH violations, and re-validate
clean in the same test" — a fresh-fixture-only test would not prove the fix path
actually clears the specific violations previously raised, only that some other
already-clean graph validates clean (a much weaker claim).

### AC6 — the semantic validation pass re-runs in full (not from a cached prior result) at the definition's actual release/promotion submission call path

**Tests**: `semantic_validation_activation_test.exs`, describe `"activate/2 (AC6) --
re-runs semantic validation in full, never a cached prior result"`, two tests:
- **THE RE-RUN-NOT-CACHED TEST**: `"clean earlier read, variable_schemas type mutated
  with no cache-invalidation hook, activate/2 blocks for the NEW reason (not the
  earlier clean result)"`. Sequence: create a draft definition whose one gateway
  condition is `"amount > 100"`; seed `variable_schemas` with `amount: number` (clean);
  call `validate_definition_graph/2` and assert `valid: true, violations: []` (the
  "earlier clean validation"); then mutate the `variable_schemas` row **directly via
  `Repo.update_all/3`** (not through `VariableSchema`'s own changeset/upsert path, and
  through no cache-invalidation hook of any kind — none exists anywhere in this path
  per the design's own re-verification) to redeclare `amount` as `string`, which makes
  the *same* condition's `amount > 100` comparison numeric-vs-string incompatible;
  then call `Definitions.activate/2` and assert it returns
  `{:error, {:semantic_validation_failed, [%Violation{code:
  :incompatible_comparison_operand_types}]}}` — the NEW reason, not the earlier
  `valid: true` result — and that the definition's row is still `:draft` (rejected,
  never transitioned). This is the direct mechanical proof: if `activate/2` ever
  cached or reused the earlier `validate_definition_graph/2` result (or any prior
  computation) instead of issuing its own fresh `fetch_schemas/3` read inside its own
  transaction, this test would see `activate/2` wrongly succeed.
- **Reverse-direction companion**: `"reverse: variable_schemas starts undeclared, is
  seeded afterward, activate/2's fresh read reflects the new clean state"`. Same
  condition, but `variable_schemas` starts with **no** row for `amount` at all (an
  earlier `validate_definition_graph/2` call sees `:undeclared_variable_reference`);
  the field is then declared for the first time; `activate/2` is called once and
  succeeds (`already_active: false`, `status: :active`). This is the mirror-image
  proof — AC6 requires the fresh read to reflect **either** direction of change (newly
  invalid **or** newly valid), and testing only the "goes invalid" direction would
  leave open the possibility that `activate/2`'s check is a one-way ratchet (e.g. an
  implementation that caches "first-seen-invalid, stays blocked" while still passing
  the first test).

Both tests seed/mutate `variable_schemas` by direct `Repo` operations, deliberately
bypassing any application-level write path, precisely because AC6's own wording is
"without going through any cache-invalidation hook" — using `Definitions`' own APIs to
change declared fields would not test the no-cache claim, since any real
cache-invalidation hook (if one existed) would fire on that path.

### AC7 — HUMAN_TASK routing/assignment-by-field scope is stated explicitly in the moduledoc with reasoning, not left for tests to imply

No test is required to prove the HUMAN_TASK-in-scope decision itself — that is a
moduledoc/doc criterion (verified by reading
`lib/letflow/definitions/semantic_validation.ex`'s moduledoc "HUMAN_TASK
routing/assignment-by-field: OUT OF SCOPE" section directly, which states the decision
and the grep-verified reasoning in prose).

One test exists that is deliberately **not** presented as proof of AC7, but as a
scope-boundary regression guard that does not imply HUMAN_TASK routing is covered:
`semantic_validation_test.exs`, describe `"validate/2 (AC7 scope boundary) -- a
HUMAN_TASK-sourced edge condition is never walked by this pass"`, test `"an edge
sourced from a HUMAN_TASK node carrying an undeclared-variable-referencing condition
produces no violation"`. This proves the *opposite* of "HUMAN_TASK routing is
validated" — it shows HUMAN_TASK-sourced conditions are outside this pass's edge
selection entirely, which is consistent with (and does not substitute for) the
moduledoc's own explicit statement of the AC7 decision.

## Anti-pattern check (ISS-0069)

Neither new test file defines a private helper with an optional/default argument that
ends up unused at every call site. `semantic_validation_activation_test.exs`'s
`provisioned_tenant/1` originally had a `\\ %{}` default (copied from
`store_test.exs`'s own convention for a context-ignoring `setup` callback) but every
actual call site (`setup :provisioned_tenant`, called by ExUnit with a context map)
supplies an argument, so the default was dead and was removed during this run's own
`mix test` sanity pass (caught directly, live, not merely asserted) — the parameter is
now a required `_context` with no default.
