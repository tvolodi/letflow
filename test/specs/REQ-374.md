### A note on real, committed test data (both files)

`platform_migration_rollouts` carries a DB-level unique index on
`(entity_type, attribute)` (design doc §3.1) — this is the natural key EO-005
depends on. `Letflow.TenantFixture.provisioned_tenant!/1` forces
`Sandbox.mode(Letflow.Repo, :auto)` (real commits, not per-test rollback), so
two tests both targeting the same `(entity_type, attribute)` pair would
silently share one rollout row and corrupt each other's assertions. Every test
below therefore mints its own attribute name via a `unique_attribute/1` helper
and deletes its own rollout/outcome/column-promotion rows in `on_exit/1`,
registered *after* every company fixture in that test so it runs *before* any
company's own `TenantFixture` teardown (`on_exit/1` callbacks run
most-recently-registered-first) — `platform_migration_rollout_outcomes.tenant_id`
and `entity_column_promotions.tenant_id` both carry a real FK to `tenants`
(`on_delete: :nothing`), so those rows must be deleted before the tenant row
is, or teardown itself raises a foreign-key violation.

## Acceptance-criteria -> test-case mapping

### EO-001 — one company's real DDL failure isolates from the rest

**Test**: `migration_rollout_test.exs`, describe
`"EO-001/EO-002 -- one company's real DDL failure isolates from the rest"`,
test `"every other active company holds the change; the poisoned company is
recorded FAILED with a plain reason (EO-001)"`.

**Why this test exists**: this is the requirement's own headline guarantee.
Three real tenant schemas are provisioned; one is pre-poisoned by hand-creating
its `entity_invoice` table with a same-named, conflicting-type column (bigint,
not the promoted `text`) — the exact real-DDL technique
`test/letflow/tenant_provisioning/column_promotion_test.exs`'s own AC2 describe
block already established, so `check_additive_only/3` rejects it via a real
`information_schema` read, never a test double. `start_rollout/3` is called
once against all three; the test asserts the two clean companies land
`"succeeded"` with `reason: nil`, the poisoned one lands `"failed"` with a
reason string that names the real conflicting/requested types, and the
rollout itself stays `status: "running"`/`completed_at: nil` (still
resumable) because one company remains outstanding.

### EO-002 — the failing company's workspace holds none of the change, and a real write succeeds immediately afterward

**Test**: same describe block, test `"the poisoned company's schema holds none
of the change, and a real write against it succeeds immediately afterward
(EO-002)"`.

**Why this test exists**: EO-001 alone would not catch a partial-DDL leak. This
test queries `information_schema.columns` directly against the poisoned
tenant's own schema (not the outcome row, not the rollout API) and asserts the
promoted column is absent while the clean company's column is genuinely
`text` (a contrast case, not merely an absence check). It then performs a real
`Letflow.Entities.Records.create_record/2` call against the poisoned schema
and asserts it succeeds — the literal mechanism the requirement text names
("a real write ... succeeding immediately").

### Queryable outcome record — completion timestamp + reason, per rollout_id

**Test**: `migration_rollout_test.exs`, describe `"queryable outcome record --
completion timestamp + reason, per rollout_id"`, test `"rollout_status/1
returns every outcome with a completion timestamp, a reason for the failed
one, and 404s for an unknown id"`.

**Why this test exists**: this is AC3's own literal contract (supports EO-003's
screen, REQ-375). Calls `rollout_status/1` — the pure read path, independent of
`start_rollout/3`'s own return value — and asserts every outcome carries a
`NaiveDateTime` `completed_at`, the failed one carries a non-empty `reason`
string, and a random/nonexistent rollout id returns
`{:error, :rollout_not_found}` rather than raising or returning stale data.

### EO-004 — resume applies only to not-yet-SUCCEEDED companies

**Test**: `migration_rollout_test.exs`, describe `"EO-004 -- resume_rollout/1
applies only to not-yet-SUCCEEDED companies"`, test `"already-succeeded
companies show no second write; the corrected company's outcome flips to
succeeded"`.

**Why this test exists**: this is the design's own most load-bearing
correctness property — a `resume_rollout/1` that re-touches an
already-succeeded company's row would silently corrupt EO-004's own contract.
After EO-001's failure state, the poisoned company's schema is corrected (the
conflicting column dropped) and `resume_rollout/1` is called. The test asserts
the corrected company flips to `"succeeded"` with `reason: nil`, while the
already-succeeded company's outcome is asserted byte-identical to its
pre-resume value — `status`, `completed_at`, AND `reason`, via direct struct
equality, not merely "still succeeded" (design §8's own explicit instruction)
— checked against both the returned summary map and a fresh `Repo.get_by!/2`
load, so the proof isn't confined to the in-memory return value. Not asserted
via `completed_at != completed_at_before` for the corrected company:
`naive_now/0` truncates to the second (design §3.2), so a fast resume in the
same wall-clock second can legitimately produce an identical value, and
asserting inequality there would make the test depend on wall-clock timing —
forbidden by this project's own test-design rules. The status/reason
transition is the real, timing-independent proof a write occurred.

### EO-005 — starting the identical rollout again performs zero writes, every company already-current

**Test**: `migration_rollout_test.exs`, describe `"EO-005 -- starting the
identical rollout again once every company already holds the change"`, test
`"performs zero writes and reports every company as already-current"`.

**Why this test exists**: this is the idempotent-re-run contract, and the
literal wording is "zero writes" — not "results look the same." After a
rollout completes fully, `start_rollout/3` is called again with the identical
`entity_type`/`attribute`/`column_spec`. The test asserts every returned
outcome carries `already_current: true`, every outcome's `completed_at` is
byte-identical to its pre-call value, the rollout row's own `completed_at` is
unchanged, and — the literal "zero writes" proof — `Repo.aggregate(Rollout,
:count, :id)` and `Repo.aggregate(Outcome, :count, :id)` are identical before
and after the call.

### Permission-gating AC — rollout endpoints gated behind :TenantsManage

**Tests**: `platform_migrations_test.exs`, describe `"permission gate --
non-PLATFORM_ADMIN caller"` (four tests: `POST /rollouts` returns 403 and
creates no rollout row; `GET /rollouts/:id` and `POST /rollouts/:id/resume`
both return 403 even for a nonexistent id, proving the domain layer is never
reached; a caller with no roles at all is rejected the same way) and describe
`"permission gate -- PLATFORM_ADMIN caller"` (`POST /rollouts`, `GET
/rollouts/:id`, and `POST /rollouts/:id/resume` all succeed end-to-end against
one real, provisioned company; `GET /rollouts/:id` returns 404, not 403, for
an unknown id once the permission check has already passed).

**Why these tests exist**: the requirement's own AC names both directions
explicitly ("proven by a test" — both a positive case with the permission and
a negative 403 case without it). The negative-case row-count assertion
(`Repo.get_by(Rollout, ...) == nil` after a 403) proves the rejection happens
*before* any domain call, not merely that the HTTP status is right. The 404
case in the positive describe block proves the permission gate and the
domain-level not-found handling are genuinely two separate layers, not
conflated.

**Test**: same file, describe `"moduledoc states the permission decision by
name"`, test `"Letflow.Routers.PlatformMigrations's moduledoc names
:TenantsManage and its reasoning"`.

**Why this test exists**: the requirement's own AC text: "stated in the
moduledoc." Asserts (via `Code.fetch_docs/1`, the same technique
`column_promotion_test.exs`'s own AC6 describe block uses) that the compiled
moduledoc contains `:TenantsManage` and `PLATFORM_ADMIN` by name, not merely
that the router happens to enforce that permission at runtime.

### PLUS — registration-time conflict (REVIEWER finding, WF02 rework)

**Test**: `migration_rollout_test.exs`, describe `"registration-time conflict
-- a pre-existing entity_column_promotions row for the target pair"`, test
`"the company is recorded failed with a plain reason, not silently absent
from rollout_status/1"`.

**Why this test exists**: this is a direct regression test for the bug
REVIEWER caught and ELIXIR-DEV fixed
(`Letflow.Platform.MigrationRollout.record_registration_conflict/5`) — before
the fix, a company that already held an `entity_column_promotions` row for the
target `(entity_type, attribute)` (a registration-time conflict, distinct from
EO-001's DDL-time conflict) fell through a `with`'s missing `else` clause
silently: the company ended up with **no outcome row at all**, not `pending`,
not `failed` — absent from `rollout_status/1` entirely, breaking AC1/EO-001's
"the failing company recorded FAILED with a plain reason" contract for this
failure class.

A pre-existing `ColumnPromotion` row is inserted directly for one company
before `start_rollout/3` is ever called (modeling "a tenant already holds a
matching row from an earlier, non-rollout registration" — the module's own
comment on this exact scenario). The test also poisons that company's own
schema (EO-001's technique) so the underlying, otherwise-healthy `"pending"`
promotion's DDL retry — which `apply_outstanding/1`'s own `status !=
"succeeded"` query picks back up in the *same* `start_rollout/3` call, since
`register_and_seed_outcome/5` runs for every tenant before `apply_outstanding/1`
runs — also genuinely fails, so the final state stays `"failed"` rather than
self-healing into `"succeeded"` within the same call and masking the very
outcome-row-creation bug this test exists to guard. The test asserts the
outcome row is not `nil`, is `"failed"`, carries a non-empty, human-readable
reason (explicitly `refute`ing that it is a raw `#Ecto.Changeset<...>` struct
dump — the exact defect `describe_failure_reason/1`'s
`%Ecto.Changeset{}` clause was added to fix, REVIEWER finding #2), confirms
the same via the independent `rollout_status/1` read path, and confirms an
unrelated, unconflicted company in the same rollout still succeeds normally
(the conflict is isolated to the one company, matching EO-001's own isolation
guarantee).

### PLUS — crash-recovery catch-up branch (design §4.4/§5.2)

**Test**: `migration_rollout_test.exs`, describe `"crash-recovery catch-up --
apply_outstanding/1's terminal-success branch"`, test `"resume_rollout/1
catches an outcome row up to a ColumnPromotion that already succeeded,
without re-issuing DDL"`.

**Why this test exists**: `apply_one_outcome/1`'s three-branch dispatch on the
underlying `ColumnPromotion`'s own status (`"pending"` → run DDL; `"ddl_failed"`
→ retry; `"ddl_applied"`/`"backfilling"`/`"backfilled"`/`"active"` → catch up
the outcome row *without* re-entering the advisory-locked DDL path) is the
mechanism that survived two CODE-DESIGN-VALIDATOR rounds specifically because
of the crash window between step 1 (DDL commit) and step 2 (outcome-row
write) in `apply_outstanding/1` — design §5.2's own explicit rationale for why
those two steps are deliberately separate transactions. This test constructs
that exact window directly: `TenantProvisioning.register_column_promotion/4` +
`run_column_promotion/1` are called directly (bypassing `MigrationRollout`
entirely) so the `ColumnPromotion` row reaches `"ddl_applied"` for real, then
the rollout/outcome bookkeeping rows are inserted by hand with the outcome
still `"pending"` — reproducing "the DDL already committed, the outcome-row
write never happened" state a crash between those two steps would leave
behind. `resume_rollout/1` is then called, and a `:telemetry` handler on
`[:letflow, :repo, :query]` (the same invocation-proof technique
`column_promotion_test.exs`'s own backfill-invocation test uses) asserts no
`ALTER TABLE` statement is issued during the call — direct proof the catch-up
branch fired instead of re-attempting DDL, not merely that the end state
happens to look correct (which an accidental second DDL attempt succeeding
idempotently could also produce, masking a regression in this exact branch).
