## AC1 — "the rollout-status screen renders one row per company with outcome,
completion time, and reason for non-succeeded companies, matching EO-003's evidence
requirement"

**File:** `web/src/pages/admin/platform-migrations/__tests__/PlatformMigrationConsolePage.test.tsx`.

- **TC-REQ375-17** — renders one `rollout-outcome-row-{tenant_id}` per outcome; a
  `succeeded` row's `rollout-outcome-reason-*` cell is empty and its
  `rollout-outcome-completed-*` cell is a real formatted timestamp; a non-succeeded
  (`failed`) row's reason cell carries the server's own reason string verbatim and its
  completed-at cell is the `—` placeholder. Exists to prove `RolloutOutcomeRow`'s field
  mapping (design §7) is wired for both branches of the "reason only for non-succeeded"
  rule — a test that only ever renders a succeeded row could pass even if the
  conditional were inverted or dropped.

**File:** `web/tests/e2e/pipelines/platform-migration-partial-failure-resume.pipeline.e2e.spec.ts`,
step 02 — asserts the same row-level fields (status badge, reason non-empty, completed-at

REAL succeeded rows for the two healthy companies. This is what makes AC1 real end to
end, not just against a hand-crafted fixture.

## AC3 — "re-running a fully-succeeded rollout renders a no-op result (EO-005)
distinguishable from a fresh run"

**File:** `PlatformMigrationConsolePage.test.tsx`.

- **TC-REQ375-15** — a fresh-run response (not every outcome `already_current`) shows
  `rollout-fresh-run-banner` and NOT `rollout-noop-banner`.
- **TC-REQ375-16** — a no-op response (every outcome `already_current: true`) shows
  `rollout-noop-banner` INSTEAD OF `rollout-fresh-run-banner` — the two are asserted as
  mutually exclusive in both directions (each test asserts the other banner's absence),
  matching design §5's "mutually exclusive" claim directly rather than trusting it.
- **TC-REQ375-18** — `isNoOpResult` is scoped to the **start** mutation's own response
  only: a resume response is deliberately crafted in this test to ALSO report every
  outcome as `already_current: true` (an adversarial case a resume response would never
  really produce, per design §5's own nuance — chosen specifically to isolate the
  screen's own gating from what the backend happens to promise) and asserts neither
  banner renders after a resume. Exists because the implementation comment at
  `PlatformMigrationConsolePage.tsx:269-271` states this scoping as a deliberate
  invariant (`lastAction === 'start'` gates both banners) — without this test, a
  regression that ran `isNoOpResult` against `lastAction === 'resume'` too would pass
  every other test silently, since a real resume response never actually exercises the
  bug in practice.

**e2e:** step 06 is the literal EO-005 scenario step — re-submitting the identical form
values against the real backend once every company holds the change, asserting the real
no-op banner and that every row's completed-at is byte-identical to before the re-run
(EO-005's "alters nothing").

### Two real gaps this spec had to solve itself (both found by UAT-RUNNER's live runs, not by static reading alone)

**Gap 1 — isolating exactly one company's failure.** REQ-374's `start_rollout/3` has no
per-company scope parameter — confirmed by reading
`lib/letflow/platform/migration_rollout.ex`'s `active_company_tenant_ids/0` (every
`:active` tenant with a Registration row, unconditionally) and
`lib/letflow/routers/platform_migrations.ex`'s request body (`entity_type`/`attribute`/
`column_spec` only, no tenant filter). There is therefore no real HTTP-only way to make
exactly one company's schema fail `Letflow.TenantProvisioning.check_additive_only/3`'s
real `information_schema.columns` check while every other company succeeds — the ONLY
real failure route is a pre-existing, same-named column of a conflicting type, which
requires DDL that ran before the rollout call.

`test/letflow/platform/migration_rollout_test.exs`'s own `poison_company_schema!/3`
solves this identical problem in the ExUnit suite with a direct `Repo.query!/2` CREATE
TABLE. `web/tests/e2e/db-exec.ts`'s `runSqlAgainstDevPostgres` is the Playwright-side
equivalent of that exact technique — it shells into the already-running `docker compose`
`postgres` service via its own `psql` client (zero new npm DB-client dependency; `docker
compose` + the `postgres` service are already this repo's own standard local/CI stack,
per `docker-compose.yml` and CLAUDE.md's "start docker compose yourself"). The resulting
DDL conflict is real: `check_additive_only/3` detects it via a genuine
`information_schema.columns` read, exactly as it would for any real pre-existing column
collision — not a mock, and not a different (weaker) failure mode substituted in its
place.

**Gap 2 — the two "healthy" companies need a real active entity definition first.**
UAT-RUNNER's first live run against the ISS-0777-fixed backend surfaced that this
spec's original pre-step only made ONE company fail (the poisoned one) but never made
the other two able to genuinely SUCCEED: `do_run_column_promotion/2` calls
`ensure_entity_table/2` before `check_additive_only/3`, and that function's
table-doesn't-exist-yet branch (`create_and_populate_entity_table/3`,
`tenant_provisioning.ex:1555`) requires a real, ACTIVE
`Letflow.Entities.EntityDefinition` for the target `entity_type` to already exist in
that tenant's schema — with none registered, `Definitions.get_active_definition_by_name/2`
genuinely returns `{:error, :not_found}` and the company fails too, for an unrelated
reason, breaking the scenario at step 02 (the earlier, incorrect assumption — corrected
here — was that `ensure_entity_table/2` builds a table from the bare `entity_type` name
alone with no definition dependency; it does not). The poisoned company (bilimbaga)
never hits this branch at all, since its `entity_<entity_type>` table already exists
from the poison step, so `entity_table_exists?/2` short-circuits straight to
`check_additive_only/3` — only the two healthy companies (bpm-default, swiftroute) need
this fix.

`web/tests/e2e/db-exec.ts`'s `createActiveEntityDefinition` calls the real
`Letflow.Entities.Definitions.create_definition/2` + `.activate_definition/4` context
functions directly via `mix run --no-start -e` (same repo checkout backing the server
under test) — the exact functions `migration_rollout_test.exs`'s own
`create_active_definition!/3` fixture calls (same field shape: `amount`/`notes` string
fields), not a raw-SQL reimplementation of entity-definition persistence (which would
risk getting the real `content_hash`/`repository_artifacts` persistence shape wrong).
`--no-start` skips `Letflow.Application.start/2` (no second Bandit/HTTP listener bound
on top of the already-running dev server) — only `:postgrex`/`:ecto_sql` and
`Letflow.Repo` itself are started, which is all `create_definition/2` needs. No HTTP
endpoint could do this instead: `POST /entities/definitions`/`.../activate`
(`lib/letflow/routers/entities.ex`) resolve their target tenant schema from the CALLING
TOKEN's own Keycloak realm (`prefix!(conn)`), and no known
`:EntitiesDefinitionsWrite`-permission fixture user is registered in bilimbaga's or
swiftroute's own realms for this pair — inventing one would be a bigger, riskier
addition than this fix warrants.

Both are genuine, disclosed technique additions (no prior pipeline spec in this
directory needed direct Postgres access or a direct `mix run` shell-out) — documented in
full in the spec file's own header comment and in `db-exec.ts`'s own moduledoc-style
comments, not silently introduced.

A third, smaller UAT-RUNNER finding (live run, "new_finding_2"): a `failed` outcome's
`completed_at` is a REAL timestamp, never the em-dash placeholder — REQ-374's
`record_outcome_result/2` sets `completed_at` the instant an outcome leaves `pending`,
for `failed` exactly as much as for `succeeded`. This spec's step 02/05/06 assertions,
and the unit test's TC-REQ375-17 fixture, originally baked in the wrong assumption
("non-succeeded implies null completed_at"); both are now corrected to assert the real
timestamp for a failed row, and TC-REQ375-19 was added as an explicit regression test
that the em-dash is reserved for a genuinely still-`pending` outcome only. See commit
`29a72762` and `lib/letflow/design/req375-rollout-status-screen.md` §7's own added
clarifying note.

### Known, disclosed gaps this spec does NOT assert

Mirrors the design doc's own §8 disclosure block:

1. This spec runs against whatever set of tenants is `:active` on the target
   environment at run time (REQ-374 has no scope parameter). On a shared dev/CI
   environment with more active tenants than the 3 fixture tenants this spec resolves
   (`bpm-default`, `bilimbaga`, `swiftroute` — the same fixtures
   `platform-definition-promotion-rollback`/`-conflict-rejected` already resolve), those
   other tenants are also targeted by both rollout calls and pick up the same
   fixture-unique `entity_type`/`attribute` pair harmlessly (fresh, additive, never
   reused). This spec's own assertions only ever read the three tenant_ids it resolved,
   never the full outcome-array length or set — the same "`>=`, not `==`" discipline
   `migration_rollout_test.exs`'s own "queryable outcome record" describe block already
   documents for the identical reason.
2. Does not re-verify OQ-1 of the REQ-374 design (scope-drift on a repeat
   `start_rollout/3` call against a newly-onboarded tenant) — no tenant is onboarded
   mid-scenario.
3. Does not re-verify §9 OQ-1 of the REQ-375 design (tenant-name pagination) — asserts
   against `rollout-outcome-row-{tenant_id}` testids directly, not resolved display
   names.

## REVIEWER-flagged gap this pass closes: StatusBadge `rollout`/`rollout-outcome` domains

**File:** `web/src/components/ui/__tests__/StatusBadge.test.tsx` (extended, not new).

REVIEWER's REQ-375 pass flagged that `StatusBadge.tsx`'s two new domains
(`rollout`/`rollout-outcome` — added specifically to fix a real bug where the rollout-
and outcome-level status enums were originally folded under one shared table and
silently fell through to FALLBACK) had zero direct test coverage. Added:

- **TC-REQ375-01/02** — `rollout` domain resolves `running` (info, pulse) and
  `completed` (success, no pulse).
- **TC-REQ375-03/04/05** — `rollout-outcome` domain resolves `succeeded` (success),
  `failed` (error), `pending` (info, pulse).
- **TC-REQ375-06** — cross-domain regression guard: `rollout`/`"succeeded"` (a valid
  `rollout-outcome` value, NOT a valid `rollout` value) falls through to FALLBACK —
  proves the two tables stay disjoint rather than silently re-merging under a future
  edit.
