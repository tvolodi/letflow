# Test Spec: REQ-376 — Postgres-native partitioning of `events`/`events_archive` + whole-partition retirement

**Requirement:** REQ-376 (see `docs/migration/decisions/0037-event-store-partitioning-and-whole-partition-retirement.md`
and `lib/letflow/design/req376-partition-event-retirement.md` for the full text —
not restated here). Acceptance criteria, per `handoffs/WF02-REQ376-20260922/step-02a-elixir-dev.json`:

1. Decision record exists, cross-references 0003/ISS-0014, carries REVIEWER sign-off — doc-only, no executable surface, not covered here (RELEASE-VALIDATOR/DOC-UPDATER's concern).
2. Whole-month retirement is single-DDL-operation-shaped (no per-row DELETE), proven by a test (EO-001).
3. Protected (`keep_forever`) record count identical before/after retiring a month containing at least one, proven by a test (EO-002).
4. A process instance with history in an already-retired month still replays complete, gap-free, error-free (EO-003), proven by a test.
5. Next month's partition is pre-created ahead of need; no write path waits on partition creation.
6. Relationship between this mechanism and `archive/1` stated explicitly — doc-only (decision 0037's own "Relationship to `archive/1`" section), not covered here.
7. `mix letflow.check` passes — ELIXIR-DEV's own Step 2a concern, not re-proven here.

**Test tier:** unit+integration (real Postgres via `Letflow.DataCase`, DIRECTIVE T-1 — no mocks). No property-test layer: `retire_month/3` is not a named-state/legal-transition machine in the `ProcessInstance` sense — it is a catalog-state-*detected* dispatch over a small, closed, exhaustively-enumerated set (§4.3.1's table: `:not_started`/`:pending_detach`/`:detached_standalone`/`:already_retired`/not-found), and every one of those five branches is covered by an explicit example test below, which is the design doc's own prescribed test shape (§4.3.3) — a generated-random-sequence property test would not exercise anything a state-machine property test is for (there is no sequence of *application-level actions* to randomize; the state is Postgres's own catalog, driven by which of five fixed setup shapes a test constructs).

## Test cases — `test/letflow/event_store/partition_maintenance_test.exs`

1. **AC2/EO-001, no per-row DELETE** — `retire_month/3` against a month fixture with nothing to reconcile (no `keep_forever` rows, no `events_archive_default` rows in range) issues zero `DELETE FROM`/row-scoped `INSERT ... SELECT` statements across the whole call (query-log capture via `:telemetry.attach/4` on `[:letflow, :repo, :query]`, the same real Ecto/Postgrex instrumentation `test/letflow/metrics/registry_test.exs` already exercises). Proves AC2's "whole-unit DDL, not row-by-row" claim under the exact condition the design doc's own §4.3.3 test shape names.
2. **EO-001, concurrent write not blocked** — a direct row insert into a *different*, live partition, run concurrently (via `Task.async/1`) with a `retire_month/3` call against an unrelated month, completes within a bounded `Task.await/2` timeout. If `DETACH ... CONCURRENTLY`'s non-blocking guarantee did not hold, this is exactly the call that would hang past the timeout, not merely run slow.
3. **Crash-recovery sub-case 1 (`:detached_standalone`)** — steps 1–2 are run by hand outside `retire_month/3` (detach `events_default`, `DETACH PARTITION` the target month, reattach `events_default` — the exact sequence `detach_partition!/2` itself performs), simulating a crash after step 2 but before step 3. A fresh `retire_month/3` call is asserted to detect `:detached_standalone` and complete steps 3–5, `resumed_from: :detached_standalone`.
4. **Crash-recovery sub-case 2 (`:pending_detach`)** — a *genuine* interrupted `DETACH PARTITION ... CONCURRENTLY` is induced against real Postgres 16 (not merely asserted): a held-open transaction on a separate connection forces Postgres's own two-phase detach to block in its wait-for-old-snapshots phase after committing phase 1 (`inhdetachpending = true`); the blocked connection is then killed, leaving a real pending-detach state (the polling loop that detects `inhdetachpending = true` is bounded, not a blind sleep — DIRECTIVE 3's determinism concern is about assertions depending on wall-clock/unseeded randomness, not about a bounded poll for a real system condition). `retire_month/3` is then asserted to detect `:pending_detach`, issue `FINALIZE`, and complete, `resumed_from: :pending_detach`.
5. **Crash-recovery sub-case 3 (`:already_retired`, idempotent no-op)** — `retire_month/3` called a second time against an already-fully-retired month asserts `{:ok, %{default_partition_rows_reconciled: 0, resumed_from: :already_retired}}` and that the second call's own query log contains no `DETACH PARTITION`/`ATTACH PARTITION` statement (query-log capture, same technique as case 1).
6. **EO-002** — a month fixture with one `keep_forever`-policy event and one ordinary event: the `keep_forever` type's row count, summed across `events` ∪ `events_archive` (never `events` alone — a successful relocation moves it out of `events` by design), is identical before and after `retire_month/3`. `protected_rows_relocated: 1` is asserted directly, not just inferred from the count.
7. **§4.4b reconciliation, ≥2 batches** — 7 rows pre-seeded directly into `events_archive_default` for the target month (simulating `archive/1`'s own ordinary early moves, per §3.2's revised destination), `reconciliation_batch_size` overridden to `3` (`Application.put_env(:letflow, :event_retention, ...)`, restored in `after`/`on_exit` — never the 5000 production default, which would exercise only one batch and prove nothing about the batch loop). Asserts `default_partition_rows_reconciled: 7` (⌈7/3⌉ = 3 batches), the rows are gone from `events_archive_default`, and present in `events_archive`.
8. **EO-003** — an instance with 2 events in an old month and 1 in the current month; the old month is retired; `read/2` with no filter returns all 3, in ascending `sequence_number` order, same `event_id`s as before retirement, no error.
9. **AC5, pre-creation + idempotency** — `ensure_future_partitions/2` with `months_ahead: 5` against a freshly-provisioned tenant (whose migrations already created `months_ahead_default/0` = 2 months ahead) creates exactly the 3 additional months (offsets 3–5); a second call with the same `months_ahead` creates none.
10. **REVIEWER correction (a), `events_default` self-heal** — after a full `retire_month/3` call, `events_default` is confirmed still attached as `events`' `DEFAULT` partition (direct `pg_inherits` query) *and* functioning, not just cataloged: a row with a `created_at` far outside every dedicated partition's range is inserted and confirmed (via `tableoid::regclass::text`) to have physically landed in `events_default`.
11. **REVIEWER correction (b), `archived_at`** — after retirement, every row in the now-`events_archive`-child partition has a non-null `archived_at` (direct SQL `count(*) WHERE archived_at IS NULL` = 0), and `read/2`'s returned `%Event{}` structs are confirmed (via `Map.from_struct/1` + `Map.has_key?/2`) to carry no `:archived_at` key at all — `archived_event_to_event/1`'s exclusion.
12. **`:partition_not_eligible`** — the current month, under the real default `min_partition_age_days` (400, no override), is not yet eligible.
13. **`:partition_not_found`** — a month 50 years in the future has no partition under any name (`events`, `events_archive`, or standalone).

## Rework addendum (TEST-DESIGN-VALIDATOR Step 3b FAIL, rework1)

Two bugs in the test *code* (not this spec's case design) were found by
TEST-DESIGN-VALIDATOR's independent multi-seed re-run against real Postgres and
fixed here — both concern case 4 and case 10's implementation, not their intent:

- **Case 10** (`correction (a)`): its raw-SQL `tableoid` lookup passed
  `event.event_id` (a canonical dashed-string UUID) straight to `Repo.query!/3` as a
  bind parameter. `Repo.query!/3` is raw SQL and bypasses `Ecto.Query`'s
  schema-driven UUID casting, so Postgrex rejected it outright
  (`DBConnection.EncodeError`) on every single run, deterministically — a bug in the
  test's own parameter encoding, not a flake and not an implementation defect. Fixed
  by dumping to the 16-byte binary form first: `Ecto.UUID.dump!(event.event_id)`.

- **Case 4** (`:pending_detach` induction): the holder and detacher `Task`s had no
  real synchronization, in two places, both confirmed by direct re-run against real
  Postgres 16 (not by inspection alone):
  1. No handshake confirmed the holder's transaction had actually opened and taken
     its snapshot before the detacher's `DETACH ... CONCURRENTLY` began — on some
     seeds the detacher ran to full completion before the holder's snapshot existed
     at all, so the interrupted state was never reached. Fixed with a real
     message-send handshake (holder sends `:holder_snapshot_open` after its `SELECT`
     executes; the detacher is not started until that message is received via
     `assert_receive/3`).
  2. Even with that handshake, killing the detacher's Elixir process
     (`Task.shutdown(:brutal_kill)`) turned out not to be synchronous with its
     underlying Postgres backend actually disconnecting — releasing the holder too
     soon let the still-technically-alive backend finish the `DETACH` for real before
     the kill signal reached it, so `pending_detach?/2` correctly went `false`
     because the detach had *genuinely completed*, not because anything reverted.
     Fixed by polling `pg_stat_activity` for the detacher's own `ALTER` statement to
     confirm the backend is actually gone before releasing the holder
     (`alter_partition_backend_active?/2`), rather than assuming the kill was
     instantaneous.

  Re-verified: the fixed induction technique reached the genuine interrupted state
  and the full file passed with all 13 cases, on 5 different `--seed` values (0–4)
  against real Postgres 16, no failures on any seed — see the Step 3 rework1
  handoff for the full quoted output.
