# REQ-377 — History retirement operator screen

## Requirement text

"A screen, reachable from the platform-admin operator console, that (1) lets
a `PLATFORM_ADMIN` retire the oldest eligible month of history in one
action, showing the resulting retirement record (EO-001's operator-console
evidence); (2) shows a retention summary including the protected-record
count, capturable before and after a retirement for EO-002's evidence; (3)
does not block or degrade the rest of the console while a retirement is
running. Wires to REQ-376's real endpoints — no mock data."

Per `lib/letflow/design/req377-history-retirement-screen.md` §0, this
requirement's scope also includes the backend HTTP surface REQ-376 never
shipped: `Letflow.Routers.EventRetention` (mounted at `/event-retention`)
and its backing context module `Letflow.EventStore.RetentionOperations`.

## Acceptance criteria → test-case map

### AC1 — retire the oldest eligible month, display the resulting retirement record

> "the retirement screen lets a PLATFORM_ADMIN retire the oldest eligible
> month and displays the resulting retirement record, matching EO-001's
> operator-console evidence requirement"

Backend (`test/letflow/event_store/retention_operations_test.exs`):

- `"inserts a running row immediately, returns before the fanout completes,
  and the row later reaches completed"` — proves the exact async contract
  the design (§1/§2.1) requires: `retire_oldest_eligible_month/1` returns a
  real, durable row *before* the fanout finishes (a `GET` issued
  immediately after must find it), and the row genuinely transitions to
  `"completed"` once the fanout drains, with a real outcome
  (`retired_partition`, `protected_rows_relocated`) recorded per tenant
  schema. Exists because a naive implementation could either block the
  caller until the fanout finished (defeating the whole async design) or
  never mark the row `"completed"` at all — both are real defects this test
  would catch.
- `"a schema with no eligible month for the chosen month is recorded
  skipped, not failed"` — proves the `:partition_not_found` /
  `:partition_not_eligible` tolerance (§2.1's `retire_one_schema/5`
  contract) is real, not merely documented: a schema legitimately lacking
  the target month must not corrupt the overall retirement's status or be
  misreported as a failure.
- `"returns {:error, :no_eligible_month} and inserts no row when no schema
  has an eligible month"` (error-path describe block) — proves the router's
  409 mapping has a real domain-level error to map, and that a rejected
  start writes nothing (no half-open row left behind).

Router (`test/letflow/routers/event_retention_test.exs`):

- `"POST /retirements (AC1) returns 202 with the retirement record; GET
  status (AC1) reaches completed with the outcome table"` — proves the full
  HTTP contract end to end: 202 (not 200/201 — the operation is not done
  when the response is sent), the response body carries the real
  `year`/`month`/`requested_by`/`status` fields, and polling
  `GET /retirements/:id` eventually surfaces the same outcome-table shape
  the frontend's `RetirementStatusPanel` renders. Exists because the
  design's central invariant (§1: "the HTTP request... must return
  immediately") is a router-level contract, not just a context-module one —
  a router that (for example) awaited the `Task` before responding would
  still pass every `RetentionOperations`-level test above while violating
  AC1/EO-001 at the only layer a real client observes.
- `"POST /retirements returns 409 when no month is currently eligible, and
  creates no row"` — proves the router maps `{:error, :no_eligible_month}`
  to 409 specifically (§2.3), not a generic 500 or misleading 200.

Frontend E2E (`web/tests/e2e/pipelines/platform-partition-retention-drop.pipeline.e2e.spec.ts`,
step 03) — drives the real screen end to end and asserts the outcome table
renders a `succeeded` row naming the exact retired partition. This is the
only layer that proves AC1's actual UI-facing promise ("displays the
resulting retirement record") — the backend tests above prove the API
contract exists and is correct, but only a real browser session against the
real screen proves an operator can actually see it.

### AC2 — retention summary incl. protected-record count, before/after

> "the retention summary shows a protected-record count capturable before
> and after a retirement, matching EO-002's evidence requirement"

Backend:

- `"oldest_eligible_month is nil, protected_record_count is 0, when no
  schema has an eligible month"` and `"...is the minimum eligible month
  across every provisioned schema"` — prove `retention_summary/0`'s two
  core computed fields (`oldest_eligible_month`, derived via the one shared
  `oldest_eligible_month_platform_wide/0` helper design §2.1 requires;
  `tenant_schema_count`) are correct, including the multi-schema minimum
  case a single-tenant fixture could never exercise.
- `"protected_record_count sums keep_forever rows across events for every
  schema, unaffected by min_partition_age_days"` — proves the count reads
  from `RetentionPolicy`'s real `:keep_forever` set and stays byte-identical
  across two successive summary calls with no retirement in between — the
  baseline invariant EO-002 is built on (decision 0037: retirement never
  deletes a row, so the count must never move on its own).
- Router: `"GET /summary returns 200 with the summary shape"` — proves the
  router's field-shaping (`summary_map/1`) doesn't drop or rename any of
  the four documented response fields.

Frontend E2E (steps 01 and 04) — captures the on-screen
`data-testid="retention-summary-protected-count"` value before the
retirement, drives it through the real UI to completion, and asserts the
same on-screen value is unchanged afterward — the exact EO-002 verification
method the UAT scenario itself specifies ("The operator console retention
summary, captured before and after"). This is deliberately an on-screen
assertion, not a second raw API call: it also proves
`RetirementStatusPanel`'s completion-triggered
`invalidateQueries(queryKeys.eventRetention.summary())` (design §3.4)
actually re-fetches and re-renders, not just that the backend's own number
is stable.

### AC3 — PLATFORM_ADMIN-only reachability

> "the screen is reachable only to a PLATFORM_ADMIN-equivalent role from the
> operator console navigation"

Backend (router permission-gate describe blocks): every non-PLATFORM_ADMIN
/ no-roles case on all three routes returns 403 with no domain call ever
reached (proven by asserting no row is written for the `POST` case) — this
is the actual security boundary (design §2.3/§0: `:TenantsManage`, server
enforced), independent of anything the frontend does.

Frontend E2E (step 05) — a real `worker-user` (TASK_WORKER) session
navigating directly to `/admin/event-retention` is redirected to
`/instances`, and the retire button never renders — proves
`EventRetentionPage`'s own role-gate (design §3.4) in addition to the
router-level enforcement above; the two are deliberately tested at both
layers since the frontend gate is UX, not the enforcement point (design's
own stated division of responsibility).

### AC4 — the E2E pipeline spec exists and passes against the real screen

`web/tests/e2e/pipelines/platform-partition-retention-drop.pipeline.e2e.spec.ts`
itself — see "Solving the real eligible-month fixture problem" below for
how it produces the one piece of real-world state (a genuinely
retirement-eligible month) that cannot be produced through the HTTP API
alone.

## Solving the "real eligible-for-retirement month" fixture problem

`PartitionMaintenance.eligible?/2` requires
`today >= last_day(month) + min_partition_age_days/0`, and the real, shipped
default for `min_partition_age_days/0` is 400 days (no override anywhere in
`config/`). Two real constraints rule out the obvious shortcuts:

1. **No config override reaches the E2E target.** The ExUnit suites above
   override `Application.put_env(:letflow, :event_retention,
   min_partition_age_days: 1)` from *inside* the same BEAM node that later
   reads it back. The E2E spec drives a separate, already-running server
   process over real HTTP (`BPM_TEST_URL`); there is no supported HTTP
   surface to change that process's own `Application` env at runtime, and
   restarting the server mid-suite would be a materially riskier fixture
   technique than the one actually used.
2. **Nothing in the running system ever creates a partition old enough to
   already be eligible.** `ensure_future_partitions/2` only ever looks
   forward from "now" (its own moduledoc, §3) — a historical month's
   partition simply does not exist anywhere to retire.

**Resolution:** `web/tests/e2e/db-exec.ts` gained three REQ-377 additions —
`pickEligibleBackdatedMonth(fixtureId)`, `createBackdatedEventPartitionSql`,
`seedHistoricalEventSql` — that fabricate a **real** `events_y<year>m<MM>`
partition, attached to the real `events` parent table via real
`CREATE TABLE ... PARTITION OF ...` DDL (shelled into the already-running
`postgres` service via `psql`, exactly the way `poisonCompanySchemaSql`
already does for a different fixture need in the sibling
`platform-migration-partial-failure-resume` spec), whose calendar-month
range is genuinely more than 400 days before the day the spec runs. One
real event row is seeded inside it. `eligible?/2`'s real, completely
unmodified aging check then reports this month eligible on its own — no
server-side config change, no mock, no stub, no bypass of `retire_month/3`
or `RetentionOperations` of any kind.

The target month is derived deterministically from the run's own fixture id
(a fresh `crypto.randomUUID()` per run, the same fixture-uniqueness idiom
`platform-migration-partial-failure-resume` already uses for its
`entity_type`/`attribute` pair), spread across roughly 401–3521 days back
(~8 years of candidate months) — so a repeat run against the same
long-lived dev/CI Postgres instance lands on a fresh, never-previously-
retired month rather than colliding with one an earlier run already
detached (once `retire_month/3` detaches a month, it can never become
"eligible" again — it is simply no longer attached to `events`, so
`eligible_months/1` stops listing it at all).

This is a genuine, disclosed constraint on the spec's own design, not a
silently-invented one: EO-003 (replaying a retired month's process
instance) is explicitly *not* re-verified by this spec (per the design's
§3.7 point 7 and this scenario's own YAML) — that path is already covered
by REQ-376's own ExUnit suite (`EventStore.read/2`'s
`events`/`events_archive` union).
