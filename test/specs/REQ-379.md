# Test Spec: REQ-379 — Solution-pack install-tracking write path

**Requirement:** REQ-379 (`docs/requirements.yaml`, stage S2, `depends_on: [REQ-041]`)
**Design:** `lib/letflow/design/req379-solution-pack-install-write-path.md`
**Shipped code:** `lib/letflow/definitions/solution_pack.ex`
(`capture_artefact_bases/4`, new public; `artefact_snapshots_from/1`,
`canonicalize_artefact_content/1`, `canonicalize_json/1`, new private;
`run_install/5`, `insert_install_row/2` changed to thread a single shared
`captured_at` instant). No schema, migration, or `lib/letflow/definitions.ex`
change — REQ-041 already shipped everything else this write path depends on
(design §0).
**Test tier:** unit+integration (real Postgres, no mocks, per
`docs/guides/test_developer_guide.md` DIRECTIVE T-1)
**Test file:** `test/letflow/definitions/solution_pack_test.exs` (extended, not
duplicated — REQ-306's own scope fence already names this file as the default
target for `SolutionPack` module coverage, and it already establishes every
fixture/tenant convention this suite reuses).

## Scope-test verdict

Real executable surface exists: a new public function
(`capture_artefact_bases/4`), three new private helpers, and a changed
transactional step inside `run_install/5`, all in `lib/letflow/definitions/solution_pack.ex`.
Proceeds to the full test-design procedure — not routed to RELEASE-VALIDATOR as
docs-only.

## Pre-existing defect fixed as part of this change

`test/letflow/definitions/solution_pack_test.exs` (as committed at `f0b17b53`)
carried two identical definitions of the private helper
`cleanup_solution_pack_installs!/1` (lines 64 and 244 of the pre-fix file) —
almost certainly introduced when REQ-306's earlier work and REQ-379's FK-cleanup
addition were merged without noticing the duplication. This compiled but
produced three compiler warnings ("clauses ... should be grouped together",
"this clause ... cannot match", "the following clause is redundant") that
`mix letflow.check.test` (this AC's own gate, AC5) would fail on. The dead
second definition — and a stray, misplaced doc-comment fragment that had
drifted onto it — is removed as part of this change; behavior is unchanged
(both definitions were byte-identical).

## Test cases

1. **AC1 (install inserts exactly one `solution_pack_installs` row, real
   `installed_at`)** — describe block `"REQ-379 AC1 -- install inserts exactly
   one solution_pack_installs row"`:
   - Regression test on **already-existing** behavior (design §0):
     `insert_install_row/2`'s row-insert predates this branch (REQ-078,
     2026-08-22). What this branch changed is *where* the clock is read —
     `run_install/5` now computes one `captured_at` instant up front and
     threads it into `insert_install_row/2` instead of that function reading
     `DateTime.utc_now/0` internally. This test proves the threading refactor
     didn't silently break AC1's behavior: exactly one row for the pack just
     installed (`Repo.all` count == 1, not "at least one"), `installed_version`
     equal to the pack's own `version`, `id` equal to the install result's own
     `install_id`, and `installed_at` bracketed between a `DateTime.utc_now/0`
     read taken just before the `install/3` call and one taken just after —
     proving it's a real, non-sentinel timestamp, not merely non-nil.

2. **AC2 (one `solution_pack_artefact_bases` row per delivered definition,
   `base_content`/`base_version` byte-for-byte canonical)** — describe block
   `"REQ-379 AC2 -- install captures one canonical base row per delivered
   definition"`:
   - Installs a pack with two definitions, each with a distinct, non-trivial
     `graph` (a `"metadata"` key added on top of the ordinary start/end graph
     — `req379_graph_with_metadata/1`). Confirmed real: `graph_start_end/0`'s
     node list satisfies `Graph.validate_graph/1`, and the extra `"metadata"`
     key survives storage untouched because `Graph.from_map/1`
     (`graph.ex:282-291`) only reads `"nodes"`/`"edges"` for validation while
     `ProcessDefinition.create_changeset/2` casts `:graph` as a plain,
     unfiltered `:map` (`process_definition.ex:97,120-125`).
   - **Revision (post TEST-DESIGN-VALIDATOR FAIL, same session):** the
     original fixture nested its unsorted keys only inside small (<=32-key)
     maps. TEST-DESIGN-VALIDATOR's own mutation testing showed this could
     never discriminate a broken canonicalizer: Erlang/Elixir maps with at
     most 32 keys ("flatmaps") always iterate in term order, which for
     binary keys is byte-lexicographic — identical to what `Enum.sort/1`
     produces — so `canonicalize_artefact_content/1` with `Enum.sort()`
     deleted from its map clause, and separately with its whole body
     replaced by a bare `Jason.encode!/1` (canonicalization skipped
     entirely), both still produced byte-identical output to this file's own
     independent `req379_canonicalize/1`, and all 21 tests kept passing
     either way. Fixed by adding `req379_large_unsorted_map/1` — a >32-key
     map nested under `"metadata"."large"` — which forces Erlang's
     hash-array-mapped-trie map representation, whose iteration order is
     hash-bucket order, not lexicographic (empirically confirmed: `Map.keys/1`
     on this exact 40-key shape comes back in a genuinely unsorted order, not
     ascending `field_01..field_40`). Both mutants were re-applied against
     the fixed fixture and confirmed to fail (then reverted and confirmed to
     pass again) as part of this revision — see the TEST-DESIGNER handoff
     for the real command output.
   - Asserts exactly one `solution_pack_artefact_bases` row per installed
     definition (count == `length(result.installed_definitions)`), each row's
     `artefact_type == "process_definition"`, `base_version` equal to the
     pack's `version`, `captured_at` non-nil.
   - Correlates each row back to its definition via `artefact_id` == the
     install result's own `new_definition_id` (§2's key choice, directly
     checkable) rather than assuming ordering.
   - Two independent assertions per row, exactly as the design's §10.2
     specifies, so a key-ordering regression is caught even if a looser check
     would pass: (a) `Jason.decode!(row.base_content)` is *structurally* equal
     to a plain JSON round-trip of the original `graph` (proves valid,
     semantically-correct JSON); (b) `row.base_content` is *byte-for-byte*
     equal to independently canonicalizing that same `graph` via
     `req379_canonicalize/1`/`req379_canonical_json/1` — a **second,
     independent** implementation of the sort-keys-then-`Jason.encode!/1`
     algorithm, written directly in the test file rather than by calling or
     copy-pasting `canonicalize_artefact_content/1` under test, so this
     assertion can actually catch a canonicalization bug rather than
     trivially agreeing with it.
   - Also confirms INV-ARTB-3: every captured `artefact_id` is a real,
     installed `ProcessDefinition.id` in the installing tenant's own schema
     (`process_definition_count_by_id/2` == 1), and is never the pack's
     source-tenant `definition_id` — directly guards the §2 key-choice
     decision, not merely implied by the correlation step above.

3. **AC3 (re-installing the same version never overwrites an existing base
   snapshot for a locally-adapted artefact)** — describe block `"REQ-379 AC3 --
   re-capture never overwrites an existing base snapshot"`:
   - Per the design's own §10.3 finding, restated here: a literal second
     `SolutionPack.install/3` call for the same `(tenant_id, pack_id)` always
     fails with `{:error, :duplicate_pack_install}`
     (`uq_solution_pack_install_active`, REQ-078) before reaching any
     artefact-base code — there is no real HTTP/`install/3` re-install path
     in this codebase today to exercise AC3 through. This is **not** a gap
     this test works around silently; the design flags it as a cross-requirement
     note for REQ-380/future pack-reinstall support, and this test instead
     calls `capture_artefact_bases/4` directly — public specifically so this
     test seam exists (design §5.1).
   - Sequence: (1) capture content A for one artefact key, assert one row
     with `base_content == canonical(A)`; (2) (documentation step — no DB
     mutation required, since `solution_pack_artefact_bases` is never touched
     by a local edit per REQ-041's own design) simulate the tenant having
     since locally adapted the artefact; (3) capture content B (different)
     for the **same** key and **same** `base_version`, assert the call
     succeeds without raising or erroring; (4) **the AC3 assertion itself** —
     still exactly one row for that key, and its `base_content` is still
     `canonical(A)`, never `canonical(B)`.
   - Confirms `INV-ARTB-1` directly: the row's own `id` is unchanged across
     both calls (same row, not a replaced one).

4. **AC4 (`compute_pack_update_plan/5` against real base rows from this write
   path classifies all four outcomes end to end)** — describe block `"REQ-379
   AC4 -- compute_pack_update_plan/5 against real base rows classifies all
   four outcomes"`:
   - Installs one real pack with exactly four definitions (four distinct
     process keys, one per intended classification bucket), so all four
     `solution_pack_artefact_bases` rows come from this write path — never
     `insert`ed directly by the test (the requirement's own wording: "not
     hand-built fixtures").
   - Reads each row's real `base_content` back from Postgres and uses it,
     verbatim, to construct `theirs_artefacts`/`incoming_artefacts` per
     `Letflow.Definitions.compute_pack_update_plan/5`'s own documented
     contract (`definitions.ex:370-371` — these two lists are caller-supplied
     by design; only `base` is ever looked up by the function itself),
     following the design §10.4 table exactly: `unchanged`
     (`theirs == incoming == base`), `clean_update` (`theirs == base`,
     `incoming` differs), `local_only` (`incoming == base`, `theirs`
     differs), `conflict` (both `theirs` and `incoming` differ from `base`
     and from each other).
   - Asserts `plan.entries` classifies exactly as expected for each of the
     four real `artefact_id`s, and that each entry's own `base` field equals
     the real row's `base_content` — proving the lookup actually hit the row
     this write path produced (a wrong `artefact_id` join, e.g. a §2
     key-choice regression using the pack's source `definition_id` instead of
     the real installed `ProcessDefinition.id`, would make every entry's
     `base` come back `nil` and every classification collapse to
     `:conflict`, which this test would catch via both the classification
     assertions and the explicit `refute is_nil(entry.base)` guard).
   - Exercises `classify_artefact/3`'s full truth table
     (`definitions.ex:483-489`) through the real 5-argument orchestration, not
     the pure function in isolation — `pack_update_migration_test.exs` already
     covers the latter for REQ-041; this test's job is specifically proving
     the write path (this requirement) and the read path (REQ-041, unchanged)
     compose correctly end to end.

5. **AC5 (`mix letflow.check` passes)** — process requirement, not a test
   case. `mix letflow.check.test`'s real output is quoted in the TEST-DESIGNER
   handoff below; ELIXIR-DEV/RELEASE-VALIDATOR re-verify independently per
   WF-02.

## Deliberately NOT covered here (scope fence, per the design)

- `variable_schemas`/`entity_definitions` base-snapshot capture — design §1
  OQ-1, explicitly out of REQ-379's scope; no AC requires it.
- Any HTTP-route-level test — REQ-379's own scope fence: "does not build ...
  any HTTP route beyond whatever install route already exists." All coverage
  here calls `Letflow.Definitions.SolutionPack.install/3`/`capture_artefact_bases/4`
  directly, matching this file's existing REQ-304/305/306 convention (context-module
  level, not router level — no HTTP surface exists yet for these paths either).
- `compute_pack_update_plan/5`'s own pure-function truth table and its
  no-base/no-install-row edge cases — already fully covered by REQ-041's
  `pack_update_migration_test.exs`; not re-derived here.
