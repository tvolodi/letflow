# Test Spec: REQ-380 — Solution-pack update review and apply API

**Requirement:** REQ-380 (`docs/requirements.yaml`, stage S2, `depends_on: [REQ-379]`)
**Design:** `lib/letflow/design/req380-pack-update-review-apply-api.md`
**Shipped code:** `lib/letflow/routers/solution_packs.ex` (two new `authz_post` routes,
`handle_update_review/2`, `handle_update_apply/2`, and their supporting private
helpers); `lib/letflow/definitions/solution_pack.ex` (`apply_pack_update/6`, new
public, plus its private helpers `assert_resolution_shapes!/1`,
`run_apply_update/8`, `insert_submitted_resolutions/6`,
`check_no_unresolved_conflicts/1`, `apply_plan_entries/6`, `apply_entry/6`,
`find_submitted_resolution/2`, `apply_from_persisted_resolution/5`,
`advance_base/6`, `applied_entry_map/2`). No migration — `pack_update_resolutions`
and `solution_pack_artefact_bases` already exist (REQ-041), and
`compute_pack_update_plan/5`/`classify_artefact/3` are untouched (design §0).
**Test tier:** integration, real HTTP (real Postgres, no mocks, per
`docs/guides/test_developer_guide.md` DIRECTIVE T-1) — this is an API-level
requirement (REQ-380's own scope fence: "backend API only, three routes/
operations"), so every test dispatches through `Letflow.Routers.SolutionPacks.call/2`,
not a bare call to `apply_pack_update/6`.
**Test file:** `test/letflow/routers/solution_packs_update_test.exs` (new file — no
router-level test file for `solution_packs.ex` existed before this requirement;
`req078_supporting_routes_test.exs`'s own `/export`/`/install` coverage is untouched).

## Scope-test verdict

Real executable surface exists: two new HTTP routes, two new router handlers with
non-trivial request validation, one new context function
(`apply_pack_update/6`, a multi-step transactional write), and the first production
caller of `PackUpdateResolution.insert_changeset/2`. Proceeds to the full
test-design procedure — not routed to RELEASE-VALIDATOR as docs-only.

## Fixture technique

Every fixture inserts `solution_pack_artefact_bases`/`pack_update_resolutions` rows
directly (`SolutionPackArtefactBase.upsert_changeset/2` via `Repo.insert!/1`) — the
same "fixture-insertable, no FK to `solution_pack_installs`" pattern INV-PU-6
documents and REQ-379's own `AC4` test (`test/letflow/definitions/solution_pack_test.exs`)
established for the read side; no real `SolutionPack.install/3` call is required to
set up any scenario here. `theirs_artefacts`/`incoming_artefacts` content strings
are opaque, distinct, deterministic tags (`"base-<bucket>-<id>"`,
`"theirs-adapted-<id>"`, etc) rather than canonicalized JSON documents:
`classify_artefact/3` compares by byte-level string equality only, and this
requirement's routes never re-canonicalize (design §6), so a real canonical-JSON
shape is not needed to exercise the classification/apply logic under test — REQ-379's
own canonicalization coverage is not re-derived here.

## Test cases

1. **EO-001 (four-way classification, one artefact per group)** — describe block
   `"EO-001: update-review returns each artefact under exactly one of the four
   groups"`:
   - Four distinct artefact ids, one base row each, `theirs`/`incoming` constructed
     per `classify_artefact/3`'s own truth table (design §3.3's wire-name table):
     `unchanged` (base==theirs==incoming), `safe_to_update` (base==theirs≠incoming),
     `local_only` (base≠theirs, base==incoming), `both_sides_conflict` (all three
     distinct). A real `POST .../update-review` call with all four in one payload.
   - Asserts each entry's wire `"classification"` matches its intended bucket, and
     that the full classification set observed across `entries[]` is exactly the
     four expected wire strings (not merely "doesn't contradict" any one bucket —
     genuinely exercises all four, per the AC's own wording).
   - Also asserts top-level `"has_unresolved_conflicts": true` (the conflict
     artefact has no resolution yet).

2. **EO-002 (block on unresolved conflict; applies nothing, including a resolution
   submitted for a DIFFERENT conflict in the same call)** — describe block
   `"EO-002: update-apply refuses and names the unresolved artefact; applies
   nothing"`:
   - Two conflict artefacts in one apply call: `conflict_a` (this call submits a
     `keep_local` resolution for it) and `conflict_b` (this call submits nothing).
   - Asserts `409`, and the response detail names `conflict_b`'s
     `artefact_id`/`artefact_type` (not `conflict_a`'s — the first unresolved entry
     in plan order).
   - Asserts, by direct query: **zero** `pack_update_resolutions` rows exist for
     this `(tenant_id, pack_id, target_version)` — proving `conflict_a`'s own
     submitted resolution in the same call did **not** survive the rollback either
     (design §4.4's "all-or-nothing, including the resolutions themselves"), not
     just that the call failed.
   - Asserts both artefacts' `solution_pack_artefact_bases` rows are byte-identical
     to their pre-call state (`base_content` and `base_version` both unchanged).

3. **EO-003/EO-004/EO-005 (keep_local unchanged+attributed; untouched artefact
   unchanged; idempotent re-review)** — describe block
   `"EO-003/EO-004/EO-005: keep_local apply, untouched artefact, idempotent
   re-review"`, one continuous scenario (mirrors the design §8 narrative: "Continue
   from case 3's committed state"):
   - One adapted conflict artefact (base≠theirs≠incoming) and one `:unchanged`
     artefact (base==theirs==incoming) in the same apply call, resolved with
     `resolutions: [{conflict artefact, "keep_local"}]`.
   - **EO-003**: asserts `200`; the conflict artefact's `applied_entries[]` action
     is `"left_unchanged"`; its `solution_pack_artefact_bases` row's
     `base_content`/`base_version` are unchanged from pre-call; exactly one
     `pack_update_resolutions` row now exists for
     `(tenant_id, pack_id, target_version, artefact_type, artefact_id)` with
     `resolution == :keep_local`, `resolved_by` equal to the calling actor's real
     `user_id` (not a placeholder), and non-nil `resolved_at`.
   - **EO-004**: asserts the `:unchanged` artefact's action is also
     `"left_unchanged"`, and its base row's `base_content` **and** `base_version`
     (the two fields EO-004 names explicitly) are byte-identical to a snapshot
     taken before the apply call.
   - **EO-005**: a second `update-review` call, same `target_version`, same
     (unchanged-by-construction, since keep_local wrote nothing) `theirs`/`incoming`
     payload for the keep_local artefact. Asserts its entry's `"classification"`
     stays `"both_sides_conflict"` (per REVIEWER's confirmed OQ-4 reading — this is
     **not** claimed to flip to a non-conflict value) **and** `"resolved"` flips to
     `true` — both fields, matching the design's explicit "assert exactly this
     shape" instruction, not just "no longer in a conflict bucket." Also asserts
     top-level `"has_unresolved_conflicts": false`.

4. **Regression — resolution immutability (OQ-3, first-attribution-wins)** —
   describe block `"Regression: a resolved artefact's attribution is immutable
   (on_conflict: :nothing)"`:
   - First apply call: one conflict artefact, resolved `keep_local` by `first_actor`.
     Captures the persisted row's `resolved_at`.
   - Second apply call, same artefact/`target_version`, a **different** resolution
     (`take_incoming`) submitted by a **different** actor (`second_actor`). Per
     `compute_pack_update_plan/5`, the artefact is already `resolved: true` from the
     first call's row, so this second call is not blocked by EO-002's check.
   - Asserts the **persisted attribution row is completely unchanged**: same row
     `id`, `resolution == :keep_local`, `resolved_by == first_actor`,
     `resolved_at` byte-identical to the first call's value — the `on_conflict:
     :nothing` insert in `insert_submitted_resolutions/6` is a genuine no-op here,
     not merely "doesn't error."
   - **Also documents, rather than silently assuming away, a real adjacent
     behavior found while writing this test**: `apply_entry/6`'s `:conflict` clause
     (`solution_pack.ex`) consults the **current call's own** `resolutions` list
     first (`find_submitted_resolution/2`) and only falls back to re-reading the
     persisted row when the current call submits nothing for that artefact (design
     §4.3 step 6, read literally). So the second call's own `take_incoming`
     submission governs the **action this call takes** (the base *is* advanced to
     `incoming`), even though its own attempted resolution-row insert was silently
     dropped. The test's first attempt asserted the opposite (that the *original*
     `keep_local` resolution would govern the second call's action too) and failed
     against the real, correct implementation — corrected to assert the actual,
     design-consistent behavior: **attribution is immutable; the per-call applied
     action is not.** This is exactly the shape of finding TEST-DESIGNER is
     expected to report, not paper over.

5. **Negative/shape coverage** (design §8 item 6, not tied to a single numbered EO)
   — describe block `"negative/shape coverage"`:
   - Malformed (non-object) body on `update-review` → `400`.
   - Both `theirs_artefacts`/`incoming_artefacts` empty on `update-review` → `422`
     with the exact stated detail string.
   - `resolution: "merged"` with no `resolved_content` on `update-apply` → `422`.
   - `resolution: "keep_local"` with a non-null `resolved_content` on
     `update-apply` → `422`.
   - An unauthenticated caller (`roles: []`) on `update-apply` → `403`.
   - A `PROCESS_OPERATOR` caller (holds `:DefinitionsRead`, not
     `:DefinitionsWrite`) on `update-apply` → `403`.
   - The same `PROCESS_OPERATOR` caller on `update-review` → `200` — this pair is
     the concrete proof for the design's §3.1/§4.1 role-matrix reasoning (OQ-1),
     not merely an assertion repeated from the design doc.

6. **`mix letflow.check` passes** — process requirement, not a test case. Real
   `mix letflow.check.test` output is quoted in the TEST-DESIGNER handoff;
   ELIXIR-DEV/RELEASE-VALIDATOR re-verify independently per WF-02.

## Deliberately NOT covered here (scope fence, per the design)

- `compute_pack_update_plan/5`'s own pure-function truth table and no-base/
  no-install-row edge cases — already fully covered by REQ-041's
  `pack_update_migration_test.exs` and REQ-379's own AC4 test; not re-derived here.
- Context-function-level (`apply_pack_update/6` called directly, bypassing HTTP) —
  the design explicitly frames this as an API-level requirement; every scenario
  above is exercised through the real route, which necessarily also exercises the
  context function.
- The `:merged` resolution's base-advancement path (`resolved_content` becomes the
  new base) — no acceptance criterion in REQ-380's set requires it; `assert_resolution_shapes!/1`'s
  defensive guard already typed-covers the shape correlation at the router-input
  boundary tested in case 5 above.
- REQ-381's frontend screen — separate requirement, separate test surface
  (`web/tests/e2e/...`), not built or tested here.
