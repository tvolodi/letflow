## Gap 2 (closed): the golden-fixture cross-language proof was not actually exercising key-sorting on the JS side

Per this task's mandate to mutation-test the canonicalizer, TEST-DESIGNER broke
`canonicalizeArtefactContent.ts`'s key-sort (`Object.keys(value).sort()` →
`Object.keys(value)`, no sort) and re-ran the Vitest golden suite. Result: only 2 of
16 tests failed (the two hand-written "unit behaviour" tests at the bottom of the
file); all 12 `it.each` golden-fixture cases and the "non-empty" check still passed
with the sort removed.

**Root cause**: `test/fixtures/canonical_json/golden_cases.json`'s `input` objects
were written with their keys **already in alphabetical order in the JSON source
text**, at every nesting level, for all 12 cases (confirmed programmatically). JS's
`JSON.parse` preserves string-key insertion order (the order keys first appear in
the source), so a parsed `input` object's own natural enumeration order already
equalled the sorted order the algorithm is supposed to produce — the `.sort()` call
was a no-op for every golden case, on the JS side only. This is a genuine hole in
the design's own stated guarantee (§2.1: "Byte-for-byte equivalence is not free — it
must be proven, not assumed... the golden-fixture test below (bullet 3) must include
at least one non-ASCII key case so the risk is measured, not assumed away") — the
fixture measured string-escaping/number-formatting/non-ASCII-key equivalence for
real, but not key-*reordering* equivalence on the JS side, despite two case names
(`simple_key_reordering`, `nested_object_reordering`) explicitly claiming to.

Note this does NOT affect the ExUnit side: Elixir maps have no key-order tied to
source text (`Jason.decode!` produces a plain, unordered map regardless of the
JSON's textual key order), so `canonicalize_json/1`'s `Enum.sort/1` was always
exercised for real on that side — this was a JS-parse-semantics-specific hole.

**Fix applied**: rewrote `test/fixtures/canonical_json/golden_cases.json`'s `input`
fields only (every case, every nesting level) into **reverse-alphabetical** key
order — `expected` fields are untouched (they were already correct canonical output,
independent of input text order). Re-ran the mutation check:

- With the fix still removed (`.sort()` deleted): **14 of 16** Vitest tests now
  fail (all 12 golden `it.each` cases plus the 2 unit-behaviour tests; only the
  "non-empty fixture" check survives, since it doesn't assert on canonicalization
  output) — the golden fixture set now genuinely exercises key-sorting.
- `.sort()` restored: all **16/16** pass again.
- ExUnit side re-run against the reordered fixture (real Postgres, this
  environment's own docker-compose instance, port 5481): **13 passed**, confirming
  the reorder is safe for the Elixir side exactly as predicted (unordered maps).

This is exactly the "fail-then-pass discipline" this task required, applied to the
fixture itself once the first mutation attempt (correctly) revealed the fixture
wasn't doing what its own case names claimed.

## Golden-fixture 13/16 count discrepancy — investigated, explainable, not a gap

ExUnit: 1 "fixture is non-empty" test + 12 generated per-case tests (one `for
golden_case <- @golden_cases do ... end` per row) = **13**. Vitest: 1 "loaded a
non-empty golden fixture set" + 12 `it.each` rows + 3 additional hand-written
"unit behaviour" tests (`sorts object keys recursively`, `preserves array element
order`, `produces identical output regardless of input key insertion order`) =
**16**. Both load the same 12-case `golden_cases.json`; the difference is exactly
the 3 extra Vitest-only sanity tests, which is why mutation-testing above caught the
sort-removal at all — ironically, via the 3 "extra" tests rather than the golden
cases themselves, before the fixture fix. Confirmed by direct inspection, not a
real coverage gap once Gap 2 above is closed.

## e2e spec — live-run status: NOT RUN, statically verified for correctness

`web/tests/e2e/pipelines/template-update-conflict.pipeline.e2e.spec.ts` (286 lines,
EO-001..EO-005 across 6 pipeline steps) has **never been executed against a live
browser+backend stack**, in this session either. This environment has:

- `docker` CLI present but the invoking user lacks socket permission

  docker ps` **does** work (confirmed — used it to stand up a scratch Postgres for
  the ExUnit golden test above), so a full Keycloak+backend+frontend stack could in
  principle be brought up with `sudo docker compose up`, but doing so is out of
  scope for this audit pass (no `docker-compose.yml` service for the frontend dev
  server + Keycloak + backend all wired for Playwright's `BPM_TEST_URL` expectation

  UAT-RUNNER/live-instance-run concern per the design's own framing, not a

  no live `BPM_TEST_URL` target.
