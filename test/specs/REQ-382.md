# REQ-382 — HTTP-reachable tenant-branding write path

## Requirement text

> A new authenticated, tenant-admin-scoped route accepts a settings PATCH and
> a valid `brand_colors.primary` round-trips through `GET /api/tenant-config`
> on the next call. Submitting a `brand_colors.primary` value that passes the
> existing hex-format check but fails a WCAG AA (4.5:1) contrast check
> against `tokens.css`'s page background is refused with a plain-language
> message naming why, and the previously-stored colour is unchanged after the
> attempt. A request whose raw input includes an out-of-allowlist top-level
> key or an out-of-allowlist `brand_colors` sub-key applies only the
> request's recognized, valid part and never 500s or rejects the whole
> request for that reason alone. The same rejected-key request writes exactly
> one `Letflow.Audit` entry naming the tenant, actor, rejected key(s), and
> attempted value(s), and `AuditLogPage`'s existing query surfaces it with no
> frontend change. `Tenant.settings_changeset/2`'s existing structural
> discipline (cast list scoped to `:settings` only) and `TenantSettings`'
> closed top-level key vocabulary are both unchanged by this requirement.

See `lib/letflow/design/req382-tenant-branding-write-path.md` for the full
design (route shape, algorithm, audit-entry shape, invariant mapping).
Implementation: `lib/letflow/routers/tenant_settings.ex`,
`lib/letflow/identity/color_contrast.ex`,
`lib/letflow/identity/tenant.ex` (`validate_brand_colors/2` gained a
contrast check), `lib/letflow/identity/tenant_settings.ex`
(`allowed_keys/0` made public), `lib/letflow/api/authorization.ex` (new
`:TenantsManage`-backed `endpoint_policy_key/2` clause).

## Acceptance criteria → test-case map

### AC1 — authenticated PATCH round-trips through `GET /api/tenant-config`

`test/letflow/routers/tenant_settings_test.exs`, `"AC1: authenticated PATCH
round-trips through GET /api/tenant-config"`:

- `"a valid brand_colors.primary written via PATCH is visible on the very
  next GET /api/tenant-config call"` — dispatches a real
  `PATCH /tenant/settings` through `Letflow.Routers.TenantSettings.call/2`
  (which runs the router's own `use Letflow.Api.AuthorizedRouter` pipeline —
  `:match` → `Letflow.Plugs.Authorize` → `:dispatch` — over a real
  `Plug.Conn`, never a direct call to
  `Letflow.Identity.update_tenant_settings/2`), then dispatches a real,
  unauthenticated `GET /api/tenant-config?realm=<slug>` through the full,
  unmodified `Letflow.Router`. Exists because a router that wrote the value
  correctly but the read side never actually observed it (e.g. a stale
  cached tenant struct, a transaction that appeared to commit but didn't, a
  `settings_response_map/2` bug that echoes the request back without really
  persisting it) would still pass a test that only inspects the PATCH
  response body — this test proves the write is durably visible through the
  independent, pre-existing read path REQ-281 already built.

### AC2 — WCAG-AA-failing colour refused; previous colour unchanged

`test/letflow/routers/tenant_settings_test.exs`, `"AC2: WCAG-AA-failing
colour is refused, previous colour unchanged"`:

- `"a hex-valid but contrast-failing primary is refused 422 naming the WCAG
  threshold, prior colour retained"` — first establishes a known-good stored
  colour (`#1864AB`, ~5.77:1/~6.09:1 against the two `tokens.css` reference
  backgrounds), then attempts to overwrite it with `#228be6` (~3.37:1/~3.56:1
  — passes the `#RRGGBB` hex-format regex but fails the 4.5:1 AA minimum).
  Asserts (a) `422`, (b) the error message names the `4.5` threshold and uses
  a "contrast"/"WCAG" word (never a bare `"validation failed"`, matching the
  design's explicit rejection of `Tenants.handle_patch/2`'s generic-message
  precedent), and (c) `Repo.get!(Tenant, ...).settings` still holds the
  original `#1864AB` — not merely that the response reported success/failure
  correctly, but that nothing was actually persisted. Exists because a naive
  implementation could reject the *request* (422) while still writing a
  partial/wrong value if the merge and the validation were sequenced wrong,
  or could accept a contrast-failing colour outright if the second `cond`
  branch in `validate_brand_colors/2` were missing or short-circuited by the
  hex-format check alone.

`test/letflow/identity/color_contrast_test.exs` pins the underlying formula
independently (see below) — this router-level test is what proves the
formula is actually *wired into* the write path, not just correct in
isolation.

### AC3 — out-of-allowlist keys apply only the recognized/valid part

`test/letflow/routers/tenant_settings_test.exs`, `"AC3: out-of-allowlist keys
apply only the recognized/valid part"`:

- `"an out-of-allowlist top-level key is dropped, the recognized app_name key
  still applies, no 500"` — a body containing both a bad key
  (`warning_color`) and a good key (`app_name`) still returns `200` with
  `app_name` applied and `warning_color` absent from both the response and
  the persisted row.
- `"an out-of-allowlist brand_colors sub-key is dropped, the recognized
  primary sub-key still applies"` — same shape, one level deeper
  (`brand_colors.secondary` rejected, `brand_colors.primary` applied).
- `"a request consisting ONLY of out-of-allowlist keys still succeeds 200
  with an unchanged settings map, never 500"` — the degenerate case: nothing
  in the request is recognized at all. Exists specifically because this is
  the case most likely to crash a partition-then-merge implementation (an
  empty `recognized_top` map reaching `Map.merge/2` or a downstream
  changeset in an unexpected shape) — proving `200`+no-op here is the
  strongest version of "never rejects the whole request for this reason
  alone."

### AC4 — exactly one audit entry naming tenant/actor/rejected keys/values

`test/letflow/routers/tenant_settings_test.exs`, `"AC4: exactly one audit
entry for a rejected-key request, surfaced via GET /api/v1/audit"`:

- `"records tenant/actor/rejected top-level key+value and rejected
  brand_colors sub-key+value in one entry"` — a single request rejecting one
  top-level key (`text_size`) and one `brand_colors` sub-key (`secondary`)
  simultaneously. Dispatches a real `GET /api/v1/audit?resource_type=tenant_settings`
  through `Letflow.Routers.Audit.call/2` (mirroring
  `req196_audit_route_test.exs`'s own `get_audit/2` helper) rather than
  reading `Letflow.Audit.list_entries/1` directly — this is the concrete
  proof that `AuditLogPage.tsx`'s existing query (`GET /api/v1/audit` →
  `audit_item/1`'s generic 8-key rendering) surfaces the new entry with zero
  frontend change, per the requirement's own explicit wording, not merely
  that a row landed in `audit_entries`. Asserts `count == 1` (not "at least
  one" — proving the "exactly one entry" design requirement, §3 step 9(a)'s
  single gated `if`, not a per-rejected-key loop that would double-write),
  and that `after_state` carries both categories' rejected key(s) and their
  exact attempted (raw, unfiltered) values.
- `"no audit entry is written when every key in the request is recognized"`
  — the negative control: a clean request must never generate a spurious
  audit entry. Without this, a bug that always wrote an entry regardless of
  rejection would still pass the positive test above.
- `"no audit entry is written on a value-validation (WCAG) rejection -- only
  key-rejections are audited"` — proves design §3 step 7's explicit
  distinction (a full-request value-validation failure is a different
  failure class than a key-rejection, and AC4's audit obligation is scoped
  to the latter only) is real, not just documented prose.

### AC5 — cannot touch `:status`/`:slug`/`:idp_realm_id`/`:display_name`

`test/letflow/routers/tenant_settings_test.exs`, `"AC5: cannot touch
status/slug/idp_realm_id/display_name"`:

- `"status/slug/idp_realm_id/display_name in the request body are silently
  rejected as unrecognized keys, never applied"` — a single request naming
  all four protected fields plus one legitimate key (`app_name`). Asserts
  the legitimate key still applies (200, not a hard failure) and that all
  four protected columns are byte-identical to their pre-request values on
  reload. Exists because this is the one acceptance criterion this
  requirement could most easily violate silently: if a future change ever
  widened `TenantSettings.allowed_keys/0` or the router's own `Map.take/2`
  partitioning to include one of these names by mistake, this is the test
  that would catch it — `Tenant.settings_changeset/2`'s own `cast/3` list
  (`[:settings]` only) already makes it structurally impossible for
  `update_tenant_settings/2` to touch these fields even if the router handed
  it a map containing those keys, but this test proves the *router* never
  even gets that far (they are already filtered out of `recognized_top`
  before `update_tenant_settings/2` is ever called).

### Router merge behavior (ELIXIR-DEV logic beyond the literal AC text; design §3 step 5, REVIEWER-confirmed Step 2d)

`test/letflow/routers/tenant_settings_test.exs`, `"shallow top-level merge: a
partial PATCH never erases previously-set keys it did not mention"`:

- `"a PATCH containing only app_name does not erase a previously-set
  brand_colors/logo_url/locales/default_locale"` — writes all five allowed
  top-level keys in one request, then a second request containing only
  `app_name`. Asserts the other four keys are still present, byte-identical,
  after the second request. Exists because `Ecto.Changeset.cast/3` on a
  `:map`-typed field replaces the field's value wholesale (design §0) —
  without the router's own shallow-merge step, this second request would
  silently erase `brand_colors`/`logo_url`/`locales`/`default_locale`, a
  data-loss footgun the design's own OQ-1 flags explicitly. This is the
  single highest-value test in this file for catching a regression to that
  wholesale-replace default, since `Identity.update_tenant_settings/2`'s own
  unchanged behavior would make that regression easy to reintroduce
  accidentally (e.g. a future refactor that "simplifies" the router by
  calling `update_tenant_settings/2` with the raw request body directly).

### Authorization (design §1/§7, `:TenantsManage` reused, `PLATFORM_ADMIN`-only)

`test/letflow/routers/tenant_settings_test.exs`, `"authorization:
:TenantsManage is PLATFORM_ADMIN-only"`:

- `"a non-PLATFORM_ADMIN authenticated caller gets 403, row unchanged"` and
  `"a caller with no roles at all gets 403, row unchanged"` — both assert the
  row is byte-identical after the attempt, proving `Letflow.Plugs.Authorize`
  denies before any `Repo` write, not merely that the HTTP response is 403.
- `"an unauthenticated request (no Authorization header) through the real
  Letflow.Router mount is rejected, never reaches the handler"` — the one
  test in this file that dispatches through the full, real
  `Letflow.Router -> Letflow.Plugs.ApiPipeline -> AuthPipeline -> ... ->
  TenantSettings` mount chain (every other test in this file dispatches
  directly against `Letflow.Routers.TenantSettings.call/2`, matching
  `tenants_test.exs`'s/`req196_audit_route_test.exs`'s established
  convention of setting `conn.assigns[:auth_context]` by hand — see this
  file's own moduledoc for why that is still "real HTTP" for the acceptance
  criteria's own purposes). This one test proves the route is actually
  reachable through the production mount (`forward("/tenant/settings", to:
  Letflow.Routers.TenantSettings)` inside `ApiPipeline`, itself forwarded
  from `Letflow.Router`'s `/api/v1`) and genuinely sits behind
  `AuthPipeline`'s bearer-token requirement — `Letflow.Plugs.AuthPipeline`'s
  own detailed token-verification behavior (expiry, signature, realm
  mismatch, etc.) is that plug's own test file's job, not duplicated here.

### `Letflow.Identity.ColorContrast` unit math (independent of the changeset/router integration)

`test/letflow/identity/color_contrast_test.exs` — pins the WCAG 2.1 §1.4.3
relative-luminance/contrast-ratio formula and the 4.5:1 AA normal-text
threshold on their own, so a future refactor of the formula's internals
(without touching `Tenant`/`TenantSettings`/the router at all) still has a
fast, DB-free regression net:

- `relative_luminance/1`: black → `0.0`, white → `1.0`, case-insensitivity on
  hex digits.
- `contrast_ratio/2`: black-on-white is the textbook maximum `21:1`; a color
  against itself is always `1:1`; symmetric in its two arguments (order never
  changes the result — the WCAG definition's own property); `#1864AB`
  against both `tokens.css` reference backgrounds (~5.77:1/~6.09:1) and
  `#228be6` against both (~3.37:1/~3.56:1) — the exact same two colors
  `tenant_settings_test.exs`'s AC2 test and `tenant_test.exs`'s own existing
  fixture comment use, kept numerically consistent across all three files
  rather than picking disconnected numbers per file.
- `meets_wcag_aa_normal_text?/2`: the boolean wrapper's pass/fail boundary
  for both fixture colors, plus the degenerate "a color against its own
  background is always exactly 1:1, never a pass" case.
- `aa_normal_text_min_ratio/0`: pins the `4.5` constant itself.
