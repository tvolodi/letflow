# REQ-383 — Company appearance settings screen

## Requirement text

> A tenant-admin-reachable screen (`web/src/pages/admin/AppearanceSettingsPage.tsx`,
> routed at `admin/appearance`) that (1) lets the tenant admin submit a new
> `brand_colors.primary` value and calls REQ-382's endpoint (EO-001's positive
> half); (2) on a successful save, shows a plain confirmation and the applied
> colour takes effect immediately without a full page reload being required to
> see it reflected somewhere on the same screen; (3) on a request that also
> attempts an out-of-scope change, the screen's own form cannot construct an
> out-of-scope key by construction — satisfied by confirming the screen has no
> way to submit one, not by testing a server-side reject path a same-origin
> form can never trigger; (4) on a contrast-refused submission (REQ-382's new
> validation), shows the endpoint's plain-language refusal message and leaves
> the previous colour visibly in effect, never a raw validation-error blob
> (EO-003); (5) confirms platform status colours (approved/waiting/failed) are
> unaffected by any tenant colour change (EO-002, structural today, needs a
> regression test not new code). Once the screen is confirmed correct, remove
> the stale NOTE (ISS-0527) from
> `test/fixtures/uat/scenarios/platform/tenant-branding-applied.yaml` and
> author `web/tests/e2e/pipelines/tenant-branding.pipeline.e2e.spec.ts`
> (the path the scenario's own `pipeline_test` already names) against the
> real screen, including a first-paint screenshot for EO-005.

See `lib/letflow/design/req383-appearance-settings-screen.md` for the full
design (component tree §2, state shape §3, error surface §4, allowlist-closure
argument §5, regression-test design §6, e2e-spec design §8, AC→design-element
map §11). Implementation: `web/src/pages/admin/AppearanceSettingsPage.tsx`,
`web/src/api/tenantSettings.ts`, `web/src/router.tsx` (route registration),
`web/src/components/ui/__tests__/StatusBadge.test.tsx` (regression block),
`web/tests/e2e/pipelines/tenant-branding.pipeline.e2e.spec.ts`,
`test/fixtures/uat/scenarios/platform/tenant-branding-applied.yaml` (NOTE
removal).

## Acceptance criteria → test-case map

### AC1 — submit a colour, round-trip through REQ-382's endpoint, confirmation shown

`web/tests/e2e/pipelines/tenant-branding.pipeline.e2e.spec.ts`,
`"EO-001/AC1: tenant admin applies a new brand colour, sees confirmation and
immediate effect"`:

- Seeds a deterministic starting colour via a direct API `PATCH` (so the test
  never depends on another test's execution order), navigates to
  `/admin/appearance`, fills the colour input with a fresh, contrast-passing
  hex value, submits, and asserts
  `data-testid="appearance-settings-confirmation"` becomes visible.
- Asserts the live `--color-brand-600` custom property (read via
  `getComputedStyle`, the same source the preview swatch renders from) equals
  the new colour, **without ever calling `page.reload()`** — this is the
  concrete proof of "takes effect immediately... without a full page reload,"
  not merely "the value is correct after a reload" (a reload would also
  happen to show the right colour via `BrandingProvider`'s own effect, which
  would stop the test from proving what AC1 actually requires).
- Exists because a screen that showed a confirmation banner but forgot to
  call `applyBrandingColors` (or called it with the wrong value) would still
  pass a test that only checks the banner — reading the actual DOM custom
  property closes that gap.

### AC2 — contrast-refused colour: plain-language message, previous colour stays

`web/tests/e2e/pipelines/tenant-branding.pipeline.e2e.spec.ts`,
`"EO-003/AC2: a contrast-refused colour is refused, shows the plain-language
message, and leaves the previous colour in effect"`:

- Seeds a known-good baseline independently of test 1's own browser-driven
  state (via the same direct-API seed helper), submits a colour known to fail
  REQ-382's 4.5:1 WCAG check (`#228be6`, the exact fixture value
  `tenant_settings_test.exs`'s own AC2 test uses, so this spec's pass/fail
  boundary matches the real backend computation rather than an independently
  guessed value).
- Asserts `data-testid="appearance-settings-error"` is visible with non-empty
  text, that the text does **not** match `%\{|Ecto\.Changeset|"errors":|changeset`
  (belt-and-braces against a raw validation-error blob leaking through), and
  **does** match `4\.5|contrast|WCAG` (proving it's the real plain-language
  message, not a generic string) — this is the check that would catch the
  design doc's own identified footgun (§0: `err.message` on a 422 is the
  generic `"Unprocessable Entity"` string; only `err.details?.detail` carries
  the real message) if the implementation had read the wrong field.
- Asserts the live `--color-brand-600` value is **unchanged** from the
  pre-submit baseline, and that the confirmation banner has zero count —
  proving the previous colour remains visibly in effect and no false-positive
  confirmation is shown on a failed save.

### AC3 — StatusBadge colours unaffected by a tenant colour change

`web/src/components/ui/__tests__/StatusBadge.test.tsx`, `describe('REQ-383/AC3
— brand colour change does not alter any StatusBadge resolution')`,
`TC-REQ383-01..04`:

- Four representative `(domain, status)` pairs (`definition/DEPRECATED`
  [warning], `instance/ACTIVE` [info, pulsing], `task/PENDING` [no dot
  column], plus a fourth badge in TC-REQ383-04) are rendered, their resolved
  inline style values captured, then the **real, unmocked**
  `applyBrandingColors({ primary: <a colour> })` (imported directly from
  `web/src/theming/applyBranding.ts`, not a stub) is called, and the same
  captured values are asserted byte-for-byte identical afterward.
- TC-REQ383-04 additionally asserts none of the captured badge
  `background`/`color` values ever equal `'var(--color-brand-600)'`, before
  **or** after the branding call — pinning the structural claim (StatusBadge
  never references the one custom property a brand-colour change can write
  to) as a real assertion, not only a code-reading claim.
- Exists because this is a genuine regression test per the design's own §6
  framing: it would fail if a future change ever added a `STATUS_TABLES`
  entry that reads `--color-brand-600` (or any
  `BRAND_COLOR_CSS_PROPERTY`-listed custom property), or if a future
  requirement widened `BRAND_COLOR_CSS_PROPERTY` to a status-adjacent custom
  property name.

### AC4 — no code path can submit an out-of-scope key

Verified by construction/enumeration against the finished file
(`web/src/pages/admin/AppearanceSettingsPage.tsx`), per the requirement's own
acceptance-criteria text ("stated and verified explicitly... since the
negative half is exercised at REQ-382's API layer, not here") and the design
doc's §5 closure argument, independently re-confirmed here by reading the
component:

1. Exactly one form control, `<input type="color" id="brand-color-primary">`
   (line 154-160), bound to exactly one state variable, `draftColor`.
2. Exactly one mutation call site, `mutation.mutate(draftColor)` in
   `handleSubmit` (line 108).
3. Exactly one request-body constructor, the literal object
   `{ settings: { brand_colors: { primary } } }` inside
   `tenantSettingsApi.patchBrandColorPrimary` (`web/src/api/tenantSettings.ts`)
   — two fixed, hardcoded key names and one fixed key name holding the one
   variable. No `...spread`, no `Object.assign`, no dynamically-keyed object,
   no free-text JSON textarea, no "advanced/raw settings" escape hatch
   anywhere in the component tree, and no other `client.patch`/`post`/`put`
   call anywhere in the file.
4. Therefore the compiled code is structurally incapable of producing any
   request body other than
   `{"settings":{"brand_colors":{"primary": <string from the one input>}}}` —
   it cannot emit any other top-level key or any other `brand_colors`
   sub-key, regardless of what the admin types into the one input that
   exists.

No runnable test is written for this criterion, matching its own stated
verification method — a same-origin form literally cannot construct the
out-of-scope request REQ-382's server-side reject path defends against, so a
test asserting the server rejects it would be testing REQ-382's own logic
(already covered by `test/letflow/routers/tenant_settings_test.exs`'s AC3),
not this screen.

### AC5 — stale NOTE removed; e2e spec exists, passes, includes the screenshot pair

- `test/fixtures/uat/scenarios/platform/tenant-branding-applied.yaml`: the
  `NOTE (ISS-0527)` block is absent (confirmed by grep — no `ISS-0527` match
  anywhere in the file); `pipeline_test:` still names
  `web/tests/e2e/pipelines/tenant-branding.pipeline.e2e.spec.ts`, which now
  exists as a real file.
- `web/tests/e2e/pipelines/tenant-branding.pipeline.e2e.spec.ts`,
  `"EO-005: first-paint vs. settled-frame colour flash is present and
  documented (MINOR, not fixed)"`:
  - Seeds a non-platform-default colour, opens a **fresh** page/session,
    navigates to an authenticated screen, and captures a screenshot
    (`shot(..., 'eo005-first-paint')`) as close to first paint as Playwright
    allows (immediately after `domcontentloaded`, before waiting on any
    branding-dependent selector).
  - Waits for the branding fetch to settle (`expect.poll` on the computed
    `--color-brand-600` value), captures a second screenshot
    (`shot(..., 'eo005-settled-frame')`) — the required screenshot pair.
  - Asserts `firstPaintColor !== settledColor` — pinning the KNOWN, accepted
    MINOR flash (`suggested_action: none` in the scenario fixture) as an
    explicit, polarity-sensitive regression assertion: a future fix to EO-005
    would need to flip this assertion, not just delete the test, which is the
    correct behaviour for a documented-not-fixed finding.
