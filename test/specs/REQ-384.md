TEST-DESIGNER pass. Both ELIXIR-DEV (Part A, backend) and FRONTEND-DEV (Part B,
frontend) wrote substantial inline coverage as part of implementation
(commit `2b7f4a28` on `feature/WF02-REQ384-20260922`). Per this session's

## AC1 — in-app control, gated on multi-membership, no full-page OIDC re-auth

> "a signed-in user whose account holds membership in more than one tenant ...
> sees an in-app control to select which tenant they are acting as, without a
> full-page OIDC re-authentication"

**Backend** (`test/letflow/routers/me_test.exs`, ELIXIR-DEV, confirmed
adequate): `GET /me/memberships` returns exactly one entry (the home tenant)
for a user with zero `tenant_memberships` rows, and two entries when an
admin-granted membership exists — this is the data AC1's gating condition
(`memberships.length > 1`) is computed from.

**Frontend gap found and closed.** `TenantSwitcher.tsx` — the component AC1 is
actually about — had **zero dedicated test coverage** from either
ELIXIR-DEV/FRONTEND-DEV's inline pass. The three existing new test files
(`useTenantScopedQueryKeys.test.ts`, `AuthProvider.switchTenant.test.tsx`,
`AuthenticatedShellRoot.test.tsx`) cover AC2/AC3's cache/remount mechanisms
but never render `TenantSwitcher` itself, so the render-gate AC1 literally
names ("sees a control" / implicitly, a single-membership user sees none) was
untested. New file: `web/src/auth/__tests__/TenantSwitcher.test.tsx`.

- TC-REQ384-16 / -17: renders `null` for a single-membership user and while
  memberships are still loading — exists why: without the loading-state case,
  a control could flash into existence and vanish, which is itself a stale-UI
  bug of the same shape AC3 is about, just at the switcher's own render gate.
- TC-REQ384-18: multi-membership user sees the trigger + menu, the **active**
  tenant is excluded from the option list, `display_label` is preferred over
  `tenant_display_name` when set — exists why: proves the render-gate isn't
  merely "any list," it's specifically "other tenants I could switch to."
- TC-REQ384-19: selecting an option calls `switchTenant(slug)` with the
  correct target — exists why: closes the loop between the UI control and the
  mechanism (`AuthProvider.switchTenant`) that actually performs the silent
  switch; without it a wiring bug (wrong slug, wrong handler) would pass every
  other test in the suite.
- TC-REQ384-20: `'interaction_required'` renders the explicit, user-initiated
  sign-in affordance (§5.2's fallback) and clicking it drives
  `getOrCreateManagerForTenant` + `manager.signinRedirect` — exists why: this
  is the concrete "no *automatic* full-page re-auth" boundary AC1 draws; an
  explicit user-chosen sign-in is allowed, an automatic one is not, and only a
  test that distinguishes the two outcomes can prove the UI respects that
  line.
- TC-REQ384-21: `'error'` renders a retry affordance, never a raw blob —
  exists why: matches design §6.1's own requirement and the platform's
  general "no raw error dumped to the user" convention.

## AC2 — tenant-namespaced query keys, verified by an actual tenant switch

> "verified by a test that switches the active tenant in a test harness and
> asserts the previous tenant's cached entries are neither read nor served
> under the new tenant's key"

**Confirmed adequate, not just "keys look namespaced."**
`useTenantScopedQueryKeys.test.ts` (FRONTEND-DEV, 6 tests, run and green)
proves every listed tenant-scoped group's key leads with
`['tenant', tenantId, ...]` and that exempt groups (`admin.tenants`,
`admin.health`, `onboarding`, `me.memberships`) never gain the prefix.
`AuthProvider.switchTenant.test.tsx`'s TC-REQ384-07 (FRONTEND-DEV) goes
further and is the requirement's own literal verification method: it seeds a
real `QueryClient` with a tenant-A-keyed entry, drives an actual
`switchTenant('tenant-b')` call through `AuthProvider`, and asserts
`getQueryData(tenantAKey)` is `undefined` afterward (removed, not merely
invalidated-and-still-synchronously-readable).

## AC3 — no stale tenant-A row anywhere, including mid-transition

> "a test asserts no stale row from tenant A is present in the rendered DOM at
> any point after a switch to tenant B, including the frame during the
> transition"

**Confirmed adequate.** `AuthenticatedShellRoot.test.tsx` (FRONTEND-DEV, 3
tests) proves both structural mechanisms design §7.3 requires together:
TC-REQ384-10 (transition placeholder renders, `AppShell` does not, while a
switch is in flight) and TC-REQ384-11/-12 (a changed `tenant_id` fully
remounts the shell — proven via a mount counter — while the *same* `tenant_id`
across re-renders does not). `AuthProvider.switchTenant.test.tsx`'s
TC-REQ384-07 covers the third mechanism (remove-not-invalidate).

**Gap found and closed: the cache-isolation race SECURITY-REVIEWER analyzed.**
Design §7.3.1 requires `cancelQueries` (abort in-flight tenant-A fetches)
strictly before `removeQueries`, specifically to prevent a straggler fetch
that was already in flight when the switch started from resolving late and
repopulating the tenant-A-keyed cache entry after the switch has moved on.
No existing test had an actually-in-flight fetch racing the switch —
TC-REQ384-07 only covers a fetch that had already **settled** before the
switch (via `setQueryData`). New test, appended to
`AuthProvider.switchTenant.test.tsx`:

- TC-REQ384-22: starts a real in-flight `queryClient.fetchQuery` against the
  outgoing tenant's key with a `queryFn` that deliberately ignores its
  `AbortSignal` (the realistic worst case) and resolves only when the test
  tells it to; drives a successful `switchTenant`; asserts `cancelQueries`
  was actually called, scoped to the outgoing tenant's own prefix, strictly
  **before** `removeQueries` (via `invocationCallOrder`); then resolves the
  straggler and re-asserts the cache entry is still gone.

  **Why this needed a spy, not just a `getQueryData` check (recorded here
  because it materially changed the test):** direct experiment (temporarily
  dropping `AuthProvider.tsx`'s own `cancelQueries` call and re-running this
  test) showed `removeQueries` alone already deletes the `Query` instance
  from the client's internal map, so a bare `getQueryData` assertion after a
  late resolution passes **even with `cancelQueries` removed** — it would not
  catch a regression that drops the call design §7.3.1 requires. The
  load-bearing, regression-sensitive assertion is that `cancelQueries` is
  actually invoked, correctly scoped, and ordered before `removeQueries`.
  Verified: with the source mutated to drop `cancelQueries`, this test fails
  (`expected "cancelQueries" to be called ... Number of calls: 0`); reverted,
  and the test passes again.

## Additional gap found and closed (not tied to a single AC by number, but
load-bearing for AC1/AC2 together): `fetchTenantConfigForSlug` isolation
from `tenantConfig.ts`'s `_cachedConfig`

Design §5.2 flags this by name as "exactly the class of bug this whole design
exists to prevent, relocated from the query cache into the auth layer, and
MUST NOT happen" — the specific failure CODE-DESIGN-VALIDATOR's rework
guarded against. No test in either inline pass exercised this property. New
tests, appended to `web/src/auth/tenantConfig.test.ts`:

- TC-REQ384-13: populating `_cachedConfig` via `fetchTenantConfig` for tenant
  A, then calling `fetchTenantConfigForSlug` for tenant B, returns tenant B's
  config (a real second network call), not tenant A's cached value.
- TC-REQ384-14: `fetchTenantConfigForSlug` never writes into `_cachedConfig`
  — a subsequent `fetchTenantConfig` call still hits the network fresh.
- TC-REQ384-15: two different slugs each get their own independently-cached
  entry in `fetchTenantConfigForSlug`'s own `Map` (second call for the same
  slug is a real cache hit; a different slug's cached value is undisturbed).

## Backend property confirmed: no shared `users` row, lookup keyed only off
the caller's own JWT (decision 0038's ratification precondition)

`test/letflow/routers/me_test.exs`'s "200 includes admin-granted memberships
alongside the home tenant" test structurally demonstrates this: `other_tenant`
has **no `users` row created in its schema at all**, and the membership still
resolves correctly via `subject_key` (normalized email) alone — the lookup
cannot be going through any per-tenant `users` join, because there is nothing
on the other side of such a join. Combined with `Letflow.Routers.Me`'s own
`resolve_caller/3` (reads `email` only from `conn.assigns.auth_context.user_id`
scoped to the *caller's own* tenant prefix — `lib/letflow/routers/me.ex`),
this confirms the property 0038 depends on: no shared `users` row, and the
subject key is derived only from the requesting JWT's own already-authenticated
identity, never a second lookup elsewhere. No new test needed — existing
coverage already proves this by construction, not merely by not-contradicting
it.

Field-selection (INV-2, "never `idp_realm_id` or OIDC config") is enforced
structurally in `lib/letflow/routers/me.ex`'s `home_tenant_json/1` and
`membership_json/1` — both hand-construct a fixed 4-key map, so there is no
code path that could leak an extra field regardless of what's on the `Tenant`
struct. Lower-risk than a data-dependent bug, but flagged as a minor
regression-safety gap: no test asserts `refute Map.has_key?(entry,
"idp_realm_id")` as a defense-in-depth regression guard. Not written — the
existing structural guarantee (a fixed map literal, not a struct passthrough)
makes this check unlikely to ever start failing silently, and TEST-DESIGNER's
mandate is closing gaps that are actually testable-and-missing, not adding a
test for every theoretically-possible-but-structurally-prevented regression.
