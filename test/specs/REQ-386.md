# Test Spec: REQ-386 — Time-limited, expiring signed URLs for attachment content

**Requirement (brief):** Time-limited, expiring signed URLs for instance-attachment
byte content, replacing direct unbounded authenticated GET. Adds
`POST /instances/:id/attachments/:attachment_id/link` (mints a signed, 5-minute/300s
token; `:AttachmentsRead`-scoped) and
`GET /instances/:id/attachments/:attachment_id/link-content?link_token=...`
(verifies the token, serves content on success, 410 with a fixed plain-language detail
on failure — never document bytes). REQ-211/212's existing not-found-folding behavior
(`fetch_scoped_attachment_content/3`) is explicitly unchanged and its existing tests
(`test/letflow/routers/req212_attachments_routes_test.exs`,
`test/letflow/repository/attachments_test.exs`) are not touched by this run.

**Test tier:** unit (`Letflow.Repository.AttachmentLinks.issue/3`/`verify/3` directly)
+ integration (the two new HTTP routes on `Letflow.Routers.Instances`).

**Full acceptance criteria:** see this run's handoff
`context.requirement_text`/`task.acceptance_criteria` (not restated here to avoid
drift) — six criteria: (1) issue-with-bounded-expiry + usable-before-expiry; (2)
expired token refused with a plain-language message, no bytes, no real sleep; (3) a
fresh link for the same attachment_id after a prior one expired succeeds; (4)
expired-or-invalid response byte-identical for a cross-tenant-presented token vs. a
token naming a never-issued attachment id; (5) REQ-211/212's existing behavior/tests
unchanged; (6) `mix compile --warnings-as-errors`/`mix test` pass.

## Test cases

### Unit — `test/letflow/repository/attachment_links_test.exs`

1. **Valid round-trip** — `issue/3` then `verify/3` recovers the same `attachment_id`.
   Proves the basic contract both routes are built on; would fail if the token format,
   HMAC signing, or payload decoding were broken in either direction. — see
   `"issue/3 + verify/3: valid round-trip"` describe block.
2. **Stated expiry is exactly 300s** — `expires_at` is exactly 300 seconds after the
   injected `now`. Proves the "stated, bounded expiry" language of AC1 is a real,
   checkable number, not just "some future timestamp" — would fail if the expiry
   constant were silently changed or miscalculated (off-by-one, wrong unit). —
   `"expires_at is exactly 300 seconds..."`.
3. **Expired via injected clock (AC2)** — a token verified 1 second past its 300s
   boundary is refused; a second case verifies the **strict** `>` boundary (verified at
   exactly `expires_at` is already expired, not still valid). Both use `opts[:now]`
   injection, never `Process.sleep` — would fail if `verify/3`'s expiry comparison used
   `>=` instead of `>`, or didn't check expiry at all. — `"verify/3: expired token
   (injected clock, no sleep)"`.
4. **Fresh issuance after a prior one expired (AC3)** — mint a token, expire it (via
   clock injection), confirm it's refused, then mint a **second**, independent token
   for the **same** `attachment_id` and confirm it verifies successfully at a time
   shortly after its own issuance. Proves `issue/3` is genuinely stateless (no "already
   issued a link for this attachment" gate) — would fail if a hidden per-attachment
   issuance record ever got added that rejected a second issuance. —
   `"issue/3: a fresh issuance for the same attachment_id after a prior one expired"`.
5. **Malformed token** — no `.` separator, invalid base64 payload, valid-base64-but-
   invalid-JSON payload, and an empty string, each individually asserted to return
   `{:error, :expired_or_invalid}` rather than raising or returning a different error
   shape. Proves `verify/3`'s `with`/`else` chain actually catches every one of these
   distinct failure shapes into the single collapsed value INV-5/AC4 depends on — would
   fail if any one of these malformed inputs raised (a `MatchError`/`FunctionClauseError`
   surfacing as a 500 at the route layer) or returned a different error atom. —
   `"verify/3: malformed token"`.
6. **Wrong-tenant token** — a token validly issued under tenant A, presented for
   verification under tenant B (no expiry involved at all — issued and verified at
   nearly the same instant), is refused. Proves cross-tenant rejection is mechanical
   (the requester's own tenant's signing key never matches what a different tenant's
   token was signed with), not merely a coincidence of the expiry check — would fail if
   `verify/3` resolved the signing key from anything other than the caller's own
   authenticated `tenant_id`. — `"verify/3: wrong-tenant token"`.
7. **Tampered payload** — swap the payload segment for a different, still well-formed
   JSON payload (different `attachment_id`), keep the original signature segment;
   refused. Proves the signature genuinely covers the payload bytes (an attacker
   cannot re-point an old, validly-signed token at a different attachment id) — would
   fail if `verify/3` decoded and trusted the payload before checking the signature, or
   recomputed the signature over something other than the raw payload bytes. —
   `"verify/3: tampered token"` (first case).
8. **Tampered signature** — flip one byte of the signature segment; refused. Proves the
   signature is actually checked byte-for-byte (`:crypto.hash_equals/2`), not merely
   present — would fail if signature verification were skipped or used a non-constant,
   loosely-comparing check that happened to still pass. — `"verify/3: tampered token"`
   (second case).

### Integration — `test/letflow/routers/req386_attachment_links_routes_test.exs`

9. **AC1 — issue response shape** — `POST .../link` returns 200 with
   `attachment_id`/`token`/`url`/`expires_at`/`expires_in_seconds`, `url` embedding the
   `link_token` query param, `expires_at` genuinely in the future. Would fail if any
   documented response key were renamed/dropped or if the URL didn't actually carry a
   usable token. — `"AC1: POST .../link"` (first case).
10. **AC1 — usable before expiry** — issue a link, then use it immediately to fetch the
    exact original bytes with the correct `Content-Type`/`Content-Disposition`. Would
    fail if the new route didn't actually reach `fetch_scoped_attachment_content/3`/
    `send_attachment_content/2`, or corrupted the response. — `"AC1..."` (second case).
11. **AC1 — 404 for a nonexistent attachment_id on issue** — matches this router's
    established not-found precedent (`fetch_scoped_attachment_metadata/3` reused
    verbatim); would fail if the issue route skipped the existence/scoping check
    entirely and minted a token for an attachment that doesn't exist. — `"AC1..."`
    (third case).
12. **AC2 — expired token, no bytes** — a token minted with an already-past `expires_at`
    (via `AttachmentLinks.issue/3`'s own `now:` option — see the file's moduledoc for
    why this, not a real sleep, deterministically produces an expired token at the HTTP
    layer) is refused with 410, the exact fixed detail string, and the response body is
    asserted to contain neither the real document bytes nor a `"content"` key. Would
    fail if expiry weren't actually enforced at the route layer, or if the response
    leaked bytes on a failure path. — `"AC2: ... -- expired token"` (first case).
13. **AC2 — malformed/missing token also 410** — a syntactically bogus `link_token` and
    a wholly absent `link_token` query param both get the same 410, not a 500 or a
    different 4xx. Would fail if the route's `verify_link_token/2` guard clause for a
    missing/non-binary token were removed. — `"AC2..."` (second, third cases).
14. **AC3 — fresh link after a prior one expired** — the same sequence AC3 requires
    exercised end to end through real HTTP: expired attempt (410) → issue a fresh link
    for the same `attachment_id` (200) → use the fresh link (200, correct bytes). Would
    fail if a prior expired/failed link somehow blocked a later legitimate one, or if
    the fresh token issued didn't actually work. — `"AC3: fresh link after a prior one
    expired"`.
15. **AC4 — byte-identical, cross-tenant-presented vs. never-issued** — THE core AC4
    test. See "AC4 construction" below. Would fail if the response for either case ever
    depended on the presented `attachment_id`, e.g. if a future change made the
    link-content route check attachment existence/scoping *before* token verification,
    or branched the 410 body/status by failure cause. —
    `"AC4: cross-tenant-presented token vs. never-issued attachment id -- byte-identical"`
    (both cases).
16. **Permission enforcement** — `AGENT_RUNNER` (holds neither `AttachmentsRead` nor
    `AttachmentsManage`, per this router's own documented role matrix) gets 403 on both
    new routes. Would fail if either `authz_post`/`authz_get` declaration were changed
    to a weaker/missing policy key. — `"permission enforcement..."`.

## AC4 construction (as required by the run's own instruction)

Two tenants (`tenant_1`, `tenant_2`), one shared `instance_id`. `tenant_1` has a real
attachment; `AttachmentLinks.issue/2` mints a **validly-signed, unexpired** token for it
under `tenant_1`'s own signing key. `tenant_2` also has its own real, different
attachment (used only to populate the URL's `:attachment_id` segment).

- **Response A ("cross-tenant"):** `tenant_2`'s authenticated caller presents
  `tenant_1`'s token against `tenant_2`'s **own real** attachment_id in the URL.
- **Response B ("never-issued"):** the same `tenant_2` caller presents the **identical**
  `tenant_1` token against a fabricated UUID that was never uploaded or issued a link by
  anyone.

Both fail identically: `AttachmentLinks.verify/2` resolves the signing key under the
**requester's own** tenant (`tenant_2`), which never matches the key `tenant_1`'s token
was actually signed with — so verification fails at the same internal step
(HMAC-SHA256 mismatch) regardless of which `attachment_id` is in the URL, and that URL
value is never inspected on this failure path at all (`check_attachment_id_matches/2`
and `fetch_scoped_attachment_content/3` are both unreached once `verify_link_token/2`
already failed). The test asserts `status`, the `content-type` header, and the full
`resp_body` are identical between the two responses — no `trace_id` normalization is
needed because both conns are built via this file's `build_conn/4`, which assigns the
same fixed `"fixed-test-trace-id"` on every request (mirroring
`req212_attachments_routes_test.exs`'s own precedent for this same fixed-trace_id
technique). A second, simpler case in the same describe block additionally compares an
expired-token response against a garbage/never-issued-token response for the same
tenant, for the same byte-identical assertion from the "expired" side of AC4's wording.
