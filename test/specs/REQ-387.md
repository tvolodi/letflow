# Test Spec: REQ-387 — Frontend document-viewer screen for instance attachments

**Requirement (brief):** REQ-387, stage S8. Adds a typed frontend API client for
attachment upload/list/signed-link (`web/src/api/attachments.ts`, `client.getBlob`), a
document-viewer route/page (`AttachmentViewerPage` + four response-state
sub-components) that renders attachment bytes through an authenticated
`fetch` → `Blob` → `URL.createObjectURL` path (never a bearer-token-less raw
`<img src>`/`<a href>`/`<iframe src>` against the backend — design §1 decision D1),
and the permanent Playwright e2e spec
`web/tests/e2e/pipelines/attachment-cross-tenant.pipeline.e2e.spec.ts`
(`attachment-cross-tenant-probe`, PW-09). Full design:
`lib/letflow/design/req387-attachment-document-viewer.md`.

**Author's note (TEST-DESIGNER audit turn):** FRONTEND-DEV already wrote substantial
self-authored coverage for this requirement (5 + 7 + 2 unit/component tests, plus the
e2e spec) and REVIEWER independently confirmed it was real, not vacuous. This spec
documents TEST-DESIGNER's independent AC-to-test audit, records the commands actually
run (not "should pass"), and adds one new test that closes a real gap found during a
targeted mutation check (see "Mutation check" below).

**Full acceptance criteria:** see this run's handoff
`context.requirement_text`/`task.acceptance_criteria` (not restated here to avoid
drift) — six criteria: (1) typed API client for upload/list/signed-link matching
`entities.ts` conventions; (2) document-viewer renders successfully for a same-tenant,
valid, unexpired link; (3) foreign-tenant vs. never-issued attachment reference →
byte-identical markup/text, checked by an explicit DOM/snapshot assertion, not "both
show an error"; (4) expired-link response → distinct message from AC3's screen, no
document content, an affordance to request a fresh link; (5) the permanent Playwright
spec exists, is real, and passes; (6) the stale ISS-0527 `NOTE` block is removed from
the scenario fixture.

## Why each test case exists (not just a restatement of the criterion)

- **AC2/AC4's two success-path cases** (`'renders AttachmentSuccessView...'` and
  `'skips issuance...'`) exist as two *separate* cases because they exercise two
  different branches of the design's step machine (§3.2 steps 2→3 vs. step 4's
  "URL already carries `link_token`" skip) that share no code path in
  `AttachmentViewerPage` — a bug that broke only the reload/bookmark branch (e.g. an
  `if` that always re-issued a link even when `link_token` was present) would pass the
  first case and fail only the second. The assertion
  `expect(issueLink).not.toHaveBeenCalled()` in the second case is what actually proves
  the skip happened, not merely that content rendered.
- **The two distinct-404-origin cases** (`'...when link issuance 404s'` and `'...when
  content-fetch 404s'`) exist because AC3's guarantee has to hold across *both* of the
  design's two 404-producing call sites (§3.2 steps 2 and 3), not just one — the design
  explicitly calls out that both branches render "the same value/same rendered
  component" (§3.2 step 3), and a regression that special-cased one branch (e.g. an
  accidental prop threaded through only the step-2 path) would show up as an asymmetry
  between these two cases that a single case covering only one branch could not catch.
- **The byte-identical-text case** exists because AC3's own wording (design §5) requires
  "a snapshot or explicit DOM assertion... not just 'both show an error'" — the test's
  `expect(secondText).toBe(firstText)` on captured `.textContent` is a literal instance
  of that required assertion shape, distinct from (and stronger than) merely asserting
  each screen individually shows `data-testid="attachment-not-found"`.
- **The 410-expired case** exists to prove two things in one assertion set that could
  independently regress: (a) the distinct `attachment-link-expired` testid renders
  (AC4's "distinct message" half) and (b) `attachment-content` is *absent*
  (`queryByTestId(...).not.toBeInTheDocument()` — AC4's "no document content" half). A
  component that rendered both the expired banner *and* a stale cached blob
  simultaneously (a real risk if `status` were derived from two separate booleans
  instead of one discriminated-union field, per design §3.2's own reasoning for using
  one `ViewerStatus` field) would pass a test that checked only (a).
- **The blob-URL-not-raw-backend-URL case (added this turn)** exists because none of
  FRONTEND-DEV's existing cases asserted on the actual `src` value of the rendered
  `<iframe>`/`<img>`/download `<a>` — every existing case stopped at "the
  `attachment-content` container is present." That leaves the single most
  security-relevant fact in the whole design (D1: bytes must flow through an
  authenticated blob, never a bearer-token-less direct backend URL) unchecked by any
  test. Demonstrated as a real, not theoretical, gap — see "Mutation check" below.

## Mutation check (security-relevant assertion)

**Target:** `AttachmentSuccessView`'s object-URL indirection (design D1) — the single
fact the whole design's security argument (§1 D1, "no bearer-token-less browser
navigation against the backend") rests on.

**Mutant applied** (`web/src/pages/instances/attachments/AttachmentSuccessView.tsx`):
replaced `URL.createObjectURL(blob)` with a raw backend path
(`` `/api/v1/instances/${instanceId}/attachments/${attachmentId}/link-content` ``) as
the `<iframe>`/`<img>`/download-`<a>` `src`/`href` — i.e., exactly the regression D1
exists to prevent.

**Before adding a new test:** ran `AttachmentViewerPage.test.tsx` (FRONTEND-DEV's
original 7 cases) against the mutant — **all 7 still passed.** None of the existing
cases inspect the actual `src`/`href` value of the rendered element, only that
`data-testid="attachment-content"` is present. This is a real, not theoretical, gap:
the mutant is the exact security regression D1 is written to prevent, and no test in
the suite caught it.

**Test added:** `'renders content via a browser-local blob: object URL, never the raw
backend link-content URL (D1)'` in `AttachmentViewerPage.test.tsx` — asserts the
rendered `<iframe>`'s `src` starts with `blob:` and contains neither
`/api/v1/instances/` nor `link-content`.

**Measured counts:**
- Against the mutant: `vitest run AttachmentViewerPage.test.tsx` → **8 tests, 1
  failed** (the new test; `AssertionError: expected false to be true` on
  `src.startsWith('blob:')`), 7 passed. Full output captured above the fix.
- Mutant reverted (`AttachmentSuccessView.tsx` restored byte-for-byte to
  FRONTEND-DEV's original, diffed against a pre-mutation backup to confirm): `vitest
  run AttachmentViewerPage.test.tsx` → **8 tests, 8 passed.**

This demonstrates the new test is load-bearing (fails on the real regression, passes on
the real fix) rather than vacuous.
