# REQ-388 — Audit-log entry for a denied cross-tenant or otherwise-failed instance-attachment access attempt

## Requirement text

> A denied instance-attachment content fetch (cross-tenant or
> cross-instance-same-tenant) writes exactly one `Letflow.Audit` entry naming
> the requesting actor, the attempted `attachment_id`, and a UTC timestamp — a
> test asserts the entry's presence and content over real HTTP, not by calling
> a context function directly. The audit write does not change
> `handle_get_attachment_content/3`'s existing byte-identical not-found
> response for a foreign-tenant id vs. a never-issued id — REQ-211/212's
> existing indistinguishability test still passes unmodified. The audit write
> introduces no observable added latency variance between the audited
> (denied) branch and the non-audited (success) branch that would itself
> become a new timing side-channel — state in the design doc how this was
> checked and why it's sufficient. `web/src/pages/admin/AuditLogPage.tsx`
> surfaces the new entry with no frontend change. `mix compile
> --warnings-as-errors` and `mix test` both pass; SECURITY-REVIEWER sign-off
> is required before merge.

See `lib/letflow/design/req388-attachment-access-denial-audit.md` for the
full design. Implementation: `lib/letflow/routers/instances.ex`
(`fetch_scoped_attachment_content/4`, widened from arity 3 to receive `conn`;
new private helper `record_attachment_access_denied_audit/5`).

## Acceptance criteria → test-case map

### AC1 — a denied fetch writes exactly one entry naming actor/attachment_id/timestamp, verified over real HTTP

`test/letflow/routers/req388_attachment_access_denial_audit_test.exs`:

- `"AC1: cross-tenant/never-issued fused denial"` → `"a cross-tenant
  attachment id writes exactly one attachment.access_denied entry naming the
  actor and attempted id"` — dispatches a real `GET
  /instances/:id/attachments/:attachment_id` through
  `Letflow.Routers.Instances.call/2` for an attachment that belongs to a
  *different* tenant, then reads the audit trail back through a real `GET
  /audit` dispatch to `Letflow.Routers.Audit.call/2` (never
  `Letflow.Audit.list_entries/1` called directly) — this is what makes the
  test prove the entry is reachable over the same HTTP surface an operator
  would actually use, not merely that a row landed in `audit_entries`.
  Asserts `count == 1` (not "at least one"), `action ==
  "attachment.access_denied"`, `resource_id == tenant_b_attachment.id`,
  `actor_id == actor_id`, `after_state["reason"] ==
  "cross_tenant_or_not_found"`, and `refute is_nil(item["timestamp"])`. Also
  asserts tenant B's own audit trail is empty (`count == 0`) — proving the
  write's `prefix` provenance (INV-1) is exercised, not just asserted in the
  design doc.
- `"a genuinely never-issued attachment id writes the same shape of entry"`
  — same assertions against an id with no row under any tenant, proving §3's
  fused-bucket boundary (cross-tenant and never-issued are structurally
  indistinguishable and therefore audited identically) is real, not just a
  design-doc claim.
- `"AC1: cross-instance-same-tenant denial"` → `"an attachment real and
  tenant-correct but belonging to a different instance writes one entry"` —
  proves the second audited branch (§2's dispatch table row 2) independently:
  `resource_id == attachment.id`, `after_state["reason"] ==
  "cross_instance"`. Together with the two fused-branch tests above, every
  row of §2's "audited?" column that says "yes" has its own concrete test.
- `"no audit entry on a successful fetch"` → the negative control: a real,
  same-tenant, same-instance fetch (200) writes zero
  `attachment.access_denied` entries. Without this, a bug that always wrote
  an audit entry regardless of outcome would still pass every test above.

### AC3 — no observable added latency variance between audited-denied and non-audited-success branches

**No runtime timing assertion exists in the test suite for this AC — it is
argued in the design doc only (§4), not measured by any test.**
`grep -n "timing\|latency\|monotonic"
test/letflow/routers/req388_attachment_access_denial_audit_test.exs` returns
no hits.

**Judgment: this is acceptable, and a runtime timing test should not be
added.** Reasoning:

1. AC3's own literal wording asks the design doc to "state ... how this was
   checked ... and why it's sufficient" — it does not ask for a test
   asserting on wall-clock timing. Design §4 does this at length: it
   discloses a *pre-existing*, upstream timing asymmetry in
   `Attachments.get_content/2` (an unconditional artifact-blob read before
   the instance-id check, independent of this design), argues structurally
   that this design's own addition (one `Audit.insert_entry/3` call, uniform
   across both audited branches) does not widen that gap, and explicitly
   declines to equalize denied-vs-success latency since the status code
   already discloses that distinction with no new information added by
   timing.
2. A wall-clock timing test in this suite would be exactly the kind of test
   this project's own directives warn against: notoriously flaky across CI
   hardware, load, and GC pauses, and — per `record_task_activation_rejection_audit/5`'s
   own established precedent (design §1) and REQ-211/212's own moduledoc,
   cited in the design doc — this codebase already relies on structural
   arguments rather than empirical timing measurements for exactly this
   class of claim, with no test infrastructure in this pipeline for
   production-shaped latency measurement (design §4 point 3 states this
   directly).
3. A coarse sanity check (e.g., "assert the audited path doesn't take 10x
   longer than the non-audited path") was considered and rejected: the
   design doc's own honest disclosure is that the *pre-existing* asymmetry
   (extra `Repo` round-trip + full blob read for cross-instance-same-tenant
   vs. none for the fused case) is real and already order-of-magnitude
   relevant depending on artifact size — a coarse test asserting "no
   order-of-magnitude difference" would be testing a claim the design doc
   itself already says is false for reasons unrelated to this requirement's
   own scope, and would either be flaky (small artifacts) or a known false
   assertion (large artifacts) rather than useful coverage.

This verdict is stated explicitly rather than silently treating "no test"
as an oversight — TEST-DESIGN-VALIDATOR should treat design §4 plus this
section as AC3's complete disposition, not an open gap.

### AC4 — frontend surfaces the entry with no code change

Nothing to test (explicitly, per the requirement's own wording — the claim

## Design-doc correction made this turn

Design doc §2's helper-arity spec (previously described a 4-arity
`record_attachment_access_denied_audit(attachment_id, found_attachment,
instance_id, conn)`) did not match the shipped 5-arity signature
(`record_attachment_access_denied_audit(attachment_id, found_attachment,
instance_id, opts, conn)` — `opts` threaded through explicitly so the
helper can derive `prefix` itself). Fixed directly in
`lib/letflow/design/req388-attachment-access-denial-audit.md` §2 (updated
`@spec`, added a note explaining the extra `opts` argument, updated both
call-site examples, and fixed two later `/4` → `/5` references in §4 that
cited the same helper).
