## Acceptance criteria and test mapping

### AC1 — Disallowed content_type rejected before size/scan/quota/DB-write

> "upload/2 rejects a caller-declared content_type outside a stated allowlist with a new,
> distinct error tag, checked before the size ceiling, the malware scan, and any DB
> write -- a test asserts no repository_artifacts or instance_attachments row is created
> for a rejected upload"

**Test 1:** `test/letflow/repository/attachments_test.exs` —
`"REQ-389: content-type allowlist" > "a disallowed content_type is rejected before any
persistence, with neither row created (AC1)"`

Calls `Attachments.upload/2` with `content_type: "video/mp4"` (an explicitly-excluded
type per design §2.1). Asserts the return is exactly `{:error, :content_type_not_allowed}`,
then queries the DB directly (`Repo.aggregate(Artifact, :count, ...)` and
`Repo.aggregate(Attachment, :count, ...)`) to prove absence of both rows — not merely
inferred from the return value. Why it would fail if violated: if the allowlist check were
missing, absent, or silently permissive, `upload/2` would return `{:ok, %Attachment{}}`
and both aggregate counts would be 1, not 0.

**Test 2 (ordering proof):** `"content_type_not_allowed wins over file_too_large and
storage_quota_exceeded when all three would independently fire (AC1 ordering)"`

Constructs a request with `content_type: "video/mp4"` (disallowed), an oversized ~26 MiB
body (would independently trigger `:file_too_large`), AND a tenant whose storage
allowance is already exhausted (would independently trigger `:storage_quota_exceeded`).
Asserts the return is exactly `{:error, :content_type_not_allowed}` — never the other two
tags. Why it would fail if violated: if the content-type guard were moved after the size
check or the quota check (instead of being the literal first statement in `upload/2`, per
design §3.1), this test would observe `{:error, :file_too_large}` instead, since that
guard runs on the same oversized body.

### AC1 (ordering non-regression) — existing REQ-390 tests unaffected

> confirm the two existing REQ-390 ordering tests remain unaffected by the reordering
> this requirement introduces (design §3.1).

Not a new test — `"storage_quota_exceeded triggers without hitting file_too_large (AC3)"`
and `"file_too_large triggers without triggering storage_quota (AC3)"`
(`test/letflow/repository/attachments_test.exs`, both pre-existing) both use
`upload_attrs/1`'s default `content_type: "text/plain"`, which is in the REQ-389 allowlist
(design §2.1/§2.3) — the new first-checked guard passes silently for both, so neither
test's outcome changes. Verified below (Verification section) by running both by name
and confirming they still pass unmodified.

### AC2 — Route-level 415 naming rejected type and allowed set, distinct from other error bodies

> "the route layer renders the rejection as a 4xx response naming the rejected
> content_type and the allowed set in plain language, distinct from the existing
> :file_too_large and :infected response bodies -- a test asserts the response body text"

**Test:** `test/letflow/routers/req212_attachments_routes_test.exs` —
`"REQ-389: POST upload with a disallowed content_type" > "returns 415 naming the
rejected type and the allowed set, distinct from file_too_large (413) and infected (422)
bodies"`

Drives a real multipart upload (`dispatch_multipart/6`, this file's own established
helper) with `content_type: "video/mp4"`. Asserts `conn.status == 415`; asserts the
decoded JSON body's `"detail"` contains `"video/mp4"` AND contains `"application/pdf"`
(a named member of the allowed set) — proving both halves of AC2's "naming the rejected
content_type and the allowed set" wording. Additionally asserts that `resp["type"]` (the
Problem-Details `type` URI) differs from the `:file_too_large` (413) and `:infected`
(422) cases' own detail text — driving one small multipart request down each of the three
paths in the same test and comparing status codes and detail strings directly, rather
than assuming distinctness from having read the source. Why it would fail if violated: if
the route rendered a generic/shared error message for all three error tags (e.g. all
mapped through `Response.unprocessable/2`), the status codes and/or detail text would
collide instead of differing.

### AC3 — application/pdf continues to be accepted (regression)

> "an allowed content_type (e.g. application/pdf) already accepted before this change
> continues to be accepted after it -- a regression test using the same fixture
> REQ-211/212's own tests use"

**Test:** `test/letflow/repository/attachments_test.exs` —
`"REQ-389: content-type allowlist" > "application/pdf continues to be accepted (AC3
regression, same fixture REQ-211/212's own tests use)"`

Per design §3.4, the exact fixture already exercised is `content_type: "application/pdf"`
with body `"PDF-BYTES-HERE"` (`test/letflow/routers/req212_attachments_routes_test.exs`
line 145, `"delivery-note.pdf"`/`"application/pdf"`/`"PDF-BYTES-HERE"`) — this test reuses
that exact `content_type`/byte fixture at the context-module level. Asserts
`{:ok, %Attachment{content_type: "application/pdf"}}`. Why it would fail if violated: if
the allowlist accidentally omitted `application/pdf` (e.g. a typo in the `MapSet.new/1`
literal), this previously-accepted type would now be rejected with
`{:error, :content_type_not_allowed}`.

## Mutation testing (fail-then-pass evidence)

Two load-bearing assertions were mutated and reverted, per this project's discipline:

1. **"no DB row created for rejected upload"** — the allowlist guard in
   `lib/letflow/repository/attachments.ex` was temporarily disabled (forced to always
   treat the content_type as allowed), confirming the AC1 test genuinely fails without
   the guard, then reverted.
2. **route-level distinct-response-body test** — the new `render_upload_attachment/3`
   clause for `{:error, :content_type_not_allowed}` was temporarily changed to render a
   generic `Response.unprocessable/2` (422) response instead of the specific 415, matching
   the shape of the existing `:infected` clause, confirming the AC2 test genuinely fails
   (both on status code and on the missing rejected-type/allowed-set text), then reverted.

Real command output for both is in the handoff report (not duplicated here — see
TEST-DESIGNER's final message for this requirement).
