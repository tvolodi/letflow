# REQ-391 — Instance-attachment attach/remove events recorded on instance history with attribution, and approval records naming the attachment reviewed

## Requirement text (acceptance criteria, `docs/requirements.yaml`)

1. uploading an attachment produces a history/timeline entry on the owning
   instance naming the file and the uploading actor — a test asserts this
   over the existing history/timeline read path, not by inspecting internal
   state directly
2. removing an attachment produces a distinct history/timeline entry naming
   the file and the removing actor, retained even after the attachment row
   itself is gone
3. an approve (or equivalent) decision recorded while an attachment is
   present on the instance results in a decision record that names that
   attachment (`file_name` at minimum) — a test asserts the recorded
   decision references it
4. the design doc states and justifies the snapshot-vs-live-reference choice
   for the approval record's attachment reference, and a test demonstrates
   the chosen behavior across a subsequent removal of that same attachment
5. `mix compile --warnings-as-errors` and `mix test` both pass, with real
   output quoted

See `lib/letflow/design/req391-attachment-history-approval-attribution.md`
for the full design.

**Provenance note**: this is an audit turn, not an authoring one.
ELIXIR-DEV wrote the full inline test coverage
(`test/letflow/repository/attachments_test.exs`,
`test/letflow/engine_complete_task_test.exs`,
`test/letflow/tenant_provisioning_event_seed_test.exs`) as part of
implementation, and SECURITY-REVIEWER/REVIEWER both already passed the

## Acceptance criteria → test-case map

### AC1 — upload/2 records a history/timeline entry naming the file and the uploading actor

`test/letflow/repository/attachments_test.exs`, describe `"REQ-391 AC1 --
upload/2 records an ATTACHMENT_ATTACHED history entry"`:

- Uploads an attachment with an explicit `uploaded_by` and `file_name`,
  then asserts over `Letflow.Instances.history/3` (not the events table
  directly) that exactly one `ATTACHMENT_ATTACHED` item exists, with
  `actor_id == uploaded_by`, `payload["attachment_id"] ==
  attachment.id`, `payload["file_name"] == "delivery-note.pdf"`.
- Also asserts over `Letflow.Instances.timeline/3` (the human-readable
  rendering path, §2.6 of the design) that the same event's
  `description == "delivery-note.pdf attached by system"` — this is a
  genuine exercise of the new `render_description/3` clause, not just a
  raw-payload check; "system" is the correct actor-display fallback here
  because no `Letflow.Identity.User` row exists for the synthetic
  `uploaded_by` UUID in this test.

This directly satisfies AC1's own wording ("over the existing
history/timeline read path"): both `history/3` and `timeline/3` are
exercised, and the latter proves the description-rendering path (§2.6)
that the design doc itself notes is not strictly required by AC1's literal
wording but is included anyway.

### AC2 — delete/2 records a distinct history entry, retained after the row is gone

`test/letflow/repository/attachments_test.exs`, describe `"REQ-391 AC2 --
delete/2 records an ATTACHMENT_REMOVED history entry"`:

- Uploads an attachment, then calls `Attachments.delete/2` with a distinct
  `deleted_by` actor.
- Confirms the row itself is gone (`Attachments.get/2` ==
  `{:error, :not_found}`).
- Confirms, over `Letflow.Instances.history/3`, that **both** a
  `ATTACHMENT_ATTACHED` and a separate `ATTACHMENT_REMOVED` entry exist
  (proving "distinct", not one event overwritten/replaced by the other),
  with `removed_event.actor_id == deleted_by` and
  `removed_event.payload["file_name"] == "signed-form.pdf"` — i.e. the
  removal entry is retained and correctly attributed even though the
  underlying `instance_attachments` row is a hard delete with no tombstone.

### AC3 — a decision recorded while an attachment is present names that attachment

`test/letflow/engine_complete_task_test.exs`, describe `"REQ-391 --
attachments_at_decision snapshot on TASK_COMPLETED"`, test `"names the
attachment(s) present on the instance at completion time"`:

- Uploads an attachment, completes the pending task via
  `Engine.complete_task/3`, then reads the resulting `TASK_COMPLETED`
  event's payload directly (`task_completed_events/2` test helper) and
  asserts `attachments_at_decision` is a one-element list naming
  `attachment_id`, `file_name`, `content_type`, and `uploaded_by` matching
  the uploaded attachment exactly.

### AC4 — snapshot-vs-live-reference: the design states and justifies the choice, and a test demonstrates it across a subsequent removal

Design doc §4 states and justifies the choice explicitly (snapshot, not a
bare `attachment_id` requiring a later lookup) — four numbered reasons,
including the concrete, load-bearing one: `delete/2` is a hard delete with
no tombstone, so a live reference would resolve to `{:error, :not_found}`
the moment the same attachment is later removed, which is exactly the
scenario this AC names.

**This is the single most important test in the requirement, and it earned
the closest scrutiny.** `test/letflow/engine_complete_task_test.exs`, same
describe block, test `"the snapshot survives a subsequent removal of that
same attachment (design §4, AC4)"`:

1. Uploads an attachment (`signed-form.pdf`).
2. Completes the pending task while the attachment is present
   (`Engine.complete_task/3`) — this produces the `TASK_COMPLETED` event
   with the embedded snapshot.
3. **Then** calls `Attachments.delete/2` on that same attachment.
4. Confirms the row is genuinely gone (`Attachments.get/2` ==
   `{:error, :not_found}`).
5. Re-fetches the **same historical** `TASK_COMPLETED` event via
   `Letflow.Instances.history/3` (the real read path, not internal state)
   and asserts `attachments_at_decision` **still** names the removed
   attachment's `file_name`/`attachment_id`, unchanged.

Confirmed by direct reading: this is exactly the (a)/(b)/(c)/(d) sequence
the design doc's own §4 "Test requirement this implies" section specifies,
in the correct order (upload → complete → delete → re-fetch and assert
unchanged) — not a weaker variant that only checks immediately after
completion (which AC3's own test already covers as a separate, narrower
case).

#### Mutation check (fail-then-pass), performed this turn

Temporarily changed `attachment_snapshot/1` in `lib/letflow/engine.ex`
(the function `append_task_completed_event/5` calls to build each
`attachments_at_decision` entry) from the full embed:

```elixir
defp attachment_snapshot(%Letflow.Repository.Attachment{} = attachment) do
  %{
    attachment_id: attachment.id,
    file_name: attachment.file_name,
    content_type: attachment.content_type,
    byte_size: attachment.byte_size,
    uploaded_by: attachment.uploaded_by,
    created_at: DateTime.to_iso8601(attachment.created_at)
  }
end
```

to a bare live-reference-shaped stub:

```elixir
defp attachment_snapshot(%Letflow.Repository.Attachment{} = attachment) do
  %{attachment_id: attachment.id}
end
```

Re-ran `mix test test/letflow/engine_complete_task_test.exs`:
**both REQ-391 tests failed** (9/11 passed, 2 failed) — both the AC3 test
and the AC4 test, since both call `Engine.complete_task/3` and the mutant
payload is now missing `file_name`, which is a `"required"` field in the
`ATTACHMENT_ATTACHED`... no — in the `attachments_at_decision` item schema
(design §3.3). The failure fires at the `EventStore.append/2` JSON-schema
validation layer, before either test's own assertion is even reached:

```
     code:  assert {:ok, _result} = Engine.complete_task(task.id, attrs, prefix: schema_name)
     left:  {:ok, _result}
     right: {:error,
             {:event_append_failed,
              {:payload_validation_failed,
               [
                 %Letflow.EventStore.Registry.ValidationFailure{
                   field_path: "/attachments_at_decision/0/file_name",
                   constraint: "required",
                   actual: nil
                 }
               ]}}}
```

This is the right failure for the right reason: the mutant produces a
payload that no longer satisfies the registered `TASK_COMPLETED`
schema_version 3 contract (§3.3's `"required": ["attachment_id",
"file_name"]` on each snapshot item), and both tests that exercise
`complete_task/3` with an attachment present correctly go red. Reverted
the mutation immediately after measuring; `git diff --stat
lib/letflow/engine.ex` showed no diff post-revert (clean revert), and
`mix test test/letflow/engine_complete_task_test.exs` returned to
`11 passed`, 0 failures.

## TEST-DESIGNER's own audit findings

### 1. Environmental gap found and resolved: stale `tenant_template` schema masked AC1/AC2 on first run

On the very first run of the four targeted test files in this session
(before any code was touched), 3 of 99 tests failed — all three in
`test/letflow/repository/attachments_test.exs`:

- `"REQ-391 -- event_type_registry seeding"` — `"ATTACHMENT_ATTACHED" in
  names` failed; the freshly-provisioned tenant's `event_type_registry`
  held only the pre-REQ-391 13 platform types.
- Both AC1 and AC2 tests above failed identically:
  `Enum.filter(items, &(&1.event_type == "ATTACHMENT_ATTACHED"))` /
  `"ATTACHMENT_REMOVED"` returned `[]`.

Root cause, confirmed by reading `test/support/tenant_fixture.ex` and
`test/support/tenant_template.ex`: `Letflow.TenantFixture.provisioned_tenant!/1`
defaults `opts[:template]` to `:clone` (ISS-0427) — new tenant schemas are
materialized by cloning a single, long-lived `"tenant_template"` Postgres
schema (`CREATE TABLE ... LIKE ... INCLUDING ALL` plus a raw `INSERT ...
SELECT * FROM "tenant_template".event_type_registry`), not by re-running
`Letflow.TenantProvisioning.replay_migrations/2`'s real seed logic per
test. `Letflow.Test.TenantTemplate.ensure_template!/0` only rebuilds this
template schema if it is **absent** (`template_built_in_db?/0` checks mere
schema *existence* in `information_schema.schemata`, not content or a
migration/seed-list version) — so a `tenant_template` schema left behind
in this shared Postgres instance by an earlier session (before this
branch's `tenant_provisioning.ex` change landed two new
`@platform_event_type_seed_attrs` entries) was silently reused, serving
every `:clone`-path test a stale `event_type_registry` missing
`ATTACHMENT_ATTACHED`/`ATTACHMENT_REMOVED`.

This is **not a REQ-391 code defect** — confirmed by
`test/letflow/tenant_provisioning_event_seed_test.exs`'s own tests, which
call `TenantProvisioning.replay_migrations/2` directly (bypassing the
clone-template fixture entirely) and correctly saw 18 rows (13 + 3
ENTITY_RECORD_* + 2 ATTACHMENT_*) on the very first run, before the
template was touched. It is a test-fixture staleness gap in
`Letflow.Test.TenantTemplate`'s own no-content-version-check design,
**pre-existing and out of REQ-391's scope to fix** (ISS-0427's own module,
not anything this requirement's design touches) — but real enough that it
silently made 3 genuinely-passing-in-production tests fail in this
worktree until diagnosed.

**Resolution applied this turn** (verification only, no code change):
dropped the stale schema directly —

```elixir
Letflow.Repo.query!(~s(DROP SCHEMA IF EXISTS "tenant_template" CASCADE))
```

— which forces `Letflow.Test.TenantTemplate.ensure_template!/0` to rebuild
the template via a genuine `replay_migrations/2` call on next use. Re-ran
the same four files immediately after: **99/99 passed**, 0 failures (see
"Verification run" below).

**Flagged, not silently worked around**: any other host/CI runner whose
Postgres instance already has a `tenant_template` schema built before this
branch's `tenant_provisioning.ex` change will see the same 3 failures on
first run of any `:clone`-path test touching the two new event types,
until that schema is dropped or the runner starts from a fresh database.
This is worth a follow-up issue against `Letflow.Test.TenantTemplate`
(content/seed-list version check, not just existence) but is explicitly
out of scope for REQ-391 itself to fix — recorded here so
TEST-DESIGN-VALIDATOR and RELEASE-VALIDATOR don't re-diagnose it from
scratch if they hit the same stale-schema state on a different host.

### 2. `render_description/3` rendering — confirmed via a real path, not just event presence

Item 4 of this turn's brief asked for confirmation that attach/remove
history entries render with the expected description text via the real
`render_description/3` path, not just that the event exists in the DB.
AC1's own test already does this (see above): it asserts
`timeline_event.description == "delivery-note.pdf attached by system"`
via `Letflow.Instances.timeline/3`, which is the one and only caller of
`render_description/3`. No additional test was needed for this — it is
already non-vacuous coverage of the exact clause the design doc adds in
§2.6. (No equivalent assertion exists for the "removed" wording variant —
AC2's test checks `payload["file_name"]` on the raw history item but does
not call `timeline/3` for the removal case. This is a minor coverage gap:
the "attached" clause is exercised end-to-end, the "removed" clause is
only exercised at the raw-payload level. Not blocking — `render_description/3`'s
two new clauses are structurally identical (file_name + actor +
attached/removed literal), and the "attached" clause proves the
actor-resolution/payload-extraction machinery both clauses share — but
noted for TEST-DESIGN-VALIDATOR to weigh.)

### 5. `delete/2`'s signature change (§2.5) — all known call sites confirmed updated

Design §2.5 named three call sites needing a 3-arity update. Confirmed by
direct read:

- `lib/letflow/routers/instances.ex:1454` (`handle_delete_attachment/3`) —
  resolves `actor_id(conn)` before calling `Attachments.delete/3`,
  matching the design exactly; also correctly maps a
  `{:error, :missing_scope_or_actor}` from `actor_id/1` to a 500, a case
  the design didn't explicitly spell out but which follows the same
  pattern `handle_upload_attachment/2` already uses.
- `test/letflow/repository/attachments_test.exs:517` (pre-existing test)
  — updated to the new 3-arity form (`Ecto.UUID.generate()` as
  `deleted_by`).
- `Letflow.Repository.EntityAttachments.delete/2` — confirmed untouched
  (separate module/table, out of scope, per design's own note).

No router-level (HTTP) test exists yet for the new `deleted_by` wiring
specifically (`test/letflow/routers/req212_attachments_routes_test.exs`
was not changed on this branch and has pre-existing DELETE coverage that
exercises the route end-to-end without asserting on the resulting history
entry's actor attribution). This is acceptable: AC1/AC2's own acceptance
criteria are stated and tested at the context-module level
(`Letflow.Repository.Attachments` + `Letflow.Instances`), which is where
this requirement's own text points ("a test asserts this over the
existing history/timeline read path" — satisfied via `Instances.history/3`
called directly in a `Letflow.DataCase` test, not necessarily via HTTP).
Re-ran `req212_attachments_routes_test.exs` as part of the full-file
targeted run below and confirmed it still passes unmodified with the new
`delete/3` arity wired in underneath it.
