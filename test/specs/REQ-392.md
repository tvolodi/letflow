## Acceptance criteria and test mapping

### AC1 — remove action calls DELETE and updates the list without a full page reload

> "the attachment widget REQ-387 builds gains a remove action that calls DELETE
> /instances/:id/attachments/:attachment_id and updates the list without a full page
> reload"

**Tests:**
`web/src/components/instances/__tests__/AttachmentPanel.test.tsx` →
`AttachmentPanel > AC1 — remove action`:
- `requires a second confirm click before calling DELETE, then updates the list` — asserts
  a single click only arms the in-row confirm affordance (no DELETE call yet), the second
  (confirm) click calls `attachmentsApi.delete(instanceId, attachmentId)` exactly once, and
  the row disappears from the SAME mounted render tree once the query re-fetches (no
  remount/navigation between the click and the assertion — this is what "without a full
  page reload" means for a mocked-API component test).
- `lets the user cancel the confirm without calling DELETE` — the two-click confirm
  pattern's cancel path must not call DELETE.

Why it would fail if violated: if the confirm button called `deleteAttachment.mutate`
directly on the first click (no confirm step), or if `onSuccess` stopped invalidating the
attachments query key, the first test's `del` call-count and post-delete
`queryByText('delivery-note.pdf')` assertions would fail.

### AC2 — distinct, readable rejection messages naming the specific limit hit

> "attempting to attach a disallowed content type and an over-quota upload each render a
> distinct, readable message naming the specific limit hit, verified by a test for each"

**Tests:** `AttachmentPanel.test.tsx > AC2 — distinct rejection messages`:
- `renders the content-type-not-allowed detail text for a 415` — mocks `upload` rejecting
  with `status: 415` and the real RFC 9457 `detail` text (design §2); asserts
  `data-error-kind="content-type"` and the rendered text names the rejected type and the
  allowlist.
- `renders the storage-quota-exceeded detail text for a 409, distinct from the 415 message`
  — mocks `status: 409` with the real quota `detail` text; asserts
  `data-error-kind="quota"` and that neither rejection's text leaks into the other's.

**Fail-then-pass mutation (frontend, see "Mutation testing" below):** confirmed the 415
test fails genuinely when `classifyUploadError`'s 415 branch is changed to return
`kind: 'quota'`.

Why it would fail if violated: if `classifyUploadError` collapsed both status codes to the
same `kind`/message, or read `error.message` (the RFC 9457 `title`, a bare "Conflict"/
"Unsupported Media Type") instead of `error.details.detail`, both assertions on the
specific limit-naming text would fail.

### AC3 — storage-usage figure changes correctly across an accepted upload and a removal

> "a storage-usage figure is shown near the widget and its rendered value changes
> correctly across an accepted upload and a removal within one test"

**Frontend test:** `AttachmentPanel.test.tsx > AC3 — storage-usage figure > rises after an
accepted upload and falls after a removal` — one test, three assertions in sequence:
initial figure (2.0 KB), after an accepted upload (4.0 KB, mocked `storageUsage` refetch),
after a removal (back to 2.0 KB) — exactly the AC's own "within one test" wording.

**Backend test:** `test/letflow/repository/attachments_test.exs > storage_summary/1 (REQ-392
design §1.1)`:
- `returns {:ok, %{used_bytes, allowance_bytes}} reflecting real uploads and the tenant's
  own allowance` — asserts the figure is `0` before any upload, `1_000` after a 1000-byte
  upload, and `3_500` after a second 2500-byte upload (SUM, not last-write-wins).
- `used_bytes falls after a removal (AC3's own 'and a removal' wording)` — upload then
  `delete/2`, asserts the figure returns to `0`.
- `is per-tenant, not per-instance` — two instances in the same tenant, asserts the figure
  is the SUM across both, not either instance's own subset (the function takes no
  `instance_id` argument at all, per design §1.1).
- `returns {:error, :tenant_not_found} when the tenant row is absent` — same
  unreachable-but-mapped edge `check_storage_quota/3` already guards (ISS-0788 precedent).

**Router test:** `test/letflow/routers/instances_test.exs > GET /instances/storage-usage
(REQ-392 design §1.2)`:
- `returns 200 {used_bytes, allowance_bytes} for the caller's own tenant`.
- `used_bytes reflects a real upload for that tenant, tenant-scoped (not another tenant's
  usage)` — two tenants, one uploads, asserts tenant B's figure stays `0` (INV-1).
- `returns 422 tenant_not_found when the tenant row is absent`.

**Fail-then-pass mutation (backend, see "Mutation testing" below):** confirmed all three
`storage_summary/1` value-assertion tests fail genuinely when the function is mutated to
hardcode `used_bytes: 0`.

Why it would fail if violated: if the frontend hook failed to invalidate the storage-usage
query key on upload/delete `onSuccess`, the figure would stay stuck at its initial value
and the second/third `waitFor` assertions would time out. If the backend summed only the
most-recently-uploaded row instead of `SUM(byte_size)`, the `3_500` assertion would fail.

### AC4 — timeline renders attach/remove entries with actor names

> "the instance history/timeline view renders an attach entry and a remove entry with
> actor names, verified by a test"

**Finding (design §6): no production code change required.**
`Letflow.Instances.render_description/3` already has dedicated
`ATTACHMENT_ATTACHED`/`ATTACHMENT_REMOVED` clauses (REQ-391), and `TimelineFeedItem`
already renders any `TimelineEntry`'s `description`/`actor_display_name` generically. This
requirement's own obligation for AC4 is purely a test, per the AC's "verified by a test"
wording — no coverage of this path existed before this requirement (confirmed: no prior
test file mounted `TimelineFeedItem`/`TimelineFeed` with either attachment event type).

**Test:** `web/src/components/instances/__tests__/TimelineFeedItem.test.tsx`:
- `renders an ATTACHMENT_ATTACHED entry with the file name and actor` — fixture
  `description` matches `render_description/3`'s exact output shape
  (`"<file_name> attached by <actor>"`, design §0/§6), asserts it renders verbatim plus the
  `event_type` and actor name.
- `renders an ATTACHMENT_REMOVED entry with the file name and actor, distinct from the
  attach entry` — same, for the removed wording; asserts the attach wording is absent.
- `renders both entries together in a TimelineFeed, in order, each with actor attribution`
  — integration-level: mounts `TimelineFeed` (not just the item) with both entries, asserts
  DOM order matches array order.

Why it would fail if violated: if `TimelineFeedItem` stopped rendering `entry.description`
(e.g. regressed to render only `event_type`), the exact-text assertions would fail. This
test would also have caught it if the backend's `render_description/3` clauses had never
existed or been removed (it is testing against literal fixture text matching the shipped
backend output shape, not calling the backend function itself — a genuine frontend-layer
regression test for a cross-cutting contract).

### AC5 — approval/decision screen renders the reviewed attachment's file_name

> "the approval/decision screen renders the reviewed attachment's file_name on a recorded
> decision, verified by a test"

**Test:** `web/src/pages/tasks/__tests__/TaskInboxPage.test.tsx`:
- `renders the reviewed attachment file_name for a COMPLETED task, sourced from
  attachments_at_decision` — mocks `tasksApi.get` returning a `COMPLETED` task and
  `instancesApi.events` returning a `TASK_COMPLETED` event whose `payload.task_id` matches
  and whose `payload.attachments_at_decision` names the reviewed file; drives the page
  through a real click on the task row (not a direct component mount, since
  `TaskDetailPanel` is not separately exported); asserts `task-decision-attachments` shows
  the file name and that `instancesApi.events` was called with
  `{ event_type: 'TASK_COMPLETED' }`.
- `renders nothing for a PENDING task (no decision yet, no premature fetch of the
  completion snapshot)` — asserts both that the decision block does not render AND that
  `instancesApi.events` is never called for a non-`COMPLETED` task (the hook's `enabled`
  gate, design §7.1).

Why it would fail if violated: if `TaskDetailPanel` read `attachments_at_decision` from the
wrong event (any `TASK_COMPLETED` event rather than the one matching this `task_id`), or if
the `enabled` gate were removed (fetching for every task regardless of status), either
assertion would fail — the first test's file-name assertion, or the second test's
"events not called" assertion.
