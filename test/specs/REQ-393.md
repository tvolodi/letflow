# REQ-393 Test Spec

## Requirement
Generic, tenant-agnostic entity-list browse screen with filter builder, sort control, and page-size control, wired to `POST /entities/query`.

## Acceptance criteria tested

### AC1: filter builder drives the API
**TC-EFB-01** — EntityFilterBuilder renders empty state: `data-testid="entity-filter-builder"` exists, zero `filter-row` elements, `filter-add` button present and enabled.  
*Why*: proves the component mounts cleanly with an empty rows array, which is the initial state users always see.

**TC-EFB-02** — Add filter button appends one new row: `onChange` is called once, the resulting array has length 1, `field` defaults to the first queried field, `id` is a non-empty string.  
*Why*: proves the add-row path populates all three required fields (id, field, op) correctly — a row missing any of these would cause `buildFilters` to silently discard it.

**TC-EFB-03** — Remove button drops only the targeted row: with two rows, clicking the second row's `filter-remove` button calls `onChange` with a one-element array containing only the kept row's `id`.  
*Why*: proves row identity is preserved across the remove path (row is identified by `id`, not by array index).

**TC-EFB-04** — Field/op/value changes propagate: changing the `filter-value` input and then the `filter-op` select each call `onChange` with the updated row value.  
*Why*: proves the three independent onChange paths in `updateRow` (value, op, field) work without interfering with each other.

### AC2: filter builder + page integration (EntityListBrowserPage)
**TC-ELBP-01** — Definition loading state: when `useQuery` returns `isLoading: true` for the definition query, the outer `QueryStateBoundary` renders a SkeletonLayout with `aria-busy="true"` and `aria-label="Loading content"`.  
*Why*: proves the component correctly delegates definition-fetch loading to the shared loading boundary rather than rendering a broken partial UI.

**TC-ELBP-02** — 422 `field_not_allowed` surfaces as `query-error-banner`: when `recordsQuery.error` has `status: 422`, the `useEffect` sets `queryError` to the API message, and the component renders `data-testid="query-error-banner"` containing the field name; no `page-size-error` is present.  
*Why*: proves the error-classification branch (status !== 400 → `queryError`, not `pageSizeError`) is wired end-to-end through the `useEffect`.

**TC-ELBP-03** — 400 `page_size_too_large` surfaces as `page-size-error`: when `recordsQuery.error` has `status: 400`, the `useEffect` sets `pageSizeError`; `data-testid="page-size-error"` is visible; no `query-error-banner`.  
*Why*: proves the 400-specific branch is wired and the two error display paths are mutually exclusive.

**TC-ELBP-04** — Successful query renders column headers and row data: when both `useQuery` calls return data, `datatable-header-name` and `datatable-header-description` are in the DOM, and `datatable-cell-name` cells contain the seeded row values `'security'` and `'safety'`.  
*Why*: proves the definition fields drive the column shape and the records page items populate the table rows end-to-end.

### AC5: Playwright E2E spec (real spec, 4 scenarios)
`web/tests/e2e/pipelines/entity-list-query.pipeline.e2e.spec.ts` — not runnable without a live stack; written as a complete real spec.

**EO-001/AC1 – filter**: seeds three `tag` records with 'req393-testitem' in the name, applies `name contains 'req393-testitem'` via the filter builder, asserts every returned row's first cell contains the substring.

**EO-002/AC2 – sort-then-page**: queries with `sort: [{field: 'name', dir: 'asc'}]` and `page_size: 1` via the API directly, asserts `firstOnPage2.localeCompare(lastOnPage1) > 0` (the cross-page sort invariant). Also drives the UI Search button to confirm the sort control is wired.

**EO-003/AC4 – non-searchable field rejection**: POSTs `/entities/query` with a field not in the queried allowlist, asserts HTTP 422; then uses Playwright route interception to inject the 422 into the UI's own fetch, asserts `query-error-banner` names the field.

**EO-005/AC3 – over-limit page-size rejection**: POSTs with `page_size: 201` (above `MAX_PAGE_SIZE=200`), asserts HTTP 400; then overrides the page-size select to 999 via `page.evaluate()` and clicks Search, asserts `page-size-error` text matches `/page size is too large/i` and `query-error-banner` has count 0.
