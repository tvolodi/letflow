# REQ-395 Test Spec

## Requirement

Deploy SwiftRoute's sequential high-value shipment-approval ProcessDefinition as a live,
browsable definition on a real tenant on QA.

## Scope note

AC1–AC3 require live QA credentials (blocked by ISS-0739). Those are not automatically
testable in CI. The QA verification procedure for each is documented below.

**Executable coverage:** AC4 is a structural drift-guard test — it verifies that
`test/fixtures/qa/swiftroute_process_definition.json` (the canonical payload sourced by
`scripts/seed_swiftroute_definition.sh`) structurally matches
`test/fixtures/simulation/swiftroute/process_route_approval.yaml`. This guards against
payload drift where one file is updated and the other is not.

## Test cases

### TC-395-01: All YAML node IDs appear in the JSON payload

**Criterion:** AC4 (drift guard)

**Why it exists:** The seed script uses the JSON fixture as the deployment payload; the
simulation harness uses the YAML fixture as its process model. If a node is added to the
YAML in a future commit but the JSON is not updated, the live definition will diverge from
the simulation fixture, causing simulation scenarios to exercise a graph that does not
match what's actually deployed on QA.

**Assertion:** Every `id` under `graph.nodes` in the YAML appears in `graph.nodes` in the
JSON.

### TC-395-02: All YAML edge IDs appear in the JSON payload

**Criterion:** AC4 (drift guard)

**Why it exists:** Same reasoning as TC-395-01 for edges — an edge rename or addition in
the YAML would silently break the deployed graph if the JSON is not kept in sync.

**Assertion:** Every `id` under `graph.edges` in the YAML appears in `graph.edges` in the
JSON.

### TC-395-03: ops-review HUMAN_TASK escalation attributes present in JSON

**Criterion:** AC4 (escalation attributes)

**Why it exists:** The escalation timer (`PT2H`) and escalation role (`role-ceo`) on
`ops-review` are the mechanism for AC3's "no ceo-approval path". If these keys are dropped
from the JSON payload during a future edit, the escalation behaviour on QA silently breaks
without any CI signal. The YAML is the design source of truth; this test checks the JSON
matches it on those specific keys.

**Assertions:**
- `ops-review` node in JSON has `attributes.escalation_timer_duration == "PT2H"`
- `ops-review` node in JSON has `attributes.escalation_role == "role-ceo"`

### TC-395-04: CEL condition `declared_value > 500` on ceo-approval-gate in JSON

**Criterion:** AC2/AC3 design parity (declared_value threshold)

**Why it exists:** The entire branching logic for AC2/AC3 depends on this condition being
exactly `variables.declared_value > 500`. If a future edit changes the operator or
threshold in one file but not the other, the QA definition will not match the simulation
fixture and the divergence will be invisible in CI.

**Assertion:** Edge `e3` in the JSON has `condition` containing `"declared_value > 500"`.

### TC-395-05: fallback-ops-review edge targets ceo-approval in JSON

**Criterion:** AC4 (escalation path consistency)

**Why it exists:** The fallback edge is the timer-fired escalation path. If its target
changes in the YAML but not the JSON (or vice versa), the escalation on QA routes to the
wrong node. This assertion locks the target to `ceo-approval`.

**Assertion:** Edge `fallback-ops-review` in the JSON has `target == "ceo-approval"`.

## QA verification procedure (AC1–AC3, not auto-executable in CI)

### AC1 — Definition exists and is ACTIVE on QA

```bash
export QA_AUTH_TOKEN="<bearer-token>"
bash scripts/seed_swiftroute_definition.sh
curl -sf -H "Authorization: Bearer $QA_AUTH_TOKEN" \
  "https://qa.bizdala.com/api/v1/definitions?name=Shipment+Approval&status=active" | jq .
# PASS: .items[0].status == "ACTIVE"
```

### AC2 — Instance with declared_value: 750 routes through ops-review then ceo-approval

```bash
DEFINITION_ID="<id from AC1>"
curl -sf -X POST -H "Authorization: Bearer $QA_AUTH_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"process_definition_id":"'"$DEFINITION_ID"'","variables":{"declared_value":750,"shipment_id":"S-001"}}' \
  "https://qa.bizdala.com/api/v1/instances" | jq .id
# Note INSTANCE_ID, then:
curl -sf -H "Authorization: Bearer $QA_AUTH_TOKEN" \
  "https://qa.bizdala.com/api/v1/instances/$INSTANCE_ID/tasks?status=pending" | jq .[0].node_id
# PASS: == "ops-review"
# Then complete ops-review with ops_decision=approve and repeat tasks query:
# PASS: == "ceo-approval"
```

### AC3 — Instance with declared_value: 400 does not route to ceo-approval

Same as AC2 but `declared_value: 400`. After completing ops-review with `ops_decision: approve`,
the next pending task should be `release-shipment` (or transition to `end-approved`), not
`ceo-approval`.
