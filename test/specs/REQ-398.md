# REQ-398 — Frontend promotion-review list/queue page + nav entry

## Requirement text (acceptance criteria, `docs/requirements.yaml`)

1. `web/src/api/promotions.ts` gains a typed list client and
   `web/src/hooks/usePromotions.ts` gains a corresponding hook, matching
   this codebase's existing API-client/hook conventions
2. a new routed list page renders the rows returned by REQ-397's endpoint,
   including status, def_type/def_id, requested_by, and a timestamp, proven
   by a test using a mocked/stubbed API response with at least two distinct
   rows
3. the page offers a status filter control that re-queries with the
   selected status, proven by a test asserting the query param/request
   changes when the filter changes
4. each rendered row links to the existing
   `definitions/:id/promotions/:reviewId` detail route with the correct
   ids, proven by a test
5. a non-PLATFORM_ADMIN session is redirected away from the list route the
   same way `PromotionReviewPage.tsx` already redirects (per ISS-0730
   design §3.1), proven by a test
6. an empty result set renders a distinct plain "no reviews" state, not
   the fetch-failure state, proven by a test
7. one new nav entry in `AppShell.tsx`'s `NAV_ITEMS` reaches the new route,
   and the design doc states this supersedes ISS-0730 design §1's
   no-nav-entry decision and why
8. a design-doc or code comment cross-reference notes that ISS-0734's
   `fix_direction` piece 2 (durable recording of submit-time conflict
   refusals) remains open and out of this requirement's scope

Design: `lib/letflow/design/req398-promotion-review-list-page.md`.
Implementation: commit `17a5292c`.

## Acceptance criteria → test-case map

All tests live in
`web/src/pages/promotions/__tests__/PromotionReviewListPage.test.tsx`.
Follows `TenantsPage.pagination.test.tsx`'s established convention of
mocking `@tanstack/react-query`'s `useQuery` directly and inspecting the
real `queryKey` a render produces (rather than mocking the `usePromotions`
hooks module), so the AC3 filter-requery test asserts on what a real
re-render actually sends, not a hand-authored stand-in. Also follows
`DefinitionListPage.test.tsx`'s `@/auth/AuthContext` mock shape and
`AppShell.candidate-nav.test.tsx`'s render-and-assert-nav-link pattern.

### AC1 — typed client + hook

Not independently test-bearing (a type declaration has no runtime
behavior to assert against). Exercised end-to-end by every test below:
each one goes through the real `usePromotionReviewList` call, the real
`queryKeys.promotions.list` key shape, and the real
`PromotionReviewListFilters`/`PromotionReviewListItem` types — a
signature mismatch here would fail `npm run type-check`, which is run and
quoted in "Verification run" below.

### AC2 — renders rows from a mocked API response

`describe('REQ-398 AC2 — renders rows from the list endpoint')`: mocks
`useQuery` to return two distinct `PromotionReviewListItem` rows
(`pending_review`/`def-a`/`alice` and `approved`/`def-b`/`bob`), asserts
status, `def_type`, `def_id`, `requested_by`, both appear in the rendered
table (scoped with `within(table)` since the status filter `<select>`'s
own `<option>` text overlaps the same status strings).

### AC3 — status filter re-queries with the selected status

`describe('REQ-398 AC3 — status filter re-queries')`: records the
`status` field read off the END of every `useQuery` call's `queryKey`
array (the real shape `queryKeys.promotions.list(tenantId, filters)`
produces) across re-renders. Asserts the initial render sends
`status: undefined`, then fires a real `change` event on the status
`<select>` and asserts the next `useQuery` call's `queryKey` carries
`status: 'approved'` — a genuine request-level assertion, not merely
"the select's displayed value changed."

**Load-bearing — verified fail-then-pass this turn** (see "Mutation
checks" below): a no-op filter (selected status never reaching the
query) fails this test.

### AC4 — each row links to the detail route with correct ids

`describe('REQ-398 AC4 — row links to definitions/:id/promotions/:reviewId')`:
asserts `linkA` and `linkB`'s `href` attributes are exactly
`/definitions/def-a/promotions/rev-a` and
`/definitions/def-b/promotions/rev-b` — each row's OWN `def_id`/`id`, not
a shared/first-row value, so a bug that hardcoded one row's ids onto every
link would fail this.

### AC5 — non-PLATFORM_ADMIN is redirected

`describe('REQ-398 AC5 — non-PLATFORM_ADMIN redirect')`: a
`PROCESS_OPERATOR`-only session renders the page inside a `MemoryRouter`
with no route registered for the redirect target — the page's own content
(`"Promotion Reviews"` heading, the table) must never appear, which is
only true if the `<Navigate>` guard actually fires before the data render.
A companion positive-path test confirms a `PLATFORM_ADMIN` session is NOT
redirected (page content renders normally) — without this companion, a
mutant that redirected UNCONDITIONALLY would still pass the negative test.

**Load-bearing — verified fail-then-pass this turn** (see "Mutation
checks" below): disabling the redirect guard fails this test.

### AC6 — empty result set renders a distinct "no reviews" state

`describe('REQ-398 AC6 — empty vs fetch-failure state')`: two tests.

1. `useQuery` returns `{data: {items: [], ...}, isError: false}` —
   asserts the literal `"No promotion reviews found."` text renders AND
   the (empty) `<table>` element itself is present (the success branch,
   not the loading-skeleton branch, which could vacuously look
   "row-less" too) AND no `/retry/i` text (the `FetchError` surface's own
   copy) appears.
2. `useQuery` returns `{data: undefined, isError: true, error: {status: 500}}` —
   asserts the "No promotion reviews found." text does NOT appear and the
   table does NOT render, proving the two states are genuinely distinct
   render outputs, not the same "no rows" case reached two ways.

### AC7 — nav entry reaches the route

`describe('REQ-398 AC7 — nav entry reaches /promotions')`: renders the
REAL `AppShell` component (not a stand-in), mocking only its data
dependencies (`useAuth`, `useQuery` for the DLQ-count badge,
`@/theming/BrandingContext`). Asserts a `PLATFORM_ADMIN` session sees a
`"Promotion Reviews"` link with `href="/promotions"`, and a
`PROCESS_OPERATOR`-only session does not see that nav entry at all — this
is the render-and-assert-link pattern
`AppShell.candidate-nav.test.tsx` already established for a prior
role-gated nav addition (ISS-0728), reused here rather than a bare
`NAV_ITEMS` array introspection, since the real component + real
`react-router-dom` `NavLink` is what actually reaches the route, not just
an array literal. The route registration itself
(`web/src/router.tsx`'s new `promotions` entry) is confirmed by direct
read of `git show 17a5292c` — a routing-table entry has no independent
runtime behavior beyond "does clicking the link land on a route that
renders `PromotionReviewListPage`," which AC2–AC6 already exercise the
page side of.

### AC8 — ISS-0734 piece 2 cross-reference

Documentation-only. Satisfied by
`lib/letflow/design/req398-promotion-review-list-page.md` §8 and
`PromotionReviewListPage.tsx`'s own header comment ("OPEN SCOPE NOTE
(REQ-398 AC8)"), both confirmed present by direct read. No executable
behavior to assert — correctly treated as non-test-bearing, not skipped
coverage.
