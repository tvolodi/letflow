# REQ-399 — Case-detail dependency-version/provenance screen

## Requirement text (acceptance criteria, `docs/requirements.yaml`)

1. the new `GET /api/v1/instances/{id}/pins` route returns, for a real
   instance, each dependency's `ref`, `resolved_id`, `version` and
   `source`, tenant-scoped per this codebase's existing prefix convention,
   proven by an integration test
2. the route is a pure read of
   `Letflow.Engine.PinResolver.reconstruct_effective_pins/2`'s
   already-computed effective pin set (zero additional catalog/module
   reads), proven by the test asserting no new `Repo` query against
   `service_catalog` or `module` tables is introduced for this path
3. SECURITY-REVIEWER sign-off is required and obtained before merge
4. the case-detail screen renders every one of `PinResolver`'s four
   source values (`:resolved`, `:override`, `:inherited`, `:rebound`)
   with a distinct human-readable label, proven by a test supplying a
   mocked/stubbed response containing all four
5. a case with zero recorded pins renders a distinct plain "no
   dependencies" state, not the fetch-failure state, proven by a test
6. a fetch failure from the new route renders this codebase's existing
   `QueryStateBoundary`/`classifyError` failure state, proven by a test
7. `git diff` confirms `Letflow.Engine.PinResolver`'s resolution logic
   is unmodified by this requirement
8. `mix letflow.check` passes and the frontend test suite passes, with
   real output quoted for both

Design: `lib/letflow/design/req399-instance-pin-provenance.md`.
Implementation: backend route pre-existing (REQ-080); AC2 telemetry test
commit `feca389b`; frontend panel commit `171cf1e8`.

## Acceptance criteria → test-case map

All tests live in
`web/src/components/instances/__tests__/InstancePinsPanel.test.tsx`.
Follows `AttachmentPanel.test.tsx`'s established convention (the design
doc's own closer precedent, §4.1/§7) of mocking `@/api/instances`
directly and `@/auth/AuthContext`, letting the real `useInstancePins`
hook and the real `useQuery`/`QueryStateBoundary`/`classifyError` wiring
run unmocked — so these tests exercise the actual
loading→success/empty→fetch-failure state machine the component drives
at runtime, not a hand-stubbed `rendererState`.

### AC4 — all four source values, each with a distinct label, matched to its own row

`describe('REQ-399 AC4 — renders all four PinResolver source values with
distinct labels')`: mocks `instancesApi.getPins` to resolve with four
pins, one per `EffectivePinSource` value (`resolved`/`svc-billing`,
`override`/`svc-shipping`, `inherited`/`svc-tax`,
`rebound`/`svc-fraud`), each with a distinct `ref`. Reads all `role="row"`
elements, drops the header row, and for each expected `ref` finds **that
row specifically** (`within(row).queryByText(ref)`) and asserts **that
row's own** source-label cell (`within(row).getByText(expectedLabel)`) —
not merely that all four label strings appear somewhere in the document,
which would pass vacuously even if labels were rendered against the
wrong rows. A closing assertion (`new Set(labels).size === labels.length`)
confirms the four expected labels are themselves pairwise distinct, so a
mutant collapsing two source values onto the same label text is also
caught by the row-matching assertions above (see "Mutation checks").

### AC5 — zero recorded pins renders a distinct "no dependencies" state

`describe('REQ-399 AC5 — zero recorded pins renders a distinct "no
dependencies" state')`: three tests, establishing genuine three-way
distinctness (not just "empty vs. one other state"):

1. `getPins` resolves `{instance_id, pins: []}` — asserts the literal
   `"No dependencies recorded for this case."` text renders, AND the
   `data-testid="data-table"` element is absent (the zero-pins branch
   renders a plain `<p>`, not an empty `DataTable`), AND no `"Retry"`
   button is present (ruling out the fetch-failure branch by absence of
   its distinguishing affordance, not just by absence of the empty
   copy).
2. `getPins` returns a promise that never resolves — asserts the
   loading skeleton (`getByLabelText('Loading content')`,
   `SkeletonLayout`'s own `aria-label`) is present and the empty-message
   text is **not** — proves the empty state is not merely "whatever
   renders before data arrives."
3. `getPins` rejects — asserts `role="alert"` (the `FetchError`
   surface) renders and the empty-message text is **not** present —
   proves the empty state and the fetch-failure state are structurally
   different render outputs, not the same "no rows" case reached two
   ways.

### AC6 — fetch failure renders the existing QueryStateBoundary/FetchError state

`describe('REQ-399 AC6 — fetch failure renders the existing failure
state')`: `getPins` rejects; asserts the real `FetchError` component's
own copy (`"Something went wrong loading this content."`) and its
`"Retry"` button render (not just "a `role=alert` div exists" — the
actual component contract), and that neither the table nor the empty
"no dependencies" message are present alongside it.
