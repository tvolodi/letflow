# Test Spec: REQ-400 — `Letflow.Modules.Module` behaviour, `Letflow.Modules.Catalog`, manifest validation, test-only fixture

**Requirement:** REQ-400 (`docs/requirements.yaml`, `id: REQ-400`, stage S11,
owner ELIXIR-DEV). **Design:** `lib/letflow/design/req400-module-behaviour-catalog.md`.
**Implementation commits:** `e34911fe`+`20d23669` (design), `e5edc4cf`
(implementation), `585ca45e` (AC4 moduledoc-wording fix).

**Test tier:** unit (pure, no database, no HTTP — `Catalog` reads only compile-time
`Application.compile_env/3` data and calls plain functions; `async: true` is safe for
both new test files).

## Acceptance criteria (verbatim, `docs/requirements.yaml`)

1. **AC1** — "`lib/letflow/modules/module.ex` defines `Letflow.Modules.Module` with
   `@callback manifest/0`, `@callback router/0` and `@callback on_install/2`, and
   `router/0` and `on_install/2` are listed in `@optional_callbacks`, verified by a
   test calling `Letflow.Modules.Module.behaviour_info(:callbacks)` and
   `behaviour_info(:optional_callbacks)`"
2. **AC2** — "`Letflow.Modules.Catalog` returns `[Letflow.Modules.Fixture]` as its
   module list in the test env ... and looks the fixture up by its id string, proven
   by an ExUnit test; `git grep -n \"config :letflow, :modules\" config/config.exs`
   shows the list is `[]`"
3. **AC3** — "a manifest-validation test fails with a named error for each of six
   deliberately bad inline manifests: a `role_grants` key not in
   `Authorization.roles/0`, a granted atom not in the module's own `permissions`, a
   `permissions` atom that is a core permission, a `depends_on` id not registered, a
   duplicate module id, and a `route_policies` entry whose permission atom is not in
   the module's own `permissions`; and the same validation returns `:ok` for every
   module the Catalog lists"
4. **AC4** — "`git grep -n \"GenServer\\|Agent.start\\|Supervisor\" --
   lib/letflow/modules/` returns no hits (the Catalog is a plain module, not a
   process)"
5. **AC5** — "`mix letflow.check` passes, real output quoted"

## Test cases → acceptance-criteria map

### AC1 — behaviour_info, `test/letflow/modules/module_test.exs`

1. `test "behaviour_info(:callbacks) includes manifest/0, router/0, on_install/2"` —
   asserts `Letflow.Modules.Module.behaviour_info(:callbacks)` contains
   `{:manifest, 0}`, `{:router, 0}`, `{:on_install, 2}`.
2. `test "behaviour_info(:optional_callbacks) includes router/0 and on_install/2 but not manifest/0"`
   — asserts `behaviour_info(:optional_callbacks)` contains `{:router, 0}` and
   `{:on_install, 2}` but does **not** contain `{:manifest, 0}` — this is the part of
   AC1 that actually proves `manifest/0` is required (a callback present in
   `:callbacks` but absent from `:optional_callbacks` is, by Elixir's own
   `@callback`/`@optional_callbacks` semantics, mandatory). Exists because AC1's own
   wording explicitly calls out that the optional set must exclude `manifest/0` — a
   test only checking the optional set's *presence* half would pass even if
   `manifest/0` were wrongly marked optional too.

### AC2 — Catalog list/lookup, `test/letflow/modules/catalog_test.exs`

3. `test "entry_modules/0 returns [Letflow.Modules.Fixture] in the test env"` —
   asserts `Catalog.entry_modules() == [Letflow.Modules.Fixture]`. Exists to prove the
   `config/test.exs` registration is actually wired through `compile_env`, not just
   present in the config file text.
4. `test "fetch/1 looks the fixture up by its id string"` — asserts
   `Catalog.fetch("fixture") == {:ok, Letflow.Modules.Fixture}`.
5. `test "fetch/1 returns {:error, :not_found} for an unregistered id"` — the negative
   half of case 4; exists because a lookup function that always returns `{:ok, _}`
   (e.g. one that ignores the id argument) would otherwise pass case 4 vacuously.
6. `test "config/config.exs registers an empty module list"` — reads
   `config/config.exs` from disk and asserts it contains the literal line
   `config :letflow, :modules, []` (the AC's own wording treats this as a grep-style
   check; encoding it as a real assertion, not a comment, means a future edit that
   silently changes the list is caught by `mix test`, not only by remembering to
   re-run a shell command by hand).

### AC3 — manifest validation, `test/letflow/modules/catalog_test.exs`

Six `test` cases, one inline deliberately-bad manifest each, built from a valid
baseline manifest (mirroring the fixture's own shape) with exactly one field mutated
to break exactly one rule — each asserts `Catalog.validate/1` (or `/2` where the rule
is set-relative) returns the specific named error tuple from `catalog.ex`'s own
`@doc`, not merely `{:error, _}`:

7. `test "validate/1 rejects a role_grants key not in Authorization.roles/0"` —
   `role_grants: %{NOT_A_ROLE: [:FixtureRead]}` → `{:error, {:unknown_role, :NOT_A_ROLE}}`.
8. `test "validate/1 rejects a role_grants value not in the module's own permissions"`
   — `role_grants: %{TASK_WORKER: [:NotDeclared]}` →
   `{:error, {:ungranted_permission_declared, :NotDeclared}}`.
9. `test "validate/1 rejects a permissions atom that collides with a core permission"`
   — `permissions: [:InstancesRead]` (a real `Authorization.permissions/0` atom) →
   `{:error, {:core_permission_collision, :InstancesRead}}`.
10. `test "validate/1 rejects a depends_on id that is not registered"` —
    `depends_on: ["nonexistent"]` → `{:error, {:unknown_dependency, "nonexistent"}}`.
11. `test "validate/1 rejects a duplicate module id"` — calls
    `Catalog.validate(manifest_a, [manifest_b])` where `manifest_a.id ==
    manifest_b.id` (two distinct inline manifests sharing one id, per design §9 item
    4's "TEST-DESIGNER's call") → `{:error, {:duplicate_module_id, id}}`.
12. `test "validate/1 rejects a route_policies entry whose permission is undeclared"`
    — `route_policies: [{"GET", "/x", :NotDeclared}]` →
    `{:error, {:undeclared_route_permission, :NotDeclared}}`.
13. `test "validate/1 returns :ok for every module the real Catalog lists"` — iterates
    `Catalog.all_manifests()` (the fixture, in the test env) and asserts
    `Catalog.validate(manifest) == :ok` for each — proves the fixture manifest itself
    is well-formed against all six rules, not just that the six rules can detect
    badness in isolation.

### AC4 — satisfied by inspection, not a new runtime test

`git grep -n "GenServer\|Agent.start\|Supervisor" -- lib/letflow/modules/` — already
independently re-run below and confirmed zero hits (also previously verified by
REVIEWER). Not encoded as an ExUnit test: AC4's own wording is explicitly a static
grep check over source text, not a runtime behavior — writing an ExUnit test that
shells out to `git grep` would just be a slower, more fragile re-implementation of the
same check `mix letflow.check` (or a human/agent) can run directly, and the design
doc (§2.4, §8) treats it the same way.
