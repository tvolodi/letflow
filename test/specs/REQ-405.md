## Acceptance criteria (verbatim, `docs/requirements.yaml`)

1. **AC1** — `classify_edge/2` correctly classifies all six rule categories (scope
   gate, Rules 0–5) and returns `{:violation, reason}` with descriptive reason strings
   for Rules 4 and 5; a unit test suite exercises every branch; `mix test
   test/mix/tasks/letflow.check_boundaries_test.exs` exits 0.
2. **AC2** — `mix letflow.check_boundaries` exits 0 on the current codebase
   (no violations), printing an OK summary with the edge count.
3. **AC3** — `parse_xref_output/1` correctly handles the four xref plain-format
   variants (backtick prefix, pipe prefix, space-indented, annotation-stripped) and
   edge cases (blank input, orphaned targets, multiple sources).
4. **AC4** — `"letflow.check_boundaries"` is wired into the `letflow.check` alias,
   positioned after `"compile --warnings-as-errors"` and before `"letflow.check.test"`.

## Test cases → acceptance-criteria map

### AC1 — `classify_edge/2` unit tests (`describe "classify_edge/2"`)

1. `VIOLATION: core file outside modules imports module-subdir file` — edge
   `{"lib/letflow/routers/x.ex", "lib/letflow/modules/m/y.ex"}` → `{:violation, _}`.
   Exercises Rule 5. Exists because this is the primary boundary-violation case:
   application code outside any module subdir must never reference a module-subdir
   file (except `catalog.ex`). Without this test, Rule 5 could silently decay to `:ok`.

2. `OK: catalog.ex is the sanctioned importer` — edge
   `{"lib/letflow/modules/catalog.ex", "lib/letflow/modules/m/m.ex"}` → `:ok`.
   Exercises Rule 1. Exists because `catalog.ex` is the one explicitly permitted
   exception to Rule 5; a test verifies the exception fires before Rule 5 does.

3. `OK: core mechanism file references another core mechanism file` — edge
   `{"lib/letflow/modules/installs.ex", "lib/letflow/modules/catalog.ex"}` → `:ok`.
   Exercises Rule 0 (target not in a module subdir). Exists to confirm the one-level
   file (`catalog.ex`) is correctly excluded by `path_in_module_subdir?/1`.

4. `VIOLATION: cross-module ref when target not in depends_on` — edge
   `{"lib/letflow/modules/a/x.ex", "lib/letflow/modules/b/y.ex"}` with
   `%{"a" => []}` → `{:violation, _}`. Exercises Rule 4. Exists because
   unauthorized cross-module references are the second major violation class; both
   Rule 4 and Rule 5 must have explicit tests.

5. `OK: cross-module ref when target is in depends_on` — same edge with
   `%{"a" => ["b"]}` → `:ok`. Exercises Rule 3. Exists as the positive complement of
   case 4: a `depends_on`-declared cross-module reference must be permitted.

6. `OK: test/support source is excluded from scope` — edge
   `{"test/support/z.ex", "lib/letflow/modules/m/y.ex"}` → `:ok`. Exercises the
   `test/support/` scope gate. Exists because fixture helpers in `test/support/`
   commonly import module files; gating them out prevents false positives on the
   test suite itself.

7. `OK: intra-module reference (same module subdir)` — edge
   `{"lib/letflow/modules/a/x.ex", "lib/letflow/modules/a/y.ex"}` → `:ok`.
   Exercises Rule 2. Exists because intra-module references must always be allowed;
   otherwise every module's own internal file graph would be flagged.

8. `OK: source outside lib/ is out of scope` — edge
   `{"_build/dev/lib/letflow/ebin/foo.beam", "lib/letflow/modules/m/y.ex"}` → `:ok`.
   Exercises the `not String.starts_with?(source, "lib/")` scope gate. Exists
   because xref output can include compiled beam paths; they must be silently skipped.

9. `violation reason names both module ids (Rule 4)` — asserts the violation reason
   string contains `"alpha"`, `"beta"`, and `"depends_on"`. Exists because a reason
   string omitting the module ids is not actionable for a developer trying to trace
   which dependency was missing.

10. `violation reason names source and target (Rule 5)` — asserts the violation reason
    string contains the literal source path, literal target path, and `"catalog.ex"`.
    Exists because the reason must name the offending files and remind the developer
    that `catalog.ex` is the only permitted importer — omitting either makes the
    message harder to act on.

### AC2 — system invocation (`describe "system invocation (AC2)"`)

11. `exits 0 on the current branch tree (AC2)` — invokes `mix letflow.check_boundaries`

### AC3 — `parse_xref_output/1` unit tests (`describe "parse_xref_output/1"`)

12. `blank input returns empty list` — two sub-assertions (`""` and `"   \n   \n"`).
13. `non-indented source with one target (backtick prefix)` — `` "`-- " `` prefix.
14. `non-indented source with one target (pipe prefix)` — `"|-- "` prefix.
15. `also handles plain-indented targets (space prefix) for compatibility` — space-only

16. `strips compile annotation from target paths` — `" (compile)"` suffix removed.
17. `strips runtime annotation from target paths` — `" (runtime)"` suffix removed.

### AC4 — alias wiring (`describe "the letflow.check alias wiring (AC4)"`)

## Known gap (REVIEWER ISS-0831)

`run/1` in `lib/mix/tasks/letflow.check_boundaries.ex` discards `_exit_code` from
`System.cmd/3`:

```elixir
{output, _exit_code} =
  System.cmd("mix", ["xref", "graph", "--format", "plain"], stderr_to_stdout: false)
```

If `mix xref` exits non-zero (e.g. a compile error in the project under analysis), the
tool silently continues, parses whatever partial or empty output it received, and
reports "0 violations OK" — a **false negative**. This is a non-blocking finding noted
by REVIEWER; it does not affect the current test suite (the test-env xref run
succeeds), but it means the task's exit-0 guarantee is conditioned on `mix xref`
itself not failing. A future fix would check `_exit_code` and call `Mix.raise/1` if
non-zero.
