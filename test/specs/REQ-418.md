## Acceptance criteria (verbatim shape, `docs/requirements.yaml`) → covering tests

### AC1 — static shape of the `letflow-mobile` client

> a new ExUnit test ... asserts the letflow-mobile client has publicClient true,
> standardFlowEnabled true, directAccessGrantsEnabled false, implicitFlowEnabled
> false, attributes['pkce.code.challenge.method'] == 'S256', redirectUris ==
> ['com.bizdala.letflow:/oauth2redirect'] exactly, webOrigins == [], a roles mapper,
> and an oidc-audience-mapper with included.client.audience 'letflow-web' and
> access.token.claim 'true'

**Covered by:** `test/letflow/api/keycloak_realm_mobile_client_test.exs`
(`Letflow.Api.KeycloakRealmMobileClientTest`), describe block `"letflow-mobile
client's shape (design §1.1)"`:
- `"publicClient is true"`
- `"standardFlowEnabled is true (Authorization Code flow, required for PKCE)"`
- `"directAccessGrantsEnabled is false -- password grant has no place on a device"`
- `"implicitFlowEnabled is false"`
- `"serviceAccountsEnabled is false -- no server-to-server use case for a mobile app"`
- `"attributes[\"pkce.code.challenge.method\"] is S256 -- server-side PKCE enforcement"`
- `"attributes[\"post.logout.redirect.uris\"] matches the app's custom-scheme redirect"`
- `"redirectUris is exactly [\"com.bizdala.letflow:/oauth2redirect\"] -- no wildcard, no http(s) entry"`
- `"webOrigins is exactly [] -- a native app makes no browser-origin CORS request"`
- `"carries a realm-roles mapper (same as letflow-web)"`
- `"carries a MANDATORY oidc-audience-mapper naming letflow-web (ISS-0275 recurrence guard)"`

Exists because these are static, file-level facts about the tracked realm JSON — a
purely mechanical `Jason.decode!/1` + field-equality check is sufficient and needs no
running Keycloak, so paying the live-container cost for this criterion would be pure
overhead.

### AC2 — no-wildcard guard + `letflow-web` byte-identical

> the same test asserts no element of letflow-mobile's redirectUris or webOrigins
> contains '*' or starts with 'http', and asserts the letflow-web client's JSON object
> equals an inline expected map ...

**Covered by:** same file, tests:
- `"no wildcard/http(s) entry hides in redirectUris or webOrigins"`
- describe block `"letflow-web client is byte-for-byte unchanged (design §1.3)"` →
  `"letflow-web's full client object equals an inline literal, exact equality"`

Exists as the regression guard this requirement is fundamentally about (letflow-web's
own `["*"]` redirect list is exactly the defect being avoided for the new client) and
as the proof that adding `letflow-mobile` touched nothing on `letflow-web`.

### AC3 — live authorization-endpoint checks (three sub-checks)

> live check against a freshly recreated dev Keycloak ...: an authorization request ...
> returns the login page (HTTP 200); the same request with redirect_uri=
> https://evil.example/cb returns a non-200 error response whose body names
> redirect_uri and does NOT redirect to evil.example; the same request with no
> code_challenge does not return the login page and instead yields an error naming
> code_challenge or code_challenge_method ...

**Covered by:** `test/letflow/integration/keycloak_mobile_client_auth_test.exs`
(`Letflow.Integration.KeycloakMobileClientAuthTest`), tagged `:keycloak`:
- describe `"AC3a — valid PKCE authorization request returns the login page"` →
  `"client_id=letflow-mobile, registered redirect_uri, response_type=code, S256 code_challenge -> HTTP 200"`
- describe `"AC3b — mismatched redirect_uri is rejected and never redirected to"` →
  `"redirect_uri=https://evil.example/cb -> non-200 error naming redirect_uri, no redirect to evil.example"`
- describe `"AC3c — missing code_challenge is rejected (server-side PKCE enforcement)"` →
  `"no code_challenge/code_challenge_method -> not the login page; error names code_challenge(_method), either in body or as error=invalid_request in a Location redirect to the registered redirect_uri"`

Exists because this is behavior only a real Keycloak, with the realm actually
imported, can prove: the static AC1 test proves the JSON *declares*
`pkce.code.challenge.method: "S256"` and a single non-wildcard `redirectUris` entry;
only a live authorization-endpoint round trip proves Keycloak actually *enforces*
those declarations at request time. AC3b/AC3c specifically exist to catch the two
ways this enforcement could silently regress: a Keycloak/realm-config change that
widens accepted redirect URIs (AC3b), or one that drops server-side PKCE enforcement
back to a client-side-only convention (AC3c) — either regression would be invisible
to the static test since the JSON attribute would still read `"S256"`/the single URI
even if Keycloak stopped honoring it.

### AC4 — live admin evaluate-scopes check

> live check: Keycloak's admin endpoint GET /admin/realms/bpm-default/clients/
> <letflow-mobile id>/evaluate-scopes/generate-example-access-token?userId=
> <admin-user id> returns claims whose aud contains 'letflow-web' and whose azp is
> 'letflow-mobile' ...

**Covered by:** same file, describe `"AC4 — evaluate-scopes example access token has
the right aud/azp shape"` → `"aud contains letflow-web, azp is letflow-mobile"`.

Exists because this is the direct, live proof that the `letflow-mobile-audience`
protocol mapper (AC1's static test proves it's *declared* in the JSON) actually
*produces* the correct `aud` claim once Keycloak evaluates it — this is precisely the
ISS-0275 defect class (design §1.4): a present-but-misconfigured or
silently-dropped-at-import-time mapper would still pass every static JSON assertion
while producing tokens that 401 on every authenticated mobile API call. `azp` is
asserted too because the design (§1.4, closing paragraph) is explicit that
`Oidcc.Token.validate_jwt/3` never checks `azp` — this assertion documents that the
mobile client's tokens carry the expected `azp` anyway (Keycloak's own default
behavior), without implying Letflow's own verifier depends on it.

## Live-check design notes (AC3/AC4 test file)

- **Why `:httpc`, not a new dependency:** `test/support/keycloak_test_client.ex`
  (design `req134-real-keycloak-token-integration.md` §3.2) already settled on
  Erlang/OTP's built-in `:httpc` for exactly this class of excluded-by-default live
  test. `KeycloakTestClient.ensure_started/0`, `.discovery_reachable?/1`, and
  `.direct_access_token/4` are reused directly — the last of these is realm/client-id
  agnostic by signature, so it is reused unmodified for AC4's master-realm `admin-cli`
  admin-token acquisition (`admin`/`admin`, matching `docker-compose.yml`'s
  `KEYCLOAK_ADMIN`/`KEYCLOAK_ADMIN_PASSWORD`).
- **Why `autoredirect: false`:** AC3b and AC3c both need to observe Keycloak's *own*
  response (status, headers, body) at the authorization endpoint directly. Letting
  `:httpc` silently follow a redirect would hide the exact signal each check is
  reading (a `Location` header pointing away from — or, in AC3c's allowed second
  shape, back to — the registered redirect_uri).
- **AC3c's two allowed response shapes:** the acceptance criterion text itself names
  two possible ways Keycloak can reject a missing-PKCE request (an error rendered
  directly in the response body, or a redirect back to the registered `redirect_uri`
  carrying `error=invalid_request`); the test's `cond do` branches on which shape the
  live response actually took and asserts the correct thing for that shape, rather
  than assuming one specific Keycloak version's behavior.
- **PKCE challenge fixture:** a freshly generated random S256 challenge
  (`:crypto.strong_rand_bytes/1` → `:crypto.hash(:sha256, ...)` → base64url) is used
  for every AC3 request that needs one. Keycloak's authorization endpoint only checks
  a challenge's *presence and declared method* at this step (the verifier itself is
  checked later, at token exchange, which none of these tests reach) — no PKCE
  interception is needed for AC3a/AC3b, and AC3c is precisely the "no challenge at
  all" case.
