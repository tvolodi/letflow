### AC4 — each guard's self-test demonstrates it FAILS on a violating fixture

**Verified by:**

- `apps/mobile/test/guards/module_boundary_guard_test.dart::self-test: checker fires on a violating fixture (Rule 2)` —
  fixture: `features/a/thing.dart` importing `../b/other.dart` with
  `a.depends_on == []`. Asserts `violations` is non-empty, `rule == 2`, and
  the importing file path matches. Exists to prove the boundary checker
  (§6a of the design) isn't a no-op that would pass vacuously against an
  empty/near-empty `lib/features/` tree at this early stage — running only
  the "real tree, zero violations" test would never demonstrate the checker
  can detect anything, since the real tree currently has no violations to
  find.
- `apps/mobile/test/guards/forbidden_dependencies_guard_test.dart::self-test: checker fires on a pubspec containing webview_flutter` —
  fixture: in-memory `pubspec.yaml` content declaring `webview_flutter`.
  Asserts a violation naming that package. Exists to prove the
  forbidden-dependency scan (§6b) — which is text/regex-based, not a real
  dependency-resolution check — correctly flags a known-forbidden package
  name rather than only ever running against an already-clean real
  `pubspec.yaml`/`pubspec.lock` (which proves absence, not detection
  capability).
- `apps/mobile/test/guards/tenant_identifier_guard_test.dart::self-test: checker fires on a literal "bpm-default"` —
  fixture: `const tenantSlug = 'bpm-default';`. Asserts a violation naming
  `bpm-default`. Exists to prove the string-literal scan (§6c) actually
  matches against the realm-name floor (`bpm-default`, sourced from
  `priv/keycloak/realms/bpm-default.json`) rather than only ever running
  against a real `lib/` tree that (correctly, today) contains no such
  literal.

**Evidence quoted (step-02b-mobile-dev.json, result.acceptance_criteria_evidence.guard_self_tests):**
```
all three PASS: boundary guard fires on cross-feature import not in depends_on (Rule 2), dependency guard fires on webview_flutter, tenant-identifier guard fires on literal 'bpm-default'
```

### AC5 — `git ls-files apps/mobile/lib | cut -d/ -f4 | sort -u` matches architecture.md §2's directory set exactly

**Verified by:** command-output demonstration (`git ls-files` + shell
pipeline), not a test file. This is a repository tracking-state check
(does git actually track a placeholder file in each required directory, and
no unlisted directory), which is outside a Dart test's reach entirely —
`flutter test` runs against the working tree, not against `git`'s index.

**Evidence quoted:**
```
git ls-files apps/mobile/lib | cut -d/ -f4 | sort -u (after `git add apps/mobile`) ->
api
app.dart
auth
bootstrap
definitions
design_system
features
i18n
main.dart
renderers
shared
```
Matches architecture.md §2's nine directories (`api`, `auth`, `bootstrap`,
`definitions`, `design_system`, `features`, `i18n`, `renderers`, `shared`)
plus `main.dart` plus exactly one app/router file (`app.dart`) — no more, no
fewer.

**Why this exists:** guards against a scaffold that has the right files on
disk but an incomplete `git add`, or an extra untracked/stray directory
that would silently expand the module surface beyond what architecture.md
§2 sanctions.

### AC6 — widget test: renderer registry shows unsupported-definition-type fallback, never an empty container

**Verified by:**
`apps/mobile/test/widgets/renderer_registry_fallback_test.dart` —
`testWidgets('RendererRegistry.build shows the unsupported-definition-type
fallback for an unknown definition type, never an empty container', ...)`.
Pumps a `RendererRegistry().build(context, 'not-a-real-type', const {})`
into a `MaterialApp`/`Builder` and asserts both
`find.byKey(unsupportedDefinitionTypeKey)` and
`find.textContaining('Unsupported definition type')` each find exactly one
widget.

**Why this exists:** this is the one behavioral (non-static-analysis, non-
guard) test in the suite — it exercises the actual widget tree the registry
produces for an unrecognized definition type, directly proving the "never
an empty `Container()`/`SizedBox.shrink()`" requirement from the design
(§4) — a requirement that a purely-static text scan couldn't verify, since
"renders visible text" is a runtime widget-tree property, not a source-text
property.

verification — so a later reader doesn't mistake "the Podfile line is
right" for "the iOS app was built and runs."
