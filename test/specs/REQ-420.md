# REQ-420 — CI: Mobile gate job in `.github/workflows/ci.yml`

## Scope test result: out of scope — no executable surface

REQ-420's only change is `.github/workflows/ci.yml` — a GitHub Actions workflow
definition (declarative job/step wiring: `if:` conditions, `needs:`, `uses:`,
shell `run:` blocks that are themselves thin invocations of `flutter analyze` /
`flutter test` / `flutter build apk --debug`). There is no Elixir, Dart, or
frontend application logic introduced by this requirement — only YAML
structure that GitHub Actions itself interprets and executes.

Per `docs/agents/workflows/WF-02_requirement_implementation.md` Step 3's scope
test: a requirement whose only output is build/CI configuration, with no
application-executable surface, is out of scope for ExUnit/Dart test code. A
test that greps `ci.yml` for a keyword or asserts on YAML string structure
would be exactly the manufactured-busywork anti-pattern `docs/anti-patterns.md`
and `core-directives.md` warn against — it would not exercise any real
behavior, only restate the YAML.

## Acceptance criteria and how each is actually verified

All six criteria are verified by command execution against the real
`ci.yml` file and the real GitHub Actions run of this PR — not by test code:

1. **`jobs` list / mobile job `name` / `if` condition** — verified by running
   `python -c "import yaml,sys; d=yaml.safe_load(open('.github/workflows/ci.yml')); print(sorted(d['jobs'])); print(d['jobs']['mobile']['name']); print(d['jobs']['mobile']['if'])"`
   and quoting its real stdout. This is YAML introspection via the real
   parser, not test assertions on behavior.
2. **No removed/changed line inside `backend`/`frontend`, no regex changes** —
   verified by `git diff origin/main -- .github/workflows/ci.yml` and reading
   the diff for additions-only in those jobs, quoted verbatim.
3. **Flutter steps carry the fail-open `if:` and `changes` emits
   `mobile=true` on the push/fail-safe/fallback branches** — verified by
   quoting the relevant lines directly out of the file (grep/read), not by
   executing them under a test harness.
4. **The PR's actual Mobile gate job runs all four flutter steps to
   success** — this is inherently a live-CI fact: it requires `gh run view
   --json jobs` against a real GitHub Actions run of this exact commit. No
   local test can substitute for "GitHub Actions actually ran this and it
   passed."
5. **`backend`/`frontend` gates' conclusions are unchanged on this same
   PR** — verified by `gh pr checks`, again a live-CI fact requiring the real
   run, not something a local test suite can assert.
6. **The job's header comment records the 0018 open question** — verified by
   reading the comment text directly out of the committed YAML and quoting
   it.

None of these six criteria are, by nature, unit- or integration-testable
against application code: four are direct inspection of the YAML/git-diff
itself, and two (AC4, AC5) require a real GitHub Actions run of this specific
PR, which only exists once pushed — no test file can fabricate that.

## Disposition

Per WF-02 Step 3: routed directly to RELEASE-VALIDATOR (Step 5), skipping
Steps 3b (TEST-DESIGN-VALIDATOR) and 4 (TEST-RUNNER) entirely. No test code
written. RELEASE-VALIDATOR verifies the six acceptance criteria by reading
`.github/workflows/ci.yml` directly and by inspecting this PR's own CI run
once pushed, per the criteria's own verification methods above.
