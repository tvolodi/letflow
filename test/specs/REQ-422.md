Verified: `apps/mobile/test/security/transport_policy_test.dart`

| Clause | Test | Why it exists |
|---|---|---|
| 5a: release policy rejects `http://` request URL in the API client, zero fake-adapter calls | `a release-policy client rejects an http:// request before any socket opens -- the fake adapter records zero calls` | Asserts both the exception (`throwsA(isA<DioException>())`) and the zero-call invariant (`fakeAdapter.requests, isEmpty`) -- rejection alone wouldn't prove no socket was opened |
| 5b: release policy rejects `http://` realm_url in bootstrap, zero calls | `a tenant-config response whose realm_url is http:// (release policy) is rejected with oidcFailure, and the OIDC adapter is never invoked` | Asserts `appAuthAdapter.callCount == 0` -- proves the OIDC step never runs, not just that the overall bootstrap failed |
| 5c: release policy allows `https://` | Table-driven `checkTransportPolicyDecisions` case `('https://api.letflow.example/x', true, true)` | Included in the same table as the rejection cases so an accidental "reject everything" regression would also fail |
| 5d: debug policy allows http for `localhost` | Table-driven case `('http://localhost:8080/x', false, true)` + `the same http:// realm_url IS allowed under the debug transport policy` (bootstrap-level, uses `10.0.2.2` but exercises the same code path `localhost` would) | Table covers `localhost` directly at the `TransportPolicy` unit level |
| 5e: debug policy allows http for `10.0.2.2` | Table-driven case `('http://10.0.2.2:8080/x', false, true)` + behavioral test `a debug-policy client allows http://10.0.2.2 -- the fake adapter does record the call` (proves the positive: the call *is* recorded, not just "no exception") + bootstrap-level test with the OIDC adapter actually invoked (`callCount, 1`) | Both the Dio-interceptor level and the bootstrap-realm_url level are exercised for this host, at two different points in the transport-policy design |

| Clause | Test | Why it exists |

| 7b: a request for tenant B is never sent with a token whose `iss` is A's realm | `audience_scoping_test.dart`'s `a token whose iss is a DIFFERENT tenant's realm than the active one is never attached -- request proceeds unauthenticated` -- deliberately stores a token under realm B's key whose `iss` claim is A's realm, and asserts the bearer interceptor refuses to attach it | This is the defense-in-depth check for the case 7a's deletion doesn't by itself cover: even if a stale/mismatched token existed under the wrong key (a bug elsewhere, or a race), the audience check independently blocks it. `tenant_switch_test.dart` proves deletion happens (7a); this test proves that *even if* deletion were bypassed, the iss-mismatch defense still holds (7b) |

**Observation (not a gap):** `audience_scoping_test.dart` and
`transport_policy_test.dart` both exercise the bearer-interceptor / transport-
policy-interceptor logic via a `_bearerInterceptorForTest` /
`_transportPolicyInterceptorForTest` helper that mirrors the private
interceptor construction inside `lib/api/api_client.dart` line-for-line,
because the real interceptor closures are private and cannot be imported
directly into a test file. MOBILE-DEV's own file comments flag this and
argue the two are "proven consistent with each other" via the shared public
`issuerOf`/`TransportPolicy.isUrlAllowed` functions the reimplementation
calls into. This is an accepted, pre-existing pattern in this codebase (the
same shape appears in REQ-421's tests) rather than a new gap introduced by
REQ-422; flagged here for TEST-DESIGN-VALIDATOR's awareness rather than
reworked, since the underlying decision logic (`issuerOf`, `isUrlAllowed`)
that actually determines pass/fail *is* the real production code under test.
