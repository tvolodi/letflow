## Gap found and closed this step

**AC5's tenant-switch isolation was proven only against
`InMemoryDefinitionCacheRepository`** (`test/definitions/
active_definition_cache_holder_test.dart`), whose `close()` is a documented
no-op (design §5.1). That test proves `ActiveDefinitionCacheHolder`'s own
field bookkeeping (assigns `current`/`currentRealmUrl`, calls the opener
exactly once per new tenant) but nothing about whether the REAL
`SembastDefinitionCacheRepository`'s on-disk `Database` handle is actually
released before the next tenant's file is opened — the exact lifecycle
property both SECURITY-REVIEWER and REVIEWER flagged as the one place a
real bug (a leaked file handle, or two tenants' data sharing one still-open
handle) could hide behind an all-green in-memory-only test suite.
`sembast_cache_repository_test.dart` tests the real repository's own CRUD
persistence (close/reopen round-trip) but was never specifically checked
against a tenant-switch scenario through `ActiveDefinitionCacheHolder`.

**Closed by extending** `apps/mobile/test/definitions/
active_definition_cache_holder_test.dart` with a new test group, `'real
SembastDefinitionCacheRepository (not the in-memory fake)'`, containing one
test: `'tenant switch A -> B against real Sembast files: A's on-disk handle
is genuinely closed ..., B is a distinct freshly-opened file with none of
A's data, and the switch itself completes with no file-lock/still-open
error'`.

**What the new test does, and why each assertion exists:**

1. Opens tenant A's repository through `ActiveDefinitionCacheHolder.openFor`
   using the REAL `SembastDefinitionCacheRepository.open(...)` (via
   `databaseFactoryIo`, pointed at a `dart:io Directory.systemTemp` temp
   dir, at the exact per-tenant file-name design §7.1 specifies —
   `cacheFileNameFor(realmUrl)`), writes one entry and a cursor, and keeps a
   direct handle to that repository instance (bypassing the holder).
2. Switches to tenant B via `holder.openFor(_realmB, ...)`, using the same
   real opener pointed at B's own distinct file path. This `await` itself
   is the first assertion in spirit: if `openFor` failed to actually close
   A's real handle before opening B's (e.g. a bug that skipped the
   `close()` call, or a store implementation that enforced file-level
   exclusivity), this call would throw instead of completing — nothing
   catches or suppresses an exception here, so a regression fails the test
   at this line with a real stack trace, not a silent pass.
3. Asserts B's repository is a distinct Dart object from A's (`isNot(same
   (repoA))`) and that B's `listAvailable()`/`readCursor()` are empty/null —
   proving isolation, not merely "the two variables point at different
   things."
4. **The genuine file-handle-release check**: calls `repoA.listAvailable()`
   directly on the OLD repository instance — still held, never discarded by
   the test, exactly the object `openFor` was supposed to have closed — and
   asserts it throws `DatabaseException` with
   `code == DatabaseException.errDatabaseClosed`. This is sembast's own
   internal `_checkOpen()` guard (verified by reading
   `sembast-3.8.7/lib/src/database_impl.dart` and
   `store_ref_impl.dart`'s `find()` → `client.getSembastStore(this)` →
   `_checkOpen()` call chain in the vendored package source, since no
   network access is available to consult docs). A test double or an
   in-memory implementation cannot produce this failure mode; only a
   real, actually-closed `sembast.Database` throws it. This is the
   assertion that would have caught a leaked/never-closed real handle,
   which is exactly the gap SECURITY-REVIEWER and REVIEWER named.
5. **Reopens tenant A's exact on-disk path directly** (bypassing the holder
   entirely, a brand-new `SembastDefinitionCacheRepository.open` call at
   the same path) and asserts A's entry and cursor are still there,
   unharmed. This does two things at once: (a) proves the close was a
   clean, durable flush — not a crash or corruption — so "closed" means
   "properly closed," and (b) proves there is no lingering OS/library-level
   file lock on A's path, since a second independent open of the same file
   immediately after the first was closed would itself fail if the handle
   had not truly been released.
6. **Reopens tenant B's own file independently a second time** and asserts
   it is empty — corroborating B is a genuinely separate on-disk store, not
   e.g. a path collision with A's file (a real risk `cacheFileNameFor`'s
   base64 encoding must avoid, and cross-checked here operationally rather
   than only by re-reading the encoding function's own unit test).

Each of these six checks would independently fail against a plausible bug
that only an in-memory-repository test cannot expose: a holder that keeps
using A's already-closed handle (fails step 4 differently — would throw
inside `openFor`'s own new-tenant path instead, or corrupt data instead of
cleanly throwing), a holder that never actually calls `close()` on A
(step 4's `DatabaseException` assertion would fail — no exception, or a
different one), or a `cacheFileNameFor` collision between two realm URLs
(step 6 would find A's leftover entry in what should be B's empty file).
