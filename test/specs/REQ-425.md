# REQ-425 — MOB-6 mobile API client hardening (single client, refresh, backoff, typed errors)

## Requirement text

> MOB-6 in `docs/mobile/requirements.md` (build-order M6; depends on M2). Built
> BEFORE MOB-4 (REQ-426..428) -- see the S9 header: the renderers' six states
> classify this requirement's `ApiError`. SECURITY-REVIEWER gate (refresh-token
> handling, token clearing).
>
> Hardens `lib/api/api_client.dart` (created by REQ-421) into the single
> client:
> 1. Attach the active tenant's bearer token (REQ-422's `iss` check).
> 2. On 401: exactly one silent refresh via `flutter_appauth`'s token refresh,
>    then exactly one retry of the original request; concurrent 401s share one
>    in-flight refresh. On refresh failure: clear the tenant's tokens (REQ-422
>    store) and route to login.
> 3. Exponential backoff on 5xx for idempotent methods only (GET), bounded
>    attempts; POST is not auto-retried (no duplicate task completion).
> 4. Normalise every failure to a sealed `ApiError` type before it leaves
>    `lib/api/`: at minimum network-unavailable, unauthorized, forbidden
>    (403), not-found, module-not-available (a 404 on any
>    `/api/v1/modules/<id>/` path -- `architecture.md` §6: absence is 404,
>    not 403, and must not render as a generic not-found), backpressure (429,
>    carrying the `Retry-After` seconds -- the backend emits 429 from
>    `lib/letflow/plugs/admission.ex` and
>    `lib/letflow/plugs/public_read_rate_limit.ex`), validation (422 with
>    RFC 9457 field errors), conflict (409), server (5xx after retries).
> 5. A static guard (`apps/mobile/test/guards/`), the counterpart of the SPA's
>    raw-fetch-outside-client guard in `web/tests/guards/`: no file outside
>    `lib/api/` imports `package:dio` or `package:http` or uses `dart:io`
>    `HttpClient`; with a self-test.

## Clause-by-clause coverage table

### AC1 — 401 refresh-then-retry

Verified: `apps/mobile/test/api/api_client_hardening_test.dart`, group
`401 refresh-then-retry (AC1)`.

| Clause | Test | Why it exists |
|---|---|---|
| 1a: a fake server returning 401 once then 200 asserts exactly one refresh call and exactly one retry | `a 401 then 200 triggers exactly one refresh and exactly one retry` — asserts `h.appAuthAdapter.refreshCallCount == 1` and `h.fakeAdapter.requests` has length 2 (the 401'd original + the one retry), plus that the retry carries the refreshed token in its `Authorization` header | Exercises the real `ApiClient._handleUnauthorized`/`_RefreshCoordinator` path end to end against a fake transport, so a regression that refreshes twice, retries twice, or forgets to re-attach the refreshed token would fail this test specifically |
| 1b: two concurrent requests both receiving 401 trigger one refresh total | `two concurrent 401s trigger exactly one refresh total, each request still retried once` — fires `Future.wait([client.get('/a'), client.get('/b')])`, both paths 401 on their first hit, and asserts `refreshCallCount == 1` while both requests still individually succeed (4 total transport calls: 2×(401+retry)) | Proves `_RefreshCoordinator.refreshOnce()`'s single-in-flight-future sharing actually coalesces concurrent 401s rather than each caller starting its own refresh — the exact race the requirement text calls out ("concurrent 401s share one in-flight refresh") |

Two additional tests in this group are not separate AC1 clauses but are
directly relevant boundary behavior that a coverage-only read of AC1 would
miss: `a second 401 on the retried request itself is terminal` (proves the
loop-prevention flag stops a second refresh) and `an unauthenticated call
... skips the refresh flow entirely` (proves `getUnauthenticated` never
refreshes). Both exercise real production code paths (`_kRetriedAfter401Flag`,
the `skipAuth` short-circuit) that AC1's two clauses alone don't force to be
tested, but that a naive implementation of AC1 could easily get wrong (e.g.
infinite refresh loop, or refreshing for anonymous calls that have no token
to refresh).

### AC2 — refresh failure: token clearing + login routing

Verified: `apps/mobile/test/api/api_client_hardening_test.dart`, group
`refresh failure (AC2)`.

| Clause | Test | Why it exists |
|---|---|---|
| 2a: refresh failure deletes the tenant's tokens from the secure store | `refresh failure deletes the tenant's tokens from the secure store and routes to login` — asserts `await h.tokenStore.read(_realmUrl)` is `null` after `h.appAuthAdapter.refreshError` is set and a 401 is received | Exercises `_RefreshCoordinator._handleFailure`'s real `_tokenStore.delete(realmUrl)` call against a real `TenantTokenStore` backed by a fake secure-storage platform — a regression that fails to delete would leave the token readable |
| 2b: refresh failure routes to the login route | Same test — asserts `h.loginRouteCallCountGetter() == 1` | Asserts the `LoginRouter` callback (`routeToLogin`) was actually invoked exactly once, not merely that tokens were cleared — clearing tokens without routing would strand the user on a broken screen |

A second test, `refresh failure when no refresh token is stored also clears
tokens and routes to login, without ever calling the adapter`, covers the
edge case where there is no refresh token to attempt a refresh with at all
(`refreshToken == null` branch in `_doRefresh`) — both clauses (2a, 2b) are
asserted again there, plus `refreshCallCount == 0` proving the adapter is
never invoked when there is nothing to refresh with.

### Cross-tenant-race regressions (SECURITY-REVIEWER rework, not in REQ-425's own AC list)

Independently verified as real, non-stub tests exercising the shipped
production code (`_RefreshCoordinator._doRefresh`'s post-await re-check,
and `_bearerInterceptor`'s own retry-dispatch-time re-check), not
reimplementations:

**Group `cross-tenant refresh race (rework 1 — SECURITY-REVIEWER BLOCKER)`**
(closes the window where `switchTenant`/`logout` flips the active tenant
while `_doRefresh`'s network `await` is still suspended):

| Test | What it asserts |
|---|---|
| `a tenant switch racing an in-flight 401 refresh aborts the retry instead of resurrecting the old tenant's tokens or serving the retry as the new tenant` | Old tenant's tokens are untouched (still the seeded values, not overwritten by the discarded refresh result); the new tenant acquires no tokens; exactly one refresh call and the retry is never sent (`requests` length 1); `loginRouteCallCountGetter() == 0` (an abort is not a genuine failure) |
| `a logout racing an in-flight 401 refresh does not resurrect the just-deleted tenant's tokens` | The logged-out tenant's tokens remain deleted (not written back by the in-flight refresh); one refresh call; the retry is never sent |

**Group `cross-tenant retry-dispatch race (rework 2 — SECURITY-REVIEWER
BLOCKER, post-refresh-success window)`** (closes the later window where the
refresh itself succeeds but the tenant switch lands between
`_handleUnauthorized`'s pre-fetch check and the retry's own pass through
`_bearerInterceptor`):

| Test | What it asserts |
|---|---|
| `a tenant switch landing after refreshOnce() succeeds but before the retry's own bearer-interceptor pass runs aborts the retry -- it is never dispatched at all, let alone carrying the new tenant's token` | Uses a purpose-built interceptor registered *before* `ApiClient.forTesting`'s bearer interceptor to flip the active tenant exactly on the retry's second pass through the chain (never the original 401'd pass) — asserts `refreshCallCount == 1` (the refresh itself succeeded, unlike rework 1's tests), `fakeAdapter.requests` has length 1 (the retry never reaches the transport layer — it is rejected by `_bearerInterceptor`'s own re-check before a token is attached), the new tenant acquires no tokens, and `loginRouteCallCount == 0` |

Both groups are real: they exercise `ApiClient.forTesting`'s actual
production `_RefreshCoordinator` and `_bearerInterceptor` closures (not
reimplementations), and each test's own in-line comments identify the exact
race window and why it is distinct from the other group's window. Confirmed
present, non-stub (each contains multiple real assertions against live
harness state, not a bare `expect(true, true)`), and consistent with what
SECURITY-REVIEWER's BLOCKER findings (named directly in the group titles)
would have required to be closed.

### AC4 — ApiError variant mapping

Verified: `apps/mobile/test/api/api_client_hardening_test.dart`, group
`ApiError variant mapping (AC4)`, plus the direct `classifyError` unit test.
AC4 requires a test per variant of the sealed `ApiError` type
(`apps/mobile/lib/api/api_error.dart`) and, explicitly, the three named
sub-cases.

| Variant / sub-case | Test | Notes |
|---|---|---|
| `NetworkUnavailableError` | `classifyError direct unit coverage of every status branch` (`statusCode: null`) AND `a connection-error DioException maps to NetworkUnavailableError, never a raw DioException/SocketException` (full flow, AC5 group) | Both a direct unit call and an end-to-end transport-exception path |
| `UnauthorizedError` (401) | `classifyError` direct case, AND covered end-to-end throughout every AC1/AC2 test (every 401 scenario throws `UnauthorizedError`) | |
| `ForbiddenError` (403) | `classifyError` direct case, AND full-flow `a 403 maps to ForbiddenError` | |
| `NotFoundError` (plain 404) | `classifyError` direct case (`bareModuleRo`, no trailing segment), AND full-flow `a 404 elsewhere (e.g. /api/v1/me/modules) maps to NotFoundError` — **the explicitly named sub-case** | |
| `ModuleNotAvailableError` (404 on `/api/v1/modules/<id>/...`) | `classifyError` direct case (`moduleRo`, `/api/v1/modules/exam/instances`), AND full-flow `a 404 on /api/v1/modules/exam/x maps to ModuleNotAvailableError with moduleId "exam"` — **the explicitly named sub-case**, asserting the extracted `moduleId` | Full-flow test hits the exact path the requirement's own text uses as its worked example |
| `BackpressureError` (429) | Full-flow `a 429 with Retry-After: 7 maps to BackpressureError(7)` — **the explicitly named sub-case**, sets `retry-after: ['7']` and asserts `retryAfterSeconds == 7`; plus `a 429 with a missing/malformed Retry-After defaults to 1 second` | The malformed-header case is not separately named in AC4 but is real coverage of `_parseRetryAfter`'s documented default-to-1 fallback |
| `ValidationError` (422, RFC 9457) | Full-flow `a 422 maps to ValidationError with parsed RFC 9457 field errors` (asserts the parsed `field`/`constraint`/`message` shape) plus `a 422 with a malformed body still maps to ValidationError, with an empty field-errors list` | Covers both the well-formed and malformed-body branches of `_parseFieldErrors` |
| `ConflictError` (409) | `classifyError` direct case, AND full-flow `a 409 maps to ConflictError` | |
| `ServerError` (5xx, and the unmapped-4xx catch-all) | `classifyError` direct case (500), AND the AC3 5xx-exhaustion test, AND full-flow `a bare 400 (unmapped 4xx) folds into ServerError as the catch-all (design §1.2 OQ-1)` | The 400 catch-all case is a deliberate design decision (flagged OQ-1 in the implementation's own comments) and is explicitly tested rather than left implicit |

Every one of the 9 `ApiError` variants declared in `api_error.dart` has at
least one test that would fail if its classification logic regressed, and
all three explicitly-named AC4 sub-cases (module-404, plain-404,
429-with-Retry-After-7) have dedicated full-flow tests using the requirement
text's own example values.

### AC5 — no raw transport exception escapes `lib/api/`

Verified: `apps/mobile/test/api/api_client_hardening_test.dart`, group
`no raw transport exception escapes lib/api/ (AC5)`.

| Clause | Test | Why it exists |
|---|---|---|
| 5a: no `DioException`/`SocketException` escapes — a connection failure is normalized | `a connection-error DioException maps to NetworkUnavailableError, never a raw DioException/SocketException` — throws a `DioException` wrapping a `SocketException` from the fake adapter, catches what `ApiClient.get` actually throws, and asserts it `isA<NetworkUnavailableError>()` and explicitly `isNot(isA<DioException>())` | The `isNot(isA<DioException>())` assertion is the one that actually proves the negative clause — merely asserting the positive type wouldn't catch a hypothetical implementation that wraps both | 
| 5b: the public client API returns or throws only `ApiError` | `every ApiError variant is a subtype of ApiError and Exception, never a DioException` — constructs one instance of each of the 9 variants and asserts each `isA<Exception>()` and `isNot(isA<DioException>())` | Confirms the type system itself enforces the invariant at the `ApiError` sealed-class level (declared `sealed class ApiError implements Exception` in `api_error.dart`), complementing 5a's single-scenario proof with a type-level one covering every variant at once |

This clause is also transitively reinforced by every other test in the file:
every `throwsA(isA<SomeApiError>())` assertion (AC1–AC4's tests) is itself
evidence that the corresponding code path throws a typed `ApiError`, not a
raw `DioException`, for that specific status/exception combination.
