## AC1 — "six widget tests, one per state ... assert the state's dedicated widget by key"

This criterion names six distinct forcing mechanisms joined by semicolons — treated as
six independent clauses (ISS-0880: an "and"/list-joined criterion gets one test per
clause, not one test that happens to hit the loudest clause). Each sub-case below forces
a *different* branch of `RendererStateView.build`'s exhaustive `switch` and exists to
prove that specific `ApiError`/definition-layer condition actually reaches its own `Key`
end-to-end — a passing 1b proves nothing about 1c's branch, since they are different
`switch` arms wired from different `ApiError` variants (design §1.2's table).

File: `apps/mobile/test/renderers/renderer_state_view_ac1_test.dart`.

- **1a (loading)** — GET `/entities/definitions/active/widgets` scripted to `hang()`
  (a `Future` that never completes). `loadFirstPage` sets `RendererLoading`
  synchronously before that `await`, so the state never advances past it. Asserts
  `rendererLoadingKey`. Exists because this is the ONE state that isn't reached through
  `rendererStateForError`/`staleVersionState` at all — it's the controller's own initial
  state, so it needs its own proof the widget's `switch` renders it, independent of the
  error-mapping path every other sub-case exercises.
- **1b (fetch-failure)** — GET throws `NetworkUnavailableError()`. Asserts
  `rendererFetchFailureKey`. Exists to prove `rendererStateForError`'s
  `NetworkUnavailableError` arm (design §1.2 table) actually reaches the widget, not just
  that the function compiles.
- **1c (permission-denied)** — GET throws `ForbiddenError()` (403). Asserts
  `rendererPermissionDeniedKey`. Per design §3.3/§8, this is necessarily forced (no real
  backend response from either of the list renderer's two calls can produce a 403) — the
  test proves the *shared wrapper* handles it, not that this screen's real endpoints
  reach it.
- **1d (stale-version)** — GET succeeds with a field whose `"type"` is `"money"` (outside
  the nine known strings). Asserts `rendererStaleVersionKey`, and additionally asserts
  `gateway.postCalls` is empty — proving the "fails loudly, short-circuits before Call 2"
  half of design §3.3, not just that the state value renders (a weaker assertion would
  pass even if Call 2 were wrongly still issued).
- **1e (validation-error)** — GET throws `ValidationError(fieldErrors: [...])` (422).
  Asserts `rendererValidationErrorKey` AND that the field error's `message` text is
  actually rendered (`find.text('unknown entity type')`) — not just the container key,
  since `RendererValidationError`'s whole point is surfacing the specific field messages.
- **1f (backpressure)** — GET succeeds; POST throws `BackpressureError(retryAfterSeconds:
  3)` (429 with `Retry-After: 3`). Asserts `rendererBackpressureKey`.

## AC2 — countdown 3, 2, 1, then exactly one retry, no throw

File: `apps/mobile/test/renderers/renderer_state_view_ac2_backpressure_countdown_test.dart`.

Builds on 1f's setup (an extra second POST response queued for the automatic retry).
Uses `tester.pump(const Duration(seconds: 1))` three times — `flutter_test`'s fake clock
intercepts `BackpressureCountdown`'s real `Timer.periodic` inside a widget test's zone
(design §1.4), so no injected clock seam is needed (unlike `ApiClient`'s own retry
backoff in REQ-425, which needed one because its retries are not driven by a widget
test's pump loop).

Asserts, as separate checks within the one test (each meaningfully independent, not
restating the same fact twice):
1. Text is `'3'` immediately after the state becomes `RendererBackpressure` — before any
   tick (catches an off-by-one that would show `'4'` or a pre-decrement value).
2. After one 1-second pump: `'2'`, and still only 1 POST call so far — proves the
   countdown does not itself trigger a request mid-count.
3. After a second: `'1'`, still 1 POST call.
4. After the third: `postCalls` becomes exactly 2 (not 0, not 3+) — the "exactly one
   retry" half of AC2. Existing separately from the text assertions because a
   requirement to show "3,2,1" says nothing on its own about how many HTTP calls fire;
   both halves need their own check.
5. `tester.takeException()` is `null` — proves `BackpressureCountdown`'s
   catch-and-swallow around `onZero` (design §1.4) actually holds even when the retry
   itself succeeds and drives a real state transition, not just in isolation.
6. `rendererBackpressureKey` is gone after the retry succeeds — proves the widget
   actually transitioned to `RendererContent`, not stuck re-rendering the same
   backpressure state.

## AC3 — filters in the POST body; next page uses previous `next_cursor`; stops at null

File: `apps/mobile/test/renderers/list/list_renderer_ac3_test.dart`. Three separate
`test()`s (not widget tests — AC3 is pure controller/request-construction logic, no
presentation involved), one per sub-assertion named in the criterion, so a regression in
any one is independently visible:

- **AC3a** — `loadFirstPage` with one `FilterClause(field: 'status', op: FilterOp.eq,
  value: 'open')` asserts the POST body's `filters` key is `[{'field': 'status', 'op':
  'eq', 'value': 'open'}]` exactly — proves `FilterClause.toJson`'s wire mapping (the
  `FilterOp.wireValue` table, design §3.3) is actually what leaves the controller, not
  just that the class has a `toJson` method.
- **AC3b** — after a first page whose response's `next_cursor` is `'cursor-1'`,
  `loadNextPage()`'s second POST body has `cursor == 'cursor-1'` exactly — proves the
  controller re-sends the *previous response's own* value, not a value it independently
  computed or a caller-supplied one.
- **AC3c** — after a first-page response whose `next_cursor` is `null`, two subsequent
  `loadNextPage()` calls issue zero further POST requests (`postCalls` stays at length 1)
  — proves the stop condition is enforced at the controller (INV-5), not merely that a
  UI scroll-listener happens not to fire again.

## AC4 — every existing renderer under `lib/renderers/{form,list,process,task}/` is
wrapped by the shared state wrapper

File: `apps/mobile/test/renderers/renderer_state_wrapper_guard_test.dart`.

`form/`, `process/`, `task/` are still placeholder libraries as of this requirement
(design §0) — REQ-427/428 build them. Per design §4 item 2, the guard is written as an
explicit, TEST-DESIGNER-maintained probe list (`_probes`) iterated by a `for` loop over
`testWidgets`, rather than a single hardcoded assertion about "4 renderers" — a future
requirement adding a real `form`/`process`/`task` renderer appends one entry to
`_probes` (its builder function + a `find.byType(RendererStateView<ItsOwnPageType>)`
finder) and gets covered with no rewrite of this file's logic. A second, plain `test()`
(`AC4 sanity`) asserts `_probes` currently names exactly `['list']` — a tripwire so this
guard cannot silently drift to covering fewer renderers than actually exist without a
visible failure calling that out.

The per-probe widget test pumps `buildListRenderer(context, {'entity_type': 'widgets'})`
under a `ProviderScope` overriding `listRendererControllerProvider` with a
`FakePostCapableHttpGateway`-backed controller (GET scripted to hang, so the renderer
never leaves `RendererLoading` — AC4 is about widget *structure*, not about a fetch
completing; `RendererStateView` renders something for every one of its seven states, so
the structural check holds regardless of fetch outcome) and asserts
`find.byType(RendererStateView<ListPage>)` finds exactly one widget immediately under
the renderer's own root — matching AC4's own suggested mechanism ("e.g. by type check in
a widget test for each").
