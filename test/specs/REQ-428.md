# REQ-428 — MOB-4 task renderer, claim/complete flow, process-instance read-only renderer

## Requirement text

> Third MOB-4 requirement. Task routes (`lib/letflow/routers/tasks.ex`): `GET
> /api/v1/tasks/inbox`, `GET /api/v1/tasks/:id`, `POST /api/v1/tasks/:id/claim`,
> `POST /api/v1/tasks/:id/complete`. The task form is resolved through REQ-424's
> pinned resolver and rendered by REQ-427's form renderer; never the active
> version. Process-instance renderer: read-only view of `GET
> /api/v1/instances/:id` and `/api/v1/instances/:id/timeline`
> (`lib/letflow/routers/instances.ex`) -- status, current step, timeline. No
> cancel/rebind/advance actions (not in MOB-4). All screens use REQ-426's
> six-state wrapper; claim/complete errors (409 already claimed, 403, 422) map
> to its states.

This is a mobile-only run (`apps/mobile/` only). Per WF-02's established
pattern for the mobile tier (same as REQ-425/426/427), MOBILE-DEV writes the
Dart test files in the Step 2b-mobile turn; TEST-DESIGNER's role here is
**independent verification against each decomposed acceptance-criterion
clause**, not authorship from scratch — write new test code only if a real
gap is found. This session applies the ISS-0880 lesson explicitly: every
multi-clause AC is decomposed into its individual clauses below, and each
clause is matched to the specific test assertion that fails if, and only if,
that clause is violated (not one test asserting the AC's gestalt).

**Result of this step: no gap found.** Every clause of every acceptance
criterion has a test whose failure would be caused specifically by that
clause's violation, verified by reading the actual test bodies (not
MOBILE-DEV's handoff summary) and by tracing each assertion back to the
production code path it exercises. No new test code was required. One
path-naming discrepancy was found and corrected below (see "Housekeeping
note").

### Six-state wrapper (requirement-text clause, cross-cutting over AC1–AC4)

> "All screens use REQ-426's six-state wrapper; claim/complete errors (409
> already claimed, 403, 422) map to its states."

- The `TaskClaimOutcome` sealed type (`TaskClaimSuccess` /
  `TaskClaimNoLongerAvailable` / `TaskClaimForbidden` /
  `TaskClaimNetworkUnavailable` / `TaskClaimOtherFailure`) is a claim-specific
  outcome type, not `RendererState` itself — by design (§3.2/§3.3), a claim
  conflict must never discard the inbox's/detail's already-loaded
  `RendererContent` (INV-5), which is exactly what `task_claim_conflict_test.dart`
  clause 3b proves. 422 on claim has no dedicated `TaskClaimOutcome` variant;
  it lands in `TaskClaimOtherFailure` (the catch-all), which is a defensible
  choice for an endpoint whose success body carries no form payload to
  422 against structurally — the requirement text's "422" is substantively
  about the complete/submit path.
- Complete's error handling is REQ-427's `FormRendererController.submit()`
  (composed thinly per design §3.5, not reimplemented) — its six-state
  mapping, including 422 (validation), is REQ-427's own test scope
  (`apps/mobile/test/renderers/form/form_submit_test.dart` and siblings),
  confirmed still passing in this run's `flutter test` output below.
- Every REQ-428 screen being wrapped by `RendererStateView` at its root is
  verified structurally by
  `apps/mobile/test/renderers/renderer_state_wrapper_guard_test.dart`'s
  `task` and `process` probe entries (see "Housekeeping note" above).
