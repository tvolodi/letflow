# REQ-436 -- Login-discovery rate limiter: test spec

Design authority: `lib/letflow/design/req436-login-discovery-rate-limiter.md` (s11 test plan T1..T13),
governed by `req434-email-first-login-directory.md` s0.3 D5/D6/D10/D11/D13/D14.
Implementation: `lib/letflow/plugs/login_discovery_rate_limit.ex`, `.../login_discovery_rate_limit/bucket.ex`.

| File | Style |
|---|---|
| `test/letflow/plugs/login_discovery_rate_limit_test.exs` | the plug through the stub chain `ClientIp -> LoginDiscoveryRateLimit -> :match`; `async: false`; Application env, telemetry handler and `/api/public` rows restored in `on_exit` |
| `test/letflow/plugs/login_discovery_rate_limit/bucket_test.exs` | the ETS bucket directly, clock injected via `now_ms` (no sleeping); `async: false` |
| `test/support/login_discovery_probe_router.ex` | test-only `Plug.Router` (`POST /probe`, `POST /probe-email`), compiled via `elixirc_paths(:test)`, no body parsing before the limiter |

Determinism: plug-level tests set refill to 0.0001/s so real elapsed time is negligible; bucket-level
tests pass an explicit `now_ms`; addresses are RFC 5737 / RFC 3849 documentation addresses; email keys are
fixed strings or random bytes; the login-discovery table is emptied before and after each test.
The superseded `login_discovery_rate_limit_smoke_test.exs` is merged into these files and deleted.

## AC1 -- namespaced, separate keys (T1)
- Bucket "every row ... starts with :login_discovery": drives all four kinds, then asserts on LIVE table
  contents (not a grep, which moduledoc text would trip). Why: a key leaking into another namespace would
  share state with something else (INV-5).
- Bucket "/api/public bucket keeps its own table and shapes": login traffic leaves the public table untouched,
  public traffic writes only `:global` / `{:ip, ip}` 3-tuples there and nothing in the login table.

## AC2 -- independence from /api/public, both directions (T2a-d)
Four plug tests: login global exhausted -> public not 429; public global zeroed (verified 429 first) ->
login still 200 and its own global bucket only lost one token; one address exhausting its login IP bucket ->
public unaffected for that address; one address exhausting its public IP bucket -> login IP bucket full.
Why both ways: sharing is a bidirectional defect; each direction is a separate way to regress.

## AC3 -- per-IP window, spoofed headers, global independent of any one IP (T3)
`ip_capacity`=5 -> 5x200 then 429 with varying `X-Forwarded-For`/`Forwarded` (and, separately, `X-Real-IP`
from an untrusted peer) -> same bucket; bucket follows `assigns.client_ip` over a different `remote_ip`, and
`remote_ip` when the assign is absent; junk assigns fall back to `remote_ip`; 9 distinct addresses against
`global_capacity`=8 trips the global bucket although no address sent more than one request.

## AC4 -- ordering (T4)
One address sends 200 = 10x`global_capacity`: first 5 admitted, 195 refused, 195 `:rate_limited_ip` events
and zero global ones, global tokens >= `global_capacity - ip_capacity`; a second address is admitted with no
global event; a refused request leaves the global token count unchanged (same `now_ms` before/after, so exact).

## AC5 -- IPv6 (T5)
`ip_bucket_id/1` table (v4, mapped, boundaries, /64 same/different, non-mapped lookalikes stay v6); end to end
two addresses in one /64 share a bucket and another /64 does not; end to end a trusted proxy forwards
`X-Real-IP: ::ffff:203.0.113.9` (also `::ffff:cb00:7109`) and `203.0.113.9` and they share ONE bucket (the
test asserts `ClientIp` really hands the limiter an 8-tuple, so the fold is the limiter's, not ClientIp's).

## AC6 -- identical 429s, body never read (T6)
IP / global / per-email refusals compared on status, sorted headers and body; two different emails give the
same bytes and the body never contains the email; `Retry-After` equals the configured constant (default and 123);
constant `cache-control` / `referrer-policy` / `x-robots-tag`. A malformed-content-type truncated-JSON POST to
an exhausted source gets 429 and `body_params` is still `%Plug.Conn.Unfetched{}` (the body was not read).

## AC7 -- bounded state, lossless eviction (T7)
10x`max_email_keys` distinct keys (both email kinds): population never above the cap, exactly `cap` admitted,
`size/1` equals a real row count; existing key still served at the cap; design s7.4 scenario with exact numbers
(hot key kept at t0+120s with ~2 tokens, not reset; non-idle never evicted at t0+299s; idle at t0+301s; swept
key then a full fresh bucket); sweep scope (`:email` leaves ip rows, `:global` never swept).

## AC8 -- two caps (T8)
Plug: with `max_ip_keys`=3 the 4th distinct /64 is refused, global token count identical before/after, no row
evicted (`sweep(:ip)` = 0, all three rows present), earlier sources still admitted, `:rate_limited_ip` emitted.
Config: `validate_config!/1` accepts `[]` / defaults, the `max_email_keys` invariant is checked at its exact
boundary (computed required and required-1), non-positive ints, small `max_ip_keys`, zero/rounds-to-zero refill
raise, and `Bucket.init/1` raises on a bad env before creating the table.

## AC9 -- compare-and-swap (T9)
200 tasks (concurrency 50) on one key with capacity 5, 20 rounds, on both the existing-row and insert-new
(global) paths: admits <= capacity (and >= 1); a refusal does not write the row.

## AC10 -- per-email and :send (T10)
Nth request for one address from 4 different source addresses trips on the 4th, another address unaffected;
`:send` is a one-token independent bucket (second refused, request bucket still 2.0 tokens, other key's send ok);
`:send` through the endpoint chain gives the same 429 bytes.

## AC11 -- outcome telemetry (T11)
Each cause emits exactly one `[:letflow, :login_discovery, :outcome]` event, measurements `%{count: 1}`,
metadata exactly `%{outcome: :rate_limited_ip | :rate_limited_global | :rate_limited_email}`; admitted
requests emit none.

## AC12 / AC14 -- process criteria (T12)
Empty `git diff` on `auth_pipeline.ex`, `api_pipeline.ex`, `public_read_rate_limit.ex`,
`public_read_rate_limit/bucket.ex`, and the existing `public_read_rate_limit_test.exs` passing unmodified, are
verified by `git diff` and by running that file, not by ExUnit (design T12; `git diff main...HEAD` inside a
test is a known anti-pattern). Compile/format/test/boundaries commands are quoted in the handoff.

## AC13 -- no identifying data in logs (T13)
`capture_log(level: :debug)` around a flood containing an email string, its hex forms and addresses asserts
none of them appears.
