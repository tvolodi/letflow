## Fail-first evidence

The code under test existed before these tests were written, so "fails against pre-change code" is trivially true of nothing and is NOT the evidence relied on.
The evidence is MUTATION of the shipped logic. Each mutant was applied to the file shown, the scoped test files run, then the original file restored
from a backup copy and `git diff -- <file>` verified empty (`git status --short lib config priv mix.exs` empty after the last revert).

## Recorded gaps and deliberate limits

- No test reaches a REAL relay (no network egress); STARTTLS / implicit TLS are exercised against the in-process sink with a generated CA that only the test-only override can supply.
- A genuine in-library crash with an error-level report could not be induced from the adapter's inputs: malformed CA, port, timeout and host options all fail inside `gen_smtp` WITHOUT crashing (`{:error, :failed}`, notices only). The forced cases therefore prove no leak and no survivor for the failure shapes reachable; the collector's ability to see a leaking crash report is proven separately by the `:proc_lib` positive control.
- The default Logger configuration drops SASL-domain reports (`handle_sasl_reports: false`); the suite un-hides them for its duration. With them visible, the hard-timeout kill produces one supervisor child-terminated report, carrying no arguments (allowed explicitly in NL).
- The `LETFLOW_MAIL_TIMEOUT_MS` ceiling and `max_concurrent` interplay is bounded by the sink-measured peak (EV f), not by a relay-specific connection limit.
- `mix letflow.check.test` (full parallel suite) was not run by this author (scoped runs only, memory); the dead-default-argument hazard was checked by a fresh forced recompile plus `mix test --warnings-as-errors` over every new file, grep count of "default values for the optional arguments" = 0.
