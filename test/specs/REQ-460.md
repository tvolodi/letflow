## Differences from the requirement text that this spec follows the DESIGN on

Accepted by REVIEWER (step 02d): (1) `rejected_keys` names a key only when it is in the
task's own `form_schema.properties` or in `required_outputs`; a rejection on any other key is
still a refusal with BOTH lists empty (design 3.2, C-4a, SECURITY-REVIEWER F-1). (2) A
service-task merge passes `nil` validations and cannot be schema-rejected, so the
engine-internal regression case is the SUB_PROCESS completion merge (design 11.1, C-12).
(3) A missing required key in the submitted map returns `rejected_keys: []` even if some
other submitted key is also rejected: the submitted-map guard (4c) refuses before the merge
step runs. The tests do not assert the combined case; they assert each half separately.

## Acceptance criteria -> tests

### AC1 -- key absent: 422, names the key, no value; task open and claimable; rows unchanged
* `engine_required_outputs_test.exs` `C-1 -- required key absent` /
  "422-shaped refusal naming the key; every row unchanged; exactly one audit row; task claimable".
  Why: proves the refusal precedes any state change by comparing full rows (a test asserting
  only the return value would pass for an implementation that wrote and rolled back
  incorrectly or left the task locked). A real `Tasks.claim_task/3` by the assignee proves
  "claimable", not merely `status == :pending`. The submitted value `TOP-SECRET-NOTE` is
  grepped out of the return value and the audit record.
* `tasks_required_outputs_test.exs` "absent key: 422 problem naming only the key; ...":
  the HTTP half: status 422, `application/problem+json`, `code` `output_refused`,
  `missing_keys ["decision"]`, `rejected_keys []`, trace id, rows equal, audit row.
* Extra cases: several required keys are all named in ascending order; the refused task can be
  completed on the next request (retryable).

### AC2 -- `decision: null` refused; rework loop still refused
* `C-2` (engine) and "null key: the same 422" (router): null counts as missing (BA 2026-10-07).
  Why: `Map.has_key?`-style implementations would accept `null`; mutant M1 below proves this fails.
* `C-3` (engine) and "rework loop ..." (router): the instance already holds `decision`
  (`initial_variables` / a direct row write), the submission omits it -> still 422. Why: the
  design binds "only SUBMITTED output counts" (C7); an implementation that checks the merged
  map would silently satisfy the requirement from the old value.

### AC3 -- out-of-enum value: retryable 422 naming the key, not value/enum; no ERROR; valid retry routes
* `C-4` (engine): `rejected_keys ["decision"]`, `missing_keys []`, `maybe-LEAKCHECK` absent from
  the return and the audit record, rows unchanged, no `EXECUTION_ERROR` event, task claimable,
  then an IMMEDIATE retry with `"approved"` completes and the active token is at
  `approved_task` (routing proved by the gateway's `variables.decision == "approved"` branch,
  versus the default edge in C-8/C-9).
* "the whole batch is refused" (engine): a valid sibling key submitted with the rejected one is
  not merged (whole-batch semantics of `merge/3` preserved on the new path).
* Router: "out-of-enum decision: 422 naming the key, never the value or the enum ..." and a
  200 on the valid retry. The body greps assert no value, no quoted enum members, no stack,
  module, Ecto, Postgrex or SQL text.
* `C-5` wrong type on a typed in-form key; also an in-form key that is not in
  `required_outputs` is nameable, and a task with `required_outputs` off still refuses a rejected
  in-form value (the schema-rejection half is independent of rule C's attribute).
* `C-6` empty string on a required key: rejected by an enum without `""` (in `rejected_keys`,
  NOT `missing_keys`) and accepted by a plain `string` schema (task completes).

### AC4 -- negative cases
* `C-8` all required keys valid -> behaves as before, routes on the value, no refusal audit row.
* `C-9` default-off: no `required_outputs` -> key may be omitted, task completes, fail-closed
  default route taken; also `required_outputs: []`; also a malformed attribute is off (one
  logged warning) and never crashes a completion.
* The amended existing tests and `engine_complete_task_test.exs` are re-run by TEST-RUNNER.

### AC5 -- C-4a: rejection on a key outside the form and `required_outputs`
* Engine and router `C-4a`: 422, BOTH lists empty, rows unchanged, instance active, and the
  distinctive key name `zz_probe_key` (and its value) is grepped out of the response body and the
  stored audit record. A second engine case uses a task with no `form_schema` at all.
  Why: this is the INV-2 probe-oracle relaxation; mutants M3 and M4 prove the relaxation is real.

### AC6 -- SUB_PROCESS regression and `merge/3` unit half
* `C-12`: parent `variable_schema` for `result` is `string`; the child's own HUMAN_TASK completion
  (output `result: true`, valid per the interface) is accepted, the parent ends in ERROR, exactly
  one `EXECUTION_ERROR` event (`variable_schema_rejected`, field `result`), variables untouched, and
  NO `task.completion_refused` audit row: the engine-internal path is not turned into a refusal.
* `required_outputs_test.exs`: `merge/3` returns `{:rejected, unchanged, [{:execution_error, ...}]}` for
  non-nil validations (whole batch unmerged) and merges for `nil` validations.
* `engine_sub_process_test.exs` ~777 is unchanged and re-run.

### AC7 -- form-expression precedence (C-7, C-10, C-11)
* `C-7`: `decision` present in the submitted map but dropped by `visible_when "amount > 0"` with
  `amount: 0` -> 422 `missing_keys ["decision"]` (step 6b-ii), rows unchanged. Control: same
  submission with `amount: 5` completes. (The "recomputed to null by a computed expression" variant
  is covered only through this `visible_when` path; both reach the same corrected-map check.)
* `C-10`: every required key present, cross-field validation fails -> still
  `{:instance_execution_error, :form_cross_field_validation_failed, {:field, "confirm"}}`, instance
  ERROR, one `EXECUTION_ERROR`, no refusal audit row (BA: unchanged).
* `C-11`: required key missing AND failing cross-field validation -> the 422 refusal, instance
  active, no `EXECUTION_ERROR`, rows unchanged. Mutant M7 proves it fails when the submitted-map
  guard is removed.

### AC8 -- audit: at most one record, exactly one when healthy; no PII; DROP-TABLE regression
* Exactly one record per refusal: `C-1` (one row; exact `after_state` map: rule, instance id,
  node id, key-name lists; `before_state` nil; `resource_type` "task"; `resource_id` the task id);
  "every refused request writes exactly one record (two refusals, two rows)".
* No submitted value / user name / email: engine greps (`TOP-SECRET-NOTE`, `maybe-LEAKCHECK`) and
  the router grep of `inspect(entry)` for the caller's email, display name, username and the value.
* Body names only: `assert_names_only!/2` in the router file (no `Elixir.`, `Ecto`, `Postgrex`,
  `SELECT`, `INSERT`, `** (`, `lib/letflow`, `enum`, no submitted value, no quoted enum member).
* `C-15`: `audit_entries` dropped (recreated in `on_exit`, ISS-0969 idiom) -> the call returns the
  same `{:error, {:output_refused, %{missing_keys: ["decision"], rejected_keys: []}}}`, does not raise,
  all rows unchanged, exactly one captured warning matching `recording task.completion_refused`
  naming the task id and not the submitted value.

### AC9 -- API token and TENANT_ADMIN (C-13, C-14)
* Router `C-14`: callers holding `TENANT_ADMIN` and `TASK_WORKER` each get the same 422 and the
  task stays pending (no role is exempt).
* Router `C-13`: through `Letflow.Router` with a real minted token (`Identity.create_token/3`) and the
  tenant slug header, for tokens holding `TENANT_ADMIN` and `TASK_WORKER`: missing key -> 422,
  enum rejection -> 422 (names only), rows equal, two audit rows, then the valid retry -> 200 and the
  task completed.
