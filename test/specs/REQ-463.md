## Requirement text (summary)

Distinct roles do not stop ONE person who holds several roles from completing several steps of the
SAME instance. A HUMAN_TASK node gets an optional attribute `distinct_from: [node ids]`: the user
(never the role) who MOST RECENTLY completed any listed node of this instance may not complete (the
authority) or claim (early feedback) this node. No role is exempt; named nodes may be on parallel
branches (compare with the completions that exist at check time, any order); a named node that never
completed imposes nothing; off by default; the refusal is HTTP 403 with the constant body
`{"detail":"separation of duties","status":403}` on both endpoints; assign/reassign do not check.

Conventions: `Letflow.DataCase`, `async: false`, one provisioned tenant per test via
`Letflow.TenantFixture`, unique users/emails/names per test, inline definitions (no shipped
definition adopts `distinct_from` yet), no wall-clock or unseeded randomness, no test-helper default
arguments (ISS-0069). REQ-461 check 2: the only definition declaring `required_outputs` (order test)
registers its `variable_schema` before activation; `distinct_from` needs no schema. Node ids are
distinctive (`first-review`, `second-review`, ...) so a grep of a body/log for an id cannot match by
accident.

"Unchanged" means: the instance projection row (incl. `updated_at`, variables, join counters), every
token row, every task row of the instance (incl. `updated_at`), the instance's event count and every
timer row (`fire_at`, `status`) compared by `==` before and after the refused call. The only write of a
refused completion is the one `task.completion_refused` audit row (a claim refusal writes none).

## Design vs requirement text

| Point | Requirement text | Design / what the tests assert |
|---|---|---|
| claim refusal status | "same refusal body" on claim | 403 on claim, deliberately unlike claim's own 409 for eligibility refusals (design D-2); tests assert both: 403 body for separation, existing 409 for ineligible callers |
| replay | "existing 409 'task is not pending'" | same (design section 10); asserted at engine (`{:task_not_pending, :completed}`) and router (409) |
| "claim ... returns :ok when graph/snapshot fail" | listed for missing snapshot / failing `build_graph/1` | design 6 additionally lists a raise and a DB error; `check_for_claim/3` itself is tested for all three (see finding F-1 below for the DB-error case inside `claim_task/3`) |
| rework loop shape | "U completes N1, V completes N1 on a second pass" | the loop passes through a DIFFERENT node (`triage-review`): the engine does not create a new task row when a token loops straight back to the node it just completed (finding F-2 below), so the tests loop N1 -> triage -> gateway -> N1 |

## Acceptance criteria -> tests

(Names below are the ExUnit test names; "E" = `engine_distinct_from_test.exs`, "R" =
`routers/tasks_distinct_from_test.exs`, "C" = `engine_distinct_from_concurrency_test.exs`.)

### AC1 -- two roles, one user (engine and router)
* E `A-1` "U completes N1, U attempting N2 is refused: detail-free error, nothing written but ONE audit row, task still claimable; V then completes N2".
  Why: compares full rows before/after (a return-value-only test passes for an implementation that
  wrote and rolled back wrongly), pins the audit record field by field (`rule`, `node_id`,
  sorted `blocking_node_ids`, `actor_id`, `before_state nil`), greps the public error and the record for
  ids/email/name/value, proves "still open and claimable" by a REAL `claim_task` by V and a real completion by V.
* E `A-1` "every refused attempt writes its own audit row (two refusals, two rows)"; "a user who did NOT
  complete the named node is accepted" (kills an always-refuse mutant); "the comparison is per instance"
  (B's N1 completed by W first, A's by U afterwards: U's row is the newest N1 row in the tenant, so a query
  that dropped `instance_id` would wrongly refuse U in B).
* E `A-1b` (3 tests): `blocking_node_ids` sorted regardless of declared order; only the node whose MOST RECENT
  completer is the actor blocks; a completion of a node that is NOT named never blocks.
* R `POST /tasks/:id/complete` "A-1: U completes N1 (200); U on N2 is 403 ...; V completes N2 (200)".

### AC2 -- 403 and the exact body, byte-identical, no ids
* R "A-2: the body and headers are byte-identical from different triggers (node, user, instance, tenant,
  endpoint) and carry no identifier": three triggers (seq/U/`second-review`/complete; chain/X/`third-review`
  with two blockers in another tenant/complete; the claim endpoint) compared with `==` on `resp_body` and
  `resp_headers`; body must equal the literal bytes; no node id, user id, name, email, username, task id,
  instance id, tenant id/slug or role name in body or any header; body has no `trace`.
  Why: a body that varied by cause (node list, trace_id) would pass any single-trigger test.
* `assert_separation!/2` (used by every router refusal test) also asserts status 403 and
  `application/problem+json`.

### AC3 -- claim
* R `POST /tasks/:id/claim` "U is refused with the same 403 body, nothing written and NO audit row; V (eligible) claims 200".
* R "a caller who is not eligible gets the EXISTING claim refusal first": W completed N1 but does not hold role-b: 409, not the separation body.
* E `A-3` (7 tests): the four WRITE clauses of `apply_claim` are each guarded and each asserted (ROLE-assigned, unassigned, GROUP-assigned, and the
  idempotent re-claim clause reached through `reassign_task`); eligibility refusals come first
  (`:assignee_role_not_held`, `:assigned_to_other_user`); default-off gains no claim failure.
  Why one test per clause: deleting the check from one clause leaves the others green.
* E `A-3a` (4 tests): snapshot row missing (control: the same actor IS refused while the snapshot exists, so the `:ok` is the fail-open),
  `build_graph/1` failing, database error (unknown tenant schema, tag `:raised`), non-task argument. Each captures logs at
  `:warning`, asserts exactly ONE `claim check failed open` line naming the task id and the tag and none of user id, email, name, node ids, instance id,
  and that the eligible claim then succeeds.
* R "default-off: a definition without distinct_from gains no claim failure".

### AC4 -- API token
* R `A-4` "U's token: complete N2 and claim N2 are 403 with the fixed body; another user's token completes N2 (200)" through the FULL `Letflow.Router`
  pipeline (`Authorization: Bearer lf_tok_...` + `x-tenant-slug`); rows unchanged after both refusals, exactly one refusal audit row (the completion's; the claim wrote none).

### AC5 -- TENANT_ADMIN not exempt
* R `A-5` two tests (direct dispatch and full pipeline with a TENANT_ADMIN token): the TENANT_ADMIN who completed N1 is 403 on complete AND claim; a
  DIFFERENT TENANT_ADMIN completes N2 (200), so the test fails both if the role is special-cased (U would pass) and if the rule over-refuses admins.

### AC6 -- parallel branches
* E `A-7` "U completes P1, then U attempting P2 and P3 is refused; V and W complete them; the join fires" (also pins the two audit records' node ids and blockers);
  "the order does not matter": all 6 ordered pairs, each on a fresh instance of one definition (U first on ANY branch is refused on every other);
  "three distinct users complete P1, P2 and P3 in every order": all 6 permutations accepted, instance COMPLETED, no refusal record.

### AC7 -- named node never completed
* E `A-9` "the path skipped N1: U completes N2 with no refusal and no audit row" + "control: the SAME definition on the path through N1 does refuse U at N2" (so the first test is not a definition that never refuses).
* E `A-10` "N2 names only N1, N1 timed out into escalated-review: U is NOT constrained" and the explicit-name counterpart (design section 9: no inheritance; an explicit name constrains).
* E `A-6` "a CANCELLED row of the named node (escalated past) is never a completion, even with completed_by forged onto it": the cancelled N1 row has
  `completed_by = U` forged, so a query that dropped the `status = COMPLETED` filter refuses U.

### AC8 -- assign / reassign
* E `A-11` "reassign_task to U ... then refused" and "assign_task of an unassigned N2 to U succeeds; U's completion is then refused; V completes"
  (the task is made unassigned by a fixture write: no authoring path leaves a role-bearing HUMAN_TASK unassigned). `Tasks.authorize_completion/3` passes for U, so
  the completion is refused by the engine rule alone.

### AC9 -- rework loop
* E `A-6` "U then V complete N1 (second pass): U accepted ... V refused", "reversed order, V then U: U refused, V accepted", "three passes U, V, U".
  Why: the accepted/refused pair distinguishes most-recent from earliest-wins and from any-completion-wins; two COMPLETED N1 rows are asserted to exist.

### AC10 -- default off
* E `A-12` "a node with no distinct_from, a null one and an empty one: the same user completes both steps as today".
* E `A-12` "regression on a SHIPPED definition (Meridian loan origination)": `test/fixtures/qa/meridian_loan_origination_process_definition.json`
  registered and activated through the real path; one user completes `credit-memo-review` and `risk-assessment`. The test first asserts neither node carries
  `distinct_from` and fails with a message to retarget it if REQ-465 ever adopts it there.

### AC11 -- a refusal writes nothing but at most one PII-free audit record; audit failure; timer
* E `A-1` (rows `==`, one record, PII greps), R `A-1` (same over HTTP), E `A-14` "the pending timer of N2 keeps its status and fire_at after a refusal"
  (control inside the test: an accepted completion DOES settle the timer, so the snapshot is not blind to timers).
* E `A-15` and R `A-15`: `audit_entries` dropped (ISS-0969 idiom, recreated in `on_exit`): same refusal, no raise, exactly ONE `recording task.completion_refused` warning,
  rows unchanged, warning names the task id and not the email/name.

### AC12 -- replay
* E `A-13`: V, who completed N2 and is now the most recent N1 completer (rework), replays V's accepted N2 row: `{:error, {:task_not_pending, :completed}}`, and no new
  refusal record, while a control shows V IS refused on the live second N2 row (so the guards WOULD have refused if reached).
* R `A-13`: U re-POSTs N1 and V re-POSTs N2: 409 `task is not pending`, body != separation body, zero `task.completion_refused` rows.

### AC13 -- default-off query count
* E `A-12` "query count": telemetry (`[:letflow, :repo, :query]`, filtered to the test process) counts the queries of completing N2 with `distinct_from` absent, `nil`, `[]`:
  all equal and non-zero; a guarded node costs exactly +1.
* E `A-12` "SeparationOfDuties.check/5 itself": 0 queries for absent/null/`[]`, 0 for a nil, integer or non-UUID actor on a guarded node; exactly 1 when guarded
  (both outcomes).

### AC14 -- concurrency
* C "A-8: the same user completing P1 and P2 concurrently -- exactly one commits, the other is refused": 6 rounds on fresh instances, two `Task.async` completions on two real connections;
  exactly one `{:ok, _}` and one `{:error, :separation_of_duties}`, exactly one task COMPLETED, 6 refusal records in total. Control: two different users both commit.
  **Own partition: `MIX_TEST_PARTITION=15`.**

* Covered by the handoffs (step 02c, PASS); not an executable test. The tests cover what the reviewer checks: body/headers leak nothing (AC2), audit record PII-free (AC11), no-role-exemption (AC5), claim fails open without a new failure mode (AC3).

### Extra (design 2.2 order)
* E "design 2.2 -- step 4b precedes step 4c" and R "step 4b precedes 4c": a request violating both separation of duties and a required output is the

## Findings recorded while writing the tests (not asserted as failing tests)

* **F-1 (claim, database error inside the claim transaction).** `SeparationOfDuties.check_for_claim/3` is total and returns `:ok` on a raise/DB error, but when the
  failing statement is the snapshot read INSIDE `claim_task/3`'s transaction, Postgres aborts the transaction, so the claim's subsequent `write_assignment` raises
  `Postgrex.Error 25P02 (in_failed_sql_transaction)` instead of the claim "failing open". Only the `run_check` query uses `mode: :savepoint`; the snapshot read does not.
  Observed with a probe (snapshot table renamed): `Tasks.claim_task/3` raised. Missing snapshot row and failing `build_graph/1` (the AC cases) fail open correctly
  (tests above). Requires an exceptional DB failure; not an AC.
* **F-2 (engine, loop straight back to the node just completed).** A token routed by a gateway straight back to the HUMAN_TASK it just completed gets no new `tasks` row
  (`instance_projections.current_nodes == ["first-review"]`, one COMPLETED task, no PENDING task). Out of REQ-463's scope; the rework tests loop through a different node.
