## AC-1 — Button.tsx's prop interface exactly matches §7.1 (variant/size/loading/
disabled/onClick/children)

**Why this needs a test, not just a read of the source:** a prop interface that
*compiles* correctly can still be wired wrong at runtime — e.g. `disabled` set but the
native `disabled` attribute never applied, or `onClick` firing even while `loading`.
Type-checking catches shape; only a render + interaction test catches behavior.

| Test | File | Asserts |
|---|---|---|
| TC-REQ272-01 | `Button.test.tsx` | Every `variant` (`primary/secondary/danger/ghost`) × every `size` (`sm/md/lg`) renders without throwing and shows `children` verbatim — a partially-implemented variant or size table can't silently pass. |
| TC-REQ272-02 | `Button.test.tsx` | `onClick` fires exactly once on a normal click of an enabled button. |
| TC-REQ272-03 | `Button.test.tsx` | `disabled` renders the button element as actually `disabled` (`toBeDisabled()`) AND a click does not invoke `onClick` — catches a "visually disabled but still clickable" mistake. |
| TC-REQ272-04 | `Button.test.tsx` | `loading` renders a spinner element (`ds-button-spinner`), disables the button, and a click does not invoke `onClick` — per §7.1 "shows spinner, disables click." |
| TC-REQ272-05 | `Button.test.tsx` | The default (not loading, not disabled) state renders NO spinner — catches an "always render the spinner" mistake, not just a missing-spinner mistake. |

status-lookup table is easy to leave half-built (e.g. only `definition` wired, others
falling through to the same fallback by accident) while still type-checking and
visually looking plausible for the one status a developer happened to eyeball.
