## AC-1 — `useToast`'s TypeScript signature matches spec (`success`/`error`/`warning`,
second `{ description }` arg)

**Why this needs a test, not just a type-check:** a signature can compile correctly
while still being wired wrong internally (e.g. `description` dropped before reaching
the stored entry, or one variant silently sharing another's handler). Only a render +
inspection test proves the description makes it all the way to a `ToastEntry`.

| Test | File | Asserts |
|---|---|---|
| TC-REQ275-01 | `useToast.test.ts` | All three methods (`success`/`error`/`warning`) accept `(message, { description }?)`; the resulting store entries carry the correct `variant`/`message`/`description` (including `description: undefined` when omitted) and preserve newest-first ordering across three distinct calls. |

## AC-2 — Each of the four Toast behaviours has its own test

**Why one test per behaviour, not one combined test:** the AC explicitly calls this
out because a single "toast basically works" test can pass while any one of the four
independent behaviours (timing, cap, order, `aria-live`) is silently broken or never
implemented — each needs its own falsifiable assertion.

| Behaviour | Test | File | Asserts |
|---|---|---|---|
| Auto-dismiss timing (4s/8s) + manual close on error | TC-REQ275-02 | `useToast.test.ts` | Store-level: `success`/`warning` entries carry `durationMs: 4000`, `error` carries `durationMs: 8000`; `vi.advanceTimersByTime` confirms success/warning are gone at 4s while error survives, and error is gone by 8s. |
| Auto-dismiss timing (4s/8s), rendered DOM | TC-REQ275-08 | `Toast.test.tsx` | Same timing proven against the rendered `[data-testid="toast-item"]` elements (not just store state) — success/warning removed from the DOM at 4s, error still present, error removed by 8s. |
| Manual close on error | TC-REQ275-09 | `Toast.test.tsx` | Clicking `toast-close` on an error toast removes it from the DOM immediately, before its 8s timer would have elapsed; advancing time past 8s afterward does not throw or resurrect it (proves the timer was actually cleared on manual dismiss, per §3.3's "no orphaned timer" invariant). |
| Cap of 4 (store) | TC-REQ275-03 | `useToast.test.ts` | A 5th `success` call drops the oldest (`'first'`) from the store; remaining order is `['fifth','fourth','third','second']`. |
| Cap of 4 (dropped entry has no orphaned timer) | TC-REQ275-03b | `useToast.test.ts` | After a 5th toast drops the oldest, advancing time by 4s does not throw and clears all remaining live entries cleanly — proves the dropped entry's timer was cleared, not left dangling. |
| Cap of 4 (rendered DOM) | TC-REQ275-10 | `Toast.test.tsx` | Same cap proven against rendered `toast-item` elements — 4 max, oldest (`'first'`) text absent, newest (`'fifth'`) present. |
| Top-right stacking order (newest-first) | TC-REQ275-04 | `useToast.test.ts` | Store-level: after each successive add, index 0 is always the just-added entry. |
| Top-right stacking order (rendered DOM) | TC-REQ275-11 | `Toast.test.tsx` | Rendered `toast-message` DOM order is `['newest','middle','oldest']` (index 0 topmost, matching `ToastContainer`'s `flex-direction: column` + `top`/`right` anchor per §3.3); container position style also asserted (`position: fixed; top: var(--space-4); right: var(--space-4)`). |
| `aria-live` polite/assertive | TC-REQ275-12 | `Toast.test.tsx` | Rendered `toast-item` elements: `aria-live="polite"` for `success` and `warning`, `aria-live="assertive"` for `error` — asserted per-variant against the actual DOM attribute, not source inspection. |

Manual dismiss (`dismissToast`) is additionally covered at the store level by
TC-REQ275-05 (`useToast.test.ts`) and `clearAllToasts` by TC-REQ275-06, both proving
the pending timer is cleared (no late auto-dismiss firing after an entry is already
gone).

## AC-3 — JsonEditor: error state for invalid JSON, pretty-printing on blur, `onChange`
reporting `isValid: false` for malformed input

| Test | File | Asserts |
|---|---|---|
| TC-REQ275-13 | `JsonEditor.test.tsx` | Typing malformed JSON (`'{ "a": '`) calls `onChange(rawValue, false)`. |
| TC-REQ275-13b | `JsonEditor.test.tsx` | Typing well-formed JSON calls `onChange(rawValue, true)` — the positive-case counterpart, so a helper that always reports `false` can't pass by accident. |
| TC-REQ275-14 | `JsonEditor.test.tsx` | Invalid JSON renders the error border (`var(--border-error)`) and the `json-editor-error` "Invalid JSON" message. |
| TC-REQ275-14b | `JsonEditor.test.tsx` | Valid JSON renders the default border (`var(--border-default)`) and no error message — proves the error state is conditional, not always rendered. |
| TC-REQ275-15 | `JsonEditor.test.tsx` | Blurring a valid but non-pretty value calls `onChange(prettyPrinted, true)` with `JSON.stringify(parsed, null, 2)` formatting, per §5.3's `handleBlur` rule. |
| TC-REQ275-15b | `JsonEditor.test.tsx` | Blurring an already-pretty value is a no-op (`onChange` not called) — proves the `pretty !== value` guard actually prevents a redundant call, not just that pretty-printing works once. |
| TC-REQ275-16 | `JsonEditor.test.tsx` | Empty string value renders no error state (§5.2's explicit "empty is valid, not malformed" decision). |
| TC-REQ275-17 | `JsonEditor.test.tsx` | Blurring an invalid value does not call `onChange` at all (pretty-print is skipped) and the error state persists unchanged. |
| TC-REQ275-18 | `JsonEditor.test.tsx` | `label`, `height`, and `readOnly` props are wired through to rendered output (label text, `height` in px, `readonly` attribute) — confirms the full prop interface, not just the validity logic. |
