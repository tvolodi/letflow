## AC — DlqPage cursor-stack-to-page pagination adaptation (the one genuinely new logic path)

**Why this is the one page needing new tests:** per design doc §5.3, DlqPage's
migration is not a pure primitive swap for its pagination controls — it *synthesizes* a
new value shape. The pre-existing code held `cursorStack: string[]` and imperative
`goNext`/`goPrev` handlers; `PaginationControls` wants a declarative `page: number` +
`onPageChange(page)`. The adaptation (`DlqPage.tsx:216-218,389-395`):

```ts
const page = cursorStack.length + 1
const pageSize = 25
const hasNextPage = data?.next_cursor != null
...
onPageChange={(nextPage) => (nextPage > page ? goNext() : goPrev())}
```

is new arithmetic/branching that did not exist before this migration (the old code had
no numeric "page" concept at all — only a cursor stack and two button `onClick`
handlers). REVIEWER's sign-off on this was a read-through ("verified DlqPage's
cursor-to-page pagination adaptation is genuinely correct"), not an executed test — so
this is exactly the kind of new logic the "genuinely risky adaptation" carve-out in
this run's task exists for, independent of AC6's "no new tests needed for pure
swaps" framing (which covers the other three files, not this one).

**Test file:** `web/src/pages/dlq/__tests__/DlqPage.pagination.test.tsx`. Mocks
`@tanstack/react-query`'s `useQuery` directly (matching this codebase's established
page-test convention — see `web/src/pages/admin/tenants/__tests__/TenantsPage.test.tsx`
and `web/src/pages/admin/__tests__/HealthDashboardPage.test.tsx`, both of which mock
`useQuery`/`useMutation`/`useQueryClient` rather than mocking the HTTP layer or using a
real `QueryClientProvider`). The mock's `useQuery` implementation reads the `cursor`
field out of the real `queryKeys.dlq.list(...)` queryKey argument DlqPage passes it and
returns a fixture keyed by that cursor — this both drives the component under realistic
render-cycle conditions (real `useState`, real re-renders) *and* lets the test observe
exactly which cursor DlqPage requested on each navigation, without needing a real
network layer.

Three server "pages" are fixtured, chained by cursor:

| Requested cursor | Returns | `next_cursor` |
|---|---|---|
| (none) | `[e1]` | `'cursor-2'` |
| `'cursor-2'` | `[e2]` | `'cursor-3'` |
| `'cursor-3'` | `[e3]` | `null` |

| Test case | Asserts |
|---|---|
| "page 1: Previous disabled, Next enabled, no cursor sent" | Initial render: `reason-e1` visible, Previous `toBeDisabled()`, Next not disabled, and the query's requested cursor is `undefined` — proves the `page = cursorStack.length + 1` formula starts at 1 with an empty stack, and `hasNextPage` correctly reads `true` from `next_cursor: 'cursor-2'`. |
| "forward twice then back once: page counter, cursor sent, and Next/Previous disabled-state track it" | Click Next → `reason-e2` renders, requested cursor is `'cursor-2'`, Previous enabled, Next still enabled (page 2's `next_cursor` is non-null). Click Next again → `reason-e3` renders, requested cursor `'cursor-3'`, Previous enabled, **Next now disabled** (page 3's `next_cursor` is `null`, proving `hasNextPage` tracks the *current* page's response, not a stale value). Click Previous → back to `reason-e2`, requested cursor reverts to `'cursor-2'`, both buttons enabled again — proves `onPageChange`'s `nextPage > page ? goNext() : goPrev()` direction inference is correct for the "go backward" branch, and that `goPrev`'s `cursorStack.slice(0, -1)` correctly pops rather than clears. |
| "applying a filter resets pagination to page 1 (cursor stack cleared)" | Navigate to page 2, then change the search filter input and click Apply (`data-testid="dlq-filter-apply"`) — DlqPage's `applyFilters()` calls `setCursorStack([])`. Asserts `reason-e1` renders again, Previous is disabled again, and the next requested cursor is `undefined` — proves the filter-reset path actually clears the stack rather than merely appearing to (a bug here would leave stale cursor-2 data displayed under the new filter). |

**Mutation check (this file's own logic did already exist before this migration in a
different shape, so this is a genuine regression test, not a "code didn't exist"
case — still, one mutant was applied and reverted to confirm the test actually fails
against a broken adaptation, not just against the pre-migration code):**

Mutant: `DlqPage.tsx`'s `onPageChange` handler changed from
`(nextPage) => (nextPage > page ? goNext() : goPrev())` to
`(nextPage) => { void nextPage; goNext() }` (Previous button always advances forward
instead of going back — simulates the direction-inference logic breaking).

- Ran `npx vitest run src/pages/dlq/__tests__/DlqPage.pagination.test.tsx` against the
  mutant: **1 failed / 2 passed** (3 total). The failing test was "forward twice then
  back once ..." — it failed at the Previous-click assertion
  (`expect(screen.getByText('reason-e2')).toBeInTheDocument()`), because the mutant
  kept calling `goNext()` and the page advanced to a 4th (non-existent) cursor with no
  matching fixture, so `reason-e2` was not on the screen. The other two tests
  (page-1-initial-state, filter-reset) never click Previous, so they correctly remained
  unaffected — proves the mutant kill is specific to the Previous-direction logic, not
  an incidental crash.
- Reverted the mutant (`git diff` confirmed clean revert to
  `(nextPage) => (nextPage > page ? goNext() : goPrev())`). Re-ran the same command:
  **3 passed / 3 total**, confirming the revert restored the original passing state.

## AC — Structural fact: the other three migrated files need no new tests

Stated explicitly, not left implicit, per this run's task framing:

- **`DefinitionListPage.tsx`, `DefinitionEditorPage.tsx`, `WebhooksPage.tsx`** each had
  **zero** pre-existing test coverage before this migration (confirmed by the design
  doc §8's own grep: `grep -rl "DefinitionListPage\|DlqPage\|WebhooksPage\|DefinitionEditorPage"
  web/src web/tests --include=*.test.* --include=*.spec.*` returns only
  `DefinitionEditorPage.promote.test.tsx`, which covers one button's testid/text and
  nothing else about these three pages).
- Their migrations, per the design doc's own per-file tables (§5.1, §5.2, §5.4), are
  **primitive swaps with no new derived-value logic**: hand-rolled `<table>` →
  `DataTable`, hand-rolled `<span>` status pills → `StatusBadge`, hand-rolled
  `<button style={...}>` → `Button`. None introduces a new computed value comparable to
  DlqPage's `page`/`hasNextPage`/direction-inference — `DefinitionListPage.tsx` and
  `WebhooksPage.tsx` have **no pagination at all** (design doc §5.1, §5.4: "No
  pagination control exists in this file"), and `DefinitionEditorPage.tsx`'s only
  behavioral element (the unsaved-changes dialog) keeps its existing
  `onConfirm`/`onCancel` handlers wired to the same functions, just through
  `ConfirmDialog` instead of a hand-rolled overlay.
- Writing a "does this table render these five columns" test for a page that has had
  zero coverage since it was created, and whose migration changes only markup shape
  (verified field-by-field by SECURITY-REVIEWER, verified idiomatically correct by
  REVIEWER) rather than behavior, would be coverage theater — it would pass identically
  whether the migration were correct or subtly wrong, because there is no
  pre-migration baseline behavior being protected and no new decision logic being
  introduced. This is why only DlqPage gets new test code in this step.
