## AC-1 — Prop interface matches §7.8 exactly

**Side-by-side quote.**

`docs/frontend/design-system.md` §7.8 spec block (`page`, `pageSize`, `totalItems`,
`onPageChange`, `onPageSizeChange`, `hasNextPage`):

```tsx
<PaginationControls
  page={number}
  pageSize={number}
  totalItems={number | null}
  onPageChange={(page: number) => void}
  onPageSizeChange={(pageSize: number) => void}
  hasNextPage={boolean}
/>
```

`web/src/components/ui/PaginationControls.tsx` (lines 16–23):

```ts
export interface PaginationControlsProps {
  page: number
  pageSize: number
  totalItems: number | null
  onPageChange: (page: number) => void
  onPageSizeChange?: (pageSize: number) => void
  hasNextPage?: boolean
}
```

Same six props, same names, same types (`onPageSizeChange` and `hasNextPage` optional
in both, matching §7.8's "optional" annotations). **Why this isn't purely a
type-check concern:** a signature can typecheck while being wired wrong internally
(e.g. `hasNextPage` accepted but never read, or read only for the known-total branch).
Every test below that renders with `totalItems={null}` and varies `hasNextPage`, or
renders with `onPageSizeChange` present/absent, exercises the interface at runtime,
not just at compile time — so the interface match is verified two ways: `npm run
type-check` (compiles the interface as documented) and the runtime behavior tests
(prove each prop actually does something, not just that it's accepted).

## AC-2 — Four behaviors, each with its own test

**Why one test per behavior, not one combined test:** the AC explicitly calls this
out — a single "pagination basically works" test can pass while any one of the four
independent behaviors is silently broken (e.g. the summary text right but Next's
disabled logic wrong, or vice versa). Each needs its own falsifiable assertion, and
each of the two variants (known total / null total) needs its own case since they use
different formulas (§7.8, §3.2 of the design doc).

| Behavior | Test | Asserts |
|---|---|---|
| "Showing X-Y of Z" summary, known total | TC-REQ287-01 | `page=1, pageSize=25, totalItems=120` → "Showing 1-25 of 120" |
| "Showing X-Y of Z", later/partial page | TC-REQ287-01b | `page=5, pageSize=25, totalItems=120` → "Showing 101-120 of 120" (partial last page, `end` clamped by `Math.min`) |
| Previous disabled on page 1 | TC-REQ287-02 | `page=1` → Previous button `toBeDisabled()` |
| Previous enabled past page 1 | TC-REQ287-02b | `page=2` → Previous button `toBeEnabled()` (negative counterpart — proves the check isn't "always disabled") |
| Next disabled on last page (known total) | TC-REQ287-03 | `page=5, pageSize=25, totalItems=120` (125 >= 120) → Next `toBeDisabled()` |
| Next enabled when not last page (known total) | TC-REQ287-03b | `page=1, pageSize=25, totalItems=120` (25 < 120) → Next `toBeEnabled()` (negative counterpart) |
| Next disabled at the exact boundary `page*pageSize === totalItems` | TC-REQ287-03c | `page=4, pageSize=30, totalItems=120` (120 === 120) → Next `toBeDisabled()` — forces `>=` rather than `>` at `PaginationControls.tsx:37`; TC-03/01b only ever exercise the strictly-greater case (125 > 120), so a `>` mutant survived them |
| Next enabled one unit below that boundary | TC-REQ287-03d | `page=3, pageSize=30, totalItems=120` (90 < 120) → Next `toBeEnabled()` (negative counterpart, strengthens the mutant-kill) |
| null-`totalItems` summary omits "of Z" | TC-REQ287-04 | `page=2, pageSize=25, totalItems=null` → text contains "Showing 26-50", does not match `/of/` |
| null-`totalItems`, Next disabled via `hasNextPage=false` | TC-REQ287-05 | `totalItems=null, hasNextPage={false}` → Next `toBeDisabled()` |
| null-`totalItems`, Next enabled via `hasNextPage=true` | TC-REQ287-05b | `totalItems=null, hasNextPage={true}` → Next `toBeEnabled()` |
| null-`totalItems`, `hasNextPage` omitted defaults to disabled | TC-REQ287-05c | `totalItems=null`, no `hasNextPage` prop → Next `toBeDisabled()` (per §7.8: "Treated as false ... when omitted") |

## AC-3 — Page size options 25/50/100; selector absent without `onPageSizeChange`

| Test | Asserts |
|---|---|
| TC-REQ287-06 | With `onPageSizeChange` supplied, `pagination-size-select` renders and its `<option>` text content is exactly `['25 / page', '50 / page', '100 / page']` (derived from the exported `PAGE_SIZE_OPTIONS` constant, so the assertion tracks the source of truth rather than a hardcoded duplicate) |

## AC-4 — Keyboard operability + accessible names (FNFR-03/WCAG 2.1 AA)

| Test | Asserts |
|---|---|
| TC-REQ287-08 | Previous/Next are real `<button>` elements (`tagName === 'BUTTON'`); `Tab` moves focus onto Previous then Next in document order; `Enter` on each activates it (`onPageChange` called with `page-1`/`page+1`) — proves native keyboard semantics work without custom keydown handling |
| TC-REQ287-09 | The disabled button carries the native `disabled` HTML attribute (`toHaveAttribute('disabled')` and `toBeDisabled()`), not merely a visual/CSS-only affordance — satisfies FNFR-03's requirement that disabled state be exposed to the accessibility tree |
| TC-REQ287-07 | (also serves this AC) `getByRole('button', { name: 'Previous' })` / `{ name: 'Next' }` succeed only if the accessible name comes from real visible text content — an icon-only or unlabeled button would fail this query |
